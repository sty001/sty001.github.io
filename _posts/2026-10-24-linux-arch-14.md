## 原理解析
{: .sec-know}

### 反向代理与负载均衡的工作流程
{: .sec-expl}

当 Nginx 作为反向代理与负载均衡器时，一次请求的完整生命周期如下：

1. 客户端请求到达 Nginx，Nginx 根据 listen 与 server_name 确定由哪个 server 块处理；
2. server 块内按 location 匹配规则（精确 > 优先前缀 > 正则 > 普通前缀）选中处理该 URI 的 location；
3. location 中若配置 proxy_pass http://backend，Nginx 从 upstream 服务器组中按调度算法挑选一台后端；
4. Nginx 以后端客户端身份发起请求，附带 Host、X-Real-IP、X-Forwarded-For 等代理头；
5. 后端返回响应，Nginx 可经过缓存、gzip 压缩等加工后返回客户端；
6. 若后端无响应或超时，Nginx 按 proxy_next_upstream 策略自动尝试下一台后端，客户端对此无感知。

upstream 服务器组支持的调度算法包括轮询（默认）、weight（权重）、ip_hash（同 IP 固定后端）、least_conn（最少连接）等；服务器可标记 backup（备份机）或 down（下线）。

### 动静分离的资源分流逻辑

1. 静态资源（图片、CSS、JS、字体等）变化不频繁，直接由 Nginx 从磁盘读取返回，并可设置过期时间让浏览器缓存；
2. 动态请求（.php、.jsp、API 等）由 Nginx 通过 fastcgi_pass 或 proxy_pass 转发给 PHP-FPM、Tomcat 等应用；
3. 两者分流后，静态请求不再占用应用进程，应用只需处理业务逻辑，整体吞吐显著提升。

## 一、搭建一个网站

搭建一个网站通常分为五个步骤：编写虚拟主机配置、准备网站代码、重载服务、配置解析、访问测试。

### 1.1 编写虚拟主机配置文件
{: .sec-expl}

```bash
cd /etc/nginx/conf.d/
vim www.conf
```

```nginx
server {
    listen        80;
    server_name   www.example.com;
    location  /demo {
        root  /usr/share/nginx/html;
        index demo.html;
    }
}
```

### 1.2 准备网站代码

第二个步骤是获取开发人员编写的网站代码：将静态页面代码放置到站点目录，并保存为 location 中指定的首页文件名（如 demo.html）。页面文件需要声明 UTF-8 编码，避免中文乱码。

### 1.3 重载 Nginx 服务

修改配置后使用平滑重载，以下两种方法等价：

```bash
systemctl reload nginx
nginx -s reload
```

nginx 命令常用参数：

| 参数 | 说明 |
| --- | --- |
| -t | 检查测试配置文件语法（test configuration and exit） |
| -s | 向 master 进程发送信号：stop、quit、reopen、reload，控制服务停止或重新启动 |

### 1.4 配置域名解析
{: .sec-expl}

- 真实域名：在阿里云等 DNS 服务商处添加解析记录
- 模拟域名：在 Windows 主机的 hosts 文件中进行配置即可，文件路径为 `C:\Windows\System32\drivers\etc\hosts`

### 1.5 访问测试
{: .sec-ver}

浏览器中访问 `http://www.example.com`。

### 1.6 常见错误与排查
{: .sec-ts}

部署搭建网站时的常见错误：

| 错误 | 可能原因 | 解决方法 |
| --- | --- | --- |
| 404 | 网站服务配置文件编写不正确（location 与站点文件不匹配） | 方法一：修改 Nginx 配置文件的 location；方法二：在站点目录中创建相应目录或文件 |
| 403 | 配置了禁止访问的规则；或站点目录中没有首页文件 | 方法一：不要禁止访问，调整 allow/deny 规则；方法二：添加首页文件 |
| 页面无法打开 | DNS 信息配置不正确 | 检查 hosts 或 DNS 解析记录 |

> **注意：** 修改 Nginx 配置文件后一定要重载服务才会生效；仅调整站点目录中的代码文件则不需要重启服务。
{: .sec-pit}

站点目录的规范顺手立好：/html/www、/html/bbs、/html/blog 一站一目录，配置文件在 /etc/nginx/conf.d/ 一站一文件，文件名与域名对应。目录一乱，后面动静分离和权限排查的成本翻倍。

## 二、搭建多个网站

企业中的多网站部署遵循两个原则：每个网站有单独的虚拟主机配置文件，每个网站有独立的站点目录。

### 2.1 编写多个虚拟主机配置
{: .sec-expl}

bbs.conf：

```nginx
server {
    listen        80;
    server_name   bbs.example.com;
    location  / {
        root  /html/bbs;
        index index.html;
    }
}
```

blog.conf：

```nginx
server {
    listen        80;
    server_name   blog.example.com;
    location  / {
        root  /html/blog;
        index index.html;
    }
}
```

www.conf：

```nginx
server {
    listen        80;
    server_name   www.example.com;
    location  / {
        root  /html/www;
        index index.html;
    }
}
```

重载服务使配置生效：

```bash
systemctl reload nginx
```

### 2.2 创建站点目录和首页文件

```bash
[root@web01 conf.d]# mkdir /html/{www,bbs,blog} -p
[root@web01 conf.d]# for name in {www,bbs,blog};do echo "10.0.0.7 $name.example.com" >/html/$name/index.html;done
[root@web01 conf.d]# for name in {www,bbs,blog};do cat /html/$name/index.html;done
```

```console
10.0.0.7 www.example.com
10.0.0.7 bbs.example.com
10.0.0.7 blog.example.com
```

### 2.3 编写 hosts 解析文件

```text
10.0.0.7    www.example.com  bbs.example.com  blog.example.com
```

### 2.4 访问测试
{: .sec-ver}

- Windows 主机：使用浏览器进行访问测试
- Linux 主机：使用 curl 命令进行访问测试

## 三、企业中的虚拟主机访问方式

### 3.1 基于域名访问

最常用的虚拟主机方式，多个站点共用同一 IP 与端口，通过 server_name 区分，适合普通 Web 服务。

域名访问的隐性前提是 Host 头：浏览器把域名放进 Host 请求头，Nginx 才能区分站点；用 IP 直接访问时 Host 里只有 IP，命中的永远是 default server，这也是测试多站点必须先配 hosts 解析的原因。

### 3.2 基于地址访问

只能用指定地址访问，常用于负载均衡与高可用服务场景：

```nginx
server {
    listen        10.0.0.7:80;
    server_name   www.example.com;
    location / {
        root  /html/www;
        index index.html;
    }
}
```

> **注意：** 服务配置文件中涉及监听地址修改时，必须重启 Nginx 服务，不能使用平滑重启。
{: .sec-pit}

> **注意：** 新版 Nginx 的 reload 通常已能应用 listen 变更（master 会先打开新的监听套接字再切换 worker），但历史上部分版本在地址变更时会出现旧套接字残留，因此生产上修改 listen 后建议执行 `nginx -t && systemctl restart nginx`，并观察 error.log 确认无 bind 报错。
{: .sec-pit}

### 3.3 基于端口访问

同一主机上运行多个服务时，通过不同端口区分。例如 apache 占用 80 端口运行 zabbix 服务，Nginx 使用 8080 端口提供 Web 服务：

```nginx
server {
    listen        8080;
    server_name   www.example.com;
    location / {
        root  /html/www;
        index index.html;
    }
}
```

### 3.4 网站页面访问原理
{: .sec-know}

1. 将域名进行解析：www.example.com 解析为 10.0.0.7
2. 建立 TCP 连接（四层协议），目标地址 10.0.0.7，目标端口 8080
3. 根据应用层 HTTP 协议发出请求，请求报文中携带 Host 信息（如 bbs.example.com）
4. 若没有相同 server_name 的 server 块，会匹配满足端口要求的第一个 server 块，显示该主机的网站页面

server_name 的匹配顺序补全：先精确匹配（www.example.com），再通配符开头（*.example.com），然后通配符结尾（www.*），接着正则，全都不中时落到 default_server（该端口第一个 server 块）。生产上栽过的场景：新加一个泛域名站点，结果把老站点的流量抢走了，回头一看是 server_name 的先后顺序没理清。一台机器同时挂泛域名站点和精确域名站点时，这条顺序决定请求落到谁头上，配错就会出现"配置明明写了却进了别的站点"的怪象。

顺手把分层对上：域名解析是应用层的 DNS，TCP 三次握手是传输层，HTTP 报文承载在 TCP 之上。"从输入网址到页面展示"贯穿这三层，本节只是应用层的最后一跳。

## 四、网站安全访问配置
{: .sec-expl}

### 4.1 根据用户访问的地址进行控制

使用 Nginx 访问模块 ngx_http_access_module，allow/deny 规则按书写顺序匹配，命中即生效。

指令用法：

| 项目 | 说明 |
| --- | --- |
| Syntax | deny address \| CIDR \| unix: \| all; |
| Default | — |
| Context | http, server, location, limit_except |

配置示例：

```nginx
location / {
    deny  192.168.1.1;
    allow 192.168.1.0/24;
    allow 10.1.1.0/16;
    allow 2001:0db8::/32;
    deny  all;
}
```

实战示例：10.0.0.0/24 网段禁止访问 /AV 目录，172.16.1.0/24 网段允许访问：

```nginx
server {
    listen        80;
    server_name   www.example.com;
    location / {
        root  /html/www;
        index index.html;
    }
    location /AV {
        deny  10.0.0.0/24;
        allow 172.16.1.0/24;
        root  /html/www;
        index index.html;
    }
}
```

补充说明：location 块外面的信息是全局配置信息，location 块里面的信息是局部配置信息。

### 辨析：access 模块与防火墙规则

ngx_http_access_module 的 allow/deny 按书写顺序自上而下逐条匹配，命中即停，后面的规则不再看。说白了，就是应用层的黑白名单，顺序反了就全盘失效：先写 deny all 再写 allow 网段，所有人都会被拒。两种惯用顺序：

- 拉黑名单：先 deny 具体地址，再放行正常网段，不做兜底拒绝；
- 只放内网：先 allow 内网网段，最后 deny all 兜底收口。

它与防火墙规则的分工：access 模块工作在应用层，HTTP 请求进来之后才能判断，能结合 location 精确到某个目录；防火墙在网络层，端口通了就通，管不到路径。两层配合使用，入口先收紧端口，应用内再按路径细分。

### 4.2 根据用户访问进行认证

使用 Nginx 认证模块 ngx_http_auth_basic_module：

```nginx
location / {
    auth_basic           "closed site";
    auth_basic_user_file conf/htpasswd;
}
```

- auth_basic：开启认证功能
- auth_basic_user_file：加载用户密码文件

实战配置：

```nginx
server {
    listen        80;
    server_name   www.example.com;
    location / {
        root                  /html/www;
        index                 index.html;
        auth_basic            "内部访问区";
        auth_basic_user_file  password/htpasswd;
    }
}
```

创建密码文件（文件中密码信息必须是密文），使用 httpd-tools 提供的 htpasswd 命令：

```console
[root@web01 conf.d]# rpm -qf `which htpasswd`
httpd-tools-2.4.6-89.el7.centos.x86_64
```

htpasswd 命令参数说明：

| 参数 | 说明 |
| --- | --- |
| -c | 创建一个新的密码文件 |
| -n | 不更新文件，仅在屏幕显示结果 |
| -b | 在命令行中直接输入密码，免交互 |
| -i | 从标准输入读取密码，不做校验（适用于脚本） |
| -m | 强制 MD5 加密（默认） |
| -B | 强制 bcrypt 加密（非常安全） |
| -C | 设置 bcrypt 算法计算耗时，越高越安全也越慢（默认 5，有效范围 4 到 31） |
| -d | 强制 CRYPT 加密（最长 8 个字符，不安全） |
| -s | 强制 SHA 加密（不安全） |
| -p | 不进行加密（明文，不安全） |
| -D | 删除指定用户 |
| -v | 校验指定用户的密码 |

使用示例（-c 新建密码文件、-b 免交互输入密码，最后修改文件权限）：

```bash
htpasswd -bc /etc/nginx/password/htpasswd admin <your-password>
chmod 600 /etc/nginx/password/htpasswd
```

> **注意：** 密码文件中保存的必须是密文；生成后应及时修改文件权限（如 chmod 600），防止密码文件泄露。
{: .sec-pit}

什么时候用 auth_basic？典型场景：交换机、路由器等设备的管理后台；Grafana、Zabbix、Kibana 这类自带登录、但想再加一道门的监控面板；phpMyAdmin 等高危入口的前置认证；测试环境临时给整站上锁。局限也明显：没有验证码、没有失败锁定、密码每次请求都在传输，必须配合 HTTPS；用户管理全靠 htpasswd 文件，人多之后建议换成应用层登录或接入统一认证。这里有个坑：auth_basic_user_file 写相对路径时基于编译时的 prefix 目录解析，换台机器部署就 404/500，直接写绝对路径最稳。

如果访问时出现 500 Internal Server Error，常见原因有两类：

1. 内部程序代码编写有问题
2. 程序服务中文件权限不正确

使用 curl 命令测试认证访问，-u 参数用于指定用户名与密码（格式为 USER[:PASSWORD]）：

```console
[root@web01 password]# curl www.example.com -u admin
Enter host password for user 'admin':
```

```console
[root@web01 password]# curl www.example.com -u admin:<your-password>
10.0.0.7 www.example.com
```

## 五、rewrite 与正则

页面跳转与 URL 重写功能由 ngx_http_rewrite_module 模块实现。rewrite 按照“匹配的正则信息，替换成什么信息”的方式工作。

指令用法：

```text
Syntax:	rewrite regex replacement [flag];
Default:	—
Context:	server, location, if
```

flag 决定重写后的行为：

| flag | 效果 |
| --- | --- |
| last | 停止执行后续 rewrite 指令，用替换后的 URI 重新匹配 location |
| break | 停止执行后续 rewrite 指令，直接使用当前 location 处理 |
| redirect | 返回 302 临时重定向 |
| permanent | 返回 301 永久重定向 |

last 与 break 的区别是高频混淆点：last 会用重写后的 URI 重新走一遍 location 匹配流程（可能进入另一个 location），break 则停留在当前 location 内，把重写结果交给当前配置处理。

### 辨析：last 与 break 的适用场景
{: .sec-ex}

- last：重写后的 URI 需要交给别的 location 处理时用。典型是伪静态，`rewrite ^/article/(\d+)\.html$ /article.php?id=$1 last;` 重写完要落到 .php 那条 location 交给 php-fpm，用 break 就停在原地找不存在的 html 文件了；
- break：重写结果就在当前 location 内处理完时用，比如配合 root 直接读改写后的路径，省掉一轮重新匹配；
- 写在 server 块的 rewrite，last 与 break 在 location 搜索层面行为一致（处理完都会按新 URI 重新匹配 location）；嵌套 location 中 last 会回到外层重新匹配，容易产生非预期跳转。

一句话总结：要换 location 用 last，就地处理用 break。

规则示例：

```nginx
rewrite www.example.com/(.*) http://www.example.com/$1 permanent;
```

### 5.1 return 指令

return 直接结束请求并返回指定的状态码或地址，执行效率比 rewrite 高（不需要继续匹配后续 rewrite 规则），适合简单的跳转与拦截：

```nginx
location / {
    return 301 https://$host$request_uri;    # 整站跳转到 HTTPS
}

location /private/ {
    return 403;                              # 直接返回禁止访问
}

server {
    listen 80;
    server_name example.com;
    return 301 http://www.example.com$request_uri;
}
```

location 里同时出现 rewrite 与 return 时，return 优先执行并直接结束请求，rewrite 规则成了摆设——排"规则不生效"这类问题时，先查有没有更早的 return 拦截。

### 5.2 if 判断与无限跳转的解决
{: .sec-ts}

if 常用于配合 rewrite/return 做条件跳转。第一种方法：利用不同的 server 区块配置打破循环：

```nginx
server {
    server_name  example.com;
    rewrite ^/(.*) http://www.example.com/$1 permanent;
}
```

第二种方法：利用 if 判断实现打破循环：

```nginx
if ($host ~* "^example.com$") {
    rewrite ^/(.*) http://www.example.com/$1 permanent;
}
```

多级路径跳转示例：

```console
www.example.com/demo01/demo02/demo.jpg --- www.example.com/demo.jpg
```

> **注意：** rewrite 规则的目标地址又匹配到自身规则时会造成无限跳转。定位这类问题可以开启 `rewrite_log on;`，在 error.log 中观察每一次重写过程，或用 `curl -I` 跟随重定向链。
{: .sec-pit}

### 5.3 常用正则速查
{: .sec-chk}

| 写法 | 含义 |
| --- | --- |
| `.` | 任意单个字符 |
| `*`、`+`、`?` | 前一个字符重复 0 次及以上、1 次及以上、0 或 1 次 |
| `^`、`$` | 匹配开头、结尾 |
| `()` | 捕获分组，通过 $1、$2 在替换目标中引用 |
| `[]` | 字符集合，如 `[0-9]`、`[a-z]` |
| `\|` | 或，多个分支任选其一 |
| `\d` | 数字（等价于 `[0-9]`） |
| `{n,m}` | 重复 n 到 m 次 |

量词默认贪婪，能吃多少吃多少；捕获路径中间段时用惰性匹配（如 `(.*?)`）或更精确的字符类（如 `([^/]+)`）收住边界，否则两个捕获组会互相吃字符。

典型伪静态示例（把 /article/123.html 映射为 /article.php?id=123）：

```nginx
location / {
    root  /html/www;
    rewrite ^/article/(\d+)\.html$ /article.php?id=$1 last;
}
```

## 六、反向代理配置
{: .sec-expl}

反向代理把客户端请求转发给后端服务，客户端不直接接触后端：

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;                          # 转发到后端服务
    proxy_set_header Host $host;                               # 向后端传递原始 Host
    proxy_set_header X-Real-IP $remote_addr;                   # 传递真实客户端 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 记录代理链
    proxy_set_header X-Forwarded-Proto $scheme;                # 传递原始协议（http/https）
}
```

> **注意：** 日志格式中的 $http_x_forwarded_for 即来自 X-Forwarded-For 首部；经过多级代理时，该首部会记录完整的代理链。
{: .sec-pit}

常用 proxy 指令：

| 指令 | 作用 |
| --- | --- |
| proxy_pass | 指定后端地址，支持 upstream 组名 |
| proxy_set_header | 设置转发给后端的请求头 |
| proxy_connect_timeout | 与后端建立连接的超时时间 |
| proxy_read_timeout | 读取后端响应的超时时间 |
| proxy_next_upstream | 后端故障时的重试策略 |
| proxy_buffering | 是否缓冲后端响应，on 可减少慢客户端对后端的占用 |

代理超时三件套一起配：proxy_connect_timeout 管建连（后端挂了快速失败）、proxy_send_timeout 管发请求、proxy_read_timeout 管等响应（慢后端的主要开关），任一超时都以 504 收场。调大 read 之前先想想后端为什么慢。

> **注意：** proxy_pass 地址结尾带 `/` 时，location 匹配的路径前缀会被替换掉。例如 `location /api/ { proxy_pass http://127.0.0.1:8080/; }`，请求 /api/user 实际转发为 /user；若 proxy_pass 不带 `/`，则原样转发 /api/user。这是代理路径错乱的常见原因。
{: .sec-pit}

## 七、负载均衡 upstream

upstream 用于定义一组后端服务器，配合 proxy_pass 实现负载均衡。upstream 必须定义在 http 块，server 块内引用：

```nginx
upstream backend {
    server 127.0.0.1:8080 weight=1;      # 权重 1
    server 10.0.0.11:8080 weight=2;      # 权重 2，分到约两倍流量
    server 10.0.0.12:8080 backup;        # 备份机，仅在其他全部故障时启用
    server 10.0.0.13:8080 down;          # 下线机器，暂不参与分发
    server 10.0.0.14:8080 max_fails=3 fail_timeout=30s;  # 30 秒内失败 3 次则摘除
}

server {
    listen 80;
    server_name www.example.com;
    location / {
        proxy_pass http://backend;
    }
}
```

调度算法（在 upstream 块内指定，互斥使用）：

| 算法 | 指令 | 说明 |
| --- | --- | --- |
| 轮询（默认） | 无需指令 | 按顺序依次分发 |
| 权重轮询 | 配合 server 的 weight | 按 weight 比例分发 |
| IP 哈希 | `ip_hash;` | 同一客户端 IP 固定落到同一后端，用于会话保持 |
| 最少连接 | `least_conn;` | 分发给当前连接数最少的后端 |

> **注意：** ip_hash 与 weight 同时指定时 weight 无效；会话保持也可以用 cookie 方式（需商业版或第三方模块），ip_hash 是最简单的方案。
{: .sec-pit}

upstream 的被动健康检查（max_fails/fail_timeout）只能等真实请求失败后摘节点，主动健康检查（nginx_upstream_check_module、商业版 health_check）能在用户请求到达前就发现坏节点。节点少、流量小的场景被动检查够用；后端一多，建议补上主动检查，别让第一批用户去试错。单台后端能力有上限时配 max_conns，限制发往该节点的最大连接数，配合 least_conn 能把慢节点自动喂得少一些。

## 八、动静分离

动静分离把静态资源与动态请求分流处理，静态由 Nginx 直接返回并利用浏览器缓存，动态转发给后端应用：

```nginx
server {
    listen 80;
    server_name www.example.com;

    # 静态资源：由 Nginx 直接处理，并设置浏览器缓存时间
    location ~* \.(jpg|png|gif|css|js|svg|woff2?)$ {
        root  /html/www;
        expires 7d;
    }

    # 动态请求：转发给后端应用处理
    location ~ \.php$ {
        proxy_pass http://127.0.0.1:9000;
    }

    # 其他请求：按站点目录返回
    location / {
        root  /html/www;
        index index.html index.htm;
    }
}
```

> **注意：** 上述正则 location 会优先于普通前缀 location 命中，图片等静态文件即使写在 `location /` 中也仍会走进静态规则，这正是动静分离的分流效果。
{: .sec-pit}

woff2 字体经 CDN 或子域加载时会被浏览器 CORS 拦截，静态 location 里加 add_header Access-Control-Allow-Origin "https://www.example.com"; 放行指定来源，比写 * 更安全。

## 九、proxy_cache 页面缓存

proxy_cache 可以把后端的响应缓存到本地磁盘，相同请求直接由缓存返回，大幅降低后端压力。缓存目录在 http 块定义，server/location 中引用：

```nginx
http {
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m inactive=1d max_size=10g;

    server {
        listen 80;
        server_name www.example.com;

        location / {
            proxy_cache           my_cache;          # 引用 keys_zone 名称
            proxy_cache_valid     200 302 10m;       # 200/302 响应缓存 10 分钟
            proxy_cache_valid     404 1m;            # 404 缓存 1 分钟
            proxy_cache_use_stale error timeout updating;  # 后端异常时使用旧缓存
            add_header            X-Cache-Status $upstream_cache_status;
            proxy_pass            http://backend;
        }
    }
}
```

| 指令/变量 | 说明 |
| --- | --- |
| proxy_cache_path | 缓存存储路径，levels 目录层级，keys_zone 共享内存区，inactive 闲置清理时间，max_size 磁盘上限 |
| proxy_cache_valid | 按状态码设置缓存有效期 |
| $upstream_cache_status | 缓存状态：MISS（未命中）、HIT（命中）、EXPIRED（过期重取）、UPDATING（更新中）、BYPASS（忽略） |
| proxy_cache_key | 默认缓存键，可按需自定义 |

> **注意：** 带用户登录态、个性化数据的响应不要整体缓存，可在对应 location 关闭 `proxy_cache off;`；清理单条缓存需要 ngx_cache_purge 等第三方模块。
{: .sec-pit}

缓存不生效的排查顺序：先看响应头 X-Cache-Status——一直是 MISS 时，检查后端响应是否带了 Set-Cookie（默认不缓存带 Cookie 的响应，把匿名用户也下发 Cookie 的应用先关掉这个行为）；再看 proxy_cache_key 是否拼入了 Cookie、UA 等变量，key 越个性化命中率越低；最后确认 proxy_cache_valid 覆盖了实际返回的状态码。levels=1:2 用缓存 key 哈希的前几位建两级目录，避免单目录文件过多拖慢查找；keys_zone 的 10m 是共享内存里存 key 索引的空间，不是磁盘缓存大小，磁盘上限看 max_size。

## 十、限流：limit_req 与 limit_conn

限流用于防止突发流量打垮后端，两类指令分工不同：limit_req 限制请求速率，limit_conn 限制并发连接数。两者都基于共享内存区统计，定义在 http 块：

```nginx
http {
    limit_req_zone  $binary_remote_addr zone=req_zone:10m  rate=10r/s;
    limit_conn_zone $binary_remote_addr zone=conn_zone:10m;

    server {
        listen 80;
        server_name www.example.com;

        location / {
            limit_req   zone=req_zone burst=20 nodelay;   # 每秒 10 个，允许 20 个突发且不延迟
            limit_conn  conn_zone 10;                     # 单 IP 最多 10 个并发连接
            proxy_pass  http://backend;
        }
    }
}
```

| 指令 | 说明 |
| --- | --- |
| limit_req_zone | 定义限速区与速率，rate 支持 r/s 与 r/m |
| limit_req | 在 location 中引用，burst 允许的突发量，nodelay 表示突发请求立即处理 |
| limit_conn_zone | 定义并发连接统计区 |
| limit_conn | 限制单个 key（如单 IP）的并发连接数 |

> **注意：** 超出限制的请求默认返回 503，可用 `limit_req_status 429;` 改为 429；限流区内存按并发 key 数量估算，10m 约可记录 16 万个 IP 状态。
{: .sec-pit}

限流的两个高频用途：一是防 CC 攻击，rate 设到正常用户访问峰值的两三倍，burst 兜住突发，让攻击流量被 503/429 挡在门外；二是保护脆弱接口，登录、短信发送这类接口按 URI 单独配 location，限得比全站更狠。zone 的 key 也不必死守 $binary_remote_addr，换成其他变量就能做按用户、按接口的限流，前提是那个变量能区分出你想限的维度。两个限制叠加时的语义要清楚：limit_conn 管"同时"，limit_req 管"频率"，下载用户开 1 个连接但每秒 20 个请求，只限 conn 拦不住；刷接口的用户单连接高频，只有 req 能拦。

## 十一、防盗链 valid_referers

通过检查请求头中的 Referer 判断资源是否被外部站点盗用，超出白名单的引用直接拒绝：

```nginx
location ~* \.(jpg|png|gif|css|js)$ {
    valid_referers none blocked server_names *.example.com;
    if ($invalid_referer) {
        return 403;
    }
    root  /html/www;
    expires 7d;
}
```

| 关键字 | 含义 |
| --- | --- |
| none | 请求头中没有 Referer 字段，视为合法 |
| blocked | Referer 存在但被防火墙或代理删除，视为合法 |
| server_names | Referer 的域名属于本 server 的所有 server_name |
| 域名/IP | 显式白名单，支持通配符与正则 |

$invalid_referer 变量：Referer 合法时为空字符串，非法时为 `1`，因此用 if 判断即可拦截。

防盗链只是低强度防线：Referer 由客户端发出，curl 一行命令就能伪造，挡爬虫和顺手盗图够用，挡不住定向抓取。真正的资源保护要靠签名 URL（带时效的 token 校验）或对象存储的私有读签名，两者经常叠加使用。

## 十二、gzip 压缩

gzip 对文本类响应做实时压缩，显著减少传输体积，提升弱网环境下的访问速度：

```nginx
http {
    gzip              on;
    gzip_min_length   1k;              # 小于 1k 的响应不压缩
    gzip_comp_level   5;               # 压缩级别 1-9，越高越耗 CPU
    gzip_types        text/plain text/css application/javascript application/json image/svg+xml;
    gzip_vary         on;              # 响应头携带 Vary: Accept-Encoding
    gzip_proxied      any;             # 对来自代理的响应也压缩
    gzip_disable      "msie6";         # 不对老 IE 压缩
}
```

> **注意：** Nginx 默认只压缩 text/html，其他类型必须在 gzip_types 中显式列出；图片、音视频本身已高度压缩，gzip 收益很低还会白白消耗 CPU。Brotli 压缩需要 ngx_brotli 等第三方模块，压缩率优于 gzip。
{: .sec-pit}

静态资源还有更省 CPU 的玩法：编译带上 --with-http_gzip_static_module 后，Nginx 直接发送发布时预先生成的 .gz 文件，省掉每次请求的实时压缩，构建流水线里加一步 gzip -k 即可。

## 十三、HTTPS 配置
{: .sec-expl}

HTTPS 配置的三要素是证书、私钥与安全协议。server 块配置如下：

```nginx
server {
    listen       443 ssl;
    server_name  www.example.com;

    ssl_certificate      /etc/nginx/ssl/www.example.com.crt;    # 证书文件
    ssl_certificate_key  /etc/nginx/ssl/www.example.com.key;    # 私钥文件
    ssl_protocols        TLSv1.2 TLSv1.3;                       # 仅启用安全协议
    ssl_ciphers          HIGH:!aNULL:!MD5;                      # 加密套件
    ssl_prefer_server_ciphers  on;                              # 由服务端决定套件

    ssl_session_cache    shared:SSL:10m;        # 会话缓存，多 worker 共享
    ssl_session_timeout  10m;                   # 会话复用有效期

    location / {
        root  /html/www;
        index index.html;
    }
}

# HTTP 强制跳转到 HTTPS
server {
    listen 80;
    server_name www.example.com;
    return 301 https://$host$request_uri;
}
```

| 指令 | 说明 |
| --- | --- |
| ssl_certificate / ssl_certificate_key | 证书与私钥路径，需支持 HTTPS（yum 源默认支持，编译需 --with-http_ssl_module） |
| ssl_protocols | 推荐 TLSv1.2 TLSv1.3，SSLv3、TLSv1.0/1.1 已废弃必须关闭 |
| ssl_session_cache / ssl_session_timeout | 会话复用：缓存会话参数，重复访问跳过完整握手，降低延迟与 CPU |
| ssl_ciphers | 限制加密套件，剔除不安全算法 |

自签名证书仅用于测试：

```bash
openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
    -keyout /etc/nginx/ssl/www.example.com.key \
    -out /etc/nginx/ssl/www.example.com.crt
```

> **注意：** 生产环境应使用受信任 CA 签发的证书（购买或使用 Let's Encrypt 免费证书，配合 certbot 自动续期）。1.25.1 及以后版本默认支持 HTTP/2，无需再写 `http2` 参数；更早版本使用 `listen 443 ssl http2;`。
{: .sec-pit}

全站 HTTPS 之后别忘了混合内容：页面里引用的 http:// 图片、脚本会被浏览器直接拦截或标记不安全，站内链接与 CDN 地址要一并改成 https，否则证书配得再对，地址栏的锁形图标照样出不来。

浏览器报"证书不受信任"但证书明明没过期，多半是证书链不完整：服务器只发了站点证书没带中间证书。用 openssl s_client -connect 域名:443 看 Certificate chain 是否两级齐全，缺级就把 fullchain 证书配上去。

## 十四、location 匹配陷阱
{: .sec-warn}

location 规则不生效、代理路径错乱等问题，多数来自下面几类陷阱：

1. **proxy_pass 结尾斜杠**：带 `/` 会替换掉 location 匹配的前缀，不带则原样转发，路径对不上时先检查这里；
2. **正则优先级误判**：普通前缀取最长匹配，但任何正则命中都优先于全部普通前缀；用 `^~` 可以阻止正则继续匹配；
3. **`.` 未转义**：`location ~ \.php$` 中的点必须转义，写成 `.` 会匹配任意字符；
4. **大小写**：`~` 区分大小写，匹配 .JPG 等扩展名要用 `~*`；
5. **alias 与 root 混用**：alias 只能用于 location，且结尾斜杠要与 location 保持一致，否则路径拼出 404；
6. **rewrite 的 last/break 差异**：last 会重新匹配 location，可能离开当前块；break 停留在当前块，用在 location 内更安全；
7. **多个 server 同名端口**：请求的 Host 不匹配任何 server_name 时，由该端口第一个 server 处理，default_server 应显式声明；
8. **location 嵌套**：嵌套 location 中的 rewrite 若使用 last，会回到外层重新匹配，容易产生非预期跳转；
9. **if 的坑**：if 在 location 内与 rewrite/return 组合时有不少历史怪癖，能用独立 location 或 return 表达的就绕开 if。

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 配置了认证返回 500 | htpasswd 文件路径错误、权限不足或文件格式不正确 | `tail /var/log/nginx/error.log`、`namei -l /etc/nginx/password/htpasswd` | 用绝对路径，确认 worker 用户可读，密码文件用 htpasswd 生成 |
| 访问返回 403 | allow/deny 顺序导致全部拒绝，或 Referer 防盗链误判 | `curl -I -e "http://evil.example.com" http://www.example.com/a.jpg` | 调整规则顺序，白名单补充合法来源 |
| 页面无限 301 | rewrite/return 目标又匹配到跳转规则自身 | `curl -I http://example.com` 观察 Location 链 | 用独立 server 块或 if 判断打破循环 |
| 代理返回 404 | proxy_pass 结尾斜杠改变了转发路径 | 直接 curl 后端地址对比路径 | 按需去掉或补上结尾 `/` |
| upstream 不生效 | upstream 定义写在了 server 块内（只允许在 http 块） | `nginx -t` | 将 upstream 移到 http 块 |
| 限流未触发 | zone 名称不一致，或 limit_req 写在未生效的 location | `nginx -T \| grep limit_req` | 统一 zone 名，确认所在 location 能命中请求 |
| gzip 无效 | 响应类型不在 gzip_types，或小于 gzip_min_length | `curl -H "Accept-Encoding: gzip" -I http://www.example.com/a.js` | 补充类型、调整最小长度 |
| HTTPS 无法启动 | 证书与私钥不匹配，或缺少 --with-http_ssl_module | `nginx -t`、`openssl x509 -noout -modulus -in a.crt \| md5sum` | 重新配置证书对，确认编译参数 |

排错的通用顺序：nginx -T 看最终生效配置（include 合并后的完整形态）→ curl -I 复现并看响应头 → tail error.log 对时间戳。三步走完，八成问题已经定位。

## 现代环境补充
{: .sec-ext}

CentOS 7 已于 2024 年 6 月停止维护，Rocky Linux、AlmaLinux、CentOS Stream 上的对应做法：

| 旧命令/做法 | 新命令/做法 | 说明 |
| --- | --- | --- |
| `yum install httpd-tools` | `dnf install httpd-tools` | htpasswd 由 httpd-tools 提供，包名不变 |
| `service nginx reload` | `systemctl reload nginx` | service 命令已废弃 |
| `iptables -A INPUT -p tcp --dport 443 -j ACCEPT` | `firewall-cmd --add-service=https --permanent && firewall-cmd --reload` | 防火墙改用 firewalld |
| `openssl`（1.0.x） | `openssl`（3.x，Rocky/Alma 默认） | OpenSSL 3 默认禁用不安全算法，生成证书参数需调整 |

其他要点：

- nginx.org 官方 yum 源在 Rocky/Alma 上直接可用（centos/7、centos/8、centos/9 目录对应）；
- Let's Encrypt 证书可通过 EPEL 中的 certbot 申请并自动续期：`dnf install certbot python3-certbot-nginx && certbot --nginx`；
- 生产建议关闭 TLS 1.0/1.1，仅保留 TLSv1.2 与 TLSv1.3，并开启 HSTS（`add_header Strict-Transport-Security "max-age=31536000" always;`）；

## 知识卡片
{: .sec-know}

**rewrite/return 速查卡**

| 写法 | 效果 |
| --- | --- |
| `rewrite ^/a/(.*)$ /b/$1 last;` | 重写 URI 并重新匹配 location |
| `rewrite ^/a/(.*)$ /b/$1 break;` | 重写 URI，停留在当前 location |
| `rewrite ^/old/(.*)$ /new/$1 permanent;` | 301 永久跳转 |
| `rewrite ^/old/(.*)$ /new/$1 redirect;` | 302 临时跳转 |
| `return 301 https://$host$request_uri;` | 直接跳转 HTTPS，效率最高 |
| `return 403;` | 直接返回状态码 |

**反向代理与负载均衡卡**

| 指令 | 用途 |
| --- | --- |
| `proxy_pass http://backend;` | 转发到 upstream 组或单机 |
| `proxy_set_header Host $host;` | 透传原始 Host |
| `proxy_set_header X-Real-IP $remote_addr;` | 记录真实客户端 IP |
| `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` | 记录代理链 |
| `upstream` + `ip_hash;` | 基于客户端 IP 的会话保持 |
| `server ... backup;` | 备份后端 |

**安全与性能卡**

| 场景 | 指令 |
| --- | --- |
| IP 黑白名单 | `allow 10.0.0.0/8; deny all;` |
| 账号认证 | `auth_basic "区域名"; auth_basic_user_file /etc/nginx/password/htpasswd;` |
| 请求限速 | `limit_req zone=req_zone burst=20 nodelay;` |
| 并发限制 | `limit_conn conn_zone 10;` |
| 防盗链 | `valid_referers none blocked server_names *.example.com;` |
| 压缩 | `gzip on; gzip_types text/css application/javascript;` |
| HTTPS | `listen 443 ssl; ssl_protocols TLSv1.2 TLSv1.3;` |

## 小结
{: .sec-sum}

1. 搭建网站五步曲：编写虚拟主机配置、准备站点代码、重载服务、配置解析、访问测试。
2. 多网站部署遵循“一站一配置、一站一目录”，通过 server_name 区分站点。
3. 虚拟主机支持基于域名、基于地址、基于端口三种访问方式；修改监听地址后必须重启服务。
4. 网站安全两类手段：access 模块按来源地址 allow/deny，auth_basic 模块做账号密码认证。
5. 404 与 403 优先排查 location 配置、站点目录文件与解析记录。
6. 修改配置文件需要重载服务，仅修改站点代码则不需要重启。
7. rewrite 的 last 与 break、proxy_pass 的结尾斜杠、正则与普通前缀的优先级，是三大高频陷阱。
8. upstream + proxy_pass 实现负载均衡，ip_hash 用于会话保持，backup 提供灾备。
9. proxy_cache、limit_req/limit_conn、valid_referers、gzip 是生产环境标配，配置前先确认所在上下文（http/server/location）。
10. HTTPS 三要素：证书、私钥、TLS 协议版本；会话复用通过 ssl_session_cache 实现。

## 自测题
{: .sec-prac}

1. `rewrite ... last` 与 `rewrite ... break` 有什么区别？各适合什么场景？
2. `location /api/ { proxy_pass http://127.0.0.1:8080/; }` 与去掉结尾 `/` 的写法，对请求 /api/user 的转发结果有什么不同？
3. upstream 中配了 3 台后端，其中 1 台标记 backup，平时流量如何分配？某台非 backup 机宕机后流量如何变化？
4. 一台 Nginx 既要限单个 IP 的请求速率，又要限制单 IP 并发连接数，需要哪几条指令？分别定义在什么上下文？
5. 给 www.example.com 配置 HTTPS，并把 80 端口请求全部跳转到 HTTPS，写出关键配置。

> **答案：**
> 1. last：停止后续 rewrite，用重写后的 URI 重新匹配 location，可能进入另一个 location，适合需要按新 URI 分发的场景；break：停止后续 rewrite，直接在当前 location 内处理，适合重写路径后仍由当前配置（如 fastcgi）处理。选错会出现在当前块死循环或跳去了错误 location 的问题。
> 2. 带 `/`：location 匹配的前缀 /api/ 被替换，请求 /api/user 实际转发为 http://127.0.0.1:8080/user；不带 `/`：原样转发 http://127.0.0.1:8080/api/user。后端接口路径对不上时，优先检查这里。
> 3. 平时流量只在两台非 backup 后端间按轮询（或 weight/ip_hash 策略）分配，backup 不接收流量；当非 backup 机全部故障时，流量才会切到 backup 机；单台非 backup 故障时由剩余机器承接（max_fails/fail_timeout 控制故障摘除）。
> 4. `limit_req_zone $binary_remote_addr zone=req_zone:10m rate=10r/s;` 与 `limit_conn_zone $binary_remote_addr zone=conn_zone:10m;` 定义在 http 块；location 内用 `limit_req zone=req_zone burst=20 nodelay;` 与 `limit_conn conn_zone 10;` 引用。
> 5. 关键配置：`listen 443 ssl;`、`ssl_certificate` 与 `ssl_certificate_key` 指向证书和私钥、`ssl_protocols TLSv1.2 TLSv1.3;`、`ssl_session_cache shared:SSL:10m;`，另写一个 `listen 80;` 的 server 块，用 `return 301 https://$host$request_uri;` 跳转。
