## 21.1 什么是错误
{: .sec-expl}

### 21.1.1 三层分类：按"谁发现它"划分
{: .sec-know}

编译期、链接期、运行期不是随意分组，每一层对应工具链上不同的程序，检查能力也完全不同：

| 层 | 检查者 | 能看到什么 | 典型现象 |
| --- | --- | --- | --- |
| 编译期 | 编译器前端 | 单个翻译单元内的语法与类型 | `error: ...`，编译中断，不出目标文件 |
| 链接期 | 链接器 | 跨翻译单元的符号匹配 | `undefined reference` / `multiple definition` |
| 运行期 | 操作系统、运行时、你 | 真实数据、真实时序、真实并发 | 段错误、断言失败、数据错乱、崩溃或"悄悄错" |

三层的能力边界值得记牢：编译器只看得到一个 `.cpp` 展开头文件之后的样子，跨文件的函数签名不匹配、忘写定义，它管不着，那是链接器的活；链接器只做符号匹配，函数参数类型不匹配它发现不了（C++ 靠名字修饰把类型编进符号名，算是间接兜住了一部分）；运行期的问题编译期完全不可见——悬空指针只要不解引用，编译链接都绿灯。

分层的实际意义在于排错顺序：程序出问题，先判断在哪一层。编译都不过的，别想运行期的事；链接报错的，去查符号和库；能跑出错的，才轮到调试器和 sanitizer。

### 21.1.2 每层的最小示例
{: .sec-prac}

三层各来一个最小复现，后面小节展开：

```cpp
// compile_err.cpp —— 编译期错误
int add(int a, int b) { return a + b; }

int main() {
    return add(1);            // 少一个参数
}
```

```text
compile_err.cpp:5:19: error: no matching function for call to 'add(int)'
```

```cpp
// link_err.cpp —— 链接期错误
int helper();                 // 声明了，没人定义

int main() { return helper(); }
```

```bash
g++ link_err.cpp -o le
```

```text
/usr/bin/ld: /tmp/ccAbCdEf.o: in function `main':
link_err.cpp:(.text+0x9): undefined reference to `helper()'
collect2: error: ld returned 1 exit status
```

```cpp
// runtime_err.cpp —— 运行期错误（SIGSEGV）
#include <iostream>

int main() {
    int* p = nullptr;
    std::cout << *p << '\n';   // 解引用空指针
}
```

```bash
g++ runtime_err.cpp -o re && ./re
```

```text
Segmentation fault (core dumped)
```

三种报错的"质感"完全不同：编译错误带文件行号和具体原因；链接错误只有符号名没有行号；运行期只有一句 Segmentation fault，现场全靠事后工具捞。

## 21.2 常见的错误分析
{: .sec-expl}

### 21.2.1 编译错误解读方法论：从第一条看起
{: .sec-know}

编译器的报错是**顺序级联**的：第一条错误引发的连锁反应会产生后续几十条衍生错误，衍生错误往往不知所云。所以规则只有一条——从第一条 error 看起，改完重编，别在第一百条上浪费生命。

另一个反直觉规则：**warning 优先看**。很多编译错误其实是"警告攒够了才爆"，比如类型截断的 `-Wconversion` 警告背后常常藏着真正的 bug。`-Werror` 把警告升格为错误是值得的纪律（见 21.4.4）。

### 21.2.2 模板错误信息为何爆炸，concepts 怎么救
{: .sec-know}

模板报错长的原因：错误发生在实例化时，编译器必须把"推导失败的全过程"报出来——它尝试了哪个候选、试到了哪一层成员、哪一步不满足要求，全部如实上报。C++20 之前没有标准方式告诉编译器"哪些要求是硬约束"，它只能把推导细节全倒出来。

对比实验，同一个错误（类型没定义 `+`），无约束模板和 concept 约束模板：

```cpp
// tmpl_err.cpp —— 需要 -std=c++20
#include <iostream>

struct Vec { double x, y; };

template <typename T>                       // 无约束版本
T twice(T v) { return v + v; }

template <typename T>
    requires requires(T a) { a + a; }       // 约束版本：要求 a+a 合法
T twice_ok(T v) { return v + v; }

int main() {
    Vec v{1, 2};
    std::cout << twice(v).x << '\n';        // 故意选无约束版制造报错
}
```

```text
g++ 13 输出（节选）：
tmpl_err.cpp:16:18: error: no match for 'operator+' (operand types are 'Vec' and 'Vec')
    9 | T twice(T v) { return v + v; }
      |                      ~~^~~
tmpl_err.cpp:9:21: note: candidate: 'template<class T> T twice(T)'
tmpl_err.cpp:9:21: note:   template argument deduction/substitution failed:
...（数十行 candidate 展开，无约束版本此处最吓人）
```

把 `twice` 换成 `twice_ok` 后，报错缩成两行：

```text
error: use of function 'twice_ok<Vec>' with unsatisfied constraints
note: constraints not satisfied
```

这就是 concept 的第二重价值：不只是文档和约束，是**报错信息压缩器**。团队的泛型接口加约束，最先受益的是每个调用者的排错时间。

### 21.2.3 no matching function 与 note: candidate
{: .sec-know}

`error: no matching function for call to 'X'` 表示没有候选能接住这组实参，紧随的 `note: candidate` 列出所有候选及其落选原因。常见落选原因四种：const 不匹配（实参 `const T&` 传给 `T&`）、右值传给非常量左值引用、参数个数/类型不匹配、模板推导失败。

```cpp
// no_match.cpp —— 需要 -std=c++20
#include <string>

int count_upper(std::string& s);            // 只收非 const 左值引用

int main() {
    const std::string name = "Hello";
    return count_upper(name);               // const 传给非 const 引用
}
```

```text
g++ 13 输出（节选）：
no_match.cpp:8:24: error: no matching function for call to 'count_upper(const string&)'
    8 |     return count_upper(name);
      |            ~~~~~~~~~~~^~~~~~
no_match.cpp:3:5: note: candidate: 'int count_upper(std::string&)'
    3 | int count_upper(std::string& s);
      |     ^~~~~~~~~~~
no_match.cpp:3:5: note:   conversion of argument 1 would be invalid
```

读法：先看 error 括号里编译器把实参**推导成了什么类型**（`const string&`），再看每个 candidate 的形参类型，差异就是答案。C++14 起诊断里会带原始列号箭头（`^` 标出具体位置），新版编译器还能指出"哪条 concept/推导规则没过"。

most vexing parse（最令人头痛的解析）是编译错误里的一类"长相特殊"的：你以为在构造对象，编译器读成了函数声明。

```cpp
// vexing.cpp —— 需要 -std=c++20
#include <iostream>

struct Timer {
    void start() { std::cout << "started\n"; }
};

int main() {
    Timer t();          // 这是函数声明！声明了一个返回 Timer、无参的函数 t
    t.start();          // 在"函数"上调成员，这里才爆
}
```

```text
vexing.cpp:9:7: error: request for member 'start' in 't',
    which is of non-class type 'Timer()'
```

报错里的 `Timer()`（带括号的类型）是识别特征。修复：`Timer t;` 或 `Timer t{};`（C++11 起花括号统一初始化让这个坑在现代代码里少多了，但函数风格转换如 `T(x)` 与声明歧义的场合仍在）。

### 21.2.4 链接错误：undefined reference 的四种成因
{: .sec-ts}

`undefined reference to 'X'` 的意思是：某处**用到了**符号 X，链接器在所有目标文件和库里都没找到**定义**。四种成因按出现频率排：

```cpp
// 成因一：声明了没定义（最直白）
// util.h
int total_bytes(const std::string& s);   // 头文件里有声明
// 忘了在任何 .cpp 里写实现 → undefined reference
```

```cpp
// 成因二：静态成员忘定义
struct Registry {
    static int count;        // 类内只是声明
};
// 忘了写 int Registry::count = 0; → undefined reference
// C++17 起的正确写法：static inline int count = 0; 类内直接给定义
```

```cpp
// 成因三：模板实现放在 .cpp 里
// tmpl.h
template <typename T> T twice(T v);         // 只有声明
// tmpl.cpp
template <typename T> T twice(T v) { return v + v; }  // 定义藏在 cpp
// main.cpp: twice(21) → 编译器在 main.cpp 里无法实例化，没有定义可找
//          → undefined reference to `int twice<int>(int)`
```

模板这条最反直觉：模板定义必须在**实例化点可见**（第 16 篇讲过根因——每个 TU 独立实例化）。修法三条：实现进头文件；或在 `tmpl.cpp` 里显式实例化 `template int twice<int>(int);`；或 C++20 起把模板搬进模块。

```bash
# 成因四：忘链库或链错顺序
g++ main.o -lssl -lcrypto       # 正确：被依赖的库放右边
g++ main.o -lcrypto -lssl       # 顺序颠倒：可能 undefined reference
```

链接器从左到右扫描，处理 `-l` 时只记录"当前已求但未满足"的符号，库放早了，后面目标文件的引用它已经扫过了。规则：**被依赖者放在依赖者右边**。循环依赖用 `-Wl,--start-group ... -Wl,--end-group` 包起来（有重复扫描的链接时间代价，能不用就不用）。

### 21.2.5 duplicate symbol 与 ODR
{: .sec-warn}

反方向的链接错误：同一个符号在多处定义。

```cpp
// bad_header.h —— 出问题的写法
#pragma once
#include <string>

std::string g_log_file = "app.log";   // 头文件里定义非 inline 全局变量
```

```bash
g++ a.cpp b.cpp bad_header.h -o app
# GCC 10+（-fno-common 默认开启）：
/usr/bin/ld: b.o:(.bss+0x0): multiple definition of `g_log_file'; a.o:(.bss+0x0): first defined here
```

头文件被两个 TU 包含，定义被粘贴两份，链接器撞车。这就是 ODR（单一定义规则）在工程里的直接表现。正确写法三选一：头文件里 `extern` 声明、`.cpp` 里定义（传统）；C++17 `inline std::string g_log_file = "app.log";`（内联变量，允许跨 TU 重复定义、链接器合而为一）；常量改 `constexpr`（内部链接，天然无冲突）。

同类事故还有：匿名命名空间写进了头文件（每个 TU 一份拷贝，不报错但内存翻倍、行为诡异）、函数体写在头文件里没标 `inline`。原则一句话：**头文件里只放声明和 inline/constexpr/模板**。

### 21.2.6 符号工具箱：nm、c++filt、ldd、readelf
{: .sec-ver}

链接错误排查的兵器谱，全部基于 ELF 符号表：

```bash
# 看.a/.o里有哪些符号，-C 解修饰（demangle）
nm -C libmath.a | grep add

# 手动解修饰：链接错误报的是修饰名，翻译回函数签名
c++filt _ZN3demo3addEii

# 看可执行文件运行时依赖哪些动态库、找到没
ldd ./app
#  libm.so.6 => /lib/x86_64-linux-gnu/libm.so.6 (0x00007f...)

# 看动态段声明的 NEEDED 库（不猜、不运行）
readelf -d ./app | grep NEEDED
```

`nm` 输出里的符号类型字母有讲究：`T`（代码段，已定义）、`U`（未定义，需要别人提供）、`W`/`w`（弱符号）。`undefined reference` 排查套路就是三步：`nm` 看提供方库里符号是不是 `T`；不是 `T` 看 `U` 旁是谁（同名不同签名）；都不在，查库链没链或版本不对。动态库问题用 `ldd` 配 `readelf`：`ldd` 模拟运行期查找，`readelf -d` 只看编译期声明，两者不一致说明运行环境路径有问题（`LD_LIBRARY_PATH`、rpath）。

C++ 的符号都是修饰名（name mangling，把命名空间、参数类型编进符号名），这既是 `undefined reference` 报错能暴露参数类型不匹配的原因，也是 `c++filt` 存在的理由。

## 21.3 程序调试常见错误
{: .sec-expl}

### 21.3.1 SIGSEGV 与 SIGABRT：两种最常见的崩溃信号
{: .sec-know}

Linux 下进程崩溃表现为信号。最常见的两个：

| 信号 | 来源 | 典型成因 |
| --- | --- | --- |
| SIGSEGV | 内核 | 解引用空指针/野指针、栈溢出（深递归、巨大局部数组）、写只读内存 |
| SIGABRT | 程序自己 | `assert` 失败、未捕获异常（`std::terminate`）、`abort()`、glibc 检测到堆破坏（double free 等） |

信号类型直接缩窄排查范围：SIGABRT 先看 stderr 最后一行——`terminate called after throwing an instance of 'std::out_of_range'` 这类信息直接给出异常类型，九成不用上调试器；SIGSEGV 必然是内存访问问题，需要现场（gdb + core 或 ASan）。

### 21.3.2 core dump：把崩溃现场存下来
{: .sec-prac}

core 文件是进程崩溃瞬间的完整内存快照，事后用它离线还原现场。开启三步：

```bash
ulimit -c unlimited                        # 当前 shell 取消 core 大小限制
cat /proc/sys/kernel/core_pattern          # 看 core 文件写到哪、叫什么
echo 'core.%p' | sudo tee /proc/sys/kernel/core_pattern   # 按进程号命名（需 root）
```

```cpp
// crash.cpp —— 必然 SIGSEGV 的最小例子
#include <iostream>

struct Node { int v; };

void touch(Node* n) {
    std::cout << n->v << '\n';             // n 为空 → SIGSEGV
}

int main() {
    touch(nullptr);
}
```

```bash
g++ -g -O0 crash.cpp -o crash && ./crash
gdb ./crash core.12345                     # 打开 core 文件（12345 是实际 PID）
```

```text
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x0000556f1a2b318e in touch (n=0x0) at crash.cpp:7
```

`-g` 不可省——没有调试信息，gdb 只能给你地址给不了行号。core 文件分析的最大价值在**事后和异机**：用户环境崩了、半夜崩了、复现不了了，core 是唯一的现场。生产环境注意 core 含内存数据，有敏感信息脱敏问题，通常接到专门的崩溃收集服务。

### 21.3.3 UB 总览：崩溃只是 UB 最走运的下场
{: .sec-warn}

undefined behavior 是标准明文说"任何行为都不保证"的代码。C++ 的 UB 清单很长，工程里最高频的这些：

| UB | 典型代码 | 常见实际后果 |
| --- | --- | --- |
| 越界访问 | `v[v.size()]`、负索引 | 踩相邻内存：改了别的变量、堆损坏，或安静通过 |
| 空悬引用/迭代器 | 返回局部变量的引用、erase 后继续用迭代器 | 读到垃圾值、偶发崩溃 |
| 有符号溢出 | `INT_MAX + 1` | 优化器直接删掉你的判断，见 21.3.4 |
| 数据竞争 | 无同步的多线程读写 | 值 torn、死循环、比崩溃难查一个量级 |
| 读未初始化 | `int x; f(x);` | 值随机，或被优化成不可预测分支 |
| 严格别名违规 | `float* → int*` 转型解引用 | 优化后赋值被删，值"莫名不对" |
| 移动后使用 | `std::move(s)` 后继续 `s`（未规定的状态当有效状态用） | 大多"能用"，某些库实现下崩 |
| 返回局部变量引用 | `T& f() { T t; return t; }` | 悬空引用，调用方读到栈上的残渣 |

核心认知：**UB 不等于崩溃，甚至不等于出错**。它等于"标准不再担保"，而优化器把"不担保"当成了"程序员担保不会发生"的许诺，据此做激进优化。下面这个例子是这条规则的著名实证：

```cpp
// ub_opt.cpp —— 有符号溢出是 UB，本例演示优化器行为，勿学
#include <iostream>

bool will_overflow(int x) {
    return x + 1 < x;      // 编译器有权假设永不溢出 → 整个判断恒 false
}

int main() {
    std::cout << std::boolalpha << will_overflow(2147483647) << '\n';
}
```

```bash
g++ -std=c++20 -O0 ub_opt.cpp -o u0 && ./u0    # 无优化
g++ -std=c++20 -O2 ub_opt.cpp -o u2 && ./u2    # 优化
```

```text
-O0：true     （加法真的回绕了，INT_MIN < INT_MAX）
-O2：false    （编译器把"溢出不可能发生"当公理，整个函数优化成 return false）
```

同一份代码，优化级别不同结果相反。这就是"debug 版好好的、release 版坏了"的一类真凶——heisenbug 的经典来源。推论：在 `-O0` 下"测试通过"对 UB 代码毫无意义，测试必须在和发布一致的优化级别下跑。

> **坑：** 遇到"加一行 printf 就好、删掉就坏"的 bug，先怀疑 UB 而不是玄学。printf 改变了时序和优化决策，是 UB 的显形剂不是修复者。

## 21.4 C++编程中的调试技巧
{: .sec-prac}

### 21.4.1 gdb 实战：断点、条件断点、watchpoint、现场翻查
{: .sec-ver}

以 gdb 为例（lldb 命令一一对应，`b`→`breakpoint set`、`bt`→`bt`、`print`→`p`）：

```text
(gdb) b main                      # 断点
Breakpoint 1 at 0x1189: file crash.cpp, line 10.
(gdb) b crash.cpp:7 if n == nullptr    # 条件断点：只在条件成立时停下
(gdb) r                           # 运行
(gdb) bt                          # 崩溃/断点时看完整调用栈
#0  touch (n=0x0) at crash.cpp:7
#1  0x0000556f1a2b3192 in main () at crash.cpp:11
(gdb) frame 0                     # 切到栈帧 0
(gdb) print n                     # 看变量
$1 = (Node *) 0x0
(gdb) watch n                     # watchpoint：n 被改写时停下
(gdb) display n->v                # 每次停下自动显示
(gdb) c                           # 继续
```

日常最值钱的三个：`bt`（崩溃后的第一件事，看调用路径）、条件断点（几百次循环里只在第 499 次停）、`watch`（"这个变量是什么时候被谁改坏的"——内存被踩类问题的终极大招）。core 文件加 `bt` 就是离线版的这套流程。

### 21.4.2 调试优化代码：为什么 -O2 下变量"看不见"
{: .sec-know}

优化会把变量放进寄存器甚至直接消掉，gdb 报 `<optimized out>`、单步跳来跳去，不是 gdb 坏了，是代码已经和你写的不一样。对策按场景：

| 场景 | 编译选项 | 说明 |
| --- | --- | --- |
| 日常调试 | `-O0 -g` | 代码与源码逐行对应，变量全可见 |
| 接近发布的调试 | `-Og -g` | 只做不影响调试的优化，性能 bug 也能初步复现 |
| 性能分析 | `-O2 -g -fno-omit-frame-pointer` | 保留帧指针，perf 火焰图栈完整 |

`-fno-omit-frame-pointer` 值得单独强调：默认省略帧指针后，perf 这类采样器在没 DWARF 展开支持的环境里拿不到完整调用栈，火焰图缺帧。做性能分析时永远加上它。`-g` 和 `-O` 不冲突，发布版也建议带 `-g`（符号信息不进指令流，不影响运行性能，strip 掉即可控制体积）。

### 21.4.3 assert 与 NDEBUG
{: .sec-know}

`assert`（`<cassert>`）是运行期自检的第一道闸，失败时打印表达式、文件、行号并 `abort`（SIGABRT）：

```cpp
// assert_demo.cpp
#include <cassert>
#include <iostream>

int div16(int v) {
    assert(v % 16 == 0 && "v 必须是 16 的倍数");   // && 字面量让消息进输出
    return v / 16;
}

int main() {
    std::cout << div16(32) << '\n';
}
```

```bash
g++ assert_demo.cpp -o ad && ./ad        # 正常
g++ -DNDEBUG assert_demo.cpp -o adr && ./adr   # NDEBUG：assert 全部蒸发
```

```text
32
```

`assert` 被定义为"依赖 NDEBUG"：定义了 `NDEBUG`（发布构建的标准做法）时展开为空。由此两条纪律：assert 里**绝不能有副作用**（`assert(f(x))` 在发布版里 `f(x)` 直接不执行）；表达"即使发布也要检查"的错误用异常或显式 `if`，assert 只验"到这一步内部不变量必须成立"。自定义 assert 宏保留 `#expr` 文本化能力，其余交给 C++20 的 `std::source_location`（第 20 篇 20.4.7）：

```cpp
// 需要 -std=c++20
#include <cstdio>
#include <cstdlib>
#include <source_location>

#define MY_ASSERT(cond)                                                        \
    do {                                                                       \
        if (!(cond)) {                                                         \
            auto loc = std::source_location::current();                        \
            std::fprintf(stderr, "%s:%d: %s: assert failed: %s\n",             \
                         loc.file_name(), loc.line(),                          \
                         loc.function_name(), #cond);                          \
            std::abort();                                                      \
        }                                                                      \
    } while (false)
```

`do { } while (false)` 包裹是让宏在任何 `if/else` 语境下都表现为一条语句的标准技巧。

### 21.4.4 警告选项：-Wall -Wextra -Wpedantic -Werror
{: .sec-best}

警告是编译期调试技巧的一半。基线配置：

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -Werror warn.cpp -o w
```

| 选项 | 抓什么 | 例子 |
| --- | --- | --- |
| `-Wall -Wextra` | 绝大多数真实 bug 模式 | 未初始化变量、未用返回值 |
| `-Wpedantic` | 非标准扩展 | 编译器私有关键字，阻碍移植 |
| `-Werror` | 警告升级为错误 | 防止"以后再修" |
| `-Wreorder` | 成员初始化顺序与声明序不符 | 见下方例子 |
| `-Wshadow` | 内层变量遮蔽外层同名变量 | 改错对象而不自知 |
| `-Wconversion` | 隐式窄化转换 | `int` → `uint8_t` 静默截断 |
| `-Wold-style-cast` | C 风格强转 `(T)x` | 逼出 `static_cast` 的明确意图 |
| `-Wnon-virtual-dtor` | 基类析构非虚却可多态删除 | 经典内存泄漏 |

```cpp
// warn.cpp —— -Wreorder 的活体标本
#include <iostream>

struct Order {
    int id;
    double amount;
    Order(int i, double a) : amount(a), id(i) {}   // 初始化顺序跟声明序走
};

int main() { Order o{1, 9.9}; std::cout << o.id << '\n'; }
```

```text
warn.cpp:7:35: warning: Order::amount will be initialized after Order::id [-Wreorder]
```

成员初始化**永远按声明顺序**执行，初始化列表写得再漂亮也改变不了——这里没有 UB，但两个成员有依赖关系时（比如用 `amount` 初始化 `id`）就是真 bug。这条警告的价值在于把"顺序是隐式规则"变成"顺序错了编译器喊"。

### 21.4.5 sanitizer 全家：运行期错误检测器
{: .sec-ver}

sanitizer 是编译器插桩 + 运行时库的组合，各管一段：

| 选项 | 抓什么 | 性能开销（量级） | 限制 |
| --- | --- | --- | --- |
| `-fsanitize=address` | 堆/栈/全局越界、use-after-free、double free | 慢约 2 倍，内存 2~3 倍 | 与 TSan 互斥 |
| `-fsanitize=undefined` | 有符号溢出、错位对齐、空引用等 UB | 慢约 1.x 倍 | 可与 ASan 同开 |
| `-fsanitize=thread` | 数据竞争 | 慢 5~15 倍，内存 5~10 倍 | 与 ASan 互斥 |
| `-fsanitize=memory` | 读未初始化内存 | 慢约 3 倍 | 只支持 Clang，需全依赖重编 |
| `-fsanitize=leak` | 内存泄漏（ASan 自带） | 同 ASan | 需要准确符号信息 |

ASan 与 TSan 不能同开是**架构限制**（两者都要接管同一批运行时插桩点），想查内存又查并发就分两轮跑。典型输出：用 21.1.1 的越界思路造一个堆越界——

```cpp
// asan_demo.cpp —— 堆越界写
#include <vector>
#include <iostream>

int main() {
    std::vector<int> v(4);
    v[4] = 1;                    // operator[] 不查边界，静默越界
    std::cout << v.size() << '\n';
}
```

```bash
g++ -std=c++20 -g -fsanitize=address asan_demo.cpp -o a && ./a
```

```text
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x602000000054
WRITE of size 4 at 0x602000000054 thread T0
    #0 0x401136 in main asan_demo.cpp:7
==12345==SUMMARY: AddressSanitizer: heap-buffer-overflow asan_demo.cpp:7 in main
```

```bash
g++ -std=c++20 -g -fsanitize=thread tsan_demo.cpp -o t && ./t
```

```text
==================
WARNING: ThreadSanitizer: data race (pid=12345)
  Write of size 4 at 0x556f1a2c1018 by thread T2:
    #0 add_ten_thousand() tsan_demo.cpp:6
  Previous read of size 4 at ... by thread T1:
    #0 add_ten_thousand() tsan_demo.cpp:6
  Summary: ThreadSanitizer: data race tsan_demo.cpp:6 in add_ten_thousand
==================
```

TSan 的输出直接给出冲突双方的栈和源码行，数据竞争从"玄学"变成"看输出"。注意两个细节：ASan 输出里的地址和 PID 每次都不同，看的是错误类型和栈；sanitizer 开销不小，测试环境用，发布版不用（也有 Google 级别"生产环境开 ASan"的先例，属于极端收益场景）。

配套的容器级检查，`-D_GLIBCXX_DEBUG` 让 libstdc++ 的容器换上带边界校验的调试实现，同样这段越界代码：

```bash
g++ -std=c++20 -g -D_GLIBCXX_DEBUG asan_demo.cpp -o d && ./d
```

```text
/usr/include/c++/13/debug/vector:xxx:
Error: attempt to subscript container with out-of-bounds index 4,
but container only holds 4 elements.
```

消息不如 ASan 精细（没有内存布局信息），但零插桩开销、和 ASan 互补（它能查 ASan 查不到的迭代器失效类问题），老项目 compiler 支持跟不上 sanitizer 时也是退路。注意它改变容器布局，所有依赖容器内存布局的第三方库必须一起重编。

### 21.4.6 静态分析：clang-tidy、cppcheck、IWYU
{: .sec-best}

静态分析不运行代码，直接在 AST/控制流图上找问题。clang-tidy 是主力，check 按前缀分组：

```bash
clang-tidy -checks='bugprone-*,performance-*,modernize-*,readability-*' \
    warn.cpp -- -std=c++20 -Iinc
```

| 分组 | 价值示例 |
| --- | --- |
| `bugprone-*` | 悬空引用、被忽略的返回值、错误的重载选择 |
| `performance-*` | 不必要的值拷贝、循环里的字符串拼接 |
| `modernize-*` | 老写法升级建议（裸指针→智能指针、`typedef`→`using`） |
| `readability-*` | 命名、复杂度、冗余代码 |

接入 CMake 一行搞定，构建时自动跑：

```cmake
set(CMAKE_CXX_CLANG_TIDY clang-tidy;-checks=bugprone-*,performance-*)
```

cppcheck 更轻量，不需要编译数据库，适合快速全量扫描（`cppcheck --enable=warning,performance .`）；IWYU（include-what-you-use）专查头文件依赖：漏包含、多余包含、该前向声明的没前向声明——第 20 篇 20.4.8 头文件纪律的机械化执行者。三者定位不重叠：tidy 深而慢按需跑，cppcheck 浅而快全量跑，IWYU 只管 include。

### 21.4.7 编译期防护：static_assert、concepts、[[nodiscard]]、final
{: .sec-know}

能挪到编译期的检查都别留给运行期：

```cpp
// 需要 -std=c++20
#include <concepts>
#include <string>

struct Packet { char tag; int value; };
static_assert(sizeof(Packet) == 8, "协议布局变了！");   // 布局锁死

enum class Status { ok, fail };
[[nodiscard]] Status connect() { return Status::ok; }    // 返回值不许扔

template <std::integral T>                               // concept 卡实参
T scale(T v) { return v * 2; }

struct Base final { };    // final：禁止继承，消灭虚调用开销与误继承

int main() {
    auto s = connect();
    (void)s;
    return scale(21);
}
```

`[[nodiscard]]`（C++17，带原因字符串是 C++20）抓的是"忘记处理错误码"这类高频事故——`connect()` 的返回值被丢弃时编译器直接警告。`static_assert` 的消息参数 C++17 起可省。concepts 在 21.2.2 已展示报错价值，防护价值同源：把"这个类型能不能用"提前到编译期。`final` 不只是性能（去虚化），更是设计表态：这个类不该被继承，谁继承谁错。

### 21.4.8 日志与可观测性：spdlog、级别与异步
{: .sec-prac}

printf 调试的问题不是"低级"，是没级别、没时间戳、没结构、同步阻塞。spdlog（基于 fmt 库）是 C++ 日志的事实标配：

```cpp
// log_demo.cpp —— 需要 -std=c++20，链接 spdlog（如 -lspdlog）
#include <spdlog/spdlog.h>

int main() {
    spdlog::set_level(spdlog::level::debug);
    spdlog::info("启动完成，耗时 {:.3f}s", 0.417);
    spdlog::warn("缓存命中率偏低：{}", 0.31);
    spdlog::debug("x = {}, y = {}", 1, 2);
}
```

```text
[2026-10-28 09:15:02.417] [info] 启动完成，耗时 0.417s
[2026-10-28 09:15:02.417] [warning] 缓存命中率偏低：0.31
[2026-10-28 09:15:02.417] [debug] x = 1, y = 2
```

（时间戳以实际运行为准。）关键实践三条：级别在运行时可调（生产 info，排查时临时调 debug，不重编）；`{:.3f}` 这类格式化由编译期检查参数个数（fmt 的编译期格式串校验），比 printf 安全；异步日志（`spdlog::async_logger`）把写文件挪到后台线程，日志密集时不拖慢业务线程，代价是崩溃瞬间最后几条可能丢失。结构化日志（键值对而不是拼句子）是给日志采集系统（ELK 这类）消费的进阶形态，微服务里值得，单体程序可缓一缓。

### 21.4.9 性能观测：perf、火焰图、gperftools、Google Benchmark
{: .sec-ver}

性能问题的第一定律：**先测量再动手**。直觉猜的热点经常是错的。

```bash
perf record -g -F 99 ./app          # 采样调用栈，99Hz
perf report                          # 交互式看热点
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg   # 火焰图
```

火焰图（Brendan Gregg 的 FlameGraph 工具链）把采样堆叠成矩形，越宽的块占用越多，一眼定位热点路径。前提别忘了 `-g -fno-omit-frame-pointer`（21.4.2），否则栈断头。gperftools 是替代品（`CPUPROFILE=cpu.prof ./app` 再用 `pprof --text ./app cpu.prof` 分析），采样原理相同，生态上 perf + 火焰图更主流。

微基准用 Google Benchmark：

```cpp
// bench.cpp —— 需要 -std=c++20，链接 benchmark 库
#include <benchmark/benchmark.h>
#include <string>

static void BM_BuildString(benchmark::State& state) {
    for (auto _ : state) {
        std::string s;
        for (int i = 0; i < 256; ++i) s.push_back(static_cast<char>(i));
        benchmark::DoNotOptimize(s);      // 防止编译器把整段删了
    }
}
BENCHMARK(BM_BuildString);
BENCHMARK_MAIN();
```

`DoNotOptimize` 是灵魂：没有它，优化器发现 `s` 没被观察，整个循环可能被删空，测出来的"性能"是零条指令的性能。另一条铁律：**基准测试永远在发布优化级别（-O2/-O3）下做**，`-O0` 的结论和真实性能可能差 10 倍以上，且优化差异会颠倒结论（21.3.4 的 UB 例子就是活证）。

### 21.4.10 CI 里的最小可观测流水线
{: .sec-best}

把上面的工具串进 CI，最小可行配置：

```yaml
# .github/workflows/check.yml（节选）
name: check
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: >
          cmake -B build
          -DCMAKE_BUILD_TYPE=Debug
          -DCMAKE_CXX_FLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -Wall -Wextra -Werror"
          -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=address,undefined"
      - run: cmake --build build -j
      - run: ctest --test-dir build --output-on-failure
```

要点：测试在 sanitizer 开启下跑（UB 和内存错误在测试阶段现形，不用等用户报崩溃）；警告当错误；ASan+UBSan 同开没问题，TSan 单独一条流水线（互斥限制）。静态分析（clang-tidy）作为独立 job 或合进构建皆可，关键是**每次提交都跑**——静态检查的价值全在增量反馈，攒 PR 一起查没人看得完。

## 21.5 技术解惑
{: .sec-expl}

### 21.5.1 debug 版好好的，release 版就坏：heisenbug 的三个来源
{: .sec-know}

"加了打印就好、开 -O0 就好、断点一挂就好"的 bug（heisenbug），来源几乎总能归到三类：

| 来源 | 机理 | 验证手段 |
| --- | --- | --- |
| UB | 优化器把"未定义"当"不可能"，激进改写；printf/断点改变优化决策 | UBSan + ASan 全量扫 |
| 未初始化 | debug 版内存被填充模式（MSVC 的 0xCC 等），release 版是随机残渣 | MSan、Valgrind |
| 时序 | 数据竞争在 debug 慢速下不触发，release 下窗口暴露 | TSan |

诊断顺序照这个表走，别从"玄学"开始。共同的深层原因：**调试行为本身改变了程序的状态和时序**——这也是"挂上调试器就不崩"的原因。

### 21.5.2 崩溃排查清单
{: .sec-chk}

按序执行，每步都有明确的产出判断：

1. 信号是什么？SIGABRT 先看 stderr 末尾（多半有异常类型），SIGSEGV 直接进下一步。
2. stderr / 日志最后几行有没有线索（异常消息、断言文本）。
3. 本地可复现：直接 gdb 挂上跑，崩溃后 `bt` 看栈。
4. 本地不可复现：开 core dump 等下一次，或加 ASan/TSan 重跑测试。
5. 怀疑 UB：ASan + UBSan（内存类）、TSan（并发类）、`-D_GLIBCXX_DEBUG`（容器类）轮番上。
6. 怀疑优化差异：固定 `-O2` 复测，对照 `-O0`，复现了再看 UBSan 报什么。
7. 拿到第一个可疑栈帧后：检查该帧所有指针和引用的有效性（空？悬空？），别急着改代码。
8. 修复后：补一条能抓住这个 bug 的测试，加进 CI——崩溃排查的终点是"以后这类问题在提交阶段就被拦下"。

{: .sec-ex}

1. 写一个头文件，故意在头文件里定义非 inline 全局变量和非 inline 函数，两个 cpp 包含它，观察链接器报错原文；然后用 `nm a.o` 和 `nm b.o` 找到重复符号的 `T` 记录，再改成 C++17 inline 变量 + inline 函数，重跑 `nm` 对比差异。
2. 构造一个未捕获异常的程序（`std::vector::at` 越界），分别用直接运行和 gdb 运行，对比两种方式下你获得的错误信息量；再给程序加上 `try/catch (const std::exception& e)`，观察 SIGABRT 消失。
3. 把 21.3.4 的 `ub_opt.cpp` 分别用 `-O0` 和 `-O2` 编译运行，确认输出相反；再开 `-fsanitize=undefined` 跑 `-O2` 版本，看 UBSan 能否在优化代码里抓到溢出（能，这正是 sanitizer 的价值）。
4. 用 `-fsanitize=thread` 跑 21.4.5 提到的数据竞争示例，读输出里"两次访问"的栈；然后加 `std::atomic<int>` 或 `std::mutex` 修复，重跑确认警告消失，顺便对比修复前后的运行结果是否总是 20000。
5. 给 21.4.8 的日志例子加一条错误级别的结构化日志（键值形式），再用 `spdlog::set_level(spdlog::level::off)` 验证 debug 级别被静默；思考：这个行为放发布版有什么风险（哪些本该永远保留的日志被一起关了）？

## 变式追问
{: .sec-think}

1. **为什么链接器能抓参数类型不匹配，却抓不住两个同名类布局不一致？** 推理：C++ 的名字修饰把函数的命名空间和参数类型编进了符号名，签名不匹配就是符号不匹配，链接器顺手就报了。但类成员的**偏移量**不在符号名里，也不在链接器视野内——布局信息活在每个 TU 的编译结果里。头文件版本不一致（TU A 看到旧布局、TU B 看到新布局）时，链接照样成功，运行期成员错位，这是"改了头文件没全量重编"型事故的机理，也是 ABI 兼容性问题的缩影。
2. **ASan 已经能抓越界，`_GLIBCXX_DEBUG` 还有什么存在价值？** 推理：ASan 的边界模型是"分配块之外的内存"，同一个 `vector` 内部 buffer 的两次逻辑错误——`v[4]`（刚出界）ASan 能抓，但"迭代器失效后继续 ++"这种仍在合法内存里游走的错误，ASan 看不见内存访问本身有问题。`_GLIBCXX_DEBUG` 的调试容器知道自己的 size 和迭代器的宿主，能抓"逻辑上失效"的访问。两者检查的是不同层的"错误"，组合使用覆盖面最大。
3. **core dump 在容器里还好使吗？** 推理：文件路径、大小限制、写权限的机制本身不变，变的是环境——容器的文件系统是易失的，Pod 重启 core 就没了；`core_pattern` 是宿主机内核全局的，容器里改不动。所以云原生环境的实际做法是把 core 写进挂载卷或直接接崩溃收集器（`core_pattern` 管道模式，如 `|/usr/bin/crashreporter %e %p`），把"拿到文件"换成"送出快照"。机制没死，交付方式换了。
4. **为什么 sanitizer 不直接永远开着？** 推理：ASan 慢 2 倍、内存 3 倍，TSan 更狠，全量生产部署成本摆在那。但反过来问更有价值——真正的原因是"永远开着"意味着所有第三方依赖都必须以插桩模式链接，闭源库直接不可用。折中方案是 Google 的做法：生产环境开 ASan 的服务确实存在，前提是依赖全部自控。普通项目把 sanitizer 留在 CI 和压测环境，是成本与覆盖率的现实平衡点。
