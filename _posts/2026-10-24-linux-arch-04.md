## NFS 存储服务概念介绍
{: .sec-know}

> NFS 是 Network File System 的缩写，中文意思是网络文件共享系统。它的主要功能是通过网络（一般是局域网）让不同的主机系统之间可以共享文件或目录。

### 存储服务的种类

**用于中小型企业：实现数据共享存储**

| 类型 | 说明 |
| --- | --- |
| FTP（文件传输协议） | 运维人员把多台服务器的数据汇总到 FTP 服务器；例如中小型电商公司（游戏点卡、游戏币、道具、Q 币、充值话费）的财务对账信息来自数据库，对账文件则放到 FTP 服务器。权限包含用户认证的权限与存储目录的权限（用户）。获取数据的方式可以用 SSH 远程服务、sFTP |
| samba | Windows ↔ Linux 之间数据传输，在 Linux 上部署 samba |
| NFS | Linux ↔ Linux 之间数据传输 |

**用于门户网站**

```text
一个用户    -- 存储服务器
上万个用户  -- 存储服务器
```

这种规模需要利用**分布式存储**：

| 方案 | 说明 |
| --- | --- |
| Moosefs（mfs） | 比较落伍，初学学习比较简单 |
| GlusterFS |  |
| FastDFS | 企业应用较多 |

> **注意：** 选型判断一句话：Linux 与 Linux 之间挂目录用 NFS；Windows 混合环境用 samba；只是"把文件传上来"不挂载用 FTP；文件量到了千万级、需要按文件名直接 HTTP 访问（图片站、APP 静态资源），上 FastDFS / 对象存储。NFS 的甜点区是"几台到几十台机器、内网、普通读写"。
{: .sec-pit}

## NFS 存储服务的作用

1. 实现数据的共享存储
2. 编写数据操作管理
3. 节省购买服务器磁盘开销（好比淘宝上万台服务器的磁盘与用电开销）

> **注意：** 第 3 条"节省磁盘开销"的实质是集中采购与集中利用：存储集中在一台大容量机器，其他机器的系统盘可以给小，数据也不用每台复制一份。
{: .sec-pit}

## 原理解析：NFS 为什么需要 RPC
{: .sec-know}

NFS 是 C/S 架构的网络文件系统：服务端把本地目录"导出"（export）给客户端，客户端通过 mount 把远程目录挂到本地挂载点，之后对挂载点的读写就像操作本地目录一样，实际操作由内核通过网络发给服务端完成。

这里有一个关键问题：NFS 服务启动后会运行多个进程，每个进程使用一个**随机端口**（mountd、status 等），客户端事先不可能知道这些端口号。解决办法就是引入 RPC：

1. RPC（Remote Procedure Call，远程过程调用）相当于"租房的中介"：服务方把"我提供什么服务、在哪个端口"注册到中介，使用方先到中介查询，再直接连接服务。
2. Linux 上这个中介程序就是 `rpcbind`（旧称 `portmapper`），固定监听 **111 端口**（TCP 与 UDP 都监听）。
3. NFS 服务启动时，各进程把自己的"程序号 + 端口"注册到 rpcbind。
4. 客户端挂载时，先连 111 端口问 rpcbind："mountd 在哪个端口？"，得到答案后再连接真正的服务端口。

RPC 的角色再强调一句：rpcbind 是本机所有 RPC 系服务共用的注册中心，不止 NFS 一家在它这里"挂号"。rpcbind 一挂，就算 NFS 进程还活着，客户端也找不到入口，所以排错永远先查 111 端口。

每个 RPC 服务有唯一的程序号（program number），`rpcinfo -p` 输出里的 100000、100005、100024 就是程序号：

| 程序号 | 服务 | 作用 |
| --- | --- | --- |
| 100000 | portmapper / rpcbind | RPC 注册与查询中介，固定 111 端口 |
| 100005 | mountd | 挂载协议：处理客户端 mount / umount 请求，维护挂载表 |
| 100003 | nfs | NFS 协议本体（内核 nfsd），负责实际文件读写 |
| 100024 | status（rpc.statd） | 网络状态监控，配合锁恢复 |
| 100011 | rquotad | 磁盘配额查询（启用配额时出现） |

### 客户端一次 NFS 挂载的全过程（文字步骤）
{: .sec-prac}

1. 客户端执行 `mount -t nfs 172.16.1.31:/data /mnt`。
2. 客户端内核向服务端 111 端口（rpcbind）查询：mountd 在哪个端口？
3. rpcbind 返回 mountd 的端口号。
4. 客户端连接 mountd，告知要挂载的路径 `/data`。
5. 服务端 mountd 检查 `/etc/exports`，确认该客户端 IP / 网段有权限，并读取导出参数（rw / ro、squash 等），返回一个"文件句柄"（file handle）。
6. 客户端内核把文件句柄与本地挂载点关联，之后对该挂载点的每次读写都通过 NFS 协议（程序号 100003）发给服务端 nfsd 处理。
7. 服务端 nfsd 把文件操作映射到本地磁盘文件系统，把结果返回客户端。
8. 卸载时同样通过 mountd 通知服务端，解除挂载关系。

### NFSv3 与 NFSv4 的差异

| 对比项 | NFSv3 | NFSv4 |
| --- | --- | --- |
| 挂载方式 | 需要 rpcbind + mountd 查询端口 | 挂载协议并入 NFS 协议，无需查询 rpcbind |
| 端口 | 多个随机端口，防火墙难配置 | 只要 2049 一个端口 |
| 状态 | 无状态协议，服务端不记录客户端状态 | 有状态协议，支持锁与租约 |
| 适用场景 | 兼容老客户端 | 新部署推荐，跨防火墙更友好 |

> **注意：** NFSv4 使用固定端口 2049；服务端通常仍启动 rpcbind 以兼容 NFSv3 客户端。指定版本用 `-o nfsvers=3` 或 `-o nfsvers=4`，纯 v4 环境防火墙只需放通 2049。
{: .sec-pit}

> **注意：** v4 下文件属主显示为 `nobody` 或数字 UID，多半是 idmapd 的域配置不一致（`/etc/idmapd.conf` 的 Domain 两端要相同）；这是 v4 时代的新坑，v3 没有这个问题。
{: .sec-pit}

{: .sec-know}

| 命令 | 作用 |
| --- | --- |
| `rpcinfo -p 172.16.1.31` | 查看服务端已注册的 RPC 程序与端口 |
| `rpcinfo -u 172.16.1.31 100005` | 以 UDP 测试 mountd 是否可达 |
| `ss -lntup \| grep 111` | 检查本机 111 端口监听（`netstat` 已废弃，建议用 `ss`） |

## NFS 服务部署流程
{: .sec-expl}

**RPC**：远程过程调用服务程序 —— 相当于租房的中介（网络编程支持）。

### 服务端部署

#### 第一个历程：下载安装软件

```bash
rpm -qa|grep -E "nfs|rpc"
yum install -y nfs-utils rpcbind
```

#### 第二个历程：编写 NFS 服务配置文件
{: .sec-expl}

```bash
vim /etc/exports (man exports)
```

配置文件格式：

```text
01     02(03)
```

| 部分 | 含义 |
| --- | --- |
| 01 | 设置数据存储的目录，如 `/data` |
| 02 | 设置网络白名单（允许哪些主机连接到存储服务器进行数据存储） |
| 03 | 配置存储目录的权限信息、存储目录的一些功能 |

```ini
/data   172.16.1.0/24(rw,sync)
```

#### 第三个历程：创建存储目录

```bash
mkdir /data
chown nfsnobody.nfsnobody /data
```

#### 第四个历程：启动服务程序

```bash
# 先启动 rpc 服务
systemctl start rpcbind.service
systemctl enable rpcbind.service

# 再启动 nfs 服务
systemctl start nfs
systemctl enable nfs
```

> **注意：** 启动顺序不能颠倒 —— 必须先启动 `rpcbind`，再启动 `nfs`，否则 NFS 的随机端口无法完成注册，客户端会挂载失败。
{: .sec-pit}

## NFS 服务工作原理
{: .sec-know}

### 服务端

1. 启动 rpc 服务，开启 111 端口
2. 启动 nfs 服务
3. 实现 nfs 服务进程和端口号的注册

### 客户端

1. 建立 TCP 网络连接
2. 客户端执行挂载命令，进行远程挂载
3. 可以实现数据远程传输存储

{: .sec-ver}

**没有注册的时候：**

```console
[root@nfs01 ~]# rpcinfo -p 172.16.1.31

 100000    2   tcp    111  portmapper
 100000    4   udp    111  portmapper
 100000    3   udp    111  portmapper
 100000    2   udp    111  portmapper
```

**NFS 服务注册之后的信息：**

```console
[root@nfs01 ~]# rpcinfo -p 172.16.1.31
program vers proto   port  service
 100000    4   tcp    111  portmapper
 100000    3   tcp    111  portmapper
 100000    2   tcp    111  portmapper
 100000    4   udp    111  portmapper
 100000    3   udp    111  portmapper
 100000    2   udp    111  portmapper
 100024    1   udp  53997  status
 100024    1   tcp  49863  status
 100005    1   udp  20048  mountd
 100005    1   tcp  20048  mountd

 100005    3   udp  20048  mountd
```

## NFS 服务端详细配置说明
{: .sec-expl}

### exports 文件逐字段详解
{: .sec-expl}

exports 每一行的完整格式为：`共享目录 客户端1(参数1) 客户端2(参数2)`。

| 字段 | 是否必填 | 说明 |
| --- | --- | --- |
| 共享目录 | 必填 | 服务端导出的目录，必须是绝对路径，如 `/data`；目录不必预先存在权限设置，但建议先创建好 |
| 客户端 | 必填 | 允许挂载的主机，可写多个，用空格分隔。支持：单个 IP `172.16.1.31`、网段 `172.16.1.0/24`、通配 `172.16.1.*`、主机名 `web01.example.com`、`*`（所有主机，危险，生产禁用） |
| 参数 | 可省 | 括号内的导出选项，多项用逗号分隔，不留空格；不写则使用编译默认值 |

> **注意：** 这里有个坑：exports 里目录与客户端之间用空格分隔，目录与括号参数之间不能有空格 —— `/data 172.16.1.0/24 (rw,sync)` 会把 `(rw,sync)` 当成第二个客户端，结果共享成只读默认权限。修改 `/etc/exports` 后必须执行 `exportfs -r` 或重启 nfs 服务才会生效；同一目录写多行时，客户端按最匹配的条目生效，建议保持"目录 - 客户端"清晰对应，避免歧义。
{: .sec-pit}

### 实现多个网段主机可以进行挂载

**第一种方法：**

```ini
/data   172.16.1.0/24(rw,sync) 10.0.0.0/24(rw,sync)
```

**第二种方法：**

```ini
/data   172.16.1.0/24(rw,sync)
/data   10.0.0.0/24(rw,sync)
```

### 共享目录的权限和哪些因素有关

1. 和**存储目录的本身权限**有关（755，属主：`nfsnobody`）
2. 和**配置文件中的权限配置**有关：`rw`/`ro`、各种 `xxx_squash`、`anonuid`/`anongid`
3. 和**客户端挂载命令的参数**有关，如 `ro`

这三处权限是叠加判定、缺一票否决：exports 参数先过第一道闸（`ro` 直接拒绝写，squash 决定身份映射）→ 映射后的 UID/GID 落到本地 ext4 文件系统再做一次常规 rwx 判定（目录 755 属主 nfsnobody，匿名用户走"其他用户"位）→ 客户端 mount 参数还能再收紧（挂成 `ro`，服务端 `rw` 也白搭）。排错就按这条链逐层查：`cat /var/lib/nfs/etab` 看生效参数，`ls -ld` 看目录权限，`mount` 看挂载参数。

### NFS 配置参数权限
{: .sec-expl}

| 参数 | 含义 |
| --- | --- |
| `rw` | 存储目录是否有读写权限 |
| `ro` | 存储目录是否是只读权限 |
| `sync` | 同步方式存储数据，直接将数据保存到磁盘（数据存储安全） |
| `async` | 异步方式存储数据，直接将数据保存到内存（提高数据存储效率） |
| `no_root_squash` | 不要将 root 用户身份进行转换 |
| `root_squash` | 将 root 用户身份进行转换 |
| `all_squash` | 将所有用户身份都进行转换 |
| `no_all_squash` | 不要将普通用户身份进行转换 |

**扩展导出参数（来自 man exports）：**

| 参数 | 含义 |
| --- | --- |
| `secure` | 只接受来自小于 1024 特权端口的请求（默认），防止普通用户伪造 NFS 请求 |
| `insecure` | 允许来自任意端口的请求，某些特殊客户端需要 |
| `subtree_check` | 检查请求的文件是否仍在导出目录子树内，更安全但影响性能 |
| `no_subtree_check` | 不做子树检查（默认），性能更好；文件不会跨导出目录移动时推荐 |
| `hide` | 导出目录下若还有子导出目录则不显示（默认） |
| `nohide` | 显示嵌套的导出目录 |
| `crossmnt` | 允许访问导出目录下已挂载的子文件系统 |
| `nocrossmnt` | 禁止跨越挂载点访问（默认） |
| `wdelay` | 延迟提交写请求，合并多个小写操作（默认） |
| `no_wdelay` | 立即提交写请求 |
| `anonuid=65534` | 指定被 squash 映射后的匿名用户 UID，默认 65534（nfsnobody） |
| `anongid=65534` | 指定被 squash 映射后的匿名组 GID，默认 65534 |
| `fsid=num` | 为导出目录指定唯一标识号，NFSv4 环境常用 `fsid=0` 指定根导出 |
| `sec=sys` | 使用本地 UID / GID 做身份校验（默认）；有 Kerberos 环境可用 `sec=krb5` 等 |

### 辨析：sync 与 async

- **sync**：每个写请求都等服务端落盘才返回。慢，但服务端断电最多丢正在写的那个请求
- **async**：写请求先在服务端内存排队，批量落盘。快数倍，但服务端宕机时内存里没落盘的数据全丢
- **怎么选**：生产上没有特殊理由一律 `sync`；`async` 只用于可丢、可重传的数据（如临时中转目录）。NFS 的 `sync` 已经比裸写快（服务端有聚合优化），先测性能再决定要不要冒险

### 操作演示：all_squash 参数功能
{: .sec-ex}

```ini
/data   172.16.1.0/24(ro,sync,all_squash)
```

```console
[ops@backup mnt]$ touch ops_data.txt
[ops@backup mnt]$ ll
total 4
-rw-rw-r-- 1 nfsnobody nfsnobody 0 May  9 12:11 ops_data.txt
```

可以看到，普通用户 `ops` 创建的文件，属主被转换成了 `nfsnobody`。

把权限链用白话串一遍：客户端用户先被 squash 规则"改名" —— `all_squash` 把所有人都改成匿名身份，`root_squash` 只改 root，`no_all_squash` 谁都不改；改完名落在 `anonuid`/`anongid` 指定的 UID/GID 上（默认 65534，即 nfsnobody）；服务端再拿这个 UID 对目录做一次普通 Linux 权限判定，过不了照样 Permission denied。所以 `all_squash + anonuid=1002` 的完整含义是：不管客户端是谁，到了服务端一律按 UID 1002 的身份、用 1002 的权限读写目录。

### 操作演示：no_all_squash 参数功能
{: .sec-ex}

```bash
[root@nfs01 ~]# vim /etc/exports
```

```ini
/data   172.16.1.0/24(rw,sync,no_all_squash)
```

```console
[ops@backup mnt]$ touch ops_data02.txt
touch: cannot touch 'ops_data02.txt': Permission denied
```

**解决权限问题：**

```bash
[root@nfs01 ~]# chmod o+w /data/
[root@nfs01 ~]# ll /data/ -d
drwxr-xrwx. 2 nfsnobody nfsnobody 52 May  9 12:11 /data/
```

```console
[ops@backup mnt]$ touch ops_data02.txt
[ops@backup mnt]$ ll
total 4
-rw-r--r-- 1 nfsnobody nfsnobody 7 May  9 10:57 backup_data.txt
-rw-rw-r-- 1 ops       ops       0 May  9 12:17 ops_data02.txt
-rw-rw-r-- 1 nfsnobody nfsnobody 0 May  9 12:11 ops_data.txt
```

加上 `o+w` 之后，普通用户保持自身身份创建文件成功。

### 操作演示：root_squash 参数功能
{: .sec-ex}

```ini
/data   172.16.1.0/24(rw,sync,root_squash)
```

```console
[root@backup mnt]# touch root_data.txt
[root@backup mnt]# ll
-rw-r--r-- 1 nfsnobody nfsnobody 0 May  9 12:20 root_data.txt
```

root 用户被转换成了 `nfsnobody`。

root_squash 为什么是默认值：NFS 默认信任客户端报上来的 UID，如果 root 身份原样透传，客户端 root 就等于服务端 root —— 一台客户端被攻破，存储服务器整个磁盘随它读写删。压成 nfsnobody 之后，客户端 root 只能碰匿名用户有权限的那点东西，破坏半径被摁在一个目录里。说白了这是安全兜底，想取消必须显式写 `no_root_squash`，写这个参数的人就得为后果负责。

### 操作演示：no_root_squash 参数功能
{: .sec-ex}

```console
[root@backup mnt]# ll
total 4
-rw-r--r-- 1 root      root      0 May  9 12:23 root_data02.txt
```

root 用户保持自身身份，创建的文件属主仍是 `root`。

### 企业互联网公司如何配置 NFS 各种 squash 参数
{: .sec-expl}

保证网站存储服务器用户数据安全性：

| 参数 | 是否需要配置 | 说明 |
| --- | --- | --- |
| `no_all_squash` | 需要进行配置 | 共享目录权限为 `www`（确保客户端用户与服务端用户的 uid 数值一致） |
| `root_squash` | 需要进行配置 | root → nfsnobody，data 目录属主 www |

> **注意：** 以上两项是默认配置，很多服务的默认配置都是从安全角度出发的。squash 映射的前提是客户端与服务端的 UID / GID 数值一致，否则会因"身份对不上"出现权限问题，批量环境建议用配置管理统一 UID。
{: .sec-pit}

> **注意：** "共享目录权限为 www"的标准动作：服务端 `useradd -u 1002 www` 建同名同 UID 用户，`chown -R www.www /data`，客户端同样建 UID 1002 的 www 用户跑 nginx —— 两端 UID 对上，权限链才通。
{: .sec-pit}

### 客户端 mount 命令参数
{: .sec-expl}

| 参数 | 含义 |
| --- | --- |
| `rw` | 实现挂载后挂载点目录可读可写（默认） |
| `ro` | 实现挂载后挂载点目录只读 |
| `suid` | 在共享目录中可以让 setuid 权限位生效（默认） |
| `nosuid` | 在共享目录中让 setuid 权限位失效，提供共享目录的安全性 |
| `exec` | 共享目录中的执行文件可以直接执行 |
| `noexec` | 共享目录中的执行文件无法直接执行，提供共享目录的安全性 |
| `auto` | 可以实现自动挂载，`mount -a` 实现加载 fstab 文件自动挂载 |
| `noauto` | 不可以实现自动挂载 |
| `nouser` | 禁止普通用户可以卸载挂载点 |
| `user` | 允许普通用户可以卸载挂载点 |

**NFS 专有挂载参数（排错与调优必知）：**

| 参数 | 含义 |
| --- | --- |
| `hard` | 硬挂载（默认）：服务端无响应时无限重试，直到恢复为止 |
| `soft` | 软挂载：重试 `timeo × retrans` 次后放弃，向调用进程返回错误 |
| `timeo=600` | 每次重试的超时时间，单位为 0.1 秒（默认 600，即 60 秒） |
| `retrans=3` | 重试次数（soft 挂载下累计超过后放弃） |
| `nfsvers=4` | 指定 NFS 协议版本，如 `nfsvers=3`、`nfsvers=4` |
| `_netdev` | 标记为网络设备，开机挂载时等待网络就绪后再挂（fstab 中配合使用） |
| `noatime` | 不更新访问时间，减少服务端写入量，提升读性能 |

```console
[ops@web01 ~]$ umount /mnt
umount: /mnt: umount failed: Operation not permitted
```

**软挂载与硬挂载的风险选择：**

| 类型 | 行为 | 风险 |
| --- | --- | --- |
| `hard`（默认） | 服务端失联时一直重试 | 访问挂载点的进程卡死在 I/O（D 状态），难以被杀掉，只能等服务恢复或 `umount -f` |
| `soft` | 超时后返回 I/O 错误 | 写操作可能已部分落盘却报失败，**有数据损坏风险**，数据库等关键业务禁用 soft |

> **注意：** 关键业务（数据库、邮件、财务数据）一律用默认 hard；只有在"程序不能被挂死"且数据可容忍重传的场景才考虑 soft，并调大 `timeo` 与 `retrans`。
{: .sec-pit}

> **注意：** 进程卡在 hard 挂载上是 D 状态，`kill -9` 都杀不掉，不要慌着重启服务器：`umount -lf` 解懒挂载，或等服务端恢复后进程自动继续。生产上先 `ps` 确认 D 状态、`dmesg` 看 NFS 超时日志，再决定动作。
{: .sec-pit}

### autofs 自动挂载

autofs（automount）的思路是"按需挂载"：挂载点平时不存在，第一次被访问时才真正触发挂载，闲置超过 `timeout` 后自动卸载。适合挂载点很多或 NFS 服务器不总在线的场景，避免开机全量挂载拖慢启动。

```bash
yum install -y autofs
systemctl start autofs
systemctl enable autofs
```

主配置文件 `/etc/auto.master`，格式为 `挂载点父目录 映射文件 --timeout 秒数`：

```ini
/nfs    /etc/auto.nfs    --timeout 60
```

映射文件 `/etc/auto.nfs`，格式为 `子目录名 -挂载选项 服务端:导出目录`：

```text
data    -rw,soft,timeo=60    172.16.1.31:/data
```

之后访问 `/nfs/data` 时 autofs 自动完成挂载，60 秒无人访问自动卸载。

> **注意：** autofs 与 fstab 开机挂载不冲突，可以组合使用：fstab 负责核心目录的开机挂载，autofs 负责低频访问目录的按需挂载。
{: .sec-pit}

> **注意：** autofs 还能做故障隔离：fstab 挂载在 NFS 服务端失联时可能拖慢开机甚至卡住启动，autofs 按需触发，服务端不在也只是访问时失败，不拦开机流程。核心目录要 fstab 保稳定，其余目录交给 autofs 更省心。
{: .sec-pit}

### 如何实现自动挂载

**方式一：利用 rc.local**

```bash
echo "mount -t nfs 172.16.1.31:/data /mnt" >>/etc/rc.local
```

**方式二：利用 fstab 文件**

```bash
vim /etc/fstab
```

```text
172.16.1.31:/data                         /mnt                    nfs     defaults        0 0
```

> **注意：** 使用 fstab 挂载网络存储时，需要确保有相应的特殊服务已经开启；建议给 nfs 条目加上 `_netdev`，表示等网络就绪后再挂载。
{: .sec-pit}

### 为什么网络存储服务无法自动挂载
{: .sec-know}

**CentOS 6：根据系统服务启动顺序**

```text
按照顺序依次启动：network 服务 --- sshd 服务 --- crond 服务 --- rsync 服务 --- rpcbind 服务 --- nfs 服务
先加载 /etc/fstab  ---  network 服务  --- autofs 服务
```

`autofs` 服务程序开机自动启动，服务启动好之后，会重新加载 fstab。

**CentOS 7：根据系统服务启动顺序**

```text
network 服务
sshd 服务
crond 服务
rsync 服务
先加载 /etc/fstab  network 服务
```

> **注意：** 在 CentOS 7 上，要让 fstab 中的 NFS 条目生效，必须让 `remote-fs.target` 服务开机自启；在 CentOS 6 上对应的是 `netfs` 服务。执行 `systemctl enable remote-fs.target` 后，开机才会按 fstab 挂载网络文件系统。
{: .sec-pit}

## NFS 性能与安全

### 性能要点
{: .sec-sum}

1. `sync` 与 `async` 是一对权衡：`sync` 每次写都落盘，安全但慢；`async` 先写内存，快但服务端宕机会丢数据。生产根据数据重要性选择，不要无脑 async。
2. 现代内核 NFSv4 走 TCP、默认较大的读写块（rsize / wsize），大数据量吞吐明显好于 v3 + UDP。
3. 读多写少、且不需要 atime 统计时，挂载加 `noatime` 减少服务端元数据写。
4. `no_subtree_check`（默认）比 `subtree_check` 性能好，确认文件不会跨导出目录移动时保持默认。
5. NFS 本质是单点共享，海量小文件高并发场景吞吐有限，门户网站规模应规划分布式存储（GlusterFS、FastDFS 等）。

### 安全要点
{: .sec-sum}

1. 最小导出原则：只导出必要目录、只开放给必要网段，禁用 `*`。
2. 除非特殊需求，不要开 `no_root_squash`：它会让客户端 root 直接等于服务端 root，一台客户端被攻破就等于存储服务器沦陷。
3. 对外共享目录用 `all_squash` + `anonuid` / `anongid` 固定映射到一个低权限用户。
4. 防火墙只对信任网段开放 111、2049 以及 mountd / status 端口。
5. NFS 流量走内网，不把 NFS 服务暴露到公网。
6. 有 Kerberos（AD / LDAP）环境时可用 `sec=krb5` 做强认证，替代默认的 `sec=sys`。

> **注意：** NFS 单点的过渡方案：小规模用 keepalived + 双机热备；数据量再往上，直接迁分布式存储或对象存储。NFS 至今仍广泛使用，靠的就是它在"中小规模、内网、普通读写"这个区间里最省心。
{: .sec-pit}

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `mount.nfs: Connection timed out` | 服务不通：rpcbind / nfs 未启动、IP 错误、防火墙拦截 | `ping 172.16.1.31`；`telnet 172.16.1.31 111`；`rpcinfo -p 172.16.1.31` | 按顺序启动 rpcbind 与 nfs-server；防火墙放通 111 / 2049 |
| `mount.nfs: access denied by server while mounting` | 客户端 IP / 网段不在 exports 允许范围 | `showmount -e 172.16.1.31` | 修改 `/etc/exports` 添加该网段，执行 `exportfs -r` |
| `mount.nfs: Stale file handle` | 服务端导出目录被删除或重建、导出项变化、服务端重启后句柄失效 | `showmount -e 172.16.1.31`；`dmesg \| tail` | 客户端 `umount -lf /mnt` 后重新挂载 |
| `rpcinfo: can't contact rpcbind` 或 `RPC: Unable to receive` | rpcbind 未启动或被防火墙拦截 | `systemctl status rpcbind`；`ss -lntup \| grep 111` | 先启动 rpcbind，再启动 nfs |
| 挂载成功但 `touch` 报 `Permission denied` | squash 映射后身份变成 nfsnobody，目录权限不足 | `ls -ld /data`；`id` | 给目录授权（`chmod o+w` 或改属主），或调整 `anonuid` / `anongid` |
| 开机后 NFS 没有自动挂载 | `remote-fs.target`（CentOS 7+）/ `netfs`（CentOS 6）未启用 | `systemctl status remote-fs.target` | `systemctl enable remote-fs.target`，fstab 加 `_netdev` |
| 服务重启后挂载点操作变慢 | 使用了 `restart` 强制断开所有连接 | — | 改用 `systemctl reload nfs-server` 平滑重载 |

> **注意：** `Stale file handle` 多发生在"删了导出目录又重建"之后：服务端句柄基于 inode，目录重建后 inode 变了，客户端手里的旧句柄全部失效。规范做法是清空目录内容而不是删目录本身。
{: .sec-pit}

## 小结
{: .sec-sum}

1. NFS 用于 Linux 之间共享目录；中小型企业可用 FTP / samba / NFS，门户网站规模则要上分布式存储（Moosefs、GlusterFS、FastDFS）。
2. 部署顺序不可颠倒：先 `rpcbind` 后 `nfs`；`/etc/exports` 格式为 `目录 网段(权限参数)`，共享目录属主设为 `nfsnobody`。
3. RPC 相当于中介，NFS 启动后把随机端口注册到 RPC 的 111 端口上，用 `rpcinfo -p` 能看到 `mountd` / `status` 才算注册成功。
4. 共享目录最终权限由三处共同决定：目录自身权限（755 + 属主）、exports 中的 `rw`/`ro` 与 squash 配置、客户端 mount 参数。
5. squash 系列决定身份映射：`root_squash`（root → nfsnobody）、`no_root_squash`（保留 root）、`all_squash`（所有用户 → nfsnobody）、`no_all_squash`（保留普通用户身份）；用 `anonuid`/`anongid` 可以指定映射目标用户。
6. 开机自动挂载可用 `/etc/rc.local` 或 `/etc/fstab`，但 fstab 方式必须依赖 `remote-fs.target`（CentOS 7）/ `netfs`（CentOS 6）；卸载不掉时用 `umount -lf`。
7. 修改 exports 后用 `exportfs -r` 生效；客户端挂载前先用 `showmount -e` 确认导出清单。
8. 软挂载（soft）有数据损坏风险，关键业务用默认 hard；大目录、多挂载点场景可用 autofs 按需挂载。

4. 硬挂载（hard）在服务端宕机时会出现什么现象？为什么数据库不用软挂载（soft）？
5. fstab 方式自动挂载 NFS 失败，最可能忘记启用哪个服务？

> **答案：** 1. 111 端口是 rpcbind（portmapper）的固定端口，NFS 的 mountd 等进程使用随机端口，客户端必须先到 rpcbind 查询端口号才能建立后续连接。2. `all_squash` 把所有用户（含普通用户）映射为匿名用户 nfsnobody，文件属主显示为 nfsnobody；`no_all_squash` 保留普通用户自身身份，文件属主仍是原用户。3. `exportfs -r` 只重新读取 exports 并刷新导出表，不断开已有连接；重启服务会强制断开所有客户端连接。4. hard 挂载会无限重试，访问挂载点的进程卡死在 I/O（D 状态）难以杀死；soft 重试超时后会返回错误，但写操作可能已部分落盘却报告失败，导致数据不一致，所以数据库等关键业务禁用 soft。5. CentOS 7 及以上是 `remote-fs.target`（CentOS 6 是 `netfs`），未启用则开机不挂载 fstab 中的网络文件系统。
