## 项目环境准备
{: .sec-expl}

三台服务器准备完毕：`web01`、`nfs01`、`backup`。开工前先确认三台机器之间 `/etc/hosts` 互通、rsync 客户端密码文件就位，这两件事没就绪，后面每一步都会卡。

### 全网备份完整架构
{: .sec-expl}

项目拓扑用文字描述如下：

- **backup 服务器（172.16.1.41）**：全网唯一的备份汇聚点，运行 rsync 守护进程（873 端口），下设 `/backup` 备份存储目录，按被备份机的 IP 分子目录存放数据；同时承担日志统一保存与校验告警职责
- **web01（172.16.1.7）**：web 服务器，备份站点目录 `/var/html/www` 与访问日志 `/app/logs`
- **db01（172.16.1.51）**：数据库服务器，备份数据库目录、慢日志与配置文件（可配合定时导出 SQL）
- **nfs01（172.16.1.31）**：存储服务器，备份共享数据与系统配置
- **其余被备份机**：按同一套脚本模板加入，目录名用各自内网 IP 区分

数据流向：各被备份机在本地 `/backup` 打包 → 通过 rsync 推送到 backup 服务器的 `backup` 模块 → backup 服务器按 IP 目录归档、定期校验并邮件通知管理员。所有传输走内网（172.16.1.0/24），对外只暴露必要服务端口。

> **注意：** 为什么每台被备份机本地也要有 `/backup`：打包需要临时落盘空间，本地留存最近几天的副本还能在 backup 服务器故障时应急恢复。本地留存设上限（本项目 7 天），防止把业务磁盘写满。
{: .sec-pit}

> **注意：** backup 服务器自身是整个体系的单点：它挂了，所有客户端的备份都堆在本地 `/backup` 等着。所以 backup 的磁盘容量要按"单日全量 × 台数 × 留存周期"预留，监控要覆盖它的磁盘使用率，它的配置与指纹索引也要有自己的一份备份。
{: .sec-pit}

## 项目需求拆解

| 编号 | 需求 | 落地主机 |
| --- | --- | --- |
| 1 | 所有服务器的备份目录必须都为 `/backup` | web01 nfs01 backup |
| 2 | 要备份的系统配置文件包括但不限于：a 定时任务服务的配置文件 `/var/spool/cron/root`（适合 web 和 nfs 服务器）；b 开机自启动的配置文件 `/etc/rc.local`（适合 web 和 nfs 服务器）；c 日常脚本的目录 `/server/scripts`；d 防火墙 iptables 的配置文件 `/etc/sysconfig/iptables`；e 自己思考下还有什么需要备份 | web01 nfs01 |
| 3 | Web 服务器站点目录假定为 `/var/html/www` | web01 |
| 4 | Web 服务器访问日志路径假定为 `/app/logs` | web01 |
| 5 | Web 服务器保留打包后的 7 天的备份数据即可（本地留存不能多于 7 天，因为太多硬盘会满） | web01 nfs01 |
| 6 | 备份服务器上，保留每周一的所有数据副本，其它要保留 6 个月的数据副本 | backup |
| 7 | 备份服务器上要按照备份数据服务器的内网 IP 为目录保存备份，备份的文件按照时间名字保存 | backup |
| 8 | 需要确保备份的数据尽量完整正确，在备份服务器上对备份的数据进行检查，把备份的成功及失败结果信息发给系统管理员邮箱中 | backup |

> **注意：** 8 条需求里最有"运维味"的是第 5、6、8 条：5 和 6 定义留存策略，8 定义质量闭环。前三条是"备什么"，这三条是"备到什么程度才算合格" —— 复述需求时把这三条讲清楚就赢了大半。
{: .sec-pit}

### 需求分析要点
{: .sec-sum}

把需求翻译成可执行的设计决策：

1. **统一 `/backup` 目录**：所有机器一个路径，脚本不用按机器写死不同位置，批量下发时也只有一个变量
2. **配置类数据用 tar 打包、按日期命名**：零散小文件打包成一个包，既减少 inode 压力，也让"哪天坏了恢复哪天"变得简单
3. **站点与日志分开打包**：站点恢复频率低、体积大；日志恢复更频繁但可以只捞某几天，分开打包避免每次恢复都拖出整个站点
4. **本地 7 天 + 服务端 6 个月的双层留存**：本地兜近期，服务端兜长期；周一数据单独保留，作为每周的"黄金快照"
5. **文件名带 IP + 时间 + 周几**：`内网IP/日期_weekN` 的命名让目录自解释，不依赖额外索引就能找到任何一台机器任何一天的数据
6. **md5 指纹 + 邮件**：备份最常见的故障不是"没传"而是"传坏了"，指纹校验 + 主动告警把"静默失败"变成"当天知道"

> **注意：** 除需求列出的文件外，通常还应纳入备份清单：`/etc/hosts`（主机名映射）、网卡配置文件 `ifcfg-*`、`/etc/fstab`（挂载关系）、`/var/spool/cron/*`（所有用户的定时任务）、服务自身配置（nginx.conf、my.cnf）。原则是："重装系统后，凭备份能把环境恢复到 90% 以上"。
{: .sec-pit}

> **注意：** 上线前先算两笔账：一笔是容量账 —— 单日全量包多大 × 客户端台数 ×（7 天本地 + 180 天服务端）+ 周一快照累积，得出 `/backup` 分区该给多大，再乘 1.5 的冗余系数；一笔是窗口账 —— 打包加推送的耗时必须明显小于夜间窗口，不够就得按机器错峰或改增量。
{: .sec-pit}

## 部署全过程

按顺序把整个项目搭起来，每一步都可验证：

1. **规划三台机器的 IP 与主机名**：web01（172.16.1.7）、nfs01（172.16.1.31）、backup（172.16.1.41），各机器 `/etc/hosts` 互相写好映射
2. **backup 服务器部署 rsync 守护进程**：装 rsync → 写 `/etc/rsyncd.conf`（uid/gid = rsync、认证用户 rsync_backup、`hosts allow = 172.16.1.0/24`）→ 建虚拟用户与密码文件（600）→ `mkdir /backup && chown rsync.rsync /backup` → `systemctl start rsyncd && systemctl enable rsyncd`
3. **验证服务端**：`ss -lntp | grep 873` 确认监听；在 web01 上执行一次手动推送，确认能连通、能认证
4. **各被备份机准备客户端**：写只含密码的 `/etc/rsync.password`（权限 600），执行免交互推送测试
5. **准备备份目录**：每台被备份机 `mkdir -p /backup/<本机内网IP>/`；服务端模块路径下由首次推送自动创建一级 IP 目录
6. **编写备份脚本**：客户端 `backup.sh`、服务端 `backup_server.sh`，放在 `/server/scripts/`，用 `sh -x` 逐行测试
7. **配置定时任务**：客户端每天 00:00 备份，服务端每天 05:00 校验，两时段错开
8. **验证全链路**：连续跑两天，检查服务端目录结构、指纹文件、邮件是否收到
9. **做一次恢复演练**：挑一天的备份包，在测试环境解包验证可用性（见下文「恢复演练的重要性」）

> **注意：** 第 3、8 步的验证不能省：备份系统的故障是"静默"的 —— 密码过期、磁盘写满、认证失败，脚本照常跑、定时任务照常"成功"，只有主动验证才能发现。建议把"每周抽查一次备份文件是否存在且大小正常"写进运维例行工作。
{: .sec-pit}

> **注意：** 生产上栽过的典型一幕：备份系统"一切正常"跑了半年，真出事要恢复时发现密码三个月前改过、脚本一直静默失败，最新可用备份停留在半年前。防的就是这个：备份结果必须每天有反馈，连续成功的也要偶尔抽查。
{: .sec-pit}

## 备份客户端要完成的工作

以 `nfs01`（内网 IP `10.0.0.31`）为例：

```bash
# 1. 创建以本机内网 IP 命名的备份目录
mkdir -p /backup/10.0.0.31/
# -p 递归创建父目录，且目录已存在时不会报错，脚本里可以放心重复执行

# 2. 打包系统配置文件（注意用 cd / 配合相对路径，避免 tar 报 "Removing leading /"）
cd /
tar zchf /backup/system_backup_$(date +%F_week%w).tar.gz ./var/spool/cron/root ./etc/rc.local ./server/scripts ./etc/sysconfig/iptables
# z=gzip 压缩、c=创建归档、h=跟随软链接打包真实文件、f=指定输出包名
# $(date +%F_week%w) 把日期和周几写进文件名：%w 中 0 表示周日、1 表示周一

# 3. 打包站点目录与访问日志（web01 上执行）
tar zchf /backup/www_backup_$(date +%F_week%w).tar.gz  ./var/html/www
tar zchf /backup/www_log_backup_$(date +%F_week%w).tar.gz  ./app/logs
# 站点与日志分开打包：日志增长快，恢复时只需捞特定几天的包

# 4. 清理本地 7 天前的备份数据
find /backup -type f -mtime +7|xargs rm
# -type f 只处理普通文件；-mtime +7 表示修改时间超过 7 天（整数向上取整，实际是 ≥8 天）
# xargs 前的管道别写成 find -exec rm {} \;，性能差距很大；文件名为空时 xargs 会执行一次空命令

# 5. 为当天新增的备份文件生成指纹文件
find /backup/ -type f -mtime -1 ! -name "finger*"|xargs md5sum >/backup/10.0.0.31/finger.txt
# ! -name "finger*" 排除指纹文件自身，否则下一轮会把自己的指纹也算进去
# md5sum 输出的是"路径 + 哈希"，路径写绝对路径，服务端才能原样校验

# 6. 推送到备份服务器
rsync -avz /backup/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
# -a 归档模式（保留权限属主等属性）、-v 显示过程、-z 传输时压缩
# --password-file 指向只含口令的 600 权限文件，否则 rsync 拒绝使用
```

> **注意：** 需求 7 要求"按内网 IP 为目录保存"，本机的内网 IP 是 172.16.1.31；示例命令沿用了课堂环境里的 `10.0.0.31` 目录名，落地时把 IP 换成机器实际的 172.16.1.x 地址即可 —— 关键是"目录名 = 该机唯一 IP"这条规则要统一，不要一台机器一个习惯。
{: .sec-pit}

### 补充：tar 命令用法
{: .sec-ext}

```text
-h, --dereference    follow symlinks; archive and dump the files they point to
                     将链接文件所指向的原文件进行保存备份
```

> **注意：** 这里有个坑：`tar zchf` 中的 `-h` 是关键 —— 不加 `-h` 时打包的是软链接本身，还原后可能指向不存在的路径。
{: .sec-pit}

> **注意：** `cd /` 之后用 `./var/spool/cron/root` 这样的相对路径打包，可以避免 tar 输出 "Removing leading `` `/' ``" 警告，同时让包内路径以 `.` 开头，解包时不会覆盖系统绝对路径，更安全。
{: .sec-pit}

## 备份服务端要完成的工作

```bash
# 1. 清理 6 个月（180 天）以前的数据，但保留所有周一的数据副本
find /backup/ -type f -mtime +180 ! -name "*week1.tar.gz"
# ! -name 把文件名含 week1 的包排除在删除范围外，保留策略靠文件名而不是额外状态表

# 2. 校验各客户端上传的指纹文件
find /backup/ -type f -name "finger.txt"|xargs md5sum -c >/tmp/check.txt
# -c 逐条比对，指纹里记的是"路径 + 哈希"，路径必须与服务端当前目录对得上
# 输出重定向到文件：后续既能发邮件也能留档，避免校验一次刷一次屏

# 3. 把校验结果发送给系统管理员
mail -s "邮件测试" admin@example.com </tmp/check.txt
# -s 是邮件主题；< 表示把文件内容当正文读进来
```

> **注意：** 第 1 步的 `find` 只做了查找，实际删除需要接 `-delete` 或 `|xargs rm`，执行前务必先确认查找结果是否正确。清理类 find 命令的标准流程是三段式：先裸跑看清单 → 加 `-delete` 前用 `-print` 复核 → 最后才真正删除，直接上删除是清理事故的第一大来源。
{: .sec-pit}

> **注意：** 指纹文件里记录的是客户端打包后、推送前的 md5；服务端对收到的文件重算 md5 再比对，一致说明传输过程没损坏。注意 `md5sum -c` 是按指纹文件里**记录的路径**逐条校验的：本项目客户端用 `find /backup/` 生成指纹，记录的是绝对路径，而推送保持了相同目录结构，所以服务端直接 `md5sum -c` 即可命中；如果脚本改成"先 cd 进备份目录再生成指纹"（相对路径），服务端也必须 cd 到同一目录再校验，否则会报 failed。
{: .sec-pit}

> **注意：** 指纹文件自身要不要校验？它不校验自己 —— `find` 生成指纹时用 `! -name "finger*"` 把自己排除了。这是刻意的：指纹的职责是证明"别的文件没坏"，它自己坏了重生成一份即可，不构成数据风险。
{: .sec-pit}

## 关键设计说明
{: .sec-expl}

### 01. 保留周一数据的方法

- **方式 a**：在数据名称信息上加上周的信息，即 `$(date +%F_week%w)` 生成 `2019-05-06_week1` 这样的名字，然后：

  ```bash
  find /backup/ -type f -mtime +180 ! -name "*week1.tar.gz"
  ```

- **方式 b**：在服务端进行检查，将每周一传输的数据进行单独保存

> **注意：** 方式 a 把" retention 策略"编码进文件名，清理逻辑只是 `find + ! -name`，无状态、可重复执行，是两种方式中更稳的；方式 b 需要在服务端维护额外的拷贝动作，多一步就多一个故障点。项目采用方式 a。
{: .sec-pit}

### 02. 如何验证数据完整性
{: .sec-ver}

利用 md5 算法进行验证数据完整性。

校验要分层看：md5 回答的是"传输过程没损坏"，回答不了"备份本身是不是好的"。完整思路三层递进：

1. **传输层**：md5sum -c 指纹比对，确认包在网络上没坏
2. **可用层**：定期抽样 `tar tzf` 列包内清单，更进一步解包到测试机、起服务验数据
3. **恢复层**：按季度走整机恢复演练，验证"从零到业务恢复"的全流程

打包那一步就出错（比如 tar 了错误的目录）的情况，md5 全部 ok 也发现不了，只有第 2、3 层能兜住。

`md5sum -c` 指纹文件命令的执行原理：

1. **第一个历程**：打开一个指纹文件，将信息记录到缓存中
2. **第二个历程**：根据指纹文件的路径信息，生成 md5 数值信息
3. **第三个历程**：将新生成 md5 数值和原有指纹文件中的数值进行比较
4. **第四个历程**：如果相同显示结果为 `ok`，如果不同显示 `failed`

> **注意：** md5 用于校验"传输损坏"足够，但若防范恶意篡改需要 SHA-256 等更强算法；对备份系统而言，威胁模型主要是链路损坏与磁盘故障，md5 是行业惯例，性价比最高。另外 md5 逐条校验大量文件时有 IO 放大，凌晨校验窗口紧张的话，可以只校验当天新增的指纹文件，全量校验放每周一次。
{: .sec-pit}

### 03. 如何实现发送邮件

**a. 配置邮箱客户端授权码**

在邮箱设置中开启 SMTP 服务并获取客户端授权码（授权码不是登录密码，且只显示一次，需妥善保存）。

**b. 编写 Linux 服务邮件相关配置文件**

```bash
vim /etc/mail.rc
```

```conf
set from=yourname@example.com smtp=smtp.example.com
set smtp-auth-user=yourname@example.com smtp-auth-password=<your-auth-code> smtp-auth=login
```

```bash
systemctl restart postfix.service
```

**c. 发送邮件测试**

```bash
echo "邮件发送测试"|mail -s "邮件测试" admin@example.com
mail -s "邮件测试" admin@example.com </etc/hosts
```

> **注意：** `smtp-auth-password` 填的是邮箱的**客户端授权码**，不是登录密码；示例中的邮箱地址与收件地址请替换成自己的。
{: .sec-pit}

> **注意：** `/etc/mail.rc` 中含明文授权码，权限应收紧（`chmod 600`）；更安全的做法是把发信职能交给监控系统或专用告警通道，备份服务器只负责产出结果文件。邮件收不到时先查 `mailq` 队列与 postfix 日志 `/var/log/maillog`。
{: .sec-pit}

> **注意：** 告警要防两个极端：天天"备份成功"的邮件没人看，真失败时也一起被忽略（狼来了效应）。所以成功邮件降级为每日一封汇总，失败邮件立刻发并走 IM 强提醒，两种通道分开。
{: .sec-pit}

## 原理解析：全量与增量备份策略
{: .sec-know}

备份策略要在"恢复粒度、存储成本、执行窗口"之间权衡，本项目的组合是：

| 策略 | 在本项目的体现 | 优点 | 代价 |
| --- | --- | --- | --- |
| 全量备份 | 每天 tar 打包一份完整数据；周一的数据长期保留 | 恢复简单，一份包就是完整状态 | 占用空间大，备份窗口长 |
| 增量备份 | rsync 只传变化块（delta 算法），未变文件跳过 | 传输快、占用小 | 依赖上次备份链，中间任一环节损坏则恢复不完整 |
| 差异 / 快照 | 每周一的副本固定保留 180 天 | 提供周级回滚点 | 比纯增量占更多空间 |

调度上的三个原则：

1. **备份窗口避开业务高峰**：本项目选凌晨 00:00，此时写入量最低
2. **保留策略分层**：本地 7 天（快速恢复）→ 服务端 6 个月（长期追溯）→ 周一快照长期保留（周级回滚）
3. **先打包再传输**：tar 打包把大量小文件合成一个流，既提升传输效率，也让 rsync 的增量判断更可靠

> **注意：** 纯增量链的最大风险是"断链"：周一全量 + 之后每天增量，若周三的增量包损坏，就只能恢复到周二。缓解办法就是本项目保留周一快照的设计 —— 每周都有一个独立完整的回滚点，最多丢一周内的增量。
{: .sec-pit}

### 辨析：增量与差异

- **增量**：相对上一次备份（不管它是全量还是增量），只备变化的部分。备份最快、占空间最小，但恢复依赖整条备份链，链上任何一环损坏都不完整
- **差异**：相对最近一次全量，只备全量之后的变化。备份比增量慢、占空间更多，但恢复只要"全量 + 最近一次差异"两份，链路短、出问题的环节少
- **取舍经验**：数据量小、备份窗口够，直接每天全量最省心；数据量大到全量跑不完窗口，用"每周全量 + 每日差异"起步，链路简单优先于空间节省

## 3-2-1 备份原则与异地备份

业界公认的备份黄金法则是 **3-2-1 原则**：

- **3 份数据**：1 份生产数据 + 至少 2 份备份
- **2 种介质**：备份存放在两种不同介质上（如服务器磁盘 + 对象存储 / 磁带），避免单一介质集体故障
- **1 份异地**：至少 1 份备份放在异地，防火防盗防机房级灾难

对照本项目：各被备份机本地留存 7 天 = 第 2 份；backup 服务器集中保存 6 个月 = 第 3 份。要凑齐完整的 3-2-1，还差"异地"这一步：

- **异地机房互备**：backup 服务器与异地机房的备份服务器之间再跑一次 rsync（用 `--bwlimit` 限速，走专线或 VPN）
- **公有云对象存储**：把周一快照等关键副本同步到云厂商的对象存储，天然异地 + 多副本
- **加密后外传**：异地传输前先加密（如用 openssl 或 restic / borg 类工具打包加密），防止备份在半路泄露

> **注意：** 面试高频题"备份和容灾的区别"：备份解决"数据丢了能找回来"（RPO 视角，允许一定时间的数据丢失），容灾解决"机房没了业务还能跑"（RTO 视角，要求分钟 / 小时级切换）。全网备份项目只是备份，再往上才是两地三中心级别的容灾。
{: .sec-pit}

> **注意：** "2 种介质"里最容易被忽略的是对象存储：它自带多副本与防误删（版本控制、合规锁），中小企业直接把周一快照同步到对象存储，一次性补齐"介质"与"异地"两条。
{: .sec-pit}

## 恢复演练的重要性
{: .sec-prac}

> 备份的终点不是"传完"，而是"能恢复"。

恢复演练要成为制度，原因有三：

1. **备份可能是坏的**：传一半网络断了、磁盘坏道、权限丢失，都会让备份"存在但不可用"，只有真正解包 / 挂载验证过才知道
2. **恢复操作本身会生疏**：事故发生时再翻文档找命令，每一分钟都是业务损失；平时演练过，恢复就是肌肉记忆
3. **能算出真实的 RTO / RPO**：演练时记录"从故障到恢复用了多久、丢了哪段时间的数据"，这两个数字是向上汇报和买设备的依据

最低限度的演练要求：

- **每月一次抽样恢复**：随机抽一台机器一天的备份，在测试环境解包、起服务、比对数据
- **每季度一次全流程演练**：模拟某台机器整机故障，走"装系统 → 恢复配置 → 恢复数据 → 服务上线"全流程
- **演练结果记录在案**：用时、问题、改进项，形成闭环

演练记录至少包含：演练日期、抽中的机器与日期、恢复耗时、发现的问题、改进项与责任人。这份记录也是给管理层看的"备份体系健康证明"。

> **注意：** 一次没演练过的备份系统，等于没有备份。这句话是数据安全领域的共识，也是备份项目从"能做"到"敢用"的分界线。
{: .sec-pit}

## 编写全网备份脚本

把上面的命令固化为脚本，客户端脚本放在 `/server/scripts/backup.sh`，服务端脚本放在 `/server/scripts/backup_server.sh`。

```bash
#!/bin/bash
# 备份客户端脚本示例：按前文命令整理

mkdir -p /backup/10.0.0.31/

cd /
# 先切到根目录，再用 ./ 开头的相对路径打包，包内结构才不会带绝对路径
tar zchf /backup/system_backup_$(date +%F_week%w).tar.gz ./var/spool/cron/root ./etc/rc.local ./server/scripts ./etc/sysconfig/iptables
tar zchf /backup/www_backup_$(date +%F_week%w).tar.gz  ./var/html/www
tar zchf /backup/www_log_backup_$(date +%F_week%w).tar.gz  ./app/logs

find /backup -type f -mtime +7|xargs rm
# 清理放在推送之前还是之后，是这套脚本最需要守住的顺序：先清理再推送，
# 一旦推送失败，数据既没上传成功本地又已被删，结果是两头空

find /backup/ -type f -mtime -1 ! -name "finger*"|xargs md5sum >/backup/10.0.0.31/finger.txt

rsync -avz /backup/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
# 末尾不要漏 2>&1，否则 rsync 的错误信息只留在屏幕上，cron 里完全看不到
```

> **注意：** 原始课堂笔记此处客户端脚本与服务端脚本均标注为"省略"，上面是按前文命令整理的版本，落地时还需要补充变量（如本机 IP）、日志与错误处理。
{: .sec-pit}

生产化改造版（客户端）：把 IP、路径抽成变量，加锁防止重复执行，加日志便于追溯：

```bash
#!/bin/bash
# 全网备份客户端脚本（生产化改造版）
IP=$(ip -4 addr show eth1 | awk '/inet /{print $2}' | cut -d/ -f1)
# ip -4 addr show eth1 只看指定网卡的 IPv4；awk 取出 "inet 地址/掩码" 的第二列
# cut -d/ -f1 再把掩码截掉，多网卡或网卡名不同的地方要改这里
BAK_DIR=/backup/$IP
LOG=/var/log/backup_client.log

# 加锁：防止上一次备份没跑完又启动一次
exec 3>/var/run/backup_client.lock
flock -n 3 || { echo "$(date) 上一次备份仍在运行，退出" >>$LOG; exit 1; }
# 3 是文件描述符编号，锁挂在这个描述符上；-n 表示抢不到锁立刻返回而不是等待

echo "===== $(date) backup start =====" >>$LOG
mkdir -p $BAK_DIR

cd /
tar zchf $BAK_DIR/system_backup_$(date +%F_week%w).tar.gz ./var/spool/cron/root ./etc/rc.local ./server/scripts ./etc/sysconfig/iptables && echo "system tar ok" >>$LOG || echo "system tar FAILED" >>$LOG
tar zchf $BAK_DIR/www_backup_$(date +%F_week%w).tar.gz ./var/html/www && echo "www tar ok" >>$LOG || echo "www tar FAILED" >>$LOG
tar zchf $BAK_DIR/www_log_backup_$(date +%F_week%w).tar.gz ./app/logs && echo "log tar ok" >>$LOG || echo "log tar FAILED" >>$LOG

find /backup -type f -mtime +7 | xargs rm
# && 与 || 只负责记录成败，不会中断脚本：某一步失败后后面的步骤仍会继续执行
# 关键步骤失败要主动 exit，否则会出现"日志说成功、实际缺包"的情况

find $BAK_DIR -type f -mtime -1 ! -name "finger*" | xargs md5sum >$BAK_DIR/finger.txt
# 指纹只覆盖本机目录，推送后服务端按同一路径结构校验

rsync -avz /backup/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password && echo "rsync ok" >>$LOG || echo "rsync FAILED" >>$LOG
# 推送整个 /backup 目录，服务端会按 IP 子目录归档
echo "===== $(date) backup end =====" >>$LOG
```

生产化改造版（服务端校验与清理）：

```bash
#!/bin/bash
# 备份服务端校验脚本（生产化改造版）
LOG=/var/log/backup_server.log
CHECK=/tmp/check_$(date +%F).txt
# 校验结果按日期落到独立文件，重跑同一天会覆盖而不是追加，便于分辨当天结果

# 清理 180 天前的数据，保留周一快照
find /backup/ -type f -mtime +180 ! -name "*week1.tar.gz" | xargs rm
# 清理同样靠文件名里的 week1 排除周一数据，与客户端的命名规则严格对应

# 逐目录校验指纹，失败的行单独统计
FAIL=0
for f in $(find /backup/ -type f -name "finger.txt"); do
  DIR=$(dirname $f)
  # 先 cd 到指纹所在目录再校验，指纹里记的路径才能被正确解析
  cd $DIR && md5sum -c $f >>$CHECK 2>&1
done
# grep -c FAILED 统计失败行数，无匹配时返回码非 0，所以后面还要 && FAIL=1
grep -c FAILED $CHECK >/dev/null 2>&1 && FAIL=1

if [ $FAIL -eq 1 ]; then
  echo "backup check FAILED, detail in attachment" | mail -s "备份校验失败 $(date +%F)" admin@example.com
else
  echo "backup check OK" | mail -s "备份校验成功 $(date +%F)" admin@example.com
fi
mail -s "备份校验明细 $(date +%F)" admin@example.com <$CHECK
# 明细单独作为附件正文发送，正文里的提示语要写清结果与明细在哪
echo "$(date) check done, fail=$FAIL" >>$LOG
```

> **注意：** 改造版新增了四个生产必备要素：① 用 `flock` 加锁防止任务重叠执行；② 每步 `&&` / `||` 记录成败，失败可追溯；③ 客户端 IP 从网卡动态获取，脚本可原样下发到所有机器；④ 校验结果按成败分别发不同主题的邮件，收件人看主题就能判断状态。
{: .sec-pit}

> **注意：** 日志与锁不是锦上添花。没有锁，某天数据量暴涨把备份窗口拖长，撞上下一次 crontab 触发，两个实例同时打包、同时推送，轻则浪费资源，重则指纹文件互相覆盖、校验结果全乱；没有日志，输出又被 `&>/dev/null` 吞掉，事后连"昨晚到底跑没跑、断在哪一步"都答不上来。日志最低要求三条：起止时间、每步成败、rsync 退出码。
{: .sec-pit}

### 测试检验脚本的方法
{: .sec-ver}

```bash
sh -x 脚本信息
```

> **注意：** `sh -x` 会把每条命令及展开后的变量值打印出来，是排查脚本"哪一步出错、变量拿到什么值"的第一工具，敲一遍就明白脚本的执行路径；`bash -n 脚本` 只做语法检查不执行，适合快速排查括号、引号配对问题。

## 实现自动完成全网数据备份（定时任务）

客户端定时任务：

```bash
crontab -e
# backup data
0 0 * * *  /bin/sh /server/scripts/backup.sh &>/dev/null
```

服务端定时任务：

```bash
# check backup data
0 5 * * *  /bin/sh /server/scripts/backup_server.sh &>/dev/null
```

> **注意：** 服务端比客户端晚 5 小时执行，是为了确保客户端当天凌晨的备份已经全部推送完成，再去做校验和清理。
{: .sec-pit}

> **注意：** cron 不会重试：凌晨那一次推送因网络抖动失败，就要等第二天。重要备份可以加一层简单的重试（rsync 失败后 sleep 再试两次，仍失败则告警），或交给 systemd timer 的 `Persistent=true` 补跑错过的任务。
{: .sec-pit}

> **注意：** crond 服务本身也要确认在跑：`systemctl status crond`，机器重启后 crond 开机自启别忘；见过太多"脚本没错、任务没跑"，最后是 crond 没起。
{: .sec-pit}

> **注意：** `&>/dev/null` 会把脚本输出全部丢弃，调试期先去掉它让输出进邮件（cron 有输出会自动发给 root）；脚本内部已写日志文件后，再恢复 `&>/dev/null`。另外 crontab 里的环境变量比交互 shell 少得多，涉及 PATH 的命令建议用绝对路径。
{: .sec-pit}

## 还有什么完善余地

原始笔记在此处结束，未展开具体内容。实践中通常还可以继续完善：脚本的错误重试与告警、备份目录容量监控、备份任务的加锁避免重复执行、以及定期做恢复演练验证备份可用性。

在前文基础上，还可以继续演进的方向：

1. **容量监控**：对 `/backup` 目录做使用率监控，超过 80% 提前告警，避免写满导致备份失败
2. **任务状态可视化**：把每日备份结果（成功 / 失败 / 耗时 / 数据量）汇入监控看板，失败时联动告警通道
3. **配置即代码**：用 Ansible 批量下发备份脚本与 crontab，新服务器加入架构时自动具备备份能力
4. **多活备份服务器**：backup 服务器自身也要备份（它的配置与索引），防止"备份的备份"缺失
5. **演练自动化**：定期自动抽一天的备份包做解包校验，把"抽查"也变成无人值守
6. **备份加密**：备份包在落盘或外传前用 openssl / age 加密，磁盘被拔走也不泄密

> **注意：** 六个方向不必一次做完：容量监控与错误重试是第一批（防事故），配置即代码是第二批（防人肉），多活与演练自动化是第三批（防长期风险）。按事故概率排优先级，一次只推进一件事。
{: .sec-pit}

## 常见问题表

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 备份目录每天都是空的 | 定时任务没执行、脚本无权限 | `crontab -l`、`tail /var/log/cron` | 确认 crontab 条目与脚本执行权限 |
| `md5sum -c` 全部报 failed | 指纹文件记录的路径与校验时所在目录不匹配（相对路径的指纹换目录校验） | `cat finger.txt` 看记录的是绝对还是相对路径 | 用绝对路径记录指纹，或 cd 到指纹所在目录再校验 |
| 周一数据被清理了 | 文件名周几标识写错、清理规则没排除 | `ls /backup/*/` 核对文件名 | 统一用 `date +%F_week%w` 命名，`! -name "*week1.tar.gz"` 排除 |
| 邮件收不到 | postfix 未启动、授权码错误、被当垃圾邮件 | `mailq`、`tail /var/log/maillog` | 重启 postfix、核对授权码、检查垃圾箱 |
| backup 磁盘写满 | 留存策略没生效、数据量超预期 | `df -h /backup`、`du -sh /backup/*` | 执行清理策略，评估扩容或缩短留存周期 |
| 恢复时解包覆盖了在线数据 | 解包路径用了绝对路径 | 解包前先看包内文件列表 | 打包用 `cd /` + 相对路径，恢复到空目录再比对 |
| 推送成功但服务端缺文件 | 被备份机本地先清理再推送，时序颠倒 | 查看客户端日志顺序 | 固定顺序：打包 → 推送 → 清理本地旧数据 |

## 现代环境补充
{: .sec-ext}

CentOS Linux 7 已于 2024 年 6 月结束维护（EOL），在 Rocky Linux / AlmaLinux / CentOS Stream 上实施本项目时的对应变化：

| 项目 | CentOS 7 旧做法 | Rocky / AlmaLinux 新做法 |
| --- | --- | --- |
| 发送邮件 | postfix + `/etc/mail.rc` 明文授权码 | 同样可用；更推荐接入监控告警通道或专用 SMTP 中继 |
| 定时任务 | `crontab -e` + `&>/dev/null` | 相同，crond 用法不变；注意脚本内自建日志 |
| 清理与查找 | `find -mtime +7 \| xargs rm` | 相同，find 语法通用 |
| 锁文件 | `flock`（util-linux） | 相同，`flock` 默认可用 |
| rsync 部署 | `yum install rsync` + `systemctl start rsyncd` | `dnf install rsync` + 相同的 systemd 管理 |

> **注意：** 该项目用到的命令（tar / find / md5sum / rsync / mail / crontab）全是跨版本稳定的核心工具，项目方案本身没有过时风险；需要与时俱进的是周边：发信通道换成更安全的告警系统、备份结果接入监控大盘、脚本用 Ansible 统一下发。

## 小结
{: .sec-sum}

1. 项目先从需求出发：统一备份目录 `/backup`、统一命名规则（内网 IP 目录 + `日期_weekN` 文件名），再拆成客户端与服务端两套动作。
2. 完整架构是"1 个 backup 汇聚点 + N 台被备份机（web01 / db01 / nfs01 等）"：本地打包 → rsync 推送 → 服务端按 IP 归档 → 校验 → 邮件告警。
3. 客户端四件事：建目录 → `tar zchf` 打包（相对路径 + `-h` 跟随软链）→ `find -mtime +7` 清理本地 → 生成 `finger.txt` 指纹并 rsync 推送。
4. 服务端三件事：`find -mtime +180 ! -name "*week1.tar.gz"` 保留周一数据并清理过期数据 → `md5sum -c` 校验指纹 → `mail` 发送结果。
5. 保留周一数据最省事的做法是把周信息 `%w` 写进文件名，清理时用 `! -name` 排除 `week1`，避免额外的状态记录。
6. `md5sum -c` 的原理是"读指纹 → 按路径重算 → 比对 → 输出 ok / failed"，这是校验备份完整性的标准手段。
7. 自动化用 crontab：客户端每天 00:00 备份，服务端每天 05:00 校验，两者错开以避免校验时数据还没传完。
8. 策略层面：本地 7 天 + 服务端 6 个月 + 周一快照长期保留，兼顾恢复速度与存储成本；按 3-2-1 原则还差异地副本，机房级灾难只能靠异地备份兜底。
9. 备份的终点是"能恢复"：每月抽样恢复、每季度全流程演练，并记录 RTO / RPO，没演练过的备份等于没有备份。
10. 生产化四要素：加锁防重跑、日志可追溯、IP 变量化可批量下发、校验结果按成败分流告警。

## 自测题
{: .sec-prac}

1. 需求 6「保留每周一的数据、其它保留 6 个月」在命令层面如何实现？为什么选这种实现？
2. 客户端为什么要"先推送、后清理"？顺序颠倒会出什么问题？
3. `md5sum -c finger.txt` 报了一整片 failed，但文件确实传上去了，最可能的原因是什么？
4. 按 3-2-1 原则衡量，本项目目前满足了几条？还差什么？
5. 脚本已经加了 crontab，连续三天没在 backup 服务器看到新数据，按顺序列出你的排查步骤。

> **答案：** 1）文件名用 `$(date +%F_week%w)` 带上周几，清理时 `find /backup/ -type f -mtime +180 ! -name "*week1.tar.gz"`，周一数据因名字不匹配而被排除。选它是因为策略编码在文件名里，无状态、可重复执行，不需要在服务端额外维护拷贝逻辑。2）先推送保证新数据已到达 backup 服务器，再清理本地只是删掉"已异地留存"的副本；顺序颠倒会先删本地，一旦推送失败（网络、认证、磁盘满），这份数据两份都不存在，直接丢失。3）指纹文件记录的路径与校验方式不匹配：`md5sum -c` 按指纹里记录的路径逐条校验，本项目客户端生成的是绝对路径，服务端直接校验即可；若指纹改成相对路径，则必须 cd 到同一目录再执行。4）目前有 3 份数据（生产 + 本地留存 + backup 服务器），介质基本是同构磁盘；差"2 种介质"与"1 份异地"—— 应把关键副本同步到异地机房或公有云对象存储。5）① 在被备份机执行 `crontab -l` 确认条目存在、`sh -x /server/scripts/backup.sh` 手动跑一遍看报错；② `tail /var/log/cron` 看任务是否被调度、有没有权限问题；③ 手动执行最后的 rsync 推送命令，验证认证与网络（`ss -lntp | grep 873` 看服务端监听）；④ 看 backup 服务器 `/backup/<IP>/` 是否收到文件、`df -h` 是否写满。
