## 一、主机清单配置回顾

主机清单（inventory）是批量管理的地基，共有五种配置方式：

| 方式 | 写法示例 | 适用场景 |
| --- | --- | --- |
| 分组管理 | `[webserver]` 下列出主机 | 最常用，按角色分组 |
| 符号匹配 | `web[01:02].example.com` | 批量展开连续编号的主机 |
| 添加端口 | `172.16.1.31:52113` / `web01:52113` | SSH 为非标准端口时 |
| 主机后加变量 | `172.16.1.31 ansible_ssh_port=52113 ansible_ssh_user=root` | 单主机的连接参数 |
| 组嵌入 | `[web:children]` / `[web:vars]` | 组的嵌套与组级变量 |

符号匹配可以把连续编号的主机压缩成一行：

```ini
web01.example.com
web02.example.com

# 等价写法
web[01:02].example.com
```

主机后直接挂连接变量：

```ini
172.16.1.31 ansible_ssh_port=52113 ansible_ssh_user=root ansible_ssh_pass=<your-password>
```

组的嵌入（children）与组变量（vars）：

```ini
[web01]
172.16.1.7

[web02]
172.16.1.8

[web:children]
web01
web02

[web:vars]
ansible_ssh_port=52113
ansible_ssh_user=root
custom_var=123
```

> **注意：** `[web:children]` 里写的是"组名"而不是主机名；`[web:vars]` 里的变量对组内所有主机生效。密码之类的敏感信息不建议明文写在清单里，实际环境应使用密钥认证或加密的变量文件（见《批量管理 Ansible（下）》中 ansible-vault 一节）。新版本中 `ansible_ssh_pass` 等旧名已废弃，建议改写为 `ansible_password`。

## 二、剧本扩展功能速查

| 扩展功能 | 关键字 | 一句话说明 |
| --- | --- | --- |
| 变量 | `vars` / `--extra-vars` / 清单变量 | 三种设置方式，优先级：命令行 > 剧本 > 清单 |
| 注册信息 | `register` + `debug` | 保存任务结果，回显命令输出 |
| 条件判断 | `when` | 依据 facts（`setup` 模块）决定是否执行 |
| 循环 | `with_items` | 遍历列表批量执行，`item` 为当前元素 |
| 忽略错误 | `ignore_errors: yes` | 允许单个任务失败，不中断剧本 |
| 标签 | `tags` + `--tags` / `--skip-tags` | 按需执行或跳过指定任务 |
| 触发 | `handlers` + `notify` | 配置变更时触发一次，如重启服务 |
| 剧本整合 | `include_tasks` / `import_playbook` | 把多个剧本组装成统一入口 |

各功能的完整写法与示例已在《Ansible 剧本扩展功能》中逐项展开，此处不再重复。官方文档始终是最权威的参考：ansible 官方文档 user_guide 中的 playbooks 一节。

速查表当索引用，别当教材背——真正要紧的是知道"什么问题找哪个功能"：变量散乱找 `vars`、结果看不清找 `register`、机器差异找 `when`、重复劳动找 `loop`、误报 changed 找 `changed_when`、重复重启找 `handlers`、跑得慢找 `tags`。按问题索引功能，比按功能背语法实用得多。

## 三、剧本执行报错的排查思路

剧本报错时不要慌，按"从剧本到命令"逐层降级定位：

1. 找到剧本中出现问题的关键点（哪个任务、哪一行）。
2. 将剧本中的操作转换成模块进行操作（用 `ansible` ad-hoc 命令单独执行该模块）。
3. 将模块的功能操作转换成 Linux 命令测试：
   - 在本地管理主机上执行命令测试；
   - 在远程被管理主机上执行命令测试。

### 辨析：把报错翻译成人话

常见报错关键字先翻译再动手：`Syntax Error while loading YAML` 是缩进或格式问题；`no action detected in task` 是模块名写错或缩进错位；`xxx is undefined` 是变量没定义或拼错；`no hosts matched` 是清单组名不匹配；`UNREACHABLE` 是 SSH 层不通，回 SSH 排错三板斧。先译后查，方向不跑偏。

例如安装软件包，yum 模块支持直接传列表：

```yaml
- name: 01-install rsync
  yum:
    name: ['rsync', 'tree', 'wget']
    state: installed
```

对比不同工具的书写习惯（列表参数是 SaltStack 风格，Ansible 更常见 `name=xxx` 的键值写法）：

```yaml
- name: xxx
  yum:
    name: xxx
    state: installed
```

> **注意：** ad-hoc 模块命令能跑通，不代表剧本一定能跑通；剧本报错优先检查 YAML 缩进、冒号、`name` 唯一性这三类语法问题。

进阶排错三板斧：

```console
# 1. 语法检查，定位 YAML 层面的错误
$ ansible-playbook site.yml --syntax-check

# 2. 列出任务与标签，确认执行范围
$ ansible-playbook site.yml --list-tasks --list-tags

# 3. 单任务单主机调试：加 -v/-vvv 看详细调用过程
$ ansible-playbook site.yml --limit web01 -vv
```

落地到具体检查项，报错先扫三处：**缩进**——tab 与空格混用、层级错位，占剧本报错的大头；**模块名**——拼错一个字母，轻则 `no action detected`，重则被当成普通变量静默跳过；**路径**——copy/template 的 src 相对谁解析（playbook 目录还是角色 files 目录），写之前想清楚。三处都正常，再用 `-vv` 看模块在远程的实际执行过程。

`--limit` 与 `serial` 是两种灰度手段，分工不同：`--limit` 由人在外面控制这一轮跑哪些主机，适合"先灰一台、确认后放开"；`serial` 是剧本内部按批滚动，每批全部成功才进下一批，适合"大组变更防集体出事"。生产变更两个一起用，互相兜底。

交付前的幂等自检也值得养成习惯：剧本连跑两遍，第二遍应该全 ok。凡第二遍仍 changed 的任务逐个审——要么真不幂等（shell 拼的），要么 `changed_when` 没声明。这个自检能拦下大半"重复执行翻车"事故。

## 四、案例一：NFS 服务一键化部署

四个案例剥掉服务差异，骨架完全一致：**装软件 → 推配置 → 备授权（用户/目录/权限）→ 起服务 → 验证**。学会一个等于学会一类，部署新服务时按骨架填空——先想清楚目标状态，再翻译成任务清单。

下面把 NFS 服务的完整部署流程固化成剧本，展示扩展功能的综合运用。

### 4.1 准备工作：目录与主机清单

先创建剧本目录结构，按服务端、客户端分子目录存放各自的分发文件：

```console
$ tree nfs-file/
nfs-file/
├── nfs-client
└── nfs-server
```

执行输出也有固定的读法：每个任务行看主机名后面的结果单词——`ok` 未变更、`changed` 有变更、`failed` 失败、`skipping` 被 when 跳过、`UNREACHABLE` 连不上；结尾的 RECAP 汇总有 failed 或 unreachable 就必须先处理，别被前面的绿色刷屏迷惑。

主机清单按"组套组"的方式编写，`nfs` 组包含服务端与客户端两个子组：

组套组写法的意图很清楚：剧本里 `hosts: nfs` 一次覆盖全部 NFS 主机（第一个 play 用它统一装软件），服务端、客户端的差异化任务再分别落到子组。清单结构直接映射部署结构，看清单就知道哪些机器同甘共苦。

```ini
[nfs:children]
nfs_server
nfs_client

[nfs_server]
172.16.1.31

[nfs_client]
172.16.1.7
#172.16.1.8
#172.16.1.9
```

### 4.2 编写剧本

整个剧本由三个 play 组成：第一个 play 给所有 NFS 主机装软件，后两个 play 分别处理服务端与客户端：

```yaml
- hosts: nfs
  tasks:
    - name: 01-install nfs software
      yum:
        name: ['nfs-utils', 'rpcbind']
        state: installed

- hosts: nfs_server
  vars:
    Data_dir: /data
  tasks:
    - name: 01-copy conf file
      copy:
        src: /etc/ansible/ansible-playbook/nfs-file/nfs-server/exports
        dest: /etc
      notify: restart nfs server

    - name: 02-create data dir
      file:
        path: "{{ Data_dir }}"
        state: directory
        owner: nfsnobody
        group: nfsnobody
        # path: ['data01', 'data02', 'data03']
        # state: directory
        # owner: nfsnobody
        # group: nfsnobody

    - name: 03-boot server
      # service:
      #   name: rpcbind
      #   state: started
      #   enabled: yes
      # service:
      #   name: nfs
      #   state: started
      #   enabled: yes
      service:
        name: "{{ item }}"
        state: started
        enabled: yes
      with_items:
        - rpcbind
        - nfs

  handlers:
    - name: restart nfs server
      service:
        name: nfs
        state: restarted

- hosts: nfs_client
  vars:
    Data_dir: /data
  tasks:
    - name: 01-mount
      mount:
        src: "172.16.1.31:{{ Data_dir }}"
        path: /mnt
        fstype: nfs
        state: mounted

    - name: 02-check mount info
      shell: df -h | grep /data
      register: mount_info

    - name: display mount info
      debug:
        msg: "{{ mount_info.stdout_lines }}"
```

剧本中用到的扩展功能一览：

- `with_items` 循环启动 rpcbind 与 nfs 两个服务；
- `handlers` + `notify` 在 exports 配置发生变化后重启 NFS 服务；
- `register` + `debug` 把挂载检查结果回显到终端；
- `vars` 中定义 `Data_dir` 变量统一管理共享目录，服务端创建、客户端挂载引用同一个值。

> **注意：** 这里有个坑：`Data_dir` 变量必须显式定义（例如在 play 的 `vars` 中写 `Data_dir: /data`），否则任务会因变量未定义而失败；也可以在主机清单或命令行 `--extra-vars` 中提供。变量放 `vars` 的好处是"服务端与客户端改一处即可同步"。

### 4.3 执行过程与验证方法

```console
# 执行剧本
$ ansible-playbook nfs.yml

# 验证一：服务端 exports 是否生效
$ ansible nfs_server -m shell -a "exportfs -arv"

# 验证二：服务端共享目录与权限
$ ansible nfs_server -m shell -a "ls -ld /data"

# 验证三：客户端挂载结果
$ ansible nfs_client -m shell -a "df -h | grep nfs"

# 验证四：客户端读写测试（在管理主机上手动执行）
$ ssh 172.16.1.7 "touch /mnt/testfile && ls -l /mnt/testfile"
```

预期结果：`exportfs -arv` 输出 `/data 172.16.1.7`，客户端 `df -h` 能看到 `172.16.1.31:/data` 挂载到 `/mnt`，`touch` 测试文件在服务端 `/data` 下可见，说明读写链路打通。

验证环节的设计也有讲究：检查类命令（`ss`、`df`、`exportfs`）全部配 `changed_when: false`，失败要能反映到退出码；验证盯三层——端口（`ss`）、进程（`systemctl status`）、功能（`curl`、读写测试），任选其二就足以判断"部署成功"。验证命令走 ansible 批量执行而非逐台 SSH，本身就是对"部署 + 连通"的双重复核，输出用 `tee` 留档，出问题时可对比部署前后差异。

### 4.4 本案例常见错误

| 现象 | 可能原因 | 解决方式 |
| --- | --- | --- |
| `'Data_dir' is undefined` | 变量未定义或拼写不一致 | 在 `vars` 中定义，或检查大小写（YAML 区分大小写） |
| 客户端 mount 任务失败，提示 permission denied | 服务端 exports 未放开该网段，或 firewalld 拦截 | 检查 exports 的 `rw/sync/no_root_squash` 配置与防火墙放行 nfs/mountd 端口 |
| showmount 看不到共享 | rpcbind 或 nfs 服务未启动 | 手动执行 `systemctl status rpcbind nfs` 确认状态 |
| 挂载成功但无法写入 | 目录 owner 为 nfsnobody 而客户端 root 被降权 | 调整 exports 的 `no_root_squash` 或改用普通用户测试 |

这个案例还能继续扩展：exports 变更后逐客户端重挂载（把 mount 任务也挂 notify）、多客户端并行挂载用 `serial` 控制节奏、`showmount -e` 检查任务化。骨架不变，往 tasks 里加任务就行。

## 五、案例二：Nginx 一键化部署（模板与 handler 实战）

Nginx 案例重点演练 `template` 模块：配置文件带变量，一次渲染适配不同主机，配合 handler 实现"配置变更才重启"。

### 5.1 目录结构

```console
$ tree nginx-file/
nginx-file/
├── nginx.conf.j2
└── site.yml
```

- `nginx.conf.j2`：Jinja2 模板文件，放在与 playbook 同级目录；
- `site.yml`：部署剧本。

### 5.2 模板文件

```nginx
server {
    listen {{ http_port }};
    server_name {{ server_name }};
    root {{ web_root }};
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

### 5.3 部署剧本

```yaml
- hosts: web
  remote_user: root
  vars:
    http_port: 80
    server_name: web01.example.com
    web_root: /data/www
  tasks:
    - name: 01-install nginx
      yum:
        name: nginx
        state: present

    - name: 02-create web root dir
      file:
        path: "{{ web_root }}"
        state: directory
        owner: nginx
        group: nginx
        mode: '0755'

    - name: 03-push test index page
      copy:
        content: "<h1>this is {{ inventory_hostname }}</h1>"
        dest: "{{ web_root }}/index.html"
        mode: '0644'

    - name: 04-render nginx conf from template
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/conf.d/site.conf
        mode: '0644'
      notify: restart nginx

    - name: 05-start nginx service
      service:
        name: nginx
        state: started
        enabled: yes

    - name: 06-check listen port
      shell: ss -lntp | grep ":{{ http_port }} " || true
      register: listen_check
      changed_when: false

    - name: display listen info
      debug:
        msg: "{{ listen_check.stdout_lines }}"

  handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted
```

### 5.4 执行过程与验证方法

```console
# 执行剧本
$ ansible-playbook nginx-file/site.yml

# 第一次执行：配置被推送，handler 触发重启 nginx
# 第二次执行：模板内容未变化，任务显示 ok，handler 不再触发

# 验证一：端口监听
$ ansible web -m shell -a "ss -lntp | grep :80"

# 验证二：本地访问页面
$ ansible web -m shell -a "curl -s http://127.0.0.1/"

# 验证三：配置语法正确性（模板渲染后可检查）
$ ansible web -m shell -a "nginx -t"
```

预期结果：`curl` 返回 `<h1>this is web01</h1>`；重复执行剧本时，"04-render nginx conf" 显示 ok 而非 changed，handler 不再重启服务 —— 这正是 handler 机制的价值。

再往前想一步：如果希望配置变更后做的是 reload 而不是重启，改 handler 里的动作即可——变更检测与收尾动作是解耦的，这是 handler 设计的精髓。案例里的 `http_port`、`server_name` 都是写在 `vars` 里的演示值；真实落地放进 `group_vars` 按环境拆分，同一剧本 `-i` 切清单即可部署到测试或生产，临时覆盖单个值用 `-e`。

### 5.5 本案例常见错误

| 现象 | 可能原因 | 解决方式 |
| --- | --- | --- |
| 访问返回 404 | `root` 指向的目录不存在或 index.html 没推过去 | 检查 `web_root` 创建任务与 copy 任务的 dest |
| `nginx -t` 报语法错误 | 模板中变量为空或 Jinja2 语法写错 | 在被管理主机查看渲染后的 `/etc/nginx/conf.d/site.conf` |
| 80 端口被占用 | 主机已有其他 Web 服务 | `ss -lntp | grep :80` 定位进程，换端口或卸载冲突服务 |
| 每次执行剧本 nginx 都重启 | copy 的 content 带变化内容（如时间戳），或未用模板 | 内容固定化，配置变更只通过 template 模块驱动 |

## 六、案例三：rsync 服务一键化部署（服务端 + 客户端）

rsync 案例展示多 play 剧本的典型形态：第一个 play 面向服务端组，第二个 play 面向客户端组，密码文件用 `copy` 模块的 `content` 直接生成，无需提前准备分发文件。

### 6.1 目录结构

```console
$ tree rsync-file/
rsync-file/
├── rsyncd.conf
└── rsync.yml
```

服务端分发文件 `rsyncd.conf`（rsync 守护进程配置，按官方 man 手册字段书写）：

```conf
uid = rsync
gid = rsync
port = 873
fake super = yes
pid file = /var/run/rsyncd.pid
log file = /var/log/rsyncd.log

[backup]
path = /backup
read only = no
list = yes
auth users = rsync_backup
secrets file = /etc/rsync.password
```

### 6.2 部署剧本

配置文件里有几个字段值得点名：`fake super = yes` 允许 rsync 守护进程不以 root 身份保留属主等属性，是安全降权的常用配套；`auth users` 里的用户名只存在于服务端 `secrets file` 的"用户:口令"行里，与系统用户无关；`[backup]` 段名就是客户端命令里 `::backup` 引用的模块名，三处对齐服务才通。

```yaml
- hosts: rsync_server
  remote_user: root
  tasks:
    - name: 01-install rsync
      yum:
        name: rsync
        state: present

    - name: 02-push conf file
      copy:
        src: rsyncd.conf
        dest: /etc/rsyncd.conf
        mode: '0644'
      notify: restart rsyncd

    - name: 03-create user
      user:
        name: rsync
        create_home: no
        shell: /sbin/nologin

    - name: 04-create backup dir
      file:
        path: /backup
        state: directory
        owner: rsync
        group: rsync
        mode: '0755'

    - name: 05-create password file
      copy:
        content: "rsync_backup:<your-password>"
        dest: /etc/rsync.password
        mode: '0600'
      no_log: true

    - name: 06-start rsync server
      service:
        name: rsyncd
        state: started
        enabled: yes

  handlers:
    - name: restart rsyncd
      service:
        name: rsyncd
        state: restarted

- hosts: rsync_clients
  remote_user: root
  tasks:
    - name: 01-install rsync
      yum:
        name: rsync
        state: present

    - name: 02-create password file
      copy:
        content: "<your-password>"
        dest: /etc/rsync.password
        mode: '0600'
      no_log: true

    - name: 03-create test file
      file:
        dest: /tmp/test.txt
        state: touch

    - name: 04-check test
      shell: rsync -avz /tmp/test.txt rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
      register: rsync_test

    - name: display rsync result
      debug:
        msg: "{{ rsync_test.stdout_lines[-3:] }}"
```

> **注意：** `no_log: true` 让带口令的任务不回显输出，防止密码泄露到终端与日志；`content` 中的口令是 `<your-password>` 占位符，实际使用时应通过 `ansible-vault` 加密的变量传入。

### 6.3 执行过程与验证方法

```console
# 执行剧本
$ ansible-playbook rsync.yml

# 验证一：服务端守护进程与端口
$ ansible rsync_server -m shell -a "ss -lntup | grep 873"

# 验证二：客户端推送测试文件（剧本第 04 步已自动完成）
$ ansible rsync_clients -m shell -a "rsync -avz /tmp/test.txt rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password"

# 验证三：服务端确认文件到达
$ ansible rsync_server -m shell -a "ls -l /backup/"
```

预期结果：服务端 873 端口有 rsyncd 监听，`/backup/test.txt` 存在，客户端 rsync 命令输出 `sent ... received ...` 且退出码为 0。

### 6.4 本案例常见错误

| 现象 | 可能原因 | 解决方式 |
| --- | --- | --- |
| `@ERROR: auth failed on module backup` | 客户端密码文件内容与服务端不一致 | 两端 `rsync.password` 中口令必须相同（客户端只写口令，服务端写 `用户:口令`） |
| `@ERROR: chroot failed` | 服务端 `/backup` 不存在或属主不是 rsync | 确认目录已创建且 owner/group 为 rsync |
| 连接超时 | 防火墙未放行 873 端口，或 SELinux 拦截 | `firewall-cmd --add-port=873/tcp` 并检查 SELinux |
| 服务端看不到文件 | 推送的模块名与服务端 `[backup]` 段名不一致 | 核对命令中 `::模块名` 与配置文件段名 |

rsync 排错有个捷径：把剧本第 04 步的命令抄到客户端手工跑，报错信息比剧本输出直观得多；`-vv` 打出来的是"远端实际执行了什么命令"，拿这条命令去服务端对照 `/var/log/rsyncd.log`，两端一对基本就能定位。

## 七、案例四：全网备份项目（备份脚本 + 定时任务）

全网备份是生产环境最常见的自动化需求：所有业务机（客户端）每天定时把本地数据通过 rsync 推送到备份服务器的指定模块。本案例把"装软件 → 发密码文件 → 发备份脚本 → 配定时任务"固化成剧本。

### 7.1 目录结构

```console
$ tree backup-file/
backup-file/
├── backup.sh
└── backup.yml
```

### 7.2 备份脚本

```bash
#!/bin/bash
# 本地待备份数据目录
Local_dir=/var/www/html
# 备份服务器与模块（需提前部署好 rsync 服务端）
Backup_server=172.16.1.41
Module=backup
Password_file=/etc/rsync.password
# 按日期生成远程目录，保留历史备份
Date=$(date +%F)
Remote_path=/${Date}

rsync -avz --password-file=${Password_file} ${Local_dir}/ rsync_backup@${Backup_server}::${Module}${Remote_path}
```

> **注意：** 源目录写成 `${Local_dir}/`（带尾部斜杠）表示同步目录内容本身；`${Module}${Remote_path}` 拼接出按天隔离的备份目录，避免不同日期的备份互相覆盖。该脚本依赖 rsync 服务端已部署（见案例三）。

脚本还可以再说明两句：放 `/server/scripts/` 并给 0750 是生产脚本管理的惯例——权限收敛到属主与属组，避免其他用户读到脚本里的服务器信息；脚本里 `date +%F` 按天分目录，配合服务端定期清理脚本就是一套完整的滚动保留策略。

### 7.3 部署剧本

```yaml
- hosts: rsync_clients
  remote_user: root
  vars:
    backup_server: 172.16.1.41
    backup_script_dir: /server/scripts
  tasks:
    - name: 01-install rsync
      yum:
        name: rsync
        state: present

    - name: 02-create password file
      copy:
        content: "<your-password>"
        dest: /etc/rsync.password
        mode: '0600'
      no_log: true

    - name: 03-push backup script
      template:
        src: backup.sh
        dest: "{{ backup_script_dir }}/backup.sh"
        mode: '0750'

    - name: 04-create test data dir
      file:
        path: /var/www/html
        state: directory
        mode: '0755'

    - name: 05-create test data file
      copy:
        content: "backup test data on {{ inventory_hostname }}\n"
        dest: /var/www/html/index.html
        mode: '0644'

    - name: 06-setup daily backup cron
      cron:
        name: "daily network backup"
        hour: "1"
        minute: "30"
        job: "/bin/bash {{ backup_script_dir }}/backup.sh &> /var/log/backup.log"

    - name: 07-run backup once for test
      shell: /bin/bash {{ backup_script_dir }}/backup.sh
      register: backup_test
      changed_when: "'sent' not in backup_test.stdout"
```

> **注意：** 脚本里出现了服务器 IP，用 `template` 模块把 `backup_server` 变量渲染进脚本，比 `copy` 更灵活；`changed_when` 根据输出中是否出现 `sent` 判断是否真正产生了同步。定时任务通过 `cron` 模块部署，比直接编辑 crontab 更幂等。

cron 模块部署的任务自带 `name` 注释标识，后续升级 job 内容时同名即覆盖，不会出现新旧两条并存——手工 crontab 做不到这一点，也是"定时任务一律走模块"的直接理由。

### 7.4 执行过程与验证方法

```console
# 执行剧本
$ ansible-playbook backup.yml

# 验证一：客户端定时任务已生成
$ ansible rsync_clients -m shell -a "crontab -l | grep backup"

# 验证二：手动触发一次备份，观察输出
$ ansible rsync_clients -m shell -a "/bin/bash /server/scripts/backup.sh"

# 验证三：备份服务器确认数据到达（按日期分目录）
$ ansible rsync_server -m shell -a "ls -R /backup/ | head -20"

# 验证四：客户端备份日志
$ ansible rsync_clients -m shell -a "tail -5 /var/log/backup.log"
```

预期结果：客户端 `crontab -l` 能看到每天 01:30 执行的备份任务；备份服务器 `/backup/$(date +%F)/` 目录下出现 `index.html`，内容与客户端源文件一致。

备份跑起来只是第一步，还得能证明"备了且可恢复"：定期抽一台客户端做恢复演练，把文件还原回来对比校验值；服务端按日期目录做保留策略（`find /backup -maxdepth 1 -mtime +7` 配合清理脚本）；监控任务实际执行——cron 日志加备份产物的时间戳双确认。备份的价值在恢复那一刻才兑现，平时不看恢复链路的备份等于没备。

### 7.5 本案例常见错误

| 现象 | 可能原因 | 解决方式 |
| --- | --- | --- |
| 备份目录为空 | 源目录路径写错，或尾部斜杠语义不清 | 确认 `${Local_dir}/` 指向的是目录内容 |
| cron 不执行 | 脚本无可执行权限或 cron 环境变量缺失 | 检查 `mode: '0750'` 与 shebang；job 中用绝对路径 |
| 历史备份被覆盖 | 远程目录未按日期隔离 | 用 `Remote_path=/${Date}` 按天分目录 |
| `password-file` 权限报警 | rsync 要求密码文件权限不超过 600 | `chmod 600 /etc/rsync.password` |

## 八、roles：让剧本结构规范化

随着剧本越写越多，会暴露几个典型问题：

1. 目录结构不够规范；
2. 编写好的任务如何重复调用；
3. 服务端配置文件改动后，客户端参数信息不能自动变化；
4. 汇总剧本中没有显示主机角色信息；
5. 一个剧本内容过多，不容易阅读，需要拆分。

roles 目录结构正是为解决这些问题而设计的标准化方案。这套目录约定不是随意划分：tasks 放动作、files 放静态产物、templates 放带变量的产物、handlers 收触发器、vars 收参数，各类东西各归其位之后，"copy 的 src 只写文件名就能找到"这类自动查找规则才成立。说白了，目录约定就是团队协作的接口——接手的人打开目录就知道去哪改配置、去哪改任务，维护成本从"读剧本"降到"看目录"。roles 的完整目录规范、调用方式与 ansible-vault 加密已在《批量管理 Ansible（下）》中详细展开，此处保留实战原始记录，演示如何把 NFS 剧本改造为标准角色。

### 8.1 规范目录结构

进入 roles 目录，为每个服务创建角色目录，并在角色下建立标准子目录：

```console
$ cd /etc/ansible/roles
$ mkdir {rsync,nfs}
$ mkdir {nfs,rsync}/{vars,tasks,templates,handlers,files}
$ tree
.
├── nfs
│   ├── files       # 保存需要分发的文件
│   ├── handlers    # 保存触发器配置信息
│   ├── tasks       # 保存要执行的任务文件
│   ├── templates   # 保存需要分发的模板文件，模板中可以设置变量
│   └── vars        # 保存变量信息
└── rsync
    ├── files
    ├── handlers
    ├── tasks
    ├── templates
    └── vars
```

各子目录的职责：

| 子目录 | 作用 |
| --- | --- |
| `files` | 存放需要分发的静态文件 |
| `templates` | 存放需要分发的模板文件（可嵌入变量） |
| `tasks` | 存放该角色要执行的任务 |
| `handlers` | 存放该角色的触发器 |
| `vars` | 存放该角色的变量 |

### 8.2 编写各子目录文件

**tasks/main.yml**：作为入口，把任务拆分成多个文件再用 `include_tasks` 组合，解决"一个剧本内容过多"的问题：

```yaml
- include_tasks: copy_info.yml
- include_tasks: create_dir.yml
- include_tasks: boot_server.yml
```

**tasks/copy_info.yml**：

```yaml
- name: 01-copy conf file
  copy:
    src: exports
    dest: /etc
  notify: restart nfs server
```

**tasks/create_dir.yml**：

```yaml
- name: 02-create data dir
  file:
    path: "{{ Data_dir }}"
    state: directory
    owner: nfsnobody
    group: nfsnobody
```

**tasks/boot_server.yml**：

```yaml
- name: 03-boot server
  service:
    name: "{{ item }}"
    state: started
    enabled: yes
  with_items:
    - rpcbind
    - nfs
```

**vars/main.yml**：集中管理变量，实现"改一处、全局生效"：

```console
$ vim main.yml
Data_dir: /data
```

**files/**：存放 exports 等分发文件：

```console
$ ll
total 4
-rw-r--r-- 1 root root 29 May 17 15:23 exports
```

**handlers/main.yml**：

```yaml
- name: restart nfs server
  service:
    name: nfs
    state: restarted
```

编写完成后，角色目录的结构如下：

```console
$ tree
.
├── files
│   └── exports
├── handlers
│   └── main.yml
├── tasks
│   └── main.yml
├── templates
└── vars
    └── main.yml
```

### 8.3 编写主剧本（site.yml）

主剧本只描述"哪些主机扮演什么角色"，具体动作由 roles 目录承载，可读性大幅提升：

```yaml
- hosts: nfs_server
  roles:
    - nfs-server

- hosts: rsync_server
  roles:
    - rsync
```

> **注意：** 角色目录名与 `roles:` 中引用的名字要对应（例如目录 `nfs` 就写 `- nfs`，引用名必须与实际目录名一致）；`copy` 的 `src` 写文件名时，Ansible 会自动在角色内的 `files/` 目录中查找。

把 NFS 案例剧本迁移成标准角色，五步走：分发文件（exports）挪进 `files/`；共享目录参数化成 `defaults/main.yml` 里的默认值；重启动作挪进 `handlers/main.yml`；任务拆到 `tasks/main.yml`；`Data_dir` 下沉到 `group_vars`。改完用同一份清单跑一遍，对比输出与迁移前一致，迁移才算完成——改结构不改行为，是重构的基本纪律。

## 知识卡片

| 关键字 | 一句话记忆 |
| --- | --- |
| `--syntax-check` | 只检查 YAML 语法，不连接远程主机 |
| `--list-tasks --list-tags` | 预演：列出所有任务与标签 |
| `--limit 主机或组` | 只对部分目标执行 |
| `-vv / -vvv` | 提高详细程度，查看模块调用细节 |
| `template` | 把 Jinja2 模板渲染成配置文件，变量驱动差异化 |
| `copy content=` | 不依赖源文件，直接生成目标文件内容 |
| `cron` | 幂等地部署定时任务（name 相同即更新） |
| `no_log: true` | 任务输出不回显，保护口令等敏感信息 |
| `register` + `debug` | 保存并回显任务结果，stdout_lines 逐行查看 |
| `handlers` + `notify` | 配置变更才触发，play 末尾执行一次 |
| `roles/` 七子目录 | tasks、handlers、vars、defaults、files、templates、meta |
| `site.yml` | 总入口，只描述主机与角色，不写任务细节 |

生产部署还要求可追溯：剧本进 Git、执行留 RECAP 归档、变更关联工单号（用 `-e` 传入，写进部署标记文件或日志）。出了问题能回答"什么时候、谁、改了什么"，这比任何事后回忆都可靠。

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 变量未定义导致任务失败 | 变量只在注释里或放在了错误作用域 | `ansible-playbook --syntax-check site.yml`；`ansible all -m debug -a "var=Data_dir"` | 在 `vars`/`group_vars`/`--extra-vars` 中显式定义 |
| 服务配置推送了但不生效 | handler 未触发：任务显示 ok 而非 changed | 观察任务输出是否为 changed | 确认配置内容确有变化；检查 notify 名称与 handler name 一致 |
| `rsync @ERROR: auth failed` | 两端密码文件内容或格式不一致 | 手动执行 rsync 命令对比 | 服务端 `用户:口令`、客户端仅口令，两侧权限 600 |
| mount 任务报 permission denied | exports 未授权该网段或防火墙拦截 | `showmount -e 172.16.1.31` | 修正 exports 配置并重放，放行 nfs 相关端口 |
| cron 任务没按时执行 | 脚本无执行权限、cron 环境差异 | `crontab -l`；`journalctl -u crond` | 用绝对路径、确保脚本可执行、job 重定向日志 |
| 二次执行剧本仍全部 changed | shell/command 任务每次都有"变更" | `ansible-playbook site.yml --diff` | 改用幂等模块或加 `changed_when: false` |

剧本中途失败会在目标机上留下半完成状态。幂等剧本重跑即可收敛；不可重跑的步骤（分区、初始化）单独拆 play 控制执行次数，或用 `creates` / 标记文件防重复执行。失败不可怕，可怕的是不知道机器停在哪一步。

## 现代环境补充

1. **服务管理**：Rocky Linux / AlmaLinux / CentOS Stream 全面使用 systemd，`service` 模块仍兼容，但直接使用 `systemd` 模块语义更准确；确认服务状态优先 `systemctl status`。
2. **包管理**：`yum` 模块在新系统上可用，等价现代写法是 `dnf` 模块；模块内的 `state: present` 与旧文档的 `state: installed` 等价。
3. **端口查看**：案例中的 `netstat -lntup` 已废弃（属于 net-tools），统一改为 `ss -lntup`；`ss -lntp | grep 873` 是验证 rsyncd 的标准姿势。
4. **firewalld**：新系统默认防火墙为 firewalld，放行服务端口用 `firewall-cmd --permanent --add-service=nfs` / `--add-port=873/tcp` 后 `--reload`，替代旧式 iptables 直接写规则。
5. **剧本分发安全**：口令类 `content` 建议改为 vault 加密变量引用（`content: "{{ rsync_password }}"`），配合 `no_log: true` 双保险。

四个案例做下来，还应该带走一个认知：剧本的价值不在"跑得快"，而在"跑得可预期"——同样的输入永远得到同样的结果，出错时停在该停的地方，重来时不留半成品。到这个程度，批量管理才算真正入门。

## 自测题

1. NFS 案例中，服务端创建目录和客户端挂载引用同一个 `Data_dir` 变量，这样做有什么好处？
2. 为什么第二次执行 Nginx 剧本时 nginx 不会重启？
3. `copy` 的 `content` 参数与 `src` 参数有什么区别？各适合什么场景？
4. 全网备份脚本里 `${Local_dir}/` 带尾部斜杠和不带斜杠，rsync 的行为差异是什么？
5. 剧本报错时的"三步定位法"是哪三步？

> **答案：**
> 1. 服务端与客户端使用同一变量，调整共享目录时只改 `vars` 一处，两端同步生效，避免"服务端改了客户端没改"的不一致。
> 2. handler 只在通知它的任务报告 changed 时触发；第二次执行时模板渲染结果与现有文件一致，任务显示 ok，handler 不触发。
> 3. `content` 直接指定文件内容，无需在管理机准备源文件，适合生成配置、密码文件；`src` 分发管理机上的已有文件，适合 exports、rsyncd.conf 等成体系的分发文件。
> 4. 带斜杠表示同步目录内容本身（不包含目录名），不带斜杠会把目录本身同步到目标下，两者生成的备份目录层级不同。
> 5. ① 找到剧本中出问题的关键点；② 把操作降级为 ad-hoc 模块命令单独测试；③ 再降级为 Linux 命令，在管理主机与远程主机上分别测试。

  1. 一键化部署全网备份项目；
  2. 一键化部署实时同步服务。

## 小结

1. 主机清单支持分组、符号匹配、端口指定、主机变量、组嵌入五种配置方式，`[web:children]` 嵌套组、`[web:vars]` 定义组变量。
2. 剧本报错按三步定位：找关键点 → 降级为模块命令测试 → 再降级为 Linux 命令在本地与远程分别测试；配合 `--syntax-check`、`--list-tasks`、`-vv` 三板斧效率更高。
3. NFS 一键部署剧本由"全体装软件、服务端配服务、客户端挂载"三个 play 组成，综合运用了循环、handler、register 与变量；`Data_dir` 变量必须显式定义，放 `vars` 中可实现服务端与客户端同步调整。
4. Nginx 案例演示 `template` 模块 + `vars` + handler 的标准组合：配置模板化、变更才重启、重复执行无副作用。
5. rsync 案例演示多 play 剧本（服务端 + 客户端）与 `copy content` 生成密码文件，`no_log: true` 保护口令不回显。
6. 全网备份案例把备份脚本与 `cron` 模块组合，实现"脚本分发 + 定时执行 + 按日期分目录"的完整备份链路，验证时依次查客户端 crontab、备份服务器目录与客户端日志。
7. roles 用 `files`、`templates`、`tasks`、`handlers`、`vars` 五个标准子目录规范剧本结构，`tasks/main.yml` 负责组织入口，`vars/main.yml` 集中管理变量。
8. 主剧本（site.yml）通过 `roles:` 声明主机角色，实现"角色清晰、任务复用、变量统一"的标准化剧本工程。
9. 四个案例共用一套骨架：装软件、推配置、授权、起服务、验证；换服务只换中间三步的具体内容，骨架本身很少变。
