## 8.1 指针的基本概念
{: .sec-expl}

把机器内存想成一条从 0 开始编号的字节带就行。你写的每个对象——`int`、`double`、结构体、数组——都占着这条带上连续的一段，这段开头的编号就是它的地址。指针自己也是个对象：占内存、有类型、有地址，唯一特别的是它存的内容——是另一个对象的地址。

拿 `int x = 42;` 说吧：编译器在栈帧里挑 4 个字节，把 42 写进去；`&x` 把这 4 个字节的首地址取出来；`int* p = &x;` 把地址存进 p；`*p` 再顺着 p 里的地址走回去，找回那个 `int`。`&` 跟 `*` 是一对互逆的活儿——一个从对象到地址，一个从地址回到对象。

那为什么语言非要把地址摊开给你？我自己的体会是四个绕不开的理由：

- 大对象搬不动。按值传参要整份拷贝，传地址只走 8 个字节（LP64 平台下指针大小，下同）。
- 函数要改调用者的变量。C 时代没有引用，传地址是唯一手段，这个习惯一直沿用至今。
- 一份数据多方使用。拷贝出去就是两份数据，传地址才是同一份。
- 尺寸或位置运行期才知道。链表、树、堆分配的对象，靠的就是“地址”这条线串起来。

### 地址与对象模型
{: .sec-know}

先把几条基本事实钉死：

- 对象有地址，指针也是对象，所以指针也有自己的地址——也就是地址的地址。二级指针（8.6 节）就是从这来的。
- `*p` 解引用的结果就是 p 所指的那个对象本身，可以读也可以写。
- 指针的类型决定解读方式。同样一个地址，`int*` 按 4 字节补码读，`double*` 按 8 字节浮点读，类型就是地址上的“取货单”。
- 地址本身没有类型之分（都是编号），带类型的是指针变量。这也是 `void*` 能充当通用容量的原因，8.3 节细说。

下面这段程序把整条链走一遍，顺便看清指针这几种大小。

```cpp
#include <iostream>

int main() {
    int x = 42;
    int* p = &x;        // p 存的是 x 的地址

    std::cout << "x 的值       : " << x << '\n';
    std::cout << "x 的地址     : " << &x << '\n';
    std::cout << "p 的值       : " << p << '\n';     // 与 &x 相同
    std::cout << "*p 解引用    : " << *p << '\n';
    std::cout << "p 自己的地址 : " << &p << '\n';     // 指针也是对象
    std::cout << "指针大小     : " << sizeof(p) << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr_basic.cpp -o ptr_basic && ./ptr_basic
```

```text
x 的值       : 42
x 的地址     : 0x7ffc8e3a2c44
p 的值       : 0x7ffc8e3a2c44
*p 解引用    : 42
p 自己的地址 : 0x7ffc8e3a2c38
指针大小     : 8
```

地址的具体数值每次跑都不一样——现代系统都开了地址随机化。前提是 LP64 平台（Linux/macOS 的 x86-64），Windows 64 位同样是 8 字节指针。你看输出里第 2 行和第 3 行一模一样，那就是“p 确实存了 x 的地址”的铁证。

> **注意：** `sizeof(p)` 量的是指针自己（8 字节），不是它指的那个对象。想知道对象多大，量 `sizeof(*p)`。
{: .sec-note}

## 8.2 定义指针的几种方式
{: .sec-know}

声明的骨架是“基本类型 + 声明符”两套。`int* p` 里 `int` 是基本类型，`*p` 整块是声明符，`*` 修饰的是 p 这个名——不是 `int`。这是 C 从 1970 年代带过来的“表达式式声明”：声明长得像你用它时的表达式。`int *p;` 读作“`*p` 是个 int”，于是 p 就是指向 int 的指针。

这套写法留了个出了名的坑：`*` 不会跟着类型一起复制下去。

> **坑：** `int* p, q;` 里只有 p 是指针，q 就是个普通 `int`。最直观的反例是这条必挂的写法：`int* r = &a, s = &b;`——s 被 `*` 甩下，成了 `int`，接不住 `&b`（类型 `int*`）。要躲这个坑，一行只声明一个变量就够了。
{: .sec-pit}

```cpp
#include <iostream>

int main() {
    int a = 1, b = 2;
    int* p = &a, q = b;       // 合法，但风格糟糕：p 是 int*，q 是 int

    p = &b;                   // 指针可以随时改指向
    std::cout << *p << ' ' << q << '\n';

    int*  s1 = &a;            // 风格一：* 靠右，强调“int* 这种类型”
    int *s2  = &a;            // 风格二：* 靠左，强调“声明符 *s2”
    std::cout << *s1 + *s2 << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr_decl.cpp -o ptr_decl && ./ptr_decl
```

```text
2 2
2
```

`int* p` 和 `int *p` 意思没区别，争论的只是可读性。前者强调“p 是 `int*` 这种类型”，适合把指针当类型看待的现代写法；后者更贴近声明符的真实语法。两派都有大人物撑腰，挑一种写满整个项目，这比纠结选哪种重要。唯一要防的就是同一行声明多个变量——那时候 `int* a, b` 最容易骗到人。

## 8.3 指针的分类
{: .sec-know}

按指向的东西分，指针有五类，每类规矩差得挺远，先放一张总表：

| 分类 | 典型声明 | 用途 | 关键限制 |
| --- | --- | --- | --- |
| 对象指针 | `int* p` | 指向普通对象或数组元素 | 算术仅限同一数组内 |
| 函数指针 | `int (*)(int, int)` | 回调、分发表 | 不能做算术 |
| 成员指针 | `int T::*` | 指向类的成员 | 配合 `.*` 与 `->*` 使用 |
| `void*` | `void* p` | 通用字节容器 | 不能解引用、不能算术 |
| 空指针 | `nullptr` | 明确表示“不指向任何对象” | 解引用是 UB |

对象指针前面已经唱了主角；函数指针和成员指针留到 8.9 节。这里先把 `void*` 讲透——它是理解“类型系统和内存”分界最顺手的教具。

### void*：万能字节容器
{: .sec-know}

任何对象指针都能隐式转成 `void*`，反过来想转回具体类型，得用 `static_cast` 明示。它的价值在 C 标准库接口里最明显——`std::memcpy` 两个参数就是 `void*`，因为它搬的是字节，压根不关心对象是什么类型。

代价是 `void*` 几乎啥也干不了：不能解引用（没有类型你拿什么解读字节？），也不能加减（走一步多长？C++ 直接禁了；C 里 GCC 曾以扩展形式放行，别当真）。真要操作，先转回具体类型的指针，或者干脆交给 `memcpy` 这类只认字节的函数。

```cpp
#include <cstring>
#include <iostream>

int main() {
    int src = 0x12345678;
    int dst = 0;

    void* v = &src;         // 任何对象指针都能隐式转 void*
    // *v;                  // 错误：void* 不能解引用
    // ++v;                 // 错误：C++ 里 void* 不能做算术

    std::memcpy(&dst, v, sizeof(int));   // 按字节搬运，正是 void* 的主场
    std::cout << std::hex << dst << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr_void.cpp -o ptr_void && ./ptr_void
```

```text
12345678
```

> **坑：** 别把函数指针塞进 `void*`。标准可没保证对象指针和函数指针能互转（POSIX 上能跑、Windows 上也行，但那只是实现约定，不是语言承诺）。要以整数形式拿着函数地址，用 `reinterpret_cast` 配 `uintptr_t`，见 8.9 节。
{: .sec-pit}

## 8.4 指针初始化
{: .sec-know}

指针能拿来初始化的来源就五种：取地址 `&obj`、另一个同类型指针、`nullptr`、`new` 的返回值、还有返回指针的函数。忘写初始化的局部指针里是随机垃圾——这就是“未初始化指针”，解引用它行为完全不可预测：可能崩、可能静默写坏别处的数据、也可能“看起来正常”。最后那种最要命，写过 C 的都懂。

### nullptr：C++11 给“空”一个专属类型
{: .sec-know}

C++98 那会儿，空指针靠字面量 `0` 或宏 `NULL` 表示，俩本质上都是整数。麻烦就出在重载决议上：

```cpp
void f(int);
void f(char*);
```

调用 `f(0)` 命中 `f(int)`——0 是 int 字面量，精确匹配，转指针反而多一步转换。调用 `f(NULL)` 更乱：`NULL` 展开成 `0` 时调 `f(int)`，展开成 `0L` 时直接二义性报错，到底展开成啥全看实现的心情。想调指针版本？门都没有。

C++11 引入关键字 `nullptr`，类型是 `std::nullptr_t`（在 `<cstddef>` 里）。它能隐式转成任意指针类型和成员指针类型，但转不成 int——重载决议从此没歧义。顺带把读写习惯也统一了：判空写 `p == nullptr`，置空写 `p = nullptr`。

```cpp
// 需要 -std=c++11
#include <cstddef>
#include <iostream>

void f(int)   { std::cout << "f(int)\n"; }
void f(char*) { std::cout << "f(char*)\n"; }

int main() {
    f(0);          // 0 是 int 字面量：选 f(int)
    f(nullptr);    // nullptr 只能转指针：选 f(char*)
    // f(NULL);    // 结果看 NULL 展开成什么：可能是 f(int)，也可能报二义

    int* p = nullptr;
    std::nullptr_t np = nullptr;    // nullptr 自己的类型
    std::cout << "sizeof(nullptr) = " << sizeof(nullptr) << '\n';
    if (p == nullptr && np == nullptr) std::cout << "都是空指针\n";
    return 0;
}
```

```bash
g++ -std=c++11 -O2 -Wall -Wextra ptr_nullptr.cpp -o ptr_nullptr && ./ptr_nullptr
```

```text
f(int)
f(char*)
sizeof(nullptr) = 8
都是空指针
```

`sizeof(nullptr)` 等于 `sizeof(void*)`，LP64 下就是 8。另外 `std::nullptr_t` 到 int 没有隐式转换，所以 `int n = nullptr;` 编不过——语言替你挡下了这类手滑。

### const 与指针的四种组合
{: .sec-know}

`const` 既能修饰指针指着的那个对象，也能修饰指针本身，两种还能叠加。记这个我有个土办法：`const` 在 `*` 左边管“被指的东西”，在 `*` 右边管“指针自己”。

| 写法 | 读法 | 指针可变 | 所指对象可变 |
| --- | --- | --- | --- |
| `const int* p` | 指向 const 的指针 | 是 | 否 |
| `int const* p` | 同上，与上一行完全等价 | 是 | 否 |
| `int* const p` | const 指针 | 否 | 是 |
| `const int* const p` | 都不可变 | 否 | 否 |

```cpp
#include <iostream>

int main() {
    int a = 10, b = 20;

    const int* p1 = &a;        // *p1 不能改，p1 能改
    int* const p2 = &a;        // p2 不能改，*p2 能改
    const int* const p3 = &a;  // 都不能改

    p1 = &b;        // OK：换指向
    // *p1 = 99;    // 错误：对象是 const
    // p2 = &b;     // 错误：指针是 const
    *p2 = 99;       // OK：a 被改成 99
    // p3 = &b;     // 错误
    // *p3 = 1;     // 错误

    std::cout << a << ' ' << b << ' ' << *p1 << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr_const.cpp -o ptr_const && ./ptr_const
```

```text
99 20 20
```

这里有个容易被忽略的规则：把 `int*` 隐式转成 `const int*` 没问题（加限制永远安全），反过来必须显式 `const_cast`。而且 `const_cast` 只是扒掉类型上的 const 标记——要是对象定义时本身就是 const，靠去 const 的指针去写它，就是 UB。const 不是装饰噪音，编译器真拿它当回事。

### 辨析：野指针、空悬指针、空指针
{: .sec-iv}

这三个词常被混着说，其实成因完全不一样：

- **未初始化指针**：出生时没人管，里面是栈上的随机垃圾。指向哪里完全碰运气。
- **野指针**：泛指“值不可信”的指针，未初始化指针是它的典型成因；把随机地址赋给它也算。
- **空悬指针**（dangling pointer）：曾经有效，但所指对象已经销毁——返回局部变量地址、`delete` 之后继续用、容器扩容导致元素搬家，都是常见成因。

空指针正好反过来：它的值清清楚楚是个 `nullptr`，明明白白表示“我啥也不指”。判空能防住它；野指针和空悬指针就只能靠纪律加工具了（AddressSanitizer 能抓住大部分空悬访问）。

```cpp
// 需要 -std=c++11
#include <iostream>

int* danger() {
    int local = 7;
    return &local;    // undefined behavior：返回局部变量地址
}                     // g++ 会给出 -Wreturn-local-addr 警告

int main() {
    int* wild;                  // 未初始化指针：值是垃圾
    // std::cout << *wild;      // undefined behavior

    int* dangling = danger();   // 空悬指针：指向的对象已销毁
    // std::cout << *dangling;  // undefined behavior

    int* nullp = nullptr;       // 空指针：明确、可判空
    if (nullp == nullptr) std::cout << "nullp 判空通过\n";

    wild = nullptr;             // 用不到了就置空，把“值不可信”变成“值明确”
    dangling = nullptr;
    return 0;
}
```

```bash
g++ -std=c++11 -Wall -Wextra ptr_dangling.cpp -o ptr_dangling && ./ptr_dangling
```

```text
nullp 判空通过
```

> **警告：** 解引用空指针、野指针、空悬指针，全都是 undefined behavior。民间总说“解引用空指针会崩”，那是经验不是标准——优化器有权假定你不会解引用空指针，并据此删掉它认为走不到的检查代码，后果可能比崩还诡异。
{: .sec-warn}

## 8.5 指针运算
{: .sec-know}

指针能玩的运算少得可怜，但每一条边界都写得明明白白：

- **加减整数**：`p + 1` 不是地址加 1，而是前进 `sizeof(元素类型)` 字节。`int*` 走 4 字节，`double*` 走 8 字节，步长由类型决定——这就是“指针有类型”的回报。
- **有效性边界**：指针算术只对“指向数组元素的指针”有定义，结果必须仍指向数组元素，或指向“最后一个元素的下一格”（尾后位置）。指向单个对象的指针可当作长度为 1 的数组处理。
- **相减**：同一数组的两个指针相减，得到元素个数差，类型是 `ptrdiff_t`（`<cstddef>`，有符号）。不同数组的指针相减是 UB。
- **比较**：`==`、`!=` 对任意指针都有定义；`<`、`<=`、`>`、`>=` 只对同一数组（或同一对象）内的指针有定义，跨数组比较是 UB。
- **尾后指针**：`arr + N` 这个位置合法存在，可作循环终点，但解引用它是 UB——那格内存不属于这个数组。

```cpp
#include <cstddef>
#include <iostream>

int main() {
    int arr[] = {10, 20, 30, 40, 50};
    int* p = arr;                  // 数组名在表达式里退化成首元素指针

    std::cout << *p << ' ' << *(p + 2) << ' ' << p[4] << '\n';

    int* end = arr + 5;            // 尾后指针：合法存在，解引用是 UB
    std::ptrdiff_t n = end - p;    // 相减得 ptrdiff_t
    std::cout << "元素个数: " << n << '\n';

    double d[3] = {0.5, 1.5, 2.5};
    double* dp = d;
    std::cout << *(dp + 2) << '\n';    // double 步长 8 字节，走两步到 d[2]
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr_arith.cpp -o ptr_arith && ./ptr_arith
```

```text
10 30 50
元素个数: 5
2.5
```

`p[4]` 能写，是因为下标不过是 `*(p + 4)` 的语法糖，8.5 这套和数组那章会再验一次。

> **警告：** 连 `p + 6`（越过尾后一格）这种表达式的求值许可，编译器都不给你——只要形成超出尾后一格的指针值，本身就是 UB。别觉得“只是算算又不用”就没事，优化器对 UB 的脑洞跟你不是一个量级。
{: .sec-warn}

### 数组退化的三个证据
{: .sec-ver}

数组名在多数表达式里会自动转成首元素指针，术语叫“退化”（decay）。光说没用，三个场景能让你亲眼看见退化确实在发生：

```cpp
#include <iostream>

void take_ptr(int* p) {
    std::cout << "函数内 sizeof(p) = " << sizeof(p) << '\n';   // 指针大小，不是数组大小
}

int main() {
    int arr[10];

    // 证据一：sizeof(arr) 是整个数组的字节数
    std::cout << "sizeof(arr) = " << sizeof(arr) << '\n';

    // 证据二：&arr 的类型是“指向整个数组的指针”int(*)[10]，不是 int**
    int (*pa)[10] = &arr;
    std::cout << "&arr+1 前进了 "
              << (reinterpret_cast<char*>(pa + 1) - reinterpret_cast<char*>(pa))
              << " 字节\n";

    // 证据三：传参后退化成 int*，数组大小信息丢失
    take_ptr(arr);
    return 0;
}
```


`pa + 1` 前进 40 字节，因为步长是“一个 `int[10]`”——反过来也说明 `&arr` 带着完整的数组类型信息。一旦传参，大小信息就没了，只剩 `int*`。数组的完整故事在第 09 章，这里先钉一句：**退化发生在传参那一刻，数组和指针本就不是一回事**。

## 8.6 指针的指针
{: .sec-prac}

指针也是对象、也占内存，自然也能有别的指针指着它。`int** pp` 读作“指向 `int*` 的指针”，得解引用两次才够到 `int`。多级指针没引入新规则，纯粹是套娃，只有一个场景它不可替代：**函数要改的是调用者手里的那个指针本身**。

普通传参是值拷贝：函数拿到 `int* p` 的一份副本，改副本碰不到调用者那边的 p。想改，就得把 p 的地址传进去，也就是 `int**`。

```cpp
#include <iostream>

void alloc_slot(int** slot) {    // 通过二级指针改写调用者的指针
    static int storage = 42;
    *slot = &storage;            // *slot 就是调用者手里的那个 p
}

int main() {
    int* p = nullptr;
    alloc_slot(&p);              // 传 p 的地址
    std::cout << *p << '\n';     // p 已经被改写

    int value = 10;
    int* a = &value;
    int** pp = &a;
    std::cout << **pp << '\n';   // 解两次引用才到 int
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra ptr2.cpp -o ptr2 && ./ptr2
```

```text
42
10
```

读多级指针别慌，从变量名顺着运算符优先级走：`**pp` 就是 `*(*pp)`，先看 `*pp`（p 指向的 a），再解一层（a 指向的 value）。三级四级一个道理，但真实代码里三级以上基本都是设计有毛病——先想想是不是该包个结构体。

## 8.7 使用指针
{: .sec-know}

平时用指针就四种姿势：指着单个对象（读写）、在数组上滑来滑去（遍历，配 8.5 的算术规则）、当输出参数（函数往调用者的变量里塞结果）、持有动态内存（这条现在交给智能指针，8.9 节先瞥一眼）。前两种前面讲过了，这里专门聊输出参数——它是裸指针最后的大舞台，而且正在退场。

### 输出参数的三代演进
{: .sec-ext}

第一代是 C 风格：传 `int* out`，函数往里写。缺点一眼就能看出来：调用处那个 `&out` 啥意图也说明不了，可能被拿去“顺便”改点别的，也可能传个空指针进去直接炸。

第二代是 C++17 的 `std::optional`：函数直接返回“可能有值”。语义清楚，缺点是有没有成功是知道了，但失败原因说不清。

第三代是 C++23 的 `std::expected`：返回值里同时装着结果和错误信息，错误路径的载体从指针参数彻底挪回了返回值。

```cpp
// 需要 -std=c++23（std::expected 需要 GCC 12 及以上）
#include <expected>
#include <iostream>
#include <optional>
#include <string>

bool parse_old(const std::string& s, int* out) {         // 第一代：输出参数
    if (s.empty()) return false;
    int v = 0;
    for (char c : s) {
        if (c < '0' || c > '9') return false;
        v = v * 10 + (c - '0');
    }
    *out = v;
    return true;
}

std::optional<int> parse_mid(const std::string& s) {     // 第二代：只报成败
    if (s.empty()) return std::nullopt;
    int v = 0;
    for (char c : s) {
        if (c < '0' || c > '9') return std::nullopt;
        v = v * 10 + (c - '0');
    }
    return v;
}

std::expected<int, std::string> parse_new(const std::string& s) {   // 第三代：带原因
    if (s.empty()) return std::unexpected(std::string("空字符串"));
    int v = 0;
    for (char c : s) {
        if (c < '0' || c > '9') return std::unexpected(std::string("非法字符: ") + c);
        v = v * 10 + (c - '0');
    }
    return v;
}

int main() {
    int out = 0;
    if (parse_old("123", &out)) std::cout << out << '\n';

    if (auto v = parse_mid("456")) std::cout << *v << '\n';

    if (auto r = parse_new("12x"); r.has_value())
        std::cout << *r << '\n';
    else
        std::cout << "失败: " << r.error() << '\n';
    return 0;
}
```

```bash
g++ -std=c++23 -O2 -Wall -Wextra parse_evol.cpp -o parse_evol && ./parse_evol
```

```text
失败: 非法字符: x
```

新写的代码里，“函数要往外吐结果”这个需求，优先用返回值（`optional`/`expected`/结构体）；输出参数只在性能敏感、要复用缓冲区的场景才留着。C 语言接口另说——那边的指针参数本身就是契约的一部分。

## 8.8 分析指针和引用的关系
{: .sec-iv}

引用（reference）就是某个对象的别名。`int& r = x;` 之后，r 就是 x 的另一个名字，对 r 做的所有操作都直接落在 x 上。指针和引用都能做“间接访问”，但语言给它们的契约天差地别：

| 对比项 | 指针 | 引用 |
| --- | --- | --- |
| 可以为空吗 | 可以（`nullptr`） | 不存在空引用 |
| 可以改绑吗 | 可以随时改指向 | 出生时绑定，终生不变 |
| `sizeof` 结果 | 指针大小（LP64 为 8） | 被引用类型的大小 |
| 能取自己的地址吗 | 能（`&p` 得二级指针） | 结果是“被引用对象的地址” |
| 能做算术吗 | 能（受 8.5 规则约束） | 不能 |
| 作为成员时 | 可以默认构造 | 必须在初始化列表里绑定 |

“引用到底占不占内存”是个高频误会点。标准压根不承诺引用占内存——语义上它就是个别名，`sizeof(r)` 吐出来的就是 int 的大小。但在成员变量、函数参数这些位置，编译器实际往往是拿一个指针实现的，只是这条实现细节被类型系统包得严严实实，你碰不到。

```cpp
#include <iostream>

void incr_ptr(int* p) { ++(*p); }    // 调用方写 incr_ptr(&x)
void incr_ref(int& r) { ++r; }       // 调用方写 incr_ref(x)

int main() {
    int x = 5;
    int& r = x;              // 引用必须初始化，之后不可重绑
    int* p = &x;

    r = 100;                 // r 就是 x 的别名
    std::cout << x << '\n';
    std::cout << "sizeof(r) = " << sizeof(r) << '\n';   // int 的大小，不是指针大小

    incr_ptr(&x);
    incr_ref(x);
    std::cout << x << '\n';
    return 0;
}
```


### const 引用绑定临时对象
{: .sec-know}

非 const 左值引用接不住右值（`int& r = a + 2;` 编不过），const 左值引用可以，而且直接绑定临时对象时，会把那个临时对象的寿命拉长到引用的作用域结束。这条规则是 C++98 的设计，为的是让 `const string& s = "abc";` 这类写法不产生悬垂。注意一个限制——寿命延长只发生在“直接绑定”时，跨函数返回引用可不会延长任何东西。

```cpp
// 需要 -std=c++11
#include <iostream>
#include <string>

struct Hold {
    int& r;                            // 引用成员：类因此没有默认构造
    explicit Hold(int& x) : r(x) {}    // 只能在初始化列表里绑定
};

const std::string& danger() {
    std::string local = "temp";
    return local;                      // undefined behavior：返回局部对象的引用
}

int main() {
    int a = 1;
    const int& r1 = a + 2;   // 直接绑定临时对象：寿命延长到 main 作用域结束
    std::cout << r1 << '\n';

    int b = 9;
    Hold h{b};               // 引用成员出生即绑定
    b = 100;
    std::cout << h.r << '\n';   // h.r 就是 b，跟着变

    const int& r3 = a;       // const 引用也能绑普通变量
    std::cout << r3 << '\n';
    return 0;
}
```

```bash
g++ -std=c++11 -O2 -Wall -Wextra ref_temp.cpp -o ref_temp && ./ref_temp
```


> **坑：** `return local;` 这种返回局部对象引用的写法，没有任何编译器能替你拦下来——它语法合法，一跑就是 UB。同理，`T& r = *ptr;` 之前得先判空：解引用空指针是 UB，那之后 r 这个“别名”就建在虚空上了。引用之所以不为空，前提是构造它的每一步都合法。
{: .sec-pit}

什么时候用指针、什么时候用引用？我的一线经验是这样的：**参数可能啥都不指、需要在函数里改指向、或者要参与指针算术——上指针；只是“给对象起个别名”或保证一定有对象——上引用**。接口上引用表达的是“必传且非空”，指针表达的是“可选”。现代 C++ 里“可选”正慢慢改用 `std::optional<T&>` 的替代方案（比如 `T*` 或 `std::optional<std::reference_wrapper<T>>`），所以引用越用越密，裸指针越来越少。

## 8.9 特殊指针
{: .sec-ext}

这一节把几类“不走寻常路”的指针收拢到一起：函数指针、成员指针，外加三个更冷门但面试常考的话题——restrict、`uintptr_t`、strict aliasing。

### 函数指针
{: .sec-know}

函数也有地址，函数指针存的正是“代码段的入口地址”。它的语法是出了名的难读：

```text
int (*fp)(int, int);   // fp 是指针，指向 int(int, int) 类型的函数
```

读法：`(*fp)` 说明 fp 是个指针，外圈 `int (int, int)` 是它指的函数类型。函数名在表达式里会自动退化成函数指针（跟数组退化一个思路），所以 `&add` 和 `add` 都能赋值。现代 C++ 用 `using` 给它起个别名，可读性立刻天差地别。

```cpp
#include <iostream>

int add(int a, int b) { return a + b; }
int mul(int a, int b) { return a * b; }

using BinOp = int (*)(int, int);     // 别名一立，语法恐惧症痊愈

int apply(BinOp op, int x, int y) { return op(x, y); }   // op 当回调用

int main() {
    BinOp f = add;
    std::cout << f(2, 3) << '\n';

    f = &mul;                        // & 可写可不写，函数名本身就是地址
    std::cout << apply(f, 4, 5) << '\n';
    std::cout << apply(add, 6, 7) << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra fptr.cpp -o fptr && ./fptr
```


函数指针不能做算术（`fp + 1` 编不过），比较和赋值倒没问题。回调是它的经典用武之地：排序的比较函数、C 库的钩子、状态机的分发表。

### 辨析：函数指针、std::function 与模板参数
{: .sec-iv}

这三样都能“把可调用物传来传去”，但取舍不一样：

| 方案 | 能装什么 | 开销 | 版本 |
| --- | --- | --- | --- |
| 函数指针 | 只能装无捕获的普通函数 | 一次间接调用，零存储 | — |
| `std::function` | 任何可调用物（含有捕获的 lambda） | 可能有堆分配与间接调用 | C++11 |
| 模板参数 | 编译期已知的具体可调用物 | 通常被内联，零开销 | — |

带捕获的 lambda 是个分水岭：它带着状态，函数指针装不下，`std::function` 装得下。

```cpp
// 需要 -std=c++14
#include <functional>
#include <iostream>

int add(int a, int b) { return a + b; }

int main() {
    std::function<int(int, int)> f1 = add;                  // 装函数
    std::function<int(int, int)> f2 = [](int a, int b) {    // 装无捕获 lambda
        return a - b;
    };
    int c = 10;
    std::function<int(int)> f3 = [c](int x) { return x + c; };   // 带捕获，函数指针装不下

    std::cout << f1(1, 2) << ' ' << f2(1, 2) << ' ' << f3(5) << '\n';
    return 0;
}
```

```bash
g++ -std=c++14 -O2 -Wall -Wextra stdfunc.cpp -o stdfunc && ./stdfunc
```


我一般按这个顺序选：模板参数（性能优先、类型编译期就定）→ 函数指针（C 接口、无状态回调）→ `std::function`（需要运行时存任意可调用物）。

### 成员函数指针与数据成员指针
{: .sec-know}

类成员也有地址，但“成员指针”不是普通指针：它存的不是绝对地址，而是“相对对象起始位置的偏移 + 类型信息”，必须绑着某个具体对象才用得了。语法上用 `T::*` 声明，用 `.*`（对象）或 `->*`（对象指针）调用。

```cpp
#include <iostream>

struct Counter {
    int base = 100;                          // 类内默认初始化
    int twice(int x)  { return 2 * x + base; }
    int thrice(int x) { return 3 * x + base; }
};

int main() {
    Counter c;

    int Counter::* dp = &Counter::base;      // 数据成员指针
    std::cout << c.*dp << '\n';              // 对象用 .*
    Counter* pc = &c;
    std::cout << pc->*dp << '\n';            // 指针用 ->*

    int (Counter::* fp)(int) = &Counter::twice;   // 成员函数指针
    std::cout << (c.*fp)(7) << '\n';
    fp = &Counter::thrice;
    std::cout << (pc->*fp)(7) << '\n';
    return 0;
}
```

> **注意：** 成员函数指针转不成普通函数指针。它的调用约定里带着“得传 this”这回事，签名本身就对不上。想统一包装，用 `std::function` 加 lambda 把对象和成员绑一起。另外成员函数指针的 `sizeof` 可能大于 8 字节（MSVC 上常是 16），别对它的尺寸做假设。

### restrict：标准里没有，GCC 里有
{: .sec-know}

C99 有 `restrict` 关键字，它向编译器承诺“这个指针是访问对象的唯一途径”，编译器据此才敢做向量化和重排。标准 C++ 一直没收录它——可性能敏感的代码离不了，于是各家编译器都以扩展形式支持：GCC/Clang 用 `__restrict`（或 `__restrict__`），MSVC 用 `__restrict`。

```cpp
// GCC/Clang 扩展，非标准 C++
#include <cstddef>
#include <iostream>

void scale(float* __restrict dst, const float* __restrict src,
           std::size_t n, float k) {
    for (std::size_t i = 0; i < n; ++i)
        dst[i] = src[i] * k;     // __restrict 承诺 dst 与 src 不重叠，编译器敢优化
}

int main() {
    float src[] = {1.0f, 2.0f, 3.0f};
    float dst[3];
    scale(dst, src, 3, 2.0f);
    std::cout << dst[0] << ' ' << dst[1] << ' ' << dst[2] << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra restrict_demo.cpp -o restrict_demo && ./restrict_demo
```

```text

```

这个承诺是用刀刃担保的：要是 `dst` 和 `src` 实际重叠，`__restrict` 之下的优化结果就是 UB。加这个关键字前，先确认调用契约，或者干脆加个断言查区间不重叠。

### 把地址当整数：uintptr_t 与 intptr_t
{: .sec-know}

想在地址上做位运算（对齐检查、哈希、打标签），得先把指针转成整数。`<cstdint>` 提供 `std::uintptr_t`（无符号）和 `std::intptr_t`（有符号）：就是能装下 `void*` 的整数类型。注意它们是**可选的**——标准不强制存在，只是所有主流平台都给了一份。

```cpp
// 需要 -std=c++11
#include <cstdint>
#include <iostream>

int main() {
    int x = 5;
    void* pv = &x;

    std::uintptr_t bits = reinterpret_cast<std::uintptr_t>(pv);
    std::cout << "地址对 16 取余: " << (bits % 16) << '\n';   // 对齐情况一眼可见

    void* back = reinterpret_cast<void*>(bits);   // 整数转回指针，仍是原地址
    std::cout << *static_cast<int*>(back) << '\n';
    return 0;
}
```

```bash
g++ -std=c++11 -O2 -Wall -Wextra uintptr_demo.cpp -o uintptr_demo && ./uintptr_demo
```

### 对齐与 strict aliasing
{: .sec-warn}

每个类型都有对齐要求（`alignof`）：`int` 通常 4 字节对齐，`double` 8 字节。编译器把对象摆在对齐的地址上，是为了让 CPU 一次读写就能完成。这条规则你平时毫无感觉，直到撞上两个问题。

问题一：跨类型读内存。想看 `float` 的位模式，`*reinterpret_cast<int*>(&f)` 看着能跑，实际是 UB——C++ 的 strict aliasing 规则说：不许用不兼容类型的左值去访问对象（`char`/`unsigned char`/`std::byte` 除外，它们能看任何对象）。编译器优化时假定“int* 和 float* 不会指向同一处”，你那点小动作会被优化得干干净净。

问题二：手动构造对象时对不齐。`std::memcpy` 到 `alignas(16)` 的缓冲区没问题，可 `new char[64]` 的指针直接 `reinterpret_cast` 成 `double*` 用就有风险——`char` 数组只保证 1 字节对齐（实际常常是 16，但那是实现的福利，不是标准承诺）。

正经做法是拿 `memcpy` 逐字节搬（编译器认得它，开 `-O2` 后零开销），C++20 起更好的选择是 `std::bit_cast`：

```cpp
// 需要 -std=c++20
#include <bit>
#include <cstring>
#include <iostream>

int main() {
    float f = 1.0f;

    int via_memcpy = 0;
    std::memcpy(&via_memcpy, &f, sizeof f);    // 逐字节搬运：行为有定义

    int via_bitcast = std::bit_cast<int>(f);   // C++20：语义同样干净，还能用于 constexpr

    // int bad = *reinterpret_cast<int*>(&f); // undefined behavior：违反 strict aliasing
    std::cout << std::hex << via_memcpy << ' ' << via_bitcast << '\n';
    return 0;
}
```

```text
3f800000 3f800000
```

`1.0f` 的 IEEE 754 位模式就是 `0x3F800000`。历史上不少代码靠 type punning 混过去，靠的是旧编译器不优化；现在的编译器真敢删代码，别赌。

### 智能指针预览
{: .sec-ext}

裸指针最大的风险是“谁来释放”没人兜底。C++11 起标准库给了答案：`std::unique_ptr` 独占所有权、零开销，出作用域自动释放；`std::shared_ptr` 引用计数共享；`std::weak_ptr` 打破循环引用。它们不是新指针，而是“带析构契约的指针包装器”。

```cpp
// 需要 -std=c++14（std::make_unique）
#include <iostream>
#include <memory>

struct Resource {
    ~Resource() { std::cout << "Resource 析构\n"; }
};

int main() {
    {
        std::unique_ptr<Resource> up = std::make_unique<Resource>();
        std::shared_ptr<Resource> sp = std::make_shared<Resource>();
        std::cout << "引用计数: " << sp.use_count() << '\n';
    }   // 作用域结束：sp 先析构（后构造先析构），两个 Resource 自动释放
    std::cout << "作用域结束\n";
    return 0;
}
```

```bash
g++ -std=c++14 -O2 -Wall -Wextra smart_preview.cpp -o smart_preview && ./smart_preview
```

```text
引用计数: 1
Resource 析构
Resource 析构
作用域结束
```

本章先立个坐标：**拥有内存的指针交智能指针，只是“看着”对象的场景才用裸指针**（观察者、视图、非拥有引用）。完整的所有权设计、循环引用、自定义删除器，留给动态内存那一章。

## 8.10 技术解惑
{: .sec-ts}

### 解引用空指针一定会崩溃吗

不一定。标准把解引用空指针划成 UB，意思是“语言不再给你任何承诺”。硬件层面访问 0 地址通常触发页错误，但编译器优化可能抢在硬件前面动手：它假定空指针解引用不会发生，于是把“防御性判空”当死代码删了。真实的诡异案例是“判空代码被优化没了，然后崩在判空之后”。结论：别依赖崩溃方式，更别写依赖 UB 行为的代码。

### 所有指针都一样大吗

对象指针在给定平台上大小一致（LP64 下 8 字节），但函数指针和成员指针是另一码事。成员函数指针在 GCC 上常见 16 字节，MSVC 上也可能是 16；它得装下“偏移 + 调整信息”甚至虚表相关的内容。对指针大小做假设的代码（比如塞进 `void*` 再取出来），换成 `uintptr_t` 或模板才是正路。

### 裸指针的当代定位

裸指针没死透，它的地盘收缩到了三块：观察非拥有对象（不负责释放）、遍历数组（`T*` 当迭代器用）、对接 C 接口。凡涉及“这块内存归谁”的地方，用 `std::unique_ptr`/`std::shared_ptr`；涉及“可能没结果”的地方，用 `std::optional`/`std::expected`。我自己就记一句：**这个指针要不要 delete？要，就别碰裸指针。**

### 常见 UB 清单
{: .sec-warn}

指针相关的 UB 高发区，逐条对着查：

- 解引用空指针、未初始化指针、空悬指针。
- 解引用尾后指针（`arr + N` 可以存在，`*(arr + N)` 不行）。
- 指针算术越过“尾后一格”，或在不同数组之间做算术。
- 用 `<` 等关系运算符比较不相关对象的指针。
- `delete` 与 `new[]` 错配（`new[]` 的用 `delete` 释放）。
- 通过 `const_cast` 去掉 const 后写入**定义时就是 const** 的对象。
- 违反 strict aliasing 的跨类型访问（用 `memcpy` 或 `std::bit_cast` 替代）。
- 通过错误类型的函数指针调用函数。

## 动手练
{: .sec-ex}

1. **两版交换**：实现 `swap_ptr(int* a, int* b)` 和 `swap_ref(int& a, int& b)`，在 `main` 里分别调用，观察调用处写法的差异（一个要 `&x`，一个直接传 x）。再想想：如果函数签名是 `swap_ptr(int* const a, int* const b)`，还能交换吗？
2. **分发表**：写三个函数 `op_add`、`op_sub`、`op_mul`，用 `using Op = int(*)(int,int)` 和一个函数指针数组实现命令行四则运算（输入 1/2/3 选操作），用 `nullptr` 表示非法选项并判空。
3. **找茬**：手写一段包含下列问题的代码——解引用未初始化的指针、返回局部变量的地址、用 `delete` 释放 `new[]` 的内存——逐处指出问题类别（未初始化/空悬/错配），修复后用 `-Wall -Wextra` 复核编译器能否抓到。
4. **对齐侦探**：分配 `double d[8]`，用 `reinterpret_cast<std::uintptr_t>` 检查首地址是否 8 字节对齐（`addr % 8 == 0`），打印结论；再用 `alignof(double)` 对照你的假设。

## 变式追问
{: .sec-think}

1. **`const int* p` 和 `int* const p` 总记混，有没有可靠的读法？** 有。从右往左读声明：`const int* p` 是“p 是指针，指向 const int”——const 靠着 int；`int* const p` 是“p 是 const 指针，指向 int”——const 靠着 p。再看等价形式 `int const* p`，const 依然在 `*` 左边，规则统一成一句：**const 在 `*` 左边管对象，在 `*` 右边管指针**。
2. **函数指针为什么不能保证转成 `void*`？** 标准把对象和函数的存储模型分开对待：对象指针要求能表达“任何字节的地址”，函数指针的表示方式（如指令地址、带描述符的句柄）标准没有约束。某些架构（历史上如 Harvard 架构机器）里两者地址空间都不连通。POSIX 平台事实上互通，所以 `dlsym` 返回 `void*` 再转函数指针能工作，但这是平台契约。跨平台代码里，函数指针就老老实实用函数指针类型传递。
3. **引用到底占不占内存？** 语义上不占：标准说引用不是对象，`sizeof(T&)` 给出 `T` 的大小。实现上通常占：作为函数参数或成员时，编译器拿指针实现它——但这个指针被类型系统藏起来了，你既取不到它的地址，也改不了它的值。判断依据看用途：如果引用成员导致类变大（`sizeof(S)` 含一个 8 字节的实现指针），那是实现细节的自然结果，不是标准的承诺。
4. **`delete p; p = nullptr;` 这个双保险值得写吗？** 分场景。指针马上离开作用域：白写。指针是长寿命的成员、且可能被重复 delete 或误用：值得——把“空悬”变成“明确为空”，误用从 UB 降级成可判空的错误。但更好的答案是：用 `std::unique_ptr`，`reset` 自带置空，这个问题从根上消失。C++11 之后的代码里还需要手动 delete 本身，就说明所有权设计该返工了。
