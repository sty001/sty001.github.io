## 25.1 技术基础
{: .sec-expl}

### 25.1.1 原书 DirectX 方案为什么被替换
{: .sec-know}

保留的背景：DirectShow 把播放器拆成一串过滤器（源过滤器读文件、拆分器解容器、解码器解压缩、渲染器出画面），数据沿管线流动。这个"管线 + 过滤器"的模型本身是媒体处理的正确抽象，FFmpeg 的管线、GStreamer 的 element 都是一脉相承。

替换的理由有三条：DirectShow 只在 Windows 上活着，微软自己都已把媒体重心移到 Media Foundation；DirectShow 的 COM 接口与 C++ 的 RAII 语义格格不入，引用计数手动管理极易漏；主流跨平台播放器（VLC、mpv）走的都是 FFmpeg 路线，社区资料、解码能力、格式覆盖全面占优。所以本篇以 FFmpeg 为解码后端、SDL2 为音频输出，这套组合在 Windows、Linux、macOS 上行为一致。

### 25.1.2 音频基础：采样率、位深、声道与回调模型
{: .sec-know}

数字音频把连续声波切成一秒里固定数量的快照存下来，三个参数定死一段音频的数据量：

| 参数 | 含义 | 常见值 |
| --- | --- | --- |
| 采样率 | 每秒采多少个点 | 44100 Hz、48000 Hz |
| 位深 | 每个点用多少比特表示 | 16 位整型、32 位浮点 |
| 声道数 | 同时记录几条独立音轨 | 1 单声道、2 立体声 |

未压缩的裸采样流叫 PCM，码率就是三者相乘：CD 音质 44100 × 16 × 2 = 1411200 bit/s，约 1.41 Mbps，一分钟 10 MB 上下。为什么采样率取 44100？奈奎斯特定理：采样率必须超过信号最高频率的两倍才能无失真还原，人耳上限约 20 kHz，所以 40 kHz 出头起步，44100 是历史折中。

播放的驱动方式决定整个软件的线程结构。现代音频输出几乎清一色是**回调模型**：你向设备注册一个函数，设备每消费完一小块数据（比如 1024 个采样）就调用它一次，让你填下一块。SDL 的音频回调就是这个模型。

回调运行在设备驱动的音频线程上，频率极高（44100 Hz、每块 1024 采样意味着每 23ms 一次），它有一条铁律：

| 铁律 | 违反的后果 |
| --- | --- |
| 只读写预分配好的缓冲 | 在回调里 new/delete 触发堆锁，一旦阻塞就断流 |
| 不加锁、不碰互斥量 | 持锁线程被抢占，音频线程排队等锁，爆音 |
| 不做 IO、不打日志 | 文件系统调用毫秒级延迟，直接卡死这一块 |
| 数据不够就填静音 | 宁可出 23ms 静音，绝不等数据 |

> **坑：** 回调里"就打一行日志"是新手最常踩的雷。日志要走 IO，一次几十毫秒，音频线程 23ms 必须交货——结果是周期性爆音，而且只在开了日志的调试构建里出现，极难排查。
{: .sec-pit}

回调之外怎么办？解码线程往一个线程安全的环形缓冲里写，回调从缓冲里读。这个缓冲的设计是 25.2.2 的主角。

### 25.1.3 视频基础：YUV、I/P/B 帧、GOP、PTS/DTS
{: .sec-expl}

**YUV 与 RGB**。RGB 每个像素三份分量；YUV 把亮度（Y）与色度（U、V）分开存，人眼对亮度敏感、对色度迟钝，所以色度可以抽稀。最常见的是 4:2:0：每 2x2 的像素组共享一组色度，数据量比 RGB 少一半。解码器输出的原始帧几乎都是 YUV，屏幕最终要 RGB，中间那次转换（以及可能的缩放）就是 FFmpeg 里 swscale 的活。

**I/P/B 帧与 GOP**。视频压缩不逐帧存全图：I 帧是完整画面（帧内压缩）；P 帧只存相对前一帧的差分；B 帧同时参考前后帧，压缩率最高。从 I 帧到下一个 I 帧之间叫一个 GOP（图像组），典型两三百帧。GOP 的直接后果是 seek 的成本：想从第 5000 帧开始解，必须先找到它前面最近的 I 帧，把整个 GOP 解下来丢掉前面不要的——seek 慢、且 seeking 状态必须有单独处理，这是 25.2.4 状态机里 Seeking 状态存在的原因。

**PTS 与 DTS**。B 帧参考后帧导致解码顺序和显示顺序不一致：显示顺序的 ABC 里，B 可能要在 C 之后才能解出来。DTS（解码时间戳）标"什么时候该解它"，PTS（显示时间戳）标"什么时候该显示它"。没有 B 帧的流两者相等；有 B 帧的流，解码器输出帧的顺序是乱序的，排序必须按 PTS。这也解释了 FFmpeg 的 send/receive 模型为什么一次 send 可能收到零帧或多帧——解码器内部要做重排缓冲。

**容器与编解码器分离**。MP4、MKV 是容器，负责打包多路流（视频轨、音频轨、字幕）与索引；H.264、H.265 是编解码器，负责压缩单路画面。一个 MP4 里的视频可能是 H.264 也可能是 H.265。解复用（读容器、拆出压缩包）与解码（还原像素）因此是 FFmpeg 里两套独立的库。

### 辨析：PTS 与 DTS
{: .sec-iv}

只解不显（转码、抽帧）时关心 DTS；按时间轴展示时关心 PTS。同步比较永远用 PTS——音频时钟走的是"已播放采样数换算的时间"，两边必须同轴。把 DTS 当 PTS 用是常见笔误，症状是画面整体提前或滞后一个固定偏移，B 帧多的流偏得更乱。

## 25.2 系统分析和设计
{: .sec-expl}

### 25.2.1 线程模型：解码、音频与渲染三线分工
{: .sec-know}

最小可用的播放器需要三个执行流：

| 线程 | 职责 | 节拍 |
| --- | --- | --- |
| 解码线程 | av_read_frame 取包、送解码器、把结果压进队列 | 尽力而为，缓冲满了就等 |
| 音频线程 | SDL 内部回调，从环形缓冲取采样交给设备 | 设备驱动节拍，约 23ms 一次 |
| 主/UI 线程 | 事件处理、界面、视频帧按音频时钟上屏 | vsync 或 UI 刷新率 |

音频当节拍器、解码当生产者、渲染当消费者的划分，核心动机是音频对断流最敏感（听感上不可掩盖），所以把最不能阻塞的部分交给驱动回调，其余线程围着它转。线程退出用 C++20 的 `std::jthread` 配 `stop_token`：析构自动 request_stop 加 join，停止路径不会忘记收尾。

```cpp
// jthread_demo.cpp —— 需要 -std=c++20
// GCC 10+ / Clang 13+ / MSVC 19.28+ 才有 jthread
#include <chrono>
#include <cstdio>
#include <thread>

int main() {
    std::jthread worker([](std::stop_token st) {
        int tick = 0;
        while (!st.stop_requested()) {
            std::printf("tick %d\n", ++tick);
            std::this_thread::sleep_for(std::chrono::milliseconds(100));
        }
        std::puts("worker: 收到停止信号，退出");
    });

    std::this_thread::sleep_for(std::chrono::milliseconds(350));
    worker.request_stop();
    // 不用 join：jthread 析构自动 request_stop + join
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra jthread_demo.cpp -o jt && ./jt
```

```text
tick 1
tick 2
tick 3
tick 4
worker: 收到停止信号，退出
```

输出取自某 Linux 环境，tick 次数在 3 到 4 之间浮动（取决于线程启动与调度时刻），最后一行一定出现——这就是 stop_token 的价值：停止是协作式的、有确认的，不是发个标志位然后祈祷。

### 25.2.2 无锁 SPSC 环形缓冲
{: .sec-know}

解码线程（单生产者）与音频回调（单消费者）之间只需要 **SPSC（单生产者单消费者）** 环形缓冲：一块预分配的定长数组，两个下标 head（写位置）与 tail（读位置）各自只有一个线程写，另一方只读。写方先读对方的 tail 算空闲空间，写完发布自己的 head；读方对称。容量取 2 的幂，取模变成按位与。

```cpp
// SPSC 环形缓冲核心（完整可运行程序见 25.3.2）
class RingBuffer {
public:
    explicit RingBuffer(std::size_t cap_pow2) : buf_(cap_pow2), mask_(cap_pow2 - 1) {}

    // 生产者线程调用。缓冲满时少写，绝不等待
    std::size_t write(const float* src, std::size_t n) {
        std::size_t w = head_.load(std::memory_order_relaxed);  // 自己写的，relaxed
        std::size_t r = tail_.load(std::memory_order_acquire);  // 看对方发布的进度
        n = std::min(n, buf_.size() - (w - r));
        for (std::size_t i = 0; i < n; ++i) buf_[(w + i) & mask_] = src[i];
        head_.store(w + n, std::memory_order_release);          // 写完才发布新 head
        return n;
    }

    // 消费者线程调用，与 write 对称
    std::size_t read(float* dst, std::size_t n) {
        std::size_t r = tail_.load(std::memory_order_relaxed);
        std::size_t w = head_.load(std::memory_order_acquire);
        n = std::min(n, w - r);
        for (std::size_t i = 0; i < n; ++i) dst[i] = buf_[(r + i) & mask_];
        tail_.store(r + n, std::memory_order_release);
        return n;
    }

private:
    std::vector<float> buf_;
    std::size_t mask_;
    alignas(64) std::atomic<std::size_t> head_{0};   // 只有生产者写
    alignas(64) std::atomic<std::size_t> tail_{0};   // 只有消费者写
};
```

内存序只用了一对：自己的下标 relaxed（没人跟它竞争），对方的下标 acquire、发布用 release——release 保证数据写入先于下标更新对对方可见，acquire 保证读到新下标后一定能读到新数据。SPSC 能做到这么轻，正是因为每个原子量只有一个写者。

`alignas(64)` 是防**假共享**：head 与 tail 若落在同一条 64 字节缓存行上，生产者每更新 head 会把消费者核上的缓存行打回无效（反过来也一样），两个核隔着缓冲互掐。两个下标各占一条缓存行，互不传染。这个改动的收益可以实测：把 alignas 去掉，多线程吞吐常有可观的劣化。

> **坑：** 无符号下标回绕是这套设计的一部分——`w - r` 在回绕后依然等于在途数据量（前提是在途量小于容量），别"好心"改成有符号数，回绕语义就坏了。
{: .sec-warn}

### 25.2.3 音视频同步：音频主时钟与丢帧策略
{: .sec-know}

两路流各自推进，总要选一个当**主时钟**。选音频的理由：音频设备按固定采样率消化数据，误差平滑积累、听感不可跳变；视频帧晚一帧早一帧人眼毫无察觉。所以以"已播放采样数 / 采样率"为主时钟，视频帧上屏前拿自己的 PTS 与它比较：视频超前就等，落后超过一帧就丢帧追赶。

```cpp
// av_sync.cpp —— 需要 -std=c++20
// 音频主时钟：视频帧上屏前拿 PTS 与音频时间比较，落后超过一帧就丢帧。
// 示例数值全取 2 的负幂（1/64、1/32），浮点运算零舍入误差，所有平台输出一致。
#include <cstdio>

double audio_clock(long long played_samples, int sample_rate) {
    return static_cast<double>(played_samples) / sample_rate;
}

int main() {
    const int sample_rate = 64000;
    const double frame_dur = 0.03125;             // 32fps，1/32 是精确的二进制小数
    const double adv[] = {0.046875, 0.015625};    // 音频每帧推进 3/64 与 1/64 交替

    long long played = 0;
    int shown = 0, dropped = 0;
    for (int i = 0; i < 8; ++i) {
        double pts = i * frame_dur;
        played += static_cast<long long>(adv[i % 2] * sample_rate);
        double diff = pts - audio_clock(played, sample_rate);
        if (diff < -frame_dur) {
            std::printf("pts=%f  diff=%+f  丢帧\n", pts, diff);
            ++dropped;
        } else {
            std::printf("pts=%f  diff=%+f  显示\n", pts, diff);
            ++shown;
        }
    }
    std::printf("显示 %d 帧, 丢 %d 帧\n", shown, dropped);
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra av_sync.cpp -o sync && ./sync
```

```text
pts=0.031250  diff=-0.031250  显示
pts=0.062500  diff=-0.046875  丢帧
pts=0.093750  diff=-0.031250  显示
pts=0.125000  diff=-0.046875  丢帧
pts=0.156250  diff=-0.031250  显示

```

策略的另一半是"重复"：视频比音频超前超过一帧时，把上一帧多挂一拍再换新帧。丢帧用于追赶，重复用于等待，阈值都取一帧时长，超过两帧还追不上就该考虑主时钟偏移了。

### 25.2.4 播放器控制类：状态机设计
{: .sec-know}

播放器控制接口（open/play/pause/seek/stop）背后是一个四态状态机，每个事件只在合法状态里生效：

| 当前状态 | 事件 | 动作 | 下一状态 |
| --- | --- | --- | --- |
| Stopped | play | 启动解码线程、打开音频设备 | Playing |
| Playing | pause | 暂停音频设备、解码线程转入等待 | Paused |
| Playing | seek | 清队列、flush 解码器、定位目标 | Playing |
| Paused | play | 恢复设备与线程 | Playing |
| Paused / Playing | stop | 停线程、关设备、释放资源 | Stopped |
| Stopped | seek | 拒绝（无流可定位） | Stopped |

seek 是最讲究的动作：环形缓冲里可能有按旧位置解码的数据，解码器内部还有 B 帧重排缓存，必须清空队列后调用 `avcodec_flush_buffers`，再从目标时间最近的 I 帧重新取包——跳过任何一步，seek 完看到的都是新旧混合的画面。

```cpp
// player_ctrl.cpp —— 需要 -std=c++20
#include <cstdio>

enum class PlayerState { Stopped, Playing, Paused, Seeking };

const char* name(PlayerState s) {
    switch (s) {
        case PlayerState::Stopped: return "Stopped";
        case PlayerState::Playing: return "Playing";
        case PlayerState::Paused:  return "Paused";
        case PlayerState::Seeking: return "Seeking";
    }
    return "?";
}

class MediaPlayer {
public:
    void play() {
        switch (state_) {
            case PlayerState::Stopped: [[fallthrough]];
            case PlayerState::Paused:
                start_threads();
                state_ = PlayerState::Playing;
                break;
            case PlayerState::Seeking:
                pending_play_ = true;    // seek 完自动开播
                break;
            case PlayerState::Playing:
                break;                   // 幂等：重复 play 不重启线程
        }
    }
    void pause() {
        if (state_ == PlayerState::Playing) {
            pause_audio();
            state_ = PlayerState::Paused;
        }
    }
    void seek(double sec) {
        if (state_ == PlayerState::Stopped) return;
        flush_queues();                  // 清空包队列与帧队列
        flush_decoders();                // avcodec_flush_buffers
        target_ = sec;
    }
    void stop() {
        stop_threads();
        state_ = PlayerState::Stopped;
    }
    PlayerState state() const { return state_; }

private:
    void start_threads()  { std::puts("[threads] start"); }
    void pause_audio()    { std::puts("[audio] paused"); }
    void flush_queues()   { std::puts("[queues] flushed"); }
    void flush_decoders() { std::puts("[decoders] flushed"); }
    void stop_threads()   { std::puts("[threads] stopped"); }

    PlayerState state_ = PlayerState::Stopped;
    double target_ = 0.0;
    bool pending_play_ = false;
};

int main() {
    MediaPlayer p;
    p.play();
    std::printf("state = %s\n", name(p.state()));
    p.pause();
    std::printf("state = %s\n", name(p.state()));
    p.seek(12.5);
    std::printf("state = %s\n", name(p.state()));
    p.stop();
    std::printf("state = %s\n", name(p.state()));
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra player_ctrl.cpp -o pc && ./pc
```

```text
[threads] start
state = Playing
[audio] paused
state = Paused
[queues] flushed
[decoders] flushed
state = Paused
[threads] stopped
state = Stopped
```

`[[fallthrough]]`（C++17）标明 Stopped 与 Paused 共用 play 分支是有意为之，`-Wimplicit-fallthrough` 不会再报。接口设计要点：play 幂等、stop 任何状态都可调、seek 在 Stopped 下拒绝——把非法转移在接口层拦掉，状态机就不可能进入未定义组合。

## 25.3 实现媒体控制类
{: .sec-prac}

### 25.3.1 FFmpeg 管线的现代 C++ 封装
{: .sec-know}

FFmpeg 是 C API，五个库各管一段：

| 库 | 职责 | 常用入口 |
| --- | --- | --- |
| libavformat | 解复用/复用（容器层） | avformat_open_input、av_read_frame |
| libavcodec | 编解码 | avcodec_send_packet、avcodec_receive_frame |
| libavutil | 工具：时间基、错误码、内存 | av_q2d、av_strerror |
| libswscale | 像素格式转换与缩放 | sws_getContext、sws_scale |
| libswresample | 音频重采样 | swr_convert |

数据流固定成一条线：`av_read_frame` 从容器取出压缩包（AVPacket）→ `avcodec_send_packet` 送进解码器 → `avcodec_receive_frame` 取出原始帧（AVFrame）→ 交给音频或视频支路。注意收发两侧的量是"压缩包"与"原始帧"——解码前数据以 AVPacket 流通，解码后以 AVFrame 流通，别混。

这些 C 资源全是裸指针加成对分配释放函数，现代 C++ 的包法就是 `unique_ptr` 配自定义 deleter，一行不写裸 new/free：

```cpp
// RAII 包装片段（完整程序见 25.3.3）
struct PacketDel   { void operator()(AVPacket* p)        const { av_packet_free(&p); } };
struct FrameDel    { void operator()(AVFrame* f)         const { av_frame_free(&f); } };
struct CodecCtxDel { void operator()(AVCodecContext* c)  const { avcodec_free_context(&c); } };
struct FmtCtxDel   { void operator()(AVFormatContext* f) const { avformat_close_input(&f); } };
using PacketUPtr   = std::unique_ptr<AVPacket, PacketDel>;
using FrameUPtr    = std::unique_ptr<AVFrame, FrameDel>;
using CodecCtxUPtr = std::unique_ptr<AVCodecContext, CodecCtxDel>;
using FmtCtxUPtr   = std::unique_ptr<AVFormatContext, FmtCtxDel>;
```

反面教材长这样——每一步单看都"能跑"，合起来就是一个稳定泄漏的播放器：

```cpp
// 反面示例：泄漏三连，别抄
AVPacket* pkt = av_packet_alloc();
while (av_read_frame(fmt, pkt) >= 0) {
    avcodec_send_packet(cc, pkt);        // 1. send 完不 unref，包内引用计数一直挂着
    avcodec_receive_frame(cc, frame);    // 2. 不循环收：有 B 帧的流 send 很快返回 EAGAIN
}
// 3. 循环退出后 pkt、frame 没有 free——每次播放漏一批
```

错误处理统一成"返回值小于零即失败"，需要细节时 `av_strerror` 转成文本。骨架程序为了篇幅用"失败即返回"的粗粒度处理，真实项目把错误码和文件名一起记进日志。

### 25.3.2 完整骨架一：WAV 播放器（环形缓冲 + jthread）
{: .sec-prac}

纯标准库加 SDL2 的完整播放器：主线程开设备、解码线程用 jthread 读 WAV 往 SPSC 环形缓冲灌数据、SDL 音频回调从缓冲取数。回车键优雅停止。只支持 16 位 PCM WAV——足够演示全部线程与同步结构。

```cpp
// wav_player.cpp —— 需要 -std=c++20；链接 SDL2
// 线程模型：主线程管设备与停止，jthread 解码线程灌数据，SDL 内部线程跑音频回调
#include <SDL.h>

#include <algorithm>
#include <atomic>
#include <chrono>
#include <cstdint>
#include <cstdio>
#include <cstring>
#include <fstream>
#include <iostream>
#include <string>
#include <thread>
#include <vector>

// ---------- SPSC 环形缓冲：容量为 2 的幂，head/tail 各占一条缓存行 ----------
class RingBuffer {
public:
    explicit RingBuffer(std::size_t cap_pow2) : buf_(cap_pow2), mask_(cap_pow2 - 1) {}

    // 生产者线程调用。返回实际写入个数；缓冲满时少写，绝不等待
    std::size_t write(const float* src, std::size_t n) {
        std::size_t w = head_.load(std::memory_order_relaxed);
        std::size_t r = tail_.load(std::memory_order_acquire);
        n = std::min(n, buf_.size() - (w - r));
        for (std::size_t i = 0; i < n; ++i) buf_[(w + i) & mask_] = src[i];
        head_.store(w + n, std::memory_order_release);
        return n;
    }

    // 消费者（音频回调）线程调用。返回实际读出个数
    std::size_t read(float* dst, std::size_t n) {
        std::size_t r = tail_.load(std::memory_order_relaxed);
        std::size_t w = head_.load(std::memory_order_acquire);
        n = std::min(n, w - r);
        for (std::size_t i = 0; i < n; ++i) dst[i] = buf_[(r + i) & mask_];
        tail_.store(r + n, std::memory_order_release);
        return n;
    }

private:
    std::vector<float> buf_;
    std::size_t mask_;
    alignas(64) std::atomic<std::size_t> head_{0};   // 只有生产者写
    alignas(64) std::atomic<std::size_t> tail_{0};   // 只有消费者写
};

// ---------- 极简 WAV 解析：只认 RIFF/WAVE 里的 16 位 PCM ----------
struct WavInfo {
    std::uint16_t channels = 0;
    std::uint32_t sample_rate = 0;
    std::uint16_t bits = 0;
    std::streamoff data_offset = 0;
    std::uint32_t data_size = 0;
};

bool parse_wav(std::istream& in, WavInfo& out) {
    char riff[12];
    in.read(riff, 12);
    if (!in || std::memcmp(riff, "RIFF", 4) != 0 || std::memcmp(riff + 8, "WAVE", 4) != 0)
        return false;
    bool have_fmt = false;
    while (in) {
        char id[4];
        std::uint32_t size = 0;
        in.read(id, 4);
        in.read(reinterpret_cast<char*>(&size), 4);   // 假设小端：x86/ARM 均满足
        if (!in) break;
        if (std::memcmp(id, "fmt ", 4) == 0) {
            char fmt[16] = {};
            in.read(fmt, 16);
            std::uint16_t format = 0;
            std::memcpy(&format, fmt, 2);
            std::memcpy(&out.channels, fmt + 2, 2);
            std::memcpy(&out.sample_rate, fmt + 4, 4);
            std::memcpy(&out.bits, fmt + 14, 2);
            have_fmt = (format == 1 && out.bits == 16);   // 只支持 16 位 PCM
            if (size > 16) in.ignore(static_cast<std::streamsize>(size - 16));
        } else if (std::memcmp(id, "data", 4) == 0) {
            out.data_offset = in.tellg();
            out.data_size = size;
            return have_fmt;
        } else {
            in.ignore(static_cast<std::streamsize>(size));
            if (size & 1) in.ignore(1);        // 块大小为奇数时补一个对齐字节
        }
    }
    return false;
}

// ---------- 音频回调：SDL 线程高频调用，只许读环形缓冲 ----------
struct AudioCtx {
    RingBuffer* rb = nullptr;
};

void SDLCALL feed(void* userdata, Uint8* stream, int len) {
    auto* ctx = static_cast<AudioCtx*>(userdata);
    float* out = reinterpret_cast<float*>(stream);
    std::size_t need = static_cast<std::size_t>(len) / sizeof(float);
    std::size_t got = ctx->rb->read(out, need);
    for (std::size_t i = got; i < need; ++i) out[i] = 0.0f;   // 缺数据补静音，绝不等待
}

int main(int argc, char** argv) {
    if (argc < 2) {
        std::fprintf(stderr, "用法: %s file.wav\n", argv[0]);
        return 1;
    }
    std::ifstream in(argv[1], std::ios::binary);
    WavInfo info;
    if (!parse_wav(in, info)) {
        std::fprintf(stderr, "不支持该文件（需要 16 位 PCM WAV）\n");
        return 1;
    }
    in.seekg(info.data_offset);

    if (SDL_Init(SDL_INIT_AUDIO) != 0) {
        std::fprintf(stderr, "SDL_Init: %s\n", SDL_GetError());
        return 1;
    }
    RingBuffer rb(1 << 16);          // 65536 float ≈ 0.37s@44.1kHz 立体声
    AudioCtx ctx;
    ctx.rb = &rb;

    SDL_AudioSpec want{}, have{};
    want.freq = static_cast<int>(info.sample_rate);
    want.format = AUDIO_F32SYS;      // 回调统一收 float，位深转换交给 SDL
    want.channels = info.channels;
    want.samples = 1024;
    want.callback = feed;
    want.userdata = &ctx;
    SDL_AudioDeviceID dev = SDL_OpenAudioDevice(nullptr, 0, &want, &have, 0);
    if (dev == 0) {
        std::fprintf(stderr, "打开音频设备: %s\n", SDL_GetError());
        SDL_Quit();
        return 1;
    }
    SDL_PauseAudioDevice(dev, 0);    // 0 = 开始拉流

    std::jthread decoder([&](std::stop_token st) {   // C++20
        constexpr std::size_t CHUNK = 4096;          // 一次读 4096 个采样
        std::vector<std::int16_t> raw(CHUNK);
        std::vector<float> tmp(CHUNK);
        while (!st.stop_requested()) {
            in.read(reinterpret_cast<char*>(raw.data()),
                    static_cast<std::streamsize>(raw.size() * sizeof(std::int16_t)));
            std::size_t got =
                static_cast<std::size_t>(in.gcount()) / sizeof(std::int16_t);
            if (got == 0) return;                    // 文件读完，线程自然退出
            for (std::size_t i = 0; i < got; ++i)
                tmp[i] = raw[i] / 32768.0f;          // int16 -> float 归一化
            std::size_t off = 0;
            while (off < got && !st.stop_requested()) {
                off += rb.write(tmp.data() + off, got - off);
                if (off < got)                       // 缓冲满了：让回调先消费
                    std::this_thread::sleep_for(std::chrono::milliseconds(2));
            }
        }
    });

    std::puts("播放中，回车键停止……");
    std::string line;
    std::getline(std::cin, line);
    decoder.request_stop();
    decoder.join();
    SDL_PauseAudioDevice(dev, 1);
    SDL_CloseAudioDevice(dev);
    SDL_Quit();
    return 0;
}
```

### 25.3.3 完整骨架二：FFmpeg 解码（RAII + send/receive 循环）
{: .sec-prac}

```cpp
// ff_decode.cpp —— 需要 -std=c++20
// 链接 libavformat libavcodec libavutil（示例输出基于 FFmpeg 6.x）
extern "C" {
#include <libavcodec/avcodec.h>
#include <libavformat/avformat.h>
#include <libavutil/avutil.h>
}

#include <cstdio>
#include <memory>

// ---------- RAII：unique_ptr + 自定义 deleter，任何提前 return 都不泄漏 ----------
struct PacketDel {
    void operator()(AVPacket* p) const { av_packet_free(&p); }
};
struct FrameDel {
    void operator()(AVFrame* f) const { av_frame_free(&f); }
};
struct CodecCtxDel {
    void operator()(AVCodecContext* c) const { avcodec_free_context(&c); }
};
struct FmtCtxDel {
    void operator()(AVFormatContext* f) const { avformat_close_input(&f); }
};
using PacketUPtr   = std::unique_ptr<AVPacket, PacketDel>;
using FrameUPtr    = std::unique_ptr<AVFrame, FrameDel>;
using CodecCtxUPtr = std::unique_ptr<AVCodecContext, CodecCtxDel>;
using FmtCtxUPtr   = std::unique_ptr<AVFormatContext, FmtCtxDel>;

int main(int argc, char** argv) {
    if (argc < 2) {
        std::fprintf(stderr, "用法: %s media.mp4\n", argv[0]);
        return 1;
    }
    AVFormatContext* raw = nullptr;
    if (avformat_open_input(&raw, argv[1], nullptr, nullptr) < 0) {
        std::fprintf(stderr, "打不开 %s\n", argv[1]);
        return 1;
    }
    FmtCtxUPtr fmt(raw);   // 成功后指针由本对象接管
    if (avformat_find_stream_info(fmt.get(), nullptr) < 0) return 1;

    int vidx = av_find_best_stream(fmt.get(), AVMEDIA_TYPE_VIDEO, -1, -1, nullptr, 0);
    if (vidx < 0) {
        std::fprintf(stderr, "找不到视频流\n");
        return 1;
    }
    AVStream* vs = fmt->streams[vidx];

    const AVCodec* codec = avcodec_find_decoder(vs->codecpar->codec_id);
    CodecCtxUPtr cc(avcodec_alloc_context3(codec));
    if (!cc || avcodec_parameters_to_context(cc.get(), vs->codecpar) < 0 ||
        avcodec_open2(cc.get(), codec, nullptr) < 0) {
        std::fprintf(stderr, "初始化解码器失败\n");
        return 1;
    }

    PacketUPtr pkt(av_packet_alloc());
    FrameUPtr frm(av_frame_alloc());
    int frames = 0;
    while (av_read_frame(fmt.get(), pkt.get()) >= 0) {
        if (pkt->stream_index == vidx) {
            // send/receive 模型：一次 send 可能产出 0~N 帧（B 帧重排），必须循环收
            if (avcodec_send_packet(cc.get(), pkt.get()) == 0) {
                while (avcodec_receive_frame(cc.get(), frm.get()) == 0) {
                    ++frames;
                    if (frames <= 3)
                        std::printf("frame %d  pts=%lld  %dx%d  fmt=%d\n", frames,
                                    static_cast<long long>(frm->pts), frm->width,
                                    frm->height, frm->format);
                    av_frame_unref(frm.get());   // 用完立刻 unref
                }
            }
        }
        av_packet_unref(pkt.get());   // 不管是不是目标流，都要 unref
    }
    // 文件读完：送空包，把 B 帧重排缓存在解码器里的尾帧冲出来
    avcodec_send_packet(cc.get(), nullptr);
    while (avcodec_receive_frame(cc.get(), frm.get()) == 0) ++frames;

    std::printf("共 %d 帧, %dx%d, 平均帧率 %.2f fps\n", frames, cc->width,
                cc->height,
                vs->avg_frame_rate.den ? av_q2d(vs->avg_frame_rate) : 0.0);
    return 0;
}
```

## 25.4 实现播放器主题
{: .sec-prac}

### 25.4.1 UI 与解码线程分离
{: .sec-know}

UI 选型两条路：SDL2 全手绘（自绘进度条、按钮，工作量在 UI 上）或 Qt（控件齐全，但要处理事件循环与解码线程的跨线程通信）。共同纪律只有一条：**UI 线程绝不直接碰解码数据**。解码线程与 UI 之间用两条单向通道连接——命令队列（UI → 解码：play/pause/seek）与状态快照（解码 → UI：播放位置、时长、缓冲水位），队列上加锁没关系（每秒几条消息），数据通道才需要无锁。

进度条更新是典型反模式高发区：UI 定时器里直接读解码线程正写的位置变量是数据竞争。正确姿势是解码线程每 250ms 发布一份带互斥量保护的快照，UI 只读快照。

### 25.4.2 硬件解码简述
{: .sec-ext}

CPU 软解 4K H.265 很吃力，各平台都有固定功能解码单元：Linux 的 VA-API、NVIDIA 的 NVDEC、macOS 的 VideoToolbox。FFmpeg 的接法统一：`av_hwdevice_ctx_create` 建设备上下文，挂到 `AVCodecContext::hw_device_ctx`，解码器选带 hwaccel 后缀的变体，输出帧的像素格式变成硬件帧（如 `AV_PIX_FMT_VAAPI`）。改动集中在初始化与帧的导入导出两端，解码循环本身不变——这也是 send/receive 模型的红利：换解码后端不动管线结构。代价是硬件帧不能直接喂 swscale，要先 `av_hwframe_transfer_data` 映射回内存，或者干脆整条渲染链留在 GPU 上。

### 25.4.3 性能与延迟
{: .sec-ver}

三个可量化的杠杆：

| 杠杆 | 取舍 | 依据 |
| --- | --- | --- |
| 队列长度 | 长：抗抖动、seek 粒度粗；短：延迟低、易饿死 | 实时场景用浅队列，本地播放用深队列 |
| 拷贝次数 | 每次拷贝都是内存带宽 | 数清楚 解码帧 → swscale → 纹理 → 屏幕 的路径 |
| 软解与硬解 | 硬解省 CPU 但受格式限制 | 看目标设备的解码单元覆盖面 |

掉帧统计自己攒：每帧比较"本应显示的 PTS"与"实际显示的 PTS"，差值超过一帧就计数，配合 diff 的分布直方图能看出是解码慢、渲染慢还是时钟漂。拷贝次数用代码走查即可数出来：mpv 这类成熟播放器的优化史几乎就是"再消掉一次拷贝"的历史——解码帧直接挂进渲染纹理（零拷贝路径）是终点形态。

## 常见坑清单
{: .sec-ts}

| 坑 | 症状 | 解法 |
| --- | --- | --- |
| AVPacket 未 unref | 内存随播放线性增长 | send 完立刻 `av_packet_unref`，出口统一 unref |
| flush 忘送空包 | 片尾最后几帧出不来 | 读循环结束后 `avcodec_send_packet(nullptr)` 再收干 |
| sws 上下文泄漏或每帧重建 | CPU 暴涨或内存缓涨 | 整段播放复用一个 SwsContext，RAII 持有 |
| 音频回调阻塞 | 周期性爆音 | 回调只读预分配缓冲，缺数据填静音 |
| time_base 换算错 | 音画同步整体漂移 | 统一换算成秒：`pts * av_q2d(stream->time_base)` |
| unique_ptr deleter 写错 | 编译错误或崩溃退出 | deleter 照 `av_xxx_free(&p)` 签名写，别写 `av_free(p)` |

三条展开说。AVPacket 的 unref 不是可选清理——包内缓冲是引用计数的，不 unref 就是不还；同一指针反复复用前也必须 unref。flush 空包问题只在有 B 帧的流上出现（无 B 帧解码器不缓存），所以测试素材里必须有一条 B 帧流，全用 I 帧测试等于没测。deleter 写错分两档：把 `av_packet_free(&p)` 写成 `av_free(p)` 编译期可能看不出问题，运行时少释放内层引用计数，属于最阴的一类。

## 知识点速查
{: .sec-chk}

| 节点 | 要点 | 版本 |
| --- | --- | --- |
| 音频参数 | 码率 = 采样率 × 位深 × 声道；采样率过 2 倍最高频率（奈奎斯特） | 语言无关 |
| 音频回调 | 只读预分配缓冲、不加锁、不分配、缺数据补静音 | 语言无关 |
| I/P/B 与 GOP | I 全图、P 前向差分、B 双向；seek 只能落在 I 帧 | 语言无关 |
| PTS/DTS | 显示用 PTS、解码用 DTS；B 帧导致两序不一致 | 语言无关 |
| FFmpeg 收发 | read → send_packet → 循环 receive_frame；收尾送空包 flush | C API |
| RAII 包装 | `unique_ptr` + deleter 调 `av_xxx_free(&p)` | C++11 |
| SPSC 环形缓冲 | 对方下标 acquire、发布 release；head/tail 各占一条缓存行 | C++11 |
| jthread | 析构自动 request_stop + join；stop_token 协作式停止 | C++20 |
| 音频主时钟 | 视频按 PTS 对齐音频时钟，落后丢帧、超前重复 | 语言无关 |

## 变式追问
{: .sec-think}

1. 音频回调不能阻塞，为什么渲染线程等 vsync 就没事？—— 音频节拍由硬件消费率决定，迟交货就是可闻的断流；渲染晚一帧只影响视觉流畅度，没有"必须在此刻交货"的硬合同。本质是两个线程的截止期软硬不同：音频是硬实时，渲染是软实时。
2. SPSC 扩到多生产者会失去什么？—— head 只有一个写者的前提没了，多生产者要 CAS 抢 head，退化为有竞争的原子操作；更麻烦的是"空闲空间"的判定要多生产者协调，常见解法要么加锁、要么按生产者分片。所以工程答案通常是：别扩，一生产者一队列。
3. 什么场景该换成视频主时钟？—— 无音轨的视频（监控回放、幻灯片式内容）没有音频时钟可用，只能以视频 PTS 为主；直播低延迟场景有时也让视频跟着源时间戳走、音频做重采样补偿，因为音频可以无损变速而视频丢帧不可逆。
4. `stop_token` 能完全替代手写的原子退出标志吗？—— 大多数场景能，而且语义更清晰（可轮询、可配合 `stop_callback` 注册清理）。但它只提供"通知"，不提供"等待确认"以外的同步点：需要"暂停"这种可恢复状态时仍要条件变量；需要线程间传递数据到达事件时仍要队列。stop_token 管停止，不管别的。
