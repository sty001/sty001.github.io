HTTP 是浏览器与服务器之间唯一的对话语言，抓包分析、性能排查、面试问答都绕不开它。本篇沿着一次完整的网站访问流程展开：HTTP 各版本的演进差异、URI 与 URL 的组成、请求与响应报文的逐行结构、常用请求方法、五类状态码、四类首部字段、无状态与 keep-alive、Cookie 与 Session 的工作机制，最后落到 HTTPS 与 HTTP 的区别、HTTP 与 Web 服务器的关系和网站评测指标。

## 一次完整的 HTTP 请求过程

### 文字步骤全流程

用户在浏览器中访问一个网站，背后依次发生以下过程：

1. 客户端：浏览器输入网址（如 www.example.com）并回车。
2. 客户端：进行 DNS 域名解析，将域名解析为网站服务器的 IP 地址。
3. 客户端：访问网站服务器，与服务器建立 TCP 连接（三次握手）。
4. 客户端：向服务器发送 HTTP 请求报文。
5. 服务端：响应客户端请求，回复 HTTP 响应报文。
6. 客户端：浏览器解析响应内容，看到网站页面。
7. 客户端：访问结束，与服务器释放 TCP 连接（四次挥手）。

把每一步展开，细节如下：

1. **输入与解析 URL**：浏览器拆分出协议、域名、端口、路径；若未写端口，HTTP 默认 80、HTTPS 默认 443。
2. **DNS 解析**：依次查询浏览器缓存 → 操作系统缓存（hosts 文件）→ 本地 DNS 服务器 → 根/顶级/权威 DNS 服务器，最终拿到 A 记录（IPv4）或 AAAA 记录（IPv6）。DNS 查询通常基于 UDP（53 端口），响应过大时退回 TCP。运维常反着用 DNS：把域名写进 hosts 指向特定 IP，做新版本灰度验证、故障时临时切流，hosts 优先级高于 DNS 查询，改完立即生效，是成本最低的流量调度手段。
3. **TCP 三次握手**：客户端发送 SYN，服务器回 SYN+ACK，客户端再发 ACK，连接建立。此后数据才能开始双向传输。
4. **发送 HTTP 请求**：浏览器按报文格式组装请求行、请求头、空行、（POST 时的）请求主体，通过已建立的 TCP 连接发出。
5. **服务器处理并响应**：Web 服务器（如 Nginx）解析报文，静态文件直接读磁盘返回；动态请求转发给后端（PHP-FPM、uWSGI 等）处理后返回。响应同样按"起始行 + 头部 + 空行 + 主体"组装发回。
6. **浏览器渲染**：解析 HTML 构建 DOM，遇到 CSS/JS/图片再发起新请求（长连接下复用同一 TCP 连接）；全部资源就绪后完成页面渲染。
7. **连接释放**：HTTP/1.0 请求结束后四次挥手关闭连接；HTTP/1.1 默认长连接，连接空闲超过 keepalive_timeout 后才关闭。

HTTP 基于 TCP 传输，建立连接要三次握手、释放连接要四次挥手；域名解析（DNS）通常基于 UDP。一个页面往往包含 HTML、CSS、JS、图片等多种资源，每获取一个资源都要一次请求与一次响应，第 4、5 步的报文往来通常往复多次。

### 原理解析：为什么 DNS 用 UDP 而 HTTP 用 TCP

DNS 查询报文短小、一次交互即可完成，UDP 无握手、开销低，适合这种"问一句答一句"的场景；超时或截断（TC 位）时才改用 TCP。HTTP 传输的是网页内容，要求可靠、有序、不丢失，TCP 的连接管理、确认重传、流量控制正好满足，HTTP 天然构建在 TCP 之上（HTTP/3 起改用基于 UDP 的 QUIC，在应用层自行实现可靠传输）。

## HTTP 协议版本演进

HTTP 常见版本有 0.9、1.0、1.1、2.0 和 3.0，各代差异如下：

| 版本 | 年代 | 连接方式 | 关键特性 |
| --- | --- | --- | --- |
| HTTP/0.9 | 1991 | TCP 短连接 | 最初版本，只支持 GET，无请求头，响应仅返回 HTML 文本 |
| HTTP/1.0 | 1996 | TCP 短连接 | 引入请求头/响应头、状态码、POST 等方法；每个文件一次连接 |
| HTTP/1.1 | 1997 | TCP 长连接 | 默认 Keep-Alive 连接复用，增加 Host 头、缓存控制、分块传输 |
| HTTP/2.0 | 2015 | TCP 长连接优化 | 二进制分帧、多路复用、首部压缩（HPACK）、服务器推送 |
| HTTP/3.0 | 2022 | 基于 QUIC（UDP） | 传输层改用 QUIC，消除 TCP 队头阻塞，连接迁移更快 |

三者在连接管理上的差异如下：

| 版本 | 连接方式 | 说明 |
| --- | --- | --- |
| HTTP/1.0 | TCP 短连接 | 每次请求响应结束后，连接即关闭 |
| HTTP/1.1 | TCP 长连接 | 连接可以复用，省去反复握手的开销 |
| HTTP/2.0 | TCP 长连接优化 | 进一步提高用户并发（同时）访问的效率 |

> **注意：** HTTP/1.1 起默认使用长连接，Nginx 中通过 keepalive_timeout 指令控制长连接的超时时间（默认 65 秒）。

> **注意：** HTTP/2 的多路复用让多个请求在一条 TCP 连接上并行传输，解决了 HTTP/1.1 的"队头阻塞"；但 TCP 层面的丢包仍会阻塞所有流，HTTP/3 改用 QUIC 后这一问题才被彻底消除。目前主流浏览器与 Nginx（1.25.0 起稳定支持）均已支持 HTTP/3。

长连接的收益有多大？HTTP/1.0 短连接下，一个页面引用 30 个资源就要经历 30 次 TCP 握手加挥手，握手本身至少一个 RTT，弱网下光握手就能吃掉大半加载时间；长连接把这些开销摊到成百上千个请求上，配合浏览器的多连接并发，页面加载提速非常直观。代价是服务端要为每条空闲连接保留 fd 和缓冲区，keepalive_timeout 设得太大、并发一高，fd 很快耗尽。说白了，长连接是用少量内存换大量握手，timeout 要在复用收益和资源占用之间取平衡。

HTTP/2 的三个核心特性分开记：二进制分帧把报文切成帧，解析不再依赖文本格式；多路复用让一条连接承载并行请求，互不排队；首部压缩用静态表加动态表消除重复的 User-Agent、Cookie 传输。三个特性都服务于同一个目标——降低同页面多资源的传输开销。

## URI 与 URL

URL 全称为 Uniform Resource Location，中文翻译为统一资源定位符；URI 全称为 Uniform Resource Identifier，中文翻译为统一资源标识符。URL 是 URI 的一个子集：URI 只负责"标识"资源，URL 进一步给出"如何定位"（从哪里获取）资源。

| 概念 | 全称 | 中文 | 示例 |
| --- | --- | --- | --- |
| URL | Uniform Resource Location | 统一资源定位符 | docs.ansible.com |
| URI | Uniform Resource Identifier | 统一资源标识符 | /ansible/latest/user_guide/playbooks_reuse_roles.html |

一个完整 URL 的各组成部分：

```text
scheme://user:password@host:port/path?query#fragment
  |        |             |    |    |      |       |
协议      用户信息       主机  端口  路径   查询参数  片段

示例：
http://user:pass@www.example.com:80/docs/index.html?page=2#sec3
```

| 组成部分 | 说明 | 示例值 |
| --- | --- | --- |
| scheme | 协议方案，http 或 https | http |
| user:password | 可选的认证信息，现已少用 | user:pass |
| host | 主机名或 IP 地址 | www.example.com |
| port | 端口，http 默认 80，https 默认 443 | 80 |
| path | 资源在服务器上的路径 | /docs/index.html |
| query | 查询参数，以 `?` 开头，多参数用 `&` 分隔 | page=2 |
| fragment | 片段，用于定位页面内锚点，不发送到服务器 | sec3 |

## 请求报文结构

HTTP 请求报文由四部分组成：

1. 请求行：包含请求方法、请求信息（请求的资源）和请求协议版本。例如 `GET /index.html HTTP/1.1`，表示用 GET 方法获取 index.html 首页文件。
2. 请求头：携带请求的附加信息，如请求主机信息（Host）。
3. 空行：请求头与请求主体之间的分隔。空行经常被忽略，却最容易踩：它就是头部与主体的分界符，服务器读到空行即认为头部结束。手工用 telnet 或 nc 模拟请求时少敲这个回车，服务器会一直等头部等到超时。
4. 请求主体：使用 GET 方法时，没有请求主体信息；使用 POST 方法时，具有请求主体内容。

一个 GET 请求示例：

```text
GET /index.html HTTP/1.1
Host: www.example.com

```

一个 POST 请求示例：

```text
POST /query HTTP/1.1
Host: www.example.com

class=sz-01&name=zhangsan
```

> **注意：** GET 用于读取、获取资源，请求中不带主体；POST 用于写入、提交数据，数据放在请求主体中发送。

### 请求报文逐行详解

以一个更完整的请求为例，逐行说明每一行的作用：

```text
GET /docs/index.html?page=2 HTTP/1.1
Host: www.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: text/html,application/xhtml+xml
Accept-Language: zh-CN,zh;q=0.9
Referer: https://www.example.com/
Cookie: sessionid=abc123
Connection: keep-alive
```

| 行 | 归属 | 作用 |
| --- | --- | --- |
| `GET /docs/index.html?page=2 HTTP/1.1` | 请求行 | 方法 + 请求 URI + 协议版本，空格分隔 |
| `Host: www.example.com` | 请求头 | 目标主机，一台服务器托管多个站点时靠它区分 |
| `User-Agent: ...` | 请求头 | 客户端身份信息（浏览器类型与版本） |
| `Accept: ...` | 请求头 | 客户端能接受的响应内容类型 |
| `Accept-Language: ...` | 请求头 | 客户端偏好的语言 |
| `Referer: ...` | 请求头 | 请求来源页面，用于统计与防盗链 |
| `Cookie: ...` | 请求头 | 携带服务端之前下发的会话标识 |
| `Connection: keep-alive` | 通用头 | 声明连接处理方式，请求长连接 |
| 空行 | 分隔 | 头部结束标志，必须有 |
| （GET 无主体） | 请求主体 | POST/PUT 等才有，内容为表单或 JSON 等数据 |

这些行不用背，抓一次包全有了：curl -v 直接把请求与响应头打在终端上，浏览器 F12 的 Network 面板能看到每个请求的完整报文，Wireshark、tcpdump 能在 TCP 层看握手与挥手。照着真实报文读一遍，比看十遍文字描述都牢。

## 响应报文结构

HTTP 响应报文同样由四部分组成：

1. 起始行：包含协议版本、状态码和状态信息，表明本次访问是成功响应还是失败响应。
2. 响应头部：携带响应的附加信息。
3. 空行：响应头与响应主体之间的分隔。
4. 响应主体：返回给客户端的具体内容。

一个响应示例：

```text
HTTP/1.1 200 OK
Content-Type: text/html

页面主体内容（HTML 代码等）
```

一个更完整的响应示例：

```text
HTTP/1.1 200 OK
Server: nginx/1.24.0
Date: Sat, 24 Oct 2026 12:00:00 GMT
Content-Type: text/html; charset=UTF-8
Content-Length: 1024
Connection: keep-alive
Cache-Control: max-age=3600

<!DOCTYPE html>
<html>页面主体内容</html>
```

| 行 | 归属 | 作用 |
| --- | --- | --- |
| `HTTP/1.1 200 OK` | 起始行（状态行） | 协议版本 + 三位状态码 + 原因短语 |
| `Server: nginx/1.24.0` | 响应头 | 服务器软件与版本 |
| `Date: ...` | 通用头 | 服务器生成响应的时间 |
| `Content-Type: text/html` | 实体头 | 主体类型与字符集，浏览器据此决定如何解析 |
| `Content-Length: 1024` | 实体头 | 主体字节数，用于判断接收完整性 |
| `Cache-Control: max-age=3600` | 通用头 | 缓存策略，允许客户端缓存 1 小时 |
| 空行 | 分隔 | 头部结束标志 |
| HTML 内容 | 响应主体 | 返回给客户端的具体数据 |

## 常用请求方法

最常见的两种请求方法：

| 方法 | 作用 | 请求主体 |
| --- | --- | --- |
| GET | 读取、获取资源（如 index.html、photo.jpg） | 无 |
| POST | 写入、提交数据 | 有 |

HTTP 定义了完整的方法集合，除 GET/POST 外，其余方法的语义、安全性与幂等性如下：

| 方法 | 语义 | 安全性 | 幂等性 |
| --- | --- | --- | --- |
| GET | 获取资源 | 安全 | 幂等 |
| POST | 提交数据，常用于新建资源或触发处理 | 不安全 | 不幂等 |
| PUT | 用请求体全量替换目标资源 | 不安全 | 幂等 |
| DELETE | 删除指定资源 | 不安全 | 幂等 |
| HEAD | 与 GET 相同，但只返回响应头，不返回主体 | 安全 | 幂等 |
| OPTIONS | 查询目标资源支持的方法与服务器能力 | 安全 | 幂等 |
| TRACE | 回显服务器收到的请求，用于诊断；有信息泄露风险，通常禁用 | 安全 | 幂等 |
| PATCH | 对资源做局部修改（不同于 PUT 的全量替换） | 不安全 | 不幂等 |
| CONNECT | 建立到目标服务器的隧道，HTTPS 代理场景使用 | 不安全 | 不幂等 |

HEAD 方法在运维里比看起来有用：探测接口是否存活、检查大文件是否更新（配合 ETag/Last-Modified）都不用下载主体，监控脚本和 CDN 回源校验大量使用它。

- **安全性**：方法不改变服务器上的资源状态（只读）；
- **幂等性**：同一方法执行一次与执行多次，服务器资源状态相同。

> **注意：** GET/PUT/DELETE/HEAD 是幂等的，网络超时重试不会造成重复副作用；POST 不幂等，重复提交可能产生多条记录，支付、下单等场景必须由业务层用 token 或唯一键防重。

### 辨析：REST 风格与请求方法的对应

REST 是接口设计风格，核心是用 URL 表示资源、用请求方法表示操作，两者组合出完整语义：

| 操作 | 请求方法 | URL 风格 | 典型响应 |
| --- | --- | --- | --- |
| 查询列表 | GET | /users | 200 |
| 查询单个 | GET | /users/42 | 200 |
| 新建 | POST | /users | 201 |
| 全量更新 | PUT | /users/42 | 200 |
| 局部更新 | PATCH | /users/42 | 200 |
| 删除 | DELETE | /users/42 | 204 |

对照着敲一遍就明白：URL 里只出现名词（users），动作全部交给方法表达；URL 里带动词的（如 /getUser?id=42）基本可以判定不是 REST 风格。这张表的响应码与前面状态码一节正好对应，排查接口问题时两边要一起看。

## 状态码：分类与常见含义

状态码位于响应报文的起始行，用于表示请求的处理结果。按第一位数字分为五类：

- 1xx：提示信息，表示请求已接收，需要继续处理；
- 2xx：成功，请求被正常处理；
- 3xx：重定向，需要客户端进一步动作；
- 4xx：客户端错误，请求本身有问题；
- 5xx：服务端错误，服务器处理请求时出错。

常见状态码：

| 状态码 | 含义 | 说明 |
| --- | --- | --- |
| 200 | 成功 | 服务器正常返回请求的资源 |
| 301 | 永久重定向 | 资源永久迁移到新地址 |
| 302 | 临时重定向 | 资源临时跳转，之后仍访问原地址 |
| 403 | 禁止访问 | 服务器拒绝执行请求，如权限不足 |
| 404 | 资源不存在 | 服务器找不到请求的资源 |
| 500 | 服务器内部错误 | 服务端程序处理请求时出错 |
| 502 | 错误网关 | 网关从上游服务器收到无效响应 |
| 503 | 服务不可用 | 服务器暂时过载或正在维护 |
| 504 | 网关超时 | 网关未能及时从上游服务器获得响应 |

> **注意：** 面试中经常被要求写出几种常见状态码，建议重点记住 200、301、302、403、404 和 5xx 系列。

### 辨析：转发与重定向

转发发生在服务器内部：一次请求，服务器把请求交给内部另一个资源处理，浏览器地址栏不变，只经历一次 HTTP 往返；重定向是服务器回 3xx 加 Location，浏览器再发一次全新请求到新地址，地址栏变化，共两次往返。前者用户无感、效率高，适合站内流程；后者能跳到外部域、能被收藏，代价是多一次往返。301 与 302 的缓存差异前面已经提过。

### 五类状态码速查表

**1xx（提示信息）**：表示请求已接收，需继续处理，实际响应中较少直接见到。

| 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| 100 Continue | 客户端可继续发送请求主体 | 大 POST 前客户端用 `Expect: 100-continue` 询问 |
| 101 Switching Protocols | 切换协议 | WebSocket 握手升级 |
| 103 Early Hints | 预加载提示 | 服务器先行返回待加载资源链接 |

**2xx（成功）**：请求被正常处理。

| 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| 200 OK | 成功并返回资源 | 最常见的成功响应 |
| 201 Created | 资源创建成功 | REST API 新建记录后返回 |
| 204 No Content | 成功但无响应主体 | 删除成功、表单提交后 |
| 206 Partial Content | 返回部分内容 | 断点续传、Range 请求、视频拖动进度 |

**3xx（重定向）**：需要客户端进一步动作才能完成请求。

| 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| 301 Moved Permanently | 永久重定向 | 域名更换、HTTP 跳 HTTPS、规范 URL |
| 302 Found | 临时重定向 | 活动页临时跳转，之后仍访问原地址 |
| 303 See Other | 重定向到另一个 URI，用 GET 获取 | POST 后跳转到结果页 |
| 304 Not Modified | 资源未修改，用缓存 | 协商缓存命中（ETag/Last-Modified） |
| 307 Temporary Redirect | 临时重定向且保持方法不变 | 与 302 的区别是 POST 不会被改成 GET |
| 308 Permanent Redirect | 永久重定向且保持方法不变 | 301 的方法不变版本 |

3xx 里最容易混的是 302/303/307 的差别：302 最初语义是临时跳转，但大量浏览器实现把 POST 改写成 GET，久而久之成了事实行为；303 明确要求改用 GET 获取新地址；307 则规定不得改方法，POST 过去还是 POST。做支付回调、表单提交跳转时用错码，会出现请求体丢失、下游接口收到 GET 的怪问题，按语义选 303 或 307 才稳。

**4xx（客户端错误）**：请求本身有问题，服务器无法处理。

| 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| 400 Bad Request | 请求报文语法错误 | 参数格式错误、请求体解析失败 |
| 401 Unauthorized | 未认证（实际含义为"未登录"） | 缺少或错误的登录凭证 |
| 403 Forbidden | 已认证但无权限 | 文件权限不足、目录不允许访问 |
| 404 Not Found | 资源不存在 | URL 写错、文件被删除、root 路径配错 |
| 405 Method Not Allowed | 方法不被允许 | 对只读资源发 PUT/DELETE |
| 408 Request Timeout | 请求超时 | 客户端发送太慢，服务器主动断开 |
| 413 Payload Too Large | 请求体过大 | 上传文件超过限制 |
| 429 Too Many Requests | 请求过于频繁 | 触发限流（限速）策略 |

**5xx（服务端错误）**：服务器处理请求时出错。

| 状态码 | 含义 | 典型场景 |
| --- | --- | --- |
| 500 Internal Server Error | 服务器内部错误 | 程序异常、配置错误 |
| 501 Not Implemented | 服务器不支持该功能 | 方法或扩展未实现 |
| 502 Bad Gateway | 网关从上游收到无效响应 | 反向代理后端的 PHP-FPM/uWSGI 挂了 |
| 503 Service Unavailable | 服务暂不可用 | 过载保护、限流、维护中 |
| 504 Gateway Timeout | 网关等待上游超时 | 后端处理太慢（慢查询、慢接口） |
| 505 HTTP Version Not Supported | 不支持的 HTTP 版本 | 服务器不识别请求的协议版本 |

生产上栽过的经验：502/503/504 都由网关侧报出，但病因不同，排查口诀——502 查进程（后端活着没、端口监听没、转发地址对不对），503 查容量（过载、限流、维护窗口没关），504 查耗时（慢 SQL、慢接口、代理超时太短）。先分清是连不上、不让连还是等不起，方向就不会跑偏。

## 首部字段分类

HTTP 首部分为四大类：通用首部（请求与响应都可用）、请求首部、响应首部、实体首部（描述报文主体）。

| 分类 | 说明 | 常见字段 |
| --- | --- | --- |
| 通用首部 | 请求与响应报文都能使用 | Date、Cache-Control、Connection、Via、Transfer-Encoding |
| 请求首部 | 补充请求的附加信息 | Host、User-Agent、Accept、Accept-Language、Accept-Encoding、Referer、Cookie、Authorization、If-Modified-Since、If-None-Match、Range、X-Forwarded-For |
| 响应首部 | 补充响应的附加信息 | Server、Set-Cookie、Location、WWW-Authenticate、Retry-After、Vary、Age |
| 实体首部 | 描述报文主体（资源本身） | Content-Type、Content-Length、Content-Encoding、Content-Language、Last-Modified、ETag、Expires |

高频首部速查：

| 首部 | 方向 | 作用 |
| --- | --- | --- |
| Host | 请求 | 请求的目标主机与端口 |
| User-Agent | 请求 | 客户端身份信息 |
| Accept | 请求 | 客户端可接受的内容类型 |
| Referer | 请求 | 请求来源页面地址 |
| Cookie | 请求 | 客户端携带的会话数据 |
| X-Forwarded-For | 请求 | 经过代理后的真实客户端 IP |
| Server | 响应 | 服务器软件信息 |
| Set-Cookie | 响应 | 服务端下发 Cookie |
| Location | 响应 | 重定向目标地址（配合 3xx） |
| Content-Type | 响应 | 主体内容类型 |
| Content-Length | 响应 | 主体长度 |
| Last-Modified / ETag | 响应 | 资源最后修改时间 / 版本标识，用于协商缓存 |
| Cache-Control | 双向 | 缓存控制策略 |
| Connection | 双向 | 连接管理（keep-alive / close） |

缓存首部是一对一的问答：第一次响应带 ETag 与 Last-Modified，第二次浏览器带上 If-None-Match / If-Modified-Since 去问，资源没变服务器回 304 不传主体。这套协商缓存让"改没改"的判断成本几乎为零，是静态资源提速的第一功臣。首部里的协商机制同理：客户端用 Accept-Encoding 声明支持的压缩算法（gzip、br），服务器用 Content-Encoding 告知实际算法，Nginx 的 gzip 模块就按这对首部工作。

请求头位于请求行之后，用于携带客户端信息与协商参数，例如 Host 指明请求的目标主机；响应头位于起始行之后，用于携带服务器信息与响应参数，例如内容类型（Content-Type）。Referer（来源页面）、User-Agent（客户端信息）、X-Forwarded-For（经过代理后的真实客户端 IP）等常见首部，也都会记录在 Nginx 的日志格式中。

## 无状态、keep-alive 与 Cookie/Session

HTTP 是无状态协议，服务器不会自动保存用户的上下文信息。网站通过 Cookie 与 Session 来标识用户身份、维持登录状态。

### 无状态与 keep-alive

- **无状态**：服务器不记录"这个请求是谁之前发来的"，每个请求都被独立处理。好处是服务器实现简单、易于水平扩展；代价是登录态等上下文需要额外机制（Cookie/Session）维持。
- **keep-alive（长连接）**：HTTP/1.1 默认开启，多个请求复用同一条 TCP 连接，省去反复三次握手的开销；连接空闲超过 `keepalive_timeout` 才关闭。并发场景下注意连接数上限与超时配置的权衡。

### Cookie 与 Session 的工作机制

与用户身份相关的两个概念：

- Cookie：标识用户身份信息，会保存在用户客户端本地（内存中）。
- Session：记录用户的一些会话操作，如记录用户登录信息，记录在服务端（内存中）。

典型交互流程：

1. 用户提交账号密码登录；
2. 服务端验证通过后生成 Session（可存内存、Redis 等），并分配唯一 Session ID；
3. 服务端通过响应头 `Set-Cookie` 把 Session ID 写入客户端；
4. 客户端后续请求自动带上 `Cookie: sessionid=xxx`；
5. 服务端凭 Session ID 找到对应 Session，识别用户身份；
6. 退出登录时销毁服务端 Session 并清空 Cookie。

| 对比项 | Cookie | Session |
| --- | --- | --- |
| 存放位置 | 客户端（浏览器） | 服务端 |
| 内容 | 键值对，体积小（约 4KB） | 任意会话数据，体积不受限 |
| 安全性 | 暴露在客户端，敏感信息须加密 | 存在服务端，相对安全 |
| 跨请求传递 | 随请求头自动携带 | 通过 Cookie 中的 Session ID 关联 |
| 过期方式 | 可设 Max-Age/Expires | 服务端超时销毁 |

> **注意：** Cookie 可以配合 `HttpOnly`（禁止 JS 读取，防 XSS 窃取）、`Secure`（仅 HTTPS 传输）、`SameSite`（限制跨站发送，防 CSRF）等属性加固安全。

这里有个坑：301 永久跳转会被浏览器长期缓存，跳转目标一旦配错，用户侧很难自己恢复，测试跳转规则优先用 302 或无痕窗口。Session 默认存内存，服务一重启全部掉线，生产环境通常把 Session 落到 Redis。单机玩 Session 没问题，一到负载均衡多机部署就出事：登录请求落在 A 机，下一个请求被分到 B 机，B 机没有这份 Session，用户被踢回登录页。解法三条路——负载均衡用 ip_hash 粘住同一用户；Session 集中存 Redis，各机共读；或改用 JWT 这类自包含 token，服务端不存状态。

## 静态资源、动态资源与伪静态

### 静态资源

服务器"要什么给什么"，直接返回文件，如 index.html、photo.jpg。特点说明：

1. 网页内容是固定不变的，因此容易被搜索引擎收录（容易被用户找到），这是优点；
2. 网页没有数据库支持，制作和维护的工作量较大，信息量很大时完全依靠静态网页比较困难，这是缺点；
3. 网页的交互性较差，在程序的功能实现方面有较大的限制，这是缺点；
4. 当客户端向服务器请求数据时，服务器会直接从磁盘文件系统上返回数据，不做任何解析。

### 动态资源

服务器"要什么信息，需要查询数据库进行解析后发送给客户端"。例如查看班级人员信息表：

| 班级 | 人名 | 年龄 | 学历 |
| --- | --- | --- | --- |
| sz-01 | 张三 | 18 | 高中 |
| sz-01 | 李四 | 20 | 大专 |

页面内容由代码直接调用数据库的内容生成。特点说明：

1. 采用动态网页技术的网站可以实现更多的功能，如用户注册、用户登录、在线调查、投票、用户管理、订单处理、发博文等；
2. 动态资源页面会出现 `?` 和 `&` 参数，不便于被搜索引擎收录；
3. 接收到用户请求后，需要让动态服务和数据库服务进行处理。

### 伪静态资源

伪静态（动态页面）兼顾两者优点：

1. 可以便于搜索引擎进行收录；
2. 有数据库服务支持，实现网页交互功能。

> **注意：** 伪静态是把动态 URL（`article.php?id=1`）通过服务器重写规则伪装成静态形式（`/article/1.html`），对搜索引擎更友好，后端仍然是动态处理。Nginx 中常用 `try_files` 与 `rewrite` 指令实现。

生产上静态资源普遍再往 CDN 前推一层：源站只回源，边缘节点就近返回图片与 JS，配合 Cache-Control 的 max-age 让浏览器连边缘节点都不用问。动静态分离的思路从服务器内部延伸到了整个分发链路。

## HTTP 与 Web 服务器的关系

HTTP 是**协议**（客户端与服务器之间通信的规范，规定报文格式与方法语义）；Web 服务器是**协议的具体实现**（监听端口、解析报文、返回数据的软件）。二者关系：

1. Web 服务器（Nginx、Apache httpd、IIS 等）在 80/443 端口监听，等待客户端连接；
2. 收到报文后按 HTTP 规范解析请求行、请求头，定位资源；
3. 静态资源直接读文件系统返回；动态请求按配置转发给后端应用（PHP-FPM、uWSGI、Tomcat 等），后端处理结果再由 Web 服务器包装成 HTTP 响应返回；
4. 处理过程与结果按规范写入访问日志（access.log）与错误日志（error.log），供排错与统计使用。

常见 Web 服务器定位：

| 软件 | 定位 |
| --- | --- |
| Nginx | 高性能 Web 服务器/反向代理，静态与并发场景优势明显 |
| Apache httpd | 老牌 Web 服务器，模块丰富，`.htaccess` 动态配置 |
| IIS | Windows 平台 Web 服务器 |
| Tomcat | Java 应用服务器，运行动态页面 |

Nginx 与后端应用之间的协议对照：PHP 走 FastCGI（fastcgi_pass 到 9000 或 sock），Python 常走 uWSGI 协议或 HTTP，Java/Tomcat 走 HTTP 反代，Golang 服务直接 HTTP。协议选错、地址配不上，是 502 的三大来源之一。

> **注意：** 反向代理架构下，Nginx 面向客户端终止 HTTP 连接，再以另一条连接转发请求到上游；此时客户端的真实 IP、协议等信息通过 `X-Forwarded-For`、`X-Forwarded-Proto` 等首部向后端传递。

## HTTPS 与 HTTP 的区别

HTTPS = HTTP over TLS/SSL，即在 HTTP 之下加入安全传输层，主要区别：

| 对比项 | HTTP | HTTPS |
| --- | --- | --- |
| 默认端口 | 80 | 443 |
| 传输安全 | 明文传输，易被窃听篡改 | TLS 加密，防窃听、防篡改、防冒充 |
| 身份认证 | 无 | 通过 CA 签发的证书验证服务器身份 |
| 性能开销 | 无握手加密开销 | TLS 握手有额外开销（TLS 1.3 已大幅优化） |
| 部署要求 | 无需证书 | 需申请证书（可用 Let's Encrypt 免费证书） |
| SEO 与浏览器 | 被 Chrome 等标记为"不安全" | 主流站点标配，搜索引擎加权 |

> **注意：** HTTPS 的加密、认证、完整性由 TLS 层完成，HTTP 层的报文格式与方法语义完全不变；HTTP/2 在实践中基本都基于 HTTPS 部署。

握手差异一句话：HTTP 在 TCP 三次握手后就能直接发请求报文；HTTPS 还要在 TCP 之上多一轮 TLS 握手——协商版本与加密套件、验证证书、交换密钥材料，TLS 1.2 要两个往返，TLS 1.3 压缩到一个往返，会话复用后可零往返恢复。HTTPS 首字节延迟略高，来源就在这里。

把 TLS 1.2 的完整握手拆开看：客户端发 ClientHello（支持的版本与套件列表、随机数）；服务器回 ServerHello 加上证书链；客户端验证证书后，用证书公钥加密预主密钥发回；双方用三个随机数算出会话密钥，互发 Finished 校验。全程只传密钥材料不传业务数据，之后的应用数据才用会话密钥对称加密。TLS 1.3 砍到一次往返并默认前向安全，细节变化大，但交换材料、验证身份、派生密钥这三步不变。

## 网站评测指标：IP、PV、UV 与并发

| 指标 | 含义 | 统计依据 |
| --- | --- | --- |
| IP | 访问网站的源 IP 数量 | 客户端 IP 地址 |
| PV | 页面访问量 | 页面被请求的次数 |
| UV | 独立访客数量 | 客户端 Cookie |

- IP：根据用户访问的源 IP 信息进行统计，例如统计一天中访问网站最多的前 10 个地址。局域网内多个用户访问时，网站服务器只记录一个 IP（NAT 技术）；家用电脑断电后会重新拨号，WAN 侧公网地址会发生变化。
- PV：根据用户页面访问量进行统计，例如统计用户访问哪个页面的次数比较多，取出前 10 名。
- UV：根据用户访问的 Cookie 信息，统计访问的用户数量。

IP 与 PV 的比值还能反映站点形态：内容站 PV/IP 普遍很高（一个访客看很多页），工具站偏低；比值突然异常上涨，除了活动引流，也要警惕刷量。

网站的并发（压测技术通常按 1、10、100、1000、10000 的量级递增），常见三种理解：

- A 种理解：网站服务器每秒能够接收的最大用户请求数；
- B 种理解：网站服务器每秒能够响应的最大用户请求数；
- C 种理解：网站服务器在单位时间内能够处理的最大连接数。

三种理解换算成运维语言就是 QPS 与 RT：QPS（每秒请求数）约等于并发数除以平均响应时间。1000 并发、平均响应 200ms，QPS 大约 5000；RT 一旦被慢 SQL 拖到 2 秒，同样 1000 并发 QPS 只剩 500。压测报告里的两个数字要一起看，单看 QPS 或单看并发数都会误判容量。

衡量并发可以类比：饭店 10:00 开餐，10 张桌子、每桌 4 人，10:00:00 至 10:01 可接待 40 人；高速公路在 5 月 1 日至 3 日的高峰期，三车道可同时通行 3 辆车。

IP 与 PV 的统计可以基于网站的 access.log，结合 awk 数组与 sort、uniq 等命令实现；并发能力则可使用 ab 等工具压测评估，具体方法见《Nginx 网站服务部署》一文的日志与排错部分。

```console
# 用 ab 做简单压测：100 并发、共 10000 请求
$ ab -n 10000 -c 100 http://127.0.0.1/

# 统计 access.log 中访问量前 10 的 IP
$ awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
```

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 502 Bad Gateway | 后端服务未启动或监听异常（PHP-FPM/uWSGI 挂掉） | `systemctl status php-fpm`；`tail /var/log/nginx/error.log` | 启动并修复后端服务 |
| 504 Gateway Timeout | 后端处理太慢（慢查询、慢接口） | 查看后端日志定位慢请求 | 优化慢逻辑，必要时调大 `proxy_read_timeout` |
| 403 Forbidden | 文件权限不足、SELinux 拦截、目录未配 index | `ls -Z /data/www`；`getenforce` | 修正属主与权限，或调整 SELinux 上下文 |
| 404 Not Found | `root` 路径配错、文件不存在、伪静态规则失效 | `nginx -T \| grep root` | 核对站点根目录与实际文件位置 |
| 301/302 跳转死循环 | server_name 与 Host 不匹配、HTTP 强制跳 HTTPS 后环 | `curl -v http://web01/` 观察跳转链 | 修正 server_name 与跳转条件 |
| curl 正常浏览器异常 | 缓存、Cookie、HTTP/2 兼容性差异 | `curl -v --http1.1` 与浏览器结果对比 | 按协议版本与缓存策略分别排查 |

表外还有一个 499 值得认识：这是 Nginx 自定义的状态码，表示客户端在响应返回前主动断开连接，多数是用户等不及刷新或客户端超时设置太短。日志里 499 扎堆，优先查后端响应耗时，不要当垃圾数据过滤掉。curl 排查三板斧也顺手记下：-v 看完整请求与响应头，-I 只看状态行与头部，-H 伪造或添加指定头部（如模拟 Referer 测防盗链）；配合 -w 把状态码与耗时格式化输出，塞进监控脚本正合适。

## 现代环境补充

1. **HTTP/2 普及**：Nginx 1.25.0 起稳定支持 HTTP/2（`listen 443 ssl http2;`），多路复用与首部压缩显著降低多资源页面的加载时间。
2. **HTTP/3 起步**：基于 QUIC（UDP）的 HTTP/3 已进入主流，解决 TCP 队头阻塞，弱网与移动场景收益明显；Nginx 可通过 `listen 443 quic reuseport;` 等指令试验性开启。
3. **TLS 1.3 与免费证书**：新站点默认 TLS 1.2/1.3，Let's Encrypt 提供免费证书，`certbot` 等工具自动化续期，HTTPS 已成标配而非可选项。
4. **安全加固**：`Strict-Transport-Security`（HSTS）强制浏览器只用 HTTPS 访问；Cookie 推荐 `HttpOnly; Secure; SameSite` 三件套；明文 HTTP 被主流浏览器标记"不安全"。
5. **性能工具链**：HTTP/2 Server Push 已逐步被 Early Hints（103）替代；性能评估除 ab 外，常用 wrk、hey、k6 等现代压测工具。

## 自测题

1. HTTP/1.0、HTTP/1.1、HTTP/2 在连接管理上的核心差异是什么？
2. 哪些请求方法是幂等的？幂等对运维和业务有什么实际意义？
3. 一次完整网页访问依次经过哪些步骤？DNS 解析通常基于什么协议？
4. 502 与 504 都出现在反向代理架构中，二者原因有何区别？
5. Cookie 与 Session 分别存放在哪里？服务端如何通过 Cookie 识别用户？

> **答案：**
> 1. HTTP/1.0 默认短连接，每次请求都新建 TCP 连接；HTTP/1.1 默认长连接（Keep-Alive），连接可复用；HTTP/2 在一条长连接上多路复用多个请求，并引入二进制分帧与首部压缩。
> 2. GET、HEAD、PUT、DELETE、OPTIONS、TRACE 是幂等的（多次执行与一次执行效果相同）；意义在于网络超时重试不会造成重复副作用，而 POST、PATCH 不幂等，重复提交可能产生重复记录，需业务层防重。
> 3. 浏览器解析 URL → DNS 解析（通常基于 UDP）→ TCP 三次握手 → 发送 HTTP 请求 → 服务器返回响应 → 浏览器渲染页面（可能多次请求/响应）→ TCP 四次挥手（或长连接保活）。
> 4. 502 是代理收到了上游的无效响应（上游服务崩溃或返回错误）；504 是上游响应太慢、代理等待超时。前者查上游是否存活，后者查上游处理性能。
> 5. Cookie 存放在客户端浏览器，Session 存放在服务端；登录成功后服务端生成 Session 并通过 `Set-Cookie` 下发 Session ID，客户端后续请求自动带上该 Cookie，服务端凭 Session ID 找到对应的会话数据。

## 小结

1. 网站访问流程：DNS 解析 → TCP 三次握手 → 多次 HTTP 请求/响应 → 浏览器渲染页面 → TCP 四次挥手释放连接；DNS 基于 UDP，HTTP 基于 TCP。
2. HTTP 版本从 0.9 演进到 3.0：短连接 → 长连接 → 多路复用 → 基于 QUIC 的 HTTP/3；报文由请求行（起始行）、头部、空行、主体四部分构成；GET 无请求主体，POST 有请求主体。
3. 请求方法共 9 种，重点掌握 GET/POST/PUT/DELETE/HEAD 的安全性与幂等性；状态码分 1xx 至 5xx 五类，重点掌握 200、301、302、304、403、404 与 5xx 系列。
4. 首部分为通用、请求、响应、实体四类，Host、User-Agent、Content-Type、Set-Cookie 是最高频字段。
5. HTTP 无状态，靠 Cookie/Session 维持登录态；HTTP/1.1 起默认长连接，由 keepalive_timeout 控制保活时间。
6. 资源分静态、动态、伪静态三类；评测网站关注 IP、PV、UV 与并发指标。
7. HTTPS 在 HTTP 之下增加 TLS 层，提供加密、认证与完整性，默认端口 443；HTTP 是协议，Web 服务器（Nginx/Apache 等）是协议的实现。
