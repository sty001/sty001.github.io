## 23.1 项目要求
{: .sec-expl}

### 23.1.1 原书项目与现代重做目标

原书项目用原生 socket 写一个"客户端发什么就回什么"的聊天程序，教学价值在 API 认知，工程价值接近零：没有 RAII（连接多了描述符泄漏）、没有并发模型（一个客户端阻塞所有人）、没有消息边界（TCP 字节流被当成"一 send 一 recv"）。

现代重做立四个递进目标，每个都有明确验收标准：

| 目标 | 内容 | 验收标准 |
| --- | --- | --- |
| echo-1 | POSIX 阻塞式 echo，一线程一连接 | `nc` 连上能回显；Ctrl+C 不留僵尸线程 |
| echo-2 | asio 协程版 echo | `wrk` 压 100 连接不掉线，CPU 不空转 |
| framed | 长度前缀协议（4 字节头 + 正文） | 任意长度消息不粘不漏，超长帧被拒 |
| httpd | 最小 HTTP/1.1 服务器 | `curl` 请求 200，keep-alive 复用连接 |

### 23.1.2 依赖与环境

- 编译器：GCC 11+ / Clang 14+ / MSVC 19.29+（C++20 协程），Linux 为主，Windows 上跑 POSIX 部分用 WSL。
- asio：standalone 版本 1.30+，FetchContent 接入（CMake 见 23.3.4 之前的骨架）。
- 压测：wrk 或 ab，二选一。

## 23.2 实现原理
{: .sec-expl}

### 23.2.1 TCP 与 UDP：什么时候用哪个
{: .sec-know}

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，三次握手 | 无连接，发就走 |
| 可靠性 | 不丢、不重、有序 | 尽力而为，可能丢、乱序、重复 |
| 数据形态 | 字节流，没有"消息"概念 | 数据报，一次 send 一条边界 |
| 拥塞控制 | 有，丢了会退避 | 无，丢了自己扛 |
| 典型场景 | HTTP、数据库协议、文件传输 | DNS、游戏帧同步、QUIC 底座、音视频流 |

一句话分工：要"完整送达一条消息"用 TCP（自己解决边界），要"快、能容忍丢"用 UDP。别被"UDP 比 TCP 快"带偏——快是因为省了握手和重传，代价是可靠性自己兜；局域网游戏和公网应用对丢包的容忍度完全不同。

### 23.2.2 三次握手、四次挥手与 TIME_WAIT
{: .sec-know}

握手挥手不是背口诀用的，每一步都对应一个工程参数：

- 三次握手：SYN → SYN+ACK → ACK。第三次是必须的——没有它，服务端无法确认"客户端收到了我的 SYN+ACK"，历史失效的连接请求也无法被拒绝。
- 四次挥手：FIN → ACK → FIN → ACK。四次是因为 TCP 全双工，两个方向各自关闭，中间可能插数据。
- **TIME_WAIT**：主动关闭方发完最后一个 ACK 后停留 2MSL（Linux 上 MSL 默认 30s，即 60s）。目的有二：让最后的 ACK 有机会重发；让旧连接的迷路报文在网络里自然消亡，不污染复用同四元组的新连接。

TIME_WAIT 的工程后果：高并发短连接服务（每秒几千个请求）主动关闭的一端会堆积上万个 TIME_WAIT 状态的 socket，报 `Address already in use`。这正是 `SO_REUSEADDR` 存在的理由——监听 socket 设置它之后，bind 可以无视处于 TIME_WAIT 的旧地址。

> **这里有个坑：** 开发阶段服务器重启最常见的就是 bind 报 `Address already in use`，根子是上一次连接的 TIME_WAIT 还没过期。监听 socket 一律开 `SO_REUSEADDR`，这不算投机取巧，是 POSIX 给服务端留的标准口子。注意它和 `SO_REUSEPORT`（多个 socket 绑同一端口做负载均衡）语义不同，别混用。
{: .sec-pit}

### 23.2.3 粘包与消息边界
{: .sec-know}

TCP 是字节流，`send` 两次各 100 字节，对端可能一次 `recv` 收到 200 字节；`send` 一次 1000 字节，对端也可能分五次收完。这不是 bug，是字节流的本义——"包"这个概念只存在于 IP 层，TCP 给应用层的只有一串字节。**消息边界必须由应用协议自己定义**，三条路：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 定长 | 每条消息固定 N 字节，不足补齐 | 解析最简单 | 短消息浪费带宽 |
| 分隔符 | 消息尾放 `\n` 之类的标记 | 文本协议直观（Redis、SMTP） | 正文里出现分隔符要转义 |
| 长度前缀 | 头部 N 字节写明正文长度 | 二进制高效、无歧义 | 头本身要定长，要处理字节序 |

本篇的 framed 服务器用长度前缀：4 字节大端长度 + 正文。HTTP 用的其实是两条路的组合：头用分隔符（`\r\n`），体用长度前缀（`Content-Length`）——现成的协议设计范例，值得细看。

### 23.2.4 字节序与 htonl/ntohl
{: .sec-know}

x86 是小端（低位字节放低地址），网络字节序约定为大端。多字节数值过网络必须转换，否则 0x1234 会被对端读成 0x3412。四个函数：`htonl`（host to network long，32 位）、`htons`（16 位）、`ntohl`/`ntohs` 反向。长度前缀协议的 4 字节头就是 `htonl(len)` 写入、`ntohl(raw)` 读出（实现见 23.3.6）。

```cpp
// byte_order.cpp —— 需要 -std=c++20
#include <arpa/inet.h>  // POSIX；Windows 换 winsock2.h，函数同名

#include <cstdint>
#include <iostream>

int main() {
    std::uint32_t x = 0x12345678;

    std::cout << "主机序: 0x" << std::hex << x << '\n';
    std::cout << "过网络后再读回: 0x" << ntohl(htonl(x)) << '\n';
    std::cout << "小端机器上 htonl 的中间值: 0x" << htonl(x) << '\n';
    std::cout << "本机是" << (htonl(1) == 1 ? "大端" : "小端") << '\n';
    return 0;
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra byte_order.cpp -o byte_order && ./byte_order
```

```text
主机序: 0x12345678
过网络后再读回: 0x12345678
小端机器上 htonl 的中间值: 0x78352637
本机是小端
```

`htonl` 在小端机器上做字节翻转，大端机器上是空操作——这也是它作为"可移植转换"的本质。单字节数据不需要转换，`char` 数组直接过网络。

### 23.2.5 IPv4 与 IPv6
{: .sec-know}

IPv4 地址 32 位（点分十进制），IPv6 地址 128 位（冒号十六进制）。工程上要紧的三点：

- 监听哪个族就 bind 哪个地址族，`tcp::v4()` / `tcp::v6()`；asio 里 `acceptor` 默认只接受对应族的连接，双栈要开 `v6_only(false)` 并 bind `::`。
- IPv6 下没有 NAT 的地址空间近乎无限，服务器间直连场景值得考虑；但国内公网 IPv6 就绪度参差，对外服务通常仍是 v4 优先。
- 解析字符串地址用 `inet_pton`，输出用 `inet_ntop`，`inet_addr`/`inet_ntoa` 是线程不安全的旧 API，别再用。

本篇代码统一 v4，扩展到 v6 只改地址族参数。

### 23.2.6 五种 I/O 模型的演进
{: .sec-know}

"recv 没数据时线程怎么办"——这个问题的五种答案，就是网络编程三十年的架构演进：

| 模型 | 怎么工作 | 适用规模 | 主要缺点 |
| --- | --- | --- | --- |
| 阻塞 I/O | recv 没数据就睡，直到数据到达 | 几十个连接以内 | 一个连接占死一个线程 |
| 多线程/多进程 | 每连接一线程，线程各自阻塞 | 千级连接 | 线程栈内存（默认 8MB 虚拟内存）+ 上下文切换开销 |
| 非阻塞 + 忙轮询 | socket 设 O_NONBLOCK，没数据立刻返回，循环再问 | 特殊低延迟场景 | CPU 100% 空转，常态不可接受 |
| select/poll | 一次系统调用监视一批 fd，谁就绪处理谁 | 千级连接 | select 有 FD_SETSIZE 1024 上限且每次全量拷贝扫描；poll 无上限但仍 O(n) |
| epoll/kqueue/IOCP | 内核维护就绪列表，事件驱动回调，O(1) | 十万级连接（C10K 的答案） | 编程模型复杂：回调、生命周期、取消 |

C10K 是 1999 年提出的经典问题："一台机器服务一万个并发连接"。答案就是第五列——epoll（Linux）、kqueue（BSD/macOS）、IOCP（Windows）。数量级差别要记牢：线程模型万级连接就到内存墙，事件模型十万级仍游刃有余，因为闲置连接几乎不占 CPU，只占一个内核对象。

现代服务端框架（nginx、Redis、envoy、asio 的 Linux 后端）全是 epoll 系。理解了这张表，"为什么用 asio"就不用背答案了——它替你封装了三个平台的第五列。

#### 辨析：Reactor 与 Proactor
{: .sec-iv}

- Reactor（反应器）：内核只告诉你"fd 可以读了"，**读这个动作你自己做**。epoll/kqueue 是典型，asio 在 Linux 上就是 Reactor。
- Proactor（前摄器）：内核直接把数据读到你的缓冲区，读完了才通知你"读好了，N 字节"。Windows IOCP 是典型，asio 在 Windows 上是 Proactor。

asio 的 API 按完成事件设计（`async_read_some` 传 handler），在两个平台上统一成同一种编程模型——这是它最大的价值。后果是：同一个 asio 程序在 Linux 上每个事件多一层"通知就绪→应用读"的往返，在 Windows 上则是真异步。写跨平台高性能服务时，别假设两平台延迟特性一致。

### 23.2.7 BSD socket API 全景
{: .sec-know}

POSIX socket 是一套 C API，写阻塞服务器之前把全景过一遍：

| 函数 | 作用 | 服务端/客户端 |
| --- | --- | --- |
| socket() | 创建一个通信端点，返回描述符 | 双方 |
| bind() | 把 socket 绑到本地地址+端口 | 服务端为主 |
| listen() | 标记为被动监听，参数是未 accept 队列长度 | 服务端 |
| accept() | 取出一个完成的连接，返回新 socket | 服务端 |
| connect() | 发起连接（触发三次握手） | 客户端 |
| send()/recv() | 写/读字节流 | 双方 |
| close() | 关闭描述符，释放资源 | 双方 |
| shutdown() | 单向关闭（读/写/读写），发 FIN | 双方 |

几个高频细节，每个都对应一个真实 bug：

- **shutdown 与 close**：close 是"我不要这个描述符了"，进程资源层面回收，缓冲区里没发完的数据内核仍会尝试发；shutdown(SHUT_WR) 是"我这边写完了"，发 FIN 但还能继续读对端——半关闭，echo 客户端的标准收尾姿势。close 时若接收缓冲区还有未读数据，内核可能直接回 RST，对端收到 `Connection reset`。
- **SIGPIPE**：向一个已被对端关闭的 socket write，内核给进程发 SIGPIPE，默认动作是**杀进程**。服务器必须在 write 时带 `MSG_NOSIGNAL`（Linux）、或 `SO_NOSIGPIPE`（macOS）、或进程启动时 `signal(SIGPIPE, SIG_IGN)` 三选一。忘了这事的进程都死于"莫名其妙就没服务了"。
- **EINTR**：慢系统调用被信号打断返回 -1 且 errno 为 EINTR，不是真错误，重试即可。写裸 socket 代码要养成 `while (ret < 0 && errno == EINTR)` 的习惯；用 asio 则不用管，库内部处理了。
- **EAGAIN/EWOULDBLOCK**：非阻塞 socket 没数据可读/缓冲区满时的返回，含义是"现在不行，等会儿再试"。事件模型里它等价于"回到事件循环继续等"。

> **注意：** send 返回成功不等于"对方收到了"，只等于"数据进了本机内核发送缓冲区"。送达确认、重传都是 TCP 的事。做应用层 ACK 的前提是先想清楚这一点。
{: .sec-note}

## 23.3 具体实现
{: .sec-prac}

### 23.3.1 RAII 阻塞式 echo 服务器

第一个完整服务器。核心工程手段是 RAII 封装描述符——socket 本质是个整数句柄，泄漏了内核不会提醒你，只能靠封装兜底：

```cpp
// echo_server.cpp —— 需要 -std=c++20；Linux（macOS 无 MSG_NOSIGNAL，要用 SO_NOSIGPIPE；Windows 需 WSAStartup，见正文说明）
#include <arpa/inet.h>
#include <netinet/in.h>
#include <sys/socket.h>
#include <unistd.h>

#include <cerrno>
#include <csignal>
#include <cstdint>
#include <iostream>
#include <string>
#include <system_error>
#include <thread>
#include <utility>
#include <vector>

// RAII 句柄：析构时 close，异常路径也不泄漏
class Socket {
public:
    Socket() = default;
    explicit Socket(int fd) : fd_(fd) {}
    ~Socket() {
        if (fd_ >= 0) ::close(fd_);
    }

    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;
    Socket(Socket&& other) noexcept : fd_(std::exchange(other.fd_, -1)) {}
    Socket& operator=(Socket&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) ::close(fd_);
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

    int get() const { return fd_; }

private:
    int fd_ = -1;
};

int checked(int ret, const char* what) {
    if (ret < 0) throw std::system_error(errno, std::generic_category(), what);
    return ret;
}

Socket create_listener(std::uint16_t port) {
    Socket sock{::socket(AF_INET, SOCK_STREAM, 0)};
    int yes = 1;
    checked(::setsockopt(sock.get(), SOL_SOCKET, SO_REUSEADDR, &yes, sizeof(yes)),
            "setsockopt");

    sockaddr_in addr{};
    addr.sin_family      = AF_INET;
    addr.sin_addr.s_addr = htonl(INADDR_ANY);
    addr.sin_port        = htons(port);
    checked(::bind(sock.get(), reinterpret_cast<sockaddr*>(&addr), sizeof(addr)), "bind");
    checked(::listen(sock.get(), 128), "listen");
    return sock;
}

void handle_client(int cfd) {
    Socket client{cfd};
    char buf[4096];
    for (;;) {
        ssize_t n = ::recv(cfd, buf, sizeof(buf), 0);
        if (n == 0) break;              // 对端正常关闭
        if (n < 0) {
            if (errno == EINTR) continue;  // 被信号打断，重试
            break;                         // 真错误，结束这条连接
        }
        ssize_t sent = 0;
        while (sent < n) {              // send 不保证一次发完，必须循环
            ssize_t m = ::send(cfd, buf + sent, static_cast<std::size_t>(n - sent),
                               MSG_NOSIGNAL);
            if (m < 0) {
                if (errno == EINTR) continue;
                return;
            }
            sent += m;
        }
    }
}

int main(int argc, char* argv[]) {
    std::signal(SIGPIPE, SIG_IGN);  // 双保险：MSG_NOSIGNAL 之外再全局忽略
    std::uint16_t port =
        argc > 1 ? static_cast<std::uint16_t>(std::stoi(argv[1])) : 55555;

    Socket listener = create_listener(port);
    std::cout << "listening on " << port << '\n';

    std::vector<std::thread> workers;  // 演示代码不回收线程；生产要管理生命周期
    for (;;) {
        int cfd = ::accept(listener.get(), nullptr, nullptr);
        if (cfd < 0) {
            if (errno == EINTR) continue;
            std::cerr << "accept failed: " << errno << '\n';
            continue;
        }
        workers.emplace_back(handle_client, cfd);  // 一线程一连接
    }
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra echo_server.cpp -o echo_server -pthread
./echo_server 55555
```

```text
listening on 55555
```

另开终端验证：

```bash

```

```text

```

三个值得盯住的细节：`SO_REUSEADDR` 在 bind 前设置（23.2.2 讲过为什么）；`MSG_NOSIGNAL` 防止对端断开后写 socket 杀死进程；`send` 用 while 循环——它只承诺"发进了缓冲区多少"，少发是常态。Windows 上跑这段需要 WSAStartup/WSACleanup 包裹、`closesocket` 代替 close，且 `MSG_NOSIGNAL` 不存在（Windows 的 send 不产生 SIGPIPE）——这就是为什么生产代码直接上 asio。

一线程一连接的天花板也在这：1000 个连接就是 1000 个线程，内存和调度都吃不消。往下走。

### 23.3.2 asio 核心概念：io_context、executor、异步操作
{: .sec-know}

asio 的三个地基：

- **io_context**：事件循环本体。所有异步操作的完成事件都在它上面排队，`ctx.run()` 驱动它，run 返回即循环结束。一个进程可以有多个 io_context（多 reactor 模式），也可以多线程共享一个。
- **executor**：io_context 的执行策略抽象，决定"这段代码在哪个线程跑"。多线程 io_context 里保护共享状态用 `strand`（串行化执行器），见 23.3.7。
- **异步操作与完成处理器**：`sock.async_read_some(buf, handler)` 发起读就立刻返回，数据到达时 asio 在 io_context 的线程里调用 handler。C++20 协程模式下，`co_await op(use_awaitable)` 把 handler 换成挂起/恢复协程，代码形状回到同步风格，执行效率是事件驱动。

死记这三者关系不如记一个画面：io_context 是一台抽水机，异步操作是接到水管上的水龙头，run() 是通电，executor 是水流走哪条管道。

### 23.3.3 三种写法对照：同步、异步回调、协程
{: .sec-know}

同一个 echo 服务器，三种范式长什么样。先同步（asio 版，阻塞语义同 23.3.1，但跨平台）：

```cpp
// sync_echo.cpp —— 需要 -std=c++20，链接 asio
#include <asio.hpp>
#include <iostream>
#include <thread>
#include <vector>

int main() {
    asio::io_context ctx;
    asio::ip::tcp::acceptor acceptor(ctx, {asio::ip::tcp::v4(), 55555});
    std::cout << "listening on 55555\n";

    std::vector<std::thread> threads;
    for (;;) {
        asio::ip::tcp::socket sock(ctx);
        acceptor.accept(sock);  // 阻塞等待新连接
        threads.emplace_back([sock = std::move(sock)]() mutable {  // 所有权移进线程
            try {
                char data[4096];
                for (;;) {
                    std::size_t n = sock.read_some(asio::buffer(data));
                    asio::write(sock, asio::buffer(data, n));
                }
            } catch (const asio::system_error&) {
                // 连接断开：read_some 抛异常，线程自然结束
            }
        });
    }
}
```

异步回调版——注意共享指针和自身递归，这是回调风格绕不开的两件套：

```cpp
// async_echo.cpp —— 需要 -std=c++20，链接 asio
#include <asio.hpp>
#include <functional>
#include <iostream>
#include <memory>
#include <vector>

void do_read(std::shared_ptr<asio::ip::tcp::socket> sock,
             std::shared_ptr<std::vector<char>> buf);

void do_write(std::shared_ptr<asio::ip::tcp::socket> sock,
              std::shared_ptr<std::vector<char>> buf, std::size_t n) {
    asio::async_write(*sock, asio::buffer(*buf, n),
        [sock, buf](std::error_code ec, std::size_t) {
            if (!ec) do_read(sock, buf);
        });
}

void do_read(std::shared_ptr<asio::ip::tcp::socket> sock,
             std::shared_ptr<std::vector<char>> buf) {
    sock->async_read_some(asio::buffer(*buf),
        [sock, buf](std::error_code ec, std::size_t n) {
            if (ec) return;  // 出错或对端关闭：什么都不做，shared_ptr 释放 socket
            do_write(sock, buf, n);
        });
}

int main() {
    asio::io_context ctx;
    asio::ip::tcp::acceptor acceptor(ctx, {asio::ip::tcp::v4(), 55555});

    std::function<void()> do_accept;
    do_accept = [&] {
        acceptor.async_accept([&](std::error_code ec, asio::ip::tcp::socket peer) {
            if (!ec) {
                auto sock = std::make_shared<asio::ip::tcp::socket>(std::move(peer));
                auto buf  = std::make_shared<std::vector<char>>(4096);
                do_read(sock, buf);
            }
            do_accept();  // 继续收下一个连接
        });
    };
    do_accept();
    ctx.run();
}
```

协程版（完整展开在下一节）。三种写法的取舍：

| 范式 | 优点 | 缺点 | 什么时候用 |
| --- | --- | --- | --- |
| 同步 | 直观、好调试 | 阻塞线程，连接多了不可行 | 工具脚本、连接数个位数的内部服务 |
| 回调 | 无协程依赖，最老的平台也支持 | 回调地狱，状态靠 shared_ptr 硬撑 | 维护旧代码、协程不可用时 |
| 协程 | 同步的形状、异步的效率，状态就是局部变量 | 需要 C++20、栈上变量生命周期要留神（23.3.5） | 新代码默认选它 |

### 23.3.4 协程版 echo 服务器（推荐写法）
{: .sec-prac}

C++20 协程（`co_await`/`co_return`）配合 asio 的 `awaitable`，同一个 echo 服务器只剩三十行：

```cpp
// coroutine_echo.cpp —— 需要 -std=c++20，链接 asio
#include <asio.hpp>
#include <iostream>

using asio::ip::tcp;

asio::awaitable<void> session(tcp::socket sock) {
    try {
        char data[4096];
        for (;;) {
            std::size_t n =
                co_await sock.async_read_some(asio::buffer(data), asio::use_awaitable);
            co_await asio::async_write(sock, asio::buffer(data, n),
                                       asio::use_awaitable);
        }
    } catch (const std::exception&) {
        // 对端关闭或网络错误：协程结束，socket 随之析构
    }
}

asio::awaitable<void> listener() {
    auto ex = co_await asio::this_coro::executor;
    tcp::acceptor acceptor(ex, {tcp::v4(), 55555});
    for (;;) {
        tcp::socket sock = co_await acceptor.async_accept(asio::use_awaitable);
        asio::co_spawn(ex, session(std::move(sock)), asio::detached);
    }
}

int main() {
    asio::io_context ctx;
    asio::co_spawn(ctx, listener(), asio::detached);
    ctx.run();
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra coroutine_echo.cpp -o coroutine_echo \
    -I build/_deps/asio-src/asio/include -pthread
```

四个协程原语的分工：

- `asio::awaitable<T>`：协程的返回类型，"这是一个可以 co_await 的异步任务，产出 T"。
- `use_awaitable`：完成令牌（completion token），把"异步操作完成时"接到"恢复本协程"上。
- `co_spawn`：把一个 awaitable 调度到 executor 上跑，返回的协程自此独立生长。
- `detached`：完成令牌的另一种——协程结束后不通知任何人。生产代码若要收集异常，换成带回调的令牌。

对照 23.3.3 的回调版看：连接状态（buffer、读写字节数）从 shared_ptr 的成员变成了局部变量，"回调链"变成了一个 for 循环。这不是语法糖，是状态管理方式的降维。

### 23.3.5 缓冲区所有权：异步写最大的坑
{: .sec-warn}

asio 的异步操作发起后**立刻返回**，真正的 I/O 在之后某刻由内核完成——这期间操作引用的缓冲区必须一直活着。看一个 undefined behavior：

```cpp
// 错误示范：undefined behavior —— 异步写还没执行，msg 已经析构
void bad_send(asio::ip::tcp::socket& sock) {
    std::string msg = "hello";
    asio::async_write(sock, asio::buffer(msg),
                      [](std::error_code, std::size_t) {});  // msg 在此销毁
    // 内核随后访问的内存已经是悬垂引用，崩溃或发出垃圾数据
}

// 正确：把缓冲区的所有权一起交给异步操作
void good_send(asio::ip::tcp::socket& sock) {
    auto msg = std::make_shared<std::string>("hello");
    asio::async_write(sock, asio::buffer(*msg),
                      [msg](std::error_code, std::size_t) {});  // msg 活到回调结束
}
```

协程版天然规避了一半：`co_await` 挂起期间协程帧活着，局部变量安全——23.3.4 的 `data[4096]` 就是这个道理。但两个变体仍会踩雷：

- 协程里 `co_await` 之前先 `return`/`co_return`，或者把缓冲区放进外层循环每次迭代重新声明的变量而异步写横跨迭代。
- 把栈上缓冲区的地址塞进某个将来才执行的异步操作（比如挂进发送队列却没拷贝数据）。

判断法只有一个：**从发起异步操作到 handler 执行完毕，这段窗口里缓冲区的每一次析构都是 UB**。写完任何异步 I/O 都拿这个窗口过一遍。

### 23.3.6 长度前缀协议完整实现
{: .sec-prac}

把 23.2.3 的"长度前缀"方案落成代码：4 字节大端长度 + 正文。收发两个函数，帧上限防恶意长度：

```cpp
// framed_echo.cpp —— 需要 -std=c++20，链接 asio
#include <arpa/inet.h>

#include <asio.hpp>

#include <cstdint>
#include <cstring>
#include <iostream>
#include <stdexcept>
#include <string>

using asio::ip::tcp;

constexpr std::uint32_t kMaxFrame = 64u * 1024u * 1024u;  // 单帧上限 64MB

asio::awaitable<void> send_frame(tcp::socket& sock, std::string body) {
    std::uint32_t len = htonl(static_cast<std::uint32_t>(body.size()));
    std::string frame(reinterpret_cast<const char*>(&len), 4);
    frame += body;
    // 一次 co_await 发完整帧；async_write 保证写够才返回
    co_await asio::async_write(sock, asio::buffer(frame), asio::use_awaitable);
}

asio::awaitable<std::string> recv_frame(tcp::socket& sock) {
    char header[4];
    // async_read 与 async_read_some 不同：读不满 4 字节绝不返回
    co_await asio::async_read(sock, asio::buffer(header, 4), asio::use_awaitable);

    std::uint32_t raw = 0;
    std::memcpy(&raw, header, 4);  // memcpy 而非重解释转换，避免对齐问题
    std::uint32_t len = ntohl(raw);
    if (len > kMaxFrame) throw std::runtime_error("frame too large");

    std::string body(len, '\0');
    if (len > 0) {
        co_await asio::async_read(sock, asio::buffer(body.data(), body.size()),
                                  asio::use_awaitable);
    }
    co_return body;
}

asio::awaitable<void> session(tcp::socket sock) {
    try {
        for (;;) {
            std::string body = co_await recv_frame(sock);
            co_await send_frame(sock, body);  // 原样回显
        }
    } catch (const std::exception&) {
    }
}

asio::awaitable<void> listener() {
    auto ex = co_await asio::this_coro::executor;
    tcp::acceptor acceptor(ex, {tcp::v4(), 55555});
    for (;;) {
        tcp::socket sock = co_await acceptor.async_accept(asio::use_awaitable);
        asio::co_spawn(ex, session(std::move(sock)), asio::detached);
    }
}

int main() {
    asio::io_context ctx;
    asio::co_spawn(ctx, listener(), asio::detached);
    ctx.run();
}
```

用 Python 客户端验证（几行就能构造合法帧）：

s.sendall(struct.pack(">I", len(msg)) + msg)   # ">I" = 大端 4 字节无符号

(body_len,) = struct.unpack(">I", header)
body = b""

`async_read` 与 `async_read_some` 的区别是这里的命门：前者读满指定字节数才完成（帧协议专用），后者"有多少给多少"（字节流语义）。用错了前者写后者、或者反过来，粘包 bug 立刻上线。

### 23.3.7 strand 与多线程 io_context
{: .sec-know}

默认所有协程跑在一个线程的 io_context 上，没有数据竞争——但也没有并行。要吃满多核，常见做法是"线程池共享一个 io_context"或"每线程一个 io_context"。前者一旦多个协程碰共享状态，就需要 **strand**：同一个 strand 上的任务保证不并发执行，等效于"细粒度的互斥，但零锁开销"。

```cpp
// strand 片段 —— 多线程 io_context 里访问共享状态必须经过 strand
auto strand = asio::make_strand(ctx);

asio::post(strand, [] { /* 排进 strand 的任务不会与其他 strand 任务并发 */ });

asio::co_spawn(strand, my_coroutine(), asio::detached);  // 协程体也被串行化
```

什么时候不用 strand：状态本来就是每连接私有的（23.3.4 的 echo 就是），单线程 io_context，或者用"每线程一个 io_context"让数据天然绑定线程。后一种要把连接固定到某个线程的 io_context 上，负载均衡自己操心——所以多数项目选共享 io_context + strand。

### 23.3.8 HTTP 最小实现
{: .sec-prac}

HTTP/1.1 是学习消息边界的最佳教材：头部用 `\r\n` 分隔符界定、以空行结束，正文用 `Content-Length` 界定。最小实现支持 GET 路由和 keep-alive：

```cpp
// http_server.cpp —— 需要 -std=c++20，链接 asio
#include <asio.hpp>

#include <iostream>
#include <string>
#include <string_view>
#include <unordered_map>

using asio::ip::tcp;

namespace http {

struct Request {
    std::string method;
    std::string target;
    std::unordered_map<std::string, std::string> headers;
};

// 请求解析：请求行 → 头部逐行 → 空行结束（状态机思想，每步只消费确定的部分）
Request parse(std::string_view text) {
    Request req;

    auto line_end = text.find("\r\n");
    if (line_end == std::string_view::npos) return req;

    std::string_view request_line = text.substr(0, line_end);
    auto sp1 = request_line.find(' ');
    auto sp2 = request_line.find(' ', sp1 + 1);
    if (sp1 == std::string_view::npos || sp2 == std::string_view::npos) return req;
    req.method = std::string(request_line.substr(0, sp1));
    req.target = std::string(request_line.substr(sp1 + 1, sp2 - sp1 - 1));

    std::size_t pos = line_end + 2;
    for (;;) {
        auto e = text.find("\r\n", pos);
        if (e == std::string_view::npos || e == pos) break;  // 空行 = 头结束
        std::string_view line = text.substr(pos, e - pos);
        auto colon = line.find(':');
        if (colon != std::string_view::npos) {
            std::string key(line.substr(0, colon));
            std::string value(line.substr(colon + 1));
            if (!value.empty() && value.front() == ' ') value.erase(0, 1);
            req.headers[key] = value;
        }
        pos = e + 2;
    }
    return req;
}

std::string response(std::string_view body) {
    return "HTTP/1.1 200 OK\r\n"
           "Content-Type: text/plain; charset=utf-8\r\n" +
           "Content-Length: " + std::to_string(body.size()) + "\r\n" +
           "Connection: keep-alive\r\n"
           "\r\n" +
           std::string(body);
}

}  // namespace http

asio::awaitable<void> session(tcp::socket sock) {
    try {
        sock.set_option(tcp::no_delay(true));  // 见 23.3.13：关 Nagle，降交互延迟
        std::string buf;
        char chunk[4096];
        for (;;) {
            // 读到完整请求头（\r\n\r\n）为止；简化实现不处理请求体
            buf.clear();
            std::size_t n =
                co_await sock.async_read_some(asio::buffer(chunk), asio::use_awaitable);
            buf.append(chunk, n);
            while (buf.find("\r\n\r\n") == std::string::npos) {
                n = co_await sock.async_read_some(asio::buffer(chunk),
                                                  asio::use_awaitable);
                if (n == 0) break;
                buf.append(chunk, n);
            }

            auto req  = http::parse(buf);
            std::string body;
            if (req.target == "/")
                body = "hello, world";
            else if (req.target == "/ping")
                body = "pong";
            else
                body = "not found";  // 生产实现该返回 404 状态行

            co_await asio::async_write(sock, asio::buffer(http::response(body)),
                                       asio::use_awaitable);
            // keep-alive：不关连接，回到循环等下一个请求
        }
    } catch (const std::exception&) {
    }
}

asio::awaitable<void> listener() {
    auto ex = co_await asio::this_coro::executor;
    tcp::acceptor acceptor(ex, {tcp::v4(), 8080});
    for (;;) {
        tcp::socket sock = co_await acceptor.async_accept(asio::use_awaitable);
        asio::co_spawn(ex, session(std::move(sock)), asio::detached);
    }
}

int main() {
    asio::io_context ctx;
    asio::co_spawn(ctx, listener(), asio::detached);
    ctx.run();
}
```

### 23.3.9 并发模型选择与线程池骨架
{: .sec-know}

| 模型 | 形态 | 适合 | 不适合 |
| --- | --- | --- | --- |
| 一线程一连接 | 每连接一个线程（或协程单线程） | 连接数百级、逻辑重、怕复杂度 | 万级连接（线程版） |
| 线程池 + io_context 池 | N 线程各跑一个 io_context，连接哈希绑定 | 连接间无共享状态，CPU 型任务 | 连接迁移、共享状态多 |
| 共享 io_context + strand | M 线程跑同一个 ctx，共享状态走 strand | 万级连接、有共享缓存/路由表 | 对单点串行化敏感的热点 |

线程池骨架（共享单 io_context 版）：

```cpp
// pool.cpp 骨架 —— 需要 -std=c++20，链接 asio
#include <asio.hpp>

#include <algorithm>
#include <thread>
#include <vector>

int main() {
    asio::io_context ctx;
    auto work = asio::make_work_guard(ctx);  // 没 IO 事件时不让 run() 返回

    const unsigned nthreads = std::max(1u, std::thread::hardware_concurrency());
    std::vector<std::thread> pool;
    for (unsigned i = 0; i < nthreads; ++i) {
        pool.emplace_back([&ctx] { ctx.run(); });
    }

    // 任务通过 co_spawn / post 投递进 ctx……
    asio::co_spawn(ctx, []() -> asio::awaitable<void> { co_return; }, asio::detached);

    work.reset();  // 释放 work guard，队列跑完 run() 自然返回
    for (auto& t : pool) t.join();
}
```

`make_work_guard` 的作用：io_context 没有任何待处理事件时 `run()` 会立刻返回，线程池模式里这等于线程全部退出。work guard 人为"占一个坑"，显式 reset 之前循环不会空转退出——23.3.10 的优雅退出靠的也是它。

### 23.3.10 优雅退出：signal_set、work guard 与 draining
{: .sec-prac}

进程收到 Ctrl+C（SIGINT）默认直接死——正在写的响应截断、正在处理的请求丢失。优雅退出三件套：

```cpp
// graceful.cpp —— 需要 -std=c++20，链接 asio
#include <asio.hpp>
#include <iostream>
#include <system_error>

using asio::ip::tcp;

asio::awaitable<void> session(tcp::socket sock) {
    try {
        char data[4096];
        for (;;) {
            std::size_t n = co_await sock.async_read_some(asio::buffer(data),
                                                          asio::use_awaitable);
            co_await asio::async_write(sock, asio::buffer(data, n),
                                       asio::use_awaitable);
        }
    } catch (const std::exception&) {
    }
}

asio::awaitable<void> listener(tcp::acceptor& acceptor) {
    auto ex = co_await asio::this_coro::executor;
    try {
        for (;;) {
            tcp::socket sock = co_await acceptor.async_accept(asio::use_awaitable);
            asio::co_spawn(ex, session(std::move(sock)), asio::detached);
        }
    } catch (const std::exception&) {
        // acceptor 被 close 后 async_accept 抛错，协程从这里退出
    }
}

int main() {
    asio::io_context ctx;
    auto work = asio::make_work_guard(ctx);

    tcp::acceptor acceptor(ctx, {tcp::v4(), 55555});
    asio::co_spawn(ctx, listener(acceptor), asio::detached);

    asio::signal_set signals(ctx, SIGINT, SIGTERM);
    signals.async_wait([&](auto, int signo) {
        std::cout << "caught signal " << signo << ", draining\n";
        std::error_code ignored;
        acceptor.close(ignored);  // 第一步：不再接新连接
        work.reset();             // 第二步：释放守卫，等存量连接自然跑完
    });

    ctx.run();                    // 存量连接全部结束后 run() 才返回
    std::cout << "server exit\n";
}
```

```text
listening on 55555
^Ccaught signal 2, draining
server exit
```

这套流程就是 **draining（排空）**：先关流量入口，让存量请求跑完，再退出。两个工程细节：

- listener 协程里的 try/catch 不能省——close 后挂起的 async_accept 以错误完成，co_await 处会抛出 system_error；detached 令牌会把这个异常静默吞掉，不加 catch 连一条日志都没有，退出路径出了问题也无从排查。
- 如果连接是 keep-alive 的（永不主动断），draining 会永远等不到头。生产做法是信号触发后再设一个总时限，到点 `ctx.stop()` 强制收摊。C++20 的 `std::stop_token`（配合 `std::jthread`）可以拿来做外部取消源的传递，但 asio 的取消体系以 completion token 为核心，两者各管各的层。

### 23.3.11 超时与心跳
{: .sec-prac}

不设超时的服务器是慢连接攻击的首选目标：一万客户端连上不发数据，资源全耗在等。asio 里用 `steady_timer` 加协程操作符做"读超时"：

```cpp
// timeout.cpp 片段 —— 需要 -std=c++20，链接 asio 1.22+（依赖对 socket 操作的取消支持）
#include <asio.hpp>
#include <asio/experimental/awaitable_operators.hpp>

#include <optional>
#include <variant>

using namespace asio::experimental::awaitable_operators;  // 提供逻辑 || 运算符
using asio::ip::tcp;

// 读一次数据；30 秒没动静就取消读并返回空
asio::awaitable<std::optional<std::size_t>> read_with_timeout(tcp::socket& sock,
                                                              char* buf,
                                                              std::size_t size) {
    using namespace std::chrono_literals;
    auto ex = co_await asio::this_coro::executor;
    asio::steady_timer timer(ex);
    timer.expires_after(30s);

    // 读和定时器赛跑：谁先完成返回谁，另一个被自动取消
    auto which = co_await (sock.async_read_some(asio::buffer(buf, size),
                                                asio::use_awaitable) ||
                           timer.async_wait(asio::use_awaitable));

    if (which.index() == 0) {
        co_return std::get<0>(which);  // 正常读到数据
    }
    sock.cancel();  // 定时器先到：取消挂起的读，调用方据此断开连接
    co_return std::nullopt;
}
```

`||` 返回 `std::variant<std::size_t, std::monostate>`，按 index 判断赢家。心跳是同一招反过来用：服务端定期发 ping 帧（23.3.6 的 send_frame 包一层循环），客户端 N 秒收不到 pong 就断线重连——把"对端还活着吗"从猜测变成测量。

### 23.3.12 TLS：asio::ssl
{: .sec-prac}

TLS 在 asio 里是套在 socket 外面的流过滤器：`ssl::stream<tcp::socket>` 换掉 `tcp::socket`，握手多一步，收发 API 形状不变。最小 TLS echo：

```cpp
// tls_echo.cpp —— 需要 -std=c++20；链接 asio 与 OpenSSL
#include <asio.hpp>
#include <asio/ssl.hpp>

#include <iostream>

using asio::ip::tcp;
namespace ssl = asio::ssl;

asio::awaitable<void> session(ssl::stream<tcp::socket> stream) {
    try {
        co_await stream.async_handshake(ssl::stream_base::server,
                                        asio::use_awaitable);  // TLS 握手
        char data[4096];
        for (;;) {
            std::size_t n = co_await stream.async_read_some(asio::buffer(data),
                                                            asio::use_awaitable);
            co_await asio::async_write(stream, asio::buffer(data, n),
                                       asio::use_awaitable);
        }
    } catch (const std::exception&) {
    }
}

asio::awaitable<void> listener(ssl::context& tls) {
    auto ex = co_await asio::this_coro::executor;
    tcp::acceptor acceptor(ex, {tcp::v4(), 55556});
    try {
        for (;;) {
            tcp::socket peer = co_await acceptor.async_accept(asio::use_awaitable);
            asio::co_spawn(ex, session(ssl::stream<tcp::socket>(std::move(peer), tls)),
                           asio::detached);
        }
    } catch (const std::exception&) {
    }
}

int main() {
    asio::io_context ctx;

    ssl::context tls(ssl::context::tls_server);
    tls.use_certificate_chain_file("server.crt");
    tls.use_private_key_file("server.key", ssl::context::pem);

    asio::co_spawn(ctx, listener(tls), asio::detached);
    ctx.run();
}
```

本地生成测试证书：

```bash
openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt \
        -days 365 -subj "/CN=localhost"
g++ -std=c++20 -O2 -Wall -Wextra tls_echo.cpp -o tls_echo \
    -I build/_deps/asio-src/asio/include -pthread -lssl -lcrypto
```

连接验证：`openssl s_client -connect 127.0.0.1:55556`，握手成功后输入的字符会回显。生产环境别用自签证书，客户端校验那套（证书链、SNI、ALPN）是另一个话题，这里只建立"TLS 就是换一层流"的心智。

### 23.3.13 性能与压测
{: .sec-know}

没有压测数据的优化都是猜。两个标准工具：

```bash

```

  Thread Stats   Avg      Stdev     Max   +/- Stdev
    Latency     1.23ms    0.87ms   25.10ms   90.34%

（数字是某次实测的形态示例，绝对值随机器、内核参数、连接数变化，看分布不看单值。）

读压测结果的三个要点：

- **延迟看分布不看均值**：Avg 1ms 但 Max 25ms 意味着长尾明显，用户感知由长尾决定。wrk 的 `+/- Stdev` 列和 `--latency` 明细是定位抖动的入口。
- **连接数与吞吐非线性**：c 从 100 到 1000，QPS 通常先升后平再降——降的那段往往撞上了线程竞争、fd 上限（`ulimit -n`）或端口耗尽。
- **TCP_NODELAY 与 Nagle**：Nagle 算法把小包攒大再发（省带宽，加延迟），交互式协议（echo、HTTP 小响应）一律 `sock.set_option(tcp::no_delay(true))` 关掉它。23.3.8 已带这行——漏掉它，curl 打一次请求偶尔平白多等 40ms，写过实时服务的人都懂这个坑的隐蔽。

> **这里有个坑：** 本机压测自家服务器，回环地址不走真实网卡，延迟天然偏低；文件描述符上限、临时端口范围（`net.ipv4.ip_local_port_range`）也和线上不同。本机结果只用于相对比较（改前 vs 改后），绝对容量要在线上环境复测。

### 23.3.14 网络编程常见坑清单
{: .sec-ts}

| 坑 | 症状 | 规避 |
| --- | --- | --- |
| 缓冲区悬垂 | 异步写偶发崩溃或发出垃圾字节 | 23.3.5 的窗口检查法；协程版让缓冲区活在协程帧里 |
| 半关闭处理错 | 客户端 shutdown 写端后收不到回显 | echo 服务端以 recv 返回 0 为终止条件，别靠"读出错" |
| 忘用 strand | 多线程 ctx 下计数器、map 偶发损坏，难复现 | 共享状态一律过 strand；或单线程 ctx |
| work guard 漏配 | io_context 没事件时 run() 直接返回，服务器"启动即退出" | 常驻服务必须 make_work_guard，退出时 reset |
| 异步操作不取消 | 关连接后回调还在跑，访问已析构对象 | close/cancel 触发 operation_aborted，handler 里先查错误码 |
| 阻塞调用混进协程 | 一个慢磁盘读写卡死整个 io_context 线程 | 协程里只允许异步 I/O；阻塞活扔 std::thread 或另起线程池 |
| SIGPIPE 忽略 | 对端断开后进程无声死亡 | 裸 socket 三选一（23.2.7）；asio 的 async_write 仍需注意同步 write 场景 |
| TIME_WAIT 堆积 | 重启报 Address already in use | 监听 socket 开 SO_REUSEADDR；架构上避免高频短连接 |

## 变式追问
{: .sec-think}

- **为什么 23.3.6 的 recv_frame 读头用 async_read 而读正文前要先检查长度上限？** 上限检查是防御恶意或损坏的输入：长度字段来自对端，读多少字节由它说了算，不设上限的话一个声称 4GB 的帧就让服务器白等或爆内存。这是"永远不信任网络输入"在网络层的具体化——和 SQL 注入是同一条原则，只是形态不同。
- **协程版的 data[4096] 是栈变量，为什么没有 23.3.5 的悬垂问题？** 协程的局部变量不放在线程栈上，而是存在协程帧（堆上的状态块）里；co_await 挂起时协程帧活着，恢复时变量还在原地。危险的写法是"把地址存到协程外面将来才用"，比如挂进一个跨协程的队列。悬垂判据不变：异步操作执行期间，缓冲区所在的那块内存必须仍然有效——协程帧只是让"活着"这件事自动成立的机制。
- **draining 时如果 keep-alive 连接永远不断，ctx.run() 会不会永远不返回？** 会。挂起的异步读本身就是"未完成的工作"，io_context 因此不会空。所以信号处理里 close 入口只是第一步，还必须加总时限：到点调 ctx.stop() 强制让 run() 返回，未完成请求按业务策略放弃或落盘。优雅退出永远是"尽力排空 + 兜底超时"的组合，没有纯排空的方案。
- **什么时候该拒绝 asio，直接写 epoll？** 连接模型极端简单（比如只有几万条长连接、每连接一条固定流程），或要对延迟做到纳秒级可控（自研网关、行情网关）。epoll 直写换来的是去掉一层抽象的间接性，代价是可移植性和取消/超时这些"库免费送"的能力全要手写。绝大多数服务端项目里，asio 抽象的成本远小于它省下的 bug——先跑通，再谈掀桌子。
