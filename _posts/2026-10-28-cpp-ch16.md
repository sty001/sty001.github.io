模板是 C++ 里唯一一套"写一次、编译多份"的机制，也是整个标准库的骨架——`vector`、`optional`、`sort`、`format` 全是它的产物。这一篇从"当年没有模板时我们怎么写通用代码"讲起，覆盖 16.1 到 16.5：模板的动机与零开销抽象、实例化模型与代码膨胀、函数模板的五种推导形态、显式实参与非推导语境、类模板的按需实例化与特化（偏特化、全特化、ODR 陷阱）、变量模板与 NTTP 三代演进、SFINAE 及其代价、C++20 Concepts 与 requires 的四种需求形式、可变参数模板与折叠表达式、完美转发、CTAD，然后是工程侧的几个硬骨头：为什么实现必须放头文件、`extern template` 怎么省编译时间、`typename` 与 `template` 关键字、模板元编程入门、错误信息怎么读、模板与 ABI。读完你应该能判断"这个需求该用重载、虚函数还是模板"，也能把一堆 SFINAE 老代码改成 concept 而不改行为。

## 16.1 基本概念
{: .sec-expl}

### 16.1.1 没有模板的年代：三条"泛型"路线及其代价
{: .sec-know}

写一个"取两个值里较大的那个"的函数，只支持 `int` 显然不够。C++98 之前只有三条路可走，各有各的坑：

| 方案 | 类型安全 | 运行期开销 | 能表达的算法 | 典型故障 |
| --- | --- | --- | --- | --- |
| 宏 `#define MAX(a,b)` | 没有，纯文本替换 | 无，但实参可能被求值多次 | 极有限，写不了复杂逻辑 | 优先级错误、实参副作用、调试器看不到 |
| `void*` + 函数指针回调 | 没有，编译器看不见类型 | 每次比较一次间接调用 | 有限，比较逻辑得拆成回调 | 类型传错不报错，直接内存错乱 |
| 手写多个重载 | 有，但靠人肉复制 | 无 | 任意 | 改一处漏一处，维护成本爆炸 |
| 模板 | 完整 | 无，实例化后就是普通函数 | 任意 | 错误信息长、可能代码膨胀 |

三条老路线至今还在代码库里躺着（C 标准库的 `qsort`、`bsearch` 就是 `void*` 路线的活标本）。它们的问题不是"慢"，而是**把类型检查的责任从编译器转移给了程序员**：`qsort` 传错元素大小，编译器一声不吭，跑起来读越界。

```cpp
// why_template.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

// 路线一：宏。参数求值次数不受控
#define MAX_MACRO(a, b) ((a) > (b) ? (a) : (b))

// 路线二：void*。类型信息在接口上被抹掉，比较逻辑退化成回调
static int cmp_int(const void* a, const void* b) {
    return *(const int*)a - *(const int*)b;   // 减法比较有溢出风险，见下方坑位
}
const void* max_voidp(const void* a, const void* b,
                      int (*cmp)(const void*, const void*)) {
    return cmp(a, b) >= 0 ? a : b;
}

// 路线三：模板。类型保留到实例化，编译期生成 int 版、double 版……
template <class T>
const T& max_of(const T& a, const T& b) {
    return a < b ? b : a;
}

int main() {
    int i = 3, j = 5;

    std::cout << "macro  : " << MAX_MACRO(i++, j) << '\n';
    std::cout << "i now  : " << i << '\n';          // 注意 i 变成了多少

    std::cout << "voidp  : " << *(const int*)max_voidp(&i, &j, cmp_int) << '\n';
    std::cout << "tmpl   : " << max_of(i, j) << '\n';
    std::cout << "tmpl   : " << max_of(std::string("aa"), std::string("bb")) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra why_template.cpp -o wt && ./wt
```

```text
macro  : 5
i now  : 4
voidp  : 5
tmpl   : 5
tmpl   : bb
```

`MAX_MACRO(i++, j)` 展开成 `((i++) > (j) ? (i++) : (j))`：`i` 是 3、`j` 是 5，条件为假，走 `j` 分支，但第一个 `i++` 已经执行过了，于是 `i` 变成 4 而宏返回 5。这就是"实参被求值多次"的实际后果——它不总是错，只在被选中的分支里才错，所以极难发现。

`cmp_int` 用减法做比较是另一个经典问题：`INT_MIN - 1` 溢出（有符号溢出是 UB），结果不可信。正确写法是 `(x > y) - (x < y)`。而模板版只需要 `a < b`，既没有溢出也没有间接调用。

> **坑：** 别用 `*(const int*)a - *(const int*)b` 当三路比较，溢出是 UB。写 `(x > y) - (x < y)`，或者干脆用模板让编译器看到真实类型。
{: .sec-pit}

### 16.1.2 模板是什么：两层参数化
{: .sec-expl}

模板不是类型，也不是函数，它是一份**带洞的蓝图**。洞有两种：类型洞（`class T` / `typename T`）和值洞（非类型模板参数，见 16.2.4）。编译器在需要的时候拿实参把洞填上，生成一份真正的类型或函数——这个填洞的过程叫**实例化（instantiation）**。

关键在于"在需要的时候"：模板本身不产生任何代码，只有被实例化才产生。所以一个模板写错了一部分，只要那部分没被实例化，整个程序照样能编译过。这条规则贯穿全篇，是后面很多"看起来该报错却没报错"现象的根因。

`class T` 和 `typename T` 在这里完全等价，纯粹是历史遗留（Bjarne Stroustrup 最初用 `class`，后来为了不与"类"概念混淆加了 `typename`）。现代代码两种都有人写，`typename` 稍占多数。但 `typename` 在**另一个位置**有完全不同的含义——16.5.1 会讲。

### 16.1.3 实例化：代码确实被生成了两份
{: .sec-know}

隐式实例化是最常见的方式：编译器看到调用，推导出实参，生成对应版本。

```cpp
// instantiate.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

template <class T>
T twice(T v) { return v + v; }

int main() {
    std::cout << twice(21) << '\n';
    std::cout << twice(3.5) << '\n';
    std::cout << twice(std::string("ab")) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra instantiate.cpp -o inst && ./inst
nm -C ./inst | grep twice
```

```text
42
7
abab
000000000000116a W int twice<int>(int)
0000000000001190 W double twice<double>(double)
00000000000011c6 W std::__cxx11::basic_string<char, std::char_traits<char>, std::allocator<char> > twice<std::__cxx11::basic_string<char, std::char_traits<char>, std::allocator<char> > >(std::__cxx11::basic_string<char, std::char_traits<char>, std::allocator<char> >)
```

上面是 x86-64 Linux + GCC 12 未开优化时的典型输出（地址随编译环境变化）。三行符号，三个**互相独立**的函数体——这就是"编译期两份代码"的字面含义。`W` 表示弱符号（COMDAT），链接器会把多个目标文件里重复的同名实例化合并掉一份，所以跨翻译单元重复实例化不会造成链接错误，只会浪费编译时间。

实例化有三种触发方式：

1. **隐式实例化**：用到时自动触发。日常 99% 的情况。
2. **显式实例化定义**：`template T twice<T>(T);` 或 `template class Buffer<int>;`，强制在此处生成。
3. **显式实例化声明**：`extern template ...`，告诉编译器"别在这生成，别处有"。见 16.5.3。

> **注意：** 隐式实例化只实例化"被用到的那部分"。类模板的成员函数只有被调用才实例化（16.2.1），所以上面 `twice<std::string>` 只生成了构造函数相关的必要部分，别的不会凭空出现。
{: .sec-note}

### 16.1.4 递归实例化深度与 `-ftemplate-depth`
{: .sec-ts}

模板递归是元编程的基本手段，但每层递归都要消耗一次实例化深度。标准只给出"实现应支持至少 1024 层"的建议（Annex B），实际默认值各家不同：

| 编译器 | 开关 | 默认上限 |
| --- | --- | --- |
| GCC | `-ftemplate-depth=N` | 900 |
| Clang | `-ftemplate-depth=N` | 1024 |
| MSVC | 无同名开关 | 超限时报 C1202，具体层数随版本变化 |

```cpp
// depth.cpp —— 需要 -std=c++20
#include <iostream>

template <int N>
struct Count { static constexpr int value = 1 + Count<N - 1>::value; };

template <>
struct Count<0> { static constexpr int value = 0; };

int main() {
    std::cout << Count<1200>::value << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra depth.cpp -o depth && ./depth
```

```text
depth.cpp:4:44: error: template instantiation depth exceeds maximum of 900 (use '-ftemplate-depth=' to increase the maximum)
    4 | struct Count { static constexpr int value = 1 + Count<N - 1>::value; };
      |                                            ^
```

加 `-ftemplate-depth=1300` 就过去了：

```bash
g++ -std=c++20 -ftemplate-depth=1300 -Wall -Wextra depth.cpp -o depth && ./depth
```

```text
1200
```

调大这个数字不难，但先问一句：**真的需要 1200 层递归吗？** 绝大多数超深递归都可以换成循环式的 `constexpr` 函数（16.5.4），既快又不吃深度。深度不够往往说明算法选型有问题，而不是编译器小气。

### 16.1.5 零开销抽象到底零在哪
{: .sec-expl}

"零开销抽象"（zero-overhead abstraction）这句话被引用得多、解释得少。它有两层意思：

- **不为不用的东西付代价**：没被调用的成员函数不会被实例化，没被用到的模板不会产生代码。
- **用得上的东西，手写不会更好**：模板实例化后就是普通函数，内联后与手写的专用函数生成同样的指令。

对比运行期多态就很清楚：

| 维度 | 模板（编译期多态） | 虚函数 / `std::function`（运行期多态） |
| --- | --- | --- |
| 分发时机 | 编译期，直接调用或内联 | 运行期，查虚表或间接调用 |
| 二进制 | 每个类型一份代码 | 一份代码，多类型共享 |
| 能否内联 | 能 | 通常不能（除非去虚化成功） |
| 类型要求 | 只要语法满足即可（鸭子类型） | 必须继承同一基类 / 签名一致 |
| 编译依赖 | 定义必须可见（头文件） | 只需声明 |
| 错误信息 | 实例化时才报，很深 | 常规 |

所以模板的"零"是**运行期零间接**，代价被转移到了编译期：编译更慢、二进制可能更大、错误信息更难读。什么时候别用模板？当类型集合在编译期不确定（比如从配置文件读出来要选算法）、或者需要跨动态库边界稳定 ABI 时（16.5.6），运行期多态才是正解。

### 辨析：模板、重载、虚函数，什么时候用哪个
{: .sec-iv}

三者的本质区别是"什么时候决定调用谁"：

- **重载**：候选集在编译期由签名决定，全部手写。类型集合固定且很小（2~3 个）时用，最直观。
- **模板**：候选集由实例化生成，类型集合开放。算法与类型无关时用。
- **虚函数**：候选集在运行期由对象动态类型决定。类型集合开放但**必须在编译期未知**（比如插件、用户回调）时用。

一个判据：如果调用点的类型你全能列出来，用重载；列不出来但编译期已知，用模板；编译期都不知道，用虚函数。

## 16.2 类模板
{: .sec-expl}

### 16.2.1 定义与实例化：成员函数按需实例化
{: .sec-know}

```cpp
// lazy_inst.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <vector>

template <class T>
struct Box {
    T value{};

    void set(const T& v) { value = v; }

    // 用到 operator<，但只要没人调用就不会被实例化
    T bigger(const T& other) const { return value < other ? other : value; }

    // 这行对 int 完全无意义，但只要不调用就永远不会报错
    void nonsense() { value.this_member_does_not_exist(); }
};

int main() {
    Box<int> bi;
    bi.set(42);
    std::cout << "int box: " << bi.bigger(7) << '\n';

    Box<std::string> bs;
    bs.set("alpha");
    std::cout << "str box: " << bs.bigger("beta") << '\n';

    // Box<std::vector<int>> 也能用，只要不去调 bigger / nonsense
    Box<std::vector<int>> bv;
    std::cout << "vec box size: " << bv.value.size() << '\n';
    // bv.bigger({1,2});      // 一旦取消注释：vector 有 operator<，其实能过
    // bv.nonsense();         // 一旦取消注释：编译错误
}
```

```bash
g++ -std=c++20 -Wall -Wextra lazy_inst.cpp -o li && ./li
```

```text
int box: 42
str box: beta
vec box size: 0
```

`Box<std::vector<int>>` 里有个 `nonsense()` 成员函数，函数体对 `vector<int>` 完全非法，但程序编译通过了——因为它没被调用，编译器连看都不看它的函数体（除了语法解析和**非依赖名**查找，16.5.2）。

这条规则有两面。好的一面：一个类模板可以对所有类型"部分可用"，比如 `std::vector<T>` 的 `push_back` 要求 `T` 可拷贝构造，但如果你只 `reserve` 不 `push_back`，不可拷贝的类型也能塞进去。坏的一面：错误被推迟到了调用点，有时候要翻十几层栈才能找到真正的问题。

### 16.2.2 成员函数模板与嵌套
{: .sec-know}

类模板里可以再放模板，两层参数各管各的：

```cpp
// member_template.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <utility>

template <class T>
struct Holder {
    T value{};

    // 成员函数模板：U 与类的 T 无关
    template <class U>
    void assign(U&& u) { value = std::forward<U>(u); }

    // 转换到别的类型
    template <class U>
    U as() const { return static_cast<U>(value); }
};

int main() {
    Holder<std::string> h;
    h.assign("hello");                 // U = const char(&)[6]
    h.assign(std::string(" world"));   // U = std::string（右值，走移动赋值）
    std::cout << h.value << '\n';

    Holder<int> n;
    n.assign(3);
    std::cout << n.as<double>() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra member_template.cpp -o mt && ./mt
```

```text
hello world
3
```

注意 `h.assign("hello")` 里 `U` 被推导成 `const char (&)[6]`（数组的引用，因为形参是 `U&&` 万能引用，不退化）。这个特性后面 16.3.2 会系统讲。

成员函数模板**不能是虚函数**——这条限制很硬：虚函数要求运行期分发的候选集固定（虚表大小编译期确定），而模板的候选集是无限的。想"虚的模板"通常得靠类型擦除（`std::any` + 手动分发表）或者访问者模式。

### 16.2.3 默认模板实参
{: .sec-know}

和函数默认实参一样，类模板的模板参数可以有默认值，从右往左连续：

```cpp
// default_args.cpp —— 需要 -std=c++20
#include <cstddef>
#include <iostream>
#include <vector>

template <class T = int, class Cont = std::vector<T>, std::size_t Hint = 16>
struct Ring {
    Cont data{};
    std::size_t hint = Hint;
    void push(const T& v) { data.push_back(v); }
    std::size_t size() const { return data.size(); }
};

int main() {
    Ring<> a;                                    // T=int, Cont=vector<int>, Hint=16
    Ring<double> b;                              // T=double
    Ring<double, std::vector<double>, 64> c;     // 全显式
    a.push(1);
    std::cout << a.size() << ' ' << a.hint << '\n';
    std::cout << b.hint << ' ' << c.hint << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra default_args.cpp -o da && ./da
```

```text
1 16
16 64
```

两个细节：

- **函数模板**从 C++11 起也支持默认模板实参（C++98 只允许类模板有）。
- 后面的参数可以使用前面的参数做默认值（`Cont = std::vector<T>` 用了 `T`），这是合法且常用的。

### 16.2.4 非类型模板参数（NTTP）与三代演进
{: .sec-know}

非类型模板参数让"值"也能进模板。它的发展分了三代，写老代码时很容易撞上限制：

| 版本 | 允许的 NTTP 类型 |
| --- | --- |
| C++98 | 整型（含 bool、char、枚举）、指针、引用、`std::nullptr_t`(C++11) |
| C++17 | 上面这些 + `auto` 自动推导（`template <auto V>`） |
| C++20 | 上面这些 + 浮点 + 字面量类类型（structural type） |

```cpp
// nttp.cpp —— 需要 -std=c++20（浮点与类类型 NTTP 是 C++20 才有的）
#include <iostream>
#include <string_view>

// C++98 就支持：整型 NTTP
template <int N>
struct Fixed { static constexpr int value = N; };

// C++17：auto 推导，不用手写类型
template <auto V>
struct Constant {
    static constexpr auto value = V;
    static constexpr auto kind = sizeof(V);
};

// C++20：浮点 NTTP
template <double Factor>
double scale(double x) { return x * Factor; }

// C++20：字面量类类型 NTTP（所有基类与非静态数据成员都是 public 且非 mutable）
struct Point { int x{}; int y{}; };

template <Point P>
struct Cell {
    static constexpr int x = P.x;
    static constexpr int y = P.y;
};

int main() {
    std::cout << Fixed<7>::value << '\n';
    std::cout << Constant<42>::value << ' ' << Constant<'A'>::value << '\n';
    std::cout << scale<2.5>(4.0) << '\n';
    std::cout << Cell<Point{3, 4}>::x << ',' << Cell<Point{3, 4}>::y << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra nttp.cpp -o nttp && ./nttp
```

```text
7
42 A
10
3,4
```

`template <auto V>` 让"传什么都行"，配合 `sizeof(V)` 或 `decltype(V)` 就能做类型分支，写反射式的代码很省事。

> **坑：** 浮点 NTTP 的相等判定是**按值**比较，`Scale<0.1>` 与 `Scale<0.10000000000000001>` 是不是同一个类型取决于实现的浮点表示。别用浮点 NTTP 做需要跨平台稳定 ABI 的事。类类型 NTTP 要求所有成员 public 且非 `mutable`，加一个 private 成员立刻编译不过。
{: .sec-pit}

### 16.2.5 变量模板（C++14）
{: .sec-know}

变量模板把"参数化"推广到变量。标准库里那一堆 `xxx_v<T>` 就是它的产物（`std::is_same_v` 等，C++17 加入）。

```cpp
// var_template.cpp —— 需要 -std=c++20（变量模板本身是 C++14）
#include <cmath>
#include <iomanip>
#include <iostream>
#include <string>
#include <type_traits>

template <class T>
constexpr T pi = T(3.14159265358979323846L);

// 全特化：给特定类型一个不同实现
template <>
constexpr const char* pi<const char*> = "3.14159";

// 主模板 + 全特化，做类型性质的判断
template <class T>
constexpr bool is_string_like = false;
template <>
constexpr bool is_string_like<std::string> = true;
template <>
constexpr bool is_string_like<const char*> = true;

int main() {
    std::cout << std::boolalpha;
    std::cout << "pi<int>    = " << pi<int> << '\n';               // 3
    std::cout << std::fixed << std::setprecision(10)
              << "pi<double> = " << pi<double> << '\n';
    std::cout << "pi<cstr>   = " << pi<const char*> << '\n';
    std::cout << is_string_like<std::string> << ' '
              << is_string_like<int> << ' '
              << is_string_like<const char*> << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra var_template.cpp -o vt && ./vt
```

```text
pi<int>    = 3
pi<double> = 3.1415926536
pi<cstr>   = 3.14159
true false true
```

`pi<int>` 是 3，因为 `T(3.14159...)` 对 `int` 是截断转换——这是变量模板最常见的用法陷阱：看起来是"常量"，实际上做了隐式转换。需要精确值就用 `pi<double>` 或 `pi<long double>`。

### 16.2.6 偏特化与全特化
{: .sec-know}

**全特化**：所有模板参数都给定，不再有模板参数。`template <> struct IsPtr<char*> {...}`。
**偏特化**：部分参数给定，或者对参数施加模式约束。只有类模板和变量模板能做。

```cpp
// specialization.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <type_traits>
#include <vector>

// 主模板
template <class T>
struct Traits { static constexpr const char* name = "unknown"; };

// 全特化：一个具体类型
template <>
struct Traits<int> { static constexpr const char* name = "int"; };

template <>
struct Traits<std::string> { static constexpr const char* name = "std::string"; };

// 偏特化：所有指针
template <class U>
struct Traits<U*> { static constexpr const char* name = "pointer"; };

// 偏特化：所有 vector
template <class U, class A>
struct Traits<std::vector<U, A>> { static constexpr const char* name = "vector"; };

// 偏特化：const 修饰
template <class U>
struct Traits<const U> { static constexpr const char* name = "const"; };

int main() {
    std::cout << Traits<double>::name << '\n';
    std::cout << Traits<int>::name << '\n';
    std::cout << Traits<std::string>::name << '\n';
    std::cout << Traits<int*>::name << '\n';
    std::cout << Traits<const int*>::name << '\n';    // int const* → U = const int
    std::cout << Traits<std::vector<int>>::name << '\n';
    std::cout << Traits<const double>::name << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra specialization.cpp -o sp && ./sp
```

```text
unknown
int
std::string
pointer
pointer
vector
const
```

`Traits<const int*>` 落到 `U*` 那一条（`U = const int`），因为指针偏特化比主模板更特化；它没有落到 `const U`，因为 `const int*` 的顶层不是 const（`const` 修饰的是 `int`，不是指针）。指针/引用/const 的组合在偏特化匹配里是高频出错点，写之前先在脑内画一遍类型。

### 16.2.7 特化的 ODR 陷阱：必须在首次使用之前
{: .sec-pit}

给一个已被隐式实例化的模板补特化，是**非法的**（ill-formed，无需诊断）。标准这么定是因为链接器会看到两份冲突的定义——一份是隐式实例化出来的，一份是你后来写的特化，两者符号相同。

```cpp
// odr_trap.cpp —— 这段代码有问题，故意演示
#include <iostream>
#include <vector>

template <class T>
struct Formatter {
    static void print() { std::cout << "generic\n"; }
};

int main() {
    Formatter<int>::print();   // ← 这里已经隐式实例化了主模板版本
}

// 太晚了：Formatter<int> 在上面已经被实例化过
template <>
struct Formatter<int> {
    static void print() { std::cout << "specialized for int\n"; }
};
```

GCC 会直接拒绝：

```text
odr_trap.cpp:19:10: error: specialization of 'Formatter<int>' after instantiation
```

实际工程里这个过程不会这么明显：特化通常写在另一个头文件里，而"首次使用"发生在某个 `.cpp` 中间的某行，include 顺序一变行为就变——最恶心的情况是恰好不报错，然后运行期行为随编译单元不同而不同。

规避方式很机械但有效：**所有特化集中放在声明主模板的同一个头文件里，紧跟主模板之后**，别散落到别处。

### 16.2.8 CTAD 与推导指引（C++17）
{: .sec-ext}

CTAD（Class Template Argument Deduction）让构造函数的实参反推类模板参数，省掉 `std::vector<int> v(v2.begin(), v2.end())` 里的 `<int>`。

```cpp
// ctad.cpp —— 需要 -std=c++17（本例按 -std=c++20 编译）
#include <initializer_list>
#include <iostream>
#include <iterator>
#include <string>
#include <vector>

template <class T>
struct Stack {
    std::vector<T> data;

    Stack() = default;
    Stack(std::initializer_list<T> il) : data(il) {}
    template <class It>
    Stack(It first, It last) : data(first, last) {}
};

// 推导指引：把迭代器对映射到元素类型（编译器自己推不出 T）
template <class It>
Stack(It, It) -> Stack<typename std::iterator_traits<It>::value_type>;

int main() {
    Stack s1{1, 2, 3};                 // 从 initializer_list 推 → Stack<int>
    std::vector<std::string> v{"a", "b"};
    Stack s2(v.begin(), v.end());      // 靠推导指引 → Stack<std::string>

    std::cout << s1.data.size() << ' ' << s1.data[0] << '\n';
    std::cout << s2.data.size() << ' ' << s2.data[0] << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra ctad.cpp -o ctad && ./ctad
```

```text
3 1
2 a
```

三条经验：

1. **大多数情况不需要写推导指引**。编译器能从构造函数签名隐式推导（`Stack(std::initializer_list<T>)` 就能推出 `T`）。只有"构造函数参数里没出现类模板参数"（比如迭代器对）时才需要手写。
2. 推导指引是**普通的函数式声明**，不写函数体，语法是 `模板参数 -> 类模板特化`。
3. `Stack s{1,2,3}` 用花括号。用圆括号 `Stack s(3)` 在有 `initializer_list` 构造函数时会走另一条路，容易踩坑——容器初始化统一用花括号是更省心的习惯。

### 辨析：类模板偏特化 vs 函数模板重载
{: .sec-iv}

函数模板**不能偏特化**，这是标准明确禁止的：

```cpp
// 编译不过：函数模板不允许偏特化
template <class T> void f(T);
template <class T> void f<T*>(T*);   // error: function template partial specialization
```

想达到同样效果，只能**重载**。看下面这个例子，第三行看起来像偏特化，其实是重载：

```cpp
// overload_not_partial.cpp —— 需要 -std=c++20
#include <iostream>
#include <typeinfo>

template <class T>
void f(T) { std::cout << "primary\n"; }

// 这是重载（独立的主模板），不是偏特化
template <class T>
void f(T*) { std::cout << "pointer overload\n"; }

// 这才是全特化，针对具体类型
template <>
void f(int*) { std::cout << "int* specialization\n"; }

int main() {
    int x = 0;
    f(x);                    // primary
    f(&x);                   // int* specialization（全特化比主模板更特化）
    double d = 0;
    f(&d);                   // pointer overload
    f(3.14);                 // primary
}
```

```bash
g++ -std=c++20 -Wall -Wextra overload_not_partial.cpp -o onp && ./onp
```

```text
primary
int* specialization
pointer overload
primary
```

为什么这么设计？因为函数已经有重载决议这套机制了，再加偏特化会出现"重载 vs 偏特化谁优先"的歧义地狱；类没有重载，所以给了偏特化。一句话记：**类是特化体系，函数是重载体系**。

## 16.3 函数模板
{: .sec-expl}

### 16.3.1 定义与调用
{: .sec-know}

```cpp
template <class T>
T max_of(const T& a, const T& b) { return a < b ? b : a; }
```

调用时三种写法：

- `max_of(1, 2)` —— 推导（最常用）
- `max_of<int>(1, 2)` —— 显式指定
- `max_of<int>(1, 2.0)` —— 显式指定后不再推导，`2.0` 走隐式转换

形参用 `const T&` 而不是 `T`，是函数模板的默认选择：避免拷贝、能接右值、还不阻止推导。`T&&` 是另一种选择（万能引用），但要配合 `std::forward` 才有意义，见 16.3.9。

### 16.3.2 模板实参推导：五种形参形态
{: .sec-know}

推导规则可以浓缩成一句话：**先按形参形态调整实参类型，再匹配**。五种形态的行为差异是模板最常考也最容易记混的地方：

| 形参形态 | 数组实参 | 函数实参 | 顶层 const | 能否接右值 |
| --- | --- | --- | --- | --- |
| `T`（按值） | 退化成指针 | 退化成函数指针 | 丢掉 | 能 |
| `T&` | **不**退化，保留数组类型 | **不**退化 | 保留，进 `T` | 不能接右值 |
| `const T&` | **不**退化 | **不**退化 | 保留，但 `const` 留在形参上 | 能 |
| `T&&`（万能引用） | **不**退化 | **不**退化 | 保留 | 能，且区分左右值 |
| 显式指定 | 不再推导 | 不再推导 | 按指定类型走 | 视指定类型 |

```cpp
// deduce.cpp —— 需要 -std=c++20
#include <iostream>
#include <string_view>
#include <type_traits>
#include <utility>

template <class T>
constexpr std::string_view tname() {
    if constexpr (std::is_same_v<T, int>)           return "int";
    else if constexpr (std::is_same_v<T, const int>) return "const int";
    else if constexpr (std::is_same_v<T, int*>)      return "int*";
    else if constexpr (std::is_same_v<T, int&>)      return "int&";
    else if constexpr (std::is_same_v<T, const int&>)return "const int&";
    else if constexpr (std::is_same_v<T, int[3]>)    return "int[3]";
    else if constexpr (std::is_same_v<T, void (*)()>)return "void(*)()";
    else if constexpr (std::is_same_v<T, void()>)    return "void()";
    else                                             return "(other)";
}

template <class T> void f_val(T)    { std::cout << "  f_val  : T = " << tname<T>() << '\n'; }
template <class T> void f_ref(T&)   { std::cout << "  f_ref  : T = " << tname<T>() << '\n'; }
template <class T> void f_cref(const T&) { std::cout << "  f_cref : T = " << tname<T>() << '\n'; }
template <class T> void f_fwd(T&&)  { std::cout << "  f_fwd  : T = " << tname<T>() << '\n'; }

void hello() {}

int main() {
    int x = 1;
    const int ci = 7;
    const int& cr = x;
    int arr[3] = {1, 2, 3};

    std::cout << "按值 T：\n";
    f_val(x);        f_val(ci);      f_val(cr);      f_val(arr);     f_val(hello);

    std::cout << "左值引用 T&：\n";
    f_ref(x);        f_ref(ci);      f_ref(arr);     f_ref(hello);

    std::cout << "常量引用 const T&：\n";
    f_cref(x);       f_cref(ci);

    std::cout << "万能引用 T&&：\n";
    f_fwd(x);        f_fwd(ci);      f_fwd(42);      f_fwd(std::move(x));
}
```

```bash
g++ -std=c++20 -Wall -Wextra deduce.cpp -o deduce && ./deduce
```

```text
按值 T：
  f_val  : T = int
  f_val  : T = int
  f_val  : T = int
  f_val  : T = int*
  f_val  : T = void(*)()
左值引用 T&：
  f_ref  : T = int
  f_ref  : T = const int
  f_ref  : T = int[3]
  f_ref  : T = void()
常量引用 const T&：
  f_cref : T = int
  f_cref : T = const int
万能引用 T&&：
  f_fwd  : T = int&
  f_fwd  : T = const int&
  f_fwd  : T = int
  f_fwd  : T = int
```

四点要记住：

1. **按值形参丢掉引用和顶层 const**。`f_val(ci)` 得到 `int` 而不是 `const int`——因为副本的 const 没有意义。
2. **引用形参保留 const，且 const 落进 `T`**。`f_ref(ci)` 得到 `T = const int`。
3. **`const T&` 的 const 在形参上，`T` 是干净的**。所以 `f_cref(ci)` 的 `T = int`（形参整体是 `const int&`）。
4. **`T&&` 只在 `T` 本次被推导时才是万能引用**。左值实参推出 `T = int&`，右值推出 `T = int`。这是完美转发的全部秘密。

`f_val(arr)` 退化成 `int*` 这件事，直接后果是**数组长度信息在按值传递时丢失**。想保留长度，用引用形参 `T&`（推成 `int[3]`），然后在函数里用 `sizeof(T)/sizeof(T[0])`。

### 16.3.3 数组与函数退化，及怎么阻止退化
{: .sec-ts}

按值传递时数组退化成指针、函数退化成函数指针，这是从 C 继承来的规则。C++ 里想保留数组类型有两种写法：

```cpp
// no_decay.cpp —— 需要 -std=c++20
#include <cstddef>
#include <iostream>

// 写法一：引用形参，T 被推成 int[N]
template <class T, std::size_t N>
constexpr std::size_t len(const T (&)[N]) { return N; }

// 写法二：std::extent（type traits 路线）
#include <type_traits>
template <class T>
constexpr std::size_t extent_of = std::extent_v<T>;

int main() {
    int a[10]      = {};
    double b[3]    = {};
    const char c[] = "hi";     // 长度 3（含结尾的 '\0'）

    std::cout << len(a) << ' ' << len(b) << ' ' << len(c) << '\n';
    std::cout << extent_of<int[10]> << ' ' << extent_of<double[3]> << '\n';
    std::cout << extent_of<int*> << '\n';    // 退化后就是 0
}
```

```bash
g++ -std=c++20 -Wall -Wextra no_decay.cpp -o nd && ./nd
```

```text
10 3 3
10 3
0
```

`std::extent_v<T>` 对已经退化的指针返回 0，所以它常被用来做"这是数组还是指针"的检测。C++17 之后，遍历只读序列更推荐直接传 `std::span`（C++20）或 `std::string_view`，它们自己带长度。

### 16.3.4 非推导语境与 `std::type_identity_t`（C++20）
{: .sec-know}

有些位置的类型不参与推导，叫**非推导语境（non-deduced context）**。最典型的是 `T::type` 这种嵌套名——编译器没法从它反推 `T`。

C++20 加了 `std::type_identity_t<T>`，专门用来"人为制造非推导语境"：

```cpp
// type_identity.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

// 两个参数都参与推导：类型不一致就冲突
template <class T>
void two_deduced(T a, T b) { std::cout << "both T = " << a << ',' << b << '\n'; }

// 第二个参数被 type_identity_t 包住 → 非推导语境，只看第一个参数
template <class T>
void one_deduced(T a, std::type_identity_t<T> b) {
    std::cout << "T from first = " << a << " second = " << b << '\n';
}

int main() {
    two_deduced(1, 2);          // 都是 int，OK
    // two_deduced(1, 2.0);     // 推导冲突：int vs double → 编译错误
    one_deduced(1, 2.0);        // T = int，2.0 转 int → 2
}
```

```bash
g++ -std=c++20 -Wall -Wextra type_identity.cpp -o ti && ./ti
```

```text
both T = 1,2
T from first = 1 second = 2
```

在 C++20 之前，同样的效果要靠一个自己写的 `identity<T>::type`，或者把第二个参数写成嵌套名。这个惯用法的实际用途是**锁死推导来源**：你希望某个参数只做"可转换检查"而不影响 `T` 时就用它。

其他常见非推导语境：

- `typename T::type` 这类依赖嵌套名；
- 出现在默认模板实参里的类型；
- 已被显式指定的参数（后面的参数若还能推导则继续推导，否则用默认值）。

### 16.3.5 显式指定实参
{: .sec-know}

显式指定在三种场合是必需的：

1. **推导不出来**（返回值类型不参与推导）：`accumulate<long long>(v.begin(), v.end(), 0)`。
2. **想强制某个类型**：`max_of<double>(1, 2)` 让 `int` 实参转成 `double`。
3. **调用没有参数的模板**：`make_thing<int>()`。

```cpp
// explicit_args.cpp —— 需要 -std=c++20
#include <iostream>
#include <numeric>
#include <vector>

template <class R, class T>
R sum_as(const std::vector<T>& v) {
    R acc{};
    for (const T& e : v) acc += e;
    return acc;
}

template <class T>
T make_default() { return T{}; }

int main() {
    std::vector<short> v{30000, 30000, 30000};

    auto bad = sum_as<short>(v);      // short 溢出
    auto ok  = sum_as<long long>(v);  // 正确
    std::cout << "short: " << bad << '\n';
    std::cout << "ll   : " << ok << '\n';

    std::cout << make_default<double>() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra explicit_args.cpp -o ea && ./ea
```

```text
short: 24464
ll   : 90000
0
```

`short` 版输出 24464 而不是 90000：`30000*3 = 90000` 装不进 `short`，每次 `acc += e` 的加法在 `int` 里做完再截回 `short`（这不是 UB，是实现定义的窄化转换，90000 的低 16 位就是 24464）。这个例子说明显式指定返回类型不只是"让编译过"，它决定了运算在哪个类型上做。

顺带一提：`std::accumulate(v.begin(), v.end(), 0LL)` 是标准库里同样的思路——用初值决定累加类型。

### 16.3.6 重载决议：偏序与"更特化"
{: .sec-know}

多个函数模板都能匹配时，编译器做**偏序（partial ordering）**：谁更特化选谁。规则大致是"能匹配 A 的实参集合是能匹配 B 的子集，则 A 更特化"。

```cpp
// partial_order.cpp —— 需要 -std=c++20
#include <iostream>

template <class T>        void g(T)   { std::cout << "g(T)\n"; }
template <class T>        void g(T*)  { std::cout << "g(T*)\n"; }
template <>               void g(int*){ std::cout << "g(int*) 全特化\n"; }

template <class T>        void h(T)        { std::cout << "h(T)\n"; }
template <class T, class U> void h(T)      { std::cout << "h(T,U)\n"; }  // 永远不会被选中

int main() {
    int x = 0;
    double d = 0;
    g(x);      // g(T)
    g(&x);     // g(int*) 全特化
    g(&d);     // g(T*)
    h(1);      // h(T)：单参数版更特化
}
```

```bash
g++ -std=c++20 -Wall -Wextra partial_order.cpp -o po && ./po
```

```text
g(T)
g(int*) 全特化
g(T*)
h(T)
```

`h(T,U)` 那一条永远选不中——`U` 无法推导也没有默认值，它其实是个坏例子（能声明但没法用，除非显式指定 `h<int,char>(1)`）。写重载时务必确认每个模板参数都能推导或都有默认值，否则那条重载就是死代码。

### 16.3.7 SFINAE：原理与两个惯用法
{: .sec-know}

SFINAE 是 **Substitution Failure Is Not An Error**（替换失败不是错误）的缩写：在模板实参替换（substitution）过程中，如果产生了**无效类型或无效表达式**，这条候选被静默地从候选集里移除，而不是报编译错误。注意边界——只有**立即语境**（immediate context）里的失败才是 SFINAE，函数体内部的失败是硬错误。

惯用法一：`std::enable_if` 做条件启用。

```cpp
// sfinae_enable_if.cpp —— 需要 -std=c++20（enable_if 本身是 C++11）
#include <iostream>
#include <string>
#include <type_traits>

// 只有整型实参时这个重载才存在
template <class T, std::enable_if_t<std::is_integral_v<T>, int> = 0>
std::string describe(T v) { return "int: " + std::to_string(v); }

// 只有浮点实参时存在
template <class T, std::enable_if_t<std::is_floating_point_v<T>, int> = 0>
std::string describe(T v) { return "float: " + std::to_string(v); }

// 能转成 std::string 时存在
template <class T, std::enable_if_t<std::is_convertible_v<T, std::string>, int> = 0>
std::string describe(T v) { return "str: " + std::string(v); }

int main() {
    std::cout << describe(42) << '\n';
    std::cout << describe(3.5) << '\n';
    std::cout << describe("hello") << '\n';
    // describe(std::vector<int>{});   // 三个重载全被 SFINAE 剔掉 → no matching function
}
```

```bash
g++ -std=c++20 -Wall -Wextra sfinae_enable_if.cpp -o se && ./se
```

```text
int: 42
float: 3.5
str: hello
```

`std::enable_if_t<条件, int> = 0` 这个写法要拆开看：它是一个非类型模板参数，`int` 类型、默认值 0。条件为真时 `enable_if_t` 就是 `int`，参数合法；条件为假时 `enable_if_t` 不存在（无 `type` 成员），替换失败 → 该候选消失。它比"写在返回类型上"更好，因为不污染签名。

惯用法二：`void_t` 检测成员是否存在。

```cpp
// sfinae_void_t.cpp —— 需要 -std=c++20（void_t 是 C++17）
#include <iostream>
#include <set>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

// 主模板：默认没有 push_back
template <class T, class = void>
struct has_push_back : std::false_type {};

// 偏特化：只有当 decltype(...) 合法时才匹配上
template <class T>
struct has_push_back<T, std::void_t<decltype(
        std::declval<T&>().push_back(std::declval<typename T::value_type>()))>>
    : std::true_type {};

int main() {
    std::cout << std::boolalpha;
    std::cout << "vector<int>   : " << has_push_back<std::vector<int>>::value << '\n';
    std::cout << "std::string   : " << has_push_back<std::string>::value << '\n';
    std::cout << "set<int>      : " << has_push_back<std::set<int>>::value << '\n';
    std::cout << "int           : " << has_push_back<int>::value << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra sfinae_void_t.cpp -o sv && ./sv
```

```text
vector<int>   : true
std::string   : true
set<int>      : false
int           : false
```

原理：偏特化的第二个实参是 `void`（由 `std::void_t<...>` 得到）。如果 `decltype(...)` 里的表达式非法，替换失败，偏特化不匹配，落回主模板 → `false`。`std::declval<T&>()` 是"在不构造对象的前提下拿到一个 `T&`"的标准手段，只能在**不被求值**的语境（`decltype`、`sizeof`）里用。

### 16.3.8 SFINAE 的代价
{: .sec-pit}

SFINAE 能干活，但三个代价让人很难受：

1. **错误信息爆炸**。约束不满足时，编译器报的是"没有匹配的函数"，然后把十几条被剔掉的候选全打出来，每条还带着展开后的 `enable_if_t<...>`。几百行是常态。
2. **编译速度**。每条候选都要做一次模板实参替换与实例化，约束写多了编译时间线性上涨。
3. **可读性**。`std::enable_if_t<std::is_integral_v<T>, int> = 0` 这句话的**意图**是"T 必须是整型"，但字面在说"如果 T 是整型，就给我一个默认的 int 非类型参数"。意图被实现细节埋了。

还有个隐蔽的问题：SFINAE 的约束写在类型系统里，一旦条件写错（比如漏了 `std::remove_reference_t`），往往是"静默地不匹配"，然后报一堆不知所云的错。

C++20 的 Concepts 就是冲着这三点来的，见 16.4.7。

### 16.3.9 完美转发与引用折叠
{: .sec-know}

想写一个"透传"函数，把实参原封不动交给下游——左值还是左值，右值还是右值，const 不丢。这需要三样东西配合：`T&&` 万能引用 + 引用折叠 + `std::forward`。

引用折叠规则（C++11）只有四条：

| 组合 | 折叠结果 |
| --- | --- |
| `T& &` | `T&` |
| `T& &&` | `T&` |
| `T&& &` | `T&` |
| `T&& &&` | `T&&` |

一句话：**只要有一个 `&`，结果就是 `&`**。这就是左值实参让 `T` 推成 `int&`，从而 `T&&` 折叠成 `int&` 的机制。

```cpp
// forward_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <utility>

struct Tracker {
    Tracker() = default;
    Tracker(const Tracker&) { std::cout << "  copy\n"; }
    Tracker(Tracker&&) noexcept { std::cout << "  move\n"; }
};

void sink(Tracker) {}

// 版本一：转发引用 + std::forward —— 保持值类别
template <class T>
void good(T&& t) { sink(std::forward<T>(t)); }

// 版本二：写死 T&& —— 只能接右值，左值传不进来
template <class T>
void bad(T&& t) { sink(std::move(t)); }   // 名字叫 bad 是因为它无条件 move

int main() {
    Tracker t;
    std::cout << "good(左值):\n";  good(t);
    std::cout << "good(右值):\n";  good(Tracker{});
    std::cout << "good(move):\n";  good(std::move(t));
    std::cout << "bad(左值)  :\n"; bad(std::move(t));
    // bad(t);   // 能编译：bad 的 T 也被推导，但它会把左值 t 无条件掏空，见下方说明
}
```

```bash
g++ -std=c++20 -Wall -Wextra forward_demo.cpp -o fd && ./fd
```

```text
good(左值):
  copy
good(右值):
  move
good(move):
  move
bad(左值):
  move
```

`good(t)` 走 copy、`good(Tracker{})` 走 move、`good(std::move(t))` 走 move——值类别被完整保留。

关于 `bad(t)` 的注释要澄清：`bad` 的形参也是 `T&&` 且 `T` 被推导，所以**它也是万能引用**，`bad(t)` 是能编译的（只是会无条件 move 左值，把 `t` 掏空）。真正"只能接右值"的写法是形参里 `T` 不被推导，比如 `void f(std::vector<int>&& v)`，或者 `template <class T> void f(std::vector<T>&& v)`。这条区别是模板最经典的误判点，值得单独记。

> **坑：** `std::forward<T>(x)` 里漏写 `<T>` 是编译错误（不是警告）。`std::forward` 的模板参数出现在非推导语境里，故意让你必须写——因为它要做的是"有条件转换"，条件就是 `T`。看到 `std::forward(x)` 报错，回去补 `<T>`，别改成 `std::move` 糊弄过去。
{: .sec-pit}

### 辨析：`std::move` 与 `std::forward`
{: .sec-iv}

| 维度 | `std::move(x)` | `std::forward<T>(x)` |
| --- | --- | --- |
| 是否需要显式模板实参 | 不需要 | 必须写 `<T>` |
| 语义 | 无条件转成右值 | 有条件：`T` 是左值引用就保持左值，否则转右值 |
| 典型场景 | 明确要搬走这个对象 | 转发引用里透传 |
| 用错的后果 | 提前掏空还在用的对象 | 左值被意外搬走（写成 `std::move`），或该搬的没搬 |

判断标准很简单：这个参数**是不是转发引用**（`T&&` 且 `T` 本次被推导）。是 → `std::forward<T>`；不是 → 要么不转换，要么明确 `std::move`。

## 16.4 模板组合
{: .sec-expl}

单个模板只能算零件，泛型库是模板与模板的组合：容器模板嵌套容器模板、把模板本身当实参传给另一个模板、用策略类在编译期换实现、用 CRTP 在编译期做"虚函数"、用类型擦除把五花八门的可调用对象收进一个盒子。这一节把这几套组合拳各打一遍，末尾用折叠表达式和 `if constexpr` 把黏合剂补齐。

### 16.4.1 模板套模板：`vector<vector<int>>` 与 `>>` 的历史
{: .sec-know}

二维容器、`map<string, vector<pair<int, int>>>` 这类嵌套写法如今信手拈来，但在 C++03 时代编译不过。原因是词法分析用的"最大 munch"规则：`>>` 永远先被当成一个整体（右移运算符），解析器轮不到模板语法就把它切走了，所以闭括号必须写成 `> >`。C++11 修改了词法规则：在模板语境下，`>>` 会被拆成两个闭括号；只有在非模板语境（比如普通表达式）里它还是右移。

```cpp
// nested.cpp —— 需要 -std=c++20
#include <iostream>
#include <map>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::vector<std::vector<int>> grid(3, std::vector<int>(4));   // C++11 起不用写 "> >"
    grid[1][2] = 7;

    std::map<std::string, std::vector<std::pair<int, int>>> pos;  // 三层嵌套也随意
    pos["alice"].emplace_back(1, 2);

    for (const auto& row : grid) {
        for (int v : row) std::cout << v << ' ';
        std::cout << '\n';
    }
    std::cout << pos["alice"].size() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra nested.cpp -o ne && ./ne
```

```text
0 0 0 0 
0 0 7 0 
0 0 0 0 
1
```

> **坑：** `>>` 的拆分只发生在模板实参列表的语境里。写 `a < b >> c` 时 `>>` 依旧是右移，`(a < b) > c` 才是你想要的比较链——这条坑在表达式模板库里真实存在过。另外嵌套超过两层时建议起别名：`using Grid = std::vector<std::vector<int>>;`，报错信息里的类型名能短一半。
{: .sec-pit}

### 16.4.2 模板模板参数：把"容器模板"当实参传
{: .sec-know}

有时要传的不是某个具体类型，而是一个还没填实参的模板——"随便什么容器，元素类型我来填"。这就是模板模板参数（template template parameter）：

```cpp
// ttp.cpp —— 需要 -std=c++20
#include <deque>
#include <iostream>
#include <list>
#include <vector>

template <class T, template <class...> class Container>   // 变参形参：C++11 起的通行写法
class Stack {
    Container<T> data;
public:
    void push(const T& v) { data.push_back(v); }
    void pop() { data.pop_back(); }
    T top() const { return data.back(); }
    bool empty() const { return data.empty(); }
};

int main() {
    Stack<int, std::vector> s1;    // 传模板本身，不是 std::vector<int>
    Stack<int, std::deque> s2;
    // Stack<int, std::set> s3;    // 编译错误：set 没有 push_back
    s1.push(1); s1.push(2);
    while (!s1.empty()) { std::cout << s1.top() << ' '; s1.pop(); }
}
```

```bash
g++ -std=c++20 -Wall -Wextra ttp.cpp -o ttp && ./ttp
```

```text
2 1 
```

历史包袱在形参的匹配规则上。C++17 之前要求逐参数精确匹配：`std::vector` 有两个模板参数（第二个是带默认值的 `Allocator`），对不上只有一个参数的形参 `template <class U> class C`。所以当年的通行写法是把形参声明成变参 `template <class...> class C`——变参总能匹配。C++17 通过 P0522R0 放宽了规则：实参模板只要"至少与形参模板一样特化"即可，`template <class U> class C` 现在能直接接 `std::vector`。GCC 和 MSVC 默认放行，Clang 至今默认关闭（要加 `-frelaxed-template-template-args`）——跨编译器的库别依赖放宽规则，写成变参形式最稳。

### 16.4.3 策略类：在编译期换实现
{: .sec-know}

策略类（policy-based design）把"可变的那部分行为"做成模板参数：比较器、分配器、Hash、线程模型，全是标准库在用的策略——`std::set<Key, Compare, Alloc>` 的后两个模板参数就是策略位。策略在编译期注入，调用被内联，零运行期开销；代价是每种策略组合都是一个新类型。

```cpp
// policy.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <memory>
#include <vector>

// 策略一：排序方向
struct GtCompare {
    template <class T>
    bool operator()(const T& a, const T& b) const { return b < a; }
};

// 策略二：分配器（在标准分配器外面加一层计数，让"策略换了"变得可观察）
template <class T>
struct CountingAlloc {
    using value_type = T;
    CountingAlloc() = default;
    template <class U> CountingAlloc(const CountingAlloc<U>&) noexcept {}
    T* allocate(std::size_t n) {
        ++alloc_count;
        std::cout << "alloc " << n << " x " << sizeof(T) << " bytes\n";
        return std::allocator<T>{}.allocate(n);
    }
    void deallocate(T* p, std::size_t n) noexcept { std::allocator<T>{}.deallocate(p, n); }
    template <class U> bool operator==(const CountingAlloc<U>&) const { return true; }
    inline static int alloc_count = 0;    // 内联静态变量：C++17
};

// 策略三：默认参数。三个模板位各司其职：元素类型、排序策略、分配策略
template <class T, class Compare = std::less<T>, class Alloc = std::allocator<T>>
class SortedVec {
    std::vector<T, Alloc> v;
public:
    void insert(T x) {
        auto it = std::lower_bound(v.begin(), v.end(), x, Compare{});
        v.insert(it, std::move(x));
    }
    void dump() const {
        for (const auto& x : v) std::cout << x << ' ';
        std::cout << '\n';
    }
};

int main() {
    SortedVec<int> asc;                 // 默认策略：从小到大
    SortedVec<int, GtCompare> desc;     // 注入策略：从大到小
    for (int x : {3, 1, 4, 1, 5}) { asc.insert(x); desc.insert(x); }
    asc.dump();
    desc.dump();

    SortedVec<int, std::less<int>, CountingAlloc<int>> traced;
    traced.insert(1);
    std::cout << "allocations: " << CountingAlloc<int>::alloc_count << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra policy.cpp -o po && ./po
```

```text
1 1 3 4 5 
5 4 3 1 1 
alloc 1 x 4 bytes
allocations: 1
```

`alloc 1 x 4 bytes` 的 4 是 `sizeof(int)`（x86-64 与 32 位主流平台均为 4 字节）。同一个类模板，换个策略实参就是换了实现，编译器能看穿每一层内联调用——这是虚函数接口做不到的。

> **坑：** 策略组合即新类型：`SortedVec<int, std::less<int>>` 和 `SortedVec<int, GtCompare>` 之间没有任何关系，不能互相赋值，也不能装进同一个容器。策略位一多，类型名组合爆炸，维护成本随之上涨。取舍标准：行为在编译期确定且追求性能，用策略；行为要运行期切换，用虚函数或 `std::function`。
{: .sec-pit}

### 16.4.4 CRTP：编译期的"虚函数"
{: .sec-know}

CRTP（Curiously Recurring Template Pattern，奇异递归模板模式）让基类模板以派生类为实参：`class Circle : public Shape<Circle>`。基类在编译期就知道派生类是谁，直接 `static_cast` 过去调它的实现——多态的分发动作发生在编译期，没有 vptr，没有间接跳转。CRTP 的析构不需要 virtual（原因见 16.5 后的变式追问第 2 问），惯用法是把基类析构声明成 `protected`。

```cpp
// crtp_shapes.cpp —— 需要 -std=c++20
#include <iostream>
#include <vector>

constexpr double kPi = 3.14159265358979;

// ---- 版本一：虚函数（运行期多态）----
struct ShapeV {
    virtual double area() const = 0;
    virtual ~ShapeV() = default;
};
struct CircleV : ShapeV {
    double r;
    explicit CircleV(double r) : r(r) {}
    double area() const override { return kPi * r * r; }
};
struct RectV : ShapeV {
    double w, h;
    RectV(double w, double h) : w(w), h(h) {}
    double area() const override { return w * h; }
};

// ---- 版本二：CRTP（静态多态）----
template <class Derived>
class Shape {
protected:
    ~Shape() = default;    // protected 析构：堵死经基类指针 delete 的路径
public:
    double area() const { return static_cast<const Derived*>(this)->area_impl(); }
};
class Circle : public Shape<Circle> {
    double r;
public:
    explicit Circle(double r) : r(r) {}
    double area_impl() const { return kPi * r * r; }
};
class Rect : public Shape<Rect> {
    double w, h;
public:
    Rect(double w, double h) : w(w), h(h) {}
    double area_impl() const { return w * h; }
};

// 求和：虚函数版要靠基类指针遍历，CRTP 版用参数包直接展开
template <class... Shapes>
double total_area(const Shapes&... s) { return (s.area() + ...); }   // C++17 折叠表达式

int main() {
    CircleV c1(1.0); RectV r1(2.0, 3.0);
    std::vector<ShapeV*> poly{&c1, &r1};
    double a = 0;
    for (const ShapeV* s : poly) a += s->area();
    std::cout << "virtual : " << a << '\n';

    Circle c(1.0); Rect r(2.0, 3.0);
    std::cout << "CRTP    : " << total_area(c, r) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra crtp_shapes.cpp -o cs && ./cs
```

```text
virtual : 9.14159
CRTP    : 9.14159
```

两版输出一致，成本结构完全不同：虚函数版每个对象多一个 vptr，每次 `area()` 一次虚表间接，编译器很难内联；CRTP 版全程静态分发，`total_area(c, r)` 实例化后就是两个直接调用，内联后归约成几个乘加指令。

> **坑：** `class Circle : public Shape<Rect>` 这种抄错模板实参的代码，编译器当场不报错——`Shape<Rect>` 对 `Circle` 来说是个合法的基类，错误要等到 `area()` 里的 `static_cast` 被实例化才炸出来。C++23 的 deducing this（见 16.4.6）能根除这类手滑。
{: .sec-pit}

### 辨析：CRTP 与虚函数
{: .sec-iv}

| 维度 | CRTP | 虚函数 |
| --- | --- | --- |
| 绑定时机 | 编译期 | 运行期 |
| 每对象开销 | 无 | 一个 vptr（LP64 下 8 字节） |
| 调用开销 | 可内联，零间接 | 一次虚表间接，阻碍内联 |
| 异构容器 | 装不了，没有共同基类 | `vector<ShapeV*>` 随便装 |
| 新增实现 | 必须重编使用方 | 插件可运行期加载 |
| 类型集合 | 编译期封闭 | 运行期开放 |

判断句和第 15 篇一样：实现何时可知。编译期封闭、性能敏感（数学库、表达式模板、ECS）选 CRTP；运行期开放、需要插件或异构容器选虚函数。两者中间还夹着类型擦除——往下看。

### 16.4.5 类型擦除：手写一个迷你 std::function
{: .sec-know}

`std::function` 能装下任何签名兼容的可调用对象——lambda、函数指针、仿函数——而它们彼此毫无继承关系。它靠的不是模板参数（那样每种可调用对象都是一个新类型），而是**类型擦除**：外层类模板按签名特化，内层用"抽象基类 + 模板包装器 + 虚调用"把具体类型藏起来。说白了就是三个零件：

```cpp
// mini_function.cpp —— 需要 -std=c++20
#include <functional>   // std::bad_function_call
#include <iostream>
#include <memory>
#include <utility>

template <class Sig>
class MiniFunction;                    // 主模板只声明，靠偏特化把签名拆开

template <class R, class... Args>
class MiniFunction<R(Args...)> {
    struct Base {                      // 零件一：统一接口
        virtual ~Base() = default;
        virtual R call(Args... args) = 0;
        virtual std::unique_ptr<Base> clone() const = 0;
    };
    template <class F>
    struct Wrap : Base {               // 零件二：模板包装器，具体类型在这里被"藏"住
        F f;
        explicit Wrap(F f) : f(std::move(f)) {}
        R call(Args... args) override { return f(std::forward<Args>(args)...); }
        std::unique_ptr<Base> clone() const override { return std::make_unique<Wrap>(f); }
    };
    std::unique_ptr<Base> p;           // 零件三：擦除后的句柄
public:
    MiniFunction() = default;
    template <class F>
    MiniFunction(F f) : p(std::make_unique<Wrap<F>>(std::move(f))) {}
    MiniFunction(const MiniFunction& other) {           // 拷贝靠 clone 转发
        if (other.p) p = other.p->clone();
    }
    MiniFunction& operator=(MiniFunction other) noexcept { p.swap(other.p); return *this; }
    MiniFunction(MiniFunction&&) noexcept = default;
    MiniFunction& operator=(MiniFunction&&) noexcept = default;

    R operator()(Args... args) const {
        if (!p) throw std::bad_function_call();
        return p->call(std::forward<Args>(args)...);
    }
    explicit operator bool() const { return p != nullptr; }
};

int main() {
    MiniFunction<int(int)> fact = [](int n) {          // 无捕获 lambda
        int r = 1;
        while (n > 1) r *= n--;
        return r;
    };
    std::cout << fact(5) << '\n';

    int base = 10;
    MiniFunction<int(int)> addb = [base](int x) { return base + x; };   // 有捕获也照装
    MiniFunction<int(int)> copy = addb;                // 拷贝走 clone
    std::cout << copy(5) << '\n';

    MiniFunction<void()> hi = [] { std::cout << "hello erasure\n"; };
    hi();
}
```

```bash
g++ -std=c++20 -Wall -Wextra mini_function.cpp -o mf && ./mf
```

```text
120
15
hello erasure
```

这个迷你版省掉了两样真货才有的东西：小对象优化（libstdc++ 的 `std::function` 会在对象内部预留空间，装得下的可调用对象免堆分配）、以及按引用传参的签名支持。但骨架完整：`Base` 定接口，`Wrap<F>` 干活，`MiniFunction` 持有擦除后的指针。每次调用一次虚表间接，构造一次堆分配——这就是类型擦除的价目表。标准库三兄弟 `std::function`、`std::any`、`std::variant`（后两者见第 15 篇 15.9）全是这套原理的变体，`variant` 算半个例外：类型集合封闭时它连虚调用都省了。

> **坑：** `std::function` 按值捕获的可调用对象随拷贝一起复制，但**按引用捕获的 lambda 不然**——拷出去的副本里存的是原对象的地址。把 `std::function` 塞进容器再让原 lambda 析构，调用就是悬垂访问。要么按值捕获，要么保证原对象活得比 `function` 久。
{: .sec-pit}

### 16.4.6 mix-in 与 deducing this：CRTP 的现代接班人
{: .sec-ext}

CRTP 有两处硌手：每个派生类都要重写一遍自己的名字（`class Circle : public Shape<Circle>`），而且写错实参编译器不吭声。C++23 的显式对象参数（deducing this，P0847）让 mix-in 免开模板门：成员函数用 `this Self&&` 声明，调用时 `Self` 自动推导成**调用者自身的类型**（含引用与 const 修饰），mix-in 从此不用知道谁继承它。

```cpp
// deducing_this.cpp —— 需要 -std=c++23（GCC 14 起、MSVC 19.32 起、Clang 18 起）
#include <iostream>
#include <string>
#include <string_view>

// mix-in：谁继承我，谁就获得链式打印能力，且不用把我写成模板
class PrintMixin {
public:
    template <class Self>
    Self&& print(this Self&& self, std::string_view msg) {
        std::cout << msg << '\n';
        return std::forward<Self>(self);   // 左值进来还是左值，右值进来还是右值
    }
};

class Job : public PrintMixin {
    int step = 0;
public:
    Job& advance() { ++step; return *this; }
    int state() const { return step; }
};

int main() {
    Job j;
    j.advance().print("step done").advance().print("another");
    std::cout << j.state() << '\n';
}
```

```bash
g++ -std=c++23 -Wall -Wextra deducing_this.cpp -o dt && ./dt
```

```text
step done
another
2
```

`j.advance()` 返回 `Job&`，`print` 的 `Self` 推导成 `Job&`，`std::forward<Self>` 原样返回左值引用，链条继续。换成右值对象调用，`Self` 就是 `Job`，返回右值引用——值类别全程保真，这在 CRTP 时代得为左值/右值各写一个重载才做得到。C++23 之前实现同样的链式 mix-in 只能上 CRTP；有了 deducing this，只有需要**在基类里使用派生类的其他成员**时（比如让基类调用派生类的 `name()`）才还需要模板基类。

### 16.4.7 Concepts：把约束写进接口
{: .sec-know}

16.3.8 列过 SFINAE 的三宗罪：报错爆炸、拖慢编译、意图被实现细节埋掉。C++20 Concepts 三刀全中：约束写进签名、检查失败直接说哪条不满足、约束参与重载决议。概念是"编译期对类型的一组体检项"，定义用 `concept`，使用有三种位置：

```cpp
// concepts.cpp —— 需要 -std=c++20
#include <concepts>
#include <iostream>
#include <string>
#include <vector>

template <class T>
concept Numeric = std::integral<T> || std::floating_point<T>;   // 概念可组合

template <class T>
concept Plusable = requires(T a, T b) {          // requires 表达式：编译期体检单
    { a + b } -> std::convertible_to<T>;         // 复合需求：合法且结果可转成 T
};

template <class C>
concept HasValueType = requires { typename C::value_type; };   // 类型需求

template <Numeric T>                             // 位置一：当类型占位符
T twice(T x) { return x + x; }

template <class T>
    requires Plusable<T>                         // 位置二：requires 子句
T add(T a, T b) { return a + b; }

static_assert(HasValueType<std::vector<int>>);   // 位置三：bool 语境随便用
static_assert(!HasValueType<int>);

int main() {
    std::cout << twice(21) << '\n';              // int 满足 Numeric
    std::cout << twice(1.5) << '\n';
    // twice(std::string("ab"));                 // 不满足 Numeric，报错直指原因
    std::cout << add(1, 2) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra concepts.cpp -o cp && ./cp
```

```text
42
3
3
```

requires 表达式里能写四种需求，覆盖了 SFINAE 惯用法的全部检测能力：

| 需求形式 | 写法 | 检查什么 |
| --- | --- | --- |
| 简单需求 | `a + b;` | 表达式能通过编译 |
| 类型需求 | `typename C::value_type;` | 嵌套类型存在 |
| 复合需求 | `{ a + b } noexcept -> std::convertible_to<T>;` | 表达式合法、（可选）不抛异常、结果满足某概念 |
| 嵌套需求 | `requires Plusable<typename T::value_type>;` | 内层约束整体成立 |

概念之间有"包含"关系（subsumption）：`std::signed_integral` 的定义展开后包含 `std::integral`，于是给同一模板写两版约束时，编译器自动认为满足 `signed_integral` 的重载"更特化"，不会报二义。这套偏序是编译器在语法树层面算出来的，不需要你手写 `enable_if` 套娃。

### 16.4.8 可变参数模板与元组展开：折叠表达式实战
{: .sec-prac}

参数包（C++11）让模板接受任意个实参，包展开（pack expansion）把"一串"铺成"一行"，折叠表达式（C++17）再把这一行套进一个运算符里。三者合起来，`std::tuple` 的逐元素操作就能写成一行代码。打印 tuple 是最经典的练手题：

```cpp
// print_tuple.cpp —— 需要 -std=c++20
#include <cstddef>
#include <iostream>
#include <string>
#include <tuple>
#include <utility>

// 写法一：index_sequence 手工展开（C++14 的老手艺，看得见机制）
template <class Tuple, std::size_t... I>
void print_tuple_impl(const Tuple& t, std::index_sequence<I...>) {
    std::cout << '[';
    ((std::cout << (I == 0 ? "" : ", ") << std::get<I>(t)), ...);   // 逗号折叠表达式
    std::cout << "]\n";
}

template <class... Args>                     // Args... 是参数包：一串类型
void print_tuple(const std::tuple<Args...>& t) {
    print_tuple_impl(t, std::index_sequence_for<Args...>{});
}

// 写法二：std::apply 把 tuple 拆成参数包喂给 lambda（C++17，推荐）
template <class... Args>
void print_tuple2(const std::tuple<Args...>& t) {
    std::apply([](const auto&... elems) {
        std::size_t i = 0;
        std::cout << '[';
        ((std::cout << elems << (++i < sizeof...(elems) ? ", " : "")), ...);
        std::cout << "]\n";
    }, t);
}

int main() {
    auto t = std::make_tuple(1, 2.5, std::string("hi"), 'x');
    print_tuple(t);
    print_tuple2(t);
    print_tuple(std::tuple<>{});             // 空包：逗号折叠允许空
}
```

```bash
g++ -std=c++20 -Wall -Wextra print_tuple.cpp -o pt && ./pt
```

```text
[1, 2.5, hi, x]
[1, 2.5, hi, x]
[]
```

折叠表达式一共四种形态，方向由包的位置决定：

| 形态 | 展开 | 典型用途 |
| --- | --- | --- |
| `(pack op ...)` | `e1 op (e2 op (... op eN))` | 右折叠，`(args + ...)` 求和 |
| `(... op pack)` | `((e1 op e2) op ...) op eN` | 左折叠 |
| `(pack op ... op init)` | `e1 op (... op (eN op init))` | 带初值右折叠，空包时返回 init |
| `(init op ... op pack)` | `((init op e1) op ...) op eN` | 带初值左折叠 |

有个细节多数人第一次都会踩：空参数包只能对 `&&`（结果 true）、逻辑或运算符（结果 false）、`,`（结果为 void 表达式）三种运算符折叠，其余是编译错误。上例选逗号折叠正是为了兼容空 tuple。`sizeof...(pack)` 求包内元素个数（C++11）；`std::index_sequence_for<Args...>` 等价于 `std::make_index_sequence<sizeof...(Args)>`。

### 16.4.9 `if constexpr`：编译期分支组合
{: .sec-know}

`if constexpr`（C++17）在编译期选支，且**被丢弃的分支不做模板实例化检查**——条件依赖模板参数时，死分支里可以写对当前实参非法的代码。这一条性质让它取代了 SFINAE 时代的大量标签分发（tag dispatch）手法：

```cpp
// if_constexpr.cpp —— 需要 -std=c++20
#include <iostream>
#include <iterator>
#include <list>
#include <string>
#include <type_traits>
#include <vector>

// 统一接口：随机访问迭代器用下标一步到位，其余逐个前进（std::advance 的思路）
template <class Iter, class Distance>
void my_advance(Iter& it, Distance n) {
    if constexpr (std::is_base_of_v<std::random_access_iterator_tag,
                   typename std::iterator_traits<Iter>::iterator_category>) {
        it += n;                              // 只有这条会被实例化
    } else {
        while (n-- > 0) ++it;                 // 死分支对 vector 迭代器是"非法"代码，但没人看它
    }
}

// 按类型类别走不同分支
template <class T>
std::string describe(const T& v) {
    if constexpr (std::integral<T>) {
        return "int " + std::to_string(v);
    } else if constexpr (std::floating_point<T>) {
        return "float " + std::to_string(v);
    } else {
        return "other";
    }
}

int main() {
    std::vector<int> v{1, 2, 3};
    auto vi = v.begin();
    my_advance(vi, 2);
    std::cout << *vi << '\n';                 // 走 it += n 分支

    std::list<int> l{1, 2, 3};
    auto li = l.begin();
    my_advance(li, 2);
    std::cout << *li << '\n';                 // 走逐个 ++ 分支

    std::cout << describe(42) << ' ' << describe(2.5) << ' '
              << describe(std::string("x")) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra if_constexpr.cpp -o ic && ./ic
```

```text
3
3
int 42 float 2.500000 other
```

`describe` 的三个分支写在一个函数体里，可读性和三套 SFINAE 重载天差地别。和 16.4.7 的 Concepts 配合是常见组合：concept 决定"谁能调用这个模板"，`if constexpr` 决定"进来之后走哪条路"，一层管接口，一层管实现。

> **坑：** "被丢弃分支不检查"的前提是条件依赖模板参数。写 `if constexpr (sizeof(void*) == 8)` 这种与模板参数无关的条件，两个分支都会被完整检查，死分支写错了照样报错。另一个小坑：`else if constexpr` 要连写，拆成普通 `else { if constexpr ... }` 会让后面的分支失去丢弃资格。
{: .sec-pit}

## 16.5 技术解惑
{: .sec-expl}

这一节是十个高频工程问题，按"为什么"到"怎么办"排列：编译模型（放头文件、实例化点）、编译性能（慢在哪、extern template、膨胀）、约束写法（concepts 还是 SFINAE）、报错阅读，最后是模板与 ABI 这块硬骨头。

### 16.5.1 为什么模板的实现必须放在头文件？
{: .sec-know}

编译器实例化模板时需要**看到完整定义**——替换实参、检查语义、生成代码，一步都离不开函数体。而 C++ 的编译单元互不可见：`main.cpp` 调用 `max_of<int>` 时，它只包含你给它的头文件，看不到 `impl.cpp` 里的定义，于是只能留一个未解析符号等链接器，链接器又找不到实例化出的代码——这就是"模板定义放 .cpp 会报 undefined reference"的完整因果链。所以模板的通行组织方式是：**声明和实现都在头文件里，每个用到它的编译单元各自实例化，链接期靠弱符号去重**（见 16.5.2）。

实现放头文件还带来一个衍生问题：模板代码是"先当普通代码解析一遍、实例化时再解析一遍"的——这就是**两阶段查找**。第一阶段（定义时）检查语法、查所有非依赖名；第二阶段（实例化时）替换实参、查依赖名。麻烦在于依赖名长什么样第一阶段判断不了，`T::value_type` 可能是类型也可能是静态成员，`obj.get<int>()` 可能是模板也可能是普通函数。C++ 规定默认按"不是"处理，你确定是时必须显式声明——`typename` 和 `template` 两个消歧关键字由此而来：

```cpp
// dependent_names.cpp —— 需要 -std=c++20
#include <iostream>
#include <vector>

struct Bag {
    using value_type = int;
    template <class U>
    int size_of() const { return sizeof(U); }
};

template <class T>
struct Reader {
    using value_type = typename T::value_type;   // 少 typename：编译错误
    std::vector<value_type> data;
};

template <class T>
int first_size(const T& obj) {
    return obj.template size_of<int>();          // 少 template：编译错误
}

int main() {
    Reader<Bag> r;
    std::cout << sizeof(r.data) << ' ' << first_size(Bag{}) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra dependent_names.cpp -o dn && ./dn
```

```text
24 4
```

`sizeof(std::vector<int>)` 的 24 是 x64 上 libstdc++/MSVC/libc++ 的共同结果（三个指针）；`4` 是 `sizeof(int)`。记忆口诀：**依赖名前，类型加 `typename`，模板加 `template`**。好消息是这口诀只对模板内部生效，模板外（比如 `main` 里写 `std::vector<int>::value_type`）不需要——因为那时一切都已知。

### 16.5.2 实例化点在哪？两阶段查找到底查了什么？
{: .sec-know}

**实例化点**（point of instantiation，POI）：类模板在其首次需要完整类型的地方实例化（比如声明一个该类型的变量）；函数模板和类模板的成员函数体在其**首次被使用**的地方实例化。16.2 里那个"成员函数没被调用就不检查"的规则就是这条的推论——函数体没进任何 POI，编译器自然不看。

两阶段查找的分工：第一阶段只查**非依赖名**——不依赖模板参数的名字，包括模板自己的参数之外的一切普通名字；第二阶段在 POI 处查**依赖名**，外加实参类型所在命名空间的 ADL 名字。所以第一阶段就能抓到这类错误：

```cpp
// two_phase.cpp —— 需要 -std=c++20
template <class T>
struct Bad {
    Unknown u;          // 非依赖名：定义处直接报错，不用等实例化
    T val;
};
```

```bash
g++ -std=c++20 -fsyntax-only two_phase.cpp
```

```text
two_phase.cpp:4:5: error: 'Unknown' does not name a type
```

而函数体里的依赖名错误要等到实例化才暴露，报错位置会指向 POI，链条一路回溯到模板定义——这就是模板报错"绕"的根源。POI 还有条 ODR 推论：同一个特化在多个编译单元里各自实例化，链接期合并成一份（符号表里表现为弱符号）；如果各编译单元因编译选项不同而实例化出**不同的**定义，合并后行为是 undefined behavior。

#### 用 nm 看实例化结果

```cpp
template <class T>
T sum_all(const std::vector<T>& v) {
    T s{};
    for (const T& x : v) s += x;
    return s;
}

int main() {
    std::vector<int> v{1, 2, 3};
    return sum_all(v) == 6 ? 0 : 1;   // sum_all<int> 的实例化点就在这一行
}
```

### 16.5.3 `extern template` 怎么用？
{: .sec-prac}

显式实例化声明的语义：**"这个特化别在我这里生成，别处有。"** 用法三步：模板定义照常放头文件；某个 .cpp 里写显式实例化**定义**（全程序唯一一份）；其他使用方的头文件里写显式实例化**声明**（`extern template`）。C++11 起标准支持，标准库自己就这么干——libstdc++ 的 `<iostream>` 早已对常用 `char` 特化做了显式实例化。

```cpp
// heavy.hpp
#ifndef HEAVY_HPP
#define HEAVY_HPP
#include <vector>

template <class T>
T sum_all(const std::vector<T>& v) {
    T s{};
    for (const T& x : v) s += x;
    return s;
}

// 声明：sum_all<int> 别在我这里实例化，去别处找
extern template int sum_all<int>(const std::vector<int>&);
#endif

// heavy_impl.cpp —— 显式实例化定义：全程序只有这一份
#include "heavy.hpp"
template int sum_all<int>(const std::vector<int>&);

// main.cpp —— 正常使用，本地不生成代码
#include <iostream>
#include "heavy.hpp"

int main() {
    std::vector<int> v{1, 2, 3, 4};
    std::cout << sum_all(v) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra main.cpp heavy_impl.cpp -o et && ./et
```

```text
10
```

收益在改模板时最明显：`sum_all` 的实现变了，只有 `heavy_impl.cpp` 重编，几十个使用它的编译单元不动。适合用在"模板很大、使用方很多"的场景；小模板不值得折腾。

> **坑：** 写了 `extern template` 声明却忘了任何地方提供显式实例化定义，链接器会报 undefined reference——声明把本地实例化关掉了，又没人兑现。排查时先搜显式实例化定义在不在。
{: .sec-pit}

### 16.5.4 模板元编程还值得学吗？
{: .sec-ext}

值得学的是**思路**，值得写的是**替代品**。C++98 时代没有 `constexpr`，数值计算只能靠模板递归——类型当数值用，特化当递归出口：

```cpp
// tmp_evolution.cpp —— 需要 -std=c++20
#include <iostream>

// C++98：模板递归，每次展开一层
template <unsigned N>
struct Fact98 { static constexpr unsigned value = N * Fact98<N - 1>::value; };
template <>
struct Fact98<0> { static constexpr unsigned value = 1; };

// C++11：constexpr 函数能递归，但函数体只许一条 return
constexpr unsigned long long fact11(unsigned n) {
    return n <= 1 ? 1 : n * fact11(n - 1);
}

// C++14 起到 C++20：循环、局部变量都合法——首选写法，不吃实例化深度
constexpr unsigned long long fact20(unsigned n) {
    unsigned long long r = 1;
    while (n > 1) r *= n--;
    return r;
}

int main() {
    static_assert(Fact98<5>::value == 120);
    static_assert(fact11(5) == 120);
    static_assert(fact20(20) == 2432902008176640000ull);
    std::cout << fact20(10) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra tmp_evolution.cpp -o tmp && ./tmp
```

```text
3628800
```

三代写法同一件事，成本天差地别：`Fact98` 每个数值实例化一个类，还烧模板递归深度（16.1.4 提过默认 900 层的限制）；`fact20` 是普通函数，编译器一次算完。所以判断很简单——**算数值（甚至算类型都不是），交给 constexpr 函数**；C++20 的 `consteval` 还能强制"必须编译期算"。模板元编程真正不可替代的领地只剩**类型级计算**：trait 推导、类型列表操作、给不同类型选不同代码路径——而这大半已被 Concepts 和 `if constexpr` 收编。读懂老代码里的 `boost::mpl` 风格递归即可，新代码别再那么写。

### 16.5.5 编译为什么这么慢？
{: .sec-know}

模板把一部分"编程"搬进了编译期，编译器就得替你写代码。慢的来源按权重排：

1. **实例化体量**。每套实参都是一次"内部再编译"，泛型库一展开就是几十上百个特化。
2. **头文件反复展开**。模板几乎都在头文件里，`#include` 是纯文本复制，一个 `vector` 头展开出来上万行，每个编译单元重复一遍。
3. **候选集爆炸**。重载决议要逐个推导、逐个 SFINAE 替换，候选一多推导次数线性上涨。
4. **膨胀反噬优化器**。生成的代码多，内联、跨过程分析的输入就大。

对应的缓解手段各有适用面：

```bash
g++ -std=c++20 -H big.cpp -o big 2>&1 | wc -l        # -H 打印头文件包含树，看展开了多少
g++ -std=c++20 -ftime-report big.cpp -o big 2>&1 | tail -n 15   # GCC 各阶段耗时报表
clang++ -std=c++20 -ftime-trace -c big.cpp           # 生成 json 火焰图，浏览器或 speedscope 打开
```

诊断优先，下药在后：头文件肥就前向声明、砍 include、上预编译头；实例化多就 `extern template` 收敛；真要根治，C++20 modules 按语义导入头文件，跳过文本展开，是标准给出的长期答案。

### 16.5.6 模板与 ABI
{: .sec-know}

模板特化**没有跨二进制的稳定 ABI**。根本原因：特化代码在各个使用方的编译单元里就地生成，标准从不承诺"换个编译器/换个版本生成的一模一样"。三个现实层面的坑：

| 场景 | 风险 | 规避 |
| --- | --- | --- |
| 混用不同编译器编译的模板库 | 内联展开的代码依赖编译器内部布局约定 | 模板库统一编译，或纯头文件随用随编 |
| 标准库实现切换 ABI 开关 | libstdc++ 的 `_GLIBCXX_USE_CXX11_ABI`、MSVC 的 `_ITERATOR_DEBUG_LEVEL` 会改变 `string`/`vector` 布局 | 链接的每个二进制用同一组宏编译 |
| 跨动态库传模板实例 | 各侧实例化的版本/选项不一致即违反 ODR | 接口收口成非模板：工厂函数返回不透明指针 |

一句话总结实践：**模板类型只在编译器、版本、编译选项全部一致的二进制族内部流通**；要跨边界，把边界做成非模板接口——传 `void*` 加工厂函数，或者像标准库那样用类型擦除把模板包在稳定接口后面。第 15 篇 15.9 讲的 pimpl 手法在这里同样适用。

### 16.5.7 Concepts 的报错为什么更友好？
{: .sec-expl}

同一个约束用两种写法，报错完全两个世界。SFINAE 版本（GCC，节选、有删减）：

```text
old.cpp: In function 'int main()':
old.cpp:9:20: error: no matching function for call to 'describe(std::string)'
old.cpp:4:13: note: candidate: 'template<class T>
    std::enable_if_t<std::is_integral_v<T>, int> describe(T)'
old.cpp:4:13: note:   template argument deduction/substitution failed:
old.cpp: In substitution of 'template<class T> ... [with T = std::__cxx11::basic_string<char>]':
old.cpp:4:13: note: ...(后面还有十几条候选的逐条展开，略)
```

Concepts 版本（同一逻辑，节选）：

```text
new.cpp:9:20: error: use of function 'T describe(T) [with T = std::basic_string<char>]'
    with unsatisfied constraints
new.cpp:4:6: note: constraints not satisfied
new.cpp:4:9: note: 'std::integral<std::basic_string<char> >' evaluated to false
new.cpp:4:35: note: 'std::floating_point<std::basic_string<char> >' evaluated to false
```

差别不在排版，在机制。SFINAE 的失败发生在实参替换**过程中**，编译器只知道"替换炸了"，不知道也不记录为什么炸——只能把每条候选的展开现场原样倒给你。Concepts 的检查是**对每条原子约束求值并记录布尔结果**：`std::integral<string>` 为 false、`std::floating_point<string>` 为 false，失败被结构化保存，报错时按需回放。这也是为什么概念报错能精确到"哪一条子约束"，而 SFINAE 报错永远是一面墙。

### 16.5.8 什么时候写 concepts，什么时候写 SFINAE？
{: .sec-iv}

C++20 可用就是 concepts，没有例外。真正的决策只发生在两个地方——**代码库还停在 C++17 及以下**（SFINAE 是唯一选择），以及**读老代码**时（得认得惯用法的对应关系）：

| 任务 | C++20 写法 | C++17 及以下的 SFINAE 对应 |
| --- | --- | --- |
| 给函数模板加约束 | `template <std::integral T> void f(T);` | `enable_if_t<is_integral_v<T>, int> = 0` |
| 检测成员或表达式是否存在 | requires 表达式 | `void_t` + `declval` 惯用法 |
| 按条件选类模板的实现 | 偏特化 + requires 子句 | 主模板 + `void_t` 偏特化两段式 |
| 概念组合与偏序 | 概念用逻辑与、逻辑或组合，编译器自动算偏序 | 手写层层嵌套的 `enable_if` 条件 |

迁移基本是机械翻译：`enable_if` 的条件搬进 requires 子句，`void_t` 检测的表达式搬进 requires 表达式，语义不变、报错变好、编译更快。

```cpp
// migrate.cpp —— 对照片段：同一约束的新旧写法（C++20）
template <class T> requires std::integral<T>
void f_old_style(T);

template <std::integral T>     // 等价的简写：概念直接当类型参数用
void f_new_style(T);
```

### 16.5.9 代码膨胀怎么控制？
{: .sec-best}

膨胀的机制在 16.1 就说过：每套模板实参生成一份独立代码，`vector<int>` 和 `vector<long>` 不会共享哪怕一行。控制手段按性价比排序：

| 手段 | 原理 | 代价 |
| --- | --- | --- |
| 收敛实参类型 | 通用引用先 `std::decay_t` 归一再转发，避免 `int`/`int&`/`const int&` 各一份 | 个别场景多一次拷贝 |
| 显式实例化集中 | `extern template` + 单点定义，使用方不生成代码 | 要维护实例化清单 |
| 类型擦除收口 | 非模板核心函数干活，模板薄壳做转发（`std::shared_ptr` 控制块的思路） | 一次虚调用间接 |
| 链接期去重 | `-ffunction-sections -fdata-sections` 配 lld/gold 的 `--icf=all` 折叠相同代码 | 只能折叠字节级相同的函数 |
| 丈量，别猜 | bloaty 对比各符号体积，定位膨胀大头 | 无 |

顺序上先丈量：多数膨胀来自少数几个大模板，收敛它们的实参集合往往一轮就见效。剩下的再谈收口——类型擦除是有运行期成本的，别为了二进制大小把热路径的静态分发也擦掉。

### 16.5.10 模板报错怎么读？
{: .sec-ts}

模板报错的信息量 90% 是噪声，有效阅读顺序是固定的：

1. **只看第一条 error**。后面的 error 多是第一条的连带反应。
2. **顺着 note 找回你的代码**。GCC/Clang 用 `required from here` 或 `in instantiation of` 把实例化链条从报错点一路指回调用现场——直接在输出里搜你自己的文件名，命中的那几行才是需要看的。
3. **Clang 比 GCC 多一步翻译**。`candidate template ignored: ...` 后面直接写明被剔原因（`deduced conflicting types`、`constraints not satisfied`），优先看这个。

常见的报错关键词与实际含义：

| 报错关键词 | 实际含义 | 先查什么 |
| --- | --- | --- |
| no matching function | 所有候选被剔（推导失败、约束失败、SFINAE） | 每条候选的 note |
| constraints not satisfied | 概念体检没过 | note 指出的那条子约束 |
| ambiguous ... | 偏序打平或转换序列等优 | 重载之间是否互不更特化 |
| use of deleted function | 匹配上了但函数被 delete | 是谁 delete 的（拷贝？移动？） |
| required from here | 实例化链条的节点 | 链条上离你代码最近的那行 |

还有个自疗手法——**探针**。把可疑表达式塞进 requires 表达式单独编译，报错会精确落在非法的那条需求上：

```cpp
// probe.cpp —— 探针写法（C++20）：逐条验证表达式合法性
#include <string>

static_assert(requires(std::string s) { s + s; });          // 过
static_assert(requires(std::string s, int i) { i + s; });   // 不过：错就错在这一条
```

```bash
g++ -std=c++20 -fsyntax-only probe.cpp   # 第二条 static_assert 失败，报错指向 i + s
```

比在大工程里大海捞针快得多——泛型代码调试，八成的功夫花在把问题缩小成一个最小表达式上。

| 知识点 | 要点 | 版本 |
| --- | --- | --- |
| 嵌套模板实参 | `vector<vector<int>>` 无需空格；C++03 必须写 `> >` | C++11 |
| 模板模板参数 | 把模板本身当实参；匹配规则放宽后可直接接 `std::vector` | 放宽：C++17 |

| 类型擦除 | 抽象基类 + 模板包装器 + 虚调用收编任意可调用对象；一次间接加一次堆分配 | std::function：C++11 |

| Concepts | requires 子句限定模板，requires 表达式含四类需求；参与重载决议与偏序 | C++20 |
| 可变参数模板 | 参数包 `Args...`，`sizeof...` 求个数，包展开发生在模式里 | C++11 |
| 折叠表达式 | 四种形态；空包只能与 `&&`、逗号、逻辑或三种运算符折叠 | C++17 |
| `if constexpr` | 编译期选支；条件依赖模板参数时被丢弃分支不做实例化检查 | C++17 |
| typename/template 消歧 | 依赖名前的类型、模板必须显式声明 | C++98 |
| extern template | 显式实例化声明抑制本地实例化，显式实例化定义全程序一份 | C++11 |
| 实例化点 | 类模板在首次需要完整类型处，函数体在首次使用处；两阶段查找分工 | — |
| 代码膨胀 | 每套实参一份代码；收敛实参、显式实例化、类型擦除三路控制 | — |

## 变式追问
{: .sec-think}

1. **"`if constexpr` 的被丢弃分支完全不检查"——这句话对吗？**
   对一半。条件依赖模板参数（如 `std::is_integral_v<T>`）时，被丢弃分支不做实例化检查，里面写对当前实参非法的代码没问题；条件不依赖模板参数（如 `sizeof(void*) == 8`）时，即便写在模板里，两个分支都会被完整检查，死分支写错照样报错。所以"让非法分支消失"的前提是条件 value-dependent。再抠细一点：不实例化不等于免语法解析——函数体的词法和语法检查在定义时总要过，`if constexpr` 不是免检通行证。

2. **CRTP 基类的析构函数需要 virtual 吗？非虚的话危险在哪？**
   危险真实存在：`Shape<Circle>* p = new Circle; delete p;` 是合法代码——`Shape<Circle>*` 本就是 `Circle*` 的基类指针，析构非虚时这是 undefined behavior，与普通继承无异。但加虚析构是开错药方：虚析构是为"经基类指针多态删除"服务的，而 CRTP 根本没有异构删除的场景。惯用解法是把基类析构声明成 `protected`——外部写不出经基类指针 delete 的代码，编译期堵死，零运行期开销。16.4.4 的示例里就是这么写的。

3. **`std::function<int(int)> f = [&](int n) { return n <= 1 ? 1 : n * f(n - 1); };` 这样写递归能跑吗？**
   能跑。lambda 按引用捕获了正在初始化的 `f` 自己，但 lambda 体只在**调用时**才求值，那时初始化早已完成，`f` 里已有可调用对象。坑在两处：拷贝后副本里存的还是原 `f` 的地址，原对象析构后再调副本就是悬垂访问；把 `f` 拷进 `vector` 后重排扩容，捕获的地址同样指向失效的旧位置。正经写法给递归一个稳定锚点——普通函数、或者 C++23 的显式对象参数：`auto fact = [](this auto self, int n) -> int { return n <= 1 ? 1 : n * self(n - 1); };`，`self` 指向 lambda 自己，拷贝后依然正确。

4. **`Stack<int, std::vector>` 在 C++14 下为什么编不过？写出两种能让它过的方法，并说明各依赖什么。**
   C++17 之前模板模板参数要求逐参数精确匹配：`std::vector` 有两个模板参数（第二个是带默认值的 `Allocator`），对不上只有一个形参的 `template <class U> class C`。方法一：把形参写成变参 `template <class...> class C`——变参能匹配任意实参数，纯 C++11 机制，所有编译器都认，是当年的通行写法。方法二：升 C++17，P0522R0 放宽后"实参至少与形参一样特化"即可匹配，`std::vector` 靠默认实参补齐差异。提醒：Clang 至今默认没开这个放宽，跨编译器的代码别赌它，变参形式是唯一稳妥解。
