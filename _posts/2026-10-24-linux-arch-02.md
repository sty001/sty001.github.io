## 原理解析：rsync 增量传输原理

rsync 最核心的能力是"只传变化的部分"，这是它区别于 `cp` / `scp` 的关键。默认算法分两个阶段：

1. **快速检查（quick check）**：发送端对每个文件比对大小与修改时间（mtime），完全相同直接跳过 —— 这是 rsync 秒级跳过 GB 级未变文件的原因
2. **增量传输（delta 算法）**：文件确有变化时，发送端把文件切成固定大小的块，对每块计算校验和（弱校验的滚动校验和 + 强校验的 MD5）传给接收端；接收端在自己文件上做同样的分块与匹配，找出"哪些块相同、哪些块不同"
3. **只传差异块**：接收端把不同的块 + 如何在目标文件拼装的指令取回，用本地已有的块 + 新块重组出完整文件

由此推出三个工程结论：

- **第一次同步必然是全量**：目标端没有文件，无从比对，只能整份传输；只有第二次起才享受增量
- **`-z` 压缩的是传输通道**：发送前压缩、接收端解压，对文本类数据（日志、配置）省带宽效果明显，对已压缩数据（图片、视频包）反而浪费 CPU
- **`--checksum` 是更严格但更慢的模式**：放弃 mtime 快速检查，逐文件计算校验和比对，适用于 mtime 不可靠（如某些同步工具改时间）的场景，日常不要开

> **注意：** 面试常考"rsync 与 scp 的区别"：scp 每次全量传输，rsync 增量传输且支持断点续传、排除、限速、删除策略；大文件或频繁同步场景 rsync 有数量级优势。rsync 增量传输的算法思想也被 git、zfs、去重存储广泛借鉴。

> **注意：** 增量算法对不同规模的数据表现不同：单个大文件改了一小块，delta 只传这一块，优势巨大；百万级小文件哪怕内容全没变，逐个 quick check 的元数据开销也不小。所以"海量小文件"场景要么先打包再传，要么以打包好的归档为同步单位 —— 备份项目里先 tar 再 rsync 就是这个道理。

## rsync 守护进程部署

客户端与服务端的交互可以类比上厕所的四个步骤，核心是：**服务端常驻监听（873 端口），客户端主动发起推送或拉取。**

部署思路先立骨架：装软件 → 写配置 → 建用户 → 建密码文件 → 建目录 → 起服务。六步每一步都有可验证的产物，做一步验一步，出问题能立刻定位到哪一步。

### 服务端配置

#### 第一个历程：下载安装软件

```bash
rpm -qa|grep rsync
yum install -y rsync
```

#### 第二个历程：编写配置文件

```bash
man rsyncd.conf
vim /etc/rsyncd.conf
```

```ini
###rsyncd.conf start##

uid = rsync       --- 指定管理备份目录的用户
gid = rsync       --- 指定管理备份目录的用户组
port = 873        --- 定义 rsync 备份服务的网络端口号
fake super = yes  --- 将 rsync 虚拟用户伪装成为一个超级管理员用户
use chroot = no   --- 和安全相关的配置
max connections = 200  --- 最大连接数  同时只能有 200 个客户端连接到备份服务器
timeout = 300          --- 超时时间(单位秒)
pid file = /var/run/rsyncd.pid   --- 记录进程号码信息 1.让程序快速停止进程 2.判断一个服务是否正在运行
lock file = /var/run/rsync.lock  --- 锁文件
log file = /var/log/rsyncd.log   --- rsync 服务的日志文件 用于排错分析问题
ignore errors                    --- 忽略传输中的简单错误
read only = false                --- 指定备份目录是可读可写
list = false                     --- 是否允许客户端查看服务端的模块信息
hosts allow = 172.16.1.0/24      --- 允许传输备份数据的主机(白名单)
hosts deny = 0.0.0.0/32          --- 禁止传输备份数据的主机(黑名单)
auth users = rsync_backup        --- 指定认证用户
secrets file = /etc/rsync.password   --- 指定认证用户密码文件 用户名称:密码信息
[backup]                         --- 模块信息
comment = "backup dir"
path = /backup                   --- 模块中配置参数 指定备份目录
```

> **注意：** `list = false` 表示**不允许**客户端列出服务端的模块信息（后文的"列表功能"需要把它改为 `true` 才能看到模块清单）。很多笔记此处注释写反了，实际行为以 `rsyncd.conf` 的 man 文档为准。

#### rsyncd.conf 全局参数逐项详解

`/etc/rsyncd.conf` 分两部分：`[模块名]` 之前的全局参数对所有模块生效，方括号内是模块级参数，只对该模块生效。

| 参数 | 作用 | 生产建议 |
| --- | --- | --- |
| `uid` / `gid` | 守护进程以哪个用户 / 用户组身份读写备份目录 | 用专用虚拟用户 `rsync`，不要用 root |
| `port` | 监听端口，默认 873 | 保持默认，防火墙放行该端口 |
| `fake super` | 让虚拟用户以 root 身份记录 / 恢复文件属性 | 需要 `-a` 完整还原权限时开启 |
| `use chroot` | 传输前是否把客户端限制在模块目录内 | 安全相关，`yes` 更安全但模块目录不能有软链逃逸 |
| `max connections` | 最大并发连接数 | 按备份高峰期客户端数量设置，防止连接打满 |
| `timeout` | 空闲连接超时时间（秒） | 300 是常用值，大文件慢网络可适当加大 |
| `pid file` / `lock file` | 进程号文件与锁文件路径 | 保持默认，`stop` 时靠 pid 文件定位进程 |
| `log file` | 服务日志路径 | 排错第一现场，务必配置 |
| `ignore errors` | 忽略传输中的非致命错误 | 谨慎开启，可能掩盖真实问题 |
| `read only` | 模块是否只读 | 备份目录设 `false`（可写）；纯分发场景设 `true` |
| `list` | 是否允许客户端列出模块清单 | 隐藏模块时设 `false` |
| `hosts allow` / `hosts deny` | 白名单 / 黑名单 | 建议只用一个，优先白名单 |
| `auth users` | 认证用户名，多个用逗号分隔 | 不配则表示匿名可访问（不推荐） |
| `secrets file` | 认证密码文件路径 | 格式 `用户名:密码`，权限必须 600 |

模块级参数：

| 参数 | 作用 |
| --- | --- |
| `comment` | 模块描述，`rsync 服务器::` 列出时显示 |
| `path` | 模块对应的真实目录，客户端上传的文件落在该目录 |
| `read only` / `list` / `auth users` / `hosts allow` | 模块级可覆盖全局同名参数，实现"不同模块不同策略" |

#### 第三个历程：创建 rsync 服务的虚拟用户

```bash
useradd rsync -M -s /sbin/nologin
```

> **注意：** `-M` 表示不创建家目录，`-s /sbin/nologin` 禁止该用户登录 shell —— 虚拟用户只用于跑服务，不能交互登录，这是最小权限原则的标准做法。

#### 第四个历程：创建备份服务认证密码文件

```bash
echo "rsync_backup:<your-password>" >/etc/rsync.password
chmod 600 /etc/rsync.password
```

> **注意：** 密码文件权限必须是 `600`，否则 rsync 会拒绝启动并报认证文件权限错误。

> **注意：** 服务端密码文件是 `用户名:密码` 格式，客户端密码文件**只放密码**，两者不要搞混。示例中的 `<your-password>` 是占位符，实际使用时替换为强密码，且不要在命令历史、聊天记录里明文传播。

> **注意：** `secrets file` 只在守护进程模式生效；`-e ssh` 模式走的是系统用户认证，与这份密码文件无关。两套认证体系并行，排错前先确认自己在哪种模式里。

#### 第五个历程：创建备份目录并修改属主属组

```bash
mkdir /backup
chown rsync.rsync /backup/
```

> **注意：** 目录属主必须是 `rsyncd.conf` 里 `uid` 指定的用户，否则客户端上传时报 permission denied —— 守护进程是以 `rsync` 身份写盘的，root 建的目录默认 755，rsync 用户照样写不进去。

#### 第六个历程：启动备份服务

```bash
systemctl start rsyncd
systemctl enable rsyncd
systemctl status rsyncd
```

> **注意：** rsync 包自带 systemd 单元文件 `/usr/lib/systemd/system/rsyncd.service`，CentOS 7 / Rocky / AlmaLinux 直接用 `systemctl` 管理即可；早期 CentOS 6 没有该单元，需要通过 `xinetd` 托管 rsync 或手动写启动脚本，那套方式已淘汰，遇到旧文档可以直接跳过。

> **注意：** 这里有个坑：改完 rsyncd.conf 只 `systemctl restart rsyncd` 不一定报错，配置里多打一个空格、模块名拼错都要靠 `cat /var/log/rsyncd.log` 才看得见。服务端排错永远先看这份日志，再看客户端报错。

### 守护进程模式的语法格式

```text
Access via rsync daemon:
```

客户端做**拉**的操作（恢复数据）：

```bash
Pull: rsync [OPTION...] [USER@]HOST::SRC... [DEST]
      rsync [OPTION...] rsync://[USER@]HOST[:PORT]/SRC... [DEST]
```

客户端做**推**的操作（备份数据）：

```bash
Push: rsync [OPTION...] SRC... [USER@]HOST::DEST
```

| 字段 | 含义 |
| --- | --- |
| `SRC` | 要推送备份数据信息 |
| `[USER@]` | 指定认证用户信息 |
| `HOST` | 指定远程主机的 IP 地址或者主机名称 |
| `::DEST` | 备份服务器的模块信息 |

另一种等价写法：

```bash
rsync [OPTION...] SRC... rsync://[USER@]HOST[:PORT]/DEST
```

### 知识卡片：rsync 三种工作方式语法速查

| 工作方式 | 方向 | 语法 | 适用场景 |
| --- | --- | --- | --- |
| 本地模式 | 本地 → 本地 | `rsync [选项] SRC... DEST` | 本机目录间同步，替代 cp |
| 远程 shell 模式 | 推送 | `rsync [选项] SRC... [USER@]HOST:DEST` | 走 SSH 加密通道，免开 873 端口 |
| 远程 shell 模式 | 拉取 | `rsync [选项] [USER@]HOST:SRC... DEST` | 从远端拉数据到本地 |
| 守护进程模式 | 推送 | `rsync [选项] SRC... [USER@]HOST::MODULE` | 生产备份主推方式，免密推送 |
| 守护进程模式 | 拉取 | `rsync [选项] [USER@]HOST::MODULE DEST` | 从备份服务器恢复数据 |
| 守护进程 URL 式 | 双向 | `rsync [选项] SRC rsync://[USER@]HOST[:PORT]/MODULE` | `::` 的等价写法 |

```bash
# 本地同步
rsync -av /data/ /backup/data/

# 远程推送（守护进程，免密）
rsync -avz /data/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password

# 远程拉取（守护进程，从备份服务器恢复）
rsync -avz rsync_backup@172.16.1.41::backup/10.0.0.31/ /backup/ --password-file=/etc/rsync.password

# 远程推送（走 SSH，无需 873 端口）
rsync -avz -e ssh /data/ root@172.16.1.41:/backup/
```

> **注意：** 三种方式的选择逻辑：同一台机器内部用本地模式；跨机器但不想开 873 端口、安全性优先，用 `-e ssh` 走 SSH 通道；集中备份、需要认证与模块管理，用守护进程模式。守护进程模式下地址写 `HOST::MODULE`（两个冒号），远程 shell 模式写 `HOST:PATH`（一个冒号），这是最常写错的地方。

### 辨析：推与拉，daemon 与 ssh

- **推（push）**：客户端主动把数据送过去，是备份的标准做法 —— 各被备份机自己掌握节奏，服务端只管收，新增一台机器不需要服务端改任何东西
- **拉（pull）**：从服务端取数据，主要用于恢复；也用于集中管控场景（备份服务器按清单去各机器收），权限集中，但服务端必须能连通所有客户端
- **daemon 模式**：需要认证、模块隔离、黑白名单、并发控制时用它；代价是多维护一个常驻服务和一份配置文件
- **ssh 模式**：机器少、临时传文件、强制走加密通道时用它；不用开 873 端口，也不用维护 rsyncd.conf，但没有模块、配额、并发管理这些企业能力

说白了：一次性搬点东西用 ssh，要长期跑的备份体系用 daemon。

### 客户端配置

#### 第一个历程：创建一个密码文件

```bash
echo "<your-password>" >/etc/rsync.password
chmod 600 /etc/rsync.password
```

> **注意：** 客户端的密码文件**只包含密码**，不包含用户名；服务端的文件才是 `用户名:密码` 格式。

#### 第二个历程：进行免交互传输数据测试

```bash
rsync -avz /etc/hosts rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
```

> **注意：** 客户端的密码文件同样必须 600 权限，否则 rsync 会以"密码文件权限过于开放"为由拒绝执行；脚本化备份一定要用 `--password-file=`，切勿把密码写在命令行参数里（会留在 ps 输出与 shell 历史中）。

> **注意：** 配置里的 `ignore errors` 看似省心，实际会掩盖传输中断、权限不足这类真问题。备份场景宁可让 rsync 报错退出、靠告警发现，也不要静默"忽略"—— 备份的失败必须是响的。

## rsync 命令参数详解

| 参数 | 含义 |
| --- | --- |
| `-v, --verbose` | 显示详细的传输信息 |
| `-a, --archive` | 命令的归档参数，包含 `rtopgDl` |
| `-r, --recursive` | 递归参数 |
| `-t, --times` | 保持文件属性信息时间信息不变（修改时间） |
| `-o, --owner` | 保持文件属主信息不变 |
| `-g, --group` | 保持文件属组信息不变 |
| `-p, --perms` | 保持文件权限信息不变 |
| `-D` | 保持设备文件信息不变 |
| `-l, --links` | 保持链接文件属性不变 |
| `-L` | 保持链接文件数据信息不变 |
| `-P` | 显示数据传输的进度信息 |
| `--exclude=PATTERN` | 排除指定数据不被传输 |
| `--exclude-from=file` | 排除指定数据不被传输（批量排除） |
| `--bwlimit=RATE` | 限制传输的速率，例如 `100Mb/8=12.5MB` |
| `--delete` | 无差异同步参数（慎用） |

扩展常用参数：

| 参数 | 含义 |
| --- | --- |
| `-z, --compress` | 传输过程中压缩数据，省带宽费 CPU，适合文本类数据 |
| `-h, --human-readable` | 以人类可读方式显示数字（K / M / G） |
| `-n, --dry-run` | 演练模式，只显示会传哪些文件，不实际执行 |
| `-e ssh` | 指定用 SSH 作为传输通道，替代守护进程模式 |
| `--progress` | 显示每个文件的实时传输进度 |
| `--partial` | 保留中断的传输文件，便于断点续传 |
| `-W, --whole-file` | 关闭增量算法整文件传输（本地同步默认行为） |
| `--checksum` | 按校验和判断文件是否变化，替代大小 + mtime 快速检查 |
| `--numeric-ids` | 传输时保留数字 UID / GID，不做用户名映射 |
| `-S, --sparse` | 稀疏文件处理，节省空洞文件的传输量 |

> **注意：** 断点续传的原理一句话：rsync 先把数据写进目标端的临时文件，中断后配合 `--partial` 保留已传完的块，重跑时从断点继续拼，不整文件重传；不加 `--partial` 时临时文件直接删掉，下次从头再来。

> **注意：** 如何让 `-o` 和 `-g` 参数生效：需要将配置文件中的 `uid` 和 `gid` 改为 `root`，并且需要将 `fake super` 参数注释掉。

> **注意：** 参数记忆抓主线：`-avz` 是日常默认组合（归档 + 详细 + 压缩），`-P` 调试时用（进度 + 断点），`--exclude` / `--delete` / `--bwlimit` 是策略三件套。剩下的按需查 man，不必硬背。

> **注意：** `--bwlimit` 的企业案例：备份要占用带宽（相当于一条马路），若不限速会挤占业务带宽（类比"人人网"高峰期），实践中一般按带宽的一半来限速。生产上需要限速的不止备份：白天跨机房搬迁数据、向公有云上传备份集、批量分发安装包，一条不限速的 rsync 就能把出口带宽吃光。

> **注意：** `--delete` 的语义是"我有的你也有，我没有的你也不能有"，慎用 —— 一旦源目录被误清空，备份端数据也会被删除。危险场景还有两个：源路径末尾少写一个 `/`，rsync 会把目标端多出来的"目录本身"当成多余内容整体删掉；源目录是挂载点但挂载丢了，rsync 看到的是空目录，`--delete` 一跑备份端跟着空。所以带 `--delete` 的同步必须先 `-n` 演练、路径写死绝对路径、脚本里先判断源目录非空。

> **注意：** 生产环境第一次对重要目录做同步，先加 `-n` 演练一遍，核对文件清单与数量无误后再去掉 `-n` 真正执行 —— 敲一遍就明白它值多少钱，这个习惯能避开绝大多数"同步成灾难"的事故。

> **注意：** 除 `--password-file` 外，还能用环境变量 `RSYNC_PASSWORD` 免交互，但脚本里 export 密码同样会进进程环境，安全性不比密码文件高，密码文件仍是首选。

### 知识卡片：rsync 服务上线自检清单

| 检查项 | 命令 / 方法 | 预期结果 |
| --- | --- | --- |
| 服务监听 | `ss -lntp \| grep 873` | rsyncd 在监听 |
| 密码文件权限 | `ls -l /etc/rsync.password` | 服务端与客户端都是 600 |
| 备份目录属主 | `ls -ld /backup` | 属主属组为 rsync |
| 手动推送 | 客户端执行一次 rsync | 无报错，文件落到模块目录 |
| 模块可见性 | `rsync user@host::` | list=false 时列不出模块 |
| 防火墙 | `firewall-cmd --list-ports` | 873 已放行 |

## 守护进程服务企业应用

### a. 守护进程多模块功能配置

不同团队的数据可以放到不同模块中：

```text
sa   sa_data.txt
dev  dev_data.txt
dba  dba_data.txt
```

```ini
[backup]
comment = "backup dir"
path = /backup

[dba]
comment = "backup dir"
path = /dba

[dev]
comment = "backup dir"
path = /devdata
```

> **注意：** 多模块的价值是**隔离与授权**：不同模块可以配不同目录、不同认证用户、不同黑白名单。DBA 团队只给他 `dba` 模块的账号，就物理上杜绝了他看到开发团队数据的可能，比"一个模块大家随便传"安全得多。

> **注意：** 模块还可以按数据类型拆：站点一个模块、日志一个模块、数据库备份一个模块，配合不同的保留策略与磁盘空间规划，避免日志把站点备份的空间挤掉。

#### 需求 02：a 目录全部备份，b 目录不备份 1.txt，c 目录不备份 1.txt 和 3.txt

使用 `--exclude-from=file` 批量排除。

```bash
[root@nfs01 /]# cat /data/exclude.txt

```

第二个历程：实现批量排除功能

```bash
[root@nfs01 /]# rsync -avz /data --exclude-from=/data/exclude.txt rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
sending incremental file list
data/
data/01.txt
data/02.txt
data/a/

data/a/2.txt
data/a/3.txt
data/b/

```

> **注意：** 排除文件自身（`exclude.txt`）也会被排除掉，需要在排除列表中显式写上它，否则它会被一起传上去。

> **注意：** `--exclude` 支持通配符：`--exclude=*.log` 排除所有日志，`--exclude=cache/` 排除目录。排除规则多的场景用 `--exclude-from=` 集中管理，规则即文档，后期维护比堆一长串参数清晰。

### c. 守护进程来创建备份目录

```bash
[root@nfs01 /]# rsync -avz /etc/hosts rsync_backup@172.16.1.41::backup/10.0.0.31/ --password-file=/etc/rsync.password
sending incremental file list
created directory 10.0.0.31
hosts

sent 226 bytes  received 75 bytes  602.00 bytes/sec
total size is 371  speedup is 1.23
```

> **注意：** 客户端**无法**在服务端创建多级目录（如 `backup/10.0.0.31/sub/`），需要先把上级目录准备好。

> **注意：** 这个"只能创建一级目录"的行为源于守护进程的安全设计：模块下的子目录需要服务端预先存在，防止客户端随意创建目录结构。项目实战里按 IP 建目录的命令（`mkdir -p /backup/10.0.0.31/`）要先在**服务端**执行，或者先推送一次让 rsync 自动创建一级目录。

### d. 守护进程的访问控制配置

守护进程具备白名单和黑名单功能：

```ini
hosts allow = 172.16.1.0/24      --- 白名单
hosts deny = 0.0.0.0/32          --- 黑名单
```

> **注意：** 建议只使用一种名单，白名单与黑名单同时配置容易产生歧义。

> **注意：** rsync 的名单判定顺序是"先查 hosts allow 是否放行，未命中再查 hosts deny"，但 allow 里没写不等于 deny —— 不同版本文档表述有差异，最稳妥的做法是只配 `hosts allow`（白名单），让策略显式可见，`hosts deny` 留空。

### e. 守护进程的列表功能配置

把 `list` 改为 `true` 后，客户端可以查看服务端有哪些模块：

```bash
[root@nfs01 /]# rsync rsync_backup@172.16.1.41::
backup          "backup dir"
dba             "backup dir"
dev             "backup dir"
```

> **注意：** `list = true` 会把模块名与 comment 暴露给任何能连通 873 端口的人，生产环境如果模块名本身敏感（如包含客户名、项目代号），应保持 `list = false`，模块名只在小范围共享。

## 定期备份与实时备份

### 定期备份（crontab + rsync）

备份体系的两种节奏先分清：定期备份是"每天全量兜底"，实时同步是"变化秒级跟上"，绝大多数企业两套都要，本节先讲定期的最小实现，实时部分展开在后续篇章。

定期备份是主力形态：每天在业务低峰期（通常是凌晨）同步一次，配合 find 清理与 md5 校验。最小可用示例：

```bash
# 每天凌晨 0 点执行备份脚本
crontab -e
# backup data
0 0 * * *  /bin/sh /server/scripts/backup.sh &>/dev/null
```

脚本骨架：

```bash
#!/bin/bash
# 定期备份脚本骨架：打包 → 清理 → 推送
cd /
tar zchf /backup/system_backup_$(date +%F_week%w).tar.gz ./etc ./var/spool/cron/root
rsync -avz /backup/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
```

骨架之外，定期备份还有三件常被忽略的事：脚本加 `flock` 锁防重复执行；每步成败写日志，别让输出静默进黑洞；rsync 退出码非 0 时要告警 —— "没报错"和"传完了"是两回事。

### 实时备份（inotify + rsync）

对"丢一条数据就出事故"的目录（如订单文件、图片上传目录），定期备份不够，要实时同步。主流组合是 inotify 监听文件系统事件 + rsync 执行传输：

- `inotify-tools` 提供 `inotifywait` 命令，监听目录的创建 / 修改 / 删除 / 移动事件
- `sersync`、`lsyncd` 是封装好的"监听 + 同步"工具，前者在国内项目中使用广泛，后者基于 Lua 配置更灵活

思路示例（用 inotifywait 手动触发）：

```bash
# 监听 /data 目录变化，变化后触发一次同步（演示最小原理）
inotifywait -mrq -e modify,create,delete,move /data |
while read line; do
  rsync -avz --delete /data/ rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
done
```

> **注意：** 实时同步是"事件驱动"，一次改一万个文件会触发一万次同步，必须做**合并与限流**（等几百毫秒把零散事件合成一批再同步），sersync / lsyncd 内置了这类机制，生产环境直接用工具，不要手写 while 循环。另外实时同步只保证"最终一致"，同步链路上任何一端宕机，期间的变更就靠下一次定期备份兜底 —— 所以实时备份不能替代定期全量备份，两者是互补关系。

### 辨析：哪些目录适合实时同步，哪些不适合

- **适合**：图片、附件、用户上传文件、静态页面 —— 单文件小、写入独立、丢了能从源头补
- **不适合**：数据库数据目录（有事务一致性要求）、频繁整批重写的临时目录、超大规模小文件目录（事件量把同步拖死）
- **折中**：日志类文件用定时 rsync 增量拉取即可，实时性要求没那么高

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `@ERROR: chroot failed` | `use chroot = yes` 但模块 path 含有软链或层级不符 | `cat /etc/rsyncd.conf`、`ls -ld /backup` | 模块路径去掉软链，或改 `use chroot = no` |
| `password file must not be other-accessible` | 密码文件权限不是 600 | `ls -l /etc/rsync.password` | `chmod 600` 后重试 |
| `@ERROR: auth failed on module backup` | 用户名 / 密码不匹配，或 secrets file 格式错误 | `cat /etc/rsync.password` | 核对服务端 `用户名:密码` 与客户端密码一致 |
| `rsync: failed to connect ... Connection refused` | rsyncd 未启动、端口未监听、防火墙拦截 | `ss -lntp \| grep 873`、`firewall-cmd --list-ports` | 启动 `rsyncd`，放行 873 端口 |
| `permission denied` 写入失败 | 备份目录属主不是配置的 uid 用户 | `ls -ld /backup` | `chown rsync.rsync /backup` |
| `rsync error: error in rsync protocol data stream` | 服务端与客户端版本不兼容、模块名写错 | `rsync --version`、`rsync 服务器::` | 统一版本，核对模块名（区分大小写） |
| 传过去的是目录本身而不是内容 | 源目录末尾没加 `/` | 检查命令 | 加 `/` 重传，注意对已有目标先清理 |
| 备份极慢、业务卡顿 | 无限速占满带宽 | `--bwlimit` 未设置 | 加 `--bwlimit= 业务带宽的一半`，避开高峰期 |

> **注意：** 生产上栽过最多的是密码文件：服务端是 `用户名:密码`，客户端只有密码，两边格式搞混，报错却指向 "auth failed"，第一反应往往是去查密码对不对，实际十有八九是格式或权限问题。

## 现代环境补充

CentOS Linux 7 已于 2024 年 6 月结束维护（EOL），rsync 本身跨版本稳定，Rocky Linux / AlmaLinux / CentOS Stream 上的部署差异主要在周边：

| 项目 | CentOS 7 旧做法 | Rocky / AlmaLinux 新做法 |
| --- | --- | --- |
| 安装软件 | `yum install -y rsync` | `dnf install -y rsync` |
| 服务管理 | `systemctl start rsyncd` | 相同，systemd 单元沿用 |
| 防火墙 | `systemctl stop firewalld` | `firewall-cmd --permanent --add-port=873/tcp && firewall-cmd --reload` |
| 配置文件 | `/etc/rsyncd.conf` + `/etc/sysconfig/network-scripts/` | rsyncd.conf 路径与参数不变；网卡侧若用 NetworkManager，注意别与 network 服务冲突 |

> **注意：** rsyncd.conf 的语法多年未变，这是 rsync 作为经典工具的优势：旧机器上的配置几乎可以平移到新系统，真正需要与时俱进的只是防火墙、服务管理与周边监控的写法。

> **注意：** 新系统上 rsync 默认是 3.x，进度显示可用 `--info=progress2` 替代 `-P`，输出更紧凑；老参数全部兼容，脚本不用改。

## 小结

1. 服务端部署六步：装软件 → 写 `/etc/rsyncd.conf` → 建虚拟用户 `rsync` → 建密码文件（权限 600）→ 建备份目录并改属主 → 启动并开机自启 `rsyncd`。
2. 客户端只需两步：写只含密码的密码文件（权限 600），然后用 `--password-file=` 做免交互传输。
3. `-a` 归档参数等价于 `rtopgDl`；想让 `-o` / `-g` 真正生效，必须把 `uid` / `gid` 改成 `root` 并注释 `fake super`。
4. 排除功能有两种写法：`--exclude` 支持绝对 / 相对路径，`--exclude-from` 支持批量排除；排除文件自身也要写进排除列表。
5. 企业常用能力包括：多模块隔离不同团队数据、客户端只能创建一级备份目录、白名单 / 黑名单访问控制（建议只用一种）、`list` 控制模块可见性。
6. `--delete` 是无差异同步，威力大风险也大，生产环境使用前务必确认源目录状态。
7. 增量传输靠"快速检查 + delta 算法"：大小与 mtime 相同直接跳过，不同则只传差异块；首次同步必然全量，`-z` 压缩传输通道，`--checksum` 用校验和替代快速检查。
8. 三种工作方式按场景选择：本地模式、`-e ssh` 远程 shell 模式、守护进程模式；地址里 `::` 与 `:` 的差别就是守护进程与 SSH 模式的差别。
9. 定期备份（crontab）与实时备份（inotify + rsync / sersync / lsyncd）互补：实时保时效，定期保全量兜底，缺一不可。

## 自测题

1. `rsync -avz /data rsync_backup@172.16.1.41::backup` 报 `@ERROR: auth failed on module backup`，最可能的原因是什么？怎么查？
2. rsync 第二次同步为什么比第一次快得多？描述它判断"要不要传某个文件"的两个层次。
3. 服务端 `/etc/rsync.password` 权限被改成 644 后启动服务，会出现什么？正确权限是多少？
4. `--bwlimit` 是做什么用的？一台百兆服务器跑备份，一般限速到多少比较合理？
5. 客户端想把文件传到 `backup` 模块下不存在的多级目录 `backup/a/b/`，直接执行会怎样？正确的做法是什么？

> **答案：** 1）认证信息不匹配：服务端 secrets file 中的 `用户名:密码` 与客户端使用的用户 / 密码文件内容不一致。先 `cat /etc/rsync.password` 核对两端格式（服务端含用户名、客户端只含密码），确认 `auth users` 指定的用户名无误后重试。2）第一层是快速检查：比对文件大小与 mtime，完全相同直接跳过；第二层是 delta 算法：确有变化时分块计算校验和，只传不同的块，本地重组。第二次同步绝大多数文件被第一层跳过，少量变化文件只传差异块，所以远快于首次全量。3）rsync 会拒绝启动，报 "password file must not be other-accessible"（或类似的权限错误），正确权限是 600（`chmod 600 /etc/rsync.password`）。4）限制传输速率，避免备份流量挤占业务带宽；百兆带宽一般按一半左右限速（如 `--bwlimit=12m`，约合 12.5MB/s），并尽量安排在业务低峰期执行。5）直接执行会失败：守护进程模式下客户端只能在模块下自动创建一级目录，多级目录需要服务端预先创建上级目录，或在推送前先在服务端 `mkdir -p /backup/a/b`。
