## 利用剧本完成服务一键化部署

本篇涉及的一键化部署场景：

- `rsync` 服务部署
- `nfs` 服务部署
- `sersync` 服务部署
- 全网备份项目

四个场景的剧本骨架完全一致，差别只在任务清单：rsync 是"服务端+客户端"双 play，nfs 是"全体装包+服务端配置+客户端挂载"三段式，备份项目是"脚本分发+定时任务"。学会一个，其余照骨架填空——这也是"先想清楚部署步骤，再翻译成任务"的最好练习。

### 剧本编写常见错误

1. 剧本语法规范是否符合（空格、冒号、短横线）
2. 剧本中模块使用是否正确
3. 剧本中**一个 `name` 标识下面只能写一个模块任务信息**
4. 剧本中尽量不要大量使用 `shell` 模块

> **注意：** 第 3 条是新手最容易犯的错误 —— 一个 `- name:` 下面挂两个模块，YAML 解析会直接报错。第 4 条是因为 `shell` 模块不具备幂等性，大量使用会导致剧本每次执行都产生变更。

### rsync 服务剧本编写

以下是一份完整的服务端 + 客户端一体化部署剧本：

```yaml
- hosts: rsync_server
  tasks:
    - name: 01-install rsync
      yum: name=rsync state=installed
    - name: 02-push conf file
      copy: src=/etc/ansible/server_file/rsync_server/rsyncd.conf dest=/etc/
    - name: 03-create user
      user: name=rsync create_home=no shell=/sbin/nologin
      #shell: useradd rsync -M -s /sbin/nologin
    - name: 04-create backup dir
      file: path=/backup state=directory owner=rsync group=rsync
    - name: 05-create password file
      copy: content=rsync_backup:<your-password> dest=/etc/rsync.password mode=600
    - name: 06-start rsync server
      service: name=rsyncd state=started enabled=yes

- hosts: rsync_clients
  tasks:
    - name: 01-install rsync
      yum: name=rsync state=installed
    - name: 02-create password file
      copy: content=<your-password> dest=/etc/rsync.password mode=600
    - name: 03-create test file
      file: dest=/tmp/test.txt  state=touch
    - name: 04-check test
      shell: rsync -avz /tmp/test.txt rsync_backup@172.16.1.41::backup --password-file=/etc/rsync.password
```

> **注意：** 剧本里被注释掉的那行 `#shell: useradd rsync -M -s /sbin/nologin` 是为了说明 —— 同样的需求既可以用 `user` 模块实现，也可以图省事用 `shell` 模块直接敲命令，但前者的幂等性更好，优先用模块。

> **注意：** 涉及口令的示例一律使用 `<your-password>` 占位符，真实环境中口令应通过 `ansible-vault` 加密后传入（见本篇第八节），不要明文写在剧本或清单里。

这套剧本体现的编排思想值得记住：**顺序即依赖**——先装软件，再推配置，然后建用户和目录，最后起服务。把"起服务"放在推配置之后，服务首次启动读到的就是最终配置，省掉"先起服务、再改配置、还得补一次重启"的返工。配置任务挂上 notify 后，重复执行时配置没变就不重启，整条链路天然幂等，敲一遍就知道这个顺序不能乱。

生产执行前再过一遍检查清单：目标机磁盘空间够不够、服务端口有没有被占用、现有配置有没有备份（`copy` 的 `backup=yes`）、出问题后的回滚剧本是否就绪。一键部署省的是时间，检查清单保的是命。变更窗口选业务低峰，开跑前同步影响范围——自动化没有降低沟通义务，只是提高了执行速度。

## 如何配置主机清单

主机清单文件是 `/etc/ansible/hosts`，共有五种配置方式。

### 第一种方式：分组配置主机信息

```ini
[web]
172.16.1.7
172.16.1.8
172.16.1.9

[data]
172.16.1.31
172.16.1.41
```

操作过程：

```console
[root@m01 ansible-playbook]# ansible data -a "hostname"
172.16.1.31 | CHANGED | rc=0 >>
nfs01

172.16.1.41 | CHANGED | rc=0 >>
backup

[root@m01 ansible-playbook]# ansible web -a "hostname"
172.16.1.7 | CHANGED | rc=0 >>
web01
```

### 第二种方式：主机名符号匹配配置

```ini
[web]
172.16.1.[7:9]
```

```ini
[web]
web[01:03]
```

### 第三种方式：跟上非标准远程端口

```ini
[web]
web01:52113
172.16.1.7:52113
```

### 第四种方式：主机使用特殊的变量

```ini
[web]
172.16.1.7 ansible_ssh_port=52113 ansible_ssh_user=root ansible_ssh_pass=<your-password>
```

```ini
[web]
web01 ansible_ssh_host=172.16.1.7 ansible_ssh_port=52113 ansible_ssh_user=root ansible_ssh_pass=<your-password>
```

> **注意：** 用 `ansible_ssh_host` 可以给主机起别名（如 `web01`），实际连接时再去解析成真实 IP。把密码写进清单只建议用于测试环境——生产上栽过"清单连仓库一起提交、密码全组可见"的跟头，必须改用密钥认证或 ansible-vault 加密变量。

### 第五种方式：主机组名嵌入配置

**嵌入子组信息：**

```ini
[rsync:children]    --- 嵌入子组信息
rsync_server
rsync_client

[rsync_server]
172.16.1.41

[rsync_client]
172.16.1.31
172.16.1.7
```

分组与子组的价值在编排时才显现：`rsync_server` 与 `rsync_client` 分开写各自的任务，`rsync` 大组用来做全体动作（比如统一装软件包）；children 组还能继续被更大的组嵌套，一层层拼出完整架构，"一键部署整套备份体系"就靠这条。

**嵌入式变量信息：**

```ini
[web:vars]         --- 嵌入式变量信息
ansible_ssh_host=172.16.1.7
ansible_ssh_port=52113
ansible_ssh_user=root
ansible_ssh_pass=<your-password>

[web]
web01
```

清单内联变量适合一两条；超过三条就该搬到 `host_vars/主机名` 文件——清单负责"有哪些机器"，变量文件负责"机器长什么样"，两边混着写迟早对不上账。

### 主机清单官方配置文档

完整的配置方法参见 ansible 官方文档 user_guide 中的 intro_inventory 一节（Building Inventories）。

### 辨析：静态清单与动态清单

静态 INI / YAML 文件适合机器数稳定的环境，一目了然、便于 review。云上弹性伸缩的机器频繁上下线，静态清单必然过期，这时用动态清单插件（AWS / Azure / 自定义脚本）按标签实时拉取；自建机房对接 CMDB 也是动态清单的思路。起步阶段静态清单加手动维护完全够用，主机数上到几百台、生命周期小于一天再考虑演进。

## roles 目录结构：让剧本规范化

随着剧本越写越多，会暴露几个典型问题：

1. 目录结构不够规范；
2. 编写好的任务如何重复调用；
3. 服务端配置文件改动后，客户端参数信息不能自动变化；
4. 汇总剧本中没有显示主机角色信息；
5. 一个剧本内容过多，不容易阅读，需要拆分。

roles 目录结构正是为解决这些问题而设计的标准化方案。

### 原理解析：role 的自动加载机制

role 是一个有约定目录结构的文件夹。playbook 中通过 `roles:` 引用角色名时，Ansible 会在角色目录中按固定规则自动加载文件：

1. 先加载 `defaults/main.yml`（默认变量，优先级最低）与 `vars/main.yml`（角色变量，优先级高）；
2. 如果存在 `meta/main.yml` 且声明了依赖，先递归加载依赖角色；
3. 执行 `tasks/main.yml` 中的任务，任务执行过程中 `handlers/main.yml` 被加载待命；
4. 任务中引用 `files/` 或 `templates/` 下的文件时，只写文件名即可，Ansible 会自动在角色目录内查找。

正是这套自动查找规则，让 `copy: src=exports` 这样的简写成为可能，也是角色可以跨剧本复用的根本原因。

### 标准目录结构

进入 roles 目录，为每个服务创建角色目录，并在角色下建立标准子目录：

```console
$ cd /etc/ansible/roles
$ mkdir {rsync,nfs}
$ mkdir {nfs,rsync}/{vars,tasks,templates,handlers,files}
$ tree
.
├── nfs
│   ├── files       # 保存需要分发的文件
│   ├── handlers    # 保存触发器配置信息
│   ├── tasks       # 保存要执行的任务文件
│   ├── templates   # 保存需要分发的模板文件，模板中可以设置变量
│   └── vars        # 保存变量信息
└── rsync
    ├── files
    ├── handlers
    ├── tasks
    ├── templates
    └── vars
```

完整的标准角色目录还包括 `defaults`、`meta` 与可选的 `tests`：

```text
roles/
└── nfs/
    ├── defaults/       # 默认变量，优先级最低，允许被覆盖
    │   └── main.yml
    ├── files/          # 静态文件，copy 模块直接引用
    │   └── exports
    ├── handlers/       # 触发器
    │   └── main.yml
    ├── meta/           # 角色元数据：作者、平台、依赖角色
    │   └── main.yml
    ├── tasks/          # 任务入口，按功能拆分成多个文件
    │   ├── main.yml
    │   ├── copy_info.yml
    │   └── boot_server.yml
    ├── templates/      # Jinja2 模板，template 模块引用
    │   └── exports.j2
    └── vars/           # 角色变量，优先级高，不建议被覆盖
        └── main.yml
```

各子目录的职责：

| 子目录 | 作用 | 加载方式 |
| --- | --- | --- |
| `tasks` | 存放该角色要执行的任务，`main.yml` 为入口 | 引用角色时自动加载 |
| `handlers` | 存放该角色的触发器 | 自动加载 |
| `vars` | 存放该角色的变量，优先级高于 play vars | 自动加载 |
| `defaults` | 存放默认变量，优先级最低，便于被覆盖 | 自动加载 |
| `files` | 存放需要分发的静态文件 | `copy`/`script` 等模块按文件名自动查找 |
| `templates` | 存放需要分发的模板文件（可嵌入变量） | `template` 模块按文件名自动查找 |
| `meta` | 声明角色依赖、支持的系统平台、作者信息 | 自动加载，依赖角色先执行 |

> **注意：** `vars/` 与 `defaults/` 都放变量，区别在优先级：`defaults/main.yml` 是最低优先级，设计为"可以被使用者覆盖的默认值"；`vars/main.yml` 优先级很高，适合放角色内部固定、不希望被随意改动的值。

分配原则落实到实战：版本号、监听端口、安装路径这类"使用者大概率要改"的值放 `defaults`；角色内部分支逻辑、固定依赖关系放 `vars`。规范做好后，调用方只看 `defaults/main.yml` 就知道这个角色能配什么——它就是角色的配置文档。优先级记法也顺带记一句：离主机越近越优先（host_vars > group_vars/组 > group_vars/all > role defaults），extra-vars 永远压轴。

### 编写各子目录文件

**tasks/main.yml**：作为入口，把任务拆分成多个文件再用 `include_tasks` 组合，解决"一个剧本内容过多"的问题：

```yaml
- include_tasks: copy_info.yml
- include_tasks: create_dir.yml
- include_tasks: boot_server.yml
```

**tasks/copy_info.yml**：

```yaml
- name: 01-copy conf file
  copy:
    src: exports
    dest: /etc
  notify: restart nfs server
```

**tasks/create_dir.yml**：

```yaml
- name: 02-create data dir
  file:
    path: "{{ Data_dir }}"
    state: directory
    owner: nfsnobody
    group: nfsnobody
```

**tasks/boot_server.yml**：

```yaml
- name: 03-boot server
  service:
    name: "{{ item }}"
    state: started
    enabled: yes
  with_items:
    - rpcbind
    - nfs
```

**vars/main.yml**：集中管理变量，实现"改一处、全局生效"：

```console
$ vim main.yml
Data_dir: /data
```

**files/**：存放 exports 等分发文件：

```console
$ ll
total 4
-rw-r--r-- 1 root root 29 May 17 15:23 exports
```

**handlers/main.yml**：

```yaml
- name: restart nfs server
  service:
    name: nfs
    state: restarted
```

编写完成后，角色目录的结构如下：

```console
$ tree
.
├── files
│   └── exports
├── handlers
│   └── main.yml
├── tasks
│   └── main.yml
├── templates
└── vars
    └── main.yml
```

**meta/main.yml**（可选）：声明角色依赖与适用平台，被依赖的角色会先于当前角色执行：

```yaml
galaxy_info:
  author: ops
  description: deploy nfs server
  license: MIT
  min_ansible_version: "2.9"
  platforms:
    - name: EL
      versions:
        - "7"
        - "8"
        - "9"
dependencies:
  - role: common
```

多个角色共用一套逻辑（时区、内核参数、基础软件包）时，抽成 common 角色让业务角色依赖：在 `meta/main.yml` 的 `dependencies` 里声明，被依赖角色先执行。公共角色的边界要守住——只放"所有机器都该有"的东西，一旦出现"只有部分机器需要"，就拆出去按组下发。

### role 的四种调用方式

**方式一：roles 列表（最常用）**，角色按列表顺序执行：

```yaml
- hosts: nfs_server
  roles:
    - nfs-server
    - common
```

**方式二：调用时传参**，参数作为角色变量传入，优先级高于角色内的 `vars/main.yml`：

```yaml
- hosts: nfs_server
  roles:
    - role: nfs
      Data_dir: /data
```

**方式三：条件调用**，结合 `when` 让同一剧本适配不同角色：

```yaml
- hosts: all
  roles:
    - role: nfs
      when: "'nfs_server' in group_names"
    - role: common
```

**方式四：任务级动态导入**，用 `include_role` 在任务流中按需加载：

```yaml
- hosts: all
  tasks:
    - name: include nfs role dynamically
      include_role:
        name: nfs
      vars:
        Data_dir: /data
```

> **注意：** 角色目录名与 `roles:` 中引用的名字要对应（目录名是什么就写什么，例如目录 `nfs` 就写 `- nfs`）；`copy` 的 `src` 写文件名时，Ansible 会自动在角色内的 `files/` 目录中查找。`import_role` 与 `include_role` 的区别同 `import_tasks` 与 `include_tasks`：前者静态导入、标签与条件传递给角色内任务；后者动态加载、循环调用更方便。

标签也可以打在 role 引用上（`role: nfs` 配 `tags: storage`），整角色的任务一起被选中。标签命名按"服务 + 阶段"两级走（如 `nfs-config`、`nfs-package`），`--tags "nfs,config"` 这样的组合筛选才有意义；杂乱的单层标签到后期基本等于没有标签。

### 辨析：roles 与平铺剧本的取舍

角色化有成本：建目录、拆文件、抽变量，三五个任务的小服务直接平铺剧本更快。角色化在两种情况下回本：同一套部署要出现在两个以上环境或清单；团队协作需要"每人认领一个服务目录"的边界。判断标准就一条——这套部署会不会被第二次使用？会，就值得抽成 role。

## playbook 组织与分层

单个剧本能跑起来只是第一步，工程化要求"入口清晰、变量集中、角色复用"。推荐的目录布局：

```text
/etc/ansible/
├── ansible.cfg            # 主配置：清单路径、角色目录、并发数等
├── hosts                   # 主机清单（也可用 YAML 动态清单）
├── site.yml                # 总入口 playbook
├── group_vars/             # 组变量目录
│   ├── all                 # 对所有主机生效
│   ├── web                 # 对 web 组生效
│   └── web:vars            # 目录写法（二选一）
├── host_vars/             # 主机变量目录
│   └── web01
├── roles/                  # 角色目录
│   ├── common/
│   ├── nfs/
│   └── rsync/
└── ansible-playbook/       # 独立剧本、临时实验目录
```

分层原则：

1. **site.yml 只描述结构**：哪些主机组、扮演哪些角色，不写具体任务；
2. **任务细节全部下沉到 roles**：一个角色干一件事，角色内用 `include_tasks` 拆分；
3. **变量分层放置**：全局变量放 `group_vars/all`，组差异放 `group_vars/组名`，单机差异放 `host_vars/主机名`，角色内部变量放角色 `defaults`/`vars`；
4. **按环境隔离**：多环境（生产/测试）用不同清单文件，如 `ansible-playbook -i inventories/production site.yml`。

"入口只描述结构"还有一层价值：入口即文档。新人看 site.yml 就知道整套环境有哪些角色、部署顺序是什么，这比 Wiki 可靠——剧本和文档永远是同一份。另外 play 在入口文件里的顺序就是部署顺序：公共初始化放最前、核心服务居中、验证任务殿后，跨 play 的依赖靠顺序保证，不靠运气。

site.yml 示例：

```yaml
- hosts: nfs_server
  roles:
    - nfs

- hosts: rsync_server
  roles:
    - rsync

- hosts: rsync_clients
  roles:
    - rsync-client

- hosts: web
  roles:
    - common
    - nginx
```

配合分组执行与语法检查：

```console
# 只对 nfs 相关主机执行
$ ansible-playbook site.yml --limit nfs

# 语法检查（不实际执行）
$ ansible-playbook site.yml --syntax-check

# 预演模式：只报告会改什么，不真正执行
$ ansible-playbook site.yml --check --diff

# 列出所有会被执行的任务与标签
$ ansible-playbook site.yml --list-tasks --list-tags
```

RECAP 汇总（ok / changed / failed / unreachable 计数）是每次执行后的最后一道检查：changed 属正常，出现 failed 或 unreachable 必须处理完再继续。把 RECAP 输出归档，就是最简单的部署记录。

> **注意：** 主剧本（site.yml）通过 `roles:` 声明主机角色，实现"角色清晰、任务复用、变量统一"的标准化剧本工程；角色目录名与 `roles:` 中引用的名字要对应。

## ansible-galaxy：角色的初始化与分发

`ansible-galaxy` 是官方的角色管理工具，常用操作如下：

| 命令 | 作用 |
| --- | --- |
| `ansible-galaxy init nfs` | 按标准结构生成一个角色骨架 |
| `ansible-galaxy install geerlingguy.nginx` | 从 Ansible Galaxy 社区安装角色 |
| `ansible-galaxy install -r requirements.yml` | 按依赖清单批量安装角色 |
| `ansible-galaxy list` | 列出已安装的角色 |
| `ansible-galaxy remove nfs` | 删除已安装的角色 |
| `ansible-galaxy collection install community.general` | 安装扩展集合 |

生成的角色骨架自带全部标准子目录与 README：

```console
$ ansible-galaxy init nfs
- nfs was created successfully
$ tree nfs
nfs
├── defaults
│   └── main.yml
├── files
├── handlers
│   └── main.yml
├── meta
│   └── main.yml
├── README.md
├── tasks
│   └── main.yml
├── templates
├── tests
└── vars
    └── main.yml
```

用 `requirements.yml` 管理角色依赖，团队协作时一份清单即可复现整套环境：

```yaml
# requirements.yml
- src: geerlingguy.nginx
  version: 3.1.2
- src: git+https://example.com/ops/internal-role.git
  name: internal-role
  scm: git
```

```console
$ ansible-galaxy install -r requirements.yml
```

用社区角色前先读它的 README 与 `defaults/main.yml`，重点核对它管理哪些文件、会不会覆盖你已有的配置；生产环境更倾向 fork 一份内化，避免上游变更直接打进生产。内部角色放 Git 仓库，`requirements.yml` 按 tag 引用，升级走"打新 tag → 测试环境验证 → 生产切换"三步，不要直接追 main 分支。

## ansible-vault：加密敏感数据

剧本中不可避免地要出现数据库口令、服务密码等敏感信息，直接明文提交到代码仓库等于泄露。`ansible-vault` 用 AES-256 对称加密保护变量文件，常用操作：

| 命令 | 作用 |
| --- | --- |
| `ansible-vault create secrets.yml` | 创建加密文件（编辑前要求输入密码） |
| `ansible-vault edit secrets.yml` | 编辑加密文件 |
| `ansible-vault view secrets.yml` | 查看加密文件内容 |
| `ansible-vault encrypt secrets.yml` | 把已有明文文件加密 |
| `ansible-vault decrypt secrets.yml` | 解密为明文文件 |
| `ansible-vault rekey secrets.yml` | 更换加密密码 |
| `ansible-vault encrypt_string 'mypassword' --name 'db_password'` | 加密单条字符串并输出 YAML |

加密文件内容与普通 YAML 文件写法完全一致，例如 `group_vars/all/secrets.yml`：

```yaml
db_password: <your-password>
rsync_password: <your-password>
```

playbook 中正常引用变量即可，执行时提供 vault 密码：

```console
# 交互式输入 vault 密码
$ ansible-playbook site.yml --ask-vault-pass

# 密码放在文件（文件权限设为 600）
$ ansible-playbook site.yml --vault-password-file ~/.vault_pass

# 多环境多密钥
$ ansible-playbook site.yml --vault-id dev@~/.vault_pass_dev --vault-id prod@~/.vault_pass_prod
```

加密后的文件可以安全提交到 Git 仓库，团队共享一份密文，各自保管 vault 密码：

```text
$ANSIBLE_VAULT;1.1;AES256
6261636b75705f7365727665722e636f6d2e6578616d706c65
```

> **注意：** vault 密码文件本身不要提交到仓库；忘记 vault 密码无法恢复数据，务必妥善备份。把单条口令嵌入普通 YAML 时，用 `encrypt_string` 生成 `vault |` 格式的密文块即可。

vault 密码本身的管理有套路：按环境拆密码（`--vault-id` 每环境一把），密码文件权限 600、放密码管理器或加密盘而不是项目目录；人员离职时 `rekey` 全部加密文件换新密码。CI 上跑剧本不能交互输密码，用 `--vault-password-file` 指向 CI 侧受控的密钥文件，配合 `no_log: true` 保证口令不进日志。

## 企业级剧本管理实践

1. **一切皆有入口**：新环境初始化只跑 `ansible-playbook -i <inventory> site.yml` 一条命令，入口即文档。
2. **角色单一职责**：一个角色对应一个服务（nginx、nfs、rsync），跨服务的公共逻辑放 common 角色。
3. **变量集中管理**：密码进 vault，环境差异进 group_vars/host_vars，角色默认值进 defaults。
4. **先 --check 再执行**：对生产环境先 `--check --diff` 预演，确认变更符合预期再实跑。
5. **用 tags 分层运维**：日常只部署配置打 `config` 标签、升级软件打 `package` 标签，避免全量重跑。
6. **剧本纳入版本管理**：Git 管理 playbook 与 roles，变更走评审，保留历史可回滚。
7. **权限最小化**：连接账号按需授权，`become` 提权只用于必要任务；生产清单中不写任何口令。

这七条不是并列的口号，而是有依赖关系的闭环：入口与角色是结构，变量与加密是数据，check 与 tags 是执行纪律，版本管理把前面全部兜住。新团队照此落地，两三个月就能形成稳定节奏。

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `ERROR! the role 'nfs' was not found` | 角色目录位置不对或名字写错 | `ansible-config dump \| grep roles_path`；`ls /etc/ansible/roles` | 确认角色目录在 roles_path 下，且引用名与目录名一致 |
| `Could not find file ... exports` | copy 的 src 路径写错，未放角色 files 目录 | `ls roles/nfs/files/` | 静态分发文件放 `files/`，src 只写文件名 |
| 变量改动了不生效 | 变量放在了优先级更低的位置（如 defaults 被 vars 覆盖） | `ansible all -m debug -a "var=Data_dir"` | 按优先级表排查来源，统一变量放置层次 |
| `Attempting to decrypt but no vault secrets found` | 执行时没带 vault 密码 | `ansible-playbook site.yml --ask-vault-pass` | 加 `--ask-vault-pass` 或 `--vault-password-file` |
| 剧本重复执行仍显示 changed | 用了 shell/command 做有副作用的操作，未声明 changed_when | `ansible-playbook site.yml --diff` | 改用幂等模块，或 `changed_when: false` |
| 角色内 notify 的 handler 不触发 | handler 写在角色外或名称不一致 | `ansible-playbook site.yml --list-tasks` | handler 放角色 `handlers/main.yml`，名称与 notify 一致 |

role 的调试三板斧值得单独记：`--syntax-check` 先过语法；`--list-tasks` 确认角色被正确展开、任务没有丢；变量不生效时 `ansible 目标 -m debug -a "var=变量名"` 直接看解析值。还有一个隐蔽问题出在 include_tasks 的动态加载上——变量求值推迟到运行时，`--list-tasks` 看到的与实际执行可能有出入，排查时以 `-vv` 输出为准。

## 现代环境补充

1. **连接变量改名**：清单中的 `ansible_ssh_user`、`ansible_ssh_pass`、`ansible_ssh_host`、`ansible_ssh_port` 是旧名称，新版本统一为 `ansible_user`、`ansible_password`、`ansible_host`、`ansible_port`；旧写法仍兼容但会提示废弃，新剧本一律用新名称。
2. **系统发行版变化**：CentOS 7 已于 2024 年 6 月 EOL，新环境建议 Rocky Linux / AlmaLinux / CentOS Stream。`yum` 模块仍可用，等价的现代写法是 `dnf` 模块；`service` 模块在 systemd 系统上可直接用 `systemd` 模块替代。
3. **ansible-core 与集合**：新版本拆分为 ansible-core（引擎）与 collections（模块集合），部分模块需先 `ansible-galaxy collection install` 安装；Galaxy 网站的角色版本要与 ansible-core 版本匹配。
4. **动态清单**：云环境与虚拟化环境主机频繁变化，静态 INI 清单可用脚本或 YAML 动态清单（inventory plugin）替代，按标签自动分组。
5. **平台化演进**：大规模团队可在 AWX / Ansible Controller 之上做调度、权限与审计，本地剧本（playbook + roles + vault）依然是底座。

## 自测题

1. roles 目录中 `vars/main.yml` 与 `defaults/main.yml` 都放变量，二者有什么区别？
2. 角色里 `copy` 模块的 `src` 只写了文件名，Ansible 去哪里找这个文件？
3. 把剧本里的数据库口令安全提交到 Git 仓库，有哪两种做法？
4. `ansible-playbook site.yml --check --diff` 是什么效果？适合什么场景？
5. `meta/main.yml` 中的 `dependencies` 有什么作用？

> **答案：**
> 1. `defaults/main.yml` 优先级最低，是"允许被调用方覆盖的默认值"；`vars/main.yml` 优先级很高，放角色内部固定、不希望被覆盖的值。
> 2. 自动在角色的 `files/` 子目录中查找；如果是模板文件则查找 `templates/` 子目录。
> 3. 用 `ansible-vault encrypt` 加密整个变量文件，或 `ansible-vault encrypt_string` 只加密单条口令，执行时通过 `--ask-vault-pass` / `--vault-password-file` 提供密码。
> 4. `--check` 预演模式不真正执行、只报告将要发生的变更，`--diff` 显示文件级差异；适合生产变更前的评估，但不是所有模块都支持 check。
> 5. 声明当前角色依赖的其他角色，被依赖的角色会先执行，用于抽取公共逻辑（如先装 common 角色再装业务角色）。

## 小结

1. 剧本是"永久化"的批量管理手段（类似脚本），ad-hoc 是"临时性"的（类似命令）；把成熟的部署流程沉淀成剧本才有复用价值。
2. 写剧本四类常见错误：语法不规范、模块用错、一个 `name` 下挂多个模块、滥用 `shell` 破坏幂等性。
3. 一个剧本里可以有多个 `- hosts:` 段落，分别面向服务端组和客户端组；rsync 部署顺序是：装软件 → 推配置 → 建用户 → 建目录 → 建密码文件 → 启动服务。
4. 主机清单五种写法：分组、`[7:9]` 符号匹配、`主机:端口` 非标准端口、`ansible_ssh_*` 特殊变量、`:children` / `:vars` 组嵌入。
5. `ansible_ssh_host` 可为主机起别名，`[组名:children]` 可以把多个子组合并成一个大组，方便一条命令覆盖整套架构。
6. roles 用 `tasks`、`handlers`、`vars`、`defaults`、`files`、`templates`、`meta` 七类标准子目录规范剧本结构，`tasks/main.yml` 是自动加载的入口，`meta/main.yml` 管理角色依赖。
7. 角色调用有四种方式：roles 列表、传参、条件调用、`include_role` 动态导入。
8. playbook 分层靠 site.yml + group_vars/host_vars + roles：入口只描述结构，变量分层放置，角色单一职责。
9. `ansible-galaxy` 负责角色的初始化与分发（init/install/requirements），`ansible-vault` 负责敏感数据加密（create/edit/encrypt_string/--ask-vault-pass），二者是团队协作与安全生产的标配。
10. 生产剧本的三道保险：`--check --diff` 预演、`--limit` 灰度、vault 加密口令；三道都齐了才谈得上安全交付。
11. 把 ad-hoc 沉淀成 role 五步走：手敲命令按顺序整理成 tasks → 参数抽进 defaults → 分发文件挪进 files/templates → 重启动作改成 notify + handlers → 连跑两遍确认第二遍全 ok。
