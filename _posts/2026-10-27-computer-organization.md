## 一、计算机概论：硬件五部件与软件三层
{: .sec-sum}

### 1.1 一句话定义

> **一句话定义**：计算机 = **运算器 + 控制器 + 存储器 + 输入设备 + 输出设备** 五部件组成的硬件系统，硬件只是骨架，真正让机器"干活"的是跑在其上的软件。
{: .callout-card}

五部件里，**运算器和控制器合称 CPU**（中央处理器），是整个系统的指挥中枢与加工车间；存储器负责存程序和数据；输入/输出设备负责与外界交换信息。

> **知识卡片**：五部件的分工与"谁最忙"
{: .callout-key}

| 部件 | 别称 | 核心职责 | 典型硬件 |
| --- | --- | --- | --- |
| 运算器 | ALU | 做算术/逻辑运算，保存操作数与中间结果 | CPU 内的 ALU、通用寄存器组、PSW |
| 控制器 | CU | 取指、译码、发出控制信号、处理中断与时序 | 指令译码器、PC、IR、MAR、MDR |
| 存储器 | 主存 | 存放当前正在执行的程序与数据 | RAM、ROM、Cache、磁盘 |
| 输入设备 | — | 把外部信息送入主机 | 键盘、鼠标、网卡、扫描仪 |
| 输出设备 | — | 把主机中的信息送出去 | 显示器、打印机、磁盘 |

### 1.2 计算机如何执行程序：取指—译码—执行的死循环

> **一句话定义**：CPU 从主存里**按顺序**取出指令 → 译码成控制信号 → 执行 → 结果写回，然后回到第一步，循环直到程序结束。
{: .callout-card}

> **原理**：为什么程序能"一条条自己跑下去"
{: .callout-why}

程序本质是指令的序列，保存在主存储器中。CPU 内部有一个**程序计数器 PC** 永远指向"下一条要执行的指令地址"，所以只要 PC 能被自动加一，指令流就能自动推进；遇到转移指令时，把 PC 改写成新地址即可实现跳转。整个过程不需要程序员干预，这就是"程序自动执行"。

> **注意**：CPU 自己并不理解高级语言，它只认**机器码**。所谓"运行程序"，实际是 CPU 在不停地搬运和解释二进制指令。
{: .callout-note}

### 1.3 软件的三个层次

> **一句话定义**：软件分**系统软件**（管资源）、**通用软件**（通用应用）、**用户程序**（用户业务代码）三层，越靠下越贴近硬件、越依赖平台。
{: .callout-card}

| 层次 | 组成 | 举例 | 是否依赖具体硬件 |
| --- | --- | --- | --- |
| 系统软件 | 操作系统、数据库管理系统 DBMS、语言处理程序 | Linux、MySQL、gcc | 强依赖 |
| 通用软件 | 应用软件、服务性程序 | 浏览器、SSH 服务、Nginx | 中等 |
| 用户程序 | 用户自编业务代码 | 你写的脚本 | 依赖最少 |

> **辨析**：编译器属于哪一层
{: .callout-bianxi}

**编译程序（编译器）属于系统软件中的语言处理程序**，不是用户程序。常见误解是"编译器是开发工具所以是应用软件"——但 gcc 输出的目标代码是**直接面向机器指令**的，其行为必须精确到硬件语义，这正是系统软件的定义。同时编译器又不参与运行时资源管理，所以它独立于操作系统之外，是"语言处理程序"这一独立类别。

### 1.4 编译程序：从高级语言到机器码

> **一句话定义**：编译程序把**源代码**翻译成**目标代码**（机器码或汇编），是"人写的语言"与"机器能懂的二进制"之间唯一的翻译官。
{: .callout-card}

> **实际示例**：用 gcc 看看翻译链条
{: .callout-prac}

```bash
# 写一个 C 程序，观察从"人类语言"到"机器码"的四级跳跃
cat > hello.c <<'EOF'
#include <stdio.h>
int main(void) {
    int a = 1, b = 2;
    printf("%d\n", a + b);   // 编译器会把这一行变成若干条机器指令
    return 0;
}
EOF

# 1) 预处理：展开 #include 头文件
gcc -E hello.c -o hello.i

# 2) 编译：把 C 翻译成汇编（-S 只停在汇编这一步）
gcc -S hello.c -o hello.s

# 3) 汇编：把汇编翻译成目标文件（.o，里面是 ELF 格式的机器码）
gcc -c hello.c -o hello.o

# 4) 链接：把目标文件和 libc 库链接成可执行文件
gcc hello.c -o hello

# 反汇编，看看 CPU 真正要执行的那些机器指令
objdump -d hello | sed -n '/<main>:/,/ret/p' | head -20
```

> **坑位**：手写汇编时容易踩的三个坑
{: .callout-pit}

- **符号地址与重定位**：多个 `.o` 链接时，每个目标文件里的函数地址都是"从 0 开始算"的相对地址，链接器要按最终加载位置做**重定位**，直接把 `.o` 反汇编看到的地址在可执行文件里会变。
- **对齐（alignment）**：x86-64 要求变量按自然边界对齐，否则编译器会插入填充字节，用 `objdump -d` 看对齐槽时容易误判指令边界。
- **链接与加载不是一回事**：链接产出的是磁盘上的 ELF 文件，真正映射到虚拟地址空间是**加载器（loader）**在进程启动时做的。

## 二、数据表示：进制、非数值编码与带符号数
{: .sec-know}

这一节回答一个问题：**CPU 眼里的"数据"长什么样**。所有上层的高级数据结构，最终都要被翻译成这一节的几种基本形态。

### 2.1 为什么是二进制：高低电平

> **一句话定义**：计算机采用二进制，是因为**电子开关只有两个稳定状态**（高电平 / 低电平），用它表示信息在物理上最简单、最抗干扰、最易实现。
{: .callout-card}

> **原理**：为什么不用十进制存数据
{: .callout-why}

若用十进制表示一位数字，硬件需要能区分 10 个稳定状态，这要么需要 10 根线 + 复杂译码，要么需要用模拟量（电压高低代表 0~9），后者极易受噪声与温漂影响。二进制只需判断"有电/没电"，两个状态之间留足阈值就能抗住干扰；而且**布尔代数天然对应逻辑运算**，让开关电路可以直接实现与/或/非。这就是"与非门"能搭出整个计算机的物理基础。

### 2.2 进制转换

> **一句话定义**：二进制是"底"，八进制和十六进制只是**打包显示**——3 位二进制凑成 1 位八进制，4 位二进制凑成 1 位十六进制，数值本身完全没变。
{: .callout-card}

> **实际示例**：转换的四种操作
{: .callout-prac}

```bash
# 1) 二进制 -> 八进制：3 位一组（8421 权重 4/2/1），不足补 0
printf "%o\n" "$((2#10110))"     # 26  —— 010 110 -> 010=2, 110=6

# 2) 二进制 -> 十六进制：4 位一组（8421 权重 8/4/2/1），不足补 0
printf "%x\n" "$((2#10110))"     # 16  —— 0001 0110 -> 1, 6

# 3) 十进制 -> 二进制：整数部分"除 2 倒取余"，小数部分"乘 2 正取整"
python3 - <<'PY'
n = 22
bits = []
while n:                       # 整数部分：除 p 倒取余
    bits.append(str(n % 2))
    n //= 2
print('整数部分:', ''.join(reversed(bits)))

x, out = 0.625, []
for _ in range(5):              # 小数部分：乘 p 正取整
    x *= 2
    out.append('1' if x >= 1 else '0')
    x -= int(x)
print('小数部分:', ''.join(out))
PY

# 4) p 进制 -> 十进制：按位权展开 10110(2) = 1x2^4+0x2^3+1x2^2+1x2^1+0x2^0
python3 -c "print(int('10110', 2))"   # 22
```

> **坑位**：为什么 Linux 里习惯用十六进制
{: .callout-pit}

- **位运算不受位宽影响**：`0xFF & 0x0F` 在 Python 里是 `0x0F`，但在 C 里 `0xFF & 0x0F` 的结果取决于 `int` 宽度——`0xFF` 若被提升为 32 位有符号整数，就变成了 `-1`，结果仍是 `0x0F` 是因为另一侧也被提升，但 `0xFF == 255` 在 C 里**为假**（因为比较时也做了整型提升）。这是 C 语言最经典的坑之一。
- **八进制陷阱**：C 语言里以 `0` 开头的字面量是**八进制**，`0644` 是十进制 420，而 `644` 是 644，写错一位就全错。Shell 里同样如此，`chmod 0644` 才是对的。
- **进制只是显示**：Python 3 里 `0o17`、`0x1F`、`0b101` 是同一套整数的不同字面量写法，`0o17 == 0x1F == 15` 全为真。

### 2.3 非数值数据编码：从 ASCII 到 UTF-8

> **一句话定义**：非数值数据（文字、符号）要变成计算机里的比特，必须先约定"字符 ↔ 比特"的映射规则，这就是**字符编码**；ASCII 是最早的国际标准，Unicode 是统一规范，UTF-8 是 Unicode 最主流的落地编码。
{: .callout-card}

> **知识卡片**：四种编码的定位
{: .callout-key}

| 编码 | 位宽 | 中文占字节 | 定位与代价 |
| --- | --- | --- | --- |
| ASCII | 7 位（存 1 字节） | 不支持 | 0~127，`'A'=65`、`'a'=97`、`'0'=48`；只覆盖英文与控制符 |
| GB2312 | 1~2 字节 | 2 字节 | 保留 0~127 的 ASCII 区，中文用两个字节；共 6763 个汉字 |
| GBK | 1~2 字节 | 2 字节 | 扩展 GB2312，汉字约 2.1 万；Windows 中文版常用 |
| Unicode | 规范本身 | — | **是规范不是编码**，规定了码点空间 U+0000~U+10FFFF |
| UTF-8 | 1~4 字节 | 3 字节 | Unicode 的变长实现，兼容 ASCII，网页与 Linux 主流 |
| UTF-16 | 2 字节（BMP 内） | 2 字节 | 定长 2 字节；含增补平面字符时用代理对占 4 字节 |
| UTF-32 | 固定 4 字节 | 4 字节 | 定长 4 字节，码点与字节一一对应，浪费空间但最省心 |

> **辨析**：Unicode 和 UTF-8 到底是不是一回事
{: .callout-bianxi}

**不是**。Unicode 是一份"给每个字符发一个全球唯一编号（码点）"的**规范**，UTF-8、UTF-16、UTF-32 是把这套编号**编码成字节**的三种不同**实现方式**。同一个汉字"中"，Unicode 码点是 U+4E2D，在 UTF-8 里是 `E4 B8 AD`（3 字节），在 UTF-16 里是 `4E 2D`（2 字节），在 UTF-32 里是 `00 00 4E 2D`（4 字节）。**字符数相同，字节数不同**——这正是"同一份文本在不同编码下文件大小不同"的根源。

> **注意**：思维导图里"UTF-32 中文字符用 3 个字节"这一条需要修正
{: .callout-note}

UTF-32 是**定长 4 字节/字符**，无论中文、英文还是 emoji 都是 4 字节；中文用 3 字节的是 **UTF-8**（因为 UTF-8 属于变长编码，U+4E2D 落在三字节区间）。UTF-16 才是 2 字节（BMP 范围内），遇到不在 BMP 的字符（如部分 emoji、生僻字）会用代理对占 4 字节。

> **实际示例**：亲手验证编码的字节数
{: .callout-prac}

```bash
# Linux 下用 iconv 观察同一字符在不同编码下的字节数
printf '中' | iconv -f UTF-8    -t UTF-8    | xxd    # UTF-8   -> 3 字节: e4 b8 ad
printf '中' | iconv -f UTF-8    -t UTF-16LE | xxd    # UTF-16  -> 2 字节: 2d 4e
printf '中' | iconv -f UTF-8    -t UTF-32LE | xxd    # UTF-32  -> 4 字节: 2d 4e 00 00
printf '中' | iconv -f UTF-8    -t GBK      | xxd    # GBK    -> 2 字节: d6 d0

# 大写转小写：ASCII 码相差 32，这也是为什么 'A'+32 == 'a'
python3 -c "print(ord('A'), ord('a'), ord('a') - ord('A'))"   # 65 97 32

# 识别一个文件到底是什么编码（先造一个待检测文件）
printf '测试\n' > note.txt
file -bi note.txt
iconv -f UTF-8 -t UTF-8 note.txt >/dev/null 2>&1 && echo "合法 UTF-8" || echo "不是合法 UTF-8"
```

> **坑位**：编码相关的运维事故
{: .callout-pit}

- **BOM（字节序标记）**：Windows 记事本给 UTF-8 加 `EF BB BF`，Linux 上某些程序会把 BOM 当成文件内容的第一个字符，导致首行匹配失败。用 `sed -i '1s/^\xEF\xBB\xBF//'` 去掉。
- **GBK 文件当 UTF-8 读**：中文乱码的最常见原因。`iconv -f GBK -t UTF-8 in.txt > out.txt` 修复。
- **"ls 显示乱码"**：不是文件坏了，是终端 locale 不对。`export LANG=zh_CN.UTF-8` 或 `C.UTF-8`。

### 2.4 带符号数的表示：原码、反码、补码

> **一句话定义**：同一串比特的最高位当符号位，负数有三种编码方式——**原码**（符号位+绝对值）、**反码**（原码数值位取反）、**补码**（反码 +1），**计算机实际只用补码**。
{: .callout-card}

> **知识卡片**：以 `-1`（8 位）为例串起三种码
{: .callout-key}

| 表示法 | -1 的机器码 | 正数的码 | 规律 |
| --- | --- | --- | --- |
| 原码 | `1000 0001` | 与自身相同 | 符号位不变，其余位是绝对值的二进制 |
| 反码 | `1111 1110` | 与自身相同 | 负数在原码基础上，符号位不变、其余位取反 |
| 补码 | `1111 1111` | 与自身相同 | 在反码基础上 +1 |

> **原理**：为什么全世界都用补码
{: .callout-why}

两个原因叠加，指向同一个结论：

1. **让加法器统一承担加减法**。如果符号位只用于"辨别正负"而不参与运算，减法就得单独做一套电路，硬件复杂度翻倍。而由运算法则 `A - B = A + (-B)`，只要把负数编码成"加法器能直接加上去"的形式，机器就**只需要一个加法器**。补码正好满足这个条件：反码 +1 后的补码，恰好能让"符号位进位丢弃"的加法直接得到正确结果。
2. **零只有一种表示**。原码和反码各有 `+0`（`00000000`）和 `-0`（`10000000`）两个零，判零逻辑要特殊处理；补码把 `-0` 归一化成 `00000000`，零唯一。

> **实际示例**：用 Python 复刻一遍补码运算
{: .callout-prac}

```python
# 位宽固定 8 位，复现三种机器码的编码规则
BITS = 8
MASK = (1 << BITS) - 1

def sign_mag(n):
    """原码：最高位为符号位，其余位是绝对值的二进制"""
    sign = 1 if n < 0 else 0
    return (sign << (BITS - 1)) | (abs(n) & ((1 << (BITS - 1)) - 1))

def ones_complement(n):
    """反码：负数在原码基础上，符号位不变、其余各位取反；正数与原码相同"""
    u = sign_mag(n)
    if n >= 0:
        return u
    return u ^ ((1 << (BITS - 1)) - 1)      # 只翻转数值位（低 7 位）

def twos_complement(n):
    """补码：按位取负 —— 补码的等价定义式，边界值 -2^(n-1) 也正确"""
    return n & MASK

def from_twos(u):
    """把补码还原成有符号整数"""
    sign = 1 << (BITS - 1)
    return (u & (sign - 1)) - (u & sign)

print('原码 -1 :', format(sign_mag(-1), '08b'))        # 10000001
print('反码 -1 :', format(ones_complement(-1), '08b'))  # 11111110
print('补码 -1 :', format(twos_complement(-1), '08b'))  # 11111111
print('正数三种码相同:', format(sign_mag(5), '08b') == format(ones_complement(5), '08b') == format(twos_complement(5), '08b'))

# 关键验证：减法被"翻译"成加法
a, b = 1, 1
print('1 - 1 =', from_twos(twos_complement(a) + twos_complement(-b)))    # 0 —— 加法器直接搞定
print('5 + (-3) =', from_twos(twos_complement(5) + twos_complement(-3))) # 2
print('-128 的补码:', format(twos_complement(-128), '08b'), '-> 唯一能表示的最小负数')
# 注意：-128 的原码/反码需要 9 位才装得下，8 位下只有补码能表示它
print('-128 的原码(8位装不下,数值位被截断):', format(sign_mag(-128), '08b'))
```

> **辨析**：真值、机器码、原码、补码是四个东西
{: .callout-bianxi}

- **真值**：数学上那个带正负号的数，比如 `-1`。
- **机器码**：带符号位的二进制串，比如 `10000001`。它同时可能是原码、反码或补码中的任意一种——**光看比特串无法判断它是哪种码**，必须先约定。
- **原码/反码/补码**：同一真值的**三种编码规则**。
- 关键区别：**正数的原码 = 反码 = 补码**，三者只在负数上分叉。所以看到正数时三种码完全一样，这正是"负数难算"的根源。

> **坑位**：补码里 0x80000000 那个"最负数"
{: .callout-pit}

- 32 位补码中 `0x80000000` 表示 **-2147483648**，但你若写 `int x = 0x80000000;` 编译器会警告，因为它先按 int 解释为负数。
- **溢出判断不能只看符号位**。两个正数相加得到负数是溢出，两个负数相加得到正数也是溢出。正确做法是看**进位**：正数相加最高位无进位而次高位有进位，或反之，才算溢出。硬件里这由**溢出标志 OF** 专门记录，与符号标志 SF 是两回事。
- C 语言里 `-2147483648` 写不出来：字面量 `2147483648` 超出了 int 范围，要写 `-(2147483647) - 1`。

### 2.5 溢出与精度

> **一句话定义**：**溢出**是运算结果的位数**装不下**（超出表示范围）；**精度**是能表示的数有多细（能区分多小的间隔）。两者都会让结果"不对"，但原因不同。
{: .callout-card}

> **知识卡片**：4 位机器的边界
{: .callout-key}

| 编码 | 4 位可表示范围 | 越界例子 |
| --- | --- | --- |
| 无符号 | 0 ~ 15 | 表示 16 时溢出（4 位最大是 15） |
| 原码 | -7 ~ +7 | 8 溢出（需要 5 位） |
| 补码 | -8 ~ +7 | 8 溢出，-9 溢出 |

> **实际示例**：精度问题的真实翻车现场
{: .callout-prac}

```python
# 1) 十进制小数在二进制里无法精确表示（无限循环），只能截断
print(0.1 + 0.2)                       # 0.30000000000000004
print(f'{0.1 + 0.2:.17f}')             # 看完整二进制尾数，误差暴露无遗
print((0.1 + 0.2) == 0.3)             # False —— 写进 if 判断就出 bug

# 2) IEEE-754 双精度把十进制小数转成二进制时丢精度
print(f'{0.1:.20f}')                  # 0.10000000000000000555

# 3) float32 的坑更夸张：0.1 在 float32 里误差达到 1e-9 量级
import struct
f32 = struct.unpack('f', struct.pack('f', 0.1))[0]
print(repr(f32))                      # 0.10000000149011612

# 4) 金额永远别用浮点：整数分 + 定点，或用 decimal
from decimal import Decimal
print(Decimal('0.1') + Decimal('0.2')) # 0.3 —— 精确十进制
```

> **原理**：字长相同时，浮点数的"范围"和"精度"必须二选一
{: .callout-why}

浮点数把固定长度的比特切成两半：阶码 E 占一部分、尾数 M 占另一部分，全部位都用来表达"大小"（阶码）**或者**"精细程度"（尾数）。
- 阶码位变多 → 能表示的数更大（范围大），但尾数位变少 → 能区分的间隔变粗（精度差）。
- 尾数位变多 → 精度高，但能表示的最大数变小。

所以"字长相同的定点数与浮点数，浮点数虽然扩大了表示范围，但精度降低了"——注意 `10^3` 这种数在浮点里**也占同样多的空间**，浮点没有"大数免费"的好处。IEEE-754 规定的双精度是 1 位符号 + 11 位阶码 + 52 位尾数，共 64 位；`float` 是 1+8+23=32 位。

> **坑位**：浮点比较与累加误差
{: .callout-pit}

- **永远不要用 `==` 比较浮点**，改用误差判断：`abs(a - b) < 1e-9`。
- **累加误差会放大**：把 0.1 累加 10 次得到 0.9999999999999999，这是二进制尾数被反复截断的结果，不是"精度不够"，是"每次加法都引入一次微小误差"。
- **精度确实不够时会"差一位"**：`0.1 + 0.2 != 0.3` 是精度损失；而 `1e308 * 10` 变成 `inf` 是**范围溢出**。两者要分清。

### 2.6 定点数与浮点数

> **一句话定义**：**定点数**的小数点位置固定不变；**浮点数**的小数点位置随阶码浮动，用 `N = M × r^E` 表示（M 是尾数，r 是基数，E 是阶码）。
{: .callout-card}

> **辨析**：为什么浮点数要规定"小数点后第一位必须有效"
{: .callout-bianxi}

尾数 M 前面补零的个数是任意的——`0.156` 和 `1.56×10⁻¹` 描述的是同一个数，但前者浪费了一位有效位。IEEE-754 因此规定**尾数必须归一化**（小数点后第一位非零，二进制下等价于最高位必须为 1），并用**隐藏位（hidden bit）**把这一位省下来不用存，从而在同样字长下多榨出 1 位精度。

> **实际示例**：亲手拆一个 IEEE-754 双精度
{: .callout-prac}

```python
import struct

def decode_f64(x):
    """把 64 位双精度拆成 符号/阶码/尾数 三段"""
    (u,) = struct.unpack('Q', struct.pack('d', x))
    sign = (u >> 63) & 1
    expo = (u >> 52) & 0x7FF
    mant = u & ((1 << 52) - 1)
    # 阶码全 1 时表示 inf/nan；否则真实阶码 = expo - 1023（偏置）
    real_expo = expo - 1023 if expo != 0x7FF else None
    return sign, real_expo, mant

s, e, m = decode_f64(1560.0)
print('符号', s, '阶码', e, '尾数', m)
print('规格化后: 1.m × 2^%d' % e)      # 1.m × 2^10 —— 小数点位置由阶码决定
print('0.1 的实际存储值: %.20f' % 0.1)  # 与十进制 0.1 并不相等
```

## 三、计算机性能指标：怎么给一台机器"打分"
{: .sec-iv}

> **一句话定义**：评价计算机性能有一组**定量指标**（主频、MIPS、主存容量、数据通路带宽、机器字长）和一组**定性指标**（可靠性、可维护性、性价比），前者可测量、后者靠经验。
{: .callout-card}

> **知识卡片**：五个核心性能指标
{: .callout-key}

| 指标 | 含义 | 单位 / 口径 | 说明与陷阱 |
| --- | --- | --- | --- |
| 主频 | CPU 时钟周期频率 | Hz | 反映**节拍**快慢，但现代 CPU 一个周期可并行完成多条指令，**不等于实际速度** |
| MIPS | 每秒执行指令数 | 条/秒 | 同一台机器上才有可比性；不同指令集之间不可比 |
| 主存容量 | 主存储器能存的字数 | 字节 | 决定能装下多大的程序与数据集 |
| 数据通路带宽 | 数据总线一次并行传输的位数 | bit/次 | 越大，单位时间搬运的数据越多 |
| 机器字长 | CPU 一次能处理的二进制位数 | bit | 64 位机一次处理 8 字节，32 位机 4 字节；影响寻址空间与单次运算精度 |

> **辨析**：主频高就一定快吗
{: .callout-bianxi}

**不一定。** 主频只是"节拍"，实际性能 ≈ `主频 × 每周期可并行完成的指令数 × IPC 效率`。
- 早期 CPU 多数指令串行执行，主频几乎等于性能；
- 现代 CPU 拥有多核、乱序执行、分支预测、多发射，同一频率下的 IPC 可以差好几倍；
- 同一款 CPU，内存带宽、缓存命中率、编译优化对性能的影响常常**大于**主频差异。

所以选型时更该看**具体业务基准**（如 SPEC CPU、真实业务的压测），而不是只看 GHz 数字。

> **延伸拓展**：现代 CPU 的性能评价为什么更复杂
{: .callout-spread}

- **多核与并行度**：多核是"横向扩展"，但受**阿姆达尔定律**限制——若串行部分占比 s，加速比上限为 `1/s`。
- **能效比（TDP）**：数据中心更关心"每瓦能跑多少任务"，而非单核峰值。
- **AI 场景另立指标**：GPU/NPU 用 TOPS（每秒万亿次运算）、Tensor Core 吞吐来衡量，和 CPU 的 MIPS 完全是两套语言。

## 四、存储器体系：从存储单元到 Cache 与虚拟内存
{: .sec-know}

这一节是整门课里**最能解释"为什么程序会变快"**的部分。

### 4.1 存储单元与指针

> **一句话定义**：**存储单元**是 CPU 访问存储器的最小单位，存放一个字节，有唯一地址（通常用十六进制表示）；**指针**就是一个对象/函数所占**连续存储单元的起始地址**。
{: .callout-card}

> **知识卡片**：三个必须分清的概念
{: .callout-key}

- **存储单元**：1 字节，地址唯一，数据可被读（get）或被覆盖（delete）。
- **相邻存储单元地址相邻**：这是后面"空间局部性"和"Cache 块"能成立的前提。
- **指针**：对象/函数占用的第一个存储单元的地址。取指针 = 取起始地址；指针运算 `p+1` 前进的是**一个元素**而不是一个字节（编译器按类型大小换算）。

> **坑位**：数组指针与"字节偏移"混用
{: .callout-pit}

`int *p; p + 1` 前进的是 `sizeof(int)`（通常 4）字节，而 `char *q; q + 1` 前进 1 字节。写 `p[1]` 却以为是"下一个地址"就会算错偏移。`&arr[3] - &arr[0]` 的结果恒为 3（元素个数），不是字节数差——这是 C 里指针算术最反直觉的一点。

### 4.2 存储器分层结构与局部性原理

> **一句话定义**：把**近期常用**的数据放在"小而快"的存储器里，**近期不常用**的放在"大而慢"的地方，用**局部性原理**做预测，就能在成本几乎不变的前提下拿到接近最快存储器的速度。
{: .callout-card}

> **原理**：局部性原理——Cache 与虚拟存储器的共同理论基础
{: .callout-why}

程序访问内存存在两种规律：
- **时间局部性**：某条指令被执行后，很可能**很快再被执行**（循环、函数反复调用）；某个单元被访问后，很可能**再次被访问**。
- **空间局部性**：某单元被访问后，其**附近的单元**很可能接着被访问（顺序取指、顺序扫数组）。

有了这两条，才能"赌"未来：把当前活跃的数据块提前搬到快的地方，赌对了就是巨大加速。

> **知识卡片**：三种典型结构与它们各解决什么
{: .callout-key}

| 结构 | 解决的问题 | 谁来管理 | 典型层次 |
| --- | --- | --- | --- |
| Cache–主存 | **速度**问题 | 纯硬件 | L1 / L2 / L3 / 主存 |
| 主存–辅存 | **容量**问题 | OS + 硬件协同 | 主存 / 磁盘（虚拟内存） |
| Cache–主存–辅存 | 速度 + 容量 | 混合 | 完整层次结构 |

> **原理**：层次结构的工作流程
{: .callout-why}

**地址总线送入地址 → 先查 Cache（最快，未命中再查主存，最后才查辅存）→ 数据总线输出数据**。其中"先查谁"这件事，是硬件在流水线里并行做出来的：Cache 用**标记（tag）+ 比较器**判断命中，未命中则触发下一级访问；主存未命中则由 OS 触发**缺页中断**，把数据从磁盘调入内存。

### 4.3 Cache 地址映射：三种方式

> **一句话定义**：Cache 地址映射解决的是"**主存块 → Cache 块**"的对应关系，直接决定了命中率和硬件成本。三种方式依次是：**直接映射**（最简单、冲突最高）、**组相连**（折中，主流）、**全相连**（最灵活、最慢最贵）。
{: .callout-card}

> **知识卡片**：三种映射的地址字段拆解
{: .callout-key}

| 映射方式 | 主存地址拆分 | Cache 地址拆分 | 特点 |
| --- | --- | --- | --- |
| 直接映射 | 区号 + 块号 + 块内地址 | 块号 + 块内地址 | 硬件最简单、速度最快；**冲突率高** |
| 组相连 | 区号 + 组号 + 组内块号 + 块内地址 | 组号 + 组内块号 + 块内地址 | 组间直接、组内全相连；**冲突率低、速度较快** |
| 全相连 | 主存块号 + 块内地址 | 块号 + 块内地址 | 主存任意块可映射任意 Cache 块；需记录表遍历，**冲突率最低但最慢最贵** |

> **辨析**：直接映射的"块冲突"到底冲突什么
{: .callout-bianxi}

直接映射把主存**等分成若干区**，一个区的大小恰好等于整个 Cache，**区号直接被丢弃**（因为 Cache 只有那么多块）。于是"主存第 1 区的第 1 块"和"主存第 2 区的第 1 块"**都会去抢 Cache 里的第 1 块**——这就是冲突。表现是：两个变量恰好相差一个 Cache 容量时，程序的性能会诡异地剧烈抖动。

> **实际示例**：把地址位拆开算清楚
{: .callout-prac}

```python
def split_addr(addr, cache_blocks, block_size, ways=1):
    """把主存地址拆成 直接映射(区号/块号/块内地址) 或 组相连(区号/组号/组内块号/块内地址)"""
    block_off = block_size.bit_length() - 1          # 块内地址位数 log2(块大小)
    if ways == 1:                                     # ---- 直接映射 ----
        cache_bits = cache_blocks.bit_length() - 1    # Cache 块号位数
        return {'区号': addr >> (block_off + cache_bits),
                '块号': (addr >> block_off) & ((1 << cache_bits) - 1),
                '块内地址': addr & ((1 << block_off) - 1)}
    # ---- 组相连：组间直接映射，组内全相连 ----
    sets = cache_blocks // ways                      # 组数 = 总块数 / 路数
    set_bits = sets.bit_length() - 1                 # 组号位数
    way_bits = ways.bit_length() - 1                 # 组内块号位数（路数）
    return {'区号(tag)': addr >> (block_off + set_bits + way_bits),
            '组号': (addr >> block_off) & ((1 << set_bits) - 1),
            '组内块号': (addr >> (block_off + way_bits)) & ((1 << way_bits) - 1),
            '块内地址': addr & ((1 << block_off) - 1)}

# 例1：32 位机，Cache 16KB，块大小 16B，直接映射
# Cache 块数 = 16KB / 16B = 1024 = 2^10  ->  块内地址 4 位、块号 10 位
print('直接映射 ->', split_addr(0x1234E8F8, cache_blocks=1024, block_size=16, ways=1))
print('Cache 地址 = 主存地址低 14 位 =', hex(0x1234E8F8 & ((1 << 14) - 1)))   # 0x28f8

# 例2：Cache 64 块(2^6)、块 128B(2^7)、每 4 块一组、主存 4096 块(2^12) 字节编址
#   Cache 地址位数 = 组号 4 + 组内块号 2 + 块内地址 7 = 13 位
#   主存地址位数 = 4096 块 x 128B = 2^12 x 2^7 = 2^19 -> 19 位
#   主存区号位数 = 19 - 13 = 6 位
print('组相连 ->', split_addr(0x123456, cache_blocks=64, block_size=128, ways=4))
print('主存地址 19 位，主存区号 6 位')
```

> **坑位**：组相连里"组数"和"路数"别搞混
{: .callout-pit}

- **路数（ways）= 一组里有几块 Cache**；**组数 = Cache 总块数 ÷ 路数**。算地址时，组内块号位数为 `log2(路数)`，组号位数为 `log2(组数)`，两者之和才是 Cache 块号位数。
- 常见结论"**2 路、4 路效果最好，最常用**"是经验值：路数太少冲突多，太多则比较器多、命中判定慢。
- 真实 CPU 常见配置是 L1 8 路 32KB、L2 4~16 路 512KB~1MB、L3 8~16 路共享。

### 4.4 Cache 的替换策略与更新策略

> **一句话定义**：**替换策略**解决"Cache 满了扔哪一块"（FIFO、LRU）；**更新策略**解决"改了 Cache 里的数据，什么时候同步回主存"（写直达 / 写回 + 脏位）。
{: .callout-card}

> **知识卡片**：FIFO 与 LRU 的实现差异
{: .callout-key}

| 算法 | 全称 | 数据结构 | 操作 | 缺陷 |
| --- | --- | --- | --- | --- |
| FIFO | First In First Out | 队列 Queue | 新数据插**队尾**，满了删**队头** | 可能淘汰"很热"但来得早的块 |
| LRU | Least Recently Used | 链表 | 新数据插**头**，命中则移到**头**，满了删**尾** | 精确 LRU 需记录访问时间戳，开销大 |

> **辨析**：LRU 为什么比 FIFO 好
{: .callout-bianxi}

FIFO 按"进入时间"淘汰，与"最近是否被用到"无关——一个刚被频繁访问的块，只因为进来得早就可能被扔掉。LRU 按"最近使用"淘汰，更贴合局部性原理的预测：既然时间局部性成立，**最近用过 = 很可能马上再用**。真实硬件常用**近似 LRU**（如 CLOCK / 伪 LRU），用便宜的分段位记录访问历史，牺牲一点精度换取低开销。

> **实际示例**：把两种淘汰算法跑出来看
{: .callout-prac}

```python
from collections import OrderedDict, deque

def fifo(cache_size, accesses):
    """FIFO：先进先出，队尾插新、队头淘汰"""
    q, cache = deque(), set()
    for a in accesses:
        if a not in cache:
            if len(cache) == cache_size:
                old = q.popleft(); cache.discard(old)
            q.append(a); cache.add(a)
    return q, cache

def lru(cache_size, accesses):
    """LRU：命中移到头部，满时淘汰尾部（OrderedDict 的 move_to_end 正好实现）"""
    cache = OrderedDict()
    for a in accesses:
        if a in cache:
            cache.move_to_end(a)          # 命中 -> 提到头部（最近使用）
        else:
            if len(cache) == cache_size:
                cache.popitem(last=False)  # 淘汰最久未用（尾部）
            cache[a] = 1
    return list(cache.keys()), set(cache.keys())

seq = [1, 2, 3, 1, 4, 2, 5]        # 容量 3：这组访问能让 FIFO 与 LRU 的淘汰结果不同
print('FIFO 末态:', list(fifo(3, seq)[0]))   # FIFO 淘汰"进来得早"的 1 -> [3, 4, 5]
print('LRU  末态:', lru(3, seq)[0])          # LRU  淘汰"最久没用"的 2 -> [4, 2, 5]
print('差异说明：第 4 次访问命中了 1，LRU 会把 1 提到最前，于是淘汰对象与 FIFO 不同')
```

> **原理**：写回（Write-Back）与脏位
{: .callout-why}

**写直达（Write-Through）**：每次写都同步更新主存。简单、一致性强，但主存带宽压力大。
**写回（Write-Back）**：只改 Cache 并置**脏位（dirty bit）**，等这块被淘汰时才写回主存。性能好得多，代价是**一致性窗口**变长——此时若另一个模块（如 DMA 控制器）直接读主存，读到的是**旧值**。所以写回必须配"脏位 + 写回时机"机制。

> **注意**：现代系统的缓存一致性靠什么保证
{: .callout-note}

- 硬件层：多核 Cache 之间用**目录（Directory）/ MESI 协议**保证同一行在多个核中的副本一致。
- 软件层：分布式场景下靠**消息通知**（数据库触发器、消息队列）或**设置缓存有效时间（TTL）**，让过期数据自动失效后回源。
- 运维层：改了数据库却看到旧值，先怀疑缓存，而不是怀疑数据库。

### 4.5 虚拟存储器：页式、段式、段页式

> **一句话定义**：**虚拟存储器**用"**内存与磁盘的动态交换**"解决程序装不下的问题——OS 把正在使用的部分留在内存，其余留在磁盘，需要时再调入。
{: .callout-card}

> **原理**：三种虚拟存储器结构的取舍
{: .callout-why}

| 结构 | 划分方式 | 基本单位 | 核心机制 | 优点 | 缺点 |
| --- | --- | --- | --- | --- | --- |
| 页式 | 主存按**等大页**划分 | 页 | 页表（虚页号→实页号）+ 缺页中断 | 页面定长，页表简单，调入方便 | 最后一页剩余空间浪费；一次调多页麻烦 |
| 段式 | 主存按**程序逻辑**划分 | 段 | 段表（段长/装入位/权限位/标志位） | 符合程序逻辑结构，便于共享与保护 | 段长不等，**外部碎片**严重；大段调入要挪动其他段 |
| 段页式 | 先分段、段内再分页 | 页 | 段表 + 页表 | 兼具两者优点，**空间利用率高** | 两级查表，**查两次表**，开销大 |

> **辨析**：段页式为什么"以时间换空间"是值得的
{: .callout-bianxi}

段页式要查两次表（先段表找页表基址，再查页表找实页号），确实比纯页式多一次访存。但它换来了**几乎为零的外部碎片**和更高的内存利用率。在内存容量成为瓶颈、且访存延迟远小于缺页代价（缺页要读磁盘，差几万倍）的场景下，这个交换**极其划算**——一次缺页的代价能抵掉成千上万次多余的查表。

> **知识卡片**：页表里存了什么
{: .callout-key}

| 字段 | 含义 | 作用 |
| --- | --- | --- |
| 虚页号 | 虚拟空间的页编号 | 索引页表的键 |
| 实页号 | 主存中的物理页编号 | 拼出主存物理地址 |
| 装入位 | 该页当前是否在内存 | 为 0 说明缺页，需触发中断 |
| 访问位 | 最近是否被访问 | 辅助置换算法判断"冷热" |
| 脏位 | 是否被修改过 | 为 0 则淘汰时无需写回，降低总线压力 |

> **实际示例**：把一次地址转换算到底
{: .callout-prac}

```python
def translate(vaddr, page_table, page_size=4096, pa_bits=32):
    """页式地址转换：虚地址 = 虚页号 + 页内地址 -> 物理地址 = 实页号 + 页内地址"""
    off_bits = page_size.bit_length() - 1
    vpn  = vaddr >> off_bits
    off  = vaddr & ((1 << off_bits) - 1)
    if vpn not in page_table:
        return {'结果': '缺页中断！需从磁盘调入', '虚页号': vpn}
    ppn = page_table[vpn]
    return {'物理地址': hex((ppn << off_bits) | off),
            '虚页号': vpn, '实页号': ppn, '页内地址': off}

pt = {0: 5, 1: 6, 2: 9}
print(translate(0x1234, pt))    # 0x1234 -> vpn=1 -> ppn=6 -> 0x6234
print(translate(0x4567, pt))    # vpn=4 不在页表 -> 缺页
```

> **坑位**：段式虚拟存储器的"缺段中断"流程容易漏步
{: .callout-pit}

段式的处理顺序是：① 内存中**是否有足够大的连续空间**容纳虚段 S？② 没有则触发**缺段中断**；③ 在中断处理里，可能要把**别的段置换出去（写回磁盘）**并**整理内存**腾出连续空间；④ 调入段 S，**修改段表**，⑤ 唤醒被阻塞的请求进程。漏掉"修改段表"和"唤醒进程"这两步，程序就会永久卡住。

## 五、指令系统：机器能听懂的话
{: .sec-know}

### 5.1 指令与指令集

> **一句话定义**：**指令**是指挥计算机完成某种操作的命令（机器指令）；一台计算机**所有指令的集合**叫**指令集 / 指令系统**。
{: .callout-card}

> **知识卡片**：指令集必须覆盖的四大类指令
{: .callout-key}

| 类别 | 子类 | 作用 | 例子 |
| --- | --- | --- | --- |
| 数据传输类 | 传送 / 装入 / 存储 | 在寄存器、内存之间搬数据 | `MOV`、`LOAD`、`STORE` |
| 运算类 | 算术 / 逻辑 / 移位 | 完成数值与位运算 | `ADD`、`AND`、`SHL` |
| 程序控制类 | 转移 / 子程序调用 / 返回 | 改变执行顺序 | `JMP`、`CALL`、`RET` |
| 输入/输出类 | I/O 指令 | 与外设交互 | `IN`、`OUT` |

### 5.2 指令格式：操作码 + 地址码

> **一句话定义**：一条指令通常由**操作码字段**（说明"做什么"）和**地址码字段**（说明"对谁做"）构成。
{: .callout-card}

- **操作码字段**：说明指令应执行什么性质的操作、具有什么功能。译码器读它来决定产生哪组控制信号。
- **地址码字段**：说明被操作数据的地址，包括**操作数地址**、**子程序入口地址**、**运算结果保存地址**。
- **一条指令的地址码个数**决定了寻址方式（如零地址、一地址、二地址指令），直接反映指令系统的规整程度。

> **辨析**：指令格式 vs 机器字长
{: .callout-bianxi}

- **指令字长** = 一条指令包含的**二进制位数**。
- **机器字长** = CPU 一次能处理的**二进制位数**。
- 两者**不必相等**：x86 机器字长 64 位，但指令字长可变（1~15 字节不等），因为它是变长指令结构。
- 定长指令结构的典型是 RISC：所有指令长度一致，译码简单、可流水线并行；变长指令结构的典型是 CISC：指令长度不等、功能强但译码复杂。

### 5.3 RISC 与 CISC

> **一句话定义**：**CISC**（复杂指令系统）指令多、单条指令功能强、常用微程序控制；**RISC**（精简指令系统）指令少、功能简单、靠指令组合实现复杂功能。
{: .callout-card}

> **知识卡片**：两者的设计哲学对比
{: .callout-key}

| 维度 | CISC | RISC |
| --- | --- | --- |
| 指令数量 | 多 | 少（典型几十到几百条） |
| 指令长度 | 变长 | 定长 |
| 指令复杂度 | 一条指令可完成复杂操作 | 只做简单操作，复杂功能靠组合 |
| 控制方式 | 常用**微程序** | 常用**硬布线**控制 |
| 寄存器数量 | 较少 | 多（典型 32 个通用寄存器） |
| 流水线 | 译码难，难做深流水 | 规整易流水 |
| 代表 | x86、x86-64 | ARM、RISC-V、MIPS、LoongArch |

> **原理**：RISC 是"把复杂度从硬件搬到软件"
{: .callout-why}

CISC 的思路是"硬件帮你做复杂事"，代价是指令长度不规整、译码阶段长、难以做深流水线，妨碍了主频提升。RISC 反过来：让每条指令都简单规整、都能在一个周期内完成，从而能**同时发射多条指令**并提高主频；原本一条复杂指令完成的事，改由编译器用若干条简单指令组合完成——复杂度被搬到了**编译器**里。

> **延伸拓展**：RISC-V 与国产指令集
{: .callout-spread}

- **RISC-V** 是**开放指令集架构（ISA）**，规范公开、 royalty-free，任何厂商都能实现；已被大量嵌入式与新兴服务器采用，扩展性通过模块化指令集（F/D/V/A 等）实现。
- **国产处理器指令集**：龙芯 **LoongArch**、鲲鹏与飞腾采用 **ARM** 指令集，申威采用 **SW64**。生态迁移的主要成本不在硬件，而在**编译器后端、基础库与中间件的重新适配**。
- **Apple Silicon** 用 ARM 指令集做桌面/服务器，说明"指令集选择"已从技术问题变成生态与商业问题。

## 六、CPU 内部结构与指令执行过程
{: .sec-know}

### 6.1 CPU 的功能与基本结构

> **一句话定义**：CPU 包含**运算器**和**控制器**两大块，核心功能是**数据加工、指令控制、时间控制、中断处理**四项。
{: .callout-card}

> **知识卡片**：CPU 四大功能
{: .callout-key}

| 功能 | 含义 | 典型实现 |
| --- | --- | --- |
| 数据加工 | 对数据进行算术运算或逻辑运算 | ALU、通用寄存器组 |
| 指令控制 | 完成取指、分析指令、执行指令 | 指令译码器、PC、IR |
| 时间控制 | 对各种操作加以时间控制，按时间顺序提供控制信号 | 时钟发生器、控制器时序电路 |
| 中断处理 | 处理运行中的异常与特殊情况 | 中断控制逻辑、向量表 |

### 6.2 运算器：对数据做加工

> **一句话定义**：运算器由**算术逻辑单元（ALU）**、**通用寄存器组**、**程序状态寄存器（PSW）**组成，是真正"算数"的地方。
{: .callout-card}

> **知识卡片**：三个部件各自的职责
{: .callout-key}

- **ALU（加法器）**：实现算术与逻辑运算。**减法靠加法器实现**——这就是补码存在的根本原因（见 2.4）。
- **通用寄存器组**：保存操作数（源操作数、目的操作数、中间结果）以及各种地址信息。x86-64 只有 16 个 64 位通用寄存器，ARM 有 31 个，寄存器数量直接影响编译器的寄存器分配效率。
- **PSW（程序状态寄存器）**：保存运算结果的各种标志位。**SF**（符号标志）、**ZF**（零标志）、**OF**（溢出标志）、**CF**（进位标志）。`if (a > b)` 这类判断，编译后就是测试这几个标志位的组合跳转。

### 6.3 控制器：系统的指挥中枢

> **一句话定义**：控制器的四项硬件各司其职——**PC** 管下一条指令在哪、**IR** 管当前指令是什么、**MAR** 管要访问的内存地址、**MDR** 管内存回来的数据，**指令译码器**把操作码翻译成控制信号。
{: .callout-card}

> **知识卡片**：四个寄存器的定位
{: .callout-key}

| 寄存器 | 全称 | 作用 | 一句话记忆 |
| --- | --- | --- | --- |
| PC | 程序计数器 | 保存**下一条**要执行的指令地址 | "我在哪儿" |
| IR | 指令寄存器 | 保存**当前正在执行**的指令 | "我在干什么" |
| MAR | 存储器地址寄存器 | 保存要访问的**内存单元地址** | "我要去哪儿" |
| MDR | 存储器数据寄存器 | 保存从内存读出 / 待写回的数据 | "数据中转站" |
| 指令译码器 | — | 对操作码译码，给控制器提供操作信号 | "把中文翻译成命令" |

> **辨析**：PC 和 IR 千万别搞混
{: .callout-bianxi}

**PC 指向"下一条"，IR 装着"当前这条"**。这是取指循环的精髓：`PC → MAR → 内存 → MDR → IR`，同时 `PC ← PC + 1`。所以在执行某条指令的过程中，PC 已经指向下一条了——除非这条指令是跳转指令，它会把 PC 改写掉。

> **坑位**：中断时"断点"和"现场"分别存什么
{: .callout-pit}

- **断点 = PC 的值**（下一条要执行的指令地址），中断返回时要重新装回 PC。
- **现场 = 各寄存器中当前程序的信息**，包括 PSW、中间结果、操作数，甚至正在执行的指令。恢复现场要一个个恢复寄存器。
- 只恢复 PC 不恢复寄存器，程序会从"正确的地方"用"错误的数据"继续跑——这是最隐蔽的中断 bug。

### 6.4 指令执行过程：五步流水

> **一句话定义**：一条指令的执行被拆成**取指 → 分析指令 → 取操作数 → 执行指令 → 送回结果**五步，其中 1、3、5 步与外部（内存）交互，2、4 步在 CPU 内部完成。
{: .callout-card}

> **实际示例**：把取指五步对应到真实硬件信号
{: .callout-prac}

```text
【第 1 步 取指】
  1) PC 的值  ->  MAR（存储器地址寄存器）
  2) MAR 的值 -> 地址总线 AB
  3) 控制单元经控制总线 CB 向存储器发"读"命令
  4) 内存 -> 数据总线 DB -> MDR（存储器数据寄存器）
  5) MDR -> IR（指令寄存器）；同时 PC <- PC + 1，为下一条指令做准备

【第 2 步 分析指令】
  指令译码器解析 IR 中的操作码，判定指令类型：
    - 有操作数的指令：还需计算操作数地址并读取操作数 -> 进入第 3 步
    - 无操作数的指令：直接跳到第 4 步执行阶段

【第 3 步 取操作数】（仅当指令需要）
  按寻址方式算出有效地址 -> 读内存/寄存器 -> 送入 ALU

【第 4 步 执行指令】
  ALU 完成指令规定的动作，形成稳定的运算结果
  （通用寄存器组保存结果，状态寄存器更新 SF/OF/ZF 等标志）

【第 5 步 送回结果】（如需要）
  把结果写回寄存器或内存

步骤 5 结束后，回到步骤 1，重复 1~5 直到程序结束
```

> **原理**：现代 CPU 为什么要做流水线
{: .callout-why}

上面五步是**串行**的教科书模型：取完才能译码，译码完才能取操作数。但各阶段用的硬件资源不同（取指用内存接口、译码用译码器、执行用 ALU），完全可以**重叠**：在译码第 N 条指令的同时，去取第 N+1 条。这条流水线就是现代 CPU 能"主频只有 3GHz 却比 20 年前 5GHz 更快"的核心原因。流水线的副作用是**分支预测**与**数据相关**问题——后面的指令可能依赖前面的结果，或者跳转让已取的指令白取，因此需要**分支预测器**与**转发（forwarding）**机制来补救。

## 七、总线与仲裁：部件之间怎么抢总线
{: .sec-know}

### 7.1 总线的基本概念

> **一句话定义**：**总线**是各模块之间传送信息的通路，它不是一根线，而是**一类线路的总称**（数据线、地址线、控制线）。
{: .callout-card}

> **知识卡片**：总线的三个特点与三种分类
{: .callout-key}

- **特点 1 —— 共享**：总线上可挂接多个设备，设备之间交换信息都通过总线完成。
- **特点 2 —— 分时**：**同一时刻只能有一个设备**在总线上传输信息。多个设备如何协调？→ **总线仲裁**。
- **特点 3 —— 分类**：
  - 按位置：**系统总线**（系统内各部件之间）、**CPU 内部总线**、**外部总线**（与外界通信）。
  - 按功能：**数据线**、**地址线**、**控制线**。

> **辨析**：总线的"分时"和"共享"是一体两面
{: .callout-bianxi}

共享带来了总线能效比高的好处（一组线服务所有设备），但也带来**冲突**问题：两个设备同时驱动同一根线会互相干扰（总线争用）。所以总线设计必然要配一套**仲裁机制**来决定"这一刻谁说了算"。这也解释了为什么现代高速总线普遍采用**点对点串行链路 + 交换结构（switch）**替代传统共享总线：串行线速率高且不存在共享冲突，交换芯片在内部做路由。

### 7.2 总线仲裁：集中式 vs 分布式

> **一句话定义**：**总线仲裁**解决"多个设备同时争抢总线控制权时，选谁"的问题；**集中式**由中央仲裁器统一决定，**分布式**由各设备自行协商。
{: .callout-card}

> **知识卡片**：三种集中式仲裁方式对比
{: .callout-key}

| 方式 | 线路构成 | 优先级 | 响应速度 | 主要缺点 |
| --- | --- | --- | --- | --- |
| 链式查询 | 所有设备共用 1 条 BR 线，BG 串行传递 | **固定**：离仲裁器越近优先级越高 | 慢（BG 要逐级传递） | 设备故障会阻塞其后所有设备；控制线最少 |
| 计数器定时查询 | 多条地址线 + 1 条控制线 | **可编程调整**（设计数器初值） | 中等 | 需更多地址线，硬件复杂，速度偏慢 |
| 独立请求 | 每个设备一条独立控制线 | 可按需设计 | **最快**（仲裁器直接知道是谁） | **控制线数量最多** |

> **原理**：链式查询里的 BR / BS / BG 到底是什么
{: .callout-why}

链式查询方式只有**一条总线请求线 BR**、**一条总线忙线 BS**、**一条总线同意线 BG**（共 3 根控制线）：
1. 所有设备都通过 BR 线向中央仲裁器发请求（所以是"共用一条线路"）。
2. 仲裁器发 BG 信号，BG **依次经过**连接在总线上的设备；第一个（离仲裁器最近）正在请求总线的设备就抢到总线——**距离决定优先级**。
3. 该设备拉起 BS，告诉其他设备"总线已忙"。

独立请求方式则是每个设备与仲裁器之间**控制线互相独立**，仲裁器能直接得知是谁在请求，响应快，但线数暴涨。

> **实际示例**：在 Linux 里观察一次真实的总线争用
{: .callout-prac}

```bash
# PCIe 总线的仲裁在硬件里完成，Linux 侧看到的是驱动层的请求队列
# 1) 看某块设备的中断与 DMA 活动（总线活动的直接证据）
cat /proc/interrupts | head -5
grep -E "^[0-9a-f]+:" /proc/interrupts | awk '$2>1000 {print $1, $2}' | head

# 2) 看 I/O 层面的传输量（DMA 是最典型的"占总线"行为）
iostat -x 1 3          # %util 接近 100% 说明设备在抢总线/磁盘通道
cat /proc/diskstats | head -3

# 3) 观察 NVMe 这类 PCIe 设备的队列深度与处理能力
cat /sys/block/nvme0n1/queue/nr_requests
nvme smart-log /dev/nvme0n1 | head -20
```

> **延伸拓展**：从共享总线到点对点链路
{: .callout-spread}

- **PCIe** 用点到点串行链路取代传统共享总线，靠**交换芯片（Switch）**在内部做路由，天然规避了仲裁冲突，也支持热插拔与多层设备树。
- **CXL** 在 PCIe 物理层上叠加"缓存一致性互连"，允许 CPU、加速卡、内存扩展设备**共享内存语义**——这是"内存池化"的关键 interconnect。
- **NUMA**（非统一内存访问）在多路服务器上把内存按 CPU 节点分组，本质是"给内存也做了一层拓扑"，跨节点访存延迟显著更高，因此绑核（`numactl`）是高性能程序的必备功课。

## 八、I/O 系统与中断：CPU 如何与外界打交道
{: .sec-iv}

### 8.1 I/O 基本概念与接口电路

> **一句话定义**：**I/O（输入/输出）系统**由 I/O 设备与 **I/O 接口电路**组成；接口负责在"CPU 的并行二进制世界"与"外设的各色世界"之间做翻译与缓冲。
{: .callout-card}

> **知识卡片**：I/O 接口电路的四项基本功能
{: .callout-key}

| 功能 | 为什么需要 | 例子 |
| --- | --- | --- |
| **数据缓冲** | CPU 一次处理一个字（并行），而部分外设串行收发（一次 1 bit），速度不匹配 | 串口 FIFO、网卡 DMA 描述符环 |
| **信号格式转换** | CPU 用二进制，外设可能用其他信号形式 | 串并转换、光电转换、电平转换 |
| **地址译码与设备选择** | 识别是哪个设备、哪个端口 | I/O 端口地址译码 |
| **传送控制命令与状态信息** | CPU 要能下达命令并读回"忙/就绪/出错" | 控制寄存器、状态寄存器 |

> **辨析**：为什么"端口"是 I/O 接口的核心抽象
{: .callout-bianxi}

**端口**是接口电路中用于读/写的寄存器地址。CPU 不直接跟设备打交道，而是读写端口：
- 往**控制端口**写命令（"开始传输"）；
- 轮询**状态端口**（"忙吗？好了吗？"）；
- 通过**数据端口**搬运实际数据。

这套"命令/状态/数据"三类寄存器模型，就是今天所有设备驱动（如 Linux 的 `ioports`、`readl/writel`）的通用抽象。

### 8.2 三种 I/O 方式

> **一句话定义**：I/O 有三种组织方式——**程序查询**（CPU 全程盯着）、**程序中断**（外设主动叫醒 CPU）、**DMA**（数据直接搬，CPU 只做授权）。
{: .callout-card}

> **知识卡片**：三种方式的对比
{: .callout-key}

| 方式 | 谁在控制 | CPU 是否全程参与数据搬运 | 并行性 |
| --- | --- | --- | --- |
| 程序查询 | CPU | **是**，一直循环查状态寄存器 | 差：外设和主机**不能同时工作** |
| 程序中断 | CPU + 硬件 | 否：外设通知 CPU，CPU 转入 ISR | 较好：实现了**一定程度上的并行** |
| DMA | DMA 控制器 | 否：数据**不经过 CPU**，外设直接与内存交换 | 好：CPU 只在开始与结束时参与 |

> **原理**：中断方式的执行时序
{: .callout-why}

CPU 启动 I/O 后**不必立即停止**当前进程——外设接到启动命令后进入准备阶段，准备完成后**主动通知** CPU。CPU 这时才中断当前进程、记录断点，转去执行中断服务程序为 I/O 服务；服务结束后**回到断点处继续执行**。这就在"CPU 算自己的"和"外设搬自己的"之间实现了并行。

> **辨析**：DMA 和中断的分工
{: .callout-bianxi}

- **中断**的粒度是"**一次 I/O 操作**"：CPU 搬运一个字或一批字，每次搬运都要中断一次，中断开销相对大。
- **DMA** 的粒度是"**一个数据块**"：DMA 控制器接管整块数据的搬运，**过程中不经过 CPU**，只在开始（请求总线）和结束（产生一次中断通知 CPU）时与 CPU 交互。代价是需要专门的 DMA 控制器与总线仲裁支持。
- 现代 NVMe 更进一步：用**队列（queue）** + **中断合并**，把多个完成事件攒起来再报一次中断，进一步摊薄开销。

### 8.3 中断的四个基本概念

> **一句话定义**：理解中断要先分清四个词——**中断源**（谁来的）、**中断判优**（先响应谁）、**中断屏蔽**（只接哪些）、**允许/禁止中断**（现在允不允许被打断）。
{: .callout-card}

> **知识卡片**：四个概念的精确定义
{: .callout-key}

- **中断源**：发送中断请求的设备或事件（键盘、网卡、时钟、硬件异常）。
- **中断判优**：**前提**是多个中断源**同时**发请求，此时需要判断优先响应谁——通常按优先级：紧急故障 > DMA 完成 > 设备 I/O > 时钟。
- **中断屏蔽**：通过程序控制，**有选择地接受**部分中断请求、屏蔽另一部分，本质是**软件设置优先级**。
- **允许/禁止中断**：如果当前执行的进程优先级很高、或处于不可被打断的关键区间（如关中断保存现场），就**禁止**接收中断请求。

> **实际示例**：在 Linux 里映射这四个概念
{: .callout-prac}

```bash
# 1) 中断源：/proc/interrupts 每行就是一个中断源（设备 + IRQ 号）
cat /proc/interrupts | head -8

# 2) 中断屏蔽：/proc/irq/<IRQ>/ 中可以查看/设置该 IRQ 的屏蔽字
#    0xffffff 表示全部屏蔽；写 1 表示只屏蔽某一位
cat /proc/irq/1/smp_affinity 2>/dev/null
cat /proc/irq/1/effective_affinity_list 2>/dev/null

# 3) 允许/禁止中断：内核里的 local_irq_save/restore
#    关中断期间不能被打断，用于保护临界区
dmesg | grep -iE "irq|interrupt" | tail -10

# 4) 观察某个 IRQ 的 CPU 亲和性（绑定到指定 CPU，可避免跨 NUMA 节点访问）
irq=$(grep -iE 'nvme|ahci' /proc/interrupts | head -1 | cut -d: -f1 | tr -d ' ')
echo "IRQ ${irq} 当前亲和性:"; cat /proc/irq/${irq}/smp_affinity_list 2>/dev/null
```

### 8.4 中断处理过程

> **一句话定义**：一次完整的中断处理是**关中断 → 保存断点与现场 → 判别中断源 → 执行中断服务程序 → 退出中断（恢复现场与断点）→ 开中断**的闭环。
{: .callout-card}

> **原理**：六个环节各自在干什么
{: .callout-why}

1. **关中断**：响应中断请求后停止接收新的中断请求，因为下面的保存过程不允许被打断。
2. **保存断点**：保存**程序计数器的值**（PC）。
3. **保存现场**：保存各个寄存器中的信息——PSW、中间结果、操作数、正在执行的指令等。
4. **判别中断源**：识别是哪个中断源；把 PC 改为该中断程序的**入口地址**，准备执行。
5. **执行中断服务程序**（ISR）。
6. **退出中断**：实际就是"关中断"状态下的恢复过程，恢复断点和现场（重设 PC、恢复寄存器）。
7. **开中断**：恢复完成后重新开放中断请求的接收。

> **知识卡片**：中断嵌套
{: .callout-key}

- **场景**：中断 1 执行中，来了优先级更高的中断 2。
- **处理**：CPU **中断中断 1**，转去执行中断 2；中断 2 结束后**恢复中断 1**；中断 1 执行完成，最后**恢复原程序**。
- **开中断的时机**：做好执行中断程序的准备后，开放中断接收，从而**允许更高级的中断请求中断低级的中断请求**，先响应优先级更高的。
- **嵌套层数**：中断服务程序的嵌套级数一般由**中断优先级**决定。

> **坑位**：中断里的三条铁律
{: .callout-pit}

- **关中断区不能太长**：关中断期间所有中断都进不来，长时间关中断会丢中断（比如网卡丢包、定时器丢 tick）。
- **ISR 要尽量短**：中断上下文里**不能睡眠**（`sleep`、阻塞式 I/O、申请内存都可能睡眠），长任务必须交给下半部/软中断/工作队列。
- **现场保存与恢复必须配对**：少恢复一个寄存器，程序就会带着脏数据继续跑。

### 8.5 中断 vs 调用子程序

> **一句话定义**：中断和子程序调用**看起来相似**（都是"跳去执行一段代码再跳回来"），但它们在**服务对象、实现方式、时间空间特性**三个维度上根本不同。
{: .callout-card}

> **知识卡片**：五组区别
{: .callout-key}

| 维度 | 中断 | 调用子程序 |
| --- | --- | --- |
| **服务对象** | 与主程序一般无关，服务的是**外部设备或异常事件** | 只为**主程序**服务 |
| **实现方式** | 需要**硬件与软件配合**（硬件产生中断请求，CPU 响应，软件写 ISR） | **完全由软件**实现（`CALL`/`RET` 指令） |
| **发生时间** | **随机发生**，事先不可预知 | 程序员**预先安排**，位置确定 |
| **时间/空间开销** | 需保存断点与现场，开销大且不确定 | 调用与返回的时间和空间都是**确定的** |
| **嵌套层数** | 由**中断优先级**决定 | 由**堆栈大小**决定（调用越多栈帧越多） |

> **辨析**：为什么"中断嵌套看优先级、子程序嵌套看堆栈"
{: .callout-bianxi}

- **中断嵌套**发生在**硬件调度层**：CPU 依据优先级判定谁能打断谁，优先级表由中断控制器（如 APIC）维护。
- **子程序嵌套**发生在**软件调用层**：每调用一层就压一个栈帧，栈帧深度完全取决于**代码的调用深度**，因此嵌套层数受限于**栈的大小**。递归太深会栈溢出，就是这个道理。
- 二者可以叠加：中断服务程序里调用了子程序，栈上就同时有 ISR 帧和子程序帧。

## 九、知识点发散与新技术延伸
{: .sec-ext}

### 9.1 知识点发散：把零散概念串成主线
{: .sec-sum}

> **知识卡片**：一条主线串起全文
{: .callout-key}

**"一切都是比特" → "比特要能表达数与字符"（进制 / 机器码 / 浮点）→ "比特要放在某处"（存储分层 / Cache / 虚存）→ "CPU 按指令搬运比特"（指令系统 / CPU 五步）→ "部件之间要连线"（总线 / 仲裁）→ "CPU 要和外界打交道"（I/O / 中断）**

理解了这六段主线，上面所有零散概念（补码、组相连、脏位、判优）就都是**这条主线上的必然产物**，而不是需要死记的知识点。

> **辨析**：三个最容易混的"一对"
{: .callout-bianxi}

1. **溢出 vs 精度**：溢出是"装不下"（范围问题），精度是"分不清"（分辨率问题）。
2. **Cache 替换策略 vs 更新策略**：替换解决"满了扔谁"，更新解决"改了什么时候同步"。
3. **中断 vs 子程序**：一个"随机、由硬件发起、服务设备"，一个"确定、由软件发起、服务主程序"。

### 9.2 新技术延伸：这门课在今天怎么落地
{: .sec-sum}

> **知识卡片**：现代硬件/系统对上述概念的延续与革新
{: .callout-key}

- **RISC-V 与开放 ISA**：RISC 思想从 MIPS/ARM 走到 RISC-V，开放规范让"指令系统"从专利壁垒变成生态竞争；LoongArch、Armv9 等新架构都在同一套"RISC 规整性"上做文章。
- **虚存与内存安全**：ASLR、SMEP/SMAP、影子栈把"内存映射"从"性能机制"升级为"安全边界"；**巨页（THP）**用更大的页减少 TLB 缺页，是典型的"用空间 locality 换性能"。
- **CXL 与内存池化**：CXL 3.0 引入内存池化，把 DRAM 从"挂在某台服务器上"变成"可按需切分共享的资源"，直接冲击了传统"内存条插槽"这个 50 年不变的设计。
- **io_uring 与异步 I/O**：把"每次 I/O 一次中断"变成"共享环形队列 + 批量完成通知"，是对 8.2 节"中断方式"的一次范式级改良，显著降低高并发网络与存储场景的中断开销。
- **eBPF 与可编程数据面**：把"用户态程序在内核里安全地跑"变成可能，让"中断/系统调用路径"成为可观测、可拦截的观测点。
- **NVMe 与多队列**：把传统"一个控制器一条队列"变成"多队列 + CPU 亲和"，是对 8.2 节"DMA 分工"的一次工程级增强。
- **字符编码的现状**：UTF-8 早已统一全球（Linux 内核 4.6 起建议源码一律 UTF-8），但 GBK/GB2312 存量仍在，老系统与遗留数据迁移仍需 `iconv` 处理。
- **RISC-V 向量与矩阵扩展（V / Zve*）**：把 SIMD 能力纳入开放 ISA 规范，回应了"AI 算力"对专用指令的需求。

### 9.3 动手验证清单
{: .sec-prac}

> **实际示例**：把今天的概念都亲手过一遍
{: .callout-prac}

```bash
# 1) 观察 CPU 到底有多少个"字长"（机器字长）
uname -m                 # x86_64 => 64 位机器字长
lscpu | grep -E "Model name|CPU\(s\)"

# 2) 看 Cache 的真实层级与组相连参数（对照 4.3 节）
for d in /sys/devices/system/cpu/cpu0/cache/index*; do
  [ -d "$d" ] || continue
  echo "== L$(cat $d/level) $(cat $d/type) =="
  echo "   容量: $(cat $d/size) | 路数: $(cat $d/ways_of_associativity) | 行大小: $(cat $d/coherency_line_size)B"
done

# 3) 看虚拟内存：页大小、页表、缺页统计
getconf PAGESIZE
grep -E "^(pgfault|pgmajfault|pgin|pgout)" /proc/vmstat

# 4) 看中断：每处理器的中断计数与亲和性
cat /proc/interrupts | head -6
cat /proc/softirqs | head -8

# 5) 亲手验证浮点精度与整数溢出
python3 - <<'PY'
import struct
print('0.1+0.2 =', 0.1 + 0.2, '| 精确相等?', (0.1+0.2) == 0.3)
u = struct.unpack('Q', struct.pack('d', 0.1))[0]
print('0.1 的真实存储值 = %.20f' % struct.unpack('d', struct.pack('Q', u))[0])

def from_twos(b, bits=8):
    """把 8 位补码还原成有符号整数"""
    s = 1 << (bits - 1)
    return (b & (s - 1)) - (b & s)

print('int8 溢出: 127+1 截断为', (127 + 1) & 0xFF, '-> 按 int8 解读 =', from_twos((127 + 1) & 0xFF))
PY
```
