> LNMP 是互联网企业最经典的动态网站架构：Linux 提供运行环境，Nginx 处理静态请求并转发动态请求，PHP 解析动态页面并连接数据库，MySQL（生产环境常用 MariaDB）负责数据存储。架构组成、环境部署、服务联动、网站上线，一篇走完整个搭建流程，坑点与排错思路都汇总在后面。

## LNMP 架构组成 {: .sec-expl}

| 组件 | 作用 |
| --- | --- |
| L（Linux） | 系统层，为整个架构提供运行环境 |
| N（Nginx） | 处理用户的静态请求，如 html、jpg、txt、mp4/avi 等 |
| P（PHP） | 处理动态页面请求，负责和数据库建立关系 |
| M（MySQL/MariaDB） | 存储用户的字符串数据信息 |

> **注意：** SELinux 必须关闭，防火墙需要关闭；此外 /tmp 目录权限为 1777 时 MySQL 服务无法启动，部署前务必检查。
{: .sec-pit}

对比 LAMP：Web 层从 Apache 换成 Nginx，静态并发能力上一个台阶；PHP 从 mod_php 模块换成独立的 php-fpm 进程池，Web 与动态层解耦、可分机部署，其余不变。

与 LNMP 相关的企业实践方向还包括：全网备份项目、实时同步项目、网站服务自动化部署（Ansible）、LNMP 环境搭建、数据库迁移项目等，本文覆盖其中最核心的环境搭建与网站上线。

## 原理解析 {: .sec-know}

### 动态请求在 LNMP 中的流转

LNMP 与纯静态站点的本质区别：静态请求（html、图片）由 Nginx 读磁盘直接返回；动态请求（.php）Nginx 自己处理不了，必须通过 FastCGI 协议交给 php-fpm，由 PHP 解释器执行脚本；脚本中需要数据时，PHP 再通过 MySQL 协议连接数据库查询。整条链路任何一个环节不通，都会在 Nginx 侧体现为 502（连不上后端）或 500（后端执行出错），这也是 LNMP 排错围绕 502/500 展开的原因。

### FastCGI 与 php-fpm 的角色

- FastCGI：Nginx 与后端语言解释器之间的通信协议，Nginx 把请求按协议格式转发，php-fpm 按协议返回执行结果；
- php-fpm：PHP 的进程管理器，预先 fork 好一组 PHP 工作进程，通过 TCP 9000 端口或 Unix Socket 与 Nginx 通信，避免每个请求都重新启动解释器；
- Unix Socket 相比 127.0.0.1:9000 少走 TCP 协议栈，本机通信延迟更低，是更推荐的监听方式。

说白了，Nginx 在 LNMP 里就是个高级搬运工：它不认识 PHP，遇到 .php 请求，fastcgi_pass 决定把请求递给哪个 php-fpm 进程池，fastcgi_param 决定告诉 fpm 去执行哪个文件。这两处配错，nginx -t 不会报语法错，全都在访问时以 502 或 File not found 的形式爆出来。解耦的收益在扩容时兑现：静态压力涨加 Nginx，动态压力涨加 php-fpm 或整体复制一台 web 节点挂到负载均衡后面，两层各自伸缩互不牵连。

## Nginx 关键配置回顾 {: .sec-sum}

### location 匹配规则

Nginx 根据用户访问的 URI 进行匹配处理，各匹配方式的优先级如下：

| 匹配方式 | 写法 | 优先级 |
| --- | --- | --- |
| 精确匹配 | location = uri | 1（最高） |
| 优先匹配 | location ^~ uri | 2 |
| 正则匹配（区分大小写） | location ~ 正则 | 3 |
| 正则匹配（不区分大小写） | location ~* 正则 | 3 |
| 普通 URI 匹配 | location uri | 3 |
| 默认匹配 | location / | 最低 |

> **注意：** 上表是课堂速记的简化版。精确规则：任何正则命中都优先于全部普通前缀匹配；多个普通前缀同时命中时取路径最长的一个；多个正则同时命中时取书写顺序最靠前的一个。配置 PHP 站点时 `location ~ \.php$` 能优先于 `location /` 命中，正是这个原因。
{: .sec-pit}

### 企业应用：多站点目录切换

大促期间（如 11.11、12.12、6.18）页面信息与平常不一样，可以准备两个站点目录，通过 location 匹配进行切换：

```nginx
location / {
    root /html/jd-normal;
}
location /特殊 {
    root /html/jd-teshu;
}
```

### 其他常用能力

- 页面跳转：rewrite 用于匹配地址（URL/URI）并跳转成目标地址；return 301 http://xxxx 直接返回跳转。
- 用户访问监控：keepalive_timeout 65s 控制长连接超时时间；HTTP 请求报文的请求头中 connection 为 keep-alive/closed，响应报文的响应头中 connection 为 closed，表示短连接。
- 日志功能：错误日志可配置错误日志级别，访问日志可配置日志格式信息，便于后续自动化分析日志（ELK）。

## 部署 LNMP 环境 {: .sec-expl}

### 部署 Nginx

Nginx 服务可以通过 Ansible 一键化部署，前提是提前修改好 yum 源。部署细节在《Nginx 网站服务部署》已有完整步骤，本篇不重复，重点放在 Nginx 与 PHP、PHP 与数据库的联动上。

### 部署 MariaDB

第一步：安装数据库软件。

```bash
yum install mariadb-server mariadb -y
```

补充：数据库初始化过程使用 mysql_install_db 命令，常用参数如下：

| 参数 | 说明 |
| --- | --- |
| --basedir=path | 指定 MySQL 程序目录 |
| --datadir=path | 指定数据信息保存的目录 |
| --user=mysql | 让 mysql 用户管理数据目录（权限 700） |

初始化过程会输出设置密码的提醒信息：

```console
PLEASE REMEMBER TO SET A PASSWORD FOR THE MySQL root USER !
To do so, start the server, then issue the following commands:
```

```bash
/application/mysql/bin/mysqladmin -u root          password 'new-password'   # 给本地数据库设置密码
/application/mysql/bin/mysqladmin -u root -h web01 password 'new-password'   # 给远程数据库设置密码
```

第二步：启动数据库服务。

```bash
systemctl start mariadb.service
systemctl enable mariadb.service
```

第三步：给 MySQL 数据库服务设置密码。

```bash
mysqladmin -u root password '<your-password>'    # 设置密码
mysql -u root -p'<your-password>'
```

> **注意：** 命令中的 `<your-password>` 仅为占位示例，生产环境务必使用强密码，并改用 `mysql -u root -p` 交互输入，避免口令留在 history 里。MariaDB 10.4 及之后版本 root 默认使用 unix_socket 认证（本机以 root 系统身份免密登录），`mysqladmin -u root password` 与 `mysql_secure_installation` 依然可用于设置和加固密码。
{: .sec-pit}

> **注意：** mysql_install_db 是早期版本的初始化方式。MariaDB 10.x 起数据目录初始化已由 systemd 在首次启动服务时自动完成（数据目录为空时自动初始化 /var/lib/mysql），无需手动执行。源码安装的 MySQL 若不用 systemd 托管，可用 `mysqld --initialize-insecure`（root 无密码）或 `mysqld --initialize`（随机密码写入 error log）初始化，再用 `mysqld_safe --user=mysql &` 后台启动（mysqld_safe 会在 mysqld 异常退出时自动重启）。
{: .sec-pit}

加固数据库（删除匿名用户、禁止 root 远程登录、删除测试库）：

```bash
mysql_secure_installation
```

```bash
yum remove php-mysql php php-fpm php-common
```

```bash
yum install -y php71w php71w-cli php71w-common php71w-devel php71w-embedded php71w-gd php71w-mcrypt php71w-mbstring php71w-pdo php71w-xml php71w-fpm php71w-mysqlnd php71w-opcache php71w-pecl-memcached php71w-pecl-redis php71w-pecl-mongodb
```

> **注意：** webtatic 源最后只支持到 CentOS 7，已停止维护。Rocky Linux / AlmaLinux / CentOS Stream 8 及以上请改用 Remi 仓库（`dnf install https://rpms.remirepo.net/enterprise/remi-release-9.rpm` 后 `dnf module install php:remi-8.2`）或系统自带的 AppStream php 模块流，安装 php、php-fpm、php-mysqlnd 等包。
{: .sec-pit}

第三步：编写配置文件 /etc/php-fpm.d/www.conf。

```ini
user = www

```

> **注意：** 必须保证 Nginx 进程的运行用户和 php-fpm 服务进程的运行用户保持一致（均设为 www），否则会出现权限问题。
{: .sec-pit}

装完先 php -m 核对模块清单，mysqlnd、mbstring、gd 缺一个，WordPress 安装向导就会卡在对应步骤，报错信息还不一定直说。

第四步：启动 PHP 服务。

```bash
systemctl start php-fpm
```

### php-fpm 核心配置（www.conf） {: .sec-sum}

/etc/php-fpm.d/www.conf 是 php-fpm 的主配置，关键项如下：

| 配置项 | 说明 | 常见值 |
| --- | --- | --- |
| user / group | worker 进程运行的用户与组，须与 Nginx 一致 | www / www |
| listen | FastCGI 监听地址，TCP 或 Unix Socket | 127.0.0.1:9000 或 /run/php-fpm/www.sock |
| listen.owner / listen.group / listen.mode | Socket 文件属主与权限，Nginx 运行用户需能写 | www / www / 0660 |
| pm | 进程管理模式：static / dynamic / ondemand | dynamic |
| pm.max_children |  worker 进程上限，内存和并发的主要矛盾点 | 50（按内存调整） |
| pm.start_servers | dynamic 模式下启动时创建的进程数 | 5 |
| pm.min_spare_servers | 最小空闲进程数，低于则补充 | 5 |
| pm.max_spare_servers | 最大空闲进程数，高于则回收 | 35 |
| pm.max_requests | 单个进程处理多少个请求后回收（防止内存泄漏） | 500 |
| request_terminate_timeout | 单个请求超时时间，0 为不限制 | 0 或 60s |
| slowlog / request_slowlog_timeout | 慢请求日志与阈值 | 按需开启 |

三种 pm 模式的取舍：

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| static | 固定维持 pm.max_children 个进程 | 流量平稳、内存充足，无启动开销 |
| dynamic | 在 min/max_spare 之间弹性伸缩 | 最常用，兼顾内存与突发 |
| ondemand | 按请求启动进程，空闲超时后回收 | 内存极敏感、可接受首次延迟 |

> **注意：** pm.max_children 不是越大越好，每个 PHP 进程约占用 20-50MB 内存，上限 ≈ 可用内存 / 单进程内存。设置过大在并发打满时会被 OOM 杀死，可在 error.log 看到 "server reached pm.max_children setting" 警告，此时应增加内存或优化程序，而不是无上限调大。
{: .sec-pit}

dynamic 三参数的调整顺序：先按内存定 pm.max_children（可用内存除以单进程占用），再定 pm.min_spare_servers 保住突发前的缓冲，让流量低谷时也不用现起进程，最后 pm.start_servers 取两者之间偏小的值。min_spare 设太高，闲时白养一堆进程；max_spare 设太低，波峰一过进程全被回收，下一波又现起，进程数上下震荡。生产上栽过的另一件事：改完 www.conf 用 systemctl reload php-fpm 平滑加载，直接 restart 会把正在处理的请求全断掉。

## LNMP 工作原理 {: .sec-know}

一次动态请求在 LNMP 架构中的流转路径如下：

1. 用户访问网站，请求首先到达 Nginx；
2. Nginx 通过 fastcgi_pass 将动态请求以 FastCGI 协议转发；
3. php-fpm（wrapper）接收到请求后，交给 PHP 解析器处理；
4. PHP 需要数据时，连接 MySQL 读取或写入；
5. PHP 处理完成后，将结果返回给 Nginx，最终响应给用户。

这条链路里只有 .php 结尾的请求会走第 2-5 步，图片、CSS、JS 仍由 Nginx 直接读盘返回——动静分离在 LNMP 里就是靠 `location ~ \.php$` 这一条规则实现的。

## 实现 Nginx 与 PHP 建立关系

第一步：编写 Nginx 配置文件，添加 PHP 解析的 location。

```nginx
location ~ \.php$ {
    root /www;
    fastcgi_index index.php;
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
    fastcgi_pass  127.0.0.1:9000;
    include fastcgi_params;
}
```

编写完成后重启 Nginx 服务。

第二步：编写动态资源文件，验证 PHP 解析是否正常。

```console
[root@web01 conf.d]# cat /html/blog/test_php.php
```

```php
<?php
phpinfo();
?>
```

第三步：进行访问测试，例如访问 `blog.example.com/test_php.php`。

### PHP location 配置详解 {: .sec-expl}

```nginx
location ~ \.php$ {
    root  /html/www;                                    # 站点目录，决定 $document_root
    try_files $uri =404;                                # 脚本不存在直接返回 404
    fastcgi_pass  127.0.0.1:9000;                       # php-fpm 监听地址
    fastcgi_index index.php;                            # 默认首页脚本
    include fastcgi_params;                             # 引入 FastCGI 默认参数
    fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;  # 告知 fpm 脚本绝对路径
}
```

各要素的作用：

- fastcgi_pass：php-fpm 的监听地址。新版 php-fpm 默认监听 Unix Socket（/run/php-fpm/www.sock），用 Socket 时改为 `fastcgi_pass unix:/run/php-fpm/www.sock;`，注意 Nginx 运行用户对 sock 文件要有读写权限；
- SCRIPT_FILENAME：PHP 要执行的文件绝对路径，由 `$document_root$fastcgi_script_name` 拼出；$document_root 取当前 location 的 root 值，root 缺失时变量为空，是 "Primary script unknown" 报错的根源；
- try_files $uri =404：先检查脚本文件是否存在，不存在直接返回 404。这是重要的安全加固：否则 `/test.php/anything.jpg` 这类路径会被交给 php-fpm 处理，配合 php.ini 中 `cgi.fix_pathinfo=1` 可能被利用执行任意 PHP 文件（保持 `cgi.fix_pathinfo=0` 与 try_files 双重保险）；
- include fastcgi_params：引入 /etc/nginx/fastcgi_params，其中已包含 SCRIPT_FILENAME 之外的一批默认参数。

fastcgi_index 的作用也别漏：请求以 / 结尾（访问目录）时，它把 index.php 追加到路径上再交给 fpm，比如 /blog/ 最终执行 /blog/index.php。

## 网站上线实战 {: .sec-prac}

### 第一步：获取代码

使用开源的网站代码（通过 git 获取）：

| 站点 | 开源程序 |
| --- | --- |
| www | DedeCMS（http://www.dedecms.com/） |
| bbs | Discuz（http://www.discuz.net/forum.php） |
| blog | WordPress（https://cn.wordpress.org/） |
| wecenter | WeCenter（http://www.wecenter.com/?copyright） |

### 第二步：解压代码并放入站点目录

```bash
tar xf wordpress-5.2.1.tar.gz
```

将解压后的信息放入站点目录中。

后续更新代码别在生产目录直接解压覆盖：新包解压到临时目录 → diff 配置文件（wp-config.php 这类带环境信息的不能覆盖）→ rsync 同步 → 改属主 → 浏览器回归验证，这是标准动作，生产事故一大半出在"直接覆盖"上。

### 第三步：修改站点目录权限

```bash
chown -R www.www blog
```

### 上传目录与 PHP 执行权限

上传目录是 LNMP 最容易被打穿的入口：用户能传文件，说明目录对运行用户可写；如果传上去的 .php 还能被解析执行，等于开放了任意代码执行。加固两步走：

1. 站点目录整体归 www 属主并保持只读，只对 uploads 这类上传子目录放开写权限；
2. Nginx 对上传路径内的 PHP 一律拒绝解析：

```nginx
location ~* ^/uploads/.*\.php$ {
    deny all;
}
```

php.ini 侧同步收紧：disable_functions 禁掉 exec、shell_exec、system、passthru、proc_open 等高危函数；open_basedir 限定站点目录与上传目录，防止脚本越目录读文件；expose_php = off 不在响应头暴露 PHP 版本。这里有个坑：只改 php.ini 不重载 php-fpm 不生效，改完记得 systemctl reload php-fpm。

### 第四步：进行网站页面初始化操作 {: .sec-prac}

通过浏览器访问站点，按安装向导提示完成页面初始化。

### 第五步：对数据库服务进行配置 {: .sec-expl}

创建数据库：

```sql
create database wordpress;
```

检查：

```sql
show databases;
```

创建数据库管理用户：

```sql
grant all on wordpress.* to 'wordpress'@'localhost' identified by '<your-password>';
```

检查：

```sql
select user,host from mysql.user;
```

> **注意：** 创建数据库的正确写法是 create database wordpress，不要写成 create databases wordpress。
{: .sec-pit}

建库时显式指定字符集：create database wordpress default charset utf8mb4;，emoji 等四字节字符靠 utf8mb4 才存得下，WordPress 新装建议直接用它。

> **注意：** 授权语句中的口令为占位示例，生产环境使用强密码；授权用户按最小权限原则，只授予其所属数据库的权限（wordpress.* 而非 *.*）。
{: .sec-pit}

### 第六步：利用 blog 网站发布博文

初始化完成后登录后台发布一篇带图片的博文，验证三件事：正文中文不乱码（UTF-8 生效）、图片能正常上传显示（uploads 目录权限对了）、访问日志里能看到静态与动态请求分别怎么走（静态由 Nginx 直接返回，动态走 fastcgi_pass）。这一步全通过，LNMP 才算真正交付。

## 数据库远程访问与独立部署

生产中通常把数据库从 Web 服务器剥离，独立部署到 db01，Web 服务器通过授权用户远程连接：

```sql
-- 在数据库服务器上执行：授权网段内的 Web 服务器连接
grant all on wordpress.* to 'wordpress'@'10.0.0.%' identified by '<your-password>';
flush privileges;
```

Web 服务器侧连接时把主机名改为数据库地址：

```php
$conn = mysqli_connect("10.0.0.20", "wordpress", "<your-password>");
```

数据库服务器需要放行监听地址与防火墙：

```bash
vim /etc/my.cnf.d/server.cnf
```

```ini
[mysqld]
bind-address = 0.0.0.0
```

```bash
systemctl restart mariadb
firewall-cmd --add-service=mysql --permanent
firewall-cmd --reload
```

> **注意：** bind-address = 0.0.0.0 会监听所有网卡，务必配合强密码、授权网段限制（'10.0.0.%' 而非 '%'）与防火墙共同收紧暴露面；永远不要把 root 授权为远程可登录。
{: .sec-pit}

Web 侧连接数据库还要留意连接数：php-fpm 每个进程都可能持有若干 MySQL 连接，max_connections 默认只有 151，进程数一多容易出现 Too many connections；PHP 的持久连接会让连接长期占着不放，用之前先算清楚 fpm 进程数与数据库连接上限的乘积关系。

## phpMyAdmin 部署简述

phpMyAdmin 是 PHP 编写的数据库 Web 管理工具，部署步骤如下：

1. 获取软件：EPEL 源可 `yum install phpMyAdmin`，或到 phpmyadmin.net 下载源码包解压到站点目录；
2. 放置代码：解压到 /html/www/phpMyAdmin，权限归 Nginx 运行用户（chown -R www.www）；
3. 配置连接：复制 config.sample.inc.php 为 config.inc.php，设置 $cfg['blowfish_secret'] 为随机字符串；
4. 访问验证：LNMP 环境中 Nginx 的 `location ~ \.php$` 已就绪，浏览器访问 `http://www.example.com/phpMyAdmin/index.php`，用数据库用户登录。

> **注意：** phpMyAdmin 能操作全库，必须加固：加 auth_basic 认证、用 allow/deny 限制内网访问、尽快删除安装目录（setup）并限制配置文件权限，生产环境建议只通过跳板机或 VPN 访问。
{: .sec-pit}

PHP 升级后 phpMyAdmin 白屏，多半是版本不兼容：老版本 phpMyAdmin 不支持 PHP 8，升级 PHP 时同步更新 phpMyAdmin 到 5.x 的新版本。

## LNMT 架构概念（+Tomcat） {: .sec-know}

LNMT 即 Linux + Nginx + MySQL/MariaDB + Tomcat，与 LNMP 的唯一区别是用 Tomcat（Java）替换 PHP 作为动态层：

- 适用场景：Java 应用（JSP、Servlet、Spring 等），安卓后端、大型企业系统常用；
- 部署方式：安装 JDK（`dnf install java-17-openjdk`），下载 Tomcat 解压即用（bin/startup.sh 启动），war 包放入 webapps 目录自动部署；
- 与 Nginx 联动：Nginx 处理静态资源，动态请求 `proxy_pass http://127.0.0.1:8080;` 反向代理给 Tomcat；Tomcat 也提供 AJP 连接器（8009 端口），可用 proxy_ajp 但生产更推荐 HTTP 代理；
- 其余部分（数据库、负载均衡、缓存、监控）与 LNMP 完全一致，Nginx 层配置通用。

什么时候选 LNMT：团队技术栈是 Java、或有现成 war 包要部署时；PHP 站点（WordPress、Discuz、DedeCMS 生态）继续用 LNMP。两者可以共存于同一台 Nginx，不同域名各配各的 location，互不影响。

## LNMP 一键部署思路

批量部署 LNMP 推荐用 Ansible 编排，核心思路是按角色拆分职责，一次编写批量执行：

| 角色 | 职责 |
| --- | --- |
| common | 修改 yum 源、关闭 SELinux、配置 firewalld、统一内核与句柄参数 |
| nginx | 安装 Nginx、用模板分发虚拟主机配置、handler 里做 reload |
| php | 安装 PHP 与 php-fpm、分发 www.conf、保证与 Nginx 用户一致 |
| mysql | 安装 MariaDB、启动服务、建库建用户（变量传密码，不落明文） |
| web | 部署网站代码、设置目录属主、触发 php-fpm/nginx reload |

执行流程：common → nginx/php/mysql 并行 → web → 冒烟测试（curl 测试页）。密码等敏感信息用 Ansible Vault 加密，剧本与配置统一纳入版本管理，实现可重复、可回滚的环境交付。

先在单台机器手搭一遍再写 playbook：没手搭过的人写出来的剧本，排障时根本说不清卡在哪一层；手搭过一遍，Ansible 只是把敲过的命令固化下来。

## 常见错误与排错 {: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 502 Bad Gateway | php-fpm 未启动；fastcgi_pass 地址与 php-fpm 实际监听不一致（TCP 9000 vs Unix Socket） | `systemctl status php-fpm`、`ss -lntp \| grep 9000`、`ls -l /run/php-fpm/www.sock` | 启动 php-fpm；按实际监听方式修正 fastcgi_pass |
| 502 且 error.log 报 Primary script unknown | SCRIPT_FILENAME 拼接错误：location 内没有 root，$document_root 为空 | `tail /var/log/nginx/error.log` | 在 location 中补上 root，或修正 $document_root 引用 |
| 403 Forbidden | Nginx 与 php-fpm 运行用户不一致；站点目录属主不对 | `ps aux \| grep -E "nginx\|php-fpm"`、`ls -ld /html/www` | 统一为 www 用户；chown -R www.www 站点目录 |
| MySQL 无法启动 | /tmp 权限为 1777；数据目录属主或权限不对 | `ls -ld /tmp`、`ls -ld /var/lib/mysql`、`journalctl -u mariadb` | 修正 /tmp 为 755；数据目录归 mysql 用户、权限 700 |
| 远程连接数据库被拒 | 未授权对应用户与来源主机；bind-address 未放行；防火墙拦截 | `select user,host from mysql.user;`、`firewall-cmd --list-all` | 补授权（'user'@'10.0.0.%'）、放开 bind-address、放行 3306 |
| 页面能开但样式全无 | 静态 location 被 PHP location 抢先；mime.types 未加载 | `curl -I http://www.example.com/style.css` | 调整 location 顺序，确认 include mime.types |
| 上传文件报 413 | client_max_body_size 默认 1m | 复现上传查看响应 | 调大 client_max_body_size 与 PHP 的 upload_max_filesize |

### 辨析：500 与 502 在 LNMP 中的分界

两个码都常见，来源完全不同：

- 502 出在 Nginx 与 php-fpm 之间：连不上 9000、sock 权限不对、fpm 进程全忙或崩溃，请求根本没进 PHP 代码；
- 500 出在 php-fpm 之内：代码语法错、函数被 disable_functions 禁用、文件权限读不了、内存超限，fpm 正常接了请求但脚本执行失败。

排查顺序因此是先看 Nginx 的 error.log 定位 502，再翻 php-fpm 日志与业务日志定位 500，两类日志分属两处现场，别混着找。

## 排错与注意事项 {: .sec-ts}

- SELinux 未关闭或防火墙未放行时，网站访问可能出现异常，部署前先关闭。
- /tmp 目录权限为 1777 时，MySQL 服务无法启动。
- php-fpm 运行用户（www）与 Nginx 运行用户不一致时，动态页面会出现权限类错误。
- 数据库初始化后，务必按照初始化输出的提示信息设置 root 密码。
- 数据库服务直接安装在 Web 服务器本地存在安全与性能隐患，企业中通常将数据库独立部署到 db01，并授权远程用户供 Web 服务器连接（迁移方法详见《负载均衡服务》一文）。

这份清单值得贴在工位上：LNMP 的故障八成落在这几条里，剩下两成翻各自的日志——Nginx 的在 /var/log/nginx/error.log，php-fpm 的在 /var/log/php-fpm/，MariaDB 的用 journalctl -u mariadb 看。

## 现代环境补充 {: .sec-ext}

CentOS 7 已于 2024 年 6 月停止维护，Rocky Linux、AlmaLinux、CentOS Stream 上的对应做法：

| 旧命令/做法 | 新命令/做法 | 说明 |
| --- | --- | --- |
| `yum install php71w...`（webtatic） | Remi 仓库 `dnf module install php:remi-8.2` 或 AppStream php 模块 | webtatic 已停止维护，Remi 是主流第三方 PHP 源 |
| `mysql_install_db` 手动初始化 | 首次 `systemctl start mariadb` 自动初始化数据目录 | MariaDB 10.x 起自动完成 |
| `service mariadb start` | `systemctl start mariadb` | service 命令已废弃 |
| `netstat -lntp` | `ss -lntp` | netstat 已废弃 |
| 关闭 SELinux：`setenforce 0` 改 /etc/selinux/config | 操作相同，但建议学习按策略放行而非长期 permissive | SELinux 机制未变 |
| `iptables -A INPUT -p tcp --dport 3306 -j ACCEPT` | `firewall-cmd --add-service=mysql --permanent` | 防火墙改用 firewalld/nftables |
| MySQL 5.6/5.7 | MariaDB 10.5/10.11（系统默认）或 MySQL 8.0（官方源） | 命令与语法高度兼容 |

其他要点：

- Rocky/Alma 上 SELinux 若需长期开启，可用 `setsebool -P httpd_can_network_connect_db on` 放行 Nginx/PHP 连接数据库，`restorecon -Rv /html/www` 修正站点目录上下文；
- MariaDB 10.4+ root 默认 unix_socket 认证，本机系统 root 直接 `mysql` 即可登录，无需密码；
- 密码统一用强随机值并通过 Ansible Vault 或密钥管理系统注入，禁止明文入库。

## 课后思考 {: .sec-think}

1. 上传 WordPress 主题时提示主题比较大，报 413 Request Entity Too Large，如何解决？
2. 图片保存在服务器什么位置？如何将图片保存在存储服务器中？
3. 数据库服务安装在 Web 服务器本地有没有问题？
4. 如何将数据库数据迁移到指定服务器中？

参考思路：

> **答案：**
> 1. Nginx 的 client_max_body_size 默认只有 1m，在对应 server/location 中调大（如 50m），同时调大 PHP 的 upload_max_filesize 与 post_max_size 并重启 php-fpm，两端都放开才能上传大文件。
> 2. WordPress 的媒体文件默认存放在站点目录的 wp-content/uploads/ 下（按年月分目录）。要集中存储可以：用 NFS 把存储服务器目录挂载到 Web 服务器（见《存储服务 NFS》一文），或把 uploads 目录单独配置为静态站点/对象存储域名，由 Nginx 直接对外提供。
> 3. 有问题：安全上数据库与 Web 同机，Web 被攻破会直接拖走数据；性能上两者争抢 CPU、内存与 IO；备份与迁移也不灵活。生产上应把数据库独立部署到 db01，Web 服务器通过授权用户远程连接。
> 4. 常规路径：在源库用 mysqldump 导出（`mysqldump --single-transaction -uroot wordpress > wordpress.sql`），在目标库创建数据库与授权用户后导入；数据量大或要求低停机时用主从复制/主主同步在线迁移（思路见《实时同步服务》《负载均衡服务》两文）。

## 自测题 {: .sec-prac}

1. 一条动态请求 `blog.example.com/test_php.php`，从浏览器到 PHP 执行结果返回，中间经过了哪些组件与协议？
2. `location ~ \.php$` 里 fastcgi_param SCRIPT_FILENAME 写成 `$document_root$fastcgi_script_name`，各变量含义是什么？为什么 location 内必须定义 root？
3. php-fpm 的 pm 三种模式分别是什么场景？pm.max_children 设置过大有什么风险？
4. 浏览器访问 PHP 页面返回 502，请按顺序给出至少三条排查命令。
5. 要把数据库独立部署到 db01 并允许 Web 服务器连接，数据库侧至少需要哪三步操作？

> **答案：**
> 1. 浏览器经 DNS 解析到 Nginx → Nginx 按 server_name/location 匹配到 PHP location → 通过 FastCGI 协议经 fastcgi_pass 转发给 php-fpm → php-fpm 交给 PHP 解释器执行 test_php.php → PHP 需要数据时经 MySQL 协议连数据库 → 执行结果经 php-fpm、FastCGI 返回 Nginx → Nginx 响应给浏览器。
> 2. $document_root 是当前 location 的 root 值（如 /html/www），$fastcgi_script_name 是请求中的脚本路径（如 /test_php.php），两者拼出脚本的绝对路径告知 php-fpm 要执行哪个文件。location 内若不定义 root，$document_root 为空，SCRIPT_FILENAME 变成相对路径，php-fpm 找不到脚本，error.log 报 "Primary script unknown" 并返回 502。
> 3. static：固定进程数，适合流量平稳、内存充足；dynamic：按空闲进程数弹性伸缩，最常用；ondemand：按需启动、空闲回收，适合内存敏感场景。max_children 过大会让所有进程常驻内存，并发打满时极易触发系统 OOM，把 php-fpm 甚至数据库一起杀掉，应按 可用内存/单进程内存 估算。
> 4. 示例顺序：`systemctl status php-fpm`（进程是否存活）→ `ss -lntp | grep 9000` 或 `ls -l /run/php-fpm/www.sock`（php-fpm 监听方式与 fastcgi_pass 是否一致）→ `tail -f /var/log/nginx/error.log`（看具体报错）→ `ps aux | grep php-fpm` 与 `ls -ld /html/www`（用户与权限）。对应处理：启动服务、修正 fastcgi_pass、补 root、统一用户。
> 5. 数据库侧三步：① 修改 server.cnf 的 bind-address 放行网卡并重启；② 执行授权 `grant all on wordpress.* to 'wordpress'@'10.0.0.%' identified by '<your-password>'; flush privileges;`；③ firewalld 放行 3306（`firewall-cmd --add-service=mysql --permanent && firewall-cmd --reload`）。Web 侧改用数据库内网地址连接即可。
