## 15.1 基本概念
{: .sec-expl}

### 15.1.1 多态到底解决什么问题
{: .sec-know}

先看没有多态时的写法。图形编辑器里要画一堆形状，C 程序员的直觉是带类型标签的结构体加 switch：

```cpp
// no_poly.cpp —— 需要 -std=c++20
#include <iostream>
#include <vector>

enum class Kind { Circle, Rect };

struct Shape {
    Kind kind;
    double a;   // 圆的半径 / 矩形的宽
    double b;   // 矩形的高（圆用不到）
};

double area(const Shape& s) {
    switch (s.kind) {                    // 每加一种形状，所有 switch 都要改
        case Kind::Circle: return 3.141592653589793 * s.a * s.a;
        case Kind::Rect:   return s.a * s.b;
    }
    return 0.0;
}

int main() {
    std::vector<Shape> shapes{
        {Kind::Circle, 2.0, 0.0},
        {Kind::Rect,   3.0, 4.0},
    };
    for (const Shape& s : shapes)
        std::cout << area(s) << '\n';
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra no_poly.cpp -o no_poly && ./no_poly
```

```text
12.5664
12
```

这段代码能跑，但改起来疼：每新增一种形状，`area`、`perimeter`、`serialize`……所有按 `kind` 分派的函数都要再添一个 case，漏一处就是线上 bug。多态把这件事反过来：形状自己知道怎么算面积，调用方只管说"算"，具体执行哪份代码由类型决定。

### 15.1.2 两条大路：静态与动态
{: .sec-know}

C++ 提供两大类多态，分水岭是**绑定发生的时间**：

| 路线 | 代表机制 | 绑定时间 | 调用形态 |
| --- | --- | --- | --- |
| 静态多态 | 函数重载、模板、CRTP | 编译期 | 直接调用，可内联 |
| 动态多态 | 虚函数 | 运行期 | 经 vtable 一次间接跳转 |

判断用哪条，就问一句：**实现要不要在运行期才确定？** 插件系统、GUI 控件树、序列化器注册表——实现来自配置或用户输入，只能动态多态。算法对不同数值类型通用、类型集合在编译期封闭——模板更合适，还能白拿内联。两条路不互斥，同一系统里常常混用：接口层虚函数，热路径内部模板。

### 15.1.3 代价对比表
{: .sec-know}

选型不是"哪个高级"，是拿不同的钱买不同的货：

| 维度 | 静态多态（重载/模板/CRTP） | 动态多态（虚函数） |
| --- | --- | --- |
| 性能 | 零间接开销，可内联、可去虚化 | 每次调用一次间接跳转，内联受阻 |
| 灵活性 | 类型集合编译期封闭，运行期不能换 | 运行期任意换实现，支持插件 |
| 编译依赖 | 实现必须在头文件，改动波及所有使用者 | 接口与实现可分离，编译防火墙 |
| 二进制兼容 | 每种类型一份代码，改模板要重编全部实例 | vtable 布局稳定，动态库可只发 .so |
| 代码体积 | 每类型一份实例化副本，可能膨胀 | 一份函数体，所有类型共享 |
| 错误时机 | 编译期报错（好处） | 错误推迟到运行期（纯虚调用、空 vptr） |

CRTP（奇异递归模板模式）是静态多态里最像虚函数的写法，值得看一眼对照：

```cpp
// crtp.cpp —— 需要 -std=c++20
#include <iostream>

template <class D>
struct Shape {
    double area() const { return static_cast<const D*>(this)->area_impl(); }
};

struct Circle : Shape<Circle> {
    double r;
    explicit Circle(double r) : r(r) {}
    double area_impl() const { return 3.141592653589793 * r * r; }
};

struct Square : Shape<Square> {
    double side;
    explicit Square(double s) : side(s) {}
    double area_impl() const { return side * side; }
};

// 注意：Circle 和 Square 没有共同基类，print_area 只能是模板
template <class S>
void print_area(const S& s) { std::cout << s.area() << '\n'; }

int main() {
    print_area(Circle{1.0});   // 3.14159
    print_area(Square{2.0});   // 4
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra crtp.cpp -o crtp && ./crtp
```

```text
3.14159
4
```

代价立刻显形：`Circle` 和 `Square` 没有共同类型，`std::vector<Shape&>` 这种"异构容器"装不了它们——想放进一个数组统一遍历，就得回到虚函数。这正是两条路的能力边界。

### 15.1.4 辨析：多态与"接口一致"
{: .sec-iv}

两个类都有 `draw()`，不代表它们构成多态关系。多态要求存在**统一的调用点**：同一个表达式 `x.draw()`，根据 `x` 的动态类型执行不同函数。重载是"编译期按参数挑函数"，本质是语法糖；虚函数才是运行期分派。后面 15.8 会看到，连"派生类里写了同名函数"都不自动构成任何一种多态——名字查找的规则会给你惊喜。

## 15.2 先看宏多态
{: .sec-expl}

### 15.2.1 宏怎么"伪造"多态
{: .sec-know}

C++98 之前、甚至模板普及之前的代码库里，有一种靠记号粘贴批量生成代码的手法，行话叫"宏泛型"：

```cpp
// macro_poly.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

// 宏仿"泛型"：记号粘贴生成类型
#define DEFINE_PAIR(T) struct Pair_##T { T a; T b; T max() const { return a > b ? a : b; } };
DEFINE_PAIR(int)
DEFINE_PAIR(double)

// 现代替代：一个模板顶掉所有 DEFINE_PAIR
template <class T>
requires std::is_arithmetic_v<T>
struct Pair {
    T a{}, b{};
    T max() const { return a > b ? a : b; }
};

int main() {
    Pair_int pi{1, 2};
    Pair<double> pd{1.5, 2.5};
    std::cout << pi.max() << ' ' << pd.max() << '\n';
    // Pair<std::string> ps{"ab", "cd"};
    // 编译错：is_arithmetic 约束当场拦下，错误指向这一行
}
```

```bash
g++ -std=c++20 -Wall -Wextra macro_poly.cpp -o mp && ./mp
```

```text
2 2.5
```

### 15.2.2 为什么不推荐
{: .sec-ts}

宏版有三宗罪，每一条都真疼过：

| 罪状 | 具体表现 | 模板版的对应改善 |
| --- | --- | --- |
| 无类型检查 | `DEFINE_PAIR(std::string)` 里 `std::string` 带冒号，粘贴后不是合法标识符；错误在宏展开的深处才爆 | concept 约束在调用点报错，信息直指那一行 |
| 调试困难 | 调试器单步进入的是展开后的一行超长代码，断点打不进去；报错没有行号语义 | 模板函数是真实函数，可单步、可打断点 |
| 作用域失控 | 宏不做名字查找，不认 namespace，`#define max` 能和 `std::max` 打架（Windows 头文件干过） | 名字遵循作用域规则，可被 using 限制 |

第四条没上表但同样致命：宏展开不产生符号信息，二进制里查不到 `Pair_int::max` 对应的调试描述，崩溃栈是乱的。

### 15.2.3 现代替代清单
{: .sec-ext}

| 老宏的用途 | 现代替代 | 版本 |
| --- | --- | --- |
| 宏泛型（记号粘贴生成类型） | 类模板 + concept 约束 | C++98 / C++20 |
| 表达式级"泛型"（MAX/SWAP） | 函数模板、`constexpr` 函数 | C++98 / C++11 |
| X-macro 列举枚举与字符串 | `constexpr` 数组、`using enum`、反射（未来） | C++20 |
| 条件编译裁剪代码 | `if constexpr` | C++17 |

真要留宏，只留那种"必须操作文本"的：`__FILE__` 拼接、日志注册。逻辑一概不用宏写。

## 15.3 虚函数
{: .sec-expl}

### 15.3.1 第一个例子：vtable 接管分派
{: .sec-prac}

```cpp
// first_virtual.cpp —— 需要 -std=c++20
#include <iostream>
#include <memory>
#include <vector>

struct Shape {
    virtual double area() const = 0;     // 虚函数：派生类按各自方式实现
    virtual ~Shape() = default;          // 虚析构：见 15.3.4
};

struct Circle : Shape {
    double r;
    explicit Circle(double r) : r(r) {}
    double area() const override { return 3.141592653589793 * r * r; }
};

struct Rect : Shape {
    double w, h;
    Rect(double w, double h) : w(w), h(h) {}
    double area() const override { return w * h; }
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(2.0));
    shapes.push_back(std::make_unique<Rect>(3.0, 4.0));
    for (const auto& s : shapes)
        std::cout << s->area() << '\n';   // 同一个调用点，两种实现
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra first_virtual.cpp -o fv && ./fv
```

```text
12.5664
12
```

15.1.1 里做不到的"异构容器统一遍历"，虚函数一句话解决。

### 15.3.2 vtable 与 vptr：虚调用到底发生了什么
{: .sec-ver}

每个含虚函数的类，编译器为它生成一张**虚函数表（vtable）**：一张按声明顺序排列的函数指针表，同类的所有对象共享一份。每个该类对象的开头藏一个指针 **vptr**，指向所属类的 vtable。构造对象时，构造函数把 vptr 填成当前类的表。

```text
d 对象（栈上）              Derived 的 vtable（只读段，全体共享）
+------------------+       +---------------------------+
| vptr ────────────┼────>  | &Derived::area            |
+------------------+       | &Derived::~Derived (D1)   |
| r = 2.0          |       | &Derived::~Derived (D0)   |
+------------------+       +---------------------------+
```

`s->area()` 的机器级行为：从对象取出 vptr，按 `area` 在表里的槽位取出函数指针，间接跳转。虚析构在表里占两个槽位是 Itanium ABI 的惯例（分别对应"析构自己"和"析构后释放内存"两种调用形式）。验证手段不用猜：`objdump -dC ./fv` 反汇编，`s->area()` 的调用处是一条 `call *offset(%rax)` 形式的**间接调用**，而普通函数调用是 `call <直接地址>`。这就是"虚调用比直接调用慢"的全部物理原因——多一次内存读取，多一个不可预测的跳转目标。

一次间接跳转本身只要一两个时钟周期（命中缓存时），真正的损失是**内联失效**：编译器不知道运行期跳到哪，没法把小函数体展开、没法跨函数优化。所以虚调用的实际代价从"几乎免费"（分支预测成功且上下文简单）到"十倍以上"（小函数、紧密循环、失去向量化）不等，量级取决于函数体多小、调用多密。

去虚化（devirtualization）是编译器把虚调用变回直接调用的优化：静态类型已是最终类型，或叶子类标了 `final`，编译器就敢把 `s.area()` 替换成直接调用并内联——一个 `const Square&` 参数上的 `area()` 调用，在 -O2 下可能被整体折叠成 `s.side * s.side`；而静态类型是基类的同款函数一般保留虚调用。由此得出三个工程结论：能写成值或模板的热路径别用虚函数；叶子类标 `final` 白拿优化；性能敏感处用实测说话（15.9.2）。

> **注意：** vtable 布局不是 C++ 标准的一部分，是各 ABI（Itanium、MSVC）的约定。不要写依赖槽位顺序的代码，跨编译器传虚对象前先确认 ABI 一致。
{: .sec-note}

### 15.3.3 构造函数里调用虚函数
{: .sec-warn}

> **坑：** 构造（和析构）期间，动态类型就是"正在构造的那一层"的类型。基类构造函数里调虚函数，执行的是**基类版本**，不会下探到派生类——vptr 是一层一层填的，走到基类构造时它还指着基类的表。
{: .sec-pit}

```cpp
// ctor_virtual.cpp —— 需要 -std=c++20
#include <iostream>

struct Base {
    Base() {
        std::cout << "Base ctor: ";
        describe();                      // 看似想调派生类版本，实际调 Base::describe
    }
    virtual ~Base() = default;
    virtual void describe() const { std::cout << "I am Base\n"; }
};

struct Derived : Base {
    int x = 42;                          // 注意：执行 Base() 时它还没初始化
    void describe() const override { std::cout << "I am Derived, x=" << x << '\n'; }
};

int main() {
    Derived d;
    d.describe();                        // 对象构造完毕，正常多态
}
```

```bash
g++ -std=c++20 -Wall -Wextra ctor_virtual.cpp -o cv && ./cv
```

```text
Base ctor: I am Base
I am Derived, x=42
```

这个行为不是缺陷而是自保：假设构造期间真的调到 `Derived::describe`，它会读还没初始化的 `x`——未定义行为。语言宁可"多态失效"也不让你踩未初始化数据。更险的是构造期间调用**纯虚函数**：编译器往往能放过（链接期或运行期报 `pure virtual method called` 后终止），标准定义为 undefined behavior。规避手法是把"构造后要做的初始化"做成显式的 `init()` 成员函数，或者用工厂函数在对象完全构造后再回调。

### 15.3.4 虚析构规则
{: .sec-know}

> **规则：** 通过基类指针 `delete` 一个派生类对象，而基类析构不是虚的——undefined behavior。实际后果通常是派生部分的析构不执行：成员没释放、RAII 资源泄漏。
{: .sec-warn}

判断口诀：**这个类会被当作接口用（有虚函数、会以基类指针管理派生对象），析构就该是虚的；不会被继承着删，析构保持非虚。** 两者都不沾的类（比如纯工具类），有人会标 `protected` 析构，从物理上禁止经基类指针删除。`std::vector`、`std::string` 就是非虚析构的典范——它们不是多态基类，标准库的设计意图就不是让你继承。

```cpp
// dtor_demo.cpp —— 需要 -std=c++20
#include <iostream>

struct GoodBase { virtual ~GoodBase() { std::cout << "~GoodBase\n"; } };
struct GoodDerived : GoodBase { ~GoodDerived() override { std::cout << "~GoodDerived\n"; } };

struct BadBase { ~BadBase() { std::cout << "~BadBase\n"; } };    // 非虚析构
struct BadDerived : BadBase { ~BadDerived() { std::cout << "~BadDerived\n"; } };

int main() {
    {
        std::unique_ptr<GoodBase> g = std::make_unique<GoodDerived>();
    }   // 输出两行析构，顺序正确
    BadBase* b = new BadDerived;
    delete b;       // undefined behavior：本环境常见输出只有 ~BadBase
}
```

```bash
g++ -std=c++20 -Wall -Wextra dtor_demo.cpp -o dt && ./dt
```

```text
~GoodDerived
~GoodBase
~BadBase
```

虚析构的连带效应：它让类多出一张 vtable、对象多一个 vptr（8 字节，LP64）。所以"有没有虚函数"本质上由"要不要多态"决定，不是风格问题。

### 15.3.5 协变返回类型
{: .sec-know}

覆盖函数的返回类型通常必须与基类完全一致，唯一的例外是**协变（covariant）**：基类虚函数返回 `Base*`（或 `Base&`），派生类覆盖版可以返回更具体的 `Derived*`（或 `Derived&`），要求派生类是基类返回类型的直接或间接派生，且指针/引用指向的类在覆盖点完整。

```cpp
// covariant.cpp —— 需要 -std=c++20
#include <iostream>

class Animal {
public:
    virtual ~Animal() = default;
    virtual Animal* clone() const = 0;      // 返回基类指针
    virtual void speak() const = 0;
};

class Dog : public Animal {
public:
    Dog* clone() const override { return new Dog(*this); }   // 协变：返回 Dog*
    void speak() const override { std::cout << "woof\n"; }
};

int main() {
    Dog d;
    Dog* d2 = d.clone();      // 协变的好处：不用写 static_cast<Dog*>(...)
    d2->speak();
    Animal* a = d.clone();    // 向上转换依旧自然
    a->speak();
    delete d2;
    delete a;
}
```

```bash
g++ -std=c++20 -Wall -Wextra covariant.cpp -o cov && ./cov
```

```text
woof
woof
```

> **坑：** 智能指针不参与协变。`std::unique_ptr<Dog>` 不构成 `std::unique_ptr<Animal>` 的协变返回——编译报错。惯用解法是 NVI 包一层：公有非虚的 `std::unique_ptr<Dog> clone()` 调用私有的虚函数返回裸指针，再包进智能指针。
{: .sec-pit}

### 15.3.6 override 与 final
{: .sec-best}

`override`（C++11）写在覆盖函数声明的尾部，声明"我要覆盖基类虚函数"。写错了签名、基类根本不是虚函数、const 缺了——编译器立刻报错，而不是给你一个安静的隐藏。`final` 有两个位置：加在虚函数上禁止再往下覆盖，加在类名上禁止整个类被继承（同时给去虚化送助攻，见 15.3.2）。

```cpp
// override_demo.cpp —— 需要 -std=c++20
#include <iostream>

struct Base {
    virtual ~Base() = default;
    virtual void run(int speed) const { std::cout << "Base run\n"; }
};

struct Ok : Base {
    void run(int speed) const override { std::cout << "Ok run\n"; }   // 签名一致，通过
};

// struct Bad : Base {
//     void run(int speed) override { }         // 编译错：漏了 const，不构成覆盖
//     void run(long speed) const override { }  // 编译错：int 变 long，不是覆盖
// };

struct Leaf final : Ok {};                    // final 加在类名上：禁止再被继承

int main() {
    Ok o;
    Leaf l;
    Base& rb = o;
    Base& rl = l;
    rb.run(1);
    rl.run(2);
}
```

```bash
g++ -std=c++20 -Wall -Wextra override_demo.cpp -o od && ./od
```

```text
Ok run
Ok run
```

规范建议：现代代码里**每一个覆盖函数都写 override**，没有一个例外。`virtual` 关键字只用在基类第一次声明处，派生类的 `virtual` 是噪音。

### 15.3.7 默认参数静态绑定：经典坑与 NVI
{: .sec-ts}

> **坑：** 默认实参在**编译期按调用的静态类型**填入，函数体却按**运行期动态类型**执行。两者走的是不同的绑定通道，于是会出现"派生类版本 + 基类默认值"的缝合怪。
{: .sec-pit}

```cpp
// default_arg.cpp —— 需要 -std=c++20
#include <iostream>

struct Widget {
    virtual ~Widget() = default;
    virtual void draw(int depth = 1) const { std::cout << "Widget depth=" << depth << '\n'; }
};

struct FancyWidget : Widget {
    void draw(int depth = 9) const override { std::cout << "Fancy depth=" << depth << '\n'; }
};

int main() {
    FancyWidget fw;
    Widget& w = fw;
    w.draw();        // 动态分派到 FancyWidget::draw，默认实参却取 Widget 的 1
    fw.draw();       // 静态类型 FancyWidget：默认实参 9
}
```

```bash
g++ -std=c++20 -Wall -Wextra default_arg.cpp -o da && ./da
```

```text
Fancy depth=1
Fancy depth=9
```

标准为什么不把默认实参也做成动态的？因为默认实参是编译期文本替换，没有运行期载体；改成动态要把它塞进 vtable，代价摊到所有函数上。语言选择了简单，责任交给程序员。

解法是 **NVI（Non-Virtual Interface，非虚接口）惯用法**：公有函数非虚，负责默认实参、参数校验、前后处理；真正的可变点藏进私有的虚函数，不带默认实参。这也是 Herb Sutter 多年推广的接口设计：

```cpp
// nvi.cpp —— 需要 -std=c++20
#include <iostream>

class Report {
public:
    void render(int indent = 2) const {          // 非虚：统一入口，默认值在这里定
        std::cout << "== begin ==\n";
        do_render(indent);
        std::cout << "== end ==\n";
    }
    virtual ~Report() = default;
private:
    virtual void do_render(int indent) const {   // 虚：只暴露可变点，不带默认实参
        std::cout << "generic body, indent=" << indent << '\n';
    }
};

class MarkdownReport : public Report {
    void do_render(int indent) const override {
        std::cout << "# markdown body, indent=" << indent << '\n';
    }
};

int main() {
    MarkdownReport m;
    Report& r = m;
    r.render();          // 默认值统一由 Report::render 控制，不存在缝合怪
    r.render(4);
}
```

```bash
g++ -std=c++20 -Wall -Wextra nvi.cpp -o nvi && ./nvi
```

```text

# markdown body, indent=2
== end ==
== begin ==
# markdown body, indent=4
== end ==
```

## 15.4 抽象类
{: .sec-expl}

### 15.4.1 纯虚函数与不可实例化
{: .sec-know}

声明时写 `= 0` 的虚函数是**纯虚函数**：派生类必须给出实现（或继续保持纯虚）。只要类里存在纯虚函数（自己声明的，或从基类继承且未覆盖的），这个类就是**抽象类**，不能创建对象，只能作为基类被继承或经引用/指针使用。

```cpp
// pure_virtual.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

class Serializer {
public:
    virtual ~Serializer() = default;
    virtual void write(const std::string& s) const = 0;   // 纯虚：接口契约
};

// = 0 不妨碍给纯虚函数提供实现体，但实现必须写在类外
void Serializer::write(const std::string& s) const {
    std::cout << "[base log] writing " << s.size() << " bytes\n";
}

class JsonSerializer : public Serializer {
public:
    void write(const std::string& s) const override {
        Serializer::write(s);                // 显式调用纯虚函数的实现体
        std::cout << "{ \"data\": \"" << s << "\" }\n";
    }
};int main() {
    JsonSerializer js;
    js.write("hello");
    // Serializer ser;   // 编译错：抽象类不能实例化
    // Serializer* p = new Serializer;   // 同样编译错
}
```

```bash
g++ -std=c++20 -Wall -Wextra pure_virtual.cpp -o pv && ./pv
```

```text
[base log] writing 5 bytes
{ "data": "hello" }
```

### 15.4.2 `= 0` 也可以有实现体
{: .sec-know}

上面代码里 `Serializer::write` 有函数体，这完全合法，而且有用武之地：把"所有派生类都要做的公共部分"写进纯虚函数的实现体，派生类覆盖版通过 `Base::write(...)` 显式调用。常见于日志、加锁、参数检查这类横切逻辑。纯虚函数的实现体不影响"抽象类不能实例化"这条规则——`= 0` 表达的是"不提供默认行为作为唯一实现"，而非"没有代码"。

派生类忘记覆盖某个纯虚函数时，它自己变成抽象类，错误在 `new` 那一行才暴露——报错信息是"cannot allocate an object of abstract type"，会把没实现的函数列出来，遇到别慌，顺着列表补 override 就行。

### 15.4.3 辨析：抽象类与"接口"
{: .sec-iv}

| 特征 | 抽象类（含数据/实现的纯虚基类） | 接口式基类（纯虚 + 无数据） |
| --- | --- | --- |
| 成员变量 | 可有 | 通常没有（有就不是纯接口） |
| 非虚函数 | 可有（模板方法骨架） | 通常没有 |
| 构造函数 | 有（供派生类调用） | 无意义，常写 protected |
| 析构函数 | 虚或 protected | 必须虚或 protected |
| 用途 | 骨架 + 可变点（NVI 天然形态） | 纯契约，多实现互换 |

C++ 没有单独的 interface 关键字，"接口"是一种约定俗成的类形态。Java/C# 背景的人注意：C++ 的抽象类能力更强也更危险——它有数据、有构造，意味着派生类和它耦合更深；纯接口式基类加 NVI 是最稳的组合。

## 15.5 运算符重载
{: .sec-expl}

### 15.5.1 可重载与不可重载清单
{: .sec-know}

运算符重载是"给自定义类型接入语言内置记号"的机制，`a + b` 既可以调内置加法，也可以调你的 `operator+`。但不是所有记号都开放：

**不可重载的四个运算符：** `::`（作用域解析）、`.`（成员访问）、`.*`（成员指针访问）、`?:`（条件运算符）。共同点是它们的结果由语言语义硬性决定——改了会破坏程序的基本结构，所以标准直接锁死。

**不在重载体系里的关键字设施：** `sizeof`、`typeid`、`alignof`、`decltype`、`noexcept`。它们长得像运算符但属于语言内省设施，重载体系碰不到。

可重载的运算符按类别和使用建议整理如下：

| 类别 | 运算符 | 建议形式 |
| --- | --- | --- |
| 算术 | `+` `-` `*` `/` `%` | 非成员（对称性） |
| 复合赋值 | `+=` `-=` `*=` `/=` `%=` | 成员 |
| 比较 | `==` `!=` `<` `<=` `>` `>=` `<=>` | 非成员，C++20 可默认化 |
| 逻辑 | `&&` \|\| | 别重载：会丧失短路求值与求值顺序 |
| 位运算 | `&` \| `^` `~` `<<` `>>` | 按语义；流插入用非成员（15.7） |
| 下标/调用/解引用 | `[]` `()` `->` `->*` | 必须成员（`->*` 除外，它成员或非成员都行） |
| 赋值 | `=` | 必须成员 |
| 自增自减 | `++` `--` | 成员；后置版加哑元 `int` 参数区分 |
| 内存管理 | `new` `new[]` `delete` `delete[]` | 成员或全局（15.5.6） |

`&&` 和 `||` 那一行要单独强调：重载版是普通函数调用，两个操作数都会被求值、顺序也不保证——写了短路依赖的代码会悄悄变质。实践里几乎不该重载它们。

### 15.5.2 成员还是非成员：选择准则
{: .sec-iv}

判定规则一句话：**左操作数必须是本类对象、或运算符天然不对称的，用成员；左操作数可能是"别的东西"（int、流、字面量）或要保证对称性的，用非成员。**

| 运算符 | 必须成员？ | 原因 |
| --- | --- | --- |
| `=` 赋值 | 是 | 保证赋值目标确实是本类，防误用与怪异转换 |
| `[]` 下标 | 是 | 语义上就是对"自己"的成员寻址 |
| `()` 调用 | 是 | 函数对象的核心 |
| `->` 箭头 | 是 | 智能指针与代理的专用通道 |
| `+` `-` `==` `<` 等 | 建议非成员 | 让左操作数也能经转换匹配，`2 + x` 和 `x + 2` 表现一致 |

为什么 `+` 要非成员？假如 `operator+` 是 `Money` 的成员且只接受 `Money`，`2.5 + money` 这个表达式里左操作数是 `double`，成员运算符根本不参与——右边怎么转换都救不了左边。非成员版两个参数都能走转换，对称成立。

### 15.5.3 canonical 实现：`+=` 造 `+`，`<=>` 造全套
{: .sec-best}

成对运算符有标准实现套路：先写复合赋值（成员、原地、返回自身引用），再用它实现普通算术（非成员、传值进出）；比较运算符在 C++20 里默认化 `<=>` 一次搞定六个关系加相等：

```cpp
// canonical_ops.cpp —— 需要 -std=c++20
#include <iostream>

class Distance {
    long mm_ = 0;
public:
    explicit Distance(long mm) : mm_(mm) {}
    long mm() const { return mm_; }

    // 成员：复合赋值。整套餐的"心脏"
    Distance& operator+=(const Distance& rhs) {
        mm_ += rhs.mm_;
        return *this;
    }
    Distance& operator-=(const Distance& rhs) {
        mm_ -= rhs.mm_;
        return *this;
    }

    // 非成员（写成 friend）：+、- 复用 +=、-=，传值返回新对象
    friend Distance operator+(Distance a, const Distance& b) { a += b; return a; }
    friend Distance operator-(Distance a, const Distance& b) { a -= b; return a; }

    // C++20：默认化 <=>，==、!=、<、<=、>、>= 全部自动可用
    friend bool operator==(const Distance&, const Distance&) = default;
    friend auto operator<=>(const Distance&, const Distance&) = default;
};

int main() {
    Distance a{1500}, b{2500};
    std::cout << (a + b).mm() << '\n';   // 4000
    std::cout << (a < b) << '\n';        // 1
    std::cout << (a != b) << '\n';       // 1
    a += Distance{500};
    std::cout << a.mm() << '\n';         // 2000
}
```

```bash
g++ -std=c++20 -Wall -Wextra canonical_ops.cpp -o co && ./co
```

```text
4000
1
1
2000
```

这个写法的好处是"一处逻辑，处处一致"：`+` 的语义就是 `+=`，永远不会出现"加法对、加等错"的两张皮。`a + b` 里 `a` 按值传入，函数内部直接改副本再返回，返回值优化会消掉大部分拷贝。

`<=>`（三路比较，俗称飞船运算符，C++20）的返回类型有三档：`std::strong_ordering`（相等即全等，如整数）、`std::weak_ordering`（相等但可区分，如大小写不敏感的字符串）、`std::partial_ordering`（可能出现"无法比较"，如含 NaN 的浮点）。成员逐个 `<=>` 默认化时，编译器按成员声明顺序比较，最终返回类型取成员中最弱的一档。注意 `<`、`<=` 等不需要你写：编译器把 `a < b` 自动改写成 `a <=> b < 0`（比较改写，rewritten candidate）。

### 15.5.4 下标、调用、箭头与多维下标
{: .sec-prac}

四个必须成员的运算符各有典型用法，一网打尽：

```cpp
// member_ops.cpp —— 需要 -std=c++20
#include <cmath>
#include <cstddef>
#include <iostream>

class Vec3 {
    double v_[3] = {};
public:
    Vec3(double x, double y, double z) : v_{x, y, z} {}
    double& operator[](std::size_t i) { return v_[i]; }              // 返回引用才能写
    double operator[](std::size_t i) const { return v_[i]; }         // const 版：只读对象也能下标
    double norm() const { return std::sqrt(v_[0] * v_[0] + v_[1] * v_[1] + v_[2] * v_[2]); }
};

class Tax {
    double rate_;
public:
    explicit Tax(double r) : rate_(r) {}
    double operator()(double amount) const { return amount * rate_; } // 函数对象
};

template <class T>
struct Box {
    T value;
    T* operator->() { return &value; }   // 返回原始指针，链到此为止
};

int main() {
    Vec3 v{1, 2, 3};
    v[1] = 20;                                    // operator[] 返回引用，可赋值
    std::cout << v[0] << ' ' << v[1] << '\n';

    Tax tax{0.13};
    std::cout << tax(100.0) << '\n';              // 对象当函数用

    Box<Box<Vec3>> nested{{Vec3{7, 8, 9}}};
    std::cout << nested->norm() << '\n';          // operator-> 递归应用两层，最终落到 Vec3
}
```

```bash
g++ -std=c++20 -Wall -Wextra member_ops.cpp -o mo && ./mo
```

```text
1 20
13
13.9284
```

`operator->` 的递归语义值得单独说：`A->B` 编译时先调 `A.operator->()`，若返回原始指针则停，返回的是另一个类对象就**继续对它应用 operator->**，直到拿到原始指针为止。智能指针链、代理层叠全靠这条规则。

C++23 给 `operator[]` 解了封——允许多个参数，多维下标不再需要 `a[i][j]` 或重载 `operator()`：

```cpp
// multi_subscript.cpp —— 需要 -std=c++23（GCC 12+ 支持）
#include <iostream>
#include <cstddef>

class Matrix {
    static constexpr std::size_t kCols = 3;
    int data_[2 * kCols] = {};
public:
    int& operator[](std::size_t r, std::size_t c) { return data_[r * kCols + c]; }
    int operator[](std::size_t r, std::size_t c) const { return data_[r * kCols + c]; }
};

int main() {
    Matrix m;
    m[1, 2] = 42;
    std::cout << m[1, 2] << '\n';
}
```

```bash
g++ -std=c++23 -Wall -Wextra multi_subscript.cpp -o ms && ./ms
```


`m[1, 2]` 里那个逗号不再是逗号运算符而是参数分隔，直观且能被编译器优化成一次寻址。

### 15.5.5 转换运算符与 explicit
{: .sec-know}

转换运算符让对象"变成"另一种类型：`operator T()`。它和单参构造函数是隐式转换的两扇大门，都容易放进来不速之客。C++11 起转换运算符可以标 `explicit`，标了之后：显式转换（`static_cast`）照常，**条件语境**（if、while、逻辑非）里的 bool 转换照常，其余隐式转换被挡住。`operator bool` 标 explicit 是标准库自己的做法（如 `std::unique_ptr`）：

```cpp
// conversion_op.cpp —— 需要 -std=c++20
#include <iostream>
#include <cstdint>

class Timer {
    std::uint64_t ms_ = 0;
public:
    explicit Timer(std::uint64_t ms) : ms_(ms) {}
    explicit operator bool() const { return ms_ != 0; }          // 条件里可用
    explicit operator std::uint64_t() const { return ms_; }      // 必须显式取值
};

int main() {
    Timer t{1500};
    if (t) std::cout << "timer running\n";                       // 语境转换，合法
    std::uint64_t ms = static_cast<std::uint64_t>(t);
    std::cout << ms << " ms\n";
    // int x = t;    // 编译错：explicit 挡住隐式转换，bool 赋值同理
}
```

```bash
g++ -std=c++20 -Wall -Wextra conversion_op.cpp -o cvo && ./cvo
```

```text
timer running
1500 ms
```

设计原则：转换运算符能不写就不写，非写不可就 explicit。每个隐式转换都是给重载决议（15.6）埋的地雷。

### 15.5.6 operator new/delete 重载概览
{: .sec-know}

类可以重载自己的 `operator new`/`operator delete`，接管**该类对象**（不含其成员指向的内存）的分配。典型用途：统计分配、池分配、内存对齐调试。注意这是"分配器钩子"不是构造函数，重载的 new 里拿到的只是未初始化内存：

```cpp
// tracked_new.cpp —— 需要 -std=c++20
#include <cstdio>
#include <new>

class Tracked {
public:
    static void* operator new(std::size_t n) {
        std::printf("[alloc] %zu bytes\n", n);
        return ::operator new(n);              // 转发全局版本
    }
    static void operator delete(void* p) noexcept {
        std::printf("[free]\n");
        ::operator delete(p);
    }
private:
    int data_[16];
};

int main() {
    Tracked* t = new Tracked;    // 走 Tracked::operator new
    delete t;
}
```

```bash
g++ -std=c++20 -Wall -Wextra tracked_new.cpp -o tn && ./tn
```

```text
[alloc] 64 bytes
[free]
```

64 字节来自 16 个 int。printf 在分配器里调用有递归风险时（printf 自身可能分配），工程上要换成无分配的记录手段，这里仅作演示。

## 15.6 函数重载
{: .sec-expl}

### 15.6.1 重载决议五步流水线
{: .sec-know}

`f(3.14)` 这种调用，编译器按固定流水线选出函数，每一步都可能提前"死亡"：

1. **名字查找**：沿作用域链找到同名声明集合，**找到即停**——这一步先于一切重载分析，派生类同名函数隐藏基类全套重载（15.8 的根源），ADL 在此处把参数所属命名空间里的候选补进来。
2. **模板处理**：候选里的函数模板做实参推导，推导失败的模板出局（SFINAE）；剩下的模板和普通函数一起进候选。
3. **可行函数筛选**：参数个数对得上、每个实参到形参存在可行转换的函数留下，其余出局。
4. **最佳匹配排序**：对每个可行函数，逐参数比较转换等级。某个函数在**所有**参数上都不劣于对手且至少一参更优，才胜出。
5. **决胜**：恰有一个最佳者入选；出现平局（分不出优劣）或无人可用，报错——前者是歧义，后者是无匹配。

转换等级从优到劣只有五档：

| 等级 | 含义 | 例子（实参 char，形参为） |
| --- | --- | --- |
| 精确匹配 | 一致或平凡变换（加 const、数组退化） | `char`、`const char&` |
| 提升 | 整数提升、浮点提升（更"窄"到"宽"的免费升格） | `int`（char 到 int 是提升） |
| 标准转换 | 其余内置转换（可能丢信息） | `double`、`long long` |
| 用户定义转换 | 经转换构造函数或转换运算符 | 自定义类型形参 |
| 省略号 | `...` 兜底 | 可变参数 |

模板候选之间另有一套**偏序（partial ordering）**规则：能被另一个模板实例化覆盖推导的更特化者胜，与转换等级正交。

### 15.6.2 歧义：等级打平就报错
{: .sec-ex}

```cpp
// overload_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <initializer_list>
#include <vector>

void f(long)   { std::cout << "f(long)\n"; }
void f(double) { std::cout << "f(double)\n"; }

void h(int)  { std::cout << "h(int)\n"; }
void h(char) { std::cout << "h(char)\n"; }

template <class T> void t(T)  { std::cout << "t(T)\n"; }
template <class T> void t(T*) { std::cout << "t(T*)\n"; }

struct Vec {
    Vec(int a, int b) { std::cout << "Vec(int,int): " << a << ',' << b << '\n'; }
    Vec(std::initializer_list<int> l) {
        std::cout << "Vec(init_list): ";
        for (int v : l) std::cout << v << ' ';
        std::cout << '\n';
    }
};

int main() {
    // f(1);        // 编译错：int -> long 和 int -> double 都是标准转换，打平，歧义
    h('a');         // char 精确匹配 h(char)，胜过 h(int) 的提升
    short s = 2;
    h(s);           // short -> int 是整数提升，胜过任何"标准转换"

    int* p = nullptr;
    t(p);           // 模板偏序：t(T*) 比 t(T) 更特化，胜出

    Vec v1(3, 5);   // 普通构造函数
    Vec v2{3, 5};   // initializer_list 版本优先
    std::vector<int> a(3, 5);   // 3 个 5
    std::vector<int> b{3, 5};   // 两个元素 3 和 5
    std::cout << a.size() << ' ' << b.size() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra overload_demo.cpp -o od2 && ./od2
```

```text
t(T*)
```

`f(1)` 的歧义值得背下来：`int` 到 `long` 和到 `double` 都是标准转换，谁也不比谁好，标准不替你猜，直接报错。修法是写 `f(1L)` 或 `f(1.0)`，或者加一个 `f(int)` 重载。

### 15.6.3 initializer_list 优先级坑
{: .sec-ts}

> **坑：** 列表初始化（花括号）时，`std::initializer_list` 重载享有最高优先级——只要它存在且元素能转，别的重载一律靠边，**哪怕语义完全不合身**。
{: .sec-pit}

上面 `Vec v2{3, 5}` 选了 init_list 版本而不是 `Vec(int,int)`，演示了这条规则的字面效果。标准库里最著名的案例就是 `std::vector`：

```cpp
std::vector<int> a(3, 5);   // 圆括号：构造 3 个值为 5 的元素
std::vector<int> b{3, 5};   // 花括号：两个元素，值为 3 和 5
```

同一份"3, 5"，两种容器内容，用过的人都被咬过。另一条相关规则在 C++17 起：`auto x{1};` 推导为 `int`（单值语义），`auto x{1, 2};` 直接编译错——花括号的"元素列表"含义在 auto 推导里被砍掉了。工程守则：想要"数量+值"语义用圆括号，想要"元素清单"语义用花括号，类作者少写 `initializer_list` 构造函数。

### 15.6.4 隐式转换意外命中
{: .sec-ts}

> **坑：** 重载决议把"用户定义转换"也当正经候选。一个不设防的单参构造函数，能让字符串、double、指针悄悄转成你的类型并命中看似无关的重载。
{: .sec-pit}

```cpp
// implicit_hit.cpp —— 需要 -std=c++20
#include <iostream>

struct Kilometers {
    Kilometers(double v) : v_(v) {}        // 非 explicit：隐式转换大门敞开
    double v_;
};

struct Miles {
    explicit Miles(double v) : v_(v) {}    // explicit：必须写明来意
    double v_;
};

double road_length(Kilometers k) { return k.v_; }

int main() {
    std::cout << road_length(3.5) << '\n';             // double 悄悄变 Kilometers：单位错了没人拦
    // std::cout << road_length(Miles{3.5}) << '\n';   // Miles 到 Kilometers 无转换：挡住了
    std::cout << road_length(Kilometers{3.5}) << '\n'; // 想转就明写
}
```

单参构造函数默认写 explicit，确有"同量纲、无歧义"的转换需求再放开，是性价比最高的防御。

## 15.7 流的重载
{: .sec-expl}

### 15.7.1 `<<` / `>>` 为什么必须非成员
{: .sec-know}

`os << v` 的左操作数是 `std::ostream`，不是你的类型。成员运算符要求左操作数是本类对象，而你的类型排在右边——成员版语法上就写不出来。所以流运算符必须是非成员：左参数流、右参数你的类型。流运算符还是链式调用的典型：`cout << a << b` 展开为 `operator<<(operator<<(cout, a), b)`，因此**必须返回流的引用**，断链写法（返回 void）会让第二个 `<<` 编不过。

```cpp
// stream_ops.cpp —— 需要 -std=c++20
#include <iostream>
#include <sstream>
#include <string>

class Version {
    int major_ = 0, minor_ = 0;
public:
    Version(int ma, int mi) : major_(ma), minor_(mi) {}
    friend std::ostream& operator<<(std::ostream& os, const Version& v) {
        return os << v.major_ << '.' << v.minor_;
    }
    friend std::istream& operator>>(std::istream& is, Version& v) {
        std::string s;
        is >> s;
        auto dot = s.find('.');
        if (dot == std::string::npos) { is.setstate(std::ios::failbit); return is; }
        v.major_ = std::stoi(s.substr(0, dot));
        v.minor_ = std::stoi(s.substr(dot + 1));
        return is;
    }
};

int main() {
    Version v{1, 9};
    std::cout << v << '\n';              // 链式输出
    std::istringstream in("2.3");
    if (in >> v) std::cout << v << '\n'; // 读取并回显
}
```

```bash
g++ -std=c++20 -Wall -Wextra stream_ops.cpp -o so && ./so
```

```text
2.3
```

### 15.7.2 friend 与 hidden friend
{: .sec-ext}

上面代码里的非成员写成 `friend` 定义在类内，这有个专门的名字：**hidden friend**（隐藏友元）。它不在外围命名空间的名字里，普通名字查找找不到它，只有 **ADL**（实参依赖查找）——因为实参类型是 `Version`——才找得到。好处三条：不污染命名空间、避免意外的隐式转换命中（实参里必须真有 `Version` 才会找到它）、编译器更容易生成优化代码。C++20 之后的惯例是：**对称运算符一律写成 hidden friend**，不再在类外单独声明。

普通 friend（类外还有一份可见的非成员函数）如今主要用于"需要让非 ADL 位置也能显式调用"的场景，比如让 `operator<<` 能写进函数指针表。拿不准就选 hidden friend。

### 15.7.3 std::formatter：C++20 的输出新通道
{: .sec-ext}

`std::format`（C++20）不走 `operator<<`，走 **`std::formatter` 特化**。给自定义类型特化一个 formatter，它就同时接入 `std::format`、`std::format_to`，以及 C++23 的 `std::print`：

```cpp
// formatter_demo.cpp —— 需要 -std=c++20；<format> 需 GCC 13+ / libstdc++ 13+
#include <format>
#include <iostream>

struct Point {
    int x = 0;
    int y = 0;
};

template <>
struct std::formatter<Point> {
    constexpr auto parse(std::format_parse_context& ctx) {
        auto it = ctx.begin();
        while (it != ctx.end() && *it != '}') ++it;   // 演示版：不支持格式说明
        return it;
    }
    auto format(const Point& p, std::format_context& ctx) const {
        return std::format_to(ctx.out(), "({}, {})", p.x, p.y);
    }
};

int main() {
    Point p{3, 4};
    std::cout << std::format("p = {}\n", p);
}
```

```bash
g++ -std=c++20 -Wall -Wextra formatter_demo.cpp -o fd && ./fd
```

```text
p = (3, 4)
```

选型建议：日志与格式化输出用 formatter（类型安全、性能好、支持编译期检查格式串），调试时的临时打印用 `operator<<`，两者并存毫无冲突。`parse` 里可以解析自定义格式说明（如 `{:#x}`），校验失败抛 `std::format_error`。

## 15.8 覆盖：override、overload、hide 三者辨析
{: .sec-iv}

这是本章最重要的一节，三个词中文都带"重"，实际是三件完全不同的事。

| 概念 | 英文 | 发生位置 | 签名要求 | virtual 参与 | 典型后果 |
| --- | --- | --- | --- | --- | --- |
| 重载 | overload | 同一作用域 | 同名不同参数 | 无关 | 编译期按实参选函数 |
| 覆盖 | override | 派生类 vs 基类 | 同名同签名同 cv | 基类函数必须是虚函数 | 运行期动态分派 |
| 隐藏 | hide | 派生类 vs 基类 | 只要同名 | 无关（基类是否虚都隐藏） | 基类同名全套不可见，常是 bug |

核心机制只有一条：**名字查找先于重载决议**。编译器先沿作用域链找名字，在派生类作用域里找到了 `h`，查找立刻停止，基类作用域根本不进入——基类的所有 `h` 不参与后续的"选哪个重载"。隐藏不是编译器犯错，是规则使然。

一组代码看全三种情况：

```cpp
// three_kinds.cpp —— 需要 -std=c++20
#include <iostream>

struct Base {
    void f(int)         { std::cout << "Base::f(int)\n"; }
    void f(double)      { std::cout << "Base::f(double)\n"; }
    virtual void g(int) { std::cout << "Base::g(int)\n"; }
    virtual void h(int) { std::cout << "Base::h(int)\n"; }
};

struct Derived : Base {
    // ① 隐藏：签名不同，且名字查找在 Derived 就停了
    void f(const char*) { std::cout << "Derived::f(const char*)\n"; }

    // ② 覆盖：同名同签名，Base::g 是虚函数，运行期分派
    void g(int) override { std::cout << "Derived::g(int)\n"; }

    // ③ 隐藏：签名不同（int -> double），即使 Base::h 是虚函数也不是覆盖
    void h(double) { std::cout << "Derived::h(double)\n"; }

    using Base::f;   // 把 Base 的 f 全套重新引入，恢复重载集
};

int main() {
    Derived d;
    d.f("txt");     // Derived::f(const char*)
    d.f(1);         // 有 using：Base::f(int)
    Base& b = d;
    b.g(1);         // 覆盖生效：Derived::g(int)
    b.h(1);         // 静态类型 Base：调 Base::h(int)，Derived::h 不是覆盖
    d.h(1);         // 名字查找只见 Derived::h(double)：1 转 double
}
```

```bash
g++ -std=c++20 -Wall -Wextra three_kinds.cpp -o tk && ./tk
```

```text
Derived::f(const char*)
Base::f(int)
Derived::g(int)
Base::h(int)
Derived::h(double)
```

逐行拆解最容易踩的三处：

1. `b.h(1)`：经基类引用调用，静态类型是 `Base`，`Derived::h(double)` 不构成覆盖（签名不同），运行的是 `Base::h(int)`。作者以为在"重定义"虚函数，实际写了个没人调用的函数——**这正是 override 关键字存在的意义**：加上 `override` 后编译器当场拒绝。
2. `d.h(1)`：经派生类对象调用，名字查找只看到 `Derived::h`，`Base::h(int)` 整个被隐藏，`1` 静默转成 double。想恢复可见性写 `using Base::h;`。
3. `d.f(1)` 在没有 `using Base::f;` 时是编译错：名字查找只找到 `Derived::f(const char*)`，`1` 转不成 `const char*`，无匹配。

> **坑：** 派生类里新增同名函数（哪怕参数不同）就会隐藏基类全套同名重载。两个纪律堵住它：所有覆盖写 `override`（签名不符立刻报错）；确需引入基类重载时显式写 `using Base::f;`，不做"顺便"的假设。
{: .sec-pit}

## 15.9 技术解惑
{: .sec-expl}

### 15.9.1 类型擦除：std::function 与 std::any
{: .sec-ext}

虚函数之外还有一条运行期多态的路：**类型擦除（type erasure）**。容器不通过继承知道类型，只保存"怎么调用它"的包装。`std::function`（C++11）擦掉可调用物的类型只留签名，`std::any`（C++17）擦掉值类型只留"存了点东西"：

```cpp
// type_erasure.cpp —— 需要 -std=c++20
#include <any>
#include <functional>
#include <iostream>
#include <string>

int add(int a, int b) { return a + b; }

int main() {
    // std::function：能装任何"可按 int(int,int) 调用"的东西
    std::function<int(int, int)> op = add;
    std::cout << op(2, 3) << '\n';
    op = [](int a, int b) { return a * b; };    // 函数指针、仿函数、lambda 都能装
    std::cout << op(2, 3) << '\n';

    // std::any：装任意可拷贝值，取回时必须给对类型
    std::any box = std::string("hello");
    std::cout << std::any_cast<std::string>(box) << '\n';
    try {
        std::any_cast<int>(box);          // 类型不对：抛 std::bad_any_cast
    } catch (const std::bad_any_cast&) {
        std::cout << "bad_any_cast\n";
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra type_erasure.cpp -o te && ./te
```

```text
hello
bad_any_cast
```

三种运行期多态选型：类型集合固定、对象有"是一致的家族"语义——虚函数；只关心"能不能按这个签名调用"、需要装 lambda/函数指针/成员函数——`std::function`（可能堆分配、调用有一次间接开销，C++23 的 `std::move_only_function` 支持只移动类型且性能更好）；跨层传"不知道是什么"的值——`std::any`，但先用 `variant` 自问一遍：类型集合要是编译期已知，`std::variant` 更快更安全。

### 15.9.2 虚调用实测方法
{: .sec-ver}

性能争议别吵，测。陷阱是编译器优化太强：没副作用的循环会被整体删除，虚版本也可能被去虚化。标准做法是用 `volatile` 接收结果、用运行期条件挑选对象类型：

```cpp
// perf_virtual.cpp —— 需要 -std=c++20
#include <chrono>
#include <cstdio>

struct Base {
    virtual int add(int v) const = 0;
    virtual ~Base() = default;
};

struct A : Base { int add(int v) const override { return v + 1; } };
struct B : Base { int add(int v) const override { return v + 2; } };

volatile long long sink;   // volatile 防止整段循环被当作死代码删除

template <class F>
long long bench(F&& f, int n) {
    auto t0 = std::chrono::steady_clock::now();
    f(n);
    auto t1 = std::chrono::steady_clock::now();
    return std::chrono::duration_cast<std::chrono::milliseconds>(t1 - t0).count();
}

int main(int argc, char**) {
    constexpr int N = 200'000'000;
    A a; B b;
    // 运行期才决定指向谁，编译器无法去虚化
    Base* bp = (argc > 1) ? static_cast<Base*>(&a) : static_cast<Base*>(&b);

    long long s = 0;
    auto ms_virtual = bench([&](int n) {
        for (int i = 0; i < n; ++i) s += bp->add(i);   // 真虚调用
    }, N);
    sink = s;

    auto ms_direct = bench([&](int n) {
        for (int i = 0; i < n; ++i) s += a.add(i);     // 静态类型 A，可内联
    }, N);
    sink = s;

    std::printf("virtual: %lld ms, direct: %lld ms\n", ms_virtual, ms_direct);
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra perf_virtual.cpp -o pv2 && ./pv2
```

```text
virtual: 173 ms, direct: 0 ms
```

数字随机器浮动，但**量级**说明问题：direct 版整个循环被优化成一条求和公式（0 ms），virtual 版老老实实跑了 2 亿次间接调用。这正是静态多态的杀手锏——不是"每次省几纳秒"，是"编译器能看穿你的循环"。本例 x86-64 Linux + GCC 13 -O2 实测，环境不同数值不同。反过来，若函数体大到内联无意义（比如内部要做 IO），虚调用开销占比趋近于零——那才是虚函数该待的地方。

### 15.9.3 分支预测与批量处理
{: .sec-know}

间接跳转的目标不确定时，CPU 的分支目标缓存（BTB）预测失误，流水线要排空——乱序执行时代这才是虚调用的大头成本，单次间接跳转本身反而便宜。由此推出两条经验：

- **分支预测友好**：同一循环里反复调同一个实现（多态对象聚簇存放），预测命中率高，虚调用几乎免费；对象类型随机混杂，预测失误率飙升，单次虚调用的实际耗时可能差出一个量级。
- **批量优于逐个**：虚函数设计成"一次处理一批"（如 `run(vector<Task>&)` 或虚函数吃整个区间）而不是外层循环逐对象调 `run_one()`，分派成本摊薄 N 倍；更激进的数据导向设计（DOD）干脆按类型分桶，每桶内部退回静态代码，把动态多态从热路径里整个请出去。

写过物理引擎或粒子系统的人都懂：把"每帧对 100 万个对象各调一次虚函数"改成"按类型分桶后每桶一个静态循环"，帧时间常常直接砍半——省的不是虚调用的间接跳转，是分支预测失误加缓存失效的组合拳。

### 15.9.4 编译开关：-fno-rtti 与 -Wnon-virtual-dtor
{: .sec-ts}

两个和虚函数绑定的编译选项，日常值得知道：

`-fno-rtti`（GCC/Clang）关掉运行期类型信息，vtable 里不再放 `type_info` 指针，`dynamic_cast` 和多态 `typeid` 直接编译失败。游戏与嵌入式常用它省内存、缩 vtable：

```cpp
struct Derived : Base {};

int main() {

    delete p;
}
```

```text
rtti_demo.cpp:9:18: error: cannot use typeid on objects of type 'Base' with '-fno-rtti'
```

第一行是正常构建的输出（Itanium ABI 的类型名修饰，7 是名字长度）。第二行在 `-fno-rtti` 下直接编译失败：对多态类型用 `typeid` 是硬错误，`dynamic_cast` 同理。所以混用 RTTI 特性与 `-fno-rtti` 构建选项的代码库，问题会拖到编译期才暴露——拿到"cannot use typeid/dynamic_cast with -fno-rtti"这类报错，先查构建配置里谁关了 RTTI。

`-Wnon-virtual-dtor`（GCC/Clang，Clang 里同名）对"有虚函数但析构非虚"的类发警告，直接对着 15.3.4 的 UB 开火：

```bash
g++ -std=c++20 -Wall -Wextra -Wnon-virtual-dtor dtor_demo.cpp -o dt2 && ./dt2
```

```text
dtor_demo.cpp: In function 'int main()':
dtor_demo.cpp:22:12: warning: deleting object of polymorphic class type 'BadBase' which has non-virtual destructor might cause undefined behavior [-Wdelete-non-virtual-dtor]
```

GCC 实际报出的通常是 `-Wdelete-non-virtual-dtor`（对 delete 点报警），`-Wnon-virtual-dtor` 则在类定义处报警。两者都开进 CI，虚析构问题基本绝迹。MSVC 对应 `/w14265` 与 `/w44265`。

## 动手练
{: .sec-ex}

1. **热身**：写一个 `class Timer`，带 `explicit operator bool()` 和 `explicit operator double()`（返回剩余秒数），在 `if` 和 `static_cast` 两种场景各验证一次，并确认 `double x = t;` 编译报错。
2. **进阶**：实现 `class BigInt` 的最小集：成员 `operator+=`、hidden friend `operator+`、默认化 `<=>`，用 `std::vector<int>` 存十进制位。测试 `a + b`、`a += b`、`a < b`、`(a <=> b) == std::strong_ordering::less`。
3. **实战**：写 `class StackMachine`，公有 `push(int)`/`execute()` 非虚（NVI），私有虚函数 `do_execute()`；派生 `AddMachine`、`MulMachine` 分别实现。故意在基类构造函数里调用 `do_execute()`，观察并解释输出。
4. **陷阱题**：给 `Base` 写三个虚函数 `f(int)`、`g(int)`、`h(int)`，在 `Derived` 里分别写成：`f(double)`、`g(int) override`、`h(int)`（无 override 关键字但签名相同）。预测每个函数经基类引用和派生类对象调用的结果，再实际编译验证；最后复刻 15.9.2 的基准，把 `add` 改成"循环 1000 次累加"的大函数，观察虚/直两版差距缩到多少。

## 变式追问
{: .sec-think}

1. **"每个有虚函数的类都有 vtable，对象都多 8 字节"——对吗？**
   前半句对（按主流 ABI），后半句要看"对象"指谁：基类子对象和完整对象都带 vptr，所以单对象确实多 8 字节（LP64）。但空基类优化救不了它——含虚函数的基类不能被压缩为 0 字节，因为 vptr 必须有地方放。推论：超小对象（如 `std::string_view` 的替代品类）加虚函数，8 字节开销可能比数据本身还大。

2. **为什么 `std::vector` 的析构不是虚的，却没人担心 delete 基类指针？**
   因为没人会这么写：`vector` 不是设计来被继承的多态基类，标准连它的派生类都没纳入语义承诺。教训反过来成立：非虚析构不是错误，是声明——"别把我当接口"。自己的类如果既想被继承又不想付 vptr 的钱，学它：析构 protected，禁止经基类删除。

3. **`override` 能被重载决议"绕开"吗？比如派生类写了 `void g(double) override`？**
   不能绕开——这句直接编译失败。`override` 检查发生在覆盖匹配阶段：基类 `g(int)` 是虚函数，派生类 `g(double)` 找不到匹配的虚函数可覆盖，报错。而如果删掉 `override`，`g(double)` 合法存在，但它是隐藏不是覆盖，经基类引用调用时执行基类版本。一句话：`override` 把"静默的错误"变成"响亮的编译错"。

4. **CRTP 能完全替代虚函数吗？什么时候不行？**
   类型集合编译期封闭时可以，且性能全面占优。三处硬伤使它替代不了虚函数：异构容器装不了（没有共同基类）；跨动态库边界分发新实现（插件）做不到，模板实例化发生在使用方编译期；二进制兼容脆弱，改基类模板要所有使用方重编。判断句还是那句：实现何时可知。
