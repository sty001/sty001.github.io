## 14.1 继承与派生的基本概念
{: .sec-expl}

### 14.1.1 is-a 还是实现复用：这是第一个岔路口
{: .sec-know}

继承有两副面孔。一副是**接口继承**：`Dog` 是一种 `Animal`，凡是能对 `Animal` 提问的地方，`Dog` 都能给出合理回答——这是 Liskov 替换原则（LSP）的要求：任何基类指针/引用出现的地方，换成派生类对象，程序行为仍然正确。另一副是**实现继承**：`MyStack` 继承 `vector` 只是想白嫖 `push_back`，可 `vector` 有的 `insert`、`operator[]` 它根本不该暴露——这不是 is-a，是"借工具"。

两副面孔用同一套语法，区别全在设计意图上，而这正是事故源头。拿实现复用的目的去用 public 继承，基类每个新成员都会漏进派生类接口：基类加了个 `size()`，你的 `Stack` 突然也能 `size()`，封装名存实亡。判断标准就一句：**"X 是一种 Y"在业务上成立吗？** 成立才谈 public 继承；不成立，用组合。

### 14.1.2 继承与组合的取舍决策表
{: .sec-know}

| 需求场景 | 选什么 | 依据 |
| --- | --- | --- |
| 基类指针要统一调度，行为在运行期替换 | public 继承 | 需要 is-a 和动态绑定 |
| 只想复用基类的代码 | 组合 | 复用实现不该绑死接口 |
| 需要空基类优化或访问 protected 成员 | private 继承 | 组合做不到这两点，见 14.2.2 |
| 想重写虚函数，但"不是那个东西" | 别继承，重设计接口 | 违反 LSP，迟早出事 |
| 基类频繁变动，派生类很多 | 组合 | 继承让基类变动波及所有派生类 |

> **注意：** "组合优于继承"不是禁令，是默认值。当且仅当 is-a 成立、且需要多态调度时，继承才是正解——`std::exception` 层次、GUI 控件层次都是正当用法。
{: .sec-note}

### 辨析：继承与组合
{: .sec-iv}

继承是"我是"（白盒：派生类看得见基类的 protected 内部），组合是"我有"（黑盒：外层类只依赖内层类的 public 接口）。白盒的代价是耦合：基类改一个 protected 成员或改一个虚函数的调用时机，所有派生类都可能坏——这就是脆弱基类问题（14.7.5）。黑盒的代价是委托代码：每个要转发的函数都得写一遍。现代设计的倾向很明确：接口用继承，实现用组合；实在要复用实现又想省委托代码，用 private 继承并想清楚 EBO 那点收益值不值（14.2.2）。

## 14.2 C++ 继承机制
{: .sec-know}

### 14.2.1 三种继承方式：只改可见性，不改内存
{: .sec-know}

class 默认 private 继承，struct 默认 public 继承。继承方式只影响"基类成员在派生类里以什么身份出现"，不影响对象布局：

| 继承方式 | 基类 public 成员 | 基类 protected 成员 | 基类 private 成员 |
| --- | --- | --- | --- |
| public | 变成 public | 变成 protected | 不可访问（但占内存） |
| protected | 变成 protected | 变成 protected | 不可访问 |
| private | 变成 private | 变成 private | 不可访问 |

private 成员"不可访问但存在"：派生类对象里照样有基类的 private 子对象，只是派生类代码摸不到。这保证了基类的封装对每个层次都成立——派生类也不是基类的特权用户。

### 14.2.2 private 继承："根据某物实现"与空基类优化
{: .sec-know}

private 继承的真实含义是把基类变成自己的**实现细节**：外部拿到的是派生类对象，但它"根据基类实现"。和组合相比它多两个独有能力：

- 能访问基类的 protected 成员；
- 能重写基类的虚函数（这也就自动满足"想参与基类接口"的需求）；
- 空基类优化（EBO）：空类作为**基类**可以不占空间，作为**成员**至少占 1 字节。

```cpp
// ebo.cpp —— 需要 -std=c++20
#include <iostream>

struct Empty {};                       // 空类仍占 1 字节（保证地址唯一）

struct WithMember {
    Empty e;                           // 作为成员：占一个字节
    int value;
};

struct WithInherit : private Empty {   // 作为私有基类：可被优化掉（EBO）
    int value;
};

int main() {
    std::cout << sizeof(WithMember) << ' ' << sizeof(WithInherit) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra ebo.cpp -o ebo && ./ebo
```

```text
8 4
```

上面是 x86-64 Linux + GCC 的结果（对齐规则见第 03 篇；MSVC 同为 8 和 4）。`WithMember` 里 Empty 占 1 字节再加 3 字节填充；`WithInherit` 把 Empty 塞进了自己 4 字节里。EBO 是分配器、比较器这类"可能为空的策略对象"能零成本存储的技术基础，标准库容器大量依赖它。

什么时候用 private 继承？想重写基类虚函数、想用 EBO、或需要"受保护地转换成基类"（类内可以 `static_cast` 到 private 基类）时。其余情况一律组合——private 继承阻止外部把派生类当基类用，语义上更接近组合而非 is-a。

### 14.2.3 protected 的设计意图与滥用
{: .sec-ts}

protected 的意图是给**派生类**一条受控的内部通道：成员对世界私有，对子类开放。它同时把基类和所有派生类焊在了一起——基类改 protected 成员的含义，等于修改所有子类看得见的合同。所以 protected 数据成员是高危设计，protected 成员函数（钩子）相对安全，因为它只是"允许子类参与某个步骤"。

> **坑：** 把成员从 private 改成 protected 是接口变更，不是实现调整。所有派生类从此依赖这个成员的名字、类型甚至不变式。多数场景下 protected 虚函数（子类定制行为）比 protected 数据（子类直改内部）安全得多。
{: .sec-pit}

## 14.3 继承和派生的基本知识
{: .sec-know}

### 14.3.1 构造与析构顺序
{: .sec-ver}

```cpp
// ctor_dtor.cpp
#include <iostream>

struct Base {
    Base() { std::cout << "Base 构造\n"; }
    ~Base() { std::cout << "Base 析构\n"; }
};

struct Member {
    Member() { std::cout << "Member 构造\n"; }
    ~Member() { std::cout << "Member 析构\n"; }
};

struct Derived : Base {
    Member m;
    Derived() { std::cout << "Derived 构造\n"; }
    ~Derived() { std::cout << "Derived 析构\n"; }
};

int main() {
    Derived d;
    std::cout << "--- 作用域结束 ---\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra ctor_dtor.cpp -o ctor_dtor && ./ctor_dtor
```

```text
Base 构造
Member 构造
Derived 构造
--- 作用域结束 ---
Derived 析构
Member 析构
Base 析构
```

规则：**基类先构造、派生类先析构**，成员按声明顺序参与（与初始化列表的书写顺序无关）。为什么必须基类先构造？派生类构造函数的函数体运行时，基类子对象必须已经是完整可用的对象——它可能正在调用继承来的函数。析构反过来，理由同理：派生类析构体里还能用基类部分，基类必须最后拆。

这个顺序还能推出一个重要约束：**构造/析构期间，对象"目前只是基类"**。派生类专属部分要么没建好、要么已拆掉。

### 14.3.2 派生类构造必须显式调用基类构造
{: .sec-know}

基类没有默认构造函数时，派生类构造函数**必须**在初始化列表里显式指定怎么构造基类，否则编译失败：

```cpp
// base_ctor.cpp
#include <iostream>

struct Base {
    explicit Base(int id) : id_(id) { std::cout << "Base(" << id_ << ")\n"; }
    int id_;
};

struct Derived : Base {
    // 不写 ": Base(42)" 就编不过：Base 没有默认构造函数可调
    explicit Derived() : Base(42) { std::cout << "Derived()\n"; }
};

int main() {
    Derived d;
    std::cout << d.id_ << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra base_ctor.cpp -o base_ctor && ./base_ctor
```

```text
Base(42)
Derived()
42
```

这是好事：编译器逼你回答"基类部分从哪来"。反过来，基类提供默认构造函数时这步可以省略，但省略也意味着"基类默认状态"，值不值得省要看语义。初始化顺序再强调一遍：**初始化列表的书写顺序骗不了执行顺序**，成员永远按声明顺序初始化，基类永远在最前面。

### 14.3.3 构造函数里调虚函数不下派
{: .sec-warn}

```cpp
// vcall_ctor.cpp
#include <iostream>

struct Base {
    Base() { greet(); }              // 危险：期望它调 Derived::greet？不会
    virtual ~Base() = default;
    virtual void greet() const { std::cout << "Base::greet\n"; }
};

struct Derived : Base {
    void greet() const override { std::cout << "Derived::greet\n"; }
};

int main() { Derived d; }
```

```bash
g++ -std=c++20 -Wall -Wextra vcall_ctor.cpp -o vcall_ctor && ./vcall_ctor
```

```text
Base::greet
```

输出的不是 `Derived::greet`。机制层面：虚函数派发靠对象的动态类型，而对象在构造过程中**动态类型逐层设定**——跑 `Base()` 时动态类型就是 `Base`，虚表也是 Base 的，虚调用自然落在基类版本。标准干脆规定构造/析构期间虚调用按"当前层"解析。后果层面：这段代码**能编译能运行**，只是行为和直觉不符，属于最隐蔽的一类 bug——如果 `greet` 在基类里是纯虚函数，结局更糟，是直接调用纯虚函数，多数实现运行期报错或更糟的未定义行为。

正确姿势：构造函数只做"无条件成立"的初始化；需要子类参与的两阶段初始化，提供显式的 `init()`/工厂函数，或者用第 16 篇讲的 CRTP 在编译期解决。析构函数同理：析构期间的虚调用也只落到当前层。

### 14.3.4 名字隐藏：派生类同名函数藏住基类全部重载
{: .sec-ts}

第 13 篇讲过规则，这里看继承里的完整形态——**派生类的同名函数隐藏基类的全部重载，不是构成重载**：

```cpp
// hiding.cpp
#include <iostream>

struct Base {
    void f(int) { std::cout << "Base::f(int)\n"; }
    void f(double) { std::cout << "Base::f(double)\n"; }
};

struct Derived : Base {
    void f(double) { std::cout << "Derived::f(double)\n"; }   // 藏住 Base 的两个 f
};

struct Fixed : Base {
    using Base::f;                                            // 修复：引入全部重载
    void f(double) { std::cout << "Fixed::f(double)\n"; }
};

int main() {
    Derived d;
    d.f(1);      // Derived::f(double)：Base::f(int) 被藏住，1 被隐式转 double
    d.f(2.5);    // Derived::f(double)

    Fixed g;
    g.f(1);      // Base::f(int)
    g.f(2.5);    // Fixed::f(double)
}
```

```bash
g++ -std=c++20 -Wall -Wextra hiding.cpp -o hiding && ./hiding
```

```text
Derived::f(double)
Derived::f(double)
Base::f(int)
Fixed::f(double)
```

关键认知：**隐藏按名字发生，不按签名发生**。名字查找先在 Derived 作用域找到 `f`，查找即停，基类那两个 `f` 根本没进重载候选。`d.f(1)` 静默走 `Derived::f(double)` 并伴随 int→double 隐式转换——语义可能已经变了。修复一句 `using Base::f;`，把基类重载集搬进来，三个 `f` 构成真正的重载。CI 开 `-Woverloaded-virtual` 能让这类隐藏主动暴露。

### 14.3.5 继承下的拷贝控制
{: .sec-know}

派生类对象 = 基类子对象 + 派生类新增部分。拷贝它 = 分别拷贝两部分，编译器生成的默认版本会**逐个调用基类的拷贝构造/拷贝赋值**：

```cpp
// copy.cpp
#include <iostream>

struct Base {
    Base() = default;
    Base(const Base&) { std::cout << "Base 拷贝\n"; }
    Base& operator=(const Base&) { std::cout << "Base 赋值\n"; return *this; }
};

struct Derived : Base {
    Derived() = default;
    Derived(const Derived&) = default;         // 编译器生成版会先调 Base 的拷贝构造
    Derived& operator=(const Derived&) = default;
};

int main() {
    Derived a;
    std::cout << "---\n";
    Derived b = a;   // 打印 Base 拷贝：基类子对象也在被复制
    b = a;           // 打印 Base 赋值
}
```

```bash
g++ -std=c++20 -Wall -Wextra copy.cpp -o copy && ./copy
```

```text
---
Base 拷贝
Base 赋值
```

两个工程推论。其一，派生类**自己写**拷贝构造却忘了初始化列表里写 `Base(other)`，基类会被默认构造而非拷贝——基类状态丢失，编译器不吭声。其二，基类析构函数是虚的、拷贝操作是"被切片语义"覆盖的重灾区（14.4.3），所以很多基类直接把拷贝操作 delete 掉，只允许通过引用使用。

### 辨析：重载、隐藏与重写
{: .sec-iv}

三个词都在描述"两个同名函数的关系"，判定完全不同：

- **重载**：同一个作用域里，名字相同、参数列表不同，调用时按实参选。
- **隐藏**：不同作用域（派生类 vs 基类），名字相同即成立，与签名无关，基类版本对派生类对象"消失"。
- **重写（override）**：派生类虚函数与基类虚函数**签名完全一致**（含 const、引用限定），运行期动态派发。

隐藏是最容易被误当重载的；重写是隐藏的特例（签名一致且都是虚函数）。写代码时的纪律：想重写就标 `override`（14.4.1），想引入基类重载就写 `using Base::f;`，剩下那些"签名对不上"的同名函数——先问自己是不是写错了。

## 14.4 派生一个类
{: .sec-prac}

### 14.4.1 override 与 final：让编译器替你核对签名
{: .sec-best}

重写最阴险的 bug 是签名差一点点：少个 const、参数类型差个引用、名字打错一个字母——编译器看到的是"派生类新函数"，静默通过，运行期基类版本照常被调。C++11 的 `override` 关键字把核对交回编译器：

```cpp
// override.cpp
#include <iostream>

struct Base {
    virtual void run(int) const { std::cout << "Base::run\n"; }
    virtual ~Base() = default;
};

struct Bad : Base {
    void run(int) { std::cout << "Bad::run\n"; }   // 少了 const：没重写成功，还藏住了基类版本
};

struct Good : Base {
    void run(int) const override { std::cout << "Good::run\n"; }
};

int main() {
    const Base* p = new Good;
    p->run(1);        // Good::run：override 保证真重写
    delete p;
    const Base* q = new Bad;
    q->run(1);        // Base::run：静默 bug
    delete q;
}
```

```bash
g++ -std=c++20 -Wall -Wextra override.cpp -o override && ./override
```

```text
Good::run
Base::run
```

把 `Bad::run` 的声明加上 `override`，编译器立刻拒绝：

```text
error: 'void Bad::run(int)' marked 'override', but does not override
```

`final`（C++11）有两个位置：修饰虚函数，禁止该函数在更深的派生类里再被重写；修饰类，禁止整个类被继承。`struct Circle final : public Shape` 的写法在性能上还有附带收益——编译器知道没有更深的派生，可以放心去虚化（devirtualization），把虚调用优化成直接调用。纪律很简单：**重写一律写 override；确定封闭的叶子类写 final**。没有任何合理理由省这两个词。

### 14.4.2 虚析构函数：什么时候必须，什么时候白付
{: .sec-warn}

判断条件只有一条：**会通过基类指针 delete 派生类对象（多态删除）时，基类析构必须虚**。

```cpp
// vdtor.cpp —— 需要 -std=c++20
#include <iostream>

struct PlainBase {
    ~PlainBase() { std::cout << "~PlainBase\n"; }        // 非虚
};
struct PlainDerived : PlainBase {
    ~PlainDerived() { std::cout << "~PlainDerived\n"; }
};

struct PolyBase {
    virtual ~PolyBase() { std::cout << "~PolyBase\n"; }  // 虚
};
struct PolyDerived : PolyBase {
    ~PolyDerived() { std::cout << "~PolyDerived\n"; }
};

int main() {
    PlainBase* p = new PlainDerived;
    delete p;    // undefined behavior：基类析构非虚
    std::cout << "---\n";
    PolyBase* q = new PolyDerived;
    delete q;    // 正确：先 ~PolyDerived 再 ~PolyBase
}
```

```bash
g++ -std=c++20 -Wall -Wextra vdtor.cpp -o vdtor && ./vdtor
```

```text
~PlainBase
---
~PolyDerived
~PolyBase
```

前半段是 **undefined behavior**：通过基类指针删除派生对象而基类析构非虚，行为无定义。上面"只打印了 `~PlainBase`"是本机 GCC 的典型表现（派生部分没被正确析构，若派生类持有资源就是泄漏），但任何结果都可能——这就是不写 virtual 的真实代价。虚函数只要出现（哪怕只想多态调用），析构就该跟着 virtual；`std::unique_ptr<Shape>` 装派生对象也依赖基类虚析构才安全。

反方向同样成立：**不打算多态删除的基类别加虚析构**。非虚析构的对象没有 vptr，能省 8 字节（x86-64）和一层间接。值不值虚析构，取决于这个基类的用途，不是"写了虚函数就得全套虚"以外的机械规则——准确说是"有多态删除才有虚析构，有多态调用才有多态删除"。

> **坑：** GCC 会用 `-Wdelete-non-virtual-dtor`（包含在 -Wall 里）对"通过多态基类指针 delete 非虚析构类"报警，务必让这条警告在 CI 里生效。
{: .sec-pit}

### 14.4.3 对象切割：按值传递丢掉派生部分
{: .sec-pit}

```cpp
// slicing.cpp
#include <iostream>

struct Animal {
    virtual void speak() const { std::cout << "...\n"; }
    virtual ~Animal() = default;
};

struct Dog : Animal {
    void speak() const override { std::cout << "汪\n"; }
};

void by_value(Animal a) { a.speak(); }     // 按值：发生切割
void by_ref(const Animal& a) { a.speak(); } // 按引用：保留动态类型

int main() {
    Dog d;
    by_value(d);   // 只拷贝了 Animal 子对象，Dog 的部分被切掉
    by_ref(d);     // 引用绑定整个对象，动态派发正常
}
```

```bash
g++ -std=c++20 -Wall -Wextra slicing.cpp -o slicing && ./slicing
```

```text
...
汪
```

按值传参时只发生一次 `Animal` 的拷贝构造——`Dog` 新增的部分根本没被复制，对象里只剩基类子对象，虚表也是基类的，`speak()` 自然落到基类版本。整个过程编译器不报错，因为"把 Dog 拷贝成 Animal"在语法上完全合法。防御手段按强度排：参数和返回值一律用引用或指针；容器存 `std::unique_ptr<Animal>` 而不是 `Animal`；最严格的基类直接把拷贝构造 delete 掉，让切割变成编译错误。GCC 的 `-Wslice` 类警告不可依赖（主流编译器对此警告能力有限），规则靠评审守住。

### 14.4.4 完整示例：一个规范的图形类层次
{: .sec-prac}

把本节要点拼起来：纯虚接口、虚析构、override、final、容器装智能指针。

```cpp
// shapes.cpp —— 需要 -std=c++20
#include <iostream>
#include <memory>
#include <vector>

class Shape {
public:
    virtual double area() const = 0;                 // 纯虚：Shape 只是接口
    virtual ~Shape() = default;                      // 虚析构：多态删除的标配
};

class Circle final : public Shape {                  // final：封闭叶子类
public:
    explicit Circle(double r) : r_(r) {}
    double area() const override { return 3.141592653589793 * r_ * r_; }
private:
    double r_;
};

class Rect : public Shape {
public:
    Rect(double w, double h) : w_(w), h_(h) {}
    double area() const override { return w_ * h_; }
private:
    double w_, h_;
};

int main() {
    std::vector<std::unique_ptr<Shape>> shapes;
    shapes.push_back(std::make_unique<Circle>(1.0));
    shapes.push_back(std::make_unique<Rect>(2.0, 3.0));

    for (const auto& s : shapes) {
        std::cout << s->area() << '\n';              // 动态派发
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra shapes.cpp -o shapes && ./shapes
```

```text
3.14159
6
```

对照检查清单：接口类 `Shape` 只有纯虚函数和虚析构，没有数据；两个实现类各自持数据；`Circle` 标了 `final`；容器存 `unique_ptr` 免切割免泄漏。这就是现代 C++ 多态层次的标准骨架，后面 14.7 会给出它的替代方案。

## 14.5 单重继承和多重继承
{: .sec-expl}

### 14.5.1 多重继承：合法，但二义性先到
{: .sec-know}

一个类可以同时继承多个基类，基类按声明顺序构造。多重继承立刻引入一个问题——两个基类有同名成员时，编译器拒绝猜测：

```cpp
// ambiguity.cpp
#include <iostream>

struct A { int value = 1; };
struct B { int value = 2; };

struct C : A, B {
    int get_a() { return A::value; }     // 必须显式限定到具体基类
    int get_b() { return B::value; }
};

int main() {
    C c;
    std::cout << c.get_a() << ' ' << c.get_b() << '\n';
    // std::cout << c.value;   // 解开注释即编译错误：value 二义
}
```

```bash
g++ -std=c++20 -Wall -Wextra ambiguity.cpp -o ambiguity && ./ambiguity
```

```text
1 2
```

二义性在**名字查找阶段**就报错，不等到重载决议——`c.value` 连"两个 value 选哪个"都答不上来。这不是缺陷，是编译器在提醒你两个基类职责重叠了。

### 14.5.2 辨析：接口多重继承与实现多重继承
{: .sec-iv}

多重继承要不要用，取决于继承来的是什么：

- **接口多重继承**（继承多个纯虚基类，如 `class File : IReadable, IWritable`）：安全。基类没数据没实现，二义性顶多是同名接口函数，用限定名就能解；这是 Java/C# 唯一保留的多重继承形态，实践证明够用且低风险。
- **实现多重继承**（继承多个有数据有实现的类）：危险区。对象布局更复杂、二义性高频、两个基类各自的不变式可能冲突。绝大多数实现复用需求，组合都能替代且耦合更低。

经验法则：多重继承的基类里**有数据成员**就先停下来想组合；只有纯虚接口的多重继承放心用。

## 14.6 虚继承和虚基类
{: .sec-expl}

### 14.6.1 菱形继承与虚继承：同一份基类只留一份
{: .sec-know}

菱形结构 `Copier → Printer → Device`、`Copier → Scanner → Device` 在普通继承下会给 `Copier` 塞进**两份** Device 子对象：两份 `id`，访问 `c.id` 二义。虚继承（`virtual Device`）让 `Device` 在最派生对象里只存在一份：

```cpp
// diamond.cpp —— 需要 -std=c++20
#include <iostream>

struct Device {
    int id = 0;
    explicit Device(int i) : id(i) { std::cout << "Device(" << id << ")\n"; }
};

struct Printer : virtual Device {
    explicit Printer(int i) : Device(i) { std::cout << "Printer\n"; }
};

struct Scanner : virtual Device {
    explicit Scanner(int i) : Device(i) { std::cout << "Scanner\n"; }
};

struct Copier : Printer, Scanner {
    // 虚基类由最派生类（这里就是 Copier）负责构造
    explicit Copier(int i) : Device(i), Printer(i), Scanner(i + 1) { std::cout << "Copier\n"; }
};

int main() {
    Copier c(42);
    std::cout << c.id << '\n';   // 只有一份 Device，不二义
}
```

```bash
g++ -std=c++20 -Wall -Wextra diamond.cpp -o diamond && ./diamond
```

```text
Device(42)
Printer
Scanner
Copier
42
```

两个关键点都在输出里。第一，`Device` 只构造了一次，且**由最派生类 `Copier` 直接构造**——中间层 `Printer(i)`、`Scanner(i + 1)` 对 `Device(i)` 的初始化请求被忽略（虚基类的初始化请求在虚继承下不生效，只有最派生类的请求算数）。这就是为什么 `Scanner(i + 1)` 传了 43 而 `id` 仍是 42。第二，虚基类先于所有非虚基类构造，所以 `Device(42)` 排在第一行。

### 14.6.2 虚继承的内存与性能代价
{: .sec-ver}

虚继承不免费。为了让"基类子对象只有一份"成立，布局必须让各中间类都能在运行期定位到共享的那份基类——实现靠虚基表/虚基指针：

```cpp
// vlayout.cpp —— 需要 -std=c++20
#include <iostream>

struct PlainBase { int v; };
struct PlainD : PlainBase { int w; };

struct VBase { int v; };
struct VD1 : virtual VBase { int w1; };
struct VD2 : virtual VBase { int w2; };
struct VDiamond : VD1, VD2 {};

int main() {
    std::cout << sizeof(PlainD) << ' ' << sizeof(VBase) << ' '
              << sizeof(VD1) << ' ' << sizeof(VDiamond) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra vlayout.cpp -o vlayout && ./vlayout
```

```text
8 4 16 32
```

上面是 x86-64 Linux + GCC（Itanium ABI）的典型结果，MSVC 布局细节不同但方向一致。代价一目了然：普通继承 8 字节搞定的事，虚继承花了 32 字节——每个有虚基类的子对象都背一个指针，访问虚基类成员多一次间接。对象布局示意：

```text
VDiamond 对象布局（x86-64 Linux，GCC，Itanium ABI，示意）
偏移 0   : VD1 的虚基表指针（vptr，指向虚基表，记录 VBase 子对象的偏移）
偏移 8   : VD1::w1
偏移 12  : （填充）
偏移 16  : VD2 的虚基表指针（vptr）
偏移 24  : VD2::w2
偏移 28  : 共享的 VBase::v
总大小   : 32 字节
```

所以虚继承是"解决菱形"的专用工具，不是常规选项。设计上更优先的路线是把共同部分拆成独立的小对象让两边共享（组合），从源头消灭菱形。标准库的 `std::iostream` 层次是虚继承最著名的实战案例。

### 14.6.3 dynamic_cast 与 typeid：运行期类型识别
{: .sec-know}

类层次一旦多态，"这个基类指针实际指向谁"就是真实需求，运行期识别（RTTI）为此服务：

```cpp
// dyn_cast.cpp —— 需要 -std=c++20
#include <iostream>
#include <typeinfo>

struct Animal {
    virtual ~Animal() = default;
};
struct Cat : Animal {
    void meow() const { std::cout << "meow\n"; }
};
struct Dog : Animal {};

int main() {
    Animal* a = new Cat;

    if (Cat* c = dynamic_cast<Cat*>(a)) {    // 成功：返回有效指针
        c->meow();
    }
    if (Dog* d = dynamic_cast<Dog*>(a)) {    // 失败：返回空指针
        d->meow();                           // 不会执行
    } else {
        std::cout << "not a dog\n";
    }

    std::cout << typeid(*a).name() << '\n';  // 多态类型：看真实类型
    delete a;
}
```

```bash
g++ -std=c++20 -Wall -Wextra dyn_cast.cpp -o dyn_cast && ./dyn_cast
```

```text
meow
not a dog
3Cat
```

使用条件与细节：

- `dynamic_cast` 的源类型必须是**多态类型**（至少有一个虚函数），否则编译错误——没有虚表就没有运行期类型信息；
- 指针版失败返回 `nullptr`；引用版失败抛 `std::bad_cast`（头文件 `<typeinfo>`）；
- `typeid(*ptr).name()` 的返回串是平台相关的：GCC 是 Itanium 编号（`3Cat`），MSVC 是 `struct Cat`，别拿它做逻辑判断，只用于调试输出；
- 虚继承下从虚基类向派生类下行**只能用** `dynamic_cast`，`static_cast` 直接编译错误（偏移要运行期才知道）；
- `-fno-rtti` 可以整体关掉 RTTI（游戏引擎、嵌入式常用），代价是 `dynamic_cast`/`typeid` 不可用，得自建类型标记。

频繁 `dynamic_cast` 是设计警报：层次里到处问"你到底是谁"，说明基类接口缺函数。转型该是例外，不该是流程。

## 14.7 技术解惑
{: .sec-ts}

### 14.7.1 std::is_base_of 与 concepts 约束
{: .sec-ext}

第 13 篇讲过名字查找，模板里的层次约束用类型特征检查更直接。`std::is_base_of`（`<type_traits>`）在编译期回答"Base 和 Derived 是不是继承关系"，private 继承也算数，相同的两个类也算数。C++20 起可以把检查包装成 concept：

```cpp
// isbase.cpp —— 需要 -std=c++20
#include <concepts>
#include <iostream>
#include <type_traits>

struct Vehicle {};
struct Car : Vehicle {};
struct Bike {};

template <class T>
concept VehicleLike = std::is_base_of_v<Vehicle, T>;

template <VehicleLike T>
void refuel(const T&) { std::cout << "加满\n"; }

int main() {
    refuel(Car{});
    // refuel(Bike{});   // 解开注释：约束不满足，编译错误且信息友好
}
```

```bash
g++ -std=c++20 -Wall -Wextra isbase.cpp -o isbase && ./isbase
```

```text
加满
```

注意方向差异：虚函数是"运行期只要满足接口就行"，concept 是"编译期就必须验证"。前者用于真正的多态调度，后者用于泛型算法想接受的类型范围——两者经常在同一项目共存。

### 14.7.2 CRTP：编译期多态
{: .sec-ext}

奇异递归模板模式（CRTP）用"派生类作为基类模板参数"在**编译期**完成类似虚函数的派发，没有 vptr、没有间接调用、可内联：

```cpp
// crtp.cpp —— 需要 -std=c++20
#include <iostream>

template <class Derived>
struct Shape {
    double area() const { return static_cast<const Derived*>(this)->area_impl(); }
};

struct Circle : Shape<Circle> {
    double r;
    explicit Circle(double r) : r(r) {}
    double area_impl() const { return 3.141592653589793 * r * r; }
};

struct Square : Shape<Square> {
    double side;
    explicit Square(double s) : side(s) {}
    double area_impl() const { return side * side; }
};

int main() {
    std::cout << Circle(2.0).area() << '\n';
    std::cout << Square(3.0).area() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra crtp.cpp -o crtp && ./crtp
```

```text
12.5664
9
```

代价同样明确：`Circle` 和 `Square` 是**不相关的两个类型**，没法装进同一个容器统一调度——CRTP 把多态从运行期挪到了编译期，也就失去了运行期的灵活性。什么时候用：类型集合编译期已知、追求零开销、或者只是给一族类注入公共接口（`enable_shared_from_this` 就是标准库里的 CRTP）。完整展开见模板篇。

### 14.7.3 std::variant 与访问者：闭集上的多态
{: .sec-ext}

C++17 的 `std::variant` 提供另一条路：不用继承，把"可能是哪几种类型"直接写进类型，用 `std::visit` 分派：

```cpp
// variant.cpp —— 需要 -std=c++17
#include <iostream>
#include <variant>

struct Circle { double r; };
struct Rect { double w, h; };

struct AreaVisitor {
    double operator()(const Circle& c) const { return 3.141592653589793 * c.r * c.r; }
    double operator()(const Rect& r) const { return r.w * r.h; }
};

int main() {
    std::variant<Circle, Rect> shape = Circle{2.0};
    std::cout << std::visit(AreaVisitor{}, shape) << '\n';
    shape = Rect{3.0, 4.0};
    std::cout << std::visit(AreaVisitor{}, shape) << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra variant.cpp -o variant && ./variant
```

```text
12.5664
12
```

和继承多态的分工靠"集合开闭"判断：类型集合**封闭**（就这几种，编译期全知道）用 variant——漏写分支编译器报错，值栈存储无堆分配；集合**开放**（用户可能扩展新图形）用继承——这正是虚函数存在的意义。状态机、AST 节点、协议消息这类天然闭集，variant 往往更合适。

### 14.7.4 "组合优于继承"的判断标准
{: .sec-best}

判断标准可以收成三问：

- **is-a 成立吗？** 把"X 是一种 Y"念出来，业务上不成立就组合。
- **需要多态调度吗？** 不需要基类指针统一处理，就没有 public 继承的必要。
- **基类稳定吗？** 基类还在频繁改，继承会把每次改动放大到所有派生类。

一个重构方向的例子——用 private 继承"复用" `vector` 实现 `Stack` 是经典反面设计（暴露了错误接口），组合版把接口完全握在自己手里：

```cpp
// compose.cpp —— 需要 -std=c++20
#include <iostream>
#include <vector>

class MyStack {
public:
    void push(int v) { data_.push_back(v); }
    int pop() { int v = data_.back(); data_.pop_back(); return v; }
    bool empty() const { return data_.empty(); }
private:
    std::vector<int> data_;     // "有一个"缓冲区，而不是"是一个" vector
};

int main() {
    MyStack s;
    s.push(1); s.push(2);
    std::cout << s.pop() << s.pop() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra compose.cpp -o compose && ./compose
```

```text
21
```

组合版多写了几行委托代码，换来的是：`vector` 未来加什么成员都影响不到 `MyStack` 的接口；`data_` 可以随时换成 deque 而不破坏任何调用方。这就是"实现复用用组合"的具体含义。

### 14.7.5 脆弱基类问题
{: .sec-ts}

脆弱基类（fragile base class）指基类的内部实现细节成为派生类的隐式依赖，基类一改，派生类行为悄悄改变。典型触发方式：派生类重写的虚函数被基类构造函数/其他虚函数间接调用，基类调整调用链后派生类的假设失效；或者派生类依赖 protected 数据的语义，基类换个存法就全线崩塌。C++ 比 Java 更脆的一点在二进制层面：基类加一个数据成员，所有派生类对象的偏移全变，已编译代码如果不重编就是内存错乱——库以二进制分发时这是硬约束。

缓解手段和前面各节一一对应：protected 数据换成 protected 虚函数钩子（14.2.3）；构造期不调虚函数（14.3.3）；实现复用走组合（14.7.4）；二进制稳定需求用接口类加 pimpl。设计时给基类立个纪律："protected 和 virtual 都是接口，改动按接口变更管理"——记住这条，大半脆弱基类问题在评审时就能拦住。

## 变式追问
{: .sec-think}

1. 为什么构造函数不能是虚函数，析构函数却经常必须是？推理：虚函数派发依赖对象的虚表指针，而虚表指针是在构造过程中逐层设置的——调用构造函数那一刻对象还不存在，"通过虚表找到该调哪个构造函数"没有载体。析构正相反：对象销毁前虚表还完整，`delete BasePtr` 时需要按真实类型找到正确的析构链，这正是虚机制能服务的场景。所以这不是语言设计者随意的取舍，是"虚派发需要已存在的对象"这一机制约束的直接推论。

2. 虚继承能不能当默认选项，"反正能防菱形"？不能，代价说明一切：每个带虚基类的子对象多一个指针，虚基类成员访问多一次间接，构造顺序还变成"最派生类说了算"，中间类失去对基类初始化的控制。没有菱形的层次用虚继承纯属白付。真要防菱形，先审设计——公共基类里塞了什么数据让两条路径都想共享？多数答案是那段数据该拆成独立对象。

3. private 继承除了 EBO 还有什么不可替代的场景？想重写基类虚函数但不想暴露 is-a 时。典型情况：想定制某个框架类的行为，又不希望用户能把你的类当那个基类用——private 继承让你能重写、能在类内转换回基类去注册回调，外部却完全看不到继承关系。组合做不到这一点，因为组合拿不到重写资格。除此之外的场景组合都能覆盖，所以 private 继承在实际代码里出现频率很低，出现时基本都值得一句注释说明"为什么不用组合"。

4. `std::variant` 加访问者能不能完全取代虚函数多态？看集合的开闭性。variant 把类型集合写死在类型定义里，加一种新类型要改类型定义本身、再补全所有 visitor——改动集中在类型侧；虚函数反过来，加新派生类不动任何既有代码，但给基类加新虚函数要动所有派生类。类型集合稳定而操作频繁增加（编译器 AST 加新操作）选 variant；类型会扩展而操作集合稳定（图形库加新图形）选继承。两者的差异是"对什么开放"的工程取舍，不是优劣关系。
