## 19.1 内存分类
{: .sec-expl}

### 19.1.1 进程内存布局：一张地址地图
{: .sec-know}

以 64 位 Linux 为例（Windows 布局思想相同，具体地址范围不同），一个进程的虚拟地址空间从低到高大致是：

| 区域 | 内容 | 生命周期 | 谁管理 |
| --- | --- | --- | --- |
| 代码段（text） | 机器指令 | 程序全程 | 加载器，只读 |
| rodata | 字符串字面量、const 常量 | 程序全程 | 加载器，只读 |
| data | 已初始化的全局/静态变量 | 程序全程 | 程序启动时布置 |
| bss | 未初始化（或零初始化）的全局/静态变量 | 程序全程 | 加载器清零 |
| 堆（heap） | new/malloc 的动态内存 | 手动控制 | 分配器（glibc 等） |
| mmap 区 | 共享库、大块分配、TLS | 各自不同 | 内核 |
| 栈（stack） | 局部对象、函数调用信息 | 作用域结束自动回收 | 编译器生成的代码 |

三个规律值得记住：地址从低到高，栈在最高处向下长，堆在 bss 之上向上长，两者之间的空隙就是进程可以自由扩张的空间；rodata 与代码段只读（写它们会段错误），所以字符串字面量不可修改；bss 不占可执行文件体积——一个 100 MB 的零初始化全局数组不会让二进制变大 100 MB，加载器只记录"这段清零"。

### 19.1.2 打印地址验证布局
{: .sec-prac}

```cpp
// memory_map.cpp —— 需要 -std=c++20
#include <iostream>

int g_init = 42;               // data 段
int g_zero;                    // bss 段
const char* g_str = "hello";   // 字面量本体在 rodata，指针变量在 data

void func() {}                 // 函数体在代码段

int main() {
    static int s_static = 7;   // 静态局部变量也在 data 段
    int local = 1;             // 栈
    int* heap = new int(9);    // 堆
    thread_local int tls = 5;  // 线程局部存储（TLS）

    std::cout << "代码段 func       : " << reinterpret_cast<void*>(func) << '\n';
    std::cout << "rodata g_str 指向 : " << static_cast<const void*>(g_str) << '\n';
    std::cout << "data  g_init      : " << &g_init << '\n';
    std::cout << "bss   g_zero      : " << &g_zero << '\n';
    std::cout << "data  s_static    : " << &s_static << '\n';
    std::cout << "TLS   tls         : " << &tls << '\n';
    std::cout << "堆    heap        : " << heap << '\n';
    std::cout << "栈    local       : " << &local << '\n';
    delete heap;
}
```

```bash
g++ -std=c++20 -Wall -Wextra memory_map.cpp -o mm && ./mm
```

数字印证了地图：代码段最低，rodata/data/bss 紧随其后，堆（brk 分配）贴着 bss 往上，TLS 和共享库落在 mmap 区，栈在最高处。`reinterpret_cast` 把函数指针转成 `void*` 打印在 POSIX/Windows 上都可行（标准里属于"实现有条件支持"，主流平台都支持）。

### 19.1.3 虚拟内存与页
{: .sec-expl}

程序里的地址全是虚拟地址，CPU 通过 MMU 查页表翻译成物理地址。翻译以**页**为单位，x86-64 常见页大小 4 KB（支持 2 MB/1 GB 大页）。这个设计带来三个日常能感知的效果：其一，物理内存按需分配——`new` 拿到虚拟地址不代表物理页已就位，首次触碰才触发缺页中断分配，这就是"内存分配快，首次使用慢"的原因；其二，每个进程有独立页表，地址空间互相隔离，野指针捅穿的只是自己的空间；其三，malloc 请求超过约 128 KB（glibc 的 MMAP_THRESHOLD，可调）时会改走 mmap，直接向内核要一整块，归还时整块还给内核——这解释了为什么大块分配和小块分配的行为差异那么大。

### 19.1.4 静态存储期与 TLS
{: .sec-know}

全局变量、静态成员、静态局部变量都是**静态存储期**：程序启动时构造（main 之前），程序退出时析构（main 之后）。两个工程提示：跨翻译单元的全局对象有初始化顺序问题，`static` 局部变量（C++11 起初始化保证线程安全）是更安全的单例写法；全局对象的构造函数里别做复杂的事，否则 main 还没开始你的程序就已经在跑业务逻辑了。

`thread_local`（C++11）给每个线程一份独立副本，线程退出时析构。它解决的是"全局变量 + 多线程 = 竞争"的矛盾——错误码缓存、随机数引擎、日志上下文这类"每线程一份刚刚好"的状态都适合放这里。代价是访问可能多一次 TLS 索引，别把它当性能优化用。

## 19.2 栈内存管理
{: .sec-know}

### 19.2.1 栈帧结构
{: .sec-know}

每次函数调用在栈上压一个**栈帧**，典型布局（x86-64 System V ABI）从高地址到低地址是：调用方实参（放不进寄存器的部分）、返回地址、调用方的栈帧指针（rbp）、本函数的局部对象与溢出的寄存器。返回地址入栈这一步就是缓冲区溢出攻击的靶子——往局部数组里写超长数据可能盖掉返回地址。现代编译器默认开栈保护（`-fstack-protector` 系列选项，部分发行版已默认启用），在返回地址前放一个哨兵值检测覆写。

栈帧的开销几乎为零：移动栈指针一条指令，没有构造查找、没有锁。这就是"栈分配比堆快"的真实来源——不是魔法，是分配动作只是指针加减，回收是反方向的指针加减。

### 19.2.2 增长方向与大小限制
{: .sec-know}

主流平台（x86-64、ARM）的栈都向低地址增长。大小有硬上限：Linux 主线程默认 8 MB（`ulimit -s` 可查可改），Windows 默认 1 MB（链接时 `/STACK` 改），pthread 创建的线程默认也是 8 MB 左右（glibc，可由 `pthread_attr_setstacksize` 调）。

```cpp
// stack_layout.cpp —— 需要 -std=c++20
#include <iostream>

void recurse(int n) {
    int marker = n;
    if (n == 0) {
        std::cout << "最深处局部变量地址: " << &marker << '\n';
        return;
    }
    recurse(n - 1);
}

int main() {
    int base = 0;
    std::cout << "main  局部变量地址: " << &base << '\n';
    recurse(3);
}
```

```bash
g++ -std=c++20 -Wall -Wextra stack_layout.cpp -o sl && ./sl
ulimit -s
```

```text
# 64 位 Linux，g++ 12
main  局部变量地址: 0x7ffd5e1a2c44
最深处局部变量地址: 0x7ffd5e1a2b64
8192
```

深处地址更小，印证向低地址增长；`ulimit -s` 输出 8192，单位 KB，即 8 MB。

### 19.2.3 栈溢出与递归深度
{: .sec-warn}

栈空间用完就是**栈溢出**，表现为 SIGSEGV（Linux）或访问违例（Windows）。两个常见来源：无界递归，和单个超大局部对象。8 MB 除以每层栈帧大小就是安全递归深度——每层 100 字节能递归约 8 万层，每层 4 KB 只剩约 2000 层。栈溢出的崩溃点在"深处"，core dump 里的调用栈可能本身已经残缺，定位体验极差，所以别等崩了再想，写递归前先算帧大小。

```cpp
// recursion_safe.cpp —— 需要 -std=c++20
#include <iostream>

struct Frame {
    char buf[4096];    // 每层约 4 KB 栈帧
};

long long used = 0;

void recurse(int depth_left) {
    Frame f;
    f.buf[0] = 1;      // 有副作用，防止整帧被优化掉
    ++used;
    if (depth_left > 0) recurse(depth_left - 1);
}

int main() {
    recurse(3);        // 有界：8 MB 栈配 4 KB 帧的极限约 2000 层，这里只 4 层
    std::cout << "递归 4 层，每层约 " << sizeof(Frame)
              << " 字节，共约 " << used * sizeof(Frame) << " 字节\n";
}
```

```text
# Linux g++ 12 下的输出
递归 4 层，每层约 4096 字节，共约 16384 字节
```

工程对策：递归改成显式栈 + 循环（树遍历常用）；递归参数用深度上限保护；超大缓冲区改用堆（`std::vector<char>`）。

### 19.2.4 alloca 与 VLA：别用
{: .sec-pit}

C99 的变长数组 VLA 不是 C++ 标准（GCC/Clang 把它当扩展），`alloca` 更是 POSIX 扩展。两者共同的问题：在栈上"动态"分配，失败时没有返回值可查——溢出就是直接段错误，而堆分配失败至少还能拿到 `bad_alloc`。栈本来就小还搞动态分配，等于在悬崖边睡觉。需要"大小运行期才知道的缓冲区"时，`std::vector` 加自定义分配器才是正路。

### 19.2.5 大对象别放栈上
{: .sec-best}

经验阈值：单个局部对象超过几 KB 就该想想要不要放堆。常见违规是按值返回大容器临时被复制成栈对象、`char buf[N]` 想开 1 MB、异常安全路径上的大临时对象。辨析一下速度问题：

### 辨析：栈分配与堆分配的速度差距
{: .sec-iv}

"栈比堆快"的完整表述是：**分配动作**栈快（一条指针加减 vs 分配器查找空闲块），**使用速度**两者一样（都是普通内存访问，热数据都进缓存）。真正把程序拖慢的往往不是分配本身，而是堆分配附带的行为：可能加锁（多线程竞争同一个分配器锁）、可能缺页（新物理页首次触碰）、缓存不友好（栈天然局部性好）。所以优化方向是"减少分配次数"（内存池、pmr、对象复用），而不是"把堆对象硬塞进栈"。

## 19.3 堆内存管理
{: .sec-know}

### 19.3.1 malloc/free 与 new/delete 的差别
{: .sec-know}

| 维度 | malloc/free | new/delete |
| --- | --- | --- |
| 语言层 | C 库函数 | C++ 运算符，可重载 |
| 构造/析构 | 只给裸内存，不构造 | 分配后调构造，delete 前调析构 |
| 失败行为 | 返回 NULL | 抛 `std::bad_alloc`（nothrow 版返回空） |
| 类型安全 | 返回 `void*`，要强转 | 返回正确类型的指针 |
| 大小计算 | 手动 `sizeof(T)` | 编译器自动 |
| 混用 | `free` 一块 new 出来的内存是 undefined behavior | `delete` 一块 malloc 出来的内存同样 UB |

需要分配未构造的裸内存（自己管理对象生命周期，比如实现容器）时，C++ 的正路是 `::operator new` / `::operator delete` 或 `std::allocator`，而不是 malloc——它们与 new 的异常语义和大小计算保持一致。

```cpp
// malloc_vs_new.cpp —— 需要 -std=c++20
#include <cstdlib>
#include <iostream>
#include <new>
#include <string>

int main() {
    // malloc：裸内存 + 手动大小 + 判空
    void* p = std::malloc(64);
    if (!p) return 1;
    std::free(p);

    // new：分配 + 构造 + 正确类型，失败抛 bad_alloc
    auto* s = new std::string("hello");
    std::cout << *s << '\n';
    delete s;

    // nothrow 版本：失败返回 nullptr，返回值风格
    auto* q = new (std::nothrow) int[100];
    if (!q) return 1;
    delete[] q;
}
```

```text
# Linux g++ 12 下的输出
hello
```

### 19.3.2 new 的三个层次
{: .sec-know}

"new"这个词在 C++ 里指三个不同的东西，混着说不清问题就得混着修不好：

1. **new 表达式**：`new T(args)`。做两件事——调用 `operator new` 分配内存，再在内存上构造 T。抛异常时自动释放已分配内存（这是语言保证，不会"构造失败还漏内存"）。
2. **operator new**：`::operator new(size)`。只分配裸内存的函数，可全局或类内重载，失败按约定抛 `bad_alloc`（或 nothrow 版返回空）。
3. **placement new**：`new (ptr) T(args)`。在 ptr 指向的现成内存上构造，完全不分配。对应的清理是**手动调用析构函数**，然后按内存的来源归还（pool 还给 pool，栈上则什么都不用做）。

```cpp
// placement_new.cpp —— 需要 -std=c++20
#include <iostream>
#include <new>
#include <string>

int main() {
    // 层次 1：new 表达式，分配 + 构造一步到位
    auto* s1 = new std::string("普通 new");

    // 层次 2：operator new，只拿裸内存
    void* raw = ::operator new(sizeof(std::string));

    // 层次 3：placement new，在裸内存上构造，不再分配
    auto* s2 = new (raw) std::string("placement new");

    std::cout << *s1 << " | " << *s2 << '\n';

    delete s1;               // 层次 1 配 delete
    s2->~basic_string();     // 层次 3：手动析构，不能 delete
    ::operator delete(raw);  // 内存从 operator new 来，还给 operator delete
}
```

```bash
g++ -std=c++20 -Wall -Wextra placement_new.cpp -o pn && ./pn
```

```text
# Linux g++ 12 下的输出
普通 new | placement new
```

placement new 的日常用法是"在栈缓冲区上构造"（配合 `alignas` 保证对齐）和容器/内存池内部实现。现代代码里 `std::destroy_at`（C++17，`<memory>`）能替你调析构，可读性更好：`std::destroy_at(s2);`。

### 19.3.3 new[]/delete[] 必须配对
{: .sec-know}

`new T[n]` 分配的内存头部有一段额外空间（俗称 cookie）记录元素个数，`delete[]` 读这个数逐个析构再归还。`delete`（不带方括号）作用在 `new[]` 的指针上是 undefined behavior——通常表现为只析构第一个元素、且归还地址错位导致分配器崩溃。编译器靠类型系统在能查的场合报错（如 `-Wmismatched-new-delete`），但跨函数传递指针后它就查不到了，纪律只能靠自己。

```cpp
// array_new.cpp —— 需要 -std=c++20
#include <iostream>

struct Tracer {
    static int alive;
    int v;
    explicit Tracer(int x) : v(x) { ++alive; std::cout << "构造 " << v << '\n'; }
    ~Tracer() { --alive; std::cout << "析构 " << v << '\n'; }
};
int Tracer::alive = 0;

int main() {
    Tracer* arr = new Tracer[3]{Tracer(1), Tracer(2), Tracer(3)};
    std::cout << "存活: " << Tracer::alive << '\n';
    delete[] arr;    // cookie 里有数量，3 个全部析构
    std::cout << "存活: " << Tracer::alive << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra array_new.cpp -o an && ./an
```

```text
# Linux g++ 12 下的输出
构造 1
构造 2
构造 3
存活: 3
析构 3
析构 2
析构 1
存活: 0
```

> **坑：** 用 `typedef int Arr[10];` 或 `using Arr = int[10];` 后，`new Arr` 实际是 `new int[10]`，必须 `delete[]`——别名把数组形状藏起来了，这是最容易被漏掉的一处配对。直接用 `std::vector` 或 `std::make_unique<T[]>` 可以让配对完全自动化。
{: .sec-pit}

### 19.3.4 对齐：alignof/alignas、aligned new 与 false sharing
{: .sec-know}

对齐是"数据地址必须是某个值的整数倍"的硬件约束：x86 上未对齐访问慢一点，某些 ARM 配置和所有原子操作上未对齐是直接错误。`alignof(T)` 查询类型的对齐要求，`alignas(N)` 提升它。编译器会为满足成员对齐在结构体里插 padding，所以成员排序影响 `sizeof`（大成员放前面能减少浪费）。

C++17 之前，超过 `alignof(std::max_align_t)`（通常 16）的"过度对齐"类型用 new 分配会翻车；C++17 引入对齐感知的 new——`new T` 自动按 `alignof(T)` 分配（内部对超对齐类型走 `std::align_val_t` 版本的 operator new），配对的 delete 同样自动。

```cpp
// alignment.cpp —— 需要 -std=c++17
#include <cstdint>
#include <iostream>
#include <new>

struct alignas(64) CacheLine {
    char data[64];
};

struct Packed {
    char a;      // 1 字节 + 7 字节 padding
    double b;    // 8 字节对齐
};

int main() {
    std::cout << "CacheLine: align=" << alignof(CacheLine)
              << " sizeof=" << sizeof(CacheLine) << '\n';
    std::cout << "Packed    : align=" << alignof(Packed)
              << " sizeof=" << sizeof(Packed) << '\n';

    CacheLine* p = new CacheLine;    // C++17：自动按 64 对齐分配
    std::cout << "new 出来的地址 64 字节对齐: "
              << (reinterpret_cast<std::uintptr_t>(p) % 64 == 0 ? "是" : "否") << '\n';
    delete p;
}
```

```bash
g++ -std=c++17 -Wall -Wextra alignment.cpp -o al && ./al
```

```text

CacheLine: align=64 sizeof=64
Packed    : align=8 sizeof=16
new 出来的地址 64 字节对齐: 是
```

对齐最出名的应用场景是多线程：现代 CPU 的缓存以**缓存行**为单位（主流 64 字节）在核间同步。两个线程各自写各自的数据，只要数据挤在同一缓存行，硬件就当它们是共享数据来回打乒乓——这叫 **false sharing**，性能杀手榜常年前排。解药就是 `alignas(64)` 把热变量隔开。

```cpp
// false_sharing.cpp —— 需要 -std=c++20，机器至少 2 个硬件线程
#include <atomic>
#include <chrono>
#include <iostream>
#include <thread>

struct Packed {                       // 两个计数器挤在同一缓存行
    std::atomic<long long> a{0};
    std::atomic<long long> b{0};
};

struct Spaced {                       // 各占一条缓存行
    alignas(64) std::atomic<long long> a{0};
    alignas(64) std::atomic<long long> b{0};
};

template <typename T>
long long run_test() {
    T t;
    std::thread t1([&] { for (int i = 0; i < 20'000'000; ++i) t.a.fetch_add(1, std::memory_order_relaxed); });
    std::thread t2([&] { for (int i = 0; i < 20'000'000; ++i) t.b.fetch_add(1, std::memory_order_relaxed); });
    t1.join();
    t2.join();
    return t.a + t.b;
}

int main() {
    auto t0 = std::chrono::steady_clock::now();
    long long r1 = run_test<Packed>();
    auto t1 = std::chrono::steady_clock::now();
    long long r2 = run_test<Spaced>();
    auto t2 = std::chrono::steady_clock::now();
    std::cout << "Packed 用时 " << std::chrono::duration_cast<std::chrono::milliseconds>(t1 - t0).count() << " ms\n";
    std::cout << "Spaced 用时 " << std::chrono::duration_cast<std::chrono::milliseconds>(t2 - t1).count() << " ms\n";
}
```

```text
# 8 核 x86-64 Linux，数值每次运行会变，倍数关系稳定
Packed 用时 612 ms
Spaced 用时 178 ms
```

代码一行没多，3 倍多的差距全来自 `alignas(64)`。C++17 标准头 `<new>` 里还有 `std::hardware_destructive_interference_size` 可查询目标平台的缓存行大小（GCC 12 起支持，用它替代写死的 64 可移植性更好）。

### 19.3.5 operator new 重载与类专属分配
{: .sec-know}

`operator new` 可以在全局重载（改整个程序的分配行为，调试追踪常用），也可以做成类的静态成员（C++11 起隐式 static），让这一个类型的分配改道——高频小对象用对象池时就是这么接进去的。

```cpp
// custom_new.cpp —— 需要 -std=c++20
#include <iostream>
#include <new>

struct Packet {
    int payload[16];

    // 类专属 operator new：这个类型的 new 全部改道
    static void* operator new(std::size_t n) {
        std::cout << "Packet::operator new(" << n << ")\n";
        return ::operator new(n);        // 演示：转手给全局版本
    }
    static void operator delete(void* p) noexcept {
        std::cout << "Packet::operator delete\n";
        ::operator delete(p);
    }
};

int main() {
    auto* p = new Packet;                 // 走类专属版本
    delete p;
    auto* q = new Packet;                 // 第二次分配：同样走类专属版本
    delete q;
    std::cout << "done\n";
}
```

```text
# Linux g++ 12 下的输出
Packet::operator new(64)
Packet::operator delete
Packet::operator new(64)
Packet::operator delete
done
```

类里定义了任意形式的 `operator new` 后，它会把全局版本整个遮蔽掉——名字在类作用域里找到了，编译器就不再看全局，只定义了普通版而用户写 `new (std::nothrow) Packet`，是编译错误而不是回落；想精确控制就把 nothrow 版、对齐版（`std::align_val_t`）都重载齐。

### 19.3.6 内存碎片与内存池
{: .sec-expl}

频繁分配释放大小不一的块，空闲内存会被切成大量不连续的小块——总量够用却凑不出一整块，这就是**外部碎片**；分配器为管理元数据占用的空间则是**内部碎片**。碎片对长期运行的服务是慢性病：内存曲线只涨不跌，监控看着像泄漏，抓个 core 又找不到谁拿着指针。

内存池的动机就是把这个慢性病管起来：启动时一次性要一大块，之后的小分配从池里划（常常只挪一个下标，无锁也无系统调用），同尺寸块反复复用不产生碎片，整池一次性归还。游戏、高频交易、网络服务器的定制分配器（allocator）本质都是它。不想自己写池的话，标准库的 `std::pmr` 就是官方成品。

### 19.3.7 分配器与 std::pmr（C++17）
{: .sec-ext}

传统 `std::allocator<T>` 是模板参数——`std::vector<int, MyPool<int>>` 和 `std::vector<int>` 是**两个不同的类型**，接口没法统一。C++17 的 PMR（polymorphic memory resource）换了个思路：容器类型不变（`std::pmr::vector<int>`），分配行为通过运行期的 `std::pmr::memory_resource*` 指针注入，"用哪种内存策略"从类型系统挪到了运行期参数。

三个核心资源：

- `monotonic_buffer_resource`：只进不出，deallocate 是空操作，整体销毁时一次释放。适合生命周期同生共死的一批对象（一次请求、一帧渲染）。
- `unsynchronized_pool_resource`：按尺寸分桶的小块池，单线程用；多线程对应 `synchronized_pool_resource`。
- `new_delete_resource`：默认资源，包装全局 new/delete。

```cpp
// pmr_demo.cpp —— 需要 -std=c++17
#include <iostream>
#include <memory_resource>
#include <string>
#include <vector>

int main() {
    // 栈上 2 KB 缓冲区作后备，池先用它，用尽才向系统要
    char buffer[2048];
    std::pmr::monotonic_buffer_resource mono(buffer, sizeof(buffer));

    std::pmr::vector<std::pmr::string> v(&mono);
    for (int i = 0; i < 8; ++i) {
        v.emplace_back("msg-" + std::to_string(i));
    }
    for (const auto& s : v) std::cout << s << ' ';
    std::cout << '\n';

    // 独立池：反复分配释放同尺寸小块的场景
    std::pmr::unsynchronized_pool_resource pool;
    std::pmr::vector<int> nums(&pool);
    nums.push_back(42);
    std::cout << nums[0] << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra pmr_demo.cpp -o pm && ./pm
```

```text
# Linux g++ 12 下的输出
msg-0 msg-1 msg-2 msg-3 msg-4 msg-5 msg-6 msg-7
42
```

> **坑：** 挂在栈缓冲区上的 resource 析构后，用它的容器必须已经死透——容器活得比 resource 久是 undefined behavior。另外 `std::pmr::vector` 拷贝构造默认**不带**源容器的 resource（新容器走默认资源），需要跟随就显式传。这两条是 pmr 的头号事故来源。
{: .sec-pit}

### 19.3.8 RAII：资源获取即初始化
{: .sec-know}

RAII 的规则一句话：**把资源的生命周期绑到对象的生命周期上——构造函数获取资源，析构函数释放资源**。局部对象在离开作用域时（包括异常造成的栈展开）保证析构，于是"释放"这件事从"记得手动做"变成"不可能不做"。忘写 delete、异常路径漏释放、提前 return 漏清理，三类事故被同一个机制一锅端。

和 GC 对比着看更清楚：

| 维度 | RAII | 垃圾回收 |
| --- | --- | --- |
| 释放时机 | 确定性：离开作用域立刻 | 不确定：等 GC 跑 |
| 能管的资源 | 任何：内存、文件、锁、socket、事务 | 通常只有内存 |
| 析构函数 | 有确定语义，可依赖 | 多数语言形同虚设 |
| 循环引用 | 不存在（所有权显式） | GC 能处理 |
| 代价 | 智能指针计数、代码要设计所有权 | 运行时停顿、内存占用上浮 |

GC 只管内存，而文件句柄忘了关、锁忘了放这些"非内存资源泄漏"，RAII 一律覆盖。RAII 不是 C++ 独有的思想，但只有 C++ 把析构时机定得足够硬，让它撑得起资源管理的全部重量。

标准库没有 scope guard，手写一个不到二十行：

```cpp
// scope_exit.cpp —— 需要 -std=c++17（CTAD）
#include <cstdio>
#include <iostream>
#include <stdexcept>

template <typename F>
class ScopeExit {
    F f_;
    bool active_ = true;
public:
    explicit ScopeExit(F f) : f_(std::move(f)) {}
    ScopeExit(const ScopeExit&) = delete;
    ScopeExit& operator=(const ScopeExit&) = delete;
    ~ScopeExit() {
        if (active_) f_();     // 正常返回、提前 return、异常展开，全都执行
    }
    void dismiss() noexcept { active_ = false; }   // 想自己接管时取消
};

void risky(bool fail) {
    FILE* fp = std::fopen("demo.txt", "w");
    if (!fp) return;
    ScopeExit guard([&] { std::fclose(fp); });   // CTAD 推导闭包类型
    if (fail) throw std::runtime_error("中途失败");   // guard 析构时文件照样关
    std::fputs("ok\n", fp);
}

int main() {
    try {
        risky(false);
        risky(true);
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```


### 19.3.9 unique_ptr：独占所有权的默认选择
{: .sec-know}

`std::unique_ptr<T>` 是"这个指针归我管、别人不许碰"的表达。零开销：无状态删除器下大小等于裸指针，访问无间接成本，析构就是一次内联的 delete。**默认情况下 new 出来的东西应该立刻交给 unique_ptr，裸指针只作为观察者出现**。

```cpp
// unique_ptr_demo.cpp —— 需要 -std=c++20
#include <cstdio>
#include <iostream>
#include <memory>

struct Widget {
    int id;
    explicit Widget(int i) : id(i) { std::cout << "Widget " << id << " 构造\n"; }
    ~Widget() { std::cout << "Widget " << id << " 析构\n"; }
};

std::unique_ptr<Widget> make_widget(int id) {
    return std::make_unique<Widget>(id);   // C++14 起；工厂返回独占所有权
}

int main() {
    auto w = make_widget(1);
    std::cout << "id = " << w->id << '\n';
    if (w) std::cout << "可作布尔判断\n";
    if (w != nullptr) std::cout << "与 nullptr 比较也行\n";

    // 数组特化：unique_ptr<T[]>，operator[]，自动 delete[]
    auto arr = std::make_unique<int[]>(3);
    arr[0] = 10; arr[1] = 20; arr[2] = 30;
    std::cout << arr[0] + arr[1] + arr[2] << '\n';

    // 自定义删除器：接管任意 C 资源
    auto closer = [](std::FILE* fp) { if (fp) std::fclose(fp); };
    std::unique_ptr<std::FILE, decltype(closer)> fp(std::fopen("demo.txt", "w"), closer);
    if (fp) std::fputs("RAII 管文件\n", fp.get());

    std::cout << "作用域结束，按构造逆序自动清理\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra unique_ptr_demo.cpp -o up && ./up
```

```text
# Linux g++ 12 下的输出

id = 1
可作布尔判断
与 nullptr 比较也行

RAII 管文件

```

几个使用要点：所有权转移用 `std::move`，拷贝是编译错误；`release()` 交出裸指针并放弃管理（接盘方必须接住），`get()` 只看不管；`reset()` 立即释放旧资源。自定义删除器若是函数指针类型，`sizeof(unique_ptr)` 会变大（要额外存储删除器），无捕获 lambda 时编译器能优化掉这块存储。

### 19.3.10 shared_ptr：控制块、计数与线程安全边界
{: .sec-know}

`std::shared_ptr<T>` 用**引用计数**实现"最后一个走的关灯"。每个受管对象挂一个**控制块**：强计数（多少个 shared_ptr 指着）+ 弱计数（多少个 weak_ptr 指着）+ 删除器 + 分配器。强计数归零析构对象，强弱都归零才释放控制块本身。计数是原子操作（`std::atomic` 实现），所以：

- **不同** shared_ptr 实例（哪怕指向同一对象）在**不同线程**上并发使用，安全；
- **同一个** shared_ptr 实例被多线程并发读写（一个线程 reset，另一个线程读），是数据竞争，UB；
- 被指的对象本身不因 shared_ptr 而线程安全，该加锁还得加锁。

```cpp
// shared_ptr_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <memory>
#include <vector>

class Session : public std::enable_shared_from_this<Session> {
public:
    std::shared_ptr<Session> handle() {
        return shared_from_this();   // 复用已有控制块，绝不写 shared_ptr<Session>(this)
    }
    ~Session() { std::cout << "Session 析构\n"; }
};

int main() {
    // make_shared：对象与控制块一次分配
    auto s1 = std::make_shared<Session>();
    std::cout << "use_count=" << s1.use_count() << '\n';   // 1

    auto h = s1->handle();                                  // 共享同一控制块
    std::cout << "use_count=" << h.use_count() << '\n';     // 2

    // 别名构造：共享 vec 的控制块，但指向其内部元素
    auto vec = std::make_shared<std::vector<int>>(4, 7);
    std::shared_ptr<int> first(vec, vec->data());
    vec.reset();                          // vector 本体靠 first 继续活着
    std::cout << "别名构造: " << *first
              << ", use_count=" << first.use_count() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra shared_ptr_demo.cpp -o sp && ./sp
```

```text
# Linux g++ 12 下的输出

use_count=2
别名构造: 7, use_count=1
Session 析构
```

三个细节值得单独记：`enable_shared_from_this` 解决"成员函数里需要拿自己的 shared_ptr"——直接 `shared_ptr<T>(this)` 会创建第二个控制块，双重 delete 等着你；用了别名的 `first` 保持整个 vector 存活，哪怕没人再指 vector 本体。`make_shared` 把对象和控制块放在**同一次分配**里，比 `shared_ptr<T>(new T)` 少一次 malloc，缓存局部性也更好——但代价是只要有 weak_ptr 还在，整块内存（含对象）都不能还，大对象的延迟释放就是这么来的。

### 19.3.11 weak_ptr：破环与探活
{: .sec-know}

`std::weak_ptr<T>` 指向 shared_ptr 管理的对象但不增加强计数——纯粹是"观察者"。两大用途：打破 `shared_ptr` 的循环引用（A 强指 B、B 强指 A，计数永远到不了零，双双泄漏；把一边换成 weak_ptr 即解），以及缓存类场景（对象归不归缓存活，使用者探活后临时拿强引用）。

```cpp
// weak_ptr_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <memory>

struct Node {
    std::weak_ptr<Node> next;    // 换成 shared_ptr 就是循环引用，永不析构
    int v;
    explicit Node(int x) : v(x) { std::cout << "Node " << v << " 构造\n"; }
    ~Node() { std::cout << "Node " << v << " 析构\n"; }
};

int main() {
    auto a = std::make_shared<Node>(1);
    auto b = std::make_shared<Node>(2);
    a->next = b;
    b->next = a;                 // 环存在，但 weak 不增计数

    if (auto locked = a->next.lock()) {      // lock：检查并提升，一步完成
        std::cout << "a->next 存活，v = " << locked->v << '\n';
    }
    b.reset();                   // 强计数归零，Node 2 立即析构
    std::cout << "b 释放后 expired = " << std::boolalpha << a->next.expired() << '\n';
    if (a->next.lock() == nullptr) {
        std::cout << "lock 返回空，安全\n";
    }
}
```


> **坑：** "先 `expired()` 判断再解引用"在多线程下有竞态——判断完对象可能刚被别的线程销毁。正确姿势只有一种：`if (auto sp = wp.lock())`，把检查和提升合成一步原子动作，拿到的 shared_ptr 保证对象存活到它离开作用域。
{: .sec-pit}

### 19.3.12 make_unique/make_shared 的必要性：异常安全
{: .sec-know}

`std::make_unique`（C++14）和 `std::make_shared`（C++11）不只是少打字，关键是**把"分配"与"接管"绑死在一次调用里**，中间不存在裸指针窗口。反例是这句经典代码：

```cpp
f(std::shared_ptr<int>(new int(42)), g());
```

两个实参的求值顺序不确定（C++17 只保证不交错，仍不保证先后）。若 `new int(42)` 先算、`g()` 后算而 g 抛异常，shared_ptr 构造函数没来得及执行，那 4 字节就漏了。改成 `f(std::make_shared<int>(42), g())` 后不存在裸指针，顺序怎么排都安全。下面用一个确定性复现让 ASan 抓现行：

```cpp
// leak_case.cpp —— 需要 -std=c++20
// 用 -fsanitize=address 编译，退出时 LeakSanitizer 抓到 4 字节泄漏
#include <iostream>
#include <memory>
#include <stdexcept>

void f(std::shared_ptr<int> a, int b) {
    std::cout << *a + b << '\n';
}

int g() {
    throw std::runtime_error("boom");
}

int main() {
    // make_shared 版本：分配 + 构造 + 控制块一次完成，异常时无泄漏窗口
    try {
        f(std::make_shared<int>(42), []() -> int {
            throw std::runtime_error("boom2");
        }());
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }

    // 确定性复现"分配与接管分家"：
    try {
        int* raw = new int(42);          // 1. 已分配
        (void)raw;
        g();                             // 2. 抛异常
        std::shared_ptr<int> take(raw);  // 3. 永远执行不到：没人 delete raw
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

### 19.3.13 所有权决策表
{: .sec-best}

| 场景 | 正确形态 | 理由 |
| --- | --- | --- |
| 函数只使用对象，不管理生命周期 | 传 `T&`（不可空）或 `T*`（可空观察者） | 观察者不拥有，别为此上计数 |
| 函数接管资源、延长对象寿命 | 传 `unique_ptr<T>` 按值 | 所有权转移写进签名，调用方看得见 |
| 多方共享、寿命无法静态确定 | `shared_ptr<T>` 按值传 | 引用计数承载"最后谁走谁关灯" |
| 共享结构的父子/反向引用 | 子持 `weak_ptr` 指父 | 破环 |
| 类持有独占子资源 | `unique_ptr` 成员 | 析构自动化，异常安全白拿 |
| 工厂函数 | 返回 `unique_ptr<T>` | 调用方需要共享时可再转 shared_ptr，反之不行 |
| 只想看看共享对象在不在 | `weak_ptr` + `lock()` | 不保活、能探活 |

补一条高频评审结论：**函数参数用不用 shared_ptr，看的是"函数内部是否需要延长寿命"，不是"对象是不是共享的"**——函数只是读一下就还回去，传 `const T&` 永远更好，引用不增加计数，语义也更轻。

### 19.3.14 内存泄漏检测：ASan 与 Valgrind
{: .sec-prac}

RAII 用对了，泄漏基本消失——剩下的泄漏往往藏在"裸 new 了一处""容器里存了裸指针没人清"这类死角。两个工具兜底：

- **AddressSanitizer（ASan）**：编译期插桩（`-fsanitize=address`），运行期拦截每一次内存访问，能抓泄漏（内置 LeakSanitizer）、越界、释放后使用、双重释放，报错直接给源码行号，慢 2 倍左右，是日常测试的首选。Linux 上链接需要运行到退出才汇总泄漏，常驻服务配合 `LSAN_OPTIONS` 或主动调用 `__lsan_do_recoverable_leak_check`。
- **Valgrind memcheck**：不改二进制、跑在虚拟机上，能抓同样的错误，慢 10~50 倍，适合无法重编译的存量二进制。命令：`valgrind --leak-check=full ./prog`。

ASan 的典型输出在 19.3.12 的 leak_case 里已经见过：`Direct leak` 是没有任何指针指着的内存，`Indirect leak` 是只被泄漏块内部引用的内存。日常开发把 ASan 加进单元测试的编译选项，泄漏在提交前就死掉。

```cpp
// uaf.cpp —— 需要 -std=c++20
// 释放后使用：undefined behavior，ASan 当场报错
#include <iostream>

int main() {
    int* p = new int(7);
    delete p;
    std::cout << *p << '\n';   // p 已释放，读它是 UB
}
```

```bash
g++ -std=c++20 -g -fsanitize=address uaf.cpp -o uaf && ./uaf
```

```text
# 64 位 Linux，g++ 12，ASan 输出（节选）
==24567==ERROR: AddressSanitizer: heap-use-after-free on address 0x602000000010
READ of size 4 at 0x602000000010 thread T0
    #0 ... in main uaf.cpp:7
freed by thread T0 here:
    #0 ... in operator delete
    #1 ... in main uaf.cpp:6
```

### 19.3.15 并发内存模型入门
{: .sec-know}

C++11 起标准定义了内存模型，三个核心概念：

- **对象与内存位置**：每个标量对象占一个内存位置，相邻位域合占一个。两个线程访问"同一个内存位置"才谈得上竞争。
- **数据竞争**：两个线程对同一内存位置的冲突访问（至少一写）、无同步、至少一个不是原子操作——三者凑齐就是 undefined behavior，不是"读到旧值"那么温柔，编译器可以假设竞争不存在并做出任何优化。
- **同步原语**：`std::atomic` 和互斥锁在访问之间建立 happens-before 关系，竞争被排除。

`std::atomic` 的内存序从弱到强：

| 内存序 | 语义 | 典型用途 |
| --- | --- | --- |
| relaxed | 只保证本原子量自身原子性，无同步 | 计数器统计、引用计数增 |
| acquire | 本读操作之后的读写不得重排到它之前 | 配合 release 构成同步对 |
| release | 本写操作之前的读写不得重排到它之后 | 发布数据 |
| acq_rel | 读改写时兼有 acquire + release | fetch_add 等读改写操作 |
| seq_cst | 以上全部 + 全局单一顺序（默认） | 需要跨变量一致顺序时 |

`memory_order_consume` 标准里已声明"暂不建议使用"（实现都把它升级成 acquire），代码里别写它。release/acquire 配对是性价比最高的一档：

```cpp
// acquire_release.cpp —— 需要 -std=c++20
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<bool> ready{false};
int payload = 0;    // 普通变量，靠 release/acquire 获得可见性保证

void producer() {
    payload = 42;                                  // 普通 store
    ready.store(true, std::memory_order_release);  // 之前的写不许下沉
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}   // 之后的读不许上浮
    std::cout << "payload = " << payload << '\n';       // 保证看到 42
}

int main() {
    std::thread c(consumer);
    std::thread p(producer);
    p.join();
    c.join();
}
```

```bash
g++ -std=c++20 -Wall -Wextra acquire_release.cpp -o ar -pthread && ./ar
```

```text
# Linux g++ 12 下的输出
payload = 42
```

> **坑：** 原子不是万能钥匙——`std::atomic<int>` 只保护它自己一个变量，"先改 a 再改 b"这种复合操作在两个线程里交错照样逻辑错，复合不变量要用互斥锁或把多个量合并进一个原子。反过来，能用原子（尤其 relaxed）的地方别上锁，计数器这类场景原子便宜一个数量级。
{: .sec-pit}

C++20 给原子补了两块拼图。`wait`/`notify` 提供原子量的阻塞等待，比"自旋轮询"省 CPU，比"条件变量"少一个互斥量：

```cpp
// atomic_wait.cpp —— 需要 -std=c++20
#include <atomic>
#include <chrono>
#include <iostream>
#include <thread>

std::atomic<int> counter{0};

void waiter() {
    counter.wait(0);    // 阻塞直到 counter != 0（伪唤醒安全，标准已处理）
    std::cout << "看到 counter = " << counter.load() << '\n';
}

int main() {
    std::thread t(waiter);
    std::this_thread::sleep_for(std::chrono::milliseconds(50));
    counter.store(7);
    counter.notify_one();
    t.join();
}
```

```text
# Linux g++ 12 下的输出（需要 GCC 11+ 的 libstdc++）
看到 counter = 7
```

`std::atomic_ref<T>`（C++20）则给**普通变量**临时授予原子性，对象本体不用声明成 atomic：

```cpp
// atomic_ref_demo.cpp —— 需要 -std=c++20
#include <atomic>
#include <iostream>
#include <thread>
#include <vector>

int main() {
    long long counter = 0;                       // 普通变量
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i) {
        ts.emplace_back([&] {
            std::atomic_ref<long long> c(counter);   // 临时获得原子性
            for (int j = 0; j < 100000; ++j) c.fetch_add(1, std::memory_order_relaxed);
        });
    }
    for (auto& t : ts) t.join();
    std::cout << counter << '\n';
}
```

```text
# Linux g++ 12 下的输出
400000
```

用 atomic_ref 有一条铁律：对象被 atomic_ref 操作期间，绝不能有对它的普通并发读写——原子性与普通访问不能混。

## 19.4 技术解惑
{: .sec-ts}

### 19.4.1 混用分配通道会怎样
{: .sec-warn}

`malloc` 的内存 `delete`、`new` 的内存 `free`、`new[]` 配 `delete`、跨模块边界的 new/delete（两边链接的运行时不同）——全是 undefined behavior。glibc 下常见的症状是 `free(): invalid pointer` 或堆损坏断言，Windows 下是堆句柄崩溃，但"常见症状"不等于"必然症状"，优化后的实现完全可能什么都不发生然后随机爆炸。纪律：一条分配通道配到底，跨 DLL/so 边界传递内存时由"分配方负责释放"或干脆传智能指针（注意定义删除器时两边用同一份运行时）。

### 19.4.2 delete 一个不完整类型
{: .sec-pit}

前向声明的类型在指针处 delete，编译器不知道析构函数和元素个数，标准定为 UB。GCC/Clang 的 `-Wdelete-incomplete` 能抓到。`std::default_delete`（unique_ptr 的删除器）在 `static_assert(sizeof(T)>0)` 处会把这类错误拦在编译期——这也是"unique_ptr 比裸指针安全"的一个具体论据。

### 19.4.3 use_count 到不了零：排查循环引用
{: .sec-know}

ASan 报"泄漏的内存里有 shared_ptr 控制块"而 valgrind 显示"still reachable"，八成是循环引用。排查顺序：用调试器在进程退出前打印可疑对象的 `use_count`；检查双向关系是否两边都是 shared_ptr；把"从属/反向"一边改成 weak_ptr。设计期预防的法子：画所有权图时先定死"每一根箭头最多一个所有者"，反向箭头一律 weak_ptr 或裸指针。

### 19.4.4 常见坑清单
{: .sec-pit}

| 坑 | 症状 | 规避 |
| --- | --- | --- |
| new[] 配 delete | 堆损坏或只析构部分元素 | 配对纪律 + `make_unique<T[]>` |
| malloc 与 new 混用 | 分配器内部状态错乱 | 一条通道配到底 |
| delete 不完整类型 | UB | unique_ptr 或让类型定义可见 |
| shared_ptr 循环引用 | 永不析构 | 反向引用用 weak_ptr |
| `shared_ptr<T>(this)` | 双控制块双重释放 | 继承 `enable_shared_from_this` |
| expired 后再访问 | 竞态 | 永远 `lock()` 一步到位 |
| 同一 shared_ptr 实例跨线程写 | 数据竞争 UB | 每线程用各自的拷贝 |
| 容器活得比 pmr resource 久 | UB | 作用域套牢：resource 在外，容器在内 |
| VLA/alloca 用尽栈空间 | 无预警段错误 | 用 vector 或固定上限 |
| 超大对象放栈上 | 栈溢出 | 大于几 KB 就上堆 |
| 递归无深度上限 | 栈溢出崩溃 | 显式栈改写或深度保护 |
| 裸指针当返回值交出所有权 | 谁释放说不清 | 返回 unique_ptr |
| what 指针、控制块悬空引用 | 随机崩溃 | 生命周期问清楚再存 |

## 变式追问
{: .sec-think}

**问：unique_ptr 传参该传值还是传引用？**

看语义。按值传 `unique_ptr<T>` 表示"我要拿走所有权"（sink 参数），调用方必须 `std::move`，意图写在签名上；`unique_ptr<T>&` 只在"函数可能重新接管或替换内部指针"这种罕见场合用；只读使用就别传 unique_ptr，传 `T&` 或 `T*`——所有权是资源管理的概念，不是访问权限的概念，把两者捆在一起会让所有调用点都被迫 move。

**问：make_shared 一次分配是纯优势吗？**

不是。它省一次 malloc、缓存更友好，但对象和控制块同生共死：只要还有 weak_ptr 指着（哪怕强计数已归零），对象占的那部分内存也不能还——大对象 + 长命 weak_ptr 的组合会出现"析构了却占着内存"。这类场景用 `shared_ptr<T>(new T)` 分开分配，对象内存随强计数归零立即归还。另外 make_shared 不能指定自定义删除器（unique 场景不受影响）。

**问：既然 RAII 能自动管理，什么时候还需要裸 new？**

比想象中少得多：placement new 的场景（在自备内存上构造）、实现容器/分配器内部、和 C 库交互的过渡层、以及对象生命周期由外部系统管理的场合（比如驱动框架）。业务代码里裸 new 出现就该多问一句——多半该是 `make_unique`，剩下的多半该是容器。

**问：数据竞争的 UB 意味着什么？"加个 volatile 不就行了？"**

UB 意味着编译器有权假设竞争不存在：可能把读缓存在寄存器里无限循环不重读，可能重排访问，可能直接删掉"无意义"的写。volatile 只禁止编译器缓存和删除该变量的访问，不建立任何线程间顺序，也告诉不了硬件什么——它是 MMIO 寄存器的工具，不是线程同步的工具。多线程共享数据的三件套只有：atomic、mutex、以及"根本不共享"（thread_local 或消息传递）。
