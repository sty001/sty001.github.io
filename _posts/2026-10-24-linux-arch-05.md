## 上节回顾：NFS 存储服务
{: .sec-sum}

| 主题 | 要点 |
| --- | --- |
| NFS 概念 | a 实现数据的共享存储；b 降低公司磁盘购买成本 |
| NFS 工作原理 | a 部署好一台存储服务器，设置好存储目录；b 客户端利用网络挂载的方式挂载存储目录；c 将数据存储在客户端本地挂载点目录 == 存储到存储服务器中 |
| NFS 部署流程 | 服务端：第一步安装 `nfs-utils rpcbind`；第二步编写配置文件；第三步创建存储目录并修改属主权限；第四步启动服务并设置开机自动（`rpcbind` 然后 `nfs`）。客户端：第一步安装 nfs 服务软件；第二步 `mount -t nfs 172.16.1.31:/data 挂载点目录` |

> **注意：** RPC 类似于租房的中介。NFS 服务启动会有多个进程、多个端口（随机端口），客户端不方便直接连接服务端，所以需要 RPC 做端口注册与查询。说白了 RPC 就是端口黄页，先查号再拨号。
{: .sec-pit}

### NFS 服务挂载不上的排查方法
{: .sec-ts}

**服务端进行排查：**

1. 检查 nfs 进程信息是否注册

   ```bash
   rpcinfo -p localhost/172.16.1.31
   ```

   问题原因：服务启动顺序不对，没有启动 nfs 服务

2. 检查有没有可用存储目录

   ```bash
   showmount -e 172.16.1.31
   ```

   问题原因：配置文件编写有问题，重启 nfs 服务

3. 在服务端进行挂载测试，确认是否能够在存储目录中创建或删除数据

**客户端进行排查：**

1. 检查 nfs 进程信息是否注册

   ```bash
   rpcinfo -p localhost/172.16.1.31
   ```

   问题原因：服务启动顺序不对，没有启动 nfs 服务

2. 检查有没有可用存储目录

   ```bash
   showmount -e 172.16.1.31
   ```

   问题原因：配置文件编写有问题，重启 nfs 服务；另外还要排查网络问题：

   ```bash
   ping 172.16.1.31
   telnet 172.16.1.31 111
   ```

## 原理解析：inotify 内核机制与限制
{: .sec-know}

inotify 不是用户态程序，而是 Linux **内核子系统**（自 2.6.13 内核引入），`inotifywait` / `inotifywatch` 只是 inotify-tools 提供的命令行封装。它的工作机制分三步：

1. 用户态调用 `inotify_init()` 创建一个 inotify 实例，内核返回一个文件描述符。
2. 调用 `inotify_add_watch()` 把要监控的路径注册到实例上，内核为每个被监控的目录维护一个 watch，返回 watch descriptor。
3. 被监控目录发生事件时，内核把事件写进该实例的事件队列；用户态 `read()` 这个文件描述符，就能按发生顺序拿到事件流。

因为内核按"目录"维护 watch，递归监控（`-r`）会为目录树里**每一个子目录**都创建一个 watch，watch 数量受内核参数限制：

| 内核参数 | 含义 | 查看方式 |
| --- | --- | --- |
| `fs.inotify.max_user_watches` | 每个真实用户最多可创建的 watch 数 | `cat /proc/sys/fs/inotify/max_user_watches` |
| `fs.inotify.max_user_instances` | 每个用户最多可创建的 inotify 实例数 | `cat /proc/sys/fs/inotify/max_user_instances` |
| `fs.inotify.max_queued_events` | 单个实例事件队列长度，超出即丢弃事件 | `cat /proc/sys/fs/inotify/max_queued_events` |

> **注意：** 这里有个坑：监控几十万文件的大目录树时，很容易耗尽 `max_user_watches`，表现为"后来新建的文件不再触发同步"。解决办法是调大 `sysctl fs.inotify.max_user_watches`（如 1000000），或缩小监控范围、用白名单排除子目录。
{: .sec-pit}

> **注意：** `max_queued_events` 溢出是另一类静默故障：队列满了新事件直接丢弃，不报错、不告警，表现为"部分文件没同步过去"。大目录高写入场景把该值调到 16384 以上，并靠 sersync 的定期全量兜底。
{: .sec-pit}

> **注意：** 顺带区分 inotify 与 fanotify：inotify 面向"监控目录树、拿事件流"，是实时同步类工具的底座；fanotify 面向"拦截文件访问、做安全软件"，粒度到整个文件系统且需要特权。做实时同步认准 inotify 即可。
{: .sec-pit}

### inotify 常用事件表

| 事件 | 触发时机 |
| --- | --- |
| `create` | 目录中新建文件或子目录 |
| `delete` | 文件被删除 |
| `modify` | 文件内容被写入（写入过程中可能多次触发） |
| `attrib` | 文件属性变化（权限、属主、时间戳等） |
| `close_write` | 以写模式打开的文件被关闭，代表一次写入完成 |
| `close_nowrite` | 以只读模式打开的文件被关闭 |
| `moved_from` | 文件被移出监控目录 |
| `moved_to` | 文件被移入监控目录 |
| `open` / `access` | 文件被打开 / 被读取 |

> **注意：** 事件表里最值得盯的是 `close_write` 与 `modify` 的区别：`modify` 在写入过程中可能触发多次（大文件分多次写），每次都触发同步就是灾难；`close_write` 代表一次写入完成，是"该同步了"的正确信号。
{: .sec-pit}

### inotifywait 输出格式占位符

| 占位符 | 含义 |
| --- | --- |
| `%w` | 被监控的目录路径 |
| `%f` | 事件相关的文件名（事件发生在目录本身时为空） |
| `%e` | 事件列表，多个事件用逗号分隔 |
| `%T` | 按 `--timefmt` 格式化的当前时间 |

`inotifywatch` 与 `inotifywait` 的区别是：`inotifywait` 持续输出事件流，`inotifywatch` 只做统计，监控一段时间后输出一张"每个文件发生了哪些事件、各多少次"的汇总表，适合评估某目录的写入频率。

## 实时同步服务的原理与概念
{: .sec-know}

实现实时同步需要三件事配合：

1. 需要部署好 **rsync 守护进程服务**，实现数据传输
2. 需要部署好 **inotify 服务**，实现目录中数据变化的监控
3. 将 rsync 服务和 inotify 服务建立联系，将变化的数据进行实时备份传输

一句话概括三者的分工：

```text
监控目录数据变化  --- inotify
将数据进行传输    --- rsync
将监控和传输进行整合  --- sersync
```

### 事件驱动与轮询的对比

rsync 本身是"比对后传输"的工具，默认不会自动运行，把它变成实时同步有两条路：

| 方式 | 原理 | 实时性 | 代价 |
| --- | --- | --- | --- |
| cron + rsync 轮询 | 每分钟跑一次 rsync 增量比对 | 有轮询周期延迟 | 实现简单，但反复校验浪费资源，小文件多时 CPU 压力大 |
| inotify + rsync 事件驱动 | 文件一变化立即触发一次 rsync | 秒级 | 需要常驻守护进程，watch 数量受内核限制 |

> **注意：** sersync 本身不传输数据，它只做两件事：监听 inotify 事件、按配置拼出 rsync 命令并执行。真正的传输始终由 rsync 完成。
{: .sec-pit}

> **注意：** 事件风暴要提前防：编译一次内核、解压一个 tar 包，几秒内能产生成千上万条事件。手写的 `while read` 循环一条事件拉起一次 rsync，上一轮还没跑完下一轮又堆起来，CPU 和 IO 直接被打满。削峰两条路：一是靠 sersync / lsyncd 内置的事件合并，把几百毫秒内的零散事件合成一次全量比对；二是过滤事件类型，只盯 `close_write`、`delete`、`moved_to` 这些"一次写入完成"的信号，放过 `open`、`access`、`modify` 的中间态。
{: .sec-pit}

### 2）部署 inotify 监控服务

#### 第一个步骤：安装软件
{: .sec-prac}

```bash
yum install -y inotify-tools
```

#### 第二个步骤：熟悉命令的使用
{: .sec-prac}

| 命令 | 作用 |
| --- | --- |
| `/usr/bin/inotifywait` | 监控目录数据信息变化 |
| `/usr/bin/inotifywatch` | 对监控的变化信息进行统计 |

> **注意：** 两个命令记一句话：`inotifywait` 是盯着的（等事件），`inotifywatch` 是统计的（跑一段出报表）。实时同步只用前者。
{: .sec-pit}

假设 `/data/` 下有 `user01.txt`、`user02.txt`、`user03.txt`，其中 `user02.txt` 希望能被排除（配合 rsync `--exclude`）。

#### inotifywait 命令参数
{: .sec-expl}

```bash
inotifywait [参数]  监控的目录
```

| 参数 | 含义 |
| --- | --- |
| `-m|--monitor` | 实现一直监控目录的数据变化 |
| `-r|--recursive` | 进行递归监控 |
| `-q|--quiet` | 尽量减少信息的输出 |
| `--format <fmt>` | 指定输出信息的格式 |
| `--timefmt` | 指定输出的时间信息格式 |
| `-e|--event` | 指定监控的事件信息 |

#### 创建文件时的监控输出

```text
/data/ CREATE user13                    --- 一个文件被创建
/data/ OPEN user13                      --- 打开创建的文件
/data/ ATTRIB user13                    --- 修改文件的属性信息
/data/ CLOSE_WRITE,CLOSE user13         --- 保存关闭一个文件
```

#### 删除文件时的监控输出

```text
/data/ DELETE user13
```

#### 修改文件时的监控输出

```text
/data/ CREATE user10
/data/ OPEN user10
/data/ MODIFY user10
/data/ CLOSE_WRITE,CLOSE user10
```

#### sed 命令修改文件的原理
{: .sec-know}

用 `sed` 修改文件时，实际发生的是"临时文件 + 重命名"，所以监控输出里会带出一串事件：

```text
/data/ OPEN user10                      --- 打开文件
/data/ CREATE sedpSAFR7                 --- 创建出一个临时文件（内存）
/data/ OPEN sedpSAFR7                   --- 临时文件进行打开
/data/ ACCESS user10                    --- 读取源文件内容
/data/ MODIFY sedpSAFR7                 --- 修改临时文件
/data/ ATTRIB sedpSAFR7                 --- 临时文件属性变化
/data/ CLOSE_NOWRITE,CLOSE user10       --- 不编辑直接关闭源文件
/data/ CLOSE_WRITE,CLOSE sedpSAFR7      --- 写入关闭临时文件
/data/ MOVED_FROM sedpSAFR7             --- 将临时文件移除
/data/ MOVED_TO user10                  --- 移入一个新的 user10 源文件
```

> **注意：** 正因为 sed/vim 走的是"临时文件 + MOVED_TO"，实时同步时通常监控 `close_write`、`moved_to`、`create`、`delete` 这几类事件，而不是只监控 `modify`。这几个事件到底什么含义，对着上面 sed 的事件序列敲一遍就明白。
{: .sec-pit}

#### inotify 监控命令格式

```bash
inotifywait -mrq --timefmt "%F" --format "%T %w %f 事件信息:%e" /data -e CREATE
```

常用事件：`create` 创建、`delete` 删除、`moved_to` 移入、`close_write` 修改。

#### 企业应用：防止系统重要文件被破坏

需要用到 inotify 进行实时一直监控：

```text
/etc/passwd
/var/spool/cron/root
```

**排除规则段：**

```xml
 6     <filter start="false">
```

**监控事件段：**

```xml
12     <inotify>
13         <delete start="true"/>
14         <createFolder start="true"/>
15         <createFile start="false"/>
16         <closeWrite start="true"/>
17         <moveFrom start="true"/>
18         <moveTo start="true"/>
19         <attrib start="false"/>
20         <modify start="false"/>
21     </inotify>
```

说明：定义 inotify 程序需要监控的事件。

**同步目标段：**

```xml
24         <localpath watch="/opt/tongbu">
25             <remote ip="127.0.0.1" name="tongbu1"/>
28         </localpath>
29         <rsync>
30             <commonParams params="-artuz"/>
31             <auth start="false" users="root" passwordfile="/etc/rsync.pas"/>
32             <userDefinedPort start="false" port="874"/>
```

说明：`<localpath>` 下可以写多个 `<remote>` 实现一对多同步；原示例中被注释停用的两条备用目标为 `<remote ip="192.168.8.39" name="tongbu"/>` 与 `<remote ip="192.168.8.40" name="tongbu"/>`，需要时取消停用即可。

| 配置项 | 含义 |
| --- | --- |
| `<localpath watch="...">` | 要监控的本地目录 |
| `<remote ip="..." name="..."/>` | 远程 rsync 主机 IP 与模块名 |
| `<commonParams params="-artuz"/>` | rsync 传输时使用的参数 |
| `<auth start=... users=... passwordfile=.../>` | 是否启用 rsync 认证，以及认证用户与密码文件 |
| `<userDefinedPort start=... port="874"/>` | 是否使用自定义 rsync 端口 |

#### confxml.xml 完整结构与逐段说明
{: .sec-expl}

sersync 的配置文件是 XML，根元素为 `<head>`，各段功能如下：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<head version="2.5">
    <host hostip="localhost" port="8008"></host>
    <debug start="false"/>
    <fileSystem xfs="false"/>
    <filter start="false">
        <exclude expression="(.*)\.svn"></exclude>
        <exclude expression="(.*)\.gz"></exclude>
        <exclude expression="^info/*"></exclude>
        <exclude expression="^static/*"></exclude>
    </filter>
    <inotify>
        <delete start="true"/>
        <createFolder start="true"/>
        <createFile start="false"/>
        <closeWrite start="true"/>
        <moveFrom start="true"/>
        <moveTo start="true"/>
        <attrib start="false"/>
        <modify start="false"/>
    </inotify>
    <sersync>
        <localpath watch="/opt/tongbu">
            <remote ip="127.0.0.1" name="tongbu1"/>
        </localpath>
        <rsync>
            <commonParams params="-artuz"/>
            <auth start="false" users="root" passwordfile="/etc/rsync.pas"/>
            <userDefinedPort start="false" port="874"/>
            <timeout start="false" time="100"/>
            <ssh start="false"/>
        </rsync>
    </sersync>
    <failLog path="/usr/local/sersync/logs/rsync_fail_log.sh" timeToExecute="10min"/>
    <crontab start="false" schedule="600">
        <crontabfilter start="false">
            <exclude expression="(.*)\.svn"></exclude>
        </crontabfilter>
    </crontab>
</head>
```

| 配置段 | 作用 |
| --- | --- |
| `<host hostip port>` | sersync 自身管理的 IP 与端口（用于命令通信，保持默认即可） |
| `<debug start>` | 是否开启调试日志，排错时改为 `true` |
| `<fileSystem xfs>` | 监控目录所在文件系统是否为 XFS |
| `<filter start>` | 排除规则总开关；`start="true"` 时下面的 `<exclude>` 才生效 |
| `<exclude expression>` | 正则表达式，匹配的路径不参与同步；注意这里写的是正则，不是 rsync 的 glob |
| `<inotify>` | 各事件开关：`delete` 删除、`createFolder` 建目录、`createFile` 建文件、`closeWrite` 写入关闭、`moveFrom` / `moveTo` 移动、`attrib` 属性、`modify` 内容修改 |
| `<localpath watch>` | 被监控的本地目录，一对 `<localpath>` 对应一个同步任务 |
| `<remote ip name>` | 同步目标：rsync 服务端地址 + 模块名；写多个 remote 即一对多同步 |
| `<commonParams params="-artuz">` | rsync 参数：`-a` 归档模式（递归并保留属性）、`-r` 递归、`-t` 保留修改时间、`-u` 目标更新才跳过、`-z` 传输压缩 |
| `<auth start users passwordfile>` | rsync daemon 认证：虚拟用户与密码文件路径 |
| `<userDefinedPort start port>` | rsync daemon 使用非默认端口（873）时在此指定 |
| `<timeout start time>` | 单次 rsync 命令超时时间 |
| `<ssh start>` | 是否走 ssh 通道传输（不用 rsync daemon 时） |
| `<failLog path timeToExecute>` | rsync 失败补偿日志：失败的事件记录成脚本，按设定周期重跑 |
| `<crontab start schedule>` | 定期全量 rsync 补偿，单位秒；`start="true"` 后按 `schedule` 周期整体推送，弥补 inotify 漏掉的事件 |

> **注意：** `-artuz` 里的 `-u`（update）会让 rsync 跳过目标端更新的文件，做实时同步时通常保留；若希望"以源为准强制覆盖"再去掉它。`<auth>` 里的密码文件权限必须是 600，否则 rsync 会拒绝读取。
{: .sec-pit}

> **注意：** `<failLog>` 是 sersync 最值钱的设计：目标端宕机期间漏掉的变更会被记进 `rsync_fail_log.sh`，按 `timeToExecute` 周期重跑，服务恢复后自动补齐。手写脚本要自己实现这套补偿，这也是不推荐生产手写的主要原因。
{: .sec-pit}

#### 第四个里程：启动 sersync 服务程序

```bash
[root@nfs01 bin]# export PATH="$PATH:/usr/local/sersync/bin"
[root@nfs01 bin]# echo $PATH
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/root/bin:/usr/local/sersync/bin
```

启动参数：

| 参数 | 含义 |
| --- | --- |
| `-d` | 启用守护进程模式 |
| `-r` | 在监控前，将监控目录与远程主机用 rsync 命令推送一遍，进行同步测试 |
| `-o` | 指定配置文件，默认使用 `confxml.xml` 文件，如 `-o /usr/local/sersync/conf/confxml.xml`、`-o /usr/local/sersync/conf/confxml02.xml` |

```bash
# 启动实时同步服务
sersync -dro  /usr/local/sersync/conf/confxml.xml

# 停止实时同步服务
yum install -y psmisc
killall sersync

# 开机自动启动
/etc/rc.local <-- sersync -dro  /usr/local/sersync/conf/confxml.xml
```

`-r` 的全量预推送值得单独说：目标端是新目录或落后较多时，先靠 `-r` 把存量一次性对齐，之后 inotify 只处理增量，避免"服务一启动就积压几万个事件"。

> **注意：** 一个 sersync 进程读一份配置；要同时同步多个目录，就复制 confxml 改 `<localpath>`，用 `-o` 各启动一个进程，`ps -ef` 里按配置文件名区分任务。
{: .sec-pit}

### 辨析：sersync 与 inotify+rsync 手写脚本

- **手写脚本**（while read + rsync）：逻辑全透明，想加判断就加判断，适合学习原理和极小规模；但没有事件合并、没有失败重传，脚本一崩同步就停
- **sersync**：C++ 写的常驻进程，自带失败补偿（failLog）、定期全量兜底（crontab 段）、多目标推送；缺点是项目多年未维护，新系统上出问题只能自己啃
- **lsyncd**：Lua 配置、社区活跃、原生支持 systemd，是新部署的优先选择
- **选择建议**：学习阶段手写一遍 inotify + rsync，理解事件驱动的工作方式；生产上用 sersync / lsyncd，把合并与补偿交给工具

#### 用 systemd 托管 sersync（替代 rc.local）

sersync 没有自带服务单元，生产环境建议自己写一个 unit，享受开机自启、崩溃重启与日志托管：

```ini
[Unit]
Description=sersync realtime sync service
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/sersync/bin/sersync -d -o /usr/local/sersync/conf/confxml.xml
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now sersync
systemctl status sersync
```

## 数据库实时同步注意事项
{: .sec-warn}

用 rsync + inotify 同步普通文件没问题，但**数据库数据目录不能直接这样同步**：

1. 数据库有内存缓冲：写入的数据可能还在 buffer pool / redo log 里，没落盘，直接复制文件得到的是不一致状态。
2. 数据库是多文件协作：数据文件、日志文件、索引文件之间没有原子快照，逐文件拷贝等于把不同时刻的数据拼在一起。
3. 运行中拷贝会把半写状态复制过去，目标端一打开就可能崩溃或静默损坏。

正确的做法：

| 场景 | 做法 |
| --- | --- |
| MySQL 逻辑同步 | `mysqldump --single-transaction` 导出后同步 dump 文件，目标端导入 |
| MySQL 物理备份 | 用 xtrabackup 等热备工具生成一致快照，再同步备份集 |
| 实时性要求高 | 用数据库自带的主从复制，而不是文件级同步 |
| 允许停服的小库 | 停服务 → 整目录同步 → 启动服务（冷备窗口） |

> **注意：** 若确实需要同步数据库相关文件，先执行 `FLUSH TABLES WITH READ LOCK` 或停止数据库服务，保证文件处于一致静止状态；否则宁可不同步，也不要同步一份会损坏的数据。
{: .sec-pit}

> **注意：** 要分清两个概念：主从复制是数据库内核级的日志重放（binlog 在从库按事务顺序重新执行），保证事务一致性；rsync + inotify 是文件级的字节搬运，不懂数据结构、没有事务概念。所以"数据库要实时同步"的答案从来不是 rsync 数据目录，而是搭主从 —— 主从也算实时，但那是应用层的实时，不是文件系统的实时。本篇的实时同步服务管的是图片、附件、日志这类普通文件。
{: .sec-pit}

## 多台服务器同步架构
{: .sec-expl}

1. **一对多**：sersync 的 `<localpath>` 下配置多个 `<remote>`，一台源主机同时推送到多台备份机，注意目标 rsync daemon 的模块与认证都要提前准备好。
2. **单向流动原则**：同步关系必须是有向的。两台主机互相同步（A → B 且 B → A）会形成回环，同一份文件被两边反复覆盖，生产环境严禁。
3. **级联架构**：机房多、链路长时用树形结构：中心机房先收齐，再向各分支转发，避免每台源机都跨专线推一遍。
4. **补偿机制**：事件驱动有漏事件风险（watch 耗尽、队列溢出），sersync 的 `<crontab>` 定期全量推送就是兜底方案，重要数据建议开启。
5. **带宽评估**：实时同步对大文件反复写入很敏感，`-z` 压缩与 `--bwlimit` 限速按需使用，避免同步流量挤占业务带宽。

> **注意：** 带宽评估要按"峰值写入速率"算而不是平均值：用户上传图片的高峰一小时可能写入几个 G，同步链路带宽要扛得住峰值，否则备份端长期落后于源端，"实时"名存实亡。上线前观察一天的写入量曲线再定带宽。
{: .sec-pit}

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| sersync 启动失败，提示打不开配置文件 | 配置文件路径写错或文件不存在 | `ls -l /usr/local/sersync/conf/` | 用 `-o` 指定绝对路径 |
| 新建文件长时间不触发同步 | watch 耗尽（`max_user_watches` 太小）或事件队列溢出 | `cat /proc/sys/fs/inotify/max_user_watches`；`dmesg \| tail` | 调大 `fs.inotify.max_user_watches`；缩小监控范围 |
| rsync 报认证失败 / password file 错误 | 密码文件不存在或权限过宽 | `ls -l /etc/rsync.pas` | `chmod 600 /etc/rsync.pas`，确认用户名与服务端一致 |
| 备份端文件删不掉（删除没同步过去） | 只开了 `closeWrite`，没开 `delete` / `moveFrom` | 检查 `<inotify>` 段 | `delete`、`moveFrom`、`moveTo` 设为 `true` |
| 大文件传输中途失败，备份端是半截文件 | rsync 超时或被中断 | sersync 日志 `/usr/local/sersync/logs/` | 调大 `<timeout>`；靠 `<failLog>` 补偿重跑 |
| sersync 进程莫名消失 | 未托管，被杀或重启后没起来 | `ps -ef \| grep sersync` | 用 systemd unit 托管并设 `Restart=on-failure` |
| 排除规则不生效 | `<filter start="false">` 总开关没打开，或正则写错 | 检查配置 | `<filter start="true">` 再验证正则 |

> **注意：** 生产上栽过最多的是单向原则：图省事把 A、B 配成互相同步，某天 A 上的旧文件被误恢复，把 B 上的新文件覆盖回去，谁也说不清哪份是最新的。同步关系一旦双向化，数据一致性基本无法审计，出问题只能两份都信不过。
{: .sec-pit}

## 实时同步服务概念总结
{: .sec-know}

1. **实现实时同步的原理**
   - 监控目录数据变化 —— inotify
   - 将数据进行传输 —— rsync
   - 将监控和传输进行整合 —— sersync
2. **实现实时同步的部署方法**
   1. 部署 rsync 守护进程
   2. 部署 inotify 软件
   3. 部署 sersync 软件

三者关系压缩成一句：inotify 是眼睛，rsync 是手，sersync 是大脑 —— 眼睛看到变化，大脑决定何时传、传给谁，手执行传输。

## 小结
{: .sec-sum}

1. 实时同步 = inotify 监控 + rsync 传输 + sersync 整合，三者缺一不可；sersync 本身不传数据，只是把前两者粘合。
2. `inotifywait` 常用组合是 `-mrq --timefmt --format -e`，事件重点看 `create`、`delete`、`moved_to`、`close_write`。
3. 理解 sed/vim 的"临时文件 + MOVED_TO"机制，才能解释为什么只监控 `modify` 会漏掉文件变更。
4. sersync 配置三个关键段：`<filter>` 排除规则、`<inotify>` 监控事件、`<localpath>` + `<rsync>` 同步目标与认证。
5. 启动用 `sersync -dro 配置文件`，`-r` 会先全量推送一遍做同步测试；停止用 `killall sersync`（需装 `psmisc`）。
6. 除了数据备份，inotify 也常用于监控 `/etc/passwd`、`/var/spool/cron/root` 等重要文件是否被篡改。
7. inotify 是内核子系统，watch 数量受 `max_user_watches` 限制，大目录递归监控前先评估 watch 消耗。
8. 数据库数据目录不能直接文件级同步，要用 dump、热备工具或主从复制；多台同步保持单向，避免回环覆盖。

## 自测题
{: .sec-prac}

1. sersync 在实时同步架构里承担什么角色？它自己传输数据吗？
2. 为什么只监控 `modify` 事件会漏掉用 sed 修改的文件？
3. inotify 递归监控一个大目录树后，部分新文件不再触发同步，最可能的原因是什么？如何确认？
4. 为什么不能把运行中的 MySQL 数据目录直接 rsync 到备份机？
5. sersync 的 `<crontab>` 配置段起什么作用？

> **答案：** 1. sersync 是"粘合层"：监听 inotify 事件、按配置生成 rsync 命令并执行；真正传输数据的是 rsync，sersync 不自己传数据。2. sed 的机制是"写临时文件 + 重命名覆盖源文件"，源文件本身没有 `modify` 事件，只有 `moved_to`；只监控 `modify` 就漏掉了这类变更，必须同时监控 `close_write`、`create`、`moved_to`、`delete`。3. 最可能耗尽了 `fs.inotify.max_user_watches`（每个子目录都占一个 watch），可 `cat /proc/sys/fs/inotify/max_user_watches` 并用 `dmesg` 查看；解决是调大该值或缩小监控范围。4. 数据库有内存缓冲未落盘，且数据文件与日志文件之间没有原子快照，逐文件复制会得到不一致状态，目标端可能损坏；应使用 mysqldump、xtrabackup 或主从复制。5. `<crontab>` 让 sersync 按设定周期做一次全量 rsync，作为事件驱动的兜底补偿，弥补漏掉的事件。
