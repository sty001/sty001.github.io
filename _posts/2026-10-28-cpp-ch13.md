## 13.1 命名空间介绍
{: .sec-expl}

### 13.1.1 C 时代怎么管名字：前缀约定
{: .sec-know}

C 语言没有命名空间，所有全局符号平铺在同一个作用域里。库作者只能靠前缀抢地盘：OpenGL 的 `gl`、SDL 的 `SDL_`、POSIX 的 `pthread_`，函数、类型、枚举项全部带前缀。前缀越长越安全，名字也越难看——`glfwSetWindowSize` 这种八词连写就是代价。

这套约定有两个硬伤。第一，它只是约定，编译器不认识：删掉前缀程序照样能编，撞上别的库时不会有人提前提醒你。第二，宏完全不受作用域控制，两个头文件各自 `#define True` 这种事故在真实项目里一抓一把。最要命的是扩展性：库要出 v2、要加子模块，前缀只能越拼越长，没有"分区"的概念。

```cpp
// prefix.cpp —— 模拟 C 时代的前缀约定
#include <iostream>

namespace legacy {
    // 假装这是一个 C 结构体，真实 C 代码里它叫 legacy_string
    struct String { const char* data; int length; };
}

// C 里只能这样起名：前缀把"库身份"写死在每个标识符里
int legacy_string_length(const legacy::String& s) { return s.length; }

int main() {
    legacy::String s{"hello", 5};
    std::cout << legacy_string_length(s) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra prefix.cpp -o prefix && ./prefix
```

```text
5
```

### 13.1.2 命名空间解决了什么
{: .sec-know}

命名空间是一个**可命名的名字作用域**：把一组名字圈起来，外部要用就必须点名（`lib::String`）或者显式引入。设计目标有三个：

- **消除冲突**：两个库各叫各的 `Address`，互不干扰；
- **表达模块边界**：`audio::codec::Format` 自带"这是哪个模块的东西"的信息，读代码的人不需要查文档；
- **支持版本化**：配合 `inline namespace`（13.2.4），同一份接口能并存 v1/v2，编译期就选好。

命名空间本身不产生任何运行期开销——它纯粹是编译期的名字分区，`::` 在生成的代码里不存在。

> **注意：** 命名空间只划分"名字"的归属，不划分可见性。`lib::secret` 只要有声明，谁都能用；想做访问控制得靠类作用域和访问限定符。
{: .sec-note}

### 辨析：命名空间、类作用域与 static 全局
{: .sec-iv}

三者都能"缩小名字的暴露面"，但机制完全不同。命名空间是开放的、只管名字归属；类作用域是封闭的、带访问控制；`static` 全局（或匿名命名空间）改变的是**链接性**——这个符号只在当前翻译单元可见，链接器拿不到它。什么时候用哪个：按模块划分名字用命名空间；需要封装和保护成员用类；只想让"内部函数"不出本 .cpp 文件，用匿名命名空间（13.2.5），C++ 里这比 `static` 全局更被推荐。

## 13.2 定义命名空间
{: .sec-know}

### 13.2.1 基本定义与嵌套
{: .sec-know}

```cpp
// define.cpp —— 需要 -std=c++17
#include <iostream>

namespace audio {
    constexpr int kMaxChannels = 8;              // 命名空间级常量

    namespace codec {                            // 传统嵌套写法
        struct Format { int sample_rate; int bits; };
    }
}

namespace audio::dsp {                           // C++17 起的嵌套简化写法
    int downmix(int l, int r) { return (l + r) / 2; }
}

int main() {
    audio::codec::Format f{44100, 16};
    std::cout << audio::dsp::downmix(10, 20) << ' '
              << f.sample_rate << ' ' << audio::kMaxChannels << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra define.cpp -o define && ./define
```

```text
15 44100 8
```

`namespace audio::dsp {}` 是 C++17 的语法糖，等价于三层花括号套写。分层设计有个实用判断：嵌套到两三层就该停了——再深说明模块边界没想清楚，使用方每写一个类型都要背一遍完整路径。

### 13.2.2 开放性与分段定义
{: .sec-know}

命名空间是**开放**的：可以在多个文件、多个位置反复"重新打开"补充内容。这一点和类完全相反——类定义一次定死，不允许重开补成员。

```cpp
// reopen.cpp
#include <iostream>

namespace util {
    int version() { return 1; }        // 第一段定义
}

namespace util {                       // 重新打开，补充新内容
    int describe() { return version() * 10; }   // 能看到第一段的名字
}

int main() { std::cout << util::describe() << '\n'; }
```

```bash
g++ -std=c++20 -Wall -Wextra reopen.cpp -o reopen && ./reopen
```

```text
10
```

开放性不是缺陷而是设计：头文件里放声明、源文件里放定义，同一个命名空间被拆到多个文件里，这是标准库和所有大型库的标准做法。标准库把 `std::vector` 声明在 `<vector>`、`std::string` 声明在 `<string>`，靠的就是"同一个 `std`，分段声明"。

> **坑：** 类不能重开，命名空间可以。想在运行中给已有类"补成员"的人（多半被 Python 惯坏了）请改用继承或组合。
{: .sec-pit}

### 13.2.3 命名空间别名
{: .sec-know}

有些名字确实长，比如 `std::filesystem`。别名让你起个短名，而且**不引入新名字进作用域**，比 `using namespace` 安全：

```cpp
// alias.cpp —— 需要 -std=c++17
#include <filesystem>
#include <iostream>

namespace fs = std::filesystem;        // 别名：一劳永逸，但没污染任何名字

int main() {
    fs::path p{"logs/app.log"};
    std::cout << p.filename() << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra alias.cpp -o alias && ./alias
```

```text
app.log
```

别名特别适合两件事：给嵌套很深的命名空间开短门（`namespace detail = lib::widget::detail;`），以及给模板库的长命名空间起绰号。注意别名不能重定义成别的目标，一个作用域里一个别名只有一个含义。

### 13.2.4 inline namespace：版本化与 ABI
{: .sec-ext}

`inline namespace`（C++11）多了一个关键词 `inline`，语义变化很关键：它的成员可以**不经限定**地在外层命名空间里直接使用——像是自动做了一次"透明的 using 指令"。这正好用来做版本化：

```cpp
// inline_ns.cpp —— 需要 -std=c++11
#include <iostream>

namespace mylib {
    inline namespace v2 {                    // 当前默认版本
        struct Point { int x, y; };
    }
    namespace v1 {                           // 旧版本，仍然可用
        struct Point { int x; };
    }
}

int main() {
    mylib::Point p{1, 2};        // 不写版本号，默认拿到 v2
    mylib::v1::Point old{3};     // 显式点名，仍能拿旧版
    std::cout << p.x << ' ' << p.y << '\n' << old.x << '\n';
}
```

```bash
g++ -std=c++11 -Wall -Wextra inline_ns.cpp -o inline_ns && ./inline_ns
```

```text
1 2
3
```

为什么用它管 ABI？因为符号修饰名里包含命名空间：`v2::Point` 和 `v1::Point` 是两个不同的符号，二进制层面互不干扰。库出 v2 时把 `inline` 移到 v2 上，旧代码显式点名 `v1` 照样能链接旧实现；用户新编译的代码不写版本号自动用 v2。符号名里带着版本号，这就是"版本化 ABI"的字面意思。标准库自己也在用这招：C++14 的 chrono 字面量放在 `std::literals::chrono_literals` 里，`literals` 和 `chrono_literals` 两层都是 inline namespace，所以一句 `using namespace std::literals;` 就能把 `100ms`、`"abc"s` 这些字面量全部引进来。

### 13.2.5 匿名命名空间：内部链接
{: .sec-ts}

匿名的命名空间没有名字，它里面的名字具有**内部链接**：只在当前翻译单元可见，链接器看不见。这是 C++ 里替代 `static` 全局函数/变量的推荐写法：

```cpp
// anon.cpp —— 匿名命名空间
#include <iostream>

namespace {
    int counter = 0;                    // 内部链接：其他 .cpp 看不见
    void note() { ++counter; }
}

int main() {
    note();
    note();
    std::cout << counter << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra anon.cpp -o anon && ./anon && g++ -c anon.cpp && nm anon.o | grep note
```

```text
2
0000000000000000 T _ZN12_GLOBAL__N_14noteEv
```

`nm` 输出里的 `_GLOBAL__N_1` 是 GCC 给匿名命名空间的内部记号，说明这个 `note` 被包在了编译器私有的分区里——其他目标文件即使声明了同名函数也链接不到它。

> **坑：** 头文件里不要写匿名命名空间。每个包含这个头文件的 .cpp 都会得到一份**自己的副本**：`counter` 不再是共享的一个变量，而是每份源文件各一个；如果这些名字又被头文件里的 inline 函数引用，同一函数在不同 TU 里行为不一致，直接违反 ODR。匿名命名空间只放在 .cpp 文件里。
{: .sec-pit}

### 13.2.6 子命名空间惯例：detail 与 v1
{: .sec-best}

两个广泛流行的子命名空间命名约定：

- **`detail`**（或 `impl`、`internal`）：放库的实现细节，不承诺接口稳定性。它不是语言级的私有——外部照样能用——但所有严肃的库（包括标准库实现自己的 `__detail`）都靠它传达"用进去后果自负"。
- **`v1`、`v2`**：配合 `inline namespace` 做版本管理（见 13.2.4），或者放不同代际的兼容接口。

给项目立规矩时这两条值得写进贡献指南：公共接口直接放命名空间顶层，内部实现一律进 `detail`，谁把 `detail` 里的东西写进公共头文件谁负责收拾。

## 13.3 使用命名空间
{: .sec-know}

### 13.3.1 三种方式与各自的代价
{: .sec-know}

用命名空间里的名字有三条路，代价差别很大：

| 方式 | 写法 | 影响范围 | 代价与风险 |
| --- | --- | --- | --- |
| 全限定 | `net::Address` | 零，点名谁是谁 | 写起来长 |
| using 声明 | `using net::Address;` | 只引入这一个名字 | 与同名局部名冲突会报错，风险可控 |
| using 指令 | `using namespace net;` | 整包引入 | 冲突可能被静默吞掉，问题延迟到调用点才爆 |

```cpp
// use_three.cpp
#include <iostream>
#include <string>

namespace net {
    struct Address { std::string host; int port; };
}

int main() {
    // 方式一：全限定。最啰嗦，最清晰
    net::Address a1{"example.com", 443};

    // 方式二：using 声明。一次引入一个名字，来源可查
    using net::Address;
    Address a2{"localhost", 8080};

    // 方式三：using 指令。整包引入，冲突风险最大
    using namespace net;
    Address a3{"10.0.0.1", 22};

    std::cout << a1.host << ' ' << a2.port << ' ' << a3.host << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra use_three.cpp -o use_three && ./use_three
```

```text
example.com 8080 10.0.0.1
```

三条路的本质区别是"出错时谁能发现"。全限定名永远不会错；using 声明在引入那一刻就可能撞名报错，问题定位明确；using 指令把名字混进当前作用域，冲突往往不报错，而是悄悄改变重载决议——直到某天某个调用突然走了另一个函数，排查的人对着几十个头文件找 `using`。

### 13.3.2 `using namespace std;` 错在哪
{: .sec-pit}

教科书开头那句 `using namespace std;` 是教学便利，不是工程实践。它的危害按严重程度排：

- **写在头文件里是最严重的**。每个包含这个头文件的 .cpp 都被迫展开整个 std，而且**无法拒绝**——你不 `using`，头文件替你 `using` 了。这正是"接口污染"的典型：一个头文件把风险强加给所有下游。
- **写在全局作用域几乎同罪**。std 里有几千个名字，其中 `swap`、`size`、`count`、`begin`、`data` 这些和你自己的工具函数重名概率极高。更阴险的是这些名字不直接冲突时会参与重载决议：你调用 `swap(a, b)`，选中你自己的版本还是 std 的版本，取决于参数类型和 ADL（13.4.4）——代码读起来完全看不出调了谁。
- **标准库升级会引入新冲突**。C++17 往 std 里加了 `std::size`、`std::data`、`std::sample`，C++20 加了 `std::format`。你今天全局展开 std 没出事，升个编译器就可能满屏二义性错误，而且错误不在你改过的任何一行。

局部作用域（函数体内写一句 `using namespace std;`）相对可接受：影响被限制在这个函数里，函数结束自动失效。脚本式的小工具、代码比赛里这么写没人管；产品代码里连局部都建议少用，因为复制粘贴的人会把这段连同函数一起搬走。

> **坑：** 头文件里出现 `using namespace` 几乎一定是错的。唯一勉强说得过去的场景是给自己的兼容层头文件兜底，而且必须明确注释原因。评审时见到直接打回。
{: .sec-pit}

### 13.3.3 全局命名空间与 :: 前缀
{: .sec-know}

没写进任何命名空间的名字都在**全局命名空间**里。它有自己的显式写法——`::` 开头的限定名。最常见的用途：内层有同名变量时，强制取全局那份。

```cpp
// scope_cpp.cpp
#include <iostream>

int value = 10;               // 全局命名空间

int main() {
    double value = 3.14;      // 局部，遮蔽了全局同名
    std::cout << value << ' ' << ::value << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra scope_cpp.cpp -o scope_cpp && ./scope_cpp
```

```text
3.14 10
```

`::value` 的另一类高频用法是对抗宏和遗留代码：宏不受作用域限制，全局函数可能被同名的成员或局部名遮住，`::func()` 一锤定音。写库代码的人还常用 `::operator new`、`::std::move` 这种写法——前者确保取的是全局的 operator new 而不是类里自定义的版本，后者防的是有人在你的命名空间里也定义了一个 `std::move` 的山寨版。

### 13.3.4 头文件里的 using 与接口污染
{: .sec-ts}

头文件是接口，.cpp 是实现——这条分界线在 using 上的含义：.cpp 里的 using 只影响自己，头文件里的 using 会**跟着 #include 扩散**。所以规则可以定得很死：

- 头文件顶层不写 `using namespace`；
- `using` 声明也尽量不写在头文件顶层；确实要简化接口（比如库想暴露 `lib::string`），在**自己的命名空间内**写 `using std::string;`，影响被圈在命名空间边界里；
- 函数内、.cpp 内随便用，自己承担自己那部分风险。

已经被污染的存量头文件怎么办？先做影响评估再收敛：全局搜 `using namespace`，统计哪些在头文件里，逐个下沉到 .cpp。下沉后通常会暴露出一批"原本靠误打误撞才编过"的调用点，这批地方才是真正该修的。

### 13.3.5 using enum：枚举项批量引入
{: .sec-ext}

`enum class` 的枚举项必须写 `Color::red`，安全但啰嗦。C++20 的 `using enum` 可以把一个枚举的全部枚举项引入当前作用域，常见位置是 switch 里：

```cpp
// using_enum.cpp —— 需要 -std=c++20
#include <iostream>

enum class Color { red, green, blue };

void print(Color c) {
    switch (c) {
        using enum Color;   // 把 Color 的枚举项引入 switch 作用域
        case red:   std::cout << "red\n";   break;
        case green: std::cout << "green\n"; break;
        case blue:  std::cout << "blue\n";  break;
    }
}

int main() { print(Color::green); }
```

```bash
g++ -std=c++20 -Wall -Wextra using_enum.cpp -o using_enum && ./using_enum
```

```text
green
```

它比 `using namespace` 安全得多：只引入一个枚举的枚举项，名字集封闭、来源明确。`enum class` 的强作用域保证了这些枚举项不会泄漏到别处。唯一要留意的是枚举项撞名——两个枚举都有 `none` 时，同时引入会报错，这点和普通 using 声明一样。

## 13.4 作用域
{: .sec-expl}

### 13.4.1 作用域的几种面孔
{: .sec-know}

教材把作用域分成五类，实际编码里你天天在它们之间切换：

| 作用域 | 从哪里开始 | 典型例子 | 容易踩的点 |
| --- | --- | --- | --- |
| 块作用域 | `{` 到 `}` | 函数体、if/for 里的局部变量 | 内层变量遮蔽外层同名变量 |
| 函数原型作用域 | 参数声明的括号内 | 声明里的参数名 | 原型里的参数名没有实际作用，可与定义处不同 |
| 命名空间作用域 | namespace 花括号内 | 全局变量、自由函数 | 全局那份最容易和别的库撞车 |
| 类作用域 | 类体内 | 成员变量、成员函数 | 成员函数体内先查类，再查外层 |
| 全局命名空间作用域 | 不在任何 namespace 里 | `main`、C 风格全局函数 | 它其实就是"根"命名空间 |

标准里还有几个更冷门的：goto 标签的作用域、`enum class` 的枚举作用域、模板参数作用域。日常记住上面五张面孔加"全局是命名空间的根"就够用。

### 13.4.2 名字解析顺序与名字隐藏
{: .sec-know}

遇到一个没写 `::` 的名字，编译器按"由内向外"查找：当前块 → 外层块逐层往外 → 包住代码的命名空间由内向外 → 全局命名空间。**查到第一个就停**，外层哪怕有"更好匹配"的同名版本也轮不到它——这就是名字隐藏。类里稍有不同：成员函数体内先查类自身和基类，再往外层走。13.3.3 的 `::value` 例子演示的就是这套顺序：局部 3.14 挡住了全局 10。

理解"查到就停"是后面两个大坑的钥匙：块里的局部变量挡住全局（无害，编译器常会警告），派生类的成员函数挡住基类全部重载（隐蔽，见 13.4.7）。

### 13.4.3 辨析：未限定查找与限定查找
{: .sec-iv}

- **未限定查找**：名字裸写，如 `swap(a, b)`。编译器按 13.4.2 的顺序逐层找，函数调用还会追加 ADL。名字可能"意外"命中某个你没打算用的版本。
- **限定查找**：名字带前缀，如 `lib::swap(a, b)`。只在指定范围内找，结果确定。

拿不准重载会选谁时，把调用写成限定形式是最快的自证手段——如果限定版本和裸写版本行为不同，说明未限定查找在你看不见的地方捞到了别的东西。限定查找只看 `::` 前缀指定（或类名指定）的范围，**不追加 ADL**，这也是排查 ADL 问题的标准实验。

### 13.4.4 ADL：实参相关查找
{: .sec-know}

先看一个不写 `using` 也能工作的例子：

```cpp
// adl.cpp
#include <iostream>

namespace geo {
struct Vec2 {
    double x = 0, y = 0;
};

std::ostream& operator<<(std::ostream& os, const Vec2& v) {
    return os << '(' << v.x << ", " << v.y << ')';
}

Vec2 operator+(const Vec2& a, const Vec2& b) {
    return Vec2{a.x + b.x, a.y + b.y};
}
}  // namespace geo

int main() {
    geo::Vec2 a{1, 2}, b{3, 4};
    geo::Vec2 c = a + b;     // 没写 geo::，却找到了 geo::operator+
    std::cout << c << '\n';  // 同样没写 geo::，却找到了 operator<<
}
```

```bash
g++ -std=c++20 -Wall -Wextra adl.cpp -o adl && ./adl
```

```text
(4, 6)
```

这就是 **ADL**（argument-dependent lookup，实参相关查找，也叫 Koenig lookup）：对未限定的函数调用，除了普通查找，编译器还会把**每个实参所属的命名空间**（对类，还包括其基类所在命名空间）里的同名函数补进候选集。`a + b` 的实参类型 `geo::Vec2` 属于 `geo`，所以 `geo::operator+` 自动进入候选。

为什么非要这个机制？没有它，运算符重载根本没法用——你总不能要求用户写 `geo::operator+(a, b)`。`std::swap(a, b)` 能交换你的自定义类型、`std::begin` 能拿到你库的迭代器，靠的都是 ADL 在实参所在命名空间里捞函数。它是运算符生态的承重墙，不是可有可无的语法糖。

ADL 也有边界：只对**函数名和运算符**生效（函数调用语境），变量和类型不参与；限定名不触发 ADL。副作用是可能意外命中——你调 `open(p)` 时只要 `p` 的类型在某个命名空间里，那个命名空间里叫 `open` 的任何函数都可能参与重载决议。日常排查手段就是 13.4.3 说的：改写成限定名对比行为。

### 13.4.5 hidden friend 与 swap 惯用法
{: .sec-best}

把友元函数**定义在类内部**，它就不属于外层命名空间的普通名字——只能通过 ADL 找到，这叫 hidden friend：

```cpp
// swap_idiom.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <utility>

namespace lib {
class Widget {
public:
    explicit Widget(std::string s) : data_(std::move(s)) {}

    // hidden friend：不是 lib::swap 的普通重载，只有 ADL（实参是 Widget）能找到它
    friend void swap(Widget& a, Widget& b) noexcept {
        using std::swap;
        swap(a.data_, b.data_);
    }

    friend std::ostream& operator<<(std::ostream& os, const Widget& w) {
        return os << w.data_;
    }

private:
    std::string data_;
};
}  // namespace lib

// 泛型代码里调用 swap 的标准写法
template <class T>
void my_swap(T& a, T& b) {
    using std::swap;   // 先把兜底版本 std::swap 摆进候选
    swap(a, b);        // 未限定调用：ADL 优先找到 T 所在命名空间的专属版本
}

int main() {
    lib::Widget a{"left"}, b{"right"};
    my_swap(a, b);
    std::cout << a << ' ' << b << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra swap_idiom.cpp -o swap_idiom && ./swap_idiom
```

```text
right left
```

两个惯用法在这里合流。hidden friend 的好处：函数不进入外层命名空间的重载集，别处裸写 `swap(x, y)` 只要实参不是 `Widget` 就绝不会命中它，误伤为零；类内定义还能直接访问私有成员，省去一遍声明。`using std::swap; swap(a, b);` 的顺序是关键——**先**引入兜底**再**未限定调用，ADL 找到专属版就用专属版，找不到就用 std 版；顺序反了（先调用再 using）就永远只会命中 std 版。

> **注意：** 不要为自定义类型去特化 `std::swap`（函数模板全特化合法但已不被推荐），标准做法就是提供 hidden friend 或同命名空间自由函数 swap，再用上面的惯用法调用。
{: .sec-note}

### 13.4.6 两阶段查找与依赖名
{: .sec-ext}

模板里的名字查找分两个阶段：模板**定义**时，非依赖名立刻绑定；**实例化**时，依赖名（依赖模板参数的名字）才查找。这导致两类代码必须加关键字消歧：

```cpp
// dependent.cpp —— 需要 -std=c++20
#include <iostream>

template <class T>
struct Buffer {
    using value_type = int;
    typename T::value_type first;   // typename 必需：T::value_type 是个类型还是静态成员？
};

// 依赖基类的成员：普通查找不会去 Buffer<T> 里找
template <class T>
struct Derived : Buffer<T> {
    void demo() {
        std::cout << this->first << '\n';   // this-> 必需，裸写 first 编译不过
    }
};

int main() {
    Buffer<int> b;
    b.first = 7;
    std::cout << b.first << '\n';

    Derived<int> d;
    d.first = 9;
    d.demo();
}
```

```bash
g++ -std=c++20 -Wall -Wextra dependent.cpp -o dependent && ./dependent
```

```text
7
9
```

三个要点：

- **`typename`**：`T::value_type` 在定义期无法判断是类型还是静态成员，`typename` 明确告诉编译器"这是个类型"。
- **`template`**：`Maker<T>::make<int>()` 里的 `make` 是依赖名的成员模板，必须写成 `Maker<T>::template make<int>()`，否则 `<` 会被当成小于号。
- **`this->`**：派生自依赖基类时，裸写基类成员编译不过（两阶段的普通查找不去依赖基类里找），加 `this->` 声明"这是成员"即可。

写过模板的人都懂这三处的报错有多迷惑——错误信息指向几十行外的实例化点，真凶却只是少了个关键字。这只是入门，完整的两阶段查找规则在模板篇（第 16 篇）展开。

### 13.4.7 名字隐藏：派生类遮住基类
{: .sec-know}

未限定查找"查到就停"的规则作用在类层次上，会产生一个反直觉结果：派生类里只要有一个同名函数，基类的**全部同名重载**都不可见——不管签名差多远，这不是重载：

```cpp
// hiding.cpp
#include <iostream>

struct Base {
    void f(int) { std::cout << "Base::f(int)\n"; }
    void f(double) { std::cout << "Base::f(double)\n"; }
};

struct Derived : Base {
    // 名字隐藏发生在这：Derived 作用域里查到了 f，查找停止
    void f(double) { std::cout << "Derived::f(double)\n"; }
};

struct Fixed : Base {
    using Base::f;                                  // 修复：把 Base 的全部 f 引入
    void f(double) { std::cout << "Fixed::f(double)\n"; }
};

int main() {
    Derived d;
    d.f(1);      // 输出 Derived::f(double)：Base::f(int) 被整个藏住，1 被转成 double
    d.f(2.5);    // 输出 Derived::f(double)

    Fixed g;
    g.f(1);      // 输出 Base::f(int)：重载集里又有它了
    g.f(2.5);    // 输出 Fixed::f(double)
}
```

```bash
g++ -std=c++20 -Wall -Wextra hiding.cpp -o hiding && ./hiding
```

```text
Derived::f(double)
Derived::f(double)
Base::f(int)
Fixed::f(double)
```

`d.f(1)` 没走 `Base::f(int)` 而是走了 `Derived::f(double)`，int 到 double 还发生了隐式转换——这种"看起来像重载、实际是隐藏"的静默行为是真实项目里的高频坑。修复就是一句 `using Base::f;`，把基类的重载集搬进派生类作用域。继承篇（第 14 篇）会在这个机制上继续展开虚函数与重写的关系。

> **坑：** 编译器对这个场景有专门警告：加 `-Woverloaded-virtual` 可以在派生类函数恰好"隐藏"基类虚函数时提醒你。CI 里值得常开。
{: .sec-ts}

## 13.5 技术解惑
{: .sec-ts}

### 13.5.1 往 std 里加东西是未定义行为
{: .sec-warn}

标准的规定很直接：程序往 `std` 里添加声明或定义，行为未定义。能写进 std 的只有一类东西——**依赖你自己类型的模板特化**（类模板全特化、以及至少涉及一个程序自定义类型的函数模板/变量模板特化）。

```cpp
// 反面教材：不要这样做
namespace std {
    struct my_traits {};    // 往 std 里塞新类型：undefined behavior
}
```

为什么罚这么重？因为标准库实现内部大量使用非保留的辅助名——你的新声明可能和实现的某个内部标识撞车，编过了也行为不可测；换个标准库版本（升级 GCC、换 MSVC）立刻爆炸。合规的扩展路径只有两条：放在自己的命名空间里；确需特化标准模板（如自定义类型的 `std::hash` 特化）时，老老实实写全特化、不添加新名字。

### 13.5.2 ODR 与命名空间
{: .sec-know}

单一定义规则（One Definition Rule）：任何实体在整个程序里只能有一个定义，但 inline 函数、类定义、模板可以在多个翻译单元（TU）里各有一份**完全一致**的定义，链接器合并。命名空间与此交互出几个工程要点：

- 头文件里声明、源文件里定义，靠"命名空间可分段重开"来组织，天然满足 ODR；
- 匿名命名空间（13.2.5）里的名字每 TU 一份**独立实体**，如果头文件里的 inline 函数引用了它们，不同 TU 里的同一个 inline 函数就引用了不同对象——违反 ODR，且链接器通常不报错，问题在运行期以诡异形式出现；
- 全局命名空间里的普通函数/变量定义只能有一份，两个 .cpp 各定义一个同名全局函数就是经典的链接期重复定义错误。

ODR 违规最难缠的地方是"多数错误链接期就能抓到，少数要等运行期"。防的办法就一条：定义放 .cpp，头文件只放声明和 inline/模板。

### 13.5.3 extern "C" 与语言链接
{: .sec-know}

C++ 函数名会被改编（mangle）成带类型信息的符号（这就是重载的实现基础），C 函数名则原样保留。`extern "C"` 声明的是**语言链接**：这个函数按 C 的规则起符号名。

```cpp
// linkage.cpp
#include <cstdio>

extern "C" int c_add(int a, int b) { return a + b; }   // C 语言链接：符号名就是 c_add

int cpp_add(int a, int b) { return a + b; }            // 默认 C++ 链接：符号名被改编

int main() { std::printf("%d %d\n", c_add(1, 2), cpp_add(1, 2)); }
```

```bash
g++ -std=c++20 -Wall -Wextra linkage.cpp -o linkage && ./linkage && nm ./linkage | grep add
```

```text
3 3
0000000000001179 T c_add
000000000000118f T _Z7cpp_addii
```

`_Z7cpp_addii` 里能看到参数类型 `ii`——这正是重载能共存的底层机制，也解释了两个 `extern "C"` 函数为什么不能同名：C 不允许重载，同名 C 符号在链接层就是同一个符号。日常用法：包装 C 库的头文件（`<cstdio>` 里的 `printf` 就是被 `extern "C"` 声明的）、导出给 C/脚本/FFI 调用的接口。注意模板不能有 C 语言链接；`extern "C"` 块里放模板是编译错误。

### 13.5.4 模块（C++20）与命名空间的关系
{: .sec-ext}

模块解决的是**头文件的文本包含问题**：`import` 不做文本展开、宏不外泄、只导出明确 `export` 的实体，编译一次缓存复用。它和命名空间是正交的两件事——模块管"代码怎么被别人拿到"，命名空间管"名字怎么组织"。模块代码里照样写命名空间：

```cpp
// 概念示意：模块单元里命名空间照常使用，模块篇（预处理与模块）再展开
export module geometry;

export namespace geo {          // 由 export 决定对外可见性，namespace 负责名字组织
    struct Point { int x, y; };
}
```

一个实用推论：迁移到模块后，头文件 using 污染问题（13.3.4）的根源（文本包含扩散）消失了，但"往自己命名空间里组织名字"的需求不变。模块时代命名空间不仅没被取代，反而因为不再需要防 include 链，可以设计得更干净。

### 13.5.5 命名冲突排查：nm、c++filt 与报错解读
{: .sec-ver}

冲突有两类，排查路径不同。

第一类是**编译期冲突**——最典型的是 using 指令叠加后的二义性：

```cpp
// conflict.cpp
#include <iostream>

namespace a {
    struct Point { int x; };
    void open(Point) { std::cout << "a\n"; }
}
namespace b {
    struct Point { int x; };
    void open(Point) { std::cout << "b\n"; }
}

int main() {
    using namespace a;
    using namespace b;
    Point p{1};          // 错：a::Point 还是 b::Point？
    open(p);             // 就算类型侥幸确定，函数还得再决议一轮
}
```

```text
conflict.cpp: In function 'int main()':
conflict.cpp:15:11: error: reference to 'Point' is ambiguous
   15 |     Point p{1};
      |           ^
conflict.cpp:5:12: note: candidates are: 'struct a::Point'
conflict.cpp:10:12: note:                 'struct b::Point'
```

上面是 GCC 的报错节选（有删节）。读法：`ambiguous` 说明是多个 using 来源叠加；`candidates are` 会把所有候选的**完整限定名和文件行号**列出来，顺着行号找到源头，删掉多余的 using 指令或改成限定名即可。

第二类是**链接期冲突**——重复定义、找不到符号。这时换 `nm` 上场：`nm -C` 列出目标文件的符号并反改编（`-C` 调用 c++filt 的效果），`T` 开头是已定义、`U` 开头是未定义待链接。重复定义时用 `nm a.o | grep 符号名` 和 `nm b.o` 各查一遍，两个都带 `T` 就是凶手；链接报 `undefined reference` 时目标里对应的符号是 `U`，说明声明有、定义没编进来。把 `-C` 去掉看原始改编名还能确认符号是否被 `extern "C"` 影响——改编名和预期不符，多半是语言链接写错了。

## 变式追问
{: .sec-think}

1. ADL 为什么只对函数（和运算符）生效，类型名却不享受同等待遇？推理：类型名如果也随实参"自动可见"，那么 `Point p;` 里的 `Point` 究竟是哪个命名空间的就无法从代码上判断，可读性崩塌；而函数调用 `a + b` 的候选集由重载决议决定，多几个候选只是决议问题，不会产生"变量身份不明"。标准把 ADL 限制在函数调用语境，正是在"运算符生态必需"和"名字来源必须可读"之间取的平衡。

2. 头文件里写 `using std::string;` 和 `using namespace std;` 是一回事吗？不是，差着一个数量级。前者只引入一个名字，冲突面是"我自己的 string 是否会和你的 string 打架"，出了事编译期就能定位；后者引入几千个名字，且这些名字会参与下游代码的重载决议，出事的位置可能在任何调用点。另外 `using std::string;` 在命名空间内部写还能被命名空间边界圈住，`using namespace std;` 写在头文件全局则没有任何边界。前者的代价是头文件接口里多了一个 `string` 的别名承诺——改标准库路径时要动接口，所以更稳妥的还是 `std::string` 全限定。

3. inline namespace 换代后，旧版本的符号要保留多久？从 ABI 角度推理：已部署的二进制里硬编码着 `v1::` 的改编名，动态库里删掉 v1 符号，旧程序加载即失败。所以符号保留期取决于你的部署形态——静态链接的程序重编译即可，动态库则要等所有下游都迁移完。代码层面倒是可以立刻删：只要对外承诺是"源码兼容"而非"二进制兼容"，`v1` 的头文件删掉也不影响新编译。两份承诺混谈是版本化翻车的主因。

4. 匿名命名空间和 `static` 全局，现在还该用哪个？两者在"内部链接"这个效果上等价，匿名命名空间的优势是形式统一——变量、函数、类型、模板全能包，而 `static` 修饰类类型和模板时语义别扭。劣势几乎没有，唯一的争论点是一些老代码规范出于惯性仍要求 `static`。新代码选匿名命名空间，并在规范里写明"仅限 .cpp 文件"。
