C++ 不是一门"专家语言"，它是一门"规范握在自己手里"的语言：越界访问、悬垂引用、数据竞争这些事编译器不替你兜底，换来的收益是可预测的性能和对内存的完全控制。我转 C++ 头半年最懵的就是"能编过为啥还炸"——根子在于没搞懂编译链路和工具链。这一篇先钉死三件事：今天哪些系统还在靠 C++ 跑、一段源码怎么变成可执行文件、2026 年该配什么样的工具链，最后用 10 个新手高频问题收尾。

## 1.1 C++概述
{: .sec-expl}

### 1.1.1 2026 年，谁还在写 C++
{: .sec-know}

判断一门语言值不值钱，我不太看排行榜，更看"哪些系统十年后还得继续维护"。我自己负责过的几个项目，最后都绕不开 C++ 存量代码——这东西像技术债里的硬通货，想换也换不动。下面这张表每一条都带了"为什么非它不可"，这才是值得读的部分，别光扫一眼谁用了 C++。

| 领域 | 代表项目 | 为什么选 C++ | 换成别的语言的代价 |
| --- | --- | --- | --- |
| 游戏引擎 | Unreal Engine、自研商业引擎、Godot 的核心 | 帧预算 16.6ms，容不得 GC 停顿；需要精确控制对象内存布局做 cache 友好 | Java/Go 的停顿会让帧率抖动；Python 连 60fps 的逻辑都跑不动 |
| 浏览器 | Chromium/Blink、V8、WebKit、Firefox Gecko | 渲染引擎是性能敏感且内存占用必须可压的巨型代码库；要嵌 JS 引擎、GPU 进程、沙箱 | Rust 正在侵入一部分组件（如样式 Vulkan 层），但整引擎重写不现实 |
| 数据库与存储 | MySQL/InnoDB、MongoDB WiredTiger、RocksDB、ClickHouse、ScyllaDB | LSM/B-tree 的读写放大要靠精细的内存与落盘控制；释放pool、Arena 分配器必须手写 | Python/Java 版本很难同时压住延迟与内存；但 Rust 选手（如部分新存储）正在出现 |
| AI 基础设施 | PyTorch libtorch、TensorFlow runtime、ONNX Runtime、TensorRT、llama.cpp、vLLM 的执行层 | Python 负责写算子，"算得快"的那层全在 C++/CUDA 里；需要 SIMD、多线程、显存管理 | 纯 Python 实现推理会慢 10~100 倍；但新写的算子 C++/Triton/Rust 都有人在试 |
| 高频交易 | 交易所撮合、做市系统、行情网关 | 延迟预算压到微秒级：要共享内存、内核旁路、无锁队列，绝不能有隐性分配 | GC 语言一次 stop-the-world 就是一次事故 |
| 嵌入式与实时 | ARM Cortex-M 固件、汽车 AUTOSAR、ROS 2、无人机飞控 | 常常没有 OS 或者只跑 RTOS，堆分配经常被明令禁止；要直接操作寄存器 | Go/Java 需要运行时，本质上不了裸机 |
| 操作系统与驱动 | Windows 内核组件、macOS 部分框架、Android HAL、各种 driver | 要与既有的 C ABI 直接对接，还要能夹在 asm 片段里 | Rust 在 Linux 驱动里开始试点，但存量接口是 C |
| 编译器本身 | LLVM/Clang、GCC（自 4.8 起用 C++ 实现）、MSVC 前端 | 编译器自己是语言最苛刻的压力测试：要编译速度 + 表达力 + 不依赖运行时 | |
| 桌面应用 | Qt/KDE、Chrome、大量专业音视频与 CAD 软件 | 跨平台 GUI + 本地性能 | 用 Electron 就得接受几百 MB 内存起步 |

我读这张表时最在意的一点：没有哪个领域是"C++ 独占"的了。Rust 在新写的系统组件里抢食，Python 拿走了编排层，Go 拿走了微服务。C++ 的位置是"存量资产 + 性能底噪最低 + 与 C 生态无缝"这三件事交叉的地方。

### 1.1.2 语言定位：跟 C / Rust / Java / Go / Python 比什么
{: .sec-know}

别问"哪个语言最好"，要问"这个场景下，我愿意为什么付代价"。下面是取舍的核心维度。

| 语言 | 内存管理 | 运行时 | 性能特征 | 最痛的点 | 什么时候选它 |
| --- | --- | --- | --- | --- | --- |
| C | 手工 | 几乎无 | 理论最优，一切手写 | 无 RAII/容器/泛型，字符串处理返古 | 要最稳最平的 C ABI、写库给别人调 |
| C++ | RAII + 显式所有权 + optional/library 检查 | 只有 RTTI/异常/vtable | 接近 C，抽象不付运行时开销 | 语法体积大，UB 面广，学习曲线陡 | 要性能又要有抽象：引擎、浏览器、推理 runtime |
| Rust | 编译期借用检查 | 几乎无 | 同 C++ | 心智负担、编译时间、与存量 C++ 互操作要过 FFI 边界 | 新写的 memory-safe 系统组件、自己能全掌控的模块 |
| Java | GC | JVM | JIT 温热后很强，启动慢 | 内存占用大、预热延迟不可控 | 后台服务、大生态、企业级 ERP/Android 应用逻辑 |
| Go | GC | 自带调度器 | 中上，GC 停顿已很短 | 无精细内存控制，延迟不绝对可预测 | 微服务、中间件、工具链、云原生组件 |
| Python | GC | CPython | 解释执行，纯循环比 C++ 慢一到两个数量级 | 性能全靠 C/C++/CUDA 扩展 | 胶水层、数据处理、AI 训练/推理编排、原型 |

记住一条：**Python 写流程，C++ 写引擎，两者通过 pybind 或者 raw C ABI 粘在一起。** 我自己写 AI 相关的东西，Python 一行都躲不掉；但真正吃 GPU/CPU 的那几十行循环，八成还在 C++（或 CUDA C++）里——别被"AI 都用 Python"的说法带偏。

> **这里有个坑：** 把"C++ 比 Python 快"当成常量收入，然后写出一堆 `std::map` + 深层多态 + 到处 `new` 的代码，最后比优化过的 Python 还慢。C++ 的快靠的是"数据局部性 + 值语义 + 编译器能看清你的意图"，不是靠"用了 C++"。
{: .sec-pit}

#### 辨析：选择语言时到底在选什么
{: .sec-iv}

我选语言时真正掂量的就是这四件事：

- **生态**：这个领域现成的库在哪个语言里。做量化中间件，C++ 的 exchange connector 比 Rust 全得多；做 Web 后端，Go/Java 的中间件是白送的。
- **团队**：你手上会写 Rust 的人有几个。说到底，语言的生产率由团队熟练度决定。
- **部署形态**：要交付一个 .so 给别人链接（C/C++ ABI），还是要一个单文件容器镜像（Go），还是 Jupyter 里能跑（Python）。
- **失败模式**：这儿出了 bug，代价是"崩进程"（native）还是"慢一点"（GC 语言）。医疗/航天/交易三者对这件事的容忍度完全不同。

### 1.1.3 ISO 标准演进时间线
{: .sec-know}

C++ 由 ISO/IEC JTC1/SC22/WG21 维护，标准文档编号 ISO/IEC 14882。每个人拿到新工具链都问的那句"某某特性支持了吗"，答案都在这张表里。

| 版本 | 代号/标准号 | 发布 | 标志性特性 |
| --- | --- | --- | --- |
| C++98 | ISO/IEC 14882:1998 | 1998 | STL（容器/算法/迭代器）、异常、模板、RTTI、iostream、`bool` 正式成为内置类型、名字空间；`export` 关键字（后在 C++11 被移除） |
| C++03 | ISO/IEC 14882:2003 | 2003 | 纯缺陷修正（TC1），引入了值初始化（`T()`）；两者 `__cplusplus` 都是 `199711L` |
| C++11 | 14882:2011 | 2011 | 右值引用与移动语义、`auto`、`nullptr`、`constexpr`、`noexcept`、lambda、变长模板、范围 for、`static_assert`、智能指针、`<thread>`/`<atomic>`/`<mutex>`、`enum class`、`override`/`final`、`initializer_list`、`decltype`、`<chrono>`、`<regex>`、`unordered_*` |
| C++14 | 14882:2014 | 2014 | 泛型 lambda、`auto` 返回值推导、`decltype(auto)`、变量模板、`constexpr` 放宽（允许循环/局部变量）、`0b` 二进制字面量、数字分隔符 `'`、[[deprecated]]、`std::make_unique`、透明比较器 |
| C++17 | 14882:2017 | 2017 | 结构化绑定、`if constexpr`、内联变量、折叠表达式、CTAD（类模板实参推导）、`std::optional` / `variant` / `any` / `string_view` / `std::byte`、`<filesystem>`、并行算法、`[[nodiscard]]`/`[[maybe_unused]]`/`[[fallthrough]]`、保证拷贝消除、`std::pmr`、`<charconv>`（from_chars/to_chars）、node handle |
| C++20 | 14882:2020 | 2020 | Concepts、Ranges、协程（`co_await` 等）、Modules、`<=>` 三路比较与默认比较、`std::format`、`std::span`、`consteval`/`constinit`、`std::bit_cast`、`source_location`、`jthread`/`stop_token`、`char8_t`、`using enum`、`[[likely]]`、`std::erase_if`、`<chrono>` 日历与时区 |
| C++23 | ISO/IEC 14882:2024 | 2024-10 发布 | `std::expected`、`std::mdspan`、`flat_map`/`flat_set`、`std::print`/`println`（`<print>`）、`views::zip`/`enumerate`/`chunk`/`slide`/`join_with`/`stride`、deducing this（`this auto`）、`if consteval`、多维 `operator[]`、`static operator()`、`size_t` 后缀 `z`/`uz`、`std::generator`、`std::move_only_function`、`std::string::contains`、`std::unreachable`、`std::flat_*` |
| C++26 | 2026-03 WG21 技术定稿 | 待正式 ISBN 发布 | 静态反射（`^^` 与 `[: :]`，P2996）、Contracts（`pre`/`post`/`contract_assert`，P2900）、`std::execution` sender/receiver（P2300）、扩展语句 `template for`（P1306）、`std::simd`、`std::inplace_vector`、`#embed`、编译期异常（P3068）、`std::hive`、`std::linalg`、hazard pointer/RCU、标准库 hardening（P3471）、包索引 `args...[0]`、`= delete("reason")`、未初始化读取从 UB 变为 erroneous behavior、`[[indeterminate]]` |

关于这张表，有三个点我踩过或栽过跟头，单独拎出来说：

1. **标准版本不等于编译器支持程度。** `-std=c++23` 能写出来不代表 `<print>` 存在——标准库是独立实现的。
2. **`__cplusplus` 宏是三种 breakage 的解毒剂**：98/03 都是 `199711L`，11 是 `201103L`，14 是 `201402L`，17 是 `201703L`，20 是 `202002L`，23 是 `202302L`，26 是 `202602L`。写跨平台库时 `#if __cplusplus >= 202002L` 是常规操作。
3. **更细的判断用特性测试宏**：`<version>` 头文件里有一整套 `__cpp_lib_*`（如 `__cpp_lib_format`）与 `__cpp_*`（如 `__cpp_concepts`），比猜编译器版本靠谱得多。

### 1.1.4 语言和标准是怎么"做出来"的
{: .sec-expl}

WG21 每年开三次会：会前提交的提案（P 开头编号，如 P2300）由 SG/LEWG/LWG/EWG/CWG 分组讨论，投票通过才进工作草案。理解这件事有两个实在用处：

- **别把自己锁在一年内**：从提案通过到三大编译器稳定实现，通常还要 2~4 年。`std::println` 是 C++23 的，但 libstdc++ 里直到 GCC 14 才可用。
- **看不清 API 时先查 paper**：不理解 `views::enumerate` 的行为边界，去读 P2164 原文比翻二手博客准确。

### 1.1.5 学习路径：按目标分流
{: .sec-best}

不同目标的人走的路线完全不同，别拿一套"从入门到放弃"的顺序硬套。

| 你的目标 | 优先级 | 建议路径 |
| --- | --- | --- |
| 校招/面试 | 语法正确性 + STL 熟练 | 先把 C++11/17 的核心（值语义、RAII、智能指针、容器、算法）写熟，`std::variant`/`optional` 能讲清为什么存在 |
| 做后端/中间件工程 | 构建、调试、并发 | 重点补 CMake、gdb/lldb、sanitizer、线程池与锁的正确用法、 profiling |
| 做性能敏感模块 | 内存布局 + 编译器视角 | 补对象模型、cache line、SIMD 基础、读汇编、perf、micro-benchmark 方法学 |
| 从 C 转过来 | 忘掉 malloc/free 惯性 | 先练 RAII 与容器，警惕把 C++ 当 "C with classes" |
| 从 Java/Python 转过来 | 建立对象所有权直觉 | 先搞清"谁负责释放"这件事，再学模板；否则智能指针用反 |

> **注意：** 别把 C++20/23 新特性当第二语言单独学——这点我年轻时吃过亏。它们是同一套东西在旧写法之上的改良，先把 C++11/17 的表达习惯建立起来，新特性是自然替换而不是重学。
{: .sec-note}

## 1.2 开发工具
{: .sec-prac}

### 1.2.1 编译四阶段：预处理 → 编译 → 汇编 → 链接
{: .sec-expl}

这是本篇最该动手跑通的一段。`g++ main.cpp -o a.out` 这一行命令背后发生了四件事，出编译错误时你能否对上 stage，直接决定你排错的速度。

| 阶段 | 命令 | 输入 → 输出 | 干了什么 | 典型报错 |
| --- | --- | --- | --- | --- |
| 预处理 | `g++ -E` | `.cpp` → `.i` | 展开 `#include`/`#define`/`#if`，删注释，加行标记 | `fatal error: xxx: No such file or directory` |
| 编译 | `g++ -S` | `.i` → `.s` | 语法/语义分析、模板实例化、优化，生成某种 ISA 的汇编 | 语法错误、模板实例化错误、`undefined type` |
| 汇编 | `g++ -c` | `.s` → `.o` | 汇编器把助记符翻成机器码与重定位表 | 汇编器错误（罕见，多见于手写 asm） |
| 链接 | `g++` 无 stop 参数 | `.o` + `.a`/`.so` → 可执行文件 | 符号解析、重定向、合并段、解析动态库依赖 | `undefined reference to xxx`、`multiple definition of xxx` |

先写两个文件：

```cpp
// math.cpp —— 只有一个函数，方便看汇编
int add(int a, int b) {
    return a + b;
}
```

```cpp
// demo.cpp —— 需要 -std=c++20
#include <iostream>

#define VERSION 2
#define SQUARE(x) ((x) * (x))

int add(int a, int b);   // 只声明，故意不在这里定义

int main() {
    std::cout << "v" << VERSION << ", add(2,3) = " << add(2, 3) << "\n";
    std::cout << "square(7) = " << SQUARE(7) << "\n";
}
```

一步一步来：

```bash
# 1) 预处理：看文本替换之后的世界
g++ -std=c++20 -E demo.cpp -o demo.i
wc -l demo.i
```

```text
36115 demo.i        # 某 Linux + GCC 14 环境的输出；几万行是常态，取决于 libstdc++ 版本
```

一个 Hello World 为什么变成几万行？因为 `#include <iostream>` 是纯文本粘贴。这就是 C++ 编译慢的根因，也是 C++20 Modules（见 02 篇）存在的动机。

```bash
# 2) 编译：得到人类可读的汇编（-O0 才看得懂人话）
g++ -std=c++20 -O0 -S math.cpp -o math.s
cat math.s

# 想看 SSA/优化 pass，可以加 -fopt-info 或者打开 -fverbose-asm
g++ -std=c++20 -O2 -S -fverbose-asm math.cpp -o math_O2.s

# 3) 汇编：得到目标文件
g++ -std=c++20 -c math.cpp -o math.o
g++ -std=c++20 -c demo.cpp -o demo.o
file math.o
nm -C math.o
```

x86-64 Linux 上 `-O0` 编出来的 `math.s` 节选（去掉了 `.cfi_*` 调试指令）：

```asm
add(int, int):
        pushq   %rbp
        movq    %rsp, %rbp
        movl    %edi, -4(%rbp)
        movl    %esi, -8(%rbp)
        movl    -4(%rbp), %edx
        movl    -8(%rbp), %eax
        addl    %edx, %eax
        popq    %rbp
        ret
```

两个参数从 `%edi`/`%esi` 来（System V AMD64 调用约定的前两个整型参数寄存器），结果放 `%eax`。这就是"调用约定"，也是 ABI 的一部分——为什么不同编译器编出来的库不能直接混用，从这里就开始分叉了。

```bash
# 4) 链接
g++ demo.o math.o -o demo
./demo
```

```text
v2, add(2,3) = 5
square(7) = 49
```

故意漏一个文件，看链接器怎么说话：

```bash
g++ demo.o -o broken
```

```text
/usr/bin/ld: demo.o: in function `main':
demo.cpp:(.text+0x1a): undefined reference to `add(int, int)'
collect2: error: ld returned 1 exit status
```

注意错误里的 `add(int, int)`——这是**名字修饰（name mangling）**后的符号被 demangle 回来的样子。真实符号是 `_Z3addii`。C 语言没有函数重载，所以 C 的符号就是裸的 `add`，这就是为什么跨语言接口要写 `extern "C"`，我们后面讲 ABI 时还会碰到它。

想知道 gcc 私底下调了哪些子命令，可以用 `-###`：`g++ -### demo.cpp` 会打印出实际执行的每一个编译环节，包括 cc1、as、collect2 的参数。

> **坑：** 别拿 `gcc` 去编 C++ 源文件——我年轻时这么干过，错拖到链接阶段才炸，提示还极具误导性。`gcc` 只是 C 驱动，不会自动链 `-lstdc++`。C++ 一律用 `g++` 或 `clang++`。
{: .sec-pit}

### 1.2.2 三大编译器与 `-std=` 选项
{: .sec-know}

| 编译器 | 默认方言（不写 `-std` 时） | 常用 `-std` | 平台/备注 |
| --- | --- | --- | --- |
| GCC | GCC 11 起默认 `gnu++17`；GCC 6.1~10 是 `gnu++14`；更早是 `gnu++98` | `-std=c++17` / `c++20` / `c++23` / `c++26`（近版本） | Linux 事实标准，代码生成激进；`-std=gnu++20` 带 GNU 扩展， `-std=c++20` 严格禁用扩展并定义 `__STRICT_ANSI__` |
| Clang/AppleClang | Clang 16 起默认 `gnu++17`；Clang 6~15 是 `gnu++14` | 同 GCC，另加 `-stdlib=libstdc++` / `-stdlib=libc++` | 诊断信息最好、Modules/libc++ 支持最快；macOS 的 Xcode 工具链默认是 AppleClang |
| MSVC | 长期默认 `/std:c++14`（与 GCC/Clang 不一致，务必显式指定） | `/std:c++17` / `c++20` / `c++23` / `c++latest`，配 `/permissive-` 与 `/EHsc` | Windows 主力；`/Zc:__cplusplus` 才能让 `__cplusplus` 报真实值，`/utf-8` 治源码编码 |

几个容易踩的点：

- **旧别名**：`-std=c++2a` == `-std=c++20`，`-std=c++2b` == `-std=c++23`。写新代码用新名字。
- **`gnu++` vs `c++`**：差的是一群 GNU 扩展（`__int128`、匿名结构体、`asm` 关键字、可变长成员数组等）。写跨平台库时用 `-std=c++20`（严格模式），同时在 Linux CI 里也跑一次 `-std=gnu++20` 防止被人依赖扩展。
- **编译器版本 vs 语言版本**：两者正交。`-std=c++23` 在 GCC 11 上就能写（很多特性已支持），但 `<format>` 到 libstdc++ 13 才有，`<print>` 到 GCC 14。

#### 辨析：编译方言、目标平台、ABI 是三件事
{: .sec-iv}

- **方言（`-std=`）**：源码被按哪个版本的语法与库契约解释。
- **目标平台（`-m64` / `-march=` / `--target=`）**：生成什么指令集的代码。
- **ABI**：二进制怎么互相调用，由平台文档 + 编译器实现决定，与 `-std` 无关。

一个典型的例子：同一个 `.cpp`，用 `-std=c++17` 和 `-std=c++20` 在 GCC 里编出来的目标文件通常可以互相链接（标准方言不是 ABI 分界），但混用 `-D_GLIBCXX_DEBUG`（改容器布局）就一定崩。

### 1.2.3 三大标准库实现
{: .sec-know}

你写的 `std::vector` 到底是哪一份代码，取决于链接哪个库：

| 库 | 编译器 | 默认平台 | 识别办法 | 备注 |
| --- | --- | --- | --- | --- |
| libstdc++ | GCC（Clang 也能用） | 绝大多数 Linux 发行版 | `_GLIBCXX_RELEASE` 宏 | GCC 5 起有两套 ABI，靠宏 `_GLIBCXX_USE_CXX11_ABI=0/1` 切换（`std::string` 从 COW 变 SSO 那次历史遗留） |
| libc++ | Clang | macOS/iOS、FreeBSD、Android NDK 部分场景 | `_LIBCPP_VERSION` 宏 | LLVM 项目，对 C++20/23 特性通常最快齐活；换用要同时换 `libc++abi`，整个依赖链都得一起换 |
| MSVC STL | MSVC | Windows | `_MSVC_STL_VERSION` 宏 | 开源在 GitHub；调试级别宏 `_ITERATOR_DEBUG_LEVEL` 会改变容器布局，混用的坑见 1.4.4 |

> **这里有个坑：** 半个工程链接了 libc++、另一半链接了 libstdc++，`std::string` 在两边布局不同，链接器可能还不会报错（符号都在），运行时却随机崩。怎么防？一句话：**一个二进制只用一种标准库，包括它链接的所有静态/动态库。**
{: .sec-pit}

### 1.2.4 现代构建：CMake 的 `target_*` 写法
{: .sec-prac}

为什么不用 Makefile 裸写？因为你要处理"多平台生成器、头文件搜索路径、编译选项传递、依赖传递、打包安装"这五件事，手写必然失控，两份平台各一份 Makefile 更是灾难。CMake 已经成了 C++ 的事实工业标准。

目录结构：

```text
hello-cpp/
  CMakeLists.txt
  include/math_utils.hpp
  src/math_utils.cpp
  app/main.cpp
```

```cpp
// include/math_utils.hpp
#pragma once

namespace math_utils {

[[nodiscard]] int square_sum(int a, int b);

}  // namespace math_utils
```

```cpp
// src/math_utils.cpp
#include "math_utils.hpp"

namespace math_utils {

int square_sum(int a, int b) {
    return a * a + b * b;
}

}  // namespace math_utils
```

```cpp
// app/main.cpp —— 需要 -std=c++20
#include <iostream>
#include "math_utils.hpp"

int main() {
    int a = 3;
    int b = 4;
    std::cout << "square_sum(" << a << ", " << b << ") = " << math_utils::square_sum(a, b) << "\n";
}
```

```cmake
# CMakeLists.txt
cmake_minimum_required(VERSION 3.20)

project(hello_cpp
        VERSION 1.0.0
        DESCRIPTION "target_* 写法的现代 CMake 示例"
        LANGUAGES CXX)

# 全局兜底设置：真正决定 target 的是下面的 target_compile_features
set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)          # 关闭 GNU 扩展，跨平台少踩坑
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)  # 生成 compile_commands.json 给 clangd/IWYU 用

add_library(math_utils src/math_utils.cpp)

# PUBLIC：既给自己用，也传给链接它的目标
target_include_directories(math_utils
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>)

# 编译器无关地声明"我至少要有 C++20"
target_compile_features(math_utils PUBLIC cxx_std_20)

add_executable(demo app/main.cpp)
target_link_libraries(demo PRIVATE math_utils)

# 按编译器 ID 分别加开关，避免这套配置到 Windows 上炸掉
target_compile_options(demo PRIVATE
    $<$<CXX_COMPILER_ID:MSVC>:/W4 /permissive->
    $<$<CXX_COMPILER_ID:GNU,Clang,AppleClang>:-Wall -Wextra -Wpedantic>)

# 可选开关：cmake -B build -DCPP_ASAN=ON
option(CPP_ASAN "enable AddressSanitizer and UBSan" OFF)
if(CPP_ASAN)
    target_compile_options(demo PRIVATE -fsanitize=address,undefined -fno-omit-frame-pointer -g -O1)
    target_link_options(demo PRIVATE -fsanitize=address,undefined)
endif()
```

构建流程：

```bash
# 单配置生成器（Ninja / Unix Makefiles）：构建时就要定 -DCMAKE_BUILD_TYPE
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build
./build/demo

# 多配置生成器（Visual Studio / Ninja Multi-Config / Xcode）：构建时再选 config
cmake -S . -B build-mc -G "Ninja Multi-Config"
cmake --build build-mc --config Release

# CI 里常用的一套
cmake -S . -B build/release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake -S . -B build/debug   -G Ninja -DCMAKE_BUILD_TYPE=Debug -DCPP_ASAN=ON
```

```text
[2/2] Linking CXX executable demo
square_sum(3, 4) = 25
```

（`[2/2]` 这种进度输出来自 Ninja；用 Unix Makefiles 时会是百分比进度。）

为什么坚持 `target_*` 而不是全局变量：

| 老写法（别用） | 现代写法 | 差别 |
| --- | --- | --- |
| `include_directories(x)` | `target_include_directories(tgt PUBLIC/PRIVATE x)` | 老写法对所有后续 target 生效，包括你不想污染的第三方 target |
| `add_compile_options(-Wall)` | `target_compile_options(tgt PRIVATE -Wall)` | 同上，且 MSVC 会因为收到 `-Wall` 直接报错 |
| `link_libraries(foo)` | `target_link_libraries(tgt PRIVATE foo)` | 同上 |
| `set(CMAKE_CXX_FLAGS ...)` | `target_compile_features(tgt PUBLIC cxx_std_20)` | CMake 会自己挑 `-std=gnu++20` 还是 `/std:c++20`，跨平台不炸 |

`PUBLIC` / `PRIVATE` / `INTERFACE` 的语义，其实就一句话：

- `PRIVATE`：只有我自己编译需要（比如 `demo` 的警告选项）。
- `INTERFACE`：只有别人用我需要（纯头文件库）。
- `PUBLIC`：两边都要（`math_utils` 的头文件路径——我自己要用，用我的 `demo` 也要能 `#include`）。

再补两个现代 CMake 的日常：

```bash
# ccache 加速重编译
cmake -S . -B build -DCMAKE_CXX_COMPILER_LAUNCHER=ccache

# 用 lld/mold 缩短链接时间
cmake -S . -B build -DCMAKE_EXE_LINKER_FLAGS="-fuse-ld=mold"
```

以及 `CMakePresets.json`（CMake 3.21+），把"我该怎么配这个工程"写进仓库：

```json
{
  "version": 3,
  "configurePresets": [
    {
      "name": "gcc-release",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/release",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Release",
        "CMAKE_CXX_COMPILER": "g++-14"
      }
    },
    {
      "name": "clang-asan",
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/asan",
      "cacheVariables": {
        "CMAKE_BUILD_TYPE": "Debug",
        "CMAKE_CXX_COMPILER": "clang++",
        "CPP_ASAN": "ON"
      }
    }
  ]
}
```

```bash
cmake --preset gcc-release && cmake --build --preset gcc-release
```

### 1.2.5 依赖管理：vcpkg / Conan / FetchContent 怎么选
{: .sec-know}

第三方库怎么用，是 C++ 工程里头号让人抓狂的事。三种主流做法：

| 方案 | 交付形态 | 版本锁定 | 优点 | 痛点 | 适合 |
| --- | --- | --- | --- | --- | --- |
| vcpkg（manifest 模式） | 源码编译 + 二进制缓存 | `vcpkg.json` + `vcpkg-configuration.json`（基线/commit 锁定） | 与 CMake 集成顺滑（`vcpkg toolchain` 或 CMakePackages），跨平台 triplet 统一 | 首次编译耗时；包版本升级要跟着基线走 | 团队内 Windows+Linux+macOS 都有的桌面/服务端项目 |
| Conan 2 | 二进制包（也可以是源码） | `conanfile.txt` / `.py`，有 lockfile 概念，需要远端（如 Artifactory 或公共远端） | 二进制包复用，版本粒度细，私有仓库友好 | 概念多（profile/settings/options），学习曲线前期陡 | 企业内需要私有包仓库、交叉 CI 多配置的项目 |
| CMake FetchContent | 源码 | 靠 git tag / commit hash | 零外部依赖（只要有 CMake + git），构建可复现 | 吃满编译时间；依赖项的 CMake 会污染你的 target；重复下载 | 高校课题、单仓库小工具、只有一个依赖的项目 |

我的习惯是：**团队项目上 vcpkg 或 Conan（取决于要不要私有仓库），个人小工具用 FetchContent。** 千万别"手动下载 zip 丢进 `third_party/` 然后忘记记录版本"——这种坑我替你踩过了。

### 1.2.6 必装工具链清单
{: .sec-prac}

下面这几样，缺一样你的开发效率就掉一档。

| 工具 | 干什么 | 最低限度用法 |
| --- | --- | --- |
| clang-format | 统一代码格式，消灭 review 里的空格战争 | 仓库放 `.clang-format`，CI 跑 `--dry-run -Werror` |

| sanitizer | 运行时插桩抓 UB | `-fsanitize=address,undefined` 跑一遍测试 |

| Compiler Explorer | 在线看汇编、对比编译器 | 看某一行代码到底生成了几条指令 |

调试器常用命令对照：

| 动作 | gdb | lldb |
| --- | --- | --- |
| 下断点 | `b math_utils.cpp:8` / `b 'math_utils::square_sum'` | `b math_utils.cpp:8` |
| 跑起来 | `r arg1 arg2` | `r arg1 arg2` |
| 单步（不进函数） | `n` | `n` |
| 单步（进函数） | `s` | `s` |
| 跳出当前函数 | `fin` | `finish` |
| 打印/美化结构 | `p x` / `p *ptr` | `p x` / `frame variable` |
| 调用栈 | `bt` / `bt full` | `bt` |
| 所有线程栈 | `thread apply all bt` | `bt all` |
| 切栈帧/线程 | `f 2` / `thread 3` | `frame select 2` / `thread select 3` |
| 观察点 | `watch var` / `awatch var` | `watch set var var` |
| 崩溃后看 | `ulimit -c unlimited` 后 gdb `a.out core` | `lldb -c core a.out` |

Sanitizer 对照（这是投入产出比最高的一类工具）：

| 类型 | 选项 | 抓什么 | 代价 | 注意 |
| --- | --- | --- | --- | --- |
| ASan | `-fsanitize=address` | 越界读写、use-after-free、double free | 约 2x 时间、内存开销大 | 需要保留符号与 `-fno-omit-frame-pointer` 才有好栈 |
| UBSan | `-fsanitize=undefined` | 有符号溢出、对齐错误、非法位移、除零 | 约 1.2x | 可与 ASan 同时开 |
| TSan | `-fsanitize=thread` | 数据竞争、锁序问题 | 5~15x | **不能**与 ASan 同时使用 |
| MSan | `-fsanitize=memory` | 未初始化内存读取 | 需要整条依赖链都插桩 | 通常只在 libc++ 环境下好用 |
| LSan | `-fsanitize=leak` | 内存泄漏 | 极小 | ASan 已内置，无需叠加 |

```bash
# 典型的 ASan + UBSan 组合
g++ -std=c++20 -g -O1 -fno-omit-frame-pointer \
    -fsanitize=address,undefined -fsanitize-recover=address \
    demo.cpp math.cpp -o demo_san
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=print_stacktrace=1 ./demo_san
```

perf 三板斧：

```bash
g++ -std=c++20 -O2 -g -fno-omit-frame-pointer app.cpp -o app
perf record -g --call-graph dwarf -- ./app
perf report
perf stat ./app
```

> **注意：** 用 `-O2` 加 `-g` 采样，比 `-O0` 有意义得多。优化后的热点分布才是用户真实感受到的那份性能；`-O0` 下每个函数调用都占一坨真实开销，采样比例的失真足以让你优化错地方。

### 1.3.1 主流 IDE 怎么选
{: .sec-know}

| 选项 | 强项 | 弱项 | 什么时候选 |
| --- | --- | --- | --- |
| VS Code + clangd + CMake Tools | 免费、跨平台、启动快、每个配置都摊在文件里看得见 | 要自己配 3 个扩展，第一次容易配错 | 跨平台、Linux/macOS 主力、想把底层搞清楚 |
| Visual Studio | Windows 上调试体验最好（含性能探查器、GPU 调试）、MSVC 原生支持 | 庞大的 IDE，不用 MSVC 时收益打折 | Windows 平台专属开发 |
| CLion | CMake 集成最深、重构/代码洞察强、自带 sanitizer/valgrind 面板、支持远程调试 | 付费；大型项目索引吃内存 | 长期 CMake 项目且愿意付费 |

| Neovim / Emacs + clangd | 键盘流、可脚本化 | 配置成本高 | 老鸟、终端党 |

判断标准不是"哪个 IDE 好用"，而是**它能否吃到和 CI 一模一样的编译命令**。这就是为什么 `CMAKE_EXPORT_COMPILE_COMMANDS=ON` 那么重要：有了 `compile_commands.json`，clangd 才知道你的 `math_utils.hpp` 该用 `-I.../include -std=c++20` 去解析。没它，你的编辑器在瞎猜，跳转和补全就会错。

### 1.3.2 VS Code 的最小可用配置
{: .sec-prac}

`.vscode/settings.json`：

```json
{
  "cmake.sourceDirectory": "${workspaceFolder}",
  "cmake.configureArgs": ["-DCMAKE_EXPORT_COMPILE_COMMANDS=ON"],
  "C_Cpp.intelliSenseEngine": "disabled",
  "clangd.arguments": [
    "--background-index",
    "--compile-commands-dir=${workspaceFolder}/build",
    "--header-insertion=never",
    "--clang-tidy"
  ],
  "editor.formatOnSave": true,
  "[cpp]": { "editor.defaultFormatter": "llvm-vs-code-extensions.vscode-clangd" }
}
```

要点：

- clangd 与 Microsoft C/C++ 扩展的 IntelliSense **别同时开**——它们对同一份符号表各算一遍，跳转经常跳错，还占双倍 CPU。只有 Windows + MSVC 的场景才考虑反过来关掉 clangd、改用 MSVC 那套。
- `compile_commands.json` 必须指向你真正用的那个构建目录，否则 clangd 用的是过期配置。

`.vscode/launch.json`（lldb/gdb 都行）：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "Debug demo",
      "type": "cppdbg",
      "request": "launch",
      "program": "${workspaceFolder}/build/demo",
      "args": [],
      "cwd": "${workspaceFolder}",
      "stopAtEntry": false,
      "externalConsole": false,
      "MIMode": "gdb"
    }
  ]
}
```

> **坑：** 真正常见的调试坑是不加 `-DCMAKE_BUILD_TYPE=Debug`：断点永远落在汇编而不是源码行，或者变量显示成 `<optimized out>`。调试就用 Debug：`-DCMAKE_BUILD_TYPE=Debug`（GCC/Clang 下等价于加 `-g -O0`）。
{: .sec-pit}

### 1.3.3 Compiler Explorer：验证 C++ 直觉的公共实验台
{: .sec-ext}

写 C++ 时间够长的人都有一个共同习惯：拿不准某段代码会不会被优化到零开销，就去 Compiler Explorer（godbolt.org）看汇编。用法建议：

- 编译器选 GCC/Clang trunk，`-std=c++20 -O2`；对比观察加 `-std=c++17` 是否行为不同。
- 写个只返回值的小函数，看 `-O2` 下是不是被完全内联消失——这就是"零开销抽象"最直观的证据。
- Compiler Explorer 里还能直接 `-fsave-optimization-record`，或者开一个 "Add new > Optimization Output" 面板，看某个优化到底有没有生效。

### 1.4.1 三代 Hello World
{: .sec-prac}

编译与运行：

```bash
g++ -std=c++20 -Wall -Wextra hello98.cpp -o hello98 && ./hello98
g++ -std=c++20 -Wall -Wextra hello20.cpp -o hello20 && ./hello20
g++ -std=c++23 -Wall -Wextra hello23.cpp -o hello23 && ./hello23
```

```text
Hello, World
Hello, World!
Hello, World!
```

三条建议：

1. **初学和写代码库时默认用 `std::cout`**。它的可用性是零门槛，`std::print` 的门槛是工具链版本。
2. **`std::format`/`std::println` 赢的地方是类型安全和格式串检查**：从 C++23（P2216）起，格式串在编译期被检查，占位符和参数不匹配会得到编译错误而不是运行时的乱码或 `std::format_error`。运行时才确定的格式串，用 `std::vformat`（C++20）/ `std::runtime_format`（C++26）。
3. **别用 `printf` 当主线**。它没有类型检查，`%d` 配 `size_t` 是经典 UB；但它确实快，做高频日志的格式部分另说。

### 1.4.2 `main` 的合法签名与返回值
{: .sec-know}

标准只要求实现支持两种签名：

```cpp
int main() { /* ... */ }                       // (1) 无参数
int main(int argc, char* argv[]) { /* ... */ } // (2) 带参数
```

`char* argv[]` 在形参里会退化成 `char** argv`，所以 `int main(int, char**)` 完全等价。另外：

- `void main()` 是**非标准**（MSVC 允许作为扩展，GCC 会报错）。别写。
- 部分平台额外提供带环境变量的第三参数（如 `char* envp[]`），不可移植。
- Windows/MSVC 专有入口 `wmain`（宽字符 `wchar_t` 版本），跨平台代码别依赖。
- `main` 不能被用于其他地方：取它的地址、调用它都是非法的（ill-formed）；它也不能是 `inline`、`static`、`constexpr`（新标准明确禁止），更不能被其他东西重载。
- 走到 `main` 末尾没写 `return`，等价于 `return 0;`——这是专门为 `main` 开的特例，其他有返回值的函数不写 return 是 UB。

返回值的含义：

| 返回值 | 含义 | 怎么读 |
| --- | --- | --- |
| `0` / `EXIT_SUCCESS`（`<cstdlib>`） | 成功 | Bash 里 `echo $?` 看到 0 |
| 非 0 / `EXIT_FAILURE` | 失败 | 具体数值是给脚本和 CI 判定的，shell 里 `if ./app; then` 只看 0/非 0 |

演示：

```cpp
// args.cpp —— 需要 -std=c++20
#include <cstdlib>
#include <iostream>
#include <string_view>

int main(int argc, char* argv[]) {
    std::cout << "argc = " << argc << "\n";
    for (int i = 0; i < argc; ++i) {
        std::string_view arg{argv[i]};
        std::cout << "argv[" << i << "] = " << arg << "\n";
    }
    return argc >= 2 ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

```bash
g++ -std=c++20 -Wall -Wextra args.cpp -o args
./args hello world; echo "exit code = $?"
```

```text
argc = 3
argv[0] = ./args
argv[1] = hello
argv[2] = world
exit code = 0
```

### 1.4.3 程序是怎么开始、怎么结束的
{: .sec-expl}

`main` 不是第一行执行的代码。之前之后都有配套动作：

1. CRT（C 运行库）初始化：设置栈/堆、`stdin/stdout` 缓冲、读取环境变量。
2. 静态初始化：常量初始化（编译期）+ 动态初始化（全局对象的构造函数等）。
3. 调用 `main`。
4. `main` 返回 → 调用 `std::exit(retval)`：执行 `std::atexit` 注册的函数（后进先出）、析构全局/静态对象（同样逆序）、刷新并关闭 C 流。
5. 交还控制权给操作系统。

几个岔路：

| 退出方式 | 局部对象析构 | 全局/静态对象析构 | `atexit` 回调 | 备注 |
| --- | --- | --- | --- | --- |
| `return` from main | 是 | 是 | 是 | 标准途径 |
| `std::exit(code)` | **否** | 是 | 是 | 在深层函数里直接退出 |
| `std::quick_exit(code)` | 否 | 否 | 否（只跑 `at_quick_exit`） | 多线程/死锁逃生用途 |
| `std::abort()` | 否 | 否 | 否 | 产生 SIGABRT，留 core 便于调试 |

> **坑：** 不要在全局对象的构造函数里依赖另一个 **translation unit** 里的全局对象——不同 TU 之间的动态初始化顺序是未指定的，这就是著名的"静态初始化顺序惨剧"（SIOF）。解决办法是用函数内的静态局部对象（C++11 起初始化线程安全），见第 02 篇 2.2.5。
{: .sec-pit}

### 1.4.4 ABI 与二进制兼容：为什么重要
{: .sec-know}

ABI（Application Binary Interface）是"二进制层面的调用约定"，包括：函数参数怎么传（寄存器还是栈）、结构体怎么对齐与填充、虚函数表布局、异常处理怎么传播、符号怎么修饰、标准库类型的内存布局。

**为什么值得在意：** 只要你交付的不是源码（闭源 SDK、插件、预编译 so/dll），ABI 就是你产品的契约。C++ 没有标准 ABI——三大编译器各自遵循各自的规则（GCC/Clang 在多数 Unix 上共同遵循 Itanium C++ ABI，Windows 的 MSVC 是另一套）。

会破坏 ABI 的典型改动：

- 给类增加/重排数据成员，或改成员类型（改了对象布局）。
- 增加或重排虚函数，或改动继承结构（改了 vtable）。
- 改动**内联**函数体的实现（旧二进制里有这份函数的机器码，不会跟着换）。
- 改变模板实参（模板实例化后的代码在调用方二进制里）。
- 改枚举的底层类型、改 inline 变量的初始值。
- 混用不同"配置宏"编译出来的对象：`_GLIBCXX_USE_CXX11_ABI=0/1`、`_GLIBCXX_DEBUG`、`_ITERATOR_DEBUG_LEVEL`（改容器布局）。

不会破坏 ABI 的：加非虚成员函数、加静态成员函数、改函数内部实现（非内联）。

**跨 ABI 边界的工程做法**：用 `extern "C"` 导出一组返回 opaque 指针的工厂函数，内部再 `static_cast` 回 C++ 类型。

```cpp
// plugin_if.h —— 对外的 C 接口，C++ 和别的语言都能调
#ifndef PLUGIN_IF_H
#define PLUGIN_IF_H

#ifdef __cplusplus
extern "C" {
#endif

typedef struct engine_t engine_t;      /* 不透明句柄，调用方不知道它的布局 */

/* 返回 NULL 表示失败；
   destroy_engine 负责释放，调用方不许自己 free —— 因为分配发生在库这一侧 */
engine_t* create_engine(const char* config_path);
int       engine_run(engine_t* self, int* result);
void      destroy_engine(engine_t* self);

#ifdef __cplusplus
}
#endif

#endif
```

```cpp
// plugin_if.cpp —— 需要 -std=c++20
#include "plugin_if.h"

#include <memory>
#include <string>

namespace {
struct Engine {                 // 真正的 C++ 类型，对外完全不可见
    std::string config;
    int counter{0};
};
}  // namespace

extern "C" engine_t* create_engine(const char* config_path) {
    if (config_path == nullptr) {
        return nullptr;
    }
    auto* e = new Engine{std::string{config_path}, 0};
    return reinterpret_cast<engine_t*>(e);
}

extern "C" int engine_run(engine_t* self, int* result) {
    if (self == nullptr || result == nullptr) {
        return -1;              // 用返回码表达错误，而不是抛异常穿过 C 边界
    }
    auto* e = reinterpret_cast<Engine*>(self);
    *result = ++e->counter;
    return 0;
}

extern "C" void destroy_engine(engine_t* self) {
    delete reinterpret_cast<Engine*>(self);
}
```

穿越边界的硬规则：

- 异常**不许**穿过 C 边界（两边异常处理模型和展开表不兼容）——改成返回错误码。
- 两侧各自分配各自释放：库创建的就由库的 `destroy_*` 销毁。Windows 上尤其明显，`/MT` 与 `/MD` 运行时的堆不是同一个。
- 约定头里不要出现 STL 类型（`std::string`、`std::vector`）——它们的布局随标准库实现与编译选项变化。
- 记录你交付给别人的二进制是用什么编译器版本 + 什么编译选项编的，并在 CI 里锁死。

## 1.5 技术解惑
{: .sec-know}

### 1.5.1 2026 年了，C++ 会不会被 Rust 取代
{: .sec-know}

不会，至少不会以"替换"的形式。Rust 解决的是"C++ 里那类靠人肉纪律避免的内存与并发错误"，编译期借用检查确实消灭了一大类 UB，新写的高风险组件（浏览器的新模块、命令行工具、系统服务）正在往 Rust 迁。但事情的另一面是：现存几十亿行 C++ 不会消失，游戏引擎/编译器/数据库/推理 runtime 这些资产本身的价值远高于重写成本；而 Rust 与 C++ 双向互操作仍然要跨 FFI 边界，来回转换不便宜。现实路径是混合：性能敏感的老部件继续 C++，新的隔离模块用 Rust——Chromium 和一部分 OS 组件已经在这么做了。

对个人的建议：如果你只能学一门，看你要进哪个行业；如果你已经会 C++，学 Rust 的借用模型反过来能让你写出更清晰的 C++ 所有权设计。

### 1.5.2 我该从 C++11 学起还是一步到 C++20
{: .sec-know}

先啃 C++11/17 的核心概念（值语义、RAII、智能指针、容器算法），再一次性把 C++20 的写法替换上去。理由：C++20 的 concepts/ranges/format 是建立在旧写法之上的改良，不是新语言；反过来，如果你先背新式写法而不懂 move semantics，你会写出"看起来很现代但到处拷贝"的代码。落地的开关：项目 CMake 里写 `target_compile_features(tgt PUBLIC cxx_std_20)`，写自己的练习代码用 `-std=c++20`。

### 1.5.3 头文件里能不能放函数实现
{: .sec-know}

能，但必须 `inline`（或在类体内定义的成员函数，它们隐式 inline，或模板）。原因：每个 `.cpp` 是独立编译的 translation unit，头文件被 `#include` 到多个 TU 里，非 inline 的定义会产生**多份**同名外部符号，链接器报 `multiple definition`。三种正确做法：

```cpp
// 方案 A：inline（同一份代码，链接器挑一个）
inline int add_inline(int a, int b) { return a + b; }

// 方案 B：类内定义，隐式 inline
struct Math {
    static int plus(int a, int b) { return a + b; }
};

// 方案 C：模板必须放头文件（实例化需要看得到定义）
template <class T>
T twice(T v) { return v + v; }
```

A、B、C 之外，还有 C++17 的 `inline` 变量，专门解决头文件里的全局常量：

```cpp
// config.hpp，被多个 TU include 也不会冲突
inline constexpr int kMaxRetries = 3;
```

### 1.5.4 `#include <...>` 和 `#include "..."` 有什么区别
{: .sec-know}

搜索路径起点不同：尖括号只搜系统路径（`-I` 给的路径也在其中），引号先搜当前文件所在目录再回落到系统路径。实践建议：自己的头文件用引号、系统/第三方用尖括号，这样读的时候一眼能看出依赖来源；同时别忘了两种都可能伪装成"能编译"，真正的隐患是**传递包含**（A 依赖 B，B 顺手 include 了 C，于是 A 直接用 C，某天 B 不再 include C，A 就炸）。规则：用到了什么就自己 include（include-what-you-use）。

### 1.5.5 为什么推荐 `-Wall -Wextra`，还有哪些该开
{: .sec-know}

`-Wall` 只开了"公认有用"的一部分开关，远不是"全部"。日常推荐组合：

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion -Wold-style-cast
```

其中 `-Wconversion`/`-Wsign-conversion` 会让符号性混算、窄化 `int`→`char` 全部暴露出来，初期会很吵，但这是最容易藏 bug 的一类。MSVC 侧对应 `/W4 /permissive-`（`/Wall` 会带来大量系统头噪音，一般用 `/W4`）。

### 1.5.6 中文输出乱码怎么办
{: .sec-know}

三个环节任一错位都会乱码：源码文件编码、编译器对源码的解读方式、终端显示编码。现代做法是全链路 UTF-8：

- 源文件存成 UTF-8（无 BOM 更稳，MSVC 需要 `/utf-8` 才不会按本地 code page 猜）。
- Linux/macOS 终端本身就是 UTF-8；Windows PowerShell 执行 `chcp 65001`，或者更直接地在程序里用宽字符 Windows API（那是另一套）。
- 字符串字面量注意三种前缀：`"中文"` 是执行字符集（MSVC 下随 options 变化）、`u8"中文"` 在 C++20 起是 `char8_t`（打印需要转换）、`L"中文"` 是宽字符。
- 跨平台工程里，**日志的人类可读文案走 UTF-8 字节流**，内部处理统一 UTF-8，是最省心的约定。

### 1.5.7 为什么 C++ 编译这么慢，怎么救
{: .sec-know}

根因有三条：`#include` 是文本粘贴（一个 `<iostream>` 就是几万行）、模板实例化是每个 TU 各做一遍的重复劳动、优化 pass 本身贵。缓解手段按性价比排：

- `ccache`/`sccache`：几乎零改动，重编译收益巨大。
- 前置声明 + 减少头文件暴露：把依赖藏到 `.cpp`，用 pimpl 或者 forward declaration 隔开变化频繁的头文件。
- 预编译头（PCH）或 C++20 Modules：Modules（第 02 篇会讲）是根治思路，但工具链与生态还在铺，新项目可以试点，老项目迁移要评估。
- 并行构建：`cmake --build build -j$(nproc)`，Ninja 默认就并行。
- 换 linker：`-fuse-ld=mold` 或 `lld`。

### 1.5.8 `using namespace std;` 到底能不能用
{: .sec-know}

函数体内的单行能接受（争议仍在），但**绝不要写在头文件全局作用域**。理由不是"不优雅"，而是它会把 `std` 的所有名字注入到每个 include 了你的头文件的 TU 里，跟用户的名字一冲突，报错位置可能在毫不相干的第三方代码里，排错成本极高。Google、LLVM 等主流风格指南都禁止 using-directive。写 `std::cout` 多打 5 个字符而已。想要短一点就用别名：`namespace fs = std::filesystem;`（放在函数或文件作用域都可以）。

### 1.5.9 CMake 和 Makefile 我该学哪个
{: .sec-know}

学 CMake，Makefile 只要能读懂别人的就行。CMake 不直接编译，它生成 Ninja/Makefile/VS 工程，所以你会 CMake 就等于同时会了各平台的构建。入门只要掌握五个东西：`add_library` / `add_executable` / `target_link_libraries` / `target_include_directories` / `target_compile_features`。至于"CMake 语法难看"这件事是真的，但它是公认的最低公约数。

### 1.5.10 遇到编译报错一头雾水，怎么办
{: .sec-know}

按这个顺序：

1. **看第一个错误**，别看最后一个。模板报错后面会跟几十行"实例化自……"的追溯，根因通常在最上面。
2. 把错误信息里的 `<typename>` 和 `iterator` 之类的别名先还原成实际类型——Clang 的诊断通常比 GCC 更容易读，装个 Clang 用来读报错是常见做法。
3. 拆：把出问题的那行拆成两条语句，或者用中间变量把嵌套调用摊开（同时也能顺便看清 `auto` 推导成了什么，见第 03 篇的 type_name 技巧）。
4. 最小化：复制到一个 20 行的小文件里复现，往往复制过程中就找到问题了。
5. 确认标准版本：有一半"这个特性我不能用的案例"是因为默认方言是 C++14。

## 动手练

1. **跑通四阶段**：抄 1.2.1 的 `math.cpp` 与 `demo.cpp`，手工依次执行 `-E`、`-S`、`-c`、链接四条命令，最后用 `nm -C demo.o` 找出未定义符号，把它和链接报错里的名字对上。再试试把 `math.cpp` 里函数的签名改成 `int add(long, long)`，看 `-S` 出来的符号怎么变。
2. **搭 CMake 工程**：按 1.2.4 的目录结构建工程，要求：库用 `target_compile_features(... PUBLIC cxx_std_20)`；可执行文件链接它；用 Ninja 分组构建 Debug/Release 两个目录；加一个 `-DCPP_ASAN=ON` 的 sanitizer 开关并验证它生效（`ldd ./demo` 能看到对应的 runtime 库）。
3. **Hello World 三代对比**：在同一台机器上编译三个版本，记录哪一步失败、失败信息是什么（这决定了你以后能不能用 `std::println`）。然后给 `hello20.cpp` 故意写成 `std::format("{} {}\n", 1)`，看编译器报不报错。
4. **`main` 返回值实验**：写个程序：参数个数小于 2 时 `return EXIT_FAILURE`，否则正常返回。在 shell 里用 `./a.out; echo $?` 验证，再用 `if ./a.out arg; then echo ok; else echo bad; fi` 验证。
5. **跨 ABI 边界**：把 1.4.4 的 `plugin_if` 编译成一个动态库（`g++ -std=c++20 -fPIC -shared plugin_if.cpp -o libplugin.so`），再写一个只依赖 `plugin_if.h` 的纯 C 文件（`gcc main.c -L. -lplugin`）去调用它，体会"C 头文件 + C++ 实现"的边界怎么搭。

## 变式追问
{: .sec-think}

1. 你在头文件里写了一个 `int g_seed = 42;`，被两个 `.cpp` include，链接时报 `multiple definition of g_seed`。改成 `const int g_seed = 42;` 却编译通过了——为什么？再改成 `inline constexpr int g_seed = 42;` 呢？

   `const` 在命名空间作用域默认具有**内部链接**（和 `static` 一样），所以每个 TU 各持一份副本，链接器不抱怨。代价也很实在：两份副本不是同一个对象，跨 TU 传它的引用、取它的地址，行为会不符合你的预期，而且改一处另一处看不见。`inline constexpr`（C++17）才是正解：全程序唯一的同一份实体，还允许放在头文件里定义。这已经是现代 C++ 写"头文件常量"的标准姿势，`static const int kFoo = 1;` 那套可以退休了。

2. 同一个源文件，用 `-std=c++17` 编出来的 `.o` 和用 `-std=c++20` 编出来的 `.o`，能链到一起吗？

   同一个编译器、同一个标准库、同一套编译选项的情况下通常能（语言方言不是 ABI 边界）。但别依赖这件事：某些库类型的布局会被特性宏或调试宏改变（libstdc++ 的 `_GLIBCXX_USE_CXX11_ABI`、`_GLIBCXX_DEBUG`，MSVC 的 `_ITERATOR_DEBUG_LEVEL`、运行时 `/MT` vs `/MD`），也有些 C++20 特性（如 `[[no_unique_address]]`）会改变类布局。工程做法就一条：**整个二进制及其所有依赖，用同一个 toolchain + 同一个 `-std` + 同一套宏**，CI 里把这条锁死。

3. 为什么 `-O0` 编译出来的程序，在调试时发现"局部变量看不见"、执行流程和源码行对不上（乱跳）？

   `-O0` 下这两件事一般都不会发生，`-O2` 才会——所以先确认 `CMAKE_BUILD_TYPE`。如果确实在 `-O0` 下也对不上，通常是构建产物和源码不同步（改了代码没重新构建、多份同名可执行文件混了路径），或者调试的是 strip 过的二进制。GCC/Clang 下 Debug 通常还需要单独加 `-g`；MSVC 需要 `/Zi` 且 PDB 路径要对得上。

4. 你的同事说"把第三方依赖用 FetchContent 拉进来最省事，不用装 vcpkg"，在什么情况下这句话会变成坑？

   依赖超过一个、或者依赖本身又有子依赖时，FetchContent 会把所有源码拉进你的构建树：编译时间线性上涨，第三方项目的 `target_*` 设置会污染你的可见性（它们甚至可能覆盖 `CMAKE_CXX_STANDARD`），CI 每次冷构建下载量巨大，而且锁定版本只能靠 git hash 手动改。团队项目、多依赖、需要二进制复用和审计的场合，用包管理器。单文件工具、教学仓库、只有一个依赖时才用 FetchContent。
