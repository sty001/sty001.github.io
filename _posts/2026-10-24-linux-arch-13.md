Nginx 是生产环境里出镜率最高的 Web 服务。本篇从常见的网站服务软件讲起，覆盖 Nginx 的软件特点与异步 IO 原理、yum 与编译两种安装方式、目录结构、主配置文件逐块详解、虚拟主机与 location 匹配规则、root 与 alias、index 与 try_files、rewrite 重写、反向代理与动静分离、状态页监控，最后是日志管理与排错思路。

## 常见网站服务软件

网站服务软件按处理的资源类型分为两类：

| 资源类型 | 服务软件 | 说明 |
| --- | --- | --- |
| 静态资源 | Apache（apache.org） | 处理静态请求的 Web 服务软件 |
| 静态资源 | Nginx（nginx.org） | 处理静态请求，兼具多种功能 |
| 动态资源 | PHP（php.net） | 浏览器端直接访问 |
| 动态资源 | Tomcat（Java） | 可利用移动端查看网页，安卓使用 Java |
| 动态资源 | Python | 开发难度比较低 |

> **注意：** 动态资源脚本（PHP、Python 等）通常需要配合对应的解释器或应用服务器才能运行：PHP 通过 php-fpm 处理，Python 可通过 uWSGI、gunicorn 等接入，Java 应用则由 Tomcat 承载。Nginx 负责接收请求并转发，这一分工在 LNMP、LNMT 架构中体现得最明显。

## Nginx 的软件特点

1. 支持高并发，消耗内存资源少。
2. 具有多种功能：
   - 网站 Web 服务功能（相当于 Apache）；
   - 网站负载均衡功能（相当于 LVS）；
   - 网站缓存服务（相当于 Squid）。
3. 在多种系统平台都可以进行部署。
4. 实现网络通讯时使用的是异步网络 IO 模型：epoll 模型（Apache 使用 select 模型）：
   - epoll 模型：如同宿舍管理员找人时查看人员登记信息；小朋友上厕所时，都站在教室的某个位置，统一管理；
   - select 模型：如同宿舍管理员找人时要一个一个屋子去问（线性轮询）；幼儿园阿姨逐个询问上厕所的小朋友。

## 原理解析

### 异步 IO 模型：epoll 与 select 的区别

Nginx 高并发的根本原因在于采用了 epoll 异步事件驱动模型。两者的工作方式可以按下面的流程对比理解。

select 模型的处理流程：

1. 进程把需要监视的所有文件描述符（fd）集合交给内核；
2. 内核线性遍历整个集合，找出其中有数据就绪的 fd；
3. 进程再次遍历集合处理就绪的 fd，每次调用都要把 fd 集合从用户态完整拷贝到内核态；
4. 单进程可监视的 fd 数量受 FD_SETSIZE 限制（默认 1024），连接数增长后轮询开销呈线性上升。

epoll 模型的处理流程：

1. 进程通过 epoll_create 创建一个 epoll 对象，把 fd 注册进去，注册之后内核持续维护这些 fd 的状态；
2. 某个 fd 就绪时，内核通过回调机制把它加入就绪链表，无需全量遍历；
3. 进程调用 epoll_wait 时，内核只返回就绪链表中的 fd，处理效率与连接总数基本无关；
4. 可监视的 fd 数量不再受 1024 限制，只受系统文件描述符上限（ulimit）约束。

> **注意：** 这正是 Nginx 单机轻松支撑数万并发连接的原因：事件就绪时才处理，空闲连接不消耗 CPU。

再补一层白话：select 像值班员每隔一会儿把全楼 1024 个房间挨个敲门问一遍，就算只有 1 个房间有动静，另外 1023 次敲门也是白跑；epoll 像每个房间装了门铃，谁有事谁按铃，值班员只处理按铃的房间。说白了，select 是轮询，epoll 是回调，连接数上万时两者差距是数量级的。Apache 早期主流的 prefork 模式更重：每个连接独占一个进程，内存开销随连接数线性上涨，上万连接先把内存吃光；后来的 event MPM 也引入了事件机制，但进程/线程模型的历史包袱仍在，静态高并发场景 Nginx 优势明显。

worker 的主循环就一句话：epoll_wait 等事件，事件来了按类型处理（新连接 accept、可读收请求、可写发响应），处理完继续等。没有线程切换、没有锁竞争，这是它单核效率高的根本。补充一个并发细节：多个 worker 共同监听 80 端口，新连接到来时可能多个 worker 同时被唤醒、只有一个成功，这就是惊群；Nginx 用 accept_mutex（或新版的 reuseport）化解。理解这一点就明白 worker_processes 设太大反而增加唤醒竞争，这也是 1:1 核数的另一个理由。

### 反向代理工作原理

反向代理指客户端访问 Nginx，由 Nginx 把请求转发给后端服务器，再把后端的结果返回给客户端，客户端不直接接触后端。请求经过反向代理时的完整流程如下：

1. 客户端通过域名解析找到 Nginx 的地址，向 Nginx 发起 HTTP 请求；
2. Nginx 根据请求的 Host 与 URI，匹配 server_name 与 location 规则，确定处理方式；
3. 若该 location 配置了 proxy_pass 或 fastcgi_pass，Nginx 以客户端身份向后端服务器（Tomcat、PHP-FPM、Node 等）发起新的请求；
4. 后端应用执行业务逻辑（查询数据库、渲染页面等），把响应返回给 Nginx；
5. Nginx 对响应做缓存、压缩、添加响应头等加工，再返回给客户端；
6. 客户端全程感知不到后端的存在，后端真实地址与拓扑被隐藏。

这样做的好处：后端地址不外泄；便于横向扩展与负载均衡；Nginx 可以在入口统一做缓存、限流、压缩、SSL 卸载等加工。

### Nginx 进程模型

- master process（主进程）：管理服务是否能够正常运行，相当于 boss；
- worker process（工作进程）：处理用户的访问请求，相当于员工。

master 负责读取配置、绑定端口、管理 worker 的生命周期；worker 以普通用户身份运行，真正处理客户端连接。执行 nginx -s reload 时，master 会重新加载配置并启动新的 worker，旧 worker 处理完存量请求后平滑退出，因此 reload 不会中断线上服务。

## 安装部署

Nginx 有两种安装方式：yum 安装和编译安装。

### yum 安装

yum 安装又分两种来源：

- 使用官方 yum 源进行安装：安装的是最新版本，软件目录结构比较标准，推荐使用；
- 使用非官方 yum 源进行安装：安装的不是最新版本，目录结构会发生变化。

使用官方 yum 源安装的步骤如下。

第一步，更新 Nginx 官方 yum 源：

```bash
vim /etc/yum.repos.d/nginx.repo
```

写入以下内容：

```ini
[nginx-stable]
name=nginx stable repo
baseurl=http://nginx.org/packages/centos/$releasever/$basearch/
gpgcheck=1
enabled=1
gpgkey=https://nginx.org/keys/nginx_signing.key
```

第二步，安装 Nginx：

```bash
yum install -y nginx
```

第三步，启动 Nginx 服务并设置开机自启，然后测试访问：

```bash
systemctl start nginx
systemctl enable nginx
```

启动后通过浏览器访问服务器 IP，看到 Nginx 欢迎页面即表示服务安装正确。

> **注意：** 非官方 yum 源安装的版本偏旧、目录结构也会变化，生产环境建议使用官方源或编译安装。

### 编译安装

编译安装分三个步骤完成。

第一步，下载源码，并提前解决软件依赖（openssl-devel、pcre-devel）：

```bash
yum install -y gcc gcc-c++ make pcre-devel zlib-devel openssl-devel
wget http://nginx.org/download/nginx-1.16.0.tar.gz
```

三个依赖各管一摊：pcre 支撑 rewrite 的正则匹配，zlib 支撑 gzip 压缩，openssl 支撑 HTTPS。缺哪个，对应功能就算编译进去也是废的，装依赖是编译前的固定动作。

第二步，解压下载好的软件，并进入软件目录：

```bash
tar xf nginx-1.16.0.tar.gz
cd nginx-1.16.0
```

第三步，执行编译安装三步曲：

```bash
./configure --prefix=PATH --user=USER --group=GROUP
make
make install
```

`./configure` 的常用参数：

| 参数 | 作用 |
| --- | --- |
| --prefix=PATH | 指定程序安装路径 |
| --user=USER | 设置一个虚拟用户管理 worker 进程（安全） |
| --group=GROUP | 设置一个虚拟用户组管理 worker 进程（安全） |
| --with-http_ssl_module | 启用 HTTPS 支持（需 openssl-devel） |
| --with-http_stub_status_module | 启用状态页监控模块（stub_status） |
| --with-http_gzip_static_module | 支持直接发送预压缩的 .gz 静态文件 |
| --with-http_sub_module | 支持对响应内容做字符串替换 |
| --with-http_realip_module | 支持从代理头中还原真实客户端 IP |
| --with-http_v2_module | 启用 HTTP/2（1.25.1 之前版本需要，之后默认支持） |
| --with-stream | 启用 TCP/UDP 四层代理模块 |
| --with-pcre=PATH | 指定 PCRE 库路径，rewrite 功能依赖它（需 pcre-devel） |
| --with-pcre-jit | 启用正则 JIT 加速，提升 rewrite 匹配性能 |
| --with-threads | 启用线程池支持 |
| --with-file-aio | 启用文件异步 IO |

一个带常用模块的完整 configure 示例：

```bash
./configure --prefix=/usr/local/nginx --user=www --group=www \
--with-http_ssl_module --with-http_stub_status_module \
--with-http_gzip_static_module --with-pcre-jit
make && make install
```

其中 make 是编译（翻译）过程：C 语言代码需要 gcc 翻译成系统能识别的指令，翻译效率比较低；Python 代码由解释器直接处理，翻译效率比较高。make install 把编译好的程序安装到指定路径。

### 两种安装方式对比

| 对比项 | yum 安装 | 编译安装 |
| --- | --- | --- |
| 安装速度 | 快，自动解决依赖 | 慢，需要完整编译过程 |
| 版本选择 | 官方源版本较新，非官方源偏旧 | 可自由选择任意版本 |
| 目录结构 | 标准（/etc/nginx、/var/log/nginx） | 集中在 --prefix 指定目录下 |
| 模块定制 | 使用源内预编译模块 | 按需增减模块 |
| 升级维护 | yum update 即可 | 需要重新编译 |
| 适用场景 | 快速部署、生产常规环境 | 需要特定版本或定制模块 |

编译安装后的目录结构（以 --prefix=/usr/local/nginx 为例）：

| 路径 | 说明 |
| --- | --- |
| /usr/local/nginx/sbin/nginx | Nginx 主程序 |
| /usr/local/nginx/conf/nginx.conf | 主配置文件 |
| /usr/local/nginx/html | 站点目录 |
| /usr/local/nginx/logs | 日志与 pid 文件目录 |

> **注意：** 编译安装的 Nginx 没有 systemd 单元文件，可以自行编写 /usr/lib/systemd/system/nginx.service 来托管，或使用源码包中自带的 sysvinit 脚本。

编译安装的版本管理有套路：新版本装到另一个 --prefix 目录，改软链接切换，出问题一条 ln -s 就回滚；这也是很多老运维坚持编译安装的原因——版本与路径完全自己掌控。另外 1.9.11 起支持动态模块，编译时用 --add-dynamic-module 生成 .so，配置里 load_module 加载，换模块不必重装整个 Nginx。

## 目录结构

yum 安装后，Nginx 的重要目录如下：

| 路径 | 说明 |
| --- | --- |
| /etc/nginx | 配置文件目录（主配置为 nginx.conf） |
| /etc/nginx/conf.d | 扩展配置目录，存放虚拟主机（server）配置 |
| /etc/nginx/mime.types | MIME 类型映射配置文件 |
| /var/log/nginx | 日志文件目录 |
| /usr/bin/nginx | Nginx 命令文件 |
| /usr/share/nginx/html | 站点目录，存放图片、附件信息、音频、视频等 |
| /etc/logrotate.d | 日志切割配置目录 |

mime.types 决定浏览器怎么对待文件：.css 返回 text/css 就当样式渲染，返回 text/plain 就当纯文本。页面样式全丢的第一嫌疑人就是它——mime.types 没被 include 或被改坏。pid 文件记录 master 进程号，日志切割、监控脚本都靠 kill -USR1 加 cat pid 文件这类操作引用它，误删不影响运行，重启后会重新生成。

站点目录中常见的前端文件：html 是页面代码，css 定义页面样式，js 定义页面特效功能。

## 主配置文件 nginx.conf

主配置文件 /etc/nginx/nginx.conf 分为三个部分：全局配置区、events 事件区和 http 区。http 区通过 include 指令加载 conf.d 目录下的扩展配置（虚拟主机配置）。

Nginx 的进程模型：

- master process（主进程）：管理服务是否能够正常运行，相当于 boss；
- worker process（工作进程）：处理用户的访问请求，相当于员工。

默认的主配置文件内容如下：

```nginx
user  www;                                # 定义 worker 进程管理的用户
worker_processes  2;                      # 定义有几个 worker 进程，建议为 CPU 核数或核数的 2 倍
error_log  /var/log/nginx/error.log warn; # 定义错误日志路径与级别
pid        /var/run/nginx.pid;            # 定义 pid 文件路径

events {
    worker_connections  1024;             # 一个 worker 进程可以同时接收 1024 个访问请求
}

http {
    include       /etc/nginx/mime.types;      # 加载 mime.types 配置文件
    default_type  application/octet-stream;   # 指定默认识别的文件类型
    log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
                      '$status $body_bytes_sent "$http_referer" '
                      '"$http_user_agent" "$http_x_forwarded_for"';   # 定义日志的格式
    access_log  /var/log/nginx/access.log  main;   # 指定访问日志路径与所用格式
    sendfile        on;         # 开启零拷贝，提高文件传输效率
    #tcp_nopush     on;         # 配合 sendfile 使用，减少报文段数量
    keepalive_timeout  65;      # 长连接超时时间（秒）
    #gzip  on;                  # 是否对传输内容进行压缩
    include /etc/nginx/conf.d/*.conf;   # 加载 conf.d 目录下的扩展配置
}
```

### 配置文件逐块详解

| 区域 | 典型指令 | 作用 |
| --- | --- | --- |
| 全局块（main 上下文） | user、worker_processes、error_log、pid | 影响 Nginx 全局运行参数，与具体业务无关 |
| events 块 | worker_connections、use、multi_accept | 配置事件驱动与连接处理能力 |
| http 块 | include、default_type、log_format、access_log、sendfile、keepalive_timeout、gzip | 配置 HTTP 服务相关参数，使用最频繁 |
| server 块（http 内） | listen、server_name、root、index、location | 一个 server 就是一个虚拟主机（网站） |
| location 块（server 内） | root、alias、index、try_files、proxy_pass | 对匹配的 URI 应用具体配置 |

### worker_processes 与 worker_connections

| 指令 | 说明 | 建议 |
| --- | --- | --- |
| worker_processes | 启动的 worker 进程数 | 设为 auto，与 CPU 核数一致；也可设为核数的 2 倍 |
| worker_connections | 单个 worker 的最大连接数 | 默认 1024，生产建议 10240 或更高 |
| worker_rlimit_nofile | worker 进程文件描述符上限 | 与 worker_connections 同步调大，避免 too many open files |

Nginx 能支撑的总并发连接数约等于 `worker_processes × worker_connections`。作为反向代理时，每个客户端请求会同时占用客户端侧与后端侧两条连接，估算上限时要按一半折算。调整 worker_connections 时记得同步提升系统的文件描述符限制，否则配置无法真正生效。

worker_processes 设为 CPU 核数为什么最合适？worker 是单线程进程，核数一致时每个 worker 独占一个核心，进程切换最少；盲目设成核数的 4 倍、8 倍，多出来的进程只会互相抢核，上下文切换的开销反而拉高延迟。IO 等待多的场景（大量反向代理）可以放到 2 倍，纯静态服务 1:1 就够。生产上直接写 auto 最省心，Nginx 自己探测核数；要精细控制还可以用 worker_cpu_affinity 把 worker 绑到固定核，减少缓存失效。

### 配置检查与服务管理

修改配置后，先测试语法再平滑重载：

| 命令 | 作用 |
| --- | --- |
| nginx -t | 检查测试配置文件语法（test configuration and exit） |
| nginx -s reload | 平滑重载配置，不中断正在处理的请求 |
| nginx -s stop | 快速停止服务 |
| nginx -s quit | 优雅停止，处理完当前请求后退出 |
| nginx -s reopen | 重新打开日志文件（配合日志切割使用） |
| systemctl reload nginx | 等价于 nginx -s reload |
| systemctl restart nginx | 完全重启服务 |

## 虚拟主机配置

http 区加载的扩展配置（/etc/nginx/conf.d/ 目录下的文件，如 default.conf）用于配置虚拟主机：每个 server 块就是一个网站（虚拟主机），通过不同端口或域名，可以在一台服务器上搭建 www、bbs、blog 等多个站点。

默认的虚拟主机配置如下：

```nginx
server {
    listen       8080;                          # 指定监听的端口
    server_name  www.example.com;               # 指定网站域名
    root   /usr/share/nginx/html;               # 定义站点目录的位置
    index  index.html index.htm;                # 定义首页文件
    error_page   500 502 503 504  /50x.html;    # 出错时优雅显示指定页面
    location = /50x.html {
        root   /usr/share/nginx/html;
    }
}
```

主要指令说明：

- listen：指定监听的端口；
- server_name：指定网站域名，同一端口下通过域名区分不同站点；
- root：定义站点目录的位置；
- index：定义首页文件；
- error_page：指定 500、502、503、504 等状态码出错时优雅显示的页面。

> **注意：** 同一端口配置多个 server 时，如果请求的 Host 与所有 server_name 都不匹配，默认使用该端口的第一个 server 处理。

default_server 建议显式声明：listen 80 default_server; 加一个匹配不到就返回 444 或 404 的兜底站点。公网机器尤其要做，否则别人把任意域名 A 记录指向你的 IP，请求会直接命中业务站，流量与备案风险都算你头上。

server_name 的匹配规则按优先级从高到低为：精确匹配、通配符开头匹配（如 `*.example.com`）、通配符结尾匹配（如 `www.*`）、正则匹配。都未命中时使用该端口的 default server（第一个 server 块），因此建议把默认站点显式声明为 `default_server`。

## location 匹配规则

location 用于对不同的请求路径应用不同的配置，匹配符与优先级如下：

| 匹配符 | 匹配类型 | 说明 | 示例 |
| --- | --- | --- | --- |
| `=` | 精确匹配 | 严格等于指定路径才命中，优先级最高 | `location = /50x.html` |
| `^~` | 前缀匹配 | 以指定字符串开头即命中，且不再进行正则匹配 | `location ^~ /images/` |
| `~` | 正则匹配 | 区分大小写的正则匹配 | `location ~ \.php$` |
| `~*` | 正则匹配 | 不区分大小写的正则匹配 | `location ~* \.(jpg\|png)$` |
| 无 | 普通前缀匹配 | 以指定字符串开头即命中 | `location /` |

匹配顺序：先检查精确匹配（`=`），再检查前缀匹配（`^~`），然后检查正则匹配（`~`、`~*`），最后使用普通前缀匹配。

多个普通前缀匹配同时命中时，取最长的那个；多个正则匹配同时命中时，按书写顺序取第一个。理解这条顺序是排查"配置了却不生效"类问题的关键。

敲一遍就明白：写一个 `location /`、一个 `location ~ \.php$`，请求 /test.php 时命中的是正则那条，哪怕普通前缀写得更具体。记住一句话——正则是特权阶级，普通前缀再长也要让路，除非前缀带 `^~`。另外注意 location 匹配的是路径、不含查询参数：/search?q=nginx 匹配的是 /search，想按参数分流要用 if 与 $arg_ 系列，或交给应用层。try_files 是磁盘检查，按顺序 stat 文件，候选档位写太多会放大磁盘 IO，两三个加一个回退足够。

### root 与 alias

root 与 alias 都用于指定文件路径，行为完全不同：

| 指令 | 路径拼接方式 | 使用位置 |
| --- | --- | --- |
| root | 把 location 匹配的 URI 拼接到 root 路径之后 | server、location、http |
| alias | 用 alias 路径替换 location 匹配的 URI 部分 | 仅 location |

```nginx
# 访问 /images/logo.jpg，实际文件为 /data/images/logo.jpg
location /images/ {
    root  /data;
}

# 访问 /images/logo.jpg，实际文件为 /data/pics/logo.jpg
location /images/ {
    alias  /data/pics/;
}
```

> **注意：** alias 只能用在 location 中，且路径结尾要与 location 保持一致（带斜杠或不带），否则容易出现 404 或路径拼错。

这里有个坑：生产上栽过的案例是站点迁移后图片全挂，排查半天发现 alias 少了个 `/`。alias 与 try_files 组合时 $uri 的拼接行为也和直觉不一致，容易拼出重复路径，这类场景多数人最终改回 root。root 写在 server 块时会被所有 location 继承，某个 location 忘了写路径时，文件到底从哪读要顺着继承链找，用 namei -l 逐层查路径比肉眼猜快得多。

### index 与 try_files

index 定义请求目录时默认返回的文件，多个文件名按顺序尝试：

```nginx
location / {
    root  /usr/share/nginx/html;
    index index.html index.htm;
}
```

try_files 按顺序检查文件是否存在，全部不存在时执行最后一个参数（回退地址），常用于单页应用与伪静态：

```nginx
location / {
    root  /usr/share/nginx/html;
    try_files $uri $uri/ /index.html;
}
```

上述配置的含义：先尝试把 URI 当作文件，再尝试当作目录，都不存在时返回 /index.html，由前端路由处理。

## rewrite 重写与跳转

rewrite 指令用于重写请求的 URL 地址，语法为：

```nginx
rewrite 正则表达式  替换目标  flag;
```

flag 决定重写后的行为：

| flag | 效果 |
| --- | --- |
| last | 停止执行后续 rewrite 指令，用替换后的 URI 重新匹配 location |
| break | 停止执行后续 rewrite 指令，直接使用当前 location 处理 |
| redirect | 返回 302 临时重定向 |
| permanent | 返回 301 永久重定向 |

示例：把 /old/ 开头的地址跳转到 /new/ 下的对应路径。

```nginx
rewrite ^/old/(.*)$ /new/$1 permanent;
```

rewrite 依赖 PCRE 库，匹配时可以使用正则捕获，通过 $1、$2 引用捕获组，更多进阶用法见《Nginx 网站服务进阶》中 rewrite 与正则一节。

生产里最常见的两种用法：域名统一（example.com 301 到 www.example.com）用 permanent，搜索引擎权重才能合并；HTTP 强制跳 HTTPS 用 return 301 更高效。rewrite 主要留给伪静态这类需要正则捕获的场景。

## 反向代理

反向代理指客户端访问 Nginx，由 Nginx 把请求转发给后端服务器，再把后端的结果返回给客户端，客户端不直接接触后端。这样可以隐藏后端真实地址，也便于统一接入与后续扩展负载均衡。

顺带分清正向代理与反向代理：正向代理站在客户端一侧，替客户端出门访问，服务端不知道真实客户端是谁；反向代理站在服务端一侧，替服务端接待，客户端不知道真实服务端是谁。名字里的正反，看它代理的是谁。对外暴露的 Server: nginx/1.24.0 顺带暴露了版本号，低版本有已知漏洞时等于给扫描器递清单，server_tokens off; 把版本藏起来，再配合自定义错误页，信息泄露面小得多。

```nginx
location / {
    proxy_pass http://127.0.0.1:8080;                          # 转发到后端服务
    proxy_set_header Host $host;                               # 向后端传递原始 Host
    proxy_set_header X-Real-IP $remote_addr;                   # 传递真实客户端 IP
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;  # 记录代理链
}
```

> **注意：** 日志格式中的 $http_x_forwarded_for 即来自 X-Forwarded-For 首部；经过多级代理时，该首部会记录完整的代理链。

## 动静分离

动静分离指把静态资源与动态资源的请求分开处理：静态资源（HTML、图片、CSS、JS 等）由 Nginx 直接从站点目录返回，效率高；动态请求转发给后端的 PHP、Python、Java 应用处理，由应用连接数据库、查询解析后再返回结果（LNMP 即 Linux + Nginx + MySQL + PHP 的经典组合）。

静态 location 里配 expires 7d，浏览器 7 天内直接用本地缓存不发请求；文件更新靠改名（带 hash 的文件名）而不是等缓存过期，这是前端工程的通行做法，Nginx 侧把 expires 配好就行。

```nginx
# 静态资源：由 Nginx 直接处理
location / {
    root   /usr/share/nginx/html;
    index  index.html index.htm;
}

# 动态请求：转发给后端应用处理
location ~ \.php$ {
    proxy_pass http://127.0.0.1:9000;
}
```

## 日志管理

Nginx 的日志分为两类：

- access_log：访问日志，记录每一个请求，默认路径为 /var/log/nginx/access.log；
- error_log：错误日志，记录服务运行错误，默认路径为 /var/log/nginx/error.log。

日志的格式与路径在主配置文件的 http 区中定义。

### 日志格式字段

log_format 定义的格式中，各变量含义如下：

| 变量 | 含义 |
| --- | --- |
| $remote_addr | 客户端 IP 地址 |
| $remote_user | 远程用户 |
| $time_local | 本地时间 |
| $request | 请求行（请求方法、URI、协议版本） |
| $status | 响应状态码 |
| $body_bytes_sent | 响应体大小 |
| $http_referer | 来源页面 |
| $http_user_agent | 客户端浏览器信息 |
| $http_x_forwarded_for | 经过代理后的真实客户端 IP |

### 日志分析

统计 IP 与页面访问量，可以基于 access.log 结合 awk、sort、uniq 实现：

```bash
# 统计访问来源 IP 前 10 名
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10

# 统计被访问页面次数前 10 名
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
```

可进一步结合 IP 归属地统计各地访问量，例如按来源统计：北京 192.168.10.1、192.168.11.2，深圳 192.169.11.1，上海 192.170.12.1 等。

### 日志切割

方式一：利用脚本实现切割。

```bash
#!/bin/bash

mv /var/log/nginx/access.log  /var/log/nginx/access_$(date +%F).log
systemctl restart nginx
```

方式二：利用专用文件切割程序 logrotate，其默认配置 /etc/logrotate.conf 如下：

```conf
# rotate log files weekly
weekly                     # 定义默认日志切割的周期

# keep 4 weeks worth of backlogs
rotate 4                   # 定义只保留几个切割后的文件

# create new (empty) log files after rotating old ones
create                     # 创建出一个相同的源文件

# use date as a suffix of the rotated file
dateext                    # 用日期作为切割后文件的后缀

# uncomment this if you want your log files compressed
#compress                  # 是否对切割后的文件进行压缩处理

# RPM packages drop log rotation information into this directory
include /etc/logrotate.d   # 加载 /etc/logrotate.d/ 目录中的文件配置

# no packages own wtmp and btmp -- we'll rotate them here
/var/log/wtmp {            # 单独对某个文件进行切割配置
    monthly
    create 0664 root utmp
    minsize 1M             # 最小大小为 1M，小于 1M 不进行切割
    rotate 1
}

/var/log/btmp {
    missingok
    monthly
    create 0600 root utmp
    rotate 1
}
```

> **注意：** 用脚本 mv 后重启 Nginx 的方式会短暂中断服务，生产中更推荐 logrotate 配合 `nginx -s reopen`（USR1 信号）实现无中断切割。

## 状态页监控（stub_status）

编译安装 Nginx 时若需要状态页，configure 要加上 `--with-http_stub_status_module`；yum 官方源默认已内置该模块。配置如下：

```nginx
server {
    listen        80;
    server_name  status.example.com;

    location = /basic_status {
        stub_status;
        allow  127.0.0.1;
        allow  10.0.0.0/24;
        deny   all;
    }
}
```

访问该页面会输出当前连接与请求统计，各字段含义在《Nginx 网站服务实战》中有详细表格说明。状态页会暴露连接数等内部信息，务必配置 allow/deny 访问控制，不要对公网开放。状态页是累计值，看趋势要取差值：两次采样相减除以间隔秒数，得到每秒新建连接与每秒请求数，监控脚本的核心就这一行减法。

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 页面返回 403 | worker 用户对站点目录无读取权限；或目录下没有 index 文件且未开启 autoindex | `ls -ld /html/www`、`namei -l /html/www/index.html`、`tail /var/log/nginx/error.log` | 修正目录权限（chmod/chown），或补齐首页文件 |
| 页面返回 404 | root 与 index 配置和文件实际位置不一致；location 写错 | `ls -lR /html/www`、`curl -I http://localhost/` | 对照实际路径修正 root/location 配置 |
| 服务无法启动 | 配置语法错误；端口被占用 | `nginx -t`、`ss -lntp \| grep 8080`、`tail /var/log/nginx/error.log` | 按 nginx -t 提示修正配置；更换端口或释放占用进程 |
| 修改配置不生效 | 忘记重载服务 | `systemctl status nginx` | 执行 `nginx -t && systemctl reload nginx` |
| 反向代理返回 502 | 后端服务未启动或监听地址不对 | `systemctl status <backend>`、`ss -lntp`、`curl 127.0.0.1:8080` | 启动后端，核对 proxy_pass/fastcgi_pass 地址 |
| 并发上不去 | worker_connections 过小或文件描述符受限 | `ulimit -n`、`cat /var/log/nginx/error.log` | 调大 worker_connections 与 worker_rlimit_nofile |

常用检查命令：

```console
# 修改配置后先测试语法，确认无误再平滑重载
nginx -t
systemctl reload nginx

# 服务异常时查看运行状态与错误日志
systemctl status nginx
tail -f /var/log/nginx/error.log

# 检查监听端口是否被占用
ss -lntp | grep 8080
```

ab 压测时留意两个数：Failed requests 里 Non-2xx responses 的数量，压出 5xx 说明并发已经越过服务承受线；Requests per second 只是相对值，同机自测的结果不能直接当容量规划用——常见的坑就是拿本机压测值去承诺线上容量，真实网络环境一进来就被打回原形。

常见问题与排查思路：

- 页面返回 403：多为站点目录权限问题，确认 worker 进程用户（www）对 root 目录有读取权限；
- 页面返回 404：检查 root 与 index 配置是否和文件的实际位置一致；
- 服务无法启动：查看 error_log，并用 nginx -t 定位配置语法错误；
- 端口冲突：用 ss -lntp 查看端口被哪个进程占用；
- 性能评估：使用 ab 等工具进行压力测试，评估网站的并发处理能力。

补两个排错心法：nginx -t 通过只代表语法合法，不代表行为正确，路径拼错、正则写反这些逻辑问题照样过检，最终要靠访问验证兜底；性能问题的排查顺序是先看状态页和系统资源（CPU、内存、IO、fd），再动配置参数，顺序反了容易白忙。日志里会记录 Cookie 与请求参数，敏感信息直接落盘，日志的访问权限与保留期限要按数据规范管理。

## 现代环境补充

CentOS 7 已于 2024 年 6 月停止维护，新系统建议使用 Rocky Linux、AlmaLinux 或 CentOS Stream。Nginx 部署的对应做法如下。

| 旧（CentOS 6） | 新（Rocky/Alma/CentOS 7+） | 说明 |
| --- | --- | --- |
| `yum install nginx` | `dnf install nginx`（yum 仍可用，是 dnf 的软链接） | 包管理器换代 |
| `service nginx start` | `systemctl start nginx` | service 命令已废弃，建议用 systemctl |
| `chkconfig nginx on` | `systemctl enable nginx` | 开机自启统一由 systemd 管理 |
| `netstat -lntp` | `ss -lntp` | netstat 已废弃，由 ss 取代 |
| `ifconfig` | `ip addr` | ifconfig 已废弃，由 iproute2 取代 |
| `iptables -A INPUT -p tcp --dport 80 -j ACCEPT` | `firewall-cmd --add-service=http --permanent` | 防火墙由 firewalld/nftables 管理 |
| `/etc/init.d/nginx` | systemd 单元 `nginx.service` | init.d 脚本已废弃 |

其他要点：

- nginx.org 官方源对 Rocky Linux、AlmaLinux 同样适用：仓库中提供 centos/7、centos/8、centos/9 目录，`$releasever` 会自动对应，也可以把 baseurl 改成 `rhel/9/$basearch/`；
- 官方源本身也有 EPEL 内的 nginx 包，版本略旧但兼容性好；
- Rocky/Alma 上源码编译的依赖安装为 `dnf install -y gcc gcc-c++ make pcre-devel zlib-devel openssl-devel`；
- 日志切割仍由 logrotate 托管，配置文件在 /etc/logrotate.d/nginx。

## 小结

1. Nginx 支持高并发、内存占用少，兼具 Web 服务、负载均衡与缓存能力，网络通讯采用 epoll 异步 IO 模型。
2. 安装推荐 yum 官方源（版本新、目录结构标准）；编译安装需先解决 openssl-devel、pcre-devel 依赖。
3. 主配置文件分全局、events、http 三个区域，虚拟主机（server 块）配置在 conf.d 目录中维护。
4. location 匹配优先级：精确匹配 > 前缀匹配 > 正则匹配；rewrite 可实现 URL 重写与 301/302 跳转。
5. 动静分离让 Nginx 直接返回静态资源，动态请求通过反向代理交给后端处理。
6. 日志可用 logrotate 或脚本切割；排错先看 error_log，修改配置后务必先 nginx -t 再重载。
7. root 与 alias 路径拼接方式不同，try_files 是单页应用与伪静态的常用手段。
8. stub_status 状态页是日常巡检利器，但必须限制访问来源。

5. 修改了 nginx.conf，执行哪两条命令可以安全地让配置生效且不中断线上请求？

> **答案：**
> 1. Nginx 采用 epoll 异步事件驱动模型，只处理就绪的事件，空闲连接不消耗 CPU，且单进程可监视的 fd 数量远超 select 的 1024 限制；Apache 默认使用 select 模型，需要线性轮询所有连接。
> 2. 优先级为：精确匹配（`=`）> 优先前缀（`^~`）> 正则（`~`/`~*`）> 普通前缀。多个普通前缀同时命中时，匹配路径最长的那一个；多个正则同时命中时，取书写顺序最靠前的一个。
> 3. alias 是替换：location 匹配的 `/images/` 被替换为 `/data/pics`，实际路径为 /data/pics/logo.jpg（注意 alias 结尾斜杠要与 location 一致，否则可能拼出 /data/picslogo.jpg）。若改用 root 则是拼接：/data/pics/images/logo.jpg。
> 4. 理论上限约为 4 × 1024 = 4096 条连接。作为反向代理时每个客户端请求要同时占用客户端侧与后端侧两条连接，实际可用上限约 2000，生产应调大 worker_connections 与 worker_rlimit_nofile。
> 5. 先执行 `nginx -t` 测试配置语法，确认无误后执行 `systemctl reload nginx`（或 `nginx -s reload`）平滑重载。
