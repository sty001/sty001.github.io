上一篇装好了 Zabbix Server 与 Agent。本篇接着监控第一台主机，完成自定义监控项、触发器、动作与告警媒介配置，覆盖页面提示、声音、邮件、微信、短信/电话五种告警方式；后半部分讲解 UserParameter 原理、主动与被动的区别、自动发现、聚合监控、图形仪表盘、报表、权限管理与日常维护。命令与配置可直接复用。

## 一、监控第一台主机

部署完成后，第一件事是把被监控主机添加到 Zabbix 中：

1. 配置 → 主机 → 创建主机
2. 填写主机信息：名称、主机组、被监控主机的地址
3. 在模板信息中指定需要链接的模板
4. 保存退出，检查主机图标有没有变绿
5. 通过 监测 → 最新数据 查看采集到的监控信息

主机名一旦确定就不要随意改：模板联动、触发器引用、主动模式的上报都以主机名为锚点，改名等于新建一台主机。

> **注意：** 主机图标变绿才表示 Zabbix Server 与 Agent 通信正常。如果长时间不变绿，先检查 Agent 配置文件中 Server 地址是否正确、10050 端口是否处于监听状态。

另外别太心急：模板里几十个监控项要按各自的采集间隔排队，新主机创建后 5-10 分钟才全部有数据属正常现象，等一个采集周期再判断。

## 二、核心概念速查

| 概念 | 作用 |
| --- | --- |
| 主机 | 被监控的对象，需配置名称、主机组与监控地址 |
| 主机组 | 对主机进行分类管理 |
| 模板 | 将监控项、触发器、图形集中配置在模板中，方便多台主机调用 |
| 监控项 | 自定义收集主机信息的条目，由键值和更新间隔等组成 |
| 应用集 | 将多个类似的监控项进行整合，便于查看检查（聚合监控） |
| 触发器 | 通过条件表达式实现报警提示，默认在页面提示报警 |
| 动作 | 指定报警信息发送给谁、定义报警的信息、定义报警的类型（邮件、微信、短信、电话） |
| 报警媒介 | 定义报警的方式 |
| 图形 | 将多个图整合成一张，便于分析数据 |
| 事件 | 触发器状态变化（故障发生或恢复）时产生的记录 |
| 问题 | 尚未恢复的故障，是运维处理告警的入口 |
| 维护 | 计划停机期间抑制告警的时间窗口，避免变更引发骚扰 |

宏（macro）的完整列表参考 Zabbix 官方文档中相关手册章节。

维护窗口要提前建：变更开始前把目标主机放进维护期，结束后确认退出并回看变更期间有没有真问题被抑制掉。养成这个习惯，告警才会一直被认真对待。

Web 界面常用路径速查：

| 目的 | 界面路径 |
| --- | --- |
| 查看最新数据 | 监测 → 最新数据 |
| 查看图形 | 监测 → 图形 |
| 查看告警 | 监测 → 问题 |
| 创建主机 | 配置 → 主机 |
| 创建监控项 | 配置 → 主机 → 监控项 |
| 创建触发器 | 配置 → 主机 → 触发器 |
| 配置动作 | 配置 → 动作 |
| 配置报警媒介 | 管理 → 报警媒介类型 |
| 权限管理 | 管理 → 用户组 / 用户 |
| 日常维护 | 管理 → 一般 → Housekeeping |

这些路径在 Zabbix 6.0 的新界面里有变化（"配置"迁入"数据收集"），概念不变，按新界面找对应菜单即可。

> **注意：** 应用集（application）的本质是"分类标签"，只影响监控项在界面上的归类展示；真正对多台机器的数据做汇总计算，需要使用类型为 aggregate 的聚合监控项（详见第七章）。二者不要混淆。

## 三、原理解析：Agent 采集数据的工作机制

自定义监控之前，先理解 agent 是如何执行一条 key 的：

1. server（或 agent 自身，主动模式）携带 key 与参数发起请求，如 server_state[nginx]。
2. agentd 收到请求后，在自身配置与 Include 目录（默认 /etc/zabbix/zabbix_agentd.d/*.conf）中查找匹配的 UserParameter 定义。
3. 若命中，agent 把 key 中的参数按位置替换进命令模板（[*] 中的第 1 个参数对应 $1），并通过 /bin/sh -c 执行该命令。
4. agent 捕获命令的标准输出（首行）与退出码：退出码为 0 表示执行成功，输出值即采集结果；退出码非 0 或超时（默认 3 秒，可由 Timeout 调整）则记为采集失败。
5. agent 将结果返回给请求方，server 写入数据库并按触发器判定是否产生告警。

由此可知三个结论：UserParameter 的命令必须短小、快速（执行慢会拖累采集周期）；命令输出决定监控值，所以 echo 返回的内容要干净可解析；agent 以 zabbix 用户身份运行，命令能否执行受文件权限与命令路径限制。

取值命令怎么写才不拖慢 agent，几条实打实的准则：

1. 别在采集命令里做重活：curl 外部接口、ssh 到别的机器、全表扫描数据库这类操作，单次几百毫秒到几秒，采集一多 poller 直接排队。
2. 耗时计算离线化：让 crond 每 N 分钟把结果算好写到临时文件，UserParameter 的命令只 cat 文件，agent 零等待。
3. 更新间隔必须大于命令最坏耗时：命令要 2 秒就把间隔设到 10 秒以上，Timeout 也要留出余量，否则采集状态永远 Not supported。
4. 结果输出一行、纯数值或固定格式，别把多行日志直接吐给监控项，解析交给触发器的 str()/regexp() 或预处理。

除自定义 key 外，Zabbix agent 自带大量内置 key，覆盖常见监控对象，能用内置 key 就不必自己写命令：

| key | 采集内容 |
| --- | --- |
| agent.ping | 探测 agent 是否可达，返回 1 或 0，是主机可用性监控的标配 |
| system.cpu.load[percpu,avg1] | 1 分钟平均负载 |
| vm.memory.size[pused] | 物理内存使用率（百分比） |
| vfs.fs.size[/,pfree] | 指定挂载点剩余空间百分比 |
| vfs.fs.inode[/,pfree] | 指定挂载点 inode 剩余百分比，小文件多的服务器必看 |
| net.if.in[eth0] / net.if.out[eth0] | 网卡入向 / 出向流量 |
| net.tcp.service[ssh,127.0.0.1] | 探测本机 TCP 端口服务是否正常 |
| proc.num[nginx] | 匹配指定条件的进程数量 |
| system.uname | 系统名称与内核版本 |
| web.page.get[http://localhost/,200] | 抓取页面并校验返回码，用于网站拨测 |

agent.ping 看似简单却最该配：给它配一个 nodata(3m) 触发器，agent 失联比任何单项指标异常都暴露得早，这是所有主机的保底监控项。

内置 key 的完整清单可查阅 Zabbix 官方文档的 agent 监控项一节。

## 四、自定义监控项与 UserParameter

### 4.1 简单自定义监控：监控 nginx 是否启动

需求：监控 nginx 服务是否启动。

#### Agent 端配置

第一个步骤，编写自定义监控命令：

```bash
ps -ef|grep -c [n]ginx
```

第二个步骤，编写 Zabbix Agent 配置文件。有两种方法：

方法一：直接修改 Agent 配置文件中的参数：

```ini
UserParameter=web_state,ps -ef|grep -c [n]ginx
```

方法二：在 `/etc/zabbix/zabbix_agentd.d/` 目录中编写自定义监控文件（推荐，便于分类管理）：

```bash
vim /etc/zabbix/zabbix_agentd.d/web_server.conf
```

```ini
UserParameter=键名,命令
UserParameter=web_state,ps -ef|grep -c [n]ginx
```

第三个步骤，重启 Zabbix Agent 服务：

```bash
systemctl restart zabbix-agent
```

#### Server 端验证

```bash
yum install -y zabbix-get
zabbix_get  -s 172.16.1.7 -k 'web_state'
```

#### Web 端配置

1. 进入到创建监控项页面：配置 → 主机 → 选择相应主机的监控项
2. 创建监控项，填写名称、键值、更新间隔时间、应用集
3. 检查是否收集到监控信息

### 4.2 UserParameter 格式与权限详解

UserParameter 的完整格式为：

```text
UserParameter=key[*],command
```

要点说明：

| 项目 | 说明 |
| --- | --- |
| key 命名 | 使用字母、数字、下划线、连字符；不允许与 agent 内置 key 重名 |
| 位置参数 | key 写作 key[*] 表示接收参数，调用时传入的第 1 个参数在命令中写作 $1，最多支持 $1 至 $9 |
| 特殊符号 | 命令中的 `$` 若表示字面量需转义为 `$$`；key 名中的 `.` 等符号有限制，命名越简单越安全 |
| 执行方式 | 命令由 agent 通过 /bin/sh -c 执行，因此管道、重定向可用（如 web_state 的写法） |
| 建议写法 | 复杂逻辑封装为独立脚本，UserParameter 只写脚本路径，避免转义与可读性问题 |
| 执行权限 | agent 默认以 zabbix 用户运行，脚本必须对该用户可读可执行（chmod +x），输出文件目录也要对 zabbix 用户可写 |
| root 场景 | 若命令必须 root 执行，需为 zabbix 用户配置 sudoers 白名单，或改用其他采集方式，切勿直接给 agent 提权 |
| 生效条件 | 修改 UserParameter 后必须重启 zabbix-agent；配置文件放入 zabbix_agentd.d/ 目录同样生效 |
| 超时 | 单条命令执行超时由 agent 配置的 Timeout 控制（默认 3 秒），命令逻辑不要依赖长耗时操作 |

调试技巧：在 agent 本机执行 `zabbix_agentd -t "key[参数]"` 可以直接测试 UserParameter 的返回值与报错，比从 server 端用 zabbix_get 更快定位问题出在 agent 侧还是 server 侧。该命令以 agent 的身份执行采集命令，会输出执行结果或错误信息，是排查自定义 key 取不到值的第一工具。这里有个坑：改了 UserParameter 忘了重启 agent，zabbix_get 会返回 ZBX_NOTSUPPORTED——先重启再排查，能省十分钟。

### 4.3 复杂自定义监控：多个服务状态

第一个步骤，在 Agent 端编写配置文件：

```bash
vim /etc/zabbix/zabbix_agentd.d/server_state.conf
```

```ini
UserParameter=server_state[*],netstat -lntup|grep -c $1
```

其中 `[*]` 表示该键值接收参数，`$1` 为调用时传入的第一个参数。

第二个步骤，在 Server 端测试：

```console
zabbix_get  -s 172.16.1.7 -k 'server_state[22]'
```

第三个步骤，修改配置页面，Web 端监控项的键值填写：

```ini
server_state[22]
```

> **注意：** 上面的示例中 netstat 已废弃，现代系统建议改写为 `UserParameter=server_state[*],ss -lntup|grep -c $1`。带参数的 key 在 Web 端填写时必须带上方括号与参数，如 server_state[nginx]，漏写方括号是取不到值的高频原因。

这类 grep -c 统计型命令还有个暗坑：匹配不到时输出 0 且退出码为 1，agent 会判定采集失败而不是返回 0；命令末尾补上 `|| true`，或改用 awk 统计，都能避开。

### 4.4 更多自定义监控示例

以下三个示例覆盖日常最高频的三种写法。

示例一：统计根分区使用率（无参数，直接返回数值）。

```ini
UserParameter=disk_root_used,df / | awk '/\/$/{gsub(/%/,"");print $5}'
```

示例二：带两个参数，监控指定 IP 的指定端口（参数依次对应 $1、$2）。

```ini
UserParameter=port_check[*],ss -lnt | grep -c "$1:$2"
```

Web 端监控项键值填写 port_check[10.0.0.7,80]，即可监控 web01 的 80 端口。

示例三：逻辑较复杂时封装为脚本，UserParameter 只负责调用。

```bash
#!/bin/bash
# /server/scripts/check_nginx_conn.sh 统计 nginx 的 80 端口连接数
ss -tan | grep -c ':80 '
```

```ini
UserParameter=nginx_active_conn,/server/scripts/check_nginx_conn.sh
```

脚本编写完成后必须执行 chmod +x /server/scripts/check_nginx_conn.sh，并确认 zabbix 用户对该路径有读和执行权限，否则采集结果为失败。

确实需要 root 权限的命令，给 zabbix 用户配 sudoers 白名单时务必限定到具体命令（zabbix ALL=(root) NOPASSWD: /usr/sbin/dmidecode 这样的粒度），别放行 ALL；sudoers 改完用 visudo -c 校验语法，语法错了 sudo 会整体失效。

## 五、触发器与告警表达式

### 5.1 创建触发器

配置 → 主机 → 选择相应监控主机的触发器 → 创建触发器，设置好表达式：

`{web01:server_state[nginx].last()}<=2`

表达式格式为 `{监控主机名称:键值名称.调用的表达式函数}<=2`，表示采集值小于等于 2 时触发报警。

写表达式前先确认监控项的单位与类型：pfree 是剩余百分比、pused 是已用百分比，条件方向写反是触发器"看起来配好了却永远不触发"的高频原因。

### 5.2 表达式函数速查

| 函数 | 说明 |
| --- | --- |
| last() | 收集到最新信息（数值），最常用 |
| max() | 在一定周期内收集到的最大值 |
| min() | 在一定周期内收集到的最小值 |
| diff() | 在一定时间内判断收集的信息是否不同 |
| change() | 在一定时间内判断收集的信息是否不同 |
| avg() | 取一段时间的平均值 |

更多函数（按需选用）：

| 函数 | 说明 |
| --- | --- |
| nodata(5m) | 5 分钟内没有采集到数据，用于监控 agent 失联，比阈值告警更及时 |
| str("string") | 采集值为字符串时使用，用于文本匹配 |
| regexp(pattern) | 按正则匹配采集值 |
| abs() | 取绝对值，适合增量类指标 |
| band(mask) | 按位与运算，常用于 SNMP 标志位判断 |

多条件示例：`{web01:system.cpu.load[percpu,avg1].avg(5m)}>2 and {web01:vfs.fs.size[/,pfree].min(10m)}<10`，表示 5 分钟平均负载大于 2 且 10 分钟内根分区最少剩余不足 10% 才触发，可避免单指标瞬时抖动造成的误告警。

阈值怎么定才不会造成告警风暴，给一套可落地的思路：

1. 先看历史再拍脑袋：拉出该指标过去两周的曲线，取高峰期的 P95 作参考，阈值至少留出 20% 余量，别按"理论上限"设。
2. 用多条件与时间窗口过滤毛刺：last() 配瞬时抖动，avg(5m)、min(10m) 才是抗抖动的主力，关键指标两者叠加。
3. 恢复阈值与告警阈值拉开差距：80% 告警、75% 才恢复（滞回），避免指标在阈值附近来回横跳、告警反复开关。
4. 上线后盯一周误报率再收敛：误报多的触发器降级或下线，比硬扛着让值班麻木强。告警风暴最贵的代价不是短信费，是"狼来了"之后没人再看告警。

### 5.3 告警信息处理思路

在企业工作中遇到告警信息，按以下步骤处理：

1. 看到告警提示信息，定位主机信息
2. 看到主机信息之后，定位报警原因，获得监控项 Key 值
3. 根据 Key 值信息，最终获得报警原因

告警分级不是摆设，它决定"谁在什么时候被哪种方式吵醒"：灾难级（业务中断）走电话、立即响应；严重级走微信/短信、15 分钟内响应；警告级走邮件、工作时间处理；信息级只记录不打扰。分级的意义就是把有限的值班精力投给真正致命的故障，同时靠动作里的升级规则兜底——警告级 30 分钟没人认领就自动升级。所有告警一个待遇的后果必然是狼来了。

## 六、Agent 主动模式与被动模式

Zabbix agent 有两种工作模式，选错模式是"图标不变绿"类问题的重要成因：

| 对比项 | 被动模式（默认） | 主动模式 |
| --- | --- | --- |
| 数据流向 | server 主动连接 agent 拉取数据 | agent 定时连接 server 推送数据 |
| agent 配置 | Server=server IP | ServerActive=server IP |
| 通信端口 | agent 监听 10050 | server 监听 10051 |
| 网络要求 | server 必须能访问 agent 的 10050 | agent 必须能访问 server 的 10051 |
| 适用场景 | 内网，server 与 agent 互通 | agent 位于 NAT、防火墙后或跨公网 |
| 列表刷新 | 由 server 侧间隔决定 | agent 按 RefreshActiveChecks（默认 120 秒）拉取监控项列表 |

工作流程：主动模式下，agent 先定时从 ServerActive 拉取"需要主动检查的监控项列表"，再按各监控项自身的更新间隔把数据发往 server。因此主动模式的 agent 不需要对外监听端口，安全性更好，也更适合分散在各分支机构的环境。两种模式可以同时配置，按监控项逐个选择。

主动模式的关键配置（agent 端 /etc/zabbix/zabbix_agentd.conf）：

```ini
ServerActive=172.16.1.71
Hostname=web01
RefreshActiveChecks=120
```

其中 Hostname 必须与 Web 界面中创建的主机名完全一致，这是主动模式最常见的配置错误：名字对不上，agent 数据发过来了，server 却找不到对应主机，界面数据永远是空的。

ServerActive 支持逗号分隔多个 server 地址，后续迁移监控中心或多 server 部署时，agent 侧改一次配置即可切换目标；把 RefreshActiveChecks 调小能让新配置更快生效，代价是 server 侧列表请求变多，常规环境保持默认 120 秒就好。

判断当前集群适合哪种模式：说白了，被动模式是 server 跑腿，主动模式是 agent 跑腿，看哪边跑腿更方便就选哪种。内网且 server 能直达 agent，用被动模式（默认，配置简单）；agent 在各地机房、NAT 后或跨公网，用主动模式；混合环境可以被动为主、主动为辅。

灵活间隔（flexible interval）是另一种常用手段：在监控项中为不同时间段设置不同的更新间隔，例如白天高峰每 30 秒采集一次 CPU，凌晨低峰每 10 分钟采集一次。配置方式是在监控项的更新间隔列点击自定义间隔，以 Schedule 形式添加时间段与间隔，既能保证高峰期数据密度，又能降低低峰期存储压力。

再澄清一个容易混的点：主动模式只改变数据的投递方式，触发器评估始终在 server 侧，所以两种模式下的触发器、动作配置完全一样，不用维护两套。

## 七、自动发现与聚合监控

### 7.1 网络发现与自动注册

批量纳管机器靠自动发现，而不是一台台手工添加：

| 机制 | 工作方式 | 典型用途 |
| --- | --- | --- |
| 网络发现 | server 按规则扫描指定 IP 范围（存活探测、开放端口等），对命中的目标执行动作 | 自动添加网段内存活主机并链接模板 |
| agent 自动注册 | agent 首次启动时主动向 server 发送注册请求，server 依据主机元数据（HostMetadata）匹配条件，自动归类主机组并链接模板 | 新增虚拟机/容器上线即自动纳管 |
| 低级别自动发现（LLD） | 对磁盘分区、网卡、SNMP OID 等"数量不固定"的对象周期性枚举，自动生成监控项、触发器与图形 | 一台机器多块盘、多个网卡的批量监控 |

三类发现的配置要点：

1. 网络发现：配置 → 自动发现 → 创建发现规则，设定 IP 范围、探测方式（ICMP 与端口）与执行频率；再在"动作"中定义命中后执行的操作（加入主机组、链接模板）。
2. 自动注册：配置 → 动作，触发条件选"自动注册"，用主机元数据（agent 配置中 HostMetadata 的值）区分用途，例如 HostMetadata=Linux-Web 的机器自动加入 Web 主机组并链接 Linux 模板。
3. LLD：模板中自带（如挂载文件系统、网络接口的发现规则），可调整刷新周期与保留的监控项，无需逐项手建。

LLD 有个容易忽略的开销：发现周期太短、生成的监控项太多，配置表会持续膨胀。旧盘、旧网卡摘除后其监控项默认还会保留，记得清理，否则库里躺着一堆 Not supported 的僵尸项。

实践中三者常配合使用：存量机房的机器用网络发现批量纳管，之后新增的虚拟机与容器用自动注册做到即上线即监控，机房里数量不固定的磁盘、网卡、数据库实例则交给 LLD 自动生成监控项。

HostMetadata 别写太泛，"Linux" 这种粒度会让不同用途的机器混进同一模板；metadata 里带上角色与环境（如 Linux-web-prod），动作条件按精确值匹配，纳管才不会跑偏。

### 7.2 聚合监控（aggregate）

当监控目标从单机变为"集群整体"时，使用聚合监控项：

| 聚合函数 | 作用 |
| --- | --- |
| grpsum | 对同组多台主机的同一 key 求和，如集群磁盘总容量 |
| grpavg | 求平均值，如集群平均 CPU 使用率 |
| grpmax | 取组内最大值，如集群中最高的单机负载 |
| grpmin | 取组内最小值 |

使用方式：创建监控项时类型选 aggregate，key 形如 grpsum("Web集群","vfs.fs.size[/,total]")，即可在最新数据与图形中看到集群级指标。聚合监控项不采集本机数据，它消费的是其他主机的历史数据。

配置步骤：配置 → 主机 → 任意主机的监控项 → 创建监控项，类型选"聚合"，填写 key（如 grpsum("Web集群","vfs.fs.size[/,total]")）、更新间隔与应用集，保存后即可像普通监控项一样查看最新数据、绘制图形、建立触发器（如集群剩余总空间低于阈值时告警）。聚合监控项的更新间隔别设太短，它每次都要查其他主机的数据，1-5 分钟一次足够。

## 八、图形、仪表盘与报表

| 功能 | 作用 |
| --- | --- |
| 图形（graph） | 将单个或多个监控项绘制成曲线，如把 CPU 的 us、sy、id 叠加为一张堆叠图 |
| 聚合图形（screen） | 把多个图形与表格编排为一个页面，适合大屏轮播 |
| 仪表盘（dashboard） | 自由组合的小部件面板，可放置最新数据、图形、拓扑图、告警列表、时钟等 |
| 拓扑图（map） | 用图标与连线还原网络架构，并实时反映各节点的告警状态 |
| 可用性报告 | 统计某段时间内监控项处于故障状态的时长占比 |
| 告警排行 | 统计触发次数最多的监控项，定位"最闹"的告警源 |
| 定时报表 | 按周期生成报表并发送给指定收件人（高版本支持 PDF 形式） |

日常使用建议：个人值班看仪表盘，汇报与复盘用报表，架构梳理用拓扑图。值班大屏只放最关键的小部件——全局问题列表、核心业务曲线、时钟，别堆满，一眼扫不到重点的仪表盘等于没有。

创建入口速查：

| 功能 | 入口 |
| --- | --- |
| 简单图形 | 配置 → 模板（或主机）→ 图形 → 创建图形，选择要叠加的监控项 |
| 仪表盘 | 监测 → 仪表盘 → 添加小部件，选择类型后保存布局 |
| 拓扑图 | 监测 → 拓扑图 → 编辑，拖入主机图标并连线，图标颜色随告警状态变化 |
| 定时报表 | 报表 → 定时报表 → 创建，选择接收人与发送周期（高版本功能） |

图形配置的几个细节：一个图形可叠加多个监控项，但建议只叠加同单位、同量纲的指标（如 CPU 的各状态、同单位流量），否则 Y 轴没有参考意义；图形支持按平均值、最大值、最小值汇总，可设置绘制类型（线、面积、柱）与 Y 轴范围；图形创建后既可挂在主机下查看，也可加入仪表盘小部件与聚合图形中复用。

## 九、权限管理

Zabbix 的权限由用户类型与用户组共同控制：

| 概念 | 说明 |
| --- | --- |
| 用户类型 | 超级管理员（全部权限）、管理员（受限的配置权限）、普通用户（仅被授权的查看权限）、访客（guest，只读默认仪表盘） |
| 用户组 | 把主机组与模板的读/读写权限授予用户组，用户加入用户组即继承权限 |
| 主机组权限 | 最常见的授权方式：按业务把主机分组，只授权对应运维团队可见可配 |
| 前端维护模式 | 维护期间关闭界面写操作，避免误配置 |
| 审计日志 | 记录配置变更与登录行为，便于追责 |

实践原则：按最小权限分配，值班人员只给读权限，模板与主机的修改权限集中到少数负责人。guest 用户默认存在、权限再小也是入口，用不上就直接停用。

配置步骤：管理 → 用户组 → 创建用户组，在权限页面对目标主机组授予只读或读写；管理 → 用户 → 创建用户，选择用户类型并把用户加入用户组；再到用户的报警媒介页绑定邮件、微信等接收方式。用户不加入任何用户组时，看不到任何主机的数据。给团队建用户组而不是逐个用户授权，人员变动只需调整组成员，权限矩阵不会散架。

## 十、Zabbix 日常维护

监控系统自身也需要维护，否则会从"帮手"变成"拖垮数据库的负担"：

| 维护项 | 说明 |
| --- | --- |
| Housekeeping | 管理 → 一般 → Housekeeping，设置事件、问题等数据的保留天数，超过即自动清理 |
| 历史与趋势数据保留 | 每个监控项可分别设置 history 与 trends 的保留天数，采集密集的项不要保留过长 |
| 清理频率 | HousekeepingFrequency 默认为 1 小时执行一次，库大时可评估清理窗口对性能的影响 |
| 数据库体积监控 | 定期查看 history、trends、events 表大小，膨胀过快说明保留策略或采集项不合理 |
| 大库优化 | 数据量极大时，MySQL 侧可按时间对 history/trends 表做分区，降低删除压力 |
| 配置备份 | /etc/zabbix/ 目录与数据库应纳入定期备份，配置误操作时靠备份回滚 |
| 版本升级 | 跨大版本升级需逐级进行（如 4.0 → 5.0 → 6.0），升级前必须备份数据库与配置文件 |

配置入口：管理 → 一般 → Housekeeping，可分别设置事件、问题等数据的保留天数；单个监控项的历史与趋势保留天数，则在监控项自身的历史数据保留时间、趋势数据保留时间中设置。默认情况下 housekeeping 每小时执行一次，保留策略遵循"够用即可"：明细数据保留 7-30 天，趋势数据保留 90-365 天，具体以排查与汇报需求为准。

生产上栽过的坑：history 全部按默认时长保留、采集项又贪多，半年后 events/history 表把磁盘撑爆，监控系统自己先宕机。上监控的第一周就把保留策略和采集间隔定下来，这事拖不得。

## 十一、告警方式配置

Zabbix 支持五种报警方式：

1. 页面提示信息报警（值班运维使用）
2. 页面声音提示报警
3. 邮件信息报警
4. 微信功能报警
5. 短信报警、电话报警

选型经验：邮件兜底、微信为主、电话留给灾难级，短信作为微信通道故障时的备份；页面提示与声音只在值班台有效，人一离开工位就指望不上，远程值守必须配移动端渠道。

### 11.1 页面提示与声音报警

创建触发器后，页面即会出现提示报警。开启声音报警的方法：

- 小人头（用户头像）→ 正在发送消息 → 勾选前端信息

修改报警铃声的步骤：

1. 找到文件所在目录（在站点目录中找）：

```bash
find /usr/share/zabbix -type f -name "alarm_disaster.wav"
```

2. 将原有声音文件替换成指定声音文件
3. 需要清除浏览器缓存，进行测试

### 11.2 邮件告警

邮件发送有两种途径：一是在报警媒介类型中直接选择 Email 类型，填写 SMTP 服务器、端口与发信账号；二是自定义脚本调用 sendmail 或 mail 命令发送。前者配置直观，后者在需要附件、模板定制时更灵活。

1. 创建触发器（方法同上）
2. 修改动作配置：配置 → 动作 → 将默认动作开启
3. 建立与 163 邮箱服务的关系：管理 → 报警媒介类型 → 创建报警媒介
4. 定义接收报警的邮件地址：小人头 → 报警媒介 → 设置收件人信息

163、126 这类公共邮箱要先在邮箱后台开启 SMTP 服务并生成授权码，媒介里填授权码而不是登录密码，直接填密码会认证失败；公司内部邮箱一般直接给 SMTP 账号。

### 11.3 微信告警（企业微信）

第一个步骤：注册企业微信，并进行配置。

- 我的企业：获取企业 ID；获取企业二维码，允许员工加入
- 管理工具：成员加入后，进行审核通过
- 应用小程序：创建应用，收集程序信息（AgentId、Secret）

第二个步骤：编写告警脚本（python）。Zabbix 服务端配置文件中定义了告警脚本的存放目录：

```bash
cat /etc/zabbix/zabbix-server.conf
```

```ini
AlertScriptsPath=/usr/lib/zabbix/alertscripts  --- 放置告警脚本
```

将编写好的 python 脚本放入 `/usr/lib/zabbix/alertscripts` 目录。

脚本目录的属主与权限别忽略：让 zabbix 用户可读可执行（root:zabbix 加 755 即可），权限不对时 server 调用脚本会静默失败，媒介、动作看起来全对，消息就是发不出去。

执行脚本报错问题解决：

- 问题一：No module named requests

```bash
yum install -y python-pip
pip install requests
```

- 问题二：脚本执行语法错误，检查并修正脚本语法

第三个步骤：修改添加报警媒介，定义发微信的配置。

第四个步骤：配置接收微信的人员。

> **注意：** 告警脚本的入参约定：Zabbix 调用告警脚本时依次传入三个参数，$1 为发送目标（用户在媒介中填写的地址）、$2 为主题、$3 为消息内容，脚本按位置取用即可，例如 Python 脚本用 sys.argv[1] 至 sys.argv[3] 接收。

> **注意：** 告警脚本的通用套路是相同的：接收 Zabbix 传入的三个参数（发送目标、主题、内容），调用对应平台的 API 完成投递。微信走企业微信 API，钉钉则是在群里添加自定义机器人取得 Webhook 地址，脚本用 POST 请求把消息内容送到该地址即可。脚本放入 AlertScriptsPath 目录后，记得在"管理 → 报警媒介类型"中创建自定义媒介并指向脚本名，动作中引用该媒介，最后在用户上绑定收件信息，四步缺一不可。

### 11.4 短信与电话告警

利用第三方短信电话报警平台：

1. 阿里大鱼（收费），可自行研究
2. OneAlert，配置步骤如下：
   - 配置报警平台：配置 → 应用 → 选择 zabbix 报警
   - 配置通知策略
   - 配置分派策略

第三方平台的本质是把 Zabbix 的事件转发出去再分发，多了一层依赖，核心业务的告警保留一条直连通道（如邮件）更稳。

告警的抑制与升级：配置 → 维护 可创建维护窗口，窗口期内主机不产生新告警，适合计划停机与变更窗口；动作中的升级操作可设置问题在指定时长内未恢复时逐级通知更高级别的负责人，例如 30 分钟未恢复通知主管、60 分钟未恢复通知总监，避免告警长时间无人处理。

## 十三、常见问题排查

| 问题现象 | 排查与解决 |
| --- | --- |
| 主机图标不变绿 | 检查 Agent 的 Server 配置与 10050 端口监听 |
| 自定义 key 取不到值 | 在 Server 端用 zabbix_get 测试键值，确认 Agent 配置后重启服务 |
| 脚本报 No module named requests | 安装 python-pip 并执行 pip install requests |
| 脚本执行报语法错误 | 检查 python 脚本语法 |
| 收不到告警信息 | 检查默认动作是否开启、报警媒介与收件人是否配置 |

扩充排错表（按现象、原因、命令、解决四列细化）：

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 主机图标不变绿 | agent 的 Server 地址写错；10050 未监听；防火墙拦截；agent 未启动 | ss -lntup \| grep 10050; zabbix_get -s 172.16.1.7 -k agent.ping | 修正 Server 参数；启动 zabbix-agent；放行 10050 端口 |
| zabbix_get 取不到自定义 key | UserParameter 语法错误；未放行 agentd.d 目录；agent 未重启；zabbix 用户无执行权限 | zabbix_get -s IP -k 'key'; tail -f /var/log/zabbix/zabbix_agentd.log; ls -l 脚本路径 | 修正语法；chmod +x；重启 agent；注意带参数 key 要写全方括号 |
| 最新数据不更新 | agent 服务停止；被动模式下 server 不在 Server 列表；更新间隔过长 | systemctl status zabbix-agent; 在 server 上 curl -s 10.0.0.7:10050 | 重启 agent；Server 加 server IP；调小更新间隔 |
| 告警不触发 | 触发器表达式写错；动作被禁用；表达式引用了错误的 key | Web 界面查看触发器最新评估值；检查动作状态 | 修正表达式；启用默认动作；确认 key 名与参数 |
| 告警发了但收不到 | 媒介未绑定用户；脚本无执行权限；依赖模块缺失；SMTP/Webhook 配置错误 | 手动执行 alertscripts 下脚本；tail /var/log/zabbix/zabbix_server.log | 绑定媒介与收件人；chmod +x 脚本；安装依赖；核对密钥与 Webhook |
| 数据库持续膨胀 | housekeeping 未开启；history/trends 保留天数过长 | 查看库表占用空间 | 开启 housekeeping 并调小保留天数；大库考虑分区 |
| 时间不同步导致图表断层 | 多台机器时间不一致或 NTP 未配置 | date; chronyc sources | 配置 NTP 同步 |
| 主机链接了模板却无数据 | 模板中监控项未启用，或主机接口地址不匹配 | 查看监控项是否启用、接口是否正确 | 启用监控项；修正接口与宏地址 |

信息收集三板斧：遇到任何数据类问题，按以下顺序收集信息，绝大多数问题可以自行定位——第一，在 server 上执行 zabbix_get -s 目标IP -k 'agent.ping' 与目标 key，确认 agent 侧返回值；第二，查看 agent 日志 /var/log/zabbix/zabbix_agentd.log 与 server 日志 /var/log/zabbix/zabbix_server.log 在报错时段的内容；第三，在 Web 界面该监控项的最新数据页确认采集时间戳是否在刷新。三者结合即可区分"agent 没执行""server 没收到""界面没刷新"三种边界。这三步敲一遍就明白，新同事排障照此流程走即可。

## 小结

- 第一台主机监控的流程是：创建主机（名称、主机组、地址）→ 关联模板 → 检查变绿 → 查看最新数据。
- 应用集实现分类展示，聚合计算要靠 aggregate 类型监控项；模板实现配置复用，动作决定告警发给谁、发送什么内容、以什么类型发送。
- 自定义监控通过 UserParameter 实现，格式为 UserParameter=key[*],command，带参数的键值在 Web 端要写全方括号与参数；命令由 agent 以 zabbix 用户通过 sh 执行，需注意脚本权限与执行耗时。
- 触发器表达式为 {主机:键值.函数()} 形式，其中 last() 是最常用的函数。
- 主动模式由 agent 推送数据（访问 server 10051），适合 NAT/防火墙后的场景；被动模式由 server 拉取数据（访问 agent 10050），适合内网直连。
- 五种告警方式中，邮件告警依赖开启默认动作、配置报警媒介类型、设置收件人三个步骤；微信与钉钉告警脚本放在 AlertScriptsPath 指定的目录。
- 权限管理遵循最小授权：用用户组把主机组的读/读写权限分配给不同团队。
- 日常维护重点在 housekeeping：合理设置数据保留天数，防止数据库无限膨胀。

## 自测题

1. UserParameter=server_state[*],ss -lntup|grep -c $1 中，[*] 和 $1 分别表示什么？Web 端监控项键值应如何填写？
2. agent 的主动模式与被动模式在配置参数、端口与适用场景上有什么区别？
3. 想统计一个 Web 集群所有机器的磁盘总容量，应该使用什么类型的监控项？写出聚合函数。
4. zabbix_get -s 172.16.1.7 -k 'web_state' 取不到值，请给出至少四种排查方向。
5. 监控系统上线半年后数据库快速增长，应从哪些方面做日常维护？

> **答案：** 1. [*] 表示该 key 接收参数，$1 是调用时传入的第 1 个参数；Web 端键值必须带上方括号与参数，例如 server_state[nginx]。2. 被动模式：agent 配置 Server=，监听 10050，由 server 主动来拉，要求 server 能访问 agent；主动模式：agent 配置 ServerActive=，由 agent 定时访问 server 的 10051 推送数据，适合 agent 在 NAT/防火墙后的场景。3. 使用 aggregate 类型监控项，聚合函数写 grpsum("主机组名","vfs.fs.size[/,total]")。4. 一、UserParameter 语法是否正确；二、agent 是否已重启；三、脚本是否对 zabbix 用户可执行；四、key 是否带全参数；五、server 到 agent 10050 端口是否连通。5. 开启并合理配置 housekeeping 的事件与数据保留天数；为采集密集的监控项单独设置较短的 history/trends 保留期；监控数据库表体积变化；数据量极大时对 history/trends 表按时间分区；清理无用的历史主机与监控项。
