只会写 `hosts` + `tasks` 的剧本只能完成固定的动作。想让剧本"聪明"起来，需要掌握一组扩展功能：变量的设置方式与优先级、`register`、`when`、`with_items` 与 `loop`、`ignore_errors`、`failed_when` 与 `changed_when`、`tags`、`handlers`、`include_tasks` 与 `import_tasks` 的区别、`block/rescue/always`，以及多个剧本的整合写法。

文中的 YAML 均经过缩进校正，可直接保存为 `.yml` 文件后通过 `ansible-playbook` 运行；示例中的主机清单组统一使用 `webserver`，读者可按自己的实验环境替换。

## 本篇知识地图
{: .sec-sum}

| 序号 | 扩展功能 | 解决的问题 |
| --- | --- | --- |
| 1 | 变量 | 把重复使用的值提取出来统一管理 |
| 2 | register | 把任务的执行结果保存下来供后续使用 |
| 3 | when | 满足条件才执行任务 |
| 4 | loop / with_items | 循环遍历列表，批量执行同类任务 |
| 5 | ignore_errors / failed_when / changed_when | 控制任务失败与变更的判定 |
| 6 | tags | 给任务打标签，按需挑选执行 |
| 7 | handlers | 配置发生变化时才触发一次收尾动作 |
| 8 | include_tasks / import_tasks | 把任务文件按静态或动态方式拆分复用 |
| 9 | block/rescue/always | 成片处理错误，实现救援与清理 |
| 10 | 剧本整合 | 把多个剧本组装成一个入口文件 |

## 一、变量设置：五种方式与完整优先级

变量是剧本参数化的基础。同一个值（比如共享目录、软件包名、监听端口）在多处出现时，应提取为变量，改一处即可全局生效。

### 方式一：在剧本文件中编写（最常用）

```yaml
- hosts: webserver
  remote_user: root
  vars:
    var01: data01
    var02: data02
  tasks:
    - name: show vars
      debug:
        msg: "{{ var01 }} {{ var02 }}"
```

### 方式二：在命令行中指定

```bash
ansible-playbook --extra-vars=var01=data01 test.yml
```

命令行变量适合临时覆盖某个取值，不需要改剧本文件。也可以写成 JSON 形式传入复杂结构：

```bash
ansible-playbook -e '{"var01":"data01","var02":"data02"}' test.yml
```

### 方式三：在主机清单文件中编写
{: .sec-chk}

```ini
[webserver]
web01
web02

[webserver:vars]
var01=data01
var02=data02
```

### 方式四：独立的变量文件（vars_files）

当变量较多、或希望变量与任务逻辑分离时，把变量集中放到一个 YAML 文件中，再用 `vars_files` 引入：

```yaml
# vars.yml
var01: data01
var02: data02
data_dir: /data
```

```yaml
- hosts: webserver
  remote_user: root
  vars_files:
    - vars.yml
  tasks:
    - name: show vars from file
      debug:
        msg: "{{ var01 }} {{ data_dir }}"
```

`vars_files` 中的路径相对于 playbook 文件所在目录；企业实践中更常见的是用 `group_vars/` 与 `host_vars/` 目录自动加载（详见 roles 与剧本分层相关章节）。

变量文件按服务拆分是好习惯：`vars/nginx.yml`、`vars/mysql.yml` 各管各的，`vars_files` 按需引入列表。再往上一层就是 group_vars 目录约定——清单同目录下自动按组名加载，连 `vars_files` 语句都省了，新项目建议直接用目录约定。

### 方式五：注册变量（register）与 set_fact

任务执行的结果可以注册成变量（详见下文 register 一节）；`set_fact` 模块则允许在剧本运行过程中动态定义变量：

```yaml
- hosts: webserver
  tasks:
    - name: set custom fact
      set_fact:
        my_service_name: nginx

    - name: use the fact
      debug:
        msg: "service is {{ my_service_name }}"
```

注册变量与 `set_fact` 设置的变量作用于后续任务，是"运行时变量"的两种来源。

`set_fact` 有个适用边界要知道：它每次执行都会重新计算并报告 changed，大量使用会破坏"重复执行全 ok"的清爽输出。能用 `vars` / 清单变量静态表达的值不要用 `set_fact`；它的价值在于运行期才能算出的东西——加工 register 结果、按 facts 拼路径、跨条件推导配置值。

### 五种方式的优先级

同时配置了同一个变量时，Ansible 按固定优先级决定最终取值。简化记忆用三级模型：

| 优先级 | 设置方式 | 说明 |
| --- | --- | --- |
| 最高 | 命令行变量（`--extra-vars`） | 临时覆盖，灵活性最强 |
| 中等 | 剧本中变量（`vars`） | 与剧本一起维护，最常用 |
| 最低 | 主机清单变量 | 适合按主机组区分的差异信息 |

完整优先级表（从低到高，越靠上越容易被覆盖，`--extra-vars` 永远获胜）：

| 层级 | 变量来源 | 说明 |
| --- | --- | --- |
| 1 | role defaults（`defaults/main.yml`） | 角色的默认值，最易被覆盖 |
| 2 | inventory 组变量（清单内联 `[组:vars]`） | 写在 hosts 文件里的组变量 |
| 3 | `group_vars/all` | 对所有主机生效的组变量目录 |
| 4 | `group_vars/*` | 按组划分的组变量目录 |
| 5 | inventory 主机变量（清单内联） | 写在主机行尾的变量 |
| 6 | `host_vars/*` | 按主机划分的主机变量目录 |
| 7 | host facts / 缓存 facts | setup 模块收集的事实信息 |
| 8 | play vars（playbook 中的 `vars:`） | 课堂方式一 |
| 9 | play vars_prompt | `vars_prompt` 交互输入 |
| 10 | play vars_files | `vars_files` 引入的文件 |
| 11 | role vars（`vars/main.yml`） | role 内部变量，优先级高于 play vars |
| 12 | block vars | 定义在 block 上的变量 |
| 13 | task vars | 定义在单个任务上的变量 |
| 14 | include_vars | 运行时动态加载的变量文件 |
| 15 | set_facts / registered vars | 运行期产生的变量 |
| 16 | role 参数（`roles:` 中传参） | 调用角色时传入的参数 |
| 17 | include 参数 | include_role 时传入的参数 |
| 18 | extra vars（`--extra-vars` / `-e`） | 永远最高优先级 |

> **注意：** 想在所有剧本之间共享变量（全局变量），推荐结合 roles 目录结构、`group_vars` / `host_vars` 目录统一管理，而不是在每个剧本里重复定义。
{: .sec-pit}

18 层不用背，实战守两条就够：想被使用者覆盖的放 `defaults`，不允许覆盖的放 `vars` 或干脆用 `--extra-vars` 压轴。排查变量问题时用 `ansible 目标 -m debug -a "var=变量名"` 直接看解析值，逐层排除来源。

变量命名也有坑：不要用 `ansible_` 前缀（与内置 facts 冲突），不要用 Python 关键字，团队统一大小写约定——YAML 区分大小写，`Data_dir` 与 `data_dir` 是两个变量，案例实战里就有人栽在这上面。

## 二、register 注册信息

任务执行后，结果默认只打印在终端里。用 `register` 可以把结果保存成变量，供后面的任务使用，配合 `debug` 模块即可显示输出，例如检查服务器端口并回显：

```yaml
- hosts: webserver
  tasks:
    - name: check server port
      shell: ss -lntup
      register: get_server_port

    - name: display port info
      debug:
        msg: "{{ get_server_port.stdout_lines }}"
```

执行后能看到逐行输出的端口信息，有监听中的服务进程，即表示服务已经正常启动。

> **注意：** `netstat` 已被废弃，建议使用 `ss` 代替。`netstat -lntup` 的等价写法是 `ss -lntup`（功能一致，输出格式略有差异），新系统（Rocky/AlmaLinux/CentOS Stream 等）默认不再安装 net-tools 软件包。
{: .sec-pit}

注册变量是一个字典，除了输出内容还带有丰富的元信息，常用字段如下：

| 字段 | 含义 |
| --- | --- |
| `stdout` | 命令的标准输出（字符串） |
| `stdout_lines` | 命令的标准输出按行拆成的列表 |
| `stderr` | 命令的标准错误输出 |
| `rc` | 命令的返回码，0 表示成功 |
| `changed` | 任务是否产生了变更 |
| `failed` | 任务是否失败 |
| `msg` | 模块附带的说明信息（部分模块有） |

因此后续任务可以直接用 `get_server_port.rc == 0` 这样的条件做判断，而不必解析文本。

register + `until` 是"等服务就绪"的最小实现：循环跑一条检查命令、注册结果、`until` 判断输出，比 `wait_for` 更灵活——端口、文件、进程、任意命令输出都能当就绪条件，只有标准端口探测这类场景才轮到 `wait_for` 上场。

> **注意：** 注册的变量名不能包含空格，否则 YAML 解析会出错；`stdout_lines` 会把输出按行拆成列表，比原始的 `stdout` 更便于阅读。
{: .sec-pit}

register 与 when 的组合是剧本里最常见的套路：先跑一条检查类命令并 register，再用 when 依据结果决定后续动作，例如 `when: get_server_port.rc == 0` 时才重启、`when: not conf_stat.stat.exists` 时才初始化。两个注意点：register 的变量在整个 play 内全局可见，跨 task 可用；判断字段要写全层级，是 `conf_stat.stat.exists` 而不是 `conf_stat.exists`。

register 与循环配合时结构会变：每次循环的结果按顺序存进 `results` 列表，取值写成 `results[0].rc` 或配合 `loop_control: label` 精简输出。第一次写容易当成单值变量取，报错信息也看不出问题——拿不准结构时先 `debug: var=注册名` 打印整个结构看一眼。

## 三、when 条件判断

### 条件判断的写法

`when` 用于让任务只在满足条件时执行，条件借助 facts（被管理主机的系统信息）书写：

```yaml
- hosts: webserver
  remote_user: root
  tasks:
    - name: Check File
      file:
        path: "/tmp/this_is_{{ ansible_hostname }}_file"
        state: touch
      when: (ansible_hostname == "nfs") or (ansible_hostname == "backup")

    - name: install httpd
      yum:
        name: httpd
        state: installed
      when: ansible_distribution == "CentOS"

    - name: install httpd2
      yum:
        name: httpd2
        state: installed
      when: ansible_distribution == "ubuntu"
```

### 获取内置变量（facts）的方法

`setup` 模块可以显示被管理主机的详细信息，用 `filter` 只取关心的字段：

```bash
ansible webserver -m setup -a "filter=ansible_hostname"
```

### 常见主机信息速查
{: .sec-chk}

| facts 变量 | 说明 |
| --- | --- |
| `ansible_all_ipv4_addresses` | 仅显示 IPv4 的地址信息 |
| `ansible_devices` | 仅显示磁盘设备信息 |
| `ansible_distribution` | 显示是什么系统，例如 CentOS、SUSE 等 |
| `ansible_distribution_major_version` | 显示系统主版本号 |
| `ansible_distribution_version` | 仅显示系统版本号 |
| `ansible_machine` | 显示系统类型，例如 32 位还是 64 位 |
| `ansible_eth0` | 仅显示 eth0 的信息 |
| `ansible_hostname` | 仅显示主机名 |
| `ansible_kernel` | 仅显示内核版本 |
| `ansible_lvm` | 显示 LVM 相关信息 |
| `ansible_memtotal_mb` | 显示系统总内存 |
| `ansible_memfree_mb` | 显示可用系统内存 |
| `ansible_memory_mb` | 详细显示内存情况 |
| `ansible_swaptotal_mb` | 显示总的 swap 内存 |
| `ansible_swapfree_mb` | 显示 swap 内存的可用内存 |
| `ansible_mounts` | 显示系统磁盘挂载情况 |
| `ansible_processor` | 显示 CPU 个数（具体显示每个 CPU 的型号） |
| `ansible_processor_vcpus` | 显示 CPU 个数（只显示总的个数） |

获取 facts 中的子信息，可以用下标方式，例如：

```bash
ansible_eth0[ipv4]
```

### when 常用表达式

| 写法 | 示例 | 说明 |
| --- | --- | --- |
| 相等比较 | `ansible_hostname == "web01"` | 最常用 |
| 逻辑与或 | `a == "x" and b == "y"` | and / or / not |
| 成员判断 | `"web01" in group_names` | 判断主机属于哪个组 |
| 列表包含 | `"'172.16.1.7' in ansible_all_ipv4_addresses"` | 判断地址是否在 facts 列表中 |
| 定义判断 | `Data_dir is defined` | 避免变量未定义报错 |
| 版本比较 | `ansible_distribution_major_version \| int >= 8` | 配合 int 过滤器转成整数 |
| 文件判断 | `ansible_os_family == "RedHat"` | 按系统家族分支 |

> **注意：** 这里有个坑：`when` 中的变量必须真实存在（多为 facts 或前面注册的变量），写"自造"的条件名不会报语法错误，但判断结果可能永远不符合预期。
{: .sec-pit}

when 里的类型坑也要留意：布尔值比较写 `var | bool`、数字比较先 `| int`、列表判空用 `var | length > 0`。三个类型转换覆盖日常八成的"条件明明该成立却不成立"问题。

### 辨析：when 与 failed_when 的分工

`when` 管"要不要执行"（前置分流），`failed_when` 管"执行了算不算失败"（后置判定），两者不互替。健康检查任务的标准写法是：`when` 控制"只在部署后才检查"，`failed_when` 表达"不健康即失败"。用 `ignore_errors: yes` 加后续 `when: rc == 0` 来模拟失败判定是反模式——错误被吞掉、统计失真，一步到位的 `failed_when` 才是正路。

## 四、循环：with_items、loop 与 with_dict

需要批量创建用户时，用 `with_items` 遍历列表，`item` 代表当前这一次取到的元素：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - name: Add Users
      user:
        name: "{{ item.name }}"
        groups: "{{ item.groups }}"
        state: present
      with_items:
        - { name: 'testuser1', groups: 'bin' }
        - { name: 'testuser2', groups: 'root' }
```

批量安装软件包同理，此时 `item` 就是一个个包名：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - name: Installed Pkg
      yum:
        name: "{{ item }}"
        state: present
      with_items:
        - wget
        - tree
        - lrzsz
```

`with_dict` 用于遍历字典，此时通过 `item.key` 与 `item.value` 取值：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - name: create dirs with dict
      file:
        path: "{{ item.value }}"
        state: directory
      with_dict:
        data01: /data01
        data02: /data02
```

`loop` 是 Ansible 2.5 之后推荐的标准写法，与 `with_items` 等价：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - name: Installed Pkg with loop
      yum:
        name: "{{ item }}"
        state: present
      loop:
        - wget
        - tree
        - lrzsz
```

循环中还可以叠加 `when` 做逐条过滤，注意此时 `item` 条件要写在 `loop` 之后的 `when` 里，作用于每个元素：

性能与输出也值得留意：循环配 `loop_control: label` 可以把终端里冗长的 item 展开缩成一行，大列表可读性完全不同；上千项的循环慎写——每一项都是一次完整的模块调用，纯文本批量生成改用 template 一次完成，快一个数量级。

```yaml
- hosts: all
  tasks:
    - name: only create big dirs
      file:
        path: "{{ item }}"
        state: directory
      loop:
        - /data/big
        - /data/small
      when: item != "/data/small"
```

> **注意：** `with_items` 是旧文档中的经典写法，Ansible 2.5 之后也可以使用等价的 `loop`；两种写法至少掌握一种，能看懂旧剧本即可。
{: .sec-pit}

## 五、ignore_errors 与失败的精修控制

默认情况下，playbook 会检查命令和模块的返回状态，遇到错误就中断整个剧本的执行。加上 `ignore_errors: yes` 可以忽略错误，让剧本继续往下执行：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - name: Ignore False
      command: /bin/false
      ignore_errors: yes

    - name: touch new file
      file:
        path: /tmp/ignore_error_demo
        state: touch
```

上例中第一个任务故意返回失败，但因为忽略了错误，第二个任务仍会正常执行。

`ignore_errors` 的范围只到单个任务，别顺手打到 play 级——整场忽略错误等于关掉 Ansible 的故障刹车，失败淹没在绿色输出里，等发现时往往已经推了一半机器。

`ignore_errors` 是"一刀切"的忽略，实际生产中更推荐用 `failed_when` 精确声明什么情况算失败，用 `changed_when` 声明什么情况算发生了变更（很多命令类任务永远没有变更，应显式告知 Ansible，避免剧本反复执行时显示 changed；健康检查、信息收集这类只读任务统一加 `changed_when: false`，`--diff` 与变更统计才只反映真实改动）：

```yaml
- hosts: all
  tasks:
    - name: check httpd process
      shell: pgrep httpd || true
      register: httpd_result
      changed_when: false
      failed_when: httpd_result.rc != 0

    - name: report status
      debug:
        msg: "httpd is running, pid lines: {{ httpd_result.stdout_lines | length }}"
```

- `failed_when`：满足条件时判定任务失败，不满足则即使命令返回码非 0 也算成功；
- `changed_when: false`：明确告诉 Ansible 该任务不改变系统状态，check 模式下也不会报变更。

`changed_when` 还能按输出内容判定：命令式部署任务写 `changed_when: "'OK' in stdout"`，输出里出现 OK 才算变更，RECAP 统计才反映真实情况。健康的检查类任务记住一个组合拳：`register` + `changed_when: false` + 判断逻辑放在 `failed_when`，三行配置就能把任意 shell 检查收敛成规范任务。

## 六、tags 标签功能

给任务打上标签后，可以只执行（或跳过）其中一部分任务：

```yaml
- hosts: webserver
  ignore_errors: yes
  remote_user: root
  tasks:
    - name: Check File
      file:
        path: "/tmp/this_is_{{ ansible_hostname }}_file"
        state: touch
      when: (ansible_hostname == "nfs01") or (ansible_hostname == "backup")
      tags: t1

    - name: bad thing
      command: ech 123
      tags: t2

    - name: install httpd
      yum:
        name: httpd
        state: installed
      when: (ansible_all_ipv4_addresses == ["172.16.1.7","10.0.0.7"])
      tags: t3

    - name: install httpd2
      yum:
        name: httpd2
        state: installed
      when: (ansible_distribution == "ubuntu")
      tags: t4
```

执行时通过参数挑选标签：

```console
# 只执行标签为 t2 的任务
$ ansible-playbook --tags=t2 test05.yml

# 跳过标签为 t2 的任务
$ ansible-playbook --skip-tags=t2 test05.yml
```

> **注意：** `bad thing` 任务中的 `ech` 是故意写错的命令名，配合 play 级别的 `ignore_errors: yes` 用来演示"命令不存在时报错但剧本不中断"的行为，实际使用时应改正为 `echo`。
{: .sec-pit}

> **注意：** `ansible_all_ipv4_addresses` 是列表类型的 facts，与列表直接相等比较通常难以命中，实战中更稳妥的写法是结合 `in` 判断其中一个地址，例如 `when: "'172.16.1.7' in ansible_all_ipv4_addresses"`。
{: .sec-pit}

除自定义标签外，Ansible 还内置了几个特殊标签：

| 特殊标签 | 作用 |
| --- | --- |
| `always` | 打上该标签的任务任何情况下都会执行 |
| `never` | 打上该标签的任务默认不执行，只有被 `--tags` 显式点名时才执行 |
| `untagged` | 选中所有没有打标签的任务 |

实际用法上，tags 最值钱的场景是多阶段剧本：装软件打 `package`、推配置打 `config`、验证打 `check`，日常改配置只跑 `ansible-playbook --tags=config site.yml`，不必全量重跑。另一个常见场景是把耗时且极少变化的任务（大包下载、编译安装）单独打标，日常用 `--skip-tags` 跳过，需要时再单独执行。

tags 与 `--check` 组合是上线前的标准验证流程：`--check --tags=config --diff` 先预演文件差异，确认无误后去掉 `--check` 实跑，灰度阶段再叠加 `--limit` 圈定单机。三件套用顺了，生产变更的心理负担小一半。

## 七、handlers 触发功能

handlers（触发器）与 tasks 平级编写，任务中用 `notify` 指定"配置发生变化时通知哪个 handler"。只有当任务真正产生了变更时，handler 才会在剧本末尾执行一次，避免了每次运行都重复重启服务：

```yaml
- hosts: backup
  remote_user: root
  tasks:
    - name: 01 Install rsync
      yum:
        name: rsync
        state: present

    - name: 02 push config file
      copy:
        src: "./file/{{ item.src }}"
        dest: "/etc/{{ item.dest }}"
        mode: "{{ item.mode }}"
      with_items:
        - { src: "rsyncd.conf", dest: "rsyncd.conf", mode: "0644" }
        - { src: "rsync.password", dest: "rsync.password", mode: "0600" }
      notify: restart rsync server

  handlers:
    - name: restart rsync server
      service:
        name: rsyncd
        state: restarted
```

> **注意：** handler 默认只在剧本全部任务执行结束后运行一次，且仅在对应任务报告 changed 时触发；`notify` 后面的名称必须与 handler 的 `name` 完全一致。
{: .sec-pit}

### 原理解析：handler 的触发机制
{: .sec-know}

handler 的执行遵循三条规则，理解它们可以避免"改了配置却没重启"的疑惑：

1. **变更驱动**：只有报告 changed 的任务发出的通知才会入队；任务显示 ok 时 notify 不生效。
2. **末尾汇总执行**：所有通知先在队列里排队，等整个 play 的任务全部结束后才统一执行，且同名 handler 只执行一次（多个任务通知同一个 handler，不会重启多次）。
3. **顺序定义**：handlers 按其在 `handlers:` 中出现的顺序执行，不按通知的先后顺序。

为什么设计成末尾执行？说白了两个理由：同一份配置可能被多个任务先后修改，中途重启多次毫无意义，末尾汇总执行一次就够；重启是破坏性动作，等前面的任务全部成功再执行，避免"前一个任务失败、服务却已经被重启过"的尴尬局面。

如果希望 handler 立刻执行（例如后面的任务依赖服务已重启），可以用 `meta: flush_handlers` 强制刷新队列：

```yaml
- hosts: backup
  tasks:
    - name: push conf
      copy:
        src: rsyncd.conf
        dest: /etc/rsyncd.conf
      notify: restart rsync server

    - name: flush handlers now
      meta: flush_handlers

    - name: check rsync status
      shell: ss -lntup | grep 873 || true
      register: rsync_check
      changed_when: false

  handlers:
    - name: restart rsync server
      service:
        name: rsyncd
        state: restarted
```

多个任务需要触发同一类动作时，还可以用 `listen` 给 handler 起一个"监听主题"，任务里 notify 主题名即可：

`meta: flush_handlers` 的典型场景是"改配置 → 立即重启 → 紧接着验证"：不 flush 的话，验证任务跑在重启之前，检查的是旧状态，结论必然失真。看到剧本里"验证任务结果不对劲"，先想想 handler 是不是还压在队尾没执行。

```yaml
- hosts: web
  tasks:
    - name: push nginx conf
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: "reload web services"

    - name: update php config
      copy:
        src: php.ini
        dest: /etc/php.ini
      notify: "reload web services"

  handlers:
    - name: restart nginx
      service:
        name: nginx
        state: restarted
      listen: "reload web services"

    - name: restart php-fpm
      service:
        name: php-fpm
        state: restarted
      listen: "reload web services"
```

## 八、include_tasks 与 import_tasks 的区别

把任务拆到多个文件后，有两种引入方式，行为差异很大：

```yaml
- hosts: all
  remote_user: root
  tasks:
    - import_tasks: f1.yml
    - import_tasks: f2.yml
    - include_tasks: f3.yml
```

| 特性 | `import_tasks` | `include_tasks` |
| --- | --- | --- |
| 导入时机 | 剧本解析时静态导入 | 任务运行时动态加载 |
| tags 传递 | 标签会传递给被导入的所有子任务 | 标签只作用于 include 语句本身 |
| when 传递 | 条件作用于每一个子任务 | 条件只判断 include 是否执行 |
| 与 loop 配合 | 不能对 import 语句加 loop | 可以用 loop 动态包含文件 |
| 报错时机 | 文件不存在时解析期即报错 | 运行到该任务时才报错 |
| 适用场景 | 结构固定的拆分 | 按条件、按循环动态选择任务文件 |

> **注意：** 静态导入（import）在剧本开始前就确定了全部任务清单，因此 `--list-tasks` 能看到完整列表；动态包含（include）在运行前不确定执行哪些文件，`--list-tasks` 只显示 include 语句本身。
{: .sec-pit}

## 九、block/rescue/always 错误处理
{: .sec-ts}

`block` 把一组任务当成一个整体，配合 `rescue`（出错时救援）与 `always`（无论成败都执行），可以写出类似编程语言的 try/except/finally 逻辑，适合安装失败回滚、临时清理等场景：

```yaml
- hosts: web
  remote_user: root
  tasks:
    - name: deploy app with rollback
      block:
        - name: install app package
          yum:
            name: myapp
            state: present

        - name: push app config
          copy:
            src: myapp.conf
            dest: /etc/myapp.conf
      rescue:
        - name: rollback app install
          yum:
            name: myapp
            state: absent

        - name: report failure
          debug:
            msg: "deploy failed, rolled back"
      always:
        - name: cleanup temp files
          file:
            path: /tmp/myapp_deploy
            state: absent
```

执行逻辑：

1. `block` 中任一任务失败，立即停止执行 block 剩余任务，进入 `rescue`；
2. `rescue` 全部成功后，整个 block 任务视为成功；
3. `always` 中的任务无论如何都会执行，常用于清理临时文件、恢复配置。

### 辨析：block/rescue 与 ignore_errors 的取舍

`ignore_errors` 只是把失败"降级"成警告继续跑，失败任务的动作已经发生，半成品状态留在机器上。`block/rescue` 有回滚语义：失败后执行清理与恢复，rescue 全部成功即算整体成功。需要回滚与清理用 block；只是"允许个别任务失败、失败无害"才用 `ignore_errors`。

## 十、多个剧本的整合

当日志结构按服务拆分后，需要一个入口把多个剧本串起来，常见三种写法：

### 方式一：include_tasks（在任务中引入）

```yaml
- hosts: all
  remote_user: root
  tasks:
    - include_tasks: f1.yml
    - include_tasks: f2.yml
```

### 方式二：include（在 play 中引入）

```yaml
- include: f1.yml
- include: f2.yml
```

### 方式三：import_playbook（按 play 整体导入）

```console
$ cat main.yml
- import_playbook: base.yml
- import_playbook: rsync.yml
- import_playbook: nfs.yml
- import_playbook: other.yml
- import_playbook: rsync.yml
- import_playbook: nfs.yml
```

三种方式的定位：

| 写法 | 引入的粒度 | 状态 |
| --- | --- | --- |
| `include` | play 文件 | 已废弃，旧剧本中可能见到 |
| `import_playbook` | 整个 play | 推荐，作为总入口 |
| `include_tasks` | 任务文件 | 推荐，用于任务级拆分 |
| `import_tasks` | 任务文件 | 推荐，静态拆分首选 |

> **注意：** `include` 写法已在新版本中废弃，新剧本推荐使用 `include_tasks`（任务级）或 `import_playbook`（play 级）；遇到旧剧本时能看懂即可。
{: .sec-pit}

标签在 `import_playbook` 层会继承到子剧本里，`--tags` 能命中子剧本内的同名标签——规划标签体系时按服务前缀命名（如 `rsync-config`、`nfs-config`）避免撞车。多个剧本整合后，入口文件建议保持"只描述结构"的纪律：哪些服务、什么顺序、跑在哪些组，细节一律拆出去，入口即架构图。

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `msg: 'var01' is undefined` | 变量名拼写错误或变量作用域不对 | `ansible-playbook --syntax-check test.yml`；`ansible all -m debug -a "var=var01"` | 检查变量定义位置与优先级，必要时给默认值 `{{ var \| default('x') }}` |
| handler 不执行 | notify 名称与 handler name 不一致，或任务显示 ok 未变更 | `ansible-playbook test.yml` 查看任务是否 changed | 对齐名称；确认任务确实产生了变更 |
| `ERROR! no action detected in task` | 模块名拼错或缩进不对，模块未被识别 | `ansible-playbook --syntax-check test.yml` | 核对模块名与 YAML 缩进 |
| 条件永远不命中 | 对列表 facts 用了相等比较 | `ansible all -m setup -a "filter=ansible_all_ipv4_addresses"` | 改用 `in` 判断：`"'172.16.1.7' in ansible_all_ipv4_addresses"` |
| `--tags` 执行了不想跑的任务 | 标签打在 play 或被 import 继承 | `ansible-playbook --list-tasks test.yml` | 明确标签作用范围，静态拆分用 import_tasks |
| block 中失败后 rescue 没生效 | rescue 写在 block 外或缩进层级错误 | `ansible-playbook --syntax-check test.yml` | block/rescue/always 必须同级缩进 |

## 现代环境补充
{: .sec-ext}

1. **连接变量改名**：`ansible_ssh_user`、`ansible_ssh_pass`、`ansible_ssh_host`、`ansible_ssh_port` 是旧名称，新版本统一为 `ansible_user`、`ansible_password`、`ansible_host`、`ansible_port`，旧写法仍兼容但会提示废弃。
2. **facts 名称规范化**：Rocky Linux 的 `ansible_distribution` 值为 `Rocky`，AlmaLinux 为 `AlmaLinux`，CentOS Stream 的取值与版本有关，以 `ansible all -m setup -a "filter=ansible_distribution*"` 的实际输出为准；判断系统家族时用 `ansible_os_family == "RedHat"` 更通用。
3. **包管理模块**：Rocky/AlmaLinux/CentOS Stream 上 `yum` 模块仍可用，等价的新写法是 `dnf` 模块；`service` 模块在新系统上建议直接使用 `systemd` 模块管理 systemd 单元。
4. **命令查询**：`netstat` 已废弃（属于 net-tools 包），统一改用 `ss -lntup`；`ifconfig` 已废弃，改用 `ip addr`。
5. **ansible-core**：新版本发行模式为 ansible-core（核心引擎）+ collections（集合），`ansible-galaxy collection install` 安装扩展集合，模块文档以集合形式维护。

## 自测题
{: .sec-prac}

1. 同一个变量在 `vars`、主机清单和 `--extra-vars` 中同时定义，最终生效的是哪一个？如果同时存在 `defaults/main.yml` 呢？
2. `register` 注册的变量里，哪些字段可以用于判断命令是否成功？请写出两个。
3. handler 什么时候会执行？多个任务通知同一个 handler，handler 会执行几次？
4. `import_tasks` 与 `include_tasks` 的核心区别是什么？各适合什么场景？
5. `block/rescue/always` 分别对应编程语言里的什么结构？

> **答案：**
> 1. `--extra-vars` 优先级最高，永远覆盖其他来源；`defaults/main.yml` 优先级最低，最先被覆盖。完整顺序参见本篇优先级表。
> 2. `rc`（返回码，0 为成功）和 `failed`（布尔值）；也可以看 `stderr` 辅助定位。
> 3. 仅当通知它的任务报告 changed 时，handler 才会入队，并在整个 play 的任务结束后执行一次；多个任务通知同一个 handler 也只执行一次。
> 4. `import_tasks` 是解析期静态导入，标签与条件会传递给子任务，适合结构固定的拆分；`include_tasks` 是运行期动态加载，标签条件只作用于自身，适合按条件或循环动态选择任务文件。
> 5. block 对应 try，rescue 对应 except，always 对应 finally。

## 小结
{: .sec-sum}

1. 变量有五种常见来源：剧本 `vars`（最常用）、命令行 `--extra-vars`（优先级最高）、主机清单、`vars_files` 外部文件、register/set_fact 运行期变量；完整优先级共 18 层，记住"extra vars 永远赢、defaults 永远输"即可。
2. `register` 把任务结果保存为变量（含 rc、stdout、stdout_lines、changed、failed 等字段），配合 `debug` 的 `stdout_lines` 可以逐行回显输出，变量名不能带空格。
3. `when` 条件判断依赖 facts（`setup` 模块可查），`ansible_hostname`、`ansible_distribution`、`ansible_all_ipv4_addresses` 是最高频的几个；列表型 facts 用 `in` 判断更稳妥。
4. `with_items` 让同类任务批量执行，`item` 即当前元素，新写法可用 `loop`；字典遍历用 `with_dict`。
5. `ignore_errors` 允许任务失败不中断剧本，更精细的控制用 `failed_when` 与 `changed_when`。
6. `tags` 配合 `--tags` / `--skip-tags` 实现按需执行，另有 `always` / `never` 两个内置标签。
7. `handlers` 由 `notify` 触发、仅在变更时执行一次，适合服务重启这类收尾动作；`listen` 可聚合多个 handler，`meta: flush_handlers` 可强制立即执行。
8. `import_tasks` 静态导入、`include_tasks` 动态包含，`include` 已废弃；`block/rescue/always` 提供 try/except/finally 式错误处理。
9. 多个剧本可用 `include_tasks`、`import_playbook` 整合为一个入口，主入口只描述结构，细节交给拆分文件与 roles。
10. 变量排查两板斧：`debug` 看 `var` 的实际解析值定位来源；命名避开 `ansible_` 前缀与大小写歧义，能省掉大半"变量不生效"的排查时间。
