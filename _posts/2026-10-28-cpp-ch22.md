## 22.1 项目要求
{: .sec-expl}

### 22.1.1 原书系统与现代重做的差距

原书的图书借阅系统大概是这个样子：一个 `Book` 结构体、一个 `vector<Book>`、菜单循环、`switch` 分发，所有代码在一个 `main.cpp` 里，数据存文本文件。作为语法练习没问题，作为工程教学有四个硬伤：业务规则和 I/O 搅在一起没法测、字符串 ID 和裸 int 满天飞、编译一次全量重编、没有自动测试。

现代重做不是"换个框架"，而是把同一套需求按可维护的方式重新组织。对照表如下。

| 维度 | 原书写法 | 现代写法 |
| --- | --- | --- |
| 代码组织 | 单文件大 main | include/src/tests/apps 分层，依赖单向流动 |
| 实体标识 | 裸 `int` 或 `std::string` | 强类型 `Id<Book>`，不同实体 ID 不能互赋 |
| 业务规则 | 藏在菜单分支里 | Service 层独立函数，输入输出可测 |
| 错误处理 | 返回 -1 或打印了事 | `std::expected<T, Error>` 显式错误通道（C++23） |
| 日期 | 自己算 `int day_offset` | `std::chrono::sys_days`（C++20） |
| 持久化 | 手写文本格式 | nlohmann/json + ADL 序列化钩子 |
| 测试 | 手工点菜单 | doctest 自动用例，含边界条件 |
| 构建 | 一条 g++ 命令 | CMake target 化 + 包管理 + CI |

### 22.1.2 角色与用例
{: .sec-know}

系统有两个角色。管理员的动作是录入图书、登记读者、看库存统计；读者的动作是检索、借阅、归还、续借、交罚金。用例拆开写清楚，每条附上业务规则——规则就是后面单元测试的用例来源。

| 用例 | 触发角色 | 业务规则 |
| --- | --- | --- |
| 检索图书 | 读者 | 按书名/作者模糊匹配，返回剩余可借数 |
| 借阅 | 读者 | 书有剩余副本；读者在借数量不超 5；同一本书同一读者同时只能有 1 笔未还 |
| 归还 | 读者 | 找到在借记录；逾期按天计罚金，未逾期为 0 |
| 续借 | 读者 | 只能续 1 次；已逾期的不能续；续借延长一个借期 |
| 逾期罚金 | 系统 | 罚金 = 逾期天数 × 0.5 元，归还时一次结清 |
| 库存统计 | 管理员 | 每本书的总副本数减去在借数 |

这里有个容易漏的点：罚金不是独立用例，它是"归还"的输出之一。把罚金做成 `give_back` 的返回值，测试时就不用专门去"查"罚金了。

### 22.1.3 领域模型与状态流转
{: .sec-know}

三个实体一个关系。Book 是书目（关心总副本数），Member 是读者，Loan 是一笔借阅关系——注意 Loan 才是核心实体，借书还书操作的都是它，不是 Book。

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| Book | id、isbn、title、author、total_copies | total_copies 是总副本，不是剩余 |
| Member | id、name | 故意做薄，演示实体最小形态 |
| Loan | id、book、member、borrow_date、due_date、renew_count、return_date | return_date 为空表示在借 |

Loan 的状态流转只有三种终态路径：在借 → 归还（可能带罚金）；在借 → 续借 → 归还；在借 → 逾期 → 归还（罚金）。没有"取消借阅"这种状态——原书没有这个需求，别自己加需求。

强类型 ID 先立起来，这是整个模型里性价比最高的一步：

```cpp
// include/library/ids.hpp —— 需要 C++20
#pragma once
#include <cstdint>
#include <functional>

namespace library {

// 强类型 ID：Id<Book> 和 Id<Member> 是不同类型，混用直接编译错误
template <typename Tag>
struct Id {
    std::uint64_t value = 0;

    friend bool operator==(const Id&, const Id&) = default;   // C++20
    friend auto operator<=>(const Id&, const Id&) = default;  // C++20 三路比较
};

struct BookTag {};
struct MemberTag {};
struct LoanTag {};

using BookId   = Id<BookTag>;
using MemberId = Id<MemberTag>;
using LoanId   = Id<LoanTag>;

}  // namespace library

// 让强类型 ID 能当 unordered_map 的 key
template <typename Tag>
struct std::hash<library::Id<Tag>> {
    std::size_t operator()(const library::Id<Tag>& id) const noexcept {
        return std::hash<std::uint64_t>{}(id.value);
    }
};
```

裸 `int` 的问题是错的组合也能编译：把会员 ID 传给查书的函数，编译器一声不吭。强类型 ID 用两个空 struct 当标签，零运行时开销，换来编译期拦截。写过大项目的人都懂，这种"让错误在编译期爆炸"的手段比任何 code review 都可靠。

实体定义放在 domain.hpp，只有数据没有行为：

```cpp
// include/library/domain.hpp —— 需要 C++20
#pragma once
#include <chrono>
#include <optional>
#include <string>

#include "library/ids.hpp"

namespace library {

// sys_days：自 1970-01-01 起的天数，类型本身说明"这是日期不是时间戳"
using Date = std::chrono::sys_days;

struct Book {
    BookId id;
    std::string isbn;
    std::string title;
    std::string author;
    int total_copies = 0;
};

struct Member {
    MemberId id;
    std::string name;
};

struct Loan {
    LoanId id;
    BookId book;
    MemberId member;
    Date borrow_date{};
    Date due_date{};
    int renew_count = 0;
    std::optional<Date> return_date;  // 空 = 还没还
};

}  // namespace library
```

`std::chrono::sys_days` 是 C++20 的日历设施（`<chrono>` 里的 `year_month_day` 家族），类型上就把"日期"和"时间戳"分开了，加减天数直接 `+ days{30}`，不用再手写"大小月"判断。

## 22.2 需求分析
{: .sec-expl}

### 22.2.1 把用例翻译成接口契约

需求分析的产品是一份接口清单，不是一段文字。Service 层对外暴露的每个方法、每个错误码，在这里定死，后面实现和测试都对着这张表干活：

| 方法 | 入参 | 成功返回 | 失败错误码 |
| --- | --- | --- | --- |
| borrow | BookId、MemberId、今天 | LoanId | BookNotFound / MemberNotFound / NoCopiesAvailable / MemberLoanLimit / DuplicateBorrow |
| give_back | LoanId、今天 | 罚金（元） | LoanNotFound / AlreadyReturned |
| renew | LoanId、今天 | 新到期日 | LoanNotFound / AlreadyReturned / RenewLimitReached / RenewOverdue |
| available_copies | BookId | 剩余副本数 | BookNotFound |

三个设计决定值得展开说：

- 每个业务方法都显式接收"今天"这个日期。时间是从外面注入的，不是在函数里调 `system_clock::now()` 拿的。理由很直接：注入后测试可以造出"逾期 35 天"而不用真等 35 天，这是整个测试策略的支点。
- 错误集中成一个枚举 `Error`，方法统一返回 `std::expected<T, Error>`（C++23），调用方用 `if (r)` 判断成功、`r.error()` 拿错误，错误通道和正常返回值在类型上分开了。
- "读者在借上限 5"这类参数放 `Settings` 结构体，不写死在 if 里。改业务参数不动代码逻辑。

错误码定义：

```cpp
// include/library/error.hpp
#pragma once

namespace library {

enum class Error {
    BookNotFound,
    MemberNotFound,
    LoanNotFound,
    NoCopiesAvailable,
    MemberLoanLimit,
    DuplicateBorrow,
    AlreadyReturned,
    RenewLimitReached,
    RenewOverdue,
};

inline const char* to_string(Error e) {
    switch (e) {
        case Error::BookNotFound:      return "书不存在";
        case Error::MemberNotFound:    return "读者不存在";
        case Error::LoanNotFound:      return "借阅记录不存在";
        case Error::NoCopiesAvailable: return "没有可借副本";
        case Error::MemberLoanLimit:   return "已达借书上限";
        case Error::DuplicateBorrow:   return "同一本书还有未还的借阅";
        case Error::AlreadyReturned:   return "该记录已归还";
        case Error::RenewLimitReached: return "续借次数已用完";
        case Error::RenewOverdue:      return "已逾期，不能续借";
    }
    return "未知错误";
}

}  // namespace library
```

### 22.2.2 目录结构设计
{: .sec-prac}

分层目录是这份需求对应的物理形态：

```text
library/
├── CMakeLists.txt
├── vcpkg.json
├── .clang-format
├── .clang-tidy
├── .github/
│   └── workflows/
│       └── ci.yml
├── include/
│   └── library/
│       ├── ids.hpp
│       ├── domain.hpp
│       ├── error.hpp
│       ├── repository.hpp
│       ├── in_memory_repository.hpp
│       ├── serialize.hpp
│       ├── json_repository.hpp
│       └── service.hpp
├── src/
│   └── service.cpp
├── apps/
│   └── main.cpp
├── tests/
│   ├── CMakeLists.txt
│   ├── test_main.cpp
│   └── test_service.cpp
└── data/
```

为什么要这么分，每一层都有明确理由：

- `include/library/` 放公共头文件，`src/` 放实现。这条分界线的含义是"别人能看到的"和"只是我的实现细节"。`service.hpp` 在 include 里，`service.cpp` 在 src 里——使用者只需要头文件就能知道怎么调，实现改一百遍他们不用重新读。
- `apps/` 放可执行入口。main.cpp 不是库的一部分，它只是"把库拼起来给人用"的胶水。分开放，将来加一个 Web 后端入口或第三个 CLI 工具，都不碰库代码。
- `tests/` 有自己的 CMakeLists.txt，测试是独立 target，链接库但不影响库的构建产物。
- `data/` 放运行时生成的 JSON 文件，不属于源码，.gitignore 掉。

### 22.2.3 依赖方向与循环依赖
{: .sec-know}

分层的灵魂是依赖方向：`apps → service → repository(接口) → domain`，箭头只能这么指。domain 不 include 任何人（除了 ids/domain 自己），service 依赖 repository 的抽象接口而不是具体实现，具体实现（内存版、JSON 版）反过来依赖接口。

判断分层是否做对了，有一个机械办法：从 domain.hpp 开始，看它 include 了什么。它应该谁都不 include（最多标准库）。一旦 domain 里 include 了 service.hpp 或某个具体存储，依赖环就埋下了——两个头文件互相 include，编译器展开时直接报"未定义"，或者更糟，靠 include 顺序碰巧能编过，换个编译顺序就炸。

> **这里有个坑：** 循环依赖最常从"图省事"开始——domain 里想加个打印函数，顺手 include 了带 I/O 的头。解法是把打印函数挪到独立的工具头，或者让 domain 保持纯数据、序列化钩子放到 serialize.hpp（本工程就是这么做的）。
{: .sec-pit}

Repository 接口是模板形式，头文件即接口：

```cpp
// include/library/repository.hpp
#pragma once
#include <optional>
#include <vector>

namespace library {

// 仓储接口：Service 只依赖这个抽象，测试时换成内存实现
template <typename T, typename IdT>
class Repository {
public:
    virtual ~Repository() = default;

    virtual std::optional<T> find(IdT id) const = 0;
    virtual void save(const T& entity) = 0;
    virtual std::vector<T> all() const = 0;
    virtual bool erase(IdT id) = 0;
};

}  // namespace library
```

## 22.3 系统具体实现
{: .sec-prac}

### 22.3.1 现代 CMake 骨架

先看根 CMakeLists.txt 全貌，再逐段拆开讲为什么：

```cmake
cmake_minimum_required(VERSION 3.20)

project(library
    VERSION 1.0.0
    DESCRIPTION "图书借阅系统"
    LANGUAGES CXX)

# 全局标准设置：只对未显式设置 target_*_features 的 target 生效
set(CMAKE_CXX_STANDARD 23)          # 本工程用 std::expected（C++23）
set(CMAKE_CXX_STANDARD_REQUIRED ON) # 编译器不支持就报错，不许静默降级到旧标准
set(CMAKE_CXX_EXTENSIONS OFF)       # 关掉 GNU 扩展（-std=c++23 而不是 -std=gnu++23）

option(LIB_BUILD_TESTS "构建单元测试" ON)
option(LIB_BUILD_APPS  "构建命令行程序" ON)
option(LIB_WITH_JSON   "启用 nlohmann/json 持久化" OFF)

# 依赖：先找系统/vcpkg/Conan 提供的，找不到再 FetchContent 拉源码
find_package(nlohmann_json 3.11 CONFIG QUIET)
if(LIB_WITH_JSON AND NOT nlohmann_json_FOUND)
    include(FetchContent)
    FetchContent_Declare(nlohmann_json
        GIT_REPOSITORY https://github.com/nlohmann/json.git
        GIT_TAG        v3.11.3)
    FetchContent_MakeAvailable(nlohmann_json)
endif()

# 库本体：先 add 再填内容，target 思维的核心写法
add_library(library_core STATIC)
target_sources(library_core PRIVATE
    src/service.cpp)
target_include_directories(library_core
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:include>)
target_compile_options(library_core PRIVATE
    $<$<CXX_COMPILER_ID:MSVC>:/W4>
    $<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wall -Wextra -Wpedantic>)

if(LIB_WITH_JSON)
    target_link_libraries(library_core PUBLIC nlohmann_json::nlohmann_json)
    target_compile_definitions(library_core PUBLIC LIB_WITH_JSON=1)
endif()

# 起个别名，工程内一律用带命名空间的名字引用它
add_library(library::core ALIAS library_core)

if(LIB_BUILD_APPS)
    add_executable(library_app apps/main.cpp)
    target_link_libraries(library_app PRIVATE library::core)
endif()

if(LIB_BUILD_TESTS)
    enable_testing()
    add_subdirectory(tests)
endif()

# 安装规则：让别人 find_package() 就能用你的库
install(TARGETS library_core
    EXPORT library-targets
    ARCHIVE DESTINATION lib)
install(DIRECTORY include/ DESTINATION include)
install(EXPORT library-targets
    FILE library-targets.cmake
    NAMESPACE library::
    DESTINATION lib/cmake/library)
```

`cmake_minimum_required(VERSION 3.20)` 不只是压版本警告。它决定了 CMake 的"策略版本"：低于这个版本写法里的旧行为不会启用，`ctest --test-dir` 这种 3.20 才有的参数也才有意义。2026 年写 3.20 起步是安全线——所有主流发行版和 CI 镜像都带得起。

`project()` 之后的三行标准设置里，`CXX_STANDARD_REQUIRED ON` 和 `CXX_EXTENSIONS OFF` 这两个经常被漏。漏了前者的后果：编译器不支持 C++23 时 CMake 静默降到最近支持的标准，代码"碰巧编不过"时你看到的是一头雾水的语法错误而不是清晰的版本提示。漏了后者的后果：GCC 默认给你 `-std=gnu++23`，`typeof` 这类 GNU 扩展混进来，换到 MSVC 就编不过。

### 22.3.2 target 思维与 PUBLIC/PRIVATE/INTERFACE 传播
{: .sec-know}

CMake 最大的历史包袱是 `include_directories()`、`add_definitions()` 这类**目录级**命令：写在哪个目录，就对那个目录及子目录里所有 target 生效。项目小的时候没感觉，target 一多就变成"谁知道哪个头文件从哪来的"玄学。

现代写法一切围绕 target：`target_sources`、`target_include_directories`、`target_compile_options`、`target_link_libraries` 都挂在具体 target 上，并且带传播语义——这个 target 的"使用要求"要不要传给链接它的人？三个关键字说清这件事：

| 关键字 | 语义 | 典型例子 |
| --- | --- | --- |
| PRIVATE | 只自己用，不传播 | 实现细节用到的头文件路径、警告选项 |
| INTERFACE | 自己不用，只传给别人 | 纯头文件库的 include 路径 |
| PUBLIC | 自己用，也传给别人 | 放在自家头文件里被 include 的第三方头 |

判断口诀：**看这个依赖出现在哪种文件里**。只在 .cpp 里 include 的东西用 PRIVATE；出现在 .hpp 里、下游编译时也需要的，用 PUBLIC。本工程 `library_core` 的 include 路径是 PUBLIC，因为 domain.hpp 这些头会被下游 include，下游得知道去哪找 `library/` 这个前缀。

链接依赖同理：`library_app PRIVATE library::core` 表示"app 用库，但库不是 app 的接口"——app 是可执行文件，没有下游，一切 PRIVATE。

#### 辨析：目录级命令与 target 级命令
{: .sec-iv}

- `include_directories(include)`：改的是目录属性，所有 target 被动接受，头文件来源不可追溯，install(EXPORT) 导不出去。
- `target_include_directories(t PUBLIC ...)`：挂在 target 上，成为 target 的使用要求，链接它的 target 自动继承，导出安装时随 `library-targets.cmake` 一起交给消费者。

新代码一律 target 级。目录级命令只在给遗留代码做过渡时短暂出现，而且应该记上"待清理"的账。

### 22.3.3 生成器表达式、option 与缓存变量
{: .sec-know}

`target_compile_options` 里那两行 `$<...>` 是**生成器表达式**：构建系统生成阶段才求值的条件表达式。它解决了"同一个 CMakeLists 要伺候 MSVC 和 GCC"的问题——`$<$<CXX_COMPILER_ID:MSVC>:/W4>` 读作"如果编译器是 MSVC，追加 /W4"。常用的还有 `$<BUILD_INTERFACE:...>`（只在构建树内有效）和 `$<INSTALL_INTERFACE:...>`（只在安装后被消费时生效），上面 include 路径就同时包了两层：构建时用源码树路径，安装后用 `include` 相对路径。这两层缺一不可，只用绝对路径导出安装后路径就废了。

`option(LIB_WITH_JSON "..." OFF)` 声明一个布尔缓存变量，命令行用 `-DLIB_WITH_JSON=ON` 覆盖。需要非布尔配置时用 `set(VAR "value" CACHE STRING "说明" FORCE)`。缓存变量存在 build 目录的 CMakeCache.txt 里，重新 configure 会保留——所以改了 option 默认值后要清 build 目录或显式 `-D` 覆盖，这是新手经常困惑"为什么我的改动没生效"的原因。

### 22.3.4 find_package 与 FetchContent
{: .sec-know}

依赖接入有两条路，优先级是先 `find_package` 后 `FetchContent`：

- `find_package(nlohmann_json 3.11 CONFIG QUIET)`：找已经装好的包（系统路径、vcpkg、Conan 都会把"怎么找到我"的信息交给 CMake）。`CONFIG` 表示找包自带的 `*Config.cmake`，`QUIET` 表示找不到不吓唬人。
- `FetchContent_MakeAvailable`：配置阶段直接把源码拉进来，作为子工程一起编译。适合没有系统包、又不想强制用户装包管理器的场景，doctest 这种单头文件测试库是最典型用户。

两者分工的判断标准：这个依赖是否需要跟你的二进制一起发？测试框架只在构建期用，FetchContent 最省事；JSON 库可能被下游链接，交给 vcpkg/Conan 管理版本更干净。本工程两者都留了口子：找到就用现成的，找不到就拉源码。

### 22.3.5 install(EXPORT) 与"别人怎么用你的库"
{: .sec-know}

`install(TARGETS ... EXPORT library-targets)` 的意思是：装的时候顺便把这个 target 的使用要求（include 路径、链接依赖）记录成一份 CMake 脚本；`install(EXPORT library-targets ...)` 把这份脚本写到 `lib/cmake/library/library-targets.cmake`。消费者之后：

```cmake
find_package(library CONFIG REQUIRED)
target_link_libraries(my_app PRIVATE library::core)
```

include 路径、传播语义全部自动跟上，这就是前面坚持 `target_*` + `$<INSTALL_INTERFACE>` 的回报。没有这套动作，你的库只能靠"手动拷头文件 + 手动告诉别人链接哪个 .a"这种原始方式流通。

### 22.3.6 包管理：vcpkg 与 Conan2
{: .sec-know}

本工程依赖极少（nlohmann/json、doctest），但依赖管理方式要一开始就定对，后面只会越加越多。

vcpkg 走 **manifest 模式**：项目根放一个 vcpkg.json，声明依赖，CMake 配置时挂上 vcpkg 工具链，依赖自动装进 build 目录，不污染全局。

```json
{
  "name": "library",
  "version": "1.0.0",
  "dependencies": [
    "nlohmann-json"
  ]
}
```

```bash
vcpkg add port nlohmann-json        # 或手写上面的 vcpkg.json
cmake -B build -S . -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_TOOLCHAIN_FILE=$VCPKG_ROOT/scripts/buildsystems/vcpkg.cmake
```

Conan 2 的风格是把依赖声明放在 conanfile 里，由 conan 命令生成 CMake 工具链文件：

```text
[requires]
nlohmann_json/3.11.3

[generators]
CMakeDeps
CMakeToolchain
```

```bash
conan install . -s build_type=Release --output-folder build --build=missing
cmake -B build -S . -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_TOOLCHAIN_FILE=build/conan_toolchain.cmake
```

| 维度 | vcpkg | Conan 2 |
| --- | --- | --- |
| 声明方式 | 项目根 vcpkg.json（JSON） | conanfile.txt / conanfile.py |
| 与 CMake 集成 | 工具链文件，find_package 无缝 | CMakeToolchain 生成工具链，同样无缝 |
| 生态 | 微软维护，包数量大、更新快 | 社区中心仓 + 可自建私有仓，二进制缓存成熟 |
| 私有依赖 | 要自建 registry 或 overlay | 原生支持私有仓库，企业场景更顺 |
| 锁定版本 | baseline + override | lockfile 机制更细 |
| 什么时候选 | 团队主要在 Windows/微软生态 | 多平台 + 私有二进制分发需求重 |

两个都能干好事，别陷入"选哪个"的争论里内耗。规则简单：团队已经在用哪个就继续用哪个；从零开始且偏 Windows，vcpkg；需要企业级私有包分发，Conan 2。

### 22.3.7 依赖选型
{: .sec-know}

| 需求 | 选型 | 理由 |
| --- | --- | --- |
| JSON 持久化 | nlohmann/json | API 直觉、ADL 钩子优雅；性能敏感场景换 simdjson 只读 |
| 单元测试 | doctest | 单头文件、编译快、FetchContent 一行接入；mock 需求重可换 GTest |
| 命令行解析 | cxxopts / argparse | 头文件、声明式；两个都可，选一个别混用 |
| 日志 | 先 `std::cout`，长大再上 spdlog | 依赖是负债，别一上来就背 |

选型的通用判断：头文件优先（接入成本趋近于零）、CMake 目标规范（能 `target_link_libraries` 直接吃）、社区活跃（三年没 commit 的库慎入）。

### 22.3.8 Repository 接口与两种实现
{: .sec-prac}

接口在 22.2.3 已经给出。内存版实现是测试的标配，几十行：

```cpp
// include/library/in_memory_repository.hpp
#pragma once
#include <map>
#include <optional>
#include <vector>

#include "library/repository.hpp"

namespace library {

template <typename T, typename IdT>
class InMemoryRepository final : public Repository<T, IdT> {
public:
    std::optional<T> find(IdT id) const override {
        auto it = items_.find(id);
        if (it == items_.end()) return std::nullopt;
        return it->second;
    }

    void save(const T& entity) override { items_[entity.id] = entity; }

    std::vector<T> all() const override {
        std::vector<T> out;
        out.reserve(items_.size());
        for (const auto& [id, entity] : items_) out.push_back(entity);
        return out;
    }

    bool erase(IdT id) override { return items_.erase(id) > 0; }

private:
    std::map<IdT, T> items_;
};

}  // namespace library
```

`std::map` 的 key 是强类型 ID，靠 `operator<=>` defaulted 生成的比较——这就是 22.1.3 强类型 ID 在这里兑现的红利。

JSON 版把"怎么序列化"交给每个实体的 ADL 钩子，仓储本身对字段一无所知：

```cpp
// include/library/json_repository.hpp —— JSON 依赖 nlohmann/json
#pragma once
#include <algorithm>
#include <fstream>
#include <optional>
#include <utility>
#include <vector>

#include <nlohmann/json.hpp>

#include "library/repository.hpp"
#include "library/serialize.hpp"

namespace library {

template <typename T, typename IdT>
class JsonRepository final : public Repository<T, IdT> {
public:
    explicit JsonRepository(std::string path) : path_(std::move(path)) { load(); }

    std::optional<T> find(IdT id) const override {
        for (const auto& entity : items_)
            if (entity.id == id) return entity;
        return std::nullopt;
    }

    void save(const T& entity) override {
        for (auto& e : items_) {
            if (e.id == entity.id) {
                e = entity;
                persist();
                return;
            }
        }
        items_.push_back(entity);
        persist();
    }

    std::vector<T> all() const override { return items_; }

    bool erase(IdT id) override {
        auto it = std::remove_if(items_.begin(), items_.end(),
                                 [&](const T& e) { return e.id == id; });
        bool removed = it != items_.end();
        items_.erase(it, items_.end());
        if (removed) persist();
        return removed;
    }

private:
    void load() {
        std::ifstream in(path_);
        if (!in) return;  // 首次启动没有数据文件，当作空库
        nlohmann::json j;
        in >> j;
        items_ = j.get<std::vector<T>>();  // 走每个实体的 from_json
    }

    void persist() {
        nlohmann::json j = items_;  // 走每个实体的 to_json
        std::ofstream out(path_);
        out << j.dump(2) << '\n';
    }

    std::string path_;
    std::vector<T> items_;
};

}  // namespace library
```

ADL 钩子写在实体所在的 `library` 命名空间里，nlohmann 序列化时按实参类型自动找到它们——这就是 ADL（参数依赖查找）在库设计里的正当用法：

```cpp
// include/library/serialize.hpp —— 需要 C++20
#pragma once
#include <nlohmann/json.hpp>

#include "library/domain.hpp"

namespace library {

// to_json / from_json 与实体同命名空间，nlohmann 通过 ADL 找到它们
inline void to_json(nlohmann::json& j, const Book& b) {
    j = nlohmann::json{{"id", b.id.value}, {"isbn", b.isbn}, {"title", b.title},
                       {"author", b.author}, {"total_copies", b.total_copies}};
}

inline void from_json(const nlohmann::json& j, Book& b) {
    j.at("id").get_to(b.id.value);
    j.at("isbn").get_to(b.isbn);
    j.at("title").get_to(b.title);
    j.at("author").get_to(b.author);
    j.at("total_copies").get_to(b.total_copies);
}

inline void to_json(nlohmann::json& j, const Member& m) {
    j = nlohmann::json{{"id", m.id.value}, {"name", m.name}};
}

inline void from_json(const nlohmann::json& j, Member& m) {
    j.at("id").get_to(m.id.value);
    j.at("name").get_to(m.name);
}

inline void to_json(nlohmann::json& j, const Loan& l) {
    j = nlohmann::json{{"id", l.id.value},
                       {"book", l.book.value},
                       {"member", l.member.value},
                       {"borrow_date", l.borrow_date.time_since_epoch().count()},
                       {"due_date", l.due_date.time_since_epoch().count()},
                       {"renew_count", l.renew_count}};
    j["return_date"] = l.return_date
                           ? nlohmann::json((*l.return_date).time_since_epoch().count())
                           : nlohmann::json(nullptr);
}

inline void from_json(const nlohmann::json& j, Loan& l) {
    j.at("id").get_to(l.id.value);
    j.at("book").get_to(l.book.value);
    j.at("member").get_to(l.member.value);
    l.borrow_date = Date{std::chrono::days{j.at("borrow_date").get<long long>()}};
    l.due_date    = Date{std::chrono::days{j.at("due_date").get<long long>()}};
    j.at("renew_count").get_to(l.renew_count);
    if (j.at("return_date").is_null())
        l.return_date = std::nullopt;
    else
        l.return_date = Date{std::chrono::days{j.at("return_date").get<long long>()}};
}

}  // namespace library
```

日期存成"自 epoch 的天数"整数值，读起来不如 `2026-10-01` 直观，但不丢精度、省一次解析，且和 `std::chrono` 的内部表示零转换。日期的 ADL 钩子这里没写——`sys_days` 的关联命名空间是 `std::chrono`，钩子写在 `library` 里 ADL 找不到，直接在 Loan 的钩子里手动转换才是对的，这个细节值得记一笔。

### 22.3.9 Service 层：业务规则的唯一住址
{: .sec-prac}

先声明后实现，头文件是契约：

```cpp
// include/library/service.hpp —— 需要 C++23（std::expected）
#pragma once
#include <expected>
#include <memory>

#include "library/domain.hpp"
#include "library/error.hpp"
#include "library/repository.hpp"

namespace library {

struct Settings {
    int max_loans_per_member = 5;
    int max_renew_count      = 1;
    int loan_days            = 30;
    double fine_per_day      = 0.5;
};

class Service {
public:
    using BookRepo   = Repository<Book, BookId>;
    using MemberRepo = Repository<Member, MemberId>;
    using LoanRepo   = Repository<Loan, LoanId>;

    Service(std::shared_ptr<BookRepo> books, std::shared_ptr<MemberRepo> members,
            std::shared_ptr<LoanRepo> loans, Settings settings = {});

    std::expected<LoanId, Error> borrow(BookId book, MemberId member, Date today);
    std::expected<double, Error> give_back(LoanId loan, Date today);  // 返回罚金
    std::expected<Date, Error> renew(LoanId loan, Date today);        // 返回新到期日
    std::expected<int, Error> available_copies(BookId book) const;

private:
    int active_loan_count(MemberId m) const;
    bool has_active_loan_for_book(MemberId m, BookId b) const;

    std::shared_ptr<BookRepo> books_;
    std::shared_ptr<MemberRepo> members_;
    std::shared_ptr<LoanRepo> loans_;
    Settings settings_;
    LoanId next_loan_id_{1};
};

}  // namespace library
```

实现把用例表的每条规则落成一行 if，规则和检查一一对应：

```cpp
// src/service.cpp —— 需要 C++23（std::expected）
#include "library/service.hpp"

#include <chrono>

namespace library {
using namespace std::chrono;

Service::Service(std::shared_ptr<BookRepo> books, std::shared_ptr<MemberRepo> members,
                 std::shared_ptr<LoanRepo> loans, Settings settings)
    : books_(std::move(books)),
      members_(std::move(members)),
      loans_(std::move(loans)),
      settings_(settings) {}

std::expected<LoanId, Error> Service::borrow(BookId book_id, MemberId member_id,
                                             Date today) {
    auto book = books_->find(book_id);
    if (!book) return std::unexpected(Error::BookNotFound);
    if (!members_->find(member_id)) return std::unexpected(Error::MemberNotFound);
    if (active_loan_count(member_id) >= settings_.max_loans_per_member)
        return std::unexpected(Error::MemberLoanLimit);
    if (has_active_loan_for_book(member_id, book_id))
        return std::unexpected(Error::DuplicateBorrow);
    if (available_copies(book_id).value_or(0) <= 0)
        return std::unexpected(Error::NoCopiesAvailable);

    Loan loan;
    loan.id          = next_loan_id_++;
    loan.book        = book_id;
    loan.member      = member_id;
    loan.borrow_date = today;
    loan.due_date    = today + days{settings_.loan_days};
    loans_->save(loan);
    return loan.id;
}

std::expected<double, Error> Service::give_back(LoanId loan_id, Date today) {
    auto loan = loans_->find(loan_id);
    if (!loan) return std::unexpected(Error::LoanNotFound);
    if (loan->return_date) return std::unexpected(Error::AlreadyReturned);

    double fine = 0.0;
    if (today > loan->due_date) {
        auto overdue = (today - loan->due_date).count();  // 两个 sys_days 相减直接是天数
        fine = static_cast<double>(overdue) * settings_.fine_per_day;
    }
    loan->return_date = today;
    loans_->save(*loan);
    return fine;
}

std::expected<Date, Error> Service::renew(LoanId loan_id, Date today) {
    auto loan = loans_->find(loan_id);
    if (!loan) return std::unexpected(Error::LoanNotFound);
    if (loan->return_date) return std::unexpected(Error::AlreadyReturned);
    if (loan->renew_count >= settings_.max_renew_count)
        return std::unexpected(Error::RenewLimitReached);
    if (today > loan->due_date) return std::unexpected(Error::RenewOverdue);

    loan->renew_count += 1;
    loan->due_date = loan->due_date + days{settings_.loan_days};
    loans_->save(*loan);
    return loan->due_date;
}

std::expected<int, Error> Service::available_copies(BookId book_id) const {
    auto book = books_->find(book_id);
    if (!book) return std::unexpected(Error::BookNotFound);
    int out = 0;
    for (const auto& loan : loans_->all())
        if (loan.book == book_id && !loan.return_date) ++out;
    return book->total_copies - out;
}

int Service::active_loan_count(MemberId m) const {
    int n = 0;
    for (const auto& loan : loans_->all())
        if (loan.member == m && !loan.return_date) ++n;
    return n;
}

bool Service::has_active_loan_for_book(MemberId m, BookId b) const {
    for (const auto& loan : loans_->all())
        if (loan.member == m && loan.book == b && !loan.return_date) return true;
    return false;
}

}  // namespace library
```

实现里没有一行 I/O，没有一行菜单，全部输入来自参数、输出通过返回值。这意味着 22.3.11 的测试可以在纳秒级跑完，不需要任何文件或网络。

### 22.3.10 辨析：std::expected 还是异常
{: .sec-iv}

两个方案都能表达"业务规则没通过"，本工程选 `std::expected`（C++23），理由围绕"错误是不是正常流程的一部分"：

- 借满被拒、没有副本、逾期不能续借——这些是**业务结果**，每天发生几百次，不是异常。用异常表达正常分支，语义拧着，而且异常抛接的开销（栈展开）在热路径上不可忽略。
- `std::expected` 把"可能失败"写进返回类型，调用方不写 `if (r)` 就拿不到值，编译器逼你处理错误分支；异常没有这个约束，漏 catch 就直接飞出 main。
- 工具链门槛：`std::expected` 需要 GCC 12+ / Clang 16+（libc++）/ MSVC 19.33+（VS 2022 17.2）。如果你的编译器只到 C++20，替换方案是返回 `std::pair<T, std::optional<Error>>` 或 `std::variant`——能接受，但可读性差一截。

什么时候该用异常：构造函数失败（没有返回值可承载错误）、跨多层传播且每一层都不关心处理、错误真的"异常"（磁盘炸了、内存耗尽）。本工程没有这类场景，Service 的构造函数不会失败，所以全层 expected 是一致的选法。别两种混着不加说明地用——一个层里既抛异常又返回 expected，调用方要同时防两种失败模式，接口就脏了。

### 22.3.11 日期处理：std::chrono 三板斧
{: .sec-know}

本工程用到的 chrono 能力一共三样，都来自 C++20 的日历扩展（`<chrono>`）：

- `std::chrono::sys_days`：以天为单位的系统时间点，类型即文档。
- `year_month_day` 与字面量：`2026y/10/1` 直接构造日期（`using namespace std::chrono` 后，`y` 是年份字面量，`October` 等月份常量可用）。
- 时间点加减 `std::chrono::days`：`due + days{30}`，编译期就检查单位。

原书时代自己写 `int days_in_month[]` 的做法可以进博物馆了——闰年、大小月、时区，chrono 的日历部分都算好了。

### 22.3.12 main 与运行输出
{: .sec-prac}

app 层把所有零件拼起来，也演示了 expected 的标准消费写法：

```cpp
// apps/main.cpp —— 需要 C++23（std::expected）
#include <iostream>
#include <memory>

#include "library/in_memory_repository.hpp"
#include "library/service.hpp"

int main() {
    using namespace library;

    auto books   = std::make_shared<InMemoryRepository<Book, BookId>>();
    auto members = std::make_shared<InMemoryRepository<Member, MemberId>>();
    auto loans   = std::make_shared<InMemoryRepository<Loan, LoanId>>();

    books->save(Book{BookId{1}, "978-7-111-55842-2", "C++ Primer 中文版",
                     "Stanley Lippman", 2});
    members->save(Member{MemberId{1}, "张三"});

    Service svc(books, members, loans);

    // “今天”显式给出：真实程序里用 floor<days>(system_clock::now())
    auto today = Date{std::chrono::year_month_day{std::chrono::year{2026},
                                                  std::chrono::month{10},
                                                  std::chrono::day{1}}};

    auto r = svc.borrow(BookId{1}, MemberId{1}, today);
    if (r) {
        std::cout << "借书成功，借阅单号 " << r->value << '\n';
    } else {
        std::cout << "借书失败：" << to_string(r.error()) << '\n';
    }

    auto stats = svc.available_copies(BookId{1});
    std::cout << "剩余可借：" << stats.value_or(-1) << '\n';
    return 0;
}
```

```text
借书成功，借阅单号 1
剩余可借：1
```

`if (r)` 利用的是 `std::expected` 的显式 bool 转换；`r->value` 在成功分支解包；`stats.value_or(-1)` 失败时给兜底值。三种消费姿势都展示了，按场景挑。


用例集中在业务规则的边界上——借满、逾期、重复借，每条都对应 22.2.1 用例表里的一行规则：

```cpp
// tests/test_service.cpp —— 需要 C++23（std::expected）
#include <doctest/doctest.h>

#include <chrono>
#include <cstdint>
#include <memory>

#include "library/in_memory_repository.hpp"
#include "library/service.hpp"

using namespace std::chrono;
using library::Book;
using library::BookId;
using library::Error;
using library::InMemoryRepository;
using library::Loan;
using library::LoanId;
using library::Member;
using library::MemberId;
using library::Repository;
using library::Service;

namespace {

struct Fixture {
    std::shared_ptr<Repository<Book, BookId>> books{
        std::make_shared<InMemoryRepository<Book, BookId>>()};
    std::shared_ptr<Repository<Member, MemberId>> members{
        std::make_shared<InMemoryRepository<Member, MemberId>>()};
    std::shared_ptr<Repository<Loan, LoanId>> loans{
        std::make_shared<InMemoryRepository<Loan, LoanId>>()};
    Service svc{books, members, loans};
    Date today = sys_days{year_month_day{year{2026}, month{10}, day{1}}};

    Fixture() {
        for (std::uint64_t i = 1; i <= 6; ++i) {
            books->save(Book{BookId{i}, "isbn-" + std::to_string(i),
                             "书" + std::to_string(i), "作者", 1});
        }
        members->save(Member{MemberId{1}, "张三"});
        members->save(Member{MemberId{2}, "李四"});
    }
};

}  // namespace

TEST_CASE("正常借书、库存随之减少") {
    Fixture f;
    auto r = f.svc.borrow(BookId{1}, MemberId{1}, f.today);
    REQUIRE(r.has_value());
    CHECK(f.svc.available_copies(BookId{1}).value_or(0) == 0);
}

TEST_CASE("借满上限后再借被拒") {
    Fixture f;
    for (std::uint64_t i = 1; i <= 5; ++i) {
        auto r = f.svc.borrow(BookId{i}, MemberId{1}, f.today);
        REQUIRE(r.has_value());
    }
    auto r6 = f.svc.borrow(BookId{6}, MemberId{1}, f.today);
    REQUIRE(!r6.has_value());
    CHECK(r6.error() == Error::MemberLoanLimit);
}

TEST_CASE("同一本书不能重复借") {
    Fixture f;
    CHECK(f.svc.borrow(BookId{1}, MemberId{1}, f.today).has_value());
    auto again = f.svc.borrow(BookId{1}, MemberId{1}, f.today);
    REQUIRE(!again.has_value());
    CHECK(again.error() == Error::DuplicateBorrow);
}

TEST_CASE("逾期归还按天算罚金") {
    Fixture f;
    auto loan = f.svc.borrow(BookId{2}, MemberId{2}, f.today);
    REQUIRE(loan.has_value());
    auto back = f.svc.give_back(loan.value(), f.today + days{35});
    REQUIRE(back.has_value());
    CHECK(back.value() == doctest::Approx(2.5));  // 超 5 天，每天 0.5 元
}

TEST_CASE("按期归还不产生罚金") {
    Fixture f;
    auto loan = f.svc.borrow(BookId{2}, MemberId{2}, f.today);
    REQUIRE(loan.has_value());
    auto back = f.svc.give_back(loan.value(), f.today + days{30});
    REQUIRE(back.has_value());
    CHECK(back.value() == 0.0);
}

TEST_CASE("续借一次后再续被拒，逾期不能续") {
    Fixture f;
    auto loan = f.svc.borrow(BookId{3}, MemberId{1}, f.today);
    REQUIRE(loan.has_value());

    auto r1 = f.svc.renew(loan.value(), f.today);
    REQUIRE(r1.has_value());
    CHECK(r1.value() == f.today + days{60});  // 30 天借期 + 再延 30

    CHECK(!f.svc.renew(loan.value(), f.today).has_value());

    auto loan2 = f.svc.borrow(BookId{4}, MemberId{1}, f.today);
    REQUIRE(loan2.has_value());
    CHECK(f.svc.renew(loan2.value(), f.today + days{31}).error() ==
          Error::RenewOverdue);
}
```

注意这些用例全靠"时间注入"才写得出来：逾期 35 天、按期 30 天归还，都是构造出来的日期，测试瞬间完成且结果确定。如果 Service 内部偷调了 `system_clock::now()`，这套测试一个都写不成。

### 22.3.14 构建与运行命令
{: .sec-prac}

完整流程四条命令：

```bash
cmake -B build -S . -DCMAKE_BUILD_TYPE=Release -DLIB_WITH_JSON=ON
cmake --build build -j           # Windows MSVC 加 --config Release
ctest --test-dir build --output-on-failure
./build/library_app
```

`-B build -S .` 是 out-of-source 构建的现代写法：源码树永远干净，build 目录删了重来零成本。`-DCMAKE_BUILD_TYPE=Release` 不给的话默认是空类型——没有优化、没有 NDEBUG，很多人遇到过"Debug 下 assert 触发、Release 下行为不同"，根子多在这。

### 22.3.15 CI：GitHub Actions 最小 workflow
{: .sec-prac}

最小够用的流水线两个 job：构建+测试、格式检查。放在 `.github/workflows/ci.yml`：

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 配置
        run: cmake -B build -S . -DCMAKE_BUILD_TYPE=Release

      - name: 构建
        run: cmake --build build -j

      - name: 测试
        run: ctest --test-dir build --output-on-failure

  format:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: clang-format 检查
        run: clang-format --dry-run --Werror $(git ls-files '*.cpp' '*.hpp')
```

`ctest --output-on-failure` 在用例挂掉时打印完整输出，没有它 CI 里只看到一行 FAIL，还得本地复现。格式检查用 `--dry-run --Werror`：不真改文件，不符合格式就以非零退出码挡住合并。测试框架走 FetchContent，CI 上第一次构建会自动拉取，不需要额外缓存也能跑，加了缓存只是更快。

### 22.3.16 代码规范落地：.clang-format 与 .clang-tidy
{: .sec-best}

格式交给工具，人只讨论设计。仓库根放两个文件，CI 的 format job 就有据可依：

```yaml
# .clang-format
BasedOnStyle: LLVM
IndentWidth: 4
ColumnLimit: 100
AllowShortFunctionsOnASingleLine: Inline
PointerAlignment: Left
SortIncludes: CaseInsensitive
```

```yaml
# .clang-tidy
Checks: >
  bugprone-*,
  performance-*,
  modernize-*,
  readability-*,
  cppcoreguidelines-*,
  -modernize-use-trailing-return-type,
  -cppcoreguidelines-avoid-magic-numbers
WarningsAsErrors: ''
FormatStyle: file
HeaderFilterRegex: 'include/.*'
```

clang-tidy 的规则别一上来全开——遗留代码上跑 `cppcoreguidelines-*` 会报出几千条，团队直接放弃治疗。从 `bugprone` 和 `performance` 两组起步（信噪比最高），稳定后再收紧。禁用项里的 `modernize-use-trailing-return-type` 是风格争论的重灾区，明确关掉省得每次都吵。

### 22.3.17 常见工程坑
{: .sec-ts}

收工前把这些坑排一遍，每条都来自真实项目：

| 坑 | 现象 | 规避 |
| --- | --- | --- |
| 头文件不自包含 | 单独 include 某个 .hpp 编译报错，得靠 include 顺序凑 | 每个头文件当独立翻译单元测：写个只 include 它的 .cpp 编一遍 |
| 循环依赖 | 两个头互相 include，或换编译顺序后炸 | 依赖方向单向（22.2.3），工具上用 include-graph 类脚本盯 |
| 编译时间失控 | 改一行头文件全量重编 | 接口瘦身、Pimpl、前置声明；模板重头放 .cpp 或显式实例化；上 ccache |
| 数据文件路径 | 本地能跑 CI 挂，或装到系统后找不到 data/ | 运行时路径不要依赖 CWD；用 `std::filesystem` 相对可执行文件定位，或配置项显式指定 |
| Release/Debug 行为差异 | Debug 正常 Release 崩（或反之） | NDEBUG 关掉 assert、优化重排暴露 UB、MSVC 迭代器检查只在 Debug 有；别在 assert 里写有副作用的表达式 |
| 日志与配置无约定 | 每人一套打印格式，配置散落各处 | 进程启动先加载配置、配置结构体集中定义；日志级别和格式第一天就定死 |

## 动手练
{: .sec-ex}

1. 给系统加"预留"用例：读者可以预留被借完的书，归还时若有预留则自动通知（打印即可）。先改用例表和错误枚举，再动 Service——体会"契约先行"。
2. 把 `JsonRepository` 接进 main，加 `-DLIB_WITH_JSON=ON` 构建一次，重启程序验证数据还在。想想 `data/` 目录应该怎么定位才不依赖工作目录。
3. 给 `Error` 换一种错误通道：改成异常（自定义异常类型），对比两种版本 main.cpp 的错误处理代码行数和可读性，写三句话结论。
4. 用 `cxxopts` 给 library_app 加 `--data-dir` 和 `--verbose` 参数，把数据目录从配置进程序里。
5. 在 CI 里加一个 sanitizer job：`-DCMAKE_CXX_FLAGS="-fsanitize=address,undefined"` 构建并跑测试，看看能不能抓到什么。

## 变式追问
{: .sec-think}

- **为什么 Repository 用模板接口而不是纯虚基类加 shared_ptr？** 两者都实现了"Service 依赖抽象"。模板版零虚表开销、类型全静态，但 Service 自己也得模板化，实例化在编译期展开；虚基类版 Service 保持具体类型，测试注入方便，代价是虚调用和堆分配。本工程实体小、调用频次低，虚表开销无所谓，选了更直白的模板头文件接口。如果 Service 想做成编译好的动态库发布给别人，虚基类（稳定 ABI）就是更对的选择——判断依据是"要不要跨编译单元稳定二进制接口"。
- **`next_loan_id_` 放在 Service 里合适吗？** 单进程单实例没问题。并发或多实例就不合适了：两个 Service 对象会发出重复的 LoanId。正确方向是把 ID 生成下沉到 Repository（数据库自增主键的角色），或者用时间戳+随机的 UUID 式方案。这个设计缺口是故意留的，面试里"你哪里设计得不够好"比"你哪里好"更能看出层次。
- **为什么罚金用 double？金额用浮点不是经典错误吗？** 是经典错误，但本工程罚金只是展示输出、不参与累计结算，0.5 元/天 × 整数天数在 double 里精确。真要记账（累加、对账），就该以"分"为单位的整数类型，或者定点数库。判断标准是"参与不等式比较和累加吗"，不是"涉及钱就绝对不能用浮点"。
- **如果不做 CI，只靠本地跑测试，最大的风险是什么？** 不是"测试没人跑"，而是"测试悄悄失效"——某次重构把一个用例注释了、某个测试环境变量没设导致整组 SKIP，没人发现。CI 的价值是把"测试通过"从个人自觉变成机器强制，失败可见、合并被挡。哪怕就一个 build-test job，也比零 CI 强一个量级。
