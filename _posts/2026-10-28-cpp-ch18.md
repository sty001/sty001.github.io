## 18.1 什么是异常处理
{: .sec-expl}

### 18.1.1 错误传递三流派
{: .sec-know}

函数调用可能失败，失败信息总要传给调用方。C++ 世界里只有三种主流做法：

| 流派 | 典型形态 | 错误不可避免吗 | 开销位置 | 代表场景 |
| --- | --- | --- | --- | --- |
| 返回错误码 | `int rc = do_work(); if (rc != 0)` | 忘了检查就静默吞掉 | 正常路径几乎为零 | C 接口、内核、驱动 |
| 异常 | `try { do_work(); } catch (const std::exception& e)` | 不 catch 就往上飞，最后 terminate | 正常路径约零，抛出路径贵 | 构造函数、无法返回值的场合 |
| 值类型承载结果 | `std::expected<int, Error>` / `std::optional<int>` | 编译器逼你处理（有 `[[nodiscard]]` 时） | 正常路径一个小结构体 | 解析、查找、网络请求 |

三种流派处理的是两类不同的失败。返回值流派擅长"可预期的失败"——用户输错了格式、文件不存在、查询没命中，这类错误是业务流程的一部分。异常流派擅长"罕见且必须打断当前流程的失败"——构造函数没法返回错误码，new 分不出内存没法假装没事。把两类失败混为一谈是错误处理设计的头号病根：用异常表达"用户输错了"会让控制流像跳蚤一样乱跳，用返回码表达"内存耗尽"会让每个调用点都堆满没人看的 if。

写过 Java 或 Python 的人都懂一个体验：异常用起来爽，但"哪些函数会抛什么"全靠文档和运气。C++ 用 `noexcept` 把"这个函数保证不抛"写进了类型系统，算是给异常补上了契约的一角。

### 18.1.2 同一功能的三种写法
{: .sec-prac}

```cpp
// three_ways.cpp —— 需要 -std=c++20
#include <charconv>
#include <iostream>
#include <optional>
#include <stdexcept>
#include <string>
#include <string_view>
#include <system_error>

// 流派一：返回错误码。错误码与合法值共用返回通道，0 表示成功
int parse_by_code(std::string_view s, int& out) {
    if (s.empty()) return -1;                      // 自己定义错误码
    const char* first = s.data();
    const char* last  = s.data() + s.size();
    auto [ptr, ec] = std::from_chars(first, last, out);
    if (ec != std::errc{}) return -2;              // 标准库的 errc 错误码
    if (ptr != last) return -3;                    // 尾部有垃圾字符
    return 0;
}

// 流派二：异常。合法值和错误分走两条通道
int parse_by_throw(std::string_view s) {
    if (s.empty()) throw std::invalid_argument("空字符串");
    int v = 0;
    for (char c : s) {
        if (c < '0' || c > '9') throw std::invalid_argument("非法字符");
        v = v * 10 + (c - '0');
    }
    return v;
}

// 流派三：expected（C++23）。成功值和错误值打包在一个返回类型里
// 需要 -std=c++23 编译（本文件整体用 c++20，此函数仅作展示，见文末编译命令说明）
// std::expected<int, std::string> parse_by_expected(std::string_view s);

int main() {
    int out = 0;
    int rc = parse_by_code("42x", out);
    if (rc != 0) std::cout << "返回码流派: 失败 rc=" << rc << '\n';

    try {
        std::cout << "异常流派: " << parse_by_throw("42") << '\n';
        parse_by_throw("4x");
    } catch (const std::invalid_argument& e) {
        std::cout << "异常流派: 失败 " << e.what() << '\n';
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra three_ways.cpp -o tw && ./tw
```

```text
# Linux g++ 12 下的输出
返回码流派: 失败 rc=-3
异常流派: 42
异常流派: 失败 非法字符
```

三种写法的信息量差异一眼可见：返回码把"哪种失败"压进一个整数，异常把人类可读的 `what()` 和精确类型都带出来，expected 则把错误类型显式写进函数签名，调用方看声明就知道会发生什么。

### 18.1.3 选型决策表
{: .sec-best}

| 场景 | 推荐流派 | 理由 |
| --- | --- | --- |
| 构造函数失败 | 异常 | 构造函数没有返回值可用 |
| 用户输入校验、参数解析 | 返回值（expected/optional） | 高频可预期失败，不该打断流程 |
| 内存耗尽、不变量被破坏 | 异常 | 罕见且无法在本地处理 |
| 与 C 代码或 ABI 边界交互 | 错误码 | 异常穿不过 C 栈帧（见 18.5） |
| 嵌入式、实时、禁用异常的项目 | 错误码或 expected | 工具链常配 `-fno-exceptions` |
| 查找可能不存在的东西 | `optional` | "没有"不是错误，是正常结果 |
| 需要携带丰富上下文的结构化错误 | expected + 自定义 Error 类型 | 错误类型进签名，调用方看得见 |
| GUI/服务顶层兜底 | 异常 + `catch(...)` 记日志 | 最后一道防线必须存在 |

一句话版本：**错误是流程的一部分就用返回值，错误意味着"此路不通请撤退"就用异常**。

### 辨析：异常与 std::expected
{: .sec-iv}

两者都能表达"失败"，差别在控制流。异常把失败处理代码放到别处（catch 块），正常逻辑一条直线读到底，代价是控制流变得不可见——看函数体猜不出哪里会跳走。expected 把失败留在返回值里，调用点必须拆包才能拿到结果，代码啰嗦但每一步的失败可能都写在明面上。经验法则是：失败概率低、失败后整个操作作废的场景用异常；失败概率不低、失败后可以就地补偿的场景用 expected。HTTP 客户端请求超时用 expected，配置文件读不到用异常，多数团队都能接受这个划分。

## 18.2 C++的异常处理机制
{: .sec-know}

### 18.2.1 try/throw/catch 三件套
{: .sec-expl}

三个关键字各司其职。`throw` 表达式把一个对象（异常对象）抛出去；`try` 块圈定"这段代码抛的异常归我管"；`catch` 子句按类型匹配接住异常对象。编译器不为每个 try 块生成跳转代码，而是在编译期生成静态表（Itanium ABI 下是 `.eh_frame` 和 LSDA），运行期抛异常时沿表回溯找匹配的 catch——这就是"零成本模型"的来历，细节见 18.4。

异常对象在 throw 时构造，由运行时负责存储与析构（标准没规定存哪里，主流实现放在堆上），最后一个 catch 块退出时销毁。catch 的类型匹配规则和函数重载不完全一样：只做基类到派生类的单向匹配——catch 基类能接住派生类异常，反过来不行。

### 18.2.2 栈展开：异常飞过的每一步
{: .sec-know}

从 throw 点到匹配的 catch 点之间，运行时会做一件大事：**栈展开（stack unwinding）**。过程分四步：

1. throw 处构造异常对象，记录抛出点；
2. 沿调用链向外逐层退出当前函数，每退一层，销毁该层所有已构造的局部对象（按构造的逆序）；
3. 每退出一层，检查该层是否有能匹配异常类型的 catch 子句；
4. 找到匹配的 catch，跳过去执行，栈展开结束；找不到就一直退到 main 之外，调用 `std::terminate`。

第 2 步是整个机制的灵魂：**栈展开期间，每个已完整构造的局部对象的析构函数都保证会被调用**。没有这条保证，RAII 就不成立——锁不敢上、文件不敢开、内存不敢 new。

### 18.2.3 看着析构函数跑一遍栈展开
{: .sec-prac}

```cpp
// unwinding.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

class Tracer {
    std::string name_;
public:
    explicit Tracer(std::string name) : name_(std::move(name)) {
        std::cout << "构造 " << name_ << '\n';
    }
    ~Tracer() {
        std::cout << "析构 " << name_ << '\n';
    }
};

void level3() {
    Tracer t3("level3");
    throw std::runtime_error("从 level3 抛出");   // 抛出点
}

void level2() {
    Tracer t2("level2");
    level3();                                     // 异常从这里继续往外飞
}

void level1() {
    Tracer t1("level1");
    level2();
}

int main() {
    std::cout << "进入 try\n";
    try {
        level1();
        std::cout << "这行永远执行不到\n";
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
    std::cout << "正常继续\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra unwinding.cpp -o uw && ./uw
```

```text
# Linux g++ 12 下的输出
进入 try
构造 level1
构造 level2
构造 level3
析构 level3
析构 level2
析构 level1
捕获: 从 level3 抛出
正常继续
```

析构严格按构造的逆序发生：level3 → level2 → level1。try 块里 throw 之后的代码、level3 里 throw 之后的代码全部跳过。

### 18.2.4 按引用捕获：按值捕获会切片
{: .sec-warn}

catch 子句写参数和写函数参数一样自由，但选择余地是假的——**异常对象是多态的，按值捕获基类会发生对象切片**，派生类的数据成员全部丢失，virtual 函数也退化成基类版本。更隐蔽的是，切片后的对象已不是原始异常对象，`throw e;` 重新抛出的会是一个新的基类对象。

```cpp
// slicing.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

struct MyError : std::runtime_error {
    int code;
    MyError(const std::string& msg, int c) : std::runtime_error(msg), code(c) {}
};

int main() {
    // 反面教材：按值捕获基类，切片。GCC 的 -Wall 会给出 -Wcatch-value 警告
    try {
        try {
            throw MyError("原始异常", 42);
        } catch (std::runtime_error e) {          // 按值：code 已经被切掉
            std::cout << "按值捕获: " << e.what() << '\n';
            throw e;                               // 重新抛出 runtime_error，类型也退化了
        }
    } catch (const MyError& e) {
        std::cout << "捕获到 MyError: code=" << e.code << '\n';
    } catch (const std::exception& e) {
        std::cout << "退而捕获基类: " << e.what() << "（code 丢了）\n";
    }

    // 正确写法：const 引用捕获 + throw; 裸重抛
    try {
        try {
            throw MyError("再来一次", 7);
        } catch (const std::exception& e) {       // 引用：多态保留
            std::cout << "引用捕获: " << e.what() << '\n';
            throw;                                  // 保留原始异常对象的类型与内容
        }
    } catch (const MyError& e) {
        std::cout << "捕获到 MyError: code=" << e.code << '\n';
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra slicing.cpp -o sl && ./sl
```

```text
# Linux g++ 12 下的输出（第一条会伴随 -Wcatch-value 编译警告，属教学故意为之）
按值捕获: 原始异常
退而捕获基类: 原始异常（code 丢了）
引用捕获: 再来一次
捕获到 MyError: code=7
```

`throw;` 和 `throw e;` 的差别一句话说清：**`throw;` 重抛当前正在处理的异常对象本身，类型、内容、抛出点全保留；`throw e;` 用 e 拷贝构造一个新异常对象再抛，e 的静态类型是什么就抛什么**。在按引用捕获的 catch 里 `throw e;` 依然会把 MyError 切成 e 的静态类型。

### 18.2.5 捕获顺序：派生类在前
{: .sec-know}

catch 子句按源码出现顺序依次尝试匹配，第一个匹配上的生效，后面的全部跳过。所以派生类 catch 必须写在基类前面——写反了派生类子句就是永远执行不到的死代码，编译器未必报错，只能靠代码评审抓。

```cpp
// catch_order.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>

int main() {
    try {
        throw std::out_of_range("下标越界");   // 层次: exception <- logic_error <- out_of_range
    } catch (const std::out_of_range& e) {     // 派生类在前
        std::cout << "out_of_range: " << e.what() << '\n';
    } catch (const std::logic_error& e) {
        std::cout << "logic_error: " << e.what() << '\n';
    } catch (const std::exception& e) {
        std::cout << "exception: " << e.what() << '\n';
    }
}
```

```text
# Linux g++ 12 下的输出
out_of_range: 下标越界
```

### 18.2.6 catch(...)：兜底可以，吞异常不行
{: .sec-pit}

`catch (...)` 能接住任何类型的异常，包括 `throw 42;` 这种抛整数的野路子。它的正当用途有两个：线程入口的最外层兜底（配合 `std::current_exception` 转存，见 18.4），以及析构函数里"绝不能让异常飞出去"的清理逻辑。除此之外它最大的贡献是制造事故——catch 住之后既不处理也不重抛，异常就这么无声无息地消失了，错误现场连尸检报告都没有。

```cpp
// swallow.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>

void work() {
    try {
        throw std::runtime_error("底层错误");
    } catch (...) {
        std::cout << "记录日志、清理现场，然后必须继续往上抛\n";
        throw;    // 裸重抛。删掉这一行，调用方将永远不知道出过错
    }
}

int main() {
    try {
        work();
    } catch (const std::exception& e) {
        std::cout << "顶层捕获: " << e.what() << '\n';
    }
}
```

```text
# Linux g++ 12 下的输出
记录日志、清理现场，然后必须继续往上抛
顶层捕获: 底层错误
```

> **坑：** `catch (...) {}` 加一句日志就完事，是生产事故的经典配方。兜底 catch 的正确姿势是"记日志 + 转 exception_ptr 存档 + `throw;` 重抛"三件套，除非你明确决定这个异常就此终结（比如进程即将退出）。
{: .sec-pit}

### 辨析：catch(const std::exception&) 与 catch(...)
{: .sec-iv}

前者只接住"讲规矩"的异常——继承自 `std::exception` 的那一族，能用 `what()` 拿到信息。后者连 `throw 42;`、`throw "oops";` 这种不继承标准层次的异常也接。第三方库（尤其 C 包装层）偶尔会抛非标准异常，程序顶层用 `catch(...)` 兜底是合理的；业务代码里优先用 `catch (const std::exception&)`，类型信息是可用的。两者常常一起出现在顶层：先 `catch (const std::exception&)`，再 `catch (...)`。

## 18.3 异常处理中的构造和析构
{: .sec-know}

### 18.3.1 栈展开的析构保证：RAII 的地基
{: .sec-know}

18.2 已经演示了局部对象在栈展开时的析构顺序，这里把保证的边界说精确：

- **已完整构造**的局部对象，析构函数保证执行；
- **半成品不析构自己**——构造函数体里抛异常时，"这个对象自己"从未存在过，它的析构函数不会被调用（细节见 18.3.2）；
- 析构调用顺序与构造顺序严格相反；
- 栈展开期间新抛出的异常没有退路，直接 `std::terminate`（见 18.3.3）。

> **注意：** 只有自动存储期（栈上）对象享受这个保证。堆上对象靠智能指针/容器这些"栈对象"间接获得保护——`std::unique_ptr` 本身是栈对象，栈展开时它的析构函数执行，进而 delete 堆上资源。这层间接性就是 RAII 的全部秘密。
{: .sec-note}

### 18.3.2 构造函数抛异常：自己不析构，成员会析构
{: .sec-prac}

对象构造分两个阶段：先按声明顺序构造基类和成员，再执行构造函数体。构造函数体里抛异常时，对象被视为"从未构造完成"，自己的析构函数不会执行——但**已经构造完成的成员和基类会按逆序析构**，这部分资源不会泄漏。

```cpp
// ctor_throw.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

struct Member {
    std::string name_;
    explicit Member(std::string n) : name_(std::move(n)) {
        std::cout << "构造 " << name_ << '\n';
    }
    ~Member() {
        std::cout << "析构 " << name_ << '\n';
    }
};

struct Widget {
    Member a{"a"};              // 成员按声明顺序构造：先 a 后 b
    Member b{"b"};
    Widget() {
        std::cout << "Widget 构造函数体开始\n";
        throw std::runtime_error("构造失败");   // 此时 a、b 已构造完成
    }
    ~Widget() {
        std::cout << "Widget 析构（永远不会执行）\n";
    }
};

int main() {
    try {
        Widget w;
    } catch (const std::exception& e) {
        std::cout << "捕获: " << e.what() << '\n';
    }
}
```

### 18.3.3 析构函数不应抛异常
{: .sec-warn}

C++11 起，所有析构函数默认隐式 `noexcept(true)`——除非类成员的析构函数声明为可能抛出。这个默认值背后是硬道理：**栈展开过程中每个局部对象都要析构一遍，如果某个析构函数此刻又抛出新异常，两个异常同时在飞，运行时无法抉择，直接 `std::terminate`**。标准把这定为 UB，主流实现的表现就是终止程序。

```cpp
// dtor_throw.cpp —— 需要 -std=c++20
// 危险演示：运行结果为 abort（terminate），不是正常退出
#include <iostream>
#include <stdexcept>

struct BadGuard {
    ~BadGuard() noexcept(false) {          // 显式声明析构可以抛——坏主意
        throw std::runtime_error("析构中抛出");
    }
};

int main() {
    try {
        BadGuard g;
        throw std::runtime_error("原始异常");   // 触发栈展开，期间析构 g
    } catch (const std::exception& e) {
        std::cout << "抓到: " << e.what() << '\n';   // 永远到不了
    }
}
```

### 18.4.1 异常规格的演进：从 throw() 到 noexcept
{: .sec-know}

C++98 提供过动态异常规格：`void f() throw(int, std::string);` 表示 f 只可能抛这两种异常，违反则在运行期调用 `unexpected`。实践证明这套机制开销大、检查时机太晚、和模板组合后基本无法维护，于是：动态异常规格在 **C++11 被标记废弃，C++17 彻底移除**（`throw(X)` 语法不能再编译）；`throw()` 这个空规格在 **C++17 里等价于 `noexcept(true)`**，并在 **C++20 彻底移除**。现代代码里唯一合法且应使用的形式是 `noexcept`。

`noexcept` 有两个身份，别混淆：

- **noexcept 说明符**：`void f() noexcept;` 承诺 f 不抛异常。违反承诺（异常逃出 f）不是未定义行为，而是直接 `std::terminate`——运行时不会展开栈去找别的 catch。
- **noexcept 运算符**：`noexcept(expr)` 是编译期常量表达式，判断 expr 是否声明为不抛。它不改任何行为，只做查询。

```cpp
// noexcept_op.cpp —— 需要 -std=c++20
#include <iostream>
#include <utility>

void may_throw();
void never_throws() noexcept;

struct A {
    A() = default;
    A(A&&) noexcept {}          // 移动构造标记 noexcept
};
struct B {
    B() = default;
    B(B&&) {}                    // 移动构造没标
};

int main() {
    std::cout << std::boolalpha;
    std::cout << noexcept(may_throw()) << '\n';      // false
    std::cout << noexcept(never_throws()) << '\n';   // true
    std::cout << noexcept(A(std::declval<A&&>())) << '\n';  // true
    std::cout << noexcept(B(std::declval<B&&>())) << '\n';  // false
}
```

### 18.4.2 移动构造与 swap 为什么必须 noexcept
{: .sec-know}

`std::vector` 扩容时要把旧元素搬到新内存。搬家用移动构造本来更快，但有个隐患：如果搬了一半移动构造抛异常，旧数据已经被破坏，强异常安全就没了。标准库的对策是：**移动构造函数标记了 `noexcept` 才用移动，否则退回拷贝**（前提是拷贝构造可用）——拷贝失败时旧数据原封不动，强保证得以维持。这就是"移动构造不标 noexcept，vector 就悄悄变慢"的完整因果链。`std::swap`、`unique_ptr` 的移动同理，它们都依赖 `std::move_if_noexcept` 这类机制做决策。

```cpp
// vector_realloc.cpp —— 需要 -std=c++20
#include <iostream>
#include <vector>

struct MoveNoexcept {
    MoveNoexcept() = default;
    MoveNoexcept(const MoveNoexcept&) { std::cout << 'C'; }
    MoveNoexcept(MoveNoexcept&&) noexcept { std::cout << 'M'; }
};

struct MoveThrowing {
    MoveThrowing() = default;
    MoveThrowing(const MoveThrowing&) { std::cout << 'c'; }
    MoveThrowing(MoveThrowing&&) { std::cout << 'm'; }   // 没标 noexcept
};

int main() {
    std::vector<MoveNoexcept> v1;
    v1.reserve(1);
    v1.emplace_back();
    v1.emplace_back();        // 扩容触发搬移：移动安全，用移动
    std::cout << '\n';

    std::vector<MoveThrowing> v2;
    v2.reserve(1);
    v2.emplace_back();
    v2.emplace_back();        // 扩容触发搬移：移动可能抛，退回拷贝
    std::cout << '\n';
}
```

### 18.4.3 异常安全三保证与 copy-and-swap
{: .sec-know}

写"异常经过时依然正确"的代码，标准把承诺强度分三档：

| 保证级别 | 承诺内容 | 实现难度 |
| --- | --- | --- |
| 不抛保证（nothrow） | 函数绝不抛异常 | 移动构造、swap、析构应达到此级 |
| 强保证（strong） | 要么成功，要么状态回滚到调用前，如同没调用过 | copy-and-swap、事务式修改 |
| 基本保证（basic） | 不泄漏资源、不变量不破坏，但状态可能改变 | 默认应达到的底线 |

强保证的经典实现是 **copy-and-swap**：先把要改的东西在副本上改（副本上随便折腾，改失败原数据无损），全部成功后用不抛的 swap 一步换入。代码骨架：

```cpp
// copy_and_swap.cpp —— 需要 -std=c++20
#include <iostream>
#include <memory>
#include <stdexcept>
#include <utility>

class Buffer {
    std::unique_ptr<int[]> data_;
    std::size_t size_;
public:
    Buffer(std::size_t n) : data_(std::make_unique<int[]>(n)), size_(n) {}

    void fill_from(const int* src, std::size_t n) {
        // 强保证：先在临时副本上做所有可能失败的工作
        Buffer tmp(n);
        for (std::size_t i = 0; i < n; ++i) {
            if (src[i] < 0) throw std::invalid_argument("负值");
            tmp.data_[i] = src[i];
        }
        // 到这里不可能再抛，swap 是不抛操作，一步提交
        swap(tmp);
    }

    void swap(Buffer& other) noexcept {
        std::swap(data_, other.data_);
        std::swap(size_, other.size_);
    }
};

int main() {
    Buffer b(4);
    int good[] = {1, 2, 3, 4};
    int bad[]  = {1, -2, 3, 4};
    try {
        b.fill_from(good, 4);
        std::cout << "第一次填充成功\n";
        b.fill_from(bad, 4);          // 抛异常，但 b 保持第一次的数据
    } catch (const std::exception& e) {
        std::cout << "失败但 b 未被破坏: " << e.what() << '\n';
    }
}
```


### 18.4.4 标准异常层次与自定义异常
{: .sec-know}

标准库的异常族谱以 `std::exception` 为根：

| 层次 | 代表异常 | 语义 |
| --- | --- | --- |
| `std::exception` | 所有标准异常的根 | `what()` 提供错误描述 |
| `std::logic_error` 及派生 | `invalid_argument`、`out_of_range`、`length_error` | 编码期可预防的错误，调用方违反契约 |
| `std::runtime_error` 及派生 | `overflow_error`、`range_error` | 运行期才暴露的错误 |
| `std::bad_alloc`（`<new>`） | `bad_array_new_length` | 内存分配失败 |
| 其他独立根 | `std::bad_cast`、`std::bad_variant_access`、`std::bad_optional_access` | 语言/库机制触发的错误 |

`what()` 返回 `const char*`，指向异常对象内部的字符串，有效性只保证到 catch 块结束——**别把指针存下来留着后用，要存就拷成 `std::string`**。

自定义异常的正确写法：继承 `std::runtime_error`（或 `logic_error`，按语义选），构造时把完整描述拼好传给基类，额外的结构化字段用自己的成员承载。反模式是继承 `std::exception` 后自己管理一个栈上缓冲区或局部对象地址——`what()` 指向的内容会悬空。

```cpp
// custom_exception.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

class NetworkError : public std::runtime_error {
public:
    enum class Code { Timeout, Refused, DnsFailed };

    NetworkError(Code c, const std::string& detail)
        : std::runtime_error(to_text(c) + ": " + detail), code_(c) {}

    Code code() const noexcept { return code_; }   // 结构化信息走成员，不进 what()

private:
    static std::string to_text(Code c) {
        switch (c) {
            case Code::Timeout:   return "超时";
            case Code::Refused:   return "连接被拒";
            case Code::DnsFailed: return "域名解析失败";
        }
        return "未知";
    }
    Code code_;
};

void connect_server() {
    throw NetworkError(NetworkError::Code::Timeout, "10.0.0.8:443");
}

int main() {
    try {
        connect_server();
    } catch (const NetworkError& e) {              // 先接派生类
        std::cout << e.what() << "，错误码 " << static_cast<int>(e.code()) << '\n';
    } catch (const std::exception& e) {            // 兜底
        std::cout << "其他异常: " << e.what() << '\n';
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra custom_exception.cpp -o ce && ./ce
```


> **坑：** `throw &local_obj;` 这类抛指针的写法等于埋雷——栈展开会销毁 local_obj，catch 到的是悬空指针。异常对象的生命周期由运行时管理，抛对象（或对象引用）永远是对的。
{: .sec-pit}

### 18.4.5 异常的性能成本：零成本模型的真相
{: .sec-expl}

主流实现（Itanium ABI，GCC/Clang）采用**表驱动展开**：编译器为可能抛异常的函数生成静态的展开表（`.eh_frame` 与 LSDA），正常运行路径上一条额外指令都不执行，这就是"零成本"的含义——零的是正常路径的成本，不是异常路径的。抛一次异常要查表、逐帧展开、析构沿途对象、构造异常对象（含其中的字符串），代价通常在微秒级，比一次函数调用高四个数量级左右。Windows 的 SEH 机制不同，是操作系统参与的两阶段展开，正常路径同样接近零开销，但代码布局的间接成本略有差异。

由此推出三条工程结论：

- 热循环里用异常表达"每迭代都发生的失败"是性能自杀，那种场景用返回值；
- 异常路径偶发（请求失败率 1% 之类）时，成本完全可忽略；
- 异常会增加二进制体积（展开表 + 展开代码），`-fno-exceptions` 编译能显著减小体积，这是嵌入式与游戏行业禁用异常的主要动机之一——但禁用后标准库接口（`std::stoi`、`new`）会直接 terminate，必须整体设计错误传递策略。

### 18.4.6 跨线程异常传递：exception_ptr
{: .sec-know}

异常无法自己飞过线程边界——工作线程里没接住的异常直接 terminate 整个进程。标准给的搬运工具是 `std::exception_ptr`：`std::current_exception()` 在 catch 块里把当前异常打包成可拷贝的指针，`std::rethrow_exception(ptr)` 在另一个线程原样重抛（类型与内容都保留）。

```cpp
// exception_ptr.cpp —— 需要 -std=c++20
#include <exception>
#include <iostream>
#include <stdexcept>
#include <thread>

int main() {
    std::exception_ptr eptr;

    std::thread worker([&eptr] {
        try {
            throw std::runtime_error("工作线程里的错误");
        } catch (...) {
            eptr = std::current_exception();   // 打包带走
        }
    });
    worker.join();

    if (eptr) {
        try {
            std::rethrow_exception(eptr);      // 主线程原地重抛
        } catch (const std::exception& e) {
            std::cout << "主线程捕获: " << e.what() << '\n';
        }
    }
}
```

### 18.4.7 system_error：错误码与异常的桥梁
{: .sec-know}

C++11 引入的 `std::system_error` 体系解决一个历史问题：errno、Windows GetLastError、各类自定义错误码全是整数，跨平台比较毫无意义。它的拆解方式是把"原始错误码"配一个"错误类别"：`std::error_code` = 原始值 + `error_category`（系统相关）；`std::error_condition` = 可移植值 + 类别（系统无关）。两者比较时走类别的等价映射，所以 Linux 的 EACCES 和 Windows 的 ERROR_ACCESS_DENIED 都能匹配 `std::errc::permission_denied`。文件系统库、线程库的失败都通过这套体系报告：要么抛 `std::system_error`（内部打包 error_code），要么直接返回 error_code 让调用方自选。

```cpp
// system_error.cpp —— 需要 -std=c++20
#include <cerrno>
#include <iostream>
#include <system_error>

int main() {
    // 直接构造一个可移植条件码
    std::error_code ec = std::make_error_code(std::errc::permission_denied);
    std::cout << ec.message() << " (value=" << ec.value()
              << ", category=" << ec.category().name() << ")\n";

    // 把 errno 包装成 error_code
    errno = ENOENT;
    std::error_code from_errno(errno, std::generic_category());

    // error_code 与 errc 的比较走 error_condition 等价映射，跨平台成立
    if (from_errno == std::errc::no_such_file_or_directory) {
        std::cout << "匹配可移植条件: " << from_errno.message() << '\n';
    }
}
```

### 18.4.8 std::expected（C++23）：把错误写进函数签名
{: .sec-ext}

`std::expected<T, E>` 是"要么装着 T，要么装着 E"的词汇类型，C++23 进标准（`<expected>` 头文件，GCC 13 起可用）。它和 `std::optional` 的分工：optional 只能表达"没有值"，说不清为什么；expected 一定携带错误值 E，适合需要把失败原因传给调用方的场景。它还提供链式算子，让错误传递代码像管道一样展开。

```cpp
// expected_demo.cpp —— 需要 -std=c++23（GCC 13 或更新）
#include <expected>
#include <iostream>
#include <string>

std::expected<int, std::string> parse_int(const std::string& s) {
    if (s.empty()) return std::unexpected(std::string("空字符串"));
    int v = 0;
    for (char c : s) {
        if (c < '0' || c > '9')
            return std::unexpected(std::string("非法字符: ") + c);
        v = v * 10 + (c - '0');    // 演示用，超长输入会溢出
    }
    return v;
}

int main() {
    // 基本用法：if 判真、operator* 取值、error() 取错误
    if (auto a = parse_int("42")) {
        std::cout << "a = " << *a << '\n';
    }
    if (auto b = parse_int("4x2"); !b) {
        std::cout << "b 失败: " << b.error() << '\n';
    }

    // 链式：and_then 接返回 expected 的函数，transform 做纯变换
    auto c = parse_int("21")
        .and_then([](int v) -> std::expected<int, std::string> { return v * 2; })
        .transform([](int v) { return v + 1; });
    std::cout << "c = " << *c << '\n';

    // or_else 在失败侧补救；value_or 提供兜底默认值
    auto d = parse_int("oops").or_else([](std::string e)
        -> std::expected<int, std::string> {
        std::cout << "补救中: " << e << '\n';
        return -1;
    });
    std::cout << "d = " << *d << '\n';
    std::cout << "value_or(0) = " << parse_int("bad").value_or(0) << '\n';
}
```

```text
value_or(0) = 0
```

链式算子的分工记一组对照就够了：`and_then` 接"返回 expected 的函数"（可继续失败），`transform` 接"返回普通值的函数"（成功路径的加工），`or_else`/`transform_error` 是前两者在失败侧的对应物。

### 18.4.9 static_assert 与 assert 的分工
{: .sec-know}

两个断言一个在编译期一个在运行期，分工不能混：

- `static_assert(常量表达式, 消息)`（C++11；C++17 起消息可省）：编译期检查，失败即编译错误，零运行期成本。用于平台假设、模板约束、常量校验。
- `assert(表达式)`（`<cassert>`）：运行期检查，`#define NDEBUG` 后整个消失。用于只有运行时才知道的值。

```cpp
// asserts.cpp —— 需要 -std=c++20
#include <cassert>
#include <cstdint>
#include <iostream>

static_assert(sizeof(int) >= 4, "本代码假设 int 至少 4 字节");
static_assert(sizeof(void*) == 8, "仅支持 64 位平台");

int parse(const char* s) {
    assert(s != nullptr && "s 不能为空");    // 发布版（-DNDEBUG）里不存在
    int v = 0;
    while (*s) v = v * 10 + (*s++ - '0');
    return v;
}

int main() {
    std::cout << parse("123") << '\n';
}
```

```text
# Linux g++ 12 下的输出
123
```

区别不只有时机。assert 是调试工具，发布版里连表达式都不会求值，所以 assert 里不能放有副作用的代码；static_assert 是契约工具，永远生效，宁可多写别省。用 assert 检查"调用方传参错误"是偷懒——那应该用异常或返回值处理，assert 只负责抓程序自身的逻辑漏洞。

### 18.4.10 契约（contracts）现状
{: .sec-ext}

`pre`/`post`/`contract_assert` 这套契约机制 C++20 周期曾纳入草案，后因实现经验不足被整体移除；C++26 周期里 P2900 提案已重新进入标准草案，语法与语义都经过大幅重设计。截至本文写作时，主流编译器的完整支持仍在推进中——生产代码先别依赖，前置条件检查继续用 static_assert（编译期）加 assert 或手工 if（运行期）的组合。

## 18.5 技术解惑
{: .sec-ts}

### 18.5.1 new 失败了会怎样
{: .sec-know}

`new` 表达式分配失败默认抛 `std::bad_alloc`，不是返回空指针——这是和 C 的 `malloc` 最重要的行为差异之一。想拿返回值风格就用 placement 形式的 nothrow 版本 `new (std::nothrow) T`，失败返回 nullptr。请求的数组尺寸大到离谱（超过实现上限）会抛 `std::bad_array_new_length`。想全局改行为可以重载 `operator new`，想局部改行为可以写 `set_new_handler` 设置分配失败时的回调。

### 18.5.2 异常穿过 C 回调：直接 terminate
{: .sec-warn}

C 函数（比如 `qsort` 的比较器、SQLite 的回调）的代码没有异常展开所需的元数据，异常试图穿过这类栈帧属于 undefined behavior，主流实现的表现是 `std::terminate` 或直接崩溃。规矩很简单：**传给 C 的回调一律是"异常防火墙"**——回调体用 try/catch 把所有异常拦住，转换成错误码或标志位再返回。

```cpp
// c_boundary.cpp —— 需要 -std=c++20
#include <cstdlib>
#include <iostream>

int compare(const void* a, const void* b) {
    int x = *static_cast<const int*>(a);
    int y = *static_cast<const int*>(b);
    // 这里绝不能 throw：qsort 是 C 函数，异常穿过去就是 UB
    return (x > y) - (x < y);
}

int main() {
    int arr[] = {3, 1, 2};
    std::qsort(arr, 3, sizeof(int), compare);
    std::cout << arr[0] << arr[1] << arr[2] << '\n';
}
```

```text
# Linux g++ 12 下的输出
123
```

### 18.5.3 常见坑清单
{: .sec-pit}

| 坑 | 症状 | 规避 |
| --- | --- | --- |
| 按值捕获异常 | 切片，派生类信息丢失 | 一律 `catch (const T&)` |
| `throw e;` 重抛 | 类型退化为 e 的静态类型 | 用 `throw;` |
| catch 后不重抛 | 异常被静默吞掉 | 兜底 catch 必须转存或重抛 |
| 派生类 catch 放基类后面 | 死代码 | 派生类在前 |
| 析构函数抛异常 | 栈展开时 terminate | 析构只做不失败的操作 |
| noexcept 函数抛异常 | 直接 terminate | 标 noexcept 前想清楚 |
| 移动构造不标 noexcept | vector 扩容退化为拷贝 | 移动构造、swap 一律 noexcept |
| 异常穿 C 回调 | UB / terminate | 回调内 try/catch 拦截 |
| 存下 `what()` 指针长期用 | catch 结束后悬空 | 拷成 `std::string` |
| 抛局部对象指针 | 悬空指针 | 抛对象，不抛指针 |
| 构造函数裸指针成员 | 中途抛异常泄漏 | 成员用智能指针/容器 |
| 正常路径高频抛异常 | 性能塌方 | 高频可预期失败用返回值 |

## 变式追问
{: .sec-think}

**问：catch 块里再抛异常，会跟原异常冲突吗？**

不会。进入 catch 块时栈展开已经结束，原异常处于"正在处理"状态；此时再 throw 是发起一次全新的抛出，正常走栈展开找下一个 catch。容易混淆的是析构函数——析构是在展开过程中被调用的，它抛异常才是"两个异常同时飞"。分界线是展开是否已结束。

**问：`noexcept` 加得越多越好吗？**

不是。noexcept 是承诺，不是优化提示——标了之后哪天函数改成可能抛的实现，违约就是 terminate。该标的是确实不会抛的：移动构造、swap、析构、纯内存操作。判断依据是 `noexcept(表达式)` 运算符，能自动推导就写 `noexcept(noexcept(成员函数调用))` 这种条件形式，让承诺跟着成员走。拿不准就别标，错误成本不对称。

**问：既然异常这么贵，全项目改用 expected 不就行了？**

改不动，也不该改。构造函数没有返回值，标准库大量接口（`new`、`std::stoi`、容器 `at`）都是异常语义；`std::expected` 要 GCC 13+ 才有，老工具链用不了。现实的做法是分层：跨模块边界的可预期失败用 expected/错误码，模块内部与构造路径用异常，边界处转换。全用 expected 的代码到处是拆包 if，可读性反而崩了。

**问：栈展开途中析构函数抛异常，标准为什么不定成"第二个异常排队"而直接 terminate？**

排队方案要求运行时同时维护两条展开轨迹，每帧的清理状态要能重入，展开表和生成代码的复杂度翻倍，而实践中"析构抛异常"几乎总是 bug——为 bug 保留一条昂贵的续命路径不值得。terminate 让问题当场炸出来，配合 core dump 定位，是工程上更便宜的选择。
