## 6.1 何谓表达式
{: .sec-expl}

### 6.1.1 表达式的三个属性
{: .sec-know}

表达式说白了就是操作数加上运算符，求值之后给出一个结果。这个结果的"脾气"由三个属性决定，少看哪一个都容易出事：

1. **类型（type）**：结果是什么类型。对引用类型的表达式，`decltype` 与 `typeid` 的处理还不一样。
2. **值类别（value category）**：结果是左值、将亡值还是纯右值。它决定"能不能取地址"、"能不能被移动"、"能绑定到哪种引用"。
3. **副作用（side effect）**：求值过程中是否修改了对象、访问了 `volatile` 对象、调用了库 I/O 函数。

```cpp
i + 1        // 类型 int，值类别 prvalue，无副作用
++i          // 类型 int，值类别 lvalue，副作用：i 被加一
std::move(s) // 类型 std::string&&（作为表达式是 xvalue），无副作用
f()          // 取决于返回类型；可能有任意副作用
```

第三点我当初就经常忘，后来发现它正好是 5.2.6 那张 UB 表的依据——判断 UB 看的根本不是"谁先算"，而是"同一个对象上的两个副作用（或者一个写加一个读）有没有被排序"。

### 6.1.2 副作用与求值：全表达式的概念
{: .sec-know}

**全表达式（full-expression）** 是个边界概念：当一个表达式不再是别的表达式的子表达式时，它就是全表达式。几个典型场合：

- 一条表达式语句（`a = b + c;` 整个是）；
- `if`/`while`/`switch` 的控制条件；
- 变量的初始化器；
- `return` 语句里的返回表达式。

它之所以要单独拎出来，是因为临时对象的生命周期一般到全表达式结束就断了——6.1.10 那节会反复用到这点。

### 6.1.3 值类别的历史包袱
{: .sec-expl}

C++98 那会儿只有两个值类别，定义粗暴得很：

- **lvalue**：能出现在赋值左边的表达式（有名字、有地址、持久）。
- **rvalue**：只能出现在赋值右边的表达式（临时量、字面量）。

在 C++11 之前这个定义够用，毕竟还没有移动语义，所有拷贝都是拷贝。等到右值引用进来，"能放赋值左边"这个判据当场作废：`std::move(x)` 明明有名字，却必须能被移动。标准只能重新分类。

### 6.1.4 C++11 的正式分类：五类，两组
{: .sec-know}

新的分类基于两个相互独立的性质：

- **有没有身份（identity）**：能不能取地址、能不能判断两个表达式是否指代同一个对象。
- **能不能被移动（movable）**：它的资源允许被窃取（可以绑定到右值引用）。

把这两个性质两两组合，得到四小类；再按历史习惯并成两组：

```text
                        表达式 expression
                              |
              +---------------+---------------+
              |                               |
           glvalue                          rvalue
       （有身份：可取地址）            （可移动：资源能复用）
              |                               |
      +-------+-------+               +-------+-------+
      |               |               |               |
    lvalue          xvalue          xvalue          prvalue
   有身份，          有身份，       （同一个东西）   无身份，
   不可移动          可移动                         可移动
```

我记这个就靠一句：glvalue = lvalue + xvalue，rvalue = prvalue + xvalue。xvalue（eXpiring value，将亡值）是两边的交集，名字也是这么来的——它还有身份，但资源马上能被搬走。

### 6.1.5 每类举例
{: .sec-know}

| 类别 | 典型例子 |
| --- | --- |
| lvalue | 变量名 `x`、函数返回的左值引用 `*p`、`a[i]`、`++i`、`m.member`（对象是左值时）、字符串字面量 `"abc"`、返回 `T&` 的函数调用 |
| xvalue | `std::move(x)`、`static_cast<T&&>(x)`、返回 `T&&` 的函数调用、`obj.member`（对象是 xvalue 时） |
| prvalue | 字面量 `42` `3.14` `true`、返回非引用类型的函数调用、`a + b`、`a++`、`&x`、`this`、lambda 表达式、`sizeof(...)` 的结果 |

最容易记错的三条：

- **字符串字面量是 lvalue**。它是 `const char[N]` 类型的左值（有静态存储期），所以能取地址。
- **`++i` 是 lvalue，`i++` 是 prvalue**。前置返回引用，后置返回旧值的副本。
- **`std::move(x)` 是 xvalue，不是 prvalue**。规则是"调用返回右值引用的函数，得到的表达式是 xvalue"——它有身份（说的还是 `x` 那个对象），同时资源允许被搬走，正好落在两组的交集上。

用重载来实测：

```cpp
// value_category.cpp —— 需要 -std=c++20
#include <iostream>
#include <utility>

void probe(int&)       { std::cout << "int&        ← 非常量左值\n"; }
void probe(const int&) { std::cout << "const int&  ← 常量左值，或右值的兜底\n"; }
void probe(int&&)      { std::cout << "int&&       ← 右值（prvalue / xvalue）\n"; }

int main() {
    int i = 1;
    const int ci = 2;

    probe(i);                 // int&
    probe(ci);                // const int&
    probe(42);                // int&&   ← prvalue
    probe(i + 1);             // int&&   ← prvalue
    probe(std::move(i));      // int&&   ← xvalue
    probe(std::move(ci));     // const int&（const int&& 只能落到 const int&）
}
```

```bash
g++ -std=c++20 -Wall -Wextra value_category.cpp -o vc && ./vc
```

```text
int&        ← 非常量左值
const int&  ← 常量左值，或右值的兜底
int&&       ← 右值（prvalue / xvalue）
int&&       ← 右值（prvalue / xvalue）
int&&       ← 右值（prvalue / xvalue）
const int&  ← 常量左值，或右值的兜底
```

最后一行才是这节最该记住的：`std::move` 一个 const 对象，拿到的是 `const T&&`，它只能绑 `const T&`——结果走的是拷贝构造，移动压根没发生。

### 6.1.6 为什么要分值类别
{: .sec-expl}

分值类别不是为分类而分类，是为了解决两个实际麻烦：

**问题一：移动语义。** 拷贝一个 `std::vector<std::string>` 要分配内存、拷贝每个元素，代价高昂；而如果源对象马上就要销毁（是右值），直接把它的内部指针"偷"过来就够了。值类别就是编译器判断"这个源对象是不是可以偷"的依据——右值可以，左值不可以（因为左值后面还要用）。

**问题二：完美转发。** 写模板时要把参数原封不动传给另一个函数，包括它原本的值类别。没有值类别的精确描述，就无法做到这一点。

```cpp
// move_semantics.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <utility>
#include <vector>

int main() {
    std::vector<std::string> src{"alpha", "beta", "gamma"};
    std::cout << "移动前 src.size() = " << src.size() << "\n";

    std::vector<std::string> dst = std::move(src);   // 走移动构造
    std::cout << "移动后 dst.size() = " << dst.size() << "\n";
    std::cout << "移动后 src.size() = " << src.size() << "\n";

    src = dst;                                        // 移走后仍可重新赋值，之后正常使用
    std::cout << "重新赋值后 src[0] = " << src[0] << "\n";

    const std::string cs = "hello";
    std::string s2 = std::move(cs);                   // const → 走拷贝，cs 内容不变
    std::cout << "从 const 对象 move 后 cs 依然 = " << cs << "，s2 = " << s2 << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra move_semantics.cpp -o ms && ./ms
```

```text
移动前 src.size() = 3
移动后 dst.size() = 3
移动后 src.size() = 0
重新赋值后 src[0] = alpha
从 const 对象 move 后 cs 依然 = hello，s2 = hello
```

那个 `src.size()` 打出 0，只是 libstdc++/libc++ 的实际表现，**标准可没保证**——移动后的源对象处于"有效但未指定"状态，标准只保证你能安全地销毁它或重新给它赋值。别去读它的内容，也别假设它一定是空的。

### 6.1.7 `std::move`：不做移动的"移动"
{: .sec-know}

我一度以为 `std::move` 会真的"搬走"东西，其实它只做一件事：把实参**无条件**转成右值引用。不分配、不调构造、不生成代码。真正的搬运是后面被选中的移动构造/移动赋值干的。

```cpp
// 标准里的等价实现（libstdc++ 大致如此）
template <class T>
constexpr std::remove_reference_t<T>&& move(T&& t) noexcept {
    return static_cast<std::remove_reference_t<T>&&>(t);
}
```

三条实践结论：

1. `std::move(x)` 之后 `x` 并没有被改变——改变它的是随后发生的移动构造。
2. 对 `const` 对象用 `std::move` 无效（6.1.5 最后一行）。想移动就不能加 const。
3. 别在 `return` 局部变量时用它。见 6.3.2。

> **坑：** `std::move` 是个**有名函数**。`std::move(x)` 这个表达式类型上写着 `T&&`，但它的值类别其实是 **xvalue** 而不是 prvalue——它有身份，属于 glvalue，所以 `&std::move(x)` 合法，拿到的就是 `&x`。这恰好说明：`std::move` 根本没造新对象，只是换了种"看待 x 的方式"。真正求不了地址的是 prvalue（`&42`、`&(x + 1)` 都编不过），因为它还没物化成一个对象。
{: .sec-pit}

### 6.1.8 `std::forward` 与引用折叠
{: .sec-know}

`std::move` 是无条件转右值，`std::forward<T>` 是**有条件**转——只有 `T` 不是左值引用时才转。这就是"完美转发"的实现基础。

```cpp
// 标准里的两个重载（简化）
template <class T> constexpr T&& forward(std::remove_reference_t<T>& t) noexcept;
template <class T> constexpr T&& forward(std::remove_reference_t<T>&& t) noexcept;
```

注意 `T` **不会**被自动推导（它处在非推导语境），必须显式写 `std::forward<T>(x)`。漏写 `<T>` 直接编不过，这是标准故意的——逼你想清楚到底要转发成什么。

背后的机制是**引用折叠**（C++11）。`T&&` 里 `T` 本身是引用类型时，按下面四条规则折叠：

| 组合 | 折叠结果 |
| --- | --- |
| `T& &` | `T&` |
| `T& &&` | `T&` |
| `T&& &` | `T&` |
| `T&& &&` | `T&&` |

规则一句话：**只要出现 `&`，结果就是 `&`。**

```cpp
// ref_collapse.cpp —— 需要 -std=c++20
#include <type_traits>

template <class T> using AddLRef = T&;
template <class T> using AddRRef = T&&;

static_assert(std::is_same_v<AddLRef<int&>,  int&>);
static_assert(std::is_same_v<AddLRef<int&&>, int&>);    // & 胜出
static_assert(std::is_same_v<AddRRef<int&>,  int&>);    // & 胜出
static_assert(std::is_same_v<AddRRef<int&&>, int&&>);

int main() {}
```

```bash
g++ -std=c++20 -Wall -Wextra ref_collapse.cpp -o rc && ./rc
```

```text
（无输出：四条 static_assert 全部通过）
```

把折叠规则跟模板推导合起来，就得到下面这张必须刻进脑子的表（针对 `template <class T> void f(T&& x)`）：

| 实参 | `T` 推导为 | 形参 `x` 的类型 |
| --- | --- | --- |
| `int` 左值 | `int&` | `int&` |
| `const int` 左值 | `const int&` | `const int&` |
| `int` 右值（prvalue/xvalue） | `int` | `int&&` |
| `const int` 右值 | `const int` | `const int&&` |

于是 `std::forward<T>(x)` 里，`T` 是 `int&` 时返回 `int&`（保持左值），`T` 是 `int` 时返回 `int&&`（保持右值）。

```cpp
// forward_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <type_traits>
#include <utility>

template <class T>
void check(T&&) {
    if constexpr (std::is_lvalue_reference_v<T>) {
        std::cout << "T 是左值引用 → 形参是左值引用\n";
    } else {
        std::cout << "T 不是引用   → 形参是右值引用\n";
    }
}

void take(std::string&)  { std::cout << "take(string&)\n"; }
void take(std::string&&) { std::cout << "take(string&&)\n"; }

template <class T>
void wrapper(T&& s) {
    take(std::forward<T>(s));       // 保持原来的值类别
}

int main() {
    std::string s = "hi";
    check(s);                       // 左值
    check(std::string("x"));        // 右值
    check(std::move(s));            // 右值

    wrapper(s);                     // take(string&)
    wrapper(std::string("tmp"));    // take(string&&)
    wrapper(std::move(s));          // take(string&&)
}
```

```bash
g++ -std=c++20 -Wall -Wextra forward_demo.cpp -o fd && ./fd
```

```text
T 是左值引用 → 形参是左值引用
T 不是引用   → 形参是右值引用
T 不是引用   → 形参是右值引用
take(string&)
take(string&&)
take(string&&)
```

三行 `take` 就是"完美转发"的实证：`wrapper` 把实参的值类别原样传给了 `take`。

#### 辨析：`std::move` 与 `std::forward`
{: .sec-iv}

| 维度 | `std::move(x)` | `std::forward<T>(x)` |
| --- | --- | --- |
| 是否需要模板实参 | 不需要（自动推导） | **必须**显式写 `<T>` |
| 语义 | 无条件转成右值 | 有条件：`T` 是左值引用就保持左值，否则转右值 |
| 使用场景 | "我确定这个对象后面不用了" | "把参数原样传给下一层"（模板转发） |
| 误用后果 | 在还能用到的对象上提前搬空 | 忘了 `<T>` 直接编译失败 |

一句话区分：`std::move` 是**决定**（我不要这个对象的内容了），`std::forward` 是**传递**（原样交给下一层）。非模板代码里只会用到 `std::move`；只有写转发函数模板时才需要 `std::forward`。

### 6.1.9 转发引用（万能引用）的判定
{: .sec-know}

`T&&` 只有在**转发引用**（forwarding reference，Scott Meyers 早年叫它"万能引用"）的场合才有上面的推导行为。标准给的定义很窄：转发引用是"对一个 **cv 无修饰**的类型推导占位符的右值引用"。判定条件有三条，缺一不可：

1. 形式必须是 `T&&`——`T` 身上不能带 `const`/`volatile`（带上就退出转发引用阵营了），`T` 是模板参数或 `auto`；
2. `&&` 必须**直接作用在 `T` 上**，`vector<T>&&` 这种不算；
3. `T` 必须是**本次调用中被推导**的——不能是已确定的类型。

对照着看下面四个声明（只有最后一个才是）：

```cpp
template <class T> void f1(std::vector<T>&& v);   // 不是：&& 没直接贴在 T 上
void f3(std::string&& s);                         // 不是：具体类型，没有推导
template <class T> void f2(const T&& v);          // 不是：T 带了 const，cv 修饰让它出局
template <class C> void f4(C&& c);                // 是：最标准的转发引用写法
```

前两个不难理解。真正容易记错的是 `f2`：直觉上"`const` 只是在修饰 pointee，`T` 还是被推导了"，但标准明确要求 **cv-unqualified**，所以 `const T&&` 走的是普通右值引用的推导规则——传左值进去直接编译失败，没有任何转发能力。很多人把它记成转发引用，那是错的。cppreference 的原文可以直接照抄：**rvalue reference to a cv-unqualified type deduction placeholder**。**判断口诀：`&&` 紧贴一个 cv 无修饰、且本次被推导的占位符。**

`auto&&` 是同一个机制在变量声明里的版本：

```cpp
// auto_ref.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <type_traits>
#include <utility>
#include <vector>

int main() {
    int i = 0;
    auto&& a = i;                 // int&      （初始化器是左值）
    auto&& b = 5;                 // int&&     （初始化器是右值）
    static_assert(std::is_same_v<decltype(a), int&>);
    static_assert(std::is_same_v<decltype(b), int&&>);

    // 范围 for 里的推荐写法：auto&& 对左值元素和代理引用都成立
    std::vector<std::string> v{"alpha", "beta"};
    for (auto&& x : v) { std::cout << x << " "; }
    std::cout << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra auto_ref.cpp -o ar && ./ar
```

```text
alpha beta 
```

日常我写 `for (const auto& x : v)`（只读）或 `for (auto& x : v)`（要改）就够；只有写泛型、或者像 `std::vector<bool>` 那种代理引用会被 `auto&` 坑到的场景，才上 `auto&&`——它是范围 for 的"万能写法"。

### 6.1.10 临时对象的生命周期与引用绑定
{: .sec-warn}

规则：把一个临时对象绑定到引用上，该临时对象的生命周期**延长到引用的生命周期结束**。

```cpp
// lifetime_extend.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <utility>

struct Widget {
    std::string name;
    explicit Widget(std::string n) : name(std::move(n)) {
        std::cout << "  Widget(" << name << ")\n";
    }
    ~Widget() { std::cout << "  ~Widget(" << name << ")\n"; }
};

int main() {
    std::cout << "绑定临时对象到 const 引用：\n";
    const Widget& w = Widget{"延长了"};        // 生命周期延长到 w 的作用域结束
    std::cout << "  使用中: " << w.name << "\n";
    std::cout << "离开作用域：\n";
}
```


注意析构发生在"离开作用域"之后——这就是延长。

但**有四种情形不延长**，它们全是高频坑：

| 情形 | 结果 |
| --- | --- |
| 绑定到**函数参数**（调用时） | 临时量存活到包含该调用的**全表达式结束**，函数返回后即悬垂 |
| 绑定到**构造函数的引用成员** | 只存活到构造函数结束，对象构造完成员就悬垂 |
| 绑定到 **`return` 语句里的引用** | 完全不延长，返回即悬垂 |
| 绑定到 **`new` 初始化器里的引用** | 只存活到该全表达式结束，堆对象里的引用悬垂 |

第一条最常撞见：

```cpp
// max_dangling.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>

int main() {
    // const int& m = std::max(3, 5);    // 悬垂！两个 int 临时量在语句结束时就销毁
    int m = std::max(3, 5);              // 正确：按值接收
    std::cout << m << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra max_dangling.cpp -o mxd && ./mxd
```

```text

```

`std::max(const T&, const T&)` 返回的是**引用**，指向它的某个实参。传字面量时实参是临时量，语句一结束就没了——`m` 立刻悬垂，而编译期一声不响。

> **坑：** `auto&& r = f();` 和 `const auto& r = f();` 都能延长生命周期，但 `auto r = f();` 不延长（它走的是拷贝/移动，临时量语句结束照常销毁，只是值留了下来）。还有，延长只发生**一次**：`const T& r1 = make(); const T& r2 = r1;` 里 `r2` 指向的还是那个临时量，它的生命周期由 `r1` 决定，不会因为多绑一次就变长。
{: .sec-pit}

### 6.1.11 `decltype` 与 `decltype(auto)`
{: .sec-know}

`decltype(e)` 求的是表达式 `e` 的**声明类型**，规则分两种：

1. `e` 是一个**不带括号**的标识符或类成员访问（id-expression / class member access）→ 结果是该实体的**声明类型**（保留 const、保留引用）；
2. 其他情况 → 按值类别推导：
   - xvalue → `T&&`
   - lvalue → `T&`
   - prvalue → `T`

```cpp
// decltype_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

int main() {
    int i = 0;
    const int ci = 0;

    static_assert(std::is_same_v<decltype(i), int>);            // 变量名 → 声明类型
    static_assert(std::is_same_v<decltype((i)), int&>);         // 加括号 → 左值表达式 → int&
    static_assert(std::is_same_v<decltype(i + 0), int>);        // prvalue → int
    static_assert(std::is_same_v<decltype(ci), const int>);     // 保留 const
    static_assert(std::is_same_v<decltype((ci)), const int&>);

    int&& rr = 0;
    static_assert(std::is_same_v<decltype(rr), int&&>);         // 变量名 → 声明类型
    static_assert(std::is_same_v<decltype((rr)), int&>);        // 具名的右值引用是左值

    std::cout << "全部 static_assert 通过\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra decltype_demo.cpp -o dd && ./dd
```

```text
全部 static_assert 通过
```

`decltype((x))` 这个坑的位置很具体：**括号把"变量名"变成了"表达式"**，于是走第 2 条规则，结果多出一个 `&`。写泛型代码时，`decltype(x)` 和 `decltype((x))` 的差异常常就是"多拷贝一次"和"返回悬垂引用"的差别。

`decltype(auto)`（C++14）让 `auto` 按 `decltype` 的规则推导，从而**保留引用和 const**：

```cpp
// decltype_auto.cpp —— 需要 -std=c++14
#include <iostream>

int g_value = 0;

decltype(auto) by_value() { return g_value; }     // 返回 int
decltype(auto) by_ref()   { return (g_value); }   // 返回 int&  ← 括号的威力

// decltype(auto) dangling() { int x = 0; return (x); }  // 返回 int& 指向局部变量 → 悬垂

int main() {
    decltype(auto) a = by_value();   // int
    decltype(auto) b = by_ref();     // int&（by_ref() 是左值调用）
    a = 1;
    b = 2;
    std::cout << "g_value=" << g_value << " a=" << a << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra decltype_auto.cpp -o da && ./da
```

```text

```

`b = 2` 改到了全局变量，`a = 1` 只改了自己的副本。而注释掉的 `dangling()` 是 `decltype(auto)` 最著名的自杀方式——`auto` 会推成 `int`（安全），`decltype(auto)` 推成 `int&`（悬垂）。泛型包装函数需要它（`decltype(auto) front(C&& c) { return std::forward<C>(c).front(); }`），普通函数里能不用就不用。

### 6.1.12 延伸：表达式模板与惰性求值
{: .sec-ext}

`operator+` 每次都构造一个新对象，于是 `a + b + c + d` 会产生三个临时对象。数值库（以及 C++20 的 ranges）用的解法是**表达式模板**：让 `a + b` 不计算结果，而是返回一个描述"这是 a 加 b"的轻量对象，直到赋值给目标时才一次性展开计算。

```cpp
// 概念示意：真实的库（比如 Eigen）会复杂得多
template <class L, class R>
struct AddExpr {
    const L& l; const R& r;
    auto operator[](std::size_t i) const { return l[i] + r[i]; }
};

template <class L, class R>
AddExpr<L, R> operator+(const L& l, const R& r) { return {l, r}; }
```

好处是省掉中间临时量；代价是类型变得极难读——`auto` 在这里会抓到一个指向临时量表达式对象的引用，直接悬垂，`auto x = a + b;` 会静默留下悬垂引用。C++20 的 ranges 把这套做法标准化成视图（view）：惰性的，`v | filter(...) | transform(...)` 不生成中间容器，遍历时才逐个算。**记住一条：表达式模板的结果别存进 `auto` 变量。**

## 6.2 说说类型转换
{: .sec-expl}

### 6.2.1 隐式转换序列的三段
{: .sec-know}

当需要的类型和实际类型不一致时，编译器尝试构造一条**隐式转换序列**（implicit conversion sequence）。它最多由三段组成：

```text
[标准转换序列]  →  [用户定义转换]  →  [标准转换序列]
   第一段              第二段              第三段
```

规则：**最多只能有一次用户定义转换**（构造函数或转换运算符），前后可以各有零次或一次标准转换。这就是"不能链式隐式转换两次"的原因：

```cpp
struct A { operator int() const { return 1; } };       // A → int
struct B { operator A() const { return A{}; } };       // B → A

// int i = B{};   // 错误：需要 B → A → int，两次用户定义转换
int j = static_cast<int>(static_cast<A>(B{}));         // OK：显式分步
```

`explicit` 之所以能拦住隐式转换，是因为它让"用户定义转换"这一段不参与隐式转换序列——显式写出来仍然可以用。

### 6.2.2 整型提升（integral promotion）
{: .sec-know}

比 `int` 窄的类型参与运算前先被提升。触发条件是"整型转换等级（rank）低于 `int`"：

| 源类型 | 提升目标 |
| --- | --- |
| `bool` | `int`（false→0，true→1） |
| `char` `signed char` `unsigned char` | `int`（若 `int` 装不下则 `unsigned int`） |
| `short` `unsigned short` | 同上 |
| `char8_t` `char16_t` | 能装下就用 `int`，否则按 `int` → `unsigned int` → `long` → ... 顺序找第一个装得下的 |
| `char32_t` `wchar_t` | 同上（32 位无符号 → 通常落到 `unsigned int`） |
| 无作用域枚举（底层类型固定除外） | 能装下就 `int`，否则 `unsigned int`，再否则不提升 |
| `int` `long` `long long` | 不提升（rank 不低于 `int`） |

注意 `char32_t` 那一行：`char32_t` 是 32 位无符号，而 `int` 装不下它的全部取值，所以它提升到 `unsigned int` 而不是 `int`。这在打印和比较时会带来意外。

```cpp
// promotion.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

int main() {
    signed char a = 100, b = 50;
    auto c = a + b;
    static_assert(std::is_same_v<decltype(c), int>);   // 不是 signed char！

    bool flag = true;
    static_assert(std::is_same_v<decltype(flag + flag), int>);

    short s = 1;
    static_assert(std::is_same_v<decltype(s + s), int>);

    std::cout << "a + b = " << c << "  sizeof = " << sizeof(c) << "\n";
    std::cout << "true + true = " << (flag + flag) << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra promotion.cpp -o pm && ./pm
```

```text
a + b = 150  sizeof = 4
true + true = 2
```

### 6.2.3 寻常算术转换（usual arithmetic conversions）
{: .sec-know}

两边都已经提升过、但类型仍不相同时，按下面的顺序把两边拉到同一个类型：

1. 一边是**浮点** → 另一边转成浮点（浮点之间按 rank：`float` → `double` → `long double`）；
2. 都是**整型**，且符号性相同 → rank 小的转成 rank 大的（`char` < `short` < `int` < `long` < `long long`）；
3. 都是**整型**，符号性不同 →
   - 若无符号那侧的 rank **≥** 有符号那侧 → 有符号的转成无符号；
   - 否则，若有符号类型能表示无符号那侧的全部取值 → 无符号的转成有符号；
   - 否则 → 两边都转成该有符号类型的无符号版本；
4. 一边是**枚举** → 先按整型提升转成 `int`/`unsigned int`（底层类型固定则转成其底层类型），再走上述规则；
5. 两边都是**同类型枚举** → 结果也不是枚举类型，而是提升/转换后的那个整型。

第 3 条就是那个经典笑话的来源：

```cpp
// usual_conv.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

int main() {
    std::cout << std::boolalpha;
    std::cout << "(-1 < 1u)         = " << (-1 < 1u) << "\n";   // false：-1 变 UINT_MAX
    std::cout << "(-1L < 1u)        = " << (-1L < 1u) << "\n";  // true：long 能装下 unsigned 全值 → u 转 long
    std::cout << "(1 < 1.5)         = " << (1 < 1.5) << "\n";   // true：1 转 double

    static_assert(std::is_same_v<decltype(1 + 1u), unsigned int>);
    static_assert(std::is_same_v<decltype(1 + 1.0), double>);
    static_assert(std::is_same_v<decltype(1L + 1u), long>);     // LP64 下 long 能装 unsigned
}
```

```bash
g++ -std=c++20 -Wall -Wextra usual_conv.cpp -o uc && ./uc
```

```text
# 前提：LP64（Linux/macOS 64 位）。Windows（LLP64）上第二行会是 false
(-1 < 1u)         = false
(-1L < 1u)        = true
(1 < 1.5)         = true
```

最后一条 `static_assert` 有平台前提：LP64（Linux/macOS）下 `long` 是 64 位，能装下 32 位 `unsigned int` 的全部取值，所以 `1L + 1u` 是 `long`；但在 LLP64（Windows）下 `long` 只有 32 位，装不下，结果会是 `unsigned long`。写跨平台代码时别依赖这个结论。

### 6.2.4 其他标准转换
{: .sec-know}

除了整型提升和算术转换，标准转换还有这些：

| 转换 | 说明 |
| --- | --- |
| 左值到右值（lvalue-to-rvalue） | 读取对象的值；除少数语境外自动发生 |
| 数组到指针 | `int[10]` → `int*`，这就是"退化" |
| 函数到指针 | `void()` → `void(*)()` |
| 布尔转换 | 算术/指针/指针到成员 → `bool`；0/nullptr 为 false，其余 true |
| 指针转换 | `nullptr` → 任意指针；`T*` → `void*`；派生类指针 → 基类指针 |
| 指针到成员转换 | `Derived::*` → `Base::*`（方向与普通指针相反） |
| 限定符转换 | `T*` → `const T*`（只能"加"const，不能"去"） |
| 函数指针转换 | C++17 起：`noexcept` 函数指针 → 非 `noexcept` 函数指针 |

布尔转换里有个细节值得单独记住：**指针转 bool 在 `if` 里可以，在算术里不行**。`if (p)` 合法；`int x = p;` 是错误（指针不能隐式转 int）。

```cpp
// bool_conv.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    std::cout << std::boolalpha;
    int* p = nullptr;
    std::cout << "if (p)     = " << (p ? true : false) << "\n";   // false
    p = new int(1);
    std::cout << "if (p)     = " << (p ? true : false) << "\n";   // true
    std::cout << "!p         = " << !p << "\n";
    // int bad = p;        // 错误：指针不能隐式转 int
    delete p;
}
```

```bash
g++ -std=c++20 -Wall -Wextra bool_conv.cpp -o bc && ./bc
```

```text

if (p)     = true
!p         = false
```

### 6.2.5 `explicit`：拦住不该发生的隐式转换
{: .sec-know}

`explicit` 有三个年代的用法：

- **C++98**：用在构造函数上，禁止它参与隐式转换（多参数构造函数也支持，C++11 起才对多参数有意义）。
- **C++11**：可以用在**转换运算符**上。`explicit operator bool()` 是最典型的用法——允许 `if (obj)`，禁止 `bool b = obj;` 和 `obj + 0`。
- **C++20**：**条件 explicit**，`explicit(常量表达式)`，可以按条件决定是否是 explicit。

```cpp
// explicit_demo.cpp —— 需要 -std=c++20
#include <iostream>

struct SafeInt {
    int value;
    explicit SafeInt(int v) : value(v) {}
    explicit operator bool() const { return value != 0; }   // C++11 起
};

struct Meters {
    double value;
    explicit(true)  Meters(double v) : value(v) {}          // C++20：等价于 explicit
    explicit(false) Meters(int v) : value(static_cast<double>(v)) {}  // C++20：明确允许隐式
};

void take(SafeInt)  { std::cout << "take(SafeInt)\n"; }
void take_m(Meters) { std::cout << "take_m(Meters)\n"; }

int main() {
    SafeInt a{5};
    // take(5);                        // 错误：explicit 阻止隐式转换
    take(SafeInt{5});                  // OK
    take(static_cast<SafeInt>(5));     // OK

    if (a) { std::cout << "语境转换到 bool 可以\n"; }
    // bool b = a;                     // 错误：explicit operator bool 不参与隐式转换
    bool b = static_cast<bool>(a);
    std::cout << std::boolalpha << b << "\n";

    // take_m(1.5);                    // 错误：explicit(true)
    take_m(3);                         // OK：explicit(false) 允许 int → Meters
}
```

```bash
g++ -std=c++20 -Wall -Wextra explicit_demo.cpp -o ed && ./ed
```

```text
take(SafeInt)
take(SafeInt)
语境转换到 bool 可以
true
take_m(Meters)
```

**语境转换到 bool**（contextual conversion to bool）是 `explicit operator bool()` 的关键：在 `if`、`while`、`&&`、`||`、`!`、`?:` 的第一个操作数、`static_assert` 这些位置，`explicit` 被忽略。这正好是智能指针、`std::optional`、`std::unique_ptr` 想要的效果——能判空，但不能拿去和整数运算。

### 6.2.6 窄化与 `-Wconversion`
{: .sec-ts}

隐式转换里最危险的一类是**值可能变掉**的转换。列表初始化（第 04 篇 4.1.3）会在编译期拦住它，但 `=` 和 `()` 不会。这时候要靠编译器开关：

| 开关 | 抓什么 |
| --- | --- |
| `-Wconversion` | 可能改变值的隐式转换（`int64_t` → `int32_t`、`double` → `int`） |
| `-Wsign-conversion` | 有符号与无符号之间的隐式转换 |
| `-Wsign-compare` | 有符号与无符号的比较（`-Wall` 里已包含） |
| `-Wfloat-conversion` | 浮点到整型的隐式转换 |

这几个开关的启用关系要分清：`-Wconversion` 和 `-Wsign-conversion` **不在** `-Wall -Wextra` 里，必须显式加；`-Wsign-compare` 在 C++ 里已经由 `-Wall` 打开；`-Wfloat-conversion` 会被 `-Wconversion` 捎带打开，一般不单写。告警量很大（尤其在老代码里），渐进式项目可以先只对新代码开，或者用 `#pragma GCC diagnostic` 局部压制。

### 6.2.7 `static_cast`：最常用，也最容易用错
{: .sec-know}

`static_cast<T>(e)` 的语义是"**在类型系统允许的范围内做明确转换**"，包括：

- 数值类型之间的转换（`double` → `int`，截断是有意的）；
- `void*` → 具体指针类型（反向也行）；
- 基类指针/引用 → 派生类（**不做运行期检查**，向下转型不安全）；
- 派生类 → 基类（向上转型，安全）；
- 枚举 ↔ 整型；
- 调用 `explicit` 构造函数或 `explicit` 转换运算符；
- 任意隐式转换的"显式版本"。

```cpp
// static_cast_demo.cpp —— 需要 -std=c++20
#include <iostream>

struct Base { int b = 1; };
struct Derived : Base { int d = 2; };

int main() {
    std::cout << static_cast<int>(3.9) << "\n";        // 3，有意截断
    std::cout << static_cast<char>(65) << "\n";        // A

    Derived d;
    Base* pb = &d;                                     // 向上转型：隐式就行
    Derived* pd = static_cast<Derived*>(pb);           // 向下转型：编译期放行，无检查
    std::cout << pd->d << "\n";                        // 这里恰好正确

    // 真正的 Base 对象转 Derived* 也能编过，但访问派生类成员是未定义行为：
    // Base pure; Derived* bad = static_cast<Derived*>(&pure);

    void* vp = &d;
    std::cout << static_cast<Derived*>(vp)->d << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra static_cast_demo.cpp -o scd && ./scd
```

```text
3
A
2
2
```

> **坑：** `static_cast` 向下转型**不插任何运行期检查**。把一个真正的 `Base` 对象转成 `Derived*` 能编过，访问派生类成员就是 UB。要检查就上 `dynamic_cast`（6.2.10）。反过来说，`static_cast` 也没法在两个无关类型之间转——那是 `reinterpret_cast` 的活，而它的代价同样是 UB。
{: .sec-pit}

#### 辨析：四种 cast 怎么选
{: .sec-iv}

| 你的目的 | 该用 |
| --- | --- |
| 数值转换、向上转型、`void*` 回原类型、显式构造 | `static_cast` |
| 去掉 const 对接不修改实参的老 API | `const_cast`（先确认对象本身不是 const） |
| 多态类型向下/交叉转型，需要运行期检查 | `dynamic_cast` |
| 重新解释位模式 | `std::bit_cast` / `std::memcpy`，实在不行才 `reinterpret_cast` |
| 上面都不匹配 | 说明类型设计有问题，回去改类型 |

判断的关键不是"哪个能编过"，而是"哪个表达了我的意图"。C 风格转换永远能编过，这正是它危险的原因。

### 6.2.8 `const_cast`：能去掉 const，但改真 const 是 UB
{: .sec-warn}

`const_cast` 只能做一件事：增删类型的 `const`/`volatile` 限定。目标类型和源类型必须**其余部分完全相同**——不能用它改类型。

```cpp
// const_cast_demo.cpp —— 需要 -std=c++20
#include <iostream>

void legacy_print(char* s) { std::cout << s << "\n"; }

int main() {
    const char* msg = "hello";
    // legacy_print(msg);                      // 错误：const char* 不能转 char*
    legacy_print(const_cast<char*>(msg));      // 只在确认它不会写入时才安全

    int not_const = 10;
    const int* cp = &not_const;                // 只是"通过这个指针不能改"
    int* mp = const_cast<int*>(cp);
    *mp = 20;                                  // OK：对象本身不是 const
    std::cout << not_const << "\n";

    // 对象本身声明为 const 时，去掉 const 再写入是未定义行为：
    // const int real_const = 10;
    // *const_cast<int*>(&real_const) = 20;    // UB
}
```

```bash
g++ -std=c++20 -Wall -Wextra const_cast_demo.cpp -o ccd && ./ccd
```

```text

20
```

区分两种情况很关键：

| 情形 | 用 `const_cast` 去掉 const 后写入 |
| --- | --- |
| 对象本身不是 const，只是经由 `const T*` 拿到 | **合法** |
| 对象本身声明为 `const` | **未定义行为**（编译器可能把它放进只读段，写入直接段错误；也可能"看起来正常"，然后某天换优化级别就崩） |

`const_cast` 的用武之地其实很窄，我自己只在接那种"不修改实参但签名没写 const"的老 C API 时才用。其余情况基本都是设计有问题——该去改那个 API 的签名，而不是在调用点拿 `const_cast` 硬怼。

### 6.2.9 `reinterpret_cast` 与严格别名规则
{: .sec-warn}

`reinterpret_cast` 做的是"把这段位模式当成另一种类型来读"。它几乎总是**实现定义**的，而且极易踩到**严格别名规则**（strict aliasing）：

> 通过一个与对象动态类型不匹配的 glvalue 访问该对象，是未定义行为。
> 允许的例外：对象的动态类型本身、cv 限定版本、对应的有符号/无符号版本、`char`/`unsigned char`/`std::byte`、以及包含上述类型的聚合/联合。

经典的违规写法与正确写法：

```cpp
// type_punning.cpp —— 需要 -std=c++20
#include <bit>
#include <cstdint>
#include <cstring>
#include <iostream>

int main() {
    float f = 1.0f;

    // auto bad = reinterpret_cast<std::uint32_t&>(f);   // 未定义行为：违反严格别名规则
    // 更常见也更隐蔽的形式：
    // std::uint32_t n = *reinterpret_cast<std::uint32_t*>(&f);   // 同样是 UB

    std::uint32_t via_memcpy;
    std::memcpy(&via_memcpy, &f, sizeof via_memcpy);   // 正确（运行期）

    std::uint32_t via_bit_cast = std::bit_cast<std::uint32_t>(f);  // 正确（C++20，编译期也能用）

    std::cout << std::hex << via_memcpy << " " << via_bit_cast << "\n" << std::dec;
}
```

```bash
g++ -std=c++20 -Wall -Wextra type_punning.cpp -o tp && ./tp
```

```text
3f800000 3f800000
```

`1.0f` 的 IEEE 754 单精度位模式就是 `0x3f800000`（符号位 0、指数 127、尾数 0）。

三种做法的取舍：

| 做法 | 是否 UB | 能否编译期 | 备注 |
| --- | --- | --- | --- |
| `reinterpret_cast<T&>(x)` | **是** | — | 严格别名违规，且 `-O2` 下经常"碰巧对"然后某天失效 |
| `std::memcpy` | 否 | 否 | 通用、安全，编译器通常会优化成一条指令 |
| `std::bit_cast<To>(from)`（C++20） | 否 | 是 | 要求两端 trivially copyable 且 `sizeof` 相同 |

`reinterpret_cast` 剩下的正当用途：指针与足够大的整型之间互转（做地址运算、塞进句柄）、把对象指针转成 `unsigned char*`/`std::byte*` 去逐字节检查（这是严格别名的例外之一）、以及底层序列化/内存映射代码。

### 6.2.10 `dynamic_cast`：唯一带运行期检查的转型
{: .sec-know}

需要运行期检查的向下/交叉转型里，`dynamic_cast` 只用于**多态类型**（至少有一个虚函数）。它在运行期检查对象是不是目标类型：

- **指针版**失败返回 `nullptr`；
- **引用版**失败抛 `std::bad_cast`（`<typeinfo>`）。

```cpp
// dynamic_cast_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <typeinfo>

struct Base { virtual ~Base() = default; };
struct Derived : Base { void only() { std::cout << "Derived::only\n"; } };
struct Other : Base {};

int main() {
    std::cout << std::boolalpha;
    Base* bd = new Derived;
    Base* bb = new Base;

    if (auto* d = dynamic_cast<Derived*>(bd)) { d->only(); }
    std::cout << "Base* 转 Derived* 失败? " << (dynamic_cast<Derived*>(bb) == nullptr) << "\n";
    std::cout << "Base* 转 Other*   失败? " << (dynamic_cast<Other*>(bd) == nullptr) << "\n";

    try {
        Derived& r = dynamic_cast<Derived&>(*bb);
        (void)r;
    } catch (const std::bad_cast&) {
        std::cout << "引用版失败抛 std::bad_cast\n";
    }

    delete bd;
    delete bb;
}
```

```bash
g++ -std=c++20 -Wall -Wextra dynamic_cast_demo.cpp -o dcd && ./dcd
```

```text
Derived::only
Base* 转 Derived* 失败? true
Base* 转 Other*   失败? true
引用版失败抛 std::bad_cast
```

两个额外用法：`dynamic_cast<void*>(p)` 返回指向**最派生对象**的 `void*`（可以用来比较两个指针是否指向同一个完整对象）；跨继承体系的"交叉转型"（sibling cast）也只有它能做。

代价是运行期开销（一般走 vtable 查类型信息）。我自己的经验是：代码里 `dynamic_cast` 扎堆出现，基本都说明设计有问题，多半该换成虚函数或访问者模式。

### 6.2.11 C 风格转换为什么不推荐
{: .sec-warn}

`(T)e` 和 `T(e)` 会按顺序尝试：

1. `const_cast`
2. `static_cast`
3. `static_cast` + `const_cast`
4. `reinterpret_cast`
5. `reinterpret_cast` + `const_cast`

取第一个能成立的。问题就在这个"自动降级"上：

| 问题 | 后果 |
| --- | --- |
| 悄悄做了 `const_cast` | 你可能不知道自己在改一个真正的 const 对象 |
| 悄悄做了 `reinterpret_cast` | 两个不相关指针类型之间的转换一声不响地通过了 |
| 能绕过访问控制 | C 风格转换可以转到不可访问的基类，`static_cast` 不行 |
| grep 困难 | `(Foo*)p` 这种形式在代码里很难用正则可靠地找全 |
| 意图不明 | 读代码的人看不出你是想截断、想转型还是想重新解释位模式 |

```cpp
// c_style.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    // const int ci = 7;
    // int* p = (int*)&ci;     // C 风格转换一声不吭地做掉了 const_cast
    // *p = 9;                 // 未定义行为

    double d = 3.9;
    std::cout << (int)d << "\n";                 // 也能用，但看不出"这是有意截断"
    std::cout << static_cast<int>(d) << "\n";    // 意图明确
}
```

```bash
g++ -std=c++20 -Wall -Wextra c_style.cpp -o cs && ./cs
```

```text
3
3
```

选择 cast 的决策树：

- 数值转换、向上转型、`void*` 回原类型、显式构造 → `static_cast`
- 去掉 const 对接老 API → `const_cast`（并确认对象本身不是 const）
- 多态类型的向下/交叉转型 → `dynamic_cast`
- 重新解释位模式 → 先想 `std::bit_cast` / `std::memcpy`，实在不行才 `reinterpret_cast`
- 其他一切 → 说明你的设计有问题，回去改类型

### 6.2.12 `std::launder`：告诉编译器"这里有个新对象"
{: .sec-ext}

`std::launder`（C++17，`<new>`）解决的问题很具体：**在同一块存储上重新构造对象之后，原来的指针/引用不能再用来访问新对象**——因为它指向的是"旧对象"，编译器可以基于旧对象的信息做优化（尤其是旧对象有 const 成员或引用成员时）。

```cpp
// launder_demo.cpp —— 需要 -std=c++17
#include <iostream>
#include <new>

struct X {
    const int i;          // const 成员：编译器可以假定它永不改变
};

int main() {
    X* p = new X{1};
    const int a = p->i;

    new (p) X{2};                        // 在同一块存储上重新构造一个新对象
    // const int b = p->i;               // 未定义行为：p 指向的是旧对象，可能读到 1
    const int c = std::launder(p)->i;    // 正确：明确告诉编译器这里有个新 X

    std::cout << a << " " << c << "\n";
    p->~X();
    ::operator delete(p);
}
```

```bash
g++ -std=c++20 -Wall -Wextra launder_demo.cpp -o ld && ./ld
```

```text
1 2
```

注释掉的那一行是最难查的 bug 类型：编译器看到 `X::i` 是 const，就假定 `p->i` 永远是 1，直接把常量 1 内联进去，于是你明明写了 `new (p) X{2}` 却读到了 1。而且它只在开优化时才暴露。

什么时候需要 `std::launder`：

- 在 placement new 复用存储之后，通过旧指针访问新对象；
- 从 `std::optional`/小缓冲区里取出对象时（库内部已经处理好了，你一般不用管）；
- 访问有 const 成员或引用成员的对象，且该存储被复用过。

不需要的场景：普通的对象生命周期内访问。别把它当成"压制编译器警告的万能膏药"——滥用反而掩盖真正的问题。

## 6.3 技术解惑
{: .sec-expl}

### 6.3.1 `std::move` 之后对象还能用吗
{: .sec-know}

能用，但只能做两件事：销毁它，或者给它赋新值。标准规定移动后的源对象处于**有效但未指定**（valid but unspecified）状态，标准库类型的自赋值、清空、`size()` 这类**没有前置条件**的成员函数都可以安全调用。不要读它的内容（`s.size()` 是多少、字符串里还剩什么，都没规定），也不要假设它是空的。想继续用它，就显式重新赋值：`src = dst;`。

### 6.3.2 为什么 `return std::move(x);` 是错的
{: .sec-know}

两层原因：

1. **它挡住了 NRVO**。返回局部变量的语句如果是 `return x;`（`x` 的类型与返回类型一致），编译器可以做"具名返回值优化"，直接在调用方的栈帧上构造对象，零拷贝零移动。写成 `return std::move(x);` 之后返回的是 `T&&`，无法匹配 NRVO 的条件，反而多一次移动构造。
2. **局部变量本来就会被当作右值处理**。C++11 起，返回局部变量时如果 NRVO 不适用，编译器会先尝试把它当右值（走移动），只有都不行才拷贝。所以 `return x;` 已经是最优的，`std::move` 一点忙都帮不上。

例外：返回的是**成员变量**、或者类型与返回类型不同（需要转换）时，`std::move` 才有用武之地——因为 NRVO 本来也不适用。

### 6.3.3 `const T&` 绑定临时对象一定安全吗
{: .sec-know}

只有"绑到变量上"才安全。四种不延长的情形见 6.1.10：函数参数、构造函数引用成员、`return` 语句、`new` 初始化器。我自己最常踩的就是 `const int& m = std::max(3, 5);` 和 `const T& r = f();`（`f` 返回引用、实参是临时量）。拿不准时，干脆用值语义（`auto m = std::max(3, 5);`）——拷一个 int 几乎零代价。

### 6.3.4 `int&& r = 5;` 和 `const int& r = 5;` 有什么区别
{: .sec-know}

两者都会延长临时对象的生命周期，区别在于**你能拿它做什么**：

- `const int& r`：只读。能绑定左值、右值、const 左值——几乎什么都能绑，所以常被用作"通用只读引用"。
- `int&& r`：可写（能 `r = 10;`），但**只能绑定右值**。这也正是它成为移动语义语法基础的原因：能绑上 `T&&` 的一定是"可以被偷"的对象。

另外 `int&& r` 这个变量本身是**左值**（它有名字、有身份）。想再次把它当右值传给别人，还得 `std::move(r)`。

### 6.3.5 `static_cast<int>(3.9)` 和 `(int)3.9` 一样吗
{: .sec-know}

结果一样（都是 3，截断小数）。不一样的是"编译器允许你在什么场合用它"。C 风格转换会自动降级到 `const_cast` 和 `reinterpret_cast`，所以 `(int*)&some_const` 这种写法一声不响就去掉了 const。用 `static_cast` 时，如果意图不是"类型系统允许的转换"，编译直接失败——这层保护正是你要的。

### 6.3.6 怎么做类型双关（type punning）才不 UB
{: .sec-know}

按优先级：

1. **改设计**，别做双关。多数"我需要把 float 当 int 看"的需求都能用正常类型转换解决。
2. `std::bit_cast<To>(from)`（C++20，`<bit>`）：要求两端 trivially copyable 且 `sizeof` 相同，编译期可用，语义清晰。
3. `std::memcpy`：运行期可用，编译器通常优化成单条指令，是最通用的兜底。
4. `reinterpret_cast`：只在转成 `unsigned char*`/`std::byte*` 逐字节检查时是安全的（这是严格别名的例外）。用它做 `float`↔`uint32_t` 是 UB，即使 `-O0` 下"跑得对"。

### 6.3.7 `dynamic_cast` 失败时指针版和引用版分别怎样
{: .sec-know}

指针版返回 `nullptr`，可以用 `if` 判断；引用版抛 `std::bad_cast`（定义在 `<typeinfo>`），因为引用没有"空"这个状态。选哪个取决于"转型失败是不是正常情况"——是正常分支就用指针版，是程序 bug 就用引用版让异常冒出去。另外，带运行期检查的向下/交叉转型要求源类型**多态**（至少一个虚函数）；单纯的向上转型不需要，非多态类型也能编译通过。

### 6.3.8 `decltype(auto)` 比 `auto` 危险在哪
{: .sec-know}

`auto` 推导时剥掉引用和顶层 const（按值语义），`decltype(auto)` 完整保留。危险点在于：一个不经意的括号就能把返回类型从 `int` 变成 `int&`。`return x;` 得到 `int`，`return (x);` 得到 `int&`——如果 `x` 是局部变量，那就是悬垂引用，而编译器可能只给 `-Wreturn-local-addr` 一条警告。泛型包装函数（要精确转发被包装函数的返回类型）该用它，普通函数不用。

### 6.3.9 `explicit operator bool()` 什么时候被调用
{: .sec-know}

只在**语境转换到 bool** 的位置：`if`、`while`、`do-while` 的条件、`for` 的条件、`&&`/`\|\|`/`!` 的操作数、`?:` 的第一个操作数、`static_assert`、`noexcept` 运算符。这些位置 `explicit` 被忽略。

它**不参与**隐式转换，所以 `bool b = obj;`、`obj1 == obj2`、`obj + 1` 都会编译失败——这正是设计意图：智能指针能判空，但不能被当成整数用。

### 6.3.10 重载决议遇到"隐式转换太多"的歧义怎么办
{: .sec-know}

典型症状是 `f(0)` 同时能匹配 `f(int)` 和 `f(char*)`（0 既是整型字面量又是空指针常量），或者自己写的类型同时提供了到多种类型的转换运算符。三种解法：

1. **减少转换路径**：把转换运算符改成 `explicit`，或者干脆改成具名成员函数（`to_string()` 而不是 `operator std::string()`）。这是最根本的解法。
2. **调用点写清楚**：`f(static_cast<int>(x))`、`f(nullptr)`（而不是 `f(0)`）。
3. **删掉多余的重载**，或者用标签/模板约束（`requires`）让只有一个候选可行。

经验是第 1 条：一个类型提供的隐式转换越多，它的重载决议越难预测。C++20 的 concept 给了更好的工具——用约束把候选集缩小，比让编译器在十几条转换路径里挑要好得多。

## 变式追问
{: .sec-think}

1. `std::move(x)` 返回的是 `T&&`，那为什么 `std::move(x)` 这个表达式本身是 xvalue 而不是 prvalue？

   因为标准规定：**返回类型是"到对象类型的右值引用"的函数调用表达式是 xvalue**，而 prvalue 是那些"初始化对象"的表达式（字面量、返回非引用类型的调用、`a+b` 等）。区别的实际意义在于：xvalue 属于 glvalue，它**有身份**——理论上可以取地址、可以判断与另一个表达式是否指代同一对象；prvalue 没有身份，它只是一个"待初始化的值"。这条区分在 `decltype` 上表现得很直接：`decltype(f())` 在 `f` 返回 `T&&` 时是 `T&&`（xvalue 规则），在 `f` 返回 `T` 时是 `T`（prvalue 规则）。日常写代码不用背这个，但被问到"为什么 `std::move` 之后还能对结果做某些事"时，答案就在这里。

2. 为什么 `const T&` 能绑定临时对象，`T&` 不能？

   这是 C++ 刻意的设计：允许 `T&` 绑定临时对象会带来"修改一个马上就消失的对象"的荒谬场景，而且没法区分"我拿到了一个左值"和"我拿到了一个即将消失的右值"。所以标准规定非常量左值引用只能绑定左值。而 `const T&` 绑定临时对象是安全的（你改不了它），加上生命周期延长规则（6.1.10），它就成了一个非常方便的"通用只读引用"——`void print(const std::string& s)` 既能接左值也能接右值，原因就在这里。C++11 之后又多了 `T&&` 这条"可写的右值"通道，两条合起来覆盖了全部四种组合，这也是为什么参数类型基本只需要在 `T`、`const T&`、`T&&` 之间选。

3. `std::forward<T>(x)` 里忘了写 `<T>` 会怎样？为什么标准要这么设计？

   直接编译错误——`std::forward` 的模板参数 `T` 出现在 `std::remove_reference_t<T>` 里，属于非推导语境，编译器推不出来。这是故意的：`std::forward` 的语义完全取决于 `T` 是什么，如果允许推导，就没有"转发"的意义了（它总是会推成实参的实际类型，退化成 `std::move` 或什么都不做）。对比一下 `std::move` 就清楚了：`std::move` 不需要模板实参，因为它做的是**无条件**转换；`std::forward` 必须显式指定，因为它做的是**有条件**转换，条件就是 `T`。所以看到 `std::forward(x)` 编译失败时，别去加 `static_cast`，回去把 `<T>` 补上——那才是问题所在。

4. 有人说"用 `memcpy` 做类型双关没有性能损失，编译器会优化掉"，这话在什么情况下不成立？

   在大多数现代编译器上、对 `sizeof` 小的类型（4~8 字节），这话是对的——`memcpy` 会变成一条 `mov`。但有两种情况不成立：一是两端的 `sizeof` 很大或者对齐不一致时，编译器可能真的生成一个 `memcpy` 调用；二是你想在**编译期常量求值**里做类型双关时，`std::memcpy` 根本不能用（它不是 `constexpr`），这时只能用 `std::bit_cast`。所以结论是：运行期的老代码用 `memcpy` 完全没问题（而且比 `reinterpret_cast` 安全），新代码和 `constexpr` 场景一律用 `std::bit_cast`。至于 `reinterpret_cast`——它在任何情况下都不是正确答案，问题从来不是性能，而是它触发的是 UB。

5. `static_cast<Derived*>(base_ptr)` 在 `base_ptr` 实际指向 `Base` 对象时是 UB，那为什么标准还允许它编译？

   因为权限和检查是两件事。`static_cast` 的契约是"程序员保证这个转换是合法的"，标准相信你，不插入运行期检查——这正是它比 `dynamic_cast` 便宜的原因，也是 C++ "不为不用的东西付代价"这条原则的体现。什么时候这份保证成立？当你**从别处确切知道**对象的动态类型就是 `Derived`（比如你刚刚才从 `Derived*` 转上去过，或者这是 CRTP 里 `static_cast<Derived*>(this)` 这种惯用法）。CRTP 是 `static_cast` 向下转型最正当的用例之一：基类模板被 `Derived` 继承，所以 `this` 的动态类型必然是 `Derived`。除此之外，凡是你对动态类型没把握的地方，就用 `dynamic_cast`，或者重新想一想这里是不是本该用虚函数。
