线上业务要持续稳定运行，离不开监控。本篇覆盖：监控概念、常用命令与监控脚本、综合架构的监控体系结构，以及 Zabbix 4.0 LTS 服务端与 Agent 的完整部署过程——yum 源配置、数据库初始化、Web 界面初始化，外加主机、主机组、模板、监控项、触发器与告警媒介的核心概念。命令与配置可直接复用。

## 一、监控服务概念

### 1.1 监控的目标

- 对系统进行不间断实时监控，实现报警通知（邮件、微信、短信、电话等）
- 实时反馈系统当前状态
- 保证服务的可靠性与安全性
- 保证业务持续稳定运行

监控做不做得好，就看三件事：该报的报了没有（覆盖）、不该报的报了没有（准确）、报了有没有人处理（闭环）。工具只是载体，这三条才是验收标准。

监控的价值在于：

- 掌握架构服务的运行情况
- 用于分析公司网站运行情况

### 1.2 监控的两种方式

| 方式 | 说明 | 示例 |
| --- | --- | --- |
| 手动执行命令监控 | 运维人员登录服务器执行命令查看 | df、w、top、ps 等 |
| 自动执行命令监控 | 编写脚本并配合定时任务自动执行 | shell、python 脚本 |

脚本监控的天花板很明显：脚本散落在每台机器的 crond 里，结果没人汇总、历史无处可查、阈值改一次要登录所有机器。这三件事正是 Zabbix 这类集中式平台要解决的——采集收敛到一处，数据进库可回溯，配置在 Web 界面统一改。

### 1.3 监控体系的四个环节

一套完整的监控体系，无论使用什么工具，都由四个环节构成，理解这四个环节就理解了监控的本质：

| 环节 | 职责 | 常见实现 |
| --- | --- | --- |
| 指标采集 | 从被监控对象获取数据 | agent、SNMP、脚本、拨测 |
| 数据存储 | 按时间序列保存采集结果 | 时序数据库、关系数据库 |
| 可视化 | 用图表与仪表盘呈现状态 | Web 界面、曲线图、拓扑图 |
| 告警通知 | 指标异常时通知责任人 | 触发器、动作、邮件/微信/钉钉 |

Zabbix 正是把四个环节全部打通的平台：agent 负责采集，MySQL 负责存储，Web 负责可视化，触发器加动作负责告警。说白了，它就是给整套架构装上了一套"体检 + 120 急救"系统。拿这四个环节去对照任何新工具（Prometheus、Grafana 告警栈）都成立，学新平台先找齐四环节的对应组件，上手就快。

## 二、常用监控命令速查

| 监控对象 | 常用命令 | 重点指标 |
| --- | --- | --- |
| CPU | top、htop、glances | us（用户态）、sy（内核态）、id（空闲） |
| 内存 | top、htop、free | 内存可用率、swap 空间使用情况 |
| 磁盘 | df、iotop、glances | 磁盘使用率、磁盘 IO 消耗 |
| 网络 | iftop、glances | 网络带宽使用情况 |
| 进程 | top、htop、ps、glances | 进程占用内存、占用 CPU 情况 |
| 负载 | w、top、uptime、glances | 10 分钟负载、15 分钟负载 |

top 里按 1 可以展开每颗 CPU 的状态：多核机器看整体负载容易掩盖"单核被打满"的问题，这是排查"平均负载不高但服务就是卡"的第一步。

补充说明：

- CPU：us 为用户态、sy 为内核态、id 为空闲。以 MySQL 进程为主的服务器要重点关注 sy（内核态）占比；三个指标的占比参考值为 us 40%、sy 40%、id 20%。
- 内存：除内存可用率外，还要关注 swap 空间的使用情况。
- 磁盘：除使用率外，用 iotop 检查磁盘 IO 消耗。
- 进程：tomcat（java）进程容易因内存占满（内存溢出）导致服务僵死，需要重启服务；MySQL 进程重点关注 CPU 占用情况。
- 负载：经验参考为 10 分钟负载值小于 CPU 内核数，同时关注 15 分钟负载的变化趋势。

另有一个高频故障点：df 看空间明明还有剩，写入却报 No space left on device，多半是 inode 耗尽，df -i 一查便知。海量小文件（会话文件、缓存碎片）场景最容易中招。

除此之外，以下命令也是排查与日常巡检的高频工具：

| 命令 | 用途 |
| --- | --- |
| vmstat 1 | 每秒刷新进程、内存、交换、IO 与 CPU 概况，适合观察瞬时抖动 |
| iostat -x 1 | 查看各磁盘 IOPS、吞吐与 await 等待时间，定位慢盘 |
| sar -n DEV 1 | 按网卡统计流量，sar 历史数据来自 sysstat 的定时采集 |
| ss -s | 一句话概览 socket 统计，快速判断连接数是否异常 |
| ss -tan state established | 按状态统计 TCP 连接，配合 time-wait 观察定位端口耗尽 |
| date 与 chronyc sources | 确认服务器时间准确，时间漂移会影响日志关联与证书有效期 |

## 三、监控脚本编写

自动监控依赖脚本完成，以下为两个基础练习题。

### 3.1 监控内存使用情况

练习题要求：

- 正常使用情况：内存使用率高于 80%
- 异常使用情况：内存使用率低于 20%，发送报警

参考实现思路：内存使用率通过 free 命令计算。注意 free 的输出中，真正可用的内存要扣除 buff/cache，因此更准确的算法是 available = MemFree + Buffers + Cached，使用率 = (MemTotal - MemAvailable) / MemTotal。可以先用下面的命令验证数据来源：

```console
free -m
```

再从 free 的输出中提取字段做计算，配合 crond 定时任务即可实现自动监控与报警。

生产上更省事的做法是直接读 free 输出里的 available 列，内核 3.14+ 已经帮你算好，比手工加 MemFree+Buffers+Cached 更准。

### 3.2 监控服务运行状态

```bash
ps -ef|grep -c [n]ginx
netstat -lntup|grep xxx
```

说明：

- `grep -c [n]ginx` 中的 `[n]ginx` 写法可以避免 grep 匹配到自身的进程，统计结果更准确。
- tomcat 服务存在僵死问题，可通过上述方式判断服务是否真正存活。

这两个命令在 keepalived 篇还会反复用到，敲一遍就明白。

> **注意：** netstat 属于 net-tools 工具包，已停止维护，现代系统建议改用 ss：`ss -lntup | grep 10050`。二者输出含义一致，ss 直接从内核 netlink 读取，速度更快。Zabbix 的模板中默认监控项也均已改用 ss 相关 key。

## 四、监控体系结构（面试重点）

综合架构的监控体系分为以下八个层面：

| 监控层面 | 监控内容 | 常用工具 |
| --- | --- | --- |
| 硬件监控 | 服务器、路由器、交换机、防火墙 | SNMP |
| 系统监控 | CPU、内存、磁盘、网络、进程、TCP（十一种状态） | top、free、df 等 |
| 服务监控 | nginx、php、tomcat、redis、memcache、mysql | 进程与端口检查 |
| 网站监控 | 请求时间、响应时间、加载时间、页面监控 | 页面拨测 |
| 日志监控 | 日志的收集、存储、分析、展示 | ELK、日志易 |
| 安全监控 | 四层及四层以上访问控制、应用层面防护 | Firewalld、WAF（Nginx + Lua）、安全宝、牛盾云、安全狗 |
| 网络监控 | 多机房网络质量 | smokeping、监控宝、站长工具、奇云测 |
| 业务监控 | 活动产生多少流量、产生多少注册量、带来多少价值 | 数据库信息统计 |

日志监控示例：通过 access 日志可以统计用户源 IP 地址分布，例如北京 1000、上海 100、深圳 500。

> **注意：** 面试中被问到"你的原公司是如何对架构服务器进行监控的"，只回答"利用 Zabbix 软件进行监控"是错误答案。应当按照上述体系分层作答：硬件、系统、服务、网站、日志、安全、网络、业务分别说明监控对象与所用工具，Zabbix 只是承载监控的工具之一。

八层看着多，归并起来就是三层：基础设施层（硬件、系统、网络）回答"机器还活着吗"，模板默认项即可覆盖；服务层（nginx、mysql、redis）回答"进程和端口正常吗"，靠自定义监控项与触发器；业务层（订单量、注册量、支付成功率）回答"生意正常吗"，通常要开发配合埋点。排障时自底向上看：业务异常先查服务，服务正常再查基础设施，层次分明才不至于抓瞎。

## 五、原理解析：监控系统的工作流程与 Zabbix 整体架构

### 5.1 监控数据流向

以 Zabbix 被动模式为例，一条监控数据从产生到展示的完整流程如下：

1. 被监控主机上的 zabbix-agent 按 key（键值）执行采集命令，如 system.cpu.load、vfs.fs.size[/,pfree]。
2. zabbix-server 按每个监控项的更新间隔，主动连接 agent 的 10050 端口请求数据。
3. agent 返回采集结果，server 将其写入数据库（history 与 trends 两类表，前者存明细、后者存小时级聚合）。
4. server 用触发器表达式对最新值进行判断，条件成立即生成事件（problem）。
5. 动作（action）根据事件条件执行操作：发送告警消息（经媒介类型送到邮件、微信等）、执行远程命令。
6. zabbix-web 从数据库读取历史数据与趋势，渲染成曲线图、仪表盘与报表，供运维查看。

监控项数量要克制，不是越多越好。原因有三：server 的 poller 进程数量有限，监控项太多会排队能采集不过来，数据出现延迟与断层；每个监控项都在持续往数据库写 history 和 trends，采集量上去了数据库先扛不住；触发器逐项评估，项多了事件量暴涨，告警反而被淹没。经验做法是先用模板里的默认项跑一段时间，观察数据库增长曲线与采集延迟，再决定加项或拉长更新间隔，能用 1 分钟间隔满足的不要上 10 秒。

### 5.2 各组件职责与数据流

Zabbix 是分布式架构，各组件通过固定端口通信，整体数据流为：agent/proxy 采集 → server 汇总判定 → 数据库存储 → web 展示与告警。

| 组件 | 部署位置 | 职责 |
| --- | --- | --- |
| zabbix-server | 监控中心 | 接收 agent/proxy 数据，执行触发器判定，产生告警，核心处理单元 |
| zabbix-agent | 被监控主机 | 采集本机指标，被动模式应答 server 请求，主动模式定时向 server 推送 |
| zabbix-proxy | 远端机房/分支网络 | 代替 server 采集远端 agent 数据并本地缓存，定期同步给 server，适合跨公网、大规模分布式监控 |
| zabbix-java-gateway | 监控中心 | 通过 JMX 协议采集 Java 应用（Tomcat 等）内部指标 |
| zabbix-web | 监控中心 | Apache/Nginx + PHP，提供 Web 界面，读写配置与展示数据 |
| 数据库 | 监控中心 | MySQL/PostgreSQL，存储配置、历史数据、趋势数据与事件 |

常用端口：

| 端口 | 所属服务 | 通信方向 |
| --- | --- | --- |
| 10051 | zabbix-server（及 proxy 的 10051 监听） | agent 主动模式、proxy 向 server 发送数据 |
| 10050 | zabbix-agent | server 被动模式拉取数据 |
| 10052 | zabbix-java-gateway | server 查询 JMX 数据 |

> **注意：** 10051 是 server 的服务端口，10050 是 agent 的服务端口，二者不要混淆。被动模式下数据流向是 server 主动连 agent 的 10050；主动模式下是 agent 定时连 server 的 10051。

### 辨析：主动模式与被动模式

模式指的是"谁去连谁"，与数据新旧无关。被动模式由 server 定时来找 agent 要数据，agent 只需要配 Server 白名单，配置最简单，内网环境默认用它；主动模式由 agent 自己按 RefreshActiveChecks 周期从 server 拉取监控项列表，采集完再推送回去，agent 不监听端口，server 侧连接压力小。三句话概括选型：内网直连用被动；agent 在 NAT、防火墙后或跨公网（server 够不着 agent）用主动；上千台规模的大集群，主动模式能把 server 的连接压力摊到 agent 侧，更扛得住。注意主动模式要求 agent 的 Hostname 与 Web 端主机名严格一致，对不上数据就进不了库。

## 六、Zabbix 架构与组件

Zabbix 各组件职责如下：

| 组件 | 角色说明 |
| --- | --- |
| zabbix-server | 监控服务端 |
| zabbix-agent | 监控客户端（部署在被监控主机上） |
| zabbix-web | 监控网站服务 |
| php | 处理动态请求 |
| mysql | 数据库，存储监控数据 |
| zabbix-proxy | 负责收集 agent 信息，汇总后告知 zabbix-server |

版本选择：4.0 LTS（long time support，长期支持版）。

常用端口：

| 端口 | 所属服务 |
| --- | --- |
| 10051 | zabbix-server 服务端端口号 |
| 10050 | zabbix-agent 客户端端口号 |

组件虽多，最小可用集是 server + web + mysql + agent，proxy 与 java-gateway 等规模上来了再上，小环境一把梭全套反而增加维护面。

## 七、Zabbix Server 部署

Zabbix Server 的 Web 环境为 LAMP 架构（apache + php 模块 + mysql），部署流程与 wordpress 网站页面部署（LNMP）类似。以下以 zabbix-server（172.16.1.71）为例。

### 7.1 第一步：安装 Zabbix yum 源

```bash
rpm -ivh https://mirrors.tuna.tsinghua.edu.cn/zabbix/zabbix/4.0/rhel/7/x86_64/zabbix-release-4.0-1.el7.noarch.rpm
```

老版本源地址如下，仅作记录：

```bash
rpm -ivh https://mirrors.tuna.tsinghua.edu.cn/zabbix/zabbix/3.4/rhel/7/x86_64/zabbix-release-4.0-1.el7.noarch.rpm  -- 老版本
```

除清华源外，也可以使用阿里云的 Zabbix yum 源。选哪个源只影响下载速度，仓库内容一致；内网环境更常见的做法是自建私有 yum 源或 rpm 离线安装——上线机器出不了公网是常态。

### 7.2 第二步：安装服务端相关软件

软件清单：

- zabbix-server-mysql：Zabbix 服务端程序软件
- zabbix-web-mysql、httpd、php：Zabbix 服务 Web 软件
- mariadb-server：数据库服务软件

```bash
yum install -y zabbix-server-mysql zabbix-web-mysql httpd php mariadb-server
```

> **注意：** Zabbix 前端对 PHP 有扩展要求，安装后可用 php -m 检查是否加载。常见必需扩展包括 mbstring、bcmath、gd、sockets、libxml、xmlwriter、xmlreader、ctype、session，具体清单以所安装版本的官方文档为准。扩展缺失时，Web 安装界面会显示 FAIL 并阻止下一步操作。

### 7.3 第三步：修改软件配置

修改 Zabbix Server 配置文件，指定数据库密码：

```bash
vim /etc/zabbix/zabbix_server.conf
```

第 126 行：

```ini
DBPassword=<your-password>
```

> **注意：** 配置文件中的口令为脱敏占位符，实际部署时请替换为你自己的数据库口令，并保证该口令与 7.4 中 grant 授权时设置的口令一致，否则 zabbix-server 会因数据库认证失败而无法启动。zabbix_server.conf 权限建议保持 640、属主 zabbix，避免口令泄露。

修改 Apache 下 Zabbix 站点配置，设置时区：

```bash
vim /etc/httpd/conf.d/zabbix.conf
```

第 21 行：

```ini
php_value date.timezone Asia/Shanghai
```

### 7.4 第四步：初始化数据库

启动并检查数据库服务：

```bash
systemctl start mariadb.service
systemctl status mariadb.service
```

登录数据库后，创建 Zabbix 数据库和数据库管理用户：

```sql
create database zabbix character set utf8 collate utf8_bin;
grant all privileges on zabbix.* to zabbix@localhost identified by '<your-password>';
```

在 Zabbix 数据库中导入相应的表信息：

```bash
zcat /usr/share/doc/zabbix-server-mysql-4.0.0/create.sql.gz|mysql -uzabbix -p<your-password> zabbix
```

> **注意：** 创建数据库时必须指定 `character set utf8 collate utf8_bin`，否则 Zabbix Web 界面中文会出现乱码；同时不要忘记在 Apache 配置中设置 `php_value date.timezone Asia/Shanghai`，保证界面时间显示正确。.gz 压缩文件可以直接用 zcat 读取、用 zgrep 检索，无需提前解压。

导入完成后，可以登录数据库抽查导入结果：

```console
MariaDB [(none)]> use zabbix;
MariaDB [zabbix]> show tables;
```

能看到 hosts、items、triggers、history、trends、users 等以监控配置与数据命名的表，即说明表结构导入成功。create.sql.gz 由 zabbix-server-mysql 软件包提供，位于 /usr/share/doc/zabbix-server-mysql-4.0.0/ 目录下，更换版本时注意目录名中的版本号随之变化。导入中途 Ctrl+C 会造成表不完整，重导前先 drop database 重建，否则残留半截表会引发各种诡异报错。

除 DBPassword 外，zabbix_server.conf 中还有几个与部署直接相关的参数：

| 参数 | 作用 |
| --- | --- |
| DBHost | 数据库地址，数据库独立部署时填写数据库服务器 IP |
| DBName / DBUser / DBPort | 库名、用户名与端口，需与 7.4 中的授权保持一致 |
| ListenPort | server 监听端口，默认 10051 |
| StartPollers | poller 进程数量，决定并发采集能力，监控规模大可适当调大 |
| AlertScriptsPath | 告警脚本目录，微信、钉钉等自定义媒介的脚本放在这里 |

> **注意：** Zabbix 5.0 及以后版本要求数据库字符集为 utf8mb4（`create database zabbix character set utf8mb4 collate utf8mb4_bin;`），mysql/mariadb 的参数建议同时开启 innodb 相关优化，具体以所安装版本的官方文档为准。

### 7.5 第五步：启动相关服务

```bash
systemctl start zabbix-server.service httpd mariadb.service
systemctl enable zabbix-server.service httpd mariadb.service
```

需要启动的服务包括数据库服务、Zabbix 服务、httpd 服务。至此，Zabbix Server 命令行操作结束。这里有个坑：启动顺序上数据库必须先起来，zabbix-server 连不上库会反复重试并在日志里刷错误，看似启动失败，其实只是在等数据库。

### 7.6 第六步：Web 界面初始化

浏览器访问 `http://172.16.1.71/zabbix/setup.php`，按提示完成初始化配置。初始化信息会记录在 `/etc/zabbix/web/zabbix.conf.php` 中。

Web 初始化的步骤分解如下：

1. 欢迎页点击 Next，进入前置条件检查页，确认所有 PHP 扩展与参数满足要求（有 FAIL 项需先安装对应扩展）。
2. 配置数据库连接：Database type 选 MySQL，填写数据库主机、库名、用户、口令，端口 3306。
3. 填写 Zabbix server 名称与主机地址（本机填 172.16.1.71），选择界面时区。
4. 检查摘要页确认配置无误，点击下一步生成配置文件。
5. 若提示无法写入，手动把生成的配置内容保存到 `/etc/zabbix/web/zabbix.conf.php`。
6. 完成安装，进入登录页。

初始化页面配错也不必重装：配置最终落在 /etc/zabbix/web/zabbix.conf.php，直接改文件再重启 httpd 即可纠正。

> **注意：** 课堂原文此处写作 http://10.0.0.71/zabbix/setup.php，与前文规划的 zabbix-server 地址 172.16.1.71 不一致，本文统一为 172.16.1.71。实际环境请以本机真实 IP 为准，关键是保持"访问地址 = zabbix-server 所在主机地址"这一对应关系。

### 7.7 第七步：登录 Web 界面

默认管理员用户名为 `Admin`，密码为 `zabbix`。

> **注意：** 首次登录后应立即修改默认管理员密码，并停用或删除不用的内置账号（如 guest），这是所有监控系统上线的基本安全要求。

生产上栽过的教训：默认口令 zabbix 忘改，监控界面被扫到后，攻击者借监控系统的远程命令功能直捣内网。监控系统手里握着所有主机的信息与执行通道，它的口令优先级比业务系统还高。

## 八、Zabbix Agent 部署

Agent 部署在被监控的主机上，以下以 web01（172.16.1.7）为例。

### 8.1 第一步：安装 yum 源

```bash
rpm -ivh https://mirrors.tuna.tsinghua.edu.cn/zabbix/zabbix/4.0/rhel/7/x86_64/zabbix-release-4.0-1.el7.noarch.rpm
```

### 8.2 第二步：安装 Agent 软件

```bash
yum install -y zabbix-agent
```

也可以直接使用 rpm 安装：

```bash
rpm -ivh https://mirrors.tuna.tsinghua.edu.cn/zabbix/zabbix/4.0/rhel/7/x86_64/zabbix-agent-4.0.0-2.el7.x86_64.rpm
```

### 8.3 第三步：配置 Agent

```bash
vim /etc/zabbix/zabbix_agentd.conf
```

第 98 行，指定 Zabbix Server 地址：

```ini
Server=172.16.1.71
```

> **注意：** Server 参数采用逗号分隔的 IP 列表，只有列表中的地址才能被动拉取该 agent 的数据；如需 agent 主动向 server 发送数据，还要配置 ServerActive=172.16.1.71，两者含义不同（详见下一篇"主动/被动模式"）。

agent 配置文件中其他常用参数：

| 参数 | 作用 |
| --- | --- |
| Server | 允许哪些 IP 被动拉取数据，逗号分隔，配合 StartAgents 使用 |
| ServerActive | 主动模式下的 server 地址，配了它 agent 才会向 server 推送数据 |
| Hostname | agent 上报的主机名，主动模式下必须与 Web 端创建的主机名完全一致 |
| ListenPort | agent 监听端口，默认 10050 |
| StartAgents | 被动模式的预分配进程数，默认 3，并发采集高时可调大 |
| Timeout | 单次请求超时时间（秒），默认 3 |
| AllowRoot / UnsafeUserParameters | 是否允许以 root 运行、是否允许参数化命令包含特殊字符，涉及安全，按需开启 |
| Include | 加载指定目录下的自定义配置，默认包含 /etc/zabbix/zabbix_agentd.d/*.conf |

改完配置记得 systemctl restart zabbix-agent 再验证。Server 列表写错的典型症状是 Web 端主机一直变灰（不可达），agent 日志里会有"connection from ... not allowed"之类的拒绝记录，对号入座很快。

### 8.4 第四步：启动并验证服务

```console
[root@web01 ~]# systemctl start zabbix-agent
[root@web01 ~]# netstat -lntup|grep 10050
tcp        0      0 0.0.0.0:10050           0.0.0.0:*            LISTEN      4509/zabbix_agentd
tcp        0      0 :::10050                :::*                 LISTEN      4509/zabbix_agentd
```

看到 10050 端口处于 LISTEN 状态，说明 Agent 启动成功。

更进一步的验证：在 server 侧安装 zabbix-get 后执行 zabbix_get -s 172.16.1.7 -k agent.ping，返回 1 即表示 server 到 agent 的链路全通，这比只看端口监听更接近真实采集路径。

现代系统上的等价验证命令：

```console
ss -lntup|grep 10050
```

## 九、主机、主机组与模板

Agent 装好只是被监控主机具备了"被采集"的能力，还需要在 Zabbix 的 Web 界面中登记主机，server 才知道该去采集谁。这层关系想清楚，后面所有配置操作都有了坐标系：Web 界面改的是 server 侧的采集计划，agent 只负责执行。相关概念如下：

| 概念 | 作用说明 |
| --- | --- |
| 主机 | 被监控的对象，需配置主机名（唯一标识）、可见名称、所属主机组与 agent 接口（IP/DNS + 端口） |
| 主机组 | 对主机进行分类管理，是批量操作与权限分配的载体 |
| 模板 | 将监控项、触发器、图形、应用集等集中配置，多台主机链接同一模板即继承全部配置 |
| 监控项 | 定义采集什么数据、用什么 key、多久采集一次、历史与趋势数据保留多久 |
| 应用集 | 将同类监控项归类展示，便于在最新数据页按类别查看 |

使用模板的价值：修改一次模板，所有链接该模板的主机同步生效。例如给 100 台 Web 服务器链接 Template OS Linux by Zabbix agent，即可一次性获得 CPU、内存、磁盘、网卡、进程等全套监控，无需逐台配置。更深一层的价值在标准化：同一类角色的机器跑同一套模板，触发器阈值、图形口径完全一致，排查问题时不会出现"两台机器指标含义对不上"的尴尬；模板升级（比如换监控 key）也是一处改全量生效，这就是配置即代码的雏形。

模板的操作要点：一台主机可以链接多个模板；监控项、触发器、图形随模板继承而来，在主机上直接修改继承项会与模板断开联动，生产环境通常的做法是改模板、统一生效。批量纳管新主机时，先选好模板再创建主机，是效率最高的路径。

官方模板开箱即用但监控项偏多，生产上常见的做法是复制一份官方模板做减法，或自建精简模板；模板命名带上角色与版本号（如 Linux-web-base-v1），后续升级与回滚有据可查。

主机接口与安全：

| 项目 | 说明 |
| --- | --- |
| 接口类型 | 一台主机可配置多个接口：agent、SNMP、JMX、IPMI，分别对应不同的采集方式 |
| 接口地址 | agent 接口填写 IP 或 DNS 加端口（默认 10050），server 据此发起采集 |
| 连接加密 | Zabbix 3.0 起支持 TLS 与 PSK 加密通信，跨公网或安全要求高的环境建议开启 |
| 启用与停用 | 主机可临时停用，停用后不采集也不告警，适合维护窗口期使用 |

接口地址填错是主机变灰的另一大原因：agent 接口填的是被监控机自己的 IP，不是 server 的 IP，方向别搞反。

## 十、触发器与告警表达式

### 10.1 触发器的作用

触发器（trigger）是一个基于监控项值的逻辑表达式，条件成立即视为出现故障，产生告警事件。表达式的基本形式为：

```text
{主机名:键值.函数()}  比较运算符  阈值
```

例如 `{web01:vfs.fs.size[/,pfree].last()}<10` 表示 web01 的根分区剩余空间低于 10% 时触发告警。

### 10.2 常用表达式函数

| 函数 | 说明 |
| --- | --- |
| last() | 取最新一次采集值，最常用 |
| min() / max() | 一段时间内的最小值 / 最大值 |
| avg() | 一段时间内的平均值 |
| nodata() | 一段时间内没有采集到数据（agent 失联时最有用） |
| diff() / change() | 判断一段时间内数值是否发生变化 |

### 10.3 告警严重等级（severity）

每个触发器都要指定严重等级，运维可以按等级过滤与分派告警：

| 等级 | 名称 | 典型场景 |
| --- | --- | --- |
| 0 | 未分类 | 未明确级别的信息 |
| 1 | 信息 | 提示类，无需立即处理 |
| 2 | 警告 | 需要关注，如磁盘使用率 80% |
| 3 | 一般严重 | 影响部分业务，需尽快处理 |
| 4 | 严重 | 核心服务受影响 |
| 5 | 灾难 | 业务已中断，最高优先级 |

触发器还支持两个表达式：问题表达式（成立即告警）与恢复表达式（成立即恢复）。只配问题表达式时，条件不成立即自动恢复；对于"低于阈值算故障"这类场景，显式配置恢复表达式可以避免告警反复抖动。多个触发器之间还可以配置依赖关系，上游告警时抑制下游告警，减少告警风暴。

nodata() 有个前提容易忽略：server 与 agent 两端时间必须同步，时间漂移会整片误报"失联"。值班时看到大面积 nodata 告警，先怀疑时间同步，再查网络。

## 十一、动作与告警媒介

### 11.1 动作的三要素

动作（action）决定"告警如何被处理"，由三部分组成：

1. 条件：满足什么条件时触发，如触发器严重等级 ≥ 一般严重、指定主机组。
2. 操作：发送消息给谁、消息内容是什么、是否需要执行远程命令（如自动重启服务）。
3. 恢复操作与升级操作：故障恢复时发送恢复通知；问题长时间未处理时逐级升级通知更高级别负责人。

### 11.2 告警媒介类型

媒介（media type）决定消息"通过什么渠道送出"：

| 媒介 | 实现方式 | 说明 |
| --- | --- | --- |
| 邮件 | zabbix-server 内置 SMTP 发送，或经邮件网关脚本 | 最常用，需在服务器上正确配置发信参数 |
| 微信 | 自定义脚本（python）调用企业微信 API | 脚本存放于 AlertScriptsPath 指定的目录 |
| 钉钉 | 自定义脚本调用钉钉机器人 Webhook | 在钉钉群添加自定义机器人，获取 Webhook 地址，脚本 POST 消息到该地址 |
| 短信/电话 | 第三方短信电话报警平台 | 如阿里大鱼、OneAlert 等 |

> **注意：** 邮件、微信、钉钉都遵循同一套配置逻辑：先定义媒介类型（脚本类媒介指向告警脚本），再在动作中引用媒介，最后给用户绑定该媒介与接收地址。三者差别只在投递通道，配置骨架相同。

告警消息内容中常用的宏：

| 宏 | 含义 |
| --- | --- |
| {HOST.NAME} | 触发告警的主机名 |
| {TRIGGER.NAME} | 触发器名称 |
| {ITEM.KEY} | 监控项键值 |
| {ITEM.VALUE} | 触发时的监控值 |
| {EVENT.DATE} / {EVENT.TIME} | 告警发生的日期与时间 |
| {TRIGGER.SEVERITY} | 告警等级 |

配置动作时，在消息内容中插入这些宏，收件人才能一眼看到是哪台机器、哪个指标、出了什么值；否则告警信息缺少可操作性，收到后还要登录界面二次排查。

消息模板建议存成团队统一格式，所有动作复用同一套写法，收到告警格式一致，值班扫一眼就能抓住重点。

## 十二、常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| zabbix-server 启动失败 | 数据库口令错误、数据库未启动、字符集不符 | systemctl status zabbix-server; tail /var/log/zabbix/zabbix_server.log | 修正 DBPassword；先启动 mariadb；按版本要求设置 utf8/utf8mb4 |
| Web 界面中文乱码 | 数据库未使用 utf8 排序规则 | show create database zabbix; | 重建数据库并指定 utf8_bin，重新导入 create.sql |
| Web 界面时间差 8 小时 | php 时区未设置 | grep date.timezone /etc/httpd/conf.d/zabbix.conf | 设置 php_value date.timezone Asia/Shanghai 并重启 httpd |
| setup.php 无法访问 | httpd 未启动或防火墙拦截 | systemctl status httpd; firewall-cmd --list-services | 启动 httpd 并放行 80 端口 |
| 主机图标不变绿 | agent 的 Server 配置错误、10050 未监听、server 到 agent 网络不通 | ss -lntup \| grep 10050; 在 server 上 telnet 172.16.1.7 10050 | 修正 Server 地址；启动 zabbix-agent；放行防火墙 |
| Web 页面 502/空白 | php-fpm 或 php 模块异常、数据库连接失败 | systemctl status httpd php-fpm; tail /var/log/httpd/error_log | 修复 php 环境；检查 zabbix.conf.php 中数据库配置 |

## 十四、现代环境补充

CentOS 7 已于 2024 年 6 月 EOL，新环境建议迁移到 Rocky Linux、AlmaLinux 或 CentOS Stream；同时 Zabbix 4.0 LTS 也已停止官方支持，新部署建议直接选择 6.0 或 7.0 LTS 系列（官方 yum 源提供 rhel8/rhel9 目录）。升级时注意 Zabbix 不支持跨大版本直接升级，须按 4.0 → 5.0 → 6.0 的顺序逐级进行，升级前务必备份数据库。

新旧环境对照：

| 旧（CentOS 7） | 新（Rocky/AlmaLinux/CentOS Stream 8/9） |
| --- | --- |
| yum install | dnf install |
| netstat -lntup | ss -lntup |
| service httpd start | systemctl start httpd |
| iptables -A INPUT -p tcp --dport 10050 -j ACCEPT | firewall-cmd --permanent --add-port=10050/tcp; firewall-cmd --reload |
| httpd（Apache）+ php 模块 | httpd 或 nginx + php-fpm 均可，LNMP 同样可以承载 zabbix-web |
| mariadb 5.5/10.1 | mariadb 10.5/10.11，注意 Zabbix 各版本对数据库版本有最低要求 |

此外还有两点提醒：一是 Zabbix 5.0+ 的数据库字符集要求为 utf8mb4，配置数据库时不要照搬 4.0 的 utf8 写法；二是 SELinux 开启的环境下，zabbix-server 访问数据库与 agent 若遇 permission denied，需按审计日志调整布尔值或策略。

## 小结

- 监控的核心是不间断实时监控与告警通知，分为手动命令监控和脚本自动监控两种方式。
- 监控体系由采集、存储、可视化、告警四个环节构成，Zabbix 把四个环节全部打通。
- 面试描述监控体系时，应按硬件、系统、服务、网站、日志、安全、网络、业务八个层面分层回答。
- Zabbix 由 server、agent、web、php、mysql、proxy 组成，4.0 为 LTS 长期支持版本，服务端与客户端端口分别为 10051 和 10050。
- Server 部署七步：安装 yum 源、安装软件、修改配置、初始化数据库、启动服务、Web 初始化、登录验证。
- 数据库初始化时指定 utf8 字符集可避免 Web 界面中文乱码，表结构通过 zcat 导入 create.sql.gz。
- Agent 部署四步：安装 yum 源、安装软件、配置 Server 地址、启动并验证 10050 端口。
- 主机、主机组、模板、监控项、触发器、动作与媒介共同构成 Zabbix 的配置骨架：模板实现配置复用，触发器负责判定，动作与媒介负责通知。

## 自测题

1. 监控体系的四个环节是什么？Zabbix 中分别由哪些组件承担？
2. zabbix-server 与 zabbix-agent 各自监听什么端口？数据流向有什么区别？
3. 初始化数据库时不指定 utf8 字符集会有什么后果？完整写出创建数据库的 SQL。
4. 触发器表达式 {web01:vfs.fs.size[/,pfree].last()}<10 的含义是什么？
5. 一台新服务器上线，从安装 agent 到能收到告警，需要经过哪些配置步骤？

> **答案：** 1. 四环节为采集、存储、可视化、告警。Zabbix 中：agent/proxy 负责采集，MySQL 负责存储，zabbix-web 负责可视化，触发器与动作加媒介负责告警。2. server 监听 10051，agent 监听 10050。被动模式下 server 主动连接 agent 的 10050 拉取数据；主动模式下 agent 定时连接 server 的 10051 推送数据。3. 不指定 utf8 会导致 Web 界面中文乱码。SQL 为 create database zabbix character set utf8 collate utf8_bin;（Zabbix 5.0+ 需使用 utf8mb4）。4. 表示当 web01 根分区剩余空间百分比的最新采集值小于 10% 时，触发器条件成立，产生告警。5. 一、安装 zabbix-agent 并配置 Server 为 zabbix-server 地址；二、启动 agent 并确认 10050 端口监听；三、在 Web 界面创建主机（填写名称、主机组、接口地址）并链接模板；四、在模板基础上按需添加自定义监控项与触发器；五、配置动作（条件与操作）与告警媒介，并为用户绑定接收方式。
