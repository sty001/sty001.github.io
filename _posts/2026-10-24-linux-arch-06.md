## 远程管理服务概念介绍
{: .sec-know}

| 服务 | 安全性 | 端口 | 默认 root 登录 | 典型场景 |
| --- | --- | --- | --- | --- |
| SSH | 安全的远程连接，数据信息是加密的 | 22 | SSH 服务默认可以 root 用户远程连接 | 系统远程连接 |
| TELNET | 不安全的远程连接，数据信息是明文的 | 23 | telnet 服务默认不可以让 root 用户远程连接 | 网络设备远程连接 |

### 补充：什么是 shell
{: .sec-know}

1. 每连接登录到一个 Linux 系统中，就是一个 shell
2. 可以一个 Linux 系统有多个会话连接，每一个会话都是一个 shell
3. 系统中用户可以实现相互转换，每转换一个用户就是一个 shell

**shell 特点说明：**

1. 一般命令行临时配置的信息，只会影响当前 shell
2. 命令配置的信息如果想生效，需要切换 shell。例如：修改主机名称

## 原理解析：SSH 的加密原理
{: .sec-know}

先记住一个类比：**私钥是钥匙，公钥是锁头。**

SSH 同时用到两类加密，各司其职：

| 加密类型 | 特点 | 在 SSH 中的角色 |
| --- | --- | --- |
| 非对称加密（公钥 / 私钥） | 公钥加密的内容只有配对的私钥能解；私钥签名的内容可用公钥验真。速度慢 | 握手阶段协商会话密钥、验证服务端主机身份、公钥认证用户身份 |
| 对称加密 | 加解密用同一把密钥，速度快 | 连接建立后，所有会话数据都用协商出的对称密钥加密传输 |

SSH 的思路是**混合加密**：握手阶段用非对称加密安全地协商出一把只有通信双方知道的对称会话密钥，之后的数据传输全部使用对称加密 —— 既保证了密钥分发的安全，又获得了对称加密的性能。

### SSH 连接的完整握手过程（文字步骤）
{: .sec-prac}

1. 客户端向服务端 22 端口发起 TCP 连接（三次握手）。
2. **版本协商**：双方各自发送协议版本串（如 `SSH-2.0-OpenSSH_8.7`），确定使用 SSH-2 协议。
3. **密钥交换（KEX）**：双方使用 ECDH / Diffie-Hellman 算法，在不安全的信道上协商出共享的会话密钥；即使握手流量被完整窃听，也推不出这把密钥。
4. **服务端身份确认**：服务端发送主机公钥（host key）指纹，客户端与本地 `known_hosts` 里记录比对。不一致时报警，这一步用来防范中间人攻击。
5. **算法协商**：确定后续使用的对称加密算法、HMAC 完整性校验算法等。
6. **用户认证**：服务端要求客户端证明身份，支持口令认证（password）与公钥认证（publickey）等方式，可配置只允许其中一种。
7. **进入会话**：认证通过后，双方用协商好的对称密钥加密传输一切数据（命令、回显、转发流量），直到连接关闭。

> **注意：** 前文的"七步连接表"是简化视角：实际流程是先完成密钥交换、建立起加密通道，再做用户认证；用户密码始终在加密通道内传输，不会明文过网络。而"服务端让客户端确认公钥"对应上面的第 4 步 —— 确认的是**服务端主机公钥**，用于防止连错服务器。
{: .sec-pit}

## SSH 服务连接工作原理（数据加密）
{: .sec-know}

连接建立的七个步骤：

| 步骤 | 发起方 | 动作 |
| --- | --- | --- |
| 第一个步骤 | 客户端 | 执行远程连接命令 |
| 第二个步骤 | 客户端 + 服务端 | 建立三次握手过程 |
| 第三个步骤 | 服务端 | 让客户端进行确认是否接收服务端公钥信息 |
| 第四个步骤 | 客户端 | 进行公钥确认，接收到公钥信息 |
| 第五个步骤 | 服务端 | 让客户端确认登录用户密码信息 |
| 第六个步骤 | 客户端 | 进行密码信息确认 |
| 第七个步骤 | 客户端 + 服务端 | 远程连接建立成功 |

### 私钥和公钥的作用

1. 利用私钥和公钥对数据信息进行**加密处理**
2. 利用公钥和私钥进行**用户身份认证**

| 连接方式 | 密钥对的作用 |
| --- | --- |
| 基于密码的方式进行远程连接 | 公钥和私钥只能完成数据加密过程 |
| 基于密钥的方式进行远程连接 | 公钥和私钥可以完成身份认证工作 |

### SSH 支持的认证方式

sshd 支持多种认证方式，可在 `sshd_config` 中分别开关，实际环境按安全等级选用：

| 认证方式 | 配置项 | 安全性 | 适用场景 |
| --- | --- | --- | --- |
| 公钥认证 | `PubkeyAuthentication yes` | 高，暴力破解无效 | 管理机、批量管理的默认选择 |
| 口令认证 | `PasswordAuthentication yes` | 低，怕暴力破解与撞库 | 临时使用，普及密钥后关闭 |
| 键盘-interactive | `KbdInteractiveAuthentication` | 取决于后端（常用于二因素） | 配合 PAM 做二次认证 |
| 基于主机认证 | `HostbasedAuthentication` | 中，信任同网段主机 | 内网受信主机批量互信，少用 |

> **注意：** 认证方式可以叠加，服务端按客户端尝试的顺序匹配；只保留公钥认证（`PasswordAuthentication no`）是生产服务器最常用的收敛姿势，但务必先确认密钥能登录再关闭口令认证。
{: .sec-pit}

## SSH 远程连接的方式

| 方式 | 特点 |
| --- | --- |
| a 基于口令的方式进行远程连接 | 连接比较麻烦，连接不太安全 |
| b 基于密钥的方式进行远程连接 | 连接方便，连接比较安全 |

### 基于密钥方式连接的过程（原理）
{: .sec-know}

1. **客户端（管理端）** 执行命令创建密钥对
2. **客户端（管理端）** 建立远程连接（口令），发送公钥信息
3. **客户端（管理端）** 再次建立远程连接
4. **服务端（被管理端）** 发送公钥质询信息（你要是能打开我的锁头吗）
5. **客户端（管理端）** 处理公钥质询信息（钥匙将锁头打开），将质询结果返回给服务端
6. **服务端（被管理端）** 接收到质询结果，建立好远程连接

顺带解释为什么公钥认证不怕窃听：私钥从头到尾不离开客户端，服务端用公钥加密质询、只有持私钥者能应答；抓包拿到的只是密文质询，且质询里掺了会话随机数，重放也过不了关。口令认证则要把密码送进通道，一旦握手被降级或误连钓鱼机，风险完全不同。

## 实现基于密钥连接的部署步骤
{: .sec-prac}

**准备工作**：准备好一台管理服务器（如 `m01`）。
{: .callout-prac}

### 第一个历程：管理端创建密钥对信息

```bash
# -t dsa 指定密钥类型；DSA 已被 OpenSSH 废弃，新环境请用 ed25519 或 rsa
# 回车接受默认路径 ~/.ssh/id_dsa；passphrase 直接回车表示不设口令，脚本化场景通常这样选
[root@m01 ~]# ssh-keygen -t dsa
Generating public/private dsa key pair.
Enter file in which to save the key (/root/.ssh/id_dsa):
Created directory '/root/.ssh'.
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in /root/.ssh/id_dsa.
Your public key has been saved in /root/.ssh/id_dsa.pub.
```

> **注意：** DSA 算法已被废弃。OpenSSH 7.0 起默认不再生成 DSA 密钥，新环境请改用 ed25519（推荐）或 RSA。生成命令分别为 `ssh-keygen -t ed25519` 与 `ssh-keygen -t rsa -b 4096`；ed25519 密钥更短、更快、更安全，是现代默认推荐。
{: .sec-pit}

**现代推荐的密钥对生成方式：**

```bash
# 推荐：ed25519
# -C 写入注释，方便日后在 authorized_keys 里辨认每把密钥的归属主机
ssh-keygen -t ed25519 -C "m01 admin key"

# 兼容老系统：RSA 4096 位
# -b 4096 指定密钥长度，位数越长安全性越高但生成与认证开销也越大
ssh-keygen -t rsa -b 4096 -C "m01 admin key"
```

**生成的密钥文件说明：**

| 文件 | 内容 | 建议权限 |
| --- | --- | --- |
| `~/.ssh/id_ed25519`（或 `id_rsa`） | 私钥，必须严格保密，只有本人持有 | 600 |
| `~/.ssh/id_ed25519.pub` | 公钥，可以任意分发 | 644 |
| `~/.ssh/authorized_keys` | 服务端存放的、被信任的公钥列表 | 600 |
| `~/.ssh/known_hosts` | 客户端记录的服务端主机公钥指纹 | 644 |

> **注意：** `~/.ssh` 目录权限必须是 700，`authorized_keys` 必须是 600，且属主必须是登录用户本人。这里有个坑：sshd 默认开启 `StrictModes yes`，权限过宽会**直接拒绝密钥认证**，这是"公钥明明分发成功却还要输密码"的头号原因，生产上栽过的次数数不清。
{: .sec-pit}

### 第二个历程：管理端将公钥进行分发

```bash
ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.31
```

`ssh-copy-id` 做的事情很简单：把 `-i` 指定的公钥内容追加到目标主机对应用户的 `~/.ssh/authorized_keys` 末尾（文件不存在会自动创建并修好权限）。说白了，它不传私钥、不改 sshd 配置，就是往服务端的"信任名单"里加一行，等价于一条免交互的 `cat 公钥 >> authorized_keys`。

`authorized_keys` 每行还能带前置选项做精细化限制：`from="10.0.0.*"` 只允许指定来源使用这把钥匙；`command="/usr/local/bin/backup.sh"` 强制这把钥匙只能执行某条命令，典型用法是给备份拉取账号上锁；`no-pty`、`no-port-forwarding` 禁掉交互终端与隧道。给第三方系统开的钥匙，至少加一个 `from` 限制。

## 批量分发公钥

### 问题 01：如何实现批量管理多台主机

如何编写脚本进行批量分发公钥？编写脚本最简单的方式：**堆命令**。

```bash
#!/bin/bash
# for 变量只放主机号后两位，前面的网段在命令里写死，改网段时只需改这一处
# do/done 是 shell 的固定语法，循环体里的 ssh-copy-id 仍会走交互流程
for ip in 31 7 41
do
  ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.$ip
done
```

> **注意：** 上面的脚本有交互过程，会遇到三个问题：
>
> 1. 需要有确认 yes 或 no
> 2. 需要输入密码信息
> 3. 服务端端口号变化了，如何分发公钥
{: .sec-pit}

### 问题 02：如何不用交互输入密码信息

**第一步骤：下载安装软件**

```bash
yum install -y sshpass
```

**第二步骤：执行免交互方式分发公钥命令**

```bash
sshpass -p'<your-password>' ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.41
```

### 问题 03：如何不输入连接 yes 或 no 的确认信息
{: .sec-ver}

```bash
ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.41 "-o StrictHostKeyChecking=no"
```

这个 yes/no 提示来自主机密钥机制：首次连接一台主机时，客户端拿到服务端的主机公钥指纹，问你要不要信任它。选 yes 后指纹写入客户端的 `~/.ssh/known_hosts`，之后每次连接都默默比对，不一致才报警——这是防中间人攻击的关卡，排错表里的 `Host key verification failed` 就是它触发的。`StrictHostKeyChecking=no` 直接跳过确认，批量脚本里基本都这么写；生产上更稳的做法是先用 `ssh-keyscan` 批量收指纹进 known_hosts，而不是永久关掉校验。

`known_hosts` 每行一条记录，格式是"主机模式 算法 指纹"；开启 `HashKnownHosts` 后主机名被哈希，文件泄露也不会暴露你连过哪些机器。指纹核对有标准方法：在服务端执行 `ssh-keygen -l -f /etc/ssh/ssh_host_ed25519_key.pub` 查看指纹，与客户端首次连接时显示的指纹肉眼比对，一致才输 yes。`StrictHostKeyChecking` 常用三档：`yes` 严格校验、`accept-new` 首连自动收指纹后转为严格校验（批量场景的折中推荐）、`no` 完全跳过（只留给一次性环境）。

### 问题 04：服务端口号发生变化，如何进行批量分发公钥

```bash
sshpass -p'<your-password>' ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.41 -p 52113 "-o StrictHostKeyChecking=no"
```

### 分发公钥脚本

```bash
[root@m01 scripts]# vim fenfa_pub_key.sh
```

```bash
#!/bin/bash
# {1..100} 是 bash 花括号展开，一次生成 1 到 100 的主机号列表
# &>/dev/null 丢掉交互输出，但分发失败的机器也看不出结果，生产上应把失败主机单独记日志

for ip in {1..100}
do
  echo "==================== host 172.16.1.$ip pub-key start fenfa ==================== "
  sshpass -p'<your-password>' ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.$ip "-o StrictHostKeyChecking=no" &>/dev/null
  echo -e "host 172.16.1.$ip fenfa success."
  echo "==================== host 172.16.1.$ip fenfa end ==================== "
  echo ""
done
```

### 分发公钥检查脚本（批量管理脚本）—— 串行批量管理
{: .sec-ver}

```bash
[root@m01 scripts]# cat check_pub_key.sh
```

```bash
#!/bin/bash
# CMD=$1 把要执行的命令作为参数传入，一个脚本就能复用查不同内容
# 循环变量只写主机号后两段，前面的 172.16.1. 固定不变
CMD=$1
for ip in {7,31,41}
do
  echo "==================== host 172.16.1.$ip check ==================== "
  # $CMD 不加引号会被按空白拆开，含空格或特殊字符的命令要写成 "$CMD"
  ssh 172.16.1.$ip $CMD
  echo ""
done
```

> **注意：** 分发脚本里把密码明文写在脚本中存在泄露风险，生产环境建议改用 ansible 的密钥方式，或在分发完成后立即清理脚本中的密码。更稳妥的做法是把密码放进只有本人可读的文件（权限 600），或改用一次性密码、推送证书的方式。
{: .sec-pit}

脚本还可以再改造一步：IP 列表从循环里抽出去放文件（`for ip in $(cat hosts.list)`），机器增减只维护列表；分发失败的机器记日志单独重试；循环体加 `&` 并 `wait` 做并发，百台机器的分发时间能从几十分钟压到几分钟。

## SSH 服务配置文件
{: .sec-expl}

配置文件路径：`/etc/ssh/sshd_config`

```ini
# 这几行是 sshd_config 的全局段，对所有连接生效
# ListenAddress 只能填本机网卡上真实存在的地址，填错会导致 sshd 启动失败
# PermitRootLogin 建议改 no 前，先确认普通用户 + sudo 的通道已验证可用
Port 22                   --- 修改服务端口信息
ListenAddress 0.0.0.0     --- 监听地址 指定一块网卡能够接受远程访问请求  *****
                              PS: 指定监听地址只能是本地网卡上有的地址
PermitEmptyPasswords no   --- 是否允许远程用户使用空密码登录,默认不允许
PermitRootLogin yes       --- 是否禁止 root 用户远程连接主机 建议改为 no
GSSAPIAuthentication no   --- 是否开启 GSSAPI 认证功能 不用的时候关闭
UseDNS no                 --- 是否开启反向 DNS 解析功能 建议进行关闭
```

| 配置项 | 建议 |
| --- | --- |
| `Port 22` | 可改成非标准端口，配合防火墙减少扫描 |
| `ListenAddress 0.0.0.0` | 只监听内网地址，能显著降低暴露面 |
| `PermitEmptyPasswords no` | 保持默认，不允许空密码 |
| `PermitRootLogin yes` | 建议改为 `no`，改用普通用户 + sudo |
| `GSSAPIAuthentication no` | 关闭可加快连接速度 |
| `UseDNS no` | 关闭反向解析，解决 SSH 连接慢的常见问题 |

### sshd_config 常用参数详解表
{: .sec-expl}

| 参数 | 作用 | 建议值 |
| --- | --- | --- |
| `Port` | 服务监听端口，可写多行监听多个端口 | 按需修改，并同步防火墙 |
| `ListenAddress` | 只监听指定网卡地址，必须是本机已有地址 | 内网地址，降低暴露面 |
| `PermitRootLogin` | 是否允许 root 远程登录 | `no`（用普通用户 + sudo） |
| `PasswordAuthentication` | 是否允许口令认证 | 密钥普及后设 `no` |
| `PubkeyAuthentication` | 是否允许公钥认证 | `yes` |
| `AllowUsers` | 白名单：只有列出的用户能登录，如 `AllowUsers ops deploy` | 按需收紧 |
| `AllowGroups` / `DenyUsers` | 按组放通 / 按用户拒绝 | 配合使用做细粒度控制 |
| `UseDNS` | 是否对客户端 IP 做反向 DNS 解析 | `no`（否则连接明显变慢） |
| `GSSAPIAuthentication` | 是否启用 GSSAPI 认证 | `no`（不用 Kerberos 时关掉） |
| `PermitEmptyPasswords` | 是否允许空密码 | `no` |
| `MaxAuthTries` | 单次连接最大认证尝试次数 | `3`，防暴力破解 |
| `ClientAliveInterval` | 服务端每隔多少秒发一次保活探测 | `300`，配合下一项防半开连接 |
| `ClientAliveCountMax` | 保活探测无响应多少次后断开 | `3` |
| `LoginGraceTime` | 认证阶段的超时时间 | `60` |
| `StrictModes` | 是否检查家目录与 authorized_keys 权限 | `yes`（保持默认，注意权限） |
| `AuthorizedKeysFile` | 公钥文件路径，默认 `.ssh/authorized_keys` | 保持默认 |
| `Protocol` | 协议版本，只支持 2 | 已废弃，新版本仅 SSH-2，无需配置 |

> **注意：** 修改 `sshd_config` 后执行 `systemctl reload sshd` 生效（reload 不断开现有连接）；改端口、改监听地址等重大调整建议先用 `sshd -t` 检查语法，并保留一个现有连接再重载，避免把自己关在门外。
{: .sec-pit}

为什么生产一定要禁掉 root 密码登录？三个原因：root 是暴力破解唯一的高价值目标，口令一旦被撞库，攻击者直接拿到最高权限；禁掉后走普通用户 + sudo 登录，每一步提权都留审计记录，出问题能定位到人；`PermitRootLogin no` 还顺带挡掉大批自动化扫描脚本——它们默认只试 root。生产上栽过的案例多数是 root 弱口令被扫出来，等发现时已经晚了。

### 辨析：客户端配置与服务端配置各管哪一头
{: .sec-expl}

`sshd_config` 管服务端（被连接方），`ssh_config` 与 `~/.ssh/config` 管客户端（发起方），两头完全独立。常见误区：服务端改了 `Port`，客户端不知道，连接报 `Connection refused`——改端口属于两头都要动的操作，客户端 config 里要同步写 `Port`。排查时先分清在哪一头：`ssh -v` 看客户端行为，`journalctl -u sshd` 看服务端日志。

## SSH 远程服务防范入侵的案例
{: .sec-ex}

1. **用密钥登录，不用密码登录**
2. **牤牛阵法：解决 SSH 安全问题**
   - a. 防火墙封闭 SSH，指定源 IP 限制（局域网、信任公网）
   - b. 开启 SSH 只监听本地内网 IP（`ListenAddress 172.16.1.61`）
3. **尽量不给服务器外网 IP**
4. **最小化原则**（软件安装 - 授权）
5. **给系统的重要文件或命令做一个指纹**

   ```text
   /etc/passwd md5sum 11110000aaaabbbb   监控
   inotify /bin                          监控
   ```

6. **给他锁上 `chattr +i`**

公网机器还可以再加一道 Fail2Ban：监控 sshd 日志，连续认证失败超过阈值就自动封禁来源 IP，装上启用 sshd jail 即可，能挡掉绝大多数自动化爆破。

## 文件传输：scp / sftp / rsync over ssh

SSH 除了远程 shell，还提供加密通道上的文件传输能力：

| 工具 | 典型命令 | 说明 |
| --- | --- | --- |
| `scp` | `scp /etc/hosts root@172.16.1.31:/tmp/` | 推送文件到远程 |
| `scp` | `scp -r root@172.16.1.31:/tmp/logs /data/` | 递归拉取远程目录 |

| `rsync` | `rsync -avz -e ssh /data/ root@172.16.1.31:/backup/` | 增量同步，只传变化部分，大数据量首选 |

## 端口转发（隧道）

SSH 端口转发把加密通道"接到"任意 TCP 服务上，是运维穿越防火墙、访问内网服务的利器。用完即关是纪律：转发通道开着就是一条活跳板，排查安全事件时 `ps -ef | grep ssh` 里的残留 `-L/-R/-D` 进程要重点看。三种模式：

| 模式 | 参数 | 数据流向 | 典型用途 |
| --- | --- | --- | --- |
| 本地转发 | `-L` | 本地端口 → SSH 服务端 → 目标:端口 | 访问服务端内网里的数据库、Web 后台 |
| 远程转发 | `-R` | 服务端端口 → SSH 客户端 → 目标:端口 | 内网机器暴露到公网服务器（内网穿透） |
| 动态转发 | `-D` | 本地端口作为 SOCKS5 代理 | 科学上网式地代理访问整个远端网络 |

**本地转发示例**：把服务端 172.16.1.31 内网里的 MySQL（3306）映射到本地 13306：

```bash
ssh -L 13306:127.0.0.1:3306 root@172.16.1.31
# 之后本地连接 127.0.0.1:13306 就等于连服务端的 3306
```

**远程转发示例**：让公网跳板机 172.16.1.31 的 8080 转发到本地内网机器的 80：

```bash
ssh -R 8080:127.0.0.1:80 root@172.16.1.31
# 访问 172.16.1.31:8080 就等于访问本地内网的 80
```

**动态转发示例**：本地 1080 开一个 SOCKS5 代理，浏览器配上即可访问远端网络：

```bash
ssh -D 1080 root@172.16.1.31
```

### 跳板机与 ProxyJump

生产环境通常不允许管理机直连各业务机，必须经过跳板机。SSH 用 `-J`（ProxyJump）一条命令穿透：

```bash
# -J 指定跳板机，ssh 会先连 jump01 再由它转发到 web01，全程仍在加密通道内
# 经跳板机 jump01 连接最终目标 web01
ssh -J root@jump01 root@web01

# scp / rsync 同样适用
scp -J root@jump01 /etc/hosts root@web01:/tmp/

# 也可以写到客户端配置里，一劳永逸
```

```ini
# 客户端 config 的 Host 段：一段配置对应一个主机别名，别名可以自己取
# HostName 是真实 IP 或域名，别名只是本地缩写，scp/ssh 都能用
# ~/.ssh/config 里的缩进不要用 Tab，否则 ssh 会报配置解析错误
# ~/.ssh/config
Host jump01
    HostName 172.16.1.1
    User root

Host web01
    HostName 172.16.1.41
    User root
    # ProxyJump 指定经由哪台跳板机中转，这里引用的是上面定义的别名 jump01
    ProxyJump jump01
```

> **注意：** 跳板机是运维审计的关键节点，跳板机上的操作会被记录；转发与 ProxyJump 都只负责"连通"，权限收敛仍靠各自主机的账号体系。
{: .sec-pit}

### 辨析：跳板机与堡垒机

跳板机是裸 SSH 中转：连通就完事，审计靠登录记录与 history，聊胜于无。堡垒机在此基础上加了统一认证、授权工单、会话录像与命令级审计，出事能回放现场。小团队跳板机加集中日志够用；有合规要求（等保、审计）就必须上堡垒机，`ProxyJump` 与堡垒机的客户端代理通常还要配合使用。

### 客户端配置与连接复用
{: .sec-expl}

管理机每周连几百次服务器，每条命令都重新握手既慢又繁琐。把常用参数写进 `~/.ssh/config`，之后直接 `ssh web01` 就能连接：

```ini
# 常用连接参数固化到 ~/.ssh/config 之后，ssh web01 就能连上，不必每次敲长命令
# ~/.ssh/config 里的缩进不要用 Tab，否则 ssh 会报配置解析错误
# ~/.ssh/config
Host web01
    HostName 172.16.1.41      --- 真实地址，可写 IP 或域名
    User root                 --- 默认登录用户
    Port 22                   --- 端口，非 22 时必填
    IdentityFile ~/.ssh/id_ed25519   --- 指定私钥
    ServerAliveInterval 60    --- 每 60 秒发保活包，防 NAT 超时断开
```

**连接复用（ControlMaster）**：首次连接后，后续连接复用同一条 TCP 通道，省去反复的密钥交换与认证，批量场景提速明显：

```ini
# ControlMaster auto：首次连接时建立主通道，后续连接复用它
# ControlPath 里的 %r/%h/%p 是用户名、主机名、端口的占位符，路径要保证各用户互不冲突
# ControlPersist 10m 表示最后一条连接关闭后，主通道还保留 10 分钟
Host *
    ControlMaster auto
    ControlPath /tmp/ssh-%r@%h-%p
    ControlPersist 10m        --- 最后一条连接关闭后，通道再保留 10 分钟
```

> **注意：** Ansible 默认并发执行大量 SSH 连接，连接复用能显著降低认证开销；但复用通道时改了服务端配置不会在新连接生效，排错时可临时加 `-o ControlMaster=no` 绕过复用。
{: .sec-pit}

### 认证失败过多与调试技巧
{: .sec-ts}

- **Too many authentication failures**：客户端 `~/.ssh` 里私钥太多时，ssh 会挨个尝试，超过服务端 `MaxAuthTries` 就被断开。用 `-o IdentitiesOnly=yes` 限定只用指定私钥，或在 config 里写 `IdentityFile` 明确指定。
- **调试三板斧**：`ssh -v` / `-vv` / `-vvv` 逐步展示握手与认证细节，定位"卡在哪一步"；服务端日志在 `/var/log/secure`（Rocky / AlmaLinux 同样路径），`journalctl -u sshd` 看单元日志，能直接看到拒绝原因（权限、用户不存在、MaxAuthTries 超限等）。

把上面这些串成完整排错流程：先 `ssh -v host` 看卡在哪一步——TCP 不通查网络、防火墙与 sshd 监听（`ss -lntp | grep sshd`）；卡在 host key 查 known_hosts；卡在认证查两头权限与服务端日志；连上但很慢查 `UseDNS` 与 GSSAPI。按阶段定位，比盯着一条报错瞎猜快得多。

## SSH 安全加固清单
{: .sec-chk}

| 序号 | 措施 | 落地方式 |
| --- | --- | --- |
| 1 | 禁止 root 直连 | `PermitRootLogin no`，普通用户登录后 sudo 提权 |
| 2 | 关闭口令认证 | 密钥分发完成后 `PasswordAuthentication no` |
| 3 | 限制登录用户 | `AllowUsers` / `AllowGroups` 白名单 |
| 4 | 修改默认端口 | `Port` 改非标准端口，减少自动化扫描 |
| 5 | 只监听内网 | `ListenAddress` 指定内网地址 |
| 6 | 关闭慢解析 | `UseDNS no`、`GSSAPIAuthentication no` |
| 7 | 限制认证次数与超时 | `MaxAuthTries 3`、`LoginGraceTime 60` |
| 8 | 防火墙限源 IP | 只放通办公网 / 跳板机访问 22（或新端口） |
| 9 | 重要文件加锁 | `chattr +i /etc/passwd` 等关键配置 |
| 10 | 文件指纹监控 | `md5sum` + inotify 监控 `/etc/passwd`、`/bin` 变化 |

落地讲究先后顺序：先分发密钥并验证新密钥能登录 → 再关 `PasswordAuthentication` → 最后改 `PermitRootLogin` 并确认普通用户 sudo 通道可用。顺序反了（先关口令再分密钥）等于亲手把自己锁在门外，任何变更都留一条已建立的会话做退路。

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `WARNING: UNPROTECTED PRIVATE KEY FILE` 后私钥被拒绝 | 客户端私钥权限过宽（同组 / 其他用户可读） | `ls -l ~/.ssh/id_ed25519` | `chmod 600 ~/.ssh/id_ed25519` |
| 公钥分发成功却仍要输密码（`Permission denied (publickey)`） | 服务端 `~/.ssh` 或 `authorized_keys` 权限过宽，StrictModes 拒绝；或属主不对 | 服务端 `ls -ld ~/.ssh`、`ls -l authorized_keys`、`journalctl -u sshd` | `chmod 700 ~/.ssh`；`chmod 600 authorized_keys`；`chown 登录用户`；必要时重新 `ssh-copy-id` |
| 连接卡在密码提示之前十几秒 | `UseDNS yes` 做反向解析超时，或 GSSAPI 认证等待 | `time ssh host` | `UseDNS no`、`GSSAPIAuthentication no` 后 `systemctl reload sshd` |
| `Host key verification failed` | 服务端重装 / 换 IP，known_hosts 里旧指纹失效 | `ssh -v host` | `ssh-keygen -R host` 删除旧记录后重新连接并核对新指纹 |
| `ssh: connect to host ... Connection timed out` | 服务端 sshd 未启动、端口改过、防火墙拦截 | `telnet host 22`；`ss -lntp \| grep sshd` | 启动 sshd、按实际端口加 `-p`、防火墙放通 |
| 私钥每次登录都要求输 passphrase | 生成密钥时设了口令 | — | `ssh-agent` + `ssh-add` 加载，或生成不带口令的密钥（按安全要求权衡） |
| `Too many authentication failures` 后断开 | 客户端私钥太多，逐个尝试超过 `MaxAuthTries` | `ssh -v` 看尝试了哪几个密钥 | `ssh -o IdentitiesOnly=yes`，或在 `~/.ssh/config` 用 `IdentityFile` 明确指定 |
| 服务端日志看不到任何登录记录 | 防火墙直接丢弃了连接包，请求没到达 sshd | `telnet host 22`；`ss -lntp \| grep sshd` | 放通防火墙；确认 sshd 监听地址与端口 |

## 按条件生效的 Match 块

`sshd_config` 支持 `Match` 条件块，对不同来源、不同用户应用不同策略，例如只允许办公网段登录 root：

```ini
# Match 段按条件覆盖全局段的同名配置，条件不满足时沿用全局设置
# Match 之后的配置只在条件命中时生效，块内缩进不能乱写
Match Address 10.0.0.0/8
    PermitRootLogin yes

# Match all 兜底关闭：即使前面的条件命中了，这一段仍然禁止 root 远程登录
Match all
    PermitRootLogin no
```

## 小结
{: .sec-sum}

1. SSH 加密、默认允许 root、端口 22；TELNET 明文、默认禁止 root、端口 23，只适合网络设备场景。
2. 密钥对有两个作用：加密数据与身份认证；口令方式只用到加密，密钥方式才用到认证。
3. 免密登录三步：`ssh-keygen -t ed25519` 生成密钥对 → `ssh-copy-id -i 公钥 user@host` 分发 → `ssh host` 验证。
4. 批量分发要解决三个交互点：密码（`sshpass -p`）、hostkey 确认（`-o StrictHostKeyChecking=no`）、非标准端口（`-p 端口号`）。
5. `sshd_config` 的安全要点：`PermitRootLogin no`、`ListenAddress` 只监听内网、`UseDNS no` 与 `GSSAPIAuthentication no` 解决连接慢。
6. 防入侵组合拳：密钥登录 + 防火墙限源 IP + 只监听内网 + 不给外网 IP + 最小化授权 + 重要文件做指纹（`md5sum` / `inotify` 监控）+ `chattr +i` 加锁。
7. 密钥认证失败的隐藏杀手是权限：`~/.ssh` 要 700、`authorized_keys` 要 600、属主必须正确，否则 StrictModes 直接拒绝。
8. `-L` / `-R` / `-D` 三种转发分别解决"访问对端内网""把内网暴露出去""整体代理"三类问题，`-J` ProxyJump 是跳板机连接的标准姿势。

## 自测题
{: .sec-prac}

1. SSH 为什么用"非对称 + 对称"混合加密，而不是全程只用一种？
2. 公钥已经 `ssh-copy-id` 分发成功，登录时仍然要求输密码，最常见的两个原因是什么？
3. `ssh -L 13306:127.0.0.1:3306 root@172.16.1.31` 这条命令实现了什么？
4. `ssh -R 8080:127.0.0.1:80 root@172.16.1.31` 与上一条的数据流向有什么不同？
5. 修改了 `sshd_config` 的端口，应该用什么命令让配置生效，又如何避免把自己关在门外？

> **答案：** 1. 非对称加密能安全地协商密钥、验证身份，但速度慢；对称加密快但密钥分发困难。SSH 在握手阶段用非对称加密协商出对称会话密钥，之后全程用对称密钥传输，兼顾安全与性能。2. 一是服务端权限问题：`~/.ssh` 不是 700、`authorized_keys` 不是 600 或属主不对，`StrictModes yes` 直接拒绝密钥认证；二是客户端私钥权限过宽（如 644）被本地 ssh 拒绝使用。3. 把本地 13306 端口的连接经 SSH 隧道转发到服务端 172.16.1.31 上的 127.0.0.1:3306，本地访问 13306 即等于访问服务端的 MySQL。4. `-R` 方向相反：访问服务端 172.16.1.31 的 8080 会被转发回本地客户端的 127.0.0.1:80，用于把内网服务暴露给外部。5. `systemctl reload sshd`；重大调整前先 `sshd -t` 检查语法，并保留一个已建立的连接不断开，确认新连接可用后再退出旧连接。
