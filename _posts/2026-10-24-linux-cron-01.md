## 二、sudo 功能配置说明
{: .sec-expl}

### 2.1 如何配置 sudo 权限信息
{: .sec-expl}

```bash
visudo                 # 推荐使用，自带语法检查功能，等价于 vi /etc/sudoers
[root@linux-node1 ~]# visudo -c   # 配置好的文件语法检查
/etc/sudoers: parsed OK
```

扩展配置方法：

```bash
# 1) 授权单个命令或多个命令
/usr/sbin/useradd, /usr/bin/rm, ,

# 2) 授权单个命令目录或多个命令目录（需要排除部分特权命令）
/usr/sbin/*, !/usr/sbin/visudo , /usr/bin/*

# 3) 不需要输入用户密码，可以直接 sudo 方式执行命令
NOPASSWD: /usr/sbin/*, !/usr/sbin/visudo , /usr/bin/*
```

> **注意：** 授权命令目录时用 `!命令` 排除特权命令（尤其是 `visudo`），否则被授权用户可能反向提权到完整 root。sudoers 完整语法与安全细则见《用户权限与提权》。
{: .sec-pit}

sudo 的另一个价值是审计：`/var/log/secure` 里记录了谁在何时用 sudo 执行了什么。直接 `su -` 切 root 干活的人，日志里只剩一条切换记录，事后查无可查——这也是生产环境推 sudo 而非共密码的核心理由。批量授权时还可以用别名（`Cmnd_Alias`、`User_Alias`）把一堆命令打包成一个名字，几百台机器统一维护；追加授权放 `/etc/sudoers.d/` 下的独立文件，别全堆在主文件里。

## 三、设置系统特殊权限位

系统文件数据除了常见的 9 个权限位（`rwx -w- --x`），实际还有 3 个特殊权限位，共 12 个。

### 3.1 setuid：4

```bash
chmod u+s  文件信息
chmod 4755 文件信息
[root@linux-node1 ~]# ll /bin/cat
-rwsr-xr-x. 1 root root 54080 Apr 11  2018 /bin/cat
```

在属主权限位多出 `s` 信息。

**总结：** setuid 一旦设置，任何人执行这个文件时都会临时获得文件属主的身份——把属主的能力分给了所有人。一般赋予二进制的命令文件或一些可执行的脚本文件。

> **注意：** 脚本有两种执行方式：① 借助解释器执行，如 `sh /server/scripts/xxx.sh`、`python /server/scripts/xxx.py`；② 当成命令直接执行，需要给脚本加执行权限（`/server/scripts/xxx.sh`），或把目录加入 `PATH` 后直接敲脚本名。
{: .sec-pit}

### 3.2 setgid：2

```bash
[root@linux-node1 ~]# chmod g+s /bin/cat
[root@linux-node1 ~]# ll /bin/cat
-rwsr-sr-x. 1 root root 54080 Apr 11  2018 /bin/cat
[root@linux-node1 ~]# chmod 2755 /bin/cat
[root@linux-node1 ~]# ll /bin/cat
-rwxr-sr-x. 1 root root 54080 Apr 11  2018 /bin/cat
[root@linux-node1 ~]# chmod 6755 /bin/cat
[root@linux-node1 ~]# ll /bin/cat
-rwsr-sr-x. 1 root root 54080 Apr 11  2018 /bin/cat
```

**总结：** setgid 一旦设置，执行者会临时获得文件属组的身份——把属组的能力分给了所有人。

sgid 用于目录时更常用：目录下新建的文件自动继承目录属组，适合同组成员协作的共享目录。

### 3.3 sticky bit：粘滞位 1

作用：可以将不同用户信息放置到一个共享目录中，实现不同用户数据可以互相查看，但不可以互相随意修改。

```bash
chmod o+t  目录信息
chmod 1777 目录信息
```

系统中已经准备好了一个共享目录，权限位为 1777：

```bash
[root@linux-node1 ~]# ll -d /tmp/
drwxrwxrwt. 10 root root 4096 Apr 25 09:35 /tmp/
```

粘滞位为什么叫"粘滞"？权限粘在目录上：目录里的文件只有属主（和 root）能删，别人看得到、删不掉。`/tmp` 全员可写却没有粘滞位的话，任何人都能删掉别人的临时文件，那还得了。

### 3.4 四种提权方式的对比

| 方式 | 优势 | 劣势 |
| --- | --- | --- |
| 01 直接切换用户 `su -` | 简单快捷 | 风险太高（root 权限泛滥） |
| 02 修改数据文件权限（9 位权限位、属主信息） | 只针对某个数据文件进行修改，只针对某个用户进行授权 | 需要了解权限位功能 |
| 03 采用 sudo 提权方式 | 可以利用文件编辑指定用户有哪些指定权限（sa 运维部门、dev 开发人员） | 配置规划复杂 |
| 04 修改数据文件权限（3 位特殊权限位） | 设置权限简单方便 | 设置好的权限所有用户都拥有 |

## 四、如何防范系统中的重要文件不被修改

目的：使 root 用户也不能直接修改相应文件。给文件加上"锁头"：

```bash
# 加锁方法
chattr +i /etc/passwd
ll /etc/passwd
-rw-r--r--. 1 root root 4820 Apr 25 11:01 /etc/passwd

# 解锁方法
chattr -i /etc/passwd

# 检查方法
[root@linux-node1 ~]# lsattr /etc/passwd
---------------- /etc/passwd
```

> **注意：** 加锁后连 root 都无法修改/删除该文件，排查"文件明明有权限却改不动"时，记得用 `lsattr` 看一眼是否有 `i` 属性。
{: .sec-pit}

`chattr` 还有 `+a`（append only，只许追加不许改删），适合日志文件防篡改。锁是把双刃剑：加锁前先想清楚解锁流程，不然锁住的是未来的自己。

## 五、定时任务的概念
{: .sec-know}

作用：

1. 类似生活中的闹钟（有的闹钟应用需要做完算术题、摇一摇或拍照才能关闭）；
2. 可以自动完成操作命令：
   - 夜里备份数据（访问量不大）：`cp /data /backup`；
   - 自动清理磁盘；
   - 自动进行时间同步更新：`ntpdate xxx`。

> **注意：** `ntpdate` 已废弃，现代系统统一用 `chronyd` 校时（`chronyc sources` 查看同步状态），时间同步对定时任务的影响见本章第 8.4 节。
{: .sec-pit}

### 5.1 定时任务软件种类

| `atd` | 实现定时任务功能，只能一次设置定时功能 |
| `anacron` | 实现定时任务功能，应用在家用电脑（非 7×24 服务器） |

### 5.2 系统级定时任务：4 个特殊目录

| 系统定时任务周期 | 控制定时任务目录 | 说明 |
| --- | --- | --- |
| 每小时 | `/etc/cron.hourly` | — |
| 每一天 | `/etc/cron.daily` | 00:00-23:59 |
| 每一周 | `/etc/cron.weekly` | 7 天 |
| 每个月 | `/etc/cron.monthly` | 30 / 28 / 31 天 |

日志文件需要定期进行切割处理，就是典型用法：

```bash
周一         secure   100M
周二(00:00)  mv secure secure-`date +%F`  100M 切割后的文件
             touch secure
```

这四个目录里的脚本由 run-parts 执行，触发链路分两路：

| 目录 | 触发方式 | 说明 |
| --- | --- | --- |
| `/etc/cron.hourly` | `/etc/cron.d/0hourly`，每小时第 1 分钟 `run-parts` 执行 | 即使机器不是 24 小时开机也能按小时跑 |
| `/etc/cron.daily`、`/etc/cron.weekly`、`/etc/cron.monthly` | `anacron` 按 `/etc/anacrontab` 的周期补跑 | 关机错过的任务开机后会补上，这正是 anacron 存在的意义 |

日志切割的经典实现 logrotate 就住在 `/etc/cron.daily` 里，每天被 run-parts 拉起来一次，按 `/etc/logrotate.d/` 下的规则切割、压缩、删除旧日志——不用自己手写切割脚本。另外 run-parts 只执行带可执行权限的文件，脚本放进去没反应，先查权限是不是漏了。

另外还有两个系统级入口：`/etc/crontab`（系统主定时任务文件，格式比用户级多一列"执行用户"）与 `/etc/cron.d/`（存放独立的任务片段文件，格式与 `/etc/crontab` 相同，适合软件包自动投放，如 `0hourly`、`sysstat`）。三者与用户级 crontab 的分工：

| 文件 / 目录 | 格式 | 使用者 |
| --- | --- | --- |
| `/etc/crontab` | 五段 + 用户 + 命令（共 7 段） | 系统管理员 |
| `/etc/cron.d/*` | 同 `/etc/crontab`，文件不带点、仅 root 可写 | 软件包、管理员 |
| `/var/spool/cron/用户名` | 五段 + 命令（共 6 段） | 各用户自己（`crontab -e` 编辑） |
| `/etc/cron.hourly|daily|weekly|monthly` | 可执行脚本，无时间字段 | 软件包、管理员 |

### 5.3 用户级定时任务

```bash
a 用户定时任务查看   crontab -l（list）    # 列表查看定时任务信息（cron table）
b 用户定时任务编辑   crontab -e（edit）    # 编辑配置定时任务信息
```

配置文件的保存位置：

```bash
crontab -e  编写定时任务     vi /var/spool/cron/         定时任务配置文件保存目录
                               /var/spool/cron/root      root 用户设置的定时任务配置文件
                               /var/spool/cron/ops       ops 用户设置的定时任务配置文件
visudo      对普通用户提权   vi /etc/sudoers
```

crontab 命令的完整参数：

| 参数 | 作用 |
| --- | --- |
| `-e` | 编辑定时任务（默认用 `EDITOR` 指定的编辑器） |
| `-l` | 列出当前用户的定时任务 |
| `-r` | 删除当前用户的全部定时任务（危险，删前先 `-l` 确认） |
| `-u 用户` | root 代其他用户查看 / 编辑 / 删除任务 |
| `-i` | 删除前交互确认（与 `-r` 搭配使用更稳） |

用户能否使用 crontab 由黑白名单控制：存在 `/etc/cron.allow` 时只有名单内用户可用；否则看 `/etc/cron.deny`，名单内用户被禁止。

`/var/spool/cron/root` 本质就是个文本文件，直接 vi 改它表面上也能生效，但这里有个坑：直接编辑不经过语法检查、日志里不会留下 `RELOAD` 记录，手滑写错格式任务就静默失效，排错时还以为 crond 没干活。规范做法永远是用 `crontab -e`，让它负责语法检查与热加载。

生产分工经验：机器级任务（时间同步、日志清理）放 `/etc/cron.d/` 下单独文件，用 Ansible 批量下发或随软件包投放，版本可控；用户相关的任务放各自的 crontab。所有任务全堆在 root 的 crontab 里，迁移机器时最容易漏。

### 6.1 原理解析：crond 是怎么工作的
{: .sec-know}

crond 是常驻内存的守护进程，工作循环如下：

1. 启动时读取 `/etc/sysconfig/crond` 配置与 `/etc/cron.deny` / `/etc/cron.allow`；
2. 每分钟被唤醒一次（sleep 到下一分钟边界），收集所有到期的 crontab 文件：`/etc/crontab`、`/etc/cron.d/*` 与 `/var/spool/cron/*`；
3. 对每个任务按五段时间字段与当前时间匹配，匹配成功则以文件属主（或 `/etc/crontab` 中指定的用户）身份 fork 子进程执行命令；
4. 子进程的标准输出与标准错误默认通过邮件发给对应用户（依赖本机 MTA，如 postfix）；
5. 开启 inotify 支持时，crontab 文件被修改会立即重新加载，不必等下一分钟；
6. 日志写入 `/var/log/cron`，包括谁编辑了任务（`BEGIN EDIT` / `REPLACE` / `RELOAD`）与每次执行记录（`CMD` / `MAIL`）。

理解这个循环就理解了 cron 的两个经典现象：任务执行环境极简（PATH 只有 `/usr/bin:/bin`，没有登录环境），以及命令一有输出就发邮件。

## 延伸理解：crond 为什么是分钟级
{: .sec-know}

crond 的设计目标不是精度，而是省资源。它每分钟睡醒一次，扫一遍所有 crontab 匹配时间字段，扫完接着睡——说白了是个闹钟，不是调度引擎。一个常驻进程就这点开销，跑在几百台机器上也无感。代价是粒度只有分钟：要秒级调度，得靠循环加 sleep 变通，或者换 systemd timer。timer 的 `OnCalendar` 支持秒级精度，任务本身是 systemd 单元，自带超时控制、依赖关系和日志，`systemctl list-timers` 一眼看清下次执行时间；`Persistent=true` 时错过的任务开机补跑，相当于内置了 anacron 的能力。新系统上不依赖用户 crontab 的任务，优先考虑 timer。

## 七、定时任务的编写语法

```bash
# Example of job definition:
# .---------------- minute (0 - 59)
# |  .------------- hour (0 - 23)
# |  |  .---------- day of month (1 - 31)
# |  |  |  .------- month (1 - 12) OR jan,feb,mar,apr ...
# |  |  |  |  .---- day of week (0 - 6) (Sunday=0 or 7) OR sun,mon,tue,wed,thu,fri,sat
# |  |  |  |  |
# *  *  *  *  * user-name  command to be executed
```

```bash
*   *   *    *   * 具体做什么事情
分  时  日   月  周
```

| 字段 | 含义 | 取值范围 |
| --- | --- | --- |
| 第 1 列 | 分钟 minute | 0 - 59 |
| 第 2 列 | 小时 hour | 0 - 23 |
| 第 3 列 | 日期 day of month | 1 - 31 |
| 第 4 列 | 月份 month | 1 - 12 或 jan,feb,mar,apr ... |
| 第 5 列 | 星期 day of week | 0 - 6（Sunday=0 或 7）或 sun,mon,tue,wed,thu,fri,sat |

注意区分两种文件：用户级 crontab（`crontab -e` 编辑，无用户列，以编辑者身份执行）与系统级 `/etc/crontab`、`/etc/cron.d/*`（多一列 `user-name`，可指定以哪个用户执行）。

特殊符号表：

| 符号 | 含义 | 示例 |
| --- | --- | --- |
| `*` | 该字段的每个取值都匹配（每） | `* * * * *` 每分钟 |
| `,` | 列举多个不连续取值 | `0 14,20 * * *` 每天 14 点与 20 点 |
| `-` | 指定连续范围 | `0 1-3 * * *` 每天 1 到 3 点整 |
| `/` | 步长，从起点开始每隔 n 取一个 | `*/10 * * * *` 每 10 分钟；`20/10 * * * *` 从 20 分起每 10 分钟 |
| 名字 | 月份与星期支持英文缩写 | `jan`、`mon` |
| `%` | 在命令中表示换行，需转义为 `\%` | `/bin/date "+\%F"` |

cron 不支持 `?` 与 `L`、`W`、`#` 这类 Quartz 表达式符号，遇到"每月最后一天"之类需求，用 `date` 判断或写 `31` 号加条件判断实现。

cron 还支持 `@hourly`、`@daily`、`@weekly`、`@reboot` 这类简写，分别等价于 `0 * * * *`、`0 0 * * *` 等，写在 crontab 里可读性更好。用不用看团队规范，但见到别人这么写要认识。

### 7.1 时间信息的写法

**01. 用数值表示时间信息：**

```bash
00 02 *  *  *   备份文件
```

**02. 利用特殊符号表示时间信息：**

```bash
*      *      *     *     *   备份文件
每分钟  每小时  每天   每月   每周
```

> **注意：** 定时任务最短执行的周期为每分钟。
{: .sec-pit}

```bash
*/5     */5    */5
每隔5分钟  每隔5小时

01-05   02    *    *    *
01 到 05 分   02 时
指定时间的范围

00      14,20  *   *    *
指定不连续的时间信息
```

### 7.2 时间写法测验
{: .sec-prac}

| 题目 | 写法 | 含义 |
| --- | --- | --- |
| 测验 01：每天下午 02:30 起来学习 | `30 14 * * *` | 每天 14:30 |
| 测验 02：每隔 3 天夜里 2 点执行数据备份 | `00 02 */3 * *` | 每 3 天的 02:00 |
| 测验 03 | `*/10 01,03 * * *` | 每天凌晨 1 点和凌晨 3 点，每隔 10 分钟执行一次 |
| 测验 04 | `*/10 01-03 * * *` | 每天 01 点到 03 点，每隔 10 分钟执行一次 |
| 测验 05 | `* 01,03 * * *` | 每天 01 点和 03 点的每一分钟 |
| 测验 06 | `* 01-03 * * *` | 每天 01 点到 03 点的每一分钟 |
| 测验 07 | `00 02 28 */2 6` | 02:00，28 号，每隔两个月，且为星期六 |

**编写时间信息的结论：**

1. 在写时间信息的时候，如果想表示每隔多久执行什么任务，`/` 上面尽量用 `*` 号表示，不要写具体数值；
2. 时间信息由左到右依次书写，尽量不要跳步；
3. 当编写定时任务时，日期信息不要和星期信息同时出现。

为什么日期和星期不能同时写？cron 的实现里这两列同时出现时是"或"关系：日期匹配或星期匹配都会执行。本意"每月 15 号且是周一"的任务，实际会变成"每月 15 号 + 所有周一"，执行次数凭空多出来。这个行为坑过很多人，规范就是二选一。

补充说明：

```bash
20/10  01,03 * * *
01:20 01:30 01:40       01:59
03:00        03:59
```

> **注意：** `20/10` 表示从第 20 分钟开始每隔 10 分钟执行一次，即 20、30、40、50 分。笔记原文的补充说明（01:59 / 03:00、03:59）表述不够准确，实际执行时间请以 `起始值/步长` 的步进规则为准。
{: .sec-pit}

## 八、实际编写与排查方法
{: .sec-ts}

### 8.1 实例：每天凌晨两点备份 /data 目录到 /backup
{: .sec-ex}

```bash
# 第一个历程：写上时间信息
00 02 * * *

# 第二个历程：写上完成任务的具体命令
cp -a /data /backup

# 第三个历程：编写定时任务
crontab -e
00 02 * * *  cp -a /data /backup
```

顺带一提，`cp -a` 是归档复制，保留权限与时间戳——备份场景几乎总是该用 `-a` 而不是 `-r`，后者会丢属性，恢复出来的文件可能服务起不来。

crontab 文件还支持在任务前定义环境变量，用来覆盖 crond 的极简默认环境：

```bash
SHELL=/bin/bash
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=root

00 02 * * *  cp -a /data /backup
```

| 变量 | 作用 |
| --- | --- |
| `SHELL` | 执行命令用的 shell，默认 `/bin/sh` |
| `PATH` | 任务中的命令搜索路径，默认 `/usr/bin:/bin` |
| `MAILTO` | 输出邮件发给谁，设为空字符串（`MAILTO=""`）则不发送 |
| `HOME` | 任务运行时的家目录，影响 `~` 的展开 |

还有个生产场景要防：任务跑得比周期慢。备份脚本本来每 10 分钟跑一次，某天数据量暴涨跑了一刻钟，下一个周期又启动一个，两个实例同时写同一份备份文件，产物直接损坏。给脚本套一层 flock 就能避免重叠，抢不到锁的实例直接退出：

```bash
* * * * *  flock -n /tmp/backup.lock /bin/sh /server/scripts/backup.sh &>/dev/null
```

锁文件建议放 `/var/lock` 而不是 `/tmp`，后者可能被系统清理。

cron 环境和登录环境差在哪？登录 shell 会读 `/etc/profile`、`~/.bashrc` 等一串文件，cron 一个都不读——你在交互 shell 里 export 的变量、定义的 alias 和函数，cron 里统统不存在。别在任务里用 alias，别指望 `~/.bashrc` 帮你补 PATH。

### 8.2 at：一次性定时任务

只需要在将某个时间点执行一次的任务（重启、临时清理、发通知），用 at 比 cron 更合适。at 由 atd 服务提供：

```bash
systemctl enable --now atd        # 启动 atd 服务

at now + 10 minutes               # 10 分钟后执行，回车后输入命令，Ctrl+D 结束
at 02:00 2027-01-01               # 指定时间点执行一次
atq                               # 查看待执行的一次性任务队列
atrm 1                            # 删除队列中编号为 1 的任务
batch                             # 系统负载低于 0.8 时执行（负载空闲时段）
```

与 cron 的分工：cron 管周期性任务，at 管一次性任务；两者的黑白名单分别是 `/etc/cron.deny` 与 `/etc/at.deny`。at 的交互实际敲一遍就明白：输入命令后按 Ctrl+D 提交，`atq` 队列里立刻能看到。at 任务同样会发邮件，想看任务内容用 `at -c 编号`。

### 8.3 anacron：为不能 24 小时开机的机器设计

笔记本电脑、开发测试机经常关机，crond 到点没开机任务就直接错过。anacron 的做法是记录每个任务"上次执行时间"，开机后发现超过了 `/etc/anacrontab` 里配置的周期就立即补跑。

```bash
cat /etc/anacrontab
SHELL=/bin/sh
PATH=/sbin:/bin:/usr/sbin:/usr/bin
START_HOURS_RANGE=3-22
RANDOM_DELAY=45

1	5	cron.daily		run-parts /etc/cron.daily
7	25	cron.weekly		run-parts /etc/cron.weekly
30	45	cron.monthly	run-parts /etc/cron.monthly
```

字段含义：周期（天）、开机后延迟多少分钟再执行、任务标识（写进 `/var/spool/anacron/` 的时间戳文件）、要执行的命令。`RANDOM_DELAY` 给执行时间加随机偏移，避免大量机器同一时刻集中执行把服务打满；`START_HOURS_RANGE` 限定补跑只发生在哪个时间段。时间戳文件里就一个日期，cat 一下就知道该任务上次实际执行的时间。

### 8.4 时间同步对 cron 的影响

cron 完全依赖系统时间。虚拟机恢复快照、主板电池没电、双系统时间互相覆盖，都会让系统时间发生跳变，进而导致：

1. 时间**往回跳**：crond 每分钟循环重新匹配，可能出现同一分钟被多次判定为到期，任务重复执行；
2. 时间**往前跳**：本该执行的任务窗口被跳过，任务直接漏跑（例如备份任务漏一天，最致命）；
3. 跨时区修改：容器与虚拟机改时区后，任务的"每天凌晨 2 点"实际执行点跟着变。

防护措施：

```bash
timedatectl                      # 查看当前时间、时区、是否开启 NTP 同步
timedatectl set-timezone Asia/Shanghai   # 修正时区
systemctl enable --now chronyd   # 启用 chrony 持续校时
chronyc sources                  # 查看时间同步源状态
```

> **注意：** `ntpdate` 是一次性校时命令且已废弃，生产环境应运行 chronyd 持续同步；硬件服务器还要确认时区与 NTP 源，避免 cron 任务在错误的时间点执行。
{: .sec-pit}

chrony 和 ntpdate 的思路差别值得展开一句：ntpdate 是"调表"，一次把时间拨过去，时间差大就造成跳变；chronyd 是"匀速追表"，慢慢把误差磨平，不跳变。数据库、交易类系统对时间回拨极其敏感，这正是 chrony 全面替代 ntpdate 的核心原因。`chronyc tracking` 能看到当前偏差多少，机房验收时值得看一眼。双机环境还要保证两台机器时间源一致，否则主备切换后任务执行点会漂移。

### 8.5 定时任务排查方法
{: .sec-ts}

**01. 检查是否有定时任务配置文件：**

排查顺序也有讲究：先确认配置落盘，再确认服务活着，最后看日志——三步分别定位配置问题、服务问题、执行问题，别一上来就翻日志大海捞针。

```bash
cat /var/spool/cron/root
00 02 * * *  cp -a /data /backup
```

**02. 检查定时任务日志文件：**

```bash
ll /var/log/cron
-rw-------. 1 root root 14050 Apr 25 15:49 /var/log/cron
```

日志信息说明：

```bash
Apr 25 15:53:22 linux-node1 crontab[3893]: (root) BEGIN EDIT (root)
Apr 25 15:54:06 linux-node1 crontab[3934]: (ops) BEGIN EDIT (ops)
Apr 25 15:54:48 linux-node1 crontab[3893]: (root) REPLACE (root)
Apr 25 15:54:48 linux-node1 crontab[3893]: (root) END EDIT (root)
Apr 25 15:55:01 linux-node1 crond[905]: (root) RELOAD (/var/spool/cron/root)
Apr 25 15:55:01 linux-node1 CROND[3939]: (root) CMD (cp -a /data /backup)
Apr 25 15:55:01 linux-node1 CROND[3937]: (root) MAIL (mailed 55 bytes of output but got status 0x004b#012)
执行时间      主机名   编辑定时任务    以什么用户编辑或执行定时任务/干了什么事情
                        执行定时任务
```

排错时日志的关键字：

| 日志内容 | 含义 |
| --- | --- |
| `BEGIN EDIT` / `REPLACE` / `END EDIT` | 有人编辑并保存了 crontab |
| `RELOAD (/var/spool/cron/root)` | crond 重新加载了某用户的任务文件 |
| `CMD (命令)` | 到点执行了某条命令 |
| `MAIL (mailed ... bytes)` | 命令有输出，已尝试发邮件；伴随 MTA 报错时检查 postfix 状态 |

一个万能自查口诀：怀疑任务没跑，先看 `/var/log/cron` 有没有对应的 CMD 行。有 CMD，说明执行了，问题在命令本身；没 CMD，说明没到点或配置没加载，问题在配置。一刀就把排查范围砍半。

安全上也要多留个心眼：crontab 是入侵持久化的重灾区，挖矿脚本最爱往 `/etc/cron.d/`、`/var/spool/cron/` 里藏。应急响应时这些目录是必查项，平时定期看一眼最近改动（`ls -lt`）就能发现异常。

## 九、定时任务编写注意事项（规范）
{: .sec-warn}

1. **编写定时任务要有注释说明；**
2. **编写定时任务路径信息尽量使用绝对路径；**
3. **编写定时任务命令需要采用绝对路径执行**，如 `/usr/sbin/useradd`。

```bash
命令执行成功条件：
useradd  ---> $PATH ---> /sbin/useradd ---> 命令执行成功
定时任务执行时，识别的 PATH 信息只有：/usr/bin:/bin
useradd 命令 ---> /usr/sbin/useradd
```

这就是 cron 最经典的坑：手工在 shell 里能跑的命令，放进定时任务就不执行，原因是交互 shell 的 PATH 里有 `/usr/sbin`，而 cron 的 PATH 只有 `/usr/bin:/bin`。解决方式二选一：命令全部写绝对路径，或在 crontab 开头显式定义 `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`。

4. **编写定时任务时，可以将输出到屏幕上的信息保存到黑洞中，避免占用磁盘空间：**

```bash
* * * * *  sh test.sh &>/dev/null
```

多个任务挤在同一分钟（整点最明显）还会造成瞬时负载尖峰，给周期加随机偏移是常见的削峰手段——写 `7,37 * * * *` 就比 `0 * * * *` 温和，anacrontab 里的 `RANDOM_DELAY` 是同一个思路。

> **注意：** 定时任务中执行命令，如果产生输出到屏幕的信息，都会以邮件方式告知用户：
> - `/var/spool/mail/root` 不断变大占用磁盘空间（占用 block 空间），解决方法：将邮件服务关闭 `systemctl stop postfix`；
> - `/var/spool/postfix/maildrop/` 不断产生小文件占用磁盘空间（占用 inode 空间），解决方法：删除小文件 `rm -f /var/spool/postfix/maildrop/*`，再 `systemctl start postfix`。
{: .sec-pit}

更彻底的做法是在 crontab 顶部设 `MAILTO=""` 直接关闭邮件发送，既不占 block 也不占 inode。

为什么小文件这么烦人？磁盘有两本账：block 存数据，inode 存元数据，一个文件再小也至少占一个 inode。一封 55 字节的邮件照样吃掉一整个 inode，几百万个小文件能把 inode 表耗尽——到时候磁盘明明还有空间，写任何文件都报 No space left on device。这就是 maildrop 堆积比大文件更隐蔽的原因，`df -h` 看不出来，要用 `df -i` 看 inode 使用率。

5. **编写定时任务，尽量不要产生屏幕输出信息：**

```bash
cp -a /data /backup
tar zcvf /backup/data.tar.gz  /data     # 有信息输出
cd /
tar zcf /backup/data.tar.gz  ./data     # 没有信息输出
```

6. **当需要多个命令完成一个定时任务需求时，可以利用脚本编写定时任务：**

```bash
vim backup.sh
cp -a /data /backup
tar zcvf /backup/data.tar.gz  /data
```

```bash
crontab -e
# xxxxx
* * * * *  /bin/sh /server/scripts/backup.sh &>/dev/null
```

7. **定时任务中无法识别任务中的一些特殊符号**（如 `%`），两种解决方式：

```bash
# 解决方式一：利用转义符号
* * * * *  /bin/date "+\%F \%T" >/tmp/time.txt

# 解决方式二：利用脚本编写任务
vim /server/scripts/date.sh
/bin/date "+%F %T"

* * * * *  /bin/sh /server/scripts/date.sh &>/dev/null
```

`%` 被特殊对待的原因是：cron 会把命令中第一个未转义的 `%` 之后的内容当作标准输入送给命令。

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 手工执行正常，定时任务不执行 | cron 的 PATH 只有 `/usr/bin:/bin`，命令未写绝对路径 | `cat /var/spool/cron/用户名`；`grep CMD /var/log/cron` | 命令与路径改绝对路径，或在 crontab 定义 PATH |
| 任务到点没执行，日志无记录 | crond 服务未启动，或时间字段写错 | `systemctl status crond` | `systemctl enable --now crond`；核对五段写法 |
| 磁盘 block 持续增长 | 任务输出触发邮件，`/var/spool/mail` 膨胀 | `du -sh /var/spool/mail/*` | 任务加 `&>/dev/null` 或设 `MAILTO=""` |
| 磁盘 inode 持续增长 | postfix 关闭后 maildrop 堆积小文件 | `ls /var/spool/postfix/maildrop/ | wc -l` | 清理小文件，改 `MAILTO=""` |
| 命令里的 `date +%F` 输出异常 | `%` 未转义，被 cron 当作分隔符 | 对比手工执行与任务输出 | 用 `\%` 转义或写进脚本 |
| 日期与星期同时设置，执行时机不符合预期 | 两个条件是"或"的关系，任一匹配即执行 | 回顾任务的时间字段 | 二选一书写，不要同时出现 |
| 关机后错过的周期任务不再执行 | 机器非 7×24，crond 到点没开机 | `cat /var/spool/anacron/` | 安装 `cronie-anacron`，把任务放进 daily/weekly/monthly 目录 |
| `crontab -r` 误删全部任务 | 删除前未确认 | `crontab -l` | 养成先 `-l` 再删的习惯，用 `-r -i` 交互确认 |

## 自测题
{: .sec-prac}

1. 用户级 crontab 与 `/etc/crontab` 的格式差异是什么？各自以谁的身份执行？

> **答案：** 用户级 crontab（`crontab -e` 编辑，存于 `/var/spool/cron/用户名`）是"五段时间 + 命令"共 6 段，以编辑者本人身份执行；`/etc/crontab`（及 `/etc/cron.d/*`）是"五段时间 + 用户 + 命令"共 7 段，可以指定以哪个用户身份执行。

2. 为什么手工执行成功的命令放进定时任务就失败？怎么解决？

> **答案：** cron 执行环境是极简非登录环境，PATH 只有 `/usr/bin:/bin`，没有交互 shell 里的 `/usr/sbin` 等路径。解决：命令与文件路径全部写绝对路径，或在 crontab 开头显式定义 `PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`。

3. 定时任务输出邮件会导致哪两种磁盘问题？分别占用什么资源？

> **答案：** 开 postfix 时输出进入 `/var/spool/mail/root`，文件不断变大，占用 block 空间；关 postfix 时输出堆积在 `/var/spool/postfix/maildrop/`，产生大量小文件，占用 inode 空间。统一解法是任务末尾加 `&>/dev/null` 或设置 `MAILTO=""`。

4. anacron 与 crond 的分工是什么？anacron 配置文件的时间字段是什么含义？

> **答案：** crond 负责到点执行周期性任务，但机器关机错过就不再执行；anacron 记录每个任务的上次执行时间，开机后发现超过配置周期就补跑，适合非 7×24 开机的机器。`/etc/anacrontab` 每行四列：周期（天）、开机后延迟分钟数、任务标识、执行命令。

5. 系统时间发生跳变会对 cron 造成什么影响？如何防护？

> **答案：** 时间往回跳可能让任务重复执行，往前跳会让任务窗口被跳过造成漏跑（备份漏跑最危险），时区变化会改变任务实际执行点。防护：启用 chronyd 持续校时，用 `timedatectl` 确认时区正确，服务器保持 NTP 同步。

## 小结
{: .sec-sum}

1. 定时任务由 `cronie` 提供，`crontab -e` 编辑、`crontab -l` 查看，配置文件保存在 `/var/spool/cron/用户名`，日志文件是 `/var/log/cron`。
2. 五段时间字段依次为**分、时、日、月、周**；`*` 表示每、`*/n` 表示每隔 n、`n-m` 表示范围、`n,m` 表示不连续取值。
3. 写时间时有三个原则：间隔写法 `/` 前尽量用 `*`、从左到右不要跳步、日期与星期不要同时出现。
4. 定时任务执行时的 PATH 只有 `/usr/bin:/bin`，所以命令和文件路径一律写绝对路径，否则会出现"手工能跑、定时不跑"。
5. 定时任务的输出会以邮件形式发给用户：开 postfix 撑爆 `/var/spool/mail/root`（block），关 postfix 撑爆 `/var/spool/postfix/maildrop/`（inode），统一在任务末尾加 `&>/dev/null` 或设 `MAILTO=""` 最省事。
6. 排错两步走：`cat /var/spool/cron/用户名` 确认配置是否落盘，`cat /var/log/cron` 确认是否被 crond 执行；多命令需求一律写脚本再定时调度。
7. 系统级任务有四类入口：`/etc/crontab`、`/etc/cron.d/`、`/etc/cron.hourly|daily|weekly|monthly`，后两类由 run-parts 与 anacron 触发，适合关机补跑。
8. 一次性任务用 at（`at` / `atq` / `atrm`，atd 服务），与 cron 分工明确；anacron 解决非 7×24 机器的周期任务补跑。
9. `%` 在 crontab 命令中是特殊符号，必须转义为 `\%` 或写进脚本执行。
10. 时间同步（chronyd）直接影响 cron 的执行准确性，服务器必须保证时区正确并持续校时。
