预处理器是你在写 C++，但编译器先看到的不是 C++。它会在真正的编译开始前，把源代码当作纯文本做一轮手术：拼接文件、替换宏、裁剪条件分支。头文件机制、`#define`、条件编译都活在这一层，而 C++ 的编译时间爆炸、宏的经典灾难，根子也在这一层。这一篇覆盖 20.1 到 20.4：翻译阶段与预处理的职责边界、`#include` 的搜索规则与文本包含的代价、include guard 与 `#pragma once` 的取舍、前向声明的能与不能、对象宏与函数宏的展开规则、`#` 与 `##`、条件编译全家桶、预定义宏与特性测试宏、宏的经典陷阱清单（`SQR(a+1)`、双重求值、参数带逗号、Windows 的 `min/max`、`#define new`）、`#pragma pack` 的风险，最后是 C++20 模块：它凭什么把编译速度提上来，怎么和头文件共存迁移，以及 `std::source_location` 这类宏的现代接班人。读完你应该能判断"这个问题该在预处理器层解决还是交给语言"，也能把一个老项目的头文件网络理出个头绪。

## 20.1 什么是预处理
{: .sec-expl}

### 20.1.1 翻译阶段：编译器在编译之前先做了一遍文本手术
{: .sec-know}

标准把"从源码到程序"拆成九个翻译阶段（translation phases），平时我们笼统说的"编译"其实是这几个阶段的串联：

| 阶段 | 干什么 | 谁负责 |
| --- | --- | --- |
| 1~3 | 字符映射、行拼接（`\` 续行）、切成预处理记号 | 预处理器 |
| 4 | 执行预处理指令：`#include`、`#define`、条件编译 | 预处理器 |
| 5~7 | 字符集转换、拼接字符串字面量、真正编译（语法分析、语义分析、生成代码） | 编译器本体 |
| 8~9 | 汇编、链接 | 汇编器、链接器 |

关键认识：**阶段 4 结束时，宏已经全部消失**。编译器本体根本不知道宏存在，它看到的是一份所有宏都被展开、所有头文件都被塞进来的完整文本。这条规则能解释后面一大堆现象——为什么调试器里看不到宏、为什么 `sizeof` 不能用在 `#if` 里、为什么宏不受命名空间和作用域约束。

预处理器的"视野"是单个翻译单元。每个 `.cpp` 都独立走一遍完整的预处理加编译，互相之间没有任何信息共享——理解了这一点，头文件为什么要写保护、模板为什么只能放头文件、重复解析为什么发生，全都顺理成章。

想亲眼看看预处理器的产物，用 `-E`：

```cpp
// pp_demo.cpp —— 需要 -std=c++20
#define GREETING "hello"
#include <iostream>

int main() {
    std::cout << GREETING << '\n';
}
```

```bash
g++ -std=c++20 -E pp_demo.cpp | wc -l      # 预处理后的总行数
g++ -std=c++20 -E pp_demo.cpp | tail -n 4  # 看末尾，宏已经展开
```

```text
约 900 行（GCC 13、libstdc++ 13 下实测，你的数字多半不同）

int main() {
    std::cout << "hello" << '\n';
}
```

一个 6 行的文件，预处理后接近千行，多出来的全是 `<iostream>`。GREETING 已经不见了，取而代之的是字面量 `"hello"`——这就是阶段 4 做完的事。

> **注意：** `-E` 只做预处理不编译，是排查宏问题最快的手法。怀疑某个宏展开得不对劲，直接 `-E` 出来看文本，比盯编译错误猜快得多。
{: .sec-note}

### 20.1.2 #include 的两种形式与搜索路径
{: .sec-know}

`#include "xxx"` 和 `#include <xxx>` 的区别只有一个：**搜索起点不同**。找到文件之后的行为完全一样——把文件内容原样粘贴进来。

以 GCC 为例，搜索顺序：

| 写法 | 搜索顺序 |
| --- | --- |
| `#include "my.h"` | 当前文件所在目录，然后 `-iquote` 目录，然后 `-I` 目录，最后系统目录 |
| `#include <my.h>` | `-I` 目录，`-isystem` 目录，系统目录 |

`-I` 按命令行出现的顺序从左到右依次尝试，命中即停。所以如果你有两个目录里都放着 `config.h`，`-Iold -Inew` 用的是 old 里的那份——这类"头文件被谁命中"的问题用 `-H` 一看便知（它会把每个头文件的查找结果打出来）：

```bash
g++ -std=c++20 -H -Iinc src/main.cpp -o app    # 打印头文件命中路径
echo | g++ -x c++ - -v -E 2>&1 | grep -A 10 "#include"   # 打印系统搜索路径
```

工程上只需要记住三条：自己项目的头文件用引号加 `-I`；第三方和标准库用尖括号；引号写法对尖括号能找到的东西是超集（引号找不到时会退回系统目录再找一遍），所以混用通常不报错，但会让读代码的人猜不出这个头是项目内的还是外部的。

> **辨析：引号与尖括号。** 区别不在"性能"也不在"能否编译"，而在**意图表达**。尖括号宣告"这是环境提供的东西，别来我项目里找"；引号宣告"这是相对我而言的本地文件"。按意图选择，构建系统出问题时排查成本低一个量级。
{: .sec-iv}

### 20.1.3 文本包含的代价：编译时间是怎么爆炸的
{: .sec-pit}

`#include` 是无脑复制粘贴。每个翻译单元都要把用到的所有头文件完整展开、重新解析一遍——哪怕展开结果和上一个翻译单元一模一样。一个 200 个 `.cpp` 的项目，如果每个都包含 `<iostream>` 和 `<vector>`，这两个巨型头就被完整解析了两百次。

量化一下这种浪费的构成：

| 开销来源 | 具体形式 |
| --- | --- |
| 重复展开 | 同一头文件在每个 TU 里各展开一次，文件总量随 TU 数线性放大 |
| 重复解析 | 模板定义（如 `std::vector` 全家）每次都要重新做语义分析和实例化 |
| 传递包含 | `a.h` 包了 `b.h`，谁包含 `a.h` 谁就背上 `b.h`，依赖指数级传染 |
| 重复实例化 | `std::vector<int>` 在几十个 TU 里各实例化一遍，链接前各自占内存 |

写过大型项目的人都懂：改一行 `common/types.h`，全量重编二十分钟，就是这三条叠加的结果。缓解手段按见效程度排序：前向声明砍掉传递包含（见 20.2.2）、预编译头（PCH）缓存稳定的大头文件、unity build 换一种方式合并 TU，以及 20.4 的模块——从机制上把"每次重新解析"变成"只解析一次"。

> **坑：** 头文件里 `#include` 图省事，是一个项目编译时间的复利债。每加一条传递包含都在给所有 TU 上税，而且没人会在 code review 里发现。
{: .sec-pit}

现代写法方面，C++20 模块直接改变了代价模型（BMI 只解析一次，见 20.4.3），C++ 之外没有等价物；在模块普及之前，include-what-you-use 和前向声明仍是主力工具。

## 20.2 C++中常见的预处理
{: .sec-expl}

### 20.2.1 头文件保护：include guard 与 #pragma once
{: .sec-know}

一个头文件会在同一个翻译单元里被包含多次（`a.h` 和 `b.h` 都包含 `types.h`，`main.cpp` 又包含两者）。重复包含意味着重复定义，直接编译错误。解决办法两种：

```cpp
// types.h —— 写法一：include guard，标准保证
#ifndef MYAPP_TYPES_H
#define MYAPP_TYPES_H

struct Point { int x, y; };

#endif  // MYAPP_TYPES_H
```

```cpp
// types.h —— 写法二：#pragma once，事实标准
#pragma once

struct Point { int x, y; };
```

include guard 是标准机制，所有编译器、所有版本都支持，靠预处理器的条件编译实现。缺点是要保证宏名全局唯一——两个不相干的库都写 `UTILS_H`，而你的 TU 恰好两个都包含，第二个会被整个吞掉，报出来的错误（一堆"undefined"）和真实原因相距十万八千里。防御做法是宏名带路径：`MYAPP_NET_TCP_SERVER_H`。

`#pragma once` 是编译器扩展，GCC、Clang、MSVC 全都支持了二十来年，没有宏名冲突问题，也不用敲三行。它的薄弱点在文件身份的判定方式：按文件路径（规范化的物理路径）识别，符号链接、网络盘、构建系统复制的文件可能被误判成不同文件（多份定义）或同一文件（该包含的被漏掉）。这类场景在日常项目里罕见，但在复杂的构建环境里真实发生过。

| 维度 | include guard | `#pragma once` |
| --- | --- | --- |
| 标准地位 | 标准 | 非标准扩展（三大编译器都支持） |
| 出错方式 | 宏名冲突，错误信息难定位 | 文件系统别名场景下误判 |
| 代码量 | 三行 + 起名负担 | 一行 |
| 能否机械检查 | 能（lint 工具可校验宏名规范） | 无需检查 |

实践建议：团队统一一种即可。混用也合法——guard 套着 `#pragma once` 的写法在一些开源库里能见到，属于双保险，不推荐，维护两套保护没有收益。

### 20.2.2 前向声明：省依赖的合法手段与边界
{: .sec-know}

头文件里只需要"有这么个类"就能写的东西——指针、引用、函数声明——不需要完整类型。这时候一行前向声明可以替掉整个 `#include`：

```cpp
// engine.h —— 只依赖 Battery 的名字，不依赖它的定义
#pragma once

class Battery;              // 前向声明，代替 #include "battery.h"

class Engine {
public:
    explicit Engine(Battery& b);   // 引用参数：不完整类型即可
    ~Engine();                     // 析构要删对象，需要完整类型，挪到 cpp
    void check();                  // 调用成员函数需要完整类型，挪到 cpp
private:
    Battery* battery_;             // 指针成员：不完整类型即可
};
```

```cpp
// engine.cpp
#include "engine.h"
#include "battery.h"        // 完整类型只在这个文件里需要

Engine::Engine(Battery& b) : battery_(&b) {}
Engine::~Engine() = default;

void Engine::check() { battery_->level(); }
```

收益不只是编译速度：`battery.h` 以后怎么改，`engine.h` 的包含者都不用重编，依赖被切断在 `.cpp` 层。头文件依赖图是编译时间的直接决定因素，前向声明是给它瘦身的第一工具。

什么时候前向声明救不了你——需要**完整类型**的场景：

| 场景 | 原因 |
| --- | --- |
| 继承它 | 基类大小和布局必须知道 |
| 用它当成员对象（非指针/引用） | 要算 `sizeof` 和偏移 |
| 调用它的成员函数 | 不知道有没有这个函数 |
| `new` / `delete` 它 | 要知道大小、要调析构 |
| 类型别名、模板实参要求完整类型时 | `std::vector<Battery>` 实例化要完整类型 |

还有一条 C++ 特有的坑：在头文件里**内联写函数体**时用了某个类型的成员，编译器当场就需要完整类型，前向声明失效——这类代码只能整体挪到 `.cpp`。

### 20.2.3 #define 与对象宏、函数宏
{: .sec-know}

`#define` 分两种。对象宏是一个名字换一段文本，典型用途是版本号、配置开关：

```cpp
#define APP_VERSION 20260
#define BUFFER_SIZE 4096
```

函数宏带参数表，展开时实参被原样替换进替换体——注意"原样"，参数不是表达式、不是变量，是**记号序列**，这是后面所有陷阱的总根源：

```cpp
#define AREA(w, h) ((w) * (h))     // 函数宏
```

现代 C++ 里对象宏的正当生存空间只剩三块：条件编译开关（配合 `#ifdef`）、和 C 接口对齐的常量、以及标准本身的 `NDEBUG` 之类的保留开关。凡是可以用 `constexpr` 变量、`enum`、`inline constexpr`（C++17）替代的场景，一律替代：

```cpp
// 需要 -std=c++20
inline constexpr int  buffer_size = 4096;   // 有类型、有作用域、能进调试器
inline constexpr auto app_version = 20260;
```

函数宏的正当生存空间更窄：它有一项语言做不到的能力——在宏里写 `#参数` 和 `参数##参数`，把代码转成字符串、拼接新名字（见 20.2.4）。断言宏、日志宏、X-macros 都靠这个活着。**逻辑**则一律交给 `inline` 函数或模板：有类型检查、参数只求值一次、能被调试器单步进去。

> **辨析：函数宏与 inline 函数。** 两者都能内联展开，区别在求值模型：函数是先算实参再传递，每个实参恰好求值一次；宏是文本替换，实参在替换体里出现几次就求值几次，且不做任何类型检查。写 `MAX(i++, j)` 这类调用时，两者的行为差异是 UB 与否的分界线。
{: .sec-iv}

### 20.2.4 字符串化 #、拼接 ## 与多行续行
{: .sec-know}

这是函数宏独有的两件武器，`constexpr` 和模板都替代不了：

- `#参数`：把实参的源码文本变成字符串字面量（字符串化，stringify）。
- `a##b`：把两个记号粘成一个新记号（记号拼接，token pasting）。

```cpp
// macro_tools.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

#define STRINGIFY_IMPL(x) #x          // 真正干活的层
#define STRINGIFY(x)      STRINGIFY_IMPL(x)   // 对外接口，多一层展开

#define JOIN(a, b)      a##b
#define JOIN_IMPL(a, b) JOIN(a, b)

#define VERSION 42

int main() {
    std::cout << STRINGIFY(VERSION) << '\n';       // VERSION 先展开成 42
    std::cout << STRINGIFY_IMPL(VERSION) << '\n';  // 直接拿到字面文本
    int JOIN_IMPL(counter, 1) = 7;                 // 拼出标识符 counter1
    std::cout << counter1 << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra macro_tools.cpp -o mt && ./mt
```

```text
42
VERSION
7
```

`STRINGIFY(VERSION)` 得到 `"42"`、`STRINGIFY_IMPL(VERSION)` 得到 `"VERSION"`，差别就在那一层转发：**`#` 和 `##` 旁边的参数不参与宏展开**，想先展开参数就必须经过一次中间调用。这个"双层宏"写法是所有日志宏、断言宏的标准姿势——`MY_ASSERT(x < 0)` 之所以能打印出 `"x < 0"` 这段源码，靠的就是 `#x`。

多行宏的续行符是行尾反斜杠 `\`，反斜杠后面必须紧跟换行，不能有空格。宏体整体算一行，中间的注释也行，但惯例是不写注释、写成对齐的多段拼接（X-macros 一节有完整例子）。

> **坑：** `##` 拼出的必须是合法记号，拼完不是合法标识符（比如 `1##abc` 想拼出 `1abc`）直接编译错误。拼接是在预处理期做的，编译器没有机会"理解"你拼了什么。
{: .sec-pit}

### 20.2.5 条件编译全家桶与 defined 运算符
{: .sec-know}

条件编译让一段代码"编译不编译"由预处理期决定。指令全家：

| 指令 | 含义 |
| --- | --- |
| `#if expr` | 表达式非零则保留该段 |
| `#ifdef X` | 等价于 `#if defined(X)` |
| `#ifndef X` | 等价于 `#if !defined(X)`，include guard 的标准写法 |
| `#elif expr` | else if |
| `#else` | 否则 |
| `#endif` | 结束 |
| `defined(X)` | `#if` 内的运算符，判断宏是否已定义 |

```cpp
// cond.cpp —— 需要 -std=c++20
#include <iostream>

#define USE_FAST_PATH 1

namespace demo {

#if USE_FAST_PATH
int process(int v) { return v << 1; }        // 快路径：移位
#elif defined(_WIN32)
int process(int v) { return v + v; }
#else
int process(int v) { return v * 2; }
#endif

}  // namespace demo

int main() {
    std::cout << demo::process(21) << '\n';
}
```

```text
42
```

表达式里能用的是整型字面量、已定义的宏、算术逻辑运算符和 `defined`。用不了的更多——所有和**类型**有关的东西都进不来，因为类型系统还没上线（见下一节）。写多分支时有个习惯值得养成：`#if/#else/#endif` 各配一行注释标明对应哪个条件，三层以上嵌套的条件编译没有注释基本没法读。

还有一个常见用途是临时屏蔽代码：`#if 0 ... #endif`。比块注释可靠，因为里面可以再含 `/* */` 而块注释不能嵌套。但它骗不过版本管理——被注释的代码要么删掉要么修好，`#if 0` 坟场是老项目的常见景观。

### 20.2.6 #if 里不能用 sizeof：预处理期没有类型
{: .sec-know}

这是预处理和编译器本体的硬边界，标准明文规定：

```cpp
// 需要 -std=c++20
#if sizeof(int) == 4        // 编译错误！
#endif
```

```text
error: token "sizeof" is not valid in preprocessor expressions
```

预处理器的世界只有整数算术和宏。`sizeof(int)` 需要知道类型系统的信息，而类型语义分析是阶段 5 以后的事，此时预处理器已经收工了。同理，`#if` 里不能写 `int`、不能调用任何函数、不能出现模板。

想把"类型的大小"作为编译期开关，路径是绕一步：先在语言层算出常量，再喂给预处理器。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <type_traits>

static_assert(sizeof(int) == 4, "本项目假设 int 为 4 字节");

#if INTPTR_MAX == INT64_MAX
    #define PLATFORM_64BIT 1
#else
    #define PLATFORM_64BIT 0
#endif

int main() {
    std::cout << (PLATFORM_64BIT ? "64-bit" : "32-bit") << '\n';
}
```

```text
64-bit
```

`INTPTR_MAX` 来自 `<cstdint>`，预期能拿到它的值——这类宏由编译器按目标平台预置，正是"平台差异在预处理期被感知"的正规通道。判断平台大小用这些标准宏，比自己 `#define` 靠谱得多。

### 20.2.7 预定义宏：__cplusplus、__FILE__、__LINE__ 与可复现构建
{: .sec-know}

编译器自动预置一批双下划线开头的宏，常用的这些：

| 宏 | 值 / 类型 | 用途 |
| --- | --- | --- |
| `__cplusplus` | `199711L`（C++98）、`201103L`（C++11）、`201402L`（C++14）、`201703L`（C++17）、`202002L`（C++20）、`202302L`（C++23） | 判断语言标准 |
| `__FILE__` | 字符串字面量，当前文件名 | 日志、断言定位 |
| `__LINE__` | 整数，当前行号 | 同上 |
| `__func__` | 静态函数名变量，C++11 | 同上 |
| `__DATE__` / `__TIME__` | 编译日期时间字面量 | 构建信息 |
| `__GNUC__` / `_MSC_VER` / `__clang__` | 编译器与版本 | 编译器分支 |

三个容易写错的细节：

`__func__` 不是宏，是 C++11 定义的静态存储期字符数组变量，预处理器碰不到它，放进字符串里拼接（`#__func__`）是错的。`__FILE__` 的内容按编译命令里写的路径展开——用绝对路径编译，日志里就是绝对路径，构建可复现性也被顺带破坏。

`__DATE__` 和 `__TIME__` 让"同一次提交、两次编译、产物不同"，可复现构建（reproducible build）的直接敌人。发布关键组件的系统都会禁止它们出现在代码里，改用构建系统注入的固定值。

```cpp
// predef.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    std::cout << "__cplusplus = " << __cplusplus << '\n';
    std::cout << __FILE__ << ':' << __LINE__ << '\n';
    std::cout << "in " << __func__ << "()\n";
}
```

```bash
g++ -std=c++20 predef.cpp -o pd && ./pd
```

```text
__cplusplus = 202002L
predef.cpp:8
in main()
```

> **注意：** MSVC 出于兼容性考虑，`__cplusplus` 永远报 `199711L`，除非加 `/Zc:__cplusplus`。用 `__cplusplus` 判断标准版本的代码在 MSVC 下必须同时检查 `_MSVC_LANG`，这是个流传很广的坑。
{: .sec-note}

### 20.2.8 特性测试宏 __cpp_* 与渐进式升级
{: .sec-know}

`__cplusplus` 只能告诉你"整体标准是哪一版"，但编译器对同一标准内各特性的实现进度不同——C++20 的 concepts 和 modules 就不是同时落地。特性测试宏（feature-test macro）解决"这个具体特性到底有没有"：

| 宏 | 判断什么 | C++20 基准值 |
| --- | --- | --- |
| `__cpp_concepts` | 语言 concepts | `201907L` |
| `__cpp_lib_ranges` | 库 ranges | `201911L` |
| `__cpp_lib_format` | `std::format` | `201911L` |
| `__cpp_lib_source_location` | `std::source_location` | `201907L` |

库类宏（`__cpp_lib_*`）需要包含 `<version>`（C++20 起有的标准头）才能可靠取得。数值随小版本演进，所以判断写法一律用 `>=`：

```cpp
// feature.cpp —— 需要 -std=c++20
#include <iostream>
#include <version>

int main() {
#if defined(__cpp_concepts) && __cpp_concepts >= 201907L
    std::cout << "concepts ok\n";
#else
    std::cout << "concepts missing\n";
#endif

#if __cpp_lib_format >= 201911L
    std::cout << "std::format ok\n";
#else
    std::cout << "std::format missing\n";
#endif
}
```

```bash
g++ -std=c++20 feature.cpp -o f && ./f     # GCC 13 + libstdc++ 13
```

```text
concepts ok
std::format ok
```

用途集中在两处：库作者按用户编译器能力提供降级路径（concepts 可用时用 concepts，不可用退回 SFINAE）；大型代码库做渐进升级，新标准特性按宏逐个启用而不是一刀切 `-std=c++20`。写业务代码的日常项目可以直接假设标准版本，别把每个特性都包进宏，可读性代价不值得。

### 20.2.9 #error、#warning 与 #pragma message
{: .sec-know}

`#error` 让预处理直接失败，消息文本进错误输出。用途是"这个配置组合我不支持，现在就死"：

```cpp
// 需要 -std=c++20
#if !defined(__x86_64__) && !defined(_M_X64)
#error "本模块只支持 64 位 x86，其他平台请单独评估"
#endif

#if __cplusplus < 201703L
#error "至少需要 C++17，请检查 -std 选项"
#endif
```

```text
cond_err.cpp:4:2: error: #error 本模块只支持 64 位 x86，其他平台请单独评估
```

`#pragma message("...")` 在编译期往输出里打一行提示（GCC/Clang 以 note 形式出现），适合"这块即将废弃"之类的温和提醒。`#warning` 是 GCC/Clang 的扩展，标准不认识，MSVC 下的对应物是 `#pragma message`——跨平台代码用后者。让已知问题在编译期出声，比埋在 issue 里等人踩强。

### 20.2.10 #undef 与 X-macros 技巧
{: .sec-know}

`#undef X` 取消宏定义。日常两个用途：给被第三方头污染的名字扫尾（典型如 Windows 的 `min/max`，见 20.3.4）；以及 X-macros——**一个宏列表，多个消费者**的技巧：

```cpp
// xmacro.cpp —— 需要 -std=c++20
#include <iostream>
#include <string_view>

#define LOG_LEVELS \
    X(TRACE, "trace") \
    X(DEBUG, "debug") \
    X(INFO,  "info")  \
    X(ERROR, "error")

enum class LogLevel : int {
#define X(name, text) name,
    LOG_LEVELS
#undef X
};

constexpr std::string_view to_string(LogLevel lv) {
    switch (lv) {
#define X(name, text) \
        case LogLevel::name: return text;
        LOG_LEVELS
#undef X
    }
    return "?";
}

int main() {
    std::cout << to_string(LogLevel::INFO) << '\n';
    std::cout << static_cast<int>(LogLevel::ERROR) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra xmacro.cpp -o xm && ./xm
```

```text
info
3
```

枚举定义和字符串表来自同一份 `LOG_LEVELS`，加一个日志级别只改一处，永远不会再出现"枚举加了、字符串表忘加"的漂移。配置项清单、错误码表、指令分发表都适合这个模式。代价是可读性：没用过 X-macros 的人第一次看要愣几秒，所以每个 `#define X` / `#undef X` 附近都值得加一行注释说明套路。

> **坑：** `#undef` 之后的宏就真的没了，包括第三方库可能正依赖它的场景。取消一个你不确定来源的宏之前，先确认没有别的包含者还需要它。
{: .sec-pit}

## 20.3 分析宏的常见陷阱
{: .sec-ts}

### 20.3.1 优先级陷阱：SQR(a+1)
{: .sec-prac}

教科书级案例，值得亲手跑一遍：

```cpp
// macro_trap.cpp —— 需要 -std=c++20
#include <iostream>

#define SQR_BAD(x)  x * x
#define SQR_OK(x)   ((x) * (x))

int main() {
    int a = 2;
    std::cout << "bad : " << SQR_BAD(a + 1) << '\n';  // 展开成 a + 1 * a + 1
    std::cout << "good: " << SQR_OK(a + 1) << '\n';   // 展开成 ((a+1) * (a+1))
}
```

```bash
g++ -std=c++20 -Wall -Wextra macro_trap.cpp -o mt2 && ./mt2
```

```text
bad : 5
good: 9
```

`SQR_BAD(a+1)` 展开为 `a + 1 * a + 1`，乘法优先级高，算出来是 `2 + 2 + 1 = 5`。编译器全程没意见——它收到的就是一份合法表达式。预防手段是纪律：**宏体和每个参数都套括号**。但括号治标不治本，双重求值这种括号包不住的坑马上就来。

### 20.3.2 双重求值：SQR(i++) 的副作用
{: .sec-warn}

`#define SQR(x) ((x) * (x))` 写得足够规范了，看它遇到副作用实参：

```cpp
// 需要 -std=c++20
int i = 3;
int r = SQR(i++);    // 展开成 ((i++) * (i++))——undefined behavior
```

同一个表达式里 `i` 被修改两次且无 sequenced 关系，这是不折不扣的 undefined behavior：不同编译器、不同优化级别给出不同结果，警告都可能没有（`-Wsequence-point` 在某些写法下不触发）。而且这个错误藏在调用方——宏看着无害，危险的是你传了什么进去。

带副作用的实参传给任何函数宏都有同类风险（`MAX(a++, b)` 也是求值两次，只是没到 UB 的程度）。根治办法是别用函数宏写逻辑，退到语言层：

```cpp
// 需要 -std=c++20
inline int sqr(int x) { return x * x; }          // 实参只求值一次
template <class T> constexpr T sqr_t(T x) { return x * x; }
```

> **坑：** 宏参数在替换体里出现几次就被求值几次，这是模型决定的，写法无法修复。逻辑进 `inline` 函数或模板，宏只留"必须拿到源码文本"的场景（断言、日志、X-macros）。
{: .sec-pit}

### 20.3.3 宏参数里的逗号
{: .sec-know}

宏的参数按**顶层逗号**分割，尖括号和方括号里的逗号不算"顶层"，只有圆括号才算。于是：

```cpp
// macro_comma.cpp —— 需要 -std=c++20
#include <iostream>
#include <utility>

#define DECLARE_PTR(type) type* p_##type;

DECLARE_PTR(int);                        // 没问题
// DECLARE_PTR(std::pair<int, int>);     // 错：宏收到 3 个参数，但只收 1 个

using PairII = std::pair<int, int>;      // 用别名把逗号收进一个类型名
DECLARE_PTR(PairII);                     // 宏只见一个记号序列，正常展开

int main() {
    p_int = nullptr;
    p_PairII = nullptr;
    std::cout << (p_int == nullptr) << (p_PairII == nullptr) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra macro_comma.cpp -o mc && ./mc
```

```text
11
```

同理适用于所有带逗号的模板类型。用 `typedef` / `using` 给宏"喂"干净的名字，比在宏里做花式补救便宜得多。

### 20.3.4 宏与命名空间、模板、标准库的冲突：Windows 的 min/max
{: .sec-know}

宏没有作用域、没有命名空间、不看类型，`#define` 过的名字从定义处到 `#undef` 处横扫一切翻译单元内容。它和标准库重名时，标准库是受害者：

```cpp
// win_minmax.cpp —— 仅 Windows 示意，其他平台无需此处理
#define NOMINMAX          // 必须在 windows.h 之前
#include <windows.h>      // 否则 min/max 被定义成函数宏
#include <algorithm>

int clamp_pos(int v) {
    return (std::max)(0, (std::min)(v, 100));   // 加括号绕开宏（若没定义 NOMINMAX）
}
```

`windows.h` 里的 `#define min(a,b) (((a)<(b))?(a):(b))` 会让 `std::min(v, 100)` 直接编译失败，或者更糟——没带 `std::` 的 `min(v,100)` 编译通过但走宏，参数被求值两次。三层防御按优先级：编译选项全局定义 `NOMINMAX`（CMake 里 `add_compile_definitions(NOMINMAX)`，一劳永逸）；不行就 `#undef min` / `#undef max`；最后才是 `(std::min)(x, y)` 括号调用技巧（函数名被括号包住后不再是宏展开语境，这是语言规则保证的）。

同类冲突不止 min/max：第三方 C 库定义 `TRUE`、`NULL`、通用短名宏后，与你的代码、模板实参名（宏会替换模板里的标识符！模板参数叫 `T` 而某头文件 `#define T char` 是真实存在过的事故）撞上的故事，属于维护过跨平台代码的人的共同记忆。预防只有一条：自己项目里的宏一律全大写加前缀，绝不定义短名宏。

### 20.3.5 #define new 的灾难
{: .sec-warn}

老项目里流传的内存泄漏定位手段——重定义 `new` 抓取文件行号：

```cpp
// 灾难示范，不要模仿
#ifdef _DEBUG
#define new DEBUG_NEW
#endif
```

这一行同时引爆多个雷：`operator new` 这个名字里的记号 `new` 也被替换，展开成 `operator DEBUG_NEW` 直接编译错误；placement new `new (buf) T` 展开成 `DEBUG_NEW (buf) T` 语法崩坏；自定义的 `operator new(size_t, const char*, int)` 配套体系要全程跟着宏走；更根本的是，它把"内存诊断"绑死在预处理期，sanitizer 这种运行期工具没法与它共存。现代方案明确：内存问题交给 AddressSanitizer（见第 21 篇），文件行号定位交给 `std::source_location`（C++20，见 20.4.7），这套宏的历史使命已经结束。

### 20.3.6 #pragma pack 的风险与 _Pragma
{: .sec-prac}

`#pragma pack` 改变结构体的对齐规则，通信协议、文件格式解析绕不开它：

```cpp
// pack_demo.cpp —— 需要 -std=c++20
#include <cstddef>
#include <iostream>

struct Sensor {              // 自然对齐：1 + 3(填充) + 4 = 8
    char tag;
    int  value;
};

#pragma pack(push, 1)
struct Packet {              // 压缩对齐：1 + 4 = 5，无填充
    char tag;
    int  value;
};
#pragma pack(pop)

int main() {
    std::cout << sizeof(Sensor) << ' ' << sizeof(Packet) << '\n';
    static_assert(sizeof(Packet) == 5);   // 编译期锁死布局，C++17 起可省消息
}
```

```bash
g++ -std=c++20 pack_demo.cpp -o pk && ./pk
```

```text
8 5
```

`push/pop` 成对使用是底线——裸 `#pragma pack(1)` 会把后续所有结构体的对齐一并改掉，错误通常在很远的地方才爆出来。风险清单：`Packet` 里的 `value` 现在落在非自然对齐的地址上，x86 上能跑但慢，某些 ARM 平台未对齐访问直接产生硬件异常；取对齐被破坏成员的指针（`&pkt.value`）传给函数再解引用，是埋雷；和第三方库交换 `packed` 结构体指针属于 ABI 冒险，两边对齐规则必须一致。

`_Pragma` 是 C++11 把 pragma 标准化的写法：`_Pragma("pack(push, 1)")` 等价于 `#pragma pack(push, 1)`，区别是它能出现在宏定义里（`#` 开头的指令不能进宏体），需要"把对齐设置打包成宏"时只有这一条路。协议结构体的替代方案还有 `alignas` 配合手工填充，以及彻底一点——序列化库按字段编解码，布局和对齐解耦。字段少、格式固定的场景 `#pragma pack` 仍是最省事的，配上 `static_assert(sizeof(...))` 锁布局即可。

## 20.4 技术解惑
{: .sec-expl}

### 20.4.1 C++20 模块：它到底解决了什么
{: .sec-expl}

模块没有引入任何新的运行期概念，它改的是**编译期信息交换的格式**。头文件模式的问题清单：文本包含导致每个 TU 重复解析（20.1.3）、宏泄漏进所有包含者、include 顺序影响语义、头文件必须和实现拆两份、编译时间随依赖图爆炸。模块的对应解法：编译器把接口解析成二进制产物（BMI），后续使用 `import` 直接读二进制，不再重复展开文本；宏不导出；没有顺序敏感；接口和实现可以同文件。

### 20.4.2 模块的语法与三种单元
{: .sec-know}

```cpp
// math.ixx —— 模块接口单元（MSVC 惯用 .ixx，Clang 惯用 .cppm）
export module demo.math;

export namespace demo {

int add(int a, int b);                  // 声明也可以导出，实现放实现单元

class Counter {
public:
    void tick() { ++n_; }
    int  value() const { return n_; }
private:
    int n_ = 0;
};

}  // namespace demo
```

```cpp
// math.cpp —— 模块实现单元：同模块的"私有 cpp"，不需要写 export
module demo.math;

namespace demo {
int add(int a, int b) { return a + b; }
}  // namespace demo
```

```cpp
// main.cpp —— 使用者：import 替代 include
#include <iostream>
import demo.math;

int main() {
    std::cout << demo::add(2, 3) << '\n';
    demo::Counter c;
    c.tick();
    c.tick();
    std::cout << c.value() << '\n';
}
```

```text
5
2
```

三个关键语法点：`export module` 声明模块接口单元，带 `export` 的名字才对 import 者可见，没导出的都留在模块内部（信息隐藏比头文件干净——内部的类、函数根本不出现在接口里）；实现单元写 `module demo.math;`，编译它需要接口的 BMI 先就位；`import demo.math;` 在语法上位于声明区，且必须在使用前出现。

复杂模块可以拆**分区**（partition）：

```cpp
// json_lexer.ixx —— 分区接口
export module demo.json:lexer;
export int token_count(std::string_view s);

// json.ixx —— 主接口，聚合分区并再导出
export module demo.json;
export import :lexer;
```

分区解决的是大模块"一个接口单元太长"的问题：每个分区独立编译出 BMI，`export import :name` 把分区内容并入模块对外接口。分区只被同模块的单元 import，外部 import 不到。

### 20.4.3 为什么模块能提速：BMI 只解析一次
{: .sec-know}

头文件模式下，`<iostream>` 被每个 TU 展开、解析、实例化一遍，预处理文本百万行只是寻常。模块模式下流程变成：编译接口单元一次，产出 BMI（Binary Module Interface，GCC 的 `.gcm`、MSVC 的 `.ifc`、Clang 的 `.pcm`，本质都是"解析完的 AST + 实例化结果"的持久化）；之后每个 `import` 它的 TU 直接加载二进制摘要，跳过文本展开和重复语义分析。

省下的不只是时间。BMI 里记录了名字的完整信息，import 时按名字直达，还顺带消灭了两类经典病：include 顺序敏感（模块间依赖由编译器从 BMI 推导）和 ODR 式的重复定义风险（定义只属于模块，不再被粘贴多份）。模板也受益——模板定义可以在模块接口里自由写，不需要"头文件声明、cpp 实现、再手动显式实例化"的杂技，实例化工作在使用者首次需要时基于 BMI 完成。

代价与边界要说清楚：BMI 目前**不保证跨编译器版本兼容**（MSVC 明确声明 BMI 不跨版本，GCC/Clang 类似），模块必须和源码一起、用同一编译器构建——这决定了"发布头文件给用户"的模式暂时替代不了，二进制发布要连 BMI 一起给且兼容性自担。构建系统也必须理解模块依赖图（先编接口再编实现再编使用者的顺序），这曾是模块落地的最大摩擦点，CMake 3.28 之后才算有标准答案。

### 20.4.4 模块与宏：不导出宏与 global module fragment
{: .sec-know}

规则一句话：**模块不导出宏**。`#define` 写在模块里，import 者看不见——宏的世界被限制在"全局模块"（所有非模块代码 + 各模块的预处理内容所在的无名空间）。这是特性不是缺陷：`windows.h` 那种宏污染从此不可能通过模块传染。

但模块内部还是可以、也经常需要用宏和 `#include`——用标准库就得包含标准头。放的位置有讲究：

```cpp
// util.ixx —— global module fragment 演示
module;                       // 全局模块片段开始：这段内容不导出
#include <string>
#include <string_view>

export module demo.util;      // 接口单元从这里开始（纯 purview）

export std::string to_upper(std::string_view s);   // 实现略
```

`module;` 到 `export module` 之间是**全局模块片段（global module fragment）**：这里可以写 `#include` 和宏，供本单元内部使用，但它们对 import 者完全不可见。`export module` 之后的部分叫纯模块 purview，规范上不再允许 `#include`（想用别的头，`import` 对应模块；现实里编译器普遍对 purview 里的 `#include` 睁一只眼闭一只眼当扩展，但写了就不可移植）。

这也解释了迁移路上的一个认知修正：模块没有"把头文件变没了"，头文件仍然是为 C 接口、为未模块化的第三方库提供信息的唯一方式。模块改变的是**你自己的代码**在接口边上的组织方式。

### 20.4.5 头文件与模块混用的迁移路径
{: .sec-know}

真实项目没有能力一夜切成模块，可行路径是增量式的：

| 步骤 | 动作 | 前提 |
| --- | --- | --- |
| 1 | 把最稳定、依赖最少的叶子模块化（工具函数、基础类型） | 编译器与构建系统支持模块 |
| 2 | 模块内需要标准库时用 global module fragment 包头 | 同上 |
| 3 | 新增代码用模块，老代码保持头文件，两者互相可见（模块可以 `#include` 全局头，头文件代码无法 `import` 未导出的内容但可以 import 模块） | 混编模式 |
| 4 | 第三方库等上游提供官方模块包后再替换 | 生态成熟度 |

关键约束：模块编译产物有构建顺序依赖（接口 BMI 必须先于实现单元和使用者），构建系统必须能推导这张图。手写 Makefile 处理这个是自讨苦吃，直接上 CMake 或用各编译器自家工具链。

### 20.4.6 编译器与 CMake 支持现状
{: .sec-prac}

三大编译器都实现了 C++20 模块：MSVC 从 VS 2019 16.8 起最完整，GCC 14/15 持续补齐（GCC 15 开始提供 `import std;`），Clang 16+ 可用。日常工程别手搓命令行，用 CMake 3.28+ 的原生模块支持（需要 Ninja 生成器）：

```cmake
# CMakeLists.txt —— 需要 CMake 3.28 及以上
cmake_minimum_required(VERSION 3.28)
project(demo CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(demo main.cpp math.cpp)
target_sources(demo PRIVATE
    FILE_SET CXX_MODULES FILES math.ixx    # 接口单元单独声明，CMake 据此排依赖序
)
```

```bash
cmake -G Ninja -B build && cmake --build build && ./build/demo
```

```text
5
2
```

MSVC 命令行单文件玩法：`cl /std:c++20 /EHsc main.cpp math.cpp math.ixx`，MSVC 自己扫描依赖。GCC 的 `-fmodules-ts` 路线兼容老的草案语义，Clang 的裸命令行参数（`--precompile`、`-fmodule-file`）版本间变动频繁——结论：模块项目从第一天就用 CMake/Ninja，裸命令行留给实验。

标准库自身的模块化（`import std;`）在 C++23 框架下落地：MSVC、GCC 15、Clang 配 libc++ 均已可用，这是后续几年最实际的迁移方向——连 `<iostream>` 这些标准头都省了。

### 20.4.7 std::source_location：告别 __FILE__/__LINE__ 传递链
{: .sec-prac}

日志宏的老套路是调用点手动展开 `__FILE__`/`__LINE__` 再层层传参，宏退场后这套信息没有跟着消失——C++20 给了语言级替代：

```cpp
// source_loc.cpp —— 需要 -std=c++20
#include <iostream>
#include <source_location>
#include <string_view>

void log_msg(std::string_view msg,
             const std::source_location& loc = std::source_location::current()) {
    std::cout << loc.file_name() << ':' << loc.line() << " ["
              << loc.function_name() << "] " << msg << '\n';
}

int main() {
    log_msg("startup ok");       // 调用点信息被自动捕获，不需要宏
}
```

```bash
g++ -std=c++20 source_loc.cpp -o sl && ./sl
```

```text
source_loc.cpp:15 [main] startup ok
```

诀窍在默认实参：`std::source_location::current()` 作为默认值时，记录的是**调用者**的位置而不是函数定义处。`file_name()`、`line()`、`column()`、`function_name()` 四个访问器覆盖宏的全部能力，且是真正的类型、能放进接口、能被调试器观察。旧代码里 `#x` 拿表达式文本的能力它没有，需要表达式文本的断言宏仍要宏来做——两者是互补而非替代关系。

### 20.4.8 头文件设计最佳实践
{: .sec-best}

模块普及之前，头文件仍是接口的主战场。这几条规则能挡住绝大部分工程事故：

自包含。每个头文件必须能被单独编译——它用到的每个名字要么自己定义要么自己包含。检验方法简单：写一个只包含它一个头文件的空 `.cpp` 进构建，CI 会替你守住。

按需包含。能用前向声明的用前向声明；包含顺序按"本文件对应的头、本项目其他头、第三方头、标准库头"排列并字母序，`include-what-you-use` 工具可以自动检查直接包含的完备性。

头文件里禁止 `using namespace std;`。它会把整个 `std` 强加给所有包含者，`swap`、`count`、`data` 这类重名灾难在几十个 TU 之外爆发，且排查时没人想到源头在某个头文件里。`.cpp` 文件里用也是能免则免。

接口最小暴露。头文件里只放必须公开的东西：能进 `.cpp` 的匿名命名空间/`static` 的别放头文件；类里只公开操作，数据成员进 `private` 或干脆 pimpl；`constexpr` 内联变量（C++17）是头文件里定义常量的正确姿势，替代 `#define` 和老式 `static const`。

保护与命名。include guard 宏名带项目前缀和路径段；头文件里不写 `using`、不定义非 `inline` 的全局变量和函数（那是 ODR 事故，见第 21 篇的 duplicate symbol）。

## 变式追问
{: .sec-think}

1. **`#pragma once` 没进标准，为什么三大编译器都支持了还不收编？** 推理：标准要给出可判定的语义，而"同一个文件"在文件系统层面没有权威定义——符号链接、网络盘、构建系统的复制，都可能让"同文件"的判定因平台而异。include guard 把判定权交给程序员（宏名），语义完全确定，这正是它留在标准里的理由。所以这不是技术落后，是"谁来定义相同"的立场差异。
2. **既然 BMI 提速巨大，为什么没有像 PCH 一样被迅速普及？** 推理：PCH 是单编译器的私有优化，怎么缓存、是否失效随便是编译器自己的事。BMI 要被"其他 TU"消费，而 C++ 的二进制兼容承诺从来只到目标文件层面；BMI 里装的是 AST 级信息，比目标文件细得多，跨版本兼容的维护成本是数量级的。生态要等"构建系统原生理解模块图 + 各编译器 BMI 格式稳定"两个条件同时成立——CMake 3.28 是前者的分水岭。
3. **`__LINE__` 在多行宏里取的是哪一行的值？宏展开会让它漂移吗？** 推理：预处理器按"展开发生处的物理行"解释 `__LINE__`，多行宏（带 `\` 续行）展开后，`__LINE__` 指向宏调用所在行而非宏体内部行——所以断言宏里 `__LINE__` 报的是调用点，这正是想要的。但要注意 `#line` 指令可以改写它，代码生成器（如 RPC 框架的 stub 生成）常用 `#line` 把错误指回源模板，排查这类工程时看到"不可能的行号"先查 `#line`。
4. **模块时代，头文件会消失吗？** 推理：三个顽固场景保住头文件的寿命——C 互操作（C 的头文件生态不会为 C++ 重写）、二进制分发（BMI 兼容性没解决前，发布头文件仍是唯一通用接口形式）、以及海量存量代码的渐进迁移成本。更可能的终局是：新建代码模块化，接口边界仍是头文件，就像今天 C++ 代码的边界仍是 C ABI 一样。学会和头文件长期共处，才是工程判断。
