## 中小规模网站架构的组成
{: .sec-expl}

用一家餐厅来类比整套架构，会非常容易理解：

| 角色 | 架构组件 | 职责 |
| --- | --- | --- |
| 顾客 | 用户 | 访问网站的人员 |
| 保安 | 防火墙（firewalld） | 进行访问策略控制 |
| 迎宾 | 负载均衡服务器（nginx） | 对用户的访问请求进行调度处理 |
| 服务员 | web 服务器（nginx） | 处理用户的请求 |
| 厨师 | 数据库服务器（mysql / mariadb） | 存储字符数据，如订单：耳机、500、索尼、黑色、北京地址、订单时间 2019-05-05 13:00 |
| 厨师 | 存储服务器（nfs） | 存储图片、音频、视频、附件等数据信息 |
| 厨师 | 备份服务器（rsync + crond 定时备份，rsync + sersync 实时备份） | 存储网站所有服务器的重要数据 |
| 厨师 | 缓存服务器（memcache / redis / mongodb） | a 将数据信息存储到内存中；b 减缓服务器的压力 |
| 经理 | 批量管理服务器（ansible） | 批量管理多台服务器主机 |

> **注意：** 数据库一行用 mariadb 替代 mysql 的写法说明：MariaDB 是 MySQL 的社区分支，兼容 MySQL 协议与命令，可作为 MySQL 的直接替代，部分发行版已默认用它替换 MySQL。
{: .sec-pit}

> **注意：** 缓存一行的三个软件定位不同：memcache 是纯粹的 KV 缓存，简单快；redis 支持持久化与丰富数据结构，如今是绝对主流；mongodb 是文档型数据库，严格说不算缓存，放在这一行是按"内存型数据服务"归的类。
{: .sec-pit}

### 部署架构时还要解决的四件事
{: .sec-ts}

四件事按"出事的概率 × 损失"排序：单点故障最常见，VPN、审计、监控属于配套体系，越往后越涉及流程与制度。

**1）解决网站架构单点问题**

| 角色 | 高可用方案 |
| --- | --- |
| 迎宾（负载均衡） | keepalived |
| 数据库 | MHA |
| 存储服务 | keepalived 实现，或分布式存储 |
| 缓存服务 | 缓存服务集群 / 哨兵模式 |

> **注意：** 面试题「公司的数据是如何备份的」，常见答案有三类：
>
> 1. 利用开源软件实现数据备份，如 rsync（免费）
> 2. 利用企业网盘或公有云对象存储进行数据备份
> 3. 利用自建备份存储架构，如两地三中心
{: .sec-pit}

**2）内部员工如何远程访问架构**
部署搭建 VPN 服务器（PPTP VPN）。

**3）内部员工操作管理架构服务器要进行审计**
部署跳板机服务器（JumpServer）。

**4）架构中服务器出现问题需要提前报警告知**
部署监控服务器（Zabbix）。

## 原理解析：企业网站架构演进
{: .sec-know}

网站架构不是一开始就设计成"全家桶"的，而是随着访问量增长一级级演进。理解这条路径，才能明白每台服务器存在的意义：

1. **单机架构（起步期）**
   Linux + Nginx + MySQL + PHP/Tomcat 全部装在一台服务器上，甚至应用、数据库、备份都在同一块盘上。
   优点：成本低、部署快；缺点：单点故障，任何服务宕机全站瘫痪，硬盘满了无处可躲。
2. **LNMT 分离架构（成长期）**
   访问量上来后，单机扛不住，按角色拆分：Web、数据库、存储各自独立成服务器。
   优点：单点缩小，可以按角色分别扩容；缺点：Web 单点仍在，数据库成为新瓶颈。
3. **集群化架构（成熟期）**
   每个角色都不再是"一台"：负载均衡做主备（keepalived 虚拟 IP）、Web 横向扩容多台、数据库做主从 / MHA、缓存上 Redis、存储用 NFS 或分布式存储，前面加备份服务器统一收数据。
   优点：消除单点、可水平扩展、容量可规划；缺点：组件多，运维复杂度、监控与发布成本上升。
4. **分布式 / 云原生化架构（大规模期）**
   应用按服务拆分，服务独立部署、独立伸缩；引入注册中心、配置中心、容器编排（Kubernetes）、CI/CD 流水线；数据库分库分表，静态资源全面上 CDN。
   优点：弹性与容错能力最强；缺点：需要成熟的自动化与平台化能力支撑。

> **注意：** 运维的价值判断标准：架构演进永远是"用下一层的最小代价解决当前层的瓶颈"，不要一上来就堆最复杂的架构。中小规模下，LNMT 分离 + 主从 + 备份就是性价比最高的形态，本篇的项目环境就是按这个目标搭的。
{: .sec-pit}

> **注意：** 演进过程还有一个贯穿始终的选择：垂直扩容（scale up，加 CPU、加内存、换 SSD）与水平扩容（scale out，加机器分摊）。垂直简单直接、不动架构，但单机有上限且越往上越贵；水平上限高、单位成本低，但要求应用支持分布式。生产上的常见路径是先垂直撑过早期，架构分离后再转水平。
{: .sec-pit}

### 辨析：高可用、集群、分布式

三个词经常混着说，实际指向不同：

- **高可用（HA）**：目标是"服务不中断"，靠冗余与自动切换实现，如 keepalived 主备、MHA
- **集群（cluster）**：多台机器干同一件事，对外像一台，重点是能力叠加与冗余，Web 集群就是典型
- **分布式（distributed）**：把一件事拆成多步分给多台机器协作，各节点职责不同，如分库分表、微服务拆分

面试可以这样区分：集群是"多个人一起干同样的活"，分布式是"把活拆开各干一段"，高可用是"任何时候都有人能顶上"。

### 常见架构图文字描述
{: .sec-expl}

架构要分层，不是机器摆着好看。接入、负载均衡、Web、数据、管理、备份各管一摊：一层出问题，故障半径被限制在这一层，排查时不用全链路翻一遍；流量涨了先扩哪一层一目了然，Web 不够加 Web，缓存不够加缓存；安全边界也清晰，数据库和存储永远不直接面对公网。说白了，分层是用机器数量换"可排查、可扩容、可加固"。

生产环境最常见的分层架构（本课程项目的目标形态），用文字描述如下：

- **接入层**：用户请求先经过 CDN（静态资源加速）与 WAF（Web 应用防火墙，过滤恶意请求），再到达防火墙，只放行业务端口（80 / 443）
- **负载均衡层**：两台 nginx（lb01 / lb02）做反向分发，前面用 keepalived 抢虚拟 IP（VIP）做主备，一台故障 VIP 自动漂移，用户无感知
- **Web 层**：多台 nginx（web01 / web02 / web03）处理动态请求，负载均衡按权重 / 轮询分发；上传的图片等文件统一写到共享存储，不在 Web 服务器本地落盘
- **数据层**：MySQL 主从（写主库、读从库），Redis 做缓存挡在数据库前面，NFS 提供跨主机的共享存储目录
- **管理层**：Zabbix 监控所有服务器，JumpServer 做统一登录与审计，Ansible 批量执行配置与发布
- **备份层**：backup 服务器通过 rsync 定时把所有服务器的配置、站点、日志收回来集中保存与校验

数据流向总结：用户 → CDN/WAF → 防火墙 → LB（VIP）→ Web → 缓存 / 数据库 / 存储；运维与管理流量全部走内网，对外只暴露负载均衡的服务端口。

### 知识卡片：常用角色与默认端口速查
{: .sec-know}

| 服务 | 默认端口 | 说明 |
| --- | --- | --- |
| SSH | 22 | 远程管理，跳板机审计的入口 |
| HTTP / HTTPS | 80 / 443 | nginx 对外服务端口 |
| rsync daemon | 873 | 备份传输 |
| MySQL | 3306 | 数据库 |
| Redis | 6379 | 缓存 |
| NFS | 2049（v4）/ 111（rpcbind） | 共享存储 |
| Zabbix | 10050 / 10051 | agent / server |

端口是排错的通用切入点：服务"不通"，第一件事就是确认端口有没有监听、防火墙有没有放行。

## 综合架构规划
{: .sec-expl}

规划先于建设：这套环境的每一台机器、每一个 IP、每一个主机名都是提前定好的，部署时照单执行。没有规划的架构，装一台算一台，最后谁也说不清哪台机器跑着什么、能不能下线。

| --- | --- | --- | --- | --- | --- |

| 02 | 负载均衡服务器 | lb01 | 10.0.0.5 | 172.16.1.5 | nginx keepalived |
| 03 | 负载均衡服务器 | lb02 | 10.0.0.6 | 172.16.1.6 | nginx keepalived |
| 04 | web 服务器 | web01 | 10.0.0.7 | 172.16.1.7 | nginx |
| 05 | web 服务器 | web02 | 10.0.0.8 | 172.16.1.8 | nginx |
| 06 | web 服务器 | web03 | 10.0.0.9（存储） | 172.16.1.9 | nginx |
| 07 | 数据库服务器 | db01 | 10.0.0.51 | 172.16.1.51 | mysql（慢）mariaDB |
| 08 | 存储服务器 | nfs01 | 10.0.0.31 | 172.16.1.31 | nfs |

{: .sec-pit}

> **注意：** 表中 10.0.0.0/24 与 172.16.1.0/24 都是私有地址段，课堂上把 10.0.0.0/24 当作"外网区"（模拟用户与公网入口）、172.16.1.0/24 当作"内网区"（服务器之间通信）使用。真实生产环境中"外网地址"是运营商分配的公网 IP，内网则保持私有地址即可。
{: .sec-pit}

{: .sec-pit}

### 服务器命名与 IP 规划规范
{: .sec-best}

| 规范项 | 规则 | 示例 |
| --- | --- | --- |
| 命名格式 | 角色缩写 + 两位编号，同角色多台依次递增 | lb01、web02、db01 |
| 角色缩写 | 全局统一，见名知意 | lb（负载均衡）、web、db、nfs、cache、backup、m（管理）、zabbix |
| 环境前缀 | 多环境时加环境标识，避免混淆 | test-web01、prod-web01 |
| 主机名管理 | 全集群统一写入各服务器 `/etc/hosts`，先保证内网互通 | 172.16.1.7 web01 |
| IP 网段划分 | 按角色划分网段或地址段，便于写 ACL 与防火墙策略 | 172.16.1.1-20 给 LB，172.16.1.21-40 给 Web |
| 网关与 DNS | 每个网段固定网关地址，DNS 统一指向内网解析服务 | 网关 172.16.1.1 |
| 地址预留 | 为扩容预留连续地址，不要用到最后几个 | 每段预留 10-20 个空闲地址 |

> **注意：** 命名与 IP 规范的价值要到故障时刻才兑现：告警里写着 "prod-web02 172.16.1.8 磁盘 90%"，任何人都能秒懂是哪台、哪个环境、该干什么。规范是写给自己三个月后看的。
{: .sec-pit}

### 环境划分（开发 / 测试 / 预发 / 生产）
{: .sec-ver}

企业里同一套代码不会直接上生产，通常至少四个环境：

| 环境 | 用途 | 数据特点 | 谁在用 |
| --- | --- | --- | --- |
| 开发环境 dev | 开发自测、联调，随时可破坏重建 | 造假的测试数据，可随时重置 | 开发工程师 |
| 测试环境 test | 功能测试、集成测试、回归 | 构造的边界数据 | 测试工程师 |
| 预发环境 staging（pre） | 上线前最后验证，配置与数据尽量贴近生产 | 生产数据的脱敏副本或仿真数据 | 开发 + 测试 + 运维 |
| 生产环境 prod | 真实业务，任何操作需谨慎 | 真实业务数据，最高保护级别 | 运维管控，按流程变更 |

> **注意：** 三个工程纪律：① 生产数据严禁直接导入开发 / 测试环境（泄露风险），预发可用脱敏后的副本；② 各环境的配置（数据库地址、域名、密钥）必须分离存放，不允许开发环境连生产数据库；③ 代码到生产的流转路径是固定的：dev → test → pre → prod，每一级验证通过才能进下一级，"跳过预发直接上生产"是重大违规。
{: .sec-pit}

> **注意：** 环境划分的根本目的是控制爆炸半径：开发环境随便折腾，坏了重建，十分钟的事；生产环境的每一个操作都要走流程，因为坏了是真金白银。环境之间的隔离做得越彻底，生产出事的概率越低。
{: .sec-pit}

> **注意：** 预发环境是四个里最常被砍掉的一个，理由通常是"成本"；砍掉的代价是配置与数据差异只能到生产上才暴露。资源紧张时宁可缩小预发规模（单机、小数据量），也不要整个砍掉 —— 它验证的是"变更本身"，不是性能。
{: .sec-pit}

### CDN 与 WAF 简述

| 组件 | 全称 | 作用 | 部署位置 |
| --- | --- | --- | --- |
| CDN | Content Delivery Network，内容分发网络 | 把静态资源缓存到离用户最近的边缘节点，加速访问、降低源站压力、隐藏源站 IP | 用户与源站之间 |
| WAF | Web Application Firewall，Web 应用防火墙 | 识别并拦截 SQL 注入、XSS、CC 攻击等恶意流量，只放行正常业务请求 | 通常在 CDN 之后、源站之前 |

> **注意：** 接入顺序建议：用户 → CDN（加速 + 抗流量）→ WAF（清洗恶意请求）→ 源站 LB。CDN 只缓存静态资源，动态请求要配置回源规则；WAF 规则初上线时先用"观察模式"收集误拦，再逐步切换到拦截模式，避免规则太严把正常用户挡在外面。
{: .sec-pit}

> **注意：** CDN 除了加速还兼职抗攻击：CC、扫描这类流量先被边缘节点消化掉，源站看到的就是"干净"流量。这也是生产上"隐藏源站 IP"的意义 —— 域名解析到 CDN，源站只接受 CDN 回源，攻击者摸不到源站就只能打 CDN，而 CDN 恰恰是最抗打的一层。
{: .sec-pit}

### 监控与日志体系概览
{: .sec-sum}

| 体系 | 关注点 | 常见方案 |
| --- | --- | --- |
| 监控 | 服务器基础指标（CPU / 内存 / 磁盘 / 网络）、服务存活（端口 / 进程）、业务指标（订单量 / 错误率） | Zabbix、Prometheus + Grafana |
| 日志 | 集中收集各服务日志、轮转归档、关键字告警、故障追溯 | rsync 统一回传 + ELK 栈检索 |
| 告警 | 分级告警（邮件 / 短信 / IM），告警必须可执行 | Zabbix 触发器 + 告警脚本 |

> **注意：** 监控的价值在"提前发现"：磁盘使用率 80% 就该预警，不要等写满才处理。日志的底线要求是"所有服务器的日志至少有一份异地副本"——这正是 backup 服务器要做的事，日志既是排错依据，也是安全审计的素材。
{: .sec-pit}

> **注意：** 三套体系有个共同的"最小可用起步"：监控先盯存活与磁盘，日志先做集中收集，告警先只发真正需要人处理的事件。一上来就追求大盘与花哨告警，往往监控比业务还先压垮服务器。
{: .sec-pit}

## 模板主机克隆操作
{: .sec-prac}

1. 进行模板机快照拍摄
2. 进行虚拟主机克隆

快照的意义：拍快照等于给模板机存一个"确认可用"的存档点。克隆出来的机器网卡、UUID 改坏了改不回来，直接回滚快照重做，几分钟的事；没快照就得重装系统、重做十项优化。注意快照不等于备份 —— 快照依赖模板机的磁盘文件，模板机磁盘坏了快照一起陪葬，重要数据仍要走备份流程。

**创建链接克隆（学习环境）**

| 优势 | 劣势 |
| --- | --- |
| a 节省物理主机资源 | a 模板主机删除，链接主机也会失效 |
| b 克隆主机效率快 |  |

**创建完整克隆（企业应用）**

| 优势 | 劣势 |
| --- | --- |
| a 模板主机删除，克隆主机依然可以使用 | a 比较消耗物理主机资源 |
|  | b 克隆主机效率低 |

3. 克隆后虚拟主机配置

```bash
# a 修改主机名称
hostnamectl set-hostname backup

# b 修改主机地址
sed -i 's#200#41#g' /etc/sysconfig/network-scripts/ifcfg-eth[01]
grep 41 /etc/sysconfig/network-scripts/ifcfg-eth[01]
sed -i '/UUID/d' /etc/sysconfig/network-scripts/ifcfg-eth[01]
grep UUID /etc/sysconfig/network-scripts/ifcfg-eth[01]
systemctl restart network
```

> **注意：** 这里有个坑：克隆好的主机要一台一台顺序启动、逐台修改，不要同时启动，否则 IP 冲突。
>
> 补充：克隆好的主机无法远程连接时的排查方式：
>
> 1. 利用 ping 方式测试
> 2. 关闭远程连接终端软件重新打开
{: .sec-pit}

> **注意：** `sed -i '/UUID/d'` 删除 UUID 的原因：多台主机携带相同 UUID 时，NetworkManager / udev 会难以区分网卡，可能出现配置错乱、接口名漂移；删除后系统下次启动会重新生成。
{: .sec-pit}

## 备份服务器说明
{: .sec-expl}

备份服务器的作用：

1. **数据备份的服务器**
2. **进行日志统一保存**

日志统一保存的价值常被低估：机器被入侵后，攻击者第一件事往往是清本机日志，日志在备份服务器上另有一份，审计才有据可查；多台机器的日志集中在一处，`grep` 一条命令跨全部服务器找关键字，比逐台登录快得多。

```bash
[root@nfs01 backup]# grep -r "关键字" /backup/
/backup/10.0.0.7_bak/app.log:关键字
```

如何部署搭建备份服务器：**rsync 服务**。

## 什么是 rsync 服务
{: .sec-know}

> Rsync 是一款开源的、快速的、多功能的、可实现**全量**及**增量**的本地或远程数据同步备份的优秀工具。

## rsync 命令的四种用法（1v4）

### a. 本地备份数据（相当于 cp）

```bash
[root@nfs01 backup]# cp /etc/hosts /tmp
[root@nfs01 backup]# ll /tmp/hosts
-rw-r--r-- 1 root root 371 May  6 16:11 /tmp/hosts
[root@nfs01 backup]# rsync /etc/hosts /tmp/host_rsync
[root@nfs01 backup]# ll /tmp/host_rsync
-rw-r--r-- 1 root root 371 May  6 16:12 /tmp/host_rsync
```

### b. 远程备份数据（相当于 scp）

```bash
scp -rp /etc/hosts root@172.16.1.41:/backup
root@172.16.1.41's password:
hosts         100%  371    42.8KB/s   00:00
```

参数说明：

| 参数 | 含义 |
| --- | --- |
| `-r` | 递归复制传输数据 |
| `-p` | 保持文件属性信息不变 |

用 rsync 完成同样的动作：

```bash
[root@nfs01 ~]# rsync -rp /etc/hosts 172.16.1.41:/backup/hosts_rsync
root@172.16.1.41's password:
```

**rsync 远程备份目录的斜杠陷阱：**

```bash
# 备份的目录后面没有 /
[root@nfs01 ~]# rsync -rp /data 172.16.1.41:/backup
root@172.16.1.41's password:
[root@backup ~]# ll /backup
total 0
drwxr-xr-x 2 root root 48 May  6 16:22 data
[root@backup ~]# tree /backup/
/backup/
└── data
    ├── 01.txt
    ├── 02.txt
    └── 03.txt

1 directory, 3 files
```

```bash
# 备份的目录后面有 /
[root@nfs01 ~]# rsync -rp /data/ 172.16.1.41:/backup
root@172.16.1.41's password:
[root@backup ~]# ll /backup
total 0
-rw-r--r-- 1 root root 0 May  6 16:24 01.txt
-rw-r--r-- 1 root root 0 May  6 16:24 02.txt
-rw-r--r-- 1 root root 0 May  6 16:24 03.txt
```

> **注意：** 在使用 rsync 备份目录时：
>
> - 备份目录后面**有** `/` —— `/data/`：只将目录下面的内容进行备份传输
> - 备份目录后面**没有** `/` —— `/data`：会将目录本身以及下面的内容进行传输备份
{: .sec-pit}

### c. 替代删除命令（rm）

```bash
[root@nfs01 ~]# rsync -rp --delete /null/ 172.16.1.41:/backup
root@172.16.1.41's password:
```

`--delete` 实现**无差异同步数据**。

> **注意：** 面试题「有一个存储数据信息的目录，目录中存储了 50G 数据，如何将目录中的数据快速删除？」—— 常规做法是 `rm /目录/* -rf`，也可以用 rsync 无差异同步一个空目录的方式来处理。
{: .sec-pit}

> **注意：** 示例中的 `/null/` 是课堂上用于演示的空目录，实际使用时先创建它（如 `mkdir -p /tmp/null`），把 `/null/` 换成实际路径即可。删除 50G 数据用 `rm` 需要逐文件遍历 inode，耗时很长；rsync 空目录同步是"批量比对后一次性删除"，在特定场景（如清空超大目录）更快，这也是面试题想听的思路。
{: .sec-pit}

### d. 替代查看文件命令（ls）

```bash
[root@backup ~]# ls /etc/hosts
/etc/hosts
[root@backup ~]# rsync /etc/hosts
-rw-r--r--            371 2019/05/06 11:55:22 hosts
```

## rsync 命令语法格式

```text
SYNOPSIS
Local:  rsync [OPTION...] SRC... [DEST]
```

**本地备份数据**

| 字段 | 含义 |
| --- | --- |
| `src` | 要备份的数据信息 |
| `dest` | 备份到什么路径中 |

**远程备份数据（Access via remote shell）**

```bash
Pull: rsync [OPTION...] [USER@]HOST:SRC... [DEST]
```

| 字段 | 含义 |
| --- | --- |
| `[USER@]` | 以什么用户身份拉取数据（默认以当前用户） |
| `HOST` | 指定远程主机 IP 地址或者主机名称 |
| `SRC` | 要拉取的数据信息 |
| `DEST` | 保存到本地的路径信息 |

```bash
Push: rsync [OPTION...] SRC... [USER@]HOST:DEST
```

| 字段 | 含义 |
| --- | --- |
| `SRC` | 本地要进行远程传输备份的数据 |
| `[USER@]` | 以什么用户身份推送数据（默认以当前用户） |
| `HOST` | 指定远程主机的 IP 地址或者主机名称 |
| `DEST` | 保存到远程的路径信息 |

**守护进程方式备份数据（Access via rsync daemon）**

```bash
Pull: rsync [OPTION...] [USER@]HOST::SRC... [DEST]
      rsync [OPTION...] rsync://[USER@]HOST[:PORT]/SRC... [DEST]

Push: rsync [OPTION...] SRC... [USER@]HOST::DEST
      rsync [OPTION...] SRC... rsync://[USER@]HOST[:PORT]/DEST
```

使用守护进程方式的优势：

1. 可以进行一些配置管理
2. 可以进行安全策略管理
3. 可以实现自动传输备份数据

## Linux 系统安装部署服务的通用流程

## 常见错误与排错
{: .sec-ts}

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 克隆机同时启动后 IP 冲突 | 模板机配置未逐台修改 | `ip addr`、`arp -a` | 关闭冲突主机，逐台改 IP 后再启动 |
| 克隆机远程连不上 | IP / 网关未改、UUID 冲突 | `ping 新IP`、`ip addr` | 关机逐台修改配置，删除 UUID 后重启 |
| sudo 修改后所有用户无法提权 | sudoers 语法错误 | `visudo -c` | 用单用户模式或救援环境修复语法 |
| `systemctl restart network` 后失联 | 网卡配置写错（IP / 掩码 / 网关） | 保存当前会话再操作 | 先在控制台确认配置，或逐字段修改 |
| yum 安装软件报错 | yum 源配置错误或失效 | `yum repolist` | 重新配置可用镜像源，检查网络 |
| hosts 配错导致服务互调失败 | 主机名与 IP 映射错误 | `ping 主机名`、`getent hosts 主机名` | 全集群统一核对 `/etc/hosts` |

> **注意：** 生产上栽过最多的就是 hosts 这一行：换机器改了 IP 没同步 hosts，服务之间还在连旧地址，表象五花八门（超时、连错库、日志里全是旧 IP），最后对一遍 hosts 才定位。凡是"服务互连"类故障，先 ping 主机名验证映射。
{: .sec-pit}

## 现代环境补充
{: .sec-ext}

CentOS Linux 7 已于 2024 年 6 月结束维护（EOL），新模板机建议基于 Rocky Linux / AlmaLinux / CentOS Stream 制作，对应变化：

| 项目 | CentOS 7 旧做法 | Rocky / AlmaLinux 新做法 |
| --- | --- | --- |
| 包管理 | `yum install` | `dnf install`（`yum` 兼容软链仍可用） |
| 软件源 | `CentOS-Base.repo` | Rocky / AlmaLinux 对应源 + EPEL，配置方式相同 |
| 防火墙 | 学习环境直接 `stop firewalld` | 保持运行，用 `firewall-cmd` 放行指定端口 |
| 时间同步 | `ntpdate` 写 crontab | `dnf install chrony` + `timedatectl set-ntp true`（ntpdate 已废弃） |
| 网络服务 | `systemctl restart network` | NetworkManager 接管：`nmcli con reload` / `nmcli con up` |
| 主机名 | `hostnamectl set-hostname` | 相同，`hostnamectl` 依然适用 |

> **注意：** 模板机的定位是"可复现的基线"：优化项越标准化，后续用 Ansible 批量下发越省力。建议把十项优化整理成一份检查清单，每做完一项打一个勾，避免漏配。
{: .sec-pit}

> **注意：** 学习环境的旧命令与生产环境的新做法，两套都要会：面试问的是原理（ntpdate 为什么被 chrony 替代、netstat 为什么被 ss 替代），落地看的是企业现状。
{: .sec-pit}

## 小结
{: .sec-sum}

1. 一套中小规模架构由防火墙、负载均衡、web、数据库、存储、备份、缓存、批量管理等角色构成，每个角色都要考虑单点问题与对应的高可用方案。
2. 架构演进路径：单机 → LNMT 分离 → 集群化 → 分布式；每上一级都是用更大复杂度换更大的容量与可用性，选型要匹配当前业务规模。
3. 架构规划先固定主机名与内外网 IP（`172.16.1.x` 内网 + `10.0.0.x` 外网），命名按"角色缩写 + 编号"，按角色预留地址段，学习阶段先"把路走通，再进行变通"。
4. 模板机优化十项：hosts、yum 源、SELinux、防火墙、sudo 提权、字符集、时间同步、文件描述符、常用软件、SSH 连接优化。
5. 克隆优先用链接克隆（省资源、速度快），克隆后逐台改主机名、改 IP、删除 UUID 再重启网络；同时启动必然 IP 冲突。
6. rsync 命令"1v4"：本地备份（cp）、远程备份（scp）、替代删除（rm）、替代查看（ls）；备份目录末尾**有无 `/`** 决定备份的是目录内容还是目录本身。
7. rsync 三种工作模式：本地、远程 shell、守护进程；守护进程模式可以做配置管理、安全策略和自动传输，是生产环境的主要用法。
8. 环境划分至少四套（dev / test / pre / prod），生产数据脱敏后才能向下流动，配置必须按环境分离。
9. 部署任何服务都按五步走：装软件 → 写配置 → 建环境 → 起服务 → 做测试。

## 自测题
{: .sec-prac}

1. 画出（文字描述）一套 LB + Web + DB + 缓存 + 存储架构的请求流向，并说明每层解决什么问题。
2. 负载均衡和数据库的单点分别用什么方案解决？存储服务的单点有哪两种思路？
3. 模板机克隆后为什么要删除网卡配置文件里的 UUID？多台机器携带相同 UUID 会怎样？
4. `rsync -av /data/ backup:/backup/` 与 `rsync -av /data backup:/backup/` 在 backup 服务器上的结果有什么区别？
5. 公司的数据备份有哪三类常见方式？本节项目采用哪一种？

> **答案：** 1）用户 → CDN/WAF → 防火墙 → LB（keepalived VIP + nginx）→ Web 集群 → Redis 缓存 / MySQL 主从 / NFS 存储；LB 解决流量分发与 Web 单点，缓存挡数据库读压力，主从解决数据库单点，NFS 解决多 Web 间文件共享，备份服务器统一收数据。2）负载均衡用 keepalived（VIP 自动漂移），数据库用 MHA（主从高可用）；存储用 keepalived 实现双写 / 共享存储的高可用，或改用分布式存储。3）UUID 是网卡唯一标识，克隆机携带相同 UUID 会让系统无法区分网卡，导致配置错乱、接口漂移；删除后系统重启时重新生成唯一 UUID。4）`/data/` 只传目录内容（文件直接落到 backup 下），`/data` 会连目录本身一起传（backup 下出现 data/ 子目录）。5）三类：开源软件备份（rsync）、企业网盘 / 公有云对象存储、自建备份存储（两地三中心）；本项目采用 rsync 自建方案。
