## 4.1 先来看变量
{: .sec-expl}

### 4.1.1 声明、定义、初始化：三件事，别混成一件事
{: .sec-know}

口语里这仨词经常混着用，但标准眼里是三件完全不同的事：

- **声明（declaration）**：把名字引入作用域，跟编译器说"有这么个东西、类型是这样"。同一个声明可以写无数遍。
- **定义（definition）**：让实体真正落地——变量分配存储、函数生成代码体。一个实体整个程序里**只能定义一次**（ODR，One Definition Rule 那套）。定义天然也是声明。
- **初始化（initialization）**：对象生命周期一开始，给它第一个值。它**不等于**赋值。

`extern` 是捅破这层窗户纸的钥匙：

```cpp
extern int g_count;      // 声明：不分配存储，不能在这里写初始化器
int g_count = 0;         // 定义：分配存储 + 初始化
extern int g_count = 0;  // 带初始化器的 extern 也是定义（extern 被"压过去"了）
```

最容易被看漏的是第三条：`extern` 顶多算个"建议外部链接"，可一旦你写了初始化器，这条语句当场变成定义——链接器眼里就有两个 `g_count` 了。

下面这张判定表，建议直接刻进脑子：

| 写法 | 是声明还是定义 | 是否分配存储 |
| --- | --- | --- |
| `extern int x;` | 声明 | 否 |
| `int x;`（命名空间作用域） | 定义 + 零初始化 | 是 |
| `int x = 5;` | 定义 + 初始化 | 是 |
| `extern int x = 5;` | 定义 + 初始化 | 是 |
| `int f();` | 声明（函数原型） | 否 |
| `int f() { return 1; }` | 定义 | 是 |
| `struct S;` | 声明（不完整类型） | 否 |
| `struct S { int a; };` | 定义 | 否（类型不占存储） |
| `typedef int T;` / `using T = int;` | 声明（别名，不是新类型） | 否 |

> **坑：** `extern int x;` 塞进函数体里居然也是合法的，但千万别这么干。块作用域里的 extern 声明会让读代码的人以为它是个局部变量，其实它是全局的——更糟的是要是同一个 TU 里已经有个同名的局部变量，行为就变得谁也看不懂了。
{: .sec-pit}

跨 TU 的玩法就这么简单：a.cpp 里 `int g_counter = 100;`（定义），b.cpp 里 `extern int g_counter;`（声明），俩文件一起链。要是把 b.cpp 那个 `extern` 去了，链接阶段直接甩你一句 "multiple definition of g_counter"——这比什么理论都直观地证明了"定义才分配存储"。

```cpp
// single_tu.cpp —— 需要 -std=c++20
#include <iostream>

extern int g_counter;                // 声明：不分配存储，可以出现多次
extern int g_counter;                // 重复声明是合法的
int g_counter = 100;                 // 定义：在这里补上，整个程序只有这一处

int main() {
    std::cout << "g_counter = " << g_counter << "\n";
    g_counter += 1;
    std::cout << "after ++  = " << g_counter << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra single_tu.cpp -o st && ./st
```

```text
g_counter = 100
after ++  = 101
```

#### 辨析：初始化 与 赋值
{: .sec-iv}

| 维度 | 初始化 | 赋值 |
| --- | --- | --- |
| 时机 | 对象生命周期开始的那一刻 | 对象已经存在之后 |
| 调用的函数 | 构造函数 | `operator=` |
| 内置类型 | 可以省略，代价是不确定值 | 必须先有对象 |
| `const` 对象 | 必须初始化 | 不能赋值 |

`const int x;` 写在函数里直接编译不过（const 对象必须有初始化器），而 `const int x = 1; x = 2;` 第二句也是错。这俩错误压根不是一回事。

### 4.1.2 四种初始化形式：一场持续二十年的大乱斗
{: .sec-know}

C++ 的初始化语法是被历史一层层堆出来的。现在算上默认初始化，一共五种带初始化器的写法（其实默认初始化是单独一类），它们之间的差别绝不是"你爱用哪种风格"那么轻描淡写：

| 形式 | 写法 | 关键语义 |
| --- | --- | --- |
| 默认初始化 | `int x;` `Widget w;` | 内置类型在块作用域里**不初始化**；类类型调用默认构造函数 |
| 拷贝初始化 | `int x = 1;` `std::string s = "hi";` | 不考虑 `explicit` 构造函数；语义上"先造临时再拷贝"（C++17 起通常被消除） |
| 直接初始化 | `int x(1);` `Widget w(1, 2);` | 考虑 `explicit` 构造函数；直接调匹配的构造函数 |
| 列表初始化 | `int x{1};` `int x = {1};` `Widget w{1, 2};` | 禁止窄化转换；优先匹配 `std::initializer_list` 构造函数 |
| 值初始化 | `int x{};` `int x = {};` `int()` | 内置类型清零；类类型走默认构造 |

为什么非得整出这么多种？因为每一种都是某个历史阶段，为了补前一种的窟窿才加进来的：

- 拷贝初始化是从 C 继承下来的；
- 直接初始化为了让构造函数能带多个参数、还能用 `explicit`；
- 列表初始化（C++11）是想把聚合类型和类类型的写法统一，顺手堵死窄化转换这个大洞；
- 值初始化给"我就想要个零值"一个正经语法（C++03 之前只能吭哧写 `int x = int();`）。

```cpp
// init_forms.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

struct Widget {
    int a;
    std::string name;
    explicit Widget(int a_) : a(a_), name("default") {}
    Widget(int a_, const std::string& n) : a(a_), name(n) {}
};

int main() {
    int a = 1;              // 拷贝初始化
    int b(2);               // 直接初始化
    int c{3};               // 列表初始化
    int d{};                // 值初始化 → 0
    int e = int();          // 值初始化的老写法 → 0
    std::cout << "a=" << a << " b=" << b << " c=" << c
              << " d=" << d << " e=" << e << "\n";

    Widget w1(7);                    // OK：直接初始化可以用 explicit
    Widget w2{7, "named"};           // OK：两个参数的构造函数
    // Widget w3 = 7;                // 错误：explicit 构造不参与拷贝初始化
    std::cout << w1.a << " " << w1.name << " / "
              << w2.a << " " << w2.name << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra init_forms.cpp -o init_forms && ./init_forms
```

```text
a=1 b=2 c=3 d=0 e=0
7 default / 7 named
```

默认初始化留下的是**不确定值**：块作用域里 `int local_int;` 你敢读它就是一个 UB（GCC 的 `-Wmaybe-uninitialized` 有时候只在 `-O2` 往上才报得准）。最典型的自欺就是那句"我跑了好几遍它一直是 0"——换套优化级别、换个编译器、甚至换个寄存器分配，值立刻就变。

> **坑：** 换成类类型照样逃不掉。`struct Plain { int value; }; Plain p;` 里的 `value` 照样是不确定值，读它也是 UB——类类型只是保证"会调默认构造函数"，可那个隐式默认构造函数对内置类型成员**什么都不做**。就两条活路：要么成员声明写成 `int value{};`，要么永远老老实实 `Plain p{};`。差的就是那对花括号。
{: .sec-pit}

### 4.1.3 列表初始化与窄化：这条规则真的救命
{: .sec-know}

`{}` 比 `()`/`=` 最值钱的一点差异就在这：**列表初始化直接禁止窄化转换（narrowing conversion）**。编译器在这儿不是"好心提醒一下"，而是直接甩编译错误。

什么算窄化？标准在 C++20 [dcl.init.list] 里列了四种：

1. 浮点 → 整型（**没有任何例外**，哪怕值是 `1.0`）；
2. `long double` → `double`/`float`，或 `double` → `float`，除非源是常量表达式且转换后的值能被目标类型表示；
3. 整型/无作用域枚举 → 浮点，除非是常量表达式且能被目标类型精确表示；
4. 整型/枚举 → 另一个整型，除非是常量表达式且其值能被目标类型完整表示。

```cpp
// narrowing.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    int  ok1{42};        // OK：常量 42 装得下
    char ok2{65};        // OK：65 在 char 的取值范围内
    double ok3{1};       // OK：int 常量 1 能被 double 精确表示
    unsigned ok4{5u};    // OK：同类型

    // int  bad1{3.14};     // 错误：浮点 → 整型，一律算窄化
    // char bad2{300};      // 错误：300 装不进 8 位 char
    // unsigned bad3{-1};   // 错误：-1 无法被 unsigned 表示
    // int  bad4{2.0f};     // 错误：同上，float 也算浮点
    // float bad5{1.0L};    // 错误：long double → float

    int n = 300;
    // char bad6{n};        // 错误：n 不是常量表达式，编译器无法证明它装得下

    std::cout << ok1 << " " << ok2 << " " << ok3 << " " << ok4 << "\n";

    // 对照：换成 () 或 = 就全都不报错，值被悄悄截断
    char silent1 = 300;         // 悄悄回绕：300 mod 256 = 44（C++20 起这是标准规定的结果）
    int  silent2 = 3.14;        // 直接丢掉小数 → 3
    std::cout << static_cast<int>(silent1) << " " << silent2 << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra narrowing.cpp -o narrowing && ./narrowing
```

```text
42 A 1 5
44 3
```

第二行那个 `44`，就是 `300` 塞进 8 位 `char` 的结果（300 mod 256 = 44）。C++20 起这事儿才被正式定死：**整型转有符号整型而目标装不下时，结果是模 2^n 同余那个唯一值**（P0907 把补码拍板之后顺手把它也定了）；C++20 之前是实践定义。但不管哪个版本，它都**一声不吭**地过了编译——你换成 `char silent1{300};`，连编译都别想过去。

这条规则凭什么值钱？它把一整类"类型悄悄缩水"的 bug 从运行期硬提到了编译期。我自己就栽过：一个 `int` 往 `int16_t` 里塞，在 x86 上跑了一年没事，换到 ARM 上才偶尔算错——就因为 `{}` 没用上。凡是写过跨平台序列化的人，都懂这种 bug 有多恶心：它不崩，只是偶尔算错个数。

#### 现代写法：默认用 `{}`
{: .sec-ext}

C++11 之后主流写法（Core Guidelines ES.23 也这么建议）就是**默认用 `{}`**：

- 它能用于任何类型（内置、聚合、带构造函数的类都统一）；
- 它禁止窄化；
- 它不会撞上最令人沮丧的解析（见 4.1.5）；
- 空 `{}` 就是值初始化，语义明确。

那啥时候**别**用 `{}`？就两类情况：

1. 明确想要"调用那个非 initializer_list 构造函数"时——见 4.1.4，这是 `vector<int> v(10)` 仍然存在的理由；
2. 类型有 `std::initializer_list` 构造函数且你要的语义是"显式指定容量/重复次数"时。

### 4.1.4 `initializer_list` 优先级：`v(10)` 与 `v{10}` 这个经典陷阱
{: .sec-warn}

列表初始化有条优先规则：**只要类有 `std::initializer_list` 构造函数，列表初始化就优先去试它；只有它走不通了才回退到普通构造函数。** 这条规则造出的后果，就是那个年年必考的题：

```cpp
// init_list_priority.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <vector>

int main() {
    std::vector<int> v1(10);              // 10 个元素，每个都是 0
    std::vector<int> v2{10};              // 1 个元素，值是 10
    std::vector<int> v3(10, 7);           // 10 个元素，每个都是 7
    std::vector<int> v4{10, 7};           // 2 个元素：10 和 7

    // 更阴的一个：string 不能从 int 构造，
    // initializer_list<string> 不可行 → 回退到 vector(size_type)
    std::vector<std::string> v5{10};      // 10 个空串，不是 1 个 "10"

    std::cout << "v1: size=" << v1.size() << " first=" << v1[0] << "\n";
    std::cout << "v2: size=" << v2.size() << " first=" << v2[0] << "\n";
    std::cout << "v3: size=" << v3.size() << " first=" << v3[0] << "\n";
    std::cout << "v4: size=" << v4.size() << " [0]=" << v4[0] << " [1]=" << v4[1] << "\n";
    std::cout << "v5: size=" << v5.size() << " empty=" << v5[0].empty() << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra init_list_priority.cpp -o ilp && ./ilp
```

```text
v1: size=10 first=0
v2: size=1 first=10
v3: size=10 first=7
v4: size=2 [0]=10 [1]=7
v5: size=10 empty=1
```

同一个 `10`，套圆括号是"个数"，套花括号是"元素"。更绕的是 `v5` 那行：`std::vector<std::string> v{10}` 又变回"个数"了——因为 `10` 压根转不成 `std::string`，`initializer_list<string>` 那条路直接走不通。

自己写类的时候这事儿是双向的：你这个类只要带了 `std::initializer_list` 构造函数，`Buf b{4}` 就永远先奔它去，你写个 `explicit Buf(std::size_t)` 也拦不住——`{}` 的优先级规则压在 `explicit` 之前生效。

> **坑：** 给一个**已经存在**的类再加个 `initializer_list` 构造函数，是破坏性改动。原本写 `Buf b{4}` 的调用方会神不知鬼不觉地改了语义，而编译期啥提示都没有。设计容器类时一开始就得把所有重载想明白；真要两路语义，用带标签的构造函数（tag dispatch）比赌 `{}` 的优先级靠谱得多。
{: .sec-pit}

### 4.1.5 最令人沮丧的解析（Most Vexing Parse）
{: .sec-warn}

你写 `Time t();` 本想默认构造个对象？标准冷冷地告诉你：这是一条**函数声明**——声明了个叫 `t` 的无参函数，返回 `Time`。这毛病叫 Most Vexing Parse，根子来自一条更底层的语言规则：**凡是能被解析成声明的，就一律按声明解析**。

```cpp
// mvp.cpp —— 需要 -std=c++20
#include <iostream>
#include <type_traits>

struct Time {
    int hour{0};
    Time() { std::cout << "Time()\n"; }
    explicit Time(int h) : hour(h) { std::cout << "Time(int)\n"; }
};

Time t4();                 // 命名空间作用域：声明函数 t4 —— 不是对象
Time t4() {                // 它的定义
    std::cout << "t4() called\n";
    return Time{23};
}

int main() {
    Time t1;               // 默认构造一个对象
    Time t2{};             // C++11 起推荐：值初始化 / 默认构造，绝不会被解析成函数
    Time t3(8);            // 直接初始化
    // Time t4_2();        // 如果这么写，它又是函数声明

    static_assert(std::is_same_v<decltype(t4), Time()>,
                  "t4 的类型是函数类型 Time()，不是 Time");

    Time obj = t4();       // 真的去调用它 —— 这行能跑通就是最硬的证据
    std::cout << "t1.hour=" << t1.hour << " obj.hour=" << obj.hour << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra mvp.cpp -o mvp && ./mvp
```

```text
Time()
Time()
Time(int)
t4() called
Time(int)
t1.hour=0 obj.hour=23
```

那条 `static_assert` 是编译器盖过章的：`decltype(t4)` 的类型是 `Time()`（一个函数类型），不是 `Time` 对象。

MVP 还有几个变体，建议都认个脸熟：

| 写法 | 实际含义 | 修法 |
| --- | --- | --- |
| `Time t();` | 函数声明 | `Time t;` 或 `Time t{};` |
| `Time t(Widget());` | 函数声明：参数类型是"返回 Widget 的无参函数" | `Time t{Widget{}};` 或 `Time t((Widget()));` |
| `std::vector<int> v(std::istream_iterator<int>(is), std::istream_iterator<int>());` | 函数声明 | 两个实参都用 `{}`，或给第一个加一层括号 |
| `std::mutex m();` | 函数声明 | `std::mutex m;` |

> **坑：** C++11 之后 `{}` 能救大部分场，但它救不了"你本来就想调那个 `initializer_list` 构造函数"的场（回头看 4.1.4）。另外 `auto t = Time();` 也是安全的——等号右边是表达式上下文，不会被当成声明。
{: .sec-pit}

### 4.1.6 静态对象的两段式初始化：零初始化 + 动态初始化
{: .sec-know}

带静态存储期的变量——全局的、命名空间作用域的、类的静态成员、函数里的 `static` 局部、`thread_local`——都不是"一下子"初始化完的。标准硬把它拆成两段：

1. **静态初始化**：先对所有静态对象做**零初始化**（把内存清零，不放任何代码）；如果初始化器是常量表达式，则进一步做**常量初始化**（直接在数据段写死初值，编译期完成）。
2. **动态初始化**：初始化器非常量表达式时，在运行期执行代码（调用构造函数、调用函数、执行 lambda）。

几个关键结论：

- 零初始化**先于**所有其他初始化发生，无一例外；
- 常量初始化与动态初始化在概念上同属"第二小段"，但前者在编译期就定了，后者要跑代码；- 同一个翻译单元（TU）内部，动态初始化按**定义出现的顺序**进行；
- **跨 TU 的动态初始化顺序未指定**——这是下一节的灾难源头。

```cpp
// static_init.cpp —— 需要 -std=c++20
#include <iostream>

int g_zero;                                                  // 零初始化
int g_const = 42;                                            // 常量初始化（编译期）
int g_dyn = [] { std::cout << "  [dyn] g_dyn 初始化\n"; return 7; }();   // 动态初始化

struct Tracer {
    const char* name;
    explicit Tracer(const char* n) : name(n) { std::cout << "  [dyn] ctor " << name << "\n"; }
};

Tracer g_tracer{"global"};                                   // 动态初始化（要调构造）

int main() {
    std::cout << "[main] 开始\n";
    std::cout << g_zero << " " << g_const << " " << g_dyn << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra static_init.cpp -o si && ./si
```

```text
  [dyn] g_dyn 初始化
  [dyn] ctor global
[main] 开始
0 42 7
```

盯着输出顺序看：`g_dyn` 和 `g_tracer` 的动态初始化在 `main` 之前就跑完了，而且按定义顺序来；而 `g_zero`、`g_const` 压根没产生任何运行期动作——它们在可执行文件的数据段里早就是 0 和 42 了。

要判断"这个静态变量到底走的哪一段"，唯一权威的标准就是——初始化器是不是常量表达式，而不是你拿 `nm` 看它落在哪个段。想验证，用 `constinit`（见 4.1.7）：能编过就说明是常量初始化。

### 4.1.7 静态初始化顺序惨剧（Static Initialization Order Fiasco）
{: .sec-warn}

上一条规则直接捅出来的后果：要是某个 TU 里的全局变量，在初始化时**去读了另一个 TU 里的全局变量**，那对方可能还没被动态初始化。你读到的就是零初始化的结果——不报错、不崩，就是值不对。

```cpp
// siof_a.cpp —— 需要 -std=c++20
extern int g_seed;                 // 定义在 siof_b.cpp
int g_value = g_seed * 2;          // 动态初始化：跨 TU 依赖

#include <iostream>
void report_a() { std::cout << "g_value = " << g_value << "\n"; }
void report_b();
int main() { report_b(); report_a(); }
```

```cpp
// siof_b.cpp —— 需要 -std=c++20
#include <iostream>
int g_seed = 21;                   // 定义在 b，动态初始化时机与 a 无关
void report_b() { std::cout << "g_seed  = " << g_seed << "\n"; }
```

```bash
g++ -std=c++20 -Wall -Wextra siof_a.cpp siof_b.cpp -o siof && ./siof
g++ -std=c++20 -Wall -Wextra siof_b.cpp siof_a.cpp -o siof2 && ./siof2
```

```text
# 两种链接顺序都可能给出下面任一种结果，取决于实现：
g_seed  = 21
g_value = 42     ← 侥幸正确
# 或者：
g_seed  = 21
g_value = 0      ← 顺序反了，读到零初始化的值
```

标准对跨 TU 的动态初始化顺序只撂下一句"未指定"，实现层面通常取决于链接顺序——于是同一个程序换个链接参数，"对"就能变"错"。这类 bug 的德行是：本地跑得好好的，上 CI 就挂；Debug 没事，Release 就翻车。我线上就撞过一回——一个全局 logger 依赖另一个全局配置，Debug 下顺序恰好对，发到 Release 就初始化成了空指针，查了半天才定位到 SIOF。

#### 修复方案一：惰性局部静态（Magic Static）
{: .sec-best}

把全局变量换成"返回引用的函数"，对象等到函数第一次被调用时才构造。这么一来依赖顺序由调用顺序说了算，而调用顺序是你自己掌握的：

```cpp
// magic_static.cpp —— 需要 -std=c++20
#include <chrono>
#include <iostream>
#include <thread>
#include <vector>

int& seed() {
    static int s = 21;             // 第一次调用 seed() 时才初始化
    return s;
}

int& value() {
    static int v = seed() * 2;     // 调 seed() 时它一定已经初始化过了
    return v;
}

struct Heavy {
    int value;
    Heavy() {
        std::this_thread::sleep_for(std::chrono::milliseconds(200));  // 故意慢
        value = 42;
        std::cout << "Heavy 构造了一次\n";
    }
};

Heavy& instance() {
    static Heavy h;               // C++11 起：初始化只发生一次，且线程安全
    return h;
}

int main() {
    std::cout << seed() << " " << value() << "\n";   // 一定是 21 42

    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i) {
        ts.emplace_back([] { std::cout << instance().value << "\n"; });
    }
    for (auto& t : ts) { t.join(); }
}
```

```bash
g++ -std=c++20 -Wall -Wextra magic_static.cpp -o ms -pthread && ./ms
```

```text
21 42
Heavy 构造了一次
42
42
42
42
```

这就是 Magic Static / Construct On First Use 那套惯用法：依赖顺序交给调用顺序，谁先调谁先构造，跨 TU 的顺序问题直接没了。C++11 起它白送一个极重要的保证——**函数内静态变量的初始化是线程安全的**，四个线程并发首调，"构造了一次"只出现一回（四个 42 的打印顺序看线程调度脸色，不作保证）。Linux 上别忘了带 `-pthread`。

> **坑：** Magic Static 还有俩残余问题。一是**析构顺序**：这些对象在 `main` 之后按构造的逆序析构，要是析构函数里又去碰另一个已经被析构的全局对象，照样是灾难——跨 TU 的析构顺序同样未指定。二是**递归重入**：在 `Heavy` 的构造函数里直接或间接地再调 `instance()`，是 UB（标准原话：初始化完成之前从初始化过程内部控制流再次进入该声明，行为未定义）。工程上的兜底：让这种单例**干脆不析构**（用 `static Heavy* p = new Heavy;` 或函数内 `static` 的 `std::unique_ptr`/`std::optional`），或者干脆要求它们的析构函数啥也不干。
{: .sec-pit}

#### 修复方案二：`constinit`（C++20）把问题消灭在编译期
{: .sec-ext}

`constinit`（C++20）断言一个静态存储期的变量是**常量初始化**的——说白了就是它压根没有动态初始化这一步。没有动态初始化，自然就不可能卷进顺序惨剧：

```cpp
// constinit_demo.cpp —— 需要 -std=c++20
#include <iostream>

constinit int g_seed = 21;                 // OK：常量初始化

struct Point {
    int x;
    int y;
    constexpr Point(int a, int b) : x(a), y(b) {}
};
constinit Point g_origin{0, 0};            // OK：constexpr 构造函数 → 常量初始化

int runtime_value() { return 7; }
// constinit int g_bad = runtime_value();  // 编译错误：不是常量初始化

int main() {
    g_seed = 99;                           // constinit 不添加 const，可以改
    std::cout << g_seed << " " << g_origin.x << "," << g_origin.y << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra constinit_demo.cpp -o ci && ./ci
```

```text
99 0,0
```

`constinit` 就一个作用：把"这个静态变量到底走不走动态初始化"变成一句**编译期就能查的承诺**。它不隐含 `const`、也不隐含 `constexpr`——上面 `g_seed = 99;` 就是证据。想同时又要常量性又要编译期求值，写 `constinit const int` 或 `constexpr`（后者自带常量初始化）。

### 4.1.8 聚合初始化与指派初始化器
{: .sec-know}

聚合类型（没有用户提供的构造函数、没有私有/保护的非静态成员、没有虚函数和虚/私有基类）可以用花括号按成员声明顺序初始化。C++20 又从 C99 那儿借来了**指派初始化器**（designated initializer），能按名字给值：

```cpp
// aggregate_init.cpp —— 需要 -std=c++20
#include <iostream>
#include <string_view>

struct Config {
    int retries;
    double timeout;
    std::string_view name;
};

int main() {
    Config a{3, 2.5, "default"};                             // 聚合初始化：按声明顺序
    Config b{.retries = 5, .timeout = 0.0, .name = "lazy"};  // C++20 指派：全部按名字给值
    Config c{.retries = 1};                                  // 省掉的成员零初始化

    // Config d{.name = "x", .retries = 1};                  // 错误：必须按成员声明顺序写
    // Config e{.retries = 1, 2.5};                          // 错误：不能混用指派和顺序写法

    std::cout << a.retries << " " << a.timeout << " [" << a.name << "]\n";
    std::cout << b.retries << " " << b.timeout << " [" << b.name << "]\n";
    std::cout << c.retries << " " << c.timeout << " [" << c.name << "]\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra aggregate_init.cpp -o ai && ./ai
```

```text
3 2.5 [default]
5 0 [lazy]
1 0 []
```

指派初始化器最大的价值是自文档化：调用方把"哪个值给哪个成员"明写在代码里，别人要是改了成员顺序或者插了个新成员，编译器直接报错，而不是让值悄悄错位——这是 `Config cfg{5, 2.5, "x"}` 那种纯位置写法给不了的。两条限制记牢就行：**必须按声明顺序写，不能中途从指派切回位置写法。**

> **坑：** 给聚合类型**加一个构造函数**，它立刻就不是聚合了，所有调用方的 `Config c{...}` 语义瞬间变成构造函数重载决议。这也是"要不要给结构体加构造函数"这个决定里藏着的隐性成本。
{: .sec-pit}

## 4.2 变量的作用域
{: .sec-expl}

### 4.2.1 五种作用域：决定"谁看得见"
{: .sec-know}

作用域（scope）就是一个名字能被看见的范围。C++ 拢共五种：

| 作用域 | 从哪到哪 | 典型例子 |
| --- | --- | --- |
| 块作用域 | 从声明点到所在 `{}` 结束 | 函数体里的局部变量、`if`/`for` 里的变量、函数参数 |
| 函数作用域 | 整个函数体 | 只有标签（`goto` 用的 `label:`） |
| 函数原型作用域 | 函数声明的形参表内 | `void f(int n, int a[n]);` 里的 `n` |
| 命名空间作用域 | 从声明点到命名空间结束 | 全局变量、命名空间里的类型和函数 |
| 类作用域 | 整个类定义及其成员函数体 | 成员变量、成员函数、嵌套类型 |

"块作用域从**声明点**才开始"这条得刻住：`void f() { /* 这里还看不见 x */ int x = 1; std::cout << x; }`。类作用域是唯一的例外——成员函数体里能用稍后才声明的成员，因为类体会被完整收集一遍后再统一处理。

### 4.2.2 名字隐藏：`::` 是你最后的退路
{: .sec-know}

内层作用域的同名声明会把外层**所有**同名实体都盖住。这里有个反直觉的地方：隐藏是按**名字**来的，不是按签名——所以派生类里只要写一个同名函数，基类的**所有**重载全给藏没了（解法是 `using Base::f;`）。

```cpp
// scope_hiding.cpp —— 需要 -std=c++20
#include <iostream>

int g = 1;                       // 全局命名空间作用域
namespace ns { int g = 2; }      // 命名空间作用域

struct S {
    static int g;                // 类作用域
    void show() const;
};
int S::g = 3;

void S::show() const {
    int g = 4;                   // 块作用域：把上面三个全藏了
    std::cout << "局部 g    = " << g << "\n";
    std::cout << "类   S::g = " << S::g << "\n";
    std::cout << "命名 ns::g= " << ns::g << "\n";
    std::cout << "全局  ::g = " << ::g << "\n";
}

int main() {
    S s;
    s.show();
}
```

```bash
g++ -std=c++20 -Wall -Wextra scope_hiding.cpp -o sh && ./sh
```

```text
局部 g    = 4
类   S::g = 3
命名 ns::g= 2
全局  ::g = 1
```

`::g` 里那个空着的前缀表示"全局命名空间"，这是唯一能穿透所有隐藏的写法。

> **坑：** 局部变量把成员变量藏起来，编译器默认是不提醒的（`-Wshadow` 不在 `-Wall -Wextra` 里，得自己显式开）。构造函数里写 `Widget(int count) : count(count) {}` 能正常工作，可要是写成 `Widget(int count) { count = count; }` 那就是自赋值——形参把成员盖住了。要么用 `this->count = count;`，要么老老实实给成员加个后缀下划线 `count_`。
{: .sec-pit}

### 4.2.3 存储期与生命周期：四个家族
{: .sec-know}

作用域管的是"能不能看见"，存储期管的是"活多久"。这俩经常被混为一谈，其实彼此独立——一个块作用域里的变量完全可以带静态存储期（函数里的 `static` 就是）。

| 存储期 | 关键字/来源 | 生命周期 | 初始化时机 |
| --- | --- | --- | --- |
| 自动（automatic） | 块作用域的普通变量 | 到所在块结束 | 每次执行到声明点 |
| 静态（static） | 命名空间作用域变量、`static` 局部、类的静态成员 | 到程序结束 | main 之前（或首次使用时） |
| 线程（thread） | `thread_local`（C++11） | 到线程结束 | 线程开始时，或首次使用时 |
| 动态（dynamic） | `new` / `delete`、智能指针 | 到你显式释放 | `new` 的那一刻 |

生命周期（lifetime）比存储期还要再细一层：对象从**初始化完成**起活，到**析构开始**为止。对类类型来说，构造函数要是抛了异常，意味着它的生命周期压根没开始（不过存储已经分出去了，而且会被自动回收）。

```cpp
// lifetime_demo.cpp —— 需要 -std=c++20
#include <iostream>

struct Tracer {
    const char* name;
    explicit Tracer(const char* n) : name(n) { std::cout << "  ctor " << name << "\n"; }
    ~Tracer() { std::cout << "  dtor " << name << "\n"; }
};

Tracer g{"global(static)"};        // 静态存储期：main 之前构造，main 之后析构

void func() {
    static Tracer s{"func static"}; // 静态存储期，但只在第一次调用时构造
    Tracer a{"func automatic"};     // 自动存储期：每次调用都构造/析构
}

int main() {
    std::cout << "[main 开始]\n";
    func();
    std::cout << "[第一次调用结束]\n";
    func();
    std::cout << "[main 结束]\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra lifetime_demo.cpp -o ld && ./ld
```

```text
  ctor global(static)
[main 开始]
  ctor func static
  ctor func automatic
  dtor func automatic
[第一次调用结束]
  ctor func automatic
  dtor func automatic
[main 结束]
  dtor func static
  dtor global(static)
```

`func static` 只在第一次调用时构造，还得等到 `main` 之后才析构——这就是"块作用域 + 静态存储期"叠在一起的效果。

### 4.2.4 生命周期陷阱：悬垂引用和悬垂指针
{: .sec-warn}

作用域能挡住编译期"看不见"的问题，挡不住运行期"对象已经死透了"。两个最常见的写法：

```cpp
int& bad_local() {
    int x = 42;
    return x;                       // 返回局部变量的引用 → 悬垂
}

const std::string& bad_temp() {
    return std::string("tmp");      // 返回临时对象的引用 → 悬垂（生命周期延长不适用）
}
```

GCC 对这两类会给 `-Wreturn-local-addr` 警告（在 `-Wall` 里）。真正要命的是编译器看不出来的那些：把引用存进成员、把指针塞进全局容器、跨线程传栈上对象的地址——这些都安安静静过了编译，然后在某个八竿子打不着的地方崩。

规则其实就一句：**引用和指针的寿命必须短于被引用对象的寿命**。栈对象往外传，一律按值传（`std::string` 按值返回会被移动或 NRVO，这点代价远比你想象的便宜）。

### 4.2.5 匿名 namespace 替代文件内 `static`
{: .sec-ext}

C 时代要让一个符号只在本 TU 可见，靠的是 `static`。C++98 弄出**匿名 namespace** 干同样的活，而且干得更漂亮：

```cpp
// anon_ns.cpp —— 需要 -std=c++20
#include <iostream>

namespace {                          // 没有名字 → 每个 TU 有一份独立副本
    int internal_counter = 42;
    void helper() { std::cout << "helper\n"; }
    struct Impl { int v = 1; };      // 类型也能藏起来
}

// static int old_style = 42;        // 老写法：只能用于变量和函数
// static struct Impl2 { int v; };   // 错误：static 不能修饰类型声明

int main() {
    std::cout << internal_counter << "\n";
    helper();
    Impl i;
    std::cout << i.v << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra anon_ns.cpp -o an && ./an
```

```text
42
helper
1
```

匿名 namespace 好在哪儿：

- `static` 只能修饰变量和函数，**修饰不了类型**；匿名 namespace 可以。
- C++11 起，匿名 namespace 里的名字具有**内部链接**（C++03 时代它们是外部链接 + 唯一名字，语义更绕）。
- 它是 C++ Core Guidelines 的正式建议（SF.22），也是大多数人看到 `namespace {` 就知道"这是本文件私有的"的视觉惯例。

> **坑：** 别把匿名 namespace 塞进头文件。头文件要被多个 TU 包含，每个 TU 都会拿到一份独立副本——代码膨胀先不说，要是这个 TU 私有的东西出现在某个 inline 函数的签名里，就直接 ODR 违规了（同一个 inline 函数在不同 TU 里指向了不同的实体）。头文件里要藏东西，用 `detail` 命名空间（比如 `namespace mylib::detail`），它是有名字的，所以是共享的。
{: .sec-pit}

### 4.2.6 `extern "C"` 与语言链接
{: .sec-know}

`extern "C"` 指定的是**语言链接**（language linkage），它影响函数名的修饰（mangling）规则，某些平台上还连带影响调用约定。它唯一的用途就是：让 C++ 代码能和 C 代码（或者其他语言）互相调。

```cpp
// extern_c.cpp —— 需要 -std=c++20
#include <iostream>

extern "C" int add_c(int a, int b) { return a + b; }     // C 语言链接

extern "C" {                                             // 批量指定
    int g_counter_c = 0;
    void reset_c() { g_counter_c = 0; }
}

// extern "C" void f(int);
// extern "C" void f(double);   // 错误：同名 C 链接函数不能重载

int main() {
    std::cout << add_c(2, 3) << " " << g_counter_c << "\n";
    reset_c();
    std::cout << g_counter_c << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra extern_c.cpp -o ec && ./ec
nm -C ec | grep -E "add_c|reset_c"
```

```text
5 0
0
0000000000001169 T add_c
000000000000117f T reset_c
```

`nm` 打出来的名字是 `add_c`，而不是 `_Z5add_cii` 那种 C++ 修饰名——这就是语言链接实打实的效果（具体怎么修饰是实现定义的，标准只保"C 链接"这个语义）。

给 C 用的头文件要写成这样，两边都包含它时才不会冲突：

```cpp
// mylib.h —— C 与 C++ 都能包含
#pragma once

#ifdef __cplusplus
extern "C" {
#endif

int mylib_add(int a, int b);

#ifdef __cplusplus
}  // extern "C"
#endif
```

`__cplusplus` 这个宏只有 C++ 编译器才定义，C 编译器一看到 `extern "C"` 直接语法错误——所以必须整个包在条件编译里。

## 4.3 再来看常量
{: .sec-expl}

### 4.3.1 `const` 的六种位置与读法口诀
{: .sec-know}

`const` 摆在哪个位置，意思能差出天际。先把规则摆清楚，再上口诀：

**规则**：`const` 修饰它**左边紧挨着的东西**；要是它左边啥也没有（站在最左边），就修饰它右边紧挨着的东西。

照这条规则读一遍：

| 写法 | 含义 | 能改什么 |
| --- | --- | --- |
| `const int x = 1;` / `int const x = 1;` | 常量整数（两种写法等价） | 都不能改 |
| `const int* p;` / `int const* p;` | 指向常量的指针 | 能改 `p` 指向别处，不能改 `*p` |
| `int* const p = &a;` | 常量指针 | 能改 `*p`，不能改 `p` |
| `const int* const p = &a;` | 指向常量的常量指针 | 都不能改 |
| `const int& r = a;` | 指向常量的引用 | 不能通过 `r` 改 `a` |
| `void f() const;` | const 成员函数 | 不能改非 `mutable` 成员 |
| `const int f();` | 返回 const 值 | 对调用方几乎无意义（按值返回加 const 通常是噪音） |

读法就一句口诀：**盯着 `const` 和 `*` 的相对位置——`const` 在 `*` 左边，数据不能动；`const` 在 `*` 右边，指针本身不能动。** 我记这个就靠那句"const 在 * 左边管数据"——当初背了好几遍才顺过来，比去数星号个数靠谱。

```cpp
// const_positions.cpp —— 需要 -std=c++20
#include <iostream>

class Counter {
public:
    int get() const { ++reads_; return value_; }   // const 成员函数里改 mutable 成员
    void set(int v) { value_ = v; }
private:
    int value_{0};
    mutable int reads_{0};                          // 见 4.3.9
};

int main() {
    int a = 1;
    int b = 2;

    const int* p1 = &a;          // 指向常量
    int* const p2 = &a;          // 常量指针
    const int* const p3 = &a;    // 两者都是

    // *p1 = 10;                 // 错误：不能改指向的值
    p1 = &b;                     // OK：可以改指向
    *p2 = 10;                    // OK：可以改值
    // p2 = &b;                  // 错误：不能改指向
    // *p3 = 20;  p3 = &b;       // 都错

    std::cout << "a=" << a << " *p1=" << *p1 << " *p3=" << *p3 << "\n";

    Counter c;                   // const 成员函数那一行的验证
    c.set(7);
    std::cout << c.get() << " " << c.get() << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra const_positions.cpp -o cp && ./cp
```

```text
a=10 *p1=2 *p3=10
7 7
```

`*p2 = 10` 借另一个指针把 `a` 改成了 10，于是自始至终指着 `a` 的 `p3` 打出来是 10；而中途被改去指向 `b` 的 `p1` 打出来是 2——同一个对象，`const` 只管"通过这条路径能不能改"，管不着对象本身（4.4.5 还要说这茬）。

另外注意 `p1` 的类型是 `const int*`：它指着的 `a` 明明不是 const 对象，可 `*p1 = 5` 照样编不过。这就是"只读视角"的意思——不是对象不能改，是你这条路不能改。

### 4.3.2 顶层 const 与底层 const：拷贝时的不对称
{: .sec-iv}

- **顶层 const（top-level const）**：对象**本身**是 const。指针自己的 const、普通变量的 const 都算这一类。
- **底层 const（low-level const）**：指针/引用**指着的那个对象**是 const。

这俩在拷贝时的规则完全不同，这也是弄懂函数传参、重载决议的一把钥匙：

```cpp
// top_low_const.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    const int ci = 42;
    int i = ci;                 // OK：拷贝时顶层 const 被忽略（拷的是值，ci 本身没被改）
    std::cout << "i=" << i << "\n";

    const int* p = &ci;         // p 有底层 const
    // int* q = p;              // 错误：不能把底层 const 丢掉
    const int* r = p;           // OK：底层 const 可以保留着拷

    int* const cp = &i;         // 顶层 const（指针本身）
    int* cp2 = cp;              // OK：顶层 const 在拷贝时被忽略

    std::cout << *r << " " << *cp2 << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra top_low_const.cpp -o tlc && ./tlc
```

```text
i=42
42 42
```

为啥规则不对称？因为拷一个"顶层 const 对象"伤不到任何人——原对象照样是 const；可要是把一个"底层 const 指针"拷给非 const 指针，等于发了张能改写原对象的许可证，而原对象可能是真 const（躺在只读段里，你写进去就是段错误）。

这条规则延伸到函数参数上：

```cpp
void f(int x);            // 与 void f(const int x) 是同一个函数
void g(const int* p);     // 与 void g(int* p) 是两个不同的重载
```

形参的顶层 const 不参与函数签名（`void f(const int)` 和 `void f(int)` 会被判"重定义"），底层 const 才参与。这也解释了为什么头文件里写 `void f(int x)`、定义里写 `void f(const int x)` 能正常链接——不过这对调用方没啥意义，一般只在定义里加 const 来防自己手滑改错。

### 4.3.3 `const` 与 `constexpr`：只读 vs 编译期
{: .sec-iv}

这一条，是我觉得整章最值钱的辨析：

- **`const`**：这个对象**不能通过这个名字改**。就这么多意思。它完全可以在运行期初始化。
- **`constexpr`**：这是一个**常量表达式**，编译期就能算出它的值（C++11）。用在对象声明上时隐含 `const`。

```cpp
// const_vs_constexpr.cpp —— 需要 -std=c++20
#include <array>
#include <iostream>

int runtime_value() { return 10; }

int main() {
    const int a = runtime_value();     // 只读，但值在运行期才知道
    constexpr int b = 10;              // 编译期常量

    std::array<int, b> arr{};          // OK：b 是常量表达式
    // std::array<int, a> arr2{};      // 错误：a 不是常量表达式
    // int c = 5; std::array<int, c> arr3{};  // 同理错误

    std::cout << a << " " << arr.size() << "\n";

    // 更直观的对照：switch 的 case 标签、模板非类型参数，都只认 constexpr
    // case a:                          // 错误
    std::cout << "a 是运行时只读，b 是编译期常量\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra const_vs_constexpr.cpp -o cvc && ./cvc
```

```text
10 10
a 是运行时只读，b 是编译期常量
```

判断就靠一句：**"它能不能写进 `static_assert` 或数组长度"是常量表达式的试金石。**

还有一条容易漏的：`const` 在**不同 TU** 里链接性不一样。命名空间作用域的 `const` 变量默认是**内部链接**（C++ 独有，C 里是外部链接），所以头文件里写 `const int kMax = 100;` 不会重复定义——每个 TU 各拿一份。这既是便利也是坑，看 4.3.6。

### 4.3.4 constexpr 函数与 constexpr 构造函数
{: .sec-know}

`constexpr` 加在函数上，意思是"**只要**实参全是常量表达式，这次调用就能在编译期求值"。注意这个"只要"——constexpr 函数同时也就是个普普通通的运行期函数。

版本演进：

| 版本 | constexpr 函数体允许什么 |
| --- | --- |
| C++11 | 只有一条 `return` 语句（递归除外，什么都不许有） |
| C++14 | 允许多条语句、局部变量、循环、条件分支、修改局部变量 |
| C++17 | 允许 lambda（在常量求值语境下） |
| C++20 | 允许 `try` 块、动态分配（必须是"瞬态"的，求值结束时释放）、虚函数调用、`union` 成员修改 |

```cpp
// constexpr_fn.cpp —— 需要 -std=c++20
#include <array>
#include <iostream>

constexpr int factorial(int n) {          // C++14 起可以写循环
    int r = 1;
    for (int i = 2; i <= n; ++i) { r *= i; }
    return r;
}

struct Point {
    int x;
    int y;
    constexpr Point(int x_, int y_) : x(x_), y(y_) {}
    constexpr int norm_sq() const { return x * x + y * y; }
};

int main() {
    constexpr int f5 = factorial(5);      // 编译期求值
    static_assert(f5 == 120, "5! == 120");

    constexpr Point p{3, 4};
    static_assert(p.norm_sq() == 25, "3-4-5");

    int runtime = 4;
    int fr = factorial(runtime);          // 运行期照常调用（它本来就是普通函数）
    std::cout << f5 << " " << fr << " " << p.norm_sq() << "\n";

    std::array<int, factorial(4)> buf{};  // 24 个元素，长度在编译期算出来
    std::cout << buf.size() << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra constexpr_fn.cpp -o cf && ./cf
```

```text
120 24 25
24
```

constexpr 构造函数要满足的条件（C++20）：所有非静态数据成员都被初始化、类型是字面类型（literal type，白话就是有 constexpr 构造函数、平凡析构函数的那些类型）。这样造出来的对象才能进常量表达式。

> **坑：** `constexpr` 函数一旦被实例化后，**无论怎么调都不可能**在编译期求值，那程序就是 ill-formed（且不要求编译器诊断）。还有一点：constexpr 函数隐含 `inline`，所以它能定义在头文件里而不违反 ODR——代价是它每改一次，所有包含它的 TU 都得重新编译。
{: .sec-pit}

### 4.3.5 `consteval`（C++20）：必须在编译期算完
{: .sec-ext}

`constexpr` 是"可以在编译期"，`consteval`（C++20）是"**必须**在编译期"。这种函数叫**立即函数**（immediate function）：任何一次调用都得产出常量表达式，否则直接编译失败。

```cpp
// consteval_demo.cpp —— 需要 -std=c++20
#include <iostream>

consteval int square(int n) { return n * n; }

constexpr int runtime_or_compile(int n) {   // 两用：取决于调用上下文
    return n * 2;
}

int main() {
    constexpr int a = square(5);       // OK
    int n = 5;
    // int b = square(n);              // 错误：n 不是常量，consteval 调用无法在编译期求值
    std::cout << a << " " << square(9) << "\n";   // square(9) 本身就是常量表达式

    std::cout << runtime_or_compile(n) << "\n";   // 这个可以：constexpr 函数允许运行期调用
}
```

```bash
g++ -std=c++20 -Wall -Wextra consteval_demo.cpp -o ce && ./ce
```

```text
25 81
10
```

`consteval` 的典型用途：编译期字符串哈希、字面量解析器、单位换算的强制校验——任何"这个值必须在编译期钉死，否则就是设计错误"的地方。它的价值在于把"希望编译器帮我折叠一下"变成"编译器必须给我折叠，不然就报错"。

相关的两个工具：

- `std::is_constant_evaluated()`（C++20，`<type_traits>`）：在 constexpr 函数里判断当前是不是在常量求值上下文，可以走不同分支（典型场景：编译期用可移植的朴素算法，运行期用 SIMD 或内建指令）。
- `if consteval`（C++23）：上面的语法糖形式。

### 4.3.6 `inline` 变量（C++17）：头文件常量的正解
{: .sec-ext}

C++17 之前，头文件里放常量就三种尴尬的选法：

| 写法 | 问题 |
| --- | --- |
| `#define K_MAX 100` | 宏没有类型、不遵守作用域、调试器看不见 |
| `const int kMax = 100;` | 每个 TU 一份副本（内部链接）；取地址时每个 TU 地址不同；非整型/非字面类型还得额外处理 |
| `extern const int kMax;` + 某个 `.cpp` 里定义 | 正确但啰嗦，且常量值不在头文件里，编译器看不到 → 无法常量折叠 |

C++17 的 `inline` 变量一把全解决：头文件里能放**带初始化器的定义**，全程序只有一份实体，每个 TU 都能看见它的值。

```cpp
// config.hpp —— 需要 C++17 起
#pragma once
#include <string_view>

inline constexpr int kMaxRetries = 3;                   // 编译期常量，全程序一份
inline constexpr std::string_view kAppName = "demo";    // 非整型也行
inline const double kTimeout = 2.5;                     // 甚至可以是非 constexpr 的
```

```cpp
// tu_a.cpp —— 需要 -std=c++20
#include <iostream>
#include "config.hpp"

const int* address_a();

int main() {
    std::cout << kMaxRetries << " " << kAppName << " " << kTimeout << "\n";
    std::cout << "本 TU 的地址: " << &kMaxRetries << "\n";
    std::cout << "另一 TU 的地址: " << address_a() << "\n";
    std::cout << "是同一个对象吗: " << (&kMaxRetries == address_a()) << "\n";
}
```

```cpp
// tu_b.cpp —— 需要 -std=c++20
#include "config.hpp"

const int* address_a() { return &kMaxRetries; }
```

```bash
g++ -std=c++20 -Wall -Wextra tu_a.cpp tu_b.cpp -o tu && ./tu
```

```text
本 TU 的地址: 0x55a1b2c3d010
另一 TU 的地址: 0x55a1b2c3d010

```

地址相同——这就是"全程序一份实体"最直白的证明（具体地址值看平台脸色，你该看的是两者相不相等）。

### 4.3.7 类内静态常量：四种写法的演进
{: .sec-know}

给类配一个编译期常量，C++ 历史上前后冒出过四种写法，每种都对应一个年代的约束：

```cpp
// static_member_const.cpp —— 需要 -std=c++17（部分特性）
#include <iostream>

struct Limits {
    enum { kLegacyMax = 100 };            // (1) C++98 "enum hack"
    static const int kOldMax = 100;       // (2) C++98：类内初始化，仅限整型/枚举
    static constexpr int kMax = 100;      // (3) C++11：constexpr；C++17 起隐式 inline
    inline static int kCounter = 0;       // (4) C++17：inline 静态成员，可修改
};

// const int Limits::kOldMax;             // C++98~C++14：若被 ODR-use 必须类外补定义
// constexpr int Limits::kMax;            // C++11~C++14：同上（C++17 起被弃用）

int main() {
    std::cout << Limits::kLegacyMax << " " << Limits::kOldMax << " " << Limits::kMax << "\n";

    const int& r = Limits::kMax;          // ODR-use：C++17 起不需要类外定义了
    std::cout << r << "\n";

    Limits::kCounter += 5;
    std::cout << Limits::kCounter << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra static_member_const.cpp -o smc && ./smc
```

```text
100 100 100
100
5
```

四种写法怎么挑：

| 写法 | 版本 | 现在还用吗 |
| --- | --- | --- |
| `enum { kMax = 100 };` | C++98 | 只在需要"保证不占存储、绝不可能被取地址"时用；也常见于老代码 |
| `static const int kMax = 100;` | C++98 | 被 `static constexpr` 取代 |
| `static constexpr int kMax = 100;` | C++11（C++17 起隐式 inline） | **默认选择** |
| `inline static T kX{...};` | C++17 | 需要可变、或非字面类型（如 `std::string`）的类级单例时用 |

`enum hack` 当年火起来原因很实在：C++98 里只有整型/枚举的 `static const` 成员能在类内初始化，`static const double` 不行；而 `enum` 不占存储、不用类外定义、也绝不会被取地址。C++11 之后这些限制基本都没了，它如今只剩历史价值。

### 4.3.8 `volatile`：它不是原子，也不是内存屏障
{: .sec-warn}

`volatile` 的意思就一条：**对这个对象的每次读写都是"可观察的副作用"，编译器不能把它优化掉，也不能把它相对其他 volatile 访问的顺序重排**。它要解决的问题是"这个值可能被程序之外的东西改掉"。

真正常用的就三个地方：

1. **内存映射硬件寄存器**（裸机/驱动）：`volatile std::uint32_t* const kStatus = ...;`
2. **信号处理器与 C++ 代码之间的通信**：`volatile std::sig_atomic_t`
3. **`setjmp`/`longjmp` 之间需要保留的局部变量**

```cpp
// volatile_demo.cpp —— 需要 -std=c++20
#include <csignal>
#include <iostream>

volatile std::sig_atomic_t g_flag = 0;    // 信号处理器里唯一保证安全的通信方式

extern "C" void on_signal(int) {
    g_flag = 1;                            // 只能写 volatile sig_atomic_t
}

int main() {
    std::signal(SIGINT, on_signal);
    std::cout << "初始 g_flag = " << g_flag << "\n";
    std::cout << "volatile 不提供原子性，也不建立线程间的 happens-before\n";
    std::cout << "多线程同步请用 std::atomic（C++11）而不是 volatile\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra volatile_demo.cpp -o vd && ./vd
```

```text
初始 g_flag = 0
volatile 不提供原子性，也不建立线程间的 happens-before
多线程同步请用 std::atomic（C++11）而不是 volatile
```

为啥 `volatile` 救不了多线程：

- 它不保证**原子性**：`volatile long long x; x++;` 依然是读-改-写三步，两个线程可以同时读到同一个值。
- 它不保证**可见性顺序**：volatile 访问之间不被重排，但 volatile 访问与普通访问之间、以及 CPU 硬件层面的重排，它一概不管。`volatile bool ready` + `volatile int data` 的经典写法在多核上是错的。
- 它不产生任何**内存屏障指令**（x86 上可能碰巧看起来能用，ARM 上就露馅）。

> **坑：** C# / Java 里的 `volatile` 是带跨线程语义的，C++ 里没有。我带过的从 Java 转过来的同事，几乎都在这栽过跟头。C++ 里线程同步就两个答案：`std::atomic`（管数据）和 `std::mutex`（管临界区）。
{: .sec-pit}

### 4.3.9 `mutable`：在 const 里开一个后门
{: .sec-know}

`mutable` 有两个八竿子打不着的用法：

**用法一：类成员。** 允许在 const 成员函数里改它。设计动机是"逻辑常量性"（logical constness）和"位常量性"（bitwise constness）的分家——对调用方来说对象"没变"，但内部实现需要动点手脚。

```cpp
// mutable_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <mutex>

class CachedValue {
public:
    int get() const {
        std::lock_guard<std::mutex> lk(mutex_);   // mutex_ 必须是 mutable
        if (!cached_) {
            value_ = expensive();                  // value_ 也必须是 mutable
            cached_ = true;
        }
        return value_;
    }
private:
    int expensive() const { return 42; }
    mutable std::mutex mutex_;
    mutable int value_{0};
    mutable bool cached_{false};
};

int main() {
    const CachedValue cv;               // const 对象
    std::cout << cv.get() << "\n";      // 依然能调：内部缓存需要改状态

    int n = 0;
    // auto bad = [n]() { return ++n; };      // 错误：按值捕获的副本是 const 的
    auto counter = [n]() mutable { return ++n; };   // 加了 mutable 就能改
    std::cout << counter() << " " << counter() << "\n";
    std::cout << "外面的 n 依然是 " << n << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra mutable_demo.cpp -o md -pthread && ./md
```

```text
42
1 2
外面的 n 依然是 0
```

**用法二：lambda。** 不加 `mutable` 时，lambda 的 `operator()` 是 const 的，按值捕获进来的变量在函数体里只是个只读副本。加了 `mutable`，`operator()` 就变非 const，副本就能改了。注意它改的是**副本**，外头的 `n` 纹丝不动（最后一行输出就是证据）。

lambda 加了 `mutable` 还有个连带副作用：它的 `operator()` 不再是 const，于是你没法通过一个 `const` 的 lambda 对象去调它。绝大多数时候你要的是引用捕获（`[&n]`），而不是 `mutable`。

### 4.3.10 `thread_local`：每个线程一份
{: .sec-know}

`thread_local`（C++11）给变量**线程存储期**：每个线程一份独立实例，互不干扰。它能跟 `static`/`extern` 组合，也能单独使。

```cpp
// thread_local_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <thread>
#include <vector>

thread_local int tls_counter = 0;      // 命名空间作用域：每个线程一份

int next_id() {
    thread_local int id = 0;           // 块作用域：thread_local 隐含 static，不用再写
    return ++id;
}

void worker(int k) {
    tls_counter += k;
    std::cout << "thread " << k << ": tls_counter=" << tls_counter
              << " next_id=" << next_id() << "\n";
}

int main() {
    std::vector<std::thread> ts;
    for (int i = 1; i <= 3; ++i) { ts.emplace_back(worker, i); }
    for (auto& t : ts) { t.join(); }

    std::cout << "主线程 tls_counter=" << tls_counter << "\n";
    std::cout << "主线程 next_id=" << next_id() << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra thread_local_demo.cpp -o tl -pthread && ./tl
```

```text
thread 1: tls_counter=1 next_id=1
thread 2: tls_counter=2 next_id=1
thread 3: tls_counter=3 next_id=1
主线程 tls_counter=0
主线程 next_id=1
```

（三行 `thread N` 的打印顺序取决于调度，每次运行可能不同。）

另外有几点值得记：块作用域的 `thread_local` 隐含 `static`（再写 `static thread_local` 纯属多余）；命名空间作用域的它默认外部链接，加 `static` 变内部链接；有动态初始化时，每个线程在**第一次 ODR-use** 时才初始化，会带一次性开销（守卫变量 + TLS wrapper），初始化器要是常量表达式则开销极小；析构发生在线程结束时。典型用途是每线程错误码（`errno` 的现代实现）、随机数发生器、内存池、日志缓冲区。

> **坑：** `thread_local` 变量初始化时若抛异常，会一路传到第一次使用它的地方——往往就是个看着人畜无害的表达式。另外，在 DLL/共享库里，`thread_local` 的动态初始化某些平台上有已知坑（Windows 上 DLL 没在进程启动时加载就会漏掉 TLS 初始化）。高可靠场景尽量让 `thread_local` 的初始化器是常量表达式，或者换成惰性局部静态 + 线程 id 索引。

## 4.4 技术解惑
{: .sec-expl}

### 4.4.1 `extern int x;` 和 `int x;` 差在哪
{: .sec-know}

前者是声明，不分配存储，能写无数次，通常搁头文件里给别的 TU 用。后者是定义，分配存储，**同一个名字整个程序里只能出现一次**，要出现在头文件里就是"重复定义"链接错误。判断窍门就一个：看有没有初始化器——`extern int x = 5;` 哪怕写了 `extern`，它照样是定义。

### 4.4.2 全局变量该怎么写才不算错
{: .sec-best}

按优先级排：能不用全局就不用（依赖注入，或者弄个命名空间里的函数返回引用）；必须跨 TU 共享就头文件 `extern int g_x;` + 某个 `.cpp` 里 `int g_x = 0;`；纯常量就上 C++17 的 `inline constexpr T kX = ...;`；有初始化顺序依赖的就改成函数内 `static` 返回引用（4.1.7 的 Magic Static）。

### 4.4.3 为什么推荐 `{}` 而不是 `=`
{: .sec-know}

就三个实打实的理由：禁止窄化转换（4.1.3）；同一种写法对内置类型、聚合类型、带构造函数的类通吃；不撞最令人沮丧的解析（4.1.5）。`=` 唯一的优点是"看着像数学里的等号，第一眼更顺"，代价是把窄化转换全放行，还不能用在 `explicit` 构造函数上。

### 4.4.4 `int x{};` 和 `int x = 0;` 一样吗？`int x;` 在函数里是什么值
{: .sec-know}

对 `int` 来说效果一样（都是 0）。差在类类型和窄化检查上：`std::string s{};` 走默认构造，`std::string s = 0;` 是编译错误；`char c{300}` 是错误，`char c = 300` 只是悄悄截断。

函数里的 `int x;` 是**默认初始化**，值是**不确定的**——读它是 UB，这可不是"大概率是 0"，而是标准连任何保证都不给了。GCC/Clang 在 `-Wall` 下会报 `-Wmaybe-uninitialized`（有时只在 `-O2` 往上才报得准）。类类型不一样：`Widget w;` 会调默认构造函数，带默认成员初始化器的成员照样会被初始化。

### 4.4.5 `const int* p` 到底能不能改东西
{: .sec-know}

不能改 `*p`，能改 `p`。也就是说：

```cpp
int a = 1, b = 2;
const int* p = &a;
p = &b;          // OK：换了指向
// *p = 3;       // 错误：不能通过 p 改它指向的东西
a = 3;           // OK！a 本身不是 const，绕过 p 照样能改
```

最后一行是很多人会漏掉的：`const int* p` 只说明"通过 `p` 改不了"，不代表"这个对象是 const"。真正的 const 对象（`const int a = 1;`）你走任何途径去改都是 UB。

### 4.4.6 constexpr 函数里能写循环吗
{: .sec-know}

看标准版本：C++11 只允许一条 `return`（所以老代码里满屏递归），C++14 放开循环和局部变量，C++20 又进一步允许 `try` 和虚调用。被锁在 C++11 的项目就只能啃递归那套写法。

### 4.4.7 头文件里写 `const int kMax = 100;` 会 ODR 违规吗
{: .sec-know}

不会报链接错误，因为命名空间作用域的 `const` 变量默认是**内部链接**——每个 TU 都拿到自己的一份私有副本。但这引出两个实际问题：

- 每个 TU 一份，如果这个常量占空间（比如一个大数组），就是实打实的二进制膨胀；
- 类型不是整型时情况更复杂：`const std::string kName = "x";` 在每个 TU 里都是一份独立构造的对象，构造开销 × TU 数量。

C++17 的正解是 `inline constexpr int kMax = 100;`（见 4.3.6）。

### 4.4.8 函数里的 `static` 局部变量是线程安全的吗
{: .sec-know}

C++11 起是的。标准保证：多线程并发首次进入该声明时，初始化只发生一次，其余线程阻塞等它完成（这也就是 Magic Static）。C++11 之前没这保证，GCC 得加 `-fno-threadsafe-statics` 才关得掉（默认是开的）。

还有俩残余风险：初始化过程中递归重入是 UB；初始化失败（抛异常）时，下次调用会**重新尝试**初始化（标准规定：若初始化因异常退出，变量视为未初始化，下次进入再重试）。

### 4.4.9 为什么 `char* p = "hello";` 编译不过
{: .sec-know}

字符串字面量的类型是 `const char[6]`，用 `char*` 指向它就丢了 const——C++11 起这是硬错误（C++03 有个给老代码留的弃用转换，C++11 给删了）。按需挑：`const char* p = "hello";`（最常用）、`const char arr[] = "hello";`（要一份可写副本）、`std::string_view sv = "hello";`（C++17 只读视图）、`std::string s = "hello";`（拥有且可改）。

### 4.4.10 什么时候用 `constexpr`，什么时候用 `const`
{: .sec-best}

按这个顺序去判断：

1. 值在编译期就确定、且要用于数组长度 / `case` 标签 / 模板参数 / `static_assert` → `constexpr`。
2. 运行期确定的只读值（函数参数、配置读取结果）→ `const`。
3. 只是想表达"这个函数不改成员" → 成员函数加 `const`。
4. 想表达"这个指针不拥有、也不改" → `const T*`（或 `T const*`）。

反过来：别为了"显得严谨"给按值返回的返回值加 `const`（`const int f();`）——C++11 起它会挡住调用方 move，收益为零。

1. **把四种初始化形式打印成一张表**：写一个程序，对 `int`、`double`、一个聚合类型、一个带 `explicit` 构造函数的类，分别用 `=`、`()`、`{}`、值初始化各初始化一次，把结果和"哪种写法编译不过"列出来。然后加 `-Wconversion` 再编一遍，看多了哪些告警。
2. **制造一次 SIOF**：照 4.1.7 写两个 TU，`g++ a.cpp b.cpp` 和 `g++ b.cpp a.cpp` 各编译一次，记录两次输出。然后改成 Magic Static 版本，确认两种链接顺序结果一致。
3. **验证线程安全的静态初始化**：把 4.1.7 的 `magic_static_thread.cpp` 里 `Heavy` 的构造睡眠改成 500ms，线程数改成 8，观察"构造了一次"是否仍然只出现一次。再把编译标准换成 `-std=c++03`（去掉 `std::thread`）不适用，改成用 `pthread` 直接测——这一步选做。
4. **头文件常量改造**：把项目里用 `#define` 写的常量改成 `inline constexpr`（C++17）或 `static constexpr` 类内常量（C++11），用 `nm` 对比改造前后二进制里该符号的数量变化。
5. **`const` 位置练习**：手写 `const char* const* p` 与 `const char* const* const r` 两个声明，先用口诀说出"谁能改、谁不能改"，再写一段代码逐个尝试赋值，用编译器的报错验证判断。

## 变式追问
{: .sec-think}

1. `constexpr int x = f();` 里 `f()` 是普通函数，这段代码能编过吗？

   取决于 `f()` 是不是 constexpr 且实参是不是常量表达式。`constexpr` 变量的初始化器必须是**常量表达式**，而调用非 constexpr 函数永远产生不了常量表达式，所以 `constexpr int x = f();` 在 `f` 不是 constexpr 时是编译错误。反过来，`const int x = f();` 完全合法——它只是运行期只读。这正是 4.3.3 那条辨析的落点：别看到 `const` 就以为编译器知道它的值。

2. `static const int kMax = 100;` 写在类里，为什么有时候能编过、有时候报 undefined reference？

   因为"类内初始化"只提供了**值**，没有提供**定义**（存储）。当这个成员只被当作值使用时（`int arr[Limits::kMax]`、`std::cout << Limits::kMax`），编译器可以直接把 100 内联进去，不需要地址，所以不需要定义。当它被 ODR-use 时——取地址 `&Limits::kMax`、绑定到引用 `const int& r = Limits::kMax`、传給按引用取参的函数——就需要一个真正的对象，链接器会去找 `Limits::kMax` 的定义，找不到就报 undefined reference。C++11~C++14 的解法是在某个 `.cpp` 里补一行 `constexpr int Limits::kMax;`（**不带**初始化器）；C++17 起 `static constexpr` 成员隐式 `inline`，类内声明就是定义，这个问题消失了。

3. 有人说"把全局变量都换成函数内 static 返回引用，就彻底没有初始化顺序问题了"，这话对吗？

   只对一半。它确实消灭了**构造**顺序问题——因为顺序由调用顺序决定，而调用一定发生在初始化完成之后。但**析构**顺序问题它没解决：函数内 static 对象在 `main` 之后按构造逆序析构，如果 A 的析构函数去访问 B，而 B 已经被析构了，一样是 UB。而且析构顺序同样跨 TU 未指定。工程上真正的做法有三条，按推荐度排：让这类单例的析构函数什么都不做（trivially destructible，反正进程结束 OS 会回收）；用 `static T* p = new T;` 故意泄漏（不析构就没顺序问题）；或者显式提供一个 `shutdown()` 函数，由 `main` 按确定顺序调用。

4. `thread_local int x = compute();` 每个线程都会跑一次 `compute()` 吗？

   会，而且是在该线程**第一次 ODR-use** `x` 时跑，不是线程启动时。这是标准的规定（[basic.stc.thread]）：具有非平凡初始化的 `thread_local` 变量在每个线程首次使用前初始化。实际影响有两个：一是首次访问有一次性开销（守卫变量 + 可能的 wrapper 函数调用）；二是如果 `compute()` 抛异常，异常会从这个看起来人畜无害的表达式里冒出来。想避免，就把初始化器写成常量表达式（`thread_local int x = 0;` 或 `constinit thread_local`），或者包一层函数内 `thread_local` 的惰性初始化。
