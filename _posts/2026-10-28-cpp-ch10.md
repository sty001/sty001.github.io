## 10.1 函数基础
{: .sec-expl}

### 10.1.1 声明与定义为什么要分开
{: .sec-know}

声明（declaration）回答"这个函数长什么样"，定义（definition）回答"它具体怎么做"。分开的理由不是风格，是编译模型：

- C++ 的编译单元是**单个 .cpp 文件**。编译器在编译 `a.cpp` 时看不见 `b.cpp`，它只需要 `b.h` 里的声明就能生成调用代码（参数怎么排、返回值在哪、符号名叫什么）。
- 链接器在最后把所有 .cpp 的目标文件拼起来，把符号引用填成真实地址。
- 如果定义也写进头文件，而这个头文件被两个 .cpp 包含，链接器就会看到两个同名符号——这就是 10.1.2 的 ODR 违规。

所以规则是：**头文件放声明（和 `inline`、`constexpr`、模板的定义），.cpp 放普通函数的定义。**

```cpp
// math_util.h
#ifndef MATH_UTIL_H
#define MATH_UTIL_H

int add(int a, int b);                            // 声明：只有签名，没有函数体

inline int square(int x) { return x * x; }        // inline 定义：允许多份，可以放头文件

#endif
```

```cpp
// math_util.cpp
#include "math_util.h"

int add(int a, int b) { return a + b; }           // 定义：整个程序里只能出现一次
```

```cpp
// main.cpp
#include <iostream>
#include "math_util.h"

int main() {
    std::cout << add(2, 3) << ' ' << square(5) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra main.cpp math_util.cpp -o demo && ./demo
```

```text
5 25
```

> **坑：** 头文件里写一个非 `inline` 的自由函数定义，被两个 .cpp 包含时，很多环境下链接期才会报 `multiple definition`。更阴险的情形是"两个头文件里各写了一个同名同签名的 `static` 函数"——那不算 ODR 违规（内部链接，各自一份），但语义上是两个不同的函数，改了一个另一个不动，调试时能查一整天。
{: .sec-pit}

### 10.1.2 单一定义规则 ODR 到底管什么
{: .sec-know}

**单一定义规则（One Definition Rule）**的核心条款，按对象分三层：

| 对象 | 要求 |
| --- | --- |
| 普通函数 | 整个程序有且仅有一份定义 |
| `inline` 函数 / 模板 | 每个用到它的编译单元都要有一份定义，且这些定义的**记号序列必须完全一致** |
| 类类型 | 每个编译单元里定义必须一致（否则是 UB，编译器通常查不出来） |

第二条那个"记号序列一致"是实操中最容易踩的：同一个 `inline` 函数在头文件里，被两个 .cpp 以不同的宏状态包含，就违规了。举个例子：

```cpp
// cfg.h
inline int buffer_size() {
#ifdef BIG_BUFFER
    return 4096;
#else
    return 64;
#endif
}
```

`a.cpp` 定义 `BIG_BUFFER` 后包含，`b.cpp` 不定义直接包含——两份定义的记号序列不同，ODR 违规，且**不要求编译器诊断**，实际表现是链接器随机选一份，两个 .cpp 里拿到的缓冲区大小不一样。这种 bug 的现象是"同一个函数调用，在不同文件里返回值不同"。

规避办法很直接：`inline` 函数的定义不要依赖会被外部改变的宏，用函数参数或模板参数代替。

> **注意：** ODR 违规属于 **no diagnostic required** 的 UB。它不一定崩，只是行为离奇。排查手段是给两个 .cpp 分别打日志打印函数地址，或者用 `-flto` 编译让链接期优化把不一致暴露出来（LTO 下 GCC/Clang 会对 ODR 不一致发出 `-Wodr` 警告）。
{: .sec-warn}

### 10.1.3 函数签名里有什么——返回类型不在其中
{: .sec-know}

**函数签名（signature）**由这几项组成：函数名、参数类型列表、所在类（成员函数）、`const`/`volatile`/引用限定（成员函数）、`noexcept`（C++17 起算签名的一部分）、模板形参（函数模板）。

**返回类型不属于签名**，所以不能只靠返回类型重载：

```cpp
// 编译错误：不能仅按返回类型重载
int    parse(const char* s);
double parse(const char* s);
```

```text
error: ambiguating new declaration of 'double parse(const char*)'
```

这个限制的理由很实在：调用点可以丢弃返回值。`parse("12");` 这么一句，编译器没法判断你要的是 `int` 版还是 `double` 版。C++ 从来不做"根据上下文反推重载"这种事——唯一接近的例外是转换运算符，而那也是靠目标类型在**转换序列**里挑，不是靠重载决议凭空猜。

但有一条容易混淆：**返回类型参与模板推导和 `auto` 推导，也参与函数指针类型匹配。**

```cpp
int (*fp)(const char*) = parse;   // 这里返回类型是函数类型的一部分，必须匹配
```

所以准确的说法是：返回类型不是**重载**的依据，但它是**函数类型**的一部分。

`noexcept` 进签名是 C++17 的事（P0012）：`void f()` 和 `void f() noexcept` 是两个不同的函数类型，可以构成重载——虽然实际没人这么写。真正的影响在别处：`void(*)() noexcept` 不能指向会抛的函数；反方向 C++17 起放行了，`noexcept` 函数指针可以隐式转成普通函数指针 `void(*)()`，但反过来把普通函数指针转成 `noexcept` 的不行。

### 10.1.4 `inline` / `constexpr` / `consteval` / `noexcept` / `[[nodiscard]]`
{: .sec-know}

这五个关键字常被混着用，其实管的是完全不同的事：

| 关键字 | 管什么 | 版本 |
| --- | --- | --- |
| `inline` | 链接属性：允许多编译单元各有一份定义（**不是**"建议内联展开"） | C++98 |
| `constexpr` | 有可能在编译期求值；修饰函数时是"承诺"，不保证每次都编译期算 | C++11 |
| `consteval` | 强制每次调用都必须产生编译期常量，否则编译错误 | C++20 |
| `noexcept` | 异常规格；违反时 `std::terminate`；影响库的分支选择 | C++11 |
| `[[nodiscard]]` | 抛弃返回值时告警（配合 `-Wunused-result`） | C++17 |

`inline` 的误区得单独说：现代编译器内联与否跟 `inline` 关键字基本无关，它看的是代价模型和 `-O` 等级。`inline` 在今天唯一实质作用是**让定义在头文件里合法**。反过来，想让编译器更愿意内联，工具是 `__attribute__((always_inline))` 或 LTO，不是 `inline`。

`constexpr` 函数如果所有实参都是常量表达式，就能在编译期求值；否则退化成运行期函数——同一个函数两种身份。`consteval` 不给这个退路：

```cpp
// fn_props.cpp —— 需要 -std=c++20
#include <iostream>
#include <array>

constexpr unsigned long long fact(unsigned n) {          // C++11 起可以有多条语句
    unsigned long long r = 1;
    for (unsigned i = 2; i <= n; ++i) r *= i;
    return r;
}

consteval unsigned mask(unsigned bits) {                  // C++20：必须编译期出结果
    return (1u << bits) - 1u;
}

[[nodiscard]] int compute(int x) { return x * 3 + 1; }    // C++17：调用者不能用完就扔

int main() {
    std::array<int, fact(4)> buf{};                       // 24 个元素，数组长度必须编译期确定
    std::cout << "buf.size() = " << buf.size() << '\n';

    unsigned m = mask(5);
    std::cout << "mask(5) = " << m << '\n';

    int runtime_n = 4;
    std::cout << "fact(runtime_n) = " << fact(runtime_n) << '\n';   // 运行期算，合法

    // unsigned bad = mask(runtime_n);                    // 编译错误：consteval 不能在运行期调用
    compute(7);                                           // -Wall 下会警告：忽略 [[nodiscard]] 返回值
}
```

```bash
g++ -std=c++20 -Wall -Wextra fn_props.cpp -o fn && ./fn
```

```text
buf.size() = 24
mask(5) = 31
fact(runtime_n) = 24
```

编译期那行 `compute(7);` 会产生一条警告，正文里不用管它，目的是让你看见 `[[nodiscard]]` 生效：

```text
warning: ignoring return value of 'int compute(int)', declared with attribute 'nodiscard'
```

`noexcept` 的真实收益不在"代码跑得快"，而在两处：一是编译器可以不生成栈展开表，目标文件变小；二是标准库会据此选分支——`std::vector` 扩容时，只有元素类型的移动构造是 `noexcept` 才敢用移动，否则退回拷贝。这就是为什么自定义类型的移动构造一定要标 `noexcept`。

### 辨析：`constexpr` 与 `consteval`
{: .sec-iv}

| 维度 | `constexpr` | `consteval` |
| --- | --- | --- |
| 实参非常量时 | 退化为运行期函数调用 | 编译错误 |
| 能否取函数指针 | 能（取的是运行期版本） | 不能（没有运行期版本可指） |
| 典型用途 | 通用计算，两种场景都要 | 编译期校验、字面量生成、编译期哈希 |

一句话：`constexpr` 是"可以编译期"，`consteval` 是"只能编译期"。写库的时候优先 `constexpr`，只有当你**需要**强制编译期（比如生成编译期错误信息的字符串哈希）才用 `consteval`。

## 10.2 函数的参数
{: .sec-expl}

### 10.2.1 三选一：值、`const T&`、`T&&`
{: .sec-know}

参数传递的决策可以压成一张表。先记住总原则：**按值传是默认起点，只有"拷贝太贵"或"要改调用方的对象"时才偏离。**

| 形参写法 | 什么时候用它 | 什么时候别用 |
| --- | --- | --- |
| `T`（按值） | 类型便宜（两个指针宽以内：int、指针、`string_view`、`span`）、函数内部本来就要拷一份（sink 参数） | 大对象（`std::vector`、长 `std::string`）、多态基类（会切片） |
| `const T&` | 只读的大对象、需要多态（基类引用）、不想暴露"我要拷贝"这个细节 | 内置类型和小对象——多一层间接，还妨碍优化 |
| `T&` | 出参，要修改调用方的对象 | 只读就该加 `const`；接不了右值和临时量 |
| `T&&` | sink 参数且要移动走（构造函数、setter） | 只读参数；模板里要转发时应该用转发引用 `T&&`（`T` 被推导） |
| `const T*` / `T*` | 可选参数（可以传 `nullptr`）、对接 C API | 参数必填时——用引用，别让调用方传 `nullptr` 进来再判空 |
| `std::string_view` | 只读字符串入参（C++17） | 需要 `'\0'` 结尾、需要长期持有、要调 C API |
| `std::span<const T>` | 只读连续区间（C++20） | 需要拥有内存、需要异构容器 |

为什么小对象按值反而更快？两条原因：

1. 引用是一次间接寻址，且编译器必须假设它可能和外部存储别名——每次读都可能要重新从内存加载；按值传进来的副本是纯局部变量，可以常驻寄存器。
2. 按值的副本有明确的生命周期，编译器的寄存器分配和常量传播都能做得更彻底。

所以 `void f(const int& x)` 是对 `int` 的负优化，而 `void f(std::string_view s)` 比 `const std::string&` 更通用——前者能直接接 `const char*`、字符数组、`std::string` 的子串，且不构造临时 `std::string`。

下面这个例子把拷贝次数摆出来：

```cpp
// param_pass.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <string_view>

struct Traced {
    std::string name;
    Traced(const char* n) : name(n) {}
    Traced(const Traced& o) : name(o.name) { std::cout << "  拷贝构造 " << name << '\n'; }
    Traced(Traced&& o) noexcept : name(std::move(o.name)) { std::cout << "  移动构造 " << name << '\n'; }
};

void by_value(Traced t)              { std::cout << "  by_value(" << t.name << ")\n"; }
void by_const_ref(const Traced& t)   { std::cout << "  by_const_ref(" << t.name << ")\n"; }
void by_rvalue_ref(Traced&& t)       { std::cout << "  by_rvalue_ref(" << t.name << ")\n"; }

void read_sv(std::string_view s)     { std::cout << "  string_view: " << s << " (len=" << s.size() << ")\n"; }
void read_str(const std::string& s)  { std::cout << "  const string&: " << s << '\n'; }

int main() {
    std::cout << "传左值给 by_value：\n";
    Traced a("A");
    by_value(a);

    std::cout << "传右值给 by_value：\n";
    by_value(Traced("B"));

    std::cout << "传左值给 by_const_ref：\n";
    by_const_ref(a);

    std::cout << "传右值给 by_rvalue_ref：\n";
    by_rvalue_ref(Traced("C"));

    std::cout << "字符串参数：\n";
    std::string s = "hello world";
    read_sv(s);
    read_sv("字面量");
    read_str(s);
    // read_str("字面量");   // 会先构造一个临时 std::string，多一次分配
}
```

```bash
g++ -std=c++20 -Wall -Wextra param_pass.cpp -o pp && ./pp
```

```text
传左值给 by_value：
  拷贝构造 A
  by_value(A)
传右值给 by_value：
  移动构造 B
  by_value(B)
传左值给 by_const_ref：
  by_const_ref(A)
传右值给 by_rvalue_ref：
  by_rvalue_ref(C)
字符串参数：
  string_view: hello world (len=11)
  string_view: 字面量 (len=9)
  const string&: hello world
```

"字面量"长度是 9 —— UTF-8 下三个汉字各占 3 字节，`std::string_view::size()` 数的是字节数不是字符数。这点在切分中文时经常翻车。

### 10.2.2 `std::string_view` 的适用边界与悬垂
{: .sec-know}

`std::string_view`（C++17，头文件 `<string_view>`）是"指针 + 长度"的一对，通常是 16 字节，按值传比引用还便宜。三条硬规则：

1. **它不拥有数据。** 只看，不负责活多久。
2. **不以 `'\0'` 结尾。** `sv.data()` 传给 `strlen`、`fopen` 这类 C API 会越界读。需要 C 串时用 `std::string(sv)` 转一份。
3. **别拿它持有临时量的视图。** 临时对象在全表达式结束时销毁，`string_view` 立刻悬垂。

```cpp
// sv_dangling.cpp —— 需要 -std=c++17
#include <iostream>
#include <string>
#include <string_view>

std::string_view good() {
    return "字面量";                 // 安全：字符串字面量有静态存储期
}

std::string_view bad() {
    std::string s = "临时字符串";
    return std::string_view(s);      // 悬垂：s 在函数返回时销毁
}

int main() {
    std::cout << "good() = " << good() << '\n';

    std::string_view d = bad();      // undefined behavior：读已销毁对象的内存
    std::cout << "bad()  = " << d << '\n';

    std::string_view d2 = std::string("又一次悬垂");  // 同样悬垂：临时 string 在这行结束就销毁
    std::cout << "d2     = " << d2 << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra sv_dangling.cpp -o sv && ./sv
```

```text
good() = 字面量
bad()  = （内容不确定，可能是乱码或空）
d2     = （内容不确定）
```

> **坑：** 这段代码是 **undefined behavior**，`-Wall` 下 GCC 会给 `-Wdangling-reference` 或 `-Wreturn-local-addr` 之类的提示，但不同版本提示强度不同，别指望它。正确写法二选一：函数返回 `std::string`（拥有数据），或者让调用方传入缓冲区/`string_view`。判断口诀——**`string_view` 适合当参数，不适合当返回值，更不适合当成员变量**，除非你能证明被视图的那个对象活得更久。
{: .sec-pit}

### 10.2.3 默认参数：只能在声明处给一次
{: .sec-know}

默认实参的三条规则：

1. **只能出现一次。** 通常写在头文件声明里，.cpp 的定义里不能再写。
2. **必须从右往左连续。** 有默认值的参数右边不能有没有默认值的。
3. **默认实参里不能用局部变量，也不能用其他形参**（实参求值顺序未指定，标准直接禁止）。

```cpp
// log.h
#pragma once
#include <string>

void log_line(const std::string& msg, int level = 1, bool flush = false);
```

```cpp
// log.cpp
#include "log.h"
#include <iostream>

// 定义处不能重复写 = 1 和 = false，否则是"重定义默认实参"错误
void log_line(const std::string& msg, int level, bool flush) {
    std::cout << "[L" << level << "] " << msg << '\n';
    if (flush) std::cout.flush();
}
```

```cpp
// use_log.cpp
#include "log.h"

int main() {
    log_line("默认级别");
    log_line("高级别", 3);
    log_line("高级别且刷新", 3, true);
}
```

```bash
g++ -std=c++20 -Wall -Wextra use_log.cpp log.cpp -o lg && ./lg
```

```text
[L1] 默认级别
[L3] 高级别
[L3] 高级别且刷新
```

默认实参是在**调用点**展开的，每次调用都会重新求值，而且调用方必须能看到它——这也是它必须放头文件的技术原因之一。

### 10.2.4 默认参数与重载冲突
{: .sec-ts}

两个坑，都很常见。

**坑一：默认实参造出调用歧义。**

```cpp
void draw(int x, int y = 0);
void draw(int x);

// draw(5);   // 编译错误：两个候选都精确匹配，歧义
```

这段是**故意写错**的代码，编译会失败：

```text
error: call of overloaded 'draw(int)' is ambiguous
```

**坑二：虚函数的默认实参是静态绑定的。** 这是经典得不能再经典的坑——默认实参按**调用表达式的静态类型**取，而函数体按动态类型派发。两者来自不同的地方，于是出现了"调了派生类的函数，用的是基类的默认值"。

```cpp
// vdefault.cpp —— 需要 -std=c++20
#include <iostream>

struct Base {
    virtual ~Base() = default;
    virtual void greet(int times = 1) {
        std::cout << "Base::greet times=" << times << '\n';
    }
};

struct Derived : Base {
    void greet(int times = 3) override {          // 默认值 3 在这里根本不会被用到
        std::cout << "Derived::greet times=" << times << '\n';
    }
};

int main() {
    Derived d;
    Base& b = d;

    d.greet();      // 静态类型 Derived → 用 3
    b.greet();      // 静态类型 Base    → 用 1，但执行的还是 Derived::greet
    Base* p = &d;
    p->greet();     // 同上：用 1
}
```

```bash
g++ -std=c++20 -Wall -Wextra vdefault.cpp -o vd && ./vd
```

```text
Derived::greet times=3
Derived::greet times=1
Derived::greet times=1
```

后两行就是坑本身：函数名是 `Derived::greet`，参数是 `1`。规避办法三条：

1. **派生类不要改默认实参**（最好干脆不写，让基类那个生效，至少行为一致）；
2. 用 **非虚接口惯用法（NVI）**：基类提供非虚的公有函数负责默认实参，虚函数在下面不带默认值；
3. 默认实参换成重载：`void greet()` 调 `greet(1)`。

NVI 写法是这样：

```cpp
struct Base {
    virtual ~Base() = default;
    void greet(int times = 1) { do_greet(times); }   // 非虚，默认实参在这里，只有一处
protected:
    virtual void do_greet(int times) = 0;            // 虚函数不带默认值
};
```

这个结构顺带还解决了"公有接口统一加日志/加锁"的问题，代价是多一层函数调用。

### 10.2.5 重载决议：六档排序
{: .sec-know}

一次函数调用要经过三步：**名字查找**得到候选集 → 模板实例化/推导 → **重载决议**挑最好的。挑的规则是"逐个实参比较转换序列的等级，取所有实参上都不差、且至少一个更好的那个"。

排序从优到劣分六层：前五层是转换序列的等级，第六层是模板与非模板之间的取舍：

| 档位 | 含义 | 例子 |
| --- | --- | --- |
| 1 精确匹配 | 无需转换，或只加 `const`/退化 | `int` → `int`、`int[5]` → `int*`、`T` → `const T&` |
| 2 提升 | 整型提升、浮点提升 | `char` → `int`、`short` → `int`、`float` → `double` |
| 3 转换 | 整型转换、浮点-整型互转、指针转换、bool 转换 | `int` → `double`、`int` → `long`、`0` → `char*`、`int*` → `bool` |
| 4 用户定义转换 | 转换构造函数、转换运算符（整个序列里最多一次） | `std::string` ← `const char*` |
| 5 省略号 | 匹配 `...` | `f(...)` |
| 6 模板 | 非模板优先；模板之间比"谁更特化" | `template<class T> f(T)` vs `f(int)` |

模板那一档要单独说清楚：**当非模板和模板的转换序列一样好时，选非模板**；只有模板之间才做偏序（partial ordering）比较。这解释了为什么 `f(int)` 会赢 `template<class T> f(T)`——不是因为更特化，而是因为规则直接写死了非模板优先。

```cpp
// overload.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

void pick(int)         { std::cout << "pick(int)\n"; }
void pick(double)      { std::cout << "pick(double)\n"; }
void pick(const char*) { std::cout << "pick(const char*)\n"; }

template <class T>
void pick_t(T)         { std::cout << "pick_t(T)\n"; }
void pick_t(int)       { std::cout << "pick_t(int)  ← 非模板优先\n"; }

int main() {
    pick('a');       // char→int 是提升(2)，char→double 是转换(3)，char→const char* 不可行 → int
    pick(3.14f);     // float→double 是提升(2)，float→int 是转换(3) → double
    pick(42);        // 精确匹配 int
    pick(0);         // 0 既是 int 又是空指针常量；精确匹配 int 赢过指针转换
    pick(nullptr);   // nullptr 只能转 const char*

    pick_t(42);      // 非模板赢
    pick_t(3.14);    // 只有模板可行
}
```

```bash
g++ -std=c++20 -Wall -Wextra overload.cpp -o ov && ./ov
```

```text
pick(int)
pick(double)
pick(int)
pick(int)
pick(const char*)
pick_t(int)  ← 非模板优先
pick_t(T)
```

歧义长什么样？把上面 `pick` 的重载换成 `void pick(long)` 和 `void pick(double)`，再调 `pick(42)`：`int→long` 是转换，`int→double` 也是转换，同档且分不出优劣 → 歧义。这也是 `f(NULL)` 在 `f(int)` 与 `f(char*)` 之间出问题的根源——`NULL` 的定义由实现决定，是 `0L` 这类整型字面量时两边都落在转换档。解法永远是用 `nullptr` 和显式的 `static_cast`，而不是加更多重载。

### 辨析：重载、覆盖、隐藏
{: .sec-iv}

三个词常被混着说，机制完全不同：

| 概念 | 发生位置 | 决议时机 |
| --- | --- | --- |
| 重载 overload | 同一作用域的同名函数 | 编译期，按实参类型 |
| 覆盖 override | 基类虚函数与派生类虚函数 | 运行期，按对象动态类型 |
| 隐藏 hide | 派生类同名函数遮住基类所有同名函数 | 编译期，按名字查找 |

隐藏最坑：派生类里写了 `void f(int)`，基类的 `void f(double)` 和 `void f(std::string)` 就全被遮住了，即使签名不同。想让基类的同名函数一起参与重载，得在派生类里写 `using Base::f;`。

### 10.2.6 现代拓展：用 concept 收窄候选集
{: .sec-ext}

C++20 之前，模板重载的约束要靠 SFINAE 写 `std::enable_if_t`，出错信息长得吓人。现在用 `requires` 直接表达意图，候选集在决议**之前**就被筛掉，歧义自然变少：

```cpp
#include <concepts>
#include <iostream>

void show(std::integral auto v)      { std::cout << "整型 " << v << '\n'; }
void show(std::floating_point auto v){ std::cout << "浮点 " << v << '\n'; }
void show(std::string_view v)        { std::cout << "字符串 " << v << '\n'; }

int main() {
    show(42);        // 整型
    show(3.14);      // 浮点
    show("文本");     // 字符串
    // show(nullptr);  // 编译错误，且报错会说"没有满足约束的重载"
}
```

这个例子不需要单独编译命令，和上一段一样用 `-std=c++20` 即可。它的价值在于：出错信息从"模板推导失败的几百行"变成"没有匹配的重载"。

## 10.3 返回值和返回语句
{: .sec-expl}

### 10.3.1 返回引用/指针不能指向局部对象
{: .sec-know}

局部自动对象在函数返回时销毁，返回它的引用或指针就是悬垂。这条规则人人会背，但变形很多：

```cpp
// ret_ref.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

const std::string& bad_ref() {
    std::string s = "局部";
    return s;                     // 悬垂引用
}

const char* bad_cstr() {
    std::string s = "局部";
    return s.c_str();             // 悬垂指针，而且连 std::string 也没了
}

int& bad_elem() {
    int arr[3] = {1, 2, 3};
    return arr[0];                // 悬垂
}

// 正确：返回静态存储期对象（注意 10.8 会讲它的线程隐患）
const std::string& ok_static() {
    static const std::string s = "静态";
    return s;
}

// 正确：返回调用方给的对象的成员
const std::string& ok_member(const std::string& s) { return s; }

// 正确：直接返回值
std::string ok_value() { return std::string("值"); }

int main() {
    std::cout << ok_static() << '\n';
    std::cout << ok_member(ok_value()) << '\n';   // 临时量活到整个全表达式结束，安全
    std::cout << ok_value() << '\n';

    const std::string& r = bad_ref();             // undefined behavior
    std::cout << "bad_ref() = " << r << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra ret_ref.cpp -o rr && ./rr
```

```text
warning: reference to local variable 's' returned
静态
值
值
bad_ref() = （内容不确定）
```

> **警告：** 前三处 `return` 都是 **undefined behavior**。GCC 会给出 `-Wreturn-local-addr`（在 `-Wall` 里），Clang 同理，但**返回 `std::string::c_str()` 这种间接形式经常躲过告警**。这就是为什么 AI 生成或手滑写出的这类代码能在测试环境跑通，上线后随机崩。判断口诀：看到 `return` 后面跟的东西是函数内声明的非 `static` 变量（或者它的成员/地址），一律红灯。
{: .sec-warn}

### 10.3.2 NRVO 与返回局部对象的隐式移动
{: .sec-know}

返回大对象看起来很贵，实际上有两层优化叠着：

1. **NRVO（Named Return Value Optimization）**：返回语句的操作数是函数内的具名局部对象，且类型与返回类型一致时，编译器可以直接在调用者的栈空间上构造它，构造/拷贝/移动全部省掉。
2. **隐式移动（C++11 起）**：即使 NRVO 没发生，返回语句里的具名局部对象也会被**先当右值**去做重载决议，于是走移动构造而不是拷贝构造。C++20（P1825）与 C++23（P2266）又放宽了适用情形。

关键是：NRVO 是**允许**省略，不是**要求**，所以构造/析构的次数不是标准保证的行为，只有"结果正确"是。

```cpp
// nrvo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <utility>

struct Big {
    std::string tag;
    explicit Big(std::string t) : tag(std::move(t)) { std::cout << "构造 " << tag << '\n'; }
    Big(const Big& o) : tag(o.tag)                  { std::cout << "拷贝 " << tag << '\n'; }
    Big(Big&& o) noexcept : tag(std::move(o.tag))   { std::cout << "移动 " << tag << '\n'; }
    ~Big()                                          { std::cout << "析构 " << tag << '\n'; }
};

Big make_nrvo() {
    Big b("nrvo");
    return b;                       // NRVO：理想情况下一次构造，零拷贝零移动
}

Big make_move() {
    Big b("move");
    return std::move(b);            // 画蛇添足：挡住 NRVO，强制走移动构造
}

Big make_pick(bool left) {
    Big a("left"), b("right");
    if (left) return a;             // 两个候选返回点，NRVO 常常失效 → 走隐式移动
    return b;
}

int main() {
    std::cout << "--- make_nrvo ---\n";
    Big x = make_nrvo();
    std::cout << "x.tag = " << x.tag << '\n';

    std::cout << "--- make_move ---\n";
    Big y = make_move();
    std::cout << "y.tag = " << y.tag << '\n';

    std::cout << "--- make_pick ---\n";
    Big z = make_pick(true);
    std::cout << "z.tag = " << z.tag << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra nrvo.cpp -o nrvo && ./nrvo
```

```text
--- make_nrvo ---
构造 nrvo
x.tag = nrvo
--- make_move ---
构造 move
移动 move
析构 move
y.tag = move
--- make_pick ---
构造 left
构造 right
移动 left
析构 right
析构 left
z.tag = left
--- 程序结束前 ---
析构 left
析构 move
析构 nrvo
```

> **坑：** `return std::move(x);` 是负优化，不是优化。它把"具名局部对象"变成了"xvalue 表达式"，NRVO 的条件（操作数必须是对象名）不再满足，结果多一次移动构造。写 `return x;` 就够了——NRVO 不成还有隐式移动兜底。唯一该写 `std::move` 的返回场景是返回**非局部**对象（比如成员、参数）且你确实要搬走它。
{: .sec-pit}

想亲眼看见 NRVO 消失，加 `-fno-elide-constructors` 重新编译，第一段就会多出一次移动构造。

### 10.3.3 `auto` / `decltype(auto)` / 尾返回类型
{: .sec-know}

C++11 给了尾返回类型，C++14 给了返回类型推导：

```cpp
auto add(int a, int b) -> int { return a + b; }            // 尾返回类型，C++11
auto add2(int a, int b) { return a + b; }                  // 推导为 int，C++14
decltype(auto) get_ref(int& x) { return x; }               // 保留引用 → int&，C++14
```

三者的取舍：

| 写法 | 特点 | 用在 |
| --- | --- | --- |
| `auto` | 按值推导，剥掉引用和顶层 const | 返回纯值，且类型写起来太长（迭代器、lambda 结果） |
| `decltype(auto)` | 完整保留引用与 const | 泛型包装器，必须精确转发被包装函数的返回类型 |
| 尾返回类型 | 能用形参名参与类型计算 | 返回类型依赖参数（`-> decltype(a + b)`）、函数指针/数组返回 |
| 显式写出 | 最清楚，还能做接口文档 | 公共 API |

两个必须知道的问题：

**问题一：多个 `return` 推导结果不一致。**

```cpp
auto f(bool b) {
    if (b) return 42;      // int
    return 3.14;           // double → 推导冲突
}
```

```text
error: inconsistent deduction for auto return type: 'int' and then 'double'
```

**问题二：`decltype(auto)` 的括号陷阱。** `return x;` 推导为声明类型，`return (x);` 推导为 `int&`——多一对括号就变成悬垂引用（见 6.3.8）。所以普通函数别用 `decltype(auto)`，它不是"更精确的 auto"，是"更容易出事的 auto"。

尾返回类型的经典用途——返回数组引用：

```cpp
// ret_auto.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <vector>

auto make_table() -> std::vector<std::vector<int>> {   // 类型太长时的可读性写法
    return {{1, 2}, {3, 4}};
}

template <class T, class U>
auto add_expr(const T& a, const U& b) -> decltype(a + b) {   // 返回类型依赖参数运算
    return a + b;
}

auto& element_at(std::vector<std::string>& v, std::size_t i) -> std::string& {
    return v[i];
}

int main() {
    auto t = make_table();
    std::cout << "t[1][0] = " << t[1][0] << '\n';
    std::cout << "add_expr = " << add_expr(std::string("ab"), std::string("cd")) << '\n';

    std::vector<std::string> v{"x", "y"};
    element_at(v, 1) = "Z";
    std::cout << "v[1] = " << v[1] << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra ret_auto.cpp -o ra && ./ra
```

```text
t[1][0] = 3
add_expr = abcd
v[1] = Z
```

### 10.3.4 用 `std::optional` 与 `std::expected` 传错误
{: .sec-ext}

"返回值 vs 出参 vs 异常"的老问题，现代 C++ 的答案是按语义分层：

| 场景 | 返回类型 |
| --- | --- |
| 一定成功 | `T` |
| 可能"没有结果"，且没有额外信息 | `std::optional<T>`（C++17） |
| 可能失败，且要带错误码/错误类型 | `std::expected<T, E>`（C++23） |
| 异常、不可恢复 | 抛异常 |

`std::expected` 是 C++23 加进来的（头文件 `<expected>`），本质是个"要么有值要么有错误"的联合体，比 `optional` 多了错误信息通道，比异常少了栈展开开销。GCC 12 起、Clang 16 起提供该头文件。

```cpp
// expected_demo.cpp —— 需要 -std=c++23（libstdc++ 12+ / libc++ 16+）
#include <expected>
#include <iostream>
#include <string_view>

enum class ParseErr { Empty, NotDigit, OutOfRange };

const char* to_str(ParseErr e) {
    switch (e) {
        case ParseErr::Empty:      return "空输入";
        case ParseErr::NotDigit:   return "含非数字字符";
        case ParseErr::OutOfRange: return "超出范围";
    }
    return "未知";
}

std::expected<int, ParseErr> parse_positive(std::string_view s) {
    if (s.empty()) return std::unexpected(ParseErr::Empty);
    long long v = 0;
    for (char c : s) {
        if (c < '0' || c > '9') return std::unexpected(ParseErr::NotDigit);
        v = v * 10 + (c - '0');
        if (v > 1000) return std::unexpected(ParseErr::OutOfRange);
    }
    if (v == 0) return std::unexpected(ParseErr::OutOfRange);
    return static_cast<int>(v);
}

int main() {
    for (std::string_view s : {"42", "7a", "", "99999"}) {
        auto r = parse_positive(s);
        if (r) {
            std::cout << "解析 \"" << s << "\" 成功：" << *r << '\n';
        } else {
            std::cout << "解析 \"" << s << "\" 失败：" << to_str(r.error()) << '\n';
        }
    }

    auto fallback = parse_positive("abc").value_or(-1);   // 出错就用一个兜底值
    std::cout << "fallback = " << fallback << '\n';
}
```

```bash
g++ -std=c++23 -Wall -Wextra expected_demo.cpp -o ex && ./ex
```

```text
解析 "42" 成功：42
解析 "7a" 失败：含非数字字符
解析 "" 失败：空输入
解析 "99999" 失败：超出范围
fallback = -1
```

`std::optional` 那边的对应写法是 `has_value()` / `value()` / `value_or()`；C++23 又给它补了 `and_then` / `transform` / `or_else` 三个单子式操作（monadic operations），可以链式处理而不写一堆 `if`。

## 10.4 调用函数
{: .sec-expl}

### 10.4.1 调用约定与栈帧
{: .sec-know}

**调用约定（calling convention）**是 ABI 的一部分，规定：参数进寄存器还是压栈、按什么顺序、由调用方还是被调方清理栈、返回值放哪里。C++ 标准不规定这些，各平台自己定：

- Linux x86-64 用 SysV AMD64 ABI：前 6 个整型/指针参数进 `rdi, rsi, rdx, rcx, r8, r9`，浮点进 `xmm0~xmm7`，返回值在 `rax`（`rdx` 辅助）。
- Windows x86-64 用 `RCX, RDX, R8, R9`。
- x86（32 位）上 Windows 才有所谓 `__cdecl` / `__stdcall` / `__fastcall` 的区别；到 x86-64 两边都统一了。

`extern "C"` 改的是**名字修饰（name mangling）**，让 C++ 函数能被 C 链接器找到，**不改调用约定**。混为一谈是常见误解。

**栈帧（stack frame）**是每次调用在栈上开的一块区域，通常装：返回地址、调用者的帧基址、需要保存的寄存器、局部变量、放不进寄存器的参数。开 `-O2` 后编译器常省略帧指针（`-fomit-frame-pointer` 在多数 64 位目标是默认），栈帧布局也未必和你脑中的模型一致，但"深度随递归增长"这件事不变。

一个和栈帧直接相关的坑：**实参求值顺序未指定**。C++17 之前连"是否交错"都没规定，C++17 起规定不交错，但顺序仍然是未指定的：

```cpp
// eval_order.cpp —— 需要 -std=c++20
#include <iostream>

int side(int x) { std::cout << "计算 " << x << '\n'; return x; }

void three(int a, int b, int c) {
    std::cout << "收到 " << a << ' ' << b << ' ' << c << '\n';
}

int main() {
    int i = 0;
    three(side(++i), side(++i), side(++i));   // 实参求值顺序未指定，同时修改 i
}
```

```bash
g++ -std=c++20 -Wall -Wextra eval_order.cpp -o eo && ./eo
```

```text
计算 1
计算 2
计算 3
收到 3 2 1
```

这段输出在 GCC 上是这样（GCC 从右往左求值实参），但 Clang 和 MSVC 的顺序可能不同，而同一表达式里三次 `++i` 之间的副作用没有被排序——这是 **undefined behavior**。别写这种代码，先算到变量里再传。

### 10.4.2 挂起与恢复：协程门径（C++20）
{: .sec-ext}

栈帧讲到这里正好接协程：普通函数的帧在返回时销毁，协程的帧要活过"返回"。

C++20 的协程是**无栈协程（stackless coroutine）**：编译器把函数体切成若干段，把跨挂起点需要保留的局部变量放进一块堆上（或就地优化掉）的**协程帧（coroutine frame）**，挂起时保存当前位置，恢复时从该位置继续。

三件套：

| 组件 | 作用 |
| --- | --- |
| `promise_type` | 决定协程对外的行为：`get_return_object`、`initial_suspend`、`final_suspend`、`yield_value`、`return_value`/`return_void`、`unhandled_exception` |
| `coroutine_handle<P>` | 调用方手里的把手：`resume()`、`done()`、`destroy()`、`promise()` |
| awaiter | `co_await` 的对象，提供 `await_ready` / `await_suspend` / `await_resume` |

三个关键字：`co_await`（挂起等待）、`co_yield`（产出一个值并挂起）、`co_return`（结束）。

标准只给了机制没给库——这是有意的。协程的语义需求差异太大（生成器、异步任务、惰性求值、状态机），标准库里塞一个具体实现会锁死设计。所以 C++20 只提供 `<coroutine>` 里那套底层 Vocabulary 类型，具体协程类型由你或第三方库写。C++23 才补了第一个标准协程类型 `std::generator`（见 10.4.4）。

手写一个最小生成器，把三件套都过一遍：

```cpp
// coro_generator.cpp —— 需要 -std=c++20（GCC 10/11 需额外加 -fcoroutines）
#include <coroutine>
#include <exception>
#include <iostream>
#include <string>
#include <utility>

template <class T>
class Generator {
public:
    struct promise_type {
        T value{};
        std::exception_ptr eptr{};

        Generator get_return_object() {
            return Generator{std::coroutine_handle<promise_type>::from_promise(*this)};
        }
        std::suspend_always initial_suspend() noexcept { return {}; }
        std::suspend_always final_suspend() noexcept   { return {}; }
        std::suspend_always yield_value(T v) { value = std::move(v); return {}; }
        void return_void() {}
        void unhandled_exception() { eptr = std::current_exception(); }
    };

    explicit Generator(std::coroutine_handle<promise_type> h) : h_(h) {}
    Generator(const Generator&) = delete;
    Generator& operator=(const Generator&) = delete;
    Generator(Generator&& other) noexcept : h_(other.h_) { other.h_ = nullptr; }
    Generator& operator=(Generator&& other) noexcept {
        if (this != &other) {
            if (h_) h_.destroy();
            h_ = other.h_;
            other.h_ = nullptr;
        }
        return *this;
    }
    ~Generator() { if (h_) h_.destroy(); }

    bool next() {
        if (!h_ || h_.done()) return false;
        h_.resume();
        if (h_.promise().eptr) std::rethrow_exception(h_.promise().eptr);
        return !h_.done();
    }
    const T& value() const { return h_.promise().value; }

private:
    std::coroutine_handle<promise_type> h_{};
};

Generator<int> range_to(int from, int to) {
    for (int i = from; i < to; ++i) {
        co_yield i;                       // 挂起，把 i 交给调用方
    }
}

Generator<long long> fib(int n) {
    long long a = 0, b = 1;
    for (int i = 0; i < n; ++i) {
        co_yield a;
        long long t = a + b;
        a = b;
        b = t;
    }
}

int main() {
    std::cout << "range: ";
    auto r = range_to(1, 6);
    while (r.next()) std::cout << r.value() << ' ';
    std::cout << '\n';

    std::cout << "fib:   ";
    for (auto f = fib(8); f.next(); ) std::cout << f.value() << ' ';
    std::cout << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra coro_generator.cpp -o coro && ./coro
```

```text
range: 1 2 3 4 5
fib:   0 1 1 2 3 5 8 13
```

几个必须知道的点：

- `initial_suspend` 是 `suspend_always`，所以协程创建后**不执行任何代码**，第一次 `resume()` 才跑到第一个 `co_yield`。想要创建即运行，把它改成 `suspend_never`。
- `final_suspend` 必须是 `suspend_always`，否则协程结束后帧已被销毁，`done()` 和 `promise()` 都不能再用——这是硬性要求。
- 协程帧默认用 `operator new` 分配。编译器在帧大小可静态确定且协程不逃逸时可能做 **HALO（coroutine elision）** 把它优化掉，但别依赖。**热点路径上每个协程一次堆分配是真实成本**，需要在 promise 里自定义 `operator new`（支持预分配缓冲）或者用第三方库的协程池。
- 协程不是线程。它没有自己的栈，也不并行；`co_await` 让出的是当前线程的执行权。并发要自己组合线程或事件循环。

### 10.4.3 协程与线程、回调的对比
{: .sec-iv}

| 维度 | 回调（callback） | 线程 | 协程 |
| --- | --- | --- | --- |
| 代码形态 | 割裂，状态要自己存 | 接近同步写法 | 接近同步写法 |
| 栈 | 无 | 独立栈（默认几 MB） | 协程帧（几十到几百字节） |
| 切换成本 | 一次函数调用 | 内核态切换，微秒级 | 一次跳转，纳秒级 |
| 并行 | 不并行 | 真并行 | 不并行（单线程上复用） |
| 典型问题 | 回调地狱、状态管理 | 数据竞争、锁 | 生命周期、帧分配 |

选型一句话：要**并行计算**用线程；要**高并发 I/O 且保持同步写法**用协程；只是简单通知一下用回调就够了，别上协程。

### 10.4.4 `std::generator`（C++23）
{: .sec-ext}

C++23 有了标准生成器 `std::generator<T>`（头文件 `<generator>`），它就是上面手写的那个东西的标准版，且实现了 `ranges::view_interface`，可以直接接 ranges 管道：

```cpp
// std_generator.cpp —— 需要 -std=c++23 且标准库提供 <generator>
#include <generator>
#include <iostream>
#include <ranges>

std::generator<int> squares(int n) {
    for (int i = 0; i < n; ++i) {
        co_yield i * i;
    }
}

int main() {
    for (int v : squares(6)) {
        std::cout << v << ' ';
    }
    std::cout << '\n';

    // 接 ranges：过滤后只留偶数平方
    for (int v : squares(6) | std::views::filter([](int x) { return x % 2 == 0; })) {
        std::cout << v << ' ';
    }
    std::cout << '\n';
}
```

```text
0 1 4 9 16 25
0 4 16
```

支持情况要提醒：`<generator>` 是 C++23 才进标准的，各标准库落地较晚（libstdc++ 与 libc++ 都是较新版本才提供）。编译不过就先用手写的 `Generator`，接口对齐，将来替换成本很低。

## 10.5 函数递归
{: .sec-expl}

### 10.5.1 基线条件与递归三要素
{: .sec-know}

递归成立要三样东西：**基线条件（base case）**、**递归步骤**、**每次递归都朝基线靠近**。缺任何一条都是死循环或栈溢出。

```cpp
// recursion.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

unsigned long long factorial(unsigned n) {          // 基线：n <= 1
    return n <= 1 ? 1 : n * factorial(n - 1);
}

unsigned long long fib_naive(unsigned n) {          // 指数复杂度，只用来演示
    return n <= 1 ? n : fib_naive(n - 1) + fib_naive(n - 2);
}

void print_digits(unsigned n) {                     // 递归顺序决定输出顺序
    if (n >= 10) print_digits(n / 10);
    std::cout << static_cast<char>('0' + n % 10) << ' ';
}

std::string reverse_copy(std::string_view s) {
    if (s.empty()) return {};
    return reverse_copy(s.substr(1)) + s.front();   // 注意：这里有 O(n^2) 的拷贝
}

int main() {
    std::cout << "10! = " << factorial(10) << '\n';
    std::cout << "fib(20) = " << fib_naive(20) << '\n';
    std::cout << "各位数字：";
    print_digits(2048);
    std::cout << '\n';
    std::cout << "逆序 = " << reverse_copy("hello") << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra recursion.cpp -o rec && ./rec
```

```text
10! = 3628800
fib(20) = 6765
各位数字：2 0 4 8
逆序 = olleh
```

`fib_naive(20)` 已经要算一万多次调用了，到 40 会明显卡住——不是栈溢出，是重复计算。这种"重叠子问题"应当改成迭代或加记忆化。

### 10.5.2 栈溢出风险
{: .sec-know}

每次调用都要一个栈帧，深度太大就爆栈。栈上限取决于平台：

- Linux 主线程默认栈通常 8 MB（用 `ulimit -s` 查，单位是 KB）；`pthread` 创建的线程栈大小由 `pthread_attr_setstacksize` 决定，glibc 默认也是 8 MB 量级。
- Windows 默认栈由链接器 `/STACK` 决定，常见 1 MB（MSVC 默认 1 MB）。
- 嵌入式和协程栈会更小。

所以"递归深度 100 万"在任何平台上都别想。爆栈的表现是 `SIGSEGV`，且往往没有栈回溯——因为回溯自己也要用栈。

```cpp
// stack_blow.cpp —— 需要 -std=c++20，演示深度过大，请勿在生产环境模仿
#include <iostream>

long long depth_sum(int n) {
    if (n == 0) return 0;
    return n + depth_sum(n - 1);
}

int main() {
    std::cout << "depth_sum(100000) = " << depth_sum(100000) << '\n';   // 通常没问题
    // std::cout << depth_sum(10000000) << '\n';   // 极可能 SIGSEGV
}
```

```bash
g++ -std=c++20 -Wall -Wextra stack_blow.cpp -o sb && ./sb
```

```text
depth_sum(100000) = 5000050000
```

注释掉那行在栈只有 1 MB 的环境（比如 Windows 默认配置）即使 10 万层也可能爆。**深度来自外部输入时，递归就是拒绝服务漏洞**——解析不可信的 JSON、XML、表达式树时尤其要小心。

### 10.5.3 尾递归为什么 C++ 不保证优化
{: .sec-know}

尾递归（tail recursion）指递归调用是函数最后一步、返回值直接被返回。很多语言（Scheme、OCaml、Erlang）保证把它编译成循环，C++ 标准**不保证**。理由是两条很实在的：

1. **析构语义。** C++ 的局部对象在返回时析构，顺序是"先算返回值，再析构局部变量，再返回"。如果编译器把尾调用改写成跳回函数开头，那些析构就被跳过了；要让优化合法，必须先析构、再跳转，而标准没要求编译器做这个分析，也没禁止——所以是"实现自定义"。
2. **ABI 与调试。** 尾调用优化会抹掉栈帧，调试器和栈回溯就看不到中间层。GCC/Clang 在 `-O2` 下经常做，但一旦局部变量有非平凡析构、或者开了 `-fno-optimize-sibling-calls`，就没了。

结论：**不要依赖 TCO**。要迭代就自己写迭代。

```cpp
// tail_to_loop.cpp —— 需要 -std=c++20
#include <chrono>
#include <iostream>

// 尾递归写法：可读性还行，但性能取决于编译器心情
long long sum_tail(long long n, long long acc) {
    return n == 0 ? acc : sum_tail(n - 1, acc + n);
}

// 迭代写法：O(1) 栈，任何优化等级都一样
long long sum_loop(long long n) {
    long long acc = 0;
    for (long long i = n; i > 0; --i) acc += i;
    return acc;
}

int main() {
    constexpr long long N = 20000000;
    std::cout << "sum_loop(N) = " << sum_loop(N) << '\n';

    auto t0 = std::chrono::steady_clock::now();
    long long a = sum_loop(N);
    auto t1 = std::chrono::steady_clock::now();
    std::cout << "迭代耗时 "
              << std::chrono::duration_cast<std::chrono::milliseconds>(t1 - t0).count()
              << " ms\n";

    auto t2 = std::chrono::steady_clock::now();
    long long b = sum_tail(N, 0);
    auto t3 = std::chrono::steady_clock::now();
    std::cout << "尾递归耗时 "
              << std::chrono::duration_cast<std::chrono::milliseconds>(t3 - t2).count()
              << " ms（相同结果：" << (a == b ? "是" : "否") << "）\n";
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra tail_to_loop.cpp -o ttl && ./ttl
```

```text
sum_loop(N) = 200000010000000
迭代耗时 14 ms
尾递归耗时 14 ms（相同结果：是）
```

这份输出来自开 `-O2` 的环境，两个耗时接近说明 GCC 确实做了尾调用优化。**换成 `-O0` 再跑一次，尾递归版本会明显变慢甚至爆栈**——这个对比就是"别依赖 TCO"的实证。计时数字本身没有可比性，只看同一台机器上两种写法的相对关系。

### 辨析：递归与迭代怎么选
{: .sec-iv}

| 判据 | 选递归 | 选迭代 |
| --- | --- | --- |
| 结构 | 问题本身是递归定义的（树遍历、表达式解析、分治） | 线性结构、计数求和 |
| 深度 | 有明确上界且很小（树的高度、几百以内） | 深度来自外部输入或可达数万 |
| 子问题 | 不重叠（快排、归并） | 重叠（斐波那契、DP）→ 迭代或记忆化 |
| 可读性 | 递归明显更短 | 两者差不多 |

经验法则：**树和分治用递归，链和计数用迭代。** 深度不可控时，改成显式栈（`std::vector` 或 `std::stack` 手动维护状态）是通用的脱递归手段。

## 10.6 指向函数的指针
{: .sec-expl}

### 10.6.1 语法与 `using` 别名
{: .sec-know}

函数指针的语法因为要把变量名夹在类型中间而格外难读，所以现代写法一律走别名：

```cpp
int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int (*fp)(int, int) = add;                 // 传统写法：变量名被夹在中间

using BinOp   = int(int, int);             // 函数类型的别名（C++11）
using BinOpP  = int (*)(int, int);         // 函数指针类型的别名

BinOp*  f1 = add;                          // 函数类型加一颗星就是指针
BinOpP  f2 = &add;                         // 取地址符可写可不写，函数会退化成指针
```

调用时 `fp(1, 2)` 和 `(*fp)(1, 2)` 都合法，后者更贴近"解引用"的语义，前者更常用。

### 10.6.2 数组形参与函数形参都会退化
{: .sec-know}

两条退化规则，都是 C 遗产：

- 形参写成数组，实际类型是指针：`void f(int a[10])` 等价于 `void f(int* a)`，那个 `10` 是给人看的，编译器不管。想保留数组大小，写成引用：`void f(int (&a)[10])`，或者用 `std::span`（C++20）。
- 形参写成函数，实际类型是函数指针：`void g(int h(int))` 等价于 `void g(int (*h)(int))`。

```cpp
// fptr.cpp —— 需要 -std=c++20
#include <array>
#include <cstddef>
#include <iostream>
#include <span>

int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }
int mul(int a, int b) { return a * b; }

using BinOpP = int (*)(int, int);

// 数组形参退化：这三个声明是完全同一个函数
void sum_ptr(int* data, std::size_t n, int& out) { for (std::size_t i = 0; i < n; ++i) out += data[i]; }
// void sum_arr(int data[10], std::size_t n, int& out);   // 与上面冲突，是同一个签名

// 保留数组大小：用引用
void sum_fixed(int (&arr)[4], int& out) { for (int v : arr) out += v; }

// 现代写法：span 同时带指针和长度
void sum_span(std::span<const int> data, int& out) { for (int v : data) out += v; }

// 函数形参退化成函数指针
int apply(int (*op)(int, int), int a, int b) { return op(a, b); }

int main() {
    BinOpP table[3] = {add, sub, mul};            // 函数指针数组，最经典的查表分发
    const char* names[3] = {"add", "sub", "mul"};
    for (int i = 0; i < 3; ++i) {
        std::cout << names[i] << "(7, 3) = " << table[i](7, 3) << '\n';
    }

    int arr[4] = {1, 2, 3, 4};
    int acc = 0;
    sum_ptr(arr, 4, acc);
    sum_fixed(arr, acc);
    sum_span(std::span<const int>(arr, 4), acc);
    std::cout << "累加三轮 = " << acc << '\n';

    std::cout << "apply(add, 2, 5) = " << apply(add, 2, 5) << '\n';
    std::cout << "sizeof(fp) = " << sizeof(BinOpP)
              << "，sizeof(int[4]) = " << sizeof(arr) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra fptr.cpp -o fptr && ./fptr
```

```text
add(7, 3) = 10
sub(7, 3) = 4
mul(7, 3) = 21
累加三轮 = 30
apply(add, 2, 5) = 7
sizeof(fp) = 8，sizeof(int[4]) = 16
```

`sizeof(BinOpP) = 8` 这个数字只在 64 位 LP64 模型下成立，32 位平台是 4。别把它写进跨平台代码。

### 10.6.3 回调注册的三种写法
{: .sec-prac}

函数指针最正经的用途就是回调注册：底层库不知道该做什么，让上层传一个函数进来。

```cpp
// callback.cpp —— 需要 -std=c++20
#include <functional>
#include <iostream>
#include <string>
#include <vector>

struct EventBus {
    using Handler = void (*)(const std::string&, void*);   // C 风格：函数指针 + 用户数据指针

    void subscribe(Handler h, void* ud) { handlers_.push_back({h, ud}); }
    void emit(const std::string& msg) const {
        for (auto [h, ud] : handlers_) h(msg, ud);
    }

private:
    std::vector<std::pair<Handler, void*>> handlers_;
};

void print_with_prefix(const std::string& msg, void* ud) {
    const auto* prefix = static_cast<const std::string*>(ud);
    std::cout << *prefix << msg << '\n';
}

struct Counter {
    int n = 0;
};

void count_event(const std::string&, void* ud) {
    ++static_cast<Counter*>(ud)->n;
}

int main() {
    EventBus bus;
    std::string prefix = "[LOG] ";
    Counter counter;

    bus.subscribe(print_with_prefix, &prefix);
    bus.subscribe(count_event, &counter);

    bus.emit("第一条");
    bus.emit("第二条");
    std::cout << "共收到 " << counter.n << " 条\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra callback.cpp -o cb && ./cb
```

```text
共收到 2 条
```

那个 `void* ud` 是 C 回调的通行做法——因为 C 函数指针没法携带状态。C++ 有更好的选择（10.7 的 `std::function` 或模板），但跟 C 库对接时这个模式躲不开。

> **坑：** 函数指针**不能**直接指向非静态成员函数，因为成员函数有隐藏的 `this` 参数，类型是 `int (C::*)(int)` 而非 `int (*)(int)`。这条区分要记牢：`int (C::*)` 是成员函数指针，`int (*)` 是普通函数指针，两者互不转换。想让成员函数当回调，用静态成员函数 + `void*` 传 `this`，或者用 lambda 包一层。
{: .sec-pit}

## 10.7 将函数作为参数
{: .sec-expl}

### 10.7.1 四种写法的代价对比
{: .sec-know}

把"一段可执行的代码"传进函数，C++ 有四种载体：

| 载体 | 能否带状态 | 能否内联 | 类型 | 典型开销 |
| --- | --- | --- | --- | --- |
| 函数指针 | 不能（要额外 `void*`） | 基本不能（间接调用） | 确定的 `R(*)(Args...)` | 一次间接跳转 |
| 函数对象（重载 `operator()`） | 能（成员变量） | 能 | 每个类一个类型 | 零（可内联） |
| lambda | 能（捕获） | 能 | 唯一的闭包类型 | 零（可内联） |
| `std::function<R(Args...)>` | 能 | 不能 | 单一类型，擦除 | 间接调用 + 可能堆分配 |

核心权衡：**`std::function` 换来的是"类型统一"，代价是类型擦除。** 而模板参数换来的是零开销，代价是"每个 lambda 实例化一份代码"，且不能存起来。

```cpp
// callable_cost.cpp —— 需要 -std=c++20
#include <functional>
#include <iostream>

// 写法一：模板参数，零开销，编译器看得见具体类型
template <class F>
int apply_twice_tmpl(F f, int x) { return f(f(x)); }

// 写法二：std::function，类型统一，可存储/可作为参数传给别的函数
int apply_twice_fn(std::function<int(int)> f, int x) { return f(f(x)); }

int main() {
    int factor = 3;
    auto mul_by = [factor](int v) { return v * factor; };      // 有捕获

    std::cout << "模板：" << apply_twice_tmpl(mul_by, 5) << '\n';
    std::cout << "function：" << apply_twice_fn(mul_by, 5) << '\n';

    std::function<int(int)> stored = mul_by;                   // 可以存进容器/成员
    std::cout << "存储后调用：" << stored(5) << '\n';

    std::cout << "sizeof(lambda) = " << sizeof(mul_by)
              << "，sizeof(std::function) = " << sizeof(stored) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra callable_cost.cpp -o cc && ./cc
```

```text
模板：45
function：45
存储后调用：15
sizeof(lambda) = 4，sizeof(std::function) = 32
```

`sizeof(std::function) = 32` 是 libstdc++ 在 64 位下的结果，属于实现定义（libc++ 是 24，MSVC 也可能是别的值）。它内部有小对象缓冲（SBO）：小的可调用物（几个指针大小以内）就地存放不分配堆；大了就 `new`。所以"零分配"这条不能保证——捕获了十几个变量的 lambda 放进 `std::function` 就会堆分配。

选型建议：

- **模板参数**（或 C++20 的 `std::invocable` 约束 + `auto&&`）：库的内部实现、热路径、回调不需要保存。
- **`std::function`**：需要把回调存成成员、放进容器、跨编译单元边界、或者接口不能是模板（比如虚函数）。
- **函数指针**：对接 C API，或者回调无状态且要省掉模板膨胀。
- C++23 还有 `std::move_only_function`：支持只移动的可调用物（捕获 `unique_ptr` 的 lambda），`std::function` 要求可拷贝，这类 lambda 存不进去。

### 10.7.2 lambda 完整语法
{: .sec-know}

lambda 的完整形状（C++20）：

```text
[捕获列表] <模板形参> (形参列表) 说明符 -> 返回类型 { 函数体 }
                                      ↑ mutable / constexpr / consteval / noexcept / 属性
```

C++20 还允许在模板形参之后写 `requires` 子句做约束。除捕获列表和函数体之外，其余部分都能省；不写形参时连括号都能省（`[]{ return 1; }`）。

捕获列表的所有形式：

| 写法 | 含义 | 版本 |
| --- | --- | --- |
| `[]` | 不捕获 | C++11 |
| `[=]` | 按值捕获所有用到的自动变量 | C++11 |
| `[&]` | 按引用捕获所有用到的自动变量 | C++11 |
| `[x]` / `[&x]` | 捕获单个变量，值/引用 | C++11 |
| `[this]` | 按引用捕获当前对象（指针语义） | C++11 |
| `[*this]` | 按值捕获当前对象的副本 | C++17 |
| `[x = expr]` | 初始化捕获，名字与类型都由 `expr` 决定 | C++14 |
| `[&r = expr]` | 初始化捕获一个引用 | C++14 |
| `[=, &x]` / `[&, x]` | 默认方式 + 例外 | C++11 |
| `[=, this]` | 显式捕获 `this`（C++20 起推荐写法） | C++20 |

```cpp
// lambda_full.cpp —— 需要 -std=c++20
#include <functional>
#include <iostream>
#include <memory>
#include <string>
#include <utility>
#include <vector>

struct Widget {
    std::string name = "widget";
    int count = 7;

    auto make_printer_this()  { return [this]  { std::cout << name << ':' << count << '\n'; }; }
    auto make_printer_star()  { return [*this] { std::cout << name << ':' << count << '\n'; }; }  // C++17
};

int main() {
    int x = 10;
    std::string tag = " Tag";

    // 1. 基础：值捕获与引用捕获
    auto by_val  = [x](int a) { return a + x; };
    auto by_ref  = [&x](int a) { x += a; return x; };
    std::cout << "by_val(1) = " << by_val(1) << '\n';
    std::cout << "by_ref(1) = " << by_ref(1) << "，x 现在是 " << x << '\n';

    // 2. mutable：默认 operator() 是 const，改副本要加 mutable
    auto counter = [n = 0]() mutable { return ++n; };      // C++14 初始化捕获
    std::cout << "counter: " << counter() << ' ' << counter() << ' ' << counter() << '\n';

    // 3. 泛型 lambda（C++14）
    auto twice = [](auto v) { return v + v; };
    std::cout << "twice(3) = " << twice(3)
              << "，twice(std::string) = " << twice(std::string("ab")) << '\n';

    // 4. 模板形参 lambda（C++20）：能约束、能拿到类型名
    auto size_of = []<class T>(const std::vector<T>& v) {
        std::cout << "元素类型大小 " << sizeof(T) << "，个数 " << v.size() << '\n';
        return v.size();
    };
    std::vector<int> vi{1, 2, 3};
    size_of(vi);

    // 5. 初始化捕获用于转移所有权（C++14）
    auto owner = [p = std::make_unique<int>(42)] { return *p; };
    std::cout << "持有 unique_ptr 的 lambda：" << owner() << '\n';

    // 6. 立即调用 IIFE
    auto init = [&] {
        std::string s = "计算出来的" + tag;
        return s;
    }();
    std::cout << "IIFE 结果：" << init << '\n';

    // 7. this 与 *this
    Widget w;
    auto p1 = w.make_printer_this();
    auto p2 = w.make_printer_star();
    w.count = 99;
    std::cout << "捕获 this（看到改后的值）："; p1();
    std::cout << "捕获 *this（看到捕获时的快照）："; p2();

    // 8. 无捕获 lambda 可转函数指针，有捕获的不行
    int (*fp)(int) = [](int v) { return v * 2; };
    std::cout << "转成函数指针：" << fp(21) << '\n';
    // int (*bad)(int) = [x](int v) { return v + x; };   // 编译错误：有捕获不能转

    // 9. 闭包大小
    auto empty_l   = [] {};
    auto one_cap   = [x] { return x; };
    auto two_cap   = [x, tag] { return x + static_cast<int>(tag.size()); };
    std::cout << "sizeof: empty=" << sizeof(empty_l)
              << " one=" << sizeof(one_cap)
              << " two=" << sizeof(two_cap) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra lambda_full.cpp -o lf && ./lf
```

```text
by_val(1) = 11
by_ref(1) = 11，x 现在是 11
counter: 1 2 3
twice(3) = 6，twice(std::string) = abab
元素类型大小 4，个数 3
持有 unique_ptr 的 lambda：42
IIFE 结果：计算出来的 Tag
捕获 this（看到改后的值）：widget:99
捕获 *this（看到捕获时的快照）：widget:7
转成函数指针：42
sizeof: empty=1 one=4 two=36
```

几个从输出里读出来的结论：

- **空闭包 `sizeof` 是 1**，不是 0——它是个空类，C++ 要求任何完整对象至少占 1 字节。
- **`[this]` 捕获的是指针**，所以 `w.count` 后来改成 99 它也能看到；`[*this]` 拷了整个对象，看到的是快照 7。
- **`[=]` 在 C++20 里捕获 `this` 已被弃用**（P0806）。原来 `[=]` 会隐式把 `this` 也捕进来，导致"看着是拷贝，实际是指针"的悬垂。C++20 起要么写 `[=, this]` 明确意图，要么写 `[=, *this]` 真拷贝。开 `-Wdeprecated` 会收到提示。

> **坑：** 返回 lambda 时按引用捕获局部变量，是闭包最常见的悬垂来源。`auto f() { int x = 1; return [&x]{ return x; }; }` —— `x` 在函数返回时销毁，调用 `f()()` 就是读野内存。规则很简单：**lambda 要活出当前作用域，就只能用值捕获或初始化捕获。**
{: .sec-pit}

### 10.7.3 `std::bind` 为什么基本被 lambda 取代
{: .sec-know}

`std::bind`（C++11，`<functional>`）做两件事：绑定部分参数（偏应用）、重排参数顺序（占位符 `_1`、`_2`）。它被冷落的原因很具体：

| 问题 | 说明 |
| --- | --- |
| 可读性 | `std::bind(f, _2, _1, 10)` 要脑内展开才知道谁去哪 |
| 重载决议 | `bind` 的结果是"万能调用包装器"，传重载函数名时经常要写 `static_cast` 才能过 |
| 求值时机 | 绑定实参默认是**拷贝**，且嵌套 `bind` 会被**急切求值**（`bind(f, bind(g, _1))` 的语义和你想的可能不同） |
| 性能 | 多一层间接，编译器更难内联 |
| 占位符 | `_1` 在 `std::placeholders` 里，全局符号，容易冲突 |

lambda 在这些维度上全面占优，唯一剩下 `bind` 的地方是"重排参数顺序"确实比 lambda 短一点点——但那个场景一年也遇不到两次。

`std::ref` / `std::cref`（`<functional>`）留下来了，因为它们解决的是另一件事：**让"按引用传递"能穿过那些默认按值拷贝的接口**。`std::thread`、`std::bind`、各种算法都会对入参做 decay-copy，想传引用就得包一层 `std::ref`。

`std::invoke`（C++17）是统一调用语法：不管你手里是函数指针、成员函数指针、数据成员指针还是任何可调用物，都用一个写法调。写泛型代码时它能省掉一大堆 `if constexpr`。

```cpp
// bind_invoke.cpp —— 需要 -std=c++20
#include <functional>
#include <iostream>
#include <string>
#include <thread>
#include <vector>

struct Greeter {
    std::string prefix;
    void say(const std::string& who) const { std::cout << prefix << who << '\n'; }
    int  count = 0;
};

int add3(int a, int b, int c) { return a + b + c; }

int main() {
    using namespace std::placeholders;

    // bind 的偏应用：把 add3 的第一个参数固定为 100
    auto add100 = std::bind(add3, 100, _1, _2);
    std::cout << "add100(1, 2) = " << add100(1, 2) << '\n';

    // 同一件事的 lambda 写法：更直白，也能内联
    auto add100_l = [](int b, int c) { return add3(100, b, c); };
    std::cout << "add100_l(1, 2) = " << add100_l(1, 2) << '\n';

    // bind 默认拷贝实参：想传引用必须 std::ref
    int counter = 0;
    auto bump = std::bind([](int& n) { ++n; }, std::ref(counter));
    bump();
    bump();
    std::cout << "counter = " << counter << '\n';

    // std::invoke：统一调用各种可调用物
    Greeter g{"你好，"};
    std::invoke(&Greeter::say, g, "世界");          // 成员函数指针 + 对象
    std::invoke(&Greeter::count, g) = 5;            // 数据成员指针也能 invoke（赋值）
    std::cout << "g.count = " << std::invoke(&Greeter::count, g) << '\n';
    std::cout << "普通函数：" << std::invoke(add3, 1, 2, 3) << '\n';

    // std::ref 的另一个主战场：thread 的入参默认被拷贝
    std::thread t([](int& n) { n += 100; }, std::ref(counter));
    t.join();
    std::cout << "线程加过之后 counter = " << counter << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra bind_invoke.cpp -o bi -pthread && ./bi
```

```text
add100(1, 2) = 103
add100_l(1, 2) = 103
counter = 2
你好，世界
g.count = 5
普通函数：6
线程加过之后 counter = 102
```

`std::invoke(&Greeter::count, g) = 5;` 这行看着怪，但合法：`std::invoke` 对数据成员指针返回的是成员的**引用**。

### 辨析：按引用捕获与 `std::ref` 传参
{: .sec-iv}

两者都叫"引用"，机制不同：

- `[&x]` 在**闭包类型里**放一个引用成员，生命周期由闭包对象管。
- `std::ref(x)` 生成一个 `std::reference_wrapper<T>`，它是个可拷贝的值类型，内部存指针。它存在的意义是"绕过 decay-copy"。

所以给 `std::thread` 传参时不能用 `[&]` 解决（lambda 捕获只影响闭包内部，thread 构造时拷贝的是整个闭包——其实按引用捕获也能工作，但引用的是调用方的局部变量，线程跑起来时那个变量可能已经没了）。**线程里要么按值捕获，要么 `std::ref`，且必须保证被引用对象活到线程结束。**

## 10.8 变量的作用域和生存期
{: .sec-expl}

### 10.8.1 四种作用域
{: .sec-know}

**作用域（scope）**是名字的可见范围，**生存期（lifetime）**是对象的存在时间。两者相关但不等价——`static` 局部变量作用域在函数内，生存期却贯穿整个程序。

| 作用域 | 名字在哪可见 | 典型 |
| --- | --- | --- |
| 块作用域 | 从声明点到块结束 | 函数体、if/for 的 `{}` 内 |
| 函数参数作用域 | 整个函数体 | 形参 |
| 类作用域 | 整个类定义 | 成员名 |
| 命名空间作用域 | 从声明点到命名空间结束 | 全局变量、`namespace` 里的东西 |

生存期对应四种存储期：**自动**（栈上，块结束时销毁）、**静态**（程序启动时或首次初始化时创建，程序结束时销毁）、**线程**（`thread_local`，C++11）、**动态**（`new`/`delete`，手动管）。

```cpp
// scope_life.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int global_counter = 0;                    // 静态存储期，命名空间作用域
static int file_local = 1;                 // 内部链接：只在当前 .cpp 可见

void demo_static_local() {
    static int calls = 0;                  // 静态局部：只在首次执行时初始化
    ++calls;
    std::cout << "第 " << calls << " 次调用（global=" << ++global_counter << "）\n";
}

int& dangerous_static() {
    static std::string cache = "共享的缓存";  // 所有调用方共用一份
    return reinterpret_cast<int&>(cache);    // 演示用：故意返回内部静态的引用
}

int main() {
    {   // 块作用域
        int block_var = 42;
        std::cout << "块内 block_var = " << block_var << '\n';
    }
    // std::cout << block_var;   // 编译错误：出了块就不可见

    demo_static_local();
    demo_static_local();
    demo_static_local();

    for (int i = 0; i < 3; ++i) {          // i 的作用域是 for 语句
        std::cout << "i=" << i << ' ';
    }
    std::cout << '\n';

    std::cout << "file_local = " << file_local << '\n';
}
```

### 10.8.2 静态局部的线程安全初始化与隐患
{: .sec-know}

C++11 起（所谓 **magic statics**），静态局部变量的初始化**保证线程安全**：多个线程同时首次执行到那一行，只有一个线程执行初始化，其余阻塞等待。这条保证终结了"要不要用 `std::call_once` 手写单例"的讨论——最简单例就是：

```cpp
Config& instance() {
    static Config cfg;      // C++11 起线程安全，且只初始化一次
    return cfg;
}
```

三个必须知道的细节：

1. **初始化期间重入是 UB。** 如果初始化表达式直接或间接又调用了这个函数，行为未定义（常见表现是死锁）。
2. **初始化只保证一次，后续访问不保证。** 返回内部静态对象的引用，之后多线程读写那个对象，就是普通的数据竞争——要自己加锁。
3. **析构顺序。** 静态对象按构造的逆序析构，跨编译单元的静态对象析构顺序**未指定**。这就是"静态析构顺序灾难"（static destruction order fiasco）。规避手段：用函数内静态（延迟构造，顺序由调用顺序决定）代替全局对象，或者干脆不依赖析构顺序（用泄漏单例）。

```cpp
// static_hazard.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <thread>
#include <vector>

// 反例：返回内部静态缓冲区的裸指针，多线程读写会数据竞争
const char* legacy_format(int v) {
    static std::string buf;               // 所有线程共用一份
    buf = "n=" + std::to_string(v);       // 数据竞争：并发写同一个 string
    return buf.c_str();                   // 而且返回的指针会被下一次调用改写
}

// 正例：返回值，各线程各持一份
std::string safe_format(int v) {
    return "n=" + std::to_string(v);
}

// 正例：只读的静态常量，安全
const std::string& app_name() {
    static const std::string name = "demo-app";   // 初始化后不再修改
    return name;
}

int main() {
    std::cout << app_name() << '\n';
    std::cout << safe_format(7) << '\n';

    // 下面这段会数据竞争，仅作演示，实际运行可能崩
    // std::vector<std::thread> ts;
    // for (int i = 0; i < 8; ++i)
    //     ts.emplace_back([i] { for (int k = 0; k < 1000; ++k) legacy_format(i * 1000 + k); });
    // for (auto& t : ts) t.join();
}
```

```text
n=7
```

注释掉的并发段是**故意不跑**的：它会触发 `std::string` 上的数据竞争，属于 **undefined behavior**，在 `-fsanitize=thread` 下会被抓出来。这类 API 在老代码里很常见（`asctime`、`ctime`、`strtok` 都是这个毛病），现代替代是返回值或者 `thread_local` 缓冲。

`thread_local`（C++11）是这里最干净的解法：每个线程一份，既避免了竞争，又不用每次分配。

### 辨析：全局变量、静态局部、`thread_local`
{: .sec-iv}

| 维度 | 全局变量 | 静态局部 | `thread_local` |
| --- | --- | --- | --- |
| 可见性 | 跨编译单元（`extern`） | 只在函数内 | 按声明位置 |
| 初始化时机 | `main` 之前（顺序未指定） | 首次执行到（线程安全） | 首次使用（每线程一次） |
| 共享 | 全程序一份 | 全程序一份 | 每线程一份 |
| 主要风险 | 初始化顺序、紧耦合 | 并发读写、重入 UB | 线程创建/销毁开销、TLS 槽位有限 |

## 10.9 函数 `main()` 和命令行处理
{: .sec-expl}

### 10.9.1 `main` 的合法形式
{: .sec-know}

标准只认两种：

```cpp
int main() { }
int main(int argc, char* argv[]) { }
```

实现可以提供更多形式，但不能减少。三个常被问到的点：

- **`void main()` 非法**，尽管 MSVC 接受。写了就是不可移植。
- **`main` 不能被程序使用**：不能递归调用、不能取地址（[basic.start.main] 明文规定）。所以"用递归调 main 重启程序"是违法的。
- **`main` 的 `return` 可以省略**，末尾默认 `return 0;`。

`argc` / `argv` 的细节：

- `argc >= 1`，`argv[0]` 是程序名（可能是空字符串，取决于执行方式）。
- `argv[argc]` 保证是空指针，可以据此遍历。
- `argv` 里的字符串可修改（标准允许），但别指望。

返回值语义：`0` 和 `EXIT_SUCCESS`（`<cstdlib>`）表示成功，`EXIT_FAILURE` 表示失败。注意 `EXIT_SUCCESS` 不一定等于 0（标准只要求它表示成功）——虽然在所有主流平台上它就是 0。POSIX 上只有低 8 位有效，所以 `return 256;` 在 shell 里看到的是 0。

### 10.9.2 `envp` 的非标准性与环境变量
{: .sec-know}

`int main(int argc, char* argv[], char* envp[])` 是 Windows 和多数 Unix 系统的扩展，**不在标准里**。可移植做法是 `std::getenv`（`<cstdlib>`）：

```cpp
// main_args.cpp —— 需要 -std=c++20
#include <cstdlib>
#include <iostream>
#include <string>
#include <string_view>

int main(int argc, char* argv[]) {
    std::cout << "argc = " << argc << '\n';
    for (int i = 0; i < argc; ++i) {
        std::cout << "argv[" << i << "] = " << argv[i] << '\n';
    }

    // 用下标遍历也行：标准保证 argv[argc] == nullptr
    for (char** p = argv; *p != nullptr; ++p) {
        std::cout << "  遍历得到：" << *p << '\n';
    }

    if (const char* home = std::getenv("HOME")) {
        std::cout << "HOME = " << home << '\n';
    } else if (const char* profile = std::getenv("USERPROFILE")) {
        std::cout << "USERPROFILE = " << profile << '\n';
    } else {
        std::cout << "没找到家目录环境变量\n";
    }

    std::string mode = argc > 1 ? argv[1] : "default";
    if (mode == "verbose") std::cout << "详细模式\n";
    return EXIT_SUCCESS;
}
```

```bash
g++ -std=c++20 -Wall -Wextra main_args.cpp -o ma && ./ma verbose
```

```text
argc = 2
argv[0] = ./ma
argv[1] = verbose
  遍历得到：./ma
  遍历得到：verbose
HOME = /home/user
详细模式
```

`HOME` 那行的具体值取决于运行环境；Windows 上通常要走 `USERPROFILE` 分支。

`std::getenv` 有两个已知问题：返回的是指向静态缓冲的指针，多次调用可能被覆盖（线程安全性由实现定义，C 标准不保证）；修改环境变量要用平台 API（`setenv` / `_putenv_s`）。

### 10.9.3 命令行解析：手写、getopt、库
{: .sec-expl}

| 方案 | 适用 | 代价 |
| --- | --- | --- |
| 手写遍历 `argv` | 两三个开关的小工具 | 无依赖；帮助文本和错误处理要自己写 |
| `getopt` / `getopt_long` | POSIX 平台，需要 `--long` 选项 | `<unistd.h>` / `<getopt.h>`，Windows 没有原生支持 |
| 头文件库（CLI11、cxxopts、argparse） | 任何正经的命令行程序 | 引入一个头文件依赖 |

`std::filesystem`（C++17）里没有命令行解析，别指望。选型的分水岭是"要不要生成 `--help`"和"要不要校验必填项"——这两件事手写起来总有遗漏，超过三个选项就该用库。

手写的最小骨架长这样，注意它的失败路径必须清清楚楚：

```cpp
// cli_hand.cpp —— 需要 -std=c++17
#include <cstdlib>
#include <iostream>
#include <string>
#include <string_view>

struct Options {
    std::string input;
    int level = 1;
    bool verbose = false;
};

void usage(std::string_view prog) {
    std::cout << "用法: " << prog << " --input <文件> [--level N] [--verbose]\n";
}

int main(int argc, char* argv[]) {
    Options opt;
    for (int i = 1; i < argc; ++i) {
        std::string_view a = argv[i];
        if (a == "--input" || a == "-i") {
            if (i + 1 >= argc) { std::cerr << "错误：--input 缺少参数\n"; return EXIT_FAILURE; }
            opt.input = argv[++i];
        } else if (a == "--level" || a == "-l") {
            if (i + 1 >= argc) { std::cerr << "错误：--level 缺少参数\n"; return EXIT_FAILURE; }
            opt.level = std::atoi(argv[++i]);
        } else if (a == "--verbose" || a == "-v") {
            opt.verbose = true;
        } else if (a == "--help" || a == "-h") {
            usage(argv[0]);
            return EXIT_SUCCESS;
        } else {
            std::cerr << "错误：未知选项 " << a << '\n';
            usage(argv[0]);
            return EXIT_FAILURE;
        }
    }

    if (opt.input.empty()) {
        std::cerr << "错误：必须指定 --input\n";
        usage(argv[0]);
        return EXIT_FAILURE;
    }

    std::cout << "input=" << opt.input << " level=" << opt.level
              << " verbose=" << (opt.verbose ? "yes" : "no") << '\n';
    return EXIT_SUCCESS;
}
```

```bash
g++ -std=c++17 -Wall -Wextra cli_hand.cpp -o cli && ./cli -i data.txt -l 3 -v
```

```text
input=data.txt level=3 verbose=yes
```

`std::atoi` 拿到非法输入会返回 0 且不报错——这是它的老毛病。C++17 起有 `<charconv>` 的 `std::from_chars`，无异常、无 locale、能区分"解析失败"和"值为 0"，第 11 篇 11.4 节会详细讲。

## 10.10 技术解惑
{: .sec-expl}

### 10.10.1 头文件里放函数定义一定会 ODR 违规吗
{: .sec-know}

不一定。三条合法通道：`inline` 函数、模板（含函数模板与类模板成员）、`constexpr`（C++11 起隐含 `inline`）。还有一条是 `static`——它不违规，但每个编译单元各得一份独立副本，函数内的静态局部也是各算各的，通常不是你想要的语义。至于类内定义的成员函数，它自动就是 `inline`，所以在头文件里写没问题。

### 10.10.2 为什么改了默认参数要重新编译所有调用方
{: .sec-know}

因为默认实参在**调用点**展开。调用方编译时会把 `f()` 变成 `f(1)`，那个 `1` 直接编进了目标文件。你改了头文件里的默认值，只重编定义所在的 .cpp 是不够的——旧的目标文件里还是老数字。这也是"改头文件要重新编译依赖它的所有东西"这条工程经验的具体来源。

### 10.10.3 `const T&` 和 `T&&` 都能接右值，选哪个
{: .sec-know}

看你要不要搬走它的资源：

- 只读 → `const T&`（或者 `T` 如果类型便宜）。它能接左值也能接右值，是"通用只读引用"。
- 要窃取资源（sink）→ `T&&`。
- 模板里要完美转发 → **转发引用** `T&&`（`T` 是本次被推导的模板参数），配合 `std::forward<T>`。

这三个 `T&&` 长得一样语义不同，判断依据是"`T` 是不是本次调用推导出来的"：`void f(std::string&& s)` 里的 `T` 是具体类型，那是右值引用；`template<class T> void f(T&& t)` 里 `T` 被推导，那是转发引用。

### 10.10.4 重载决议里"非模板优先"会不会导致选错
{: .sec-know}

会，而且现象很隐蔽：你写了一个模板 `template<class T> void save(const T&)`，又写了一个 `void save(const char*)`。对 `save("abc")` 来说，非模板的 `const char*` 是精确匹配，赢；但 `save(std::string("x"))` 只能走模板。于是同一个调用名在不同实参下走完全不同的实现，而两个实现的行为如果不一致，就是 bug 温床。规避办法是让非模板版本和模板版本语义一致，或者干脆只留模板并用 concept 约束。

### 10.10.5 返回 `std::optional<T>` 和返回 `T` 加一个 `bool` 出参怎么选
{: .sec-know}

`std::optional<T>` 赢在三点：不可能忘记检查（调用方不检查就拿不到值）、可以链式（`value_or`、C++23 的 `and_then`）、不用先默认构造一个 `T`。

出参版唯一的优势是"错误信息更丰富"——但那正好是 `std::expected<T, E>` 的地盘。所以现代代码里 `bool` 出参基本只在对接 C API 时出现。

### 10.10.6 递归函数能不能 `inline`
{: .sec-know}

编译器可以做有限深度的内联展开（GCC 的 `--param max-inline-insns-recursive`），但不能无限展开。标 `inline` 关键字只是让它能在头文件里定义，和展开无关。深度已知的浅递归（比如编译期递归模板）才有意义；运行期递归别指望内联帮上忙。

### 10.10.7 函数指针和成员函数指针的大小为什么不一样
{: .sec-know}

普通函数指针就是一个地址（64 位下 8 字节）。成员函数指针要额外处理虚函数和多重继承：它得能表达"偏移 + 虚表下标"或者"调整 `this` 的 thunk"，所以大小是实现定义的，在 Itanium ABI（GCC/Clang）下通常是 16 字节，MSVC 下因继承方式不同可能是 8/12/16 字节。这也是"别把成员函数指针当普通指针用"的直接原因。

```cpp
#include <iostream>
struct C { void f() {} virtual void g() {} };
int main() {
    std::cout << sizeof(&C::f) << ' ' << sizeof(void(*)(int)) << '\n';
}
```

在 Itanium ABI 的 64 位环境下这行输出 `16 8`；换编译器可能不同，所以别把它写进断言。

### 10.10.8 `std::function` 到底什么时候会堆分配
{: .sec-know}

取决于两件事：可调用物本身的大小、标准库实现的 SBO 容量。libstdc++ 的 `std::function` 内部有一个联合体缓冲，能就地放下的就放，放不下才 `new`。容量是实现定义的，MSVC、libstdc++、libc++ 各不相同。所以：

- 捕获少量小对象（两三个指针/整数）→ 通常不分配；
- 捕获多个大对象（`std::string`、多个容器）→ 很可能分配；
- 传函数指针 → 不分配。

想确定就用 `std::function` 的 `target_type()` 配合自定义分配器，或者干脆在热路径上用模板参数避开它。C++23 的 `std::move_only_function` 也一样有这个不确定性，但它至少支持只移动的可调用物。

### 10.10.9 协程会不会让代码自动变快
{: .sec-know}

不会，它只是把"等待"变成"挂起"，本身还引入了帧分配和状态机开销。协程真正的收益在**并发 I/O 密度**：一个线程上挂着一万个协程，内存占用远小于一万个线程。如果任务是 CPU 密集的，协程一点用没有，反而变慢。另外每个协程默认一次 `operator new`，高频创建（比如每个请求一个协程）时必须做帧分配优化，否则分配器会成为瓶颈。

### 10.10.10 为什么 lambda 的类型写不出来
{: .sec-know}

每个 lambda 表达式产生一个**唯一的、无名的闭包类型**，标准故意不让你写它的名字——这样编译器就能自由决定它的布局（捕获成员的顺序、对齐），也能保证两个不同位置的 lambda 类型不同。要拿到类型只有两条路：`auto` 推导（`auto f = []{...};`）或者 `decltype`。需要把类型写出来的时候（比如做返回类型），用 `auto` 返回类型推导：

```cpp
auto make_adder(int n) {          // C++14 起返回类型可以推导 lambda
    return [n](int x) { return x + n; };
}
```

### 10.10.11 `[[nodiscard]]` 该标在哪些函数上
{: .sec-know}

三类：

1. **返回值是唯一结果的函数**（纯函数、查找、解析）——忘了用返回值说明调用方写错了。
2. **返回错误码的函数**——`[[nodiscard]]` 能有效减少"忘检查返回值"这类 bug。
3. **返回资源句柄的函数**——丢掉句柄等于泄了资源。

不要标在"副作用是主要目的、返回值只是顺带"的函数上（`std::vector::push_back` 就没标——它干脆连值都不返回）。C++20 起标准库大量补了这个属性：`std::async`、`std::accumulate`、`std::empty` 都标了。

## 变式追问

1. 为什么标准不允许只按返回类型重载，却允许 `explicit operator bool()` 这种"看上下文决定"的转换？

   因为两者的信息方向不同。重载决议是"从实参类型推出要调哪个函数"，实参类型在调用点是确定的；返回类型由调用点**使用方式**决定，而使用方式可以有很多层（赋给 `int`、赋给 `double`、直接丢弃、传给另一个重载函数），编译器要在这么多可能性里反推，代价是无法接受的，而且会产生"改一个不相关的代码就换了重载"的诡异行为。`explicit operator bool()` 之所以能工作，是因为它只在**语境转换到 bool** 的少数几个位置参与，那些位置的目标是唯一确定的（`if`、`while`、`&&`、`!`），不存在歧义。换句话说：C++ 允许"上下文决定"只在这些上下文集合明确且封闭的地方。

2. `return std::move(x);` 挡住 NRVO，那是不是说明"编译器很笨"？

   不是笨，是规则要求。NRVO 的条件写得很具体：返回语句的操作数必须是一个**具名对象的名字**（id-expression），且该对象的类型和返回类型一致。这么写是因为编译器要能静态确定"这个对象的存储就是返回值的存储"，才能直接在调用者的空间上构造它。`std::move(x)` 返回的是 `T&&`，`return` 语句的操作数是一个函数调用表达式，编译器必须先求值这个表达式（得到一个引用），再用它初始化返回值——这就进入了"用右值引用初始化返回对象"的路径，走的是移动构造。这不是优化器能力问题，而是两条不同的语言规则。所以 `return x;` 永远不比 `return std::move(x);` 差，很多情况下更好。

3. 递归深度 100 万就爆栈，那把栈调大到 100 MB 行不行？

   技术上可行（`ulimit -s`、Windows 的 `/STACK`、`pthread_attr_setstacksize`），但这是把问题推后而不是解决。三个理由不该这么干：一是栈大小是线程级的，开 100 个线程就要 10 GB 的虚拟地址空间（虽然多数是惰性提交，但 32 位进程和容器环境会先撑不住）；二是深度来自外部输入时，攻击者只要多给数据就能爆掉你调多大的栈；三是爆栈是 `SIGSEGV`，没有可捕获的异常，程序直接死，没有任何优雅降级的机会。正解是改写为迭代，或者用显式堆上的栈（`std::vector<Node>` 手动维护），那样深度上限受堆大小约束，且可以自己检查并报错。`std::expected` 那类错误返回通道这时候才用得上。

4. `std::function` 的参数为什么常写成 `std::function<void(int)>&&` 或者干脆用模板？用 `const std::function<void(int)>&` 有什么问题？

   `const&` 版看着最"省"，实际有几个毛病：一是调用方传一个 lambda 时，会先构造一个临时 `std::function`（可能堆分配），再绑定到引用上，你没省掉任何分配；二是 `const std::function<...>` 的 `operator()` 是 const 的，要求被存储的可调用物的 `operator()` 也是 const——捕获后要修改状态的 lambda（标了 `mutable`）就装不进去；三是它把"我要拷贝一份存起来"和"我只是借用一下"这两种意图混在一起了。所以现在的主流写法是：接口**不存储**回调 → 用模板参数或者 `std::invocable auto&&`；接口**要存储** → 按值 `std::function<...>` 形参，然后在函数体里 `std::move` 到成员（按值传参 + move 是 sink 参数的标准套路）。`const&` 只在"百分百确定只是临时借用且不存"时才合理，而这种场景模板参数更好。

5. 协程号称"同步写法、异步性能"，那它到底省了什么？

   省的是**栈内存和内核态切换**，不是 CPU 时间。一万个并发连接用线程模型要一万个栈（几 MB × 一万 = 几十 GB），用协程只需要一万个协程帧（几百字节 × 一万 = 几 MB），而且挂起/恢复是一次用户态跳转，不进内核。代价是三样：帧分配（可用自定义 `operator new` 或 HALO 优化掉）、生命周期管理难度陡增（协程帧里的引用在挂起期间必须一直有效，跨 `co_await` 持有局部对象的引用是新的悬垂来源）、以及调试困难（栈回溯是断的）。所以判断标准很简单：如果瓶颈是"大量并发等待"（网络服务、I/O 密集），协程收益巨大；如果瓶颈是"算力不够"（图像处理、数值计算），协程纯属额外开销，直接上线程池。
