## 17.1 string类的方法
{: .sec-expl}

### 17.1.1 std::string 的本质与内存布局
{: .sec-know}

`std::string` 是 `std::basic_string<char>` 的别名，模板参数还有 traits（字符比较与复制策略）和 allocator（内存来源），日常都用默认值。要抓住的性质有三条：

1. **连续存储**（C++11 起标准保证）：内部缓冲区在内存里是一段连续空间，`data()` 返回首地址，可以用指针算术随便走。
2. **以空字符结尾**：`data()` 和 `c_str()` 返回的序列满足 `data()[size()] == '\0'`（C++11 起 data 也有此保证，两个函数几乎等价）。所以任何需要 C 字符串的地方都能直接喂。
3. **size 独立于 '\0'**：与 C 字符串"扫到 0 才算完"不同，string 随身携带长度，内容里可以含 `'\0'`（读二进制数据时有用），`size()` 永远是"字符数"不是"到 0 为止"。

```cpp
// string_nature.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string s = "hello";
    std::cout << "size     = " << s.size() << '\n';
    std::cout << "data()[5] 是 '\\0'? "
              << (s.data()[s.size()] == '\0') << '\n';

    s.push_back('\0');            // 内容里可以带 0
    s += "world";
    std::cout << "size     = " << s.size() << '\n';   // 11：0 也算一个元素
    std::cout << "c_str 停在 0: " << s.c_str() << '\n'; // 打印到隐含的 0 为止
}
```

```bash
g++ -std=c++20 -Wall -Wextra string_nature.cpp -o sn && ./sn
```

```text
size     = 5
data()[5] 是 '\0'? 1
size     = 11
c_str 停在 0: hello
```

结尾两行正是"双重身份"的现场：按 string 的规则它有 11 个元素，按 C 字符串的规则它在第 6 个字节就结束了。两边混用前先想清楚自己要哪一种语义。

### 17.1.2 SSO 小字符串优化
{: .sec-ver}

短字符串如果也要去堆上申请内存，日志、协议解析这类高频小串场景会被内存分配拖死。于是主流实现都在 string 对象内部划出一小块栈上空间，短串直接放进去不碰堆——这就是 **SSO（Small String Optimization）**。验证它的方式就是打印 `sizeof` 和 `capacity`：

```cpp
// sso_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::cout << "sizeof(std::string) = " << sizeof(std::string) << '\n';

    std::string short_s = "abc";
    std::cout << "short: capacity=" << short_s.capacity() << '\n';

    std::string long_s = "this string is definitely longer than SSO";
    std::cout << "long : capacity=" << long_s.capacity() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra sso_demo.cpp -o sso && ./sso
```

```text
sizeof(std::string) = 32
short: capacity=15
long : capacity=41
```

三大标准库实现的具体数字不同，使用结论却一致：

| 实现 | sizeof(string)（LP64） | SSO 容量 | 溢出后 |
| --- | --- | --- | --- |
| libstdc++（GCC） | 32 字节 | 15 字符 | 转堆分配 |
| libc++（Clang） | 24 字节 | 22 字符 | 转堆分配 |
| MSVC | 32 字节 | 15 字符 | 转堆分配 |

libc++ 把对象压到 24 字节、SSO 阈值提到 22，换来的是更多短串完全零堆操作——它内部用了"长模式/短模式"的标志位复用技术。libstdc++ 和 MSVC 是指针 + size + capacity（或联合体）的经典布局。

SSO 带来三条性能含义：构造和析构短串不碰分配器；移动短串等于拷贝那 15 个字节（移动堆串才是纯指针交换）；**指向字符串内部的指针/引用在"修改"面前极其脆弱**——短串就地改写、长串扩容搬堆，都可能让旧指针失效，这与后面 17.4.2 的 c_str() 生命周期是同一件事的两面。

> **注意：** `sizeof(std::string)` 与实现强相关，别把它写进序列化格式或跨模块 ABI 约定；判断"短串"也别写死 15/22，用 `capacity()` 动态判断。
{: .sec-note}

### 17.1.3 构造、赋值与移动
{: .sec-know}

构造途径覆盖了几乎所有来源：C 字符串、`count` 个字符、迭代器区间、另一个 string、`string_view`（C++17 起显式构造）。赋值同理。移动语义（C++11）让"从一个 string 转移到另一个"变成指针级操作：

```cpp
// construct_move.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <string_view>

int main() {
    std::string a(5, 'x');                    // "xxxxx"
    std::string b(a, 2);                      // 从 a[2] 起到结尾："xxx"
    std::string c(b.begin(), b.end());        // 迭代器区间
    std::string_view sv = "from view";
    std::string d(sv);                        // C++17：string_view 构造

    std::cout << a << ' ' << b << ' ' << c << ' ' << d << '\n';

    std::string e = "a string long enough to live on the heap";
    std::string f = std::move(e);             // 移动：f 接管缓冲区
    std::cout << f.size() << '\n';
    // e 此后处于"有效但未指定"状态：还能析构、能赋新值，但内容别猜
}
```

```bash
g++ -std=c++20 -Wall -Wextra construct_move.cpp -o cm && ./cm
```

```text
xxxxx xxx xxx from view
40
```

三条实用纪律：拷贝是深拷贝，代价与长度成正比，参数传递能 `(const std::string&)` 或 `string_view` 就别按值传；移动之后不要读旧对象的内容；从字符串字面量构造时 `std::string s = "abc";` 与 `std::string s{"abc"};` 效果相同，团队统一一种即可。

### 17.1.4 容量管理
{: .sec-know}

string 的容量语义和 vector 完全一致，因为底层就是同一套动态数组逻辑：

| 操作 | 作用 | 关键细节 |
| --- | --- | --- |
| `size()` / `length()` | 当前字符数 | 两者完全等价 |
| `capacity()` | 已分配的字符容量 | 可能大于 size，多出的空间免费使用 |
| `reserve(n)` | 预留至少 n 容量 | C++20 起标准保证传小值**不缩容**；参数传 0 也不许缩 |
| `resize(n)` | 改变 size 到 n | 变长时**用指定字符（默认 '\0'）填充**，不是预留 |
| `shrink_to_fit()` | 请求缩容到 size | 非绑定请求，实现可以拒绝 |
| `clear()` | 清空内容 | size 归 0，**capacity 不变** |
| `empty()` | 判空 | 等价 `size() == 0` 但更快更清晰 |

`resize` 和 `reserve` 的混淆是高频事故：`resize` 真的会创建元素并填值，`reserve` 只是圈地不动内容。

```cpp
// capacity_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string s;
    std::size_t last = 0;
    for (int i = 0; i < 64; ++i) {
        s.push_back('x');
        if (s.capacity() != last) {                    // 容量变化点 = 扩容发生点
            std::cout << "size=" << s.size()
                      << " capacity=" << s.capacity() << '\n';
            last = s.capacity();
        }
    }

    std::string t = "abcdef";
    t.resize(9, '-');                                  // 尾部填 '-'
    std::cout << t << '\n';
    t.resize(3);                                       // 截断
    std::cout << t << '\n';

    t.clear();
    std::cout << "after clear: size=" << t.size()
              << " capacity=" << t.capacity() << '\n'; // 容量还在
}
```

```bash
g++ -std=c++20 -Wall -Wextra capacity_demo.cpp -o cd && ./cd
```

```text
size=1 capacity=15
size=16 capacity=30
size=31 capacity=60
size=61 capacity=120
abcdef---
abc
after clear: size=0 capacity=60
```

上面是 libstdc++（GCC 13，x86-64 Linux）的典型输出：容量 15 起步、翻倍增长；`resize(9, '-')` 按预期填 `-`、`resize(3)` 截断；`clear()` 之后 size 归零而 capacity 纹丝不动。不同实现的扩容节奏不同，数字仅供参考，规律才是重点。

> **最佳实践：** 已知上限或量级的拼接场景，先 `reserve()` 一次到位，避免 15→30→60 的反复搬家。resize 需要填充时永远写明填充字符，别依赖默认 '\0' 造成"看不见但存在"的尾巴。clear 之后想真正归还内存，配 `shrink_to_fit()`（理解它是请求不是命令）。
{: .sec-best}

### 17.1.5 元素访问
{: .sec-know}

| 访问方式 | 越界行为 | 说明 |
| --- | --- | --- |
| `s[i]` | `i < size()` 快；`i == size()` 返回 '\0'（C++11 起，只读合法）；`i > size()` 是 undefined behavior | 不检查，最快 |
| `s.at(i)` | 抛 `std::out_of_range` | 带检查，慢一点但安全 |
| `s.front()` / `s.back()` | 空串调用是 UB | 等价 `s[0]` / `s[size()-1]` |
| `s.data()` | — | 只读语义用 `const char*` 接 |

```cpp
// access_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

int main() {
    std::string s = "abc";
    std::cout << s.front() << s[1] << s.back() << '\n';   // abc

    std::cout << (s[s.size()] == '\0') << '\n';           // 合法：返回空字符
    // s[s.size()] = 'x';   // undefined behavior：写隐含的 0 是 UB

    try {
        s.at(10);
    } catch (const std::out_of_range& e) {
        std::cout << "out_of_range\n";                    // at 带检查
    }
    // s[10];   // undefined behavior：[] 不检查，直接越界读
}
```

```bash
g++ -std=c++20 -Wall -Wextra access_demo.cpp -o ad && ./ad
```

```text
abc
1
out_of_range
```

> **坑：** `[]` 的 `i == size()` 返回 '\0' 是刻意设计——方便把 string 当 C 字符串遍历（`while (s[i] != '\0')`）。但边界就停在"等于"：`i > size()` 没有任何保护，是纯 UB。不信任调用方输入的边界代码，用 `at()`；自己能保证下标合法的热点循环，用 `[]`。
{: .sec-pit}

### 17.1.6 修改操作
{: .sec-know}

修改接口按"从哪里动"分四类：尾部（`append`/`+=`/`push_back`）、任意位置（`insert`）、删除（`erase`）、替换（`replace`）。尾部操作性价比最高——有 capacity 就地写；中间插入删除是 O(n) 搬家，避不开但要知道代价。

```cpp
// modify_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string s = "hello";
    s.append(", world");        // 尾部追加，等价 s += ", world"
    s.push_back('!');           // 单字符专用，比 += 少一层构造
    std::cout << s << '\n';

    s.insert(5, "---");         // 位置 5 处插入：O(n) 搬家
    std::cout << s << '\n';

    s.erase(5, 3);              // 从位置 5 删 3 个字符
    std::cout << s << '\n';

    s.replace(0, 5, "HELLO");   // 替换 [0,5) 区间
    std::cout << s << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra modify_demo.cpp -o md && ./md
```

```text
hello, world!
hello---, world!
hello, world!
HELLO, world!
```

说完了接口，看拼接的性能形态。链式 `+` 是重灾区：

```cpp
// concat_cost.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    // 反面教材：每次 s = s + "ab" 都生成一个全新 string 并整体拷贝
    std::string s1;
    for (int i = 0; i < 12; ++i)
        s1 = s1 + "ab";         // O(n^2)：第 i 轮拷贝 2i 个字符
    std::cout << s1.size() << '\n';

    // 正确姿势：+= 原地追加，摊还 O(1)
    std::string s2;
    s2.reserve(24);
    for (int i = 0; i < 12; ++i)
        s2 += "ab";             // 零临时对象
    std::cout << s2.size() << '\n';
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra concat_cost.cpp -o cc && ./cc
```

```text
24
24
```

`s = s + "ab"` 的完整流程：调用非成员 `operator+(s, "ab")`，函数内构造一个 s 的拷贝、追加、按值返回、再移动赋回 s——长度 n 的串每轮白拷一次，n 轮总代价 O(n²)。`s += "ab"` 只在容量不足时扩一次容，摊还 O(1)。循环里出现 `x = x + ...` 的字符串拼接，直接改 `+=`，零风险纯收益。

### 17.1.7 查找家族与 npos 的坑
{: .sec-know}

查找函数六个方向：正向找子串（`find`）、反向找子串（`rfind`）、找字符集合（`find_first_of` / `find_last_of`）、找"不在集合里"的第一个/最后一个（`find_first_not_of` / `find_last_not_of`）。全部返回 `size_type` 下标，找不到返回 **npos**。

> **坑：** `npos` 是 `size_type` 的最大值，也就是 `size_t` 的全 1 位。它和 `-1` 在二进制上一样，于是 `int` 与它比较的代码"看起来能跑"，实际埋着类型地雷。
{: .sec-pit}

```cpp
// npos_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string s = "ab,cab,cabb";

    std::cout << s.find("ab")          << '\n';   // 0：正向找子串
    std::cout << s.rfind("ab")         << '\n';   // 8：反向找子串
    std::cout << s.find_first_of("ab") << '\n';   // 0：第一个属于集合 {a,b}
    std::cout << s.find_last_of("ab")  << '\n';   // 9：最后一个属于集合
    std::cout << s.find_first_not_of("ab,") << '\n';  // 3：第一个不属于 {a,b,逗号}
    std::cout << (s.find('x') == std::string::npos) << '\n';  // 1：找不到返回 npos

    // 经典 bug：把返回值塞进 int
    int bad = static_cast<int>(s.find('x'));
    std::cout << (bad == -1) << '\n';             // 看似成立：截断后恰好是 -1
    // 但 LP64 上 npos = 0xFFFFFFFFFFFFFFFF，int 只剩低 32 位；
    // 位置一旦超过 20 亿，截断后的值会撞上有效下标，错误静默发生

    // 正确写法：永远用 size_t 接，永远与 npos 显式比较
    for (std::size_t p = s.find('b'); p != std::string::npos; p = s.find('b', p + 1))
        std::cout << p << ' ';                    // 遍历所有 'b'：位置 1、5、9、10
    std::cout << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra npos_demo.cpp -o nd && ./nd
```

```text
0
8
0
9
3
1
1
1 5 9 10
```

编译这条代码 `-Wall` 会给出 signed/unsigned 比较警告，别无视它。纪律三句话：接 find 返回值一律 `std::size_t`；判存在一律 `!= std::string::npos`（或 `==`）；循环续查记得从 `p + 1` 开始，否则死循环。

### 17.1.8 substr 与比较
{: .sec-know}

`s.substr(pos, len)` 返回**新 string**，把 `[pos, pos+len)` 完整拷贝一遍——代价 O(len)。这没什么不对，但意味着两件事：循环里反复 substr 处理大字符串是 O(n²) 累积；只想"看"不"存"的时候，`string_view` 的 substr 是零拷贝（见 17.2.4）。另一个细节：`pos` 超过 `size()` 时 substr 抛 `out_of_range`，不是返回空串。

比较有三层：

```cpp
// compare_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string a = "apple", b = "banana";

    std::cout << (a == b) << (a < b) << '\n';       // 运算符：逐字符按字典序
    std::cout << (a <=> b < 0) << '\n';             // C++20：三路比较，强序

    int r = a.compare(b);                           // compare：返回负/零/正
    std::cout << r << '\n';                         // apple < banana：负值

    std::cout << a.compare(0, 3, "app") << '\n';    // 只比较 a 的前 3 个字符：相等得 0
}
```

```bash
g++ -std=c++20 -Wall -Wextra compare_demo.cpp -o cpd && ./cpd
```

```text
0 1
1
-1
0
```

日常用 `==` 和 `<` 就够；`compare` 的价值在"部分区间比较"和"需要负/零/正三分结果"的场合。字符比较按 `char_traits<char>::lt` 执行，内部按 unsigned char 解释——纯 ASCII 没问题，多字节编码下"字典序"是字节序，和语言意义上的排序不是一回事（17.4.1 展开）。

C++20 补了 `starts_with` / `ends_with`，C++23 再补 `contains`，三个都是 O(k) 且不产生临时对象，从此告别 `rfind(x, 0) == 0` 这种前缀判定的黑话写法：

```cpp
// prefix_demo.cpp —— 需要 -std=c++23（contains；前两者 C++20 即可）
#include <iostream>
#include <string>

int main() {
    std::string s = "config.json";
    std::cout << s.starts_with("config") << '\n';   // C++20
    std::cout << s.ends_with(".json")    << '\n';   // C++20
    std::cout << s.contains("fig.j")     << '\n';   // C++23
}
```

```bash
g++ -std=c++23 -Wall -Wextra prefix_demo.cpp -o pd && ./pd
```

```text
1
1
1
```

## 17.2 string类的运算
{: .sec-expl}

### 17.2.1 算术与比较运算符
{: .sec-know}

`operator+` 是非成员函数——设计动机在 15.5.2 讲过：让 `"abc" + s` 和 `s + "abc"` 都合法，左操作数是字面量也不破功。`+=` 是成员，原地追加。比较运算符两侧都允许 string、C 字符串、混合出现：

```cpp
// ops_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string a = "ab", b = "cd";

    std::string c = a + b;          // 非成员 +：两侧任意组合
    std::string d = "prefix" + a;   // 字面量在左：只有非成员写法才支持
    a += b;                         // 成员 +=：原地
    std::cout << c << ' ' << d << ' ' << a << '\n';

    std::cout << (a == c) << ' ' << (a < "zz") << '\n';  // 内容比较，不是地址比较
}
```

```bash
g++ -std=c++20 -Wall -Wextra ops_demo.cpp -o opd && ./opd
```

```text

1 1
```

"内容比较"是 string 相对 C 字符串的质变：`strcmp` 时代比较的是指针还是内容全看你传了什么，`==` 在 string 语境下永远是内容。注意 `+` 两边**不能同时是字面量**（`"a" + "b"` 是两个 `const char*` 相加，编译错），想拼字面量用 `std::format` 或至少一边加 `"s"` 后缀。

### 17.2.2 数值互转：三套工具的取舍
{: .sec-know}

string 与数字互转有三代工具，取舍各不相同：

| 工具 | 版本 | 错误处理 | locale | 适用 |
| --- | --- | --- | --- | --- |
| `stoi`/`stol`/`stod` 等 | C++11 | 抛异常 | `stod` 系受 locale 影响 | 方便优先、输入可信 |
| `to_string` | C++11 | 不抛 | 无 | 快速转字符串，但浮点格式固定 |
| `to_chars`/`from_chars` | C++17 | 错误码，不抛 | 完全无关 | 性能敏感、要精确控制 |
| `std::format` | C++20 | 抛 `format_error`（解析期） | 无 | 输出格式化 |

```cpp
// num_conv.cpp —— 需要 -std=c++20
#include <iostream>
#include <stdexcept>
#include <string>

int main() {
    std::size_t used = 0;
    int v = std::stoi("42px", &used);      // 第二个参数收"消费了多少字符"
    std::cout << v << ' ' << used << '\n'; // 42 2

    try {
        std::stoi("abc");                  // 一个数字都没有
    } catch (const std::invalid_argument&) {
        std::cout << "invalid_argument\n";
    }
    try {
        std::stoi("99999999999999");       // 超出 int 范围
    } catch (const std::out_of_range&) {
        std::cout << "out_of_range\n";
    }

    std::cout << std::to_string(42) << ' '
              << std::to_string(3.14159) << '\n';   // 浮点固定 6 位小数
}
```

```bash
g++ -std=c++20 -Wall -Wextra num_conv.cpp -o nc && ./nc
```

```text
42 2
invalid_argument
out_of_range
42 3.141590
```

`stoi` 家族的两个特性别忽略：`pos` 出参告诉你消费到哪（处理 "42px" 这类混合内容必需）；异常分两种——完全无法转换抛 `invalid_argument`，转换了但放不下抛 `out_of_range`。`to_string(3.14159)` 得到 `"3.141590"` 是因为它按 `printf` 的 `%f` 走，浮点格式不可控，想控制格式用 format 或 to_chars。

`<charconv>`（C++17）是性能与正确性的天花板：不分配、不抛异常、不认 locale，浮点输出还是"最短往返"表示（保证 round-trip 恢复原值的最短形式）：

```cpp
// charconv_demo.cpp —— 需要 -std=c++20（浮点重载需 GCC 11+）
#include <charconv>
#include <iostream>
#include <string>
#include <string_view>
#include <system_error>

int main() {
    char buf[32]{};
    auto [p1, ec1] = std::to_chars(buf, buf + sizeof buf, 3.14159);
    std::cout << std::string_view(buf, p1 - buf)
              << " ok=" << (ec1 == std::errc{}) << '\n';

    std::string_view sv = "12345x";
    int v = 0;
    auto [p2, ec2] = std::from_chars(sv.data(), sv.data() + sv.size(), v);
    std::cout << v << " consumed=" << (p2 - sv.data()) << '\n';   // 5 个字符

    double d = 0;
    auto r3 = std::from_chars(sv.data(), sv.data() + sv.size(), d); // "12345x" 转 double
    std::cout << "double: " << (r3.ec == std::errc{} ? "ok" : "fail") << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra charconv_demo.cpp -o cvd && ./cvd
```

```text
3.14159 ok=1
12345 consumed=5
double: ok
```

`to_chars`/`from_chars` 返回一个小结构（`ptr` + `ec`），配结构化绑定一行接住；`ec` 等于 `std::errc{}` 即成功。`from_chars` 不跳前导空白（与 `strtol` 的行为差异，别踩）；失败时不写入结果、返回 `invalid_argument` 或 `result_out_of_range`，错误处理是纯判断没有异常开销。解析热路径（配置文件、网络协议、CSV）用它，比 `stoi` 快数倍。

`std::format`（C++20）负责另一头——把数值按格式拼进字符串：

```cpp

#include <iostream>

int main() {
    std::cout << std::format("{} + {} = {}\n", 1, 2, 3);
    std::cout << std::format("{:>8.2f}|\n", 3.14159);   // 右对齐、宽 8、两位小数
    std::cout << std::format("{0} {1} {0}\n", "x", 42); // 按位置复用参数
}
```

格式串在编译期检查（字面量格式串与参数不匹配直接编译错），这是它对 `printf` 和 iostream 操纵符的碾压性优势。

### 17.2.3 string_view：零拷贝的只读视图
{: .sec-ext}

`std::string_view`（C++17）是一个"指针 + 长度"的只读窗口，本身不拥有任何内存。它解决的问题是：函数参数不想拷贝、不想限定调用方必须持有 string、也不想被 C 字符串的 `strlen` 卡一下——`string_view` 接住字面量、string、字符数组一切形态，构造全是 O(1)：

```cpp
// sv_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <string_view>

int count_vowels(std::string_view sv) {   // 值传视图：零分配零拷贝
    int n = 0;
    for (char c : sv)
        if (c == 'a' || c == 'e' || c == 'i' || c == 'o' || c == 'u') ++n;
    return n;
}

int main() {
    std::cout << count_vowels("hello world") << '\n';  // 字面量直接进，不构造 string

    std::string s = "beautiful day";
    std::cout << count_vowels(s) << '\n';              // string 隐式转 view

    std::cout << count_vowels(s.substr(0, 4)) << '\n'; // string::substr：O(n) 拷贝
    std::cout << count_vowels(std::string_view{s}.substr(0, 4)) << '\n';  // view::substr：零拷贝

    std::string_view path = "  indent";
    path.remove_prefix(2);                             // 头部裁剪：只动指针，O(1)
    std::cout << '[' << path << "]\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra sv_demo.cpp -o svd && ./svd
```

```text
3
6
3
3
[indent]
```

`remove_prefix` / `remove_suffix` 是 view 独有的 O(1) 修剪——string 做同样的事要么 erase 要么 substr，都绕不开数据搬家。

view 的规则是"只借不还"，于是所有坑都来自**底下的内存比 view 先死**：

| 悬垂场景 | 代码形态 | 后果 |
| --- | --- | --- |
| 绑定临时 string | `string_view v = std::string("x");` | 语句结束临时析构，v 悬垂 |
| 函数返回 view 指向局部 | `return std::string_view(local);` | 离开函数即悬垂 |
| 函数返回参数的 view 却存起来长期用 | `auto v = get_name();` 底层对象随后销毁 | 延迟引爆 |
| 容器里存 view 指向会变动的 string | `vector<string_view> vv{...v[0]...}` 后再 push_back | SSO 串搬家、堆串重分配都可能导致悬垂 |

```cpp
// sv_dangle.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>
#include <string_view>

std::string_view bad() {
    std::string local = "temporary";
    return local;                       // 返回指向局部变量的视图：悬垂（编译器通常会警告）
}

std::string_view also_bad() {
    return std::string("temporary");    // 同样悬垂：临时对象当场死
}

std::string_view ok(std::string& s) {   // 合同写清楚：调用方保证 s 活着
    return s;
}

int main() {
    // std::cout << bad() << '\n';      // undefined behavior，别执行
    std::string s = "live long enough";
    std::cout << ok(s) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra sv_dangle.cpp -o svg && ./svg
```

```text
live long enough
```

> **坑：** string_view **不保证以 '\0' 结尾**。切出来的子视图尾部就是普通字符，直接把 `sv.data()` 传给要 C 字符串的 API（`fopen`、`printf %s`、`execvp`……）会读到越界。需要 C 字符串时构造一份 `std::string(sv)` 拿它的 `c_str()`。GCC/Clang 对返回局部 string 的 view 通常能警告（`-Wreturn-local-addr` 及其 string_view 变体），MSVC 也有对应警告，但编译器救不了"容器存 view"这类跨语句悬垂——纪律只能靠自己：**view 是函数参数和局部变量的语言，不是成员变量和容器的语言**。
{: .sec-pit}

### 17.2.4 字面量后缀："s" 与 "sv"
{: .sec-know}

裸字面量的类型是 `const char[5]`，很多 bug 源于把它误当 string 用。两个用户定义字面量（C++11 机制）把类型拉正：

```cpp
// literals_demo.cpp —— 需要 -std=c++20

#include <string>
#include <string_view>

using namespace std::string_literals;        // ""s：C++14
using namespace std::string_view_literals;   // ""sv：C++17

int main() {
    auto s1 = "plain";     // const char*
    auto s2 = "text"s;     // std::string
    auto s3 = "view"sv;    // std::string_view

    std::cout << s2.size() << ' ' << s3.size() << '\n';
    // s1 + "!"          // 编译错：指针加指针
    std::cout << (s2 + "!") << ' ' << (s3 == std::string_view{"view"}) << '\n';
}
```

g++ -std=c++20 -Wall -Wextra literals_demo.cpp -o lt && ./lt
```

```

`"s"` 后缀还有一个隐性福利：`"hello\0world"s` 的 size 是 11——字面量带内嵌 0 时，C 字符串构造会截断，而 `""s` 按数组完整长度构造。需要含 0 内容时这是唯一干净路径。两个 using 指令建议写在函数内或统一放文件头，别裸放头文件里污染所有包含者。

### 17.2.5 辨析：string 与 string_view 的所有权
{: .sec-iv}

| 维度 | std::string | std::string_view |
| --- | --- | --- |
| 内存所有权 | 拥有，负责分配释放 | 不拥有，只引用 |
| 修改内容 | 可以 | 不可以（只读视图） |
| substr 代价 | O(n) 拷贝 | O(1) 改指针和长度 |
| 传给 C API | `c_str()` 直接用 | 必须先转 string |
| 存入容器/成员 | 安全 | 危险，需证明底层活得够久 |
| 作为函数参数 | 拷贝或引用，可能分配 | 零拷贝，首选 |

一句话分工：**产生和保存数据用 string，读取和检查数据用 string_view**。写"输入参数"时默认 string_view，写"存储成员"时默认 string，这条分界线清晰之后，两类问题（多余拷贝、悬垂指针）都会大幅减少。

## 17.3 string类综合应用
{: .sec-prac}

### 17.3.1 完整程序一：日志行格式化
{: .sec-prac}

日志行格式化的核心诉求：时间戳 + 级别 + 消息拼成一行，高频调用下不产生内存抖动。下面的实现复用一条 string 缓冲区（`clear()` 后 capacity 保留，稳态零分配），时间戳用 `<ctime>` 的 `strftime` 生成：

```cpp
// log_format.cpp —— 需要 -std=c++20
#include <ctime>
#include <iostream>
#include <sstream>
#include <string>
#include <string_view>

enum class Level { Info, Warn, Error };

std::string_view level_name(Level lv) {
    switch (lv) {
        case Level::Info:  return "INFO";
        case Level::Warn:  return "WARN";
        case Level::Error: return "ERROR";
    }
    return "?";
}

std::string timestamp() {
    std::time_t t = std::time(nullptr);
    char buf[24]{};
    std::strftime(buf, sizeof buf, "%H:%M:%S", std::localtime(&t));
    return buf;
}

class Logger {
public:
    explicit Logger(std::ostream& os) : os_(os) {}

    void log(Level lv, std::string_view msg) {
        line_.clear();                        // clear 不还内存：稳态下后续 += 零分配
        line_ += '[';
        line_ += timestamp();                 // timestamp() 内部有一次小分配，可再优化
        line_ += "] [";
        line_ += level_name(lv);
        line_ += "] ";
        line_ += msg;
        line_ += '\n';
        os_ << line_;
    }

private:
    std::ostream& os_;
    std::string line_;
};

int main() {
    Logger logger{std::cout};
    logger.log(Level::Info,  "service started");
    logger.log(Level::Warn,  "disk usage 91%");
    logger.log(Level::Error, "connection lost");
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra log_format.cpp -o lf && ./lf
```

```text
[14:22:07] [INFO] service started
[14:22:07] [WARN] disk usage 91%
[14:22:07] [ERROR] connection lost
```

时间字段每次运行不同，上面是某次运行的输出。三个设计点值得咀嚼：`line_` 复用让拼接主路径零分配；`level_name` 返回 `string_view` 是"只读引用常量数据"的标准用法；`timestamp()` 返回 `std::string` 每行仍有一次分配，追求极致可以改成往 `line_` 上直接 `append` 一个 `to_chars` 写出的 buffer——17.4.3 的路线。若能用 C++20 的 `std::format`（GCC 13+），整个拼接可写成 `std::format("[{}] [{}] {}", ts, level_name(lv), msg)`，可读性更好。

### 17.3.2 完整程序二：CSV 解析
{: .sec-prac}

CSV 的难点不在逗号切分，在**引号字段**：字段内可以有逗号（整个字段加引号）、可以有转义的 `""`（表示一个引号字符）。下面用单遍字符状态机实现，数值列用 `from_chars` 转换：

```cpp
// csv_parse.cpp —— 需要 -std=c++20
#include <charconv>
#include <iostream>
#include <string>
#include <string_view>
#include <system_error>
#include <vector>

// 单遍状态机：in_quotes 为真时逗号和引号按转义规则处理
std::vector<std::string> split_csv_line(const std::string& line) {
    std::vector<std::string> out;
    std::string cur;
    bool in_quotes = false;
    for (std::size_t i = 0; i < line.size(); ++i) {
        char c = line[i];
        if (in_quotes) {
            if (c == '"') {
                if (i + 1 < line.size() && line[i + 1] == '"') {
                    cur += '"';       // "" 转义成一个引号
                    ++i;              // 跳过后一个引号
                } else {
                    in_quotes = false;
                }
            } else {
                cur += c;
            }
        } else {
            if (c == '"') {
                in_quotes = true;
            } else if (c == ',') {
                out.push_back(cur);
                cur.clear();
            } else {
                cur += c;
            }
        }
    }
    out.push_back(cur);               // 最后一个字段
    return out;
}

int to_int(std::string_view sv) {
    int v = 0;
    auto [p, ec] = std::from_chars(sv.data(), sv.data() + sv.size(), v);
    return ec == std::errc{} ? v : -1;    // 解析失败给哨兵值，工程上应上报
}

int main() {
    std::string data =
        "name,age,score\n"
        "Alice,30,91\n"
        "\"Bo,\"\"Bob\"\", Jr\",25,88\n"     // 引号字段：内含逗号与转义引号
        "Cathy,28,95\n";

    std::size_t start = 0;
    bool header = true;
    while (start < data.size()) {
        std::size_t end = data.find('\n', start);
        if (end == std::string::npos) end = data.size();
        std::string line = data.substr(start, end - start);
        start = end + 1;                      // end == size 时 start 越界一格，循环条件收尾

        if (!line.empty() && line.back() == '\r')  // 兼容 Windows 换行
            line.pop_back();
        if (line.empty())
            continue;

        auto fields = split_csv_line(line);
        if (header) { header = false; continue; }

        std::cout << fields[0] << " | age=" << to_int(fields[1])
                  << " | score=" << to_int(fields[2]) << '\n';
    }
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra csv_parse.cpp -o csv && ./csv
```

```text
Alice | age=30 | score=91
Bo,"Bob", Jr | age=25 | score=88
Cathy | age=28 | score=95
```

这份实现覆盖了 CSV 的核心弯路：引号内逗号不切分、`""` 转义、CRLF 兼容、空行跳过、表头跳过。真实工程还差 UTF-8 BOM（文件头三个字节 `EF BB BF`，读第一行时剥掉）、字段数校验、错误行报告——以及一个反直觉的性能结论：这种逐字符状态机配合 `cur += c` 在 -O2 下已经非常快，把 `cur` 声明提到循环外复用（像 17.3.1 那样）能再省一截。字段解析用 `string_view` 切片再 `from_chars`，全程除结果串外零分配。

### 17.4.1 编码：UTF-8、char8_t 与宽字符
{: .sec-know}

`std::string` 存的是**字节**，不是字符。UTF-8 里一个汉字 3 字节、emoji 4 字节，所以：

```cpp
// utf8_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::string s = "\xE4\xB8\xAD\xE6\x96\x87";   // "中文" 的 UTF-8 字节，避免源码编码干扰
    std::cout << s.size() << '\n';                 // 6：字节数，不是 2 个字符
    std::cout << s.substr(0, 3) << '\n';           // 前 3 字节恰好是 "中"

    std::string bad = s.substr(0, 2);              // 从中间砍断：非法 UTF-8 序列
    std::cout << bad.size() << '\n';               // 2：string 不校验编码，照样存
}
```

```bash
g++ -std=c++20 -Wall -Wextra utf8_demo.cpp -o u8d && ./u8d
```

```text
6
中
2
```

结尾一行演示了标准库的立场：**string 只管字节，不做任何编码校验和转码**。砍断的字节序列照样塞进容器，直到输出环节才表现成乱码。多字节字符的"字符数"（code point 数）、字素数（用户眼中的字符数）都要专门的库来数。

C++20 引入 `char8_t` 与 `std::u8string`，让"UTF-8 字节串"在类型系统里与普通字节串分开：

```cpp
// u8string_demo.cpp —— 需要 -std=c++20
#include <iostream>
#include <string>

int main() {
    std::u8string s = u8"中文";           // 每个元素是 char8_t，内容仍是 UTF-8 字节
    std::cout << "bytes = " << s.size() << '\n';    // 6
    // std::cout << s << '\n';            // 编译错：char8_t 串不能直接进 char 流
    std::string raw = reinterpret_cast<const char*>(s.c_str());  // 逃生门：char 可别名任何对象
    std::cout << raw << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra u8string_demo.cpp -o u8s && ./u8s
```

```text
bytes = 6
中
```

`char8_t` 的设计初衷是类型安全（防止 UTF-8 字节和普通 char 混流），代价是与既有 `char` 接口的互操作性变差——上面那个 `reinterpret_cast` 是社区公认的过渡手段（char 别名访问在标准里合法）。务实建议：**内部一律用 `std::string` 存 UTF-8，边界处转码**，u8string 用于需要编译器把关的少量场景。

宽字符体系的要点是平台差异：

```cpp
// wchar_demo.cpp —— 需要 -std=c++20
#include <iostream>

int main() {
    std::cout << sizeof(wchar_t) << " bytes\n";    // Windows: 2，Linux: 4
    std::cout << sizeof(char16_t) << ' ' << sizeof(char32_t) << '\n';   // 2 4，全平台一致
}
```

```bash
g++ -std=c++20 -Wall -Wextra wchar_demo.cpp -o wd && ./wd
```

```text
4 bytes
2 4
```

| 类型 | 宽度 | 编码 | 平台差异 |
| --- | --- | --- | --- |
| `wchar_t` | Windows 2 字节 / Linux 4 字节 | Windows 是 UTF-16，Linux 是 UTF-32 | 大，跨平台代码慎用 |
| `char16_t` / `std::u16string` | 恒 2 字节 | UTF-16 | 无 |
| `char32_t` / `std::u32string` | 恒 4 字节 | UTF-32 | 无 |
| `char8_t` / `std::u8string` | 恒 1 字节 | UTF-8 | 无，C++20 起 |

标准库同样不提供 UTF-16/UTF-32 与 UTF-8 之间的转码。需要真转码（图标转换、字素切分、locale 感知的大小写、规范化 NFC/NFD）上第三方库：**ICU** 是全功能重量级，**utf8cpp** 是轻量单头文件方案。工程上最省心的策略是"UTF-8 everywhere"：进程内部一律 UTF-8 + `std::string`，只在 OS API 边界（Windows 的宽字符 API、文件系统路径）做一次转换。

### 17.4.2 与 C API 互操作：c_str() 的生命周期
{: .sec-know}

`c_str()` 的合同是：返回的指针**在 string 自身未被修改期间**有效。失效条件比直觉宽——不只是扩容搬家，**任何**修改操作（包括就地改写一个 SSO 短串）都使旧指针作废：

```cpp
// c_api_demo.cpp —— 需要 -std=c++20
#include <cstdio>
#include <cstring>
#include <string>

int main() {
    std::string s = "c api";
    std::FILE* f = std::fopen("demo.txt", "w");
    std::fputs(s.c_str(), f);          // 指针在 fputs 本次调用内有效，安全
    std::fclose(f);

    char line[64]{};
    f = std::fopen("demo.txt", "r");
    std::fgets(line, sizeof line, f);
    std::fclose(f);
    std::string got = line;            // C 世界的数据收进 string，交还所有权
    std::size_t n = std::strlen(got.c_str());
    std::cout << "read " << n << " bytes\n";

    got += '\n';                       // 从这一刻起，之前任何 c_str() 指针全部失效
    std::fputs(got.c_str(), stdout);   // 所以重新取，别缓存旧指针
}
```

```bash
g++ -std=c++20 -Wall -Wextra c_api_demo.cpp -o capi && ./capi
```

```text
read 5 bytes
c api
```

> **坑：** 把 `c_str()` 存进变量"以后用"是最常见的死法——中间任何一次 `+=`、`insert`、甚至 resize 都可能让缓冲区搬家。规矩：`c_str()` 只在"取指针、立刻传参"这个原子动作里存在，绝不落变量、绝不存成员、绝不过函数边界。需要长期持有 C 形式的字符串，说明它应该就是一份独立的 `char` 数组拷贝。
{: .sec-pit}

反方向（C 数据进 string）倒是简单：`std::string(buf)` 或 `std::string(buf, len)` 拷贝接管，之后 C 缓冲区怎么变都与 string 无关。注意 `std::string(ptr)` 靠找 '\0' 定长——C 缓冲区若无 '\0'（如二进制数据），必须用带长度的构造。

### 17.4.3 性能实践：选对工具
{: .sec-best}

拼接字符串的三种主流写法，适用场景完全不同：

| 方式 | 分配行为 | 可读性 | 适用 |
| --- | --- | --- | --- |
| `+=`（配 reserve） | 复用缓冲，稳态零分配 | 一般 | 热路径、日志、循环拼接 |
| `ostringstream` | 内部缓冲 + 最终 str() 一次拷贝 | 好 | 少量复杂格式化、旧代码库 |
| `std::format` | 通常一次成型 | 最好 | C++20 可用时的默认选择 |

结合全篇，性能实践的优先级清单：

1. **循环拼接用 `+=`，永不用 `x = x + ...`**（17.1.6 的 O(n²) 教训）。
2. **量级已知先 `reserve`**，一次扩容到位，避免 15→30→60 的连锁搬家。
3. **只读参数用 `string_view`**，消灭传参拷贝；返回切片用 view 或迭代器对，消灭 substr 拷贝。
4. **缓冲复用**：高频路径上的临时 string 提出来做局部复用（17.3.1 的 `line_` 模式），`clear()` 不还内存正好是特性。
5. **数值转换用 `<charconv>`**：不抛异常、不认 locale、最短往返，比 `stoi`/`to_string` 快数倍。
6. **消灭中间临时**：`a + b + c` 每个加号产生一个新串；C++20 后编译器对某些形态能优化，但显式 `tmp += a; tmp += b; tmp += c;` 永远不会更差。

一个反直觉的收尾：`std::format` 在 GCC 13+ 里对简单场景比 `ostringstream` 快一倍以上，比手写 `+=` 慢不了多少——可读性和性能在这里不冲突，新代码默认用它，热点再降级到 `+=`。

### 17.4.4 变式自测：三个高频疑问
{: .sec-think}

1. **`s.data()` 和 `s.c_str()` 有区别吗？**
   C++11 起功能上等价（都以 '\0' 结尾、都返回 `const char*`）。历史上 `data()` 不保证结尾、`c_str()` 保证，C++11 统一并把 C++17 的非 const `data()` 也纳入。语义区分只剩习惯：给 C API 传参用 `c_str()`，做字节层访问用 `data()`。

2. **`string` 参数传值还是传 const 引用？**
   传值在调用方传临时对象时可以靠移动省一次深拷贝，传 const 引用在传左值时省一次拷贝指针的开销……实际上主流结论很无聊：输入参数用 `string_view`，需要"留下所有权"的场景再传值（拿移动语义），只有"必须长期持有且调用方保证 string"这种窄场景才值得 const 引用。别在这上面过度设计。

3. **为什么 `find` 家族不返回迭代器？**
   历史包袱。string 的接口一半来自 C（下标、npos），一半来自容器（迭代器），设计时选了下标风格，与 `std::search` 等泛型算法的迭代器风格并存至今。想要迭代器风格，把 string 当 range 用 `<algorithm>`：`std::ranges::search(s, pat)`。两种都合法，同一个项目里统一即可。

## 变式追问
{: .sec-think}

1. **SSO 让"移动 string 不一定比拷贝快"——那移动还值得写吗？**
   值得，但理由变了。移动堆串是三次指针交换，移动 SSO 串是拷贝 15 字节加标志位，两者都是纳秒级；真正要避开的是深拷贝（任意长度）。所以结论不是"别用移动"，而是"别为单个小 string 过度纠结，为容器扩容、函数返回这些批量场景保留移动"。写 `std::move` 的收益从来是"避免未知长度的深拷贝"，不是"一定快"。

2. **为什么 `operator[](size())` 特意定义为返回 '\0'，而 `at(size())` 抛异常？**
   这是对两种使用习惯的兼容：C 背景的代码依赖 `while (s[i] != '\0')` 的遍历方式，`operator[]` 在合法边界上多给一个 '\0' 能让这类代码无缝工作且不越界；`at()` 的合同是"严格的边界检查"，多给任何东西都违背它的语义。两个函数服务两种正确性模型，同时存在不打架。

3. **`string_view` 既然这么危险，为什么不干脆禁用？**
   它的收益集中在两个无可替代的位置：函数参数（零拷贝接受一切字符串形态）和解析切片（O(1) 窗口）。禁用它等于退回"每个解析函数都要么拷贝要么模板化"的世界。风险管理的正确姿势是约束使用场景——参数与局部变量用，成员与容器不用——而不是整体放弃。语言也在收敛风险：C++23 删掉了"从右值 range 构造 string_view"这条最容易悬垂的路径（P2446），编译器与静态检查工具对局部悬垂的警告也越来越全。

4. **如果要自己实现一个"带编码感知的字符串类"，最该先解决的问题是什么？**
   不是接口，是**迭代单位**：按字节、按 code point 还是按字素迭代，决定了 size、find、substr 的全部语义。UTF-8 的可变长让"第 n 个字符"退化为 O(n) 操作，任何声称 O(1) 随机访问又能按字符切分的方案都不存在（UTF-32 也有字素簇问题）。想清楚这一点后，多数项目会得出结论：底层存 UTF-8 字节、按字节给容器式接口、按字符的视图用现成库（ICU 的 BreakIterator）——自己从零写转码和字素分析，性价比极低。
