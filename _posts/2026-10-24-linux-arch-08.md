1. 管理端没有分发好主机的公钥

```text
/usr/sbin/sshd -D   --- 负责建立远程连接

```

### 模块应用回顾

| 模块 | 作用 |
| --- | --- |
| `command` | 在远程主机上执行命令操作（默认模块） |
| `shell` | 在远程主机上执行命令操作（万能模块） |
| `script` | 批量执行本地脚本 |
| `copy` | 用于批量分发传输数据信息，管理端 → 多个被管理端 |
| `fetch` | 用于将远程主机数据进行拉取到本地管理主机，管理端 ← 多个被管理端 |
| `file` | 修改数据属性信息 / 创建数据信息 |

> **注意：** 有时剧本不能反复执行，编写剧本时要考虑幂等性。幂等性说白了就是"重复执行不出事"：模块执行前先检查目标状态，符合预期就直接返回 ok、不再动手。所以同一个剧本第一次跑是 changed，第二次全 ok，第三次照跑不误——部署动作天然可以重放，裸脚本做不到这一点。

### 辨析：inventory 五种写法的适用场景 {: .sec-bianxi}

主机清单常见五种写法各有场景：少量固定机器，直接一行一个 IP；连续编号的主机，用 `web[01:03]` 区间匹配省行数；SSH 改过端口，用 `主机:端口`；单机需要特殊连接参数（别名、专用用户）时，挂在主机行尾做主机变量；一套架构分服务端、客户端多个角色时，用 `[组:children]` 把子组收拢成大组，一条命令打整套。选择原则一句话：能用分组表达的不要散写主机，能进组变量的不要每台机器重复一遍。

## fetch 模块：批量拉取数据

与 `copy` 方向相反，把被管理端的文件拉回管理端。

| 参数 | 说明 |
| --- | --- |
| `src` | 远程主机上的源文件 |
| `dest` | 管理端本地保存的目标目录 |

```bash
ansible 172.16.1.31 -m fetch -a "src=/tmp/test.txt dest=/tmp"
```

有个容易犯迷糊的点：fetch 拉回来的文件会按"目标主机名/IP"自动分目录存放（`dest/主机名/src路径`），`dest` 是目录不是文件名。要聚合多台机器的同名文件（比如各机日志），这个自动分目录反而是便利——按 `inventory_hostname` 归档，不会互相覆盖。配合 `archive` 模块先在远端打包、再 fetch 回管理端，就是没有备份系统时的最小备份方案。

## yum 模块：批量安装软件

| 参数 | 说明 |
| --- | --- |
| `name` | 指定安装软件名称 |
| `state` | 指定是否安装软件 |

`state` 的取值：

| 取值 | 含义 |
| --- | --- |
| `installed` | 安装软件 |
| `present` | 安装软件 |
| `latest` | 安装最新版本 |
| `absent` | 卸载软件 |
| `removed` | 卸载软件 |

```bash
ansible 172.16.1.31 -m yum -a "name=iotop state=installed"
```

时间字段支持区间与步进：`*/5` 每 5 分钟、`1-5` 周一到周五、`0,30` 第 0 和第 30 分，原样填进对应参数即可。拿不准格式时先在测试机 `crontab -e` 手写验证，再用模块固化。

### 补充：cron 模块与手工 crontab 的区别

手工 `crontab -e` 是"编辑文件"：不可重复、不可追溯，谁改过一行无从查起。cron 模块是"声明状态"：`name` 就是任务的身份证，同名即更新、`state=absent` 即删除，剧本可以反复跑。生产定时任务一律用模块管理，手工任务只留给临时排查，用完即删。

## service 模块：管理服务运行状态

用于管理服务器的运行状态：停止、开启、重启。

| 参数 | 说明 |
| --- | --- |
| `name` | 指定管理的服务名称 |
| `state` | 指定服务状态：`started`（启动）/ `restarted`（重启）/ `stopped`（停止） |
| `enabled` | 指定服务是否开机自启动 |

```bash
ansible 172.16.1.31 -m service -a "name=nfs state=started enabled=yes"
```

## cron 模块：批量设置定时任务

先回顾一下定时任务的时间格式：

```text
crontab -e
*   *  *  *  *  定时任务动作
分 时 日 月 周
```

| 参数 | 说明 |
| --- | --- |
| `minute` | Minute when the job should run ( 0-59, *, */2, etc )：设置分钟信息 |
| `hour` | Hour when the job should run ( 0-23, *, */2, etc )：设置小时信息 |
| `day` | Day of the month the job should run ( 1-31, *, */2, etc )：设置日期信息 |
| `month` | Month of the year the job should run ( 1-12, *, */2, etc )：设置月份信息 |
| `weekday` | Day of the week that job should run ( 0-6 for Sunday-Saturday, *, etc )：设置周信息 |
| `job` | 用于定义定时任务需要干的事情 |

**基本用法：**

```bash
ansible 172.16.1.31 -m cron -a "minute=0 hour=2 job='/usr/sbin/ntpdate ntp1.aliyun.com >/dev/null 2>&1'"
```

**扩展用法：**

```bash
# 01. 给定时任务设置注释信息（用 name 参数）
ansible 172.16.1.31 -m cron -a "name='time sync' minute=0 hour=2 job='/usr/sbin/ntpdate ntp1.aliyun.com >/dev/null 2>&1'"

# 02. 如何删除指定定时任务
ansible 172.16.1.31 -m cron -a "name='time sync01' state=absent"

# 03. 如何批量注释定时任务
ansible 172.16.1.31 -m cron -a "name='time sync' job='/usr/sbin/ntpdate ntp1.aliyun.com >/dev/null 2>&1' disabled=yes"
```

> **注意：** Ansible 可以删除的定时任务，只能是 Ansible 自己设置好的定时任务。手工 `crontab -e` 写进去的任务没有 `name` 注释标识，无法通过 `state=absent` 精确删除。

## mount 模块：批量进行挂载操作

| 参数 | 说明 |
| --- | --- |
| `src` | 需要挂载的存储设备或文件信息 |
| `path` | 指定目标挂载点目录 |
| `fstype` | 指定挂载时的文件系统类型 |
| `state` | 挂载或卸载，见下表 |

`state` 的四种取值区别（**这是最容易混淆的地方**）：

| `state` 取值 | 是否立即生效 | 是否修改 `/etc/fstab` |
| --- | --- | --- |
| `present` | 不会实现立即挂载 | 修改 fstab 文件，实现开机自动挂载 |
| `mounted` | 会实现立即挂载 | 并且会修改 fstab 文件，实现开机自动挂载（**推荐**） |
| `absent` | 会实现立即卸载 | 并且会删除 fstab 文件信息，禁止开机自动挂载 |
| `unmounted` | 会实现立即卸载 | 但是不会删除 fstab 文件信息（**推荐**） |

记忆口诀：带 `ed` 的（mounted / unmounted）动当下的挂载状态，不带的（present / absent）只动 fstab 文件。临时验证用 `unmounted`，永久下线用 `absent`，别删错。

## user 模块：实现批量创建用户

**基本用法：**

```bash
ansible 172.16.1.31 -m user -a "name=user01"
```

**扩展用法：**

```bash
# 1) 指定用户 uid 信息
ansible 172.16.1.31 -m user -a "name=user02 uid=6666"

# 2) 指定用户组信息
ansible 172.16.1.31 -m user -a "name=user03 group=user02"
ansible 172.16.1.31 -m user -a "name=user04 groups=user02"

# 3) 批量创建虚拟用户
ansible 172.16.1.31 -m user -a "name=rsync create_home=no  shell=/sbin/nologin"
```

> **注意：** `group` 指定用户的基本组，`groups` 指定用户的附属组，两者含义不同。

### 给指定用户创建密码

> **注意：** 利用 Ansible 的 `user` 模块设置用户密码信息，需要将密码明文信息转换为密文信息进行设置，直接写明文不会生效。

**方法二：（忽略）**


**方法三：利用 Python 的 passlib 库生成**

#### 使用密文创建用户

```bash
ansible 172.16.1.31 -m user -a 'name=user08 password=$6$mysalt$/wTG/l1S/9yvHqUNpSsvNc78LrCKoSNXJ.2S2QNSfx3jA6ech5wyZk8jXnLh8vTIcfEre/T299vLPkHfEOHqa.'
```

> **注意：** 密码串中含有 `$` 符号，外层必须用**单引号**包裹，否则 shell 会把它当作变量展开。

还有一个值得知道的细节：`password_hash('sha512', 'mysalt')` 的盐固定，生成的密文就固定——同一台机器重复执行密码不会变，这对幂等是好事；代价是所有机器密文一致，碰撞分析更容易。安全要求高的环境用随机盐（接受每次执行报 changed），或改用密钥体系彻底避开口令。

### 辨析：常用模块的幂等差异 {: .sec-bianxi}

`yum` / `file` / `copy` / `service` / `user` 这类"资源型"模块都幂等：它们描述的是期望状态，已满足就跳过。`command` 与 `shell` 是"动作型"，只负责执行、不负责检查——`touch /tmp/a` 跑两次没事，`echo x >> /tmp/a` 跑几次就追加几行，`systemctl restart` 跑几次就重启几次。写剧本的经验法则：能用资源型模块表达的，绝不落到 `shell`；实在要用，配 `creates` / `removes` 参数或 `changed_when` 把副作用管住。

## 进阶模块：template / archive / stat / wait_for

### template 模块与 Jinja2

`copy` 是"原样拷贝"，`template` 是"先渲染再拷贝"：把模板里的变量替换成实际值再写到被管理端。一份模板适配所有主机的差异化配置，改端口、改地址只动模板一处。

Jinja2 基础语法速查：

| 语法 | 含义 |
| --- | --- |
| `{{ 变量名 }}` | 输出变量值 |
| `{{ 变量名 \| 过滤器 }}` | 输出经过滤器处理的值，如 `{{ name \| default('www') }}` |
| `{% for x in list %} ... {% endfor %}` | 循环，可配 `{% if %}` 条件 |
| `{% if 条件 %} ... {% endif %}` | 条件分支 |
| `{# 注释 #}` | 模板注释，不出现在渲染结果里 |
| `-`（连字符） | `{{-` 或 `-%}` 控制空白，避免渲染出多余空行 |

模板示例 `templates/hosts.j2`：

```ini
127.0.0.1 localhost
{% for host in groups['web'] %}
{{ hostvars[host].ansible_default_ipv4.address }} {{ host }}
{% endfor %}
```

```bash
ansible web -m template -a "src=/etc/ansible/templates/hosts.j2 dest=/etc/hosts owner=root group=root mode=0644"
```

> **注意：** `groups['web']` 是清单里的主机组，`hostvars[主机][事实名]` 取该主机收集到的 facts；模板文件统一放 `templates/` 目录管理，与剧本一起纳入版本控制。

注意 template 的渲染发生在管理端：变量在推送前就替换完毕，被控端拿到的已经是纯文本。这意味着模板里引用的变量必须已经定义，渲染失败会直接报 `undefined variable`——所以模板调试时先在管理端用 debug 模块打印关键变量，确认取值无误再推送。

### archive / unarchive 模块

| 模块 | 作用 | 常用参数 |
| --- | --- | --- |
| `archive` | 把被管端目录打包成压缩包 | `path` / `dest` / `format`（`gz` / `bz2` / `xz` / `zip`） |
| `unarchive` | 把压缩包解压到被管端 | `src` / `dest` / `remote_src=yes`（源在远程时）/ `creates`（已存在则跳过） |

```bash
# 打包远程日志目录
ansible web -m archive -a "path=/var/log/nginx dest=/backup/nginx-logs.tar.gz"

# 把管理端的压缩包解压到远程
ansible web -m unarchive -a "src=/server/tools/app.tar.gz dest=/opt/ creates=/opt/app"
```

> **注意：** `unarchive` 的 `src` 默认在管理端查找，加了 `remote_src=yes` 才在远程主机查找，这点与 `copy` 的 `remote_src` 行为一致。

### get_url 模块

`get_url` 相当于被管端的 `wget` / `curl`，支持 HTTP / HTTPS / FTP 下载：

```bash
ansible web -m get_url -a "url=https://example.com/pkg.rpm dest=/server/tools/pkg.rpm mode=0644"
```

### stat 模块

`stat` 只做检查不做修改，返回文件的存在性、权限、大小、校验值等属性，常配合 `register` + `when` 实现"存在才跳过"的逻辑：

```bash
ansible web -m stat -a "path=/etc/nginx/nginx.conf"
```

```console
web01 | SUCCESS => {
    "stat": {
        "exists": true,
        "path": "/etc/nginx/nginx.conf",
        "mode": "0644",
        "size": 541
    }
}
```

### 补充：stat 与 shell 判断的选择

检查文件或服务状态时，优先用 `stat` 模块加 register，而不是在 `shell` 里拼 `test -f`：stat 返回结构化字段（`exists`、`mode`、`checksum`），when 判断直接写字段路径，不用解析文本；shell 拼出来的判断既不幂等，换台机器输出格式差异还会翻车。只有"进程是否存活"这类没有对应模块的场景才落到 shell，并配 `changed_when: false`。

### wait_for 模块

等待某个条件成立再继续，常用于"等服务端口就绪"或"等文件出现"：

```bash
# 等待 80 端口就绪，最多等 30 秒
ansible web -m wait_for -a "port=80 state=started timeout=30"

# 等待某个文件出现
ansible web -m wait_for -a "path=/var/run/app.pid state=present timeout=60"
```

### debug 与 assert 模块

| 模块 | 作用 | 示例 |
| --- | --- | --- |
| `debug` | 打印变量或提示信息，剧本调试必备 | `- debug: msg="当前 IP 是 {{ ansible_default_ipv4.address }}"` |
| `assert` | 断言：条件不满足就让任务失败，用于前置校验 | `- assert: that: - ansible_os_family == "RedHat"` |

## facts 收集与自定义 facts

**facts** 是被管理主机自动上报的系统信息，由 `setup` 模块收集，剧本里可以直接当变量用：

| 常用 fact | 含义 |
| --- | --- |
| `ansible_hostname` | 主机名 |
| `ansible_default_ipv4.address` | 默认网卡 IPv4 地址 |
| `ansible_memtotal_mb` | 内存总量（MB） |
| `ansible_processor_vcpus` | CPU 核数 |
| `ansible_distribution` / `ansible_distribution_version` | 发行版与版本 |
| `ansible_os_family` | 系统家族（RedHat / Debian） |

```bash
# 只看感兴趣的部分，filter 支持通配
ansible web -m setup -a "filter=ansible_default_ipv4"
```

**自定义 facts**：把本机特有的信息（应用版本、角色标识等）放到被管端的 `/etc/ansible/facts.d/` 目录，Ansible 会自动收集并挂到 `ansible_local` 变量下：

```bash
mkdir -p /etc/ansible/facts.d
```

```ini
# /etc/ansible/facts.d/app.fact（INI 或 JSON 均可）
[app]
version=1.2.3
env=prod
```

```bash
# 通过 ansible_local 读取
ansible web -m setup -a "filter=ansible_local"
```

```text
"ansible_local": {
    "app": {
        "app": {
            "env": "prod",
            "version": "1.2.3"
        }
    }
}
```

> **注意：** facts 收集要花时间（每台主机执行一次），主机多又不需要 facts 时，在剧本里写 `gather_facts: no` 跳过；需要"不同主机不同配置"时，facts 是最可靠的判断依据。

两个实操细节：`gather_facts: no` 只对当前 play 生效，需要时可以在单独的 play 里开；facts 本身可以缓存（`fact_caching=jsonfile`），几百台机器的剧本起步时间能差出一个量级。另外 `setup` 收集的字段非常多，`filter` 过滤不只是省输出，也省网络传输与解析时间。

## 条件、循环与返回值

### when 条件

`when` 让任务只在满足条件时执行，常与 facts 配合：

```yaml
- name: 只对 RedHat 系安装 nginx
  yum:
    name: nginx
    state: installed
  when: ansible_os_family == "RedHat"

- name: 多个条件是"与"的关系（列表写法）
  service:
    name: nginx
    state: started
  when:
    - ansible_os_family == "RedHat"
    - ansible_distribution_major_version == "7"
```

### 循环

`with_items`（老语法）对列表逐项执行，新版推荐等价的 `loop` 关键字：

```yaml
- name: 批量创建用户（with_items 写法）
  user:
    name: "{{ item }}"
    state: present
  with_items:
    - user01
    - user02
    - user03

- name: 批量创建用户（loop 新写法）
  user:
    name: "{{ item }}"
    state: present
  loop:
    - user01
    - user02
    - user03
```

字典循环用 `with_dict` 或 `loop: "{{ 字典 | dict2items }}"`：

```yaml
- name: 按字典创建多个目录
  file:
    path: "{{ item.key }}"
    state: directory
    owner: "{{ item.value.owner }}"
  with_dict:
    /data/web: {owner: www}
    /data/log: {owner: www}
```

### until 重试

`until` + `retries` + `delay` 组成"重试直到成功"，适合等待服务自愈、接口就绪的场景：

```yaml
- name: 反复检查接口直到返回 200
  shell: curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1/health
  register: result
  until: result.stdout == "200"
  retries: 10
  delay: 3
```

`until` 的重试上限要按最坏情况估：`retries` 用尽任务即失败、剧本中断。等待外部系统就绪的窗口别设太小，把偶发的慢响应误判成故障。

### register 与返回值

`register` 把模块执行结果存成变量，供后续任务取用：

```yaml
- name: 检查配置文件是否存在
  stat:
    path: /etc/nginx/nginx.conf
  register: conf_stat

- name: 存在才备份
  copy:
    src: /etc/nginx/nginx.conf
    dest: /backup/nginx.conf.bak
    remote_src: yes
  when: conf_stat.stat.exists
```

| 返回字段 | 含义 |
| --- | --- |
| `changed` | 本次执行是否对主机产生了变更 |
| `rc` | 命令类模块的返回码，0 表示成功 |
| `stdout` / `stderr` / `stdout_lines` | 命令类模块的标准输出 / 错误 / 按行拆分 |
| `stat.exists` | `stat` 模块返回的"文件是否存在" |
| `failed` | 模块是否失败（一般无需手动判断） |

> **注意：** 还可以用 `failed_when` / `changed_when` 自定义"什么算失败、什么算变更"，例如一条监控命令返回码非 0 但业务上正常时，用 `failed_when: false` 修正判定。

## 剧本的编写方法

### 剧本的作用

剧本（playbook）的作用：**可以一键化完成多个任务**。

剧本里的任务和 ad-hoc 命令一一对应：`ansible-playbook` 本质是把多条 ad-hoc 按顺序、按条件组织起来。调试剧本某一步时，直接把该任务的模块与参数抄成 ad-hoc 单跑，能快速区分是任务本身的问题还是编排的问题。

动手写剧本前先回答三个问题：**目标状态是什么**（装到哪个版本、服务起没起、权限多少——写不出来说明需求没想清）；**依赖顺序是什么**（先有用户再有目录、先推配置再起服务）；**失败怎么办**（回滚剧本还是重跑即可，幂等剧本天然支持重放）。三问过一遍，剧本结构基本就出来了。

先看不用剧本时，自动化部署 rsync 服务要敲多少条命令。

**服务端的操作：**

```bash
# 第一个历程：安装软件
ansible 172.16.1.41 -m yum -a "name=rsync state=installed"

# 第二个历程：编写文件
ansible 172.16.1.41 -m copy -a "src=/xxx/rsyncd.conf dest=/etc/"

# 第三个历程：创建用户
ansible 172.16.1.41 -m user -a "name=rsync create_home=no shell=/sbin/nologin"

# 第四个历程：创建目录
ansible 172.16.1.41 -m file -a "dest=/backup state=directory owner=rsync group=rsync"

# 第五个历程：创建密码文件
ansible 172.16.1.41 -m copy -a "content='rsync_backup:<your-password>' dest=/etc/rsync.password mode=600"

# 第六个历程：启动服务
ansible 172.16.1.41 -m service -a "name=rsyncd state=started enabled=yes"
```

**客户端的操作：**

```bash
# 第一个历程：创建密码文件
ansible 客户端地址 -m copy -a "content='rsync_backup:<your-password>' dest=/etc/rsync.password mode=600"
```

### 剧本的组成部分

用拍电影来类比剧本的两个核心元素：

| 类比 | 剧本关键字 | 说明 |
| --- | --- | --- |
| 演员信息：男一号 | `hosts` | 指定在哪些主机上执行 |
| 干的事情：吻戏 | `tasks` | 指定具体执行哪些任务 |

一个剧本里可以有多个"演员"，每个演员有自己的若干件事：

```text
演员信息: 男一号   → hosts
干的事情: 吻戏     → tasks

演员信息: 男二号   → hosts
干的事情: 看着     → tasks
```

**完整的剧本结构**还包括 `vars`（变量）与 `handlers`（处理器）：

```yaml
- hosts: web
  become: yes               # 是否提权执行
  gather_facts: yes         # 是否收集 facts
  vars:                     # 剧本级变量
    nginx_port: 80
  tasks:                    # 任务列表
    - name: 安装 nginx
      yum:
        name: nginx
        state: installed
  handlers:                 # 由 notify 触发的善后任务
    - name: 重启 nginx
      service:
        name: nginx
        state: restarted
```

> **注意：** handler 只有在被任务 `notify` 命中、且该任务确实产生变更时才会执行；配置类任务的标准写法是"改配置 → notify 重启服务"，配置没变就不会重启。

### 剧本编写规范：pyyaml 三点要求

#### 1. 合理的信息缩进

两个空格表示一个缩进关系：

```text
标题一
  标题二
    标题三
```

> **注意：** 在 Ansible 中**一定不能用 tab 进行缩进**，必须用空格。

#### 2. 冒号的使用方法

```yaml
hosts: 172.16.1.41
tasks:
yum: name=xx
```

> **注意：** 使用冒号时后面要有空格信息；以冒号结尾、或者冒号信息出现在注释说明中时，后面不需要加上空格。

#### 3. 短横线应用（列表功能）

```text
- 张三
  男
    - 打游戏
    - 运动

- 李四
  女
    学习
       湖南
- 王五
  男
    运动
       广州
```

> **注意：** 使用短横线构成列表信息，短横线后面需要有空格。

#### 4. YAML 其他要点

| 要点 | 说明 |
| --- | --- |
| 字典写法 | `键: 值`，嵌套时逐级缩进两个空格 |
| 列表写法 | `- 项`，列表项可以是字典，此时 `-` 后直接跟 `键: 值` |
| 多行字符串 `\|` | 保留换行，适合写脚本、配置文件 |
| 多行字符串 `>` | 折叠换行，多行合并为一行，适合长描述 |
| 注释 | `#` 开头，`#` 前建议留空格 |
| 布尔值陷阱 | `yes` / `no` / `true` / `false` / `on` / `off` 都会被 YAML 解析为布尔，想当字符串需加引号 |

布尔值陷阱在剧本里最典型的翻车点：`when: some_var == "yes"` 里如果 `some_var` 来自未加引号的 `yes`，它实际是布尔 `true`，字符串比较永远不相等。同理 `version: 1.10` 会被解析成浮点 `1.1`。凡是"看起来像布尔或数字的字符串"，一律加引号。

```yaml
# 多行字符串示例
script_content: |
  #!/bin/bash
  echo "hello"
  touch /tmp/demo.txt

long_desc: >
  这是一段会被折叠成
  一行的长描述文字。
```

### 开始编写剧本

```bash
mkdir /etc/ansible/ansible-playbook
vim rsync_server.yaml
```

> **注意：** 剧本文件扩展名尽量写为 `yaml`，原因有两点：
> 1. 方便识别文件是一个剧本文件
> 2. 文件编写时会有颜色提示

最简单的剧本形态：

```yaml
- hosts: 172.16.1.41
  tasks:
    yum: name=rsync state=installed
    copy: src=/tmp/rsyncd.conf dest=/etc/
```

加上 `name` 描述后的规范写法：

```yaml
- hosts: 172.16.1.41
  tasks:
    - name: 01-install rsync
      yum: name=rsync state=installed
    - name: 02-push conf file
      copy: src=/tmp/rsyncd.conf dest=/etc/
```

现代 Ansible 推荐把模块参数拆成字典（可读性更好，也方便写条件与注释）：

```yaml
- hosts: web
  become: yes
  tasks:
    - name: 安装 nginx 并启动
      ansible.builtin.yum:
        name: nginx
        state: installed
    - name: 推送首页
      ansible.builtin.copy:
        src: files/index.html
        dest: /usr/share/nginx/html/index.html
        owner: root
        group: root
        mode: "0644"
```

> **注意：** 上面这种 `模块名: 键值对` 的写法里，`mode: "0644"` 必须加引号 —— YAML 会把 `0644` 解析成八进制外的其他含义（历史上曾被解析为八进制 420 的坑），加引号保证它是字符串。

### 如何执行剧本

**第一个步骤：检查剧本的语法格式**

```bash
ansible-playbook --syntax-check  rsync_server.yaml
```

**第二个步骤：模拟执行剧本**

```bash
ansible-playbook -C rsync_server.yaml
```

**第三个步骤：直接执行剧本**

```bash
ansible-playbook rsync_server.yaml
```

> **注意：** 养成"先检查语法 → 再模拟执行 → 最后真正执行"的习惯，敲几遍就明白这三步值多少回滚时间，可以避免把错误的配置推到生产主机上。`-C` 可与 `--diff` 同用，看清每个文件会怎么变；加 `--limit web01` 只跑指定主机，方便灰度。

## 常见错误与排错

一套代码多套环境时，清单按目录组织：`inventories/production/hosts` 与 `inventories/staging/hosts` 各自成套，各自带 `group_vars/` 子目录，执行时 `-i inventories/production` 切换。变量同名不同值，剧本一行不用改——这是最朴素也最可靠的多环境隔离方式。

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| `ERROR! Syntax Error while loading YAML` | 缩进用了 tab、冒号后缺空格、短横线后缺空格 | `ansible-playbook --syntax-check xx.yaml` 定位行号 | 统一两个空格缩进，修正报错行的冒号与短横线 |
| `The error appears to be in ... line N` 实际错在别处 | YAML 结构性错误（如列表项没对齐到 tasks 下） | 对照规范检查缩进层级 | 检查 `tasks` 下每个 `- name` 是否同级对齐 |
| 任务报 `'item' is undefined` | `with_items` / `loop` 的列表为空或写成了字典 | 用 `debug` 打印变量 | 确认循环数据结构，字典循环用 `with_dict` |
| handler 没有执行 | 任务没写 `notify`，或 notify 的名字与 handler 的 `name` 不一致 | 检查任务 `notify` 与 handler 名 | 保持两者完全一致，且任务确实产生变更 |
| `stat` 判断文件存在却仍报错 | register 变量后用错了层级 | `- debug: var=conf_stat` 看结构 | 用 `conf_stat.stat.exists` 而非 `conf_stat.exists` |
| 密码创建用户不生效 | 密码明文直接写入，或 `$` 被 shell 展开 | `getent shadow 用户名` 看密文是否写入 | 先用 `password_hash` 生成密文，外层用单引号包裹 |
| 模块执行报 Python 解释器错误 | 被管端只有 Python 3 或路径不同 | `ansible web -m ping` 看报错 | 设置 `ansible_python_interpreter=/usr/bin/python3` |

这张表之外还有一类"清单级"错误：目标组名写错，剧本输出 `skipping: no hosts matched`，退出码还是 0——剧本"成功"了但什么都没做，最容易被忽略。跑完剧本先扫一眼每台主机有没有被正确命中，再看任务结果。

| 项目 | 旧写法 | 现代推荐 |
| --- | --- | --- |

## 小结

1. Ansible 轻量的关键：管理端无服务进程、受控端无 agent，只靠 SSH + Python；被管理端装上 `libselinux-python` 可以在 selinux 开启的情况下照常工作。
2. 远程主机管不上时按三层排查：公钥有没有分发 → 被管理端 SSH 服务是否正常 → `sshd` 进程是否僵死（注意 `sshd: root@notty` 是 Ansible 建立的连接）。
3. 查模块用 `ansible-doc -l` 列清单、`-s` 看参数、不带参数看剧本中的用法。
4. `mount` 模块的 `state` 四选一最易混：`mounted`（立即挂载 + 写 fstab）与 `unmounted`（立即卸载 + 保留 fstab）是日常最常用的两个。
5. `user` 模块设密码必须先用 `password_hash('sha512', salt)` 生成密文，且外层要用单引号防止 `$` 被 shell 展开。
6. 剧本就是把一串 ad-hoc 命令固化下来：pyyaml 三规范（空格缩进不能用 tab、冒号后加空格、短横线后加空格），执行走"检查语法 → 模拟执行 → 真正执行"三步。
7. `template` 用 Jinja2 渲染变量后下发，一台模板适配多主机；`copy` 是原样拷贝，两者按需选用。
8. `when` 做条件、`with_items` / `loop` 做循环、`until` 做重试、`register` 接返回值、`notify` + `handlers` 做变更后重启，这五件事支撑起剧本的自动化逻辑。

## 自测题

1. `copy` 与 `template` 模块的区别是什么？什么场景必须用 `template`？
2. `mount` 模块的 `state=mounted` 与 `state=present` 有什么不同？
3. 剧本里如何让"修改了 nginx 配置文件"之后自动重启 nginx，配置没变则不重启？
4. `user` 模块设置密码时，直接把明文密码写在参数里会发生什么？正确步骤是什么？
5. 写剧本时 `mode: 0644` 不加引号有什么风险？

> **答案：** 1. `copy` 原样拷贝文件；`template` 先把模板里的 Jinja2 变量渲染成实际值再下发。需要"同一份配置在不同主机有差异"（如各自主机名、IP、端口不同）时必须用 `template`。2. `present` 只写 `/etc/fstab` 实现开机挂载，不立即挂载；`mounted` 立即挂载并且写 fstab，一步到位。3. 在改配置的任务里加 `notify: 重启 nginx`，再写一个 handler：`- name: 重启 nginx` 下用 `service: name=nginx state=restarted`；handler 只在任务真正产生变更时执行。4. 明文不会生效，`/etc/shadow` 里写入的不是可用口令；正确步骤是先用 `password_hash('sha512', 盐值)` 生成密文，再用单引号包裹密文（防止 `$` 被展开）传给 `password` 参数。5. YAML 对无引号的 `0644` 有歧义解析风险（可能被当作数字而非权限字符串），必须写成 `mode: "0644"`，否则可能得到错误权限。
