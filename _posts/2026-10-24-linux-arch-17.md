> 单机 Web 服务器扛不住访问量时，就把多台服务器组成集群，由负载均衡服务器把请求调度到各后端节点。内容依次覆盖：LNMP 网站上线的遗留问题（上传限制、存储对接、数据库迁移、域名跳转），负载均衡原理，四层与七层的区别，调度算法，upstream 参数，会话保持方案与排错思路。

## LNMP 架构常见问题与扩展

### 上传大文件报 413 错误

上传 WordPress 主题时提示 413 Request Entity Too Large，说明上传数据大小超过了服务端限制，需要同时调整 Nginx 与 PHP 的配置。

修改 Nginx 配置文件（blog.conf），放大请求体大小限制：

```nginx
server {
    client_max_body_size 50m;   # 指定用户上传数据的大小限制（默认 1M）
}
```

再修改 php.ini 配置文件：

```ini
upload_max_filesize = 50M
```

upload_max_filesize 用于让 PHP 接收用户上传的更大数据（默认 2M）。

> **注意：** 413 错误必须同时修改两处：Nginx 的 client_max_body_size 与 PHP 的 upload_max_filesize。只改一处仍会报错，因为请求体在 Nginx 层就被拒绝，根本到不了 PHP。此外 php.ini 中还有 post_max_size（默认 8M）限制表单 POST 总大小，也应一并调整。

#### 解决默认无法存储数据的问题

> **注意：** 默认情况下存储服务器无法正常存储数据：root_squash 会把 root 用户映射为 nfsnobody，导致管理用户无法存储；all_squash 会把所有用户都映射为 nfsnobody，普通用户同样无法存储。

解决方法如下。

修改 NFS 配置文件，定义映射用户为 www：

```bash
useradd www -u 1002
chown -R www /data
```

使 root 用户可以上传数据：

```bash
sed -ri.bak 's#(sync)#\1,anonuid=1002,anongid=1002#g' /etc/exports
```

### 数据库迁移至独立服务器

#### 备份 Web 服务器本地数据库

```bash
mysqldump -uroot -p<your-password> --all-databases >/tmp/web_back.sql
```

> **注意：** `-p` 后面直接跟口令会把明文口令写入 Shell 历史（~/.bash_history），存在泄露风险。生产环境建议使用交互式输入（只写 `-p`）、或使用受权限保护的配置文件（如 /root/.my.cnf，权限 600），或使用 mysql_config_editor 保存加密凭据。文中 `<your-password>` 为占位符，请替换为实际口令。

```bash

```

172.16.1.51 即独立的数据库服务器 db01。

数据库迁移到独立服务器 db01 后，应停止 Web 服务器上的本地数据库服务，避免端口冲突与资源浪费，同时确认站点已改为连接远程数据库。


### 常见连接类错误

> **注意：** 数据库服务没有正确启动时，网站会报 Error establishing a database connection，本质是连接不上 3306 端口，先检查数据库服务状态与端口监听情况。

> **注意：** PHP 服务没有开启时，访问网站会报 502 错误，先检查 php-fpm 进程是否正常运行。

这两个错误码要分清：502 表示"连上了但后端不对劲"（进程死了、拒绝连接），504 表示"连得上但一直没回应"（后端卡死、慢查询拖住），一个指向进程状态，一个指向处理耗时，排查方向完全不同。

### 迁移后域名跳转问题

将 web01 的代码迁移到 web02 并修改网站域名后，访问新域名会自动跳转到老的域名。解决方法有两种：

- 方法一：修改 WordPress 后台设置信息，将后台中老的域名改为新的域名。
- 方法二：修改数据库中一个和域名有关的条目信息（可通过 phpMyAdmin 执行 update 操作）。

## 负载均衡概念

### 什么是集群

完成相同任务或工作的一组服务器，例如 web01、web02、web03 组成 Web 集群。

### 什么是负载均衡

1. 实现用户访问请求的调度分配；
2. 实现用户访问压力的分担。

说白了，负载均衡就是给后端集群请了一位"分单员"：请求先到它，它按规则把单子派给最合适的节点。

### 反向代理与正向代理

| 类型 | 流量方向 | 部署方式 | 说明 |
| --- | --- | --- | --- |
| 反向代理 | 外网用户 → 代理服务器 → 内网 Web 服务器 | 代理服务器 eth0 接外网、eth1 接内网 | 外网用户（客户端）访问代理服务器（服务端），代理服务器（客户端）再访问内网 Web 服务器（服务端） |
| 正向代理 | 内网主机 → 代理服务器 → 互联网 Web 服务器 | 代理服务器位于内网与外网之间 | 内网（局域网）主机通过代理服务器访问互联网上的 Web 服务器 |

判别方法很简单：看代理替谁办事。替客户端办事、隐藏客户端身份的是正向代理（翻墙、上网行为管理）；替服务端办事、隐藏后端拓扑的是反向代理。负载均衡器本质上是反向代理的一种业务化用法。

### 四层与七层负载均衡

负载均衡按工作的协议层次分为四层（传输层）与七层（应用层）两类，选型时绕不开。

| 对比项 | 四层负载均衡 | 七层负载均衡 |
| --- | --- | --- |
| 工作层次 | 传输层（TCP/UDP） | 应用层（HTTP/HTTPS） |
| 调度依据 | 目标 IP + 端口，不解析报文内容 | URL、Host、Cookie、User-Agent、请求头等 |
| 代表软件/设备 | LVS、HAProxy（TCP 模式）、F5 | Nginx、HAProxy（HTTP 模式）、F5 |
| 性能 | 高，仅做转发，不解析内容 | 相对低，需要解析与重组应用层报文 |
| 功能丰富度 | 低，只做流量转发 | 高，可实现动静分离、 rewrites、压缩、缓存、WAF |
| 会话保持 | 基于 IP 哈希 | 可基于 Cookie、URL、Header |
| 健康检查 | 端口级探测 | 可检查 URL 返回码与内容 |
| 典型场景 | 大并发入口、数据库/网关入口 | 网站入口、API 网关、动静分离 |

两者的本质区别不在"改不改报文"，而在调度时机与可用的信息量：四层在握手阶段就完成选路，一条连接从建立到关闭固定在同一台后端上，调度器不维护任何应用层语义；七层要等请求头到达才能决策，同一条 TCP 连接上的每个请求都可能被分给不同后端，还能按 URI 重写、限流、缓存。选型记住一条就够了：只关心"把流量匀开"，四层足够；要按业务语义路由（域名、路径、用户身份），必须上七层。生产里最常见的组合是 LVS 做四层入口扛并发，Nginx 藏在它后面做七层内容处理，各干各的擅长事。

### 常见负载均衡设备与软件

| 名称 | 类型 | 工作层次 | 特点 |
| --- | --- | --- | --- |
| LVS | 开源软件（Linux 内核模块 IPVS） | 四层 | 性能最高，集群内置于内核，常与 Keepalived 组成高可用四层方案 |
| Nginx | 开源软件 | 七层（也可代理 TCP/UDP） | 配置灵活，动静分离、缓存、反向代理能力强，国内 Web 入口最常用 |
| HAProxy | 开源软件 | 四层/七层均可 | 专职负载均衡，支持丰富的算法与健康检查，稳定性好 |
| F5 | 商业硬件设备 | 四层/七层 | 功能全面（含 SSL 加速、WAF），价格高，多见于金融、电信行业 |

LVS 的定位一句带过：它是内核态的四层转发引擎，只负责把 TCP/UDP 连接快速甩给后端，不理解也不修改应用内容，所以性能极高、功能单薄。企业里几乎总是三个一起用：keepalived 保 LVS 高可用，Nginx 补七层能力。

## 原理解析 {: .sec-why}

### 负载均衡工作流程

以七层 Nginx 反向代理为例，一次请求的完整流程如下：

1. 用户在浏览器输入域名，DNS 解析得到负载均衡服务器（lb01）的公网 IP，客户端与 lb01 建立 TCP 连接并发送 HTTP 请求。
2. lb01 的 Nginx 根据 server_name 与 location 匹配对应的虚拟主机与路由规则，决定请求应交给哪个 upstream 服务器组。
3. Nginx 按 upstream 配置的调度算法（rr、ip_hash、least_conn 等）从服务器组中选出一台后端节点。
4. Nginx 以客户端身份与选中的后端节点建立新连接，转发 HTTP 请求，并通过 proxy_set_header 补充 Host、X-Forwarded-For 等头部信息。
5. 后端节点（如 web01）处理请求并返回响应，响应沿原路回到 lb01，由 Nginx 转发给最终用户。
6. 若后端节点连接失败、超时或返回指定的错误码，Nginx 按 proxy_next_upstream 策略自动重试其他节点，用户侧无感知。

多级代理场景下 X-Forwarded-For 会逐跳追加，值形如 client, proxy1, proxy2，第一个 IP 才是原始访客。还要防伪造：用户可以自带 XFF 头发请求，所以最外层的 LB 应直接覆盖该头而不是追加，内层节点才追加。

### 四层与七层转发的原理差异

四层负载均衡（以 LVS 为例）工作在传输层：调度器只修改报文的目的 IP/端口或 MAC 地址，把连接原样转发给后端真实服务器，不关心报文里承载的是不是 HTTP，也不需要等请求体完整即可转发，因此吞吐高、延迟低。七层负载均衡（以 Nginx 为例）必须等应用层报文头（甚至报文体）到达后，解析出 URL、Host、Cookie 等信息才能决策，因此功能丰富但 CPU 开销更高。可以概括为：四层转发"连接"，七层理解"请求"。

顺带解释一个常见疑问：四层为什么快？LVS 工作在内核态，报文在网卡驱动层就被转发，不进用户态进程，没有上下文切换；Nginx 是用户态进程，每个连接都要经过 epoll 与内存拷贝。差距不在算法，在实现层次。

### LVS 三种工作模式

LVS（Linux Virtual Server）基于内核 IPVS 实现，有三种典型工作模式：

| 模式 | 全称 | 原理 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| NAT | Virtual Server via NAT | 修改请求报文的目的 IP 为后端真实 IP，响应报文经过 LVS 时修改源 IP 为 VIP | 后端只需指向 LVS 为网关，配置简单，支持端口映射 | 所有响应都要经过 LVS，LVS 容易成为带宽瓶颈 |
| DR | Virtual Server via Direct Routing | 只修改报文的目的 MAC 地址，直接转发给同网段后端 | 后端直接回包给客户端，性能最高 | 调度器与后端必须同一二层网络，不支持端口映射 |
| TUN | Virtual Server via IP Tunneling | 把请求封装在 IP 隧道中转发给后端 | 后端可跨网段部署 | 需要后端支持 IP 隧道协议，配置较复杂 |

### 辨析：负载均衡与高可用 {: .sec-bianxi}

两件事经常被一起提起，但目标不同。负载均衡解决"压力大"——把请求摊到多台机器，平时大家都在干活；高可用解决"挂了怎么办"——平时备机闲着，主节点故障时顶上去。同一个集群完全可以两者兼有：LB 层用 Nginx 做负载均衡，再靠 keepalived 给 LB 自己上一份高可用。判断当前需求属于哪一类，看痛点是"扛不住"还是"不敢停"。

## 负载均衡环境准备

### 集群服务器部署

集群中每台服务器的配置需要一模一样。企业中的部署方式如下：

1. 先部署好一台 LNMP 服务器，上传代码信息；
2. 进行访问测试；
3. 批量部署多台 Web 服务器；
4. 将 Nginx 配置文件进行分发；
5. 将站点目录分发给所有主机。

教学环境中，可以将 web01 作为模板主机克隆，再修改 IP 与主机名：

```bash
sed -i 's#\.7#.8#g' /etc/sysconfig/network-scripts/ifcfg-eth[01]
hostnamectl set-hostname web02
```

多台 Web 节点的一致性要靠分发机制兜底，不要人肉逐台改：配置文件用 rsync/scp 或 ansible 分发，站点目录变更后同步推送。不然跑着跑着就会出现"同一个域名在不同机器上返回不同页面"的诡异现象。

利用手动方式实现负载均衡时，修改 hosts 主机地址和域名映射文件即可。

### 负载均衡服务器配置

第一步：安装部署 Nginx 软件。

第二步：编写 Nginx 负载均衡配置文件，涉及两个核心模块：

| 模块 | 指令 | 作用 |
| --- | --- | --- |
| ngx_http_upstream_module | upstream | 负载均衡，定义后端服务器组 |
| ngx_http_proxy_module | proxy_pass | 反向代理，将请求转发给后端服务器 |

```nginx
upstream webcluster {
    server 10.0.0.7:80;
    server 10.0.0.8:80;
    server 10.0.0.9:80;
}

server {
    listen       80;
    server_name  www.example.com;
    location / {
        proxy_pass http://webcluster;
    }
}
```

这里有个容易踩的细节：proxy_pass 后面的地址带不带斜杠，转发路径完全不同。`proxy_pass http://webcluster;` 把原始 URI 原样传给后端；写成 `proxy_pass http://webcluster/;`（带斜杠）则会把 location 匹配的部分替换掉再拼接。搞混了就会出现 404，排查时先对比两边 access 日志里的 URI。

第三步：实现负载功能测试。先在 3 台后端服务器上分别准备测试页面，每台页面内容带上本机 IP，请求落到谁身上一看便知，敲一遍就明白：

```bash
for name in www bbs blog;do echo "$name 10.0.0.7">/html/$name/test.html;done
for name in www bbs blog;do echo "$name 10.0.0.8">/html/$name/test.html;done
for name in www bbs blog;do echo "$name 10.0.0.9">/html/$name/test.html;done
```

再修改 Windows 解析文件（hosts）：

```console
10.0.0.5    www.example.com  blog.example.com bbs.example.com
```

### 访问异常排错思路

1. 第一步：在负载均衡服务器上测试后端 Web 节点服务器是否能够正常访问。

```console
[root@lb01 conf.d]# curl -H host:www.example.com 10.0.0.7/test.html
www 10.0.0.7
[root@lb01 conf.d]# curl -H host:www.example.com 10.0.0.8/test.html
www 10.0.0.8
[root@lb01 conf.d]# curl -H host:www.example.com 10.0.0.9/test.html
www 10.0.0.9
```

2. 第二步：利用 curl 命令访问负载均衡服务器，并查看两个配置文件（upstream 与 server 配置）。
3. 第三步：另开一个终端连接，执行 ping www.example.com，确认域名解析是否正常。
4. 第四步：排查配置文件是否编写正确。

这套流程适用于任何代理类架构：先分段验证后端，再验证代理层，最后验证入口解析，从内向外收窄范围。

## upstream 模块详解

ngx_http_upstream_module 通过 upstream 指令实现不同的调度功能。

### 调度功能与参数速查

| 功能 | 配置写法 | 说明 |
| --- | --- | --- |
| 轮询分配请求 | server 10.0.0.7:80; | 默认方式，平均分配请求 |
| 权重分配请求 | server 10.0.0.7:80 weight=3; | 能力越强责任越重 |
| 热备（备胎）功能 | server 10.0.0.9:80 backup; | 正常服务器出现故障时才启用 |
| 最大失败次数 | max_fails=5 | 健康检查参数 |
| 失败重发间隔 | fail_timeout=10s | 健康检查参数，会给失败的服务器一次机会 |
| 手动下线 | server 10.0.0.9:80 down; | 维护期间临时摘除节点，不接收请求 |
| 限制单机并发 | server 10.0.0.7:80 max_conns=100; | 限制单台后端最大连接数，超出部分分给其他节点 |

权重分配示例：

```nginx
upstream webcluster {
    server 10.0.0.7:80 weight=3;
    server 10.0.0.8:80 weight=2;
    server 10.0.0.9:80 weight=1;
}
```

热备示例：

```nginx
upstream webcluster {
    server 10.0.0.7:80;
    server 10.0.0.8:80;
    server 10.0.0.9:80 backup;
}
```

backup 与 down 的语义再区分一下：backup 是"别的节点都挂了才轮到我"，自动接管；down 是"人工摘除"，改配置 reload 才生效。生产变更的稳妥流程是先用 down 摘节点观察，确认无影响再彻底下线，出问题删一行配置就能恢复。

> **注意：** max_fails 与 fail_timeout 是健康检查参数：max_fails=5 定义最大失败次数，fail_timeout=10s 定义失败之后重发的间隔时间，会给失败的服务器一次机会。fail_timeout 同时承担两个职责：一是统计失败次数的时间窗口，二是服务器被判定失败后的冻结时长，冻结期满后 Nginx 会再次放行请求进行探测。

### 调度算法详解

| 算法 | 配置方法 | 说明 | 适用场景 |
| --- | --- | --- | --- |
| 轮询 rr | 默认，无需配置 | 各后端平均分配请求 | 后端性能一致的集群 |
| 加权轮询 wrr | server 10.0.0.7:80 weight=3; | 能力越强的服务器承担越多请求 | 后端配置不一致 |
| ip_hash | 在 upstream 块中加 ip_hash; | 按客户端 IP 哈希调度，同一 IP 固定落到同一后端 | 会话保持，避免反复登录 |
| least_conn | 在 upstream 块中加 least_conn; | 按后端当前连接数调度，连接越少分得越多 | 请求处理时长差异大的场景 |
| url_hash | 在 upstream 块中加 hash $request_uri consistent; | 按请求 URL 哈希调度，相同 URL 固定落到同一后端 | 后端带本地缓存的场景，提升缓存命中率 |
| fair | 需安装第三方 fair 模块 | 按后端响应时间调度，响应越快分得越多 | 后端性能不均且负载波动大 |

补充说明：

- ip_hash 与 least_conn 需要 Nginx 1.7.10 及以上版本；url_hash 是标准 hash 指令的典型用法，consistent 参数开启一致性哈希，节点增减时缓存抖动更小。
- fair 算法需要 ngx_http_upstream_fair_module 第三方模块，官方 Nginx 默认不包含，需重新编译或使用已集成该模块的发行版。
- ip_hash 与 weight 同时配置时，weight 不生效（算法由 IP 决定，权重无意义）。

### 健康检查机制

Nginx 的健康检查分为被动与主动两类：

1. 被动健康检查（开源版原生支持）：Nginx 把真实请求的失败情况作为判断依据。由 max_fails 与 fail_timeout 实现，判定失败的条件包括连接错误、超时，以及 proxy_next_upstream 中列出的错误状态码（如 http_502、http_504）。优点是零额外开销，缺点是没有请求时就无法探测，且失败阈值只能按次数粗略设定。
2. 主动健康检查（需要扩展）：开源 Nginx 不内置主动探测，可通过 Tengine 的 ngx_http_upstream_check_module 模块或 Nginx Plus 的 health_check 指令实现，周期性地向后端发送探测请求（如 GET /health），根据返回码判断存活。
3. 高可用兜底：负载均衡器自身也可能宕机，因此生产中还会在 LB 层再加一层高可用（Keepalived + VIP），保证 LB 单点故障时秒级切换，详见 18-高可用服务keepalived。

max_fails 与 fail_timeout 的配合再展开说：max_fails 只在 fail_timeout 的时间窗口内计数，窗口结束计数清零；节点被冻结 fail_timeout 之后，Nginx 会放行一个真实请求去试探，成功则恢复轮询，失败则再次冻结。这里有个坑：什么算"失败"由 proxy_next_upstream 决定，配置里没列出的状态码（比如 http_502）不计入失败次数，节点永远摘不掉。被动检查还有个天然盲区——没有用户请求就发现不了后端已死，流量低谷期坏掉的节点要等下一波请求进来才暴露。这正是大流量场景要上主动健康检查的原因。

### 会话保持方案

用户登录态通常保存在单台后端的 Session 中，如果同一用户的相邻请求被分到不同后端，就会出现"反复登录"问题。常用方案对比如下：

| 方案 | 实现方式 | 优点 | 缺点 |
| --- | --- | --- | --- |
| IP 哈希 | upstream 中加 ip_hash; | 配置简单，无需后端配合 | 同一 NAT 出口用户全部打到同一台；后端增减导致哈希重算 |
| Cookie 保持 | HAProxy 的 cookie 插入；Nginx 需第三方 sticky 模块 | 精确到单个用户会话 | 依赖模块；Cookie 失效后仍会漂移 |
| URL 哈希 | hash $request_uri consistent; | 提升后端缓存命中率 | 只保证同 URL 同机，不保证同用户同机 |
| Session 集中存储 | 后端将 Session 写入 Redis/Memcached | 后端完全无状态，扩容摘除节点不影响用户 | 需要改造应用，引入缓存组件 |

ip_hash 的副作用值得单独说透。其一，运营商和企业出口普遍走 NAT，成千上万用户共享一个公网 IP，ip_hash 会把这一大群人全部压到同一台后端，负载直接失衡。其二，哈希结果与节点总数强相关，增减一台机器，绝大多数用户的会话会重新洗牌，"反复登录"在扩容瞬间集中爆发。其三，它只认客户端 IP，同一用户从 WiFi 切到 4G 就换了哈希桶，会话照样丢。生产上栽过的另一个坑：ip_hash 与 weight 同时配置时 weight 静默失效，不报任何错，排查半天才发现是算法优先级的问题。

结论：小规模、快速上线用 ip_hash；规范化、可平滑扩容的架构优先把 Session 集中到 Redis 等外部存储，从根上消除对"粘住某台机器"的依赖。两者之间还有个折中——HAProxy 的 cookie insert 由负载均衡器在响应里植入会话标记，应用零改造就能精确到单个用户会话，规模不大又不想动代码时可以用它过渡。

### 完整案例：Nginx 反向代理负载均衡

以下配置综合了权重、健康检查参数、真实 IP 传递与故障切换，可直接作为生产模板：

```nginx
upstream webcluster {
    server 10.0.0.7:80 weight=3 max_fails=2 fail_timeout=30s;
    server 10.0.0.8:80 weight=2 max_fails=2 fail_timeout=30s;
    server 10.0.0.9:80 backup;
}

server {
    listen       80;
    server_name  www.example.com;

    location / {
        proxy_pass http://webcluster;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
    }
}
```

要点解读：

1. 三台后端按 3:2 的权重分担流量，10.0.0.9 作为 backup 只在其他节点全部不可用时接管。
2. max_fails=2 配合 fail_timeout=30s，表示 30 秒内失败 2 次即把节点冻结 30 秒。
3. X-Forwarded-For 记录真实客户端 IP，后端 access 日志才能统计访客来源。
4. proxy_next_upstream 明确列出哪些错误触发重试，默认值为 error timeout，生产建议显式声明。
5. 需要会话保持时，把 upstream 的第一行换成 ip_hash;（此时 weight 参数需移除）。

再补一个进阶点：高并发 QPS 场景下，可以在 upstream 块中配置 `keepalive 32;`，配合 proxy_http_version 1.1 与清空 Connection 头，让 LB 与后端之间复用 TCP 连接，省掉每个请求反复三次握手的开销，QPS 提升明显。这也是很多性能压测调优的第一步。

## proxy 模块常用配置

ngx_http_proxy_module 提供 proxy_pass 反向代理能力，以下配置出镜率最高：

| 指令 | 作用 | 解决的问题 |
| --- | --- | --- |
| `proxy_set_header Host $host;` | 向后端传递真实 Host | 访问不同的网站地址，不能显示不同的网站页面（面试题） |
| `proxy_set_header X-Forwarded-For $remote_addr;` | 向后端传递真实客户端 IP | 访问网站的用户地址信息无法进行分析统计（面试题） |
| `proxy_next_upstream error timeout http_404 http_502 http_403;` | 出现错误时切换后端服务器 | 访问负载均衡会出现错误页面，影响用户体验 |

其他常用参数：

| 指令 | 作用 |
| --- | --- |
| proxy_connect_timeout | 与后端建立连接的超时时间，默认 60s |
| proxy_send_timeout | 向后端发送请求的超时时间，默认 60s |
| proxy_read_timeout | 读取后端响应的超时时间，默认 60s |
| proxy_buffering on | 开启响应缓冲，慢客户端不会拖慢后端，默认开启 |
| proxy_http_version 1.1 | 与后端使用 HTTP/1.1 通信，配合 keepalive 提升性能 |
| proxy_intercept_errors on | 后端返回的错误页由 Nginx 统一处理 |

生产上栽过的另一个坑：proxy_next_upstream 会重试非幂等请求。默认的 error timeout 只在网络层失败时重试，相对安全；一旦把 http_500 之类的状态码加进去，POST 下单这类请求就可能在后端已经处理成功的情况下被重试到另一台节点，造成重复下单。涉及写操作的接口要么不配置重试，要么让后端做幂等。

> **注意：** proxy_set_header Host $host 中，$host 取请求行中的 Host 或实际主机名，是变量且不含端口；若后端虚拟主机按 Host 区分站点，不传递正确 Host 会导致所有域名都落到默认站点，表现为"换个域名访问还是同一个页面"。

## 常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 上传文件报 413 | Nginx 或 PHP 上传限制过小 | grep client_max_body_size /etc/nginx/nginx.conf; php -i \| grep upload | 同步调大 client_max_body_size 与 upload_max_filesize、post_max_size |
| 访问报 502 Bad Gateway | 后端 php-fpm 未启动或 upstream 全部故障 | systemctl status php-fpm; curl 10.0.0.7; tail /var/log/nginx/error.log | 启动后端服务；检查 upstream server 地址与端口 |
| 访问报 504 Gateway Time-out | 后端响应慢或代理超时太短 | 后端机器 top/iotop; 检查 proxy_read_timeout | 优化慢查询与慢接口；调大超时；扩容节点 |
| 用户反复要求重新登录 | 未配置会话保持，请求分到不同后端 | 多次 curl -c/-b 观察登录态；cat upstream 配置 | 配置 ip_hash，或将 Session 存入 Redis |
| 某台后端始终收不到请求 | 被配成 backup/down，或 ip_hash 下 weight 不生效 | nginx -T 查看最终配置 | 移除 backup/down 标记；会话保持场景改用其他算法 |
| 后端统计的访客 IP 全是 LB 地址 | 未传递真实客户端 IP | 查看后端 access log 首列 | 增加 proxy_set_header X-Forwarded-For $remote_addr |
| 改完配置不生效 | 未重载或语法错误 | nginx -t; systemctl reload nginx | 修正语法后 reload；部分参数需 restart |

## 小结

1. LNMP 架构可通过 NFS 扩展存储、通过独立数据库服务器（db01）扩展数据库，迁移时要注意备份、恢复、授权与站点代码配置联动修改。
2. 负载均衡的作用是调度分配用户请求、分担访问压力，核心模块为 ngx_http_upstream_module 与 ngx_http_proxy_module。
3. 四层负载均衡转发连接（LVS），七层理解请求（Nginx）；LVS 有 NAT、DR、TUN 三种模式。
4. upstream 支持 weight、backup、down、max_fails、fail_timeout、max_conns 等参数，调度算法包括 rr、wrr、ip_hash、least_conn、url_hash、fair。
5. ip_hash 基于客户端 IP 调度，是实现会话保持、避免反复登录的常用手段；更彻底的方案是将 Session 集中存储。
6. proxy_set_header Host 与 X-Forwarded-For 分别解决站点识别与真实 IP 记录问题，proxy_next_upstream 在故障时自动切换后端，提升用户体验。
7. 排错时先用 curl 测试后端节点，再逐段检查负载均衡配置、域名解析与配置文件正确性。

## 自测题

1. 四层负载均衡与七层负载均衡的核心区别是什么？各举一个代表软件。
2. upstream 中 max_fails=2 fail_timeout=30s 表示什么含义？
3. ip_hash 为什么不能与 weight 同时使用？它有哪些局限？
4. 用户访问反向代理网站报 502，请给出至少三步排查过程。
5. 后端想统计真实访客 IP，Nginx 侧需要如何配置？

> **答案：** 1. 四层工作于传输层，只按 IP+端口转发连接，不解析应用层内容，代表为 LVS；七层工作于应用层，可解析 URL、Host、Cookie 等请求内容，代表为 Nginx。2. 30 秒的时间窗口内，某台后端失败达到 2 次就被标记为不可用并冻结 30 秒，冻结期满后自动放行探测。3. ip_hash 的转发目标由客户端 IP 哈希唯一决定，权重参数没有作用，因此同时配置无意义；局限是同一 NAT 出口用户都会打到同一台后端，且后端节点增减会造成哈希重新分布。4. 一、curl 直接访问各后端节点，确认后端本身正常；二、检查 php-fpm/后端服务状态与监听端口；三、查看 Nginx 错误日志与 upstream 配置，确认 server 地址、端口与健康检查参数是否正确。5. 在 location 中配置 proxy_set_header X-Forwarded-For $remote_addr;，必要时同时传递 X-Real-IP。
