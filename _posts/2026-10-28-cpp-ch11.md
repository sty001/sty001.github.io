## 11.1 iostream 对象
{: .sec-expl}

### 11.1.1 类层次：状态、缓冲、流是三件事
{: .sec-know}

iostream 这套类常被画成一棵"继承树"，但真正要记的是它把三件事拆开了：**状态**（好不好用）、**缓冲**（数据堆在哪）、**流接口**（读写操作）。分层如下：

| 层 | 代表类型 | 职责 |
| --- | --- | --- |
| 格式与状态 | `std::ios_base` | 流状态位、格式 flags、locale，与字符类型无关 |
| 缓冲接入 | `std::basic_ios<char>` | 持有 `streambuf` 指针，状态位与缓冲区联动 |
| 输入接口 | `std::basic_istream` | `>>`、`get`、`getline`、`seekg` |
| 输出接口 | `std::basic_ostream` | `<<`、`put`、`write`、`seekp` |
| 双向接口 | `std::basic_iostream` | 虚继承 istream 与 ostream，解决菱形继承 |
| 文件侧缓冲 | `std::basic_filebuf` | 真正读写文件的是它，不是流本身 |
| 字符串侧缓冲 | `std::basic_stringbuf` | 把一块字符串当缓冲区用 |

平时写的 `std::ostream`、`std::ifstream` 都是 `basic_` 模板对 `char` 的特化别名：`using ostream = basic_ostream<char>`。宽字符版本 `wcout`、`wifstream` 同理。为什么要这么拆？因为"往哪写"（filebuf、stringbuf、用户自定义的设备）和"怎么写"（格式化、状态管理）是两个独立维度，`streambuf` 这个基类就是给自定义设备留的插槽——把网络套接字包一个 `streambuf` 子类，就能用 `cout <<` 的语法往网络写。

为什么 `basic_iostream` 要虚继承？一个双向流同时是 istream 和 ostream，而两者共享同一份 `basic_ios`（同一个缓冲区、同一组状态位），普通继承会出现两份状态，虚继承强制合并成一份。

### 11.1.2 cin/cout/cerr/clog：四个对象，两种缓冲策略
{: .sec-know}

| 对象 | 对应 C 流 | 缓冲 | 去向 |
| --- | --- | --- | --- |
| `std::cin` | `stdin` | 有 | 标准输入 |
| `std::cout` | `stdout` | 有 | 标准输出 |
| `std::cerr` | `stderr` | 无（`unitbuf`，每次插入即刷） | 标准错误 |
| `std::clog` | `stderr` | 有 | 标准错误 |

关键差异就一行：`cerr` 不缓冲，`clog` 缓冲——但两个都写到 stderr。设计动机很直白：错误信息必须"尽快出去"，程序下一秒崩了也得让用户看到最后一条错误；而日志类输出（clog）追求吞吐，攒一批再写。代价是 `cerr` 逐次系统调用，性能差，所以别拿它打常规日志。

`cin` 和 `cout` 之间还有一条隐藏纽带：默认 `cin.tie() == &cout`，即 `cin` 每次做输入前会先刷一遍 `cout`。这是为了交互场景——

```cpp
std::cout << "请输入年龄: ";   // 没有 '\n'，还留在缓冲区里
std::cin >> age;               // tie 机制先刷 cout，提示语才会出现在屏幕上
```

没有这条纽带，交互程序的用户会看到"程序卡住了"，其实提示语还在缓冲区里睡觉。

### 11.1.3 缓冲区什么时候刷新——以及崩溃时数据去哪了
{: .sec-know}

`cout` 的数据不是直接到屏幕的，它先进缓冲区，攒够了或遇到触发条件才真正写出去。触发刷新的时机一共五类：

1. 缓冲区满（大小实现定义，通常几 KB）；
2. 显式刷新：`flush`、`endl`、`unitbuf`；
3. 流析构或程序正常退出（`main` 返回后静态对象析构时统一刷）；
4. 绑定流做输入：`cin` 读之前刷 `cout`（tie 机制）；
5. 重定向文件关闭时由底层 `filebuf` 析构刷出。

反过来说，**崩溃、`abort()`、`std::_Exit`、被 `kill -9`，都不刷新**。缓冲区里没出去的数据直接蒸发。这就是"日志打了一半程序崩了，崩溃前的输出却找不到"的原因。写关键诊断信息用 `cerr`，或者在崩溃点之前手动 `std::cout.flush()`。

拿重定向一验便知（管道下 `cout` 从行缓冲变成全缓冲，效果最明显）：

```cpp
// 需要 -std=c++17
#include <iostream>

int main() {
    std::cout << "buffered: 第一条\n";   // 进缓冲区，不出去
    std::cerr << "unbuffered: 直达\n";   // 立即写 stderr
    std::cout << "buffered: 第二条\n";
    return 0;                            // 到这里 cout 的两条才一起刷出
}
```

```bash
g++ -std=c++17 -Wall -Wextra buf_demo.cpp -o buf_demo && ./buf_demo 2>&1 | cat
```

```text
unbuffered: 直达
buffered: 第一条
buffered: 第二条
```

前提：Linux、输出经管道。直接打在终端上时，行缓冲让三条基本按书写顺序出现——所以这个坑只在重定向、管道、日志文件里暴露，恰恰是你最难复现的场景。

### 11.1.4 endl 的代价：每一次 flush 都是一次系统调用
{: .sec-prac}

`std::endl` 做两件事：输出 `'\n'`，然后 flush。写日志循环时用它，等于每行强制一次系统调用，缓冲机制形同虚设。量一下：

```cpp
// 需要 -std=c++17
#include <chrono>
#include <iostream>

int main() {
    constexpr int N = 200000;

    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i)
        std::cout << i << std::endl;          // 每行刷一次
    auto t1 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i)
        std::cout << i << '\n';               // 只换行，攒着
    auto t2 = std::chrono::steady_clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration_cast<std::chrono::milliseconds>(b - a).count();
    };
    std::cerr << "endl: " << ms(t0, t1) << " ms, '\\n': " << ms(t1, t2) << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra endl_demo.cpp -o endl_demo && ./endl_demo > /dev/null
```

```text
endl: 89 ms, '\n': 12 ms
```

前提：Linux、GCC `-O2`、输出重定向到 `/dev/null`。绝对值因机器而异，没有意义，看量级差距——重定向下差数倍到数十倍是常态。

选择规则一句话：交互提示、错误诊断、崩溃前的最后遗言，用 `endl` 或 `cerr`；循环里的批量输出，用 `'\n'`。拿不准就用 `'\n'`，需要刷新时显式写 `std::flush`，让"刷不刷"成为一个看得见的决定。

### 11.1.5 sync_with_stdio(false) 与 cin.tie(nullptr)
{: .sec-know}

iostream 慢，历史上有一半原因是两条默认的安全带：

- `sync_with_stdio(true)`（默认）：C++ 流与 C 的 `stdio` 共享同一缓冲并保持同步，让你能混用 `printf` 和 `cout` 而不乱序。代价是每次输出都要穿过 C stdio 这一层。
- `cin.tie(&cout)`（默认）：每次 `cin` 读入前都刷一遍 `cout`。交互程序需要它，批量读写就是纯浪费。

竞赛代码和批量 I/O 程序开头常见的三连，就是把两条都摘掉：

```cpp
// 需要 -std=c++17
#include <chrono>
#include <iostream>

int main() {
    auto t0 = std::chrono::steady_clock::now();
    for (int i = 0; i < 200000; ++i)
        std::cout << i << '\n';
    auto t1 = std::chrono::steady_clock::now();

    std::ios::sync_with_stdio(false);   // 解除与 C stdio 的同步
    std::cin.tie(nullptr);              // 解除 cin 对 cout 的绑定

    auto t2 = std::chrono::steady_clock::now();
    for (int i = 0; i < 200000; ++i)
        std::cout << i << '\n';
    auto t3 = std::chrono::steady_clock::now();

    auto ms = [](auto a, auto b) {
        return std::chrono::duration_cast<std::chrono::milliseconds>(b - a).count();
    };
    std::cerr << "默认: " << ms(t0, t1) << " ms, 关同步后: " << ms(t2, t3) << " ms\n";
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra sync_demo.cpp -o sync_demo && ./sync_demo > /dev/null
```

```text
默认: 96 ms, 关同步后: 34 ms
```

前提同上：Linux、GCC `-O2`、重定向。注意第二段循环还占了缓存预热的便宜，严谨测法要各跑多轮取中位数——11.6.2 会展开讲 benchmark 前提。

这两行有明确的适用边界。`sync_with_stdio(false)` 之后**不能再混用 `printf` 与 `cout`**（同一缓冲不再同步，输出会乱序交错）；`cin.tie(nullptr)` 之后，`cout` 里的提示语不再保证在读入前出现，交互程序要么别解绑，要么每次读入前手动 `std::cout.flush()`。写过交互题的人多半踩过后者：本地跑得好好的，一交上去卡在"没输出提示"。

> **坑：** 标准规定在标准流上已经发生过 I/O 之后再调用 `sync_with_stdio(false)`，行为是**实现定义**的——所以它最稳的位置是 `main` 第一行。上面的示例特意在输出一段之后才调用做对比：主流实现上这没有问题，前提是切换之后不再混用 `printf` 与 `cout`（两套缓冲不再同步，输出会乱序交错），并且最终正常退出让两侧缓冲都刷出。
{: .sec-pit}

### 辨析：cerr 与 clog
{: .sec-iv}

两者都写 stderr，区别只有缓冲策略。选哪个看的是"这条消息允许延迟多久"：崩溃路径上的错误、必须立刻让运维看到的信息，用 `cerr`，哪怕它慢；常规诊断日志、错误汇总，用 `clog`，攒批写，吞吐高。工程里更常见的做法是两个都不直接用——日志库自己管理缓冲与落盘，`clog` 只在没有日志库的小工具里出场。

## 11.2 输出
{: .sec-expl}

### 11.2.1 `<<` 为什么能连着写
{: .sec-know}

`operator<<` 返回 `basic_ostream&`，返回的就是左操作数自己，于是 `cout << a << b` 被解析成 `(cout << a) << b`——先写 `a`，返回 `cout`，再写 `b`。链式调用能成立，全靠这个返回值。

求值顺序是另一回事。C++17 之前，`cout << f() << g()` 里 `f` 和 `g` 的执行顺序完全未指定，两个函数如果都往屏幕打印或改共享状态，输出可能乱。C++17（P0145）把规则改了：对 `E1 << E2`，`E1` 的求值（含它触发的完整函数调用）排在 `E2` 之前。所以现在的保证是：先求 `f()` 并写入，再求 `g()` 并写入。老代码迁移到 C++17 时这类"输出顺序玄学"会自动消失，但别指望更老的编译器。

### 11.2.2 指针、字符与数组的输出
{: .sec-prac}

`<<` 对不同类型的重载行为差异很大，最经典的一片雷区在指针上：

```cpp
// 需要 -std=c++17
#include <iostream>

int main() {
    int n = 65;
    std::cout << n << ' ' << static_cast<char>(n) << '\n';  // 数字 65 vs 字符 A

    const char* s = "hi";
    std::cout << s << ' ' << static_cast<const void*>(s) << '\n';  // 内容 vs 地址

    int* p = &n;
    std::cout << p << '\n';                 // 非 char 指针直接打地址
}
```

```bash
g++ -std=c++17 -Wall -Wextra ptr_demo.cpp -o ptr_demo && ./ptr_demo
```

```text
65 A
hi 0x5662c3a2a01a
0x7ffd2a1b3c94
```

地址每次运行都不同，这里只取形态。三个要点：

- `char*` 走"当字符串打"的重载，要打地址必须 `static_cast<const void*>`；
- 非 char 指针默认打地址，没有特殊动作；
- `std::cout << nullptr` 直到 C++23（P2527）才有明确定义，之前是 undefined behavior。想表达空指针，自己写 `"(null)"`，别赌。

> **警告：** `char buf[2] = {'h', 'i'}; std::cout << buf;` 是 undefined behavior——重载会从 `buf` 开始一直找 `'\0'`，越界读多少字节全看内存布局。字符数组没以 `'\0'` 结尾时，用 `std::string` 或 `std::string_view`（C++17）携带长度信息再输出。
{: .sec-warn}

## 11.3 输入
{: .sec-expl}

### 11.3.1 `>>` 的两个默认行为：跳空白与失败置 0
{: .sec-know}

`cin >> x` 的提取规则有两层，理解了它们，后面一半的输入坑都能提前避免：

- **跳过前导空白**：由流的 `skipws` 标志控制，默认开着。`>>` 会先扔掉空格、制表符、换行，再开始读。想读"下一个字符包括空白"，用 `get`，别用 `>>`。
- **失败置 0**（C++11 起）：提取失败时把目标值写成 0 并置 `failbit`。C++11 之前失败时值保持不变，所以老教材里"失败值不变"的说法对新标准已经不成立。越界时（比如往 `int` 里塞 `99999999999`）则写入类型的最大值并置 `failbit`（也是 C++11 起）。

失败置 0 是个双刃剑：好处是变量不会带着上一次的旧值蒙混过关；坏处是有人拿"是不是 0"当错误判断，而合法输入 0 和失败无法区分——判断失败只能看流状态，不能看值。

### 11.3.2 流状态位与 `while (cin >> x)`
{: .sec-know}

流的健康状况用四个状态位表达，`rdstate()` 返回它们的组合：

| 状态位 | 含义 | 典型来源 |
| --- | --- | --- |
| `goodbit` | 值为 0，一切正常（它不是独立的位） | — |
| `eofbit` | 读到了流末尾 | 文件读完、`getline` 没遇到分隔符就到尾 |
| `failbit` | 本次操作失败，流还能继续用 | 给 `int` 喂 `abc`、文件打开失败 |
| `badbit` | 流本身坏了，后续操作无意义 | 底层缓冲区 I/O 错误 |

`if (cin)`、`while (cin >> x)` 里的布尔转换等价于 `!fail()`，即"没有 failbit 也没有 badbit"。注意一个微妙点：**只有 `eofbit` 时布尔转换仍是 true**。`cin >> x` 在文件末尾提取不到任何字符时，`eofbit` 和 `failbit` 会一起置上，循环就此结束；但 `getline` 读到最后一行（没有行尾换行符）只置 `eofbit`，流依然是"好"的，所以 `while (getline(...))` 不会漏掉最后一行。

失败之后流不会自动恢复——所有后续操作都因为 `failbit` 还在而立即失败。恢复的标准三步是 `clear()` 清状态、`ignore()` 丢弃坏数据、再继续：

```cpp
// 需要 -std=c++17
#include <iostream>
#include <limits>

int main() {
    int n = -1;
    std::cin >> n;                    // 喂 "abc"：提取失败
    std::cout << "n=" << n << " fail=" << std::cin.fail() << '\n';

    if (!std::cin) {
        std::cin.clear();             // 先清状态，不清则后面全部立即失败
        std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');
    }                                 // 再把 "abc\n" 整行丢掉

    std::string line;
    std::getline(std::cin, line);     // 现在才能正常读下一行
    std::cout << "读到的行: " << line << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra state_demo.cpp -o state_demo && printf 'abc\nhello\n' | ./state_demo
```

```text
n=0 fail=1
读到的行: hello
```

`ignore` 的第一个参数是"最多丢多少字符"，用 `std::numeric_limits<std::streamsize>::max()` 表示不设上限，遇到 `'\n'` 停。这两个函数必须成对出现：只 `clear` 不 `ignore`，坏字符还堵在流里，下一次提取照样失败；只 `ignore` 不 `clear`，状态没清，提取根本不会执行。

> **坑：** `while (cin >> x)` 结束后 cin 处于 eof 或 fail 状态，直接接着用（哪怕只是再读一个字符串）全部静默失败。循环结束、且确认还要复用这个流时，先 `clear()`。
{: .sec-pit}

### 11.3.3 getline、`>>` 混用的经典坑
{: .sec-ts}

`std::getline(cin, s)` 读"从当前位置到下一个 `'\n'`"的整行，包括空格，读完后把 `'\n'` 从流里拿走并丢弃。它和 `>>` 对分隔符的处理逻辑不同：`>>` 把 `'\n'` 当空白跳过，`getline` 把 `'\n'` 当行终结符消费掉。两者混用时，经典的死亡剧本是这样上演的：

```cpp
// 需要 -std=c++17
#include <iostream>
#include <string>

int main() {
    int age = 0;
    std::string name;
    std::cin >> age;              // 输入 25 回车：age=25，流里剩下一个 '\n'
    std::getline(std::cin, name); // 立刻遇到那个 '\n'，读到空行就返回
    std::cout << "age=" << age << " name=[" << name << "]\n";
}
```

```bash
g++ -std=c++17 -Wall -Wextra mix_bad.cpp -o mix_bad && printf '25\nTom\n' | ./mix_bad
```

```text
age=25 name=[]
```

`name` 是空的——`>>` 读完数字后把回车留在了流里，紧随其后的 `getline` 什么都没干就"成功"了。修法是在 `>>` 之后、`getline` 之前把残留吃掉：

```cpp
// 需要 -std=c++17
#include <iostream>
#include <limits>
#include <string>

int main() {
    int age = 0;
    std::string name;
    std::cin >> age;
    std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');  // 吃掉残留
    std::getline(std::cin, name);
    std::cout << "age=" << age << " name=[" << name << "]\n";
}
```

```bash
g++ -std=c++17 -Wall -Wextra mix_ok.cpp -o mix_ok && printf '25\nTom\n' | ./mix_ok
```

```text
age=25 name=[Tom]
```

这条坑的判定口诀：**同一个流上，`>>` 之后第一次 `getline` 之前，必须有 `ignore`**。反过来 `getline` 之后接 `>>` 没有这个问题（`>>` 自己会跳空白）。统一策略是"读数字用 `>>` 加 `ignore`，读文本一律 `getline`"，从头到尾不混着裸用。

### 11.3.4 get / peek / putback：逐字符处理
{: .sec-prac}

需要逐字符控制（写词法分析、解析器）时，`>>` 的自动跳空白反而碍事，这层有四个趁手的工具：

- `get(char&)`：读一个字符，空白也照读；
- `peek()`：往前看一个字符但不消耗，返回 `int_type`，流末尾返回 `traits::eof()`；
- `putback(c)`：把刚读的字符放回流里；
- `unget()`：退一个字符，不用自己保存刚才读到了什么。

```cpp
// 需要 -std=c++17
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::istringstream in("42abc");        // 用字符串流演示，换成 cin 逻辑相同
    int n = 0;
    in >> n;                               // 读走 "42"，停在 'a'

    int pk = in.peek();                    // 看一眼，不消耗
    if (pk != std::char_traits<char>::eof())
        std::cout << "n=" << n << " peek=" << static_cast<char>(pk) << '\n';

    char c = 0;
    in.get(c);                             // 真正读走 'a'
    std::cout << "get=" << c << '\n';

    in.putback(c);                         // 放回去
    in.get(c);
    std::cout << "放回再读=" << c << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra peek_demo.cpp -o peek_demo && ./peek_demo
```

```text
n=42 peek=a
get=a
放回再读=a
```

`peek` 返回 `int` 而不是 `char`，是为了表达 `EOF`——直接 `char c = in.peek()` 会把流末尾的 `eof` 值截断成普通字符，判断就失效了。`putback` 也可能失败（缓冲区已重置时无位可放），失败会置 `failbit`，稳妥的解析器会检查状态。

### 11.3.5 std::quoted（C++14）：带转义的字符串读写
{: .sec-ext}

把含空格、引号、反斜杠的字符串写进文本文件再读回来，裸的 `>>` 会栽在空格上，裸的 `getline` 会把转义符当普通字符。`<iomanip>` 里的 `std::quoted`（C++14）专门解决这件事：写出时加引号并转义内部的 `"` 和 `\`，读入时自动解转义。

```cpp
// 需要 -std=c++14
#include <iomanip>
#include <iostream>
#include <sstream>
#include <string>

int main() {
    std::string path = R"(C:\temp\报告 "final".txt)";   // 含反斜杠和引号
    std::ostringstream out;
    out << std::quoted(path);
    std::cout << "写出: " << out.str() << '\n';

    std::istringstream in(out.str());
    std::string back;
    in >> std::quoted(back);                // 读回时自动解转义
    std::cout << "读回一致? " << (back == path) << '\n';
}
```

```bash
g++ -std=c++14 -Wall -Wextra quoted_demo.cpp -o quoted_demo && ./quoted_demo
```

```text
写出: "C:\temp\报告 \"final\".txt"
读回一致? 1
```

它本质是个转义协议，不关心文件格式。做配置文件、日志里嵌套字符串字段时很好用；需要标准 JSON 那种完整语义的场景另请专业库，`quoted` 只处理引号和反斜杠。

### 辨析：getline 与 `>>`
{: .sec-iv}

一句话分工：`>>` 读"一个词"，`getline` 读"一句话"。`>>` 适合结构化字段（数字、单词），自动处理任意空白；`getline` 适合含空格的自由文本，需要你显式处理行尾。混用的规则只有一条要背：`>>` 之后接 `getline` 必须先 `ignore`。另外注意 `getline` 读空行返回的空串也算成功（流状态良好），别用字符串非空当循环条件。

### 11.4.1 iomanip 操纵符：粘性与一次性
{: .sec-know}

`<iomanip>` 的操纵符本质是往流对象上设标志（或触发动作），它们的生效范围分两派，记混了就是格式错乱的根源：

| 操纵符 | 生效范围 | 说明 |
| --- | --- | --- |
| `std::setw(n)` | **一次性** | 只对紧随其后的一次输出（或字符串提取）有效 |
| `std::quoted(s)` | 一次性 | 只作用于当次读写 |
| `std::setprecision(n)` | 粘性 | 之后所有浮点输出 |
| `std::setfill(c)` | 粘性 | 之后所有补宽用的填充字符 |
| `std::hex` / `oct` / `dec` | 粘性 | 之后所有整数输出的进制 |
| `std::boolalpha` / `noboolalpha` | 粘性 | 布尔输出 `true`/`false` 还是 1/0 |
| `std::showbase` / `noshowbase` | 粘性 | 进制前缀 `0x`、`0` |
| `std::showpos` / `noshowpos` | 粘性 | 正数带 `+` 号 |
| `std::left` / `right` / `internal` | 粘性 | 对齐方式与填充位置 |
| `std::fixed` / `scientific` / `defaultfloat` | 粘性 | 浮点记法 |
| `std::endl` / `std::flush` | 立即动作 | 换行并刷新 / 只刷新 |
| `std::ws` | 立即动作 | 输入流上跳过前导空白 |

为什么 `setw` 特立独行？流是长生命周期的全局对象，宽度如果粘住，后面所有输出都会被莫名补齐到旧宽度，那才是灾难；所以标准把它设计成用一次就失效。而精度、进制这类有"默认合理值"的属性，粘住反而省事。一个是"参数"，一个是"模式"——这么记就不会错。

### 11.4.2 setw 之坑与完整演示
{: .sec-prac}

```cpp
// 需要 -std=c++17
#include <iomanip>
#include <iostream>

int main() {
    std::cout << std::hex << std::showbase;         // 粘性：之后整数全是十六进制
    std::cout << 255 << ' ' << 255 << '\n';

    std::cout << std::setw(6) << 255 << '|'         // setw 每个值前都要重新写
              << std::setw(6) << 255 << "|\n";

    std::cout << 255 << "|\n";                      // setw 已失效，不再补宽

    std::cout << std::setw(8) << std::setfill('*') << 255 << "|\n";
    std::cout << std::setfill(' ') << std::dec << std::noshowbase;   // 恢复默认

    std::cout << std::left << std::setw(6) << "ab" << "|\n";
    std::cout << std::internal << std::showpos << std::setw(6) << -42 << "|\n";

    std::cout << std::noshowpos << std::boolalpha << (3 > 2) << ' ' << (3 < 2) << '\n';
    std::cout << std::fixed << std::setprecision(2) << 3.14159 << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra iomanip_demo.cpp -o iomanip_demo && ./iomanip_demo
```

```text
0xff 0xff
   255|   255|
ff|
****0xff|
ab    |
-   42|
true false
3.14
```

逐行对照能看到几个细节：第四行 `setw(8)` 配 `setfill('*')` 补的是星号；第六行 `internal` 把填充放在符号和数字之间（`-   42`）；`setfill` 是粘性的，用完立刻恢复成空格，否则后面的输出全带星号。

> **坑：** `std::cout << std::setw(6) << a << b;` 里只有 `a` 被补宽，`b` 原样输出——`setw` 用一次就没了。给一列数据对齐时，`setw` 必须写在每个值前面。另一个冷知识：`setw` 对提取也有效，`cin >> std::setw(10) >> buf;` 最多读 9 个字符留位置给结尾，是 C 风格字符数组防溢出的老手段；用 `std::string` 的话用不到它。

### 11.4.3 std::format（C++20）：占位符语法
{: .sec-know}

`std::format`（`<format>`，C++20）把 Python 风格的格式化搬进了标准库，一套语法覆盖所有类型。占位符结构：`{参数索引:格式说明}`，索引和说明都可省略。格式说明按顺序是：

`[[填充]对齐] [符号] [#] [0] [宽度] [.精度] [L] [类型]`

| 元素 | 取值 | 示例效果 |
| --- | --- | --- |
| 对齐 | `<` 左、`>` 右、`^` 居中，前面可选一个填充字符 | `{:*^10}` 星号填充居中 |
| 符号 | `+` 正负都带、`-` 只负数带、空格 正数留空格位 | `{:+}` |
| `#` | 备用形式：进制前缀 `0x`、`0`，浮点保留小数点 | `{:#x}` |
| `0` | 用前导零补宽度 | `{:06}` |
| 宽度 | 十进制数字，或 `{n}` 引用参数 | `{:8}` |
| 精度 | `.数字`，浮点限小数位数，字符串限长度 | `{:.3f}` |
| `L` | 使用 locale（千分位等） | `{:L}` |
| 类型 | 整数 `b c d o x X`，浮点 `a e f g` 等，字符串 `s` | `{:b}` |

索引规则：要么全用 `{}` 自动编号，要么全用 `{0}` `{1}` 手动编号，**混用是错误**；想重复某个参数就手动编号。字面的大括号用 `{{` 和 `}}` 转义。

```cpp
// 需要 -std=c++20，GCC 13 起才带 <format>
#include <format>
#include <iostream>
#include <string>

int main() {
    std::string name = "C++";
    int ver = 20;
    double pi = 3.14159265;

    std::cout << std::format("{} {} 版本 {}\n", "你好", name, ver);
    std::cout << std::format("{1} {0}\n", "甲", "乙");        // 手动编号
    std::cout << std::format("{:>8}|\n", "hi");               // 右对齐宽 8
    std::cout << std::format("{:*^10}|\n", "mid");            // 星号填充居中
    std::cout << std::format("{0:b} {0:#x} {0:#o}\n", 255);   // 进制
    std::cout << std::format("{:.3f} {:+.2e}\n", pi, pi);     // 浮点
    std::cout << std::format("{0} {0} {1}\n", "ok", 1);       // 重复用同一参数
}
```

```bash
g++ -std=c++20 -Wall -Wextra fmt_demo.cpp -o fmt_demo && ./fmt_demo
```

```text
      hi|
```

### 11.4.4 编译期检查与 vformat：运行期格式串
{: .sec-ext}

`std::format` 最值钱的一点：格式串参数是 `format_string` 类型，模板会在**编译期**检查占位符和实参是否匹配——参数个数不对、类型不支持对应格式说明，直接编译错误。`printf` 的 `%s` 配上 `int` 这类静默 UB，在这里变成了编译期报错：

```cpp
std::format("{} {}", 1);        // 编译错误：占位符比参数多
std::format("{:d}", "abc");     // 编译错误：字符串不支持 d 类型
```

代价是格式串必须是编译期常量。格式串来自配置文件、命令行或用户输入时，走运行时版本 `std::vformat`——它接受任意 `string_view`，参数用 `make_format_args` 打包，错误推迟到运行时抛 `std::format_error`：

```cpp
// 需要 -std=c++20
#include <cstdlib>
#include <format>
#include <iostream>
#include <string_view>

int main() {
    const char* msg = std::getenv("FMT");     // 运行期才拿到的格式串
    if (!msg) msg = "fallback: {}";

    int answer = 42;
    std::cout << std::vformat(msg, std::make_format_args(answer)) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra vfmt_demo.cpp -o vfmt_demo && ./vfmt_demo
FMT="十进制 {:d}, 十六进制 {:#x}" ./vfmt_demo
```

```text
fallback: 42
十进制 42, 十六进制 0x2a
```

运行期路径少了编译期保护，格式串错不错要靠测试覆盖——能写死在代码里的格式串，永远优先写死。

### 11.4.6 格式化 chrono（C++20）
{: .sec-prac}

`std::format` 对 `<chrono>` 的所有类型内置了支持，`strftime` 风格的 `%` 说明符直接可用，不用再绕 `std::tm`：

```cpp
// 需要 -std=c++20，GCC 13 起可用
#include <chrono>
#include <format>
#include <iostream>

int main() {
    using namespace std::chrono;
    auto now = system_clock::now();

    year_month_day date = floor<days>(now);          // 截断到天
    std::cout << std::format("{:%Y-%m-%d}\n", date); // 日期

    hh_mm_ss tod{now - floor<days>(now)};            // 当天经过的时长
    std::cout << std::format("{:%H:%M:%S}\n", tod);  // 时刻

    weekday wd{sys_days(date)};
    std::cout << std::format("今天星期几：{:%A}\n", wd);
}
```

```bash
g++ -std=c++20 -Wall -Wextra chrono_fmt.cpp -o chrono_fmt && ./chrono_fmt
```

```text
09:30:15
今天星期几：Monday
```

输出随运行时刻变化，星期名默认按 classic locale 给英文。这里三个类型各司其职：`floor<days>` 把时间点截到天，`hh_mm_ss` 把"一天内的时长"拆成时分秒，`weekday` 从日期推导星期。比 `time_t` 加 `localtime` 那套类型安全得多——月份从 1 数、星期从星期日数的混乱历史包袱直接消失。

### 11.4.7 自定义 std::formatter
{: .sec-prac}

自己的类型想进 `format`，特化 `std::formatter` 即可，两步：`parse` 解析冒号后的格式说明，`format` 真正输出。

```cpp
// 需要 -std=c++20
#include <format>
#include <iostream>

struct Point {
    int x, y;
};

template <>
struct std::formatter<Point> {
    constexpr auto parse(std::format_parse_context& ctx) {
        auto it = ctx.begin();                        // 指向 ':' 之后（或 '}' 之前）
        while (it != ctx.end() && *it != '}') {
            if (*it != 'm' && *it != 'p')
                throw std::format_error("只支持 m 或 p");
            mode = *it;
            ++it;
        }
        return it;                                    // 必须返回停在 '}' 的迭代器
    }

    auto format(const Point& pt, std::format_context& ctx) const {
        if (mode == 'm')
            return std::format_to(ctx.out(), "({}, {})", pt.x, pt.y);
        return std::format_to(ctx.out(), "Point[{}, {}]", pt.x, pt.y);
    }

    char mode = 'm';
};

int main() {
    Point p{3, 4};
    std::cout << std::format("{} / {:m}\n", p, p);    // 默认与 m 等价
    std::cout << std::format("{:p}\n", p);
}
```

```bash
g++ -std=c++20 -Wall -Wextra point_fmt.cpp -o point_fmt && ./point_fmt
```

```text
(3, 4) / (3, 4)
Point[3, 4]
```

三个约定要守住：`parse` 返回的迭代器必须停在 `'}'` 上，否则标准库认为你没解析完；`format` 要声明成 `const`（后续标准修订强制了这一点）；非法说明在 `parse` 里抛 `std::format_error`，这样 `{:q}` 这类笔误能在运行时得到清晰报错——如果 `parse` 写成 `constexpr` 且检查都编译期可判，错误还能提前到编译期。

### 11.4.8 `<charconv>`：to_chars 与 from_chars（C++17）
{: .sec-know}

数字与字符串互转有四条路：C 的 `atoi`/`sprintf`、`std::stoi`/`to_string`、`stringstream`、以及 C++17 的 `to_chars`/`from_chars`。最后一对是最快的，快在三个"没有"上：**无异常**（错误用返回值表达）、**无 locale**（不查本地化表，永远是 C 风格数字）、**无分配**（调用方提供缓冲区，直接写内存）。

```cpp
// 需要 -std=c++17（浮点重载 GCC 11 起）
#include <charconv>
#include <iostream>
#include <string_view>

int main() {
    // --- to_chars：写进预分配缓冲区，返回 {ptr, ec} ---
    char buf[16]{};
    auto [pc, ec] = std::to_chars(buf, buf + sizeof buf, 3.14159265);
    std::cout << std::string_view(buf, pc - buf)
              << " 成功=" << (ec == std::errc{}) << '\n';   // 浮点版给最短往返表示

    // --- from_chars：三个"不"：不跳空白、不吃 + 号、不认 0x 前缀 ---
    std::string_view s1 = "  42";
    int v = 0;
    auto r1 = std::from_chars(s1.data(), s1.data() + s1.size(), v);
    std::cout << "带前导空格: 成功=" << (r1.ec == std::errc{} ? "yes" : "no") << '\n';

    std::string_view s2 = "42abc";
    auto r2 = std::from_chars(s2.data(), s2.data() + s2.size(), v);
    std::cout << "v=" << v << "，消耗 " << (r2.ptr - s2.data()) << " 个字符\n";

    std::string_view s3 = "+42";
    auto r3 = std::from_chars(s3.data(), s3.data() + s3.size(), v);
    std::cout << "带 + 号: 成功=" << (r3.ec == std::errc{} ? "yes" : "no") << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra charconv_demo.cpp -o charconv_demo && ./charconv_demo
```

```text
3.14159265 成功=1
带前导空格: 成功=no
v=42，消耗 2 个字符
带 + 号: 成功=no
```

返回值是 `to_chars_result` / `from_chars_result`，各含一个指针和一个 `std::errc`：`ec` 等于 `std::errc{}` 即成功；`ptr` 指向"消费到的最后一个字符之后"，拿它算进度、判断"整个串都解析完了没有"（严格解析就是检查 `ptr == end`）。浮点 `to_chars` 默认给出"最短且往返一致"的表示——同样的数字打印出来再读回去值不变，而且字符串尽量短，这是它比 `printf` 的 `%f` 高明的地方。

为什么强调"不跳空白"？这是刻意的分层设计：要不要跳、跳哪些空白（本地化后空白的定义都会变）是调用方的业务决定，库不替你做主。省掉的每个决策都是性能。

### 辨析：from_chars 与 stoi/atoi
{: .sec-iv}

`std::stoi` 好用但有三个暗坑：跳过前导空白（你可能不想要）、失败抛 `std::invalid_argument` 或 `out_of_range`（热路径上异常代价高）、无法轻量区分"解析到一半"和"全串解析"。`atoi` 更糟：失败返回 0，和合法输入 0 无法区分。`from_chars` 把这些全变成显式的：空白自己跳、错误看 `ec`、进度看 `ptr`，代价是接口啰嗦一点。批量解析日志、网络协议这类性能敏感场景选 `from_chars`；随手写个脚本式小程序，`stoi` 也没毛病。

## 11.5 文件
{: .sec-expl}

### 11.5.1 打开模式：一张表说清截断规则
{: .sec-know}

`ifstream`（读）、`ofstream`（写）、`fstream`（读写）共享同一组打开模式标志：

| 标志 | 含义 |
| --- | --- |
| `std::ios::in` | 允许读；`ifstream` 默认 |
| `std::ios::out` | 允许写；`ofstream` 默认 |
| `std::ios::trunc` | 打开时清空已有内容 |
| `std::ios::app` | 每次写之前自动定位到文件尾；不截断 |
| `std::ios::ate` | 打开后立刻定位到文件尾；之后可以随意移动读写位置 |
| `std::ios::binary` | 关闭文本模式转换（Windows 上影响换行） |

坑全部藏在"组合"里，核心是三条规则：**`out` 单独使用隐含 `trunc`**；`app` 永不截断；带 `in` 的组合打开不存在的文件会失败。常用组合逐个过一遍：

| 组合 | 文件已存在 | 文件不存在 | 典型用途 |
| --- | --- | --- | --- |
| `out`（ofstream 默认） | 清空 | 创建 | 生成新文件 |
| `out`+`app` | 保留，写到尾 | 创建 | 日志追加 |
| `in`（ifstream 默认） | 保留 | 打不开 | 读取 |
| `in`+`out`（fstream 默认） | 保留 | 打不开 | 中途修改 |
| `in`+`out`+`trunc` | 清空 | 创建 | 重写整个文件 |
| `in`+`binary` | 保留 | 打不开 | 二进制读 |

最容易踩的是第一行：`std::ofstream out("log.txt");` 本意"打开日志文件"，实际把日志清空了。想要追加，必须写 `std::ofstream out("log.txt", std::ios::app);`。

### 11.5.2 RAII、打开检查与显式 close
{: .sec-prac}

文件流是最典型的 RAII 示范：构造时打开，析构时自动 `close` 并刷出缓冲区，忘不掉也漏不掉。唯一必须手动的动作是**检查打开是否成功**——路径写错、没权限，构造函数不报错也不抛异常，只是把 `failbit` 置上，不检查就往下读写，全部静默失败：

```cpp
// 需要 -std=c++17
#include <fstream>
#include <iostream>
#include <string>

int main() {
    {   // 写：ofstream 默认 out（隐含 trunc），不存在则创建，存在则清空
        std::ofstream out("demo.txt");
        if (!out) {                          // 打开失败不抛异常，必须自己查
            std::cerr << "打不开 demo.txt\n";
            return 1;
        }
        out << "第一行\n" << 42 << ' ' << 3.14 << '\n';
    }                                        // 离开作用域，析构自动 close 并 flush

    std::ifstream in("demo.txt");
    if (!in) return 1;
    std::string line;
    std::getline(in, line);
    int n = 0; double d = 0;
    in >> n >> d;
    std::cout << line << " | " << n << ' ' << d << '\n';

    std::ofstream app("demo.txt", std::ios::app);   // 追加，不清空
    app << "追加的一行\n";
}
```

```bash
g++ -std=c++17 -Wall -Wextra file_demo.cpp -o file_demo && ./file_demo
```

```text
第一行 | 42 3.14
```

析构关闭有个盲区：**它无法报告关闭时的错误**。缓冲区在 close 阶段才真正落盘，磁盘满、网络盘断连都发生在这里，而析构不能抛异常。对"写出去的数据一条都不能少"的场景，显式 `close()` 并检查：

```cpp
out.close();
if (out.fail()) { /* 落盘失败，处理或报告 */ }
```

### 11.5.3 二进制读写与 Windows 文本模式
{: .sec-warn}

文本模式（默认）下，流会做字符转换；二进制模式（`std::ios::binary`）下字节原样进出。转换最典型的就是 Windows 的换行：文本模式下写 `'\n'` 落盘变成 `0x0D 0x0A`（CRLF），读回时再转回来。后果有三个：写入的字节数和 `file_size` 对不上；数据里恰好有 `0x0A` 或 `0x1A`（老式 Ctrl+Z 结束符）字节的二进制内容被悄悄改写——文件直接损坏；文本模式下 `tellg` 返回的位置不保证对应真实字节偏移。结论一句话：**只要不是纯文本，一律加 `binary`**，Linux 上它同样无害。

```cpp
// 需要 -std=c++17
#include <cstdint>
#include <fstream>
#include <iostream>
#include <vector>

int main() {
    const std::vector<std::uint32_t> data{1, 22, 333, 4444};

    std::ofstream out("nums.bin", std::ios::binary);
    if (!out) return 1;
    out.write(reinterpret_cast<const char*>(data.data()),
              static_cast<std::streamsize>(data.size() * sizeof(std::uint32_t)));
    out.close();                             // 显式关，批量二进制写建议查落盘结果

    std::ifstream in("nums.bin", std::ios::binary);
    if (!in) return 1;
    std::vector<std::uint32_t> back(data.size());
    in.read(reinterpret_cast<char*>(back.data()),
            static_cast<std::streamsize>(back.size() * sizeof(std::uint32_t)));
    if (in.gcount() != static_cast<std::streamsize>(back.size() * sizeof(std::uint32_t))) {
        std::cerr << "读到的字节数不足\n";
        return 1;
    }
    for (std::uint32_t v : back) std::cout << v << ' ';
    std::cout << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra bin_demo.cpp -o bin_demo && ./bin_demo
```

```text
1 22 333 4444
```

`read`/`write` 只认 `char*`，所以有 `reinterpret_cast`——它把任意对象的内存当字节序列搬。这带来两个可移植性陷阱：直接 `write` 整个结构体，会把**填充字节**和**宿主字节序**一起写进文件，换一台机器读回来可能面目全非。跨平台持久化要么逐字段读写定宽类型（`uint32_t` 这类），要么在写入前显式约定字节序做转换。"把结构体一把 write 进文件"只适合同机临时存储。

### 11.5.4 seekg / seekp / tellg
{: .sec-prac}

每个文件流内部有**两个独立位置指针**：读指针（`seekg` 移动、`tellg` 查询）和写指针（`seekp`/`tellp`）。纯读流只用前者，纯写流只用后者，`fstream` 读写都用。定位支持三种基准：流开头（默认）、当前位置 `std::ios::cur`、文件尾 `std::ios::end`：

```cpp
// 需要 -std=c++17
#include <fstream>
#include <iostream>
#include <string>

int main() {
    {
        std::ofstream out("patch.txt");
        out << "0123456789";
    }

    std::fstream f("patch.txt", std::ios::in | std::ios::out);  // 读写，不截断
    if (!f) return 1;

    f.seekg(4);                              // 读指针到下标 4（从 0 数）
    char c = 0;
    f.get(c);
    std::cout << "下标 4 是 " << c << "，此时 tellg=" << f.tellg() << '\n';

    f.seekp(3);                              // 写指针到下标 3，原地改写
    f << 'X';
    f.seekg(0);                              // 读指针拨回开头
    std::string s;
    std::getline(f, s);
    std::cout << "改完是 " << s << '\n';

    f.seekg(-2, std::ios::end);              // 相对文件尾定位
    f.get(c);
    std::cout << "倒数第二个是 " << c << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra seek_demo.cpp -o seek_demo && ./seek_demo
```

```text
下标 4 是 4，此时 tellg=5
改完是 012X456789
倒数第二个是 8
```

`tellg` 读回来的是"当前读指针的位置"，负偏移只允许相对 `end`。提醒一句 11.5.3 的坑：Windows 文本模式下这些位置值带字符转换的失真，随机访问配合 `binary` 才可靠。

### 11.5.5 std::filesystem（C++17）
{: .sec-ext}

`<filesystem>` 把"目录、路径、遍历、增删改查"从平台相关的系统调用泥潭里捞了出来。先看日常全家桶：

```cpp
// 需要 -std=c++17（GCC 8 及以前链接时要加 -lstdc++fs）
#include <filesystem>
#include <fstream>
#include <iostream>

namespace fs = std::filesystem;

int main() {
    fs::path sub = fs::path("work") / "logs" / "2026-11";  // operator/ 拼路径
    fs::create_directories(sub);             // 相当于 mkdir -p，已存在不算错误

    fs::path f = sub / "run.log";
    { std::ofstream out(f); out << "hello fs\n"; }          // ofstream 直接收 path

    std::cout << "存在? " << fs::exists(f)
              << " 大小=" << fs::file_size(f) << " 字节\n";
    fs::rename(f, sub / "renamed.log");      // 同盘改名/移动

    for (const auto& entry : fs::recursive_directory_iterator("work"))
        std::cout << (entry.is_directory() ? "[目录] " : "[文件] ")
                  << entry.path() << '\n';

    fs::remove_all("work");                  // 整棵子树删除
    std::cout << "删完了，还存在? " << fs::exists("work") << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra fs_demo.cpp -o fs_demo && ./fs_demo
```

```text
存在? 1 大小=9 字节
[目录] "work"
[目录] "work/logs"
[目录] "work/logs/2026-11"
[文件] "work/logs/2026-11/renamed.log"
删完了，还存在? 0
```

要点拆开说：

- `path` 用 `operator/` 拼接，正斜杠在所有平台都认，Windows 反斜杠也认，不用手写分隔符；`entry.path()` 打印时带引号，这是 `path` 的输出约定，不是路径的一部分。
- 常用操作：`exists`、`is_directory`、`is_regular_file`、`create_directory`（单层，已存在返回 false）、`create_directories`（递归）、`remove`（删文件或空目录）、`remove_all`（递归删，返回删除条数）、`rename`、`copy_file`（目标已存在会抛异常，除非传 `overwrite_existing`）、`file_size`、`last_write_time`。
- 遍历两兄弟：`directory_iterator` 只走一层，`recursive_directory_iterator` 深度优先走整棵树（构造时可传 `skip_permission_denied` 跳过无权限目录）。两者都是范围可迭代的，直接上 range-based for。
- `last_write_time` 返回 `file_time_type`，它挂在自带的时钟上，和 `system_clock` 纪元不同，直接当系统时间用会差出几十年，要换算。

第二套 API：上面这些函数默认版本出错抛 `std::filesystem::filesystem_error`，而每个函数都有对应的 `error_code` 重载——出错不抛，把错误填进你传入的 `ec`。批量处理用户给的目录树时，`error_code` 版几乎是唯一选择：一个无权限目录不该让整个遍历任务中断。

```cpp
// 需要 -std=c++17
#include <filesystem>
#include <iostream>
#include <system_error>

int main() {
    std::error_code ec;
    std::uintmax_t n = std::filesystem::file_size("no_such_file", ec);
    std::cout << "n=" << n << " ec=" << ec.message() << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra fs_ec.cpp -o fs_ec && ./fs_ec
```

```text
n=18446744073709551615 ec=No such file or directory
```

前提：Linux。失败时 `error_code` 版的 `file_size` 返回 `uintmax_t` 的最大值（即 -1 的无符号形态），`ec` 携带具体原因。所以判错永远看 `ec`，别看返回值——这正是异常版和 `error_code` 版的分工：异常版适合"失败就该立刻终止"的路径，`error_code` 版适合"失败是预期之内、逐项兜底"的路径。

### 辨析：remove 与 remove_all
{: .sec-iv}

`remove` 只能删空目录或普通文件，删非空目录直接报错；`remove_all` 递归删整棵子树，返回删除的条目数。风险也和能力成正比：`remove_all("data")` 一个手滑，路径拼接出错就是数据事故。稳妥做法是删之前用 `is_directory` 确认目标类型，或者干脆限制到固定的工作子目录内再操作。两者都区分异常版与 `error_code` 版，选择逻辑和 11.5.5 说的一致。

### 11.6.1 stringstream：解析与按分隔符切分
{: .sec-prac}

`<sstream>` 提供三个类：`istringstream`（把字符串当输入流）、`ostringstream`（攒输出）、`stringstream`（双向）。它们让"解析一段文本"可以先在内存里完成，出错不落盘。最常用的两个姿势是整体提取和按分隔符切分：

```cpp
// 需要 -std=c++17
#include <iostream>
#include <sstream>
#include <string>
#include <vector>

std::vector<std::string> split(const std::string& line, char delim) {
    std::vector<std::string> out;
    std::istringstream iss(line);
    std::string tok;
    while (std::getline(iss, tok, delim))    // getline 的第三参就是分隔符
        out.push_back(tok);
    return out;
}

int main() {
    std::string csv = "name,age,city";
    for (const auto& tok : split(csv, ','))
        std::cout << '[' << tok << "]\n";

    std::istringstream data("3.14 42 hello");
    double d = 0; int n = 0; std::string w;
    data >> d >> n >> w;                     // 提取规则和 cin 完全一样
    std::cout << d << ' ' << n << ' ' << w << '\n';
}
```

```bash
g++ -std=c++17 -Wall -Wextra sstream_demo.cpp -o sstream_demo && ./sstream_demo
```

```text
[name]
[age]
[city]
3.14 42 hello
```

两个坑：一是连续分隔符（`"a,,b"`）会产生空字段，而行尾分隔符（`"a,b,"`）之后的空字段会丢——`getline` 读到流尾失败，循环就停了，需要严格保留空字段的格式别用它；二是 `>>` 的失败置 0、跳空白这些行为在 `stringstream` 上一模一样，`cin` 上的坑这里一个不少。数字解析密集的场景换 `from_chars`，快一个量级。

### 11.6.2 printf、iostream、format 谁快
{: .sec-know}

先说结论的边界：**没有跨机器成立的绝对数字**，能给你的是定性排序和正确的测量方法。定性结论（同机同条件下通常是这个顺序）：`to_chars` 与 `std::format` 在第一梯队，`printf` 居中，iostream 默认配置最慢、`sync_with_stdio(false)` 后明显改善。

原因在架构上，不看汇编也能推理：

- `to_chars`：无 locale、无异常、无分配，直接写内存，没什么可减的了。
- `std::format`：编译期解析格式串，运行期按类型直接分派，同样无 locale（除非 `L`）。
- `printf`：格式串每次**运行时**重新解析一遍，参数走 varargs，类型检查缺席，但 C 层实现高度优化，不至于垫底。
- iostream：每个 `<<` 都是一串虚调用（sentry 检查、`streambuf` 虚函数、locale facet 查询），默认还与 C stdio 同步。机制最灵活，代价也最贵。

要自己测，先把前提钉死，否则测出来的只是噪声：

1. 输出去向：终端、文件、`/dev/null` 是三回事，终端渲染本身就能吃掉全部差距，一律重定向；
2. 是否 flush：`endl` 与 `'\n'` 差一个数量级，被测代码里必须统一；
3. `sync_with_stdio` 的状态；
4. 优化级别（`-O2` 起步）和编译器版本；
5. 分开测"格式化"与"输出"：格式化到 `std::string` 再统一落盘，才能把两者拆开看；
6. 多轮取中位数，冷热顺序轮换，避免缓存偏袒某一方。

背别人的数字没有意义，跑一遍自己的负载才有。

### 11.6.3 线程安全：并发写同一个流
{: .sec-know}

C++11 起标准保证：多个线程并发对**同一个**流对象调 `operator<<`，不会产生数据竞争（不会 UB），但**字符可能交错**——两个线程的输出可能揉成 `helABClo` 这种碎片。也就是说，安全性和可读性是两回事。

要"整行原子"，C++20 给了 `std::osyncstream`（`<syncstream>`）：它把作用范围内的输出攒起来，析构时一次递交，中间不会被别的线程插队。

```cpp
// 需要 -std=c++20（GCC 11 起支持 <syncstream>）
#include <iostream>
#include <syncstream>
#include <thread>
#include <vector>

int main() {
    std::vector<std::jthread> ts;
    for (int i = 0; i < 4; ++i) {
        ts.emplace_back([i] {
            std::osyncstream(std::cout)
                << "线程 " << i << " 的这一整行不会被打断\n";
        });
    }
}                                             // jthread 析构自动 join
```

```bash
g++ -std=c++20 -Wall -Wextra syncstream_demo.cpp -o syncstream_demo && ./syncstream_demo
```

```text
线程 2 的这一整行不会被打断
线程 0 的这一整行不会被打断
线程 1 的这一整行不会被打断
线程 3 的这一整行不会被打断
```

行的先后次序不定（这是并发的本分），但每行完整。顺带一提 `jthread`（C++20）析构自动 join，比裸 `std::thread` 省一个"忘 join 就 terminate"的坑。写日志库时，锁或 `osyncstream` 是标配；裸奔多线程共享 `cout` 的输出，看着像乱码别怀疑编译器。

### 11.6.4 locale 的坑
{: .sec-ts}

locale 决定数字怎么读、怎么写：小数点是 `.` 还是 `,`、有没有千分位。iostream 和它纠缠出几条隐蔽的规则：

- 流对象在**构造时**捕获当时的全局 locale。`cout` 在 `main` 之前就已构造，事后改 `std::locale::global(...)` 对它无效，除非显式 `imbue`——这是"我改了 locale 怎么没生效"的头号来源。
- 每条流默认 classic（"C"）locale：小数点必是 `.`，无千分位。多数程序全程碰不到本地化，这是合理的默认。
- `std::format` **默认不本地化**，加了 `L` 标志（`{:L}`）才走 locale；`to_chars`/`from_chars` 永远无视 locale。两代格式化在这个问题上的答案恰好相反，混用时留神。

```cpp
// 需要 -std=c++17；最后一段输出取决于系统是否装有 en_US.UTF-8
#include <iomanip>
#include <iostream>
#include <locale>
#include <stdexcept>

int main() {
    std::cout << 1234567.5 << '\n';                 // 默认格式：1.23457e+06
    std::cout << std::fixed << 1234567.5 << '\n';   // fixed 下：1234567.500000
    std::cout << std::defaultfloat;

    std::cout.imbue(std::locale("C"));              // 显式 classic，任何平台可用
    std::cout << std::fixed << 1234567.5 << '\n';

    try {
        std::cout.imbue(std::locale("en_US.UTF-8"));   // 系统没装就抛异常
        std::cout << std::fixed << 1234567.5 << '\n';  // 千分位：1,234,567.500000
    } catch (const std::runtime_error&) {
        std::cout << "本机没有 en_US.UTF-8\n";
    }
}
```

```bash
g++ -std=c++17 -Wall -Wextra locale_demo.cpp -o locale_demo && ./locale_demo
```

```text
1.23457e+06
1234567.500000
1234567.500000
1,234,567.500000
```

前提：Linux，系统装有 `en_US.UTF-8` locale；没有则走 `catch` 分支，前两行输出不变。

反过来还有一条读入的坑：把流 imbue 成逗号当小数点的 locale（如某些欧洲区域）后，`cin >> d` 读 `"3.14"` 会在点号处停下，`d` 得到 3，后面的 `.14` 留在流里污染后续解析。解析外部数据永远用 classic locale 或 `from_chars`，别让环境设定偷偷改你的语义。

### 11.6.5 printf 还要学吗
{: .sec-know}

要，理由有三：维护存量 C/C++ 代码绕不开它；对接 C 库时 `snprintf` 系函数仍是标准接口；面试和阅读老代码时它是必修课。但新代码的默认选择应该是 `std::format`/`std::println`（C++20/23）：编译期查错、类型安全、性能更好，`vformat` 对应 `vprintf` 的运行时格式串场景。两套语法并存的日子里，别用 `printf` 的思维写 `format`——比如 `printf` 的宽度精度语法（`%6.2f`）到 `format` 里是 `{:6.2f}`，符号体系不同，习惯需要切换一次。

## 变式追问
{: .sec-think}

1. `cerr` 故意不缓冲，如果让它也缓冲会怎样？

   崩溃路径上的错误信息会和普通输出一起滞留在缓冲区里，程序一崩全部蒸发——而错误信息的价值恰恰集中在"最后时刻"。这是一次明确的取舍：`cerr` 用"每次插入即系统调用"的性能代价，换"随时死掉随时保全"的可靠性。反过来看 `cout` 缓冲是为了吞吐，代价是崩溃丢数据。两条通道分工不同，谁也替代不了谁。这也解释了为什么日志库都有自己的落盘策略：iostream 的默认缓冲满足不了任何一种严肃的可靠性需求。

2. `while (cin >> x)` 结束后 cin 处于什么状态？不清就继续用会发生什么？

   两种可能：正常读到尾是 `eofbit` 加 `failbit`（最后一次提取没读到字符，失败和到尾同时发生）；中途遇到非法字符则只有 `failbit`。此时流的布尔转换是 false，所有后续提取操作**立即失败且不消耗任何字符**——现象通常是"循环提前结束""后面的读取全部是空"，数据不会报错，只会静默丢失。恢复靠 `clear()` 加 `ignore()`；如果流还能继续用是前提，那这个前提就要靠你自己维护。判断流是否到尾的正确姿势是读失败之后再查 `eof()`，而不是反过来。

3. `from_chars` 为什么坚持不跳过前导空白？加一行 `isspace` 判断很难吗？

   不难，但"哪些字符算空白"没有唯一答案：classic locale 下是五种，本地化后可能更多；`>>` 跳空白就因此引入了 locale 依赖。`from_chars` 的定位是零依赖的最底层原语，任何"智能"行为都会把决策强加给所有调用方。需要跳空白？调用方一行 `while (*p == ' ') ++p;` 自己解决，成本几乎为零；库替你跳了，你想不跳都拆不掉。这就是分层：底层原语只提供无争议的最小语义，上层组合出各种策略。顺手解释了它为什么快——它连"决定要不要跳"的时间都省了。

4. 程序 `abort()` 时 `cout` 缓冲区里 3 KB 日志会怎样？换成 `cerr` 呢？怎么设计崩溃日志？

   `cout` 的 3 KB 直接丢失：`abort()` 不走静态对象析构，没人负责刷缓冲区；`cerr` 无缓冲，写一句出一句，全都在。设计上因此有条分工线：崩溃前后要留存的信息走 `cerr` 或带自主落盘的日志库；`cout` 只放"丢了也无所谓"的正常输出。进一步的做法是在信号处理函数里什么都别做（async-signal-safe 限制下几乎不能做），而是在关键路径上用 `cerr` 逐步打点——指望崩溃时补救，不如平时就选对通道。

5. Windows 文本模式把 `'\n'` 写成 CRLF，这个设计今天还需要吗？

   历史包袱：CP/M 时代用 CRLF 标记一行结束（当时设备逐行输出），DOS 继承，Windows 一路兼容至今。它今天没有存在必要，却删不掉——删了会破坏海量存量文件和工具的兼容性。对 C++ 程序员的实际含义是：跨平台文本文件要容忍两种换行（读入时处理 `\r`），二进制数据、网络协议、随机访问一律 `binary` 模式自己管字节。C 标准库的 `"wb"`、C++ 的 `std::ios::binary`、`std::filesystem` 的按字节 `file_size`，都是在这层历史之上给出的现代答案。
