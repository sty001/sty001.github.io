面向对象这章，最容易被当成"背概念"——封装、继承、多态，三句话就能讲完。可真到项目里，你多半卡在"我这个类到底该不该用虚函数""全局状态到底能不能碰"。这一篇就聊这些落地才会冒出来的问题。

## 2.1 什么是面向对象
{: .sec-expl}

### 2.1.1 封装：把不变式关进类型里
{: .sec-know}

封装不是"把成员藏起来再塞一堆 getter"，而是"让类型的每个公开操作都守住某些永远为真的条件"——这些就叫不变式（invariant）。我自己判断一个类该不该用 class，就看一件事：有没有不变式？有，就用 class 把状态设为 private；没有，它其实就是一包能自由组合的数据，用 struct 公开成员更顺手（Core Guidelines C.2、C.8）。

```cpp
// stack_demo.cpp —— 需要 -std=c++20
#include <cstddef>
#include <iostream>
#include <stdexcept>
#include <string>
#include <vector>

class Stack {                       // 有不变式：元素个数绝不超过 cap_，所以是 class
public:
    explicit Stack(std::size_t cap) : data_(), cap_(cap) { data_.reserve(cap); }

    void push(int v) {
        if (data_.size() == cap_) {                 // 维持不变式的地方
            throw std::overflow_error("stack full");
        }
        data_.push_back(v);
    }

    int pop() {
        if (data_.empty()) {
            throw std::underflow_error("stack empty");
        }
        int v = data_.back();
        data_.pop_back();
        return v;
    }

    std::size_t size() const noexcept { return data_.size(); }
    bool empty() const noexcept { return data_.empty(); }

private:
    std::vector<int> data_;
    std::size_t cap_;
};

int main() {
    Stack s(2);
    s.push(10);
    s.push(20);
    std::cout << "size = " << s.size() << ", top = ";
    std::cout << s.pop() << "\n";
    try {
        s.push(1);
        s.push(2);                  // 第三次 push 会抛
        s.push(3);
    } catch (const std::overflow_error& e) {
        std::cout << "caught: " << e.what() << "\n";
    }
    std::cout << "final size = " << s.size() << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra stack_demo.cpp -o stack_demo && ./stack_demo
```

```text
size = 2, top = 20
caught: stack full
final size = 2
```

封装到底算不算真封装，一个细节就能看出来：`data_` 是 private，外部没法改掉 `reserve` 留下的容量信息，也没法在不知道 `cap_` 的情况下硬塞第三个元素。要是写成 `struct Stack { std::vector<int> data; size_t cap; };`，那"size 不超过 cap"只能靠每个调用点自觉——那叫文档，不叫封装。

> **坑：** 一上来就给每个成员写 getter/setter（C.131 说的 anemic class），等于把 `private` 又拆掉了。问一问：外部真的需要读这个值吗？需要的话，是需要"这个值"还是"基于这个值算出的一句话"（比如 `empty()` 而不是 `size() == 0`）。
{: .sec-pit}

### 2.1.2 继承：表达的是 substitutability，不是省代码
{: .sec-know}

`public` 继承表达的是"派生对象能在任何基类出现的地方替上去"（Liskov 替换原则）。编译器只会替你查签名对不对，查不了语义——比如 `Rectangle` 继承 `Square` 还允许分别设长宽，`Square` 上"面积 = 边长²"这个不变式就破了。我在一个几何库里真踩过这个：把正方形当矩形的特例来继承，面积算出来全是错的。

三种继承的区别：

| 写法 | 对外表达的关系 | 常见用途 |
| --- | --- | --- |
| `class D : public B` | D **是一种** B，满足替换原则 | 接口继承（抽象基类） |
| `class D : private B` | D **是根据** B 实现的，外部看不到这层关系 | 实现复用，替代组合的一种写法（很少用） |
| `class D : protected B` | 只有 D 的派生类看得到这层关系 | 罕见 |

落到具体选型，我的默认顺序是（Core Guidelines C.10、C.129）：

- 要表达"一组可替换的实现"→ 接口基类 + 虚函数。
- 要复用代码 → 优先**组合**，或者 CRTP / 模板静态多态；如果只是"类型就那么几种形态"，`std::variant`（C++17）通常比继承干净得多。

### 2.1.3 多态：静态 vs 动态，两张不同的成本表
{: .sec-know}

| 维度 | 静态多态（模板/CRTP/重载） | 动态多态（虚函数） |
| --- | --- | --- |
| 决议时机 | 编译期 | 运行期（查 vtable） |
| 代码体积 | 每个实例一份（可能膨胀） | 一份，运行时间接跳转 |
| 能否放进容器 | 需要同类型（或 `variant`） | `unique_ptr<Base>` 天然可行 |
| 能否跨 ABI | 头文件库，全部重编译 | 可以做成插件/动态库接口 |
| 内联优化 | 容易（编译器看得见实现） | 需 devirtualization，跨 TU 基本靠 LTO |
| 二进制兼容 | 差（改即重编） | 好（vtable 稳定即可） |

虚函数的三条硬规则：

1. **通过基类指针删除派生对象，基类析构函数必须是 virtual**，否则是 **undefined behavior**。
2. 基类的析构要么 `public` 且 `virtual`，要么 `protected` 且非虚（C.35、C.127）——后者封死"通过基类指针删除"这条路，问题自动消失。
3. 多态类型应当抑制公开拷贝/移动（C.67），否则 slicing（对象切片）随时发生：`Derived d; Base b = d;` 只拷了基类那部分。

第 1 条的错误示范，注意这里的行为是标准明确定义的 UB，不是"可能泄漏"：

```cpp
// vdtor_ub.cpp —— 需要 -std=c++20
#include <iostream>

struct Base {
    ~Base() { std::cout << "~Base\n"; }        // 故意不写 virtual
};

struct Derived : Base {
    ~Derived() { std::cout << "~Derived\n"; }
    int* owned = new int[4];                   // 派生类持有资源
};

int main() {
    Base* p = new Derived;
    delete p;                                  // undefined behavior：只调用 ~Base
}
```

```cpp
// vdtor_ok.cpp —— 需要 -std=c++20
#include <iostream>
#include <utility>
#include <vector>

struct Base {
    Base() = default;
    virtual ~Base() = default;                 // 规则 1
    Base(const Base&) = default;
    Base& operator=(const Base&) = default;
    Base(Base&&) = default;
    Base& operator=(Base&&) = default;
    virtual void draw() const = 0;             // 规则 3 的前提：这是个接口
};

struct Widget : Base {
    std::vector<int> data;
    Widget() = default;
    explicit Widget(std::vector<int> d) : data(std::move(d)) {}
    void draw() const override { std::cout << "widget with " << data.size() << " items\n"; }
};

int main() {
    Base* p = new Widget{std::vector<int>{1, 2, 3}};
    p->draw();
    delete p;                                  // 正确：先 ~Widget 再 ~Base
}
```

注意 `Widget` 继承了虚函数，已经不属于聚合类型，所以别指望 `new Widget{{}, {1,2,3}}` 这种大括号聚合初始化能编译——给它一个正常的构造函数才是通用写法。


#### 辨析：继承 vs 组合
{: .sec-iv}

判断依据不是"是不是 is-a"这种语法题，而是三件事：

- **生命周期谁管**：继承意味着派生对象的基类部分由它自己携带，二者的生命周期绑死；组合则是"我持有一个"——可以是值、可以是智能指针、可以延迟构造，自由度更高。
- **变化频率**：基类一旦改，所有派生都得重编。跨组件边界用继承，等于把两边的编译依赖焊死。
- **是否真的需要运行时切换**：如果调用方在编译期就知道具体类型，模板/CRTP/concepts 更快也更安全；只有在"容器里放一堆不同实现"时才真的需要虚函数。

### 2.1.4 现代 C++ 为什么转向值语义 + 泛型 + 组合
{: .sec-expl}

这条路转向的技术原因很实在：

- **确定性析构（RAII）让生命周期变成值的问题**：对象在栈上，`}` 处自动析构，不用管 `delete`。指针和 `new` 退到 rare case（Core Guidelines R.5、ES.60）。
- **值语义避免 aliasing**：`std::vector<Point>` 里每个元素独立，不会有人在别处偷偷改你的数据；推理难度大幅下降。这也是为什么 C++ 里"值语义 + 移动语义"这套东西能成立，而 Java 式的引用语义需要到处 defensive copy。
- **泛型把多态提前到编译期**：模板 + concepts 让"能编译就正确"，性能还更好。
- **组合 + variant 替代深层次类**：三层继承树在维护成本上通常输给一层组合。

同一个需求（"一堆形状，各自算面积"）的三种写法，直接对比：

```cpp
// shape_three_ways.cpp —— 需要 -std=c++20
#include <cmath>
#include <concepts>
#include <iostream>
#include <memory>
#include <numbers>
#include <type_traits>
#include <variant>
#include <vector>

// ---------- A. 动态多态：运行时才知道具体类型时用它 ----------
struct ShapeV {
    virtual ~ShapeV() = default;
    virtual double area() const = 0;
};

struct CircleV final : ShapeV {
    double r;
    explicit CircleV(double radius) : r(radius) {}
    double area() const override { return std::numbers::pi * r * r; }
};

struct RectV final : ShapeV {
    double w;
    double h;
    RectV(double width, double height) : w(width), h(height) {}
    double area() const override { return w * h; }
};

// ---------- B. std::variant：类型集合封闭且已知（C++17） ----------
struct Circle { double r; };
struct Rect { double w, h; };
using ShapeVar = std::variant<Circle, Rect>;

double area_of(const ShapeVar& s) {
    return std::visit([](const auto& g) -> double {
        using T = std::decay_t<decltype(g)>;
        if constexpr (std::is_same_v<T, Circle>) {
            return std::numbers::pi * g.r * g.r;
        } else {
            return g.w * g.h;
        }
    }, s);
}

// ---------- C. 静态多态：编译期已知类型（concepts，C++20） ----------
template <class T>
concept ShapeLike = requires(const T& t) {
    { t.area() } -> std::convertible_to<double>;
};

template <ShapeLike T>
double describe(const T& s) {
    return s.area();
}

int main() {
    std::cout << "-- A 虚函数 --\n";
    std::vector<std::unique_ptr<ShapeV>> shapes;
    shapes.push_back(std::make_unique<CircleV>(1.0));
    shapes.push_back(std::make_unique<RectV>(2.0, 3.0));
    for (const auto& s : shapes) {
        std::cout << s->area() << "\n";
    }

    std::cout << "-- B variant --\n";
    std::vector<ShapeVar> list{Circle{1.0}, Rect{2.0, 3.0}};
    for (const auto& s : list) {
        std::cout << area_of(s) << "\n";
    }

    std::cout << "-- C concepts --\n";
    std::cout << describe(CircleV{1.0}) << "\n";
    std::cout << describe(RectV{2.0, 3.0}) << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra shape_three_ways.cpp -o shape3 && ./shape3
```

```text
-- A 虚函数 --
3.14159
6
-- B variant --
3.14159
6
-- C concepts --
3.14159
6
```

（浮点输出的实际位数取决于实现，`std::cout` 默认 6 位有效数字。）

怎么选：

| 场景 | 选哪个 |
| --- | --- |
| 类型集合开放（第三方可以加新形状），要跨动态库边界 | A：虚函数 + `unique_ptr` |
| 类型集合封闭、就那么几种，想省一次间接跳转和一次堆分配 | B：`std::variant` |
| 写的是通用组件、要把性能榨到最后一点 | C：模板 + concepts |

> **这里有个坑：** `std::variant` 的大小等于最大候选类型的大小再加一个 discriminant，把它塞进容器前先看一眼 `sizeof`。而虚函数方案每个对象多一个虚指针（典型 8 字节）加一次堆分配。二者都用在这两件事上时，性能差距通常没你想的那么大，别拿"少一次间接跳转"当设计依据，先量（Per.1、Per.6）。

## 2.2 分析C++的程序结构
{: .sec-expl}

### 2.2.1 编译单元与头文件模型
{: .sec-know}

一个 `.cpp`（连同它 `#include` 的全部头文件、展开后）构成一个**翻译单元（translation unit, TU）**。编译器一次只看一个 TU，看不到别的 TU 里有什么；跨 TU 的一致性由链接器和 ODR 保证。这条事实几乎解释了 C++ 里所有"为什么这么麻烦"的问题：

- 模板为什么必须写在头文件里：实例化时需要看到完整定义。
- 为什么 C++ 编译慢：每个 TU 都要重新解析一遍被 include 的几万行。
- 为什么 link 错误往往出现在"我明明写了这个函数"上：那个 TU 没有这个符号，或者符号名不一致。

一份典型的物理结构：

```text
project/
  include/foo/math_utils.hpp     # 对外公布的声明
  src/math_utils.cpp             # 实现，单独编译
  src/internal_detail.hpp        # 内部头，不对外
  app/main.cpp
```

头文件保护两种写法：

```cpp
// 方案 1：include guard，任何编译器任何年代都对
#ifndef FOO_MATH_UTILS_HPP
#define FOO_MATH_UTILS_HPP
// 内容
#endif
```

```cpp
// 方案 2：#pragma once（非标准但被三大编译器普遍支持）
#pragma once
```

| 写法 | 优点 | 缺点 |
| --- | --- | --- |
| include guard | 标准内、跨-U符合性最好 | 宏名要手写且唯一，写重了静默失效；有的编译器对"先判断宏再打开文件"的缓存优化支持较弱 |
| `#pragma once` | 一行、不会写重、编译器能记住"这个文件已包含"，通常更快 | 依赖文件系统识别同一份文件：硬链接/同一文件的两份拷贝/网络文件系统上的奇怪路径可能失效 |

实践上我的建议：新项目直接 `#pragma once`；只有要塞进 SDK 给外人编译的头文件才退回 include guard（可移植性优先）。

### 2.2.2 ODR：单一定义规则
{: .sec-know}

ODR 说两件事：**一个 TU 内**，任何变量/函数/类只能定义一次；**整个程序里**，非 inline 的函数与非 inline 的普通变量只能有一个定义。类的定义、模板、inline 函数可以在多个 TU 出现——但每一处的 token 序列必须完全一致（否则是 IFDR/ODR 违反，UB，编译器不保证报错）。

把它 violate 的最常见手法，是把普通函数定义放进头文件：

```cpp
// bad_util.hpp
#pragma once

// 坑：非 inline 的函数定义，每个 include 了它的 TU 都会产出一份 _Z5twicei
int twice(int x) { return x * 2; }
```

```cpp
// a.cpp
#include "bad_util.hpp"
int use_a() { return twice(21); }
```

```cpp
// b.cpp
#include "bad_util.hpp"
int use_b() { return twice(1); }
int use_a();
int main() { return use_a() + use_b(); }
```

```bash
g++ -std=c++20 a.cpp b.cpp -o ab
```

```text
/usr/bin/ld: b.cpp:(.text+0x0): multiple definition of `twice(int)'; a.cpp:(.text+0x0): first defined here
collect2: error: ld returned 1 exit status
```

三处修改任选其一：

```cpp
// util.hpp —— 正解一：inline，全程序同一份实体
#pragma once
inline int twice(int x) { return x * 2; }
```

```cpp
// util.hpp —— 正解二：只声明，定义挪到 util.cpp（编译防火墙效果最好）
#pragma once
int twice(int x);
```

```cpp
// util.hpp —— 正解三：模板天然可以放头文件（实例化发生在调用方 TU）
#pragma once
template <class T>
T twice_generic(T x) { return x + x; }
```

还有一种更阴的情况：改成 `static int twice(int x)` 之后链接通过了，但每个 TU 各自一份拷贝；如果不同 TU 里这份函数体不同（比如靠 `#ifdef` 编出了不同的实现），那就是标准的 ODR 违反——没有任何诊断，运行行为随机。

| 声明/定义关键字 | 链接性 | 会产生几份实体 | 跨 TU 冲突 | 什么时候用 |
| --- | --- | --- | --- | --- |
| `int g;`（命名空间作用域） | 外部 | 全程序唯一，重复定义即链接错误 | 会 | 真的要跨 TU 共享的变量（越少越好） |
| `extern int g;` | 外部（仅声明） | 零 | — | 头文件里声明、唯一的 `.cpp` 里定义 |
| `static int g;` | 内部 | 每 TU 一份 | 不会，但各 TU 的 `g` 不是同一个对象 | 本 TU 私有状态 |
| 匿名 namespace 内的名字 | 内部 | 每 TU 一份 | 不会 | 本 TU 私有的类型/函数/变量（推荐优于 `static`） |
| `constexpr int g = 0;` | 内部（`const` 的默认行为） | 每 TU 一份 | 不会 | 老式头文件常量 |
| `inline constexpr int g = 0;`（C++17） | 外部，允许多份合并 | 唯一 | 不会 | 现代头文件常量的标准写法 |
| `inline` 函数 | 外部，允许多份合并 | 唯一 | 不会 | 头文件里的函数实现 |
| `constexpr` 函数（C++11起） | 隐含 inline | 唯一 | 不会 | 编译期可求值的函数 |

#### 辨析：声明 vs 定义
{: .sec-iv}

- **声明**：告诉编译器"有这个名字，类型是 XXX"，不分配存储、不产出代码。可以出现无数次。
- **定义**：把实体造出来（变量分配存储、函数产出机器码、类给出成员布局）。受 ODR 约束。

容易搞混的几处：`extern int x;` 是声明，`int x;` 是定义；`struct S;` 是前向声明（incomplete type，只能用于指针/引用），`struct S { int a; };` 才是定义；类内 `int f();` 是声明，`int f() { return 1; }` 是定义（且隐式 inline）；`static int x;` 在类内是声明（类静态成员），需要在 `.cpp` 里给出定义（C++17 起 `inline static` 可免除）。

### 2.2.3 静态与动态初始化的坑：main 之前发生了什么
{: .sec-prac}

```cpp
// lifecycle.cpp —— 需要 -std=c++20
#include <cstdlib>
#include <iostream>

struct Tracer {
    const char* name;
    explicit Tracer(const char* n) : name(n) { std::cout << "ctor " << name << "\n"; }
    ~Tracer() { std::cout << "dtor " << name << "\n"; }
};

Tracer g1("global1");              // 动态初始化，发生在 main 之前
static Tracer g2("global2");       // 同上，且是内部链接

void by_exit() { std::cout << "atexit handler\n"; }

const Tracer& lazy() {             // Meyers singleton：第一次调用才构造（C++11 起线程安全）
    static Tracer t("lazy");
    return t;
}

int main() {
    std::cout << "--- main begin ---\n";
    std::atexit(by_exit);
    lazy();
    std::cout << "--- main end ---\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra lifecycle.cpp -o lifecycle && ./lifecycle
```

```text
ctor global1
ctor global2
--- main begin ---
ctor lazy
--- main end ---
dtor lazy
atexit handler
dtor global2
dtor global1
```

（Linux + glibc 上的顺序：静态析构与 `atexit` 回调走同一张 `__cxa_atexit` 表，严格按注册逆序执行。别的平台可能略有差异，别依赖这条具体顺序。）

这张输出里藏着三条规则：

1. **同一 TU 内**，全局/静态对象的动态初始化按定义顺序进行，析构严格逆序。这是被保证的。
2. **跨 TU 的动态初始化顺序未被规定**——A.cpp 的全局对象在构造时用到 B.cpp 的全局对象，结果取决于链接器把谁放前面，这就是 SIOF（静态初始化顺序惨剧）。
3. 解决方案是**函数内 static 局部对象**：`T& instance() { static T obj; return obj; }`，它保证"第一次调用时才初始化"，且 C++11 起初始化本身线程安全（俗称 magic statics）。想彻底不要延迟初始化，就让它成为 `constexpr`（编译期完成）。

> **坑：** 别在 DLL/so 卸载的场景里指望这些析构顺序，动态库卸载时的静态析构顺序更混乱；跨 ABI 边界的资源释放一律走显式的 `init()`/`shutdown()` 函数，别靠全局对象析构。
{: .sec-pit}

### 2.2.4 现代替代：Modules（C++20）
{: .sec-ext}

头文件模型最大的问题是"文本重复粘贴"。Modules 的思路是把接口编译成编译器可读的二进制接口单元（BMI），import 时不再重解析。

```cpp
// math.cppm —— 需要 C++20 且编译器支持 modules
export module demo.math;

export int add(int a, int b) {
    return a + b;
}

namespace detail {                 // 未 export，模块外不可见
    int helper() { return 42; }
}
```

```cpp
// main.cpp —— 需要 C++20
import demo.math;

#include <iostream>

int main() {
    std::cout << add(20, 22) << "\n";
}
```

现实的状态要说实话：截至 2026 年，三大编译器的 Module 支持都已可用（Clang 最积极，MSVC 次之，GCC 14/15 之后逐步完善），CMake 侧需要较新版本并开启实验性 modules 支持；标准库模块（`import std;`）的可用性差异更大。新项目可以试点，老项目迁移要评估第三方依赖是否支持。

## 2.3 必须遵循的编码规范
{: .sec-best}

### 2.3.1 可执行清单：来自 C++ Core Guidelines
{: .sec-know}

C++ Core Guidelines 是一份由 Bjarne Stroustrup 与 Herb Sutter 维护的规则集合，规则编号（P/I/F/C/E/ES/NL/Per/CP/R/CPL）方便在 review 里直接引用。下面按主题挑出最该先落实的部分，每条配了"具体该怎么做"。

资源与所有权（R.*）：

| 规则 | 内容 | 落地动作 |
| --- | --- | --- |
| R.1 | 用 RAII 管理资源 | 看到 `new` 就问：能不能直接用容器或 `make_unique` |
| R.3 / R.4 | 裸指针/裸引用表示"不拥有" | 函数参数里出现 `T*` 就是"借用"，所有权要用 `unique_ptr`/`shared_ptr` 或值传递 |
| R.5 | 优先栈对象，别无谓地堆分配 | 局部变量默认直接用值，除非对象很大或需要延长生命周期 |
| R.6 | 避免非常量全局变量 | 全局可变量是隐式的跨模块依赖，改成显式传参或服务对象 |
| R.11 | 避免显式 new/delete | 用 `make_unique`（C++14）/ `make_shared` |
| R.20 / R.21 | 所有权用智能指针，优先 `unique_ptr` | 只有真的要共享才用 `shared_ptr` |
| R.24 | 用 `weak_ptr` 打破 shared_ptr 环 | 父子互相持有、观察者模式里必备 |
| R.30 | 只在需要表达生命周期语义时才用智能指针作参数 | 只是读一下对象就传 `T&` 或 `T const&` |

接口与函数（I.* / F.*）：

| 规则 | 内容 | 落地动作 |
| --- | --- | --- |
| I.2 / I.4 | 接口要明确，优先传 bool 之外的自解释类型 | 用 `std::chrono::duration`（C++11）代替裸 int 毫秒，用强类型 enum 代替整数选项 |
| I.11 / I.12 | 不用裸指针转移所有权；非 RAII 的指针参数就写 `T*` | 见下方 2.3.3 的辨析 |
| I.23 | 控制函数参数数量 | 超过 3~4 个就打包成 struct |
| I.27 | 需要转移所有权时用 `unique_ptr<T>` | `std::unique_ptr<Connection> connect(...)` |
| F.16 | 便宜的类型按值传，贵的按 const 引用 | 经验线：能放进一两个寄存器的（int、double、指针、`std::pair<int,int>`）按值 |
| F.20 | 优先返回值，少用输出参数 | 多个返回值用 struct 或 `std::tuple`（但 struct 可读性更好） |
| F.6 | 不可能抛异常的函数标 `noexcept` | 移动构造、析构、`swap` 尤其该标（它们不该失败，E.16） |
| F.2 / F.3 | 函数做一件事，短 | 超过一屏就考虑拆 |

类（C.*）：

| 规则 | 内容 | 落地动作 |
| --- | --- | --- |
| C.2 / C.8 | 有不变式用 `class`，纯粹数据包用 `struct` | 别给 struct 写 `private` |
| C.20 / C.21 | Rule of Zero，其次 Rule of Five | 能用 `= default` 就别手写拷贝/析构；要手写就五个一起写 |
| C.35 / C.127 | 基类析构：public+virtual 或 protected+非虚 | 见 2.1.3 |
| C.41 | 构造函数要产出完整初始化的对象 | 构造完马上可用的语义；做不到就改成工厂函数返回 `optional`/`expected` |
| C.45 / C.48 | 用类内初始化器，别在构造函数里赋默认值 | `int retries{3};` 写在成员处 |
| C.46 | 单参数构造函数默认 `explicit` | 防隐式转换的出 whitelist |
| C.49 | 构造函数里用初始化列表而不是赋值 | `: name_(name)` 写法 |
| C.67 | 多态类抑制公开拷贝/移动 | `Shape(const Shape&) = delete;` 或 protected |
| C.90 | 别用 `memset`/`memcpy` 处理对象 | 会绕过构造与析构，平凡类型除外 |

表达式与语句（ES.*）：

| 规则 | 内容 |
| --- | --- |
| ES.1 | 优先标准库而不是手写或外部库 |
| ES.5 / ES.6 | 作用域尽量小，把变量声明在 for 的初始化段或 if 的条件里（C++17 `if (auto it = m.find(k); it != m.end())`） |
| ES.10 | 一条声明只声明一个名字（别写 `int* p, q;`） |
| ES.20 | 对象必须初始化 |
| ES.23 / ES.64 | 优先 `T{...}` 大括号初始化（能捕获窄化转换） |
| ES.25 | 不打算改的值就声明 `constexpr`（编译期能算）或 `const` |
| ES.28 | 复杂初始化用 lambda 一次性算好并赋给 const 变量 |
| ES.30 / ES.31 / ES.32 | 别用宏做代码生成、常量、函数；宏名全大写且加前缀 |
| ES.43 | 别依赖未定义的求值顺序（`f(a++, a++)` 是 UB） |
| ES.47 | 用 `nullptr` 而不是 `0`/`NULL`（C++11） |
| ES.48 / ES.49 / ES.50 | 别随便转型；必须转时用命名转换（`static_cast` 等）；绝不去掉 const |
| ES.56 | 只在真的要转移所有权时写 `std::move` |
| ES.63 | 别切片（值传递派生对象到基类参数） |
| ES.71 / ES.72 / ES.73 | 能用范围 for 就用；离散常量优先 `switch`；没循环变量时用 `while` |
| ES.100 / ES.101 / ES.102 | 别混有符号与无符号算术；无符号只用于位操作；数值用有符号（详见第 03 篇） |

命名与格式（NL.*）：这部分的建议比法律弱，团队统一最重要。

| 规则 | 建议的具体约定 |
| --- | --- |
| NL.8 | 全项目统一一套 style，写进 `.clang-format` |
| NL.9 | ALL_CAPS 只留给宏 |
| NL.10 | Guidelines 推荐 snake_case；LLVM/libc++ 系用 `lowerCamel` 变量 + `UpperCamel` 类型；Google 系再给类成员加 `trailing_`。选一套，别混 |
| NL.19 | 别用容易看错的名字（`l` `I` `1`、`rn` `m`） |
| NL.5 | 别把类型编进名字（`strName`、`pFoo`）——匈牙利命名在现代 C++ 里是纯负债 |
| NL.7 | 作用域越长名字越完整，短作用域可以用短名（`i`、`it`） |
| NL.11 | 字面量要可读：`1'000'000`（C++14）、`0b1010'1100`（C++14）、`15min`（chrono 字面量） |

## 2.4 输入输出基础
{: .sec-know}

这一节的定位是"够用即可"：知道几件事、避开几个坑就够往后学了。格式化、文件流、自定义 `operator<<`、locale 全在《11-流文件系统与格式化》里。

### 2.4.1 iostream 的三件套与缓冲
{: .sec-know}

| 对象 | 用途 | 是否带缓冲 |
| --- | --- | --- |
| `std::cout`（`<iostream>`） | 标准输出 | 带缓冲（行缓冲/全缓冲取决于是否连终端） |
| `std::cerr` | 错误信息 | 无缓冲倾向（`unitbuf` 默认打开），适合报错 |
| `std::clog` | 日志 | 带缓冲 |
| `std::cin` | 标准输入 | 输入缓冲 |

`<<` 是位左移运算符被重载出来的插入运算符；因为返回流本身的引用，所以能链式写 `std::cout << a << b << c`。

```cpp
// io_basic.cpp —— 需要 -std=c++20
#include <iomanip>
#include <iostream>
#include <limits>
#include <string>

int main() {
    std::cout << "请输入一行文字: ";
    std::cout.flush();                       // 没有换行符时必须手动刷，提示语才看得见

    std::string line;
    if (!std::getline(std::cin, line)) {
        std::cerr << "读取失败\n";
        return 1;
    }

    std::cout << "请输入一个整数: ";
    int n = 0;
    if (!(std::cin >> n)) {                  // 输入不是整数时，流进入 fail 状态
        std::cerr << "那不是整数\n";
        return 1;
    }
    std::cin.ignore(std::numeric_limits<std::streamsize>::max(), '\n');  // 吃掉残留的换行

    std::cout << "line = " << line << ", n = " << n << "\n";
    std::cout << std::fixed << std::setprecision(3) << 12.3456789 << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra io_basic.cpp -o io_basic && ./io_basic
```

```text
请输入一行文字: hello modern cpp
请输入一个整数: 42
line = hello modern cpp, n = 42
12.346
```

（`12.346` 是 `fixed` + 3 位精度的结果；不同平台的默认浮点 printed 位数与舍入可能有最后一字的差别。）

### 2.4.2 `endl` 的代价与 `sync_with_stdio`
{: .sec-ts}

```cpp
std::cout << "x\n";            // 只写一个换行符，留在缓冲区
std::cout << "x" << std::endl; // 写换行 + 强制 flush（一次系统调用）
std::cout << "x" << std::flush;// 不写换行，只 flush
```

在循环里每写一行都 `std::endl`，等于每行一次 write 系统调用，慢一个数量级是常事。**默认写 `\n`，要立刻看见再用 `std::flush`**（比如需要把提示语在读数前打出来）。

`std::cin.tie(nullptr)` 和 `std::ios::sync_with_stdio(false)` 是竞赛里常见的两行：

```cpp
std::ios::sync_with_stdio(false);   // 断开 C 的 stdio 与 iostream 的同步
std::cin.tie(nullptr);              // 读 cin 时不再自动 flush cout
```

它们对"一次读写几十 MB"的场景才有明显收益，代价是**不能把 `scanf/printf` 和 `cin/cout` 混着用**（输出顺序可能错乱）。业务代码里一般不需要，开了反而容易踩混用的坑。

> **坑：** `>>` 和 `getline` 混用。读完一个 int 后缓冲区里还留着回车，`getline` 立刻读到空行。要么统一用 `getline` 再自己解析，要么在 `>>` 之后 `ignore(...)`（如 2.4.1 所示）。这个坑几乎每个学过 C++ 的人都踩过。
{: .sec-pit}

### 2.4.3 格式化的一瞥
{: .sec-ext}

```cpp
// io_format.cpp —— 需要 -std=c++20
#include <format>
#include <iostream>
#include <iomanip>

int main() {
    int user_id = 42;
    double ratio = 0.125;              // 二进制精确表示，便于对比两条路的输出

    std::cout << std::format("user={:>5d} ratio={:.2%} hex={:#x}\n", user_id, ratio, 255);
    std::cout << "legacy stream: user=" << std::setw(5) << user_id
              << " ratio=" << std::fixed << std::setprecision(2) << ratio * 100 << "%\n";
}
```

```text
user=   42 ratio=12.50% hex=0xff
legacy stream: user=   42 ratio=12.50%
```

这里两边完全一致，是因为 0.125 在二进制里精确。换成无法精确表示的小数（比如 0.12345），最后一位就可能出现分歧：`std::format` 明确规定用 round-half-to-even，而 iostream/printf 的舍入取决于底层 locale 与标准库实现。迁移格式化代码时这是最容易被忽略的差异。

流向这门学问的完整内容（locale、自定义类型的 `operator<<`、`std::osyncstream`（C++20）、文件 IO、`std::fstream` 缓冲策略、`std::print`（C++23））在第 11 篇展开。

#### 辨析：`std::endl` vs `'\n'` vs `std::flush`
{: .sec-iv}

- `'\n'`：字符，写进缓冲区，最便宜。绝大多数时候要的是它。
- `std::flush`：操纵符，把缓冲区推出去，不写任何字符。
- `std::endl`：等于写 `'\n'` 再 `flush()`。它唯一的合理用途是"下一行输出前必须让用户看见"（交互式进度、崩溃前的最后一句话），或者懒得想。

## 2.5 算法是程序的灵魂
{: .sec-expl}

### 2.5.1 为什么优先标准库算法
{: .sec-know}

三条理由，按重要性排：

**1. 正确性。** 手写循环的错误率远高于你的想象，而且错误形态高度一致：差一错误、循环变量用错、条件写反、忘了空区间。

```cpp
// hand_vs_algo.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <numeric>
#include <vector>

int main() {
    std::vector<int> v{3, 1, 4, 1, 5, 9, 2, 6};

    // 手写：看着没问题，其实空区间时 UB（解引用 begin()）
    // int max_val = *v.begin();  // 假如 v 为空就已经炸了

    auto it = std::max_element(v.begin(), v.end());
    if (it != v.end()) {
        std::cout << "max = " << *it << "\n";
    }

    // 求和：注意初值类型决定了结果类型
    std::vector<double> d{0.5, 0.25, 0.25};
    auto wrong = std::accumulate(d.begin(), d.end(), 0);      // 初值 int → 累加过程中被截断
    auto right = std::accumulate(d.begin(), d.end(), 0.0);    // 初值 double
    std::cout << "wrong = " << wrong << ", right = " << right << "\n";

    // 计数、判定、变换：一条算法代替一段
    std::cout << "count(1) = " << std::count(v.begin(), v.end(), 1) << "\n";
    std::cout << "any >8 = " << std::any_of(v.begin(), v.end(), [](int x) { return x > 8; }) << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra hand_vs_algo.cpp -o hand_vs_algo && ./hand_vs_algo
```

```text
max = 9
wrong = 0, right = 1
count(1) = 2
any >8 = 1
```

 (`std::accumulate(d.begin(), d.end(), 0)` 中，`0` 是 `int`，累加结果全程保持 `int`，`0.5+0.25+0.25` 被截断成 `0`。这是最典型的"算法是对的，我的调用是错的"。)

**2. 性能。** 标准实现知道一些你手写不会去想的事：`std::fill` 对 trivially copyable 类型会退化为 `memset`；`std::copy` 对连续迭代器会退化为 `memmove`；`std::find` 在 libstdc++ 里有 memchr 特化；`std::sort` 是 introsort（快排 + 堆排兜底 + 插入排序处理小分段），不会出现快排的最坏 O(n²)。

**3. 表达力。** `std::ranges::count_if(users, is_active)` 是一个短语，"这个数量的用户是活跃的"；等价的手写循环要读 5 行才知道在干嘛。算法还把"意图"告诉了编译器和未来的读者。

什么时候**该**手写循环（别走极端）：

- 需要索引去访问另一个容器（`i` 同时用于 `a[i]` 和 `b[i]`）。
- 需要复杂的提前退出或者多段状态机。
- 需要跨步访问（`i += 3`）或者要在遍历中修改容器结构。
- 要手写 SIMD intrinsics、精确控制循环展开，或者写的是 GPU kernel 那种形态的代码。

### 2.5.2 迭代器类别与算法复杂度约束
{: .sec-know}

迭代器的"类别"决定哪些算法能用、以及它们的复杂度。C++20 之前用 tag（`std::random_access_iterator_tag` 等），C++20 起用 concept（`std::random_access_iterator` 等）。

| 类别 | 能干什么 | 代表 | 可用的典型算法 |
| --- | --- | --- | --- |
| input（含 output） | 单趟读取/写入，`++` 后旧的失效 | `istream_iterator`、`views::basic_istream_view` | 单趟算法：`count`、`find`、`copy` |
| forward | 可多趟，`++`，可保存迭代器 | `forward_list`、`unordered_*`（多数实现） | 多趟但不需要后退：`rotate`、`search`、`unique` |
| bidirectional | 额外支持 `--` | `list`、`set`、`map` | `reverse`、`inplace_merge`、`stable_partition` |
| random access | 额外支持 `+= n`、`[]`、`<` | `vector`、`deque`、`array`、`string` | `sort`、`nth_element`、`lower_bound`、``std::heap` 系列 |
| contiguous（C++20） | 元素在内存里真连续，可 `std::to_address` | `vector`、`array`、`string`、`span`（C++20） | `std::ranges::sort` 乃至 memcpy/memmove 级的优化 |

几个和复杂度直接绑定、值得记住的事实：

| 事实 | 后果 |
| --- | --- |
| `std::sort` 要求 random access，复杂度 O(n log n) 次比较 | `std::list` 不能用 `std::sort`，只能调成员 `list::sort`（O(n log n)，稳定） |
| `std::distance` 对 random access 是 O(1)，其余是 O(n) | 在 forward_list 上反复 `distance` 会写出 O(n²) |
| `std::lower_bound` 要求已排序区间，O(log n) 次比较但 forward 迭代器上是 O(n) 次自增 | 不要在 `list` 上跑二分搜索，代价会退化到 O(n) |
| `std::nth_element` 平均 O(n)，单趟划分 | 找 top-k 或中位数比 `sort` 便宜得多 |
| `std::stable_sort` 额外内存可能是 O(n)（无足够内存时退化到 O(n log² n)） | 排序大对象又不关心顺序时用 `sort` |

### 2.5.3 常用算法族与它们的内部实现
{: .sec-expl}

按行为分类，每类挑出常用的和必须知道内部行为的：

**非修改序列操作**（`<algorithm>`）

| 算法 | 作用 | 版本/备注 |
| --- | --- | --- |
| `all_of` / `any_of` / `none_of` | 谓词量化判断 | C++11 |
| `for_each` / `for_each_n` | 对每个元素执行动作 | `for_each_n` 是 C++17 |
| `count` / `count_if` | 计数 | |
| `find` / `find_if` / `find_if_not` | 找单个位置 | `find_if_not` 是 C++11 |
| `adjacent_find` | 找相邻重复（或满足二元谓词的一对） | 做"连续相等"检查最方便 |

**修改序列操作**

| 算法 | 作用 | 内部行为（知道这个才不会踩坑） |
| --- | --- | --- |
| `copy` / `copy_if` / `copy_n` / `copy_backward` | 拷贝区段 | `copy` 允许区间重叠的方向受限，任意重叠用 `copy_if`/`std::move` 谨慎；`copy_backward` 反向拷 |

| --- | --- | --- | --- |

**二分查找（要求按同一比较器已排序）**

```cpp
// lower_bound_demo.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 2, 2, 3, 5, 8};

    auto lo = std::lower_bound(v.begin(), v.end(), 2);   // 第一个 >= 2
    auto hi = std::upper_bound(v.begin(), v.end(), 2);   // 第一个 > 2
    std::cout << "lo index = " << (lo - v.begin()) << ", hi index = " << (hi - v.begin()) << "\n";
    std::cout << "count of 2 = " << (hi - lo) << "\n";

    auto eq = std::equal_range(v.begin(), v.end(), 2);   // 一次拿到 [lo, hi)
    std::cout << "equal_range size = " << (eq.second - eq.first) << "\n";

    bool exists = std::binary_search(v.begin(), v.end(), 4);   // 只回答 yes/no，不给你位置
    std::cout << "has 4? " << exists << "\n";

    // 插入但要保持有序：用 lower_bound 拿到位置，而不是先 insert 再 sort
    v.insert(std::lower_bound(v.begin(), v.end(), 4), 4);
    for (int x : v) { std::cout << x << ' '; }
    std::cout << "\n";
}
```

```text
lo index = 1, hi index = 4
count of 2 = 3
equal_range size = 3
has 4? 0
1 2 2 2 3 4 5 8
```

### 2.5.4 erase-remove 惯用法与它的现代替代
{: .sec-prac}

```cpp
// erase_remove.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <vector>

int main() {
    std::vector<int> v{1, 2, 3, 2, 4, 2, 5};

    auto print = [&v] {
        for (int x : v) { std::cout << x << ' '; }
        std::cout << "(size=" << v.size() << ", capacity=" << v.capacity() << ")\n";
    };

    std::cout << "remove 之前: "; print();

    auto new_end = std::remove(v.begin(), v.end(), 2);
    std::cout << "remove 之后: "; print();                 // size 没变！只是把后面的元素挪了

    v.erase(new_end, v.end());                             // 真正擦除（C++11 之前的经典惯用法）
    std::cout << "erase 之后: "; print();

    std::erase(v, 5);                                      // C++20：一行搞定值删除
    std::erase_if(v, [](int x) { return x % 2 == 1; });    // C++20：谓词删除（所有容器都有）
    std::cout << "erase_if 之后: "; print();
}
```

```text
remove 之前: 1 2 3 2 4 2 5 (size=7, capacity=7)
remove 之后: 1 3 4 5 4 2 5 (size=7, capacity=7)
erase 之后: 1 3 4 5 (size=4, capacity=7)
erase_if 之后: 4 (size=1, capacity=7)
```

（`remove` 之后尾部的 `4 2 5` 是实现随便留下的有效值，具体的旧值取决于实现；`capacity` 不会因为 erase 变小。）

要记三点：

1. `remove` / `remove_if` 只重排，不删，`size()` 不变。
2. `unique` 只消掉**相邻**重复，所以必须先 `sort`：`v.erase(std::unique(v.begin(), v.end()), v.end())` 只有排序后才有意义。
3. C++20 起，序列容器（`vector`/`deque`/`string`/`list`/`forward_list`）有 `std::erase(c, value)`；所有容器（含 `set`/`map`/`unordered_*`）都有 `std::erase_if(c, pred)`。

### 2.5.5 C++20 Ranges：把算法组合成管道
{: .sec-ext}

Ranges 做了三件事：让算法直接吃容器（`std::ranges::sort(v)` 而不是 `sort(v.begin(), v.end())`）、把 begin/end 的类型可以不一样（sentinel）、以及引入可组合的 `views`。

```cpp
// ranges_basic.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <ranges>
#include <string>
#include <vector>

int main() {
    std::vector<int> v{5, 3, 8, 1, 9, 2, 7, 4, 6};

    // 1) 直接吃容器
    std::ranges::sort(v);
    std::cout << "sorted: ";
    for (int x : v) { std::cout << x << ' '; }
    std::cout << "\n";

    // 2) 管道组合：偶数 → 平方 → 取前 3 个，全程惰性、无中间容器
    auto pipeline = v | std::views::filter([](int x) { return x % 2 == 0; })
                      | std::views::transform([](int x) { return x * x; })
                      | std::views::take(3);
    std::cout << "pipeline: ";
    for (int x : pipeline) { std::cout << x << ' '; }
    std::cout << "\n";

    // 3) 反向遍历（不修改底层）
    std::cout << "reverse: ";
    for (int x : v | std::views::reverse) { std::cout << x << ' '; }
    std::cout << "\n";
}
```

```bash
g++ -std=c++20 -Wall -Wextra ranges_basic.cpp -o ranges_basic && ./ranges_basic
```

```text
sorted: 1 2 3 4 5 6 7 8 9
pipeline: 4 16 36
reverse: 9 8 7 6 5 4 3 2 1
```

几个必须理解的性质：

- **惰性求值（lazy）**：`views::transform` 不会预先算出所有结果，只在迭代时才算。上面 `take(3)` 意味着 `transform` 只被调用 3 次。
- **zerocost 组合**：整条管道是一个编译期确定的类型，`v | views::filter(...) | views::transform(...)` 里没有类型擦除，也没有堆分配。
- **底层容器必须活得比 view 长**（见下方陷阱）。

### 2.5.6 投影（projection）
{: .sec-know}

投影是 C++20 ranges 算法里最实用的小改动：多传一个"从元素提取被比较/被处理的那部分"的可调用对象。

```cpp
// projection_demo.cpp —— 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <string>
#include <vector>

struct User {
    std::string name;
    int age;
    int score;
};

int main() {
    std::vector<User> users{
        {"ann", 31, 88},
        {"bob", 24, 95},
        {"cid", 46, 71},
    };

    // 按 score 找最大：第三个参数是投影（前两个是 comp 和 proj）
    auto best = std::ranges::max_element(users, {}, &User::score);
    std::cout << "best = " << best->name << " score=" << best->score << "\n";

    // 按 age 排序
    std::ranges::sort(users, {}, &User::age);
    for (const auto& u : users) {
        std::cout << u.name << '(' << u.age << ") ";
    }
    std::cout << "\n";

    // 降序 + 投影
    auto older = [](int a, int b) { return a > b; };
    std::ranges::sort(users, older, &User::age);
    std::cout << "oldest = " << users.front().name << "\n";

    // 投影也能用于计数
    std::cout << "age<30 count = " << std::ranges::count_if(users, [](int a) { return a < 30; }, &User::age) << "\n";
}
```

```text
best = bob score=95
bob(24) ann(31) cid(46)
oldest = cid
age<30 count = 1
```

写 `&User::score` 而不是 lambda 的好处不只是短：编译器能直接看到这是个成员指针，`std::invoke` 把它折叠成一次成员访问。

### 2.5.7 常用 view 逐个演示（C++20 / C++23）
{: .sec-prac}

```cpp
// views_tour.cpp —— 需要 -std=c++23（zip/enumerate/chunk_by/chunk/slide/stride/join_with 都是 C++23）
#include <iostream>
#include <ranges>
#include <string>
#include <string_view>
#include <vector>

void print_heading(std::string_view title) { std::cout << title << ": "; }

template <class R>
void print_range(R&& r) {
    for (auto&& x : r) { std::cout << x << ' '; }
    std::cout << "\n";
}

int main() {
    std::vector<int> v{1, 2, 3, 4, 5, 6, 7, 8};

    print_heading("take(3)");            print_range(v | std::views::take(3));
    print_heading("drop(5)");            print_range(v | std::views::drop(5));
    print_heading("take_while(<5)");     print_range(v | std::views::take_while([](int x) { return x < 5; }));
    print_heading("drop_while(<5)");     print_range(v | std::views::drop_while([](int x) { return x < 5; }));
    print_heading("stride(3)");          print_range(v | std::views::stride(3));
    print_heading("chunk(3)");           print_range(v | std::views::chunk(3) | std::views::join_with(0));
    print_heading("slide(3)");           print_range(v | std::views::slide(3) | std::views::join_with(0));

    std::vector<int> seq{1, 1, 2, 3, 3, 3, 4};
    print_heading("chunk_by(equal)");    print_range(seq | std::views::chunk_by([](int a, int b) { return a == b; }) | std::views::join_with(0));

    std::vector<std::string> names{"alpha", "beta", "gamma"};
    std::cout << "zip(names, v): ";
    for (auto&& [n, x] : std::views::zip(names, v)) { std::cout << n << '=' << x << ' '; }
    std::cout << "\n";

    std::cout << "enumerate(names): ";
    for (auto&& [i, n] : std::views::enumerate(names)) { std::cout << i << ':' << n << ' '; }
    std::cout << "\n";

    // split：以 0 为分隔符切整数序列
    std::vector<int> raw{1, 2, 0, 3, 4, 0, 5};
    std::cout << "split by 0: ";
    for (auto group : raw | std::views::split(0)) {
        std::cout << '[';
        for (int x : group) { std::cout << x; }
        std::cout << "] ";
    }
    std::cout << "\n";
}
```

```bash
g++ -std=c++23 -Wall -Wextra views_tour.cpp -o views_tour && ./views_tour
```

```text
take(3): 1 2 3
drop(5): 6 7 8
take_while(<5): 1 2 3 4
drop_while(<5): 5 6 7 8
stride(3): 1 4 7
chunk(3): 1 2 3 0 4 5 6 0 7 8
slide(3): 1 2 3 0 2 3 4 0 3 4 5 0 4 5 6 0 5 6 7 0 6 7 8
chunk_by(equal): 1 1 0 2 0 3 3 3 0 4
zip(names, v): alpha=1 beta=2 gamma=3
enumerate(names): 0:alpha 1:beta 2:gamma
split by 0: [12] [34] [5]
```

几点解释：

- `zip` 在最短的那个 range 结束时停（`names` 只有 3 个元素）。`views::zip_transform`（C++23）则 zip 之后再按函数变换。
- `enumerate` 的下标类型是 `range_difference_t`，通常是有符号的；想改元素用 `auto&& [i, x]`，`auto [i, x]` 会拿到拷贝。
- `slide(n)` 是窗口大小为 n、步长 1 的滑动窗口。
- `split` 这里用的是 C++23 的单值分隔符形式；C++20 里需要传一个 patterns range，或改用 `views::lazy_split`。

> **坑：** `views::filter` 要求谓词"equality-preserving"（多次调用同一值结果一致）。在 filter 的 lambda 里统计次数、改外部状态、或者通过引用修改元素，都会让 view 的行为不确定（它会缓存 begin，可能实际只调用一次谓词）。要副作用就用 `for_each` 或普通循环。
{: .sec-pit}

### 2.5.8 range-for 与结构化绑定
{: .sec-prac}

```cpp
// bindings.cpp —— 需要 -std=c++20
#include <iostream>
#include <map>
#include <ranges>
#include <string>
#include <vector>

int main() {
    std::map<std::string, int> inventory{{"apple", 12}, {"banana", 5}, {"cherry", 30}};

    // 结构化绑定可以直接拆 pair<const Key, T>
    for (const auto& [item, count] : inventory) {
        std::cout << item << " -> " << count << "\n";
    }

    // views::keys / views::values（C++20）
    std::cout << "keys: ";
    for (const auto& k : inventory | std::views::keys) { std::cout << k << ' '; }
    std::cout << "\n";

    std::cout << "big counts: ";
    for (int c : inventory | std::views::values | std::views::filter([](int x) { return x > 10; })) {
        std::cout << c << ' ';
    }
    std::cout << "\n";

    // 遍历 map 用值类别要写对：auto 会拷贝整个 pair
    std::vector<std::pair<int, std::string>> items{{1, "one"}, {2, "two"}};
    for (auto&& [id, name] : items) {          // 引用，避免拷贝；要改 name 就用 auto&&
        name += "!";
        std::cout << id << "=" << name << " ";
    }
    std::cout << "\n";
}
```

```text
apple -> 12
banana -> 5
cherry -> 30
keys: apple banana cherry
big counts: 12 30
1=one! 2=two!
```

（`map` 按 key 排序，所以输出顺序是 apple/banana/cherry，不是插入顺序。）

> **坑：** 在 range-for 里写 `auto [k, v]`（不带引用）会拷贝整个 pair。元素是 `std::string` 之类的时候，这就变成沉默的性能杀手。默认写 `const auto&`，要修改才用 `auto&&`。
{: .sec-pit}

### 2.5.9 迭代器失效：一张表记住所有容器
{: .sec-ts}

| 容器 | 插入后 | 删除后 | 备注 |
| --- | --- | --- | --- |
| `vector` / `string` | 若触发重新分配，全部迭代器/引用/指针失效；否则插入点之后失效 | 删除点之后（含 `end()`）全部失效 | `reserve()` 能避免中途重分配 |
| `deque` | 中间插入全部失效；头尾插入使迭代器失效但引用仍有效 | 中间删除全部失效；头尾删除只失效被删元素 | 分段连续存储 |
| `list` / `forward_list` | 不失效 | 只失效被删元素 | 节点式容器 |
| `set` / `map` 及其 multi 版本 | 不失效 | 只失效被删元素 | 节点式 |
| `unordered_*` | rehash 时全部失效，否则不失效 | 只失效被删元素 | `reserve()` 可抑制 rehash |
| `vector<bool>` | 特化实现（`bitset` 式代理），代理对象语义特殊 | 同 vector | 尽量避开；需要位集用整型 + 位运算 |

派生出的规范：

- 在遍历中删除元素时，**用 erase 返回的迭代器继续**（所有容器都返回紧跟被删元素之后的有效迭代器）：`it = bad(*it) ? v.erase(it) : std::next(it);`
- 需要条件批量删除时别在循环里逐个 erase（vector 上退化成 O(n²)），用 erase-remove 或 `std::erase_if`；缓存迭代器之前先确认这次操作不会让它失效。

### 2.5.10 算法的其它常见坑
{: .sec-pit}

- **`std::unique` 先 sort**（`std::remove` 不清 size 那条见 2.5.4）：`[1,2,1]` 的 unique 结果还是 `[1,2,1]`。
- **`std::sort` 不稳定**：相等元素的相对顺序未定义。要保序用 `stable_sort`，或让比较器带上第二关键字（tie-break）。
- **累加重整第三参数的类型**：`accumulate(v.begin(), v.end(), 0)` 配 `vector<double>` 得 int。
- **在 filter 之后的 view 上排序**：`views::filter` 的迭代器类别最多是 bidirectional，`ranges::sort` 要求 random_access + sortable，编译不过。要么先 `ranges::to<std::vector>`（C++23）物化，要么对原容器排序。
- **悬挂的 view**：holder 的生命周期必须覆盖 view。
  ```cpp
  // dangling_view.cpp —— 错误示范
  auto make_view() {
      std::vector<int> data{1, 2, 3};
      return data | std::views::filter([](int x) { return x > 1; });  // UB：data 已销毁
  }
  ```
  函数内的 `data` 是左值，`views::all` 得到 `ref_view`（只持引用），返回它就是在返回一个悬垂迭代器对。如果右侧是**右值**（比如 `get_vector() | views::filter(...)`），C++20 会用 `owning_view` 接管所有权，反而安全——但别依赖这种细节。同理，view 里的 lambda 若捕获了引用、而 view 又逃离当前作用域（比如存成成员），那些引用也得活得够久。

## 2.6 技术解惑
{: .sec-know}

### 2.6.1 面向对象是不是要求"万物皆对象"
{: .sec-know}

不是。C++ 从来不是纯 OO 语言，它同时是函数式的（算法/ranges）、泛型优先的（模板/concepts）、值语义优先的。现代代码里你更常见的是 `struct` 数据包 + 自由函数 + 标准算法，而不是一张巨大的继承树。回到 2.1.1 那条线：有没有不变式？没有不变式的数据包硬塞进 class 再配 getter/setter，只是把公开访问换成了啰嗦写法。

### 2.6.2 什么时候该用虚函数，什么时候不该
{: .sec-know}

满足下面任意一条才考虑虚函数：

1. 需要在同一个容器里放多种实现，而这些类型在编译期无法确定。
2. 需要跨动态库边界的可替换实现（插件/驱动）。
3. 改动频繁、希望编译器少重编（vtable 隔离）。

反之，如果调用方编译期就知道具体类型，用模板/concepts（可内联、零间接开销）；如果类型集合封闭且已知，用 `std::variant`（无堆分配、无虚指针）；只是想复用代码，用组合或普通函数调用。

### 2.6.3 为什么通过基类删除派生对象必须是 UB
{: .sec-know}

严格说，"通过基类指针 delete 且基类析构非虚"这个动作本身在标准里就是 undefined behavior（前提是被删对象实际类型与静态类型不同）。它之所以被定为 UB，是因为编译器不知道你到底要析构哪个派生部分：静态类型是 `Base*`，它只能调到 `~Base`，派生部分的成员（以及它们持有的资源）全都泄漏，vptr 也不被正确处理。修复方法：给基类加 `virtual ~Base() = default;`；或者把析构做成 `protected` 非虚，从类型上封锁"通过基类指针删除"。

### 2.6.4 头文件里能放 `using namespace` 吗
{: .sec-know}

不能。它会污染每一个 include 了该头文件的 TU，包括你下游用户的代码，冲突时报错位置可能离真正的原因很远。想省键盘就在 `.cpp` 里写，或者用别名（`namespace chrono = std::chrono;`）把范围收窄到最低限度。`using std::swap;`（把名字引入到 overload set）这种 ADL 惯用法是例外，它有明确的目的。

### 2.6.5 `#pragma once` 还是 include guard
{: .sec-know}

内部项目用 `#pragma once`：短、不会写重、编译器能省一次文件打开。要交付给外部、可能遇到奇怪的构建环境（网络文件系统、多重 symlink、同一文件的硬链接复制）的头文件，用 include guard。两者混用（既有 guard 又有 pragma once）也没问题，只是显得谨慎过头。

### 2.6.6 全局变量和单例到底能不能用
{: .sec-know}

可以有，但要满足三个条件：不可变（`constexpr` 或者构造后不再改）、顺序安全（不依赖其他 TU 的全局对象）、生命周期明确（有显式的 init/shutdown，而不是靠静态析构）。

这三个条件同时满足的场景其实不多。多数"全局状态"更好的形态是：一个显式的 `Context` 对象，从 `main` 开始一路传下去。真要惰性初始化就用函数内 static（2.2.3），线程安全由标准保证。

### 2.6.7 手写循环和标准算法之间怎么划界线
{: .sec-know}

默认先想"有没有现成算法"。找不到的情况下，判断它符不符合下面任一条，符合就手写：需要同时操作两个以上容器、需要复杂的提前退出/状态机、需要跨步访问、目标已经是要手写 SIMD。写完之后问一句：这个循环能不能拆成"一个标准算法 + 一个 lambda"？往往能。

### 2.6.8 `std::endl` 到底用不用
{: .sec-know}

基本不用。默认写 `\n`；要在换行之外真的把缓冲区推出去，写 `std::flush`；只有极少数情况（交互式提示、写日志的部分场景）需要在换行同时 flush，`std::endl` 的语义正好是那两件事的组合，但它被滥用成了"换行"的同义词，这才是问题。

### 2.6.9 为什么 `std::remove` 之后我 `size()` 没变
{: .sec-know}

因为它叫 remove，干的却是 partition。标准给它起这个名字的历史包袱不要去记了，只记结论：`remove` 返回新的逻辑末尾迭代器，必须拿它去 `erase`；C++20 起直接写 `std::erase(v, value)` / `std::erase_if(v, pred)`。

### 2.6.10 ranges 会不会比手写循环慢
{: .sec-know}

Release 构建下通常一样快，有时更快（算法/introsort/退化 memcpy 这些优化你手写不一定有）。它确实是零开销抽象：view 是编译期类型，`|` 只是构造嵌套类型。真正可能变慢的是 Debug 构建（`-O0` 下每一层 view 的调用都不被内联，开销显著），以及少数极端写法：

- `views::filter` 的 begin 会缓存首个命中位置，谓词不会被重复调用；谓词很贵（比如字符串查找）时用 view 反而更省。
- 把 view 塞进 `std::function` 或跨 ABI 传递会引入类型擦除，那时才真的有开销；hot loop 里反复构造同一条管道建议先存成变量。

任何情况下，结论由 `perf` 给，不由直觉给（Per.2、Per.6）。

## 变式追问
{: .sec-think}

1. `std::vector<int> v{1,2,3,2,4};v.erase(std::unique(v.begin(), v.end()), v.end());` 之后 v 里还剩什么？

   还剩 `1 2 3 2 4`。`unique` 只消除**相邻**重复，这里没有任何相邻重复，`new_end == v.end()`，erase 什么都没删。要真正去重必须先 `std::sort`（然后再看是否需要保序——保序的话得用别的方法，比如 `unordered_set` 辅助，这里 sort 会打乱原顺序）。这个 bug 在线上代码里的典型形态是"数据局部小重复没被清掉"。

2. 为什么 `std::sort` 定义在 `<algorithm>` 里，却没法用来排序 `std::list`？

   `std::list` 的迭代器是 bidirectional，而 `sort` 要求 random access（它要 `it + n` 做 introsort 的划分和 `it < it2` 比较距离）。强行调用会得到一屏 template 实例化错误，根因在第一行：约束（C++20 起是 concept）没有满足。list 有自己的成员 `list::sort()`（链表归并排序，稳定，O(n log n)），因为它不需要随机访问。C++20 起这个约束用 concept 表达，`std::ranges::sort(some_list)` 的错误信息会直接告诉你 `sortable` 不满足。

3. 下面这段有什么问题？

   ```cpp
   auto odd = v | std::views::filter([](int x) { return x % 2 == 1; });
   v.push_back(9);
   for (int x : odd) { /* ... */ }
   ```

   `v.push_back` 可能触发 rehash/reallocation → `odd` 里缓存的迭代器失效（见 2.5.9）。`views::filter` 的 `begin()` 会缓存首个满足谓词的位置，如果后续再 `begin()`，它是懒惰的——但如果在这次 push_back 之前已经调用过 begin，缓存的就是旧 iterator。安全的做法：先 `reserve` 保证不重分配，或者在使用 view 期间不要修改底层容器的结构。这条也是『view 是容器上的惰性视图，不是快照』的直接后果。

4. 大家都说 Ranges 是零开销抽象，那为什么我的 Debug 构建慢了 10 倍？

   零开销的前提是"编译器把抽象优化掉"。`-O0` 下每一层 view 的构造、`dereference`、`advance` 都是真实的函数调用（还不内联），一条 5 段的管道在 hotspot 里跑百万次，累加起来非常可观。Release 下全部内联，通常退化成和手写循环一样的指令。所以基准一定要用 `-O2`；也别为了避免这点 Debug 开销就放弃 Ranges。真正的微调点是：把热点的 view 提到循环外、避免在语义上多余的 `views::common`、以及别用运行时的 `std::function` 当谓词。
