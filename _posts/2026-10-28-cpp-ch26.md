## 26.1 系统分析：监控什么、给谁用
{: .sec-expl}

### 原书硬件方案为什么被替换
{: .sec-know}

原书的"视频监控卡"是一块 PCI/PCIe 插卡，把模拟摄像头的复合视频信号数字化，再由 DirectShow 过滤器链取帧。这套东西有两个死穴：一是模拟摄像头本身已被网络摄像头（RTSP/ONVIF 直接出流）全面取代，插卡失去了存在理由；二是 DirectShow 只在 Windows 上活着，COM 引用计数与 RAII 语义格格不入——第 25 篇已经把解码后端换成了 FFmpeg，这里沿用。

更根本的变化在监控对象：原书只盯"画面"，而现代系统监控的主体是指标（数值时间序列）、日志（文本流）和事件（离散记录），画面只是其中一路。所以"选购监控卡"这个问题，今天变成了"选哪些采集源、用什么协议接入"。功能主线倒是一行没变：

| 功能 | 原书形态 | 本篇形态 |
| --- | --- | --- |
| 实时监控 | 摄像头画面实时上屏 | 实时指标/事件流经 SSE 推送到页面 |
| 事件告警 | 画面移动侦测 | 规则引擎 + 滑动窗口 + 告警状态机 |
| 历史回放 | 录像文件按时间轴回放 | segments 段索引 + 事件/帧区间查询 |
| 权限管理 | 单机软件，基本没有 | 会话 token + RBAC 三角色 |

非功能需求同样要写进分析：采集吞吐（每秒多少条事件、多少路流）、查询延迟（回放点开到出画面的时间）、可靠性（进程被杀后数据不丢、能自动重启）、安全（谁登录过、密码怎么存）。这些数字不用一开始就精确，但量级必须先定——它决定 26.4 选 SQLite 还是 TimescaleDB、26.5 要不要线程池。

### 需求到架构的映射
{: .sec-know}

四条功能各自压到不同层：实时监控压在采集层与展示层之间（数据要"直通"，不能被存储拖慢）；事件告警压在查询层（对流入数据做计算）；历史回放压在存储层（索引设计好不好全看它）；权限管理横切所有入口。后面每层的取舍都从这张映射来。

## 26.2 系统设计：五层架构与线程划分
{: .sec-know}

| 层 | 职责 | 本篇选型 |
| --- | --- | --- |
| 采集层 | 对接各类源，归一化成事件/帧 | 每源一个采集 jthread（26.3） |
| 传输层 | 源到存储的搬运，带背压 | 有界队列 + 批量聚合（26.3） |
| 存储层 | 落盘、索引、轮转 | SQLite WAL 单写线程（26.4） |
| 查询层 | 时间范围查询、告警判定、API | CPU 线程池 + REST（26.5、26.6） |
| 展示层 | 实时图表、回放界面 | Web 前端 + SSE（26.10） |

为什么分层而不是一个大全 function？因为每一层的失败模式和扩容方式不同：采集层怕上游断流（要重连），传输层怕下游太慢（要背压），存储层怕锁（要单写者），查询层怕慢查询（要限流）。分层让每个问题在层内解决，不传染。

线程划分是第一设计决策，原则只有一条：**阻塞 I/O 不进 CPU 线程池**。

| 线程 | 类型 | 干什么 | 为什么单独 |
| --- | --- | --- | --- |
| 采集线程（每源一个） | I/O | 拉流/收数据，推入队列 | 上游网络慢不能拖累别人 |
| 写盘线程（仅一条） | I/O | 从队列批量取数写 SQLite | SQLite 单写者，见 26.4 |
| 日志线程（仅一条） | I/O | 异步刷结构化日志 | 日志走磁盘，不能同步打 |
| CPU 线程池 | CPU | 规则计算、聚合、查询执行 | 计算密集，阻塞会饿死池 |
| 主线程 | — | 信号等待、健康检查 | 只做协调 |

> **坑：** 把 SQLite 写入或日志输出扔进 CPU 线程池是新手最常犯的架构错。一次 fsync 几毫秒到几十毫秒，池里 4 个线程全卡在磁盘上，告警计算就停摆了——而告警恰恰是最不能停的。
{: .sec-pit}

## 26.3 采集源选型与采集管道（对应原书 26.5）
{: .sec-prac}

### 采集源选型
{: .sec-know}

原书"选购监控卡"考察的是插卡参数，本篇对应的问题是采集源怎么选、怎么接：

| 采集源 | 数据形态 | 接入方式 | 典型频率 |
| --- | --- | --- | --- |
| RTSP/ONVIF 摄像头 | 音视频帧 | RTSP 拉流，FFmpeg 解码（第 25 篇管线直接复用） | 25 fps |
| 系统与业务指标 | 数值时间序列 | 服务暴露 /metrics，采集端定时来拉 | 15~60 秒一次 |
| 日志 | 文本/结构化行 | 文件 tail 或 syslog/UDP 接收 | 不定，突发每秒千行 |
| 事件/告警 | 离散记录 | SDK 写入或 HTTP 上报 | 事件驱动 |

选型判断只有两条：源能不能主动重连（网络抖动是常态，采集线程必须自带重连循环），数据能不能归一化成统一的事件结构（时间戳 + 类型 + 值 + 来源）。归一化做在采集层，后面四层全都省事。

### 采集管道：有界队列与背压
{: .sec-prac}

采集与存储之间用一条**有界队列**连接：队列满时生产者阻塞，这就是背压——下游消化不了，上游自动减速，内存占用被封死在队列容量以内。

```cpp
// pipeline.cpp —— 需要 -std=c++20
// 单生产者-单消费者 + 有界队列：队列满则生产者阻塞（背压）
#include <condition_variable>
#include <cstddef>
#include <cstdio>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

template <typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t cap) : cap_(cap) {}

    void push(T v) {
        std::unique_lock<std::mutex> lk(mtx_);
        not_full_.wait(lk, [this] { return q_.size() < cap_; });
        q_.push(std::move(v));
        not_empty_.notify_one();
    }

    T pop() {
        std::unique_lock<std::mutex> lk(mtx_);
        not_empty_.wait(lk, [this] { return !q_.empty(); });
        T v = std::move(q_.front());
        q_.pop();
        not_full_.notify_one();
        return v;
    }

private:
    std::mutex mtx_;
    std::condition_variable not_empty_, not_full_;
    std::queue<T> q_;
    std::size_t cap_;
};

int main() {
    BoundedQueue<int> q(4);          // 容量 4：消费慢时生产者会被顶住
    long long sum = 0;

    std::jthread producer([&] {
        for (int i = 1; i <= 100; ++i) q.push(i);
    });
    std::jthread consumer([&] {
        for (int i = 0; i < 100; ++i) sum += q.pop();
    });
    // jthread 析构自动 join：两个线程都跑完才继续
    std::printf("sum = %lld\n", sum);
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra pipeline.cpp -o pipeline && ./pipeline
```

```text
sum = 5050
```

生产者消费 1 到 100，队列封顶 4 条，结果与无界队列完全一致——背压只影响节奏，不影响正确性。

批量写发生在队列的存储侧：写盘线程不逐条落库，而是攒一批（比如 2000 条或 100 毫秒，先到者触发）再一次事务写入。批量的大小是延迟与吞吐的交换：批越大吞吐越高，但最坏落盘延迟也越大。

### 辨析：背压与降级
{: .sec-iv}

背压是让上游**减速**，数据一条不少；降级是主动**丢数据**保核心链路，比如日志量爆炸时按级别丢弃。监控服务里两者常配合：指标与告警链路永不降级（丢了就瞎），日志和低价值事件队列满时可以先丢再背压。把"丢"包装成"背压"是偷懒——背压的前提是下游最终能追上。

### 假共享：计数器分片
{: .sec-know}

多线程各自累加自己的计数器时，哪怕写的是不同变量，只要两个变量落在同一条缓存行（x86 常见 64 字节，Apple Silicon 是 128 字节），缓存一致性协议就会让两个核来回抢这条行——吞吐可能掉一个量级。规避手段是 `alignas(64)` 强制对齐，或者干脆每个线程一份计数、输出时再汇总（分片）。验证手段也简单：把两个计数器从相邻布局改成各自对齐 64 字节，压测前后对比吞吐即可。

> **坑：** 一上来就上无锁环形缓冲是过度设计。互斥量加条件变量的有界队列在中等吞吐（每秒几万条）下完全够用，先量出瓶颈再优化。
{: .sec-pit}

## 26.4 存储层：SQLite 落盘（对应原书 26.4）
{: .sec-prac}

### 为什么 SQLite 够用
{: .sec-know}

单机监控服务的写入量通常在每秒几百到几千条，SQLite 在 WAL 模式加批量事务下轻松扛住（下面实测）。它零部署、单文件、备份就是拷贝文件——运维成本几乎为零。什么时候不用它：写入超过每秒几万行、多机共享存储、需要按时间自动分块和分析聚合，那时换 TimescaleDB（26.4.5）。

### 四张表
{: .sec-know}

```sql
CREATE TABLE IF NOT EXISTS events (
    id    INTEGER PRIMARY KEY,           -- rowid 别名，自增
    ts    INTEGER NOT NULL,              -- Unix 秒，一律 UTC
    kind  TEXT    NOT NULL,              -- cpu / mem / disk / net / frame ...
    value REAL    NOT NULL,
    src   TEXT    NOT NULL DEFAULT ''    -- 来源标识
);
CREATE INDEX IF NOT EXISTS idx_events_kind_ts ON events(kind, ts);

CREATE TABLE IF NOT EXISTS segments (
    id       INTEGER PRIMARY KEY,
    path     TEXT    NOT NULL,           -- 录像/转储文件位置
    start_ts INTEGER NOT NULL,
    end_ts   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_segments_start ON segments(start_ts);

CREATE TABLE IF NOT EXISTS users (
    id       INTEGER PRIMARY KEY,
    name     TEXT NOT NULL UNIQUE,
    phc_hash TEXT NOT NULL,              -- PHC 格式哈希串，盐内嵌其中
    role     TEXT NOT NULL DEFAULT 'viewer',
    created  INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS alerts (
    id          INTEGER PRIMARY KEY,
    rule        TEXT    NOT NULL,
    state       TEXT    NOT NULL,        -- normal / pending / firing
    fired_at    INTEGER,
    resolved_at INTEGER
);
```

时间戳统一存 Unix 秒（UTC），这是整张库里最重要的约定——时区转换只在展示层做，库里出现任何"本地时间"都是事故源头。索引建在 `(kind, ts)` 复合列上而不是单列 ts：最常用的查询是"某类指标在某个时间段"，复合索引直接命中，单列 ts 索引对它帮助有限。

### 批量事务：快两个数量级的写法
{: .sec-ver}

SQLite 默认每条语句是一个自动提交事务，每次提交都要 fsync 一次 journal——单条插入慢就慢在这。把十万条包进一个事务，fsync 只发生一次：

```cpp
// sqlite_batch.cpp —— 需要 -std=c++20，链接 SQLite3 开发库
// Debian/Ubuntu: sudo apt install libsqlite3-dev
// macOS:         brew install sqlite3
#include <chrono>
#include <cstdio>
#include <cstdlib>
#include <random>
#include <sqlite3.h>

class Db {
public:
    explicit Db(const char* path) {
        if (sqlite3_open(path, &db_) != SQLITE_OK) {
            std::fprintf(stderr, "open failed: %s\n", sqlite3_errmsg(db_));
            std::exit(1);
        }
        exec("PRAGMA journal_mode=WAL");      // 读写不互斥
        exec("PRAGMA synchronous=NORMAL");    // WAL 下的推荐档位
        exec("PRAGMA busy_timeout=3000");     // 遇锁最多等 3 秒
        exec("CREATE TABLE IF NOT EXISTS events("
             "id INTEGER PRIMARY KEY, ts INTEGER NOT NULL,"
             "kind TEXT NOT NULL, value REAL NOT NULL)");
        exec("CREATE INDEX IF NOT EXISTS idx_events_kind_ts"
             " ON events(kind, ts)");
    }
    ~Db() { sqlite3_close(db_); }

    void exec(const char* sql) {
        char* err = nullptr;
        if (sqlite3_exec(db_, sql, nullptr, nullptr, &err) != SQLITE_OK) {
            std::fprintf(stderr, "exec failed: %s\n", err ? err : "?");
            sqlite3_free(err);
            std::exit(1);
        }
    }
    sqlite3* handle() const { return db_; }

private:
    sqlite3* db_ = nullptr;
};

int main() {
    Db db("events.db");
    sqlite3_stmt* st = nullptr;
    if (sqlite3_prepare_v2(db.handle(),
            "INSERT INTO events(ts, kind, value) VALUES(?, ?, ?)",
            -1, &st, nullptr) != SQLITE_OK) {
        std::fprintf(stderr, "prepare failed: %s\n", sqlite3_errmsg(db.handle()));
        return 1;
    }

    auto t0 = std::chrono::steady_clock::now();
    sqlite3_exec(db.handle(), "BEGIN", nullptr, nullptr, nullptr);
    std::mt19937 rng(42);
    std::uniform_real_distribution<double> dist(20.0, 80.0);
    for (int i = 0; i < 100000; ++i) {
        sqlite3_reset(st);
        sqlite3_bind_int64(st, 1,
            std::chrono::duration_cast<std::chrono::seconds>(
                std::chrono::system_clock::now().time_since_epoch()).count());
        sqlite3_bind_text(st, 2, "cpu", -1, SQLITE_STATIC);
        sqlite3_bind_double(st, 3, dist(rng));
        if (sqlite3_step(st) != SQLITE_DONE) {
            std::fprintf(stderr, "insert failed: %s\n",
                         sqlite3_errmsg(db.handle()));
            return 1;
        }
    }
    sqlite3_exec(db.handle(), "COMMIT", nullptr, nullptr, nullptr);

    auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
        std::chrono::steady_clock::now() - t0).count();
    std::printf("10 万条批量写入耗时 %lld ms\n", static_cast<long long>(ms));
    sqlite3_finalize(st);
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra sqlite_batch.cpp -o batch -lsqlite3 && ./batch
```

```text
10 万条批量写入耗时 270 ms
（NVMe SSD + WAL + synchronous=NORMAL 的普通笔记本量级；
把 BEGIN/COMMIT 两行删掉再跑，同一台机器通常要慢两个数量级）
```

预处理语句（`sqlite3_prepare_v2` + `sqlite3_bind_*`）一石二鸟：SQL 文本只编译一次，循环里只换参数；同时用户数据永远以参数身份进入，拼接 SQL 的注入路径被物理切断。任何把用户输入 `sprintf` 进 SQL 的写法都是红线。

### 轮转：时序数据的保留策略
{: .sec-know}

监控数据只增不删会把库撑爆，保留策略要在设计期定好。SQLite 没有原生分区，常用两招：按月分表（events_202610、events_202611，过期整表 DROP，代价几乎为零），或者单表定期 `DELETE FROM events WHERE ts < ?` 再择机 `VACUUM`（删除会留空洞，VACUUM 回收但要独占锁，放在业务低峰跑）。分表方案还顺带解决了"查询天然带时间范围"的裁剪问题。

### TimescaleDB 什么时候上
{: .sec-ext}

TimescaleDB 是 PostgreSQL 的时序扩展：`create_hypertable` 把大表按时间自动分块（chunk），查询按时间裁剪只扫相关块，配 retention policy 自动删过期数据，continuous aggregates 预先算好每分钟/每小时聚合。迁移信号：写入逼近每秒几万行、SQL 分析需求变多、或者要求数据库层面的高可用。PostgreSQL 生态换过去，SQL 几乎不用改写——这正是事件表坚持用标准 SQL 写法的原因。

> **坑：** 多线程写库配 `database is locked` 报错是组合拳。SQLite 默认编译成 serialized 模式，同一个连接跨线程用倒是安全的，只是内部互斥量把所有操作串行化了；真正的冲突在多个连接抢同一个库文件——而整个库同一时刻只允许一个写事务。正确姿势二选一：单写线程独占连接（本篇架构），或每线程独立连接加 busy_timeout。长事务是第三根引线——事务拉得越长，别的写者等得越久。
{: .sec-pit}

## 26.5 C++20 并发骨架（对应原书 26.6 的实现核心）
{: .sec-prac}

### 服务里的 jthread 与 stop_token
{: .sec-know}

第 25 篇讲过 `std::jthread` 析构自动 `request_stop` + `join`（C++20，`<thread>`/`<stop_token>`，GCC 10+/MSVC 19.28+ 起可用），这里补服务化的三条纪律。第一，检查点密度：每个外层循环每轮都要查 `st.stop_requested()`，一次重连尝试、一次批量写都算一轮——藏在三层循环深处的采集代码最容易漏。第二，阻塞点要可打断：普通 `condition_variable::wait` 对停止信号无感，`condition_variable_any::wait(lock, stop_token, pred)` 这个 C++20 重载会在停止信号到达时醒来（GCC 11+、MSVC 19.28+ 起可用；libc++ 落地偏晚，跨编译器项目用前确认）。第三，`std::stop_callback` 用来注册"停止时必须做"的清理动作，比在循环里散落判断干净。

同步原语三件套——`std::latch`（一次性倒计时）、`std::barrier`（可复用栅栏）、`std::counting_semaphore`（计数信号量，天然适合限流）也都是 C++20 的，`<latch>`/`<barrier>`/`<semaphore>` 三个头文件：

```cpp
// sync20.cpp —— 需要 -std=c++20（GCC 11+ / MSVC 19.28+）
#include <barrier>
#include <chrono>
#include <cstdio>
#include <latch>
#include <semaphore>
#include <thread>
#include <vector>

int main() {
    std::latch ready(3);                  // 三人各减一次，减到 0 放行 main
    std::barrier sync(3);                 // 三人到齐一起继续，可反复用
    std::counting_semaphore<3> slots(2);  // 最多两个并发槽位，第三个要等

    std::vector<std::jthread> workers;
    for (int i = 0; i < 3; ++i) {
        workers.emplace_back([&, i] {
            slots.acquire();              // 槽位满则阻塞：最朴素的限流
            std::printf("worker %d 进入\n", i);
            std::this_thread::sleep_for(std::chrono::milliseconds(50));
            ready.count_down();
            sync.arrive_and_wait();
            std::printf("worker %d 完成阶段任务\n", i);
            slots.release();
        });
    }
    ready.wait();
    std::puts("main: 三个 worker 全部进入工作状态");
    // workers 析构时逐个自动 join
}
```

```text
worker 1 进入
worker 0 进入
worker 2 进入
worker 0 完成阶段任务
main: 三个 worker 全部进入工作状态
worker 2 完成阶段任务
worker 1 完成阶段任务
（"完成阶段任务"与 main 一行的先后不固定：到达栅栏的先后取决于调度）
```

三个原语的分工：启动同步用 latch（用完即弃），阶段性齐步走用 barrier（反复同步），并发上限用 semaphore（本服务里限制同时打数据库的查询数就靠它）。

### 线程池：完整骨架
{: .sec-prac}

查询层的计算任务（规则判定、聚合、查询执行）没有线程专属需求，进通用池。骨架的关键点全在注释里：

```cpp
// thread_pool.cpp —— 需要 -std=c++20
#include <condition_variable>
#include <cstdio>
#include <functional>
#include <mutex>
#include <queue>
#include <stop_token>
#include <thread>
#include <vector>

class ThreadPool {
public:
    explicit ThreadPool(unsigned n) {
        for (unsigned i = 0; i < n; ++i) {
            workers_.emplace_back([this](std::stop_token st) {
                for (;;) {
                    std::function<void()> task;
                    {
                        std::unique_lock<std::mutex> lk(mtx_);
                        // 带 stop_token 的等待：任务到达或停止信号都会醒
                        cv_.wait(lk, st, [this] { return !tasks_.empty(); });
                        if (tasks_.empty()) return;  // 停止且队列已清空
                        task = std::move(tasks_.front());
                        tasks_.pop();
                    }
                    try {
                        task();
                    } catch (const std::exception& e) {
                        std::fprintf(stderr, "task threw: %s\n", e.what());
                    } catch (...) {
                        std::fprintf(stderr, "task threw unknown exception\n");
                    }
                }
            });
        }
    }

    void submit(std::function<void()> f) {
        {
            std::lock_guard<std::mutex> lk(mtx_);
            tasks_.push(std::move(f));
        }
        cv_.notify_one();
    }

    ~ThreadPool() {
        for (auto& w : workers_) w.request_stop();  // jthread 析构再自动 join
    }

private:
    std::mutex mtx_;                       // 声明顺序即销毁顺序的反序：
    std::condition_variable_any cv_;       // workers_ 最先析构（join），
    std::queue<std::function<void()>> tasks_;  // 此时锁与队列仍然健在
    std::vector<std::jthread> workers_;
};

int main() {
    ThreadPool pool(4);
    for (int i = 1; i <= 8; ++i) {
        pool.submit([i] { std::printf("task %d done\n", i); });
    }
    // 析构：先 request_stop，已入队任务仍会执行完，再逐个 join
}
```

```text
task 2 done
task 1 done
task 4 done
task 3 done
task 5 done
task 7 done
task 6 done
task 8 done
（顺序不固定：4 个工作线程并发消费）
```

骨架里三个容易看漏的点：成员声明顺序决定销毁顺序，`workers_` 必须最后声明，否则 join 时锁已销毁，直接 UB；停止策略是"排空再退"——队列里已提交的任务会执行完，析构之后不得再 submit（生产实现可加一个原子标志位拒绝）；任务在池内统一 try/catch，异常穿出线程入口就是 `std::terminate`。

### 辨析：std::async 与线程池
{: .sec-iv}

`std::async(std::launch::async, ...)` 每次调用起一个新线程，返回的 `future` 析构时会**阻塞等待任务完成**——这是最常被忽略的一条，循环里随手接返回值会悄悄串行化。它没有取消机制（没有 stop_token 的对应物）、线程不复用，高频提交会线程爆炸。它的用武之地是一次性并行计算：把数组切四块并行求和。常驻服务里持续到达的工作负载，正确归宿是线程池。

### atomic::wait 与 C++26 展望
{: .sec-ext}

C++20 给 `std::atomic` 加了 `wait(old)` 与 `notify_one/notify_all`：原子值仍等于 `old` 时阻塞，别的线程改值后调 notify 叫醒。适合"等一个标志位翻转"的单值等待，免掉互斥量；等不了"队列非空"这类复合谓词，那种还是 condvar。各标准库落地时间不一，跨编译器项目用前查支持表。再往前看，C++26 已纳入 `std::execution`（sender/receiver，源自 P2300），把"提交任务、组合依赖、管理执行资源"统一成可组合的模型——线程池大概率是它的第一种落地形态，值得保持关注。

> **坑：** `pool.submit([&] { use(local); })` 里的 `&` 是定时炸弹：捕获的是局部变量引用，任务入队后当前作用域随时可能退出，工作线程拿到的是悬垂引用，崩溃点位随机。跨线程提交一律按值捕获，需要共享大对象就 `shared_ptr` 持有——写过异步回调的人都懂这条的代价。
{: .sec-pit}

### 路由与 RBAC 骨架
{: .sec-prac}

socket 收发交给任意 HTTP 库，这里把最能体现设计的路由与鉴权层做成完整可编译的程序：

```cpp
// http_api.cpp —— 需要 -std=c++20
// 只演示路由与鉴权分层；socket 层交给任意 HTTP 库（cpp-httplib、Boost.Beast 等）
#include <cstdio>
#include <map>
#include <string>
#include <string_view>

struct Request {
    std::string method;
    std::string path;
    std::string token;   // 从 Authorization: Bearer <token> 解出
};

struct Response {
    int status = 200;
    std::string body;
};

enum class Role { Viewer, Operator, Admin };   // 权限从低到高

struct Session {
    std::string user;
    Role role;
};

bool lookup_session(std::string_view token, Session& out) {
    // 生产实现：会话存内存或 Redis，带过期时间；这里用静态表方便演示
    static const std::map<std::string, Session, std::less<>> sessions{
        {"tok-alice", {"alice", Role::Admin}},
        {"tok-bob",   {"bob",   Role::Viewer}},
    };
    auto it = sessions.find(token);            // 透明比较器：string_view 直接查
    if (it == sessions.end()) return false;
    out = it->second;
    return true;
}

bool has_role(const Session& s, Role need) {
    return static_cast<int>(s.role) >= static_cast<int>(need);
}

Response handle(const Request& req) {
    Session s;
    if (!lookup_session(req.token, s))
        return {401, R"({"error":"unauthorized"})"};

    if (req.method == "GET" && req.path == "/api/events")
        return {200, R"({"events":[{"id":1,"kind":"cpu","value":87.5}]})"};

    if (req.method == "GET" && req.path == "/api/stream")
        return {200, R"({"stream":"sse","interval_ms":1000})"};

    if (req.method == "GET" && req.path == "/api/replay") {
        if (!has_role(s, Role::Operator))      // 回放导出要 Operator 及以上
            return {403, R"({"error":"forbidden"})"};
        return {200, R"({"segment":"seg-01","from_ts":1769472000})"};
    }

    return {404, R"({"error":"not found"})"};
}

int main() {
    for (const Request& r : {
             Request{"GET", "/api/events", "tok-bob"},
             Request{"GET", "/api/replay", "tok-bob"},
             Request{"GET", "/api/replay", "tok-alice"},
             Request{"GET", "/api/events", "bad-token"},
         }) {
        Response resp = handle(r);
        std::printf("%s %s -> %d %s\n", r.method.c_str(), r.path.c_str(),
                    resp.status, resp.body.c_str());
    }
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra http_api.cpp -o api && ./api
```

```text
GET /api/events -> 200 {"events":[{"id":1,"kind":"cpu","value":87.5}]}
GET /api/replay -> 403 {"error":"forbidden"}
GET /api/replay -> 200 {"segment":"seg-01","from_ts":1769472000}
GET /api/events -> 401 {"error":"unauthorized"}
```

RBAC 三个角色的边界要落在数据操作上：Viewer 只读实时数据，Operator 能触发回放导出与确认告警，Admin 管用户与规则。判断只用一个 `has_role`，等级比较让"新增一个角色"不牵动任何端点代码。

## 26.7 管理员登录模块（对应原书 26.7）
{: .sec-know}

### 登录流程
{: .sec-know}

| 步骤 | 动作 | 失败处理 |
| --- | --- | --- |
| 1 | 限速检查：同 IP 15 分钟内失败超 5 次直接拒绝 | 返回 429，不查库 |
| 2 | 按 name 查 users 取 phc_hash | 用户不存在也跑一遍哈希验证，耗时对齐 |
| 3 | argon2id 验证密码 | 写审计日志，失败计数 +1 |
| 4 | 生成 128 位随机 token，服务端存会话与过期时间 | — |
| 5 | 返回 token，后续请求带 Authorization: Bearer | — |

第 2 步的"耗时对齐"防的是用户名枚举：如果用户不存在就直接返回，攻击者靠响应时间差就能筛出有效用户名——查无此人也走一遍哈希计算，两条路径耗时一致。登录接口永远只说"用户名或密码错误"，不给额外提示。

### 密码怎么存：哈希与盐
{: .sec-best}

密码用 argon2id（内存难解，抗 GPU 暴力破解；bcrypt 亦可接受），存成 PHC 标准格式的字符串，盐内嵌其中：

```text
argon2id$v=19$m=65536,t=3,p=1$<base64盐>$<base64哈希>
```

盐每个用户独立随机生成，哈希随盐一起入库——不需要单独的盐表。验证时用库的 verify 函数做**常量时间比较**，杜绝时序侧信道。三条红线：绝不明文存储；绝不用 MD5/SHA 系裸哈希（它们太快，正是为哈希大文件设计的）；绝不自己发明哈希方案。登录成功后的 token 用密码学安全随机源生成（Linux 上 `getrandom`，Windows 上 `BCryptGenRandom`），别拿 `std::mt19937` 凑数——它可预测。

### 失败限速与审计日志
{: .sec-know}

限速的最小实现是每 IP 一个滑动窗口：`std::map<ip, std::deque<时间戳>>`，检查前先弹出窗口外的旧记录，窗口内失败次数超阈值就锁 15 分钟。锁定期满自动解锁，不做永久封禁（封 IP 会误伤出口 NAT 后的一整栋楼）。

审计日志用结构化 JSON 行，人能读、机器也能 ingest：

```text
{"ts":"2026-11-02T08:30:11Z","level":"info","event":"login","user":"alice","ip":"10.0.0.8","result":"ok"}
{"ts":"2026-11-02T08:30:19Z","level":"warn","event":"login","user":"root","ip":"203.0.113.7","result":"fail","reason":"bad_password"}
```

审计日志与业务日志分开落文件、只追加不修改，登录成功失败各记一条——事后追溯"谁在什么时候动过系统"全靠它。

## 26.8 告警模块（对应原书 26.9 广角自动监控）
{: .sec-prac}

### 规则引擎与滑动窗口
{: .sec-know}

原书"广角自动监控"的内核是"无人值守、条件满足自动动作"，本篇把它落成规则引擎。一条规则五要素：指标名、比较算子、阈值、滑动窗口、持续点数。滑动窗口用 `std::deque` 维护最近 N 个采样，超阈值点数连续达到 K 个才动作——这就是去抖，专治毛刺：CPU 一次冲到 90% 又立刻回落，是正常调度波动，不该叫醒任何人。

### 告警状态机
{: .sec-prac}

状态机四个状态走完整生命周期：Normal 无事；Pending 预警（接近触发，去抖中）；Firing 告警已发；恢复需连续 M 个正常点，防阈值附近来回横跳把人烦死。Firing 期间不重复发通知，这就是抑制：

```cpp
// alert_fsm.cpp —— 需要 -std=c++20
// 规则：CPU > 80 连续 3 点触发；恢复需连续 5 点正常；Firing 期间抑制重复通知
#include <cstdio>
#include <vector>

enum class St { Normal, Pending, Firing };

int main() {
    const int kThreshold = 80;   // 阈值（%）
    const int kNeedBreach = 3;   // 连续 3 个采样点超阈值才升级
    const int kNeedOk    = 5;    // 连续 5 个采样点正常才恢复

    std::vector<int> samples{85, 90, 88, 70, 82, 60, 55, 50, 45, 40};
    St st = St::Normal;
    int breach = 0, ok = 0;

    for (int v : samples) {
        if (v > kThreshold) { ++breach; ok = 0; }
        else                { ++ok; breach = 0; }

        switch (st) {
        case St::Normal:
            if (breach >= kNeedBreach) {
                st = St::Firing;
                std::printf("cpu=%d 触发告警（Firing）\n", v);
            } else if (breach == kNeedBreach - 1) {
                st = St::Pending;
                std::printf("cpu=%d 进入预警（Pending）\n", v);
            }
            break;
        case St::Pending:
            if (breach >= kNeedBreach) {
                st = St::Firing;
                std::printf("cpu=%d 触发告警（Firing）\n", v);
            } else if (breach == 0) {
                st = St::Normal;             // 毛刺结束，静默回落
            }
            break;
        case St::Firing:
            if (ok >= kNeedOk) {
                st = St::Normal;
                std::printf("cpu=%d 告警恢复（Normal）\n", v);
            }
            break;                            // 其余情况：抑制，不重发
        }
    }
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra alert_fsm.cpp -o alert && ./alert
```

```text
cpu=90 进入预警（Pending）
cpu=88 触发告警（Firing）
cpu=40 告警恢复（Normal）
```

去抖门槛体现在前三个点：85、90 两点不够，第三点 88 才升级；82 在 Firing 期间再次超阈，被抑制吞掉（没有产生第二条通知）；恢复要连续 5 个正常点，60 到 45 攒了四个，第 40 个点才凑满放行。状态每次迁移写回 alerts 表，fired_at、resolved_at 留痕，回放页面才能画出完整告警时间线。

### 辨析：去抖与抑制
{: .sec-iv}

去抖发生在**触发前**：条件不够持续就当没看见，防误报；抑制发生在**触发后**：告警已发出，持续期间不再重复轰炸，防骚扰。两者常被混为一谈，后果是参数调反——把抑制时长当去抖点数用，告警要等几分钟才响，错过处置窗口。

> **坑：** 告警风暴的典型剧本：数据库挂了，所有依赖它的规则同时触发，200 条通知一分钟内打爆值班手机。解法是抑制链——根因告警（数据库不可达）触发时，自动抑制它下游的派生告警；再加全局限速（每分钟最多 N 条），宁可少报也别把通知渠道打成哑巴。
{: .sec-pit}

## 26.9 历史回放（对应原书 26.10 视频回放）
{: .sec-know}

### 时间范围查询与段索引
{: .sec-know}

回放的数据模型是 segments 段表：每段存储文件有起止时间戳，seek 就是"时间 → 段 → 文件内偏移"三级定位：

```sql
-- 事件回放：先按复合索引过滤，LIMIT 兜底防大范围拖库
SELECT ts, kind, value FROM events
WHERE kind = :kind AND ts BETWEEN :from AND :to
ORDER BY ts LIMIT 1000;

-- 视频回放：找与时间区间有交集的所有段
SELECT id, path, start_ts, end_ts FROM segments
WHERE start_ts <= :to AND end_ts >= :from
ORDER BY start_ts;
```

第二条查询用 `idx_segments_start` 走范围扫描，段表有序所以很快；定位到段之后，文件内再找目标时间之前最近的关键帧（I 帧），从它开始解码——GOP 成本的分析在第 25 篇讲透了，直接复用。

### 倍速与 seek 的实现要点
{: .sec-know}

倍速的本质是让"数据供给节奏"跟上"播放节拍"：1x 时解码供给与显示按原始时间轴走，4x 时供给提速四倍、显示端按 PTS 间隔缩到四分之一。音频升调问题交给重采样（如 FFmpeg 的 atempo 滤镜）处理。seek 后必须清空旧缓冲、重置时钟基准，否则画面会先快进一段旧数据——第 25 篇播放器状态机里的 Seeking 状态就是为它准备的。

> **坑：** "回放出来整体偏移 8 小时"九成是时区：库里存了本地时间字符串，换个时区的机器就错位。铁律重申一遍——存储层只有 UTC epoch 秒，转换只发生在展示层。第二个常见坑是回放查询不带 LIMIT：用户拖一根"查全年"的滑杆，几十万行直接把连接和前端一起拖死。
{: .sec-pit}

## 26.10 展示层与"绚丽界面"（对应原书 26.3 系统预览与 26.11）
{: .sec-expl}

### 为什么 C++ 只做后端更划算
{: .sec-know}

原书用 MFC 自绘界面控件凑"绚丽"，这条路今天性价比极低：MFC 生态停滞、跨平台为零、做一张像样的图表要从画素点开始。现代做法是 C++ 只写后端（采集、存储、API），界面交给 Web 前端——HTML/CSS/JS 的图表生态（ECharts 等）成熟到开箱即用，改版不需要重编译后端，浏览器天然跨平台。什么时候例外：嵌入式设备没有浏览器运行环境，或者桌面应用需要深度系统集成（全局快捷键、托盘、多窗口精密控制），那时 Qt 是正解，且只把"壳"用 Qt 写，数据仍走本地 API。

### 绚丽的现代定义
{: .sec-know}

值班室盯屏八小时，界面好坏的标准是信息密度与长时间观看舒适度，三件事最值钱：

| 要点 | 动机 | 实现手段 |
| --- | --- | --- |
| 暗色主题 | 暗环境久盯不刺眼，告警红色对比度更突出 | CSS 变量统一色板，跟随系统偏好 |
| 虚拟列表 | 事件表几十万行，全量渲染 DOM 直接卡死 | 只渲染可视区 ± 缓冲的几十行，滚动换内容 |
| 图表流式刷新 | 整页轮询延迟大、闪烁 | SSE 推增量，前端只画新点，降频到人类感知极限即可 |

虚拟列表是其中最容易低估的：DOM 节点超过几千个，滚动帧率肉眼可见地掉；虚拟化后无论十万行还是百万行，DOM 数量恒定在几十。图表同理，一屏固定只保留最近 N 个点，新点进、旧点出。

## 26.11 可观测性：服务自己也要被监控
{: .sec-prac}

### 指标、日志、追踪
{: .sec-know}

监控服务自己先得透明。三大件分工：指标回答"现在健康吗"（数值，低成本聚合），日志回答"刚才发生了什么"（文本，按条检索），追踪回答"一次请求的时间花在哪"（span 树）。指标暴露 Prometheus 文本格式，日志用 26.7 那样的 JSON 行异步落盘，追踪给每个 API 请求生成 trace_id 贯穿"进路由 → 查库 → 回包"全程，跨服务时通过 HTTP 头传递。

### 辨析：counter 与 gauge
{: .sec-iv}

counter 只增不减（事件总数、告警次数），看的是速率，图上画的是 `rate()`；gauge 可升可降（队列水位、连接数），看的是瞬时值，图上画的是原始值。把队列水位存成 counter 再去 rate，出来的曲线毫无意义——选错类型是自研指标最常见的错误。

### 指标暴露的最小实现
{: .sec-prac}

```cpp
// metrics.cpp —— 需要 -std=c++20
// Prometheus 文本暴露格式（text/plain; version=0.0.4）的最小实现
#include <atomic>
#include <cstdio>
#include <memory>
#include <mutex>
#include <string>
#include <vector>

class Metrics {
public:
    static Metrics& instance() {
        static Metrics m;   // C++11 起静态局部变量初始化线程安全
        return m;
    }

    void add_counter(std::string name, std::string help) {
        std::lock_guard<std::mutex> lk(mtx_);
        counters_.push_back(
            std::make_unique<Counter>(std::move(name), std::move(help)));
    }

    void inc(const std::string& name, long long v = 1) {
        std::lock_guard<std::mutex> lk(mtx_);
        for (const auto& c : counters_)
            if (c->name == name) {
                c->value.fetch_add(v, std::memory_order_relaxed);
                return;
            }
    }

    std::string render() const {
        std::lock_guard<std::mutex> lk(mtx_);
        std::string out;
        for (const auto& c : counters_) {
            out += "# HELP " + c->name + " " + c->help + "\n";
            out += "# TYPE " + c->name + " counter\n";
            out += c->name + " "
                 + std::to_string(c->value.load(std::memory_order_relaxed))
                 + "\n";
        }
        return out;
    }

private:
    struct Counter {
        std::string name;
        std::string help;
        std::atomic<long long> value{0};
        Counter(std::string n, std::string h)
            : name(std::move(n)), help(std::move(h)) {}
    };
    mutable std::mutex mtx_;
    std::vector<std::unique_ptr<Counter>> counters_;  // atomic 不可拷贝，
                                                      // 用指针避开 vector 扩容移动
};

int main() {
    auto& m = Metrics::instance();
    m.add_counter("obs_events_total", "收到的采集事件总数");
    m.add_counter("obs_alerts_fired_total", "触发的告警总数");
    for (int i = 0; i < 1200; ++i) m.inc("obs_events_total");
    m.inc("obs_alerts_fired_total", 3);
    std::fputs(m.render().c_str(), stdout);
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra metrics.cpp -o metrics && ./metrics
```

```text
# HELP obs_events_total 收到的采集事件总数
# TYPE obs_events_total counter
obs_events_total 1200
# HELP obs_alerts_fired_total 触发的告警总数
# TYPE obs_alerts_fired_total counter
obs_alerts_fired_total 3
```

`/metrics` 端点直接返回这段文本，Prometheus 定时来拉，Grafana 配图即可——自研监控不用自己写图表轮子。高频累加走 `atomic::fetch_add`（relaxed 序足够，计数器不需要跨变量的顺序保证），注册表查询才动互斥量，热点与冷点分开。

### 优雅退出与部署
{: .sec-prac}

systemd 停服务发 SIGTERM，进程要在时限内做完收尾——停采集、刷队列、关库。C++11 起，信号处理函数里操作**无锁**（lock-free）的原子变量就是有正式定义的行为（`is_lock_free()` 为 true 的对象都可以）：

```cpp
// graceful.cpp —— 需要 -std=c++20
#include <atomic>
#include <chrono>
#include <csignal>
#include <cstdio>
#include <thread>

std::atomic<bool> g_stop{false};

extern "C" void on_term(int) { g_stop.store(true, std::memory_order_relaxed); }

int main() {
    std::signal(SIGTERM, on_term);
    std::signal(SIGINT, on_term);
    while (!g_stop.load(std::memory_order_relaxed)) {
        std::this_thread::sleep_for(std::chrono::milliseconds(200));
    }
    std::puts("收到 SIGTERM，开始收尾：停采集、刷盘、关库");
}
```

```bash
g++ -std=c++20 -O2 -Wall -Wextra graceful.cpp -o graceful
./graceful & sleep 1; kill -TERM $!; wait $!
```

```text
收到 SIGTERM，开始收尾：停采集、刷盘、关库
```

处理函数里只置标志，收尾动作全部回到主流程做——信号处理函数里调 printf 以外的任何复杂函数都可能踩重入问题。健康检查端点 /healthz 除了返回 200，顺手检查 SQLite 连接可打开、采集队列水位未满，把"活着"和"能干活"区分开。

### 安全三件事
{: .sec-best}

## 常见坑速查
{: .sec-ts}

| 坑 | 症状 | 规避 |
| --- | --- | --- |
| 任务捕获悬垂引用 | 工作线程读了已析构对象，崩溃点位随机 | 按值捕获；共享大对象用 shared_ptr 持有 |
| 长循环缺 stop 检查点 | 退出时卡在 join 不动 | 每层外循环查 stop_requested，阻塞点用可打断等待 |
| SQLite 多线程写 | database is locked 反复出现 | 单写线程，或每线程独立连接 + busy_timeout |

## 变式追问
{: .sec-think}

**问：为什么写盘线程只开一条，反而比多条更快？**

答：SQLite 的并发模型是单写者——同一时刻整个库只允许一个写事务，开四条写线程等于四个人排队用一个窗口，还得额外付出锁等待与 busy_timeout 重试的代价。WAL 解决的是"写不阻塞读"，不是"多个写并行"。所以正确架构是把写收敛成一条线程、用队列喂它，扩展性交给批量事务的吞吐提升，而不是线程数。

**问：stop_token 检查点应该加多密？卡在条件变量上的线程怎么停？**

答：粗粒度看，每个"可能耗时超过几百毫秒"的操作边界都要有检查点：一次重连尝试前后、一批写入前后。密到每条循环也不划算——检查本身近乎免费，但把一个原子写拆成十几处会让代码难读。卡在 condvar 上的线程不能靠轮询救，必须用带 stop_token 的 wait 重载（本篇线程池的做法），或者停止时由别线程 notify_all 把它叫醒再检查。判断标准一句话：任何一个阻塞点，都要保证停止信号到达后能在可接受时间内醒来。

**问：有人提议 /metrics 也要鉴权，说指标泄露系统信息。你怎么权衡？**

答：指标确实会泄露拓扑（路径名、标签里的主机名、QPS 规模），但有鉴权的 /metrics 会让 Prometheus 抓取配置复杂化（要配 token）。主流做法是网络隔离：/metrics 只绑内网网卡或防火墙白名单，应用层不做鉴权。如果合规要求应用层防线，用独立的 scrape token 而不是复用用户会话——监控凭据和用户身份分开，审计时才分得清"是采集端在拉"还是"有人在看"。

**问：如果事件量涨 100 倍，这套架构先在哪里裂开？**

答：按顺序裂。第一道裂缝是 SQLite 单写线程——每秒几万行的批量写入封顶后，队列水位持续走高，背压反压采集层。第二道是单机磁盘顺序写带宽与查询扫描量。解法不是调参而是换件：存储换 TimescaleDB（自动分块 + 分布式扩展），热点写入前面加一层缓冲队列（Kafka 类），查询按时间分片路由。采集层与告警层的代码几乎不动——这正是分层架构在 26.2 就定下来的回报：换一层，不动五层。
