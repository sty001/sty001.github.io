## 12.1 类
{: .sec-expl}

### 12.1.1 struct 与 class：唯一差别在两个"默认值"
{: .sec-know}

C++ 留了两个关键字给类类型，语法能力完全一样，差别只有两条，全在"默认"上：

| 关键字 | 成员默认访问权限 | 默认继承方式 |
| --- | --- | --- |
| `struct` | public | public |
| `class` | private | private |

```cpp
// 需要 -std=c++20
#include <iostream>

struct SBase { int x = 1; };              // struct：成员默认 public
class CClass { public: int x = 1; };      // class：成员默认 private，这里显式放开

struct SDerived : CClass {};              // struct 默认 public 继承
class CDerived : SBase {};                // class 默认 private 继承

int main() {
    SBase s;
    s.x = 10;                             // struct 成员默认 public：直接可访问
    SDerived sd;
    sd.x = 20;                            // public 继承：基类的 public 成员仍是 public
    CDerived cd;
    // cd.x = 30;   // 编译错误：'int SBase::x' is private within this context
    //                private 继承把 SBase::x 压成了 CDerived 的 private
    std::cout << s.x + sd.x << ' ' << sizeof(cd) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
30 4
```

两条使用建议：只想打包数据、不打算维护不变量（聚合、POD 风格）就用 struct；一旦有了私有成员和成员函数，用 class，让"访问控制是有意设计的"这件事在关键字上就能看出来。私有继承是个冷门工具（想复用实现但不暴露"是一个"关系），见到 `class D : private B` 先怀疑是不是写错了关键字。

两个冷知识：一是前向声明和定义可以混用两个关键字，`struct X;` 之后 `class X { ... };` 合法，它们指同一个类；二是 `enum class` 和 `enum struct` 都合法且等价（C++11），模板形参只能写 `class` 或 `typename` 不能写 `struct`——出了"类类型定义"这个语境，两个关键字的能力就有区别了，但那不属于本节的类定义范畴。

### 12.1.2 访问控制：封装保护的是不变量，不是数据
{: .sec-know}

把成员设成 private 的目的不是"藏数据防偷看"，而是**让非法状态无法被构造出来**。一个类总有它必须时刻成立的条件（余额不为负、下标在界内、指针指向有效内存），这些条件叫**不变量**。public 数据成员等于宣告"本类没有不变量"——任何人随时可以把 `balance` 改成 `-999`，之后所有成员函数都得在崩溃的边缘做防御。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <stdexcept>

class Account {
    long cents_;                       // 单位用"分"，顺便躲开浮点误差
public:
    explicit Account(long cents) : cents_(cents) {
        if (cents < 0) throw std::invalid_argument("negative initial balance");
    }
    void deposit(long c) {
        if (c <= 0) return;            // 不给"余额变负"留任何门
        cents_ += c;
    }
    bool withdraw(long c) {
        if (c <= 0 || c > cents_) return false;
        cents_ -= c;
        return true;
    }
    long balance() const { return cents_; }
};

int main() {
    Account a(100);
    a.deposit(50);
    std::cout << a.withdraw(200) << ' ' << a.balance() << '\n';   // 0 150
    // a.cents_ = -999;   // 编译错误：cents_ 是 private——不变量没法被绕过
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text

```

这里有个坑：很多人把 private 当成"隐私保护"，于是大量写 `get_x()`/`set_x()`，访问控制和全 public 没有本质区别。判断标准是：如果 setter 只是一行赋值，说明这个成员根本不需要 setter，要么它由构造函数一次性定死，要么它该通过"维护不变量的语义操作"（`deposit`/`withdraw`）来修改。

> **注意：** `explicit` 挡住的是"用一个值悄悄变出一个对象"。没有 explicit 时 `Account a = 100;` 也合法，函数形参、返回值、比较表达式里都会发生这种隐式构造，几乎总不是你想要的。单参数构造函数默认写 explicit，确认需要隐式转换时再去掉。
{: .sec-best}

### 12.1.3 成员函数与 this
{: .sec-know}

成员函数编译后本质上是一个普通函数：`t.size()` 大致等价于 `size(&t)`，那个隐藏的指针就是 `this`。在 `T` 的非 const 成员函数里，`this` 的类型是 `T*`；在 const 成员函数里，`this` 的类型是 `const T*`——这就是"const 成员函数不能修改成员"的底层机制：编译器把所有成员访问都强制经过了 const 指针。

```cpp
// 需要 -std=c++20
#include <cctype>
#include <iostream>
#include <string>
#include <string_view>

class Text {
    std::string data_;
public:
    explicit Text(std::string d) : data_(std::move(d)) {}

    Text& append(std::string_view s) {      // 返回 *this，就能链式调用
        data_ += s;
        return *this;
    }
    Text& to_upper() {
        for (char& c : data_)
            c = static_cast<char>(std::toupper(static_cast<unsigned char>(c)));
        return *this;
    }
    std::size_t size() const {              // const 成员函数：this 是 const Text*
        return data_.size();
        // data_ += "x";   // 编译错误：const 成员函数里 this 是 const Text*
    }
    const std::string& str() const { return data_; }
};

int main() {
    Text t("hello");
    t.append(", ").append("world").to_upper();    // 链式：每一步返回的都是 t 自己
    std::cout << t.str() << ' ' << t.size() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```


链式 API 的返回类型有讲究：可变链返回 `Text&`（改自己）；只读链可以返回 `const Text&`；如果对象是只移动的，C++11 起可以返回 `Text`（值），让链在临时对象上也能续下去。返回 `*this` 的拷贝而不自知是常见错误——每一步都在改一个临时副本，最后一看什么都没变。

> **现代拓展：** const 与非 const 两个成员函数版本代码几乎重复，C++23 的显式对象形参（deducing this，P0847）允许写成 `std::size_t size(this const Text& self) { return self.data_.size(); }`——一份定义同时覆盖 const/非 const、左值/右值调用，编译器按调用者的实际类型推导 `self`。
{: .sec-ext}

### 辨析：const 对象、const 成员函数与 mutable
{: .sec-iv}

const 对象只能调 const 成员函数，这是编译器保证"逻辑只读"的关口。但"逻辑只读"不等于"一个字节都不动"：缓存、计数、锁这些实现细节改了也不影响对外观察到的状态，把它们标成 `mutable`，const 成员函数里就能改。判断标准只有一条——改了之后，站在类外面的观察者角度，对象的行为有没有变化。有变化就不许 mutable。12.2.2 有完整示例。

### 12.1.4 构造函数家族
{: .sec-know}

构造函数不是一种函数，是一族重载。C++20 里你需要分清这几种：

| 种类 | 形态 | 说明 |
| --- | --- | --- |
| 默认构造 | `T()` | 无参调用；没写任何构造函数时编译器生成 |
| 带参构造 | `T(int, double)` | 常规重载 |
| 拷贝构造 | `T(const T&)` | 用同类型对象造新对象 |
| 移动构造 | `T(T&&) noexcept` | C++11，"偷"右值的资源 |
| 委托构造 | `T() : T(args) {}` | C++11，转调同类的另一个构造函数 |
| 转换构造 | 单参数、非 explicit | 允许隐式转换，需要警惕 |

```cpp
// 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <string>
#include <utility>

class Buf {
    std::string tag_;
    int* data_ = nullptr;
    std::size_t n_ = 0;
public:
    Buf() : Buf("empty", 0) {}                       // 委托构造（C++11）
    Buf(std::string tag, std::size_t n)              // 带参构造
        : tag_(std::move(tag)), data_(n ? new int[n]{} : nullptr), n_(n) {}
    Buf(const Buf& other)                            // 拷贝构造：深拷贝
        : tag_(other.tag_ + ".copy"), data_(other.n_ ? new int[other.n_] : nullptr),
          n_(other.n_) {
        if (n_) std::copy(other.data_, other.data_ + n_, data_);
    }
    Buf(Buf&& other) noexcept                        // 移动构造（C++11）：接管资源
        : tag_(std::move(other.tag_)), data_(std::exchange(other.data_, nullptr)),
          n_(std::exchange(other.n_, 0)) {}
    ~Buf() { delete[] data_; }                       // 赋值两个兄弟见 12.3.1

    const std::string& tag() const { return tag_; }
};

class Watt {
    double v_;
public:
    explicit Watt(double v) : v_(v) {}               // explicit：挡住单参隐式转换
    double value() const { return v_; }
};

double half(const Watt& w) { return w.value() / 2; }

int main() {
    Buf a("log", 4);
    Buf c = a;                    // 拷贝构造
    Buf d = std::move(c);         // 移动构造：c 之后只可赋新值或析构
    Buf e;                        // 委托到 ("empty", 0)
    std::cout << c.tag().empty() << ' ' << d.tag() << ' ' << e.tag() << '\n';

    Watt w(3.0);
    // Watt w2 = 3.0;             // 编译错误：explicit 挡住 double -> Watt
    // half(3.0);                 // 同样编译错误——没有 explicit 时这里会静默构造
    std::cout << half(w) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

单参数隐式转换的灾难长这样：一个 `File(const std::string&)` 没加 explicit，某天手滑写出 `open_file(42)`，编译器不报错，它兴高采烈地把 42 转成 string（那是字符 42 对应的字节）再去开文件。转换构造只应该在"数学上说得通"的场景开放（比如 `Fraction` 从 `int` 构造），其余一律 explicit。C++11 起 explicit 也能修饰多参数构造函数，挡住 `f({1, 2})` 这类花括号隐式转换。

> **坑：** 委托构造函数的初始化列表里只允许出现对另一个构造函数的委托，不能再写 `: T(x), member_(y)` 这种混搭——成员初始化全权交给被委托的那个构造函数。写了混搭直接编译错误。
{: .sec-pit}

### 12.1.5 初始化列表 vs 体内赋值
{: .sec-know}

构造函数体开始执行之前，所有成员必须已经"出生"——要么被初始化列表初始化，要么被默认初始化。初始化列表是**直接初始化**，函数体里的赋值是"先默认构造再赋值"，两码事。三类成员**只能**用初始化列表：

| 成员 | 为什么体内赋值不行 |
| --- | --- |
| const 成员 | const 只能初始化不能赋值 |
| 引用成员 | 引用只能绑定不能改绑 |
| 无默认构造的成员 | 函数体执行前它已经被"默认构造"过一次并失败 |

```cpp
// 需要 -std=c++20
#include <iostream>

class Inner {
public:
    explicit Inner(int v) : v_(v) {}
    int v_;
};

class Outer {
    int a_;
    int b_;
    const int id_;
    Inner in_;
public:
    Outer(int a, int b)
        : b_(b), a_(a), id_(7), in_(a) {}   // 故意乱序写：实际仍按声明顺序初始化
    void print() const {
        std::cout << a_ << ' ' << b_ << ' ' << id_ << ' ' << in_.v_ << '\n';
    }
};

int main() {
    Outer o(1, 2);
    o.print();
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo
```

程序能跑、结果也对（`1 2 7 1`），但 `-Wextra` 的 `-Wreorder` 告警了：**成员永远按声明顺序初始化**，列表里写什么顺序都没用。这个坑在成员之间有依赖时爆炸——比如 `n_` 在声明上排在 `data_` 之后，列表里却先写 `data_(new int[n_])`，此时 `n_` 还是垃圾值。规则：声明顺序和列表顺序保持一致，列表顺序写成声明的镜像。

```cpp
// 需要 -std=c++20
#include <cstdint>
#include <iostream>
#include <string>

class Session {
    const std::uint64_t id_;         // const 成员：只能初始化
    std::string& log_;               // 引用成员：只能绑定
public:
    Session(std::uint64_t id, std::string& log) : id_(id), log_(log) {}
    void ping() { log_ += "ping;"; }
};

class Config {
    int retries_ = 3;                // 类内成员初始化器（C++11 NSDMI）
    std::string host_ = "localhost";
public:
    Config() = default;                                  // 全用默认值
    Config(std::string host, int retries)
        : host_(std::move(host)), retries_(retries) {}   // 列表覆盖 NSDMI
    void print() const { std::cout << host_ << ' ' << retries_ << '\n'; }
};

int main() {
    std::string log;
    Session s(1, log);
    s.ping();
    std::cout << log << '\n';

    Config c1;
    Config c2("db.prod", 5);
    c1.print();
    c2.print();
}
```

类内成员初始化器（NSDMI，C++11）的价值在于：任何构造函数忘了初始化某个成员，它也有一个确定的值，不会带垃圾上场。经验法则是所有成员都给 NSDMI，构造函数列表只覆盖与默认不同的那些。初始化顺序仍是声明顺序，NSDMI 只提供"初值"，不改变顺序。

> **坑：** 一个成员在初始化列表里出现两次（`a_(1), a_(2)`）是编译错误；用成员初始化另一个成员时，被依赖者必须在声明上靠前，否则读到未初始化值，且 `-Wreorder` 会提醒你。
{: .sec-pit}

### 辨析：初始化列表与体内赋值
{: .sec-iv}

功能上两者都能"让成员有值"，差别在成本和可能性。成本：`std::string` 成员走体内赋值，先默认构造（可能分配）再赋值（可能再分配），初始化列表一步到位。可能性：const、引用、无默认构造的成员在体内赋值路径上根本走不通。结论：能写初始化列表就写初始化列表，体内只放"初始化干不了"的逻辑（校验、抛异常、日志）。

### 12.1.6 析构与 RAII
{: .sec-know}

析构函数在对象死亡时自动运行，而且**异常路径也逃不掉**：栈展开会逐层调用已构造完成对象的析构函数。把"释放资源"写进析构函数、把"获取资源"写进构造函数，资源就绑在了对象生命周期上，这套手法叫 **RAII**（Resource Acquisition Is Initialization，构造即初始化）。它被称为 C++ 头号惯用法，理由很硬：`return`、`break`、异常、提前退出，无论从哪条路径离开作用域，清理代码都会执行，人肉配对的 `open`/`close` 做不到这一点。

```cpp
// 需要 -std=c++20
#include <cstdio>
#include <stdexcept>
#include <string>
#include <string_view>

class File {
    std::FILE* f_;
public:
    explicit File(const std::string& path, const char* mode = "r")
        : f_(std::fopen(path.c_str(), mode)) {
        if (!f_) throw std::runtime_error("cannot open " + path);
    }
    ~File() {
        if (f_) std::fclose(f_);           // 无论怎么离开作用域都会执行
    }
    File(const File&) = delete;            // 句柄独占：不许拷贝
    File& operator=(const File&) = delete;
    void write(std::string_view s) {
        if (std::fwrite(s.data(), 1, s.size(), f_) != s.size())
            throw std::runtime_error("write failed");
    }
};

void save() {
    File f("demo.txt", "w");
    f.write("hello raii");
}                                          // 出作用域自动 fclose，异常路径同理

int main() {
    try {
        save();
    } catch (const std::exception& e) {
        std::printf("err: %s\n", e.what());
    }
    std::FILE* check = std::fopen("demo.txt", "r");   // 验证数据确实落盘了
    if (check) {
        char buf[32] {};
        std::fread(buf, 1, 31, check);
        std::printf("content: %s\n", buf);
        std::fclose(check);
    }
}
```


RAII 管的不只是内存：文件句柄、互斥锁、数据库连接、事务、GPU 缓冲，一切"必须配对释放"的东西都适用。C++ 标准库自己就是最大的 RAII 用户：`std::string`、`std::vector` 管 内存，`std::lock_guard` 管锁，`std::unique_ptr`/`std::shared_ptr` 管裸指针指向的对象。顺手的好处是异常安全：`f.write` 抛异常时 `fclose` 照样执行，绝不泄漏。

> **坑：** RAII 对象析构里抛异常是雷区——栈展开期间再抛第二个异常，程序直接 `std::terminate`。析构函数默认就是 `noexcept` 的，清理逻辑里的失败（比如 `fclose` 返回错误）记录日志即可，别往外抛。
{: .sec-pit}

> **现代拓展：** 业务代码几乎不用手写 RAII 类：文件直接上 `std::fstream`，堆对象交给 `std::unique_ptr`，锁交给 `std::lock_guard`。真需要"离开作用域时执行任意清理回调"（scope guard）时，库基础技术规范（LFTS）有 `std::experimental::scope_exit`，但它尚未并入正式标准，保守起见自己写二三十行的等价物更稳妥。手写 `File` 这种类留给库作者和教学。
{: .sec-ext}

### 12.1.7 特殊成员函数六件套与自动生成规则
{: .sec-know}

六个特殊成员函数：**默认构造、析构、拷贝构造、拷贝赋值、移动构造、移动赋值**。你不写，编译器有时替你生成；你写了某几个，另一些的生成会被抑制。完整规则如下（前提是成员和基类允许对应操作，否则隐式版本被定义为删除）：

| 你声明了什么 | 默认构造 | 析构 | 拷贝构造 | 拷贝赋值 | 移动构造 | 移动赋值 |
| --- | --- | --- | --- | --- | --- | --- |
| 什么都不写 | 生成 | 生成 | 生成 | 生成 | 生成 | 生成 |
| 任一非拷贝/移动构造函数 | 不生成 | 生成 | 生成 | 生成 | 生成 | 生成 |
| 析构函数 | 生成 | — | 生成（弃用） | 生成（弃用） | 不生成 | 不生成 |
| 拷贝构造 | 不生成 | 生成 | — | 生成（弃用） | 不生成 | 不生成 |
| 拷贝赋值 | 不生成 | 生成 | 生成（弃用） | — | 不生成 | 不生成 |
| 移动构造 | 不生成 | 生成 | 删除 | 删除 | — | 不生成 |
| 移动赋值 | 不生成 | 生成 | 删除 | 删除 | 不生成 | — |

三行注解：

1. "生成（弃用）"指 [depr.impldec]：你声明了析构还依赖自动生成的拷贝，属于被标准标记弃用的行为，GCC/Clang 用 `-Wdeprecated-copy` 会告警。
2. "删除"是硬的：声明了移动构造，拷贝构造和拷贝赋值直接不存在，用即编译错误。
3. 声明任何构造函数（含拷贝/移动）都会抑制默认构造——移动构造也是构造函数。

由这张表推出三套经验法则：

- **Rule of Zero**（首选）：类里的成员全部会用自己管理资源（`std::string`、`std::vector`、智能指针），六个特殊成员一个都不写，编译器生成的版本天然正确。
- **Rule of Three**（C++98 遗产）：写了析构函数（说明你在手动管资源）就必须补齐拷贝构造和拷贝赋值——编译器生成的浅拷贝会双重释放。
- **Rule of Five / Six**：手动管资源的类把五个（再加默认构造凑成六个）要么全写、要么显式 `=delete`，别让编译器猜。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <map>
#include <string>

// Rule of Zero：六个特殊成员一个都不写
class Settings {
    std::map<std::string, std::string> kv_;
public:
    void set(std::string k, std::string v) { kv_[std::move(k)] = std::move(v); }
    std::string get(const std::string& k) const {
        auto it = kv_.find(k);
        return it == kv_.end() ? std::string{} : it->second;
    }
};

int main() {
    Settings s;
    s.set("theme", "dark");
    Settings t = s;              // 深拷贝：map 知道怎么拷贝自己
    t.set("theme", "light");
    std::cout << s.get("theme") << ' ' << t.get("theme") << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
dark light
```

Rule of Zero 之所以排第一，是因为手写五件套每一件都是出错机会（漏成员、漏基类、漏自赋值检查、忘了 noexcept），而编译器生成的版本由标准保证正确。写代码前先问一句：这个类真的需要我手动管资源吗？

### 12.1.8 `=default` 与 `=delete`
{: .sec-know}

`=default`（C++11）告诉编译器"生成默认版本但我要显式写出来"——常用于把六件套里被抑制的成员补回来，或把定义搬到类外。`=delete`（C++11）把一个函数标记为禁用，任何调用点直接编译错误。

```cpp
// 需要 -std=c++20
#include <iostream>

class Token {
public:
    Token() = default;
    Token(const Token&) = delete;               // 调用点直接编译错误
    Token& operator=(const Token&) = delete;
};

class TokenOld {                                // C++98 旧写法对比
public:
    TokenOld() {}
private:
    TokenOld(const TokenOld&);                  // 只声明不定义
    TokenOld& operator=(const TokenOld&);
};

void f(long v) { std::cout << v << '\n'; }
void f(double) = delete;                        // =delete 也能用在普通函数上

int main() {
    Token t;
    TokenOld o;
    (void)t; (void)o;                           // 只为压掉 -Wunused-variable
    // Token t2 = t;      // 编译错误：use of deleted function
    // TokenOld o2 = o;   // 这里其实先报 private 访问错误；在成员函数里则会链接错误
    f(42);                // int -> long，正常
    // f(3.14);           // 编译错误：use of deleted function 'void f(double)'
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
42
```

`=delete` 在普通函数上的妙用是堵隐式转换：上面 `f(double)` 被删除后，`f(3.14)` 不会悄悄转成 `long`，而是当场报错。想要"这个函数拒绝所有浮点实参"，一行搞定。

### 辨析：`=delete` 与"私有化旧写法"
{: .sec-iv}

旧写法把拷贝构造声明为 private 且不定义：类外的拷贝在编译期报 private 访问错误，但**类内部和友元的拷贝能通过编译，直到链接期才报 undefined reference**；而且错误信息是"无法解析的符号"，和"你拷贝了一个不该拷贝的东西"相去甚远。`=delete` 把错误提前到编译期调用点，信息直白，还能删除任意函数（包括自由函数、运算符、特定重载）；代价只是要求 C++11。没有任何理由再用私有化写法。

### 12.1.9 移动构造必须 noexcept
{: .sec-know}

`std::vector` 扩容时要把旧元素搬到新内存。如果元素的移动构造可能抛异常，搬家搬到一半抛了，新内存里一半是搬来的、旧内存里一半是没搬的，vector 无法同时维持两边一致——强异常保证就破了。所以标准库的策略是 `move_if_noexcept`：移动构造是 `noexcept` 才用移动，否则退回拷贝（前提是可拷贝）。移动构造忘写 noexcept，性能可能原地塌方。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <utility>
#include <vector>

template <bool Noex>
class Tracked {
    inline static int copies_ = 0;               // C++17 inline static，见 12.2.1
    inline static int moves_  = 0;
    int* p_;
public:
    explicit Tracked(int v) : p_(new int(v)) {}
    Tracked(const Tracked& o) : p_(new int(*o.p_)) { ++copies_; }
    Tracked(Tracked&& o) noexcept(Noex)          // 唯一差别：noexcept 与否
        : p_(std::exchange(o.p_, nullptr)) { ++moves_; }
    ~Tracked() { delete p_; }
    static void report(const char* tag) {
        std::cout << tag << ": 拷贝 " << copies_ << " 移动 " << moves_ << '\n';
    }
};

int main() {
    std::vector<Tracked<true>> v1;
    v1.push_back(Tracked<true>(1));
    v1.push_back(Tracked<true>(2));
    v1.push_back(Tracked<true>(3));
    Tracked<true>::report("noexcept=true ");

    std::vector<Tracked<false>> v2;
    v2.push_back(Tracked<false>(1));
    v2.push_back(Tracked<false>(2));
    v2.push_back(Tracked<false>(3));
    Tracked<false>::report("noexcept=false");
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
noexcept=true : 拷贝 0 移动 4
noexcept=false: 拷贝 3 移动 1
```

三次 `push_back`：第一次从临时对象构造（1 次移动），后两次各触发一次扩容，分别搬迁 1 个和 2 个旧元素。移动是 noexcept 的，搬迁全走移动（共 4 次移动）；不是 noexcept 的，搬迁退化为拷贝（3 次拷贝 + 1 次移动）。搬 10 万个元素进 vector，差别就是 10 万次堆分配对 10 万次指针交换。三大标准库（libstdc++、libc++、MSVC STL）都按 `move_if_noexcept` 策略实现，这是标准要求的强异常保证换来的。

> **坑：** "移动构造 noexcept"要连着移动赋值一起看：`vector` 的扩容只看移动构造，但 `swap`、`erase` 等路径会用到移动赋值，两个都该 noexcept。另外 `noexcept` 是类型系统的一部分，声明了 noexcept 的移动构造在派生类里被重写时也必须保持 noexcept。
{: .sec-ts}

### 12.1.10 拷贝消除与 NRVO
{: .sec-know}

按值返回一个对象，语言本来的流程是：函数内构造 → 析构局部对象前拷贝/移动到返回位置 → 调用方再接住。这套流程常有两到三次多余动作，编译器允许把它们优化掉，这就是**拷贝消除**。分两类，性质完全不同：

- **NRVO**（具名返回值优化）：`return` 一个具名局部对象。允许消除，但不强制——所有主流编译器在开优化甚至 `-O0` 下都会做，但标准没背书，写了依赖它才有正确结果的代码是错的。
- **纯右值强制省略**：C++17 起（核心语言规则 P0135），返回纯右值（`return T(args);`）、用纯右值初始化（`T x = T(T());`）时**强制**消除，prvalue 从"临时对象"改成了"初始化的配方"，根本没有中间对象可以省。

```cpp
// 需要 -std=c++20
#include <iostream>

struct Num {
    int v_;
    explicit Num(int v) : v_(v) { std::cout << "构造 "; }
    Num(const Num& o) : v_(o.v_) { std::cout << "拷贝 "; }
    Num(Num&& o) noexcept : v_(o.v_) { std::cout << "移动 "; }
};

Num make_nrvo(int v) {
    Num n(v);
    return n;                    // 具名对象：NRVO，允许但非强制
}

Num make_prvalue(int v) {
    return Num(v);               // 纯右值：C++17 起强制省略
}

int main() {
    Num a = make_nrvo(1);
    std::cout << "| ";
    Num b = make_prvalue(2);
    std::cout << '\n' << a.v_ << ' ' << b.v_ << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
g++ -std=c++20 -fno-elide-constructors demo.cpp -o demo_noelide && ./demo_noelide
```

```text
构造 | 构造
1 2
```

第二个命令（关掉优化开关）的输出：

```text
构造 移动 | 构造
1 2
```

`-fno-elide-constructors` 下 NRVO 消失了（`构造 移动`：局部对象构造一次，再移动进返回位置），但 `make_prvalue` 依旧只有一次构造——强制省略是语言规则，不是优化开关能关掉的。写代码的守则：返回局部对象就老老实实 `return n;`，写 `return std::move(n);` 反而把 NRVO 路径堵死、强制走移动（第 10 篇详述过）；`return T(args);` 形式则从 C++17 起零成本。

## 12.2 对象
{: .sec-expl}

### 12.2.1 静态成员与静态成员函数
{: .sec-know}

static 成员属于类而不属于任何对象：整个程序只有一份，所有对象共享，访问写 `类名::成员`。静态数据成员传统上"类内声明、类外定义"——定义必须恰好出现在一个 .cpp 里；C++17 的 `inline static` 让定义直接写进类内，头文件里多份拷贝也不会链接冲突，从此静态成员的写法舒展多了。

```cpp
// 需要 -std=c++20
#include <iostream>

class IdGen {
    inline static int next_ = 1;      // C++17：类内直接定义
    int id_;
public:
    IdGen() : id_(next_++) {}
    int id() const { return id_; }
    static int issued() { return next_ - 1; }   // 静态成员函数：没有 this
};

class Legacy {                        // C++17 之前的传统写法
public:
    static const int LIMIT = 10;      // const 整型允许类内给初值（C++98 起）
    static double rate;               // 非 const：类内只能声明
};
double Legacy::rate = 0.75;           // 类外定义，通常放 .cpp

int main() {
    IdGen a, b, c;
    std::cout << a.id() << b.id() << c.id() << ' ' << IdGen::issued() << '\n';
    std::cout << Legacy::LIMIT << ' ' << Legacy::rate << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
123 3
10 0.75
```

静态成员函数没有 `this`，推论一连串：摸不到非静态成员、不能标 const、不能是虚函数、取地址得到的是普通函数指针。它本质上是"挂在类命名空间下的自由函数"，适合表达与状态无关的操作或对静态成员的操作。

> **坑：** C++17 之前，类内给初值的 `static const int` 一旦被 odr-used（比如绑定到引用、取地址），链接器就找类外定义去了，报 undefined reference。C++17 起 `inline` 变量和 `static constexpr`（隐式 inline）解决了这个问题，但维护旧代码时要记得这个坑。
{: .sec-pit}

### 12.2.2 const 成员函数与 mutable
{: .sec-know}

const 成员函数承诺"不修改对象的对外状态"，是接口设计的一部分：逻辑上只读的操作就标 const，const 对象、`const T&` 形参才能调用它。mutable 给这条纪律开了个受控的口子。

```cpp
// 需要 -std=c++20
#include <cctype>
#include <iostream>
#include <string>

class Name {
    std::string full_;
    mutable int lookups_ = 0;         // mutable：const 函数里也能改
public:
    explicit Name(std::string f) : full_(std::move(f)) {}
    void rename(std::string f) { full_ = std::move(f); }
    char first_letter() const {       // 逻辑只读
        ++lookups_;                   // 改的是实现细节，观察者看不出来
        return static_cast<char>(std::toupper(static_cast<unsigned char>(full_.front())));
    }
    int lookups() const { return lookups_; }
};

int main() {
    const Name n("gangolf");          // const 对象只能调 const 成员函数
    std::cout << n.first_letter() << n.first_letter() << ' ' << n.lookups() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
GG 2
```

mutable 的合法用法都长一个样：缓存（memoize）、访问计数、互斥锁（`std::mutex` 本身要能在 const 函数里 lock）、惰性求值标记。非法用法是"const 函数其实改了可观察状态"——那是骗编译器。另外 mutable 不能修饰引用成员、const 成员和 static 成员：前两个本来就不受 const 约束，最后一个不属于对象。

### 12.2.3 友元：单向、不传递、不继承
{: .sec-know}

friend 授予某个外部函数或类访问本类私有成员的权利，三条铁律记住就够：**单向**（A 认 B 做 friend，B 并不回礼）、**不传递**（B 的 friend 摸不到 A）、**不继承**（A 的 friend 摸不到派生类，派生类也不继承这份友谊）。friend 破坏封装吗？恰恰相反，它是把"这个函数和类是一体的"显式写出来——比把成员设成 public 精确得多。

```cpp
// 需要 -std=c++20
#include <iostream>

class Secret {
    int value_ = 0;
    friend void peek(const Secret&);   // 友元函数
    friend class Auditor;              // 友元类
public:
    explicit Secret(int v) : value_(v) {}
    friend std::ostream& operator<<(std::ostream& os, const Secret& s) {
        return os << "Secret(" << s.value_ << ')';   // hidden friend：定义在类内
    }
};

void peek(const Secret& s) { std::cout << s.value_ << '\n'; }

class Auditor {
public:
    void audit(const Secret& s) const { std::cout << "audit " << s.value_ << '\n'; }
};

int main() {
    Secret s(42);
    peek(s);
    Auditor a;
    a.audit(s);
    std::cout << s << '\n';            // 经 ADL 找到 hidden friend
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
42
audit 42
Secret(42)
```

运算符写成 hidden friend 是现代推荐做法：把 `operator<<` 的定义直接放在类内，它不是普通名字，普通查找找不到它，只有对 `Secret` 实参做参数依赖查找（ADL）时才会被找到。好处有二——命名空间不被无关的 `operator<<` 污染、编译器少处理一层声明。C++20 标准库自己也用了这招（如 `std::filesystem::path` 的流运算符）。

> **坑：** 友元声明不是成员声明，`friend void peek(const Secret&);` 之后若从未提供定义，链接期才炸。另外友元函数如果在类内首次声明，它可能不属于任何命名空间——调用时务必让实参类型参与 ADL，别写 `::peek(s)` 这种全限定名。
{: .sec-pit}

### 12.2.4 嵌套类与局部类
{: .sec-know}

类里还能定义类。嵌套类是外层类的一个成员：名字藏在外层作用域里（`Matrix::Row`），C++11 起标准明确它可以访问外层类的私有成员（反过来不行，外层访问嵌套类的私有得看嵌套类自己）。局部类则定义在函数体内，作用域到函数结束为止。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <vector>

class Matrix {
    std::vector<double> data_;
    std::size_t rows_, cols_;
public:
    Matrix(std::size_t r, std::size_t c) : data_(r * c, 0.0), rows_(r), cols_(c) {}

    class Row {                        // 嵌套类：矩阵一行的代理视图
        Matrix& m_;
        std::size_t r_;
    public:
        Row(Matrix& m, std::size_t r) : m_(m), r_(r) {}
        double& operator[](std::size_t c) {
            return m_.data_[r_ * m_.cols_ + c];   // 访问外层私有成员：合法（C++11 起）
        }
    };
    Row row(std::size_t r) { return Row(*this, r); }
};

int main() {
    Matrix m(2, 3);
    m.row(0)[1] = 3.14;
    std::cout << m.row(0)[1] << '\n';

    class Local {                      // 局部类：只在函数内可见
    public:
        void hello() const { std::cout << "hello from local class\n"; }
    };
    Local().hello();
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
3.14
hello from local class
```

嵌套类的典型用途：实现细节类型（迭代器、`Row` 这类代理）、把名字藏进外层避免污染外层命名空间。局部类现在很少手写——lambda 覆盖了它绝大部分场景，且局部类不能有静态数据成员、不能当模板实参（C++11 前），能力受限。

### 12.2.5 对象大小：sizeof 的一套账
{: .sec-know}

对象占多少字节，四条规则算清楚：空类至少 1 字节（保证不同对象地址不同）；成员函数和静态成员不占对象空间（代码在代码段，静态在静态区）；有虚函数的对象多一个 vptr（指向类的虚表）；成员按对齐规则填充。

```cpp
// 需要 -std=c++20
#include <iostream>

struct Empty {};
struct FuncOnly { void f(); static int s; };   // 只有函数和静态成员
struct OneInt { int x; };
struct CharInt { char c; int x; };             // 1 + 3 填充 + 4
struct WithVirt { virtual void f(); int x; };  // vptr + int + 填充
struct EboDerived : Empty { int x; };          // 空基类优化：基类占 0
struct FieldEmpty { Empty e; int x; };         // 成员没有空类优化
struct Compact { [[no_unique_address]] Empty e; int x; };   // C++20

int main() {
    std::cout << sizeof(Empty) << ' ' << sizeof(FuncOnly) << ' '
              << sizeof(OneInt) << ' ' << sizeof(CharInt) << ' '
              << sizeof(WithVirt) << ' ' << sizeof(EboDerived) << ' '
              << sizeof(FieldEmpty) << ' ' << sizeof(Compact) << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
1 1 4 8 16 4 8 4
```

前提：x86-64 平台、GCC 实测。逐项解释——`Empty` 和 `FuncOnly` 都是 1（函数不占对象空间）；`CharInt` 8（int 要求 4 字节对齐，char 后垫 3 字节）；`WithVirt` 16（8 字节 vptr + 4 字节 int + 4 字节填充；32 位平台 vptr 是 4 字节，总数会变 8）；`EboDerived` 4 是**空基类优化**（EBO），基类为空时允许占 0 字节——但同样的 Empty 做成员就得占 1 字节（`FieldEmpty` 8），两个同类型空子对象还要求地址不同。C++20 的 `[[no_unique_address]]` 授权编译器让空成员复用填充空间（`Compact` 4），GCC/Clang 实现了，MSVC 接受该属性但不优化（它提供了 `[[msvc::no_unique_address]]`）。

### 12.2.6 聚合类与聚合初始化
{: .sec-know}

聚合类是"没有自定义构造逻辑"的类。C++20 的准确条件：没有用户声明或继承的构造函数、无私有或受保护的非静态数据成员、无虚函数、无私有或受保护基类（public 基类允许，C++17 起；类内默认成员初始化器 NSDMI 允许，C++17 起恢复）。聚合可以用花括号按成员顺序初始化，C++20 还加了指派初始化器（designated initializers）。

```cpp
// 需要 -std=c++20
#include <iostream>

struct Point { int x = 0; int y = 0; };        // 聚合（NSDMI 不影响聚合身份）

struct Segment {
    Point a;
    Point b;
    int id = -1;
};

class NonAgg {
public:
    NonAgg() = default;         // C++20 起：类内 "=default" 也算用户声明的构造函数
    int x = 0;                  // 因此 NonAgg 不是聚合，不能 {3} 初始化
};

int main() {
    Point p1{1, 2};              // 聚合初始化：按声明顺序
    Point p2{.x = 3};            // 指派初始化器（C++20）：y 走 NSDMI 的 0
    Segment s{.a = {1, 2}, .b = {.x = 3, .y = 4}};   // 嵌套指派
    // Point p3{.y = 5, .x = 6}; // 编译错误：指派必须按声明顺序
    // Point p4{.x = 1, .x = 2}; // 编译错误：不许重复指派
    std::cout << p1.x << p1.y << ' ' << p2.y << ' ' << s.b.y << ' ' << s.id << '\n';
    std::cout << NonAgg{}.x << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
12 0 4 -1
0
```

指派初始化器的规矩：`.name =` 必须按成员声明顺序出现、可以跳过成员（跳过的走 NSDMI 或值初始化）、不能重复。GCC 还要求一个列表里要么全指派、要么全不指派，混着写直接报错，写的时候就别混。它解决的真实痛点是"只有部分字段需要显式给值"的长参数列表——比一串同类型位置参数安全得多，读代码的人不需要数第 3 个 int 是什么。

> **坑：** C++20 改了聚合的判定（P1008）：类内写 `T() = default;` 的类型从此不是聚合。C++17 时代它能聚合初始化，升级编译器后同样的代码报错。修法是把 `=default` 挪到类外定义，或者老实写普通构造函数。
{: .sec-pit}

### 辨析：聚合初始化与构造函数
{: .sec-iv}

聚合初始化是"逐个成员照着填"，没有构造逻辑介入，也不能有校验；构造函数是"有逻辑的初始化"，能校验、能推导、能拒绝。选择标准就是不变量：没有不变量（纯数据打包）用聚合 + 花括号，连构造函数都不用写；有不变量就走构造函数，聚合身份随之失效——两者天然互斥，这正好逼你表态"这个类型有没有契约"。另外花括号初始化禁止窄化转换（`int x{3.14}` 是编译错误），圆括号不会（`int x(3.14)` 得 3），这是花括号另一层安全垫。

### 12.2.7 值语义 vs 引用语义
{: .sec-iv}

C++ 的默认对象模型是**值语义**：赋值和传参产生独立副本，`a = b` 之后两者互不相干。引用语义（赋值共享同一实体）必须显式声明——写引用、写指针，或者用智能指针这类"值语义的壳包着共享资源"的类型。Java、Python 程序员转过来最容易栽在这里：以为 `=` 是引用，实际发生了深拷贝。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <vector>

int main() {
    std::vector<int> a{1, 2};
    std::vector<int> b = a;      // 值语义：真拷贝
    b.push_back(3);
    std::cout << a.size() << ' ' << b.size() << '\n';     // 2 3

    std::vector<int>& r = a;     // 引用语义：显式写 &
    r.push_back(9);
    std::cout << a.size() << ' ' << r.size() << '\n';     // 3 3
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
2 3
3 3
```

值语义的工程价值在别处：对象可以被安全地移动、放进容器、跨线程传递而不用担心"还有别人攥着它"；拷贝的那一刻起独立演化，没有隐藏的耦合。代价是拷贝本身的开销——所以 C++ 又补了移动语义让"转移所有权"也便宜。引用语义省拷贝但引入别名问题：谁也不知道一个 `T&` 背后还有几个人在看。经验法则：默认值语义，能证明拷贝昂贵且确实只需要观察时才写 `const T&`，需要共享可变所有权才上 `shared_ptr`。

### 12.2.8 PIMPL：把实现藏到编译墙后面
{: .sec-know}

PIMPL（Pointer to IMPLementation）在公开头文件里只留一个 `unique_ptr<Impl>`，所有私有成员和重依赖（`<regex>`、`<thread>` 这类重量级头文件）全部搬进 .cpp。收益是**编译隔离**：改实现不用重编所有包含者，头文件也不再传染依赖。代价要认账：每次访问成员多一层指针间接，构造时多一次堆分配。

```cpp
// pimpl.h —— 对外头文件，干净得看不到任何重依赖
#ifndef PIMPL_H
#define PIMPL_H
#include <memory>
#include <string>

class Task {
    struct Impl;                        // 前向声明的嵌套实现类
    std::unique_ptr<Impl> p_;
public:
    explicit Task(const std::string& name);
    ~Task();                            // 四个特殊成员都得放 .cpp，原因见下
    Task(Task&&) noexcept;
    Task& operator=(Task&&) noexcept;
    Task(const Task&) = delete;
    Task& operator=(const Task&) = delete;
    void run() const;
};
#endif
```

```cpp
// pimpl.cpp —— 重依赖全部关在这里
#include "pimpl.h"
#include <cstdio>
#include <regex>
#include <utility>

struct Task::Impl {
    std::string name;
    std::regex pattern;
    explicit Impl(std::string n) : name(std::move(n)), pattern(name) {}
};

Task::Task(const std::string& name) : p_(std::make_unique<Impl>(name)) {}
Task::~Task() = default;                // 此处 Impl 是完整类型，unique_ptr 才能析构
Task::Task(Task&&) noexcept = default;
Task& Task::operator=(Task&&) noexcept = default;

void Task::run() const {
    std::smatch m;
    if (std::regex_search(p_->name, m, p_->pattern))
        std::printf("task %s matched %s\n", p_->name.c_str(), m.str(0).c_str());
    else
        std::printf("task %s no match\n", p_->name.c_str());
}
```

```cpp
// main.cpp —— 只认识 pimpl.h，regex 的编译时间与它无关
#include "pimpl.h"

int main() {
    Task t("build");
    t.run();
}
```

```bash
g++ -std=c++20 -Wall -Wextra main.cpp pimpl.cpp -o demo && ./demo
```

```text
task build matched build
```

四个特殊成员必须放 .cpp 里定义（析构和移动哪怕 `=default`），因为 `unique_ptr<Impl>` 的析构要求 `Impl` 是完整类型，头文件里只有前向声明。这个"必须"恰好也是 PIMPL 的教学价值：它逼着你想清楚每个特殊成员在哪个翻译单元里实例化。适用场景：ABI 稳定的库接口、要切断重依赖传播的头文件、实现频繁变动的模块。内部小工具别用——一层间接和一次分配，换不来多少编译时间。

## 12.3 技术解惑
{: .sec-expl}

### 12.3.1 自赋值安全与 copy-and-swap
{: .sec-know}

写赋值运算符绕不开两个问题：`a = a` 怎么办？新资源申请失败怎么办？常规写法要单独判自赋值、先分配后释放、异常时回滚，三件事每一件都可能写漏。copy-and-swap 用一个换法把三个问题一起消掉：

```cpp
// 需要 -std=c++20
#include <algorithm>
#include <iostream>
#include <utility>

class Buffer {
    std::size_t n_ = 0;
    int* p_ = nullptr;
public:
    explicit Buffer(std::size_t n) : n_(n), p_(n ? new int[n]{} : nullptr) {}
    Buffer(const Buffer& o) : n_(o.n_), p_(o.n_ ? new int[o.n_] : nullptr) {
        if (n_) std::copy(o.p_, o.p_ + n_, p_);
    }
    Buffer(Buffer&& o) noexcept
        : n_(std::exchange(o.n_, 0)), p_(std::exchange(o.p_, nullptr)) {}
    ~Buffer() { delete[] p_; }

    friend void swap(Buffer& a, Buffer& b) noexcept {   // 只交换句柄，绝不失败
        using std::swap;
        swap(a.n_, b.n_);
        swap(a.p_, b.p_);
    }
    Buffer& operator=(Buffer o) noexcept {   // 按值传参：拷贝构造发生在参数里
        swap(*this, o);                      // 交换后，旧资源随 o 析构
        return *this;
    }
    std::size_t size() const { return n_; }
};

int main() {
    Buffer a(3);
    Buffer b(5);
    b = a;               // 拷贝赋值：参数 o 是 a 的深拷贝
    a = a;               // 自赋值：天然安全，o 是 a 的副本，交换无损
    Buffer c(0);
    c = Buffer(2);       // 移动赋值：参数 o 由右值移动构造而来
    std::cout << b.size() << ' ' << a.size() << ' ' << c.size() << '\n';
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
3 3 2
```

原理拆开看：形参按值传入，拷贝/移动构造在**进入函数之前**完成——那时还没动 `this` 的任何状态，所以分配失败抛异常时对象完好（强异常保证）；自赋值时形参就是 `a` 的副本，交换完原对象原样保留；旧资源挂在形参 `o` 上，函数返回时随它析构。一份代码同时正确充当拷贝赋值和移动赋值，也不用判 `this == &o`。代价是多一次拷贝的机会成本：资源本来能"偷"，现在必先复制一份。追求极限性能的场景手写两个赋值运算符并自己处理自赋值与异常，一般场景 copy-and-swap 的正确性红利更值钱。

### 12.3.2 类不变量与设计契约
{: .sec-know}

把 12.1.2 的观点升级成设计方法：**每个类先写下不变量，再决定接口**。不变量写不出来（"这两个 int 是啥关系？"），说明这个类可能只是个数据包，用聚合；写得出来，构造函数负责"建立"它，所有成员函数负责"维护"它，析构函数不需要管它。

```cpp
// 需要 -std=c++20
#include <iostream>
#include <stdexcept>

class Interval {
    int lo_, hi_;                        // 不变量：lo_ <= hi_
public:
    Interval(int lo, int hi) : lo_(lo), hi_(hi) {
        if (lo > hi) throw std::invalid_argument("lo > hi");
    }                                    // 构造即校验：对象要么合法要么不存在
    void shift(int d) { lo_ += d; hi_ += d; }          // 平移天然保持不变量
    void widen(int d) {
        if (d < 0) throw std::invalid_argument("d < 0");
        lo_ -= d; hi_ += d;              // 扩张前后 lo_ 仍 <= hi_
    }
    int lo() const { return lo_; }
    int hi() const { return hi_; }
};

int main() {
    Interval i(2, 5);
    i.shift(3);
    i.widen(1);
    std::cout << '[' << i.lo() << ',' << i.hi() << "]\n";
    try {
        Interval bad(7, 3);              // 非法对象根本没有出生机会
    } catch (const std::exception& e) {
        std::cout << e.what() << '\n';
    }
}
```

```bash
g++ -std=c++20 -Wall -Wextra demo.cpp -o demo && ./demo
```

```text
[4,7]
lo > hi
```

契约的好处从第一个使用点就开始兑现：调用方拿到 `Interval` 就可以放心假设 `lo() <= hi()`，类内代码也不用处处防御。三个补充判断——修改器破坏不变量时宁可抛异常也别"先改成错的再修复"，中间态可能被异常路径观察到；能整体替换的操作（如 `std::string` 的赋值）天然原子，copy-and-swap 是它的通用实现；public 成员变量等于公开宣告"没有不变量"，二者只能选一个。

### 12.3.3 三个高频追问
{: .sec-know}

**声明了析构函数，为什么移动构造就没了？** 编译器不敢替你猜。需要析构函数通常意味着资源是手动管的，而编译器生成的移动是逐成员浅移动——对裸指针成员就是双重释放。标准干脆规定：声明了析构/拷贝操作，移动不再生成；拷贝仍生成但标记弃用。补救就是 Rule of Five 或 `=default` 显式补回。

**`=default` 的移动构造一定是 noexcept 的吗？** 不一定。defaulted 移动构造的 noexcept 由成员逐个决定：所有成员的移动构造都 noexcept（或根本没有移动构造但有拷贝），整体才是 noexcept；任何一个成员的移动可能抛，整体就不是。所以换掉一个成员类型可能悄悄改变整个类的 noexcept 属性，进而影响 vector 扩容策略——重要类型值得写 `static_assert(std::is_nothrow_move_constructible_v<T>);` 钉死。

**空类对象真的不占内存吗？** 占 1 字节。标准要求两个不同的完整对象地址必须不同，0 字节做不到，所以编译器给空类至少 1 字节。但空数组元素、空基类子对象允许为 0（EBO），`[[no_unique_address]]` 空成员也可以复用填充——"占 1 字节"只针对独立对象和普通成员。

## 变式追问
{: .sec-think}

1. 空类为什么是 1 字节，EBO 却能让基类占 0 字节？这不是自相矛盾吗？

   约束条件不同。独立对象受"不同对象地址必须不同"约束，0 字节没法给两个对象分配不同地址，所以下限 1。EBO 的场景里，基类子对象和派生对象**共享同一地址**是允许的——标准专门为此开了口子，因为"派生对象开头有个不占空间的基类"不产生任何歧义：你没法单独取基类子对象的地址与派生对象比较。普通成员没有这个豁免，因为取成员地址（`&obj.e`）是合法操作，两个成员地址必须不同。规则的分界线其实就一条：有没有办法独立寻址。

2. 析构函数默认 noexcept，那析构里抛异常到底会发生什么？

   析构函数若未显式声明，隐式就是 `noexcept` 的；抛出异常会直接 `std::terminate`，连 `catch` 的机会都没有。更糟的是栈展开期间：异常 A 正在传播、各层析构函数陆续执行，此时某个析构又抛出异常 B——同时处理两个异常没有定义良好的机制，同样 terminate。所以结论不是"析构里小心点抛"，而是析构里根本别抛：清理失败就吞掉、记日志、设置状态位，让下一个操作去报告。历史上确实有人用"检查是否正在栈展开"（`std::uncaught_exceptions`）让析构双态运行，但那是给特殊工具（如某些 scope guard）用的，普通业务类的析构只做不会失败的事。

3. `= default` 的移动构造一定 noexcept 吗？怎么在编译期验证？

   不一定。defaulted 的 noexcept 逐成员决定：所有成员的移动构造都 noexcept（或没有移动但有 noexcept 的拷贝路径），整体才是；只要有一个成员可能抛，整体就不带 noexcept。验证不用查文档，一行 `static_assert(std::is_nothrow_move_constructible_v<T>);` 把契约钉进代码。这个断言的价值在于**防退化**：今天类里的成员全是 noexcept 移动的，明天有人塞进一个非 noexcept 移动的成员，整个类的移动属性悄悄变差，vector 扩容跟着退化为拷贝——性能损失没有任何编译错误，只有 static_assert 能当场拦截。

4. explicit 到底在挡什么？`Watt w(3.0);` 也是"隐式"的吗？

   explicit 挡的是**拷贝初始化语境**下的用户定义转换：`Watt w = 3.0;`、函数实参 `half(3.0)`、`return 3.0;`、`w == 3.0` 这类"从一个别的类型出发、让编译器自己找路"的位置。`Watt w(3.0)` 是直接初始化，永远合法——它本来就写明了目标类型，谈不上"隐式"。换句话说，explicit 拒绝的是"代码里根本没出现类型名"的构造，而所有显式写出 `Watt(...)` 的写法不受影响。这也是判断要不要 explicit 的准绳：如果每个调用点都该明确写出类型，就加 explicit；如果这个转换像 `std::string` 从字面量构造那样"处处自然"，才考虑放开。
