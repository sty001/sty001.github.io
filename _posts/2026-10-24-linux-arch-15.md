## 前置知识回顾

- 利用 Nginx 搭建单个网站
- 利用 Nginx 搭建多个网站：每个网站有单独的虚拟主机配置文件、独立的站点目录
- 利用 Nginx 配置安全控制：access 模块根据用户访问的地址进行控制（返回 403），认证模块根据用户访问信息进行认证控制
- 网站服务访问方式：基于域名访问、基于地址访问

## 原理解析

### 一次请求在 Nginx 内部的处理顺序

1. 客户端连接到达，Nginx 的 worker 进程按事件驱动模型接受连接；
2. 根据请求的 IP 与端口匹配 server 块（server_name 与 listen 共同决定），Host 不匹配任何 server_name 时使用该端口的第一个 server；
3. 在选中的 server 内，按 location 规则（精确 > 优先前缀 > 正则 > 普通前缀）匹配处理该 URI 的 location；
4. location 内依次执行 rewrite/return、访问控制（allow/deny、auth_basic）、内容处理（静态文件、proxy_pass、fastcgi_pass）；
5. 生成响应，按 access_log 格式记录日志，返回客户端。

理解这个顺序有助于解释"为什么改了配置不生效""为什么静态规则抢走了动态请求"等问题。

### 状态页指标的含义

stub_status 输出的 Waiting 值是监控服务压力的重要指标：它表示已经建立连接、但既不在读请求也不在写响应的空闲连接数。Waiting 持续偏高说明连接被慢客户端或后端拖住；Active connections 突增则通常意味着突发流量或攻击。

## 一、搭建文件共享服务器

使用 ngx_http_autoindex_module 模块开启站点目录索引功能。

指令用法：

| 项目 | 说明 |
| --- | --- |
| Syntax | autoindex on \| off; |
| Default | autoindex off; |
| Context | http, server, location |

配置文件 www.conf：

```nginx
server {
    listen                80;
    server_name           www.example.com;
    location / {
        root                  /html/www;
        auth_basic            "内部访问区";
        auth_basic_user_file  password/htpasswd;
        autoindex             on;
    }
}
```

使用要点：

- 需要将站点首页文件删除，否则会优先展示首页而不是目录列表
- mime.types 媒体资源类型文件的作用：文件中已定义的扩展名资源，访问时会直接看到数据信息；文件中没有的扩展名资源，访问时会直接下载资源

如果目录页面数据中文出现乱码，添加 charset 指令即可解决：

```nginx
location / {
    root                  /html/www;
    #index index.html;
    auth_basic            "内部访问区";
    auth_basic_user_file  password/htpasswd;
    autoindex             on;
    charset               utf-8;
}
```

autoindex 开着的目录务必套上 auth_basic 或 allow/deny，加公网等于把服务器目录结构公开，爬虫和扫描器最喜欢这种站。

## 二、多域名访问（server_name 别名）

一个 server 块可以配置多个域名，实现同一站点通过多个域名访问：

```nginx
server_name  www.example.com alt.example.com;
```

作用：

1. 方便网站访问测试
2. 定位要访问的网站服务器

配置好后，需要同步配置好各域名的解析信息。

server_name 还支持泛域名 *.example.com 与正则写法（server_name ~^www\d+\.example\.com$;），批量子域接入时不用一个个列。

## 三、状态页监控

使用 ngx_http_stub_status_module 模块对网站进行监控。

指令用法：

```nginx
location = /basic_status {
    stub_status;
}
```

配置文件 state.conf：

```console
[root@web01 conf.d]# vim state.conf
```

```nginx
server {
    listen        80;
    server_name  status.example.com;
    stub_status;
}
```

重启服务并编写解析文件：

```bash
systemctl reload nginx
```

```text
10.0.0.7     status.example.com
```

状态页各字段含义：

| 字段 | 含义 |
| --- | --- |
| Active connections | 当前激活的连接数 |
| accepts | 累计接收的连接数（TCP 层） |
| handled | 累计处理的连接数（TCP 层） |
| requests | 累计的 HTTP 请求总数 |
| Reading | Nginx 正在读取客户端请求报文的连接数 |
| Writing | Nginx 正在写响应报文的连接数 |
| Waiting | 处于队列中等待处理（读取或写响应）的连接数，是监控服务压力的重要指标 |

> **注意：** stub_status 输出的是全局统计，不区分 server 块；该页面不要对公网开放，建议加 allow/deny 或 auth_basic 保护。yum 官方源默认内置该模块，编译安装需要 --with-http_stub_status_module。

几个字段放在一起看更有信息量：Active connections 恒等于 Reading + Writing + Waiting 之和，这是核对状态页读数是否正常的基本关系式；accepts 与 handled 的差值变大，说明有连接建好了却没被处理，警惕 worker 打满或 backlog 溢出；requests 除以 accepts 就是长连接复用率，比值越高 keepalive 发挥越充分，跟前面的 keepalive_timeout 配置正好互相印证，敲一遍数值就能对上。接入 Zabbix 或 Prometheus（nginx-exporter）监控时，就是把 curl 提取数值固化成采集项，间隔 30-60 秒一次，重点看 Waiting 与每秒请求增量曲线。

## 四、日志配置

### 4.1 访问日志

访问日志默认路径为 /var/log/nginx/access.log，由 ngx_http_log_module 模块提供。通过 log_format 定义日志内容格式，再通过 access_log 调用该格式：

```nginx
log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
                  '$status $body_bytes_sent "$http_referer" '
                  '"$http_user_agent" "$http_x_forwarded_for"';
access_log  /var/log/nginx/access.log  main;
```

高流量站点给 access_log 加 buffer=64k flush=5s 参数，日志先攒缓冲再落盘，减少磁盘写次数；代价是宕机时可能丢最后几秒日志，取舍看业务。监控探活的请求会把日志刷满，单独给 /basic_status 之类的 location 配 access_log off;，日志干净很多也省磁盘。

日志变量说明：

| 变量 | 说明 |
| --- | --- |
| $remote_addr | 显示用户访问的源 IP 地址信息 |
| $remote_user | 显示认证的用户名信息 |
| [$time_local] | 显示访问网站的时间 |
| $request | 请求报文的请求行信息 |
| $status | 用户访问网站的状态码信息 |
| $body_bytes_sent | 显示响应的数据尺寸信息 |
| $http_referer | 记录调用网站资源的来源链接地址，可用于防止用户盗链 |
| $http_user_agent | 记录用户使用什么客户端软件访问页面（谷歌、火狐、IE、安卓、iPhone 等） |
| $http_x_forwarded_for | 与负载均衡场景相关，记录经过代理层时客户端的真实 IP 信息 |

关于 $http_referer：例如外部站点的页面直接引用了本站的图片链接，访问日志中就会记录该外部站点的 referer 信息，据此可以发现并处理盗链。

关于 $remote_addr 与真实 IP：直连场景下 $remote_addr 就是客户端地址；一旦前面挂了 CDN、LB 或另一层 Nginx，$remote_addr 记录的只是上一跳代理的 IP，全公司访问在日志里看起来都来自同一个地址。要拿真实 IP 得靠两样东西——代理层转发时带上 X-Forwarded-For（日志里取第一列才是最初客户端），本机再用 realip 模块还原：

```nginx
set_real_ip_from  10.0.0.0/24;
real_ip_header    X-Forwarded-For;
```

配置后 $remote_addr 直接变回真实客户端 IP，日志、限流、防盗链全部跟着受益。这里有个坑：信任网段配得太宽（比如放行 0.0.0.0/0），客户端可以伪造 X-Forwarded-For 头冒充任意 IP，set_real_ip_from 只写自己可控的代理网段。

### 4.2 错误日志

错误日志默认路径为 /var/log/nginx/error.log。

| 项目 | 说明 |
| --- | --- |
| Syntax | error_log file [level]; |
| Default | error_log logs/error.log error; |
| Context | main, http, mail, stream, server, location |

```nginx
error_log  /var/log/nginx/error.log warn;
```

错误日志级别（由详到简）：

| 级别 | 说明 |
| --- | --- |
| debug | 调试级别，服务运行的状态信息和错误信息详细显示，信息最多 |
| info | 信息级别，只显示重要的运行信息和错误信息 |
| notice | 通知级别，对更加重要的信息进行通知说明 |
| warn | 警告级别，可能出现了一些错误信息，但不影响服务运行 |
| error | 错误级别，服务运行已经出现了错误，需要进行纠正，推荐选择 |
| crit | 严重级别，必须进行修改调整 |
| alert | 严重警告级别，即警告，而且必须进行错误修改 |
| emerg | 灾难级别，服务已经不能正常运行，信息最少 |

> **注意：** 排错阶段可临时把级别调到 info 甚至 debug，日志量会显著增加，定位问题后务必调回 warn。

补充两点：debug 级别要输出完整调试信息，需要编译时带 --with-debug（nginx.org 官方源的包已内置）；生产长期开 debug 一天能写满一块盘，用完即关。

### 4.3 日志切割

> **注意：** 日志文件信息需要做切割处理，否则会增长到几个 GB 甚至更大，建议定期按天切割并归档压缩，避免磁盘占满影响服务。

logrotate 托管 Nginx 日志的关键配置（/etc/logrotate.d/nginx）：

```conf
/var/log/nginx/*.log {
    daily                # 按天切割
    missingok            # 日志缺失时不报错
    rotate 30            # 保留 30 份
    compress             # 切割后压缩
    delaycompress        # 延迟一天压缩，避免正在写入
    notifempty           # 空文件不切割
    create 0640 nginx adm
    sharedscripts
    postrotate
        if [ -f /var/run/nginx.pid ]; then
            kill -USR1 `cat /var/run/nginx.pid`
        fi
    endscript
}
```

`kill -USR1`（等价于 `nginx -s reopen`）让 Nginx 重新打开日志文件，无需重启服务即可完成切割，是生产环境的推荐做法。

## 五、location 匹配规则

location 指令由 ngx_http_core_module 模块提供，用于匹配 URI，也常用于错误页面的优雅显示。

指令用法：

```text
Syntax:	location [ = | ~ | ~* | ^~ ] uri { ... }
        location @name { ... }
Default:	—
Context:	server, location
```

匹配方式与优先级：

| 匹配方式 | 示例 | 优先级 |
| --- | --- | --- |
| 精确匹配 | location = / | 01（最高） |
| 优先前缀匹配 | location ^~ /images/ | 02 |
| 目录前缀匹配 | location /documents/ | 03 |
| 正则匹配（不区分大小写） | location ~* \.(gif\|jpg\|jpeg)$ | 03 |
| 默认匹配 | location / | 04（最低） |

> **注意：** 正则命中优先于全部普通前缀匹配；多个普通前缀同时命中时取路径最长的一个；多个正则同时命中时取书写顺序最靠前的一个。`location @name` 是命名 location，只能被 try_files 或 error_page 内部跳转，不能被外部请求直接命中。

排查 location 不生效有个笨办法但最有效：临时在每个 location 里写一条不同的 `add_header X-Debug "rule-B";`，重载后 curl -I 一看响应头，走的是哪条规则一目了然，比反复改配置瞎猜快得多。error_page 404 /404.html; 的跳转是内部重定向，URI 不变、浏览器地址栏不变，与 return 301 的外部跳转是两回事。try_files 的最后一个参数也可以指向命名 location（如 @fallback），把回退逻辑集中管理，多个 location 共用同一个兜底。

配置示例：

```nginx
location = / {
    # 精确匹配，优先级 01 最高
    [ configuration A ]
}

location / {
    # 默认匹配，优先级 04 最低
    [ configuration B ]
}

location /documents/ {
    # 按照目录进行匹配，优先级 03
    [ configuration C ]
}

location ^~ /images/ {
    # 优先匹配，不识别 URI 信息中的符号信息，优先级 02
    [ configuration D ]
}

location ~* \.(gif|jpg|jpeg)$ {
    # 不区分大小写进行匹配，优先级 03
    [ configuration E ]
}
```

错误页面优雅显示示例，不同 location 可以返回不同的 404 页面：

```nginx
location /docs {
    root         /html/www;
    error_page   404  /demo.jpg;
}
location /media {
    root         /html/www;
    error_page   404  /demo2.jpg;
}
```

## 六、页面跳转（rewrite）

页面跳转功能由 ngx_http_rewrite_module 模块实现。

指令用法：

```text
Syntax:	rewrite regex replacement [flag];
Default:	—
Context:	server, location, if
```

rewrite 按照“匹配的正则信息，替换成什么信息”的方式工作，规则示例：

```nginx
rewrite www.example.com/(.*) http://www.example.com/$1 permanent;
```

跳转方式：

| 跳转方式 | 状态码 | 说明 |
| --- | --- | --- |
| 永久跳转（permanent） | 301 | 会将跳转信息进行缓存 |
| 临时跳转（redirect） | 302 | 不会缓存跳转信息 |

301 被浏览器缓存后，改规则用户侧不生效，测试一律用 302，验证通过再换成 301 上线。rewrite 的替换串里 $1、$2 引用正则捕获组，$args 会自动保留（除非替换串以 ? 结尾显式丢弃），带参数的 URL 重写不用手动拼参数。

### 6.1 无限跳转的解决方法

第一种方法：利用不同的 server 区块配置打破循环：

```nginx
server {
    server_name  example.com;
    rewrite ^/(.*) http://www.example.com/$1 permanent;
}
```

第二种方法：利用 if 判断实现打破循环：

```nginx
if ($host ~* "^example.com$") {
    rewrite ^/(.*) http://www.example.com/$1 permanent;
}
```

多级路径跳转示例：

```console
www.example.com/demo01/demo02/demo.jpg --- www.example.com/demo.jpg
```

> **注意：** 更简单的场景优先用 `return 301 https://$host$request_uri;`，效率高于 rewrite；判断无限跳转可以用 `curl -I http://example.com` 观察 Location 链，或在 error.log 中开启 rewrite_log 排查。

last 与 break 也要分清：last 用重写后的 URI 重新走一遍 location 匹配，可能跳进另一个 location；break 停在当前 location 内直接处理。伪静态把 /article/1.html 重写成 /article.php?id=1 时用 last，让请求落到 .php 的处理 location；确认重写结果在当前块内就能处理完的，用 break 少绕一轮匹配。选错轻则多匹配一次，重则死循环。

## 七、生产环境完整配置案例

下面给出一份可直接投产的反向代理 + 动静分离 + 缓存 + 日志完整配置，按 /etc/nginx/nginx.conf 与 /etc/nginx/conf.d/prod.conf 两部分组织。

主配置 /etc/nginx/nginx.conf：

```nginx
user  www;
worker_processes  auto;                       # 与 CPU 核数一致
worker_rlimit_nofile 65535;                   # 提升文件描述符上限
error_log  /var/log/nginx/error.log warn;
pid        /var/run/nginx.pid;

events {
    use epoll;
    worker_connections  10240;
    multi_accept        on;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    log_format  main  '$remote_addr - $remote_user [$time_local] "$request" '
                      '$status $body_bytes_sent $request_time "$http_referer" '
                      '"$http_user_agent" "$http_x_forwarded_for"';
    access_log  /var/log/nginx/access.log  main;

    sendfile           on;
    tcp_nopush         on;
    tcp_nodelay        on;
    keepalive_timeout  65;

    gzip               on;
    gzip_min_length    1k;
    gzip_comp_level    5;
    gzip_types         text/plain text/css application/javascript application/json;

    # 缓存区定义（仅 http 块可用）
    proxy_cache_path   /var/cache/nginx levels=1:2 keys_zone=prod_cache:64m inactive=1d max_size=20g;

    include /etc/nginx/conf.d/*.conf;
}
```

站点配置 /etc/nginx/conf.d/prod.conf：

```nginx
# 后端应用服务器组
upstream app_backend {
    server 10.0.0.11:8080 weight=1 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 weight=1 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 backup;
}

# 状态页（仅内网）
server {
    listen       80;
    server_name  status.example.com;
    location = /basic_status {
        stub_status;
        allow  10.0.0.0/24;
        deny   all;
    }
}

# 生产站点
server {
    listen       80;
    server_name  www.example.com;

    # 静态资源：Nginx 直接返回 + 浏览器缓存
    location ~* \.(jpg|jpeg|png|gif|css|js|svg|woff2?)$ {
        root    /html/www;
        expires 7d;
        access_log /var/log/nginx/static.log main;
    }

    # 动态请求：反向代理 + 页面缓存
    location / {
        proxy_pass         http://app_backend;
        proxy_set_header   Host             $host;
        proxy_set_header   X-Real-IP        $remote_addr;
        proxy_set_header   X-Forwarded-For  $proxy_add_x_forwarded_for;

        proxy_cache        prod_cache;
        proxy_cache_valid  200 302 10m;
        proxy_cache_valid  404 1m;
        add_header         X-Cache-Status $upstream_cache_status;
    }

    # 错误页面优雅显示
    error_page 500 502 503 504 /50x.html;
    location = /50x.html {
        root  /html/www;
    }
}
```

> **注意：** 生产环境务必加 `listen 443 ssl;` 并将 80 跳转 HTTPS，证书使用 CA 签发（Let's Encrypt 等）；日志中追加 $request_time 便于统计慢请求；缓存区目录 /var/cache/nginx 需要提前创建并授权给 Nginx 运行用户。

这套配置上生产前，先在测试环境用同版本 Nginx 过一遍 nginx -t 加 ab 压测。里面的每一段（upstream、状态页、静态、代理缓存、错误页）都能单独摘出来复用，不必整套照搬。压测时单独压一遍 /basic_status，验证 allow/deny 是否真拦住了外网；把 nginx -t 挂进发布流程——配置改动先在测试机过 -t，再灰度一台机器 reload，观察十分钟无异常再全量，回滚就是改回配置再 reload。

## 八、性能调优参数表

| 参数 | 作用域 | 推荐值 | 说明 |
| --- | --- | --- | --- |
| worker_processes | main | auto | 与 CPU 核数一致 |
| worker_rlimit_nofile | main | 65535 | 解除文件描述符限制 |
| worker_connections | events | 10240 | 单 worker 最大连接数 |
| use | events | epoll | Linux 下默认即 epoll |
| multi_accept | events | on | 一次接受多个新连接 |
| sendfile | http | on | 零拷贝传输静态文件 |
| tcp_nopush | http | on | 配合 sendfile 减少报文数 |
| tcp_nodelay | http | on | keepalive 连接下即时发送 |
| keepalive_timeout | http | 65 | 长连接超时（秒） |
| keepalive_requests | http | 1000 | 单连接最多处理的请求数 |
| open_file_cache | http | max=10000 inactive=60s | 缓存文件句柄与元数据 |
| open_file_cache_valid | http | 30s | 缓存校验间隔 |
| client_header_timeout | http | 15 | 读取请求头超时 |
| client_body_timeout | http | 15 | 读取请求体超时 |
| send_timeout | http | 15 | 发送响应超时 |
| reset_timedout_connection | http | on | 重置超时连接释放资源 |
| client_max_body_size | http | 20m | 允许的请求体大小（防 413） |
| client_body_buffer_size | http | 128k | 请求体内存缓冲 |
| proxy_connect_timeout | location | 5s | 与后端建连超时 |
| proxy_read_timeout | location | 60s | 读取后端响应超时 |
| limit_req | location | 按业务 | 请求速率限制 |
| limit_conn | location | 按业务 | 并发连接限制 |

> **注意：** 参数不是越大越好：worker_connections 要与 worker_rlimit_nofile 和系统 `ulimit -n` 匹配；gzip_comp_level 每提高 1 级 CPU 消耗明显上升，5 是通用甜点位；调优后必须用 `nginx -t` 验证并以 ab、wrk 等工具压测对比。

调参前先确认瓶颈真在 Nginx：top 看 CPU、iostat 看磁盘、ss -s 看连接堆积，这些前置数据比任何参数都管用——参数只是放大硬件能力，硬件不够时调参是安慰剂。调优的顺序感：先解决能不能用（进程数、连接数、fd 上限），再解决快不快（sendfile、gzip、缓存），最后才是稳不稳（超时、限流、监控），顺序反了会把时间花在收益最小的地方。

## 九、常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 502 Bad Gateway | 后端（php-fpm/Tomcat/业务进程）未启动；fastcgi_pass 或 proxy_pass 地址端口错误；SCRIPT_FILENAME 路径不对 | `systemctl status php-fpm`、`ss -lntp \| grep 9000`、`tail -f /var/log/nginx/error.log` | 启动后端；核对转发地址；修正 $document_root 路径 |
| 504 Gateway Timeout | 后端执行超时（慢 SQL、死循环）；代理超时设置过短 | `tail /var/log/nginx/error.log`（upstream timed out）、`mysqladmin processlist` | 调大 proxy_read_timeout；优化后端逻辑 |
| 403 Forbidden | 站点目录权限不足；deny 规则命中；目录无首页且未开 autoindex | `ls -ld /html/www`、`namei -l /html/www/index.html` | chmod/chown；调整 allow/deny；补首页或开 autoindex |
| 404 Not Found | root 与文件实际位置不符；location 匹配错；伪静态规则未生效 | `ls -lR /html/www`、`curl -I http://localhost/xx.html` | 修正 root/location；补齐文件；检查 rewrite |
| 413 Request Entity Too Large | client_max_body_size 小于上传文件体积 | 上传复现并查看响应 | 调大 client_max_body_size |
| 499（日志中） | 客户端主动断开，多为等待超时后取消 | 结合 $request_time 分析 | 优化后端响应速度，增大客户端容忍度 |
| 500 Internal Server Error | 程序代码错误；文件权限问题；htpasswd 文件异常 | `tail /var/log/nginx/error.log`、查看应用日志 | 修复程序；修正权限与文件格式 |
| 页面样式错乱 | MIME 类型未识别（mime.types 缺失）；静态请求被动态 location 拦截 | `curl -I http://www.example.com/a.css` 看 Content-Type | 确认 include mime.types；调整 location 顺序 |

### 辨析：502 与 504 的分水岭

两者都发生在代理等后端这一段，分水岭在于连接与响应的状态：

- 502：连接建不起来，或后端回了废包——进程没起、端口不对、php-fpm 崩溃、返回畸形响应。error.log 里常见 connect() failed（111: Connection refused）；
- 504：连接建好了，但在 proxy_read_timeout 内没等到完整响应——慢 SQL、接口卡死、后端假死。error.log 里常见 upstream timed out (110: Connection timed out)。

看 error.log 的报错关键词比猜状态码快得多：Connection refused 基本是进程和端口问题，timed out 才往慢逻辑方向查。另外 503 多来自主动拒绝：limit_req 触发、后端自己返回 503 被透传、或维护页配置的 return 503。日志里偶尔见到 499：Nginx 自定义码，客户端在响应返回前主动断开，多为用户等不及或客户端超时太短，499 扎堆先查后端耗时，别当垃圾数据过滤。

## 十、日志分析实战

以 main 格式的 access.log 为例，字段位置：$1 客户端 IP、$4 时间、$7 请求 URI、$9 状态码、$10 响应字节数、$request_time 视格式位置而定。

```bash
# PV：总请求量（页面浏览量）
wc -l /var/log/nginx/access.log

# UV：独立访客数（按客户端 IP 去重近似）
awk '{print $1}' /var/log/nginx/access.log | sort | uniq | wc -l

# 统计访问来源 IP 前 10 名
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10

# 统计被访问页面次数前 10 名
awk '{print $7}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10

# 统计 HTTP 状态码分布
awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn

# 抓出返回 404 的来源 IP 前 10 名
awk '$9==404 {print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10

# 统计响应体流量最大的 10 个页面
awk '{print $7, $10}' /var/log/nginx/access.log | sort -k2 -rn | head -10

# 按小时统计请求趋势（$4 形如 10/Oct/2026:13:55:36）
awk '{print $4}' /var/log/nginx/access.log | cut -c2-15 | uniq -c | sort -k2 | tail -24

# 统计各浏览器（UA）占比
awk -F'"' '{print $6}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -10
```

可进一步结合 IP 归属地统计各地访问量，例如按来源统计：北京 192.168.10.1、192.168.11.2，深圳 192.169.11.1，上海 192.170.12.1 等。

> **注意：** UV 按 IP 去重只是近似值（NAT 出口会合并多个真实用户）；精确 UV 需要按 Cookie/Session 统计。日志量大的场景建议用 ELK（Elasticsearch + Logstash + Kibana）或 GoAccess 等工具做可视化分析。

慢请求定位有个省事的路子：用 $request_time 减 $upstream_response_time，差值大说明耗时在 Nginx 自身（缓冲、网络、客户端慢），差值小说明耗时在后端。生产上栽过的教训：页面慢、$request_time 高达 3 秒，团队盯着 Nginx 调了一下午参数，最后发现瓶颈在一条慢 SQL。先做这道减法，再决定去哪一层找答案。日常统计慢请求分布：对 $request_time 做分桶，超过 1 秒的请求占比一旦超过 5%，就该按前面的减法拆分 Nginx 与后端的责任了。

## 十一、平滑升级与热部署

### 配置热更新

```bash
nginx -t && nginx -s reload        # 语法检查通过后平滑重载
```

reload 不会中断存量请求：master 启动新 worker 接管新连接，旧 worker 处理完手头请求后退出。

### 日志热切换

```bash
nginx -s reopen                     # 或 kill -USR1 `cat /var/run/nginx.pid`
```

配合 logrotate 的 postrotate 使用，实现不重启服务完成日志切割。

### 版本热升级（二进制热部署）

仅适用于源码编译安装的 Nginx，步骤简述如下：

1. 备份现有安装目录与配置：`cp -a /usr/local/nginx /usr/local/nginx.old`；
2. 下载新版本源码，用与旧版本相同的 configure 参数重新 `./configure && make`（不要执行 make install）；
3. 备份并替换二进制：`mv /usr/local/nginx/sbin/nginx /usr/local/nginx/sbin/nginx.old && cp objs/nginx /usr/local/nginx/sbin/nginx`；
4. 发送 USR2 信号启动新版 master：`kill -USR2 $(cat /var/run/nginx.pid)`，此时新旧 master 并存，旧 worker 继续服务；
5. 发送 WINCH 信号让旧 worker 优雅退出：`kill -WINCH $(cat /var/run/nginx.pid.oldbin)`；
6. 验证新版本工作正常后，发送 QUIT 信号退出旧 master：`kill -QUIT $(cat /var/run/nginx.pid.oldbin)`。

> **注意：** yum/rpm 安装的 Nginx 升级用 `dnf upgrade nginx` 即可（服务会短暂重启）；热升级的核心是不中断服务地替换二进制，操作前务必备份配置与二进制，并在测试环境验证。

热升级后别急着退旧 master：新版本至少观察一个完整业务高峰（error.log 无新增报错、状态页指标正常），再发 QUIT，回退窗口就是这么留出来的。

## 小结

1. autoindex 可快速搭建文件共享服务器，注意首页文件与 mime.types 对展示效果的影响，中文乱码用 charset 解决。
2. server_name 支持配置多个域名，便于访问测试与站点定位。
3. stub_status 状态页提供连接与请求级别的监控数据，是日常巡检的常用手段。
4. 访问日志通过 log_format 自定义格式，$http_referer 与 $http_user_agent 在排障与防盗链中最常用。
5. location 五种匹配方式优先级不同，精确匹配最高、默认匹配最低，error_page 可定制错误页面。
6. rewrite 支持 301/302 跳转，出现无限跳转时用独立 server 块或 if 判断打破循环。
7. 生产配置三段式：静态直接返回 + 动态反向代理 + 热点页面缓存，日志追加 $request_time 便于慢请求分析。
8. 性能调优先调 worker_processes/worker_connections/文件描述符，再调 sendfile、tcp_nopush/nodelay、gzip 与 open_file_cache。
9. 502 查后端进程与转发地址，504 查超时设置，403 查权限与访问规则，404 查路径映射。
10. 平滑升级不中断服务：reload 用于配置、USR1 用于日志、USR2+WINCH+QUIT 用于二进制热替换。

## 自测题

1. stub_status 页面中 Waiting 数值持续偏高，可能说明什么问题？应该从哪些方向排查？
2. 网站突然大量 502，请给出至少三条排查命令与对应的处理思路。
3. 写出统计昨天 UV 与状态码分布的 awk 命令（假设 access.log 在 /var/log/nginx/ 下）。
4. `nginx -s reload` 为什么不会中断正在处理的请求？日志切割用什么信号做到不重启服务？
5. 上传大文件报 413 Request Entity Too Large，如何调整？该参数作用域是什么？

> **答案：**
> 1. Waiting 偏高说明大量连接已建立但既不读请求也不写响应，通常是慢客户端拖住连接，或后端响应慢导致请求排队。排查方向：看后端（php-fpm/业务进程）状态与响应时间、检查 proxy_read_timeout 等超时配置、结合 access.log 的 $request_time 与 $upstream_response_time 定位慢请求、观察是否存在异常连接（攻击）。
> 2. 示例：`systemctl status php-fpm`（后端是否存活）、`ss -lntp | grep 9000`（转发端口是否在监听）、`tail -f /var/log/nginx/error.log`（看 connect() failed 还是 upstream timed out）。处理：后端未启动则启动；端口不对则修正 fastcgi_pass/proxy_pass；权限问题则统一 nginx 与 php-fpm 运行用户。
> 3. UV：`awk '{print $1}' /var/log/nginx/access.log | sort | uniq | wc -l`；状态码分布：`awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn`。按日期筛选时可先 grep 日期字段，如 `grep "$(date -d yesterday +%d/%b/%Y)" access.log`。
> 4. reload 时 master 重新加载配置并启动新 worker 接收新连接，旧 worker 继续处理完存量请求后优雅退出，因此不断流。日志切割使用 `nginx -s reopen`（即 kill -USR1）让 Nginx 重新打开日志文件，无需重启。
> 5. 调大 `client_max_body_size`，如 `client_max_body_size 50m;`，可写在 http、server 或 location 块（作用域为 http/server/location）。同时注意后端（如 PHP 的 upload_max_filesize、post_max_size）也要同步调大，只改 Nginx 仍会在后端报错。
