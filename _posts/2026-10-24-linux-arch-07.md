## 上节回顾：SSH 远程管理服务

Ansible 默认基于 SSH 工作，所以先回顾 SSH 的关键知识点。

### SSH 与 telnet 的对比

| 远程服务 | 数据传输方式 | 默认端口 |
| --- | --- | --- |
| `ssh` | 数据加密传输 | 22 |
| `telnet` | 数据明文传输 | 23 |

### SSH 工作原理

涉及一对密钥：**私钥** 与 **公钥**，有两个用途：

1. 对数据进行加密处理
2. 对用户访问进行认证

### SSH 远程连接的两种方式

- 基于**口令**的方式进行连接
- 基于**密钥**的方式进行连接

### 基于密钥连接的部署方式

**第一个历程：创建密钥对（管理端服务器）**

```bash
ssh-keygen -t 密钥的类型(dsa|rsa)
```

**第二个历程：将公钥进行分发（被管理端服务器）**

```bash
ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.31
```

### 如何批量分发公钥

批量分发时会遇到三个典型障碍，逐一解决即可脚本化：

**01. 需要输入连接确认信息 yes/no**

```bash
ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.31 "-o StrictHostKeyChecking=no"
```

**02. 第一次连接需要输入密码**

```bash
yum install -y sshpass
sshpass -p'<your-password>' ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.31 "-o StrictHostKeyChecking=no"
```

**03. 远程服务器 SSH 服务端口号被改动过**

```bash
sshpass -p'<your-password>' ssh-copy-id -i /root/.ssh/id_dsa.pub root@172.16.1.31 -p 52113 "-o StrictHostKeyChecking=no"
```

### 基于密钥连接的排错思路

1. 利用命令进行连接测试
2. 检查公钥在被管理主机上是否存在，并且与管理端公钥信息是否相同
3. 利用公钥分发命令重新分发公钥
4. 检查脚本的编写
5. 调试脚本功能 —— `sh -x`

## Ansible 批量管理服务介绍

### 批量管理服务的意义

1. 提高工作的效率
2. 提高工作准确度
3. 减少维护的成本
4. 减少重复性工作

### 批量管理服务的功能

1. 可以实现批量系统操作配置
2. 可以实现批量软件服务部署
3. 可以实现批量文件数据分发
4. 可以实现批量系统信息收集

### 辨析：批量管理的三条路线 {: .sec-bianxi}

从手工到自动化，批量管理有三条递进的路线。第一条是纯 shell 脚本：零依赖、灵活，但每换一个需求都要重写循环，没有状态检查，跑错一次后果自负；第二条是 SSH 密钥互信：解决的是认证问题，它是三条路线共同的地基，上一篇的批量分发脚本就属于前两条路线的组合；第三条才是 Ansible——在密钥之上提供幂等模块、并发执行和编排能力，相当于把"写脚本"这件事标准化了。三条路线不是替代关系，密钥分发永远是 Ansible 的前置条件。

## 原理解析：Ansible 架构与工作原理 {: .sec-why}

Ansible 最大的特点是**无 agent**：被管理端不需要安装任何客户端程序，管理端也不需要常驻服务。一次 ad-hoc 命令的完整执行流程如下：

1. 管理端解析命令行参数，读取主机清单（inventory），展开出本次要操作的主机列表。
2. 管理端通过 SSH 并行连接各目标主机（并发数由 `forks` 控制，默认 5）。
3. 管理端把**模块代码**传输到被管理端的临时目录（`~/.ansible/tmp/` 下）。
4. 被管理端用本机 Python 解释执行模块，模块把执行结果以 JSON 格式返回。
5. 管理端解析 JSON，向终端输出 `ok` / `changed` / `failed` 等状态，随后删除临时文件。

> **注意：** 正因为被管理端要"用 Python 执行模块"，被管主机必须装有 Python（Python 2.7 或 3.5+，视 Ansible 版本而定）；这也是 Ansible 与"纯 SSH 执行命令"的本质区别 —— 它执行的是结构化模块，而不是一串难以解析的文本输出。

### 什么是幂等性

**幂等性**说白了就是"重复执行不出事"：同一个操作跑一次和跑多次结果一致。Ansible 的模块大多先检查目标主机的当前状态，已经满足就不做变更：

| 场景 | 非幂等的做法 | Ansible 幂等的做法 |
| --- | --- | --- |
| 装软件 | 再执行一次 `yum install` 也报成功但无意义 | `yum` 模块检测已安装则直接返回 `ok` |
| 推文件 | 无论内容是否变化都覆盖 | `copy` 模块比对文件校验值，一致则跳过 |
| 建目录 | 已存在报错 | `file` 模块 `state=directory` 已存在则跳过 |

幂等性让剧本可以**反复执行**而不会把系统改乱，这是 Ansible 能支撑"配置即代码"的基石。反过来，自己写 `shell` 模块拼命令时，如果命令本身不幂等（比如 `echo >> 文件`），执行几次就会追加几行。

幂等不是银弹：它由模块保证，命令拼进 `shell` 就失守。常见的破坏点——命令里带时间戳（`tar czf backup-$(date +%F).tar.gz` 每天都生成新文件）、`>>` 追加重定向、用 shell 拼 `useradd` 而不是 `user` 模块。剧本里出现这类命令，要么换模块，要么用 `creates` / `changed_when` 圈住副作用。

### 知识卡片：Ansible 核心概念卡 {: .sec-card}

| 概念 | 一句话解释 |
| --- | --- |
| 无 agent | 被管理端不装软件，靠 SSH + Python 执行模块 |
| inventory | 主机清单，定义"管理哪些机器"，INI 或 YAML 格式 |
| module | 模块，一次具体动作的最小单元（装包、拷文件、起服务） |
| ad-hoc | 临时命令，`ansible ... -m 模块 -a 参数`，适合一次性操作 |
| playbook | 剧本，把多个任务按顺序编排成 YAML 文件，可重复执行 |
| handler | 处理器，由任务 `notify` 触发，通常用于"配置变更后重启服务" |
| facts | 事实，被管主机自动上报的系统信息（IP、内存、发行版等） |
| 幂等 | 重复执行结果一致，剧本可反复运行 |

## Ansible 服务部署

角色先分清：**控制机**（管理端）只装 Ansible、存主机清单和剧本，自己不跑业务；**被控机**什么都不装，只要求 SSH 可达且装有 Python。整套架构里唯一"重"的就是控制机——模块由它临时推送到被控端，执行结果也由它汇总。生产上通常拿一台独立的内网机器做控制机，不与其他服务混部，控制机挂了所有自动化都停摆。

在管理端服务器上进行操作。

### 第一个历程：安装部署软件

```bash
yum install -y ansible     # 需要依赖 epel 的 yum 源
```

安装完成后有三个核心路径需要记住：

| 路径 | 说明 |
| --- | --- |
| `/etc/ansible/ansible.cfg` | Ansible 服务配置文件 |
| `/etc/ansible/hosts` | 主机清单文件，定义可以管理的主机信息 |
| `/etc/ansible/roles` | 角色目录 |

**其他安装方式：**

```bash
# pip 安装（想要指定版本时）
pip install ansible          # 完整包
pip install ansible-core     # 仅核心引擎，模块在 collections 里按需安装
```

### 第二个历程：编写主机清单文件

```bash
vim /etc/ansible/hosts
```

这里写的是全局默认清单。实际项目更推荐把清单放进项目目录（配合项目级 `ansible.cfg`），多套环境互不干扰；全局清单留给临时操作与测试机。

### 主机清单 inventory 详解

inventory 就是"被管理机器的花名册"，支持 INI 与 YAML 两种写法。

**INI 格式（默认写法）：**

```ini
# 01. 直接写主机（IP 或域名）
172.16.1.31

# 02. 组：方括号内是组名，组内一行一台
[web]
172.16.1.7
web01.example.com ansible_user=root ansible_port=22

# 03. 组变量：对组内所有主机生效
[web:vars]
ansible_user=deploy
ansible_python_interpreter=/usr/bin/python3

# 04. 组的嵌套：children 表示"这个组包含下面这些组"
[prod:children]
web
nfs

# 05. 主机变量：别名写法，连接参数跟在主机名后面
[nfs]
nfs01 ansible_host=172.16.1.31
```

**YAML 格式（结构更清晰，适合程序生成）：**

```yaml
all:
  children:
    web:
      hosts:
        172.16.1.7:
          ansible_port: 22
    nfs:
      hosts:
        172.16.1.31:
```

**主机模式（pattern）**：ad-hoc 第一个参数除了单个主机，还支持模式表达式：

| 模式 | 含义 |
| --- | --- |
| `all` | 清单里全部主机 |
| `web` | web 组全部主机 |
| `web:nfs01` | web 组与 nfs01 的并集 |
| `web:!nfs01` | web 组里排除 nfs01 |
| `172.16.1.*` | 按通配匹配主机名或地址 |

> **注意：** 变量优先级上，**主机变量优先于组变量**；组变量写在 `[组名:vars]` 段，主机变量跟在主机行后面。清单支持分组管理（web / db / nfs），也可以按环境拆成多个清单文件，用 `-i` 指定。

新手最常踩的清单错误：组名拼错（`ansible web` 报 `could not match`）、主机没缩进到组里、YAML 格式清单里混用 INI 的 `[组:vars]` 语法。写完清单先用 `ansible-inventory --graph` 或 `--list` 看解析结果再跑命令——清单是地基，地基歪了后面全歪。

清单还有第三种形态值得知道：把 `-i` 指向一个目录，Ansible 会合并目录下所有清单文件，多环境按 `production/`、`staging/` 子目录各放一套；云上机器频繁启停时更进一步用动态清单脚本按标签实时拉取，起步阶段静态文件完全够用。

### ansible.cfg 常用配置

```ini
[defaults]
inventory = /etc/ansible/hosts
remote_user = root
forks = 10
host_key_checking = False
gathering = smart
roles_path = /etc/ansible/roles
deprecation_warnings = False
```

| 配置项 | 作用 |
| --- | --- |
| `inventory` | 主机清单路径 |
| `remote_user` | 默认远程登录用户 |
| `forks` | 默认并发数 |
| `host_key_checking` | 是否校验 known_hosts，测试环境可关，生产建议保持开启 |

关于 `host_key_checking = False` 再多说一句：它跳过的是"对方是不是我认识的那台机器"的校验，等于放弃了中间人攻击防线。生产更稳的做法是改成 `accept-new`（首次自动收指纹、之后严格校验），或在部署系统里先跑 `ssh-keyscan` 统一收指纹。
| `gathering` | facts 收集策略，`smart` 表示有缓存则不重复收集 |
| `roles_path` | 角色目录搜索路径 |
| `deprecation_warnings` | 是否显示弃用警告 |

> **注意：** ansible.cfg 的查找顺序是：当前目录 `./ansible.cfg` → 当前用户家目录 `~/.ansible.cfg` → `/etc/ansible/ansible.cfg`，先找到先用。所以把配置和清单放进项目目录，就能实现"一个项目一套配置"。

想进一步压缩 facts 开销可以配 fact 缓存：`fact_caching = jsonfile` 加 `fact_caching_timeout`，收集结果落盘，超时前不再重复收集。主机几百台时，这个配置能把剧本起步时间从分钟级压到秒级。

### 第三个历程：测试是否可以管理多个主机

```bash
ansible all -a "hostname"
```

```console
[root@m01 scripts]# ansible all -a "hostname"
172.16.1.41 | CHANGED | rc=0 >>
backup

172.16.1.7 | CHANGED | rc=0 >>
web01

172.16.1.31 | CHANGED | rc=0 >>
nfs01
```

注意这里的 `ping` 与后面速查表里的 `ping` 模块都不是网络层的 ICMP ping：它是通过 SSH 通道在被控端跑一个 Python 模块再返回 `pong`。所以 ping 通 = 密钥、Python、SSH 网络三者全部正常，一个模块测三件事，这也是它被当作部署后第一验证手段的原因。

## Ansible 服务架构信息

要让 Ansible 正常工作，需要落实以下五件事：

| 序号 | 组成 | 说明 |
| --- | --- | --- |
| 1 | 主机清单配置 | 在 `/etc/ansible/hosts` 中定义被管理主机 |
| 2 | 软件模块信息 | Ansible 通过模块完成具体动作 |
| 3 | 基于密钥连接主机 | 管理端需要先把公钥分发到被管理端 |
| 4 | 主机需要关闭 selinux | 被管理端 selinux 未关闭会影响管理 |
| 5 | 软件剧本功能 | 用 playbook 实现一键化编排 |

> **注意：** 第 4 条严格说是"要么关闭 selinux，要么安装 `libselinux-python`"（详见中篇）；生产环境出于安全考虑不能随便关 selinux 时，装齐依赖包即可正常管理。

## Ansible 软件模块应用

Ansible 官方文档：https://docs.ansible.com/

### 模块应用语法格式

```bash
ansible 主机名称/主机组名称/主机地址信息/all  -m(指定应用的模块信息)  模块名称  -a(指定动作信息)  "执行什么动作"
```

即：`ansible` + 目标 + `-m` 模块名 + `-a` 模块参数。

模块文档随查随用是基本功：`ansible-doc -l | grep 关键字` 找模块，`ansible-doc -s 模块名` 看参数速览，`ansible-doc 模块名` 里直接搜 `EXAMPLES` 段——示例是上手最快的入口，比任何博客都准。

ad-hoc 与 playbook 的分工要趁早分清：临时查状态、重启单个服务、验证连通性这类一次性动作，用 ad-hoc 敲完就走；需要重复执行、有先后顺序、要进 Git 仓库留档的操作，一律沉淀成 playbook。判断标准很简单——这条命令明天还要不要敲一遍？要，就写进剧本。从 ad-hoc 到剧本的演进路径也自然：先把重复敲的命令记下来 → 抽出可变参数做变量 → 按 play 分组 → 进版本控制。

## ad-hoc 命令进阶

日常排查和临时操作都靠 ad-hoc，下面几个参数用熟了能省不少事：

| 参数 | 作用 |
| --- | --- |
| `-i 清单文件` | 指定主机清单，默认 `/etc/ansible/hosts` |
| `-f 并发数` | 并行处理多少台主机，默认 5；机器多可调大，如 `-f 20` |
| `-u 用户` | 指定远程登录用户 |
| `-k` | 询问远程登录密码（还没分发密钥时用） |
| `-b` / `--become` | 提权执行，相当于 sudo |
| `--become-user 用户` | 指定提权成哪个用户，默认 root |
| `-K` | 询问 sudo 密码 |
| `--list-hosts` | 只列出本次匹配到的主机，不真正执行 |
| `--check` | 模拟执行，只报告"会改什么"，不真正改 |
| `--diff` | 显示文件变更前后差异，配合 `--check` 或 copy/template 模块使用 |

```bash
# 查看哪些主机会被操作（先确认目标，再动手）
ansible web -i /etc/ansible/hosts --list-hosts

# 以 deploy 用户登录、sudo 提权执行
ansible all -u deploy -b -m service -a "name=nginx state=restarted"

# 模拟安装，看看哪些主机会发生变化
ansible all -m yum -a "name=iotop state=installed" --check
```

`--check` 不是所有模块都支持：`copy`、`file`、`yum` 这类资源型模块支持得很好，`shell` / `command` 天然无法预判副作用，check 模式下会误报 changed。所以预演结果要区别对待——文件类的变更可信，命令类的变更仅供参考。

### 辨析：什么时候不该用 Ansible {: .sec-bianxi}

三类场景别硬上。一是单机一次性操作：直接 SSH 敲命令更快，写剧本纯属浪费。二是毫秒级响应的实时编排（服务注册发现、动态调度）：Ansible 的 SSH 推送模型延迟在秒级，天然不合适。三是动态密钥管理：vault 只解决静态数据的加密，运行期密钥应交给 Vault / KMS 类系统。把工具用在它擅长的场景——批量、幂等、可编排。

## 命令类型模块

### command（默认模块）

> `command – Executes a command on a remote node`：在一个远程主机上执行一个命令。

**简单用法：**

```bash
ansible 172.16.1.31 -m command -a "hostname"
```

```console
172.16.1.31 | CHANGED | rc=0 >>
nfs01
```

> **注意：** `command` 是默认模块，不写 `-m` 时就是它，例如 `ansible all -a "hostname"`。

**扩展应用：**

| 参数 | 官方说明 | 中文含义 |
| --- | --- | --- |
| `chdir` | Change into this directory before running the command. | 在执行命令之前对目录进行切换 |
| `creates` | If it already exists, this step won't be run. | 如果文件存在了，不执行命令操作 |
| `removes` | If it already exists, this step will be run. | 如果文件存在了，这个步骤将执行 |
| `free_form`（必填） | The command module takes a free form command to run. | 使用 command 模块时，`-a` 参数后面必须写上一个合法的 Linux 命令 |

```bash
# 1) chdir：执行前切换目录
ansible 172.16.1.31 -m command -a "chdir=/tmp touch test.txt"

# 2) creates：文件已存在则跳过
ansible 172.16.1.31 -m command -a "creates=/tmp/hosts touch test.txt"

# 3) removes：文件存在才执行
ansible 172.16.1.31 -m command -a "removes=/tmp/hosts chdir=/tmp touch test.txt"
```

关于 `free_form` 的补充说明：

> There is no parameter actually named 'free form'. See the examples!
> 并没有一个真正叫 `free form` 的参数，它只是表示"这里直接写一条合法的 Linux 命令"。

> **注意：** 使用 `command` 模块时，有些符号信息无法识别：`<`、`>`、`|`、`;` 和 `&`。需要用到管道、重定向等 shell 特性时，请改用 `shell` 模块。

### 辨析：command、shell、raw 三兄弟怎么选 {: .sec-bianxi}

优先级从高到低：能用 `command` 就不用 `shell`——少一层 shell 解析，命令注入面更小，也更接近"声明一个动作"；需要管道、重定向、通配符展开时才升级到 `shell`；`raw` 只留给没有 Python 的裸机做初始化，它不传模块、不比对状态，用完尽快切回正规模块。审查别人剧本时，看到大量 `shell` 基本可以判定幂等性堪忧。

### shell（万能模块）

> `shell – Execute commands in nodes`：在节点上执行操作。

**简单用法：**

```bash
ansible 172.16.1.31 -m shell -a "hostname"
```

```console
172.16.1.31 | CHANGED | rc=0 >>
nfs01
```

**扩展应用：** `shell` 模块的参数与 `command` 模块类似，同样支持 `chdir` / `creates` / `removes`：

```bash
# 1) chdir：执行前切换目录
ansible 172.16.1.31 -m shell -a "chdir=/tmp touch test.txt"

# 2) creates：文件已存在则跳过
ansible 172.16.1.31 -m shell -a "creates=/tmp/hosts touch test.txt"

# 3) removes：文件存在才执行
ansible 172.16.1.31 -m shell -a "removes=/tmp/hosts chdir=/tmp touch test.txt"
```

**实践应用：利用 shell 执行脚本**

需要四个步骤：

1. 编写一个脚本
2. 将脚本发送到远程主机
3. 将脚本权限进行修改（添加执行权限）
4. 运行 ansible 命令执行脚本

### script（脚本模块）

`script` 模块把上面四步压缩成两步：

1. 编写一个脚本（脚本只存在于管理端本地）
2. 运行 ansible 命令执行脚本

> **注意：** `script` 模块的参数功能和 `command` 模块类似。它省去了"分发脚本"和"加执行权限"两个步骤，是批量执行本地脚本最省事的方式。

### raw（裸命令模块）

`raw` 模块直接通过 SSH 的 exec 通道执行命令，不走 Python 模块机制：

```bash
ansible 172.16.1.31 -m raw -a "yum install -y python3"
```

> **注意：** `raw` 的最大用途是给**还没装 Python** 的主机打底（先装上 Python，之后才能用其他模块）；它不返回结构化结果，也没有幂等性，日常操作应尽量少用。

#### Ansible 输出颜色说明

执行结果的颜色是判断"有没有改动"的第一手信息：

| 颜色 | 含义 |
| --- | --- |
| 绿色信息 | 查看主机信息 / 对主机未做改动 |
| 黄色信息 | 对主机数据信息做了修改 |
| 红色信息 | 命令执行出错了 |
| 粉色信息 | 忠告信息（警告） |
| 蓝色信息 | 显示 ansible 命令执行的过程 |

返回 JSON 里最该看三个字段：`changed` 是否动了机器、报错时的 `msg` 与 `stderr`、命令类模块的 `rc` 与 `stdout`。读输出先看颜色（上表），再看 `changed` 与报错详情——大部分"命令手工跑得通、ansible 却报错"的问题，答案就在 JSON 的 `msg` 与 `stderr` 字段里。

#### 扩展用法

```bash
# 01. 在传输文件时修改文件的属主和属组信息

ansible 172.16.1.31 -m copy -a "src=/etc/ansible/file/rsync/rsync.password dest=/etc/ mode=1777"

# 03. 在传输数据文件信息时对远程主机源文件进行备份
ansible 172.16.1.31 -m copy -a "src=/etc/ansible/file/rsync/rsync.password dest=/etc/ backup=yes"

# 04. 创建一个文件并直接编辑文件的信息
ansible 172.16.1.31 -m copy -a "content='rsync123' dest=/etc/rsync.password"
```

#### 自行研究：remote_src / directory_mode / local_follow

关于 `remote_src` 的含义：

> If no, it will search for src at originating/master machine.
> 取值为 no 时，`src` 参数指定的文件会在本地管理端服务器上查找。
>
> If yes it will go to the remote/target machine for the src. Default is no.
> 取值为 yes 时，`src` 参数指定的文件会从远程主机上查找。默认值为 no。

#### 复制目录时的斜杠差异

> **注意：** 用 `copy` 复制目录时，`src` 后面**有没有斜杠**结果完全不同，这是最容易踩的坑。

```bash
# src 后面目录没有 / ：将目录本身以及目录下面的内容都进行远程传输复制
ansible 172.16.1.31 -m copy -a "src=/data dest=/data"

# src 后面目录有 / ：只将目录下面的内容进行远程传输复制
ansible 172.16.1.31 -m copy -a "src=/data/ dest=/data"
```

## 批量执行与并发

主机数量上来后，并发度直接影响执行速度，这与 Ansible 的工作原理直接相关：

| 控制手段 | 说明 |
| --- | --- |
| `-f 并发数` | ad-hoc 临时指定，如 `ansible all -f 20 -m ping` |
| `ansible.cfg` 的 `forks` | 全局默认并发数（默认 5） |
| `serial`（剧本关键字） | 按"批"滚动执行，如每批 10 台，避免一锤子打死全部业务 |
| 连接复用 | SSH ControlMaster 复用 TCP 通道，减少重复握手开销（详见 SSH 篇） |

> **注意：** 并发不是越大越好：同时重启上百台服务的操作，建议用 `serial` 分批，留出观察窗口；`-f` 过大时管理端 CPU 与网络也会成为瓶颈。并发调优先测再调，拿生产环境当试验场是运维大忌。

| 模块 | 作用 | 典型参数 |
| --- | --- | --- |
| `command` | 远程执行单条命令（默认模块） | `chdir` / `creates` / `removes`；不支持管道重定向 |

## 常见坑与注意事项

1. **`command` 不认管道重定向**：`ansible web -m command -a "ps aux | grep nginx"` 会把 `|` 当普通字符传给 `ps`，结果报错；需要管道必须用 `shell` 模块。
2. **`copy` 复制目录的斜杠**：`src=/data` 传目录本身，`src=/data/` 只传目录内容，差之毫厘谬以千里。
3. **`shell` 模块默认不是登录 shell**：依赖 `~/.bashrc` 里环境变量时才生效的命令会找不到，必要时显式 `source` 或用绝对路径。
4. **被管端 Python**：老系统默认 Python 2，新模块可能要 Python 3，用 `ansible_python_interpreter` 主机变量指定解释器路径。
5. **selinux**：被管端 selinux 开启又缺 `libselinux-python` 时，模块会报错，装包或（在知情前提下）调整策略。
6. **`yum` 模块不能装本地 rpm 包之外的东西**：需要本地 rpm 安装用 `yum` 模块的 `name=/path/pkg.rpm` 或 `command`；离线源要提前配好 repo。

这六个坑的共同点是"命令行能跑、剧本里翻车"，或"单机能跑、批量翻车"，根源都是 Ansible 在 shell 外又包了一层执行环境。写完剧本先在单台测试机跑，再放量到全组。

## 小结

1. Ansible 的价值在于"提高效率、提高准确度、减少维护成本、减少重复工作"，功能覆盖批量配置、批量部署、批量分发、批量信息收集四类场景。
2. 部署只需三步：`yum install -y ansible`（依赖 epel 源）→ 编写 `/etc/ansible/hosts` 主机清单 → 用 `ansible all -a "hostname"` 做连通性测试。
3. 服务架构五要素：主机清单、模块、基于密钥的 SSH 连接、被管理端关闭 selinux、剧本功能。任何一项没落实都会导致管理失败。
4. `command` 是默认模块但**不识别** `<` `>` `|` `;` `&` 等符号；需要管道重定向时用 `shell`，需要执行本地脚本时用 `script`，给无 Python 主机打底用 `raw`。
5. `copy` 负责管理端 → 被管理端的批量分发，支持 `owner` / `group` / `mode` / `backup` / `content` 等参数；复制目录时 `src` 末尾**有无斜杠**行为不同。
6. `file` 模块既能改属性，也能通过 `state` 创建（`directory` / `touch` / `hard` / `link`）和删除（`absent`）数据，还能用 `state=file` 检查文件是否存在。
7. Ansible 无 agent，靠 SSH 把模块推到被管端临时目录用 Python 执行，结果以 JSON 返回；并发由 `forks` 控制（默认 5）。
8. 幂等性是 Ansible 的基石：模块先检查状态再变更，剧本可以反复执行而不改乱系统；输出颜色（绿 ok / 黄 changed / 红 failed / 粉 warning / 蓝过程）是判断结果的第一手信息。

## 自测题

1. Ansible 为什么被称作"无 agent"架构？被管理端还需要满足什么前提条件？
2. 为什么说 Ansible 的幂等性让剧本可以反复执行？举一个模块层面的例子。
3. `ansible web -m command -a "df -h | grep /"` 为什么执行结果不符合预期？应该怎么改？
4. `copy` 模块执行时 `src=/data` 与 `src=/data/` 有什么区别？
5. 临时想把一次 ad-hoc 操作的并发从默认 5 调到 20，并且先看看会动哪些主机，命令怎么写？

> **答案：** 1. 因为被管理端不需要安装任何客户端程序、也不需要运行常驻服务，Ansible 只在执行时通过 SSH 把模块代码推到被管端临时目录，用本机 Python 执行完即删除。前提是被管主机装有 Python 且 SSH 可达（密钥已分发）。2. 因为模块执行前会先检查目标主机当前状态，已满足预期就不做变更，所以执行一次和执行多次结果一致；例如系统已装 iotop 时，`yum: name=iotop state=installed` 直接返回 `ok` 而不重复安装。3. `command` 模块不识别管道符 `|`，整串被当作一条命令的参数，`df` 会报错；应改用 `shell` 模块：`ansible web -m shell -a "df -h | grep /"`。4. `src=/data` 会把 `/data` 目录本身连同其内容一起传到目标；`src=/data/` 只传 `/data` 目录下的内容（相当于 rsync 尾部斜杠语义）。5. `ansible web --list-hosts -f 20` 先确认目标清单，再执行正式命令；`-f 20` 指定并发，`--list-hosts` 只列主机不执行。
