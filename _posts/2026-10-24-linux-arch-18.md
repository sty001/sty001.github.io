## 三、负载均衡企业实践

### 3.1 根据用户访问的 URI 进行分流（动静分离）

第一阶段：架构环境规划。

| URI | 后端集群 | 站点目录 | 说明 |
| --- | --- | --- | --- |
| /upload | 10.0.0.8:80 | html/www/upload | upload 服务器集群 |
| /static | 10.0.0.7:80 | html/www/static | static 服务器集群 |
| / | 10.0.0.9:80 | html/www | default 服务器集群 |

第二阶段：在各 Web 服务器上部署测试数据。

```bash
# web02 上进行环境部署
[root@web02 ~]# mkdir /html/www/upload
[root@web02 ~]# echo "upload-web集群_10.0.0.8" >/html/www/upload/test.html

# web01 上进行环境部署
[root@web01 html]# mkdir /html/www/static
[root@web01 html]# echo "static-web集群_10.0.0.7" >/html/www/static/test.html

# web03 上进行环境部署
echo "default-web集群_10.0.0.9" >/html/www/test.html
```

第三阶段：编写负载均衡配置文件。

```nginx
[root@lb01 conf.d]# cat lb.conf
upstream upload {
   server 10.0.0.8:80;
}
upstream static {
   server 10.0.0.7:80;
}
upstream default {
   server 10.0.0.9:80;
}


server {
    listen       80;
    server_name  www.example.com;
    location / {
       proxy_pass http://default;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_next_upstream error timeout http_404 http_502 http_403;
    }
    location /upload {
       proxy_pass http://upload;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_next_upstream error timeout http_404 http_502 http_403;
    }
    location /static {
       proxy_pass http://static;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_next_upstream error timeout http_404 http_502 http_403;
    }
}
```

总结：以上实现网站集群动静分离，好处如下。

1. 提高网站服务安全性
2. 管理操作工作简化
3. 可以划分不同人员管理不同集群服务器

### 3.2 根据 User-Agent 显示不同页面（多终端适配）

第一阶段：准备架构环境。

| 终端 | 域名 | upstream 名称 | 后端集群 | 说明 |
| --- | --- | --- | --- | --- |
| iPhone | www.example.com | mobile | 10.0.0.7:80 | 移动端集群 |
| Chrome（谷歌） | www.example.com | web | 10.0.0.8:80 | Web 端集群 |
| IE / 360 | www.example.com | default | 10.0.0.9:80 | default 端集群 |

环境部署：

```bash
# web01
echo "iphone_access 10.0.0.7" >/html/www/test.html
# web02
echo "google_access 10.0.0.8" >/html/www/test.html
# web03
echo "default_access 10.0.0.9" >/html/www/test.html
```

第二阶段：编写负载均衡配置文件。

```nginx
[root@lb01 conf.d]# cat lb.conf
upstream web {
   server 10.0.0.8:80;
}
upstream mobile {
   server 10.0.0.7:80;
}
upstream default {
   server 10.0.0.9:80;
}


server {
    listen       80;
    server_name  www.example.com;
    location / {
       if ($http_user_agent ~* iphone) {
          proxy_pass http://mobile;
       }
       if ($http_user_agent ~* Chrome) {
         proxy_pass  http://web;
       }
       proxy_pass http://default;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_next_upstream error timeout http_404 http_502 http_403;
    }
}
```

> **注意：** location 块中多个 if 与 proxy_pass 混用属于该场景下的特殊写法，if 在 Nginx 中多数场景并不安全（ infamous "if is evil"），生产环境做多终端分流更推荐用 map 指令预定义变量再选择 upstream，行为更可控。

## 四、高可用服务概述

- 要解决的问题：避免负载均衡服务出现单点故障。
- 实现方式：使用 keepalived 软件。
- keepalived 的两大作用：
  1. 为 LVS 服务而诞生（keepalived + LVS 组成 4 层负载均衡高可用方案）
  2. 独立实现高可用服务功能

说白了，keepalived 就是 VRRP 协议的工程化落地：把"多台机器抢一个虚拟 IP"这件事变成几行配置，再顺手加了健康检查与告警钩子。

## 五、原理解析

### 5.1 高可用的概念与 VIP

高可用（High Availability，HA）的目标是消除单点故障：集群中任意一台设备宕机，服务在用户几乎无感知的情况下继续可用。衡量高可用的两个核心指标：

- MTBF（Mean Time Between Failure，平均无故障时间）：系统两次故障之间的平均运行时长，越大越好。
- MTTR（Mean Time To Repair，平均修复时间）：故障发生到恢复的平均时长，越小越好。
- 可用性等级：可用性 = MTBF / (MTBF + MTTR)。行业常以 9 的个数分级，例如 99.9% 全年停机约 8.8 小时，99.99% 约 52 分钟，99.999% 约 5 分钟。VIP + VRRP 的切换通常在秒级，正是为了逼近更高的可用性等级。

换算成运维语言：想把可用性从 99.9% 提到 99.99%，靠的不是买更贵的机器，而是压缩 MTTR——故障发现要快（监控）、切换要自动（keepalived）、修复要有预案（runbook）。

VIP（Virtual IP，虚拟 IP）是高可用的入口地址：它不属于任何一台物理机，而是漂移在集群节点之间。用户与 DNS 只记住 VIP，当前持有 VIP 的节点就是对外提供服务的 MASTER。DNS 记录无需随节点切换而修改，这是 VIP 方案相比改 DNS 解析的核心优势。

### 辨析：VIP 漂移与 DNS 切换

两种方案都能把流量从坏节点挪到好节点，差别在速度与成本。DNS 切换靠改解析记录，受 TTL 缓存拖累，客户端可能几分钟到几小时都还在连旧地址，做不到秒级；VIP 漂移靠免费 ARP 更新同网段的 MAC 映射，秒级生效，但只对同一个二层网络有效。生产上两者并不互斥：机房内用 VIP 保证秒级切换，机房级容灾再叠加 DNS（或 GSLB）把用户引到另一个机房。

### 5.2 VRRP 协议原理详解

VRRP（Virtual Router Redundancy Protocol，虚拟路由器冗余协议，RFC 3768/5798）把多台设备组织成一个"虚拟路由器"，对外统一提供一个 VIP。协议工作过程如下：

1. 分组：各节点依据 interface（网卡）与 virtual_router_id（VRID，1-255）加入同一个备份组，同一备份组共享同一组 VIP。VRID 相同的设备才互相通信，同一网段内不同业务的 VRID 不能重复。
2. 初始状态：所有节点启动时默认为 BACKUP 状态，等待接收通告报文。
3. 通告：成为 MASTER 的节点周期性发送 VRRP 通告报文，目的组播地址为 224.0.0.18，IP 协议号为 112，发送间隔即 advert_int（秒，默认为 1）。通告报文是心跳，承载发送者的优先级等信息。
4. 选举：组内成员比较优先级（priority，1-254，默认 100）竞选 MASTER，优先级高者胜出；若优先级相同，则接口 IP 地址大者胜出。配置文件中的 state 只是初始期望值，最终角色由竞选决定。
5. 抢占：MASTER 宕机或心跳链路中断后，BACKUP 若在约 3 个通告周期（3 × advert_int）内收不到任何通告，即判定 MASTER 失效，优先级最高的 BACKUP 升级为 MASTER，把 VIP 配置到本机网卡，并发送免费 ARP（gratuitous ARP）通知同网段设备更新 IP 与 MAC 的映射关系，业务流量随之切换。这一过程即 VIP 漂移。
6. 抢占行为：默认开启抢占（preempt），原 MASTER 恢复后会因为优先级更高而重新夺回 VIP；若配置 nopreempt，则只要当前 MASTER 不故障，恢复节点只做待命，避免网络闪断导致 VIP 在两台机器间来回抖动。
7. 认证：authentication 块为通告报文提供简单口令认证（auth_type PASS），防止同网段非法设备接入备份组抢走 VIP。
8. 优先级动态调整：通过 vrrp_script 周期执行业务检测脚本，脚本失败时按 weight 动态调整本节点优先级，从而实现"业务挂了就让出 VIP"的联动切换（详见 8.2）。

nopreempt 的适用场景单独说一下：它要求节点的 state 配置为 BACKUP 才生效（MASTER 状态下配置无效），并且两台机器的优先级谁高谁低无所谓。适合"主备配置对等、谁当主都一样"的对称架构——故障切换一次后就稳定在新主上，旧主恢复时不再抢回，业务和网络都少抖动一次。反过来说，如果两台机器性能不对等（一强一弱），还是保留抢占，让流量尽量跑在强的那台上。

> **注意：** 主备通信依赖心跳线路，一旦主备之间通讯线路中断，或安全策略阻止了组播，BACKUP 会误判主节点故障并自动生成 VIP，这就是"脑裂"（详见 9.2）。

通告机制有两个容易忽略的细节。一是单向性：只有 MASTER 发通告，BACKUP 只听不说，BACKUP 彼此之间也不通信，所以协议里不存在"备机间商量"，一切以"能否听到通告"为准。二是快速让位：MASTER 主动关闭或降级时会发出优先级为 0 的通告报文，BACKUP 收到后立即进入选举，不用干等 3 个周期，切换速度更快。

## 六、keepalived 架构

keepalived 最初为 LVS 设计，现已成为通用的高可用软件，其软件架构由以下部分组成：

- 主进程（parent）：负责读取配置、启动并监控各子进程，子进程异常退出时自动重新拉起。
- watchdog 子进程：守护各子进程，周期心跳检测，进程挂掉后通知主进程重启。
- vrrp 子进程：实现 VRRP 协议栈，负责 VIP 的竞选、持有与释放，是 keepalived 高可用能力的核心。
- checkers 子进程：健康检查框架，周期执行配置中定义的各种检测（进程、URL、TCP 端口等），检测结果可驱动 vrrp 子进程调整优先级。
- libipvs：提供 LVS（IPVS 内核负载均衡）规则的管理能力，即配置文件中 LVS CONFIGURATION 部分的实现。

各子进程的日志默认统一落到 /var/log/messages（新版支持独立日志文件），排错时 grep keepalived 过滤即可。

这种"框架 + 多子进程"的结构意味着：即使某个子进程崩溃，watchdog 也会将其重启，keepalived 自身具备一定的自愈能力。

### 辨析：keepalived 与 corosync + pacemaker

同样做高可用，两套方案定位不同。keepalived 只管"一个 IP 在谁身上"，切换快、配置轻，适合无状态的入口层（LB、网关）；corosync + pacemaker 是完整的集群资源管理器，能编排服务启停、依赖关系、隔离策略，适合数据库、共享存储这类对数据一致性要求高的场景。入口层用 keepalived，数据层再考虑 pacemaker，别用错场合。

## 七、keepalived 部署流程

### 7.1 准备高可用服务架构

| 主机 | 角色 | 地址 | 说明 |
| --- | --- | --- | --- |
| lb01 | MASTER | 10.0.0.5 | priority 150 |
| lb02 | BACKUP | 10.0.0.6 | priority 100 |
| VIP | 虚拟地址 | 10.0.0.3/24 | 对外提供服务的虚拟 IP |

备机平时不是纯浪费：可以把监控采集、日志备份、灰度验证这类低优先级工作放在备机上跑，但别放有状态业务，免得切换时拖泥带水。

### 7.2 安装部署 keepalived 软件

在 lb01、lb02 上执行：

```bash
yum install -y keepalived
```

版本说明：CentOS 7 的 yum 源里一般是 keepalived 1.3.5，单主、双主、track_script 这些功能完全够用；需要单播（unicast）等特性时确认版本不低于 1.2.16，再新才考虑编译安装。

### 7.3 配置文件结构

配置文件为 `/etc/keepalived/keepalived.conf`，由三大配置块组成：

| 配置块 | 说明 |
| --- | --- |
| GLOBAL CONFIGURATION | 全局配置部分 |
| VRRPD CONFIGURATION | VRRP 协议配置部分 |
| LVS CONFIGURATION | LVS 服务管理配置部分 |

三大块并非都要写：纯高可用场景只写前两块，LVS CONFIGURATION 整块可以删掉；配了 virtual_server 才需要第三块。

### 7.4 完整配置示例（含逐行注释）

```ini
[root@lb01 ~]# cat /etc/keepalived/keepalived.conf
! Configuration File for keepalived

global_defs {                   --- 全局配置部分
   notification_email {         --- 设置发送邮件信息的收件人
     admin@example.com
     ops@example.com
   }
   notification_email_from admin@example.com   --- 设置发件人信息（邮件服务器信息）
   smtp_server smtp.example.com
   smtp_connect_timeout 30
   router_id LVS_DEVEL           --- 高可用集群主机身份标识(集群中主机身份标识名称不能重复)
}

vrrp_instance VI_1 {             --- VRRP 协议实例
    state MASTER                 --- 标识所在家族中的身份 (MASTER/BACKUP)
    interface eth0               --- 指定虚拟IP地址出现在什么网卡上
    virtual_router_id 51         --- 标识家族身份信息 多台高可用服务配置要一致
    priority 100                 --- 设定优先级 优先级越高,就越有可能成为主
    advert_int 1                 --- 定义组播包发送的间隔时间(秒)  主和备配置一样  1
    authentication {             --- 实现通讯需要有认证过程
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {          --- 配置虚拟IP地址信息
        192.168.200.16
        192.168.200.17
        192.168.200.18
    }
}
```

> **注意：** 以上示例为 keepalived 官方文档风格的教学演示配置。notification_email 与 smtp_server 在原文中为示例值，脱敏后统一使用 example.com 占位；生产环境如果不需要邮件通知，整个 notification_email 块可以省略。auth_pass 为 VRRP 认证口令，同一实例内主备必须一致，且长度不能超过 8 个字符。

### 7.5 生产精简配置（lb01 / lb02）

lb01 配置信息：

```ini
[root@lb01 ~]# cat /etc/keepalived/keepalived.conf
! Configuration File for keepalived

global_defs {
    router_id lb01
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 150
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        10.0.0.3/24
    }
}
```

lb02 配置信息：

```ini
! Configuration File for keepalived

global_defs {
   router_id lb02
}

vrrp_instance VI_1 {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        10.0.0.3/24
    }
}
```

> **注意：** 两台机器的 router_id 不能重复；同一实例内主备的 virtual_router_id、advert_int、auth_pass 必须一致，否则无法正常通信。

### 7.6 启动 keepalived 服务

```console
systemctl start keepalived
systemctl status keepalived
```

生产环境记得补一条 systemctl enable keepalived，保证机器重启后服务自动拉起，否则一次计划内重启就会让高可用形同虚设。

### 7.7 修改域名和 IP 地址解析关系

将域名解析到 VIP（10.0.0.3），用户访问域名即访问整个高可用集群。解析生效先验证一步：ping 域名应返回 10.0.0.3，解析错了后面所有验证都会白做。

## 八、keepalived.conf 参数详解

### 8.1 global_defs 全局配置参数

| 参数 | 作用说明 |
| --- | --- |
| router_id | 高可用集群主机身份标识，集群内不能重复 |
| notification_email | 告警邮件收件人列表 |
| notification_email_from | 发件人地址（邮件服务器信息） |
| smtp_server | SMTP 邮件服务器地址 |
| smtp_connect_timeout | SMTP 连接超时时间（秒） |

### 8.2 vrrp_instance 参数表

| 参数 | 作用说明 |
| --- | --- |
| state | 实例角色：MASTER / BACKUP，仅初始值，实际角色由竞选决定 |
| interface | 指定虚拟 IP 出现在什么网卡上，如 eth0 |
| virtual_router_id | 标识家族身份信息（1-255），多台高可用服务配置要一致 |
| priority | 设定优先级（1-254），优先级越高越有可能成为主 |
| advert_int | 定义组播包发送的间隔时间（秒），主和备配置一样 |
| auth_type | 通讯认证类型：PASS（口令认证） |
| auth_pass | 通讯认证口令，同一实例内主备一致，最长 8 个字符 |
| virtual_ipaddress | 配置虚拟 IP 地址信息，可配置多个 |
| nopreempt | 抢占关闭开关，防止恢复节点反复抢回 VIP，常与 preempt_delay 配合 |
| virtual_routes | 定义随 VIP 一起漂移的静态路由 |
| track_script | 引用 vrrp_script，将业务检测结果与优先级联动 |

### 8.3 vrrp_script 检测脚本相关配置

| 参数 | 作用说明 |
| --- | --- |
| script | 定义需要监控的脚本（脚本需要有执行权限） |
| interval | 执行脚本的间隔时间（秒） |
| weight | 检测结果变化时对优先级的动态调整值 |
| fall | 连续失败多少次才判定脚本失败，默认 3，防止瞬时抖动误判 |
| timeout | 单个脚本执行的超时时间（秒） |
| track_script | 在 vrrp_instance 中调用执行 vrrp_script |

关于 weight：课堂笔记此处标注为"???"，结合课后作业第 2 题可知，检测脚本执行失败时优先级会按 weight 扣减，从而触发 VIP 向对端转移；业务恢复后优先级回升，VIP 随之被抢回。

weight 的正负号决定脚本结果作用在哪个方向，规则如下：

- weight 为正：脚本执行成功时优先级变为 priority + weight，失败时维持 priority。适合"业务正常就抬高一筹"的写法。
- weight 为负：脚本执行失败时优先级变为 priority + weight（负数直接拉低），成功时恢复 priority。适合"业务挂了就让位"的写法，也是生产上最常见的用法。
- weight 为 0（或不配置）：脚本失败不会调整优先级，而是直接把实例踢进 FAULT 状态，VIP 立即释放，恢复后自动重新加入竞选。

用一个例子验证：lb01 priority 150 配 `weight -250`，脚本失败后优先级变成 -100，低于 lb02 的 100，VIP 漂移；脚本恢复后回到 150，默认抢占开启，VIP 又被抢回。改完配置记得用 `tcpdump -i eth0 -nn vrrp` 观察通告里携带的优先级数值，是否生效抓包一看便知。

### 8.4 LVS 配置块简介（virtual_server 与 virtual_server_group）

keepalived 的第三大配置块 LVS CONFIGURATION 用于管理 LVS 四层负载均衡，核心指令如下：

| 指令 | 作用 |
| --- | --- |
| virtual_server | 定义一个虚拟服务：VIP + 端口 + 协议 + 调度算法 + 后端真实服务器列表 |
| real_server | virtual_server 内的后端真实服务器（RIP + 端口 + weight 等） |
| virtual_server_group | 把多个 virtual_server 归组统一管理，可通过 fwmark 结合防火墙标记使用 |
| lb_algo / lb_kind | 调度算法与转发模式（NAT/DR/TUN） |

简单理解：只用 VRRPD 部分（vrrp_instance）时，keepalived 是任意服务的高可用"管家"；配合 LVS 部分（virtual_server）时，它同时是四层负载均衡的"调度员"。本文主要使用前者。

再补充一句 keepalived 与 LVS 的配合细节：virtual_server 块里可以给每个 real_server 配健康检查（TCP_CHECK、MISC_CHECK 等），后端挂掉时 IPVS 自动把该节点从转发列表摘除。这就是 keepalived + LVS 组合的完整高可用图景：VRRP 保调度器，健康检查保真实服务器，两层各管各的。

## 九、企业应用场景

### 9.1 单主、双从与双主架构

根据节点数量与 VIP 数量，常见的高可用架构有以下几种形态：

| 架构形态 | 节点与角色 | VIP 归属 | 特点 |
| --- | --- | --- | --- |
| 单主单备 | lb01 主、lb02 备 | 全部 VIP 在 lb01 | 最简单，lb02 平时空闲，资源利用率低 |
| 单主双从 | lb01 主、lb02 与 lb03 备 | 全部 VIP 在 lb01 | 备机冗余度更高，一台备机故障仍可切换 |
| 双主（互为主备） | lb01、lb02 各持一个 VIP | VIP-A 在 lb01，VIP-B 在 lb02 | 两台都干活，利用率翻倍，本文 9.3 的配置即此形态 |
| 双主双从 | lb01 主、lb02 备；lb03 主、lb04 备 | VIP-A 归 lb01，VIP-B 归 lb03 | 适合两个业务入口各自冗余，扩展性最好 |

选型判断：入口流量不大时，单主单备最省心；流量大、心疼备机闲置，就上双主。双主的收益是资源利用率翻倍，代价是配置与排错复杂度翻倍，动手前先掂量团队的维护能力。

### 9.2 脑裂问题

出现原因：高可用备服务器接收不到主服务器发送的组播包，备服务器上会自动生成 VIP 地址。

| 类别 | 原因 |
| --- | --- |
| 物理原因 | 高可用集群之间通讯线路出现问题 |
| 逻辑原因 | 有安全策略阻止（组播被拦截） |

定位属于哪一类很简单：两台机器互 ping 对端真实 IP，通则查防火墙与组播策略（逻辑原因），不通则查交换机与网卡（物理原因）。

脑裂的本质是"双方都认为对方已死"，两台机器同时持有 VIP，对外提供同一服务，极易造成数据错乱（例如双主都写同一份数据）。除下述方案外，生产环境还常用以下手段预防：

1. 多链路心跳：为节点配置两块网卡或独立心跳线路，单条链路故障不会造成误判。
2. 仲裁机制：引入第三方参考（如默认网关或独立仲裁节点），双方都无法感知对方时以仲裁结果为准。
3. 隔离（fencing / STONITH）：切换前先确保旧主已真正失效或已被隔离（如关闭其服务、阻断其网络），从机制上杜绝"两台都活"。
4. 防止抖动：配合 nopreempt 与 preempt_delay，避免网络闪断引发 VIP 反复漂移。

解决方案一：进行监控，发出告警。备服务器出现 VIP 地址有两种可能：a. 主服务器出现故障（正常切换）；b. 出现脑裂问题。编写脚本进行判断，若本机持有 VIP 则发送告警邮件：

```bash
#!/bin/bash
ip a s eth0|grep "10.0.0.3" >/dev/null
if [ $? -eq 0 ]
then
  echo "keepalived服务出现异常，请进行检查"|mail -s 异常告警-keepalived  admin@example.com
fi
```

解决方案二：直接关闭一台服务器的 keepalived 服务，快速恢复业务。

脑裂现场的止损动作要快，顺序建议是：先用 `tcpdump -i eth0 -nn vrrp` 确认通告是否还按周期到达，判断是"主真挂了"还是"链路断了"；再确认两台机器谁在真正处理业务（看连接与日志）；最后停掉不该持有 VIP 那台的 keepalived，摘掉多余 VIP，业务恢复后再回头查链路根因。生产上栽过的教训是先纠结根因，业务干瞪眼几分钟——先止损，后排查。

附：shell 脚本比较判断运算符速查。

| 运算符 | 含义 |
| --- | --- |
| -eq | 等于 |
| -ne | 不等于 |
| -lt | 小于 |
| -gt | 大于 |
| -le | 小于等于 |
| -ge | 大于等于 |

### 9.3 业务联动：nginx 异常时自动释放 VIP

思路：nginx（皇帝）+ keepalived（妃子）：nginx 服务停止（皇帝死了），keepalived 也必须停止（殉情），VIP 自动漂移到对端。比喻好记，但方向别搞反：是 keepalived 检测 nginx 并让出 VIP，不是 nginx 去拉起 keepalived；恢复时靠 vrrp_script 检测成功、优先级回升后自动抢回。

第一阶段：编写监控 nginx 服务状态的脚本 `/server/scripts/check_web.sh`。

```bash
#!/bin/bash
num=`ps -ef|grep -c [n]ginx`
if [ $num -lt 2 ]
then
   systemctl stop keepalived
fi
```

说明：`[n]ginx` 的写法可避免 grep 匹配到自身进程；`ps -ef | grep -c [n]ginx` 计数小于 2，说明 nginx 进程异常，此时停止 keepalived，让 VIP 漂移到对端。

第二阶段：测试监控脚本（赋予执行权限并手动执行验证）。

第三阶段：在 keepalived 配置文件中实时调用该脚本。

```ini
check_web=/server/scripts/check_web.sh
vrrp_script check_web {
   script "/server/scripts/check_web.sh"   --- 定义需要监控脚本(脚本是执行权限)
   interval 2                              --- 执行脚本的间隔时间(秒)
   weight 2                                --- 检测失败时优先级的动态调整值
}
```

```ini
track_script {
     check_web                             --- 调用执行你的脚本信息
}
```

lb01 上的完整配置如下：

```ini
[root@lb01 scripts]# cat /etc/keepalived/keepalived.conf
! Configuration File for keepalived
 global_defs {
   router_id lb01
}

vrrp_script check_web {
 script "/server/scripts/check_web.sh"
 interval 3
 weight 2
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 150
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
     10.0.0.3/24
    }
   track_script {
         check_web
   }
}
```

> **注意：** weight 的取值方向决定优先级的变化方向。课后作业第 2 题要求"nginx 停了 keepalived 停、nginx 恢复 keepalived 自动恢复"，除了上述直接 systemctl stop keepalived 的做法，还可以把 weight 设为负数（如 weight -250）：脚本失败时优先级被大幅拉低，低于对端优先级，VIP 自然漂移；nginx 恢复后脚本成功，优先级回升，由于默认开启抢占，VIP 又被抢回。两种写法效果等价，负数 weight 的方案切换过程更平滑，推荐掌握。

这里有个坑：check_web.sh 只数进程，nginx 僵死（进程还在但不响应请求）是发现不了的。更彻底的做法是脚本里再 curl 一次本机 80 端口，拿到真实响应才返回成功，进程数与端口探测双保险。

### 9.4 双主配置（双 vrrp 实例）

思路：一台设备同时加入两个 VRRP 家族，在家族一中做 MASTER、家族二中做 BACKUP，两台设备错位配置，即可让两个 VIP 分别由不同主机承载，形成双主。

第一阶段：编写 lb01 服务器 keepalived 配置文件。

```ini
[root@lb01 ~]# cat /etc/keepalived/keepalived.conf
! Configuration File for keepalived
 global_defs {
   router_id lb01
}


vrrp_instance VI_1 {            --- 家族一：VIP 10.0.0.3，lb01 为主
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 150
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
     10.0.0.3/24
    }
}
vrrp_instance VI_2 {            --- 家族二：VIP 10.0.0.4，lb01 为备
    state BACKUP
    interface eth0
    virtual_router_id 52
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
     10.0.0.4/24
    }
}
```

第二阶段：编写 lb02 服务器 keepalived 配置文件。

```ini
! Configuration File for keepalived
global_defs {
   router_id lb02
}

vrrp_instance VI_1 {
    state BACKUP
    interface eth0
    virtual_router_id 51
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        10.0.0.3/24
    }
}
vrrp_instance VI_2 {
    state MASTER
    interface eth0
    virtual_router_id 52
    priority 150
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        10.0.0.4/24
    }
}
```

第三阶段：编写域名和 IP 地址解析信息，并通过抓包验证 DNS 查询走向。

| 域名 | VIP | 当前所在主机 |
| --- | --- | --- |
| www.example.com | 10.0.0.3 | lb01（10.0.0.5） |
| bbs.example.com | 10.0.0.4 | lb02（10.0.0.6） |

> **注意：** 双主场景中两个 vrrp_instance 的 virtual_router_id 必须不同（51 / 52），否则属于同一家族，无法分别竞选。

双主的流量分配还依赖 DNS 侧配合：两个域名分别解析到两个 VIP，或者一个域名解析多条 A 记录做粗粒度分流。这里有个坑：VRID 在同一网段内必须全局唯一，如果隔壁团队也在这个网段搭 keepalived 且 VRID 撞车，两个不相干的备份组会互相竞选，VIP 乱漂。规划阶段先摸清同网段已占用的 VRID。

### 9.5 负载均衡安全访问（只监听 VIP）

需求：nginx 只监听 VIP 地址，不直接暴露真实 IP；VIP 漂移时对端 keepalived 自动接管服务。

第一阶段：修改 nginx 负载均衡文件。

```nginx
upstream webcluster {
   server 10.0.0.7:80;
   server 10.0.0.8:80;
   server 10.0.0.9:80;
}
server {
    listen       10.0.0.3:80;
    server_name  www.example.com;
    location / {
       proxy_pass http://webcluster;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
       proxy_next_upstream error timeout http_404 http_502 http_403;
    }
}
server {
    listen       10.0.0.4:80;
    server_name  bbs.example.com;
    location / {
       proxy_pass http://webcluster;
       proxy_set_header Host $host;
       proxy_set_header X-Forwarded-For $remote_addr;
    }
}
```

第二阶段：修改内核文件，解决"如何设置监听网卡上没有的地址"问题。

```bash
echo 'net.ipv4.ip_nonlocal_bind = 1' >>/etc/sysctl.conf
sysctl -p
```

第三阶段：重启 nginx 负载均衡服务。

```bash
systemctl restart nginx
```

> **注意：** 监听 VIP 前必须开启 net.ipv4.ip_nonlocal_bind，否则 nginx 会因绑定不存在的地址而启动失败，这是本场景最典型的排错点。

只监听 VIP 还有个附带好处：真实 IP（10.0.0.5 / 10.0.0.6）上不再开 80 端口，用户无法绕过 VIP 直接访问某台 LB，配合防火墙可以做到 LB 节点对用户完全透明，管理流量走 SSH 端口单独控制。

## 十、VIP 漂移验证

1. 在 MASTER 上确认 VIP 已生成：

```console
ip a s eth0 | grep 10.0.0.3
```

2. 模拟主节点故障，停止 MASTER 的 keepalived：

```console
systemctl stop keepalived
```

3. 在 BACKUP 上确认 VIP 已漂移过来：

```console
ip a s eth0 | grep 10.0.0.3
```

4. 恢复 MASTER 服务，由于其优先级更高，会重新抢占回 VIP：

```console
systemctl start keepalived
```

这四步敲一遍就明白，比光看文档记得牢。

除上述步骤外，还可以从更多角度验证与观测漂移过程：

| 验证手段 | 命令 | 观察点 |
| --- | --- | --- |
| 查看网卡地址 | ip a s eth0 | 是否出现 inet 10.0.0.3/24 |
| 探测 VIP 响应 | arping -I eth0 -c 3 10.0.0.3 | VIP 是否应答 ARP，以及应答的 MAC |
| 查看路由与邻居表 | ip route; ip neigh | VIP 对应哪块网卡、哪台主机 |
| 抓取 VRRP 报文 | tcpdump -i eth0 -nn vrrp | 通告报文是否按 advert_int 周期到达 |
| 查看服务日志 | journalctl -u keepalived -f 或 tail /var/log/messages | Entering MASTER/BACKUP STATE 状态迁移记录 |
| 业务层验证 | curl -I http://10.0.0.3 | 漂移后业务是否由新节点正常响应 |

keepalived 自身的监控也不能落下，重点盯四件事：

1. 进程存活：zabbix 监控 keepalived 进程数量，挂了立即告警；
2. VIP 位置：每台节点定时执行 ip a 检查本机是否持有 VIP，备机持有 VIP 就意味着发生过切换或脑裂，正是 9.2 告警脚本的思路；
3. 切换事件：监控 /var/log/messages 或 journalctl 中的 Entering MASTER STATE 记录，作为切换发生的历史证据；
4. 脑裂征兆：多台节点同时报告持有 VIP，触发最高级别告警。

## 十一、常见错误与排错

| 现象 | 可能原因 | 排查命令 | 解决方式 |
| --- | --- | --- | --- |
| 主停了 VIP 没有漂移 | virtual_router_id、advert_int、auth_pass 主备不一致；interface 网卡名写错；组播被防火墙拦截 | ip a; systemctl status keepalived; journalctl -u keepalived; tcpdump -i eth0 vrrp | 统一主备三项参数；按实际网卡名配置 interface；firewalld 放行 vrrp 协议 |
| 两台机器都持有 VIP（脑裂） | 心跳线路中断，或组播被安全策略拦截 | ip a \| grep 10.0.0.3; ping 对端真实 IP; tcpdump -i eth0 vrrp | 排查链路；部署多链路心跳与仲裁；按预案关闭一台 keepalived 并告警 |
| keepalived 启动失败 | 配置语法错误；priority 超出 1-254；VRID 冲突 | journalctl -u keepalived; keepalived -t -f /etc/keepalived/keepalived.conf | 修正语法；priority 与 VRID 取规定范围内取值 |
| VIP 漂移后业务打不开 | nginx 未监听 VIP；ip_nonlocal_bind 未开启；后端故障 | ss -lntp \| grep 10.0.0.3; curl -I http://10.0.0.3 | 开启 net.ipv4.ip_nonlocal_bind；nginx listen VIP:80；排查 upstream 后端 |
| VIP 在主备间频繁抖动 | 网络闪断；vrrp_script 的 interval/fall 设置过敏感 | journalctl -u keepalived 观察切换频率 | 加大 advert_int 与 fall；配置 nopreempt 与 preempt_delay |
| 虚拟机环境 VRRP 不工作 | 虚拟交换机限制组播或混杂模式 | tcpdump -i eth0 vrrp 确认能否收到通告 | 虚拟交换机放行组播；或改用 unicast_src_ip 与 unicast_peer 单播模式 |

> **注意：** 阿里云等公有云环境通常不转发 VRRP 组播报文，直接部署 keepalived 无法通信。云上实现同效果需使用单播配置（unicast_src_ip 本机地址、unicast_peer 对端地址，keepalived 1.2.16 以上版本支持），或使用云厂商提供的高可用产品。

## 十三、现代环境补充

CentOS 7 已于 2024 年 6 月 EOL，新环境建议迁移到 Rocky Linux、AlmaLinux 或 CentOS Stream，部署 keepalived 时的差异对照如下：

| 项目 | 旧（CentOS 7） | 新（Rocky/AlmaLinux/CentOS Stream 8/9） |
| --- | --- | --- |
| 安装软件 | yum install -y keepalived | dnf install -y keepalived（yum 为兼容软链） |
| 服务管理 | systemctl start/status keepalived | 相同，统一使用 systemctl |
| 网卡名称 | 常见 eth0 | 常见 ens160 等可预期命名，配置 interface 前先执行 ip a 确认实际网卡名 |
| 网络配置 | /etc/sysconfig/network-scripts/ifcfg-* | NetworkManager 管理，用 nmcli con mod 修改 IP，改完 nmcli con up 生效 |
| 防火墙 | iptables | firewalld（nftables），VRRP 需放行协议：firewall-cmd --permanent --add-protocol=vrrp 后 reload |
| 端口查看 | netstat -lntup | ss -lntup |
| 日志查看 | tail /var/log/messages | journalctl -u keepalived -f |
| 配置检查 | 无独立命令 | keepalived -t -f /etc/keepalived/keepalived.conf 可在启动前校验配置 |

云环境与虚拟化环境还要注意两点：一是公有云通常不转发 VRRP 组播，需要改用单播模式；二是部分虚拟交换机默认过滤组播，虚拟机内 tcpdump 抓不到通告报文时，先检查虚拟交换机（或 VMware/Hyper-V 虚拟网络）的组播与混杂模式设置。

## 小结

1. 高可用的核心目的是消除单点故障：负载调度层通过 keepalived + VRRP 实现 VIP 在主机之间漂移。
2. keepalived.conf 由全局配置、VRRP 配置、LVS 配置三部分组成，核心是 vrrp_instance 实例。
3. 同一实例内主备的 virtual_router_id、advert_int、auth_pass 必须一致；priority 决定竞选结果，原主恢复后高优先级会重新抢占 VIP。
4. 脑裂的根源是主备心跳通信中断，解决思路是监控告警，必要时直接关闭一台服务器的 keepalived；预防手段包括多链路心跳、仲裁与 fencing 隔离。
5. 通过 vrrp_script + track_script 可将业务服务（nginx）状态与 VIP 绑定，业务异常时自动释放 VIP；weight 控制优先级的动态调整，负数 weight 可实现降级漂移。
6. 双主通过一台设备加入两个 vrrp_instance 实现，两个实例的 virtual_router_id 必须不同。
7. 验证 VIP 漂移可组合使用 ip a、arping、tcpdump vrrp 与 curl VIP 多种手段，日志中 Entering MASTER STATE 是最直接的状态证据。

## 自测题

1. keepalived 配置中 state MASTER 的机器一定就是最终的主吗？决定最终角色的因素是什么？
2. advert_int = 1 时，BACKUP 大约多久收不到通告会升级为 MASTER？
3. 什么是脑裂？请说出三种应对或预防手段。
4. vrrp_script 中 weight 为正数和负数时，对优先级的调整有什么不同？
5. 双主架构下，两台机器的 virtual_router_id 能否相同？双主相比单主有什么好处？

> **答案：** 1. 不一定。state 只是启动时的初始期望值，最终角色由竞选决定：优先级高者为 MASTER，优先级相同则接口 IP 大者为 MASTER。2. 约 3 × advert_int，即约 3 秒。3. 脑裂是主备心跳中断后双方都认为对方故障、都持有 VIP 的现象。应对与预防：监控告警并人工或自动关闭一台；部署多链路心跳；引入仲裁节点；使用 fencing 隔离确保旧主失效；配置 nopreempt 防止抖动。4. weight 为正时，脚本失败优先级下降、恢复时上升；weight 为负时相反，脚本失败优先级上升（即相对降级），适合"业务故障即让出 VIP"的场景，配合默认抢占可在业务恢复后自动抢回。5. 不能相同。相同 VRID 属于同一备份组会互相竞选，双主要求两个实例 VRID 不同（如 51 与 52）。双主的好处是两台设备都承载业务（各持一个 VIP），资源利用率相比"一主一备、备机空闲"更高。
